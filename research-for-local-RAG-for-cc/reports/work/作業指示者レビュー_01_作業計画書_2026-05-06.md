## CRITICAL 指摘（承認の障害になりうる）

### C1. 工数・期間・コスト見積もりが計画書に存在しない
- **対象箇所**: 全体（特に 5 章タスク別計画、7 章担当モデル）
- **観点**: コスト・投資対効果 / 意思決定材料の十分性 / 承認の押し戻し条件
- **指摘内容**: 計画書として「これを承認すると、何時間／何日／概算 API コストでどこまで進むか」がまったく示されていない。フェーズ単位（02 で 8 サブタスク × ?、04 で最低 5 検証対象 × ?）の概算オーダーすら無く、Opus を多用する 7 章の方針と合わせるとコスト判断ができない。最終報告書まで「やってみないと分からない」状態で承認するのはリスクが高い。
- **改善提案の方向性**: フェーズ別に「想定セッション数 / 想定実時間レンジ / 想定モデル消費の概算」を記載。確度が低くても「現時点の見立て」として置いておくことで打ち切り判断の基準にもなる。

### C2. 打ち切り・スコープ縮退の基準が無い
- **対象箇所**: 10 章（次の見直しポイント）/ 5.4・5.5 完了条件
- **観点**: リスク評価 / コスト・投資対効果
- **指摘内容**: 見直しトリガーは「次フェーズに進むためにこれを決める」の追加方向の更新ばかりで、「想定より時間がかかった」「フィジビリティ検証で全件不通過」「有効性検証で対照群（Filesystem Exploration）が圧勝」のような **撤退・縮退・スコープ削減のトリガー** が無い。承認した後に「無限に続く」可能性が読み手として見えてしまう。
- **改善提案の方向性**: 各フェーズに「打ち切り条件」または「縮退判断条件」を 1〜2 項目で良いので明記。例: 「02 で当初想定の 1.5 倍の期間を超えたら、03 着手前に作業指示者へエスカレーション」。

### C3. 04 通過基準の内部矛盾（精度不問 vs 想定通りの結果）
- **対象箇所**: 5.4「通過基準（フィジビリティ合格の定義）」項目 2 と項目 4
- **観点**: 実装可能性・現実性 / 読み手の認知負荷
- **指摘内容**: 項目 2「最低 1 件のクエリで結果が返ること（**精度不問**、疎通確認）」と、項目 4「**正常クエリのパターンごとに最低 1 クエリずつ、想定通りの結果が返ること**」は精度判定の有無で矛盾している。読み手として「結局フィジビリティ検証は精度を見るのか見ないのか」が判断できない。実装担当者によって解釈が割れる。
- **改善提案の方向性**: 項目 2 と項目 4 の関係を「項目 2 = 疎通確認の最低ライン、項目 4 = フィジビリティ通過に必要な動作確認の最終ライン」のように **段階性** を明記する、または項目 2 を削除して項目 4 に統合する。

### C4. 検証対象数の上限と検証実施数の最終確定ロジックが不明
- **対象箇所**: 5.4「検証対象候補」/ TBD5
- **観点**: 実装可能性・現実性 / コスト
- **指摘内容**: 「最低 3 件、必要に応じて追加」「最大 N」と書かれているが、N の上限・選定の打ち切り基準がない。現状ドラフトで以下が並ぶ: 既掲 5 件（DuckDB / sqliteVec / pgvector / Chroma / FilesystemExploration）+ CAG 系 + 追加検討候補 3 件（Codebase-Memory / codegraph / mcp-local-rag）= 計 9 件以上が候補に上がっており、これを「全部やる」のか「絞る」のかが計画書からは判断できない。
- **改善提案の方向性**: 「最大 N 件（推奨 5〜7 件、絞り込み基準は 03.02 の設計網羅性で決定）」のように **数値レンジ + 絞り込み判断主体** を明記。

### C5. 計画書単体での自己完結性が弱い（外部参照依存が強い）
- **対象箇所**: 全体（変更履歴の Pre-XX / U-XX / 02.99 I-1 等の頻出、CLAUDE.md・ハマりどころ.md・Issue運用ルール.md・improvements/ への参照）
- **観点**: 意思決定材料の十分性 / 読み手の認知負荷
- **指摘内容**: 作業指示者ペルソナで読むと、Pre-XX や U-XX の内訳が分からない／参照ドキュメントが手元に揃わないと判断できない場面が多い。特に変更履歴は「何が変わったか」より「Pre-XX への対応」が前面に出ていて、変更内容の本質が読み取りづらい。GitHub の閲覧者や将来の引き継ぎ者が単独でこの計画書を読むことを想定すると、追跡コストが大きい。
- **改善提案の方向性**: (a) Pre-XX 等の略号を使う場合は計画書冒頭または末尾に対応表（または別紙へのリンク）、(b) 変更履歴は「Pre-XX 反映」ではなく「何を加え／何を変えたか」を主語にする。

## IMPORTANT 指摘（承認可だが改善が望ましい）

### I1. 版数表記の混在（v1.0 / v1.1）
- **対象箇所**: 冒頭メタ情報「版数: 1.0」と変更履歴「2026-05-05: v1.1 化」
- **観点**: 読み手の認知負荷
- **指摘内容**: 冒頭は v1.0 のまま、変更履歴では v1.1 化済みと書かれている。どちらが現行かが冒頭一見では分からない。レビュー対象がどの版かで承認の意味が変わる。
- **改善提案の方向性**: 冒頭メタの版数を v1.1 に更新、または「現行版: v1.1（最終更新 2026-05-05）」と一行で明示。

### I2. 「確定度」と「v1.0 化」の意味の重なり
- **対象箇所**: 冒頭メタ「確定度: 1.0 版（v1.0）—」
- **観点**: 読み手の認知負荷
- **指摘内容**: 「確定度」と「版数」が独立した概念のはずだが、確定度の説明文が版数の説明と重なって冗長。読み手は「確定度って何の指標？」と立ち止まる。
- **改善提案の方向性**: 確定度の指標体系（例: ドラフト / 承認候補 / 確定 / 改訂）を別途定義するか、版数管理に統合する。

### I3. 想定読者に「人間レビューア（作業指示者）」が明記されていない
- **対象箇所**: 1 章「想定読者」
- **観点**: 読み手の認知負荷
- **指摘内容**: 想定読者が「Claude Code 自身、レビュー・引き継ぎ作業者」とあるが、**承認権限を持つ作業指示者** が明示されていない。承認可否を判断する立場の読み手として違和感。
- **改善提案の方向性**: 想定読者に「作業指示者（承認権限保持者）」を追加。

### I4. TBD3（規模感）が承認時点で未確定なまま
- **対象箇所**: 4 章 TBD3 / 2 章スコープ / 5.2 サブタスク順序
- **観点**: 意思決定材料の十分性 / 実装可能性
- **指摘内容**: 規模感（KB / MB / GB / ファイル数オーダー）が 02.01 完了時点で確定とされているが、**承認時点ではまだ確定していない**。承認後に「実は GB オーダーでした、フェーズ全部見直しが必要」となるリスクをどう許容するか、計画書からは読み取れない。
- **改善提案の方向性**: 「想定する規模感の幅」（最小〜最大の見立て）を計画書時点で明示し、「想定上限を超えた場合は計画書改訂＋再承認」と明記する。

### I5. v1.0 承認後の改訂時の再承認プロセスが不明
- **対象箇所**: 1 章「更新タイミング」/ 6 章レビュー計画
- **観点**: 承認の押し戻し条件
- **指摘内容**: 「生きたドキュメント」として見直しトリガーで改訂するとあるが、改訂時に **再承認が必要かどうか** が書かれていない。重大な変更（スコープ拡張、検証対象大幅追加等）まで Claude セルフ改訂で進む懸念がある。
- **改善提案の方向性**: 「軽微な改訂は Claude 改訂のみ・重大改訂は作業指示者の再承認」のように影響度別の承認基準を明示。

### I6. 8 リポジトリ全件調査の妥当性根拠が薄い
- **対象箇所**: 5.2「08.オフライン GitHub リポジトリ調査」
- **観点**: コスト・投資対効果 / 網羅性
- **指摘内容**: 8 件全件を「アーキテクチャ概要・主要構成要素・採用候補度」までやるのはコストが大きい。途中で「採用候補度=低」と判明したリポジトリでも完了条件で全項目埋めることが要求されている。早期足切りの仕組みが無い。
- **改善提案の方向性**: 「初期スクリーニングで採用候補度=低と判定された場合、判定根拠のみ記載で足切り可」を完了条件に追加。

### I7. 検証実施数の数値基準（「最低 8 件」「最低 5 件」）の根拠不在
- **対象箇所**: 5.2 各サブタスクの完了条件
- **観点**: 実装可能性 / コスト
- **指摘内容**: 「最低 8 件」「最低 5 件」「最低 3 件」など数字が散在しているが、どの数字も根拠（網羅性確保のため？単純な経験則？）が書かれていない。読み手は「なぜ 8 なのか」で立ち止まる。
- **改善提案の方向性**: 数値基準の横に短く根拠を併記（例: 「最低 8 件（先行インプット 6 件 + 競合候補補完 2 件以上）」）。一部は既に補足されているが全体に展開すべき。

### I8. ライセンス確認の網羅性が embedding-gemma 以外で見えない
- **対象箇所**: 5.4 検証対象 02（embedding-gemma の Gemma Terms of Use 懸念）
- **観点**: リスク評価 / 網羅性
- **指摘内容**: embedding-gemma だけ商用利用ライセンス懸念が明示されているが、他のモデル・DB・MCP プロダクトのライセンス確認が体系的に行われた形跡が無い（02.基礎調査の完了条件には個別記載があるが、計画書本体としての「ライセンス確認の方針」が無い）。承認後に他プロダクトでも同種の懸念が発覚するリスクが残る。
- **改善提案の方向性**: 02.02（埋め込みモデル）/ 02.03（DB）/ 02.07（コードベース向け OSS）の完了条件に「ライセンス（特に商用利用条件）の調査」が含まれることを冒頭で明示、または横断ルールとして 1 節立てる。

### I9. 「最大 3 つ（2 位・3 位）」の表現の重複と曖昧さ
- **対象箇所**: 5.6 構成案 §3、完了条件 (a)
- **観点**: 読み手の認知負荷
- **指摘内容**: 「最も有効な構成 1 つに加え、…最大 3 つ（2 位・3 位）まで記載可能」が二箇所に出てくる。また「最大 3 つ」と「2 位・3 位」で数の整合がとれていない（最大 3 つは 1 位 + 2 位 + 3 位 で 3 件か、追加で 3 件で計 4 件か曖昧）。
- **改善提案の方向性**: 表現を「**最大 3 構成（1 位必須、2 位・3 位は任意）**」のように一義化し、片方の記載に集約。

### I10. 評価指標 8 項目の重み付けが計画書時点で未確定
- **対象箇所**: 5.5 評価指標表 / 05.01 評価指標の設計
- **観点**: 意思決定材料の十分性
- **指摘内容**: 評価指標 8 項目（単発トークン効率 / セッション圧迫度 / 通信回数 / Recall@k / Precision@k / 応答速度 / インデックスコスト / 対照群優位度）の **重み付けが 05.01 まで決まらない** ため、「何を重視した RAG が選ばれるか」が承認時点で見えない。トークン効率重視なのか精度重視なのかで結論が変わりうる。
- **改善提案の方向性**: 計画書時点で「重視軸の優先順位」（例: 1. トークン削減 → 2. 精度維持 → 3. 応答速度）を仮置きしておき、05.01 でその仮置きを基に重み付けを精緻化する流れにする。

### I11. CAG 検証対象の確定タイミングと N 件カウントへの算入が不透明
- **対象箇所**: 5.4「CAG 系検証対象」項
- **観点**: 実装可能性
- **指摘内容**: CAG 系は「03.02 で構成確定」とあるが、04 の検証対象数に含めるかどうかが書かれていない。また 03.02 で構成が確定しなかった（CAG 不要と判定された）場合のフォールバックも不明。
- **改善提案の方向性**: 「CAG 検証対象は 03.02 で確定。確定した場合は 04 の検証対象数にカウント、不要と判定された場合は H0 を 04 ではなく 02.01 文献調査のみで判定する」のように分岐を明記。

### I12. 90.クロージングが POSITIVE 棚卸しのみ
- **対象箇所**: 5.7 90.クロージング
- **観点**: 網羅性
- **指摘内容**: クロージングの内容が「POSITIVE 指摘のバックログ化」だけで、本調査全体の振り返り・NEGATIVE 総括・次回活動への教訓抽出が無い。「クロージング」という言葉から期待される範囲としては薄い。
- **改善提案の方向性**: 振り返り（KPT 形式等）と「ハマりどころ.md / improvements/ の最終整理」をクロージングのタスクに追加検討。

### I13. レビュー繰り返しの収束保証
- **対象箇所**: 6.2 レビュー繰り返しルール
- **観点**: リスク評価 / 実装可能性
- **指摘内容**: 「新規 NG 検出ゼロまで繰り返す」とあるが、収束しない（毎回新規 NG が見つかる）場合の **上限ループ回数** や **エスカレーション基準** がない。実用性レビュー等で「3 回以内に収束しなければ作業指示者へ相談」のような設計が必要。
- **改善提案の方向性**: レビューサイクル数の上限を明記し、超過時のエスカレーションフローを定義。

## SUGGESTION 指摘（細部の改善・任意）

### S1. 3.2 候補要素表の単位ゆれ
- **対象箇所**: 3.2「埋め込みモデル候補」表
- **指摘内容**: 「次元」列に「-（300 MB）」「-（小）」など単位混在の値が入っている。読みづらい。
- **改善提案の方向性**: 次元と概略サイズの列を分け、不明値は「不明」または「TBD」で統一。

### S2. 検証対象命名ルールの本文と追加候補テーブルの整合

- **指摘内容**: 命名ルール本文は `<DB>_<連携方式>` を原則としつつ単一製品優先の例外を述べているが、追加候補の `mcp-local-rag_shinpr` のような **発行元接尾辞** ルールは命名ルール本文に書かれていない。テーブル側で後付けされた形。
- **改善提案の方向性**: 命名ルール本文に「同名衝突時は発行元接尾辞で区別」という条項を追加。

### S3. 80 → 90 のフェーズ番号の空きの意図
- **対象箇所**: 5.6 / 5.7
- **指摘内容**: 80.最終報告書 → 90.クロージング の番号空き（81〜89）の意図が明示されていない。拡張余地確保なのか単に運用上の慣習なのか不明。
- **改善提案の方向性**: 「将来 81〜89 に追加タスクを差し込む余地を確保」のように一行注記。

### S4. リポジトリのアーカイブ／停止状態の扱い
- **対象箇所**: 5.2「08.オフライン GitHub リポジトリ調査」
- **指摘内容**: 8 リポジトリのうちアーカイブ済み・更新停止状態のものがあった場合の判定方針（採用候補度を自動的に下げるか等）が未定義。
- **改善提案の方向性**: 完了条件に「アーカイブ・最終更新日の記載」を追加し、判定への反映ルールを記載。

### S5. 9 章申し送り事項のスコープ
- **対象箇所**: 9 章申し送り事項 §1「命名規則の汎用ルール化」
- **指摘内容**: 本調査スコープ外の「全 Claude 活動への命名規則昇格」が申し送り事項に混入している。本調査の目的（ローカル RAG）から外れる項目を申し送ること自体は良いが、混在することで「本調査として何を決めるか」がぼやける。
- **改善提案の方向性**: 申し送り事項を「本調査内の課題」と「本調査範囲外の発見」で 2 区分に分ける。

### S6. 6.4 と 6.3 の整合性
- **対象箇所**: 6.3 必須レビュー（報告書を必須とする）/ 6.4 レビュー対象の形式（報告書である必要はない）
- **指摘内容**: 6.3 では「報告書」を必須レビュー対象としつつ、6.4 で「報告書である必要はない」とゆるめている。読み手として「結局必須レビュー対象は何の形式？」で迷う。
- **改善提案の方向性**: 6.4 の「報告書である必要はない」が適用されるのは **必須レビュー以外** であることを明記、または 6.3 と 6.4 の主語を分離。

### S7. 11 章課題・制約セクションの記載量
- **対象箇所**: 11 章
- **指摘内容**: Docker 不在 1 件のみで、調査計画書全体に対するリスク網羅としては薄い。例: 「Windows 11 環境前提」「Opus / Sonnet モデル変更時の再評価」「8 リポジトリの調査時点での最新性」など、計画書時点で認識可能な制約が他にもありそう。
