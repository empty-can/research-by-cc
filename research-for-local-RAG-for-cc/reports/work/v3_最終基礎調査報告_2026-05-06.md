## 1. 冒頭サマリ（調査内容 / 結果 / 結論・示唆）

### 1.1 調査内容

02.基礎調査では、ローカル RAG 構築に必要な意思決定を 8 つのサブタスクに分解して情報を体系化した。対象は **RAG パターン分類 / 埋め込みモデル / ベクトル DB / チャンク戦略 / 検索アルゴリズム / Claude Code 連携方式 / コードベース向け RAG / 既存 OSS リポジトリ調査** の 8 領域である。

### 1.2 調査結果（要点 5 件）

1. **RAG パターン**: 本ユースケース（仕様書要約 / 脆弱性差分分析 / コードリバース）には **ハイブリッド RAG**（仕様書）/ **Agentic + ハイブリッド**（脆弱性）/ **コードグラフ + シンボル検索**（コードリバース）が適合する。Graph RAG 既製ツール（GraphRAG / LightRAG）は KG 構築に LLM が必須でスコープ外。
2. **埋め込みモデル**: **BAAI/bge-m3**（多言語・8192 トークン・MIT）を主軸候補とする。日本語精度を最大化したい場合は **cl-nagoya/ruri-v3-310m**（JMTEB 77.24・SOTA）を補完候補に置く。`paraphrase-multilingual-mpnet-base-v2`（128 トークン上限）/ `all-MiniLM-L6-v2`（日本語非対応）/ `embeddinggemma-300m`（Gemma 独自ライセンス）は除外。
3. **ベクトル DB**: Windows 11 + Docker 不可前提下で **DuckDB+vss / LanceDB / sqlite-vec / Chroma** が採用候補。**pgvector**（Docker 必須）/ **Milvus Lite**（Windows 非対応）は除外。
4. **検索アルゴリズム**: ハイブリッド検索（BM25 + ベクトル + RRF）が単純ベクトル検索（recall@10 約 78%）に対し約 91% へ精度を引き上げる。リランカーは **bge-reranker-v2-m3**（MIT・278M・多言語）が第一候補。
5. **連携方式**: **MCP サーバー型（stdio + 軽量 SQLite/DuckDB）** が透過的呼び出し・運用簡便性で最有力。Skills CLI 都度起動型は毎回 8〜9 秒のモデルロードが発生し反復検索に不向き。

### 1.3 結論・示唆（GO/NO-GO 判断材料）

- **GO 判断を支持する事実**: 採用候補が各レイヤで Windows 11 / OSS / 商用利用無料の制約を満たしつつ複数特定できた。コードベース向けは **Codebase-Memory MCP**（file-explorer 比でトークン 1/10）/ **isink17/codegraph**（Claude Code 自動設定対応）などのフィージブルな OSS が確認できた。
- **NO-GO に振れうるリスク**: (a) bge-m3（約 4.6GB）の Windows 11 低スペック環境での実動作が未検証、(b) DuckDB+vss の HNSW 永続化が experimental、(c) コードグラフ系 Go ツールが Go 1.26+（2026-05-03 時点で安定版未満）を要求、(d) MCP 登録ツールのトークン消費（5 サーバー 58 ツールで約 55,000 トークン）の見落としリスク。
- **次フェーズへの示唆**: 03 設計フェーズでは、**「ドキュメント主体構成」「コード主体構成」「ハイブリッド構成」の 3 系統の検証対象**を確定する方向が妥当（詳細は §4 / §9）。

## 3. 採用候補と除外候補（レイヤ別）

> 各候補は「採用根拠 / 主要数値 / 注意点」を統一フォーマットで記述する。除外候補も同様。03 設計フェーズで参照しやすいように、レイヤ単位で章立てしている。

### 3.1 埋め込みモデル

#### 3.1.1 採用候補

##### BAAI/bge-m3 — 主軸

- **ライセンス**: MIT（商用可）
- **モデルサイズ / 次元 / 最大トークン**: 約 4.6GB / 1024 次元 / 8192 トークン
- **ベンチマーク**: MIRACL 多言語 nDCG@10 = 70.0（多言語 SOTA 水準）
- **採用根拠**: 100 言語以上をカバー、Dense / Sparse / ColBERT の 3 出力を同時生成可能（ハイブリッド検索構築が容易）。日英混在 + コード + Markdown という多様な本ユースケース要件を単一モデルで満たす。
- **注意点**: GPU メモリ 9GB 程度が推奨（CPU 動作も可だが速度低下）。Windows 11 低スペック（RAM 8GB 以下）での実動作は未検証。

##### cl-nagoya/ruri-v3-310m — 日本語補完

- **ライセンス**: Apache 2.0（商用可）
- **モデルサイズ / 次元 / 最大トークン**: 約 1.2GB / 768 次元 / 8192 トークン
- **ベンチマーク**: JMTEB 平均 77.24（日本語 SOTA、2025〜2026 時点）
- **採用根拠**: JMTEB で OpenAI text-embedding-3-large を上回る日本語精度。30m 軽量版（約 140MB / 256 次元 / JMTEB 74.51）も選択可。
- **注意点**: 日本語専用のため、英語・コード中心ドキュメントには単独採用不可。bge-m3 との並行運用は実装複雑化リスクあり。

##### Qwen/Qwen3-Embedding-0.6B — 軽量多言語

- **ライセンス**: Apache 2.0（商用可）
- **モデルサイズ / 次元 / 最大トークン**: 約 1.2GB / 32〜1024 次元（可変）/ 32768 トークン
- **ベンチマーク**: MTEB Multilingual 64.33
- **採用根拠**: 0.6B サイズで多言語 + 32K トークン対応。CPU オンリー環境での実用候補。インストラクション付きエンコードで +1〜5% 精度向上。

#### 3.1.2 除外候補

| モデル | 除外根拠 |
|---|---|
| `sentence-transformers/all-MiniLM-L6-v2` | 英語主体、日本語精度が著しく低い。256 トークン上限もコード・Markdown に不向き |
| `paraphrase-multilingual-mpnet-base-v2` | 最大 128 トークンの致命的制約。長文チャンクを処理できない |
| `google/embeddinggemma-300m` | Gemma 独自利用規約（Prohibit Use Policy 準拠義務等）。Apache 2.0 / MIT 前提と異なる調達リスク。MTEB スコアも bge-m3 より低い |

### 3.2 ベクトル DB / 検索基盤

#### 3.2.1 採用候補

##### DuckDB + vss — 第一候補

- **形態 / ライセンス**: 単一ファイル DB / MIT
- **スケール目安**: 数十万〜数百万ベクトル（RAM 依存）
- **採用根拠**: 単一 `.duckdb` ファイル + 標準 SQL。Windows 公式サポート。Zenn 参考記事で「数万チャンクでもミリ秒検索」が実証済み。HNSW インデックス対応。
- **注意点**: HNSW のディスク永続化は **experimental**（`hnsw_enable_experimental_persistence = true` 必須、WAL リカバリ未実装）。インメモリ展開時の RAM 上限に注意（1536 次元 × 100 万ベクトルで約 6GB）。

##### LanceDB

- **形態 / ライセンス**: 単一ファイル組み込み型 / Apache 2.0
- **スケール目安**: 数百万〜数十億（分散時）。ローカル単体でも数百万快適
- **採用根拠**: Arrow ネイティブ・ディスク効率高い・DuckDB 連携公式。クロスプラットフォーム動作。
- **注意点**: 約 25,600 件未満は自動でフルスキャン。大規模化時に `create_index()` 明示呼び出しが必要。

##### sqlite-vec

- **形態 / ライセンス**: SQLite 拡張 / Apache 2.0
- **スケール目安**: 〜100 万ベクトル（ブルートフォース中心）
- **採用根拠**: 最軽量。`pip install sqlite-vec` で完結。既存 SQLite との同居可。
- **注意点**: Windows では組み込み SQLite が古い場合があり `pysqlite3` 利用推奨。HNSW 非対応（線形劣化のリスク）。

##### Chroma

- **形態 / ライセンス**: サーバー型（ローカルモードあり）/ Apache 2.0
- **スケール目安**: 〜1,000 万ベクトル（プロトタイプ向け）
- **採用根拠**: `chromadb.PersistentClient(path="./chroma_db")` の 1 行で永続ストレージ使用可。SQLite バックエンドで安定性高い。
- **注意点**: クエリレイテンシ約 30ms（Qdrant の約 12ms より遅い）。

#### 3.2.2 除外候補

| DB | 除外根拠 |
|---|---|
| pgvector | PostgreSQL 拡張、実用導入には Docker が前提。WSL ネイティブビルドはコスト過大 |
| Milvus Lite | 公式に「Windows is not yet supported」と明記、現環境で利用不可 |

#### 3.2.3 Docker 環境整備時の追加候補（申し送り）

pgvector（Docker `pgvector/pgvector:pg17` で即時利用可、1,000 万〜5,000 万ベクトル中規模に適する）/ Qdrant サーバーモード（OSS 最高水準レイテンシ p50 4ms）/ Weaviate（ハイブリッド検索・GraphQL）。

### 3.3 チャンク分割・インデックス手法

#### 3.3.1 推奨デフォルト

| データ種別 | 推奨手法 | チャンクサイズ目安 | オーバーラップ |
|---|---|---|---|
| コード（Python / TypeScript） | tree-sitter による AST チャンキング | 1,000〜1,500 非空白文字（100〜200 トークン相当） | 原則不要（必要時 10 行） |
| Markdown | `MarkdownHeaderTextSplitter` + 再帰分割（二段階） | 800〜1,200 文字（250〜400 トークン） | 10〜20% |
| PDF | 前処理（Markdown 変換）→ ヘッダーベースまたはページ単位 | 512〜1,024 トークン | 10〜20% |
| 一般テキスト（フォールバック） | 再帰分割（`RecursiveCharacterTextSplitter`） | 256〜512 トークン | 10〜20% |

#### 3.3.2 主要根拠

- **cAST 論文（CMU / EMNLP 2025）**: AST チャンキングで RepoEval Recall@5 +4.3pt、SWE-bench Pass@1 +2.67pt。
- **NVIDIA 2024 ベンチマーク**: ページ単位チャンキングが精度 0.648 で最高（ページ化 PDF 限定）。
- **Vectara 2026**: 再帰 512 トークン + 10〜20% オーバーラップが「ベンチマーク検証済みデフォルト」。
- **SCSK TechHarmony 2026**: 日本語は英語の 2〜3 倍トークン。文字数ではなくトークン数で管理することが必須。

#### 3.3.3 重複排除方針

二段階アーキテクチャを採用する:

- **インデックス時**: SHA-256 で完全一致除外 → コサイン類似度 ≥ 0.90 の近似重複に顕著度 +15% ブースト（lucidRAG 方式）
- **検索時**: スコア順走査時に既選択チャンクとの類似度 ≥ 0.90 をスキップ
- **閾値根拠**: NVIDIA NeMo の業界標準（0.90〜0.92）

### 3.4 検索アルゴリズム

#### 3.4.1 採用候補（優先度順）

##### 第 1 候補: ハイブリッド検索（BM25 + ベクトル + RRF）+ クロスエンコーダーリランキング

| コンポーネント | 採用候補 | 主な数値 |
|---|---|---|
| ベクトル検索 | Chroma / Qdrant（ローカル）+ bge-m3 / multilingual-e5-large | recall@10 約 78%（単体） |
| BM25 | `rank_bm25` + `sudachipy`（日本語形態素解析） | recall@10 約 65%（単体） |
| スコア融合 | RRF（k=60） | ハイブリッドで recall@10 約 91% |
| リランカー | `bge-reranker-v2-m3`（MIT / 278M / 多言語） | NDCG@5 +12〜18pt 向上 |

- **追加遅延**: ハイブリッド +6ms（p50）、リランカー +200〜400ms（CPU、50 候補時）
- **適用基準**: recall@50 ≥ 90% を確保した上位 N=20〜100 件をリランカーへ投入

##### 第 2 候補: ハイブリッド検索のみ（リランカーなし）

リランカー常駐メモリ・推論遅延が許容できない場合のスモールスタート構成。recall@10 約 91% を BM25+ベクトル+RRF だけで確保可能。

#### 3.4.2 リランカーモデル候補

| モデル | ライセンス | パラメータ | 多言語 | 遅延（50 候補・CPU） | 推奨度 |
|---|---|---|---|---|---|
| `BAAI/bge-reranker-v2-m3` | MIT | 278M | 100+言語（日本語含む） | 200〜400ms | 推奨（多言語環境第一候補） |
| `cross-encoder/ms-marco-MiniLM-L-6-v2` | Apache 2.0 | 33.4M | 英語のみ | 50〜100ms | 推奨（英語コード主体・低遅延要件） |
| `hotchpotch/japanese-bge-reranker-v2-m3-v1` | MIT | 278M | 日本語特化 | bge-v2-m3 同等 | 推奨（日本語精度重視時の追加） |
| FlashRank（+ MiniLM） | Apache 2.0 | 軽量ラッパー | 英語 | <20ms | 推奨（CPU 環境・低遅延最優先） |
| `jinaai/jina-reranker-v2-base-multilingual` | CC-BY-NC-4.0 | 278M | 100+言語 | - | **除外**（非商用ライセンス） |

### 3.5 Claude Code 連携方式

#### 3.5.1 推奨方式

##### 第 1 候補: MCP サーバー型（stdio transport + 軽量 SQLite/DuckDB）

- **応答速度**: セッション開始時にモデルロード吸収、2 回目以降高速
- **実装コスト**: 既製品利用なら低（`.mcp.json` 数行）。自作は中
- **Claude Code 統合**: 自動呼び出し（Claude 側が判断）
- **採用根拠**: 既製 MCP サーバー（`mcp-local-rag`、`code-index-mcp` 等）が豊富で OSS / 商用無料の条件を満たす。SQLite + 軽量モデルで運用重量度を抑えられる。
- **注意点**: 登録ツール数に応じてコンテキストトークンが増加（5 サーバー 58 ツールで約 55,000 トークン）。Tool Search 機能で最大 85% 削減可能。

##### 第 2 候補: Skills（常駐 HTTP サーバー型）

- **応答速度**: 約 0.1 秒（モデルロード済み）
- **実装コスト**: 中（FastAPI 等のサーバーコード追加が必要）
- **採用根拠**: karaage0703 記事で実測値が確認済み。CLI 都度起動型（約 8〜9 秒）の約 90 倍の高速化。手動制御を残しつつ低レイテンシを実現できる。

##### 第 3 候補: Skills（CLI 都度起動型）— 検証用

- **応答速度**: 毎回 8〜9 秒のモデルロード

## 4. 構成パターンの統合ビュー

レイヤごとの採用候補を組み合わせた **構成案 3 系統** を提示する。03 設計フェーズではこれを起点に検証対象を絞り込む。

### 4.1 構成案 A: ドキュメント主体（仕様書要約向け）

```
[Markdown / PDF] → MarkdownHeaderTextSplitter / pymupdf4llm
                ↓
            BAAI/bge-m3（埋め込み）
                ↓
        DuckDB + vss（HNSW）
                ↓
   ハイブリッド検索（BM25 + ベクトル + RRF）
                ↓
       bge-reranker-v2-m3（リランカー）
                ↓
       MCP サーバー（stdio）→ Claude Code
```

- **想定規模**: 数百〜数千ファイル / 数万〜数十万チャンク
- **主な根拠**: §3.1〜§3.5 の第一候補を直列で組み合わせた標準構成
- **想定ストレージ**: embedding のみで数十 MB〜数百 MB（バイナリ量子化適用なら 1/32）

### 4.2 構成案 B: コード主体（コードリバース向け）

```
[ソースコード] → tree-sitter（66 / 12 言語）→ コールグラフ + シンボルインデックス
                ↓                                    ↓
        Codebase-Memory MCP                isink17/codegraph
                ↓                                    ↓
        14 MCP ツール（構造クエリ）        29 MCP ツール（依存関係）
                                ↓
                ripgrep（シンボル文字列補完層）
                                ↓
                    Claude Code（MCP 経由自動呼び出し）
```

- **想定規模**: 数千〜数万ファイルのリポジトリ
- **主な根拠**: §3.6 の採用候補を組み合わせ。Filesystem Exploration（grep/glob）比でトークン 1/10 を狙う
- **トレードオフ**: 回答品質は file-explorer 比 9pt 低い領域もあるため、grep/glob とのフォールバックを保持する設計が望ましい

### 4.3 構成案 C: ハイブリッド（脆弱性差分分析向け / 汎用）

```
[コード + 仕様書 + CVE データ等] → 種別判定
       ├── コード → 構成案 B のパス
       └── 自然言語 → 構成案 A のパス
                ↓
        Agentic RAG（LLM が反復検索クエリ生成）
                ↓
            Claude Code
```

- **想定用途**: RAVEN（2025）型の多段推論。Explorer エージェント + RAG + Analyst エージェント構成
- **採用根拠**: 脆弱性差分分析は CVE 識別子（キーワード）と意味的概念（ベクトル）の双方が必要 → ハイブリッド検索が必須。さらに多段推論で精度を高める
- **注意点**: レイテンシ・コスト増。本プロジェクトは Claude Code が LLM 役を担うため、ローカル LLM 不要

### 4.4 3 構成の比較表

| 観点 | 構成案 A | 構成案 B | 構成案 C |
|---|---|---|---|
| 主要ユースケース | 仕様書要約 | コードリバース | 脆弱性差分分析 |

### 8.2 解決不能な制約（受容前提）

- **コードのベクトル類似度限界**: コードのグラフ的依存構造は本質的にベクトル類似度では捉えられない。コードグラフ系との組み合わせで対応する。
- **CAG / RAG の汎用最適チャンクサイズの不在**: 文献コンセンサスとして「ユースケース依存」。A/B テストによる継続最適化が現実的。
- **MCP プロトコル仕様の継続的変更**: 本調査時点（2026-05）の知見が恒久的に適用できない可能性がある。

### 8.3 既知ハマりどころ抜粋（設計時に意識すべき）

各サブタスクから抽出した、設計フェーズで影響の大きいものを抜粋する。

1. **e5 系モデルのプレフィックス必須**: `intfloat/multilingual-e5-*` はインデックス時 `passage:`、検索時 `query:` を付与しないと精度大幅低下（02 / 06）
2. **異なる埋め込みモデルの混在バグ**: インデックス作成時と検索時で同一モデル必須。メタデータにモデル名を記録する設計が望ましい（02 / 06）
3. **BM25 + 日本語**: `rank_bm25` に日本語をそのまま渡すと文字単位分割になる。sudachipy 等の前処理必須（05）
4. **DuckDB vss の RAM 上限**: HNSW は操作時に全量 RAM 展開。1536 次元 × 100 万ベクトルで約 6GB（03）
5. **MCP トークン消費の見落とし**: 5 サーバー 58 ツールで約 55,000 トークン。Tool Search 機能で削減可（06）
6. **Markdown コードブロック誤分割**: RecursiveCharacterTextSplitter のセパレータ `"\n"` がコードブロック内改行で誤分割。MarkdownHeaderTextSplitter 推奨（04）
7. **日本語・英語混在のトークン数膨張**: 日本語は英語の 2〜3 倍トークン。文字数ではなくトークン数で管理（04）
8. **コードへのベクトル埋め込みの「沈黙した失敗」**: 間違ったチャンクが返されても LLM が誤った推論を続けるリスク。コードには AST チャンキング + 構造クエリの組み合わせ必須（07）

詳細は `research-for-local-RAG-for-cc/ハマりどころ.md` を参照。

### 9.4 GO/NO-GO 判断材料の最終整理

#### GO を支持する事実
1. 各レイヤで Windows 11 / OSS / 商用無料の制約を満たす採用候補が複数特定できた（§3）
2. 主要数値根拠が揃っている: ハイブリッド recall@10 91%、Codebase-Memory トークン 1/10、ハイブリッド追加遅延 +6ms 等（§3.4 / §3.6）
3. 既存 OSS リポジトリで採用候補度「高」が 2 件確認できた（§3.7）
4. 仮説 H1〜H5 はいずれも棄却ではなく支持または条件付き支持に到達（§5）

#### NO-GO に振れうるリスク
1. bge-m3 / リランカーの Windows 11 低スペック実動作が未検証（§8.1 #1, #5）
2. DuckDB+vss / Codebase-Memory MCP / isink17/codegraph に experimental / プレリリース要件あり（§8.1 #2, #3）
3. MCP トークン消費の定量評価が未実施（§8.1 #7）

#### 推奨される 03 設計フェーズの方針
- §4 の 3 構成案をベースに、各構成の検証対象を確定（TBD5）
- リスクが高い項目（bge-m3 動作 / DuckDB+vss 永続化 / Go 1.26+）は **検証対象選定時点で代替案を併記**（フォールバック性を確保）
