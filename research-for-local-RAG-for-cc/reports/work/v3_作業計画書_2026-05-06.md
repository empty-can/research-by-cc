## 0. 冒頭サマリ（承認判断のための要点）

> このサマリ単独で「計画書としての承認可否」を判断できる構成にする（[執筆ガイドライン §4.1](../../ドキュメント執筆ガイドライン.md) 計画書要件）。

### 0.1 目的（1 文）

Claude Code に **大量ファイル群を扱わせる際のトークン・コンテキスト消費を、精度を維持したまま最小化する仕組み** を、**完全ローカル・OSS / 商用利用無料** のみで構築する方法を明らかにする。

### 0.2 スコープの境界

| 含む | 含まない |
|---|---|
| RAG の基礎情報・ローカル構築事例の調査 | 有料サービス型 RAG |
| Claude Code 連携方式（CLI / Skills / MCP） | 生成 LLM のローカル構築・学習（埋め込み・リランカー・小型クエリ書き換えモデルは「専用ツール」として含む） |
| ローカル環境での構築・動作・有効性検証 | Claude Code に置換不能な構成中の特定ローカル LLM 前提構成 |
| 専用ツール用ローカルモデル（埋め込み・リランカー・小型クエリ書き換え） | SNS 系信頼性の低い情報源 |

### 0.3 成功条件（プロジェクト完了の定義）

以下を **すべて** 満たした時点で本調査は成功とする。

1. 推奨構成が最低 1 件、根拠付きで 80.最終報告書に記載されている
2. 推奨構成が **本作業環境（Windows 11 + WSL2）で再現構築可能** な手順で記述されている
3. 評価指標（[§5.5 05.有効性検証](#55-05有効性検証)）に対する実測値が記録されている
4. Filesystem Exploration（H1 対照群）と CAG（H0 対照群）に対する優位度が示されている
5. 作業指示者レビューにより 80.最終報告書が承認されている

### 0.4 打ち切り条件（プロジェクト中断の定義）

以下のいずれかが発生したら **作業指示者へ即時相談**（自動継続しない）。

1. 04.フィジビリティ検証で **全検証対象が通過基準を満たさない**
2. 05.有効性検証で **全構成が Filesystem Exploration（grep/glob）に劣後** する
3. ライセンス制約により **採用候補がすべて除外** される
4. 想定外コスト（ストレージ・メモリ・実行時間）が当初見積りの **3 倍超**

### 0.5 残リスク（承認時に把握すべき主要事項）

| # | リスク | 発生時の影響 | 対応方針 |
|---|---|---|---|
| R1 | Docker 必須構成（pgvector 等）の検証不能 | 検証対象が縮小 | 検証保留扱い・別環境で将来検証（[§9.2](#92-主要リスク詳細-環境制約)） |
| R2 | 埋め込みモデルのライセンス変更（Gemma Terms 等） | 採用候補の差し替え | 03.02 設計時にライセンス再確認・MIT/Apache 2.0 系を優先 |
| R3 | CAG が大半のユースケースで RAG を上回る可能性（H0） | 本調査の前提が揺らぐ | H0 検証結果を 02-01 / 04 / 05 で正面から扱う（[§3.1](#31-仮説テーブル) H0） |

## 1. 調査の目的とスコープ

### 1.1 大前提

**「LLM でなくてもできることは Claude Code にさせない」** を徹底する。データ構造化・取得は専用ツールに任せ、Claude Code には推論・統合の役割に集中させる（[調査 CLAUDE.md](../../CLAUDE.md) §背景・大前提）。

### 1.2 調査の中核問い

3 つの問いに答える:

1. **構成問題**: ローカル RAG をどう構築すれば本ユースケース（仕様書要約・脆弱性差分分析・コードリバース）の精度を維持できるか
2. **連携問題**: Claude Code からどの形態（Skills / MCP / ハイブリッド）で利用するのが最適か
3. **比較問題**: ベクトル系 RAG が Filesystem Exploration（grep/glob）や CAG に対して、本ユースケースで有意に勝るか

### 1.3 スコープに含むもの・含まないもの

[§0.2](#02-スコープの境界) のテーブルを正準とする。詳細補足:

- **専用ツール用ローカルモデル**（埋め込み・リランカー・小型クエリ書き換え）は含む。「LLM をローカル構築しない」原則と矛盾しないことを明記（生成 LLM のみがスコープ外）
- **Claude Code 置換可能な構成中の LLM** は調査対象内（構成全体が特定 LLM 専用なら対象外）

## 2. 前提条件と先行知識

### 2.1 用語整理（[先行インプット 01](../先行インプット/01.RAG-vs-Agentic-Search.md) 由来）

| 用語 | 定義 | 本調査での扱い |
|---|---|---|
| **RAG（広義）** | 外部データを取得してモデル生成を補強する全般 | 本調査の主対象 |
| **CAG**（Context-Augmented Generation） | 必要情報をプロンプトに全量ロード | 対照群として測定（[§3.1](#31-仮説テーブル) H0） |
| **Vector Search RAG** | ベクトル類似検索による RAG | 主検証対象 |
| **Filesystem Exploration RAG** | grep / glob で直接探索 | 必須対照群（H1） |
| **Agentic Search** | LLM 推論を伴う反復検索 | RAG の対立概念ではない（実行スタイル軸） |

### 2.2 先行インプットから抽出した候補要素

#### 2.2.1 埋め込みモデル候補（[先行インプット 02・04・05・06](../先行インプット/) 由来）

| モデル | 次元 | サイズ | ライセンス懸念 |
|---|---|---|---|
| `intfloat/multilingual-e5-small` | 384 | 約 100〜500 MB | なし |
| `intfloat/multilingual-e5-large` | 1024 | 大 | なし |
| `BAAI/bge-m3` | 1024 | 約 2.2 GB | なし（MIT） |
| `cl-nagoya/ruri-v3-30m` / `ruri-v3-310m` | 256 / 1024 | 約 120 MB / 1.2 GB | なし |

| `all-MiniLM-L6-v2` | 小 | 小 | なし（ただし日本語精度に難） |

| 軸 | 選択肢 |

| **連携方式軸** | 常駐型 / CLI 都度起動型 / ハイブリッド |

| **埋め込み次元軸（評価軸）** | 小型（≦ 384）/ 中型（〜 768）/ 大型（≧ 1024） |

### 5.2 02.基礎調査

#### 5.2.1 目的

ローカル RAG 構成各レイヤー（埋め込み / DB / 検索アルゴリズム / 連携方式）と本ユースケース固有論点（コード対応・日本語対応・トークン削減）について、**意思決定に必要な事実を体系化** する。

#### 5.2.2 サブタスク一覧

サブタスクは **同じ構造（目的 / 問い / 完了条件）** で記述する（執筆ガイドライン G2-3 パターン化）。

##### 02-01. RAG パターン分類とユースケース適合性

- **目的**: CAG / Vector Search RAG / Filesystem Exploration RAG / Graph RAG / ハイブリッドの適用条件を整理

| **単発クエリトークン効率** | 1 質問当たりの入力トークン総量。RAG 利用時 / 直接ファイル読み込み時 / CAG 時を比較 | 同一クエリで各方式実行・トークン計測 |
| **セッション累積コンテキスト圧迫度** | 同一タスク完了までに必要だったクエリ数 × クエリ当たりトークン、後続タスクへのノイズ汚染（マルチターン累積） | セッションログから計測。RAGAS Context Relevancy 等で半定量化 |
| **Claude Code 通信回数削減度** | 同一アウトプットを生成する `Claude Code クライアント ↔ Anthropic API` 間の通信回数比 | セッションログ・API 呼び出しログから計測 |
| **取得精度（Recall@k）** | 想定正解ドキュメントが上位 k 件に含まれる割合 | テストクエリ + 正解セットを構築し計測 |
| **取得精度（Precision@k）** | 上位 k 件のうち関連あるものの割合 | 同上 |
| **応答速度** | クエリ投入 → Claude Code 応答までの時間 | 計測スクリプト |
| **インデックス構築コスト** | 単位データ量あたりのインデックス時間・ストレージ | 一定規模のサンプルデータで計測 |
| **対照群（Filesystem Exploration / CAG）に対する優位度** | 対照群との精度向上度・トークン削減度の差分 | 同一タスクで実行・比較 |

> **注**: 「ノイズ汚染度」は「セッション累積コンテキスト圧迫度」に統合（Pre-10 由来。作業指示者回答「成果が期待通り達成された場合、ノイズ汚染も自然と減少する。各構成ごとの差異を定量的に把握できれば十分」）。

#### 5.5.5 05 全体の完了条件

- 各検証対象 `検証報告書.md` に上記指標の実測値が記載
- 99 にて、推奨構成・除外構成・本調査目的に対する達成度が結論付け

## 9. 打ち切り条件・主要リスクとカウンター反論（Devil's Advocate）

> 執筆ガイドライン G3-7 / §4.1 計画書要件。**承認判断に影響する主要結論ごとに「最強の反論」を 1 件ずつ書き残す**。

### 9.1 打ち切り条件（再掲、[§0.4](#04-打ち切り条件プロジェクト中断の定義) より）

1. 04 で全検証対象が通過基準を満たさない
2. 05 で全構成が Filesystem Exploration に劣後
3. ライセンス制約により採用候補がすべて除外
4. 想定外コストが見積りの 3 倍超

### 9.2 主要リスク詳細（環境制約）

| # | リスク | 想定影響 | 対応 |
|---|---|---|---|
| R1 | Docker 不在 | pgvector 等の検証保留 | Issue `[04][将来解決]` 化、別環境で将来検証 |
| R2 | ライセンス変更 | 採用候補差し替え | 03-02 で再確認、MIT/Apache 2.0 系優先 |
| R3 | H0 で CAG 優位 | 本調査前提揺らぎ | H0 を正面から扱い、結論として提示 |

### 9.3 採用方針別 Devil's Advocate

#### D1. 採用方針「ローカル RAG を構築する」への反論

> **反論**: 「Claude Code は既にプロンプトキャッシュを持つ。CAG（コンテキスト直接ロード + プロンプトキャッシュ）で十分なケースが多数を占めるなら、RAG 構築コストは正味マイナスではないか？」

- **棄却根拠 / 残存リスク**:
  - 棄却根拠（部分的）: 大規模データ（GB オーダー、数千ファイル超）では CAG はそもそも入らないため、RAG が必要となるケースは確実に存在
  - 残存リスク: 中規模データ（MB オーダー）の閾値で RAG 構築コストを上回る価値が出るかは **H0 検証で確認** する。検証結果次第で「対象ユースケースの規模を絞った提案」になる可能性を承認時点で受容

#### D2. 採用方針「Filesystem Exploration を必須対照群とする」への反論

> **反論**: 「ripgrep の比較では『grep が速い・正確』という当然の結論しか出ない。比較自体に価値があるのか？」

- **棄却根拠**:
  - コードベースでは grep が優位な可能性が高いが、**仕様書要約・脆弱性差分分析等の自然言語ドキュメント** では grep が劣後する可能性が高い
  - **どのユースケースで grep が優位 / 劣後するかの境界** を明らかにすることが本調査の中核価値の 1 つ。比較しないと境界は出ない

#### D3. 採用方針「Docker 必須構成は検証保留」への反論

> **反論**: 「pgvector は実運用で広く使われる選択肢。検証保留は調査の網羅性を損なうのでは？」

- **棄却根拠 / 残存リスク**:
  - 棄却根拠: 本フェーズの環境制約は所与であり、別環境での将来検証を申し送ることで網羅性は保たれる
  - 残存リスク: 推奨構成として「pgvector」が最終的に挙がる可能性は本フェーズでは検証できない。承認時点でこの限界を受容

#### D4. 採用方針「評価指標は RAGAS 系をデファクト優先で採用」への反論

> **反論**: 「RAGAS は LLM-as-a-judge 系の指標。評価対象自体が LLM を使うことで、評価がブレるのでは？」

- **棄却根拠 / 残存リスク**:
  - 棄却根拠（部分的）: RAGAS の Context Relevancy / Context Recall は機械的な計算可能。Faithfulness / Answer Relevancy は LLM-as-a-judge だが、構成間の **相対比較** で使う限りはブレが構成間で平均化される
  - 残存リスク: 絶対値ではなく相対比較に限定する。05-01 で「性質適合性・比較有効性をしっかり確認する」を完了条件に組み込み済み
