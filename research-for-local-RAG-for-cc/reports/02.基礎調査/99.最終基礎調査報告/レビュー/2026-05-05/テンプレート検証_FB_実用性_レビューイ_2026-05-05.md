## 1. 「レビューイ見解」欄の不在に関する設計上の影響評価

### 1.1 不在の事実

実用性テンプレート（v 改訂版）には、**レビューイの見解・回答・補足を記入する既定セクションが存在しない**。各指摘エントリ（C-n / I-n / S-n / P-n）の構造は以下になっている:

```
### {指摘ID}: {タイトル}
**該当箇所**: ...
**問題** / **観点** / **評価点**: ...
**修正案** / **提案**: ...
**作業指示者の態度表明**:
| 態度 | コメント |
|---|---|
| ... |  |
```

すなわち、「レビュアー → 作業指示者」の片方向で完結しており、レビューイがレビュー内容に対して立場表明・補足・反論を残す既定の場所がない。

一方、論理整合性テンプレート（並走している論理整合性レビュー側で確認していないが、本リポジトリの設計上、改訂版テンプレートに「レビューイからの回答・見解・補足」セクションが既定で存在することがユーザ指示で明示されている）には、既定でレビューイ見解欄が存在する。

### 1.2 設計上の影響（FB 観点）

#### 1.2.1 影響①: テンプレート間の一貫性欠如

論理整合性テンプレートと実用性テンプレートで、**同じクロスレビューフローでありながらレビューイ表現の場所が異なる**ため、以下の懸念がある:

- レビューイ作業者（Claude や人間）が、観点ごとに記入位置を切り替える必要があり、認知負荷が増える
- 将来的に「レビューイ見解が記入されていない」ことが、観点ごとに「省略されている」のか「テンプレート構造上欠落している」のか判別しにくくなる
- フロー定義（`.claude/templates/cross-review/README.md`）を読まないと、両テンプレートの差異が運用上意図された差なのか不明

#### 1.2.2 影響②: レビューイの表現機会の制限

実用性指摘は SUGGESTION や IMPORTANT が中心で、論理整合性ほど「事実認定の対立」が発生しにくい性質を持つため、「レビューイ見解欄を省いてもレビューが回る」という設計判断は **理論的にはあり得る**。しかし実際の運用では:

- レビューイは「採用案の選択判断」「修正案の追加提案」「ラベル文言の具体化」など、レビュアーが提示した抽象提案を **作業可能なレベルに具体化する役割** を担うことが多い
- この具体化情報が記入される場所がないと、作業指示者の態度表明が「抽象提案 vs 何の合意もない」状態で発生し、判断材料が不足する

つまり実用性レビューにおいてもレビューイ見解の **情報的価値は高い** ため、欄が無いことの実質的なデメリットは無視できない。

#### 1.2.3 影響③: 収束判定の支援機能の欠如

論理整合性テンプレートにはレビューイ見解欄があるため、レビューイは「収束見込み」を各指摘で記入できる。実用性テンプレートにはこの仕組みが無く、収束判定が「作業指示者の態度表明後でないと判断できない」状態になる。今回ユーザ指示で「収束判定セクションを文書末尾に追加」とされたのはこの欠落を補う指示だったが、テンプレート既定で対応していれば指示なしで収束判定が記入できたはず。

## 2. 自分が選択した記入方式と判断理由

### 2.1 選択した方式

**方式 1: 各指摘エントリの末尾に新規セクション `#### {指摘ID}. 作成者からの見解` を追加して見解を記入する**

### 2.2 判断理由

- **エントリ単位の自己完結性**: 指摘・修正案・作業指示者態度・作成者見解が同じセクション内に並ぶため、作業指示者がレビュー結果を判断する際に上下スクロール不要で全情報を取得できる
- **論理整合性テンプレートとの暗黙の整合**: 論理整合性テンプレートではレビューイ見解欄が既定で各エントリ末尾に存在する（ユーザ指示より把握）。方式 1 はこの構造を実用性側で擬似的に再現するため、**両観点のレビュー文書を読み比べる際の認知負荷が最小化** される
- **方式 2（末尾一覧）の不採用理由**: 末尾一覧形式だと指摘ごとに「指摘本体（前半）→ 見解（末尾）」と分離するため、長文ドキュメントでは参照負荷が高い。論理整合性テンプレートともレイアウトが乖離する
- **方式 3（独自方法）の不採用理由**: 既存の 2 案（方式 1・方式 2）を超える積極的なメリットを思いつかなかった

### 2.3 副次効果

方式 1 を採用した結果、実用性テンプレートに **「レビューイ見解欄を既定セクションとして追加すべき」という改善提案** の根拠データが蓄積された（本ファイル §1.2 と §3 の不足項目欄）。今回の作業はテンプレート検証を兼ねるため、この副次効果は意図通り。

## 3. 不足項目（あった方が良かった欄）

### 3.1 必須レベルで追加すべき（テンプレート構造の根本欠落）

- **「レビューイからの見解」欄の既定追加**: 各指摘エントリ末尾に、論理整合性テンプレートと同じ構造で配置すべき
  - 同意の程度（全面同意 / 部分同意 / 同意せず）
  - 同意の根拠
  - 作業指示者向けの補足
  - 修正案への見解（採用 / 別案 / 補足）
  - 必要に応じて追加修正提案
- **「レビューイ収束判定」セクションの既定追加**: 文書末尾（変更履歴の前）に固定的に配置すべき。テンプレート未確定だと作業者によって判断記録の場所がブレる

### 3.2 推奨レベルで追加すべき

- **修正案への「採用 / 改変採用 / 却下」の予測欄**（レビュアー側）: レビュアーが推奨案を出す段階で「レビューイ・作業指示者がどの程度受け入れる見込みか」を記入できる欄があると、収束見込みの精度が上がる。ただしレビュアーの主観が強くなりすぎるリスクもあるので、優先度は低め
- **観点別サマリ表での「変更影響範囲」列**: 実用性指摘は「文書のどこをどの程度変更するか」が指標として有用。例えば I-1 は §2.1 表の 1 行修正、S-3 は §9.1 冒頭 1 行追加など、変更の大きさが事前にわかると作業指示者の判断負荷が下がる

### 3.3 オプションレベル

- **「指摘の発見経緯」欄**: 観点別レビューだとレビュアーがどの順序で文書を読んで指摘を発見したかが分からない。発見経緯（精読順序や検索キーワード）が分かると、再現性のあるレビュー手法として横展開できる。ただし全指摘で記入するのはコスト過大なので、オプションで十分

## 4. 冗長項目

特になし。改訂版実用性テンプレートは現時点で **ほぼ最小構成** に近い設計と感じた。POSITIVE エントリの「作業指示者の態度表明（維持 / その他）」は形式上の冗長感が若干あるが、これは「POSITIVE でも作業指示者が異論を持つ可能性」を排除しないための設計と理解できるため、削除提案はしない。

## 5. 困った点 Top 3

### Top 1: レビューイ見解欄の不在

- **困り具合**: 高
- **内容**: 「テンプレートに既定欄が無いのに、ユーザ指示でレビューイ見解の記入を求められる」という状況に直面し、記入位置を自分で設計する必要があった。設計時間（方式 1〜3 の比較）に約 5 分要した。テンプレート既定で欄があれば、即座に記入開始できたはず
- **改善提案**: §3.1 の「必須レベル」改善を実施する

### Top 2: 収束判定の指示と既定構造の乖離

- **困り具合**: 中
- **内容**: ユーザ指示で「収束判定セクションを文書末尾（変更履歴の前）に追加」と明示されたため迷わなかったが、テンプレート既定では位置が決まっていないため、将来の運用で記入位置がブレる懸念がある
- **改善提案**: §3.1 の「レビューイ収束判定」セクション既定追加を実施する

### Top 3: POSITIVE への見解記入のフォーマット適合性

- **困り具合**: 低
- **内容**: POSITIVE 指摘に対するレビューイ見解は「同意の程度」「修正案への見解」というフォーマットがやや不自然（「同意せず」が成立しにくい、「修正案」が存在しない）。今回は「評価点の認識として全面同意」「維持の見解として維持」という形で対応したが、POSITIVE 専用のフォーマットがあると記入しやすい
- **改善提案**: POSITIVE 用レビューイ見解欄は「評価点の認識: 一致 / 一部不一致 / 不一致」「維持・縮小の見解」のような形式で別フォーマット化すると整理される

## 6. 助かった点 Top 3

### Top 1: 修正案テーブル形式の統一

- **助かり具合**: 高
- **内容**: 修正案が表形式（# / 修正案 / メリット / デメリット）で統一されており、推奨案に「★」マーク・推奨根拠の太字強調も明示されているため、レビュアーの推奨意図が明確に読み取れた。これにより「★1 を採用」「案 2 を不採用」の判断が即座にできた
- **設計意図の評価**: テンプレート設計者の意図（「人間のレビューアにとって読みやすいドキュメントとするため」）が機能している

### Top 2: 該当箇所・問題・修正案の構造化

- **助かり具合**: 高
- **内容**: 各指摘が「該当箇所 → 問題 → 修正案」という明確な順序で構造化されており、自分の作品（02.99 報告書）の該当箇所を即座に参照できた。指摘 ID（C/I/S/P）の優先度も即座に把握できるため、見解記入の優先順位を組み立てやすかった

### Top 3: 判断依頼サマリーの存在

- **助かり具合**: 中
- **内容**: 文書冒頭の「判断依頼サマリー」表で全指摘 ID・タイトル・態度表明状況が俯瞰できるため、見解記入の進捗管理（「あと何件残っているか」）が容易だった。アンカーリンク（`[I-1](#i-1-...)`）で本文へジャンプできるのも便利

## 7. セルフレビュー反復回数

- **回数**: **2 回**
- **1 回目の検出事項**:
  - I-1 への見解で、推奨案★1 への賛成根拠が「重複登場の解消」に偏っており、「§3.8.1 評価との整合」という観点が抜けていた → 修正
  - S-2 への見解で、当初「全面同意」としていたが、執筆時点の意図（「03.02 担当者の自由度を残す」）を改めて見直すと、本書側で選択方針まで踏み込むことへの慎重さは合理的だったため「部分同意」に修正
- **2 回目の検出事項**:
  - P-1・P-2 の「全面同意（評価点の認識として）」という表現が初期は単に「全面同意」だったが、POSITIVE では「同意の程度」が「評価点の認識が一致するか」を指しているので、明示する形に修正
  - 収束判定の「全体所感」欄で、当初は所感のみ記載していたが、ユーザ指示で「収束に追加ラウンドが必要かの判断」を明記とあったため、判断結論を末尾に追加
- **3 回目（最終確認）**: 新規 NG 検出なし。出力確定

### 防衛的・後付け弁解チェック

- 各見解で「執筆時点ではこう考えていた」という意図説明を入れているが、これは指摘への正当化（防衛）ではなく、**作業指示者が判断するための材料提供**として機能している
  - 例: S-2「部分同意」では、執筆時意図（03.02 担当者の自由度を残す）を述べた上で、レビュアー指摘の妥当性も認め、補足追記の文言案まで具体化している
  - 単なる弁解（「執筆時の意図は正しかった」で終わる）ではなく、レビュアー指摘を改善機会として受け入れる姿勢で記述している
- バイアスによる指摘矮小化の確認: 4 件中 4 件（I-1・S-1・S-3 の改善提案、P-1・P-2 の評価）でレビュアー提案を採用または採用方向で受け入れており、自己擁護のための矮小化は発生していない。S-2 のみ「部分同意」だが、これは「02.99 のスコープ判断」という構造的論点に基づく合理的な対立であり、矮小化ではない

## 8. 総合評価

### 8.1 改訂版実用性テンプレートの完成度

- **記入のしやすさ**: 中（レビューイ見解欄の不在が最大のネック）
- **作業指示者向けの判断材料の整理度**: 高（修正案テーブル・判断依頼サマリーが優秀）
- **論理整合性テンプレートとの一貫性**: 中（レビューイ見解欄の有無で乖離）

### 8.2 推奨される次の改善ステップ

1. **最優先**: 実用性テンプレートに「レビューイ見解」欄を既定追加（§3.1 必須レベル）
2. **優先**: 「レビューイ収束判定」セクションをテンプレート末尾に既定配置
3. **検討**: POSITIVE 用レビューイ見解の専用フォーマット化（§5 Top 3）
4. **将来検討**: §3.2 推奨レベル・§3.3 オプションレベルの追加項目

これらの改善により、実用性テンプレートは論理整合性テンプレートと同等の運用性を獲得できると考える。
