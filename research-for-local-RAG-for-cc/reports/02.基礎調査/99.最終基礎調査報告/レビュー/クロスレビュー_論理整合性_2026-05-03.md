### C1. H1 仮説の「現時点ステータス」評価が、計画書の H1 命題に対する判定として未解決のまま残っている

**問題点**:

計画書 §4 の H1 は「コードベース系データには Filesystem Exploration RAG（grep/glob）の方がベクトル検索より精度・速度で有利」という明確な命題である。

99 報告書 §2.3 / §4 H1 では、現時点ステータスを「**対立軸が補正された**（grep/glob 単独 vs 汎用ベクトルではなく、コードグラフ+シンボル検索 vs 汎用ベクトル）」と記載しており、H1 そのものへの判定（成立 / 不成立 / 部分成立 / 修正後再評価）が明示的に下されていない。サブタスク 07 §4 では Codebase-Memory 論文（2026-03）を引用して「コードグラフ系は file-explorer 比でトークン 1/10、ツール呼び出し 2.1 倍削減、回答品質 83%（**file-explorer: 92%**）」と報告しており、この数値は **「精度（回答品質）では file-explorer が 9 ポイント優位」** という H1 成立寄りの根拠と、**「トークン効率では grep/glob が劣後」** という H1 不成立寄りの根拠の両方を示している。

「対立軸補正」は調査の進展としては正しい記述だが、計画書で立てた H1 命題に対しては:

- 精度面: H1（grep/glob 優位）寄りに支持あり（file-explorer 92% vs Codebase-Memory 83%）
- 速度面: H1 寄り（grep <0.02s）
- トークン効率: **H1 と逆方向**（コードグラフ系がトークン 1/10）

という多面的判定がサブタスク 07 から導けるはずである。99 報告書ではこの判定を「対立軸補正済み」の一語で済ませており、計画書 §4 で立てた H1 命題（精度・速度の両軸での優劣）への明確な回答がない。

これは「02.99 完了条件: 各仮説（H0〜H5）の現時点の検証状況が整理されていること」（計画書 §5.2）に対するカバレッジ欠落に該当する。下流の 03 設計フェーズで H1 を引き継ぐ際、「H1 の真偽は何だったのか」が判定不能となり、検証対象選定（特に Filesystem Exploration を必須対照群として残す根拠）の論理的トレーサビリティが断たれる。

**修正案**:

§2.3 / §4 H1 のステータスを以下のような多面判定に書き換える:

- **H1 精度面**: 部分成立（コードベースデータでは file-explorer 系が Codebase-Memory 系を 9 pt 上回る／GrepRAG では Vanilla RAG を 54% 上回る）
- **H1 速度面**: 成立（grep p50 <0.02s vs ベクトル ~30ms）
- **H1 トークン効率面**: 不成立（grep/glob は線形増加、コードグラフ系は 1/10）
- **対立軸の補正**: 元の二択（grep/glob vs 汎用ベクトル）は不適切と判明し、04 では「Filesystem Exploration（H1 検証用必須対照群）」「コードグラフ系（新規追加候補）」「汎用ベクトル」の 3 軸比較が必要

この多面判定により、H1 が単純な真偽ではなく評価軸ごとに異なる結論を持つことを下流フェーズに正確に引き継げる。

### I3. TBD3「解消」と「03.01 で再確定」の二重表現が論理的に矛盾している

**問題点**:

99 報告書 §2.4 残 TBD ステータス表で TBD3（規模感）を「**解消**（数 MB〜数百 MB、ファイル数百〜数万件…）」と評価する一方、同じ行の「次フェーズでの確定方針」列で「**03.01 でユースケース別の代表サンプルとして規模を再確定**」と記述している。§5 TBD3 でも同じ二重表現がある。

「解消」と「再確定」は同時に成立しない。実際にサブタスク 01 §4 を確認すると、規模感は「本調査の想定規模は数MB〜数百MBオーダー、ファイル数は数百〜数万件（前回サマリー通り確認）」とあり、これは **代表ユースケースから導いた値ではなく、調査着手時の仮想定オーダー** である。計画書 §4 TBD3 の検証方法は「文献調査による『探索空間の閾値』『CAG / RAG / Filesystem Exploration の境界』の特定」であり、これは満たしているが、計画書 §5.3.1 の 03.01 完了条件「TBD3（データ規模）が代表サンプル選定により概算値として記入されていること」とは別の解像度の作業である。

つまり TBD3 は **「探索空間境界としての規模感は解消（02.01）」「代表ユースケースの個別値としての規模は 03.01 で確定」** という 2 つの粒度に分けて記述するべきで、「解消」だけでは下流の 03.01 担当が「もう確定済みで再作業不要」と誤解する余地を残す。

**修正案**:

TBD3 のステータスを以下のように 2 段階で記述する:

- **TBD3-a（探索空間境界の規模感）**: 解消（02.01 で文献ベース概算オーダー確定）
- **TBD3-b（代表ユースケース別の規模値）**: 03.01 で確定予定（計画書 §5.3.1 完了条件）

または「**部分解消**（探索空間境界の概算オーダーは確定。代表ユースケース別値は 03.01 で確定）」と表現する。

**問題点**:

計画書 §4 TBD2 の問いは「**Graph RAG の本ユースケース適用可能性**（脆弱性パッチ・コード関連グラフ等）」。

99 報告書 §2.4 / §5 TBD2 では「**解消（スコープ外確定）**」と記述しつつ、§5 TBD2 の補足で「**ただし、コードベース向けの『コードグラフ系』（Codebase-Memory MCP / isink17/codegraph）はローカル LLM 不要のため別カテゴリとしてスコープ内**」と書き加えている。

これは論理的に「Graph RAG は何を指していたのか」の定義問題に行き当たる。サブタスク 01 §6 の TBD2 結論では「Graph RAG（KG構築フェーズで LLM 必須なツール群: Microsoft GraphRAG / LightRAG / Neo4j+LangChain）はスコープ外」と限定して書いており、これは「LLM 必須ツール群 = Graph RAG」という暗黙の定義に立っている。

しかしサブタスク 07 §2.2 / §4 では「コードグラフ系（Codebase-Memory MCP / isink17/codegraph / GitNexus / Code-Graph-RAG）」も含めて「コードベース版の Graph RAG 的アプローチ」として扱っており、Graph RAG の定義範囲が広がる。

99 報告書はサブタスク 01 の狭義 Graph RAG（既製ツール群）を「スコープ外」、サブタスク 07 の広義コードグラフ系を「スコープ内」として両立させようとしているが、TBD2 の問い「Graph RAG の本ユースケース適用可能性」に対しては「**狭義: スコープ外、広義: スコープ内（コードグラフ系として）**」という二分判定が論理的にあるべき。「解消」という単語だけでは不十分。

**修正案**:

§5 TBD2 のステータスを以下のように再整理する:

- **狭義 Graph RAG（KG 自動構築に LLM 必須の既製ツール: GraphRAG / LightRAG / Graphiti 等）**: スコープ外確定
- **広義コードグラフ系（KG 構築が AST/シンボル解析ベースで LLM 不要: Codebase-Memory MCP / isink17/codegraph 等）**: スコープ内（§3.7 参照）。03 設計フェーズで検証対象追加検討
- **「擬似 Graph RAG」（Claude Code 自身が JSON で依存関係を構築）**: 構築・維持コスト高のため当面除外、申し送り（§8.4）

これにより TBD2 の問い「Graph RAG の本ユースケース適用可能性」への論理的に完結した回答となる。
