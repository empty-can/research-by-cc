## IMPORTANT

### I-1: mcp-local-rag（shinpr）の検証対象命名ルール逸脱が未解決のまま次フェーズに送られている

**該当箇所**: §5（TBD5）の検証対象ドラフト表、および §6.2「検証対象構成の見直し論点3」

**問題**: 計画書§5.4「検証対象の命名ルール」は `<DB>_<連携方式>` の複合語を原則とし、単一ツール・ライブラリ・プロダクトのみが検証対象の場合は正式名称を優先すると定めている。`mcp-local-rag（shinpr）` は「MCP 汎用 RAG サーバーの既製品」として検証対象追加を 03.02 に委ねているが、**採用された場合の正式検証対象名が未定義のまま**であり、命名ルールとの整合が 03 担当者に丸投げされている。

03 設計フェーズで「コードグラフ系」と「mcp-local-rag 系」が検証対象に加わった場合、計画書§5.4 の命名ルール（`<DB>_<連携方式>` vs 製品名優先）のどちらを適用すべきかの判断根拠が本報告書に示されていないため、03 担当者が迷う可能性がある。

**修正案**:
§6.2 の「論点3」に以下を追記する:

```
追加検討時の命名案（計画書§5.4 命名ルール適用判断）:
- mcp-local-rag（shinpr）は単一製品が検証対象となるため「製品名優先ルール」を適用し、
  検証対象名は `mcp-local-rag_shinpr` または製品名そのまま（03.02 で確定）
- コードグラフ系の場合も同様に製品名優先ルールを適用し、
  `Codebase-Memory-MCP` または `codegraph_isink17` 等（03.02 で確定）
- 上記命名案は「命名ルールの適用根拠」とともに 03.02 で記録すること
```

### I-2: §7.3「計画書更新提案」が「03.02 完了時に実施」と先送りされており、02 完了時点での計画書状態との乖離が管理されていない

**該当箇所**: §7.3「02 完了に伴う作業計画書の更新提案」

**問題**: §7.3 は計画書側への改訂候補を4件列挙しているが、**いずれも「03.02 完了時の見直しで実施」と先送り**されている。現時点で計画書は v1.0 のまま、本報告書の発見（H1 補正・コードグラフ系追加・embedding-gemma 置換・mcp-local-rag 追加）が計画書本体に反映されていない。

03 設計フェーズの担当者が計画書を参照した際、計画書本文（例：§4 の H1 記述、§5.4 の検証対象 02 の構成）と本報告書の内容に乖離があることに気づかない場合、誤った前提で設計判断をするリスクがある。特に「§4 仮説テーブル H1 の補正（コードグラフ+シンボル検索 vs 汎用ベクトル）」は設計上の根本的な対立軸に関わるため、計画書が古い記述のままだと混乱を招く。

**修正案**: 以下の2択から選択する。

**案 A（推奨）**: §7.3 に「02 完了時点での計画書との乖離サマリ」を追記し、03 担当者が本報告書から正確な最新情報を参照できるようにする。

```
#### 参照順序の注意事項（03 担当者向け）
作業計画書 v1.0 の以下の箇所は 02 完了時点の発見により内容が更新されている。
03 作業では本報告書の記載を計画書より優先して参照すること：

| 計画書箇所 | 計画書記載（旧） | 本報告書での更新内容 | 本書参照先 |
|---|---|---|---|
| §4 H1 仮説テーブル | grep/glob vs 汎用ベクトル | コードグラフ+シンボル検索 vs 汎用ベクトル | §4 H1、§3.7 |
| §5.4 検証対象 02 | embedding-gemma-300M | ライセンス懸念あり。bge-m3 等へ置換を 03.02 で検討 | §6.2 論点1 |
| §5.4 検証対象候補 | 5 件+CAG 系のみ | コードグラフ系・mcp-local-rag 追加検討あり | §6.2 論点2・3 |
```

**案 B**: 03 着手前に計画書 v1.1 改訂を実施し、本報告書の発見を計画書本体に反映する（コミット候補として作業指示者に提案）。

## SUGGESTION

### S-1: §4 の H0/H1/H3/H4/H5 の「04 での扱い」「05 での扱い」が一部「検討する」止まりで具体的なアクションが不明

**該当箇所**: §4 各仮説の「04 での扱い」「05 での扱い」記述

**観点**: H0・H1・H2 の「04 での扱い」記述は概ね具体的だが、以下の箇所が「〜を 03 設計フェーズで検討」「〜を 03.02 で判断」で終わっており、03 担当者が何を決定事項として受け取ればよいかが不明確。

- H1「04 では Filesystem Exploration を必須対照群として維持しつつ、**コードグラフ系（Codebase-Memory MCP / isink17/codegraph）を検証対象として追加することを 03 設計フェーズで検討する**」
- H3「04 での扱い: 環境構築工数・ストレージ効率の実測。」（どのDBを対象とするか未記載）

完了条件の観点では、03 担当者が「この報告書を読んで、自分が 03 フェーズで何を決めれば良いか、何はすでに決まっているか」を把握できることが求められる。「検討する」のみの記述は、04 での具体的な検証設計ができない。

**提案**: H1 の「04 での扱い」に以下の程度の具体化を加える。

```
04 での扱い:

- コードグラフ系（Codebase-Memory MCP または isink17/codegraph）を新規検証対象として追加するか否かを 
  03.02 で決定する（未定事項）
- 追加する場合は検証対象命名を確定し、計画書§5.4 を改訂する
```

H3 の「04 での扱い」には対象 DB の候補（DuckDB+vss / LanceDB / sqlite-vec）を明示する。

### S-3: §3.6「既製 MCP RAG サーバーの最有力候補」の採用理由に比較根拠が薄い

**該当箇所**: §3.6「既製 MCP RAG サーバーの最有力候補: mcp-local-rag（shinpr）」

**観点**: `mcp-local-rag（shinpr）` を「最有力候補」として記載しているが、採用理由が「軽量（90MB 埋め込みモデル）、`npx` で即利用可能」「実装コストが最低水準」のみであり、§3.8.2 で同じく「高」と評価されている `DeusData/codebase-memory-mcp` との使い分け基準が明示されていない。

03 設計フェーズの担当者が「汎用ドキュメント RAG 向けには mcp-local-rag、コード特化には codebase-memory-mcp」という使い分けを読み取れるかが不明確。また「最有力候補」という表現は §2.1 の採用候補表にも記載があるが、「第一候補」ではなく「既製品として追加検討」という位置付けとの関係が紛らわしい。

**提案**: §3.6 の「既製 MCP RAG サーバーの最有力候補」節に以下を追記する。

```
**用途の区分**:
- ドキュメント・自然言語テキスト向け RAG: mcp-local-rag（shinpr）が最短実装パス
- コードベース特化 RAG: §3.7 の Codebase-Memory MCP / isink17/codegraph が適切
- 両方を扱う場合は MCP サーバーを機能別に分離して登録することを推奨（§3.6 注意点参照）
```
