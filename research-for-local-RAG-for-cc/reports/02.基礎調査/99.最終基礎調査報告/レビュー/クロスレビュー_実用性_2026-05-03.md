### S-3: §3.6「既製 MCP RAG サーバーの最有力候補」の採用理由に比較根拠が薄い

**該当箇所**: §3.6「既製 MCP RAG サーバーの最有力候補: mcp-local-rag（shinpr）」

**観点**: `mcp-local-rag（shinpr）` を「最有力候補」として記載しているが、採用理由が「軽量（90MB 埋め込みモデル）、`npx` で即利用可能」「実装コストが最低水準」のみであり、§3.8.2 で同じく「高」と評価されている `DeusData/codebase-memory-mcp` との使い分け基準が明示されていない。

03 設計フェーズの担当者が「汎用ドキュメント RAG 向けには mcp-local-rag、コード特化には codebase-memory-mcp」という使い分けを読み取れるかが不明確。また「最有力候補」という表現は §2.1 の採用候補表にも記載があるが、「第一候補」ではなく「既製品として追加検討」という位置付けとの関係が紛らわしい。

**提案**: §3.6 の「既製 MCP RAG サーバーの最有力候補」節に以下を追記する。

```
**用途の区分**:
- ドキュメント・自然言語テキスト向け RAG: mcp-local-rag（shinpr）が最短実装パスの暫定候補
- コードベース特化 RAG: §3.7 の Codebase-Memory MCP / isink17/codegraph が適切
- 両方を扱う場合は MCP サーバーを機能別に分離して登録することを推奨（§3.6 注意点参照）
  ただし、多数 MCP 同時登録時のツール一覧トークン消費（≒55,000 トークン）に留意し、
  Tool Search 機能（tool_search=true、最大 85% 削減）の活用を前提とすること
```

#### 作成者からの見解・コメント

##### 指摘内容に対して

指摘の前半（「最有力候補」の表現が §2.1 の「既製品として追加検討」位置付けと紛らわしい）は妥当と認める。これは論理整合性レビュー I1 と同根の問題で、v1.1 にて mcp-local-rag（shinpr）を「最有力候補」から「暫定候補」に格下げ済み（§3.6 / §2.1 / §3.8.2 / §6.2 / §8.4 で表現を統一）。

指摘の後半（mcp-local-rag と DeusData/codebase-memory-mcp の使い分け基準が不明）は **部分同意** とする。理由:

- **同意する点**: 両者ともに「採用候補度: 高（または最有力暫定）」で並列に並んでいるため、03 担当者が「どちらを優先採用するか」「両方採用するなら使い分けは何か」を読み取れない構造は確かに改善余地がある
- **留意事項**: 両者は **対象データ種別が異なるため本質的に競合関係にない**（mcp-local-rag = ドキュメント／自然言語テキスト RAG、Codebase-Memory MCP = コードベース特化）。報告書 §3.6 が「MCP RAG サーバー」、§3.7 が「コードベース向け RAG」と章を分けている時点で暗黙的に使い分けは示されているが、明示しないと読み手の負担になる

##### 修正案について

レビュアー修正案（§3.6 に「用途の区分」を追記）は妥当な改善であり、v1.1 にて §3.6 「mcp-local-rag」節下に「用途の区分」を追加採用済み。

ただし、作成者として **以下の追加検討事項** がある:

- 「両方を扱う場合は MCP サーバーを機能別に分離して登録することを推奨」という記述は、§3.6 の「注意点（新規発見）」での MCP 多数登録時のツール一覧トークン消費（55,000 トークン、ハマりどころ #14）と一見矛盾する印象を与える可能性がある。「機能別に分離」と「多数登録するとトークン消費が大きい」を両立させるには、Tool Search 機能（最大 85% 削減）の活用が前提となる。この前提条件を明示的に併記する方が安全
- 03.02 で実機動作確認するときは、両 MCP サーバーを同時登録した状態でのトークン消費も実測項目に含めるべき
