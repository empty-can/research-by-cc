## 3. 採用候補の詳細（03 設計フェーズへの入力）

### 3.1 埋め込みモデル

#### 第一候補: BAAI/bge-m3

- **ライセンス**: MIT（商用可）
- **次元**: 1024（Dense モード）
- **モデルサイズ**: 約 4.6 GB
- **多言語対応**: 100 言語以上、日本語含む（MIRACL nDCG@10=70.0）
- **特長**: Dense / Sparse / ColBERT の 3 モード出力を単一モデルで生成可能 → ハイブリッド検索構築が容易
- **最大トークン**: 8192
- **採用理由**: 日英混在・コード・Markdown という本ユースケースの多様なデータに単一モデルで対応可能。多言語+コード対応の SOTA 水準
- **注意点**: モデルサイズが大きく初回ダウンロード・低スペック環境での動作検証が必要（フィジビリティ検証フェーズ）

#### 補完候補: cl-nagoya/ruri-v3-310m（日本語精度を最大化したい場合）

- **ライセンス**: Apache 2.0
- **次元**: 768
- **モデルサイズ**: 約 1.2 GB
- **多言語対応**: 日本語専用（JMTEB 平均 77.24 で日本語 SOTA）
- **採用理由**: 日本語クエリでの最高精度。bge-m3 と並行運用で「日本語クエリ時のみ ruri を呼ぶ」設計も可能
- **注意点**: 英語・コードへの単独適用は不可（ハマりどころ #7）。並行運用時はチャンクメタデータにモデル名・次元を保持して空間混在バグを防ぐ（ハマりどころ #2）

#### 軽量候補: Qwen/Qwen3-Embedding-0.6B（CPU オンリー環境向け）

- **ライセンス**: Apache 2.0
- **次元**: 32〜1024（可変）
- **モデルサイズ**: 約 1.2 GB
- **特長**: 32K トークン対応（長文コード/ドキュメントに有利）、100 言語以上対応
- **注意点**: クエリ側にインストラクションプロンプトの付与が必要（ハマりどころ #10）

### 3.2 ベクトル DB

#### 順位付けの判断基準

(1) Windows 11 公式サポート、(2) 単一ファイル型優先（Docker 不在環境のため）、(3) 既存事例による実証、(4) 本ユースケース想定規模（数千〜数十万チャンク、§5 TBD3）での動作余裕、の順で評価。Qdrant は Windows ローカルモード安定性の懸念から第一〜第四候補から外している（02-03 §3.1）。

#### 第一候補: DuckDB + vss

- **ライセンス**: MIT
- **形態**: 単一ファイル（`.duckdb`）
- **採用理由**: 標準 SQL 操作、Python/Node.js から直接利用、Windows 公式サポート、参考記事で実証済み（数万チャンクでミリ秒検索）
- **注意点**: HNSW 永続化が experimental（`hnsw_enable_experimental_persistence = true`、ハマりどころ #4）。1024 次元 × 100 万ベクトルで RAM 約 6GB 消費（ハマりどころ #13）→ 本ユースケース規模（〜数十万チャンク）では問題なし

#### 第二候補: LanceDB

- **ライセンス**: Apache 2.0
- **形態**: 単一ファイル（組み込み型）
- **採用理由**: Arrow ネイティブで効率的、数百万ベクトルをローカルで快適、DuckDB との連携公式サポート
- **注意点**: 25,600 件未満ではインデックス自動作成されずフルスキャン（ハマりどころ #11）。`create_index()` 明示呼び出しが必要

#### 第三候補: sqlite-vec

- **ライセンス**: Apache 2.0
- **形態**: 単一ファイル（既存 SQLite に同居可）
- **採用理由**: 最軽量、`pip install sqlite-vec` のみで導入完了
- **注意点**: HNSW 非対応のため数十万件超で線形劣化（ハマりどころ #12）。Windows では `pysqlite3` を推奨（最新 SQLite バンドル）

#### 第四候補: Chroma

- **ライセンス**: Apache 2.0
- **形態**: ローカルファイル + サーバー両用
- **採用理由**: `chromadb.PersistentClient(path=...)` 1 行で永続ストレージ完結、開発体験良好
- **注意点**: クエリレイテンシ約 30ms（Qdrant の約 12ms より遅い）。プロトタイプ向け

### 3.3 検索アルゴリズム

#### 推奨構成: ハイブリッド（BM25+ベクトル+RRF）+ クロスエンコーダーリランキング

- **ハイブリッドの効果**: recall@10 が 78%（ベクトル単体）→ 91%（ハイブリッド）へ向上、追加レイテンシは p50 で約 +6ms（無視できる水準）
- **リランキングの効果**: NDCG@5 が +12〜18 ポイント向上（クエリが長く複雑なほど効果大）
- **RRF の k**: 60（業界標準値）
- **BM25 日本語処理**: `rank_bm25` + `sudachipy`（形態素解析必須、ハマりどころ追記候補）

#### 第二候補: ハイブリッドのみ（リランキングなし、スモールスタート）

- リランカー常駐メモリ・推論遅延が許容できない場合や、コーパスが小規模の場合
- recall@10 約 91% は確保可能

### 3.4 リランカー

#### 第一候補: BAAI/bge-reranker-v2-m3

- **ライセンス**: MIT
- **パラメータ**: 278M
- **多言語対応**: 100 言語以上（日本語含む）
- **遅延（CPU、50 候補）**: 200〜400ms

#### 補完候補: hotchpotch/japanese-bge-reranker-v2-m3-v1

- **ライセンス**: MIT
- **特長**: 日本語特化ファインチューン版

#### 英語コード主体時の代替: cross-encoder/ms-marco-MiniLM-L-6-v2

- **ライセンス**: Apache 2.0
- **パラメータ**: 33.4M
- **遅延（CPU、50 候補）**: 50〜100ms（最速候補）

### 3.5 チャンク戦略

| データ種別 | 推奨手法 | チャンクサイズ | オーバーラップ |
|---|---|---|---|
| コード（Python/TypeScript） | tree-sitter + cAST（AST 構造認識） | 1,000〜1,500 非空白文字（100〜200 トークン相当） | 0〜10 行（原則不要） |
| Markdown | MarkdownHeaderTextSplitter + 再帰分割 | 800〜1,200 文字（250〜400 トークン相当） | 10〜20% |
| PDF（前処理後） | ページ単位 or 再帰分割 | 512〜1,024 トークン | 10〜20% |

#### 重複排除（推奨）

- 二段階重複排除アーキテクチャ
  - **インデックス時**: SHA-256 ハッシュで完全一致除外、コサイン類似度 ≥ 0.90 の近似重複は「除去」ではなく「顕著度 +15% ブースト」に統合
  - **検索時**: スコア順走査で既選択チャンクとの類似度 ≥ 0.90 をスキップ
- 閾値 0.90 は NVIDIA NeMo 業界標準

#### メタデータ設計（必須フィールド）

`source_path` / `document_id`（ハッシュ）/ `chunk_id` / `language` / `chunk_text_length`

#### 推奨フィールド

`start_line` / `end_line` / `section_headers` / `entity_type` / `entity_name` / `scope_chain` / `created_at` / `page_number`

### 3.6 Claude Code 連携方式

#### 推奨構成: MCP サーバー型（stdio transport）+ 軽量 SQLite/DuckDB

- **採用理由**:
  - 設定コストが CLI 型と同等以下（`.mcp.json` 数行）
  - 常駐型のため毎回のモデルロードコスト（CLI 型 8〜9 秒、ハマりどころ #6）を排除
  - 自動呼び出しによりエージェント側で透過的に RAG を活用可能
  - 既製品が豊富（mcp-local-rag、qmd 等）

#### 第二候補: Skills 常駐 HTTP サーバー型（自作・高制御性）

- 反復検索・高速応答要件（コードリバースなど）に最適
- Windows 環境では常駐管理（タスクスケジューラ / WinSW 等）の追加検討が必要

#### 用途限定: Skills CLI 都度起動型

- プロトタイプ・初期検証フェーズのみ
- 8〜9 秒の遅延が顕在化するため本番採用不可

#### 既製 MCP RAG サーバーの暫定候補: mcp-local-rag（shinpr）

- **ライセンス**: OSS（商用利用可、ただしリポジトリの正式ライセンス文言は 03.02 で再確認）
- **特長（02-06 内 Web 調査依拠）**: 軽量（90MB 埋め込みモデル）、`npx` で即利用可能
- **採用理由（暫定）**: MCP サーバー型の既製品として実装コストが最低水準
- **要再評価事項**: スペック詳細（モデル名・実装言語・最大トークン等）の出典補強と、Windows 11 環境での実機動作確認が 03.02 の検証対象追加判断時に必要

**用途の区分**:

- **ドキュメント・自然言語テキスト向け RAG**: mcp-local-rag（shinpr）が最短実装パスの暫定候補
- **コードベース特化 RAG**: §3.7 の Codebase-Memory MCP / isink17/codegraph が適切
- **両方を扱う場合**: MCP サーバーを機能別に分離して登録することを推奨（下記「注意点」のツール一覧トークン消費に留意）

#### 注意点（新規発見）

MCP サーバーの多数登録（5 サーバー・58 ツール規模）でツール一覧 ≒ 55,000 トークン消費（ハマりどころ #14）。Tool Search 機能（`tool_search=true`）で最大 85% 削減可能。**RAG 専用 MCP は機能を絞った軽量サーバーを選定する**ことが重要。

### 3.7 コードベース向け RAG（コード特化）

#### 第一候補: Codebase-Memory MCP（DeusData/codebase-memory-mcp）

- **ライセンス**: MIT

## 4. 仮説（H0〜H5）の検証状況

### H0: 一定規模以下のデータでは CAG が RAG よりトークン効率・精度ともに優れる可能性がある

**現時点ステータス**: **境界条件特定済み（02-01）**

| 境界軸 | CAG 有効域 | RAG 移行推奨域 | 根拠 |
|---|---|---|---|
| ファイル数 | 1〜50 ファイル | 100 ファイル超 | Zenn 記事「数ファイル程度」、Monte Carlo Data 2025（500 ドキュメント超でコンテキスト超過リスク顕在化） |
| トークン数 | 〜50,000 | 200,000 超で精度劣化 | ACM Web Conference 2025（CAG 有効域実証）、claude-3.5-sonnet の 200K 上限 |
| データ更新頻度 | 静的（月 1 回以下） | 日次・リアルタイム | KV キャッシュ再構築コスト |
| データ性質 | 全量アクセス必要 | クエリ依存の部分検索で十分 | Zenn 記事 |

**04 での扱い**: 計画書 §5.4 の CAG 系検証対象（命名・構成は 03.02 で確定）として、規模が小〜中規模の代表ユースケースで CAG vs RAG のトークン効率・精度を直接比較する。

### H1: コードベース系データには Filesystem Exploration RAG（grep/glob）の方がベクトル検索より精度・速度で有利

**現時点ステータス**: **多面判定（精度面: 部分成立／速度面: 成立／トークン効率面: 不成立／対立軸: 補正、02-07）**

評価軸別判定:

- **H1 精度面**: **部分成立** — コードベースデータでは file-explorer 系が Codebase-Memory 系を回答品質で 9 ポイント上回る（92% vs 83%、Codebase-Memory 論文 2026-03）、GrepRAG（2026-01）では Vanilla RAG を Python exact match で 54% 上回る
- **H1 速度面**: **成立** — grep p50 <0.02 秒、ベクトル検索は ~30ms 以上
- **H1 トークン効率面**: **不成立** — grep/glob はトークン消費が線形増加し本プロジェクトのゴール（コンテキスト最小化）に反する。コードグラフ系は file-explorer 比でトークン 1/10
- **対立軸の補正**: 元の二択（grep/glob vs 汎用ベクトル）は不適切と判明。正しい比較は「Filesystem Exploration（H1 必須対照群） vs コードグラフ+シンボル検索（新規追加候補） vs 汎用ベクトル RAG」の 3 軸

文献根拠:

- GrepRAG（2026-01）: grep ベースが Python exact match で Vanilla RAG を 54% 上回る、レイテンシ <0.02 秒
- LlamaIndex 2026 ベンチ: vector ≒60% vs agentic search（grep/find/cat）≒68%（Django コードベース）
- Codebase-Memory 論文（2026-03）: コードグラフ系は file-explorer 比でトークン 1/10、ツール呼び出し 2.1 倍削減、回答品質 83%（file-explorer: 92%）

**04 での扱い**:

- 計画書 §5.4「05.検証_フィジビリティ_FilesystemExploration」を必須対照群として維持（**決定済み**、計画書通り）
- コードグラフ系（Codebase-Memory MCP または isink17/codegraph）を新規検証対象として追加するか否かを **03.02 で決定**（未定事項）
- 追加する場合は §6.2「検証対象追加時の命名案」表（製品名優先ルール適用）に従い検証対象命名を確定し、計画書 §5.4 を改訂

### H2: 常駐型 RAG プロセスは CLI 都度起動型より応答速度で優位

**現時点ステータス**: **方向性確認**（軽量モデル `multilingual-e5-small` 構成で CLI 都度起動 8〜9 秒の実測値、bge-m3 等の大型モデルでは更に増加見込み、02-06 / ハマりどころ #6）

- **限定条件下の実測値**: 構成 = `multilingual-e5-small` (約 100〜500MB) + Skills (CLI 都度起動) + DuckDB の単一記事報告（karaage0703）

  - Skills 常駐 HTTP 型: 約 0.1 秒（モデルロード済み）

## 8. 課題・制約

### 8.1 将来解決が必要

- **Docker 不在環境のため pgvector の検証が保留**: 計画書 §5.4 で既知。Issue 化対象（`[04][将来解決]`）
- **bge-m3 の低スペック環境動作検証**: 4.6GB モデルの低 RAM Windows 11 環境での動作実測（04 で実施）
- **Codebase-Memory MCP の品質差（9 ポイント）の本ユースケース固有検証**: コードリバースという本プロジェクト固有用途での回答品質を 04/05 で確認
- **isink17/codegraph および Codebase-Memory の Go 1.26+ 要件**: 2026-05-03 時点で Go 安定版は 1.24.x。インストール時の最新バージョン確認が必要
- **Windows 環境でのサービス常駐化（Skills 常駐 HTTP 型採用時）**: タスクスケジューラ / WinSW 等の具体的設定方法を 04 で検証
- **MCP トークン消費の定量評価**: ツール定義トークンの本ユースケースコスト要件への影響を 04 で実測
- **TBD1（探索空間広すぎる閾値）の精緻化**: 04/05 の実測で 500 ファイル/5MB 暫定値を検証

### 8.2 解決不能

- **Graph RAG の自動 KG 構築**: ローカル LLM 不使用の制約下では既製ツールの KG 構築フェーズを代替する手段がない
- **ベクトル埋め込みによるコード構造の捕捉限界**: ベクトル類似度は本質的にコードの依存構造を表現できない。コードグラフ系との組み合わせが必然
- **日英コード混在コンテンツに対する単一最良モデルの不在**: 日本語専用モデル（ruri-v3）と多言語モデル（bge-m3）はトレードオフ関係。複数モデル並行運用かトレードオフ受容かの設計判断が必要
- **BM25 の意味理解限界**: 同義語・言い換え対応は不可。ハイブリッド構成でカバー
- **クロスエンコーダーの O(N) スケーリング**: リランキング対象数に対し線形に推論コスト増加（N=100 以内が実用上限）
- **MCP の仕様変更リスク**: 2025-03-26 以降 Streamable HTTP 標準化など継続的変更が予測される
- **汎用的な最適チャンクサイズ**: 文献・ベンチマーク一致して「ユースケース・文書特性に依存」と結論。A/B テストによる継続最適化が現実的
- **Filesystem Exploration の根本的スケーリング問題**: トークン消費が線形増加。コードグラフ系に切り替えても「グラフに存在しない知識」は grep に頼らざるを得ない

### 8.3 解決不要

- **クラウド RAG サービスの評価**: スコープ外
- **ローカル LLM のパフォーマンスチューニング**: スコープ外
- **GPU なし環境での Agentic RAG 速度問題**: API 側の問題（本調査範囲では Claude API 利用のため影響なし）
- **all-MiniLM-L6-v2 の日本語非対応**: 採用しないと確定済み
- **EmbeddingGemma のライセンス問題**: 採用しないと確定済み
- **paraphrase-multilingual-mpnet の 128 トークン制限**: 採用しないと確定済み
- **Jina Reranker v2 の CC-BY-NC**: 同等性能の bge-reranker-v2-m3（MIT）で代替可能
- **Sourcegraph のライセンス問題**: OSS 代替（SeaGOAT / Hound / OpenGrok / mcp-ripgrep / Codebase-Memory）で代替可能
- **isink17/codegraph の FSL-1.1-MIT**: 本プロジェクトは調査・社内利用範囲のため実質影響なし（最終採用時の法務確認は推奨）
- **通常埋め込み系の日本語コード精度**: コード識別子は英語中心のため日本語埋め込みへの強い要求は発生しない
- **クラウド依存の高精度チャンキング手法（LLM ベース）**: ローカル・OSS 制約に適合せず採用対象外

### 8.4 申し送り事項（02 完了時点）
