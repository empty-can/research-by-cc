主要な活動計画への影響(詳細は §4):

1. **02.基礎調査の結論は概ね維持** されるが、99.最終基礎調査報告にソース文書最適化(Agent E)とプロダクト境界整理(Agent A)の補強候補あり
2. **03.ローカル RAG 設計が最大の影響を受ける**: 4 つの主要変化(検索結果引渡し規約の必要性 / ソース文書最適化指針の追加 / 接続経路適合性マトリクスの導入 / auto memory との連携設計)。詳細は §4.2 参照
3. **04.フィジビリティ検証の検証対象選定基準が明確化**: パターン採用度(1.A〜1.D)と接続経路適合性(A〜E)の二次元判定により、必須対照群と独自価値中核の優先順序が確定
4. **05.有効性検証の対照群整理に補正**: CAG パターンは「公式機能で代替可能な境界条件確認」として再定義し、**対照群として維持**(ローカル RAG の下限性能ベースラインとして扱う、05 でも残す)。Filesystem Exploration は Subagent(Explore)併用に対照群を拡張(詳細は §4.4 / 確定は 05.01)

## 1. 調査の背景・目的・スコープ

### 1.1 本紙の目的(インパクト評価ドキュメントへの再定義)

本紙の初版(2026-05-17、再構成前)は「Claude Code 公式 RAG 機能との位置づけマップ」として、公式機能の全体像整理を主目的としていた。しかし起点記事のプロダクト誤認(§1.2)判明後の再構成、および後続フェーズ(03 設計以降)への直接的なインプットとしての性質を踏まえ、本紙の主目的を **「追加調査の結果が活動計画の各フェーズにどのような変化を要求するか」の把握** に再定義する。

Agent A〜E の網羅的な調査内容と発見は各 Agent 報告書に詳細化されているため、本紙では **発見の要点と計画への影響の対応関係** に絞った記述に統一する。

### 1.2 当初想定との差異(プロダクト誤認の経緯)

本調査は当初 Anthropic 公式サポート記事 `https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects` を起点として「Claude Code 標準 RAG 機能との位置づけマップ」を作成する目的で開始したが、起点記事が **Claude(SaaS)コレクション**(`support.claude.com/en/collections/4078531-claude`)配下で **Claude Code とは別プロダクト** の機能説明であると判明したため、本紙は **Claude Code スコープのインパクト評価ドキュメント** に再構成済。

Claude(SaaS)の RAG 機能(Projects RAG / Drive Cataloging / Chat Search / claude.ai Memory)は別紙 `99.追加調査報告書【付録】Claude_SaaSに関する情報.md` 参照。Phase 1〜4 の再構成詳細は本紙末尾の「変更履歴」参照。

### 1.3 調査スコープと対象外

#### スコープ内(本紙の対象)

- **Claude Code 内蔵機構**: 公式 docs(`research-for-local-RAG-for-cc/resources/references/claude-code-llms-full.txt`)全文・Help Center 19 記事

- **MCP プロトコル仕様**: 2025-11-25(2026-05-17 時点で最新版・後継バージョン / draft 公開なし)
- **設計予定 15 パターン**: `research-for-local-RAG-for-cc/` 内の 02.基礎調査成果物
- **ソース文書執筆品質(AWS Prescriptive Guidance 視点)**: ローカル RAG に投入するソース文書側のベストプラクティス(Agent E)

#### スコープ外

- **Claude SaaS の RAG / 知識管理機能**: 別紙 `99.追加調査報告書【付録】Claude_SaaSに関する情報.md` を参照

- **AWS マネージドサービス前提のソリューション**: 本リポジトリはローカル RAG が前提のため。AWS ガイドのうち AWS サービス利用前提の事項は付録 B に整理

## 3. 新しく判明した制約事項(§4 関連分のみ)

§4 で扱うフェーズ別影響の根拠となる制約事項のみを抽出。

### 3.1 MCP プロトコル仕様の制約

- **tool result `content` 許容 type は 5 種閉じた enum**(`text` / `image` / `audio` / `resource_link` / `resource`)
- `search_result` 型は許容外、カスタム type 拡張規定もなし
- MCP プロトコル仕様 2025-11-25 が 2026-05-17 時点で最新版(後継バージョン / draft 公開なし)

→ 影響: §4.2(03 設計の検索結果引渡し規約)、§4.3(04 検証時の MCP 連携実装)

### 3.2 Anthropic Messages API レイヤの利用不可

- **直接利用不可**: Memory tool / Search results blocks / Citations / Tool search 等を Claude Code から enable する公式手段なし(Agent D §4.1 確証)
- **MCP 経由間接利用も不可**: 「Claude Code → MCP server → Anthropic Messages API」公式利用フローは存在しない(メインセッション追加検証で 4 経路から確証)
- **唯一の例外**: Agent SDK で自前ハーネスを構築する場合のみ可能だが、本調査スコープ外

→ 影響: §4.2(03 設計の検索結果引渡し規約)、§4.3(04 検証時の Citations 機能利用不可)

### 3.3 ソース文書側の前処理制約

人間向けに書かれた既存文書を RAG に流用する際、retriever のトークン予算が浪費される代表的課題(AWS §2.3 challenges 由来):

- リンク・URL 密度の高さ
- 画像・図表の混入
- 表(二次元構造)の存在
- 略語・固有名詞の未定義
- 冗長性・反復
- ドメイン文脈の欠如

→ 影響: §4.2(03 設計のソース文書最適化指針)、§4.1(02.99 最終基礎調査報告への補強候補)

### 3.4 Claude Code 標準機構の制約

- **Skill 本文ロード後の永続性**: ロードされた Skill 本文はそのセッション中ずっとコンテキストに残る。コンパクション後の再注入は各 skill 最大 5,000 トークン、全 skill 合計 25,000 トークン上限
- **CLAUDE.md は launch 時に全部ロード**: `@import` で物理ファイルを分割してもコンテキスト削減にはならない
- **path-scoped rule はコンパクション後失われる**: 次にトリガーファイルが読まれるまで再注入されない
- **Subagent は他の Subagent を spawn できない**(ネスト構造不可)
- **`fileSuggestion` setting**: 返却パスは最大 15 件
- **UserPromptSubmit hook**: default timeout は 30 秒、hook 出力は会話履歴扱いでコンテキスト消費
- **MCP サーバ多数登録時のツール一覧で ≒55,000 トークン消費**(5 サーバ・58 ツール規模、ハマりどころ #14)→ Tool Search 機能(`tool_search=true`)で 85% 削減可能
- **MCP tool 出力 default 10,000 トークン警告**(`MAX_MCP_OUTPUT_TOKENS` で拡張可)

→ 影響: §4.2(03 設計の連携経路選択)、§4.3(04 検証時の運用制約)、§4.4(05 評価指標としての Skill / MCP 起動コスト)

- **02.99 最終基礎調査報告への追記候補**: ソース文書最適化に関する補強(数百字〜1 ページ程度)
  - **判断タイミング**: 02.99 のクロスレビュー完了後、テンプレート検証/§3.3 設計着手前
  - **判断材料**: 本紙 §3.3 制約事項(前処理制約 6 項目) + Agent E §6(前処理パイプライン素案 10 ステップ + メタデータスキーマ素案 12 項目)

  - **判断 no の場合**: 03 設計時に Agent E §6 を直接参照する形でカバーする運用に倒し、02 完了判定は 99 クロスレビュー完了・テンプレート検証/§3.3 設計完了の従来条件のみで判定
- **02 フェーズの完了判定そのものは変更不要**: ただし「99 のクロスレビュー完了・テンプレート検証/§3.3 設計 待ち」状態は本紙とは別タスクとして継続(上記補強候補の判断結果と並行進行)

#### 4.2.2 03.02 ローカル RAG 設計への影響(中核)

##### (1) 設計予定 15 パターンの取扱い変更

Agent C と本紙 Phase 3 の統合で、15 パターンに **二次元判定** を導入した:

- **接続経路適合性(A〜E)**: A 完全代替 1 件(CAG)/ B 部分代替 1 件(FilesystemExploration)/ C 並存 10 件 / D 独自価値 3 領域(ハイブリッド検索・コードグラフ・日本語特化) / E 除外 1 件(狭義 Graph RAG)
- **ソース文書最適化の必要度(高/中/低)**: ベクトル/全文検索を伴うパターンは「高」、コードグラフ系は「中」、Filesystem Exploration は「低」

この二次元判定により、**設計時の優先順序が明確化**:

- **D 判定領域(独自価値の高い 3 領域)** が本調査の中核として 03 設計の重点対象
- **C 判定(並存)パターン** は MCP server として実装し、Tool Search による on-demand ロードを前提とする
- **A 判定(CAG)** は「Claude Code 標準機能で代替可能な境界条件」として再定義、03 設計の独自実装スコープからは除外候補

##### (2) 検索結果引渡し規約の必要性

§3.1 / §3.2 の制約から、**MCP 経由では Anthropic 公式 Citations の自動付与は不可**。代替経路 4 案を比較:

- **A. text ブロック構造化埋め込み(MCP 標準型のみ)**: デフォルト規約として全 MCP パターン共通で採用
- **B. MCP `resource` / `resource_link` 型で source URI を渡す**: spike 検証対象
- **C. UserPromptSubmit hook の `additionalContext` 経由で `search_result` ブロック注入**: 検証コスト高、spike 検証対象(優先度低)
- **D. Claude Code を経由しない直接 API 利用(Agent SDK)**: 本調査スコープ外

経路 A を採用する場合の text ブロックレイアウトで、**`summary` / `abbreviations` / `session_starter` をオプションフィールドとして検討** する価値あり(Agent E 由来、AWS Best Practice #6/#7/#9)。

##### (5) auto memory との連携設計

Memory tool(API)への直接バックエンド化は不可(§3.2)だが、Claude Code auto memory(`~/.claude/projects/<project>/memory/`)と Memory tool は設計思想が対応関係にあるため、設計予定パターン(特にパターン 7 / 8: Codebase-Memory / codegraph)を **「auto memory の topic file を補完・拡張する外部 RAG レイヤ」** として位置付ければ Memory tool 思想に乗ったまま運用可能。

具体連携候補:

- (a) auto memory ↔ ローカル RAG の手動 sync(最小コスト)
- (b) UserPromptSubmit hook 経由で RAG 結果を auto memory に注入
- (c) MCP server 経由で auto memory 補完(Skill で標準化)

03 設計でいずれを採用するかを決定する必要あり。

##### (6) 「公式機能で代替可能な領域を二重構築しない」原則の明文化

- **「特定ファイルパスでのドメイン規約」**: `.claude/rules/`(path-scoped)で十分、RAG にしない

- **「大量データに対する意味検索・ハイブリッド検索・コード構造解析」**: 本調査の真の独自価値領域
