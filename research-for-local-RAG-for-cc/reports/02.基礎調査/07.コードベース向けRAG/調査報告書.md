## 1. 調査概要

本調査では、ソースコードに特化した RAG 構成（AST 解析 / コードグラフ / シンボル検索 / 通常埋め込み）を4カテゴリに分類し、各カテゴリの代表ツール・手法を整理する。また、Filesystem Exploration（grep/glob）との対照比較を行い、「H1: grep/glob派 vs ベクトル派のどちらが本調査の精度要件を満たすか」への示唆を導出する。

**調査対象環境の前提**:
- 対象データ: ソースコード主体（コードリバース：ソースから設計書を生成）
- 実行環境: Windows 11、完全ローカル、OSS/商用利用無料のみ
- 特定ユースケース: Claude Code が大量ファイルを扱う際のコンテキスト消費最小化
- 調査期間: 本調査時点（2026-05-03）時点の OSS・論文情報を対象

**主な情報源**:
- cAST 論文（arxiv 2506.15655、EMNLP 2025）
- Codebase-Memory 論文（arxiv 2603.27277、2026-03）
- GrepRAG 論文（arxiv 2601.23254、2026-01）
- LlamaIndex 2026 ベンチマーク（Filesystem Tools vs Vector Search）
- 既存サブタスク08（オフライン GitHub リポジトリ調査）の isink17/codegraph・johnhuang316/code-index-mcp・sebastianhutter/local-rag の知見

## 2. アプローチカテゴリ別整理

### 2.1 AST解析系

#### 概要

ソースコードを構文解析して Abstract Syntax Tree（AST）を生成し、関数・クラス・メソッドといった構文単位でチャンク化する手法。テキストの固定長分割と異なり、構文境界を維持したチャンクを生成するため、コードの意味的まとまりを壊さない。

#### 代表ツール・手法

**tree-sitter**（OSS / MIT）

- 66 以上の言語に対応した汎用 AST パーサー。Neovim・Helix・Zed のシンタックスハイライトとして実績のある battle-tested ライブラリ。
- Python バインディング（`tree-sitter-languages`）により Windows でも即時利用可能。
- cAST（2025 EMNLP）が tree-sitter を基盤に採用し、Recall@5 を 4.3 ポイント向上（RepoEval）、Pass@1 を 2.67 ポイント向上（SWE-bench）を達成。

**cAST 方式**（OSS / GitHub: yilinjz/astchunk）

- AST ノードを再帰的に分割しつつサイズ制限を尊重する構造的チャンキング。
- 4 つの設計目標: (1) 構文整合性、(2) 高情報密度、(3) 言語非依存、(4) チャンク連結による原ファイル完全復元。
- 固定長チャンクへの改善: 関数・クラスを途中で切断しない、インポート文やコメントを孤立させない。

**code-index-mcp**（OSS / PyPI / Windows 対応）

- tree-sitter + ripgrep を組み合わせた MCP サーバー（サブタスク08 調査済み）。
- 10 言語を AST パース、50 以上のファイルタイプに fallback。ファイル監視による自動更新あり。
- ベクトル埋め込みなし（テキスト検索のみ）。

**Codebase-Memory MCP**（OSS / MIT / GitHub: DeusData/codebase-memory-mcp / Windows 対応）

- tree-sitter で 66 言語を解析し、コールグラフ・影響分析・コミュニティ検出を含む知識グラフを SQLite に永続化、14 MCP ツールとして公開。
- 2026-02-25 公開後 4 週間で GitHub Stars 900+・Fork 100+。
- Codebase-Memory 論文（2026-03、arxiv 2603.27277）評価: 31 リポジトリで file-explorer 比で **トークン消費 1/10・ツール呼び出し 2.1 倍削減**、回答品質は 83% vs 92%（file-explorer）。グラフネイティブクエリ（ハブ検出・呼び出し元ランキング等）では 31 言語中 19 言語で file-explorer と同等以上の精度。

#### 評価サマリー

| 観点 | 評価 |
|---|---|
| 精度（コードリバース向け） | 高。構文単位チャンクにより関数・クラス定義が途切れない。 |
| 実装コスト | 低〜中。tree-sitter は OSS で多言語対応。Python バインディングあり。 |
| Windows 対応 | 問題なし。tree-sitter / Python は クロスプラットフォーム。 |
| トークン消費 | 中。チャンク品質向上でコンテキスト効率化に貢献するが、ベクトル検索との組み合わせが必要。 |

### 2.2 コードグラフ系

#### 概要

ソースコードから関数呼び出し関係・依存関係・シンボル参照関係をグラフ構造として抽出し、知識グラフや依存関係グラフとして永続化した上で検索する手法。「このクラスを変更すると何が影響を受けるか」「この関数はどこから呼ばれているか」といった構造的クエリに強い。

#### 代表ツール・手法

**isink17/codegraph**（OSS / FSL-1.1-MIT → 2年後 MIT / Windows 対応）

- Go 製。tree-sitter（12 言語）で AST 解析し、シンボル・呼び出し関係をグラフとして SQLite に格納。
- Claude Code 自動設定対応（`--claude-code` フラグ）。29 MCP ツール提供。シングルバイナリで外部 DB 不要。
- Ollama 連携でセマンティック検索をオプション追加可能。
- サブタスク08 で採用候補度「高」と評価済み。

**Codebase-Memory MCP**（上記 AST 系と重複・グラフ機能も有する）

- コールグラフ解析・依存関係トレース・影響半径（impact radius）クエリをサポート。
- AST 解析 + グラフ構造の両方を提供するハイブリッドツールとして位置付け可能。

**GitNexus**（OSS / MCP ネイティブ）

- GitHub リポジトリをインタラクティブなビジュアルマップ（知識グラフ）に変換。Graph RAG エージェント内蔵。
- バックエンドインフラ不要のサーバーレス設計（ブラウザベース）。

**Code-Graph-RAG**（OSS / Web: code-graph-rag.com）

- tree-sitter ベース AST 解析で 12 言語のグラフスキーマ（関数・クラス・モジュール・依存関係）を統一。
- ベクトル検索（意味的類似性）＋グラフ走査（依存関係）を組み合わせる Graph-Augmented RAG。

#### 評価サマリー

| 観点 | 評価 |
|---|---|
| 精度（コードリバース向け） | 最高水準。関数・モジュール間の依存関係を構造的に解析できる。設計書リバースに最も適した手法。 |
| 実装コスト | 中〜高。グラフ構築・維持のオーバーヘッドあり。ただし isink17/codegraph・Codebase-Memory はシングルバイナリで比較的低コスト。 |
| Windows 対応 | isink17/codegraph・Codebase-Memory は明示的に Windows 対応。 |
| トークン消費 | 非常に低。構造クエリは必要情報のみ返せるためトークン消費を最小化できる。 |

### 2.3 シンボル検索系

#### 概要

LSP（Language Server Protocol）やコードインデックスエンジンを使い、関数名・クラス名・変数名などのシンボルをキーワードで正確に検索する手法。「go to definition」「find all references」のような IDE 機能をプログラム的に利用する形態。

#### 代表ツール・手法

**LSPRAG**（研究・参照実装 / 論文: arxiv 2510.22210）

- LSP バックエンドを活用してシンボル定義・参照をリアルタイム取得し LLM にコンテキストとして供給。
- 精度: Golang で行カバレッジ 174.55% 向上、Java で 213.31% 向上、Python で 31.57% 向上（ユニットテスト生成タスク）。
- LSP サーバーは言語別に用意する必要あり（TypeScript: tsserver、Python: pylsp、Go: gopls など）。

**GrepRAG**（研究手法 / 論文: arxiv 2601.23254）

- grep によるシンボル・識別子の正確な文字列マッチングを RAG の取得ステップとして利用。
- 精度: Python の exact match 38.61%（Vanilla RAG: 24.99% より 54% 高い）、Java の exact match 41.70%。
- CrossCodeEval で最良ベースライン比 7.04〜15.58% 相対改善。
- 平均取得レイテンシ 0.02秒未満。

**SeaGOAT**（OSS / MIT / GitHub: kantord/SeaGOAT）

- ChromaDB（ベクトル DB）+ ripgrep（キーワード検索）のハイブリッドローカルコード検索エンジン。
- 完全ローカル・サーバー常駐型。APIキー不要。リポジトリを git の履歴も含めてインデックス。
- macOS/Linux 中心の設計だが Python ベースのため Windows でも動作可能性あり（要確認）。

**mcp-ripgrep**（OSS / GitHub: mcollina/mcp-ripgrep）

- ripgrep（rg）を MCP ツールとして公開するシンプルな MCP サーバー。
- ripgrep は Windows バイナリも公式提供。キーワード検索・正規表現検索。

**mcp-ragex**（OSS / GitHub: jbenshetler/mcp-ragex）

- ripgrep（正規表現）+ tree-sitter（シンボル）+ ベクトル埋め込み（意味検索）の3モード検索 MCP サーバー。Claude Code 向け設計。

#### 評価サマリー

| 観点 | 評価 |
|---|---|
| 精度（コードリバース向け） | 高。シンボル定義・参照追跡はコードリバースで最も頻繁に必要な操作。 |
| 実装コスト | 低〜中。GrepRAG/ripgrep は即時利用可。LSP サーバーは言語別に設定が必要。 |
| Windows 対応 | ripgrep は Windows 公式バイナリあり。LSP サーバーは言語別（概ね Windows 対応）。 |
| トークン消費 | 低。シンボル単位の正確な取得でトークン消費が抑えられる。 |

### 2.4 通常埋め込み系

#### 概要

ソースコードをテキストとして扱い、汎用または専用の埋め込みモデルでベクトル化してベクトル DB に格納、コサイン類似度でクエリに近いチャンクを取得する手法。自然言語のドキュメント RAG と同じパイプラインをコードに適用する。

#### 代表ツール・手法

**汎用埋め込みモデル（コード対応）**

| モデル名 | ライセンス | 次元数 | コード精度 | 多言語 | 備考 |
|---|---|---|---|---|---|
| `nomic-ai/nomic-embed-code` | Apache 2.0 | 768 | 高（Python 81.7%、Java 80.5%） | 英語中心 | 2025 年最高水準のコード埋め込みモデル |
| `microsoft/UniXcoder-base` | MIT | 768 | 高（6 言語対応） | Python/Java/JS/PHP/Ruby/Go | コード+自然言語のクロスモーダル埋め込み |
| `microsoft/CodeBERT-base` | MIT | 768 | 中〜高（6 言語対応） | Python/Java/JS/PHP/Ruby/Go | 2020 年発表。コード理解向け先行モデル |
| `voyage-code-3` | Commercial (有料) | - | 最高水準 | 多言語 | 参考（有料のため除外対象） |

**汎用多言語埋め込みモデル（コードも対応可）**

- `BAAI/bge-m3`（MIT）、`intfloat/multilingual-e5-large`（MIT）: 自然言語主体だが英語コードの埋め込みは一定の精度で動作。日本語ドキュメント混在コーパスには有効。

**代表的パイプライン実装例**

- `n-irei/local-rag-mcp-server`（サブタスク08 調査済み）: ChromaDB + Ollama nomic-embed-text。コード以外のドキュメント向けだが基本構成として参考になる。
- LanceDB + tree-sitter AST チャンキング（lancedb.com ブログ「Building RAG on codebases」）。

#### コード向けベクトル埋め込みの限界

- コードは自然言語と異なり依存関係・型情報・実行順序といった「グラフ的構造」を持つ。ベクトル類似度のみでは意味的依存関係を捉えきれない。
- 関数名・変数名などの固有識別子はベクトル空間で「近い」とは限らない（`getUserById` と `fetchUserData` はセマンティックに近いが全く異なる）。
- ベクトル RAG は「沈黙した失敗（silent failure）」を引き起こしやすい: 間違ったチャンクを返しても LLM が誤った推論を黙って続けるリスク。

#### 評価サマリー

| 観点 | 評価 |
|---|---|
| 精度（コードリバース向け） | 中。意味検索は有効だが、シンボル定義・依存関係の正確な追跡は不向き。 |
| 実装コスト | 低。ドキュメント RAG と同一パイプラインを流用可能。 |
| Windows 対応 | 問題なし。Python + HuggingFace Transformers で即時利用可。 |
| トークン消費 | 中〜高。類似チャンクを複数取得するため、精度が低いと無関係チャンクが混入しトークン無駄遣いになる。 |

## 3. Filesystem Exploration（grep/glob）との比較表

対照群として、Claude Code がデフォルトで使用する Filesystem Exploration（grep/glob/read_file）との比較を行う。

| 比較軸 | Filesystem Exploration (grep/glob) | AST解析系 | コードグラフ系 | シンボル検索系 | 通常埋め込み系 |
|---|---|---|---|---|---|
| **精度（コードリバース）** | 中。正確な文字列マッチは得意だが、構造的関係は追えない。 | 高。構文境界を維持したチャンクで構造を把握できる。 | 最高。依存関係・コールグラフを直接クエリ可能。 | 高。シンボル定義・参照の正確な取得が可能。 | 中。意味的類似検索は有効だが固有識別子は不得手。 |
| **速度** | 最高（ripgrep: p50 <0.02s）。インデックス不要。 | 中（インデックス構築後は高速）。 | 中（グラフ構築後は高速。初回インデックスに時間）。 | 高（grep ベースは ripgrep 同等。LSP は起動後高速）。 | 中（インデックス構築後は高速）。 |
| **実装コスト** | 最低。追加ツール不要。Claude Code 組み込み。 | 低〜中。tree-sitter Python バインディング。 | 中。codegraph/Codebase-Memory は単一バイナリで簡単。 | 低〜中。ripgrep は即時利用。LSP は言語別設定要。 | 低。既存ドキュメント RAG パイプラインを流用可。 |
| **メンテナンス性** | 最高。インデックス更新不要。コード変更に即対応。 | 中。ファイル変更時に再インデックス（多くはウォッチャー対応）。 | 中。ファイルウォッチャーによる自動更新あり（Codebase-Memory など）。 | 中〜高。ripgrep はインデックス不要。LSP サーバーは起動管理が必要。 | 中。埋め込み更新コストあり。モデル変更時は全再構築。 |
| **適用規模** | 小〜中（大規模は token 消費が急増）。 | 中〜大。 | 中〜大（設計上大規模リポジトリを想定）。 | 小〜大（ripgrep は大規模でも高速）。 | 中（大規模ほどインデックス構築コスト増）。 |
| **トークン消費（Claude Code）** | 高。ファイル全文読取でトークン消費が線形増加。 | 低〜中。構文単位チャンク取得でトークンを節約。 | 最低。グラフクエリで必要シンボルのみ取得（Codebase-Memory: file-explorer の 1/10）。 | 低。シンボル定義のみ取得で無関係コードを含まない。 | 中。関連チャンク Top-N 取得。チャンク品質次第でトークン増減。 |
| **依存関係把握** | 不可。grep は文字列を返すのみ。 | 限定的。チャンク内の構造は把握できるが、ファイル間依存は追えない。 | 最高。依存グラフを直接クエリ可能。 | 中。「どこから呼ばれているか」はシンボル検索で把握可。 | 不可。ベクトル類似度は依存関係を反映しない。 |
| **コードリバース適合性** | 低〜中。全ファイル探索で時間・トークンを消費するが確実。 | 中〜高。モジュール・クラス単位の構造を保持した検索が可能。 | 最高。アーキテクチャ・依存関係を直接ナビゲート可能。 | 高。定義追跡・参照探索はコードリバースの主要操作。 | 中。概念的な類似検索は有効だが構造的正確さは低い。 |

**補足**: 「Filesystem Exploration のトークン消費が高い」理由については MindStudio の調査が端的に示している。Claude Code が grep を使う場合、大量の一致行（無関係なコメント・テストコード・定数定義など）をコンテキストに取り込んでしまう。一方でベクトル RAG の「沈黙した失敗」と比較すると、grep の冗長さは失敗を明示的に見えやすくするという利点もある。

## 4. H1（grep/glob派 vs ベクトル派）への示唆

### 前提：2026 年時点の研究・実務のコンセンサス

2026 年時点で、主要な AI コーディングエージェント（Claude Code・Cursor・Devin）が grep ベースのファイル探索を採用していることが多数の文献で確認されている。ただしこれはベクトル RAG の否定ではなく、「用途に応じた選択の結果」として解釈するのが正確である。

- **GrepRAG 論文（2026-01）**: grep ベースの検索は Python exact match 38.61%（Vanilla RAG: 24.99% を 54% 上回る）、取得レイテンシ 0.02 秒未満を達成。
- **LlamaIndex 2026 ベンチマーク**: Django コードベースで vector search 約 60% vs agentic search（grep/find/cat）約 68% の精度。ただし vector search はトークン消費が顕著に多い。
- **Codebase-Memory 論文（2026-03）**: コードグラフ系は file-explorer（grep/glob ベース）比でトークン 1/10、ツール呼び出し 2.1 倍削減、回答品質 83%（file-explorer: 92%）。

### 本プロジェクトへの示唆

| 問い | 答え |
|---|---|
| **grep/glob のみで十分か？** | 否。小規模コードベースや軽微な調査には十分だが、本プロジェクトのゴール「大量ファイルをトークン最小で扱う」には不向き。規模が増えるにつれてトークン消費が線形増加するため、スケールしない。 |
| **通常ベクトル RAG で十分か？** | 否。コードの固有識別子・依存関係はベクトル類似度では捉えにくく、「沈黙した失敗」リスクがある。コードリバースの主要操作（定義追跡・依存関係把握）に不向き。 |
| **最適な選択は？** | **コードグラフ系（AST + グラフ）＋ シンボル検索系（ripgrep）のハイブリッド構成**。構造的クエリはグラフ系が担い、識別子の正確なマッチングは ripgrep が補完する。通常埋め込みは自然言語クエリへの補完として加えるオプション。 |
| **H1 への直接回答** | コード特化の文脈では「grep/glob 派」が単純ベクトル派に精度・トークン効率で優位。ただし**グラフ系 + シンボル検索の組み合わせが両者を凌駕する**。H1 は「grep/glob 派 vs ベクトル派」の二択ではなく、**「コードグラフ + シンボル検索（AST・グラフ・grep を統合したコード特化構成）vs 汎用ベクトル RAG」**が正しい対立軸である。 |

## 5. 採用候補の整理

### 5.1 採用候補（根拠付き）

#### 第1候補: Codebase-Memory MCP（DeusData/codebase-memory-mcp）

- **根拠**: tree-sitter 66 言語対応のコードグラフ系ツール。14 MCP ツールで Claude Code に直接統合可能。file-explorer 比でトークン 1/10 削減という実証済みの効果は、本プロジェクトの最重要ゴール（コンテキスト消費最小化）に直接合致する。Windows 対応明記。OSS（MIT）。シングルバイナリで外部 DB 不要。ファイルウォッチャーによる自動更新あり。
- **注意点**: 回答品質 83%（file-explorer: 92%）という 9 ポイントの品質差があるため、高精度が必要なクエリには file-explorer との併用が望ましい。

#### 第2候補: isink17/codegraph

- **根拠**: コードグラフ系。29 MCP ツールで Claude Code 自動設定対応。Go シングルバイナリで Windows 11 対応確認済み。依存関係トレース・影響範囲分析・デッドコード検出等、コードリバースで有用な機能が豊富。サブタスク08 でも採用候補度「高」と評価済み。
- **注意点**: ライセンスが FSL-1.1-MIT（2 年後 MIT 転換）。商用利用時は要確認。

#### 第3候補: mcp-ripgrep / mcp-ragex（シンボル検索補完層として）

- **根拠**: シンボル検索系。ripgrep は Windows 公式バイナリ提供。GrepRAG 研究が示す通り、コード識別子の正確なマッチングでベクトル RAG を上回る精度。Codebase-Memory や codegraph との補完関係にある。
- **注意点**: 単体では意味検索なし。グラフ系ツールと組み合わせる前提。

#### 第4候補: cAST / astchunk（AST チャンキングライブラリとして）

- **根拠**: AST 解析系。コードに埋め込みを適用する場合のチャンク品質を大幅に向上させる。EMNLP 2025 で実証済み。Python OSS（MIT）で Windows で即時利用可。
- **利用場面**: 通常埋め込み系と組み合わせてコード向け RAG のチャンク品質を底上げする場合に採用。単独では意味検索不可。

## 6. 課題・制約

### 将来解決が必要な課題

- **Codebase-Memory MCP の品質差（9 ポイント）の実態確認**: 論文評価は汎用的なリポジトリ群での結果。コードリバース（ソースから設計書生成）という本プロジェクト固有のユースケースでの精度差は別途フィジビリティ検証で確認が必要。
- **isink17/codegraph の Go 1.26+ 要件確認**: 2026-05-03 時点での Go 安定版は 1.24.x。1.26 のインストール要否を確認。
- **SeaGOAT の Windows 11 動作確認**: Linux/macOS 中心設計のため、Windows での実動作確認が必要。
- **cAST + ベクトル埋め込みの組み合わせ効果の実測**: AST チャンキング + nomic-embed-code / UniXcoder の組み合わせ精度をコードリバースタスクで検証。
- **コードグラフ系とベクトル系のハイブリッド構成の設計**: Codebase-Memory（構造クエリ）+ ベクトル検索（意味クエリ）を組み合わせたパイプラインの実装方針を設計フェーズで確立。

### 解決不能な課題

- **ベクトル埋め込みによるコード構造の捕捉限界**: ベクトル類似度は本質的に「文書の意味的近似」であり、コードのグラフ的依存構造（呼び出し関係・型参照・継承関係）を表現できない。グラフ系ツールとの組み合わせが必然。
- **Filesystem Exploration の根本的スケーリング問題**: grep/glob は大規模コードベースでトークン消費が線形増加する。コードグラフ系に切り替えても「グラフに存在しない知識（自由形式のコメント等）」は grep に頼らざるを得ない。

### 解決不要な課題

- **Sourcegraph のライセンス問題**: OSS 代替（SeaGOAT / Hound / OpenGrok）または MCP ツール（mcp-ripgrep / Codebase-Memory）で機能的に代替可能。
- **isink17/codegraph のライセンス（FSL-1.1-MIT）**: 本プロジェクトは調査・社内利用の範囲であり、FSL-1.1-MIT の商用制限に抵触しない可能性が高い。最終採用時に法務確認で対処可能。
- **通常埋め込み系の多言語精度（日本語コード）**: コードのシンボル・識別子は英語が中心であり、日本語埋め込みモデルへの強い要求は発生しない。コードリバース成果物（日本語設計書）はクエリ側の問題であり、インデックス側には影響しない。

## 7. ハマりどころ追記候補

以下は本調査で発見したハマりどころとして、`ハマりどころ.md` への追記を推奨する項目。

1. **コードに対するベクトル埋め込みの「沈黙した失敗」**
   - 関数定義・型参照・依存関係はベクトル類似度で正確に捉えられない。間違ったチャンクが返されても LLM が誤った推論を続けるリスクがある。コード向けには AST チャンキングや構造クエリとの組み合わせが必須。

2. **Codebase-Memory MCP の Go 1.26+ 要件**
   - `codebase-memory-mcp` は Go 1.26+ が必要。2026-05-03 時点の Go 安定版は 1.24.x 系のため、インストール時に最新 Go バージョンを確認する。

3. **isink17/codegraph の Go 1.26+ 要件**（再掲・サブタスク08 6.5 と同内容）
   - サブタスク08 で既に指摘済み。コードグラフ系 Go ツールに共通する注意点として確認。

4. **AST チャンキングとチャンクサイズの相互作用**
   - AST チャンキングは構文境界を守るため、大きな関数・クラスは 1 チャンクサイズ制限を超えることがある。cAST は「大ノードを再帰的に分割」するが、チャンク最大サイズを小さく設定しすぎると構文整合性とのトレードオフが生じる。チャンクサイズはサブタスク04（チャンク分割・インデックス手法）との整合が必要。

5. **ripgrep の Windows パス区切り**
   - ripgrep（rg）は Windows でもスラッシュ（`/`）区切りのパスを受け付けるが、MCP サーバー経由でパスを渡す場合にバックスラッシュとスラッシュの混在に注意。FastMCP や Go 実装の MCP サーバーはパス正規化を実装していないことがある。
