## 1. 調査概要

本サブタスクでは、ローカルRAGシステムをClaude Codeから呼び出す際の連携方式として以下の3形態を比較・整理した。

1. **Skills（CLI都度起動型）**: スキル実行時に毎回プロセスを起動してRAGを呼び出す
2. **Skills（常駐HTTPサーバー型）**: バックグラウンドでHTTPサーバーを常駐させ、スキルからHTTPで呼び出す
3. **MCPサーバー型**: MCPプロトコルに準拠したサーバーを常駐させ、Claude Codeがツールとして自動呼び出す

比較軸は「応答速度・実装コスト・運用形態・Claude Codeとの統合難易度・推奨ユースケース」とした。

調査に際しては、参考記事5本のWebFetch読み込みとWebSearchによる補足情報収集を実施した。

## 2. 各連携方式の特徴

### 2.1 Skills（CLI都度起動型）

**概要**

`.claude/skills/<skill-name>/SKILL.md` にコマンド定義を記述し、Claude Codeが `/skill-name` スラッシュコマンドを呼び出すとCLIプロセスが都度起動する方式。`uv run --with duckdb python rag_ask.py` のように実行する形が典型的。

**応答速度**

- 埋め込みモデルの初回ロードに **約8〜9秒**（モデルロード約8秒 + DB操作約1秒）
- セッション中に複数回呼び出すと毎回このオーバーヘッドが発生する
- 検索自体のレイテンシは数十ms程度（HNSWインデックス等使用時は「数万チャンクでもミリ秒」）

**実装コスト**

- 最も低い。`uv sync` だけでセットアップ完了
- SKILL.md の記述と Pythonスクリプト数本で完結
- DBはSQLiteやDuckDBなど単一ファイルで管理でき、Dockerや外部サービス不要
- 環境汚染がなく、`uv run --with` による依存管理が可能

**運用形態**

- 常駐プロセスなし。呼び出し時のみ起動・終了
- `.duckdb` / `.sqlite` ファイルをそのまま管理。洗い替え・再構築が容易
- Windows環境でもsystemdレスで動作

**ユースケース**

- 呼び出し頻度が低い（1セッションで1〜2回程度）場面
- プロトタイプ・初期検証フェーズ
- 応答速度よりも構築の簡便さを優先する場合
- インデックス作成（`/rag-index`）のような一度きりの処理

---

### 2.2 Skills（常駐HTTPサーバー型）

**概要**

RAGバックエンドをHTTPサーバー（FastAPIなど）として常駐させ、SKILL.mdのコマンドからHTTPリクエストで呼び出す方式。モデルはサーバー起動時にメモリへロード済み。

**応答速度**

- **約0.1秒**（モデルロード済みのため）
- CLIプロセス起動オーバーヘッドがなく、ネットワークラウンドトリップもローカルループバックで無視できる
- セッション中の繰り返し呼び出しでも速度が劣化しない
- モデルロード済みかつローカル実行のため、クエリレイテンシは50ms未満が期待できる

**実装コスト**

- 中程度。HTTPサーバーのコード（FastAPI等）が追加で必要
- 常駐プロセス管理のためのsystemdユーザーサービス設定が必要（Windows環境ではWindowsサービスまたはスタートアップタスク相当）
- CLI都度起動型に比べ起動シーケンスと管理が複雑化
- シンボリックリンク設定が必要になるケースあり（複数エージェント間共有時）

**運用形態**

- バックグラウンドプロセスを常駐させる必要がある
- OS起動時の自動起動設定が推奨
- サーバーのクラッシュ・再起動管理が必要
- エンドポイント (`localhost:PORT`) の管理が発生

**ユースケース**

- セッション中に複数回RAGを呼び出す場面（AIエージェントが繰り返し検索する場合）
- 応答速度が体験品質に影響する対話的なワークフロー
- 仕様書解析・コードリバース等の反復的な調査タスク
- 複数のSkillsコマンドから同一RAGバックエンドを共有する場合

---

### 2.3 MCPサーバー型

**概要**

MCPプロトコル（JSON-RPC over stdio または Streamable HTTP）に準拠したサーバーを構築し、`~/.claude/mcp.json` や `.mcp.json` に登録する方式。Claude Codeがセッション開始時にサーバーを起動し、ツールとして自動的に呼び出す。

**応答速度**

- Claude Codeとの通信はstdioまたはローカルHTTP経由のため実質的な通信レイテンシはなし
- 初回クエリ時はモデルロードにより数秒〜数十秒の遅延が発生しうる（常駐型の場合はセッション開始時に吸収）
- 2回目以降はモデルがロード済みのため高速
- 大量ドキュメントのインデックス化は「数分〜数十分」かかる場合がある

**実装コスト**

- 既製MCPサーバーを利用する場合: 低〜中（設定ファイル数行 + `npx` / `uv run` コマンド）
- 自作する場合: 高（MCPプロトコル対応が必要、LangChain等依存ライブラリの追加）
- 既製の選択肢が豊富（`mcp-local-rag`、`mcp-rag-server`、`zotero-local-rag` 等）
- PostgreSQL + pgvector + Docker を要求するサーバーは運用コストが大きい
- 軽量構成（SQLite + 小型埋め込みモデル + stdio transport）なら設定のみで完結

**運用形態**

- Claude Codeセッション開始時に自動起動・終了（stdio transport の場合）
- 常駐管理がClaude Code側に委譲されるため、ユーザー側の運用負担が小さい
- ツール発見が自動的で、Claude側への明示的な指示が不要
- トークン消費: MCP登録ツールが多いほどコンテキストを消費（5サーバー58ツールで約55,000トークン）、Tool Search機能で85%削減可能

**ユースケース**

- Claude Codeが自律的に判断してRAGを呼び出す必要がある場面
- 自然言語での指示だけでRAG連携を透過的に行いたい場合
- 複数のMCPツールを組み合わせるアーキテクチャ（例: 検索 + 書誌情報取得の連携）
- 既製MCPサーバーを活用して実装コストを抑えたい場合

## 4. 参考記事からの知見まとめ

### 記事1: DuckDBでローカルRAGを作ってClaude Codeから使う（sasadango28）

Skills（CLI都度起動型）の具体実装例。`/rag-index` と `/rag-ask` の2スキル構成で、`uv run --with duckdb` で環境汚染なしに実行。DuckDB + HNSWインデックスで数万チャンクでもミリ秒検索を実現。埋め込みモデルはデフォルトで `multilingual-e5-small`（384次元）、日本語特化なら `ruri-v3-30m` を推奨。

**本調査への示唆**: CLI都度起動型でも検索自体は高速。問題は毎回の「モデルロード時間」であり、これは常駐化（HTTP型/MCP型）で解決できる。

### 記事2: qmd MCPサーバーによるObsidian高速検索（tumf）

MCPサーバー型の具体実装例。`qmd mcp` コマンド一つでMCPサーバーとして起動し、`.mcp.json` 設定だけでClaude Codeと連携。自然言語での指示だけで自動呼び出しが実現。初回検索は遅いが2回目以降は高速化。

**本調査への示唆**: MCPサーバー型はClaude Codeとの統合が最も透過的。設定コストが低い反面、初回レイテンシへの対処（事前インデックス化等）が必要。

### 記事3: Skillsで実現する軽量パーソナルRAG（karaage0703）

**本調査の中核資料**。CLI都度起動型（約9秒）と常駐HTTPサーバー型（約0.1秒）の数値比較が明示されている唯一の記事。著者が「AIエージェントが複数回検索するケースでは待ち時間の影響が大きい」と指摘。MCPサーバー版（前作）はPostgreSQL + pgvector + Docker必須で重厚だったが、Skills版はSQLite + 軽量モデルで大幅にシンプル化。

**本調査への示唆**: 8〜9秒のCLI起動コストは確認された既知事実。常駐HTTP型は約90倍の高速化を実現。MCPは機能的に等価だが運用重量度が高い傾向あり。

### 記事4: ローカルRAGを手軽に構築できるMCPサーバ（mkj）

MCPサーバー型の実装例。PostgreSQL + pgvector を使用するが外部APIは不要な完全ローカル構成。差分インデックス化（新規・変更ファイルのみ処理）でインデックス更新を効率化。LangChainに依存しない設計で安定性を確保。

**本調査への示唆**: MCPサーバー型でも設計次第で外部サービス依存を排除できる。差分インデックス化は運用コスト削減に有効。

### 記事5: LLM経由でZotero内の資料を全文検索する（knag）

MCPサーバー型の応用例（学術文献検索）。`zotero-local-rag` + `zotero-mcp` を組み合わせた複合MCP構成。日本語文献は埋め込みモデルの選定が精度に大きく影響（Qwen2.5-7Bより Llama-3.1-Swallow-8B-Instructが大幅改善）。Claude ProプランまたはLM Studio（ローカルLLM）のどちらでも動作。

**本調査への示唆**: 複数MCPサーバーの連携は強力だが設計コストが上がる。日本語対応には埋め込みモデルの選定が重要（本調査の別サブタスクにも関連）。

## 5. 本ユースケースへの推奨方式

本調査の目的である「仕様書要約・脆弱性分析・コードリバースのためのローカルRAG」に対して、各ユースケース別の推奨を整理する。

### 5.1 初期検証・プロトタイピングフェーズ

**推奨: Skills（CLI都度起動型）**

実装コストが最も低く、RAGが機能するかを確認するのに適している。モデルロード8〜9秒の遅延は許容可能（1回呼ぶだけなら実害なし）。まずCLI型で動作確認し、頻度要件に応じて常駐型へ移行するという段階的アプローチが現実的。

### 5.2 仕様書要約ユースケース

**推奨: Skills（常駐HTTPサーバー型）またはMCPサーバー型**

仕様書要約は大量テキストを扱い、関連箇所を複数回検索することが多い。1セッションで5〜10回程度のRAG呼び出しが想定されるため、毎回8〜9秒かかるCLI都度起動型は非実用的。常駐型が必須。

- 既製MCPサーバー（`mcp-local-rag` 等）が使える場合はMCPサーバー型が設定コスト低
- 自作構成ならHTTP常駐型（実装制御がしやすい）

### 5.3 脆弱性分析ユースケース

**推奨: MCPサーバー型**

脆弱性パターンのナレッジベースをMCPツールとして公開し、Claude Codeが自律的にRAG検索を呼び出す設計が適している。「このコードに既知の脆弱性パターンが含まれるか確認して」という自然言語指示だけで透過的に動作することが重要。自動呼び出しができるMCPサーバー型が最適。

### 5.4 コードリバースユースケース

**推奨: Skills（常駐HTTPサーバー型）**

コードリバースでは同一セッション中に短時間で多数の検索（関連コード・ライブラリ仕様の確認）が発生する。高頻度・低レイテンシ要件に対しては常駐HTTPサーバー型が最適。スラッシュコマンドで明示的に呼び出す形（`/rag-search <クエリ>`）でもユーザー制御が効きやすい。

### 5.5 統合推奨構成

本ユースケース全体の最終推奨は「**MCPサーバー型（常駐・stdio transport）+ 軽量SQLite/DuckDB構成**」。

根拠:
- Claude Codeへの統合がCLI型と同等またはそれ以下の設定コスト
- 常駐型のため毎回のモデルロードコストを排除
- 自動呼び出しにより「RAGを呼ぶ」という操作をエージェントに委譲でき、作業指示者は目的に集中できる
- 既製MCPサーバー（`mcp-local-rag`等）が豊富でOSS・商用利用無料の条件を満たす
- MCPサーバー型でもSQLite + 小型モデル構成なら運用重量度を抑えられる

## 6. 既知ハマりどころとの照合

### CLI起動8〜9秒遅延問題

**確認**: karaage0703の記事で実測値として「モデルロード約8秒 + DB操作約1秒」が報告されており、既知情報と一致。

**対応方針**:
- 常駐HTTPサーバー型: セッション開始時にモデルをロードしておくことで、2回目以降の呼び出しを約0.1秒に短縮
- MCPサーバー型（stdio transport）: Claude Codeセッション開始時にサーバープロセスが起動し、その時点でモデルロードが発生。最初のツール呼び出しは遅いが、セッション中の後続呼び出しは高速
- MCPサーバー型（常駐型）: OSと同時に起動しておけばClaude Code起動時には既にモデルロード済み

**実用的な対処**: Windows環境では、MCPサーバーをWindowsスタートアップに登録し常駐させるか、`.mcp.json` 設定でClaude Code起動時に自動起動させることで初回レイテンシを吸収できる。

## 8. 課題・制約

### 将来解決が必要な課題

- **Windows環境でのサービス常駐化**: Linuxのsystemdユーザーサービスと異なり、Windows環境での常駐プロセス管理（タスクスケジューラ / WinSW 等）の具体的な設定方法を別途検証が必要
- **MCPトークン消費の定量評価**: MCP登録時のツール定義トークン消費（約55,000トークン/5サーバー）が本ユースケースのコスト要件に与える影響の評価が必要
- **初回モデルロードの計測**: 採用候補の埋め込みモデル（multilingual-e5-small, ruri-v3-30m 等）ごとの実測ロード時間の計測（別サブタスクとの連携）

### 解決不能な課題

- **MCPの仕様変更リスク**: MCPは2025-03-26以降Streamable HTTPが標準となったが、プロトコル仕様の継続的変更が予測される。本調査時点（2026-05）の知見がそのまま恒久的に適用できない可能性がある

### 解決不要な課題（参考情報）

- **外部APIへのネットワーク依存**: Skills・MCP双方ともローカル埋め込みモデルを使用すれば外部API依存を排除可能。これは本調査のOSS・商用利用無料要件と完全に一致しており、追加対応不要
- **複数エージェント間のRAG共有**: 常駐HTTPサーバー型やMCP型では同一エンドポイントを複数セッションから利用可能。本ユースケースでは基本的に単一セッション利用のため優先度低

## 9. ハマりどころ追記候補

調査を通じて新たに発見したハマりどころを記録する。

1. **MCPトークン消費の見落とし**: MCPサーバーを複数登録すると、ツール定義がコンテキストに加算される（5サーバー/58ツールで約55,000トークン）。RAG専用MCPサーバー1つに絞った場合でも、ツール定義の記述量次第で数百〜数千トークンが消費される。Claude Code Docs のTool Search機能を活用することで最大85%削減可能。

2. **MCPサーバーのstdio vs HTTP transport の選択**: stdio transportは Claude Code が自動起動・終了を管理するため運用が簡単。Streamable HTTP transportはサーバーレス環境への展開が可能だが、Windows環境での常駐プロセス管理が別途必要。ローカル単独利用ならstdio一択。

3. **埋め込みモデルの一貫性**: インデックス作成時と検索時で異なるモデルを使うとベクトル空間が一致せず検索精度が激減する。メタデータテーブルにモデル名を保持して一貫性を強制する仕組みが必要。

4. **e5系モデルのプレフィックス要件**: `intfloat/multilingual-e5-*` 系のモデルでは、インデックス時は `passage:` プレフィックス、検索時は `query:` プレフィックスを付けなければ検索精度が大幅低下する。実装時の見落とし頻度が高い。
