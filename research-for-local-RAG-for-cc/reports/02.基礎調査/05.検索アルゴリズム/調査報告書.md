## 1. 調査概要

本調査では、ローカルRAGシステム向けの検索アルゴリズムを「純粋ベクトル検索」「BM25（キーワード検索）」「ハイブリッド検索」「リランキング」の4軸で比較し、精度・遅延・構築複雑度の観点から整理した。また、ローカル動作可能なOSSリランカーモデル候補を特定し、選定指針を示した。

**調査対象環境の前提**:
- 対象データ: 日本語・英語混在、コード・Markdown・仕様書
- 実行環境: Windows 11、商用利用無料OSSのみ
- RAGの文脈: Claude Code が大量ファイルを扱う際の最小トークン・コンテキスト作業支援

## 2. 検索アルゴリズム比較

### 2.1 純粋ベクトル検索

**概要**:
クエリとドキュメントをそれぞれ埋め込みモデルでベクトル化し、コサイン類似度またはユークリッド距離でランキングする方式。

**特性**:
- 意味的（セマンティック）な類似性を捉える。言い換えや同義語に強い。
- 日本語・英語混在コーパスでも多言語埋め込みモデルを使えば言語をまたいだ検索が可能。
- recall@10 は単体で約 78%（業界ベンチマーク平均）。
- インデックス構築後の検索は高速（ANN/HNSW 等の近似最近傍探索で O(log n) 相当）。
- 固有名詞・製品コード・APIシンボルなど字面が重要な語の取りこぼしが発生しやすい。

**代表的実装**:
- ChromaDB、Qdrant、Milvus Lite（いずれも OSS）
- 埋め込みモデル: `text-embedding-3-small`（OpenAI）、`multilingual-e5-large`（OSS）等

### 2.2 BM25（キーワード検索）

**概要**:
TF-IDF の改良版であるBM25（Best Match 25）は、語の出現頻度と逆文書頻度（IDF）を組み合わせてスコアリングする古典的な全文検索手法。

**特性**:
- 完全一致・部分一致クエリに強い。製品コード、法律用語、APIシンボル等の固有表現の検索精度が高い。
- recall@10 は単体で約 65%（業界ベンチマーク平均）。
- 計算コストが低く、インデックス更新も軽量。
- セマンティックな意味は捉えられない（「車」と「自動車」は別語扱い）。
- **日本語の制約**: BM25は空白区切りを前提とするため、日本語テキストは形態素解析が必須。
  - 標準的なBM25ライブラリ（`rank_bm25`等）をそのまま使うと単語境界が崩れ精度が大幅低下。
  - 対策: Sudachi（`sudachipy`）や MeCab による前処理トークナイズが必要。

**代表的実装**:
- `rank_bm25`（Python、OSS）
- Elasticsearch / OpenSearch の BM25 内蔵機能
- LangChain の `BM25Retriever`

### 2.3 ハイブリッド検索

**概要**:
ベクトル検索（セマンティック）と BM25（キーワード）を並列実行し、結果を融合する方式。代表的な融合アルゴリズムは Reciprocal Rank Fusion（RRF）。

**RRF の仕組み**:
各リトリーバーから返された文書に対してランク順位ベースのスコアを付与し合算する。
```
RRF_score(d) = Σ 1 / (k + rank(d))  （k=60 が標準値）
```
- スコアスケールのキャリブレーション不要（ランクのみ使用）。
- いずれかのリトリーバーにのみ現れた文書も低スコアで拾える。
- k=60 の定数によりどちらかのリトリーバーへの過剰依存を防ぐ。

**精度向上実績**:
- recall@10 が hybrid で約 91%（ベクトル単体 78%、BM25 単体 65% と比較）。
- 精度 (Precision) は ~0.68（BM25 単体）→ ~0.87（ハイブリッド）へ改善。
- 企業採用調査では 85% が「ハイブリッド採用後に検索精度が向上した」と回答。
- 追加レイテンシは p50 で約 +6ms（ベクトル単体比）。LLM 推論（500ms〜2s）に対して無視できる水準。

**日本語・コード混在への適合性**:
- BM25 側: Sudachi 等による形態素解析トークナイズで日本語精度を確保。
- ベクトル側: 多言語埋め込みモデルで意味検索を補完。
- コードシンボル（関数名・変数名）は BM25 が強く、コンテキスト理解はベクトルが補う。

### 2.4 ハイブリッド + リランキング

**概要**:
ハイブリッド検索で「recall（再現率）が高い上位N件」を取得した後、クロスエンコーダー型のリランカーで「precision（精度）」を高める 2 ステージ構成。

**推奨フロー**:
```
クエリ
  ↓
① ハイブリッド検索（BM25 + ベクトル + RRF） → 上位 50 件取得
  ↓
② クロスエンコーダー リランカー → 上位 5〜10 件に再整列
  ↓
③ LLM (Claude) へのコンテキスト投入
```

**精度向上効果**:
- リランキング追加により NDCG@5 が約 12〜18 ポイント向上（クエリが長く複雑なほど効果大）。
- 短いキーワードクエリは効果が限定的（ベクトル検索の精度がすでに高いため）。

**適用条件**:
- recall@50 が 90% 超を確保できていることが前提（リランカーは順序を変えるが件数を増やさない）。
- 候補数（N）の上限を設けることで推論コストを制御する（一般的には N=20〜100）。

## 3. 検索アルゴリズム比較表

| 手法 | 精度 (recall@10) | 遅延 (p50) | 構築複雑度 | 推奨ユースケース |
|---|---|---|---|---|
| 純粋ベクトル検索 | ★★★☆ 約78% | ★★★★ 低 | ★☆☆☆ 低 | 意味検索主体・英語中心・プロトタイプ |
| BM25 のみ | ★★☆☆ 約65% | ★★★★ 最低 | ★☆☆☆ 低 | 固有名詞・コード検索・小規模 |
| ハイブリッド（BM25+ベクトル+RRF） | ★★★★ 約91% | ★★★☆ 低〜中 | ★★☆☆ 中 | 日英混在・コード+仕様書・本番品質要求 |
| ハイブリッド + リランキング | ★★★★★ 最高 | ★★☆☆ 中〜高 | ★★★☆ 高 | 高精度要求・複雑クエリ・候補数が多い場合 |

**補足**:
- 遅延評価はLLM推論（500ms〜2s）を除くリトリーバル部のみ。
- 構築複雑度の「高」は BM25 インデックス＋ベクトル DB＋リランカーモデルの3コンポーネント管理を指す。
- 精度数値は BEIR / MSMARCO ベースの業界ベンチマーク参考値（コーパス・クエリ性質で変動する）。

## 5. 構築複雑度に対するメリット分析

### 構成別メリット/コスト

| 構成 | 構成要素 | メリットが出始める規模感 | 主なメリット | 主なコスト |
|---|---|---|---|---|
| ベクトル検索のみ | 埋め込みモデル + ベクトルDB | 〜1,000ファイル | 構築が最も簡単 | 固有名詞・コードシンボルの取りこぼし |
| BM25 + ベクトル（RRF） | 上記 + BM25インデックス | 500ファイル〜 | recall+13pt向上、追加遅延微小 | BM25インデックス管理、日本語形態素解析導入 |
| ハイブリッド + リランキング | 上記 + リランカーモデル | 2,000ファイル〜（※TBD3待ち） | precision大幅向上 | リランカーモデル常駐メモリ（300MB〜1GB）、追加推論遅延（50〜400ms） |

### 日本語・コード混在コーパスにおける判断基準

1. **ベクトル単体で十分なケース**: コーパスが英語中心、クエリが意味検索主体、許容精度が低め（プロトタイプ）。
2. **ハイブリッドを加えるべきケース**: 日本語が含まれる、コードシンボルや固有表現の検索が重要、本番品質が必要（recall 90%超を目標とするとき）。ハイブリッド化のコストはほぼ「BM25インデックス追加」だけで追加遅延は無視できる（+6ms程度）。
3. **リランキングまで加えるべきケース**: 上位N件の中に不要チャンクが多く入り込みトークン無駄遣いが顕著、LLMへの入力チャンク数を削減したい（入力コンテキスト最小化が特に本プロジェクトのゴールに合致）、複雑な自然言語クエリが多い。

### 本プロジェクト（Claude Code ローカルRAG）向けの暫定判断

- **ハイブリッド（BM25+ベクトル+RRF）は採用を強く推奨**: コード・Markdownファイルはキーワード一致が重要。追加コストに対して recall 向上幅が大きい。
- **リランキングは有力候補だが規模次第**: Claude Codeのコンテキスト最小化という目的に直結するため有力だが、リランカー常駐メモリ・推論遅延のコストが受容可能かはコーパス規模（ファイル数・総チャンク数）に依存。TBD3の結果を待って最終判断。

## 6. TBD3（規模感）依存部分の仮分析

以下の判断は、サブタスク01 TBD3（対象コーパスの規模感：ファイル数・総チャンク数・クエリ頻度）が確定した後に精緻化が必要。

| 判断項目 | 現在の仮定 | TBD3 確定後に見直すこと |
|---|---|---|
| リランキング導入の閾値ファイル数 | 約2,000ファイル〜でメリットが出始めると仮定 | 実際のチャンク数・クエリ複雑度で調整 |
| リランカー候補数（N） | 上位20〜50件を暫定値として設定 | コーパス規模・許容遅延に応じてチューニング |
| CPU vs GPU | CPUのみを前提（Windows 11 ローカル） | GPU（CUDA）が利用可能な場合は遅延数値が大幅改善、モデル選択余地が広がる |
| 常駐メモリ許容量 | 300MB〜1GBを目安 | ホストマシンのRAM・CCワーカープロセス数で変動 |
| BM25 日本語トークナイザー選択 | Sudachi（`sudachipy`）を第一候補 | 実際の日本語テキスト品質・固有表現頻度で MeCab との比較検証が必要 |

## 7. 採用候補の整理

### 推奨構成（優先度順）

#### 第1候補: ハイブリッド検索（BM25+ベクトル+RRF）＋ クロスエンコーダー リランキング

| コンポーネント | 採用候補 | 理由 |
|---|---|---|
| ベクトル検索 | ChromaDB または Qdrant（ローカル） | OSS・軽量・Python統合が容易 |
| 埋め込みモデル | `multilingual-e5-large` または `bge-m3` | 多言語対応・OSS・商用利用可 |
| BM25 | `rank_bm25` + `sudachipy` | Python OSS・日本語形態素解析統合 |
| スコア融合 | RRF（k=60） | パラメータ調整不要・ロバスト |
| リランカー | `bge-reranker-v2-m3` | 多言語（日本語含む）・MIT・278M・CPUで動作可 |

#### 第2候補: ハイブリッド検索のみ（リランキングなし・スモールスタート）

リランカー常駐メモリ・推論遅延が受容不能な場合、またはコーパスが比較的小規模の場合。BM25+ベクトル+RRF だけで recall@10 約91% を確保可能。

#### 英語コード主体の場合の代替リランカー

`cross-encoder/ms-marco-MiniLM-L-6-v2`（Apache 2.0、33.4M、CPU 50〜100ms）。日本語には対応しないが遅延・モデルサイズが最小。

## 8. 課題・制約

### 将来解決が必要な課題

- **日本語BM25トークナイズの実装検証**: `sudachipy` と MeCab の精度・速度比較を実ファイルで検証する必要がある（理論的には Sudachi が推奨だが、コード混在時の挙動は未検証）。
- **リランカー常駐メモリの実測**: `bge-reranker-v2-m3`（278M）の Windows 11 CPU ランタイム上でのメモリフットプリントを実測し、CCワーカープロセスとの競合を確認。
- **候補数（N）の最適値チューニング**: recall@N が飽和するポイントはコーパス特性に依存。TBD3確定後に実コーパスで検証。

### 解決不能な課題

- **BM25 の意味理解限界**: BM25 は本質的に bag-of-words であり、同義語・言い換えへの対応は不可。ハイブリッド構成でカバーするのが現実的限界。
- **クロスエンコーダーの O(N) スケーリング**: リランキング対象文書数に対して線形に推論コストが増加するため、大規模コーパスで N を増やすと遅延が無制限に増加する（N=100 以内での運用が実用的上限）。

### 解決不要な課題（参考情報）

- Jina Reranker v2 は多言語・高精度だが CC-BY-NC-4.0 ライセンスのため本プロジェクト対象外。同等性能の `bge-reranker-v2-m3`（MIT）で代替可能なため、ライセンス問題は実質影響なし。
- GPU（CUDA）なしで動作するか: `bge-reranker-v2-m3` は CPU 動作可能（use_fp16=False 設定）。Windows 11 GPU なし環境でも機能する。ただし遅延は GPU 比で 3〜5 倍増。

## 9. ハマりどころ追記候補

- **BM25 + 日本語の落とし穴**: `rank_bm25` に日本語テキストをそのまま渡すと、文字単位分割になり精度が著しく低下する。`sudachipy` での前処理が必須。pip での追加インストール（`pip install "AutoRAG[ja]"` または `sudachipy` 単体）が必要。
- **RRF の k パラメータ**: k=60 はデフォルト推奨値。BM25 の精度がベクトル検索より大幅に低い場合、k を大きくすることでベクトル側を重視できるが、過度な調整は一般化性を失う。
- **クロスエンコーダーのバッチ処理**: 候補を 1 件ずつスコアリングすると遅延が線形増加する。必ずバッチ推論（FlagEmbedding / sentence-transformers の batch モード）を使うこと。
- **リランカーの入力長制限**: bge-reranker-v2-m3 のトークン長上限（512〜1024 トークン）を超えるチャンクはスコアリングが不正確になる。チャンキング設計（サブタスク03）との整合が必要。
- **Windows 11 での ONNX 高速化**: FlagEmbedding は `use_fp16=True` によりGPUでの高速化が可能だが、CPU環境では ONNX Runtime 経由の推論に切り替えると約 1.5〜2x 速度改善が見込める（要検証）。
