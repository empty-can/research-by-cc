## 1. 調査概要

本調査では、ローカルRAGシステム構築に向けて、主要なRAGパターン（CAG / Vector Search RAG / Filesystem Exploration RAG / Graph RAG / ハイブリッドRAG / Agentic RAG）それぞれの適用条件・限界・本プロジェクトのスコープ適合性を整理した。

**調査対象の代表ユースケース**:
- 仕様書要約（大量テキスト文書からのサマリー生成）
- 脆弱性差分分析（コード変更前後の差分から脆弱性を検出・分析）
- コードリバース（既存コードベースからの設計書リバースエンジニアリング）

**調査方法**: 前回実行済みの知見をベースに、参考記事（Zenn/Microsoft, 2024）および複数のWebSearch結果（2024–2025）で補足・検証した。

**解消したTBD**:
- TBD3（規模感）: 本報告書 §4 で解消
- CAG境界条件（H0への入力）: §5 で定量化
- Graph RAGのスコープ適合性（TBD2）: §6 で評価

## 2. RAGパターン一覧と適用条件

| パターン名 | 概要 | 主な適用条件 | 限界・制約 | 本調査スコープとの適合 |
|---|---|---|---|---|
| **CAG**（Context Augmented Generation） | コーパス全量をコンテキストウィンドウに事前ロードし、KVキャッシュで高速応答 | 50ファイル以下、50,000トークン以内、静的・安定データ | コンテキスト上限を超えると精度劣化、ノイズ増大；動的更新に不向き | 小規模静的コードベースに限定適用可 |
| **Vector Search RAG** | テキストをチャンク化してembeddingし、意味的類似度で検索 | 自然言語ドキュメント群、表記揺れが多い、意味的検索が必要 | インデックス構築コスト；チャンク境界で文脈が断絶しやすい | 仕様書要約に高適合。OSS embedding（BGE等）でローカル構築可能 |
| **Filesystem Exploration RAG** | LLMがgrep/glob等のシェルコマンドを生成・実行して探索 | 具体的な文字列・シンボル検索、比較的狭い探索空間（数百ファイル以内が目安） | 探索空間が広大化すると実行時間・コストが爆発；曖昧な意味検索には不向き | 脆弱性差分分析・コードリバースの補助的探索に適合 |
| **Graph RAG** | ナレッジグラフ（KG）でエンティティ・関係を構造化し、グラフ探索とembeddingを組み合わせる | 大規模データの圧縮・構造化、エンティティ間関係の推論が必要 | LightRAG・GraphRAG標準版はLLMによるKG構築フェーズが必須でローカルLLM依存；構築コスト高 | KGの概念自体は適用可能だが、**OSS商用無料・ローカルLLM不要の制約下では既製ツールはスコープ外**（§6参照） |
| **ハイブリッドRAG** | Vector Search（意味検索）＋BM25（キーワード検索）を並列実行し、RRFで融合・リランキング | 意味検索と文字列マッチ双方が必要、精度重視 | Vector + BM25 のインデックス二重管理が必要；設定の複雑さ増 | 仕様書要約・脆弱性分析双方に高適合。LangChain/LlamaIndex等のOSSで実現可能 |
| **Agentic RAG** | LLMがReasoningに基づき検索クエリを動的生成・反復検索（ReAct等） | 複雑な多段推論が必要、精度最優先のタスク | レイテンシ大（反復呼び出し）、コスト高、コンテキスト肥大化リスク | 脆弱性差分分析の深掘り段階や、複数ファイル横断の設計推論に限定活用 |

## 3. ユースケース別適合パターン

### 3.1 仕様書要約

**特性**: 長文の自然言語ドキュメント（PDF/Markdown/Word等）を対象とし、特定セクションや要点を抽出・要約する。

**適合パターン（推奨順）**:

1. **ハイブリッドRAG**（主力）
   - 仕様書は意味的類似検索（「認証の要件は」）とキーワード検索（「RFC 7231」「MUST」等）の双方が有効なため、Vector + BM25 の組み合わせが最適。
   - OSSのみで実現可能（Chroma/Qdrant + BM25s + BGE-M3 等）。

2. **Vector Search RAG**（代替）
   - 仕様書がすべて自然言語で表記揺れが多い場合、意味検索のみでも十分なことがある。
   - インデックスシンプルで実装コスト低。

3. **CAG**（小規模時のみ）
   - 仕様書が50ファイル以下かつ50,000トークン以内に収まる場合は検索精度が最も高い。
   - ファイル数・トークン数が境界を超えた時点でベクトル検索へ移行。

**不適合パターン**: Filesystem Exploration RAG（仕様書に対してgrep検索は意味的マッチに弱い）、Agentic RAG（コスト対効果が低い）。

---

### 3.2 脆弱性差分分析

**特性**: 変更前後のソースコードdiffと既知CVEデータベース・CWEリストを照合し、潜在的な脆弱性を検出・報告する。

**適合パターン（推奨順）**:

1. **Agentic RAG**（精度重視）
   - RAVEN（2025）等の先行研究が実証：ExplorerエージェントがCWE分類を行い、RAGエンジンがGoogle Project Zero / MITRE CWEデータベースから関連知識を取得し、Analystエージェントが影響評価を行う4フェーズ構成が有効。
   - 多段推論が必要なため、単純な1回検索より高精度。

2. **ハイブリッドRAG**（ベースライン）
   - CVEエントリは「CVE-2023-XXXX」のような固有識別子（キーワード）と「バッファオーバーフロー」のような意味的概念の双方で検索するため、Hybrid検索が有効。

3. **Filesystem Exploration RAG**（補助探索）
   - 特定の関数名・変数名・ライブラリバージョンを探索する際に有効。
   - コードリポジトリ内の探索空間が数百ファイル以内に絞り込まれた後の段階で活用。

**不適合パターン**: CAG（CVEデータベース全体はコンテキストに収まらない）、Graph RAG単体（KG構築フェーズでローカルLLM依存）。

---

### 3.3 コードリバース（設計書のリバースエンジニアリング）

**特性**: 既存コードベース（数百〜数万ファイル）を解析し、モジュール構成・クラス階層・依存関係・設計意図を文書化する。

**適合パターン（推奨順）**:

1. **Filesystem Exploration RAG**（主力）
   - コード内のシンボル・関数名・importパスといった具体的な文字列で探索するため、grep/globベースのツール呼び出しが最も効率的。
   - Claude Code の組み込みツール（Bash, Glob, Grep）をそのまま活用できる。
   - **探索空間の閾値**: ファイル数が数千件を超えると実行時間・トークン消費が増大するため、対象ディレクトリを絞り込む前処理（例: `*.py` のみ対象）が必要。

2. **ハイブリッドRAG**（中・大規模コードベース）
   - ファイル数が数千〜数万件になった場合、全探索ではなくインデックスベース検索へ移行。
   - コメント・docstringの意味検索（Vector）と関数名・クラス名のキーワード検索（BM25）を組み合わせる。

3. **Agentic RAG**（設計推論フェーズ）
   - モジュール間の依存関係を多段推論で追跡する段階（「このクラスを使っているすべてのモジュールを特定し、その役割を推論する」等）に限定活用。

**不適合パターン**: CAG（大規模コードベース全体はコンテキストに収まらない）、Graph RAGスタンドアロン（ローカルLLM依存）。

## 4. TBD解消: 規模感（TBD3）の概算オーダー

### 対象データの規模感

| 指標 | 小規模 | 中規模 | 大規模 |
|---|---|---|---|
| ファイル数（コードベース） | 〜数百件 | 数百〜数千件 | 数千〜数万件 |
| ファイル数（ドキュメント群） | 〜数十件 | 数十〜数百件 | 数百〜数千件 |
| データサイズ（テキスト原文） | 〜数MB | 数MB〜数十MB | 数十MB〜数百MB |

本調査の想定規模は **数MB〜数百MBオーダー、ファイル数は数百〜数万件**（前回サマリー通り確認）。

### ベクトルDBストレージ推計

**前提条件**:
- embedding次元数: 768次元（BGE-M3等、一般的なOSS embedding）
- 精度: float32（4バイト/次元）
- チャンク数との関係: 1チャンク ≈ 256〜512トークン（英文で200〜400文字程度）

**計算式**:
```
1チャンクのembeddingサイズ = 768次元 × 4バイト = 3,072バイト ≒ 3KB
```

| チャンク数 | embeddingのみ | インデックス込み（×2〜3倍概算） | バイナリ量子化時（×1/32） |
|---|---|---|---|
| 1万チャンク | 約30MB | 約60〜90MB | 約1MB |
| 10万チャンク | 約300MB | 約600MB〜1GB | 約10MB |
| 100万チャンク | 約3GB | 約6〜9GB | 約100MB |

**換算の目安（チャンク数 → ファイル数）**:
- コードファイル1件（平均500行）: 約10〜20チャンク（ファイル分割あり）
- 仕様書PDF1件（平均50ページ）: 約50〜100チャンク
- → 1,000ファイルのコードベース: 約1〜2万チャンク → **embeddingのみで約30〜60MB**

**結論（TBD3解消）**: 本調査の想定規模（数百〜数万ファイル）では、Vector DBストレージは **数MB〜数GBオーダー** に収まる。ローカルディスク（SSD標準搭載のWindows環境）に対して問題のない規模。バイナリ量子化を利用すれば100万チャンク超でも200MB以内に収められる。

## 5. H0検証への入力: CAGが成立するユースケースの境界条件

### 定量的境界条件（文献ベース）

| 境界軸 | 下限（CAG有効域） | 上限（移行推奨） | 根拠 |
|---|---|---|---|
| ファイル数 | 1〜50ファイル | 100ファイル超でRAGへ移行 | Zennの参考記事「数ファイル程度」の記述；500ドキュメント超でコンテキストウィンドウ超過リスクが顕在化（Monte Carlo Data, 2025） |
| トークン数 | 〜50,000トークン（150ページ相当） | 200,000トークン超で精度劣化リスク上昇 | ACM Web Conference 2025論文（CAG有効域の実証）；claude-3.5-sonnetの200Kコンテキストが上限の目安 |
| データ更新頻度 | 静的・安定（更新頻度: 月1回以下） | 動的更新（日次・リアルタイム）になった時点でRAGへ | KVキャッシュの再構築コストがインクリメンタル更新を上回る |
| データ性質 | 全量アクセスが必要（「すべての仕様を網羅した上で判断」型） | クエリ依存の部分検索で十分な場合はRAGが効率的 | Zenn記事「全量アクセスが必要な場合」の記述 |

### 定性的条件

**CAGが成立するケース**:
- 仕様書が小規模（50ページ以内、数ファイル）で、全体を俯瞰した上で回答が必要
- コードベースが単一モジュール程度（〜50ファイル）で変更頻度が低い
- Claudeのフラッグシップモデル（Sonnet/Opus）を使用できる環境

**CAGが成立しないケース**:
- コードリポジトリ全体（数千ファイル）を対象とする場合
- CVEデータベース等の大規模外部知識源を参照する場合
- 頻繁に更新されるドキュメント群を扱う場合

### H0仮説への示唆

- H0「CAGはXXXファイル以下かつXXXトークン以内で有効」の検証閾値として、**50ファイル / 50,000トークン** を実験の基準値として採用することを推奨
- 上限検証点: 100ファイル / 200,000トークン（CAGが破綻に近づく領域）

## 6. Graph RAGの適用可能性評価（TBD2）

### Graph RAGの概念整理

Graph RAGは「ナレッジグラフ（KG）によるエンティティ・関係の構造化」と「グラフ探索」を組み合わせるアーキテクチャで、大規模データの圧縮・構造化表現と多段関係推論に強みを持つ。

### 主要OSSの制約確認

| ツール | ローカルLLM要否 | embedding のみローカル可否 | OSS / 商用無料 | 本調査スコープ |
|---|---|---|---|---|
| Microsoft GraphRAG | LLMによるKG構築が必須（Ollama等のローカルLLM利用可能） | KG構築フェーズはLLM必須 | OSS（MIT） | **スコープ外**（LLM構築フェーズが必須） |
| LightRAG（HKUDS） | LLMによるKG構築が必須（Ollama互換API対応） | 同上 | OSS（MIT） | **スコープ外**（同理由） |
| Neo4j + LangChain | LLMによるKG構築が必須 | 同上 | Community版はOSS | **スコープ外**（同理由） |

**確認事項**: GraphRAG/LightRAGともに「ローカルLLM（Ollamaによるllama3、Mistral等）を使ってKG構築」する代替実装が存在する（GraphRAG-Local-UI等）。しかしこれは「ローカルLLMの構築・運用」に該当し、本調査の「スコープ外: ローカルLLMの構築/学習」に抵触する。

### TBD2結論

**Graph RAGの既製ツール（LightRAG / GraphRAG等）は、KG構築フェーズでLLMが必須なため本調査スコープ外。**

ただし以下の部分的活用は検討余地がある:

1. **KG概念の活用**: 既成ツールに頼らず、Claude Code自身がコードの依存関係グラフをJSON等で構造化し、それをVector DBに格納する「擬似的なGraph RAG」は実現可能。ただし構築・維持コストは高い。
2. **グラフDB単体（Neo4j Community）**: LLMなしのグラフDB＋embeddingのハイブリッドは技術的に実現可能だが、KG構築の自動化に課題が残る。

→ **本調査では Graph RAG を「将来的な発展オプション」として位置付け、当面の主力候補から除外する。**

## 7. Filesystem Explorationの位置付け

Filesystem Exploration RAG（grep/globコマンドをLLMが生成・実行）は、本調査のユースケース（コードリバース・脆弱性差分分析）において独自の強みを持つ。

### Claude Codeとの親和性

Claude Codeは Bash / Glob / Grep ツールをネイティブに持つため、別途インデックスを構築せずにFilesystem Explorationが即時実行可能。これは本調査環境の大きな優位点。

### 適用可能な探索空間の定量目安

| 探索規模 | 実行時間の目安 | 推奨可否 |
|---|---|---|
| 〜100ファイル | 数秒〜十数秒 | 推奨 |
| 100〜1,000ファイル | 数十秒〜数分（grep再帰の深さ次第） | 条件付き推奨（対象絞り込みを前提） |
| 1,000ファイル超 | 数分〜（ファイル種別フィルタ必須） | 非推奨（Vector DBへ移行） |

### 「探索空間が広すぎる」の定量閾値（TBD1解消の示唆）

- Filesystem Explorationが破綻する境界: **1,000ファイル前後（grep再帰での探索が数分を超えるライン）**
- ただし `*.py` / `*.ts` 等のファイル種別フィルタやディレクトリ絞り込みで対象を200〜300ファイル以内に収めれば、数千ファイルのリポジトリでも実用範囲内
- **定量閾値（TBD1への暫定回答）**: 対象ファイル数が絞り込み後も **500ファイル超** または **対象テキスト総量が 5MB超** になる場合、Vector DB RAGへの移行を推奨

## 8. 採用候補の整理

本調査の制約（OSS・商用利用無料・ローカルLLM不要・Windows 11）下での採用候補を以下に整理する。

### 主力構成（推奨）

| 役割 | 採用候補 | 備考 |
|---|---|---|
| Embeddingモデル | BGE-M3（BAAI）/ nomic-embed-text | ローカル実行可能、商用無料、多言語対応 |
| Vector DB | Qdrant（ローカルモード）/ Chroma | ローカルファイルモードで起動、Python API |
| BM25検索 | BM25s（Python実装）/ rank_bm25 | PIP install可能、Windows対応 |
| リランキング | BGE-Reranker-v2-m3 / Jina Reranker v2 | ローカル実行可能、商用無料 |
| オーケストレーション | LangChain / LlamaIndex | OSS、Windows Python環境で動作 |

### 補助構成（条件付き活用）

| 役割 | 採用候補 | 活用条件 |
|---|---|---|
| CAG | Claude Code 組み込みコンテキスト | 50ファイル以下・静的データのみ |
| Filesystem Exploration | Claude Code 組み込み Bash/Glob/Grep | 500ファイル以下の絞り込み探索のみ |

### 採用候補から除外するもの

| パターン | 除外理由 |
|---|---|
| Graph RAG（LightRAG / GraphRAG） | KG構築フェーズでローカルLLM必須（スコープ外） |
| クラウドRAGサービス | 有料（スコープ外） |
| Pinecone / Weaviate Cloud | 有料クラウドサービス（スコープ外） |

## 9. 課題・制約

### 将来解決が必要な課題

- **チャンクサイズの最適化**: ユースケース（仕様書 vs コード）によって最適なチャンクサイズが異なる（256〜1,024トークン）。実験による検証が必要（後続フェーズで実施）。
- **日本語コードコメントへの対応**: BGE-M3は多言語対応だが、日英混在コードの検索精度は検証要。
- **Qdrant vs Chroma の選定**: ローカルモードでのパフォーマンス・使いやすさの実証が必要。
- **TBD1の精緻化**: Filesystem Explorationの「500ファイル超」閾値は暫定値であり、実際の応答時間計測で検証が必要。

### 解決不能な課題

- **Graph RAGの自動KG構築**: ローカルLLM不使用の制約下では、既製Graph RAGツールのKG構築フェーズを代替する手段がない。Graph DBの活用は手動KG定義が前提となり、大規模コードベースへの適用は現実的でない。

### 解決不要な課題（参考情報）

- **クラウドRAGサービスの評価**: スコープ外のため評価不要。
- **ローカルLLMのパフォーマンスチューニング**: スコープ外。
- **GPUなし環境でのAgentic RAG速度問題**: Agentic RAGはAPI呼び出しのみで実行するため、ローカルGPU不要。レイテンシはAPI側の問題。

## 10. ハマりどころ追記候補

以下は後続フェーズで実装・検証を進める中で確認が必要な潜在的ハマりどころ:

1. **Qdrant のローカルモード起動**: Windows環境でのDockerなしローカルファイルモード（`QdrantClient(path="./qdrant_storage")`）の動作確認が必要。Dockerモードとの互換性に注意。
2. **BGE-M3のメモリ消費**: モデルサイズが約570MB。16GB RAM環境では問題ないが、他プロセスとの競合で Out of Memory になる可能性がある。`FlagEmbedding` の `batch_size` 調整で対応可能。
3. **BM25とベクトル検索のスコア正規化**: BM25スコア（非正規化整数）とコサイン類似度（0〜1）を直接加算するとスコアが偏る。RRF（Reciprocal Rank Fusion）での融合が推奨。
4. **チャンク境界による文脈断絶**: コード関数が複数チャンクにまたがると検索ヒットしても文脈が不完全になる。Overlap設定（チャンク間50〜100トークンの重複）で緩和。
5. **Windows改行コード（CRLF）の影響**: テキスト前処理時に `\r\n` を `\n` に統一しないとchunk_sizeの計算がずれる場合がある。
