## 中程度の指摘（論理の補強余地）

### 指摘 1: §3.1.2 経路 C（UserPromptSubmit hook で `additionalContext` に `search_result` ブロック注入）の実現可能性根拠が薄い

- **箇所**: 99.位置づけマップ.md §3.1.2 経路 C / §3.1.3 推奨優先順
- **問題**:
  - 経路 C は「Anthropic API レイヤに直接届くため `search_result` ブロックが許容される可能性、Citations 自動付与の可能性」とメリットを挙げているが、Agent D §4.2 採用可能性 3 の記述では「`additionalContext` が content block 形式を受けるかは別途未検証」と明記されている
  - すなわち「hook 出力（stdout / JSON）がどう Anthropic API に変換されるか」という変換レイヤの存在は **MCP の場合とほぼ同じ問題構造**を持つ。Agent B §2.5 の hook 説明では `additionalContext` は「JSON フィールドを返すと追加コンテキストを注入」と記述されるのみで、content block 配列を受ける記述は確認できない
  - したがって経路 C の「実現可能性」根拠は経路 B（MCP `resource` / `resource_link`）と同程度かそれ以下の不確実性を持つ可能性がある
- **影響**: 大筋への影響度 **低**（§3.1.3 で「spike 検証」と位置付けているため致命的ではない）
- **推奨対応**: **03 設計時検討**（経路 C のメリット欄に「hook 出力が content block 配列を受けるか自体が未文書化」を補足追加。経路 B より検証コストが高いことの根拠を明示）

### 指摘 2: §3.3.2 表「Memory tool ↔ Claude Code auto memory の構造的等価性」の主張強度

- **箇所**: 99.位置づけマップ.md §3.3.2 / Agent D §採用可能性への影響 (1)
- **問題**:
  - 「**構造的に等価**」と強い表現が使われているが、表の中身は対応関係を示すアナロジーであり、実装的な等価ではない
  - 特に重要な差異: Memory tool（API）は **Claude モデルが tool call で `view` / `create` / `str_replace` 等を能動的に発火**してメモリを操作するのに対し、Claude Code auto memory は **Claude Code 内部のハーネス層が自動でロード/トリミングを行う**（モデルからの直接操作インタフェースは異なる）
  - 「設計予定パターンを auto memory 補強として位置付ければ Memory tool 思想に乗ったまま運用可能」という結論は妥当だが、「構造的等価」と書くと「同じインタフェースで差し替え可能」という誤読を招く可能性
- **影響**: 大筋への影響度 **低**（結論は変わらない。表現の正確性問題）
- **推奨対応**: **03 設計時検討で可**（表のタイトルを「Memory tool（API）と Claude Code auto memory の設計思想の対応関係」程度にトーンダウン、または「構造的に類似（実装インタフェースは異なる）」と注釈追加）

### 指摘 3: §2.2 表のパターン 12（code-index-mcp）「B+C」判定における B 要素の妥当性

- **箇所**: 99.位置づけマップ.md §2.2 パターン 12 / §2.1 凡例
- **問題**:
  - §2.1 凡例で B は「部分代替 + 大規模時に独自 RAG 必要」と定義され、§2.3 B の詳細で挙げられているのはパターン 5（FilesystemExploration）のみ
  - パターン 12 / 13 が「B+C」とされる根拠は §2.2 の補足欄「標準 Grep と機能重複部分あり、tree-sitter シンボル検索が差分価値」「mcp-ripgrep は標準 Grep ツールとほぼ重複」だが、これは「公式機能による部分代替」というよりは「公式機能と機能重複」を意味しており、B の凡例定義「部分代替 + 大規模時に独自 RAG 必要」とは微妙にずれる
  - 「重複部分は B 相当（既存機能で代替可能）+ 差分部分は C 相当（MCP 経由連携で独自価値）」という解釈は読み取れるが、§2.1 凡例の B 定義からは直接導けない
- **影響**: 大筋への影響度 **低**（パターン 5 と 12/13 で B の意味が異なるという解釈ぶれだが、結論の独自価値判定は変わらない）
- **推奨対応**: **03 設計時検討で可**（§2.1 凡例で「B は単独評価だけでなく『B+C』のように複合判定でも使用し、複合時は『公式機能と重複する部分（B 要素）+ 公式機能を超える部分（C/D 要素）』を意味する」と注記を追加。または §2.3 で「B+C」型のパターンの説明を補う）
