## エグゼクティブサマリー

1. **Claude Code 自体には RAG 機能は存在しない**（Agent B 確認）。公式 glossary は RAG を「Claude プラットフォーム層の概念」として明示的に切り離している。本調査のローカル RAG は **Claude Code の外側に構築し MCP server として接続する** のが公式アーキテクチャ上の素直な選択である。
2. **公式 RAG 機能は二層構造**: ①UI 完結（Projects RAG / Drive Cataloging / Chat Search、内部実装非公開、Claude Code から呼べる API なし）、②**Anthropic Messages API 直接呼出時のみ利用可**な BYOR スキーマ群（Search results blocks + Citations + Files API + Memory tool、スキーマ公開・実装は利用者責任）。**Claude Code CLI / IDE 内蔵 tool として直接 enable できるのは Files API 系の document/image ブロックや MCP 連携、Skill / Subagent / Hook / fileSuggestion 等の progressive disclosure 機構のみで、`search_result` ブロックや `memory_20250818` tool は Claude Code 経由では使えない**（Agent D 確証）。
3. **設計予定 15 パターンの公式機能カバー判定**（後述 §3）: 完全代替 1 件・部分代替 1 件・公式と並存（MCP 経由連携）10 件・独自価値が高い領域 3 件・除外確定 1 件。本調査の中核（ハイブリッド検索・コードグラフ・日本語特化）は公式機能でカバーされず、**独自 RAG 構築のスコープは正当**。
4. **検索結果引渡し規約は要再設計**: 初版で「最重要推奨」として提示した「`search_result` ブロック規約準拠」は MCP 仕様レベルで採用不可と確定（Agent D 確証）。代替経路 4 案（text 構造化埋め込み / MCP `resource` 系 / hook 経由 / Agent SDK 直接 API）の比較と推奨優先順は **§3.1.2 参照**。
5. **連携経路の選択肢拡張**: 02.基礎調査では「MCP / Skills」が連携方式の主候補だったが、Agent B 発見により **fileSuggestion setting（カスタム `@`-mention 検索）** と **UserPromptSubmit hook（`additionalContext` 注入）** が新たな比較対象として浮上。とくに「ファイルパス検索」用途は MCP より fileSuggestion の方が自然な可能性あり。

- **※5**: Sonnet 4+ / Opus 4+ / Haiku 4.5+ で利用可

### 1.2 「公式 RAG」と呼ばれているものの実態

- **claude.ai 側 RAG（Projects RAG / Drive Cataloging / Chat Search）**: 「RAG を使う」とは明記されているが、チャンク粒度・埋め込みモデル・検索アルゴリズムは **全て非公開**。`「documents, images, and other files」`程度の抽象記述に留まる。
- **API 側 BYOR スキーマ（Search results blocks + Citations）**: **検索は利用者側が実装** することを前提に、Claude への結果引渡しと citation 付与の規約を提供する設計。公式は明示的に「This feature is particularly powerful for **RAG (Retrieval-Augmented Generation) applications**」と RAG ユースケースを謳う（Agent A §10 引用）。**ただし利用経路は Anthropic Messages API への直接呼出に限定** され、Claude Code 経由（MCP tool レスポンス含む）では使えない（Agent D §4.2 確証。MCP 仕様 2025-11-25 の tool result `content` 許容 type に `search_result` が含まれない）。
- **Memory tool**: **ファイル名駆動の just-in-time retrieval**。ベクトル RAG ではない。ストレージ実装（file/DB/S3）と検索戦略は完全にクライアント側責任。`/memories` 仮想ディレクトリへの view/create/str_replace 等のツールを Claude が呼ぶ構造。**Claude Code CLI / IDE 拡張からは enable する公式手段がない**（Agent D §4.1 確証）。`docs/en/memory` ページは CLAUDE.md + Claude Code auto memory の 2 機構のみを「How Claude remembers your project」として定義し、API Memory tool への言及はない。Agent SDK で自前ハーネスを書く場合に限り組み込み可。

### 1.3 Claude Code 内の「RAG 的」機構

| 機構 | progressive disclosure 適合度 | 「大量ファイル → 必要部分」用途への適合 |
|---|---|---|
| Skill | 公式が用語使用（行 30748）。description 1,536 字のみ常時保持、本文は on-demand | 中（知識・工程ガイド向き、検索エンジン代替ではない） |
| Subagent（特に Explore） | 親には要約のみ返却、中間 tool call は親コンテキストから完全分離 | **高**（公式ドキュメントが「verbose output を subagent 内に閉じ込めて summary だけ返す」パターンを推奨） |
| MCP Tool Search | tool 名のみ常時保持、schema は ToolSearch で on-demand fetch、85% 削減実証 | 高（ツール定義に対する RAG。ドキュメント本文には適用範囲外） |
| Hook（UserPromptSubmit）| プロンプト発火時に hook が外部システム問い合わせ → `additionalContext` を注入 | 高（外部 RAG の差し込み口として最も汎用） |
| `fileSuggestion` setting | `@` 入力時にカスタムスクリプトが最大 15 件のパスを返す | 中（ファイルパス検索専用、本文取得には別途 Read 必要） |
| `.claude/rules/`（path-scoped）| 該当 path 編集時のみコンテキスト追加。**コンパクション後は失われる** | 低〜中（ドメイン特化ルール向き） |
| Auto memory（MEMORY.md）| インデックスは 200 行/25KB のみ常時保持、topic file は Claude 判定で on-demand Read | 中（Claude 自身の学びの蓄積向き、外部データの検索ではない） |

### 2.3 判定の解説

#### A（完全代替候補）の詳細: パターン 6（CAG）

CAG の本質は「全量を context に載せて検索しない」。Claude Code は **拡張モデルで 1M tokens の context window** を持つ（Pro/Max/Team/Enterprise の Claude Code、Sonnet 4.6/Opus 4.7、Agent A §2）。50K トークン以下の静的データは:

- **方法 1**: CLAUDE.md or 個別 CLAUDE.md（遅延ロード）に全文を `@import` → セッション開始時に全量保持
- **方法 2**: Skill の SKILL.md に全文埋め込み → ユーザー明示呼び出し / Claude 判定でロード
- **方法 3**: API 経由なら Files API でアップロード + document block として渡す → Citations 自動付与

いずれも標準機能で対応可能。**したがって CAG パターンを「公式機能の境界条件確認」として位置付け直すと、H0 検証の意義はそのまま残しつつ、03 設計フェーズで新規実装すべき独自要素は存在しない**。

#### B（部分代替）の詳細: パターン 5（FilesystemExploration）

FilesystemExploration は「インデックスなし、Bash/Glob/Grep オンデマンド」と定義されており、これは **Claude Code 標準の Glob/Grep/Read ツールそのもの**。さらに `Explore` subagent を使えば「読んで要約だけ親に返す」も標準で実現可能（Agent B §2.3）。

ただし以下の点で標準機能は不足:
- **大規模時のトークン線形増加問題**は未解決（02.99 §8.2、Agent C §3「Claude 標準機能では不十分」）
- 標準 Grep は ripgrep ベースだが、**tree-sitter ベースのシンボル境界検索は標準ツールに存在しない**（パターン 12 / 13 が補う領域）

→ パターン 5 を「H1 検証の必須対照群」として残す意義は変わらない。**ただし計画書では「組み込み Bash/Glob/Grep」と書かれている連携方式を、Subagent（Explore）併用に拡張すべき可能性が浮上**。03 設計フェーズで再検討推奨。

#### C（並存・MCP 経由連携）の詳細: パターン 1〜4, 7〜13

これらは全て「ローカル RAG を MCP server として公開し、Claude Code から MCP 経由で呼ぶ」構造。公式機能 MCP のスコープに**完全に乗る**。MCP 採用時のメリット:

- **Tool Search による on-demand ロード**: MCP tool 一覧が 55K トークン消費という既知のハマりどころ #14（02.99 §3.6）に対し、`tool_search=true` で 85% 削減（A-9 / B-2.4）
- **MCP resources の `@`-mention**: 検索結果を `@server:resource` 形式で attachment 注入
- **`search_result` ブロック直接返却は不可**: MCP プロトコル仕様 2025-11-25 の tool result `content` 許容 type は `text` / `image` / `audio` / `resource_link` / `resource` の 5 種閉じた enum（D-§4.2）。`search_result` 型はこの enum 外のため、MCP 経由での Citation 自動付与は仕様レベルで不可。代替案: ①text ブロック内に source/title を構造化埋め込み（Citations 機能は失うが運用可能）、②MCP `resource_link` / `resource` 型で source URI を渡し Claude 側に文脈整理を任せる、③Method 2（top-level content）系の経路（UserPromptSubmit hook 等）を別途設計

#### D（独自価値の高い領域）の詳細

公式機能にも BYOR スキーマにも対応物がなく、本調査が独自構築する正当性が立つ領域:

1. **ハイブリッド検索ロジック**（BM25 + ベクトル + RRF + クロスエンコーダーリランカー）— 02.99 §3.3 / §3.4 の本命構成。公式は「検索は利用者側で実装」と明示
2. **日本語特化処理**（sudachipy/MeCab + bge-m3 / ruri-v3）— 公式機能で日本語特化処理への言及なし
3. **コードグラフ構造**（tree-sitter + コールグラフ + 影響半径 + 依存トレース）— 「ベクトル類似度はコードの依存構造を表現できない（沈黙した失敗）」(02.99 §8.2) という本質的問題に対し、公式機能には対応物がない

#### E（除外確定）の補足

- パターン 14（狭義 Graph RAG）: ローカル LLM 必須 → スコープ抵触で除外確定
- パターン 15（擬似 Graph RAG）: Claude Code 自身が依存関係を JSON 化する案。構築・維持コストが高く当面除外、申し送り

### 2.4 「Anthropic 公式ドキュメント検索」ユースケース（派生）の位置付け

CLAUDE.md「Anthropic 公式ドキュメント調査の手順」では現在 `claude-code-llms.txt` + `claude-code-llms-full.txt` + Grep を「暫定運用」としている。**本格 RAG 完成後の置き換え対象**（improvements/C01-001 / C01-003 既登録）。

公式機能側で対応可能か:
- **Claude.ai Projects RAG**: ドキュメントを Project knowledge base にアップロード可能だが、**Claude Code から API 経路がない** ため不可（A-1, A-3）
- **Files API + Search results blocks**: ドキュメントを Files API にアップロード後、利用者側で検索実装 → API レスポンスとして渡す経路は可能（C 判定相当）

→ **本暫定運用は本格 RAG 構築のドッグフード対象**として最適。03 設計の検証用ユースケースに採用する価値あり。

## 第 3 部: 設計上の含意・推奨方針

### 3.1 検索結果引渡し規約の設計（03 設計時の最優先検証項目）

> **改訂注**: 初版では「最重要推奨」として `search_result` ブロック規約準拠を提示したが、Agent D §4.2 確証で MCP プロトコル仕様（2025-11-25）の tool result `content` 許容 type に `search_result` が含まれず、**Method 1（MCP 経由）は仕様レベルで不可** と判明した。本節は代替経路の比較検討の場に再定義する。

**本節の結論**: A 案（text ブロック構造化埋め込み）を default 規約として全 MCP パターン共通で採用、B / C 案（MCP `resource` 系 / UserPromptSubmit hook 経由）を 03 設計早期の spike 検証対象、D 案（Agent SDK 直接 API）は本調査スコープ外。失う主便益は sentence-level citation の自動付与で、text ブロック内に source/title を構造化埋め込みする実装で部分代替可能。詳細は §3.1.1〜§3.1.4。

#### 3.1.1 採用不可と確証された経路

- **Method 1（MCP tool 経由で `search_result` ブロック返却）**: MCP 仕様で許容されない（D-§4.2）。Claude Code 実装が type を passthrough している可能性はゼロではないが、未文書化の挙動であり公式依存は不可

#### 3.1.2 03 設計フェーズで比較する代替経路

| 経路 | 概要 | 想定メリット | 想定デメリット | 検証コスト |
|---|---|---|---|---|
| **A. text ブロック構造化埋め込み（MCP 標準型のみ使用）** | MCP tool の `text` レスポンス内に `[source: ..., title: ...] 本文` 形式で source/title をテキスト埋め込み | MCP 仕様準拠・追加検証不要・全 MCP パターン共通で即適用可能 | 公式 Citations 機能は使えない（sentence-level citation 喪失） | 低 |
| **B. MCP `resource` / `resource_link` 型で source URI を渡す** | tool レスポンスを `resource_link`（URI 参照）または embedded `resource`（URI + 本文）で返却 | MCP 仕様準拠・Claude 側で `@`-mention attachment 風に扱われる可能性 | Citations 自動付与は同じく不可、Claude の引用挙動は実機検証が必要 | 中 |
| **C. UserPromptSubmit hook の `additionalContext` に Method 2 形式（top-level content）で `search_result` ブロック注入** | プロンプト送信時に hook が外部 RAG 問い合わせ → 結果を top-level content として注入 | Anthropic API レイヤに直接届くため `search_result` ブロックが許容される可能性、Citations 自動付与の可能性 | hook 出力が content block 形式を受けるか未検証、毎プロンプトでのコスト過大懸念 | 高 |
| **D. Claude Code を経由しない直接 API 利用**（参考） | Agent SDK / 自前ハーネスで Anthropic Messages API を直接呼ぶ | `search_result` + Citations を本来通り利用可能 | Claude Code CLI / IDE 拡張のユーザー体験を放棄。本調査スコープ外 | — |

#### 3.1.3 03 設計時の推奨優先順

1. **A を default 規約**（MCP 仕様準拠・追加検証不要・即適用可能）として全 MCP パターン共通で採用
2. **B / C は spike 検証** を 03 設計の早期に実施し、Citations 自動付与が実現できる経路があれば差分採用
3. **D は本調査スコープ外** として参照のみ

#### 3.1.4 失われる便益と代替策

`search_result` ブロックが使えないことで失う主便益は **sentence-level citation の自動付与**。これに対する代替策:

- text ブロック内に source/title を構造化埋め込みすれば、Claude が回答内で「[source: ...]」を再現する自発的引用は期待できる（明示プロンプトで強化可能）
- リランカー段階で各 chunk に `source` メタデータを付与して text ブロック先頭に明示
- 03 設計時に「Claude の自発的引用がどの程度の精度で発生するか」を spike 検証項目に追加

### 3.2 連携経路の選択肢拡張（03.02 検討項目）

| 連携経路 | 適合ユースケース | 既知の制約 |
|---|---|---|
| MCP server（stdio）| 全文検索・ハイブリッド検索・コードグラフ | tool 一覧の context 消費（Tool Search 必須） |
| MCP server（HTTP/SSE）| 常駐サーバー型、複数クライアント | 既存 Skills 常駐 HTTP 案と同概念 |
| Skill（CLI 都度起動）| プロトタイプ用途のみ | モデルロード 8-9 秒（bge-m3 で悪化見込み） |
| **fileSuggestion setting**（新候補）| ファイルパス検索（`@`-mention 拡張）| 返却 15 件まで、本文取得は別途 |
| **UserPromptSubmit hook**（新候補）| プロンプト発火時の自動 context 注入 | timeout 30 秒、hook 出力サイズ注意 |
| **MCP resources の @-mention**（新候補）| 検索結果の attachment 注入 | tool との使い分け要設計 |
| **MCP prompts**（新候補）| 定型クエリ + 結果取得の 1 コマンド化 | 利用者が `/mcp__name__prompt` 明示呼び出し |

### 3.3 Claude Code auto memory との連携設計（Memory tool 概念の取込み）

> **改訂注**: 初版では「Memory tool（API）のバックエンドとして設計予定パターンを位置付ける」案を提示したが、Agent D §4.1 確証で Claude Code から `memory_20250818` を enable する公式手段が存在しないことが判明。本節は **Claude Code auto memory（`~/.claude/projects/<project>/memory/`、MEMORY.md インデックス + topic files）の補強・拡張機構** として設計予定パターンを位置付ける形に再定義する。

**本節の結論**: Memory tool API への直接バックエンド化は不可だが、Claude Code auto memory と Memory tool は設計思想が対応関係にあるため（§3.3.2）、設計予定パターンを auto memory の補強・拡張機構として位置付ければ Memory tool 思想に乗ったまま運用可能。具体連携イメージ a / b / c は §3.3.3 で 03 設計の選定候補として整理。

#### 3.3.1 直接連携が不可と確証された経路

- **Memory tool（`memory_20250818`）のバックエンド化**: Claude Code から有効化できないため不可（D-§4.1）。`allowedTools` / `--allowedTools` / settings のいずれにも当該 API beta tool を組み込む経路は公式に存在しない

#### 3.3.2 採用可能な経路: Claude Code auto memory の補強

Memory tool の設計思想（ファイル名駆動 just-in-time / multi-session 永続）は、Claude Code auto memory と **構造的に等価**:

| Memory tool（API）の特性 | Claude Code auto memory の対応 |
|---|---|
| `/memories` 仮想ディレクトリ | `~/.claude/projects/<project>/memory/` 物理ディレクトリ |
| `view` で directory listing | セッション開始時に MEMORY.md 先頭 200 行 / 25KB を自動ロード |
| 関連ファイル名で `view` 取得 | Claude 判定で topic file を on-demand Read |
| ストレージは利用者実装 | machine-local、リポジトリ単位、Claude 自身が編集 |
| just-in-time retrieval | 同上 |

→ 設計予定パターンを **「Claude Code auto memory の topic file を補完・拡張する外部 RAG レイヤ」** として位置付ければ、Memory tool 思想に乗ったまま運用可能。

#### 3.3.3 具体連携イメージ（03 設計時の検討項目）

- **a. auto memory ↔ ローカル RAG の手動 sync**: Claude が auto memory に書き込んだ知識を、人間が定期的に RAG インデックスへ batch sync（最も単純）
- **b. UserPromptSubmit hook 経由で RAG 結果を auto memory に注入**: hook が外部 RAG 問い合わせ結果を `additionalContext` に載せ、Claude が auto memory への保存判断を行う
- **c. MCP server 経由で auto memory 補完**: ローカル RAG MCP server を呼んだ後、Claude が結果を auto memory の topic file に追記する運用を Skill で標準化

03 設計時にいずれを採用するかは未確定。**a が最小コスト、b / c が自動化度の高い候補**。

#### 3.3.4 Agent SDK 経由での Memory tool 利用は対象外

Agent SDK（`@anthropic-ai/claude-agent-sdk` 等）で自前ハーネスを構築する場合に限り Memory tool は組み込み可能だが、これは「Claude Code CLI / IDE 拡張」ではなく「Agent SDK で構築した別アプリ」になるため本調査スコープ外（D-§4.1 留保事項より）。

### 3.4 Claude Code 内 progressive disclosure 機構との重複回避

本調査の関心は「Claude Code から呼べるローカル RAG」だが、**Claude Code 内蔵の progressive disclosure 機構（Skill / Subagent / MCP Tool Search）でカバーできる範囲は二重構築しない** ことが望ましい:

- **「知識・ワークフロー」レベル**: Skill で十分。RAG にしない
- **「特定ファイルパスでのドメイン規約」**: `.claude/rules/`（path-scoped）で十分。RAG にしない
- **「大量ファイルの探索 → 要約」**: 標準 Subagent（Explore）で代替可能か比較対象に。FilesystemExploration（パターン 5）対照群はこの観点で意義
- **「大量データに対する意味検索・ハイブリッド検索・コード構造解析」**: これが本調査の真の独自価値領域（D 判定）

### 3.5 H0 / H1 検証の解釈アップデート

| 仮説 | 02.99 時点の理解 | 公式機能調査後の解釈アップデート |
|---|---|---|
| H0（CAG 成立） | 50 ファイル/50K トークン以下で有効 | **本質的に「Claude 公式機能で代替可能な境界条件」と一致**。CAG 実装の独自要素はゼロ。検証は標準機能の境界判定として実施 |
| H1（FilesystemExploration vs ベクトル）| コードグラフ+シンボル検索 vs 汎用ベクトルへ補正済 | **対照群を「Bash/Glob/Grep」のみではなく「+ Subagent（Explore）」併用に拡張すべき**。Subagent 併用が標準機能の真の天井 |
| H2（常駐 vs CLI）| CLI 都度起動 8-9 秒 | 公式 MCP は **stdio サーバーが標準**（再接続なし）。常駐 HTTP も公式 MCP transport で実現可（不変） |
| H3〜H5 | （独自価値領域） | 公式機能には影響なし、調査継続 |

## 第 4 部: 論点ステータス（決着済み / 03 設計時検討）

### 4.1【決着済み: ✗ 確証】公式 Memory tool は Claude Code から直接利用可能か

- **結論**: Claude Code CLI / IDE 拡張からは `memory_20250818` を enable する公式手段が存在しない（D-§4.1）
- **根拠**: `claude-code-llms-full.txt` 全文 Grep で `memory_20250818` / `Memory tool` / `memory-tool` のヒットゼロ。`docs/en/memory`（"How Claude remembers your project"）は CLAUDE.md と auto memory の 2 機構のみで構成。`allowedTools` / `--allowedTools` / settings に API beta tool を組み込む経路は公式記述なし
- **本マップへの反映**: §1.1 / §1.2 / §2.2 パターン 7 / §3.3 を全面改訂済み。Memory tool（API）への言及は概念的親和性の参照点のみに留め、直接連携不可を明示

### 4.2【決着済み: ✗ 確証】Search results blocks + Citations は MCP tool レスポンスで使えるか

- **結論**: MCP プロトコル仕様 2025-11-25 で許容されない（D-§4.2）
- **根拠**: 仕様 `https://modelcontextprotocol.io/specification/2025-11-25/server/tools` の tool result `content` 許容 type は **`text` / `image` / `audio` / `resource_link` / `resource` の 5 種閉じた enum**。`search_result` は含まれず、カスタム type 拡張規定もない。Anthropic 公式 search-results docs にも MCP 経由利用の言及ゼロ
- **本マップへの反映**: §1.1 / §1.2 / §2.2 パターン 4 / §2.3 C 詳細 / §3.1 を全面改訂済み。Method 1（MCP 経由）は採用不可と明示、代替経路 A〜D を §3.1.2 に整理

### 4.3 fileSuggestion の制約（最大 15 件）が本ユースケースで十分か

- パス検索特化の連携経路として有望だが、検索結果が 15 件に制限される（B-2.5）。
- 「コードリバース」ユースケースで「関数名から関連ファイル候補を引く」程度であれば十分だが、「キーワードから網羅的にヒット」用途では不足。
- 推奨アクション: 03 設計時に MCP vs fileSuggestion の使い分けマトリクスを作成。

### 4.4 UserPromptSubmit hook の `additionalContext` を本ユースケースで使う場合のコスト

- プロンプト送信時に自動で外部 RAG 問い合わせ → 結果注入が可能（B-2.5）。
- ただし hook 出力は会話履歴扱いでコンテキスト消費。「毎プロンプトで RAG 結果を載せる」運用はコスト過大の懸念。
- 推奨アクション: 「ユーザーが明示的にトリガーしたとき（特定キーワードや MCP tool）」のみ発火する判別ロジック設計。

### 4.5 Anthropic 公式ドキュメント検索 RAG（improvements/C01-003）の優先度引き上げ検討

- 本暫定運用（CLAUDE.md「Anthropic 公式ドキュメント調査の手順」）は **本調査のドッグフード対象**として最適。
- Claude.ai Projects RAG では Claude Code から呼べないため、本格構築は本調査スコープに完全に乗る。
- 推奨アクション: 03 設計のユースケース整理（03.01）で派生ユースケースから昇格させる候補として検討。
