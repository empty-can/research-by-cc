## 論点 1: Memory tool は Claude Code から直接利用可能か

### 検証結果: **✗（公式に許容されない / 利用不可と確証）**

ただし「✗ に近い △」と読むこともできる留保あり（後述）。

### 根拠

#### 1) Claude Code 公式ドキュメントには `memory_20250818` / API Memory tool への言及が一切ない

`claude-code-llms-full.txt`（全文・最新 DL）を以下キーワードで Grep:

- `memory_20250818` → **0 件**
- `Memory tool`（大文字小文字込み） → **0 件**（"a memory tool" という一般名詞例示 2 件のみ、`openWorldHint` の解説で）
- `memory-tool` → **0 件**

`claude-code-llms.txt`（カタログ）でも:
- `memory` セクション（`/docs/en/memory`） は全て **CLAUDE.md / auto memory（`MEMORY.md` インデックス + topic file）/ `.claude/rules/`** の説明に終始。API Memory tool への参照リンクすら無し

`claude_code_docs_map.md` でも同様（API Memory tool への navigation entry 無し）。

#### 2) `docs/en/memory` 本文（claude-code-llms-full.txt 行 25977-26410）の構造的確認

ページタイトル: **"How Claude remembers your project"**

冒頭定義:
> "Each Claude Code session begins with a fresh context window. Two mechanisms carry knowledge across sessions:
> - CLAUDE.md files: instructions you write to give Claude persistent context
> - Auto memory: notes Claude writes itself based on your corrections and preferences"

つまり Claude Code の「memory」は **CLAUDE.md と auto memory の 2 つのみ** と公式定義されている。`memory_20250818` tool は **このページの構成要素として一切登場しない**。

#### 3) API Memory tool 側のドキュメント構造（client-side 実装責任）

`https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool` 取得結果（要点）:

> "The memory tool operates **client-side**: you control where and how the data is stored through your own infrastructure."
>
> "To use the memory tool:
> 1. Add the memory tool to your request
> 2. **Implement client-side handlers for memory operations**"
>
> 提供 SDK バインディング: cURL / Python / TypeScript / C# / Go / Java / PHP / Ruby（全て **直接 Anthropic Messages API を叩く** 形）

Memory tool の使用には **アプリケーション側で `view` / `create` / `str_replace` / `insert` / `delete` / `rename` の 6 コマンドハンドラ実装が必須**（`BetaAbstractMemoryTool` Python / `betaMemoryTool` TypeScript を継承）。

#### 4) Claude Code には「任意の API tool を enable する手段」が存在しない

`allowedTools` / `disallowedTools` は **Claude Code 内蔵 tool（Read/Edit/Bash/Glob/Grep/Agent/Skill/MCP）の許可制御** のための仕組み（`claude-code-llms-full.txt` での 100+ hit を確認）。**API beta tool を新規に組み込む経路ではない**。

`/tools` / settings / `--allowedTools` のいずれにも `memory_20250818` を追加できる仕様記述なし。

#### 5) Agent A §8 の記述「Claude API 経由（Claude Code でも利用可能、API 経由のため）」の再評価

この記述は Agent A 側の **誤った帰納推論** と判定。実態は:

- Memory tool は **Anthropic Messages API を直接叩くアプリ実装者向けの beta tool**
- Claude Code は内部で Anthropic API を呼ぶ消費者である一方、その内部の request 組み立てを **ユーザーが介入する仕組みは公開されていない**
- したがって「Claude Code から `memory_20250818` を enable する公式手段は存在しない」

### 「✗ に近い △」と読む余地

- Agent SDK（`@anthropic-ai/claude-agent-sdk` 等）経由で **自前ハーネスを書く場合** は Memory tool を組み込める可能性がある（Agent SDK は API ラッパーであるため）。ただしこれは「Claude Code CLI / IDE 拡張」ではなく「Agent SDK で構築した別アプリ」になるため、本論点（Claude Code 直接利用）の対象外
- 公式が「Claude Code でも Memory tool を使える」と **明示否定** している記載も無いため、将来的に integrations が追加される可能性はゼロではない

### 採用可能性への影響（位置づけマップ §3.3 の判断材料）

位置づけマップ §3.3 は次の 2 段階の主張をしている:

1. **概念的親和性**: 設計予定パターン（特にパターン 7 Codebase-Memory MCP）を Memory tool の「multi-session software development pattern」に寄せた設計にする
2. **実装連携**: 「Memory tool のバックエンドとして設計予定パターンを位置付け」

**判断**:
- (1) **概念的親和性は維持可能**: Memory tool の設計思想（ファイル名駆動 just-in-time / multi-session 永続）は、Claude Code 内の auto memory（`~/.claude/projects/<project>/memory/MEMORY.md` インデックス + topic files）と **構造的に類似**。実際 Claude Code auto memory は Memory tool の設計を Claude Code 内部に取り込んだもの と読める。設計予定パターンを **Claude Code auto memory の補強 / 拡張機構** として位置付ければ、Memory tool 思想に乗ったまま運用可能
- (2) **実装連携の直接バックエンド化は不可**: Claude Code から `memory_20250818` を enable する経路がない以上、「設計予定 MCP server を Memory tool API のストレージ実装として刺す」直接連携は **本調査スコープでは実現不可**

→ **位置づけマップ §3.3 の文言は要修正**:
- 「Memory tool のバックエンドとして位置付け」→ **「Claude Code auto memory（MEMORY.md / topic files）の補強として位置付け」** に置き換え推奨
- Memory tool（API）への言及は「概念的親和性の参照点」に留め、「Claude Code から直接連携可能」とは記載しない

## 論点 2: Search results blocks は MCP tool レスポンスで使えるか

### 検証結果: **✗（公式に許容されない / 利用不可と確証）**

### 根拠

#### 1) MCP 公式仕様（2025-11-25）の tool result `content` 配列の許容 type は閉じた enum

`https://modelcontextprotocol.io/specification/2025-11-25/server/tools` の "Tool Result" 節:

> "All content types (**text, image, audio, resource links, and embedded resources**) support optional annotations..."

明示的に列挙される 5 type:

| Type | 用途 |
|---|---|
| `text` | テキスト |
| `image` | base64 画像 |
| `audio` | base64 音声 |
| `resource_link` | リソース URI 参照 |
| `resource` | embedded resource（URI + 本文） |

**`search_result` は列挙されていない**。

カスタム type を許容する拡張規定（"extensions" / "custom types" / "vendor-specific blocks"）も明文化されていない（"Tool Result" 節および周辺セクションには extensibility provision 無し）。

#### 2) MCP は JSON-RPC ベースの **モデル非依存プロトコル**

MCP 仕様の Overview:
> "MCP provides a standardized way for applications to: Share contextual information with language models..."

MCP は Claude 専用ではなく **任意の LLM ホスト** を想定。`search_result` は **Anthropic Messages API 固有の content block type** であり、MCP プロトコル層に持ち込むのは設計レイヤ違反。

#### 3) Anthropic Search results 公式ドキュメント（`/docs/en/build-with-claude/search-results`）にも MCP 連携の明示記述なし

ページ全文取得結果から:

- "Method 1: Search results from tool calls" 節の説明:
  > "The most powerful use case is returning search results from your custom tools. This enables dynamic RAG applications where tools fetch and return relevant content with automatic citations."
- 全提供 SDK サンプル（Python / TypeScript / C# / Go / Java / PHP / Ruby）は **全て直接 Anthropic Messages API の `tool_result` ブロックに `search_result` を埋め込む** 例
- **"MCP" / "Model Context Protocol" の文字列はページ内に 1 回も出現しない**

つまり Anthropic 側は `search_result` を「**Anthropic Messages API の `tool_result.content[]` に渡す」use case のみ想定**しており、MCP プロトコル経由での使用は example も言及も無い。

#### 4) MCP tool result と Anthropic `tool_result` の変換レイヤの存在

実態として:
- MCP server は `tools/call` レスポンスを返す（content type は MCP 仕様準拠）
- Claude Code（または Anthropic Messages API ラッパー）が **MCP レスポンスを Anthropic API の `tool_result` ブロックに変換**
- この変換は MCP の許容 type → Anthropic の許容 type マッピングであり、**MCP 側で `search_result` を返しても変換レイヤがそれを認識しない** ことが強く想定される（実装確認はしていないが仕様レベルでマッピング規定が存在しない）

仮に Claude Code 実装が type を passthrough しているとしても、それは **未文書化の挙動** であり公式に依存可能ではない。

### 採用可能性への影響（位置づけマップ §3.1 の判断材料）

位置づけマップ §3.1 は **「最重要推奨」** として:
> "全 MCP パターン共通の設計指針として組み込むことを強く推奨: 全 RAG パターンの検索結果を `{type: "search_result", source, title, content: [...], citations: {enabled: true}}` 形式で返す"

**判断**: この推奨は **そのままでは成立しない**。MCP プロトコル仕様上 `search_result` 型の content block は許容されていない。

#### 採用可能性の再評価（3 段階）

1. **仮説扱いに留めるべき**（最有力）:
   - §3.1 の表現を **「設計指針候補（未検証）」** に格下げ
   - 03 設計時に「MCP server → Claude Code の中継経路で `search_result` ブロックが実際に通るか」を **実機検証（spike）** したうえで採用判断

2. **再設計が必要**（次善）:
   - MCP tool レスポンス本来の `text` ブロックで「source URL + 本文」を構造化テキストとして返す（プレーン text 内に source/title を埋め込む）
   - Citations は使えないが、Claude が text 内の URL を回答に含める運用は可能
   - sentence-level citation のメリットは喪失

3. **補強できる**（最も理想に近いが工夫が必要）:
   - **Method 2（Top-level content として）** で Search results blocks を使う経路を活用
   - Claude Code 側で UserPromptSubmit hook（`additionalContext`）に `search_result` ブロックを注入する形なら、MCP プロトコルを介さず Anthropic API レイヤに直接渡せる **可能性** がある（ただし `additionalContext` が content block 形式を受けるかは別途未検証）
   - 検証コストは MCP 経由より高い

#### 推奨される位置づけマップの修正方針

- §3.1 のステータスを **「最重要推奨」→「03 設計時の最優先検証項目（仮説）」** に変更
- §1.2 の API 側 BYOR スキーマの説明から「MCP server レスポンスとして使える」という暗黙の前提を取り除く
- 設計予定パターンの C 判定（並存・MCP 経由連携）について、「Citation 自動付与」の便益は **MCP 経路では仮説段階** と注記
- パターン 1〜13 の便益期待値を「Citations 付与による信頼性向上」を含まずに再計算する選択肢を 03 設計で検討
