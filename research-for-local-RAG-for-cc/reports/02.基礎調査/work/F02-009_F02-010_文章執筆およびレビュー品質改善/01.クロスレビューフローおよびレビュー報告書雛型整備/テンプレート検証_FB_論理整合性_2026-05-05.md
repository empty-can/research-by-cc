## 3. テンプレート構造に関する FB（記入順）

### 3.1 メタ情報テーブル（はじめに）

**助かった点**:
- 「レビュアー」「レビュー区分」「版」が明示されており、複数レビューが並走する場面で取り違えを防げる
- 「判断基準」のコメントブロックに記載例（作業計画書 §, CLAUDE.md など）が含まれており、何を引用すべきか迷わなかった

**気になった点**:
- 「版」の定義（0.8 → 0.9 → 1.0）が「版数とレビュー指摘件数」節のコメントブロック内にあり、メタ情報テーブルの「版」フィールドを書く時点では参照しにくい。**メタ情報テーブル直下に「※版の定義は次節を参照」と一文加えるか、定義コメントを冒頭に出した方が記入しやすい**

### 3.2 件数サマリ表

**助かった点**:
- 0.8 / 0.9 / 1.0 の 3 列構造が「いつ何件あったか」を一覧で追跡できる
- ラベル別（CRITICAL / IMPORTANT / SUGGESTION / POSITIVE）の集計だけで十分情報量がある

**気になった点**:
- 0.8 版だけ記入し、0.9 / 1.0 は `<TBD>` のまま残すという指示が**テンプレートに明示されていない**（タスク指示書側で受領）。**テンプレート側のコメントに「0.8 版作成時点では 0.9 / 1.0 列は `<TBD>` で良い」と記載した方が、別レビュアーが同じ手順を踏みやすい**
- 件数表が 2 つ存在する（冒頭の「版数とレビュー指摘件数」と末尾の「観点別サマリ表」）。**冒頭は版×ラベル、末尾は観点×ラベル** という直交関係になっているのは合理的だが、初見では「2 表ある理由」が分かりにくい。冒頭または末尾の片方に「※もう一方の表は観点別の内訳」と相互参照を加えると親切

### 3.3 判断依頼サマリー

**助かった点**:
- 各指摘エントリへのアンカーリンク（`[I1](#i1-...)`）形式により、長文報告書でも判断ジャンプができる
- 態度表明列が空欄スタートで、後続改訂時に追記する運用が読み取りやすい

**気になった点**:
- アンカーリンクのスラッグ生成は **GitHub Flavored Markdown と異なる正規化ルール** がレンダラーごとに混在しているため、日本語タイトル時にリンクが壊れることがある。今回は念のため日本語タイトルをそのままアンカーに含めた（記入時に「リンクが効くか不明」という不安が残った）。**スラッグ生成ルールの注記、もしくは ID を `{{id}}` プレースホルダから自動展開するスニペット例があると安心**
- 判断依頼サマリーの行数と、「CRITICAL / IMPORTANT / SUGGESTION の指摘エントリ実体の件数」が一致するかをテンプレ側で書く際の整合チェックは手作業になる。**指摘件数 (§版数表) との整合チェックリストがテンプレ末尾にあると見落としを防げる**

### 3.4 指摘エントリの個別フィールド

#### 概要・詳細・根拠の三段構造

**助かった点**:
- **概要 → 詳細 → 根拠** の三段構造は論理整合性指摘で非常に書きやすい。「何が問題か」「どう問題か」「なぜそう言えるか」が明確に分離される
- 「詳細」と「根拠」の番号が対応するルール（コメント記載）も、指摘の論理構造を担保する強い仕組みになっている

**気になった点**:
- **POSITIVE エントリでも「概要・詳細・根拠」の三段構造を流用できる構成** は良いが、POSITIVE では「根拠」に何を書くべきか迷った（「評価できる根拠」≒「なぜそれが優れているか」と解釈して記入）。**POSITIVE 用の例示（評価対象、評価が成立する根拠の書き方）があるとなお良い**

#### 修正案テーブル

**助かった点**:
- 「★」と「太字」のルールにより、推奨案・推奨理由・非推奨理由が一目で読める
- 「メリット・デメリットがないセルには『なし』と明記」というルールが、考慮漏れの誤読を防ぐ

**気になった点**:
- 修正案 1 件しかない場合の表記が、コメントの「修正案が 1 つしかない場合や、デメリットがない場合でも、表形式で記載する」で明示されているのは助かった
- 修正案テーブルの直下「1. 修正案1.詳細」リストが、表に書ききれない情報を補足する箱として用意されているが、**表に十分な情報を書いた場合「無し」と明記するルール** が、表 → 詳細リストの順で見ると初見で分かりにくかった。**表のすぐ下に「※表で十分な場合、詳細リストは『無し』と記載」のリマインダがあると良い**

#### レビューイ回答欄 / 作業指示者の態度表明欄

**助かった点**:
- 0.8 版作成時点で「空欄またはテンプレ既定の状態のまま」とする運用が指示書で明確だった（テンプレ側にもそのコメントがあると新規レビュアーがより迷わない）
- 「指摘内容に対する同意の程度の根拠」「作業指示者向けの補足」の二段構造で、レビューイの態度を示しつつ作業指示者の判断材料を分離して提供できる構造になっている

**気になった点**:
- POSITIVE エントリの態度表明が「（維持 / その他）」となっており、IMPORTANT/SUGGESTION の「（採用 / 条件付き採用 / 差戻し / 保留 / 却下）」とラベル体系が異なる。これは合理的（POSITIVE は維持判断が中心）だが、**「その他」が想定する具体例がコメントに無い** ため、何が「その他」に該当するか分からなかった。例: 「その他: 維持に加え横展開する / 維持しつつ強化する / 維持不要と判断する 等」

### 3.5 観点別サマリ表

**助かった点**:
- 観点（論理整合性 / カバレッジ十分性 / 調査目的との整合性 / 仮説の妥当性）×ラベル（C/I/S/P）の二次元分類で、レビューの傾向が一目で分かる
- 「ステータス」列で「指摘あり / 指摘なし / スコープ外」を明示する運用は、レビュー観点ごとの濃淡が見える

**気になった点**:
- 「各指摘がどの観点に属するか」を観点別サマリに書く際、**判断依頼サマリーや指摘本文側に観点列がない** ため、表側でしか観点割当が把握できない。今回はサマリ表直下のコメントブロックに「各指摘の観点割当の補足」として一覧を残したが、**指摘エントリ自体に観点ラベルを付ける欄をテンプレ側で用意してほしい**（例: 各指摘の見出し直下に「観点: 論理整合性」のような行）。観点ベースで再集計するときの追跡性が大幅に向上する
- 観点別サマリ表で 1 つの指摘が複数観点にまたがる場合の集計ルールが不明だった。今回は単一観点に割り当てたが、**「複数観点にまたがる場合は主観点に割り当て、副次観点はコメントで注記」など運用ルールがあると揺れが減る**

### 3.6 変更履歴

**助かった点**:
- 「未到達版（将来到達する可能性がある）: 日付・内容欄を空欄」「スキップ版（フロー上発生しない）: 両方を `-` とする」の使い分けルールが明確
- 「初版作成」「レビューイ FB 取り込み」「作業指示者指摘取り込み」と各版の目的が記載されており、誰がどの版で何をするか迷わなかった

**気になった点**:
- 0.8 版作成時点では 0.9 / 1.0 が未到達なので、空欄でよいことは分かったが、**枠（行）はテンプレ通り残すべきか、削除すべきか** が不明だった（残す方針で記入）。**「未到達版の行は残す」と明示しておくと迷いがなくなる**

## Round 3 レビューア再対応時の追加FB

### 1. レビューア再対応時に困った点

#### 1.1 テンプレートに「レビューア最終所見」枠が無いことの影響

**最大の摩擦点**。改訂版テンプレートには **レビューイ FB 取り込み後にレビューア側が記入する欄** が存在しない（テンプレ構造は「問題点 → レビューイ回答 → 修正案 → レビューイ修正案見解 → 作業指示者態度表明」の順で、最後の作業指示者欄の前にレビューア再対応欄が無い）。

今回はレビューイ修正案見解の直後に `##### {ID}. レビューア最終所見（v0.9）` というレベル 5 見出しを独自に追加して対応したが、以下の判断を毎エントリで強いられた:

- **見出しレベル**: レビューイ欄が `#####`（H5）なので合わせるか、本文相当の `####`（H4）にするか
- **配置位置**: 修正案の後・態度表明の前で確定だが、見出し構造が「問題点回答 → 修正案 → 修正案見解」と二系統あるので、どちらの後に置くべきか
- **必須記載項目**: 「最終結論」「収束ステータス」だけで足りるのか、レビューイ追加案への採否判断も明示すべきか

結局「見出しレベル H5（レビューイ修正案見解と同レベル）」「配置: 修正案見解の直後」「記載項目: 所見本文 + 最終修正案 + 収束ステータス」で統一したが、**テンプレ側でこの欄を構造化しておけば、本判断を 10 回繰り返す必要は無かった**。

**改善提案（高優先）**:
- 各指摘エントリ末尾（態度表明の直前）に `##### {ID}. レビューア最終所見（{版数}）` を **テンプレ既定欄として追加**
- サブ項目として「最終結論（修正案確定 / 取下げ / 維持）」「最終修正案（レビューイ追加案を取り込んだ場合は明示）」「収束ステータス（達成 / 1ラウンド継続 / 議論継続）」「レビューイとの認識一致状況」をテンプレ化

#### 1.2 「収束」ラベルの定義揺れ

「収束: 達成 / 1ラウンド継続 / 議論継続」というラベル体系は本タスク指示書で受領したが、**テンプレ側にラベル体系の定義が無い**ため、各エントリでどの基準で「達成」と判定するかは個別判断になった:

- I1 のように「レビューイ追加案を全面取り込み」→ 達成
- I4 のように「部分同意の事実認識補正をレビューア側で承認」→ 達成？ 1ラウンド継続？

今回は「最終修正案が双方合意で確定し、新規論点が発生していない」を「達成」の判定基準として運用したが、**テンプレ側に判定基準の例示があると揺れが減る**。

**改善提案（中優先）**:
- 「収束ステータス」のテンプレ定義に「達成 = 最終修正案が双方合意で確定し新規論点なし」「1ラウンド継続 = レビューイ追加案の採否判断にレビューア側で再検証が必要」「議論継続 = 認識不一致が残る」を例示

### 2. 「レビューイからの見解・指摘・補足（修正案）」フィールドの実用性評価

**結論: 非常に実用性が高かった**。

#### 2.1 助かった点

- **「採用推奨案／採用すべきでない案／追加案」の 3 区分** がテンプレに組み込まれているため、レビューイは「修正案 ★1 を支持」「修正案 2 は不採用」「追加案: ★1 + α」という形で網羅的に立場表明してくれた。レビューア側で取り込み判断する際、レビューイの論点を見落とすリスクが大幅に下がった
- **追加案が「修正案・メリット・デメリット」の表構造でレビューア側の修正案テーブルと同一フォーマット** で書かれていたため、最終修正案の確定時に追加案を「★1 + 追加案 α」として一体化する作業がスムーズだった
- I4 の「部分同意」のように、レビューイが指摘の方向性は同意しつつ事実認識の一部を補正する形のフィードバックも、本フィールドで自然に表現できた（「レビューア側の認識前提では妥当だが、サブタスク 06 §記事 3 に multilingual-e5-small が明示」という補強情報が読み取れた）

#### 2.2 改善余地

- **追加案が「★1 + 拡張」形式の場合のラベリング欠如**: レビューイ視点FB §5 でも指摘されている通り、今回 4 件の追加案中 3 件（I1 / I2 / I4）が「★1 を採用しつつ拡張」する形式だった。レビューア側で再対応する際、これを「別案」として扱うか「★1 の拡張」として扱うかの判断が必要だった。最終的にすべて「★1 + 拡張」として統合したが、**テンプレ側で「採用推奨案の拡張提案」区分を独立させる**と、レビューアの取り込み判断が機械的になる
- **追加案の「採否」をレビューア側で記入する場所がテンプレ上明示されていない**: 今回はレビューア最終所見の中で「追加案を採用」と書いて処理したが、「追加案ごとに採否欄を設ける」形式の方が抜け漏れリスクが下がる

### 3. 件数表 0.9 列更新時の使用感

#### 3.1 取下げ時の件数表示ルール明示の必要性
