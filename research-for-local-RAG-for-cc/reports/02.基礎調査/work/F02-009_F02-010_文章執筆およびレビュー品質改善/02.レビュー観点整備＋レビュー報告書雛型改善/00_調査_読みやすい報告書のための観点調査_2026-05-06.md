## 4. 既存 7 観点に追加すべき観点の提案

### 既存 7 観点との重複排除

| 既存観点 | 重複する抽出観点（追加候補から除外） |
|---|---|
| 5. 読み手の認知負荷 | O3, O4, O5, O6 は同観点の下位細目として吸収可（追加観点に格上げしない） |
| 1. 意思決定材料の十分性 | O14, O16 は密接に関連する。ただし「具体性の三点セット」は粒度が違うので別観点にできる |
| 6. 網羅性 | O15（Devil's Advocate）は近接するが、既存観点が「他の選択肢を見落としていないか」、追加観点は「主張に対する最強反論を検討したか」で軸が違う |
| その他 | O17, O18, O19 は単独で観点化するほどの分量がなく、既存観点（読み手認知負荷）の細目として運用可 |

### 追加推奨観点（既存に**ない**観点に絞り込み）

| # | 観点名 | 優先度 | 既存 7 観点との差分 | 具体的な確認方法（1〜2 行） |
|---|---|---|---|---|
| **新8** | **Reader-AI フレッシュ読みテスト（独立読者検証）** | **高** | 既存 5「読み手の認知負荷」は静的レビュー。これは**動的テスト**。原典 J | 文脈ゼロの Claude に文書だけ渡し、想定読者が抱く Q を 5〜10 件投げて、正答率と「曖昧と感じた箇所」を集計する。誤解 1 件以上か曖昧指摘 3 件以上で要修正 |
| **新9** | **AI スロップ／前置き句・冗長表現の排除** | **高** | 既存 5 は「冗長さ」を一般論で問う。これは LLM 起因のパターン化された冗長を**形態素レベル**で排除する | (a) 「近年〜」「重要なのは〜」「以上を踏まえると〜」のような中身のない前置き句を grep、(b) em-dash 連用、(c) 同一段落内の文長の単調さ（標準偏差が極端に小さい）、(d) ハッジ語（「と思われる」「可能性が高い」）の頻度を点検 |
| **新10** | **全文「重み検査」（every sentence carries weight）** | **中** | 既存 5 とは粒度が違う（章単位ではなく**文単位**） | 完成版を通読し、各文に対して「この一文を削除して情報損失が出るか」を二択判定。No が一定割合（例：10% 以上）なら冗長過多 |
| **新11** | **主張の Specificity 三点セット（what / where / evidence）** | **中** | 既存 1「意思決定材料の十分性」は文書全体の話。これは**主張単位**で「事象・該当箇所・根拠」を揃えているかを問う | 主要主張（H2 直下の結論文や箇条書き）ごとに、(a) 何を主張しているか明確、(b) どの節・図表・データで根拠が示されているか、(c) 反証された場合の影響、の 3 点が揃っているか確認 |
| **新12** | **読了時間制約の事前宣言と実測** | **中** | 既存観点には時間軸の制約がない | 文書冒頭に「想定読了時間：X 分」を宣言し、原稿の文字数・段落数から実測値を算出して妥当性を確認。乖離が大きい場合は要約セクションを追加するか分割を検討 |
| **新13** | **Devil's Advocate（最強反論の織り込み）** | 低〜中 | 既存 6「網羅性」と一部近接するが、軸は「**主張ごとの反証**」 | 主要結論ごとに「これに対する最強の反論は何か」を 1 件記述し、(a) 採用しなかった理由、または (b) 残存リスクとして承認者に明示する |

**最重要は 新8・新9・新10 の 3 件**。これらは既存 7 観点に**完全に欠けている**側面（独立検証 / LLM 起因冗長 / 文単位品質）を補う。

新11・新12・新13 は既存観点の延長線上で吸収もできるが、独立観点として運用したほうがレビュー時に確認の網が細かくなる。

## 5. 総合所感

**資産は十分に存在した**。特に Anthropic 公式の `anthropics/skills/doc-coauthoring` は本調査の趣旨に直接マッチする 1 級資産で、「Reader Claude testing」「slop 検査」「every sentence carries weight」など、既存 7 観点を**直接的に補強する具体手法**を持っている。Microsoft Writing Style Guide の Scannable Content も具体性が高く、日本語 Markdown 文書にもそのまま適用可能。

一方で、**Anthropic 公式に「人向け報告書のレビュー観点」を網羅した単一の Skill は存在しない**。`doc-coauthoring` は「書く」ワークフローであり、「レビューする」観点集ではない。本リポジトリの既存 7 観点はそれ自体が独自の価値を持つが、(a) LLM が書いた文章の機械的冗長（AI スロップ）への対処、(b) 独立読者による動的検証、の 2 点は公開資産でも取り組みが薄い領域で、追加観点として組み込む価値が高い。

**コミュニティ系（awesome-claude-skills, claude-skills-collection 等）は概ねコンテンツ生成・整形系で、レビュー観点設計のための一次資料は限定的**。Imbad0202/academic-research-skills は学術特化だが、Devil's Advocate / Traceability Matrix / Specificity は汎用的に応用可能で、特に審議資料・意思決定文書の品質に効く。

**Minto Pyramid と Diátaxis は古典的だが今でも有効**。報告書設計の前段（構造選択）として、新規観点に格上げするほどではないが、既存観点 5「読み手の認知負荷」のサブガイドとして参照する価値はある。

採用する場合の優先順は：

1. **新8（Reader-AI フレッシュ読みテスト）** — 既存 7 観点と独立、最も独自性が高い
2. **新9（AI スロップ排除）** — LLM が書いた報告書を扱う以上、必須に近い
3. **新10（全文重み検査）** — レビュー所要時間と引き換えに品質が大幅に上がる

を最低限追加し、新11〜新13 は既存観点の細目として運用するか、観点数を増やせる場合に独立観点化する判断が無難。
