## 1. 指摘一覧

### I-1. §3.1 推奨「案 A」の根拠が薄い（観点: 1. 意思決定材料の十分性）

- **対象箇所**: §3.1 改訂アプローチの選択肢、推奨欄
- **指摘内容**: 「中優先の 2.2.1〜2.2.6 はいずれも『コメント追記』『ルール明示』レベルで、新たな摩擦を生む確率は低い」とあるが、**確率が低いという主張の根拠が示されていない**。中優先の中には「§2.2.4 敢えての意図のサブ項目を条件付き記入欄に再設計」のように、構造変更を伴う案も含まれている。承認者として「改訂量が多い vs 摩擦が起きにくい」という二律背反を判断するには、せめて「中優先 6 件のうち構造変更を伴うのは 1〜2 件、残りはコメント追記」のような **改訂タイプ別の内訳** が欲しい。
- **改善提案の方向性**: 中優先 6 件を「コメント追記のみ」「既定欄追加」「構造再設計」の 3 タイプに分け、件数を提示。低リスクであることの定量的補強を加える。

### I-2. §2 と §3.2 の対象範囲の食い違い（観点: 2. 実装可能性・現実性）

- **対象箇所**: §2.1.4（4 件目の高優先項目）と §2.1.1〜§2.1.3（3 件） / §3.1（推奨案 A の文言「高優先 3 件 + 中優先 6 件」） / §3.2（改訂対象ファイル 4〜5 件） / §4.3（想定工数の前提「高優先 4 件 + 中優先 6 件」）
- **指摘内容**: §3.1 では「高優先 **3 件** + 中優先 6 件」と記載されているが、§2.1.4 を含めると高優先は **4 件**。§4.3 の表側は「高優先 4 件 + 中優先 6 件」と正しいが、§3.1 の表は v1.1 改訂時に同期し損ねた可能性が高い。承認者目線では「結局案 A は何件を対象にするのか」が混乱する。
- **改善提案の方向性**: §3.1 の表と推奨欄の文言を「高優先 4 件 + 中優先 6 件」に統一。同様に §3.1 案 B も「高優先 4 件のみ」に修正。

### I-3. §2.1.4 の改訂が複数ファイル横断であることのリスク評価が無い（観点: 4. リスク評価）

- **対象箇所**: §2.1.4 改訂方向（README.md / 両テンプレ / `research-for-local-RAG-for-cc/CLAUDE.md` の 3 箇所同時改訂）
- **指摘内容**: §2.1.4 は単独でテンプレ 2 件・README・プロジェクト CLAUDE.md の **計 4 ファイルへの同時改訂**を要求している。提案文書として「位置付け: 他項目への影響なく取り込み可能」とあるが、これは §2.1.1〜§2.1.3 との独立性の話であり、**§2.1.4 内部の整合性リスク**（テンプレ冒頭注記の文言と README 節の文言の不整合、CLAUDE.md と README の役割分担の曖昧化など）には触れていない。承認後に「テンプレと README で運用ルールの記述が二重管理になり、片方が古くなる」事態は想定されないか。
- **改善提案的な方向性**: §2.1.4 改訂方向の末尾に「ルールの **真の出所**は README.md とし、テンプレ冒頭注記と CLAUDE.md は **参照を強制する記述に留める**（具体的な数値・条件は重複させない）」という方針を明記。ルート CLAUDE.md の「README.md は CLAUDE.md の派生物」と同様の二重管理回避思想と整合させる。

### I-4. §3.3 確認ポイントに「定量的判定基準」が不足（観点: 1. 意思決定材料の十分性）

- **対象箇所**: §3.3 改訂後の確認ポイント（再試行時）
- **指摘内容**: 確認ポイントは観察項目として列挙されているが、いずれも「〜が改善されたか」「〜が機能するか」と **定性表現のみ**。例えば「終了条件『直近の試行でゼロ』が客観的判定として機能するか」を再試行で何をもって判定するのか（誤検知が出てもゼロと判定する事象が発生したらNG とする、など）が決まっていない。再試行の結果がまた主観で評価されると、改訂効果の確認がループに陥る。
- **改善提案の方向性**: 各確認ポイントに「**測定方法**」を 1 行追加（例: 「観点フィールド追加 → 観点別サマリ表との突合工数を v0.9 と比較し、半減を目安」「セルフレビュー上限 → 上限到達による打ち切り回数 / 全試行で過半数を下回ること」）。

### I-5. §4.3 想定工数の根拠（特に短縮余地の見積）が不透明（観点: 3. コスト・投資対効果）

- **対象箇所**: §4.3 想定工数の表
- **指摘内容**: 「再試行（Round 1〜3 並列実行）: 60〜90 分。**セルフレビュー上限適用により短縮余地あり**」とあるが、前回検証ではセルフレビューが 6〜8 巡だったところを上限 5 巡に抑えるだけで、ラウンド 1 全体が大きく短縮されるかは不明。「短縮余地あり」が **2.5〜3.5 時間という合計値に既に織り込まれているのか / 楽観値として上振れ前提なのか** が不明瞭。承認者として「想定上限 = 3.5 時間」なのか「現実的最大 = 4 時間以上もありうる」のかで判断が変わる。
- **改善提案の方向性**: 「短縮余地あり」を削除し、**ベースライン値 + バッファ**として「セルフレビュー上限を遵守した条件下での想定値」と明記。あるいは「短縮余地」を別行（例: 「最良ケース 2.0 時間 / 想定 3.0 時間 / 最悪 4.0 時間」）として可視化。

### I-6. §5.1 の選択肢で「1 を選ぶ場合の観察設計」が無い（観点: 1. 意思決定材料の十分性）

### I-8. §2 全般、優先度区分の根拠が「困り具合」「複数視点で一致」程度の主観表現（観点: 1. 意思決定材料の十分性）

### I-15. 承認後に困るシナリオ：再試行の比較ベースライン（観点: 7. 承認の押し戻し条件）

- **対象箇所**: §3.3 / §4.1
- **指摘内容**: 「比較ベースラインが明確（v0.9 まで収束した検証結果）」とあるが、改訂後の再試行で **新たな比較対象（既存 v1.0 / 新規 v0.9 / 改訂後 v1.0' の三項比較）**になる。三項比較を最初から想定しているなら良いが、提案書には「改訂後 vs v0.9 の二項比較」しか書かれていないように読める。三項比較ならばそのフォーマットの定義が必要、二項比較ならば既存 v1.0 を「初期ベースライン」として残す扱いの明示が必要。
- **改善提案の方向性**: §3.3 冒頭に「比較フォーマット: <二項 or 三項>。前者の場合 v1.0 は参考情報扱い」と一言追加。

### I-16. §2.3 低優先テーブルの粒度が雑（観点: 5. 読み手の認知負荷 / 2. 実装可能性）

- **対象箇所**: §2.3 低優先（L1〜L8）
- **指摘内容**: L1 〜 L8 が 1 行記述のみで、**承認者が「これは本当に低優先で良いのか」を判断する材料が不足**。例えば L4「アンカーリンクのスラッグ生成ルール注記（日本語タイトル時の挙動）」は使うツール（GitHub / VSCode プレビュー / Pandoc）依存で挙動が違う実装課題で、軽くないかもしれない。低優先でも一律「実装難易度: 低 / 中」だけ列に追加してほしい。
- **改善提案の方向性**: §2.3 表に「実装難易度」「想定影響箇所」の 2 列を追加。低優先のまま塩漬けする項目と、案 B 採用時に拾える項目を識別しやすくする。

### I-17. メタ情報の版数管理（観点: 2. 実装可能性・現実性）

- **対象箇所**: 冒頭メタ情報「版数」 / 変更履歴
- **指摘内容**: 版数が「1.2」、変更履歴に 1.0 → 1.1 → 1.2 の記載がある。1.1 と 1.2 の改訂日付が同じ（2026-05-05 と 2026-05-06）なのは良いが、**v1.2 で取り込んだ「実用性レビューア Round 3 FB §3-2」が v1.0 / v1.1 で漏れた経緯**は変更履歴に書かれているものの、これが他にも同様の漏れが無いかチェックする運用に繋がっていないように見える（再発防止の言及が無い）。承認者として「他にも漏れがあったらどうするか」が気になる。
- **改善提案の方向性**: 変更履歴 v1.2 行末尾に「漏れの再発防止として、改訂方向欄を全件 FB ノート §3-1〜§3-3 と機械的に突合し、欠落が無いことを確認した」のような検証アクションを 1 行追加。
