## IMPORTANT

### U-I-1: 修正案「確定」と本体反映の区別が曖昧で「指摘解消済み」と読めてしまう

**対象箇所**: 「レビューア最終収束判定（v0.9 完了時点）」テーブル、各指摘の「収束: 達成」表記、指摘内の「即収束」記述

**観点**: 意思決定材料の十分性 / 承認の押し戻し条件

**指摘内容**:
v0.9 時点で「修正案確定」「収束: 達成」「次フェーズ要否: v1.0 へ進行可」と書かれているため、ぱっと読むと **02.99 報告書本体への反映が完了しているように誤読** する。だが本レビュー報告書はあくまで「修正案について合意できた」段階で、本体（`報告書.md`）への反映自体は v1.0（作業指示者承認後）でなされる設計のはず。

作業指示者として承認判断する際、「自分が承認した時点で本体は既に直っているのか／これから直るのか」が読み取れないのは決定的な障害になる。承認後に「本体まだ直ってませんでした」が判明したら、承認の前提が崩れる。

特に I-1 と S-1 は §2.1 表のセット改修であり、レビューイ自身が「v0.9 反映時に一括処理する方が変更履歴も整理しやすい」と書いている。だが現状の「収束: 達成」表記は読み手に誤った安心感を与える。

**改善提案**:
- 「収束: 達成」は「**修正方針の合意: 達成**（本体反映は 1.0 化時に実施）」のように、合意レベルと実施レベルを言葉で区別する
- もしくは収束判定テーブルに「本体反映ステータス」列を加えて、`未着手 / 着手中 / 完了` を明示する
- v1.0 化のタイミングで「02.99 本体側の変更箇所と diff 概要」を本レビュー報告書末尾に追記する運用を 1.0 化フローに組み込む

### U-I-2: 判断依頼サマリーが「未記入」のままで進行判定が出ている

**対象箇所**: 「判断依頼サマリー」テーブル（態度表明列がすべて「（未記入）」）、および「次フェーズ要否: v1.0 へ進行可」記述

**観点**: 意思決定材料の十分性 / 読み手の認知負荷

**指摘内容**:
冒頭の「判断依頼サマリー」テーブルでは I-1・S-1・S-2・S-3 の態度表明列が全て「（未記入）」になっている。一方、末尾の「レビューア最終収束判定（v0.9 完了時点）」では「v1.0 へ進行可（作業指示者レビュー待ち）」と書かれている。**テンプレートの「報告書作成完了後（0.8版）に記入し、態度表明が完了した指摘は『（記入済み）』に更新する」ルール（実用性_template.md L40-42）に照らすと、現状は v0.9 完了時点で更新が必要だったか、あるいは「未記入」のままで良いかが報告書から判断つかない**。

承認者の動きとしては「サマリーで未記入を見つけたら態度表明する」が自然で、まさにそのために用意された欄に空欄が並んでいる現状は混乱を招く。さらに POSITIVE 行（P-1・P-2）はサマリーに含まれていない（態度表明列が「維持/その他」だが態度表明そのものは必要）。

**改善提案**:
- サマリーテーブルに **POSITIVE 2 件も含める**（態度表明欄 = 「維持/その他」の選択を作業指示者に求める）
- 「未記入」表記の意味を冒頭に補足する（「v1.0 化フローで作業指示者が記入する欄。0.9 版では未記入が正しい状態」など）
- もしくはテンプレート側を改訂し、サマリーは「（v1.0 で記入）」のような記入待ち明示文言にする

## SUGGESTION

### U-S-1: 修正案ごとのコスト・影響範囲の見積もりが無い

**対象箇所**: I-1 / S-1 / S-2 / S-3 各「修正案」セクション

**観点**: コスト・投資対効果

**指摘内容**:
作業指示者として「指摘を採用するコストがどれだけか」を判断する材料が乏しい。各指摘の修正案には「メリット／デメリット」はあるものの、変更ファイル・行数・他箇所への波及・所要時間の見積もりが書かれていない。レビューイの見解で「変更影響範囲は §9.1 冒頭 1 行のみで小さい」（S-3）のように個別に言及されてはいるが、I-1・S-1・S-2 にはこの記述が無い。

実用性レビューでは「軽微な改善」と「表のリファクタリング」が混在しているため、指摘ごとに以下の粒度で揃っていると採否判断がしやすい。

- 変更対象ファイル数 / 行数規模
- 他の章節への副次的変更要否（参照リンク・章番号など）
- 1.0 化作業として要する見込み時間（ざっくり）

**改善提案**:
- 修正案テーブルに「変更影響範囲」列を追加する（テンプレート改訂候補）
- もしくはレビューイ見解の「追加修正提案」「作業指示者向けの補足」枠で必ず影響範囲に触れる運用に統一

### U-S-2: スコープ外宣言の根拠記述位置と命名規則遵守観点との整合

**対象箇所**: メタ情報直下の「スコープ外の理由 — 検証パターン具体性」段落、版数別観点表

**観点**: 網羅性 / 読み手の認知負荷

**指摘内容**:
1. **記述位置**: スコープ外の理由がメタ情報テーブル直下に独立段落で書かれているが、テンプレート（実用性_template.md）にはこの位置への記述指示は明確には無い（README.md には「メタ情報セクションの『スコープ外』欄に記載」とある）。テーブル内の「スコープ外」セルにこの長文が入らないのは仕方ないが、**README.md の指示と運用に乖離**がある。判断としては「テーブルセルから本文へのリンクを置く」「テンプレ側を運用に合わせて改訂する」のいずれかを選ぶべきで、現状は記述場所の運用が不安定。
2. **観点と指摘の整合**: 観点別件数表で `S-2（命名案2択）` を「命名規則遵守」に分類しているが、指摘内容の本質は「**選択基準の文書化不足**」であり、命名規則そのものへの違反ではない。実用性_template.md の「観点」記載は「分類軸」であり、観点と指摘の対応根拠が薄い分類があると、観点別の網羅性チェックが機能しなくなる。

**改善提案**:
- スコープ外段落はテーブル内セルに「（本文参照）」と書き、本文に「スコープ外の理由」節を切る
- 観点分類は指摘の本質（S-2 は「完了条件明瞭性」または「文書構造」寄り）に合わせて再分類するか、観点定義の運用ルールを README.md に補記

### U-S-3: 「テンプレート検証を兼ねた」運用上の所見が報告書側に残っていない

**対象箇所**: メタ情報・変更履歴（変更履歴 0.8 版に「テンプレート検証を兼ねたクロスレビュー」と記載）

**観点**: 網羅性

**指摘内容**:
変更履歴 0.8 版に「テンプレート検証を兼ねたクロスレビュー」と書かれており、ファイル名にも「テンプレート検証_」のプレフィックスがある。だが報告書本文には**テンプレート使用上の気づき・改善提案が残されていない**。

作業指示者の立場では「テンプレート検証を兼ねた」とあれば「次回のテンプレ運用に活かす知見が出ているはず」と期待する。実際にレビューイ補足で「§2.1 表は構成レイヤーと採用候補度・特性軸が混在した設計」「他§3.x への横展開可否は別途検討事項」のような **テンプレや運用への示唆** が散見されるが、これらが集約されていないため、テンプレ検証の成果が拾い上げられない。

**改善提案**:
- 報告書末尾に「テンプレート検証フィードバック」節を追加し、本レビュー実施を通じて見えたテンプレ運用上の課題（例: 観点分類の粒度、修正案の影響範囲列の不在、サマリーの POSITIVE 含めない問題等）を 1〜3 件箇条書きする
- もしくは別ファイル（FB ノート）への参照を本報告書側からも明記する

### U-S-4: I-1 修正案 2 の入れ子表現不採用根拠が技術制約止まり

**対象箇所**: I-1 修正案テーブル — 案 2 のデメリット記述

**観点**: 実装可能性・現実性

**指摘内容**:
案 2 のデメリットが「表のレイアウトが複雑になる。テーブルの入れ子・インデントが Markdown で表現しにくい」となっている。だが Markdown でテーブルを入れ子にする手段（リスト化・別表化など）は複数あり、**「Markdown 制約」という言葉で却下するのは弱い**。本当の不採用根拠は「採用候補表は単独参照されることが多く、入れ子はその参照容易性を損なう」のような 03 担当者目線の論点であるはず。

レビューイ見解では「案 2 の表入れ子は Markdown 表現上の制約が大きく可読性が下がるため不採用」となっており、ここも技術寄りの根拠で止まっている。

**改善提案**:
- 案 2 のデメリットを「**サマリ表が単独参照される利用シナリオ（03 担当者の設計フェーズ参照）に対して、入れ子構造は読み解きコストを増やす**」のように利用シナリオに紐付けて書き直す
- もしくは案 2 の不採用は I-1 § 修正案直下の補足で 1 行追加する

### U-S-5: リンクアンカーの未検証で承認後にナビゲーションが壊れるリスク

**対象箇所**: 「判断依頼サマリー」テーブルの ID リンク（`#i-1-採用候補サマリ表における-isink17codegraph-の二重登場と優先度の矛盾` 等）

**観点**: 読み手の認知負荷

**指摘内容**:
日本語見出しのアンカーリンクは Markdown レンダラ依存で、生成規則が GitHub・VSCode プレビュー・他ツールで揃わないことがある。`isink17/codegraph` の `/` がエスケープされるかどうかなど、リンク切れの発生確度は無視できない。**承認後にナビゲーションが壊れるリスク** は読み手の認知負荷を直接押し上げる。

**改善提案**:
- 1.0 化前に GitHub プレビュー上でアンカー動作を確認（クリックでセクション末尾へ飛ぶか）
- 動作不良がある場合は、明示的な HTML アンカー（`<a id="i-1"></a>`）を見出し直前に置く運用を検討

### U-S-6: S-3 で参照されている CLAUDE.md「追記ルール」の所在と実体一致が未確認

**対象箇所**: S-3 指摘内容・レビューイ見解で参照されている「CLAUDE.md『ハマりどころ.md 参照ルール — 追記ルール』」

**観点**: 意思決定材料の十分性

**指摘内容**:
作業指示者として S-3 を判断する時、参照根拠が「CLAUDE.md にある追記ルール」と書かれているが **どの CLAUDE.md（ルート / 個別調査）か** がレビュー報告書のみからは特定しきれない。実際には個別調査の CLAUDE.md（`research-for-local-RAG-for-cc/CLAUDE.md`）の「ハマりどころ.md 参照ルール」節を指していると推測されるが、参照を辿るのに 1 ステップ余計な認知負荷がかかる。

**改善提案**:
- 「`research-for-local-RAG-for-cc/CLAUDE.md` の『ハマりどころ.md 参照ルール — 追記ルール』」のようにフルパスで参照を書く
- 引用文言（「新たに発見したハマりどころは、作業中または作業終了時にハマりどころ.mdに追記する」）を脚注ではなく該当箇所のすぐそばに残す（ただし既に引用されているので位置の問題のみ）

## POSITIVE

### U-P-1: I-1 + S-1 をセット反映と明示しているのは良い

**対象箇所**: I-1 レビューイ見解・S-1 レビューイ見解・最終収束判定テーブル

**評価点**:
同一テーブル（§2.1）に対する 2 件の指摘について「v0.9 反映時に一括処理する方が変更履歴も整理しやすい」とレビューイが明示し、レビューア最終所見でも「I-1 とのセット反映（§2.1 表リファクタリング一括処理）も整合的」と確認している。**変更影響範囲が重複する指摘をまとめて処理する設計**は、本体反映時の手戻り・整合性破綻を防ぐ良い運用で、他のクロスレビューでも踏襲したい。

---

### U-P-2: レビューイ収束判定セクションで収束見込みを先出ししているのは良い

**対象箇所**: 「レビューイ収束判定（v0.8 完了時点）」テーブルの「収束見込み」列

**評価点**:
v0.8 時点で「即収束 / 1往復で収束」と収束見込みを明示してあり、レビュー往復回数の予測がつく。作業指示者として「あと何ラウンドで承認できそうか」を見立てるのに直接役立つ情報で、版数管理（0.9, 0.9.1, 0.9.2... の細分化要否判断）にも資する。

- 「指摘 ID が `S-1` `S-2` `S-3` の順で並んでいない章節がある」 → 現状並びに問題なし
