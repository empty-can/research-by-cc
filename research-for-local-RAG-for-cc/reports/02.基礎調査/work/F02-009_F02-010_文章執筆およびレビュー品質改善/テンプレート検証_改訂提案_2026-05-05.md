## 0. v3.0α リリース方針

### 0.1 α 表記の意義

`v3.0α` は以下の方針を明示するための表記:

- **詳細化途上のリリース**: 一部項目（後述 §6 L3 該当）の仕様詳細詰めが完了していない状態でも、必須項目（L1）は早期に運用開始することで実装効果を先取りする
- **運用しながら詰める前提**: L3 該当項目は実テンプレ実装時または初回運用時に仕様を確定する。確定した内容は v3.1 で正式版とする
- **既存運用との互換性確保**: v3.0α 反映後も既存テンプレートの基本構造（指摘エントリの CRITICAL/IMPORTANT/SUGGESTION/POSITIVE 区分・修正案テーブル形式）は維持

### 0.2 v3.0α → v3.1 移行条件

- L3 該当 7 件（§6 で詳細仕様を詰める対象）について、初回運用または別途検討で仕様確定
- L4 該当項目（作業指示者判断要）について、作業指示者の方針確認が完了
- 上記完了後、`α` を外して v3.1 として正式リリース

### 0.3 v3.0α リリース時の懸念リスクと対応

| リスク | 内容 | 対応 |
|---|---|---|
| 仕様未確定項目の運用混乱 | L3 項目の運用判断が分散・属人化する | テンプレ・README に「v3.0α 暫定」と明記し、暫定運用ルールを併記 |
| 既存資産との整合性破綻 | 既存レビュー報告書（02.99 等）との整合性が取れない | 既存資産は機械的置換せず、新規執筆ドキュメントから v3.0α を適用 |
| 用語混乱（押し戻し → 差し戻し） | 過去成果物の用語と新規成果物の用語が混在 | 既存「押し戻し」表現は維持。新規成果物から「差し戻し」で統一（§8.2 参照） |
| L3 詳細化が進まない | 運用しながら詰めるという方針が空文化する | §7 で v3.1 移行条件を明示し、初回運用時に詳細化要件を強制チェック |

## 2. v0.9 検証で抽出されたテンプレート問題

4 つの FB ノートと Round 3 の追記から、テンプレート構造に関する問題を **優先度別** に整理する。各項目に v3.0α 反映時の **項目 ID**（H1〜H5 / M1〜M6 / L1〜L8）を付与した。

### 2.1 高優先（H1〜H5、実運用上の摩擦が大きく、複数視点で一致）

#### 2.1.1 【H1: 両テンプレ】「レビューア最終所見」枠の不在
- **症状**: v0.8 → v0.9 の取り込みフェーズでレビューアが再対応する際、所見を書く既定欄がテンプレに無い。見出しレベル・配置位置・記載項目を毎エントリ個別判断する必要があった
- **論理整合性レビューア**: 「最大の摩擦点」と明記
- **実用性レビューア**: 困り具合「中」だが同様の指摘
- **改訂方向**: 各指摘エントリの末尾（態度表明の直前）に `##### {ID}. レビューア最終所見（{版数}）` を既定欄として追加。サブ項目に「最終結論／最終修正案／収束ステータス／レビューイとの認識一致状況」をテンプレ化

#### 2.1.2 【H2: 実用性テンプレ】「レビューイ見解」欄の不在 + 作業指示者態度表明欄の配置順序
- **症状(1) レビューイ見解欄の不在**: 実用性テンプレには既定セクションが無く、レビューイは記入位置を自分で設計する必要があった
- **症状(2) 作業指示者態度表明欄の配置順序**: 現状の実用性テンプレでは「修正案 → 作業指示者の態度表明」の順で配置されており、レビューイ見解を末尾に追加すると **作業指示者態度表明がレビューイ見解より前** に配置されてしまう構造になる
- **改訂方向**:
  - 実用性テンプレに「レビューイからの見解」欄を既定追加。論理整合性テンプレと同等の構造（同意の程度／同意の根拠／作業指示者向け補足／修正案への見解）にする
  - **配置順序: 修正案 → レビューイ見解 → 作業指示者態度表明**（論理整合性テンプレと同一順序）

#### 2.1.3 【H3: 両テンプレ】指摘エントリ自体に「観点」フィールドが無い
- **症状**: 観点別サマリ表との突合が手作業になる。複数観点にまたがる指摘の主観点割当も指摘本文に残せない
- **改訂方向**: 各指摘の見出し直下に「**観点**: <観点名>」を 1 行追加。複数観点にまたがる場合の運用ルール（主観点割当 + 副次観点を注記）もコメントに記載

#### 2.1.4 【H4: 両テンプレ + README + CLAUDE.md】セルフレビュー運用ルールの欠如

- **症状**: セルフレビューの繰り返し方針（回数上限・終了条件・フェーズ分離）が明文化されておらず、レビューア・レビューイがセルフレビューを過剰に反復する傾向があった
- **議論経緯**: `テンプレート検証_セルフレビュー運用考察_2026-05-05.md` §2 〜 §4 で詳細議論。作業指示者と合意済みの最終版運用提案（同ファイル §4「Claudeからの運用提案（最終版）」）を取り込み対象とする
- **改訂方向**: 以下を一括反映
  1. **`cross-review/README.md` にセルフレビュー運用ルール節を新設**
     - レビューアセルフレビュー（フェーズ分離あり）: 前半 5 回 / 後半 Opus 3 回・Sonnet 4 回（暫定）
     - レビューイセルフレビュー（フェーズ分離なし）: 上限 3 巡
     - レビューア再対応（Round 3）: 上限なし
  2. **両テンプレ冒頭の「レビュアーへの指示」HTML コメントに README 参照必須を明記**
  3. **`research-for-local-RAG-for-cc/CLAUDE.md` §レビュー実施ルール 冒頭注記の強化**

#### 2.1.5 【H5: 両テンプレ + 執筆ガイドライン】ドキュメント全体構成の可視化（目次・リンク化・冒頭サマリ）

- **由来**: v2 トライアル取りまとめサマリ §9.2「作業指示者的に認識しているレビュー対象ドキュメントの要改善点」（2026-05-06 作業指示者記入）
- **症状**:
  - (1) ドキュメント全体構成を把握できる目次の欠落
  - (2) ドキュメント内外の参照の相互リンク化欠如
  - (3) 調査報告書冒頭の調査内容・結果・結論サマリの構成欠如
- **改訂方向**:
  - クロスレビュー両テンプレ: 既定で目次・冒頭サマリを持つため、本項目の主たる適用先は **執筆ガイドライン側**
  - 既定の `cross-review/README.md` に「ドキュメント参照を記載する場合は **必ずリンク化する**」を執筆ルールとして明記
  - **新規ファイル `research-for-local-RAG-for-cc/ドキュメント執筆ガイドライン.md`**（§9.3 完了時点で v2.0 整備済み）に上記 (1)〜(3) を統合済み

### 2.2 中優先（M1〜M6、運用時の判断揺れを生む）

#### 2.2.1 【M1: 両テンプレ】v0.8 / v0.9 / v1.0 列の運用ルール明示不足

  - 観点別件数表で v0.8 から変動なしの場合は「v0.8 と同一」と省略可とする

#### 2.2.2 【M2: 両テンプレ】「収束ステータス」ラベル定義の例示不足
- **症状**: 「達成 / 1ラウンド継続 / 議論継続」の判定基準が個別判断
- **改訂方向**: テンプレに判定基準を例示

  - 1ラウンド継続: レビューイ追加案の採否判断にレビューア側で再検証が必要
  - 議論継続: 認識不一致が残る

#### 2.2.3 【M3: 両テンプレ】IMPORTANT / SUGGESTION 境界の補助基準
- **症状**: 「品質を著しく損なう」「任意採否」の境界が主観的で複数回のセルフレビューが必要
- **改訂方向**: README.md `指摘ラベルの定義` に補助基準として「本文全体を精読しなければ理解できない問題かどうか」「サマリ表など本文を読まずに参照される箇所への影響があるか」を追加

#### 2.2.4 【M4: 論理整合性テンプレ】「敢えての意図」サブ項目の条件化
- **症状**: 「自己判断で敢えてそのような記述にした場合の意図・判断根拠」サブ項目が、整理漏れ・チェック漏れ起因の指摘では「敢えての判断ではない」を毎回書く違和感
- **改訂方向**: コメントに「敢えての判断による意図がある場合のみ記入。無い場合は省略可」と明記。または欄を **条件付き記入欄** に再設計

#### 2.2.5 【M5: 実用性テンプレ】判断依頼サマリーの「該当なし」処理
- **症状**: CRITICAL 0 件の場合、行削除と「該当なし」テキスト記入のどちらが正かテンプレ指示が曖昧
- **改訂方向**: 「該当ラベルの指摘がない場合は、該当ラベル行を削除して『{ラベル}: 該当なし』という独立行を 1 行追加」と明示

#### 2.2.6 【M6: 両テンプレ】観点別サマリ表の振り分けルール明示
- **症状**: 1 指摘が複数観点にまたがる場合の集計ルール不明
- **改訂方向**: 「1 指摘は主観点に 1 件計上。複数観点にまたがる場合は影響が大きい観点を主観点とする。副次観点はコメント注記」を明記

### 3.3 X.3 Round 3 で実装したレビューア確認セクションの仕様

§9.3 Phase X.3 Round 3 で各指摘に追加した **レビューア確認セクション** の具体仕様を文書化する。これは B1（必須反映）の詳細仕様として v3.0α テンプレに既定化する。

#### 3.3.1 配置位置

各指摘エントリ内の以下の位置に追加（論理整合性・実用性・作業指示者レビュー共通）:

```markdown
##### {ID}. レビューア確認（{版数: 例 0.9}）

###### レビューア確認: 問題点（レビューイ回答への反応）

（レビューイの「問題点」への回答に対するレビューア見解）

###### レビューア確認: 修正案（レビューイ回答への反応）

（レビューイの「修正案」への回答に対するレビューア見解）
```

#### 3.3.2 確認セクションの記入項目

各レビューア確認セクションには以下を記入:

| 項目 | 内容 |
|---|---|
| **レビューア態度** | `受容` / `取り下げ` / `重要度変更` / `再指摘` / `修正採用` のいずれか |
| **理由** | レビューイ回答に対する判断根拠（典拠ベース） |
| **最終結論** | 受容: 元の指摘 + レビューイ修正案を確定 / 取り下げ: 指摘自体を撤回 / 重要度変更: 例 IMPORTANT → SUGGESTION / 再指摘: 0.9.1 を発行 / 修正採用: レビューイ提案の改変版を採用 |
| **収束ステータス** | `達成` / `1ラウンド継続` / `議論継続` |

#### 3.3.3 態度区分の定義

- **受容（Accept）**: レビューイの完全同意・部分同意を踏まえ、元の指摘および修正案を確定。最も多いケース
- **取り下げ（Withdraw）**: レビューイの典拠ベース反論で指摘自体が事実誤認・前提取り違えと判明。指摘を撤回（件数表で「取り下げ累計」に計上）
- **重要度変更（Re-label）**: レビューイの提案でラベルを変更（IMPORTANT → SUGGESTION 等）。件数表で重要度別に件数を再計算
- **再指摘（Re-issue）**: レビューイ反論を踏まえてもなお問題が残ると判断。0.9.1 を発行して再ラウンド継続
- **修正採用（Modified Accept）**: レビューイの逆提案・部分反論を取り込んだ改変版を採用。元の指摘と異なる修正案で確定

#### 3.3.4 件数表との連動

レビューア確認セクションの態度区分と、ファイル冒頭の件数表が連動:

- 受容・修正採用 → 現役件数に計上
- 取り下げ → 現役件数から除外、別途「取り下げ累計」を記載
- 重要度変更 → 新ラベルで現役件数に計上、旧ラベルから除外
- 再指摘 → 0.9.1 として枝番管理、件数表は枝番別に作成

### 3.4 F02-009 由来の指摘記載ルール明文化候補

F02-009（クロスレビュー指摘記載ルールとセルフレビュー観点の規定）で起票された明文化候補のうち、v3.0α 反映時に着手するものを整理。

#### 3.4.1 指摘記載ルール

##### 事実認定型 vs 表現改善型の区分
- **事実認定型**: 「{X} は誤っている」「{Y} は不整合」など、事実認定に依拠する指摘
  - 必須項目: 典拠（参照すべき箇所）・誤りの認定根拠
- **表現改善型**: 「{X} の表現は曖昧」「{Y} は冗長」など、表現の改善余地を指摘
  - 必須項目: 改善後の具体例（修正案で明示）

##### 根拠記述要件
- すべての指摘に **典拠** または **判断根拠** を記述
- 典拠が無い場合（推測ベース）は、その旨を明示（例: 「推測ですが」）

##### ラベル選定の補助基準（M3 の具体化）
- **CRITICAL**: 押し戻し（差し戻し）リスクのある本質的問題、または成果物の信頼性を損なう問題
- **IMPORTANT**: 本文の理解・運用に支障が出る問題（修正なしでは品質を損なう）
- **SUGGESTION**: 任意採否の改善余地（修正なしでも運用可能）
- **POSITIVE**: 評価点（強化・横展開を提案する場合あり）

#### 3.4.2 セルフレビューの観点

レビューア・レビューイ各々で実施するセルフレビューの観点を明文化:

##### レビューアセルフレビュー（前半フェーズ: 新規 NG 検出）
- 各観点に新規指摘候補があるか
- 指摘候補の典拠は明確か
- 重複・冗長指摘がないか

##### レビューアセルフレビュー（後半フェーズ: 誤検知チェック）
- 出した指摘が事実認定として正しいか
- ラベル選定が適切か（CRITICAL の過剰計上がないか）
- レビューイから典拠ベース反論で覆る可能性が高い指摘がないか

##### レビューイセルフレビュー
- 立場表明が全件で完了しているか
- 防衛的記述になっていないか（典拠ベースで反論しているか）
- 補正情報の十分性が確保されているか

##### レビューア再対応（Round 3）セルフレビュー
- 取り込み後の文書整合性が保たれているか
- 取り下げ・重要度変更の判断根拠が明確か
- 件数表とレビューア確認セクションが連動しているか

- 指摘記載ルール → **README.md に節として追加**（M3 と統合）
- セルフレビュー観点 → **README.md セルフレビュー運用ルール節に追加**（H4 と統合）

## 4. 作業指示者からの追加リクエスト（A1〜A8）

### 4.1 ドキュメント全般について

#### 4.1.1 【A1】箇条書きの書き方（フォーマット）

以下のルールを制定したい。特に、箇条書きで伝えたい情報量が多い場合に効果が高い。

- 箇条書きの1行目は、その箇条内の主題だけを1文で書くこと。
  - 読み手が主題を迅速かつ明確に把握することを支援するため。
- 2文目以降で書きたい内容は（1行目の書いた主題の詳細情報や補足情報などであるはずなので）、一段下げた箇条として書くこと。
- ある箇条の記載に関連する情報は、その箇条と並列に箇条書きするのではなく、一段下げた箇条として記載し、記載内容の関係性を箇条書きの階層として表現すること。
  - 記載している内容が、どの箇条に関するものかを文章の構造から視覚的に素早く把握できるようにすることが狙い。

**v3.0α 反映方針**: 執筆ガイドライン v2.0 §G2-8 で反映済み（2026-05-06 ガイドライン v1.0 → v2.0 改訂時に統合）。テンプレ側への影響は限定的。

#### 4.1.2 【A2】比較項目については、箇条書きよりも表形式を採用することを検討する

- 見やすさの向上と、過度な箇条書き化によるドキュメントの縦長化を抑えることが意図。
- 比較対象でない情報まで無理に表に収めようとすると可読性が低下するため、そういった部分は表に続けて箇条書きで記載するなど、表形式で記述することに固執しないこと。
- 心がけて欲しいくらいのもの（ルールというよりもガイドライン）。

**v3.0α 反映方針**: 執筆ガイドライン v2.0 §G2-3.2 に反映済み（緩いガイドラインとして整備）。

### 4.2 計画書について

#### 4.2.1 【A3】読了時間に関するコメント

計画書は全記載内容を時間をかけて十分にレビューする必要がある、そういう性質のドキュメントなので、今回の分析に当たっては、分量が多いことに起因する読了時間が長くなることについては、他のドキュメントと異なりとりわけ問題視する必要は無い。
重要なのは以下であり、これは他のドキュメントと同様に、計画書というドキュメントの性質に対応する固有のレビュー観点として、計画書のガイドラインという形で追々整備する必要があるものと認識している。

- ドキュメントの全体構成や各セクションの要点が把握しやすい文章構成になっているか
- 各セクションの記載順序は、理解容易性や妥当性のチェック容易性という面から適切か
- 必要な情報が漏れなく記載されているか
- その他、レビューアの指摘にあるような判断基準やマイルストーンなど計画遂行に必要な観点や方針についても漏れなく記載されているか

#### 4.3.2 【A5】判断依頼サマリー表に記載する（しない）指摘の基準

表に記載される指摘が、作業指示者が優先して回答すべきものに絞られるよう、含めない指摘の基準を追加/明確化:

## 8. 用語整理

### 8.1 「差し戻し」と「手戻り」の概念整理

§9.3 トライアル取りまとめ時の議論で、以下の用語整理に合意した（2026-05-06）:

| 用語 | 意味 | 性質 |
|---|---|---|
| **差し戻し** | 承認権限者が承認時に「これでは GO できない」と判断し、レビュー成果物を執筆者に戻すこと | イベント・原因 |
| **手戻り** | 上流工程の不備に起因して、後続工程の作業がやり直し（それまで実施していた作業が無駄）になること | 現象・結果 |

両者の関係: **差し戻しは手戻りの代表的な原因の一つ**。「差し戻し」を未然に防ぐことが「手戻り」の予防に直結する。

#### 8.1.1 用語登録の取りやめ理由

- Claude Opus 4.7 が両用語を文脈から適切に使い分け可能と判断
- 用語定義の明示文書化は実装コストに見合わないため取りやめ（運用知識として処理）
- 万一誤用が発生した場合は本ファイル §8.1 への追記で再対応する

### 8.2 観点 7 の名称変更（押し戻し → 差し戻し）

#### 8.2.1 変更内容

- 旧名称: 観点 7「**承認の押し戻し条件**」
- 新名称: 観点 7「**承認の差し戻し条件**」（v3.0α 以降の正式名称）

#### 8.2.2 変更理由

- 「押し戻し」は普段使いの語ではなく、作業指示者と Claude の間で意味解釈が分かれる懸念があった
- 「差し戻し」は一般的に「承認権限者が承認時に成果物を執筆者に戻す」意味で使用され、観点 7 の本来の意味と一致

#### 8.2.3 既存資産との互換

- 既存「押し戻し」表現は **機械的置換せず、過去成果物のまま維持**（§9.3 比較分析報告書 §0.1, §4.2 等を含む）
- 新規執筆ドキュメントから「差し戻し」で統一
- 必要に応じて、新規執筆時に「観点 7（旧称: 承認の押し戻し条件）」と注記

#### 8.2.4 v3.0α 反映対象

- テンプレート: 観点 7 に関連する記述（テンプレ内コメント・サマリ表・件数表ヘッダ等）を「差し戻し」に統一
- README: 観点 7 の説明を「承認の差し戻し条件」に変更
- 執筆ガイドライン v2.0: 観点 7 関連箇所の用語を「差し戻し」に統一
- F02-009 別紙: 関連記述を v3.0α 移行時に確認
