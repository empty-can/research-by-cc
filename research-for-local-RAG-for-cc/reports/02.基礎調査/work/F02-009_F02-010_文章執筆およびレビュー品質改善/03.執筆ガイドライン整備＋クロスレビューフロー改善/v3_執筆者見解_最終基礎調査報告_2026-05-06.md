## 1. 執筆過程の所感

### 1.1 ガイドラインの適用しやすさ

- **G1-1 想定読者像 / G1-2 全体構成可視化 / G1-4 内外参照リンク化** は適用が機械的で、執筆開始前にメタ情報・目次を整える流れが自然に確立できた。冒頭サマリ（調査内容 / 結果 / 結論・示唆）の 3 部構成を G1-2 で明示してくれている点は、報告書の骨格決めを大幅に短縮した。
- **G2-1 結論先出し** は「§1 冒頭サマリ」と「§3 採用候補と除外候補（レイヤ別）」で素直に適用できた。各章の最初に「結論または核となる主張」を明示する型がガイドラインで定型化されているため、迷わず書ける。
- **G2-3 パターン化された構造** は §3.1（埋め込みモデル）の各候補で「ライセンス / モデルサイズ・次元・最大トークン / ベンチマーク / 採用根拠 / 注意点」を統一フォーマットで記述する型として活用できた。サブタスク報告書の元データが揃っているため、表 + 統一構造への落とし込みが容易だった。
- **G2-6 データドリブン** は、サブタスク報告書側に既に十分な数値・固有名詞があるため、執筆中にハッジ語化する誘惑が少なかった。

### 1.2 困難だった観点

- **G3-2 全文「重み検査」**: 統合報告書という性質上、「サブタスクからの再掲」と「統合の意義」の境界が曖昧になりやすく、§7（サブタスク 01〜08 の調査結果サマリ）の各項を「§3〜§6 の再掲ではないか？」と問うと削除候補になりがちだった。最終的には「§3〜§6 はレイヤ横断の統合ビュー、§7 はサブタスク単位の参照入口」と役割分担を明確化することで残存させたが、執筆中にこの判断のために 2 回往復した。
- **G3-5 Specificity 三点セット（what / where / evidence）**: 主張ごとに where（該当節リンク）を貼ること自体は機械的だが、「evidence が崩れたときの影響範囲」を 1 件ずつ書き残す観点は自然な記述に紛れ込ませにくく、§9.4 の GO / NO-GO 判断材料セクションに集約する形で対処した。
- **G3-6 想定読了時間との乖離点検**: 21,500 文字 / 想定 20〜30 分は日本語 600〜800 字/分換算で許容範囲内だが、「20〜30 分」と「+50% 以内」のバッファをどこまで取るか、ガイドラインだけでは厳密な判定が難しい。事前宣言の幅を狭めると違反リスクが上がる。
- **G3-7 Devil's Advocate**: 「最強反論」を 1 件ずつ書き残す観点は、報告書の §9.4 GO / NO-GO 判断材料に NO-GO に振れうるリスクとして集約した。一方で、§3 の各採用候補 1 件 1 件に最強反論を併記すると報告書が膨張する。今回は採用候補の「注意点」項目で代用したが、ガイドラインとしてはどの粒度で適用するか曖昧。
- **G3-10 リンクアンカー動作確認**: 日本語見出しのアンカー挙動（GitHub プレビュー / VSCode プレビュー差）は静的検証が難しく、目次リンクが実際に動作するかは GitHub 上で確認する以外に手段がない。本トライアルでは目次の各リンクが GitHub Markdown のアンカー命名規則（小文字化・記号削除・空白ハイフン化）に従うように記述したが、実際の動作確認はトライアル後の運用で実施する想定。

### 1.3 ガイドラインへの改善案

#### 改善案 1: G3-7 Devil's Advocate の適用粒度の明示

**観点**: G3-7 は「主要結論（特に承認判断に影響するもの）」に対して 1 件ずつ実施するとあるが、報告書のどの粒度（章単位 / 節単位 / 主張単位）まで適用すべきかが不明瞭。統合報告書のように主張が多階層で並ぶドキュメントでは、全主張に適用すると本文より反論が長くなる。

**提案**: 「Devil's Advocate は **GO/NO-GO 判断・採用判定など承認判断に直結する主張** に限定して適用する。それ以外の主張に対しては、採用候補なら『注意点』、結論なら『反証時の影響範囲』を 1〜2 行で残す簡略形で代用してよい」と粒度ガイドを追加。

#### 改善案 2: G3-2 重み検査と G2-3 パターン化構造の競合の整理

**観点**: G3-2 は「削れるものはないか」を能動的に問い、G2-3 は「同じ種類の情報は同じ構造で書く」を求める。統合報告書の §7 サブタスクサマリのような「並列構造の保持」は G2-3 を優先すると、G3-2 では削除候補になりがち。

**提案**: G2-3 が優先される場面（パターン化された参照入口・カタログ・サマリ）と、G3-2 が優先される場面（説明文・前置き）を明示する。具体的には「G3-2 重み検査は説明文に対して適用、G2-3 パターン化構造は参照入口・カタログには優先適用」と役割分担を明記。

#### 改善案 3: G3-10 リンクアンカー動作確認の半自動化観点

**観点**: 日本語見出しのアンカー挙動は環境依存で執筆中に検証できない。GitHub Markdown 仕様に従う命名規則（小文字化・記号削除・空白ハイフン化）に倣うのが最も安全だが、ガイドラインはそこまで踏み込んでいない。

**提案**: G3-10 に「日本語見出しのアンカーは GitHub Markdown 仕様（小文字化 / 記号削除 / 空白ハイフン化）に従って記述する。環境差で挙動が揃わない見出しには明示的な HTML アンカー `<a id="..."></a>` を付ける」を追加。または「リンク動作確認は執筆段階ではベストエフォートとし、最終確認は GitHub プレビューで行う」を明記。

#### 改善案 4: 統合報告書向け §4「ドキュメント種別ごとの追加観点」の拡充

**観点**: 現行の §4.2「調査報告書（フェーズ報告書 / 統合報告書）」は 3 観点のみで、統合報告書特有の「サブタスク間の用語不統一・矛盾」「サブタスクからの再掲とレイヤ横断統合の使い分け」のような統合特有の課題に対する観点が薄い。

**提案**: §4.2 に「統合時の用語統一チェック」「サブタスク間の数値差・結論差の併記または優先順位付け」「再掲セクションと統合ビューの役割分担」を追加。

#### 改善案 5: G3-6 想定読了時間の許容バッファの精緻化

**観点**: 「+50% 以内: 許容、+50% 超: 要検討、2 倍超: 要見直し」だが、想定読了時間の事前宣言が幅を持つ場合（「20〜30 分」など）、どちらの値を基準にするかが不明瞭。

**提案**: 想定読了時間の事前宣言は **単一値での宣言を推奨** する旨を G1-1 に追記。または G3-6 で「幅をもって宣言した場合は上限値を基準にする」を明記。

## 3. サブタスク報告書 8 件への評価

### 3.1 全体評価

サブタスク 8 件の調査報告書は、いずれも以下の観点で **統合作業を支援する高い品質** を持っていた:

- **完了条件の明確化**: 各報告書が「採用候補・除外候補・根拠」を明示しており、§3 のレイヤ別整理に直接転記可能だった
- **比較表の整備**: 各サブタスクが冒頭近くに比較表を配置しており、本書 §3 / §4 への転記が容易
- **ハマりどころの抽出**: 各報告書末尾の「ハマりどころ追記候補」セクションが §8.3 の横断ハマりどころ抜粋に直結
- **ライセンス情報の併記**: 全モデル・ツールにライセンスが明記されており、OSS / 商用無料制約への適合判定が容易

### 3.3 統合時に困った点（横断）

#### A. 用語の不統一

| 用語 | サブタスクごとの揺れ | 本書での統一表記 |
|---|---|---|
| 「ハイブリッド検索」/「ハイブリッド RAG」 | 01 / 05 で「ハイブリッド検索」、04 / 07 で「ハイブリッド RAG」 | 「ハイブリッド検索」（検索アルゴリズム文脈）、「ハイブリッド RAG」（パターン分類文脈）と使い分け |

| 「Filesystem Exploration」/「grep/glob」/「Filesystem Exploration RAG」 | サブタスクごとに揺れ | 「Filesystem Exploration」を主、「grep/glob」を補足表現として使用 |
| サブタスク番号の表記（02-07 / 02.07 / 07） | 各サブタスク報告書で揺れ | 本書では「サブタスク 07」で統一 |

#### B. 数値の単位・基準の揺れ

- **チャンクサイズ**: 04 で「文字数」「トークン数」「非空白文字」の 3 単位が混在。日本語トークン膨張の文脈で「トークン数」推奨が結論だが、報告書本文では文字数表記も残っている → 本書では併記で対応
- **モデルサイズ**: GB / MB の表記揺れ。本書では「約 4.6GB」「約 1.2GB」のように統一

#### C. サブタスク間の結論差・矛盾の可能性

明確な矛盾は検出されなかったが、以下は **解釈に注意が必要** な箇所だった:

- **05（検索アルゴリズム）の埋め込みモデル候補**: `multilingual-e5-large` または `bge-m3` を併記。02（埋め込みモデル比較）では bge-m3 を主軸候補化、e5 large は条件付き採用候補という温度差あり。本書では 02 の判定（bge-m3 主軸）を優先
- **04（チャンク）の埋め込みモデル前提**: 768 次元（BGE-M3 等、一般的な OSS embedding）と記述。02 では bge-m3 は 1024 次元 → 報告書間の前提に齟齬。本書 §3.3 では 04 の推奨値そのものに次元依存はないため影響なしと判断

#### D. データ欠落

明確なデータ欠落は検出されなかった。各サブタスクが「課題・制約」「ハマりどころ追記候補」を末尾に置く構造を共通フォーマットで採用しているため、抜け漏れが起きにくい。

### 3.4 統合作業の総合評価

サブタスク 8 件は **統合のしやすさが極めて高い** 状態で揃っていた。理由は以下の 3 点:

1. **共通の章構成パターン**: 各報告書が「調査概要 → 比較表 → 採用候補 / 除外候補 → 課題・制約 → ハマりどころ追記候補」という共通構造を持ち、§3 / §8 への転記が機械的に進められた
2. **ライセンス・Windows 対応・OSS / 無料の制約適合判定の徹底**: 全候補が制約への適合可否を明示しており、§3 の採用 / 除外判定がそのまま使えた
3. **数値根拠の充実**: ベンチマーク・実測値・閾値が具体的に記述されており、本書の「データドリブン（G2-6）」観点を高水準で満たせた

統合時の主な工夫は、(a) 用語統一、(b) サブタスク間の役割分担明確化（§3 はレイヤ横断、§7 はサブタスク参照入口）、(c) 横断的な課題・ハマりどころの §8 への集約、の 3 点に集中した。
