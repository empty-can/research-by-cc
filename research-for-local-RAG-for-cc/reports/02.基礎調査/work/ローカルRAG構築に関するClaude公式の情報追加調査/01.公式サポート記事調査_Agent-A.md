## 1. Projects RAG（起点記事） — **公式 RAG 機能**

### 機能名・正式呼称
- 正式名: **"Retrieval Augmented Generation (RAG) for Projects"**
- 位置づけ: Claude.ai の Projects 機能の自動拡張モード

### 概要
Project の knowledge base にアップロードされたコンテンツが context window 上限に近づいた際、Claude が自動的に「project knowledge search tool」を使ってアップロード文書から関連箇所だけを取得するように切り替わる仕組み。容量を最大 **10x** まで拡張する。

### RAG としての構造
- **検索手法**: 記事には明記なし（"project knowledge search tool" としか表現されていない）
- **チャンク化方針**: 記事には明記なし
- **埋め込みモデル**: 記事には明記なし
- **ストレージ**: 記事には明記なし（Anthropic 内部管理）

### 対応ファイル形式・サイズ・件数の制限
- 対応ファイル: documents, images, and other files（具体形式は記事には明記なし）
- サイズ・件数: 記事には明記なし
- Free プランは **最大 5 projects** まで（Projects 機能側の制限）

### 利用面の前提条件
- **プラン**: 全プラン対応（Free / Pro / Max / Team / Enterprise）と明記
- **Workspace スコープ**: Project 単位
- **API/UI**: **claude.ai (UI) 専用**。API 経由でアクセスする方法は記事に記載なし
- **Claude Code からの呼出**: 記事には明記なし（プロジェクト機能自体が claude.ai UI 機能のため、Claude Code から直接利用する方法は未言及）

### コスト・課金モデル
- 記事には明記なし。Projects 機能自体はプラン内に含まれる。
- 関連: Usage limit ベストプラクティスでは「Project にアップロードしたドキュメントはキャッシュされ、参照時は new/uncached 部分だけが limit に計上される」とある

### ユースケース
- 知識量の多い参照資料（マニュアル、研究論文、コード等）を扱う Project
- context window 上限を超える長大資料を扱いたい場合

### 制約・限界
- **手動制御不可**: ユーザーは RAG モードの起動タイミングを制御できない（自動切替）
- knowledge が閾値を下回ると自動的に context-based 処理に戻る

### 派生関連リンク
- Context window サイズ記事
- Projects 概念記事 / 作成管理記事
- Usage limit best practices
- Google Workspace connectors

## 2. Context Window（参考情報）— **RAG 機能ではない**

### 概要
RAG 機能ではなく **背景情報**。Projects RAG が「いつ起動するか」の閾値を理解する材料。

### 主要数値
- **標準モデル context window**: 200K tokens（有料プラン、~500+ pages）
- **拡張モデル** (Sonnet 4.6 / Opus 4.6 / Opus 4.7): **500K tokens** — 全有料プランのチャット
- **Claude Code 経由の特例**:
  - Opus 4.7: **1M tokens** (Pro/Max/Team/Enterprise の Claude Code)
  - Sonnet 4.6: **1M tokens** (全有料プランの Claude Code、Pro は追加 usage 必要)
- **自動 summarization**: code execution 有効時に context window 上限に近づくと自動で過去メッセージを要約（usage limit には計上されない）

### Projects との関連（同記事内記述）
「Projects は RAG を活用して context window に大量情報を載せる代わりに必要部分だけロードする」と明記 → **Projects RAG が公式に推奨される knowledge 管理経路**であることを補強。

### RAG としての位置づけ

### 対応ファイル形式・サイズ・件数の制限

- Free 5 projects 上限

### 利用面の前提条件
- 全プラン対応（Free 含む）
- RAG 拡張は **有料プラン (Pro/Max/Team/Enterprise) 限定**
- **claude.ai UI 専用**。API 経由のアクセスは記事に明記なし

### Chats 間の知識共有
**「Context is not shared across chats within a project unless the information is added into the project knowledge base.」** → knowledge base への投入が project 内チャット横断の知識共有の唯一手段。

### Team/Enterprise の追加機能

## 6. Files API — **補助的 RAG 部品（公式 RAG ではないがチャンク ストレージ + Citations と組み合わせ可能）**

### 機能名・正式呼称
- **Files API**（Beta、`anthropic-beta: files-api-2025-04-14`）

### 概要
Claude API で文書・画像を事前アップロードし `file_id` で再利用可能にする。**RAG 機能ではない** が、文書ストレージ層として RAG 構成要素になる。

### RAG としての構造
- **検索機能なし**: 単純な KV ストア（file_id → file）
- アップロードした file は Messages API で `document` ブロック / `image` ブロック / `container_upload` ブロックとして参照
- 検索は別途実装（Citations や Search results blocks と組み合わせる）

### 対応ファイル形式・サイズ・件数の制限
| 項目 | 値 |
|---|---|
| 最大ファイルサイズ | **500 MB / file** |
| 組織全体の総ストレージ | **500 GB / organization** |
| 対応 MIME（document block） | `application/pdf`, `text/plain` |
| 対応 MIME（image block） | `image/jpeg`, `image/png`, `image/gif`, `image/webp` |
| 対応 MIME（container_upload） | datasets 等（code execution 経由）|
| ファイル名長 | 1-255 chars、特定文字禁止 |
| 非対応 file 形式 | .csv, .docx, .xlsx, .md → plain text 変換が必要 |

### 利用面の前提条件
- **Claude API / Claude Platform on AWS / Microsoft Foundry で利用可**
- **Amazon Bedrock / Vertex AI では未対応**
- ファイルは API key の workspace スコープ。同一 workspace の他 API key からも参照可
- **Claude Code から利用可能**（API 経由のため）
- ZDR（Zero Data Retention）対象外
- Rate limit: ~100 reqs/min（beta 期間）

### コスト・課金モデル
- **File 操作（upload/download/list/get/delete）は無料**
- Messages リクエスト時の参照は input token として課金
- skills や code execution が生成した file のみ download 可能（user upload file は download 不可）

### ユースケース
- 頻繁参照する文書・画像の再アップロード回避
- code execution 入出力のファイル受け渡し
- citations のソース文書として `file_id` 参照

## 8. Memory tool（API）— **補助的 RAG 部品（just-in-time retrieval）**

### 機能名・正式呼称
- **Memory tool**（`memory_20250818`、GA、client-side execution）

### 概要
Claude が会話間で永続的に情報を保存・取得できる **ファイル仮想ディレクトリ**（`/memories`）。tool call で view/create/str_replace/insert/delete/rename。**ストレージ実装はクライアント側責任**（file / DB / S3 等を実装者が選択）。

### RAG としての構造
- **検索手法**: **ベクトル検索ではない**。`view` で directory listing → 関連ファイル名で `view` 取得という **ファイル名駆動の just-in-time retrieval**
- チャンク化なし、埋め込みなし
- ストレージは利用者実装

### 利用面の前提条件
- **Claude API 経由（Claude Code でも利用可能、API 経由のため）**
- ZDR 対象（クライアント側で実装するため）
- 全モデル対応（具体は Tool reference 参照）

### コスト
- tool 自体は API 課金（input/output tokens のみ）

### ユースケース（公式記載）
- 複数 agent 実行間の project context 保持
- 過去交流・決定・フィードバックからの学習
- 長期 software development の進捗・チェックリスト保存（公式が "multi-session software development pattern" として詳細パターン提示）

### 制約・限界
- Path traversal 攻撃対策をクライアント側で実装する必要
- セッション中断対応のため "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" が system prompt に自動追加
- ファイル名駆動のため **大量ファイル時の発見性は実装者が工夫する必要**（embedding-based search ではない）

### Compaction との組み合わせ
- Memory + Compaction（サーバー側自動要約）の併用が公式推奨

## 9. Tool search tool（API）— **RAG 的だが対象は「tool 定義」(ファイルではない)**

### 機能名・正式呼称
- **Tool search tool**
- 2 バリアント:
  - `tool_search_tool_regex_20251119`（Python regex 検索）
  - `tool_search_tool_bm25_20251119`（natural language → BM25）

### 概要
数百〜数千のツール定義を context に積まずに、**Claude が必要時に検索して on-demand ロード** する仕組み。typical 多 MCP サーバー構成で 55k tokens → 85% 削減を実現。

### RAG としての位置づけ
**「ツール定義に対する RAG」** と言える構造。検索対象は **tool 名 / description / argument 名 / argument description**（文書ではない）。

### 検索手法
- **Regex** バリアント: Python `re.search()` 構文（最大 200 chars）
- **BM25** バリアント: BM25 自然言語クエリ
- **セマンティック検索ではない**（ただし、Custom tool search 実装でクライアント側 embedding 検索に置き換え可能 — cookbook あり）

### 利用面の前提条件
- API（server-side tool）
- 全 paid プラン（API 利用の前提）
- Model: Sonnet 4.0+ / Opus 4.0+ / Haiku 4.5+
- ZDR 対象
- 最大ツール数 **10,000**、検索結果 **3-5 tools/search**

### コスト
- `server_tool_use.tool_search_requests` として usage 計上

### MCP との組み合わせ
- MCP toolset で `defer_loading` をかけ Tool search と組み合わせるパターンが推奨

### Custom tool search 実装
- 公式が **「embedding ベースのクライアント側 tool search を自前実装する」cookbook へのリンクあり** — `https://platform.claude.com/cookbooks/tool_use`

## 10. Search results content block（API）— **公式 RAG 用ファーストクラス機能**

### 機能名・正式呼称
- **Search result content blocks**（`type: "search_result"`）

### 概要
**RAG アプリケーション向けに公式が用意した「検索結果」コンテンツブロック**。Tool 結果として、または top-level user message に search_result を渡すと、Claude は自動で **source 付きの自然な citations** を出力する。

> **公式記述（引用）**: "Search result content blocks enable natural citations with proper source attribution, bringing web search-quality citations to your custom applications. This feature is particularly powerful for RAG (Retrieval-Augmented Generation) applications"

### RAG としての構造
- **検索は利用者側で実装**（=「BYOR: Bring Your Own Retriever」）
- ベクトル検索でも全文検索でも OK
- 検索結果を `{type: "search_result", source, title, content: [text blocks], citations: {enabled: true}}` 形式で渡すと、Claude が **block 単位で精密に引用** する
- citations 粒度: **content 配列の block 単位**（block を細かく分割するほど citation 粒度が細かくなる）

### 2 つの提供方法
1. **Method 1: Tool 結果として** — 「動的 RAG」用途。Claude が tool 呼出 → 自前検索 → search_result 配列を返却
2. **Method 2: Top-level content として** — 事前取得済み search result を user message に直接挿入

### 対応モデル
- Opus 4.7 / 4.6 / 4.5 / 4.1 / 4
- Sonnet 4.6 / 4.5 / 4
- Haiku 4.5 / 3.5 (Bedrock/Vertex のみ)

### 利用面の前提条件
- Claude API / Amazon Bedrock / Google Cloud Vertex AI（すべての主要経路で利用可）
- ZDR 対象
- **Claude Code から利用可能**（API 経由）

### コスト
- 通常の input token 課金
- `cited_text` は output token に計上されない（コスト効率良い）

### ユースケース（公式記載）
- カスタム RAG アプリで「web 検索並みの引用品質」を実現したい時
- 独自 knowledge base / proprietary documents の検索結果に citation を付けたい時

### 制約・限界
- citations は **all-or-nothing**: 1 リクエスト内の search results はすべて enabled かすべて disabled でなければエラー
- Structured Outputs と非互換

## 11. Citations（API）— **Search results block の姉妹機能・公式 RAG 引用基盤**

### 機能名・正式呼称
- **Citations**（document block / search_result block の `citations: {enabled: true}` 設定で有効化）

### 概要
**Claude が文書から回答する際、自動的に正確な引用情報を生成** する API 機能。プロンプトで「引用しろ」と書く方式より引用精度・コスト両面で優れる。

### 対応 document タイプ
| Type | 最適用途 | チャンク化 | Citation 形式 |
|---|---|---|---|
| Plain text | プロセ文書 | **自動 sentence chunking** | Character indices (0-indexed) |
| PDF | PDF | **自動 sentence chunking**（テキスト抽出後）| Page numbers (1-indexed) |
| Custom content | 箇条書き・トランスクリプト等 | **チャンク化なし**（block ごと提供）| Block indices (0-indexed) |

### RAG 設計上の含意
- 公式ヒント引用: **"if you want Claude to be able to cite specific sentences from your RAG chunks, you should put each RAG chunk into a plain text document. Otherwise, if you do not want any further chunking to be done... you can put RAG chunks into custom content document(s)."**
- → **RAG パイプラインで取得したチャンクを直接 document block として渡せば、Claude 側が自動で sentence-level citation を付ける**

### 対応ファイル
- PDF / text/plain は直接 document block 可
- .csv / .xlsx / .docx / .md / .txt は事前にプレーンテキスト変換が必要

### 利用面の前提条件
- 全 active モデル対応（Haiku 3 除く）
- Claude API / Claude Code（API 経由）/ Bedrock / Vertex
- ZDR 対象

### コスト
- 入力 token がチャンク化分わずかに増える
- `cited_text` は output token に計上されない
- 後続ターンで `cited_text` を渡し直しても input token に計上されない

### Files API との組み合わせ
- `source: {type: "file", file_id: "..."}` 形式で Files API 上の文書を document block として参照可能

### 制約・限界
- Citations と Structured Outputs は **非互換**
- 1 リクエスト内で all-or-nothing
- 画像 citations は未対応
- スキャン PDF（テキスト未抽出）は citable にならない

## 最重要発見トップ 3

1. **公式の "RAG 機能" は二層構造**: claude.ai 側に「Projects RAG / Drive Cataloging / Chat Search」(UI 完結・内部実装非公開)、API 側に「**Search results content blocks + Citations + Files API**」(BYOR=Bring Your Own Retriever 型・スキーマ完全公開)。**Claude Code 経由でローカル RAG を組む場合、後者の組み合わせが公式推奨パターン**であり、ローカル RAG が出す chunk を Search results block に詰めて Claude に渡せば、自動 citation 付きで動的 RAG が成立する。

2. **Memory tool は「ファイル名駆動の just-in-time retrieval」であってベクトル RAG ではない**: クライアント側が file/DB/S3 を自由に実装でき、検索戦略も実装者次第。本ワークスペースのローカル RAG が「Memory tool に裏で接続される RAG バックエンド」として位置付けられる可能性が高い。公式の "multi-session software development pattern" は Claude Code のセッション再開シナリオに直結する。

3. **Projects RAG は Claude Code から直接呼べる API 経路が示されていない**: Projects 機能は claude.ai UI 専用と読める記述ばかりで、Claude Code（API 経由）から Project knowledge を検索する公式手段は support 記事にもドキュメントにも記載がない。**→ Claude Code 向けローカル RAG を OSS で構築するスコープは公式機能とほぼ非競合**であり、Search results block + Citations を「Claude への結果引渡し規約」として準拠することで、メイン RAG 機構自体は独自実装する正当性が立つ。
