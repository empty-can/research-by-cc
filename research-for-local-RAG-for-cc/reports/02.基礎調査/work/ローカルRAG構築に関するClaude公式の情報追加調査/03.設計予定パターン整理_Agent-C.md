#### 構成レイヤー別 第一候補（02.99 §2.1 採用候補テーブル要約）

| 構成レイヤー | 第一候補 | 補完／代替候補 |
|---|---|---|
| 埋め込みモデル | **BAAI/bge-m3**（MIT、1024 次元、最大 8192 トークン、約 4.6 GB） | ruri-v3-310m（日本語補完）、Qwen3-Embedding-0.6B（軽量多言語） |

| 検索アルゴリズム | **ハイブリッド（BM25+ベクトル+RRF k=60）+ クロスエンコーダーリランキング** | ハイブリッドのみ（リランカーなし） |
| リランカー | **BAAI/bge-reranker-v2-m3**（MIT、278M） | hotchpotch/japanese-bge-reranker-v2-m3-v1（日本語強化）、ms-marco-MiniLM-L-6-v2（英語低遅延、33.4M） |

| Claude Code 連携方式 | **MCP サーバー型（stdio transport）+ 軽量 SQLite/DuckDB** | Skills 常駐 HTTP サーバー型（自作・高制御性）、Skills CLI 都度起動型（プロトタイプ用途のみ） |

## Part 3: 設計上の重要制約・前提

### 不変条件（CLAUDE.md / 計画書 §1〜§2 由来）

1. **完全ローカル動作**: オンラインサービスに依存しない
2. **OSS または商用利用無料のプロダクトのみ**: Apache 2.0 / MIT を基本、Gemma 独自規約・CC-BY-NC 等は除外
3. **ローカル LLM 構築は行わない**: LLM は Claude Code を利用する前提のため、Ollama 等によるローカル LLM 構築はスコープ外（→ Graph RAG 既製ツールが除外される根拠）
4. **OS**: Windows 11 をプライマリとする
5. **Docker 利用不可**: 現環境は Docker 不在（→ pgvector が本フェーズ検証保留となる根拠）
6. **Claude Code から利用可能であること**: Skills / MCP / CLI のいずれかで連携できる必要あり
7. **データ性質**: 日本語・英語混在、コード（Python/TypeScript）+ Markdown + PDF
8. **ゴール**: 大量ファイルを扱う際の Claude Code のトークン・コンテキスト消費最小化（精度を維持したまま）

### Claude 標準機能では不十分と判断された記述

02.99 §3.7「H1 軸の補正」および 07.§3〜§4 で、以下が明示されている:

- **Claude Code 組み込みの Filesystem Exploration（Bash/Glob/Grep）は対象ファイル数が増えるとトークン消費が線形に増加し、本プロジェクトのゴール（コンテキスト最小化）と相反する**（02.99 §8.2、07.§3 比較表「トークン消費」列）
- **コードグラフ系は file-explorer 比でトークン 1/10 を達成する一方、回答品質は 9 ポイント劣る場合があるため、組み合わせが必要**（02.99 §3.7、07.Codebase-Memory 論文）
- **ベクトル類似度はコードの依存構造（呼び出し関係・型参照・継承）を表現できない → 「沈黙した失敗」リスク**（02.99 §8.2、07.§2.4）
- **MCP サーバー多数登録時のツール一覧だけで ≒55,000 トークン消費**（5 サーバー・58 ツール規模、ハマりどころ #14） → Tool Search 機能（`tool_search=true`）で 85% 削減可能（02.99 §3.6、§8.4）
- **CAG（Context Augmented Generation）は 50 ファイル / 50,000 トークン超で精度劣化**（02.99 §4 H0、01.§5）

### スコープ外として明確に切られているもの

- クラウド RAG サービス（Pinecone / Weaviate Cloud 等の有料 SaaS）
- ローカル LLM のパフォーマンスチューニング（LLM は Claude Code 利用前提）
- Reddit / X / YouTube / LinkedIn / Instagram など信頼性の低い情報源
- 大量ファイル取得は Claude Code 自身ではなく専用ツールに任せる（CLAUDE.md 大前提）
