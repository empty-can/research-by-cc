## 2. 各セクション要旨

### 2.1 Introduction（`introduction.html`）

**原典の要旨**

- LLM は学習データの範囲でしか動けない制約があり、それを埋めるのが RAG。RAG は「(1) 情報取得 → (2) 応答生成」の 2 段構成。
- 本ガイドの目的は **「ナレッジベースのテキスト系コンテンツのフォーマットと執筆スタイルを RAG 向けに最適化する方法を示す」** こと。
- システムレベルでコンテキスト供給プロセスを最適化することを **context engineering** と呼び、agentic RAG（実行前に別の LLM が推論・行動する RAG）でも本質的に重要。
- RAG アーキテクチャがどれほど複雑化しても、**source content の最適化は最も直接的なコンテキスト改善手段**である。

**Objectives（このガイドの達成目標）**

- 構造化・意味的に豊かなソース文書を提供し、トークン使用と冗長性を最適化することで RAG 応答の精度と関連性を向上。
- ソース文書に明確な定義と説明を含めることで、ドメイン固有知識・文脈を RAG に理解させる。
- 一貫したフォーマットと構造化規約により、ナレッジベースのメンテナンスと更新を容易にする。
- 大きなモノリス文書を **小さい self-contained ユニット**に分割することで、RAG ソリューションのスケーラビリティを向上。

**Intended audience**

- LLM アプリを構築する AI エンジニア / データサイエンティスト / データエンジニア / ソフトウェア開発者。vector DB と LLM プロンプトの基礎を前提。

### 2.2 Understanding LLMs and RAG（`understanding.html`）

**原典の要旨**

- LLM の力の源泉は **self-attention 機構と transformer アーキテクチャ**。入力シーケンスの位置や距離によらず文脈を関連付けられる。
- LLM は最新情報や専門領域に弱いため、RAG が retrieval コンポーネントで外部情報を取り込み、materialized prompt として LLM に渡す。
- RAG のワークフロー（diagram の本文要旨）:
  1. ユーザがクエリを RAG アプリに送る
  2. RAG アプリが vector DB（ドキュメント・データ・メディアを保持）に問い合わせる
  3. クエリと格納文書の semantic similarity に基づき関連情報を取得
  4. 取得 context で元プロンプトを augment して LLM エンドポイントに送る
  5. LLM が応答を生成して返す
  6. RAG アプリがユーザに応答を返す
- RAG は 2 ステージプロセス: (1) retrieval（伝統的 IR / dense retriever / 両者の組合せ）→ (2) LLM への materialized prompt 投入。**LLM は retriever 経由の source content の品質に強く依存**する。
- AWS 文脈では Amazon Bedrock を foundation model 入口として例示。

**Vectors and embeddings（小見出し）**

- Vector: 大きさと方向を持つ数学オブジェクト。NLP では語・文・文書を高次元ベクトル空間で表す。
- Embedding: 低次元ベクトル空間でオブジェクトを表現し、ベクトル間の関係が意味的・構文的類似性を捉える。

**Vector databases（小見出し）**

- ドキュメント・クエリ等のベクトル表現を保管・管理する DB。HNSW グラフや KNN アルゴリズム等の特殊データ構造でインデックス化し、近傍探索を高速化。

**Semantic search（小見出し）**

- キーワードではなく意図と文脈を理解する検索。Retrieval strategy の例:
  - **HNSW** — 近傍探索を効率化するグラフベースデータ構造
  - **KNN** — 距離尺度（cosine similarity 等）に基づき近傍 K 件を返す
  - **Cosine similarity** — 高次元空間で 2 ベクトルの方向の類似性を測る
  - **LSH (Locality-sensitive hashing)** — 類似ベクトルを同一/近傍バケットにハッシュし、近似近傍探索を高速化

### 2.3 Challenges in source data（`challenges.html`）

**原典の要旨**

- 多くの企業は人間向けに書かれた既存文書（ハイパーリンク、画像スクリーンショット入り）を RAG に流用するが、それらは **excerpt の token 上限を圧迫**し、retriever 性能を悪化させる。
- 代表的な raw document の問題（6 種）:
  1. **Lack of structured formatting and metadata** — 見出し・サブ見出し・メタデータの欠如により、関連情報の特定と抽出が困難。
  2. **Informal and inconsistent language** — インフォーマルな表現や不統一な用語、未定義略語が RAG を混乱させる。
  3. **Verbosity and redundancy** — 冗長・反復・矛盾する情報が RAG を圧倒し、簡潔で関連性の高い応答を妨げる。
  4. **Ambiguous terms and phrases** — 複数解釈可能な語句が誤解を生み、不正確な応答に繋がる。
  5. **Injection of graphic and hyperlink elements** — 画像・URL 等のグラフィカル要素が retrieval トークン予算を消費し、後続段落のキー情報が欠落する。
  6. **Lack of domain-specific knowledge or context** — 専門概念を文脈なく参照する文書は、ドメインで意味のある応答を妨げる。
- 上記は網羅ではなく出発点。1 文書に複数該当することも多い。

### 2.4 Best practices（`best-practices.html`） — 最重要

**原典の要旨（10 項目）**

1. **Use headings and subheadings properly**
   - 明確な見出し・サブ見出しで構造化し、RAG モデルが文書構造を理解できるようにする。情報のナビゲーションと抽出を改善し、応答品質を向上。

2. **Ensure numbering is sequential**
   - 番号付きリストは番号をスキップせず順番に。明瞭性と一貫性を維持。

3. **Add transitions between list items**
   - 箇条書き間にトランジション（例: "After completing step 2, do..."）を入れて LLM のフローを案内する。

4. **Replace tables**
   - **表は避ける**。多段箇条書きまたは flat-level syntax に変換する。
   - *flat-level syntax* = 階層的従属を持たない同レベルでの並列配置。
   - 多くのインデックス済み文書は左→右に読まれるため、フラット構造は追加次元（表の縦軸）参照なしに情報が流れる。RAG にとって構造化されて消化しやすい形。

5. **Preprocess graphical information for efficiency**
   - マルチモーダル LLM は画像とテキスト両方を取れるが、画像解像度を下げる・冗長画像を削除・グラフィカル要素のテキスト説明を付ける、の 3 点で意味的コンテキストを改善しトークン浪費を防ぐ。アクセシビリティも向上。

6. **Add session starters for common queries**
   - 「ソフトウェアの注文方法は?」のような common query には、読み手を手順に誘導する **session starter**（例: 「ソフトウェアを注文するには以下の手順に従ってください…」）を冒頭に追加する。high semantic matching を作り LLM の応答構築を助ける。

7. **Add summarization to each section**
   - 各見出し／サブ見出しの直後に簡潔な要約を追加。semantic coverage を増やし、key points を補強。embedding 空間内の similarity search 精度を改善。**LLM と人間の両方が読む文書、または表・図表が必要な場合に特に有効**。

8. **Disambiguation**
   - 文書は簡潔で焦点を絞ったものに。LLM は retrieved excerpt に基づき応答を生成するため、曖昧性除去で clear で relevant な情報を使えるようにする。

9. **Define abbreviations and set context**
   - LLM はインターネットの大量データで学習されているが、企業の内部文書文脈は持たない。**コンテキスト設定・略語定義・企業固有用語の回避または定義**が、LLM の企業データ理解と hallucination 防止に寄与する。

10. **Restructure large documents into smaller documents for efficient tagging and indexing**
    - 複数サブトピックを含む大文書をインデックス化することを避け、**明確なタイトルを持つ小さな self-contained 文書に分割**する。インデックス化とタグ付けが改善される。

### 2.5 FAQ（`faq.html`）

**原典の Q&A 一覧**

- **なぜ RAG 向けに文書を最適化するのが重要か?** — 人間向け文書のままだと RAG の性能と精度に悪影響。構造化・曖昧性排除・関連性のある情報を提供すれば改善する。
- **raw 文書のどんな課題が RAG を阻害するか?** — 構造化フォーマット・メタデータの欠如、インフォーマル/不統一な用語、冗長・反復、曖昧な語句、ハイパーリンクの混入、ドメイン文脈の欠如（§2.3 へのリンク）。
- **見出し／サブ見出しはなぜ RAG 性能を高めるか?** — 構造と文脈の理解、関連情報のナビゲーションと抽出を支援。
- **なぜ表をフラット構造に置換すべきか?** — 表は二次元構造の理解を要するため RAG モデルが解釈しにくい。フラットや bulleted list の方が処理しやすい。
- **要約追加はなぜ性能を高めるか?** — 各セクション冒頭の簡潔要約が semantic coverage を増やし、similarity search 精度を改善。
- **略語定義とコンテキスト設定はなぜ重要か?** — LLM は企業特有の略語/用語の文脈を持たないため、定義とコンテキスト提供で hallucination や誤解釈を防ぐ。

### 2.6 Next steps and resources（`next-steps.html`）

**原典の要旨**

- 文書-レベル課題と緩和策のベストプラクティスを業界リーダーへのインタビュー知見と企業ユースケースで裏付けた、と位置付け。

  4. **新規文書向けにガイドラインとテンプレートを確立** — 著者がベストプラクティスを遵守する一貫性を担保。

## 3. 本リポジトリ設計への示唆

### 3.1 ソース文書の前処理・チャンク戦略への示唆

本リポジトリでは Claude Code 公式 docs / Anthropic API docs / MCP プロトコル仕様などを取り込む可能性が高い。AWS ガイドの観点から派生する具体的示唆:

- **ハイパーリンク・URL の前処理** — Claude Code docs の Markdown には大量のリンク（`https://docs.anthropic.com/...` 等）が含まれる。**embedding 対象から URL を除去**するか、リンクテキストのみ残してアンカーを別フィールドに退避する前処理が retriever トークン予算保護に直結する（§2.3-5 / §2.4-5 と整合）。
- **画像・図表の扱い** — Claude Code docs には diagram の画像参照がある。マルチモーダルではなくテキスト RAG として組む場合、**画像 alt text / 図表キャプションをテキスト化したものを別チャンクとして併合**するのが望ましい。
- **章節サマリの自動付与** — AWS の Best Practice #7（Add summarization to each section）を機械的適用するため、**インデックス時に各セクションの最初の N 文を抽出し、章チャンクのプレフィックスとして付与**する。Claude Code docs はもともと構造化されているが、API リファレンス系は記述が淡白で similarity が出にくいため、特に効く想定。
- **大文書の分割** — Claude Code の docs ページ単位ではすでに分割されているものが多いが、**1 ページ内で複数サブトピックを跨いでいるページ**（例: `settings.md`、`hooks-guide.md` 等の長尺）は、見出し階層を境界としてさらに分割する戦略を採るべき（§2.4-10 と整合）。
- **表のフラット化** — Claude Code docs 内には設定キー表や hook 入力スキーマ表が散見される。**Markdown table を `- key: value` 形式の flat list に変換する前処理**を入れると、RAG の理解度が上がる可能性が高い（§2.4-4 と整合）。原典の表は注釈として別チャンクに残し、相互リンクメタデータで結ぶのが妥協案。
- **略語辞書チャンクの併合 retrieval** — Anthropic / Claude 周辺の略語（MCP / LLM / RAG / KNN / HNSW / SDK / CLI 等）と本リポジトリ固有の略語（CLAUDE.md / SKILL.md 等の意味）を **専用辞書チャンクとして用意し、全クエリに併合 retrieval する**設計（§2.4-9 と整合）。

### 3.2 本リポジトリで自前作成する文書の執筆ガイドラインへの示唆

本リポジトリは将来の自身の RAG 入力としても CLAUDE.md / Skill / Rule / 報告書を蓄積する立場にある。AWS ガイドの観点から派生する執筆ガイドラインの強化点:

- **見出し階層の徹底**（§2.4-1） — CLAUDE.md / SKILL.md には既に `## ` 階層運用が定着しているが、**Rule（短文ファイル）でも `### ` 単位の節を切る**ことで chunk 境界の semantic coherence が改善する。
- **番号付きリストのシーケンス維持**（§2.4-2） — レビュー指摘の挿入で番号が飛ぶことが現運用で散発的に起きうる。`cross-review` テンプレ等の更新時に番号整合性チェックを習慣化したい。
- **箇条書き間のトランジション語**（§2.4-3） — 手順記述（`mechanism-builder` の B フロー等）で「次に」「これが終わったら」のような接続語を意図的に置く。
- **表のフラット化**（§2.4-4） — 現状 CLAUDE.md / SKILL.md には設定表や対応表が多い。**人間可読性を損なわない範囲で、表とフラット箇条書きを二重に持つ／表の直後にフラット要約を付ける**戦略が検討候補。
- **session starter の組込み**（§2.4-6） — 各 Skill の SKILL.md 冒頭に「いつこの Skill を使うか」を**ユースケースの定型クエリ文に近い表現**で書くと、Claude Code の Skill 自動発火（description マッチ）にも、将来のローカル RAG にも効く可能性。
- **章節サマリの常設**（§2.4-7） — CLAUDE.md / 長文 SKILL.md の各 `##` 直下に 2〜3 行のセクションサマリを置く運用の検討。**本紙の§0 報告書サマリーと同じ思想を、長文ドキュメント内の各章でも実施する**イメージ。
- **略語定義と context setting**（§2.4-9） — 本リポジトリ固有用語（成果物 / フェーズ / クロスレビュー / mechanism-builder 等）を**ルート CLAUDE.md の冒頭付近に用語集ブロックとして集約**しておくと、RAG 化したとき必ず併合 retrieval される。
- **大文書の分割**（§2.4-10） — ルート CLAUDE.md は既に肥大化傾向。**「Git 運用ルール」「Agent 活用ガイドライン」「外部情報源・経路選択ルール」等を独立ファイル（path-scoped rule 化）に切り出す**判断は AWS ガイドからも追認される。

### 3.3 RAG 評価・FAQ 設計への示唆

- **FAQ 自体が session starter** — AWS ガイドの§2.5 FAQ の Q&A 構造は、そのままユーザクエリ ↔ 該当ベストプラクティス箇所への誘導として機能している。本リポジトリの RAG でも、**Claude Code / 本リポジトリ運用に関する FAQ を準備し、クエリ起点として組込む**ことで session starter（§2.4-6）に近い効果を狙える。
- **評価データセットとしての FAQ** — Q&A ペアは RAG の retrieval 精度評価データセット（gold standard）として再利用しやすい。FAQ を整備すること自体が、評価準備にもなる。
- **disambiguation チェックリスト**（§2.4-8） — 評価時のエラーケース類型として「曖昧な語句に起因する誤答」を独立カテゴリにする。
- **next steps の監査プロセス**（§2.6） — 「既存文書を監査 → 課題特定 → 頻出/重要文書を優先 → SME と協働 → テンプレ整備 → 自動化投資」というプロセスは、本リポジトリでローカル RAG を導入する際の**ロールアウト手順テンプレ**としてそのまま使える。

## 6. 03 設計フェーズへの直接インプット候補

設計判断にそのまま投入できる具体値・スキーマ案・前処理パイプラインの素案を以下に列挙する。

### 6.1 チャンク戦略の具体値（仮提案、03 設計フェーズで実測検証要）

| 項目 | 案 | 根拠（AWS ガイド §） |
|---|---|---|
| チャンク境界 | Markdown の `##` / `###` 見出し階層を境界として優先採用。1 セクション内が長尺（>1500 token 目安）の場合は段落境界でさらに分割 | §2.4-1, §2.4-10 |
| チャンクサイズ目安 | 300〜1000 token 程度の self-contained ユニット（AWS ガイドは具体値非明示だが「self-contained」を強調）。**Claude Code 内蔵機構の SearchResults との互換性**を考慮して上限を設ける | §2.4-10（self-contained 強調） |
| チャンクオーバーラップ | 隣接チャンク間で 1〜2 文程度オーバーラップさせ、境界の semantic 連続性を保つ | §2.4-3（transitions の思想を chunk 境界にも適用） |
| プレフィックス（章節サマリ） | チャンク先頭に「セクション要約（2〜3 行）+ 親見出しパス（breadcrumb）」を機械生成して付与 | §2.4-7 |
| サフィックス（disambiguation） | 略語・固有名詞が含まれる場合、定義スニペットを末尾に付与（または別チャンクで併合 retrieval） | §2.4-9 |

### 6.2 チャンクメタデータスキーマ案

```yaml
# 1 チャンクあたりのメタデータ（仮）
chunk_id: string         # 文書 ID + セクションパスのハッシュ
source_doc: string       # 元ファイル絶対パスまたは URL
source_section_path: list[string]  # ["セクション 2", "2.4 Best practices", "Add summarization to each section"]
summary: string          # 章節サマリ（§2.4-7 由来）。先頭 2〜3 行で自動生成
abbreviations: list[{abbr: string, full: string}]  # §2.4-9 由来
session_starter: string  # §2.4-6 由来。「この章はこういう質問に答える」形式
content_type: enum       # text | code | table_flat | image_alt | abbreviation_dict
original_format: enum    # markdown | html | pdf | code
language: string         # ja | en
char_count: int
token_count: int
flat_table_from: chunk_id  # 表を flat 化した場合、元の表チャンクへのリンク
```

`summary` / `abbreviations` / `session_starter` の 3 フィールドが **AWS ガイド由来の RAG 強化フィールド**で、本紙§5.1「検索結果引渡し規約」の設計にもそのまま流用可能。

### 6.3 前処理パイプライン素案

03 設計フェーズで実装する場合の素案ステップ:

1. **収集** — Claude Code 公式 docs / Anthropic API docs / MCP 仕様 / 本リポジトリの CLAUDE.md / SKILL.md / Rule / 報告書を Glob で列挙。
2. **正規化** — Markdown 化、改行コード統一、見出しレベルの正規化。
3. **リンク剥離** — `[text](url)` の URL 部を embedding 対象から除外し、メタデータに退避（§2.3-5）。
4. **表のフラット化** — Markdown table を `- 列名: 値` 形式に展開し、`content_type: table_flat` チャンクとして格納。原表は別チャンクで保持（§2.4-4）。
5. **画像 alt 抽出** — `![alt](path)` の alt をテキストチャンクとして昇格（§2.4-5）。
6. **見出し分割** — `##` / `###` を境界にチャンク化（§2.4-10）。
7. **章節サマリ生成** — 各チャンクの先頭 2〜3 行を抽出するか、軽量 LLM で要約を自動生成して `summary` フィールドに格納（§2.4-7）。
8. **略語辞書併合** — 全文から略語候補（大文字 2-5 字、定義パターン）を抽出して `abbreviations` 辞書を構築し、専用チャンクとして全クエリに併合（§2.4-9）。
9. **session starter 生成** — 章タイトル + サマリから「この章はこういうユーザ意図に対応」という宣言文を自動生成（§2.4-6）。
10. **重複除去** — verbosity / redundancy 排除のため、chunk 間の cosine similarity が閾値以上のものをマージ候補にフラグ（§2.3-3）。

### 6.4 特筆すべき 3 件（要約）

03 設計フェーズで早期に検証する価値が高いもの:

1. **章節サマリのメタデータ昇格** — §2.4-7 の知見を「サマリ文字列を embedding 計算時に章本文と合体させる」「retrieval 時に章本文と並列で similarity を取り和を取る」など複数手法で実測比較する価値あり。
2. **表のフラット化前処理** — Claude Code docs / MCP 仕様には設定キー表が散在しており、フラット化の効果計測は具体値が出やすい。前処理パイプラインの先行検証対象として最適。
3. **略語辞書チャンクの併合 retrieval** — 本リポジトリ固有略語（CLAUDE.md / SKILL.md / クロスレビュー等）と Anthropic 用語（MCP / Sonnet / Opus / Bedrock 等）を辞書化し、**毎クエリ強制併合**することで disambiguation コストを 1 回の前処理に閉じ込められる可能性。
