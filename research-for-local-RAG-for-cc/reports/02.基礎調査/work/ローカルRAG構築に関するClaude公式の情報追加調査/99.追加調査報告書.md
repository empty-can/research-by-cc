## 0. 報告書サマリー

1. **Claude Code には公式 RAG 機能が存在しない**。Anthropic 公式 glossary(行 18563)が RAG を「Claude プラットフォーム層の概念」として明示的に切り離しており、Claude Code 公式 docs / Help Center 全 19 記事のいずれにも RAG / 検索インデックス / 知識ベース機能の記載なし。

2. **本調査の当初参照記事(Projects RAG)は Claude(SaaS)の機能で本調査スコープ外**。Claude SaaS と Claude Code は別プロダクトであり、Claude SaaS の RAG 機能(Projects RAG / Drive Cataloging / Chat Search / claude.ai Memory)は Claude Code から呼べる公式 API 経路を持たない。詳細は別紙参照。

3. **Anthropic Messages API レイヤの「BYOR スキーマ」機能群(Search results blocks / Citations / Files API / Memory tool / Tool search 等)は、Claude Code から直接 / 間接ともに利用不可と確証された**:
   - **直接利用不可**: Memory tool(`memory_20250818`)について Claude Code 公式 docs / SDK サンプルに該当機能を enable する経路ゼロ(Agent D §4.1)。同型の制約が他 API 機能にも適用される蓋然性が高い
   - **MCP 経由間接利用不可**: 「Claude Code → MCP server → Anthropic Messages API」公式利用フローは存在しない(メインセッション追加検証で 4 経路から確証)

4. **設計予定 15 パターンの接続経路適合性判定**: 完全代替 1 件・部分代替 1 件・Claude Code 標準機構(MCP / Skill / Hook / fileSuggestion 等)と並存 10 件・独自価値の高い領域 3 件・除外確定 1 件。本調査の中核(ハイブリッド検索・コードグラフ・日本語特化)は Claude Code 標準機構ではカバーされず、**独自 RAG 構築のスコープは正当** であることが確定。

5. **検索結果引渡し規約は要再設計**。MCP プロトコル仕様 2025-11-25(2026-05-17 時点で最新版・後継バージョン / draft 公開なし)の tool result `content` 許容 type に `search_result` が含まれず、Anthropic 公式 Citations の自動付与は MCP 経由で実現不可。代替経路 4 案(text 構造化埋め込み / MCP `resource` 系 / hook 経由 / Agent SDK 直接 API)の比較と推奨優先順は §5.1 参照。

## 1. 調査の背景・目的・スコープ

### 1.1 当初の想定と実態の差異(起点記事のプロダクト誤認)

本調査は、Anthropic 公式サポート記事 `https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects` を起点として「**Claude Code 標準 RAG 機能** の有無・カバー範囲」を整理する目的で開始した。

しかし調査過程で、以下が判明した:

- 起点記事のパンくず: `All Collections > Claude > Features and capabilities > Retrieval augmented generation (RAG) for projects`
- 帰属コレクション: **「Claude」(SaaS)**(`support.claude.com/en/collections/4078531-claude`、85 記事)
- 別コレクション「Claude Code」(`support.claude.com/en/collections/14445694-claude-code`、19 記事)は存在するが、**RAG / Projects / Memory 関連の記事は一切含まれない**

→ 起点記事は **Claude(SaaS)の機能の説明** であり、**Claude Code とは別プロダクト** だった。当初想定「Claude Code 標準 RAG 機能との位置づけマップ作成」は前提崩壊。

### 1.2 本調査の真の目的への再定義

前提崩壊を踏まえ、本調査の目的を以下に再定義する:

> **Claude Code 向けのローカル RAG 構築に寄与する Claude 公式情報を網羅整理し、設計予定 15 パターンを Claude Code に統合する際の接続経路・制約事項・推奨設計指針をまとめる**

1. Claude Code 内蔵の progressive disclosure 機構(Skill / Subagent / MCP / Hook / fileSuggestion 等)の整理

## 2. 調査結果: Claude Code が利用できる Claude 公式機能の整理

### 2.1 Claude Code 内蔵 progressive disclosure 機構

Claude Code 自体には RAG / 埋め込みベクトル / セマンティック検索機能は存在しないが(Agent B 公式 docs 全文 Grep で `RAG` / `retrieval-augmented` / `embedding`(ベクトル意味)/ `vector` / `semantic search` がいずれも 0 件)、「**大量データから必要部分を最小コンテキストで取得する**」という RAG 的ユースケースに寄与する標準機構として、以下の **6 系統** が存在する。

#### 2.1.1 機構一覧

| 機構 | progressive disclosure 適合度 | 「大量ファイル → 必要部分」用途への適合 | 出典 |
|---|---|---|---|
| **Skill(`SKILL.md`)** | 公式が用語使用(行 30748)。description 1,536 字のみ常時保持、本文は on-demand | 中(知識・工程ガイド向き、検索エンジン代替ではない) | B-2.1 |
| **Subagent(特に `Explore`)** | 親には要約のみ返却、中間 tool call は親コンテキストから完全分離 | **高**(公式が「verbose output を subagent 内に閉じ込めて summary だけ返す」パターンを推奨) | B-2.3 |
| **MCP servers + MCP Tool Search** | tool 名のみ常時保持、schema は ToolSearch で on-demand fetch、55K → 85% 削減実証 | 高(外部 RAG への標準接続経路。本調査の核心) | B-2.4 |
| **Hook(特に UserPromptSubmit)** | プロンプト発火時に hook が外部システム問い合わせ → `additionalContext` を注入 | 高(外部 RAG の差し込み口として最も汎用) | B-2.5 |
| **`fileSuggestion` setting** | `@` 入力時にカスタムスクリプトが最大 15 件のパスを返す | 中(ファイルパス検索専用、本文取得には別途 Read 必要) | B-2.5 |
| **CLAUDE.md / `.claude/rules/` / auto memory** | 常時 or path-scoped ロード、auto memory はインデックスのみ常時保持 + topic file は on-demand | 中(always-on 知識 / ドメイン特化規約 / Claude 自身の学び蓄積) | B-2.2 |

#### 2.1.2 「RAG 機能なし」公式宣言の根拠

`claude-code-llms-full.txt` 行 18563(glossary):

> "This glossary defines Claude Code terminology. … For model-level concepts like tokens, temperature, and **RAG**, see the [platform glossary]."

→ Anthropic は RAG を **Claude Code のレイヤーではなく Claude プラットフォーム(モデル)のレイヤーの概念** として位置付けている。Claude Code 自体には埋め込みベクトル化・セマンティック検索・ベクトルストアといった機能は **公式ドキュメント内に一切存在しない**。

### 2.2 Anthropic Messages API レイヤの利用可否(決着済み: ✗ 確証)

Anthropic Messages API は、Anthropic 社が開発者向けに提供する **オンラインの HTTP/JSON API サービス**(エンドポイント: `https://api.anthropic.com/v1/messages`、API キー認証)。Claude Code はこの API を内部で呼ぶ消費者だが、「API のどの機能を Claude Code から enable できるか」は別問題。

以下、本調査で確証された結論を整理する。

#### 2.2.1 Memory tool(`memory_20250818`、2026-05-17 時点で最新版)

**結論**: **✗ Claude Code から enable する公式手段は存在しない**(Agent D §4.1 確証)

根拠:
- `claude-code-llms-full.txt` 全文 Grep で `memory_20250818` / `Memory tool` / `memory-tool` ヒット **ゼロ**
- `docs/en/memory`("How Claude remembers your project")は **CLAUDE.md と auto memory の 2 機構のみ** で構成、API Memory tool への言及なし
- `allowedTools` / `--allowedTools` / settings に API beta tool を組み込む経路は公式記述なし
- Memory tool 公式ページ(`https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool`、2026-05-17 時点で全 SDK サンプルが `memory_20250818` ID を使用、Claude Code 統合言及なしを再確認済み)も Anthropic Messages API への直接呼出例のみ
- Claude Code Help Center 19 記事に Memory tool 関連記事なし

留保: Agent SDK で自前ハーネスを構築する場合に限り Memory tool は組み込み可能だが、これは「Claude Code CLI / IDE 拡張」ではなく「Agent SDK で構築した別アプリ」となるため本調査スコープ外。

#### 2.2.2 Search results blocks + Citations の MCP tool レスポンス経由利用

**結論**: **✗ MCP プロトコル仕様レベルで許容されない**(Agent D §4.2 確証)

根拠:
- MCP プロトコル仕様 2025-11-25(**2026-05-17 時点で最新版・後継バージョン / draft 公開なし** を再確認済み。公式 llms.txt 全 22 ページが `2025-11-25` のみ)の tool result `content` 許容 type は **`text` / `image` / `audio` / `resource_link` / `resource` の 5 種閉じた enum**
- `search_result` 型は enum 外、カスタム type 拡張規定もなし
- Anthropic 公式 search-results docs(`https://platform.claude.com/docs/en/build-with-claude/search-results`)は MCP 言及ゼロ、全 SDK サンプルが Anthropic Messages API への直接呼出のみ
- MCP は LLM 非依存プロトコル(OpenAI 等にも実装可能)であり、`search_result` 型は Anthropic Messages API 固有の content block。MCP プロトコル層に持ち込むのは設計レイヤ違反

#### 2.2.3 その他の Anthropic Messages API レイヤ機能(Files API / Citations / Tool search 等)

**結論**: **追加確証は実施せず、Memory tool パターンが支配的と判定して「✗ 利用不可」を確定**

判定根拠:
- Memory tool で確証された「Anthropic Messages API レイヤの機能 = Claude Code から自動的に使えるとは限らない」というパターンが支配的
- かつ §2.3 で確証する通り、MCP 経由間接利用ルートも公式には不在
- 追加調査の期待値はゼロに近い(直接利用ルート不在 + MCP 経由ルート不在)

### 2.3 MCP プロトコル経由の接続経路と制約

#### 2.3.1 MCP プロトコルの設計思想

MCP(Model Context Protocol)は、AI アプリ ← → **外部システム**(local files / databases / search engines / calculators / specialized prompts)を接続する標準プロトコル(`modelcontextprotocol.io` トップより)。

> "MCP is an open-source standard for **connecting AI applications to external systems**."
> "Think of MCP like a **USB-C port** for AI applications."

→ MCP は「**AI アプリ → 外部システム**」方向の接続を想定。「AI アプリ → 別の LLM API」という二次アクセス用途は **設計範囲外**。

#### 2.3.2 「Claude Code → MCP server → Anthropic Messages API」公式利用フローの不在

メインセッションが追加検証で 4 経路を WebFetch + Grep で確認した結果、**該当する公式利用フローは存在しない** ことが強く示唆される:

| 検証経路 | 結果 |
|---|---|
| MCP プロトコル設計思想(modelcontextprotocol.io トップ) | 「AI アプリ → 外部システム」方向、LLM API への二次アクセスは設計範囲外 |
| 公式 MCP サーバ実装一覧(`modelcontextprotocol/servers` リポジトリ) | Reference Servers 7 件(Everything / Fetch / Filesystem / Git / Memory / Sequential Thinking / Time)に Anthropic Messages API / Files API / Citations / Anthropic Memory tool 提供サーバなし |
| Anthropic 公式「MCP connector」(`platform.claude.com/docs/en/agents-and-tools/mcp-connector`) | 方向は **「Messages API → MCP server → 外部システム」で逆方向**、ローカル STDIO サーバは直接接続不可(HTTP/SSE のみ) |
| Claude Code 公式 docs Grep | 該当利用フローへの言及ゼロ |

→ Anthropic Messages API レイヤ機能(Files API / Citations / Tool search 等)の Claude Code 経由利用可能性は **直接・間接ともに不可** と確定。

#### 2.3.3 Claude Code から実際に使える MCP 経由連携

Anthropic Messages API レイヤの機能を MCP 経由で利用するルートは公式に存在しないが、**「Claude Code → MCP server → 外部 OSS 機能」のルートは公式かつ堅牢に提供されている**。本調査の設計予定 RAG パターン群は、このルートに乗せることが想定される(§3 参照)。

詳細制約(Agent B §2.4 / B-2.4 より):
- 3 種の MCP 資産: **Tools**(関数呼出)/ **Resources**(`@server:resource` での attachment 注入)/ **Prompts**(`/mcp__name__prompt` での明示呼出)
- **MCP Tool Search**(`tool_search=true`)が default 有効: tool 一覧が 55K トークン消費する既知のハマりどころに対し 85% 削減を実証
- MCP tool 出力は default 10,000 トークン警告、`MAX_MCP_OUTPUT_TOKENS` で拡張可
- Tool description / server instructions は各 2 KB で truncate
- 接続失敗時は exponential backoff で 5 回まで自動再接続(stdio サーバーは再接続なし)

### 3.3 判定の解説

#### A(完全代替候補)の詳細: パターン 6(CAG)

CAG の本質は「全量を context に載せて検索しない」。Claude Code は **拡張モデルで 1M tokens の context window** を持つ(Pro/Max/Team/Enterprise の Claude Code、Sonnet 4.6/Opus 4.7)。50K トークン以下の静的データは以下の方法で標準機能対応可能:

- **方法 1**: CLAUDE.md or 個別 CLAUDE.md(遅延ロード)に全文を `@import` → セッション開始時に全量保持
- **方法 2**: Skill の SKILL.md に全文埋め込み → ユーザー明示呼び出し / Claude 判定でロード

いずれも Claude Code 標準機能で対応可能。**したがって CAG パターンを「公式機能の境界条件確認」として位置付け直すと、H0 検証の意義はそのまま残しつつ、03 設計フェーズで新規実装すべき独自要素は存在しない**。

#### B(部分代替)の詳細: パターン 5(FilesystemExploration)

FilesystemExploration は「インデックスなし、Bash/Glob/Grep オンデマンド」と定義されており、これは **Claude Code 標準の Glob/Grep/Read ツールそのもの**。さらに `Explore` subagent を使えば「読んで要約だけ親に返す」も標準で実現可能(Agent B §2.3)。

ただし以下の点で標準機能は不足:
- **大規模時のトークン線形増加問題**は未解決(02.99 §8.2、Agent C §3「Claude 標準機能では不十分」)
- 標準 Grep は ripgrep ベースだが、**tree-sitter ベースのシンボル境界検索は標準ツールに存在しない**(パターン 12 / 13 が補う領域)

→ パターン 5 を「H1 検証の必須対照群」として残す意義は変わらない。**ただし計画書では「組み込み Bash/Glob/Grep」と書かれている連携方式を、Subagent(Explore)併用に拡張すべき可能性が浮上**。03 設計フェーズで再検討推奨。

#### C(並存・MCP 経由連携)の詳細: パターン 1〜4, 7〜13

これらは全て「ローカル RAG を MCP server として公開し、Claude Code から MCP 経由で呼ぶ」構造。Claude Code 標準機能 MCP のスコープに**完全に乗る**。MCP 採用時のメリット:

- **Tool Search による on-demand ロード**: MCP tool 一覧が 55K トークン消費という既知のハマりどころ #14(02.99 §3.6)に対し、`tool_search=true` で 85% 削減
- **MCP resources の `@`-mention**: 検索結果を `@server:resource` 形式で attachment 注入
- **`search_result` ブロック直接返却は不可**: MCP プロトコル仕様 2025-11-25(2026-05-17 時点で最新版・後継バージョン / draft 公開なし)の tool result `content` 許容 type は `text` / `image` / `audio` / `resource_link` / `resource` の 5 種閉じた enum(§2.2.2)。`search_result` 型はこの enum 外のため、MCP 経由での Citation 自動付与は仕様レベルで不可。代替案は §5.1 参照

#### D(独自価値の高い領域)の詳細

公式機能にも BYOR スキーマにも対応物がなく、本調査が独自構築する正当性が立つ領域:

1. **ハイブリッド検索ロジック**(BM25 + ベクトル + RRF + クロスエンコーダーリランカー)— 02.99 §3.3 / §3.4 の本命構成。公式は「検索は利用者側で実装」と明示
2. **日本語特化処理**(sudachipy/MeCab + bge-m3 / ruri-v3)— 公式機能で日本語特化処理への言及なし
3. **コードグラフ構造**(tree-sitter + コールグラフ + 影響半径 + 依存トレース)— 「ベクトル類似度はコードの依存構造を表現できない(沈黙した失敗)」(02.99 §8.2) という本質的問題に対し、公式機能には対応物がない

#### E(除外確定)の補足

- パターン 14(狭義 Graph RAG): ローカル LLM 必須 → スコープ抵触で除外確定
- パターン 15(擬似 Graph RAG): Claude Code 自身が依存関係を JSON 化する案。構築・維持コストが高く当面除外、申し送り

### 3.4 「Anthropic 公式ドキュメント検索」ユースケース(派生)の位置付け

CLAUDE.md「Anthropic 公式ドキュメント調査の手順」では現在 `claude-code-llms.txt` + `claude-code-llms-full.txt` + Grep を「暫定運用」としている。**本格 RAG 完成後の置き換え対象**(improvements/C01-001 / C01-003 既登録)。

本調査の追加情報を踏まえた整理:
- Claude SaaS 側の Projects RAG は **別プロダクトの機能** で本ユースケースの実現手段とはならない(別紙参照)
- Anthropic Messages API レイヤの Files API + Search results blocks 利用も Claude Code 経由では不可(§2.2)
- → **本暫定運用の置き換えは、本調査で構築するローカル RAG(MCP server 化)が唯一の現実解**。03 設計の検証用ユースケースに採用する価値あり

## 4. 設計時の制約事項

03 設計フェーズで設計予定パターンを Claude Code に統合する際の制約事項を、本調査の確証結果からまとめる。

### 4.1 MCP プロトコル仕様の制約

- **tool result `content` 許容 type は 5 種閉じた enum**(`text` / `image` / `audio` / `resource_link` / `resource`)。`search_result` 型は許容外(§2.2.2)
- **カスタム type 拡張規定なし**
- MCP プロトコル仕様 2025-11-25(2026-05-17 時点で最新版・後継バージョン / draft 公開なし)

### 4.2 Anthropic Messages API レイヤ機能の利用不可

- **直接利用不可**: Memory tool / Search results blocks / Citations / Tool search 等を Claude Code から enable する公式手段なし(§2.2)
- **MCP 経由間接利用も不可**: 「Claude Code → MCP server → Anthropic Messages API」公式利用フローは存在しない(§2.3.2)
- **唯一の例外**: Agent SDK で自前ハーネスを構築する場合のみ可能だが、本調査スコープ外

### 4.3 Claude Code 標準機構の制約

- **Skill 本文ロード後の永続性**: ロードされた Skill 本文はそのセッション中ずっとコンテキストに残る(再ロードなし)。コンパクション後の再注入は各 skill 最大 5,000 トークン、全 skill 合計 25,000 トークン上限
- **CLAUDE.md は launch 時に全部ロード**: `@import` で物理ファイルを分割してもコンテキスト削減にはならない
- **path-scoped rule はコンパクション後失われる**: 次にトリガーファイルが読まれるまで再注入されない
- **Subagent は他の Subagent を spawn できない**(ネスト構造不可)
- **`fileSuggestion` setting**: 返却パスは最大 15 件
- **UserPromptSubmit hook**: default timeout は 30 秒、hook 出力は会話履歴扱いでコンテキスト消費

### 4.4 既知のハマりどころ(02.99 由来)

- **MCP サーバ多数登録時のツール一覧で ≒55,000 トークン消費**(5 サーバ・58 ツール規模、ハマりどころ #14)→ Tool Search 機能(`tool_search=true`)で 85% 削減可能
- **MCP tool 出力 default 10,000 トークン警告**(`MAX_MCP_OUTPUT_TOKENS` で拡張可)

## 5. 推奨設計指針

### 5.1 検索結果引渡し規約の設計(03 設計時の最優先検証項目)

#### 5.1.1 採用不可と確証された経路

- **Method 1(MCP tool 経由で `search_result` ブロック返却)**: MCP 仕様 2025-11-25(2026-05-17 時点で最新版・後継バージョン / draft 公開なし)で許容されない(§2.2.2)。Claude Code 実装が type を passthrough している可能性はゼロではないが、未文書化の挙動であり公式依存は不可

#### 5.1.2 03 設計フェーズで比較する代替経路

| 経路 | 概要 | 想定メリット | 想定デメリット | 検証コスト |
|---|---|---|---|---|
| **A. text ブロック構造化埋め込み(MCP 標準型のみ使用)** | MCP tool の `text` レスポンス内に `[source: ..., title: ...] 本文` 形式で source/title をテキスト埋め込み | MCP 仕様準拠・追加検証不要・全 MCP パターン共通で即適用可能 | 公式 Citations 機能は使えない(sentence-level citation 喪失) | 低 |
| **B. MCP `resource` / `resource_link` 型で source URI を渡す** | tool レスポンスを `resource_link`(URI 参照)または embedded `resource`(URI + 本文)で返却 | MCP 仕様準拠・Claude 側で `@`-mention attachment 風に扱われる可能性 | Citations 自動付与は同じく不可、Claude の引用挙動は実機検証が必要 | 中 |
| **C. UserPromptSubmit hook の `additionalContext` に Method 2 形式(top-level content)で `search_result` ブロック注入** | プロンプト送信時に hook が外部 RAG 問い合わせ → 結果を top-level content として注入 | Anthropic API レイヤに直接届くため `search_result` ブロックが許容される可能性、Citations 自動付与の可能性 | hook 出力が content block 形式を受けるか未検証、毎プロンプトでのコスト過大懸念 | 高 |
| **D. Claude Code を経由しない直接 API 利用**(参考) | Agent SDK / 自前ハーネスで Anthropic Messages API を直接呼ぶ | `search_result` + Citations を本来通り利用可能 | Claude Code CLI / IDE 拡張のユーザー体験を放棄。本調査スコープ外 | — |

#### 5.1.3 03 設計時の推奨優先順

1. **A を default 規約**(MCP 仕様準拠・追加検証不要・即適用可能)として全 MCP パターン共通で採用
2. **B / C は spike 検証** を 03 設計の早期に実施し、Citations 自動付与が実現できる経路があれば差分採用
3. **D は本調査スコープ外** として参照のみ

#### 5.1.4 失われる便益と代替策

`search_result` ブロックが使えないことで失う主便益は **sentence-level citation の自動付与**。これに対する代替策:

- text ブロック内に source/title を構造化埋め込みすれば、Claude が回答内で「[source: ...]」を再現する自発的引用は期待できる(明示プロンプトで強化可能)
- リランカー段階で各 chunk に `source` メタデータを付与して text ブロック先頭に明示
- 03 設計時に「Claude の自発的引用がどの程度の精度で発生するか」を spike 検証項目に追加

### 5.2 連携経路の選択肢

| 連携経路 | 適合ユースケース | 既知の制約 |
|---|---|---|
| MCP server(stdio) | 全文検索・ハイブリッド検索・コードグラフ | tool 一覧の context 消費(Tool Search 必須) |
| MCP server(HTTP/SSE) | 常駐サーバー型、複数クライアント | 既存 Skills 常駐 HTTP 案と同概念 |
| Skill(CLI 都度起動) | プロトタイプ用途のみ | モデルロード 8-9 秒(bge-m3 で悪化見込み) |
| **fileSuggestion setting** | ファイルパス検索(`@`-mention 拡張) | 返却 15 件まで、本文取得は別途 |
| **UserPromptSubmit hook** | プロンプト発火時の自動 context 注入 | timeout 30 秒、hook 出力サイズ注意 |
| **MCP resources の @-mention** | 検索結果の attachment 注入 | tool との使い分け要設計 |
| **MCP prompts** | 定型クエリ + 結果取得の 1 コマンド化 | 利用者が `/mcp__name__prompt` 明示呼び出し |

### 5.3 Claude Code auto memory との連携設計(Memory tool 概念の取込み)

**本節の結論**: Memory tool API への直接バックエンド化は不可(§2.2.1)だが、Claude Code auto memory と Memory tool は設計思想が対応関係にあるため、設計予定パターンを auto memory の補強・拡張機構として位置付ければ Memory tool 思想に乗ったまま運用可能。

#### 5.3.1 Memory tool(API)と Claude Code auto memory の設計思想の対応関係

| Memory tool(API)の特性 | Claude Code auto memory の対応 |
|---|---|
| `/memories` 仮想ディレクトリ | `~/.claude/projects/<project>/memory/` 物理ディレクトリ |
| `view` で directory listing | セッション開始時に MEMORY.md 先頭 200 行 / 25KB を自動ロード |
| 関連ファイル名で `view` 取得 | Claude 判定で topic file を on-demand Read |
| ストレージは利用者実装 | machine-local、リポジトリ単位、Claude 自身が編集 |
| just-in-time retrieval | 同上 |

→ 構造的に類似(実装インタフェースは異なる)。設計予定パターンを **「Claude Code auto memory の topic file を補完・拡張する外部 RAG レイヤ」** として位置付ければ、Memory tool 思想に乗ったまま運用可能。

#### 5.3.2 具体連携イメージ(03 設計時の検討項目)

- **a. auto memory ↔ ローカル RAG の手動 sync**: Claude が auto memory に書き込んだ知識を、人間が定期的に RAG インデックスへ batch sync(最も単純)
- **b. UserPromptSubmit hook 経由で RAG 結果を auto memory に注入**: hook が外部 RAG 問い合わせ結果を `additionalContext` に載せ、Claude が auto memory への保存判断を行う
- **c. MCP server 経由で auto memory 補完**: ローカル RAG MCP server を呼んだ後、Claude が結果を auto memory の topic file に追記する運用を Skill で標準化

03 設計時にいずれを採用するかは未確定。**a が最小コスト、b / c が自動化度の高い候補**。

### 5.4 「公式機能で代替可能な領域を二重構築しない」原則

本調査の関心は「Claude Code から呼べるローカル RAG」だが、**Claude Code 内蔵の progressive disclosure 機構(Skill / Subagent / MCP Tool Search)でカバーできる範囲は二重構築しない** ことが望ましい:

- **「知識・ワークフロー」レベル**: Skill で十分。RAG にしない
- **「特定ファイルパスでのドメイン規約」**: `.claude/rules/`(path-scoped)で十分。RAG にしない
- **「大量ファイルの探索 → 要約」**: 標準 Subagent(Explore)で代替可能か比較対象に。FilesystemExploration(パターン 5)対照群はこの観点で意義
- **「大量データに対する意味検索・ハイブリッド検索・コード構造解析」**: これが本調査の真の独自価値領域(D 判定)

### 5.5 H0 / H1 検証の解釈アップデート

| 仮説 | 02.99 時点の理解 | 本調査後の解釈アップデート |
|---|---|---|
| H0(CAG 成立) | 50 ファイル/50K トークン以下で有効 | **本質的に「Claude Code 標準機能で代替可能な境界条件」と一致**。CAG 実装の独自要素はゼロ。検証は標準機能の境界判定として実施 |
| H1(FilesystemExploration vs ベクトル) | コードグラフ+シンボル検索 vs 汎用ベクトルへ補正済 | **対照群を「Bash/Glob/Grep」のみではなく「+ Subagent(Explore)」併用に拡張すべき**。Subagent 併用が標準機能の真の天井 |
| H2(常駐 vs CLI) | CLI 都度起動 8-9 秒 | Claude Code 標準の MCP は **stdio サーバーが標準**(再接続なし)。常駐 HTTP も公式 MCP transport で実現可(不変) |
| H3〜H5 | (独自価値領域) | 公式機能には影響なし、調査継続 |
