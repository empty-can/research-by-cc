## 1. 調査概要

本調査では、ローカルRAGシステム構築に向けて、チャンクサイズ / オーバーラップ / 重複排除 / メタデータ設計のベストプラクティスを収集した。対象データの特性（Python・TypeScriptコード / Markdownドキュメント / PDF仕様書）に対応した推奨値を、2024〜2026年の文献・ベンチマーク・実装事例をもとに整理する。

調査の主要な知見は以下の通り。

- チャンクサイズに「万能な正解」は存在しない。ただし **256〜512 トークン + 10〜20% オーバーラップ** が一般的な出発点として広くサポートされている
- コードは AST ベースのチャンキングが固定サイズ比で大幅な性能向上（Recall@5 で +4.3 pt）を示す
- Markdown はヘッダー階層を分割単位とする「構造認識チャンキング」が最もコンテキストを保持できる
- PDF は前処理（OCR・Markdown 変換）の品質がボトルネックとなり、変換後は再帰分割またはページ単位が有効
- 日本語を含む混在コーパスでは、文字数ではなく **トークン数** を基準にサイズを管理することが必須

## 2. データ種別ごとの推奨チャンク戦略

### 2.1 コード（Python / TypeScript等）

#### 推奨チャンクサイズ
- **一次推奨**: AST ベース（関数・クラス単位）で意味的境界に合わせてチャンクを作成し、上限を **1,000〜1,500 非空白文字**（非空白文字カウントで管理。100〜200 トークン相当）に設定
- **代替（AST が使えない場合）**: 再帰分割で 512〜1,024 トークン、オーバーラップ 10〜20 行

#### 分割手法
- **推奨**: AST パーサー（tree-sitter）による構造認識チャンキング
  - 分割単位: `function_declaration`, `class_body`, `method_definition`, `import_statement` などの AST ノード
  - ノードがサイズ上限を超える場合は再帰的に子ノードへ分割
  - サイズに収まる隣接ノードは贪欲にマージして断片化を防ぐ
- **チャンクに付加するコンテキスト**: ファイルパス・スコープチェーン（`UserService > getUser`）・エンティティシグネチャ・使用インポートをチャンク先頭にプレフィックスとして追加することで埋め込み品質が向上する（code-chunk 実装）

#### オーバーラップ
- AST ベースでは原則不要（構造単位で完結）
- ただし境界付近のコードを補完したい場合は `overlapLines: 10` 程度を設定可能

#### 根拠
- cAST 論文（EMNLP 2025 / CMU）: AST チャンキングにより RepoEval Recall@5 で **+4.3 pt**、SWE-bench Pass@1 で **+2.67 pt** の改善
- StarCoder2-7B での評価: RepoEval で平均 **+5.5 pt**
- 固定長チャンキングは関数を中途で切断し、埋め込みベクトルが「未完成の文脈」を表現してしまうため精度が低下する

---

### 2.2 Markdown

#### 推奨チャンクサイズ
- **ヘッダー単位分割** を基本とし、過大セクションには再帰分割で **800〜1,200 文字**（英語なら約 250〜400 トークン）の上限を設ける
- 日本語混在時は文字数ではなくトークン数で管理（例: `chunk_size=512` トークン相当）
- オーバーラップ: **10〜20%**（セクション間で共有情報がある場合）

#### 分割手法
- **一次推奨**: MarkdownHeaderTextSplitter（LangChain）でヘッダー階層（`#`, `##`, `###`）を分割ポイントに使用。各チャンクにヘッダーパス（`H1 > H2 > H3` 形式）をメタデータとして付加
- 一つのセクションが上限を超える場合は RecursiveCharacterTextSplitter で二次分割
- 日本語文書のセパレータ例: `["\n## ", "\n### ", "\n\n", "\n", "。", ""]`
- コードブロック（`` ``` ``）は分割しない（コードブロックの内側に改行が含まれるため、通常の改行区切りでは誤分割しやすい）

#### ヘッダー活用の是非
- **是**: ヘッダー構造が一貫しているドキュメント（API リファレンス、仕様書、技術ブログ）
- **否（代替に再帰分割）**: ヘッダーが少ないまたは不規則なドキュメント（README の断片、メモ）

#### 根拠
- Weaviate blog（2025）: 「ドキュメント構造に基づいた分割はセマンティック境界とも一致しやすく、文書ベースチャンキングはコード・Markdown に最適」
- Unstructured.io（2024）: 「By title 戦略により、異なるセクションの内容が一つのチャンクに混在することを防ぎ、検索精度が向上する」
- 日本語ではトークナイザーによる差異が大きく（英語の 2〜3 倍のトークンになる場合がある）、文字数ベースでの管理は想定外のチャンク肥大を招く

### 2.3 PDF / 仕様書

#### 推奨チャンクサイズ
- **前処理後（Markdown/テキスト変換済み）**: 512〜1,024 トークン、オーバーラップ 10〜20%
- **ページ単位チャンキング（構造的なPDF）**: 各ページを 1 チャンクとして扱うことも有効（NVIDIA 2024 ベンチマークで最高精度 0.648）
- オーバーラップ: セクション境界で情報が分断される場合に 10〜15% を設定

#### 分割手法
- **推奨前処理フロー**:
  1. OCR（スキャン PDF の場合）または PDF パーサー（pymupdf, pdfminer, unstructured）でテキスト抽出
  2. Markdown 形式に変換（見出し・表構造を保持）
  3. MarkdownHeaderTextSplitter またはページ単位分割を適用
- **表・図表の扱い**: 表は分割しないよう制御。表全体を 1 チャンクとし、テーブルメタデータ（ページ番号・テーブル番号）を付加
- **ページ境界の扱い**: ページをまたぐ文は、オーバーラップで吸収するか、文境界まで遡って分割位置を調整する

#### 根拠
- NVIDIA 2024 ベンチマーク: ページ単位チャンキングが 0.648 の精度で最高、標準偏差が最小（=結果が安定）。ただし「ページ区切りが意味的に適切」な場合に限定
- Weaviate（2025）: 「PDF は視覚フォーマットのため、テキスト抽出の信頼性を高めるには Markdown への前処理変換が最も確実なアプローチ」
- スキャン PDF や列レイアウト PDF は、直接テキスト抽出すると読み取り順序が崩れるため OCR + レイアウト解析（unstructured / Azure Document Intelligence 等）が必要

## 3. チャンク手法の比較表

| 手法 | 対象データ | チャンクサイズ目安 | オーバーラップ | 精度 | コスト | 実装難度 | 主な弱点 |
|---|---|---|---|---|---|---|---|
| **固定長（トークン）** | 全般 | 256〜512 トークン | 10〜20% | 低〜中 | 低 | 低 | 文・関数・段落を途中で切断 |
| **再帰分割** | テキスト・Markdown | 512〜1,024 トークン | 10〜20% | 中 | 低 | 低 | 表・コード構造を崩すことがある |
| **セマンティック分割** | 長文・論文・記事 | 可変（平均 43〜200 トークン） | 不要（境界で切る） | 中〜高 | 高（全文センテンス埋め込み） | 中 | 最小チャンクが短すぎて文脈不足になりやすい |
| **ヘッダーベース（Markdown）** | Markdown・HTML | ヘッダー単位（上限あり） | 10〜20% | 高（構造文書） | 低 | 低 | ヘッダーのない文書では適用不可 |
| **ページ単位** | PDF | ページ = 1 チャンク | なし | 高（構造的PDF） | 低 | 低 | テキスト重複・巨大ページに弱い |
| **AST ベース（コード）** | Python / TypeScript | 関数・クラス単位（上限 1,000〜1,500 非空白文字） | 0〜10行 | 高 | 中（パース処理） | 高 | 言語ごとのパーサー設定が必要 |
| **構造認識（Unstructured）** | Markdown / HTML / PDF | 要素単位（上限付き） | なし | 高 | 中 | 中 | ライブラリ依存 |
| **Late Chunking** | 全般（長文書） | チャンク後に切り出し | なし | 中〜高 | 中（全文埋め込み） | 中 | 全文エンコードが必要（長文書では遅延） |
| **LLM ベース** | 複雑な混在文書 | 可変 | なし | 最高 | 高 | 高 | コスト大・速度低 |

**推奨デフォルト（本プロジェクト向け）**:
- コード → AST ベース（tree-sitter）
- Markdown → ヘッダーベース + 再帰分割（二次）
- PDF → 前処理後にページ単位 or 再帰分割

## 4. 重複排除・メタデータ設計の方針案

### 4.1 重複排除の方針

#### 二段階重複排除アーキテクチャ（推奨）

**フェーズ1: インデックス登録時（イングレスション）**

| ステップ | 処理 |
|---|---|
| 1 | チャンクテキストを正規化（空白・改行の統一） |
| 2 | SHA-256 などのハッシュを計算し、完全一致チャンクを即座に除外 |
| 3 | 埋め込みベクトルを生成し、コサイン類似度 >= 0.90 の近似重複を検出 |
| 4 | 完全一致（ハッシュ一致）→ 静かに除外 |
| 5 | 近似重複（ハッシュ不一致、類似度 >= 0.90）→ 残した方の顕著度を +15% ブースト |

**フェーズ2: 検索時（リトリーバル）**

| ステップ | 処理 |
|---|---|
| 1 | 検索スコア順に結果をソート（RRF / 密度スコアなど） |
| 2 | スコア順に走査し、既選択チャンクとのコサイン類似度 >= 0.90 のものをスキップ |
| 3 | LLMに渡す前に重複排除済みの Top-K を提供 |

#### 閾値の根拠
- 類似度 0.90: NVIDIA NeMo がセマンティック重複排除に採用する業界標準（0.90〜0.92）
- 完全一致はハッシュで高速処理し、近似重複のみ埋め込み比較を行うことで計算コストを抑制

#### 留意点
- LSH（Locality-Sensitive Hashing）を大規模コーパス（>10万チャンク）では検討する
- クロス言語重複排除（日本語チャンクと英語チャンクの意味的重複）は誤排除リスクがあるため、原則として非推奨

---

### 4.2 メタデータ設計の方針

以下のフィールドを各チャンクに付与する。

#### 必須メタデータ

| フィールド名 | 型 | 説明 | 例 |
|---|---|---|---|
| `source_path` | string | リポジトリルートからの相対パス | `src/utils/parser.py` |
| `document_id` | string | ファイルの UUID または一意 ID（ファイル内容のハッシュを推奨） | `sha256:abc123...` |
| `chunk_id` | string | ドキュメント内でのチャンク連番（0-indexed） | `chunk_0042` |
| `language` | string | コード言語 or ドキュメント種別 | `python`, `typescript`, `markdown`, `pdf` |
| `chunk_text_length` | int | チャンクの文字数 | `1240` |

#### 推奨メタデータ

| フィールド名 | 型 | 説明 | 例 |
|---|---|---|---|
| `start_line` | int | 元ファイルでの開始行番号 | `42` |
| `end_line` | int | 元ファイルでの終了行番号 | `87` |
| `section_headers` | list[string] | 上位ヘッダーの階層パス | `["## セットアップ", "### 依存関係"]` |
| `entity_type` | string | コードの場合のエンティティ種別 | `function`, `class`, `method` |
| `entity_name` | string | コードの場合の関数/クラス名 | `calculate_total` |
| `scope_chain` | string | 親スコープのパス | `UserService > getUser` |
| `created_at` | ISO 8601 | ファイルの最終更新日時 | `2026-04-01T12:00:00Z` |
| `page_number` | int | PDF の場合のページ番号 | `5` |

#### メタデータ活用パターン
1. **フィルタリング**: `language=python` かつ `section_headers` に `"テスト"` を含むチャンクのみ検索
2. **ソース引用**: `source_path` + `start_line` から元ファイルの正確な位置を提示
3. **デバッグ**: `chunk_id` でどのチャンクが使用されたか追跡可能
4. **増分更新**: `document_id`（ファイルハッシュ）の変化を検出し、変更ファイルのチャンクのみ再生成

## 6. 採用候補戦略の整理

本プロジェクト（OSS のみ・ローカル構築・Windows 11）向けの採用候補を以下に整理する。

### コード（Python / TypeScript）向け

**第1候補: tree-sitter + ASTChunk / code-chunk**

- OSS ライセンス: tree-sitter は MIT。ASTChunk（PyPI: `astchunk`）は Python 向け OSS、code-chunk（npm）は TypeScript 向け OSS
- 性能: cAST 論文で証明済み（Recall@5 +4.3pt）
- 注意点: tree-sitter の言語パーサー（`tree-sitter-python`, `tree-sitter-typescript`）の事前インストールが必要

**第2候補: LangChain RecursiveCharacterTextSplitter（コード特化セパレータ）**

- コード向けセパレータ（`"\n\nclass "`, `"\n\ndef "` など）を指定することで AST なしでも関数・クラス単位の近似分割が可能
- 実装コストが低く、ベースライン構築に適している

### Markdown 向け

**第1候補: LangChain MarkdownHeaderTextSplitter + RecursiveCharacterTextSplitter（二段階）**

- MarkdownHeaderTextSplitter: セクション単位に分割し、ヘッダー階層をメタデータに保存
- RecursiveCharacterTextSplitter: 大きすぎるセクションを二次分割
- 完全 OSS（MIT）、Windows 11 での動作実績あり

### PDF 向け

**第1候補: pymupdf4llm（前処理）+ MarkdownHeaderTextSplitter（分割）**

- pymupdf4llm は PyMuPDF（AGPL）ベースで PDF を Markdown に変換。商用利用はライセンス確認が必要（フリープランあり）
- 代替（商用利用フリー確実）: pdfminer.six（MIT）でテキスト抽出後に再帰分割
- unstructured（Apache 2.0）: PDF・画像・Office 文書を統一 API でチャンキング可能な最有力 OSS

## 7. 課題・制約

### 将来解決が必要な課題

1. **チャンクサイズ最適値の実験的決定**: 本調査は文献ベースの推奨値を整理したが、実際のコーパス（本プロジェクト対象リポジトリ）での最適値は RAGAs・Hit Rate・MRR などの評価指標を用いた実験で決定する必要がある
2. **日本語トークン数の事前見積もり**: 使用する埋め込みモデルのトークナイザーによって日本語のトークン数が大きく変わる。選定した埋め込みモデルで代表的ドキュメントのトークン数を計測した上でチャンクサイズを設定する
3. **PDF の前処理品質問題**: スキャン PDF・複雑なレイアウトの PDF は OCR + レイアウト解析が必要であり、抽出品質がチャンク品質に直結する。処理フローの検証が必要
4. **インクリメンタル更新時の重複排除**: ファイルを部分更新した際に既存チャンクとの重複を正しく解消する更新フローの設計が未検討

### 解決不能な課題

1. **汎用的な最適チャンクサイズ**: 文献・ベンチマークが一致して「ユースケースと文書特性に依存する」と結論しており、「全データ種別で最適な単一値」は原理的に存在しない。A/B テストによる継続的最適化が現実的

### 解決不要な課題（参考情報）

1. **クラウド依存の高精度手法**: LLM ベースチャンキング（最高精度だがコスト大）は本プロジェクトのローカル・OSS のみ制約に適合しないため採用対象外
2. **セマンティックチャンキングの単独採用**: Vectara 2026 の検証で平均 43 トークンの過小チャンクを生成し精度が低下することが判明。最小チャンクサイズの下限設定（>=150 トークン）が必要であり、ヘッダー構造のある本プロジェクトの対象データに対しては構造認識チャンキングの方が適している

## 8. ハマりどころ追記候補

以下は実装フェーズで問題になりやすいポイント。後続の「ハマりどころ.md」への追記候補として整理する。

1. **日本語・英語混在テキストのトークン数膨張**: `chunk_size=512` と設定しても日本語部分でトークンが想定の 2〜3 倍になり、実際のチャンクが極端に短くなる。tiktoken（OpenAI）や sentencepiece ベースのトークナイザーで事前に実測してから設定する
2. **tree-sitter パーサーのバージョン依存**: `tree-sitter-python`, `tree-sitter-typescript` は tree-sitter 本体とのバージョン互換性が厳しく、バージョンミスマッチで parse が失敗しやすい。インストール時のバージョン固定が重要
3. **Markdown コードブロック内の誤分割**: RecursiveCharacterTextSplitter でセパレータに `"\n"` を含めると、コードブロック（` ``` ` 〜 ` ``` `）内部の改行で誤分割される。コードブロックを先に抽出してからテキスト部分のみを分割するか、MarkdownHeaderTextSplitter を使用する
4. **PDF テキスト抽出の読み取り順序崩れ**: 2 カラムレイアウトの PDF を pymupdf や pdfminer で抽出すると、左右カラムが混ざった順序でテキストが取得される。unstructured + hi-res モデルまたは Azure Document Intelligence でレイアウト解析を適用する
5. **重複排除の過剰適用**: コサイン類似度の閾値（0.90）は「同じ概念を異なる言い方で説明した文」を誤って重複と判定することがある。特に短いコードコメントやリスト項目で誤排除が起きやすいため、最小文字数フィルタ（例: 100 文字未満は重複排除スキップ）を設ける
6. **オーバーラップによるインデックス肥大**: オーバーラップを 20% より大きく設定すると同一情報が複数チャンクに含まれ、ベクトル検索の結果に重複した情報が返されやすくなる。検索時の重複排除と合わせて設計する
7. **コードエンティティのドックストリング欠如**: tree-sitter で抽出したエンティティにドックストリングがない場合、コンテキストプレフィックスを付けても埋め込み品質が向上しにくい。関数シグネチャのみでも付加する価値はあるが、ドックストリング生成の前処理（LLM で補完）も検討対象
