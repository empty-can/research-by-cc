## 1. 調査概要

本ユースケースは「日本語・英語混在、コード（Python/TypeScript）・Markdownドキュメントを扱うローカルRAGシステム」への埋め込みモデル適用を前提とする。調査方針として以下を設定した。

- **スコープ**: ローカル動作可能・OSS系（商用利用無料）モデルのみ。有料APIは参照比較のみ
- **評価軸**: 多言語対応可否（特に日本語）・日本語精度（JMTEB/MTEBスコア）・ライセンス・モデルサイズ・次元数・コード検索適性
- **参照ベンチマーク**: MTEB Multilingual（多言語）、JMTEB（日本語専用）、MIRACL（多言語検索）、BEIR（英語検索）

WebSearch・WebFetchにより8件以上のモデルについて公式Hugging Faceモデルカード・技術ブログ・ベンチマーク記事を収集し、2025年9月以降のモデル（EmbeddingGemma）を含む最新情報を反映した。

## 3. 採用候補と除外候補

### 3.1 採用候補

#### 第一推奨: BAAI/bge-m3

**根拠**:
- MIRACL多言語ベンチマークにおいてnDCG@10=70.0を記録し、100言語以上をカバーする多言語モデルとして最高水準
- 日英混在・コード・Markdownという本ユースケースの多様なデータに単一モデルで対応可能
- **Dense（セマンティック）・Sparse（キーワード）・ColBERT（多ベクトル）の3種類の出力を同時生成できる唯一のモデル**。ハイブリッド検索構築が容易
- 最大8192トークン対応で長文チャンクにも対応
- MITライセンスで商用利用制限なし
- **注意**: 約4.6GBとモデルサイズが大きく、GPUメモリ9GB程度が推奨されるがCPU動作も可能

#### 第二推奨: cl-nagoya/ruri-v3-310m（日本語補完用途）

**根拠**:
- JMTEB平均スコア77.24は日本語埋め込みモデルの現時点SOTA（2025〜2026年時点）
- ruri-v3-30mでもJMTEB 74.51とOpenAI text-embedding-3-largeを上回る報告があり、コストパフォーマンスが高い
- Apache 2.0ライセンスで商用利用制限なし
- 8192トークン対応
- **注意**: 日本語専用のため、英語・コード中心のドキュメントには単独での採用は不向き。bge-m3との並行利用（日本語クエリ時はruri、英語/コードはbge-m3等）も検討できるが、複数モデル混在によるバグリスクに注意が必要

#### 軽量候補: Qwen/Qwen3-Embedding-0.6B

**根拠**:
- MTEB Multilingual 64.33と0.6Bサイズとしては高スコア
- 32Kトークン対応でコード・ドキュメント長文を扱いやすい
- Apache 2.0ライセンス
- 日本語・英語・コードを含む100言語以上に対応
- bge-m3よりもモデルサイズが小さく（約1.2GB）、CPUオンリー環境でも実用的

### 3.2 除外候補

#### 除外: sentence-transformers/all-MiniLM-L6-v2

**根拠**:
- **英語主体モデルであり日本語精度が著しく低い**。公式ドキュメント自体が「日本語等の多言語には paraphrase-multilingual 系を推奨」と明記
- 本ユースケース（日英混在・コード）の主要要件を満たさない
- 256トークン上限という制約もコード・Markdownの長文チャンクに不向き
- ベースライン比較用として参照価値はあるが、本番採用は不可

#### 除外: google/embeddinggemma-300m

**根拠**:
- ライセンスが「Gemmaライセンス（独自利用規約）」であり、「商用利用は可能だが条件付き（Prohibit Use Policyへの準拠義務・配布時の条件付け義務等）」となる
- 本プロジェクトのスコープは「完全にOSS・商用利用無料製品のみ」であり、Apache 2.0/MITなどの標準的なOSSライセンスと異なるGemmaライセンスは調達リスクになりうる
- MTEB Multilingual 61.15はbge-m3（70.0）・Qwen3-Embedding-0.6B（64.33）より低く、ライセンスリスクを上回るスコアメリットがない

#### 除外: sentence-transformers/paraphrase-multilingual-mpnet-base-v2

**根拠**:
- **最大入力長128トークン（128 word pieces）という致命的制約**。コードファイルや長文Markdownのチャンクを処理する本ユースケースには不十分
- 日本語を含む50言語対応ではあるが、精度・コンテキスト長ともに現世代モデルに比べて見劣りする
- 代替選択肢（bge-m3, ruri-v3, Qwen3-Embedding）が全てより優れているため積極採用理由がない

## 4. 本ユースケースでの考察

### 4.1 日英混在・コード・Markdownへの対応

本ユースケースは「日英混在テキスト + Python/TypeScript コード + Markdownドキュメント」という異種コンテンツが混在する構成を持つ。

| コンテンツ種別 | 推奨モデル | 理由 |
|---|---|---|
| 日本語自然言語 | ruri-v3-310m（または bge-m3） | JMTEB SOTA / MIRACL多言語SOTA |
| 英語自然言語 | bge-m3 または Qwen3-Embedding-0.6B | MTEB高スコア・多言語安定 |
| Python/TypeScript コード | bge-m3 または Qwen3-Embedding-0.6B / 8B | コード検索ベンチマーク実績あり |
| Markdown（混在） | bge-m3 | 長文対応（8192トークン）・多言語安定 |

単一モデルで全種別を扱うなら **bge-m3 が最適解**。日本語精度を最大化したい場合はruri-v3との組み合わせが有効だが、複数モデル運用の複雑性とのトレードオフになる。

### 4.2 リソース制約との関係

CPU動作のみを想定する場合は Qwen3-Embedding-0.6B（約1.2GB）または ruri-v3-30m（約140MB）が現実的。bge-m3（約4.6GB）はCPUでも動作するが速度面での制約が大きくなる。

## 5. 既知ハマりどころとの照合

| ハマりどころ | 該当モデル | 対応策 |
|---|---|---|
| e5系モデルの `passage:` / `query:` プレフィックス必須 | multilingual-e5-small, multilingual-e5-large | クエリエンコード時に `"query: " + text`、ドキュメントエンコード時に `"passage: " + text` を付与する実装が必須。付与漏れは精度を著しく損なう |
| `all-MiniLM-L6-v2` は日本語精度が不足 | all-MiniLM-L6-v2 | 本報告書において**除外判定済み**。日本語コンテンツには一切使用しないこと |
| 異なる埋め込みモデルの混在バグ | bge-m3 + ruri-v3 並行運用時など | インデックス構築時と検索時で同一モデルを必ず使用すること。モデルを切り替えた場合は必ずインデックスを再構築する。チャンクメタデータに「どのモデルで生成したか」を記録する設計が望ましい |

## 6. 課題・制約

### 将来解決が必要な課題

- **bge-m3の4.6GBダウンロード・初回インデックス構築時間**: 低スペックWindows 11環境（RAM 8GB以下等）での動作検証が未実施。フィジビリティ検証フェーズで実測が必要
- **ruri-v3の英語・コード精度の定量評価**: JMTEB（日本語専用）以外のベンチマーク数値が確認できていない。英語クエリで日本語文書を検索する（クロスリンガル）シナリオへの対応力は未測定
- **Qwen3-Embedding-0.6Bの日本語専用ベンチマーク（JMTEB）スコアの未確認**: MTEB Multilingualのスコアはあるが、日本語単体の精度は不明

### 解決不能な課題

- **日英コード混在コンテンツに対する単一最良モデルの不在**: 日本語専用モデル（ruri-v3）と多言語モデル（bge-m3）はトレードオフ関係にあり、単一モデルで全種別を最高精度でカバーすることは現時点では不可能

### 解決不要な課題

- **all-MiniLM-L6-v2 の日本語非対応**: 本ユースケースでは採用しないと確定したため改善不要
- **有料APIとのスコア差**: 本調査はローカルOSSモデルのみを対象とするため、Gemini/OpenAI APIとの精度差はスコープ外

## 7. ハマりどころ追記候補

以下を「既知ハマりどころ」リストへの追記候補として提案する。

1. **ruri-v3は日本語専用のため英語クエリ・コードチャンクへの適用に注意**: `cl-nagoya/ruri-v3-*` シリーズは日本語テキストのみを想定した学習データで構築されている。英語・コードが多い環境では bge-m3 または Qwen3-Embedding 系との切り分けが必要

2. **bge-m3はマルチベクトル（ColBERT）機能使用時にメモリ消費が増大**: Dense embedのみ使用するなら約4.6GBだが、ColBERTモードを有効にするとトークンレベルの埋め込みが生成されインデックスサイズが数倍になる場合がある

3. **EmbeddingGemma（Gemmaライセンス）は完全OSSと混同しやすい**: `google/embeddinggemma-*` は open-weights だが Apache 2.0 ではなく Gemma 独自利用規約が適用される。Apache 2.0/MIT 前提のシステムに混入しないよう注意

4. **Qwen3-Embedding はインストラクション付きエンコードに対応**: クエリ側に `"Instruct: <タスク説明>\nQuery: "` を付与することで 1〜5% の精度向上が見込める設計。使用しない場合でも動作するが、最大精度を引き出すには実装が必要
