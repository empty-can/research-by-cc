## 1. 調査概要

本調査では、ローカル RAG システムの検索基盤として利用可能なベクトル DB を比較・評価した。前提条件は以下の通り。

- **環境**: Windows 11（Docker 利用不可）
- **条件**: OSS・商用利用無料のみ対象
- **目的**: Claude Code から利用できる最小運用コストのローカルベクトル検索基盤を選定する

調査対象は指定の 6 候補（DuckDB+vss、sqlite-vec、Chroma、Qdrant、pgvector、Milvus Lite）に加え、LanceDB・FAISS の 2 候補を追加調査し、合計 8 件を比較した。

参考資料として以下を参照した。
- Zenn 記事「DuckDB でローカル RAG を作って Claude Code から使う」(https://zenn.dev/sasadango28/articles/duckdb-local-rag-20260406)
- DuckDB 公式 VSS ドキュメント (https://duckdb.org/docs/current/core_extensions/vss)
- sqlite-vec GitHub (https://github.com/asg017/sqlite-vec)
- Qdrant 公式ドキュメント (https://qdrant.tech/documentation/)
- LanceDB 公式ドキュメント (https://docs.lancedb.com/)
- 各種ベンチマーク比較記事 (2025–2026)

## 3. 採用候補と除外候補

### 3.1 採用候補

#### 第一候補: DuckDB + vss
- **根拠**: 単一 `.duckdb` ファイルに埋め込み、標準 SQL で操作でき、Python/Node.js/Go 等から直接呼び出せる。参考記事（Zenn）でも実証済みの構成であり、「数万チャンクでもミリ秒で検索できる」との報告がある。Windows 公式サポート済み。
- **注意**: `hnsw_enable_experimental_persistence = true` を設定しない場合、DB 再起動のたびにインデックスを再構築する必要があり、この永続化機能は experimental（詳細は §6 を参照）。

#### 第二候補: LanceDB
- **根拠**: Apache-2.0 ライセンス、完全組み込み型でサーバー不要。Arrow ネイティブ設計でディスク効率が高く、数百万ベクトルをローカルで快適に扱える。DuckDB との連携も公式サポート（Lance-native SQL retrieval via DuckDB）があり、本プロジェクトのエコシステムと親和性が高い。クロスプラットフォーム動作確認済み。

#### 第三候補: sqlite-vec
- **根拠**: SQLite に直接組み込める最軽量構成。`pip install sqlite-vec` のみで導入完了。既存 SQLite データベースとの同居が可能で、追加インフラゼロ。ブルートフォース検索中心だがコード量最小。
- **注意**: Windows では組み込み SQLite が古い場合があるため `pysqlite3` パッケージの利用が推奨される。

#### 第四候補: Chroma
- **根拠**: `chromadb.PersistentClient(path="./chroma_db")` の 1 行で永続ストレージが使える最も開発体験が良い選択肢。Docker 不要で Windows + pip 環境で完結。SQLite バックエンドを持ち、安定性が高い。
- **注意**: クエリレイテンシは約 30ms（Qdrant の約 12ms より遅い）。プロトタイプや 1,000 万ベクトル未満のユースケース向け。

### 3.2 除外候補

#### pgvector
- **根拠**: PostgreSQL 拡張であり、実用的なインストール方法は Docker イメージ（`pgvector/pgvector:pg17`）を使うことが前提となっている。現環境（Docker 利用不可）では利用不可。WSL 経由でのネイティブビルドも可能だが運用コストが大きく、本プロジェクトの「ゼロ運用コスト」方針に反する。

#### Milvus Lite
- **根拠**: 公式ドキュメントおよび PyPI ページに「Windows is not yet supported」と明記されている。現環境では使用不可。

### 3.3 Docker 環境が整備された際の追加候補（申し送り）

| DB 名 | 形態 | 備考 |
|---|---|---|
| pgvector | PostgreSQL 拡張 | Docker イメージ `pgvector/pgvector:pg17` で即時利用可。1,000 万〜5,000 万ベクトルの中規模 RAG に適する |
| Milvus Lite | Python ライブラリ | Docker 不要だが Windows サポート次第。Docker + Milvus Standalone も選択肢 |
| Qdrant（サーバーモード） | サーバー型 | Docker イメージが最も安定。OSS 最高水準のレイテンシ（p50: 4ms） |
| Weaviate | サーバー型 | ハイブリッド検索・GraphQL API に強み。Docker 推奨 |

## 4. 単一ファイル型 vs サーバー型の運用コスト比較

| 観点 | 単一ファイル型（DuckDB、LanceDB、sqlite-vec） | サーバー型（Chroma、Qdrant） |
|---|---|---|
| **起動コスト** | ゼロ（ライブラリ import のみ） | プロセス起動が必要（ただし Chroma/Qdrant はローカルモードで Python 内に埋め込み可） |
| **設定複雑度** | 低（ファイルパス指定のみ） | 中（ポート・接続設定が必要） |
| **バックアップ** | ファイルコピーで完結 | データディレクトリのバックアップが必要 |
| **同時アクセス** | 基本的に単一プロセス（SQLite 同様の制約） | マルチクライアント対応が容易 |
| **メモリ管理** | アプリプロセスと共有（競合リスク） | 独立プロセス（Qdrant サーバーモード時） |
| **スケール上限** | RAM 容量が実質的な制限 | サーバー設定・ハードウェア次第で拡張可能 |
| **CI/CD 組み込み** | 容易（ファイルパスで再現可能） | 中程度（ポート競合・プロセス管理が必要） |
| **Claude Code MCP 統合** | 直接 Python スクリプトで操作しやすい | HTTP API 経由も可能だが設定が増える |

**結論**: Claude Code からの MCP/スクリプト経由利用においては、単一ファイル型が「起動コストゼロ・設定最小・バックアップ容易」の三点で優れる。サーバー型は同時接続・大規模・チーム共有が必要になった段階で採用を検討する。

## 5. TBD3（規模感）依存部分の仮分析

サブタスク 01（RAG パターン分類）で確定する規模感（TBD3）が未定のため、以下は仮分析として記録する。

### TBD3 確定後に精緻化が必要な箇所

| 項目 | 仮の前提 | TBD3 が変わった場合の影響 |
|---|---|---|
| DuckDB vss の RAM 要件 | 数万〜数十万チャンク（数万〜数十万ベクトル）と仮定 | 100 万ベクトルを超える場合、HNSW インデックスの RAM 全展開が課題になる可能性 |
| sqlite-vec の採否 | ブルートフォース許容規模（〜100 万）と仮定 | 規模が 100 万を大幅に超える場合は HNSW 対応の DuckDB や LanceDB へ移行推奨 |
| LanceDB の IVF_PQ インデックス必要性 | 数十万ベクトルならフラットインデックスで十分と仮定 | 数百万を超える場合は ANN インデックス（IVF_PQ）の設定が必要になる |
| Chroma の採否 | 100 万ベクトル未満と仮定 | 1,000 万ベクトルを超える場合はスケール限界に達するため不採用を検討 |

### 現時点での暫定推奨

Claude Code の利用規模（数千〜数十万チャンク程度）を想定すると、DuckDB + vss または LanceDB が妥当な選択肢であると判断できる。規模が確定した段階で本節を更新すること。

## 6. 既知ハマりどころとの照合

### ハマりどころ 1: DuckDB vss の `hnsw_enable_experimental_persistence` は experimental

**照合結果**: 確認・詳細補足

DuckDB 公式ドキュメントおよび GitHub 情報より、以下が判明している。

- デフォルトでは HNSW インデックスはインメモリ DB にのみ作成可能。ディスク DB に対して使うには `SET hnsw_enable_experimental_persistence = true;` が必要
- **WAL リカバリが未実装**: 未コミット変更がある状態でクラッシュまたは予期せぬシャットダウンが発生した場合、インデックスの消失・破損が起こりうる
- バージョン更新時（DuckDB 0.10.x 以降）の動作確認が必要
- **対策案**: インデックスをインメモリで保持し、起動時に毎回再構築する運用（コールドスタートが数秒以内なら許容範囲）を検討する。あるいは LanceDB など永続化が安定しているDBへの切り替えを検討する。

### ハマりどころ 2: macOS での sqlite-vec は Homebrew 版 SQLite が必要

**照合結果**: Windows には該当しないが類似問題あり

Windows では組み込み SQLite のバージョンが古い場合がある。Python から利用する際は `pysqlite3` パッケージ（最新 SQLite をバンドルした PyPI パッケージ）を使用することで回避できる。

```python
# 通常の sqlite3 の代わりに pysqlite3 を使う
import pysqlite3
import sqlite_vec
```

### ハマりどころ 3: Docker 依存の構成（pgvector、Milvus 等）は現環境では実行不可

**照合結果**: 確認済み・比較表に反映済み

- pgvector: 現環境で除外（§3.2 参照）
- Milvus Lite: Windows 非対応で除外（§3.2 参照）
- Qdrant: ローカルモード（Python 組み込み）を使えば Docker 不要で動作可能。ただし Windows バイナリの安定性は要確認

## 7. 課題・制約

### 将来解決が必要な課題（Docker 不在環境での制約等）

| 課題 | 内容 | 解決のトリガー |
|---|---|---|
| pgvector の利用不可 | Docker がなければ PostgreSQL + pgvector の最も手軽な構成が使えない。中規模（1,000 万〜）RAG では pgvector が最有力候補になりうる | Docker Desktop 導入 |
| Milvus Lite の Windows 非対応 | PyPI の `milvus-lite` は Windows をサポートしていない旨が公式に記載されており、現時点では利用不可 | Milvus Lite の Windows 対応リリース（GitHub で追跡推奨） |
| Qdrant サーバーモードの安定運用 | Windows バイナリを直接実行する場合、ファイルシステムの挙動（Docker + WSL でデータ消失の報告あり）に注意が必要 | Docker 利用または WSL2 + バイナリで検証 |
| DuckDB vss の WAL リカバリ未実装 | experimental persistence の完全化を待つか、再構築前提の設計が必要 | DuckDB vss の正式安定化リリース |

### 解決不能な課題

- Milvus Lite の Windows 対応はサードパーティ依存であり、本プロジェクト側では解決不可。代替 DB（LanceDB、DuckDB vss）での対応が現実的。

### 解決不要な課題（参考情報）

- FAISS の永続化問題: FAISS 単体ではインデックスをファイルに書き出す機能はあるが、メタデータ管理・フィルタリングが別途必要になる。本プロジェクトでは LanceDB / DuckDB のほうが上位互換のため、FAISS 単体採用は不要と判断。

## 8. ハマりどころ追記候補

本調査を通じて、既知のハマりどころ一覧に追加を推奨する項目。

1. **Qdrant ローカルモードのバージョン依存性**: `QdrantClient(path="./qdrant_db")` のローカルモードは `qdrant-client` の Python ライブラリバージョンによって挙動が変わることがある。`pip install qdrant-client[fastembed]` と単純 `pip install qdrant-client` では依存関係が異なるため注意。

2. **LanceDB のインデックス自動作成タイミング**: LanceDB はデフォルトで小規模データ（約 25,600 件未満）ではインデックスを作成せずフルスキャンを行う。規模が大きくなった際に `create_index()` を明示的に呼ぶ必要がある。これを知らないと、大規模化した際に突然パフォーマンスが劣化したように見える。

3. **sqlite-vec の HNSW インデックス非対応**: sqlite-vec はブルートフォース検索が主体であり、HNSW インデックスは（現バージョンでは）サポートされていない（後継候補の `sqlite-vector` はより高速だが別プロジェクト）。数万件を超えると検索速度が線形劣化するため、規模に応じて DuckDB vss や LanceDB へ切り替える判断が必要。

4. **Windows における DuckDB vss のメモリ上限**: HNSW インデックスは操作時に全量 RAM に展開される。64 次元 × 10 万ベクトルで約 25 MB、1536 次元 × 100 万ベクトルでは約 6 GB となり、ラップトップ環境では RAM 不足に陥る可能性がある。
