## 1. 調査概要

### 1.1 目的

Claude Code 向けローカル RAG システム構築の候補となる OSS リポジトリを GitHub 上で直接調査し、各リポジトリのアーキテクチャ・技術スタック・Claude Code 連携方式・埋め込みモデル・ベクトル DB を把握する。その上で、本プロジェクト（Windows 11 環境・OSS/無料限定・ローカル LLM 不要をベース構成）への採用候補度を評価する。

### 1.2 調査対象リポジトリ一覧

| # | リポジトリ | 主要言語 | 概要 |
|---|---|---|---|
| 01 | sebastianhutter/local-rag | Go | SQLite+sqlite-vec+FTS5 ハイブリッド検索 MCP サーバー（macOS 向け GUI 付き） |
| 02 | suwa-sh/local-RAG-backend | Docker Compose / Python | Graphiti + Neo4j を使ったグラフ RAG バックエンド |
| 03 | n-irei/local-rag-mcp-server | Python | ChromaDB + Ollama によるシンプルなローカル RAG MCP サーバー |
| 04 | michelabboud/claude-code-helper | TypeScript / Python | Claude Code 総合ヘルパーキット（RAG MCP サーバーを内包） |
| 05 | saiprashanths/code-analysis-mcp | Python | シンプルなコード解析 MCP（RAG なし・ファイルアクセスのみ） |
| 06 | najva-ai/sourcegraph-mcp | Python | Sourcegraph API ラッパー MCP（外部サービス依存） |
| 07 | isink17/codegraph | Go | ローカルファーストのコードナレッジグラフ + MCP サーバー |
| 08 | johnhuang316/code-index-mcp | Python | Tree-sitter + ripgrep によるコードインデックス MCP |

### 1.3 調査スコープ

各リポジトリに対して以下を調査した:

- アーキテクチャ概要（コンポーネント構成・データフロー）
- 技術スタック（言語・主要ライブラリ・DB）
- Claude Code / LLM 連携方式（MCP ツール定義・トランスポート）
- 埋め込みモデル・ベクトル DB の種類
- Windows 11 対応状況
- 採用候補度（高 / 中 / 低）と根拠

## 2. 各リポジトリ詳細

### 2.1 sebastianhutter/local-rag

#### アーキテクチャ概要

完全オフライン RAG システムで、MCP サーバーと Fyne GUI アプリの両方を提供する。データフローは「ドキュメント / コードリポジトリ → tree-sitter / PDF パーサーによるチャンク分割 → Ollama (bge-m3) で埋め込み → SQLite (sqlite-vec + FTS5) に格納 → ハイブリッド検索 (vector 0.7 + FTS 0.3、RRF で融合) → MCP tool 応答」の順で流れる。

```
cmd/local-rag/
internal/
  config/    # 設定管理
  db/        # SQLite + sqlite-vec + FTS5
  embeddings/ # Ollama bge-m3
  chunker/   # テキスト分割
  search/    # ハイブリッド検索 (RRF)
  parser/    # tree-sitter (13言語) + PDF
  indexer/   # インデックス処理
  mcp/       # MCP サーバー (mcp-go)
  gui/       # Fyne GUI
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | Go 1.24+ |
| ベクトル DB | SQLite + sqlite-vec + FTS5 |
| 埋め込みモデル | Ollama bge-m3 (ローカル) |
| MCP フレームワーク | mcp-go |
| コードパーサー | go-tree-sitter (13 言語) |
| PDF | go-pdfium |
| GUI | Fyne v2 |

#### MCP ツール一覧

| ツール名 | 機能 |
|---|---|
| `rag_search` | ハイブリッド検索 |
| `rag_list_collections` | コレクション一覧 |
| `rag_collection_info` | コレクション情報取得 |
| `rag_index` | ドキュメント / コードリポジトリのインデックス |
| `rag_prune` | インデックス削除 |

#### Claude Code 連携方式

stdio トランスポートの MCP サーバーとして Claude Code に登録する。`mcp-go` ライブラリを使用した Go 実装。

#### Windows 11 対応状況

**非対応（macOS 専用）。** README に macOS のみ明示。Fyne GUI・sqlite-vec の CGO ビルドが macOS 前提。

#### 採用候補度: **中**

ハイブリッド検索・コード特化 tree-sitter 解析・MCP ネイティブ設計と技術的完成度は高い。ただし macOS 専用であり、Windows 11 をターゲットとする本プロジェクトでは **そのままでは使用不可**。Go ソースからのクロスコンパイルを試みる価値はあるが、CGO 依存 (sqlite-vec) があるため難易度が高い。アーキテクチャ設計の参考として価値が高い。

### 2.2 suwa-sh/local-RAG-backend

#### アーキテクチャ概要

Docker Compose で起動するグラフ RAG バックエンド。従来のベクトル類似検索ではなく Graphiti フレームワークによるナレッジグラフ (Neo4j) を使う点が特徴。データフローは「ドキュメント取り込み (Unstructured) → Graphiti で関係エンティティ抽出 → Neo4j に格納 → AI エージェント → MCP Server (SSE) → Graphiti → Neo4j 検索」となる。

```
Docker Compose サービス:
  neo4j:5-community          # グラフ DB (7474/7687)
  graphiti-mcp-server        # MCP サーバー (8000/SSE)
  graphiti-ingest            # 取り込みパイプライン
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| グラフ DB | Neo4j 5 Community |
| RAG フレームワーク | Graphiti |
| 埋め込みモデル | Ollama kun432/cl-nagoya-ruri-large (ローカル) |
| LLM（必須） | OpenAI API (gpt-4o-mini / gpt-4.1-nano) |
| MCP トランスポート | SSE (HTTP ポート 8000) |
| 文書取り込み | Unstructured |

#### Claude Code 連携方式

SSE トランスポートの MCP サーバーとして Claude Code に登録。`graphiti-mcp-server` コンテナが MCP エンドポイントを公開する。

#### Windows 11 対応状況

Docker Compose で動作するため Windows 上でも起動可能。ただし Ollama と OpenAI 両方の設定が必要。

#### 採用候補度: **低**

埋め込みはローカル Ollama だが、**グラフ構築と再ランキングに OpenAI API (有料) が必須**。「OSS/無料のみ」という本プロジェクトの制約に抵触する。ローカル LLM (Ollama) に変更する方法は README に記載がなく、変更コストが高い。グラフ RAG というアーキテクチャの参考としての価値はある。

### 2.3 n-irei/local-rag-mcp-server

#### アーキテクチャ概要

Python 製のシンプルなローカル RAG MCP サーバー。ChromaDB + Ollama の定番構成をそのまま MCP 化したもの。データフローは「ドキュメント (PDF / TXT / MD) → Ollama nomic-embed-text で埋め込み → ChromaDB に格納 → MCP tool 経由で類似検索」。

```
server.py (FastMCP)
  ├── add_document    # ドキュメント追加
  ├── search_documents # 類似検索
  └── list_documents  # ドキュメント一覧
ChromaDB (ローカルファイル)
Ollama (nomic-embed-text / qwen3.5:9b)
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | Python 3.x |
| ベクトル DB | ChromaDB (ローカルファイル) |
| 埋め込みモデル | Ollama nomic-embed-text (ローカル) |
| MCP フレームワーク | FastMCP |
| PDF パーサー | PyMuPDF |
| 設定 | python-dotenv |

#### MCP ツール一覧

| ツール名 | 機能 |
|---|---|
| `add_document` | ドキュメント追加・チャンク化・インデックス |
| `search_documents` | 類似検索 |
| `list_documents` | インデックス済みドキュメント一覧 |

#### Claude Code 連携方式

stdio トランスポートの MCP サーバー。FastMCP を使用した Python 実装。README に Windows パス (C:\...) を使ったインストール例が記載されており、Windows 前提で書かれている。

#### Windows 11 対応状況

**Windows 対応確認済み。** README に Windows パスを使ったセットアップ手順が明示されている。

#### 採用候補度: **高**

- 完全ローカル・無料 (Ollama + ChromaDB + FastMCP)
- Windows 11 での動作が README で確認済み
- インストールが pip のみでシンプル
- ただし対象がドキュメント (PDF/TXT/MD) 中心で、コードベース向けのコード構造解析 (tree-sitter など) は持たない
- ハイブリッド検索なし (ベクトル類似検索のみ)

ドキュメント RAG の最短実装パスとして採用候補度「高」。コードベース特化には別途拡張が必要。

### 2.4 michelabboud/claude-code-helper

#### アーキテクチャ概要

59 個のエージェント・68 の MCP ツール (10 サーバー)・13 スキルを含む Claude Code 総合ヘルパーキット。RAG そのものではなく、その中に `mcp-servers/rag-mcp/` という RAG MCP サーバーを内包する。RAG バックエンドとして ChromaDB / Redis / Qdrant を選択可能。`/rag init` ウィザードでセットアップでき、2 層の自動検出 (auto-discovery) を持つ。

```
mcp-servers/
  rag-mcp/             # RAG MCP サーバー (TypeScript)
  api-specialist-mcp/
  code-review-mcp/
  design-system-mcp/
  testing-mcp/
  uiux-review-mcp/
  ...
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | TypeScript (MCP サーバー群) |
| ベクトル DB | ChromaDB / Redis / Qdrant (選択制) |
| MCP フレームワーク | TypeScript MCP SDK |
| RAG スキル | `/rag init`, コードベースインデックス, 意味検索, 2 層自動検出 |
| 全体構成 | 59 agents + 68 tools + 13 skills |

#### MCP ツール一覧（RAG MCP のみ抜粋）

詳細ツールリストは rag-mcp ソース要調査。README からは「コードベースインデックス」「意味検索」「2 層自動検出」が確認されている。

#### Claude Code 連携方式

TypeScript 製 MCP サーバー群を Claude Code に登録。stdio または SSE トランスポート (詳細は rag-mcp ソース参照)。

#### Windows 11 対応状況

Node.js / TypeScript ベースのため Windows 動作自体は可能。ただし 10 サーバー・59 エージェントの初期設定コストが高い。

#### 採用候補度: **中**

RAG MCP 単体では ChromaDB/Redis/Qdrant をバックエンドに持つ本格実装。ただし全体が非常に大規模なリポジトリ (59 agents / 68 tools) であり、RAG 部分だけを取り出して使うのに大きな理解コストがかかる。TypeScript ベースで拡張はしやすい。ベクトル DB の選択肢が広い点は利点。

### 2.5 saiprashanths/code-analysis-mcp

#### アーキテクチャ概要

コード解析 MCP サーバーだが、**RAG (埋め込み・ベクトル検索) 機能は持たない**。ファイルシステムを走査してリポジトリ構造を返す、いわば「ファイルブラウザ」MCP。FastMCP を使ったシングルファイル Python 実装 (`code_analysis.py`)。

```
CodeAnalysisServer (FastMCP)
  RepoStructureAnalyzer  # ディレクトリツリー生成 (gitignore対応)
  FileReader             # ファイル読み取り (1MB / 1000行上限)
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | Python 3.x |
| MCP フレームワーク | FastMCP |
| ベクトル DB | なし |
| 埋め込みモデル | なし |

#### MCP ツール一覧

| ツール名 | 機能 |
|---|---|
| `initialize_repository` | リポジトリ初期化・構造スキャン |
| `get_repo_info` | リポジトリ基本情報 |
| `get_repo_structure` | ディレクトリツリー取得 |
| `read_file` | ファイル内容読み取り |

#### Claude Code 連携方式

stdio トランスポートの MCP サーバー。FastMCP 実装。シングルファイル構成で極めてシンプル。

#### Windows 11 対応状況

純粋 Python + ファイルシステム操作のため Windows 対応は問題なし。

#### 採用候補度: **低**

RAG システムではなく、ファイルアクセス・構造閲覧のみの MCP。埋め込みなし・ベクトル検索なし・意味検索なし。「ファイルを直接読んで渡す」方式はトークン消費増大につながりやすく、本プロジェクトの「トークン・コンテキスト消費を抑える」という目的と逆方向。シンプルな実装例の参考コードとして価値はある。

### 2.6 najva-ai/sourcegraph-mcp

#### アーキテクチャ概要

Sourcegraph API を MCP 経由で呼び出すラッパー。ローカル RAG ではなく、外部の Sourcegraph インスタンス (クラウドまたはセルフホスト) に対して検索を委譲する構造。FastMCP + requests で Sourcegraph REST API を叩く。

```
MCP Server (FastMCP)
  ├── search           # コード検索
  ├── search_prompt_guide # 検索クエリ補助
  └── fetch_content    # コンテンツ取得
  → Sourcegraph Instance (外部 HTTP)
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | Python 3.13+ |
| MCP フレームワーク | FastMCP 2.12.0 |
| ベクトル DB | なし (Sourcegraph が内部で管理) |
| 埋め込みモデル | なし (Sourcegraph 依存) |
| 外部依存 | Sourcegraph インスタンス (SRC_ENDPOINT 必須) |

#### MCP ツール一覧

| ツール名 | 機能 |
|---|---|
| `search` | Sourcegraph コード検索 |
| `search_prompt_guide` | 検索クエリガイド |
| `fetch_content` | コンテンツ取得 |

#### Claude Code 連携方式

stdio トランスポートの MCP サーバー。FastMCP 実装。`SRC_ENDPOINT` 環境変数で Sourcegraph インスタンス URL を指定する。

#### Windows 11 対応状況

Python + HTTP 通信のため OS 依存なし。ただし Sourcegraph サービスの用意が前提。

#### 採用候補度: **低**

外部 Sourcegraph サービスへの依存が必須であり、「完全オフライン・ローカルのみ」という本プロジェクト要件に根本的に合致しない。Sourcegraph のセルフホストは可能だが、Docker + 大規模サービスの運用コストが高い。ローカル RAG の実装パターンとしては参考にならない。

### 2.7 isink17/codegraph

#### アーキテクチャ概要

ローカルファーストのコードナレッジグラフエンジン + MCP サーバー。リポジトリを解析し SQLite に永続的なナレッジグラフ (`codegraph.sqlite`) を構築する。Tree-sitter AST で 12 言語の構造を解析し、シンボル・呼び出し関係・依存関係をグラフとして保存。オプションで Ollama のベクトル埋め込みを追加可能。29 個の MCP ツールを提供し、Claude Code との緊密な連携を想定している。

```
codegraph CLI / MCP Server (Go)
  ├── Tree-sitter AST パーサー (12 言語)
  ├── SQLite (codegraph.sqlite) — ナレッジグラフ永続化
  ├── 意味検索: Ollama nomic-embed-text (オプション)
  ├── Agentic: Ollama llama3.2 (オプション)
  └── 29 MCP Tools
```

#### 主要コンポーネント

| 区分 | 技術要素 |
|---|---|
| 言語 | Go 1.26+ |
| グラフ/DB | SQLite (moderncdata/sqlite) |
| 埋め込みモデル | Ollama nomic-embed-text (オプション) |
| コードパーサー | go-tree-sitter (12 言語) |
| MCP 統合 | 29 MCP ツール (claude-code 自動設定対応) |
| ライセンス | FSL-1.1-MIT (2 年後 MIT に転換) |

#### MCP ツール一覧（抜粋）

| ツール名 | 機能 |
|---|---|
| `find_symbol` | シンボル検索 |
| `search_symbols` | パターンマッチシンボル検索 |
| `search_semantic` | 意味検索 (Ollama 有効時) |
| `find_callers` / `find_callees` | 呼び出し元 / 呼び出し先 |
| `get_impact_radius` | 変更影響範囲分析 |
| `trace_dependencies` | 依存関係トレース |
| `find_related_tests` | 関連テスト検索 |
| `find_dead_code` | デッドコード検出 |
| `context_for_task` | タスク向けコンテキスト収集 |
| `architecture_overview` | アーキテクチャ概要 |
| `graph_analytics` | グラフ分析 |
| `detect_frameworks` | フレームワーク検出 |

#### Claude Code 連携方式

claude-code の自動設定 (`--claude-code` フラグ) に対応した stdio MCP サーバー。バイナリ単体で動作し Docker 不要。

#### Windows 11 対応状況

**クロスプラットフォーム対応。** README に Linux / macOS / Windows 対応が明記されている。シングルバイナリで外部 DB 不要。

#### 採用候補度: **高**

- コードベース特化設計（AST 解析・シンボルグラフ・依存関係）
- Windows 11 対応確認済み
- 単一バイナリ・外部サービス不要でインストールが極めて簡単
- Claude Code 自動設定サポート (`--claude-code` フラグ)
- 29 MCP ツールによる豊富なコード解析 API
- ベクトル埋め込みはオプション (Ollama 必須ではない)
- ライセンスが FSL-1.1-MIT (現時点では純粋 MIT ではないが実用上問題は限定的)
- コード以外のドキュメント RAG としては不向き

コードベース向け RAG / コンテキスト提供ツールとして最も本プロジェクトの要件に近い候補。

### 2.8 johnhuang316/code-index-mcp

code-index-mcp (FastMCP / Python)

| 言語 | Python 3.x |
| ベクトル DB | なし |
| 埋め込みモデル | なし |
| MCP フレームワーク | MCP SDK (mcp>=1.21.0) |
| コードパーサー | tree-sitter (10 言語) + fallback (50+ 種) |
| ファイル監視 | watchdog |
| 検索エンジン | ripgrep / ugrep / ag / grep |
| 配布 | PyPI (`code-index-mcp`) |

#### MCP ツール一覧

詳細ツールリストは README に明示されていないが、コードインデックスのクエリ・構造検索・ファイル検索が主機能と推定。

#### Claude Code 連携方式

stdio トランスポートの MCP サーバー。`uvx code-index-mcp` による即時起動が可能。

#### Windows 11 対応状況

**クロスプラットフォーム対応。** README にクロスプラットフォーム対応が明記されている。

#### 採用候補度: **中**

- `uvx` 1 コマンドで即時セットアップ可能
- Windows 11 対応確認済み
- ファイル監視による自動更新は実用的
- ただし RAG ではなくテキストインデックス + grep ベース検索

- 大規模コードベースでのテキスト検索精度は ripgrep に依存
- コード RAG の補完ツール (テキスト検索層) として組み合わせ利用の価値がある

## 4. 本調査への示唆

### 4.1 コードベース向け RAG の有力候補

**isink17/codegraph** がコードベース特化型として最も本プロジェクトの要件に近い。以下の特徴が特に評価点となる:

1. **コード構造の深い理解** — tree-sitter AST による 12 言語のシンボル解析・依存関係グラフ化。単純なテキスト分割 + 埋め込みではなく、コードの意味構造を活かした検索が可能
2. **Claude Code 自動設定** — `--claude-code` フラグによる自動設定で導入障壁が低い
3. **段階的な Ollama 統合** — 埋め込みはオプションのため、Ollama なし (グラフ検索のみ) でも動作する
4. **シングルバイナリ** — Docker 不要・外部 DB 不要で Windows 11 へのインストールが簡単

### 4.2 ドキュメント RAG の参考実装

**n-irei/local-rag-mcp-server** は ChromaDB + Ollama + FastMCP の定番構成をシンプルに実装しており、ドキュメント (Markdown / PDF) RAG の最短実装パスとして参考になる。Windows 11 での動作が README で確認されているのも評価点。

### 4.3 ハイブリッド検索アーキテクチャの参考

**sebastianhutter/local-rag** は macOS 専用という制約があるが、「ベクトル検索 0.7 + FTS5 0.3、RRF で融合」というハイブリッド検索の具体的な実装比率と融合手法が参考になる。SQLite 一本化（外部 DB 不要）のアーキテクチャも設計の参考となる。

### 4.4 組み合わせ戦略の可能性

調査した OSS を単独採用するのではなく、以下の組み合わせが有効と考えられる:

- **コードベース検索**: isink17/codegraph (シンボル・依存関係グラフ)
- **ドキュメント検索**: n-irei/local-rag-mcp-server または sebastianhutter/local-rag の設計を参考にした独自実装
- **テキスト補完**: johnhuang316/code-index-mcp (ripgrep 層)

## 5. 課題と制約

### 5.1 Windows 11 環境での CGO ビルド

sebastianhutter/local-rag は sqlite-vec の CGO ビルドが macOS 前提。Windows でビルドするには CGO クロスコンパイル環境の構築が必要で、難易度が高い。将来的に Windows 対応が追加されるかどうかは不明。

### 5.2 isink17/codegraph のライセンス

FSL-1.1-MIT (Functional Source License) は、ライセンス発行から 2 年後に MIT に転換する条件付きライセンス。商用利用は制限される場合があるが、調査・開発利用では問題は限定的。本プロジェクトは社内利用・個人利用の範囲では問題ない可能性が高いが、最終採用時に法務確認を推奨する。

### 5.3 suwa-sh/local-RAG-backend の OpenAI 依存

グラフ構築と再ランキングに OpenAI API が必須であり、完全無料・完全ローカルの制約に抵触する。Ollama ローカル LLM への差し替えは技術的に可能だが、Graphiti フレームワークの内部実装を変更する必要があり、コストが高い。

### 5.4 コードベース向け RAG の意味検索品質

コードに対するベクトル埋め込みの品質は、自然言語テキストと比較して一般的に低い傾向がある。isink17/codegraph はグラフ構造 (シンボル・依存関係) を活用することでこの問題を回避しているが、自然言語クエリでのコード検索精度については実際の検証が必要。

## 6. 注意点・落とし穴

### 6.1 "ローカル RAG" の定義のばらつき

調査対象の中に「完全ローカル」と「外部サービス必須」が混在していた。`suwa-sh/local-RAG-backend` は「local-RAG」とリポジトリ名に掲げているにもかかわらず OpenAI API が必須であり、`najva-ai/sourcegraph-mcp` は外部 Sourcegraph サービスが前提となっている。リポジトリ名だけで完全ローカル性を判断しないことが重要。

### 6.2 macOS 専用リポジトリの識別

sebastianhutter/local-rag は README の冒頭に macOS のみ明記しているが、リポジトリ名からは OS 制約が読み取れない。Windows 環境での事前動作確認が必要。

### 6.3 RAG と「コード閲覧ツール」の混同

saiprashanths/code-analysis-mcp のようにファイルを直接読み取るだけの「コード閲覧 MCP」は RAG ではない。トークン消費の観点では、ファイルを丸ごと渡す方式は RAG の目的（コンテキスト圧縮）と逆方向に作用する。

### 6.4 FastMCP バージョン互換性

調査したリポジトリで FastMCP のバージョンが異なる (n-irei は最新版を想定, najva-ai は `fastmcp==2.12.0` を固定)。FastMCP は活発に更新されており、バージョン間の API 互換性に注意が必要。

### 6.5 isink17/codegraph の Go バージョン

Go 1.26+ が必要とされているが、2026-05-03 時点の Go 安定版は 1.24.x 系である。1.26 はリリース候補またはプレリリース版である可能性があり、インストール時に最新バージョンの確認が必要。
