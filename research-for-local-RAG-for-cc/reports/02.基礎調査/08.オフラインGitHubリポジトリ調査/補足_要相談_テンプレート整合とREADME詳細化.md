## 1. README / CLAUDE.md 階層運用（C-2 + E-2 + E-3 統合）

### 1.1 議論の対象範囲

検討項目一覧票における関連項目:
- **C-2**: 「保留」運用範囲の記載先 — README に書く想定だが、どの README か未確定
- **E-2**: レビューフロー運用ガイドの記載先 — `cross-review/README.md` でよいか確認
- **E-3**: 収束条件数値化の階層設計 — cross-review/README → プロジェクト CLAUDE.md → サブフォルダ CLAUDE.md の階層運用

これら 3 項目は「**運用ルール・定義をどの階層のどのファイルに記載するか**」という同一論点。本セクションで統合的に整理する。

### 1.2 提案する階層構造

E-3 でユーザーが提示した階層運用方針（「真のデフォルト値はプロジェクト非依存の cross-review/README.md → プロジェクト単位は CLAUDE.md → 活動単位はサブフォルダの CLAUDE.md → 上位を下位が覆す」）を全運用ルールに適用する形で提案します。

```
┌─────────────────────────────────────────┐
│ Level 1 (デフォルト値・テンプレート資産) │
│ .claude/templates/cross-review/README.md │
└─────────────────────────────────────────┘
                  ↓ 必要に応じて上書き
┌─────────────────────────────────────────┐
│ Level 2 (プロジェクト単位の上書き)        │
│ research-for-xxx/CLAUDE.md               │
│   (「レビュー実施ルール」節)             │
└─────────────────────────────────────────┘
                  ↓ 必要に応じて上書き
┌─────────────────────────────────────────┐
│ Level 3 (活動単位の上書き)                │
│ research-for-xxx/<サブフォルダ>/CLAUDE.md │
└─────────────────────────────────────────┘

参照時のルール: 現在のセッションが対応する CLAUDE.md に該当ルールが記載されていなければ、より上位の値（最終的には Level 1 のデフォルト値）を採用する。
```

## 2. テンプレート間の整合性（D-2）

### 2.1 議論の対象範囲

D-2 で作業指示者から提示された「修正案」セクションの記述ルール:
- 表形式は必須維持（メリット/デメリット欄含む）
- 修正案が一つでも、デメリットが無い場合でも、表形式で記載

## 3. 補足相対評価示唆への対応（B-5 4 細目）

### 3.1 改善示唆 #3 — Anti-skip rule（観点 × 版数の表拡張）

#### 3.1.1 拡張表の例示

現状の件数推移表（論理整合性テンプレート）:
```markdown
| ラベル | 0.8 | 0.9 | 1.0 |
|---|---|---|---|
| CRITICAL | <TBD> | <TBD> | <TBD> |
| IMPORTANT | <TBD> | <TBD> | <TBD> |
| SUGGESTION | <TBD> | <TBD> | <TBD> |
| POSITIVE | <TBD> | <TBD> | <TBD> |
```

**拡張案**: 観点ごとの「ステータス + ラベル別件数」を版数別に記録する形に拡張。

```markdown
### 版数とレビュー指摘件数（観点別）

#### 版 0.8 のレビュー結果

| 観点 | ステータス | CRITICAL | IMPORTANT | SUGGESTION | POSITIVE |
|---|---|---|---|---|---|
| 論理整合性 | 指摘あり | 1 | 2 | 0 | 1 |
| カバレッジ十分性 | 指摘なし | 0 | 0 | 0 | 0 |
| 調査目的との整合性 | 指摘あり | 0 | 1 | 1 | 0 |
| 仮説の妥当性 | スコープ外 | - | - | - | - |
| **合計** | — | 1 | 3 | 1 | 1 |

#### 版 0.9 のレビュー結果

| 観点 | ステータス | CRITICAL | IMPORTANT | SUGGESTION | POSITIVE |
|---|---|---|---|---|---|
| 論理整合性 | 指摘なし | 0 | 0 | 0 | 1 |
| カバレッジ十分性 | 指摘なし | 0 | 0 | 0 | 0 |
| 調査目的との整合性 | 指摘なし | 0 | 0 | 0 | 0 |
| 仮説の妥当性 | スコープ外 | - | - | - | - |
| **合計** | — | 0 | 0 | 0 | 1 |
```

ステータスの値:
- **指摘あり**: 該当観点でレビュー実施し、何らかの指摘（CRITICAL/IMPORTANT/SUGGESTION/POSITIVE のいずれか）が出た
- **指摘なし**: 該当観点でレビュー実施し、指摘ゼロ（POSITIVE もゼロ）
- **スコープ外**: 該当観点をレビューの対象外とした（D-3「観点の取捨選択可ルール」に基づく明示的な除外）

#### 3.1.2 期待される効果

1. **「指摘ゼロ」と「観点スキップ」の区別が明確化**: 現行の件数推移表では「ある観点に指摘がない」と「ある観点をレビューしていない」が同じく「件数ゼロ」と表現されてしまう。観点別ステータスの明示により、レビュアーが本当にチェックしたかが可視化される。
2. **レビュアーの自己レビュー促進**: 観点ごとに記入を強制することで、レビュアー自身が「全観点を漏れなくチェックしたか」を意識する効果。

### 3.4 改善示唆 #6 — 指摘の確度欄（必須化 vs 不採用）

#### 3.4.1 議論の対象範囲

ユーザー判断基準: 「レビューイにとって有用と思われるのであれば必須項目として追加。寄与しないのであれば追加しない」

確度欄（HIGH/MEDIUM/LOW）を各指摘エントリに追加するかどうかを判断する。

#### 3.4.2 採用した場合のメリット・デメリット

##### メリット
1. **レビュアー自身の自己整理**: 指摘を出す際に「自分はどの程度確信しているか」を明示することで、過度な指摘抑制（自己検閲の促進）。
2. **作業指示者の判断補助**: 確度 LOW の指摘は却下しやすくなる。
3. **レビューイの応答強度の調整**: 確度 LOW の指摘には簡潔に応答、HIGH の指摘には詳細に応答、といった粒度調整。

##### デメリット
1. **判断基準の曖昧さ**: 「HIGH/MEDIUM/LOW」の境界が主観的。レビュアーごとに揺れる可能性。
2. **新フェーズとの重複**: レビューイFB フェーズ（0.9 版）で「同意の程度」がレビューイから返ってくるため、結果的に確度の補正が事後的に行われる。事前に確度を表明する意義が薄まる。
3. **記入負荷**: 全指摘に確度を付与する負担。
4. **「自信がない指摘は出さない」という原則との整合**: クロスレビューの本質は「指摘の質」であり、確度 LOW の指摘を許容するのは設計思想と矛盾する可能性。

#### 3.4.3 レビューイ作業への寄与判断

ユーザーの判断基準（レビューイにとって有用かどうか）に照らすと:

- レビューイは「指摘内容に対して同意の程度を判断する」のが本来の作業
- 同意の程度の判断は、**指摘の内容自体**を読んで行うものであり、**確度ラベル**を見て行うものではない
- 確度 LOW の指摘でも、内容が妥当であればレビューイは「全面同意」と回答する（確度ラベルは判断材料ではない）
- 結局、**確度ラベルがレビューイの回答内容や作業量に直接影響する場面はほぼない**

#### 3.4.4 Claude の推奨

**不採用**。理由:
1. レビューイへの寄与が限定的（上記 3.4.3）
2. 新フェーズ（レビューイFB）導入により、確度の事後補正が自然に行われる仕組みが既に存在する
3. レビュアーが「自信がない指摘」を表現したい場合は、本文中で「（要確認: ◯◯のため）」のように記述する余地がある
4. 雛型に項目化するメリットが、記入負荷・判断曖昧性のデメリットを上回らない

#### 3.4.5 作業指示者の判断コメント

本提案は取り下げ（不採用）という結論は変わらない前提で、いくつか見解や質問を記載します。

> #### 3.4.2 採用した場合のメリット・デメリット
> ##### メリット
> 1. **レビュアー自身の自己整理**: 指摘を出す際に「自分はどの程度確信しているか」を明示することで、過度な指摘抑制（自己検閲の促進）。

この点については、過度な指摘の抑制／自己検閲の促進として、Claudeが具体的にどのような処理（プロセス）を行うかが重要なポイントであります。  
たとえば、気になった内容は全て指摘として挙げるが、挙げっぱなしにすることなく、その指摘が妥当かどうか、指摘そのものが誤っていないかという自身の指摘の検証作業が必ず実行されるようになる、というのであれば価値があります。  
もっとも、確度欄を設けるのではなくレビュー時のルールとして明記すればよいものと思うので、本提案の採用理由にはなりません。（見解・コメント）

> ##### デメリット
> 1. **判断基準の曖昧さ**: 「HIGH/MEDIUM/LOW」の境界が主観的。レビュアーごとに揺れる可能性。

レビューアごとに揺れが発生することは、LLMや人間の特性上致し方ないことであり、確度欄に限った話でもなく、その揺れの影響を少しでもカバーするためのアプローチの一つがクロスレビュー（正確には複眼レビュー）ですから、そのような揺れのある観点が評価の絶対的要素に位置づけられない限りは、殊更デメリット視する必要は無いかと思います。（見解・コメント）

> 3. **記入負荷**: 全指摘に確度を付与する負担。

人間のレビューアに課す場合は確実にそこそこの負担になりますが、Claudeに書かせる場合も、Claudeのリソースをそこそこ消費してしまうものでしょうか？（質問）

> 4. **「自信がない指摘は出さない」という原則との整合**: クロスレビューの本質は「指摘の質」であり、確度 LOW の指摘を許容するのは設計思想と矛盾する可能性。

この原則に関して、「1. **レビュアー自身の自己整理**」へのコメントとも関連しますが、原則に合致していたとしても、自信の無い指摘は自分でセルフチェックを行ったうえで、妥当でないものについてはその自信をもって取り下げた結果、自信がない指摘が出なくなることを前提としていますが、そもそも自信が無い指摘は検証することなくそもそも指摘にされないようになっている場合、流出（誤陰性）の可能性が発生するため望ましくありません。  
そうならないような仕組みとして、確度欄を設けることが唯一の対応ではないとは思いますが、現状Claudeがレビューする時のスタンスとして、前者としてふるまうことが、どこかに明記されているか確認をお願いします。（確認依頼）

**その他**  
上記にコメントした私の理解が、本改善提案の出所（オリジナル）の意図から外れてしまっていないことを念のため確認したいので、出所（Claudeから出た改善提案なのか、情報収集したGitHubリポジトリ内のレビュー関連資産内に記載されたルールなのか、など）

#### 3.4.5 作業指示者の判断コメントに対するClaudeからの回答
