## 0. 本プロジェクトのレビューアプローチ要約（比較の前提整理）

比較を始める前に、本プロジェクトのレビューアプローチを構成要素別に整理しておく。

| 要素 | 現状の定義 |
|---|---|
| 多段構成 | セルフレビュー → クロスレビュー（Claude Opus / Sonnet 並列） → 作業指示者レビュー（必須対象のみ） |
| 観点担当 | Opus = 論理整合性・カバレッジ・調査目的との整合性・仮説妥当性 / Sonnet = 完了条件・命名規則・文書構造・検証パターン具体性 / 人間 = 任意（自由記入） |
| ラベル区分 | CRITICAL / IMPORTANT / SUGGESTION / POSITIVE（4段階固定） |
| 接頭辞 | `C/I/S/P`（論理）、`C-/I-/S-/P-`（実用）、`U-C/U-I/...`（作業指示者）で出所を区別 |
| 収束条件 | 「新規 NG 検出がゼロになるまで」セルフ／クロスレビューを反復。各段で全 NG 対応完了後に次段へ |
| 必須対象 | 計画書 v1.0 完成時 / 各フェーズ完了時報告書 / 最終報告書（作業指示者承認を兼ねる） |
| 個別レビュー依頼 | セルフ／クロスで作業指示者判断を仰ぐべき指摘が出た場合、または手戻り懸念がある場合（相談ドキュメントまたは Issue 形式可） |
| テンプレート構造 | 指摘エントリ単位で「作業指示者の態度表明」テーブルを内蔵し、レビュアーと作業指示者のやり取りを 1 箇所に集約 |
| 作業指示者の関与 | レビュアー（自由観点） + 各指摘への態度表明（採用 / 却下 / 保留 / 改変）+ 自由記述「その他のコメント」欄 |
| 対象除外 | コードレビューは対象外（ルートの `code-reviewer` agent は本調査で不使用） |

以下の各観点で、上記の現状を外部事例と相対評価する。

## A. レビューフローの構造

### A.1 段階数・フェーズ構成

#### 現状

- **3 段階構成**: セルフレビュー → クロスレビュー（Opus + Sonnet 並列） → 作業指示者レビュー（必須対象のみ）
- セルフ／クロスレビューは「新規 NG 検出ゼロ」まで反復
- 各段で全 NG 対応を完了した状態で次段へ進む（段階のゲート化）

#### 外部事例との比較

| 観点 | 現プロジェクト | gstack | doc-lint | borghei contract-review |
|---|---|---|---|---|
| 段数 | 3 段（セルフ → クロス → 人間） | 1 段の中に 4–7 セクション。スキル間連鎖あり（eng → design → CEO） | 1 段の中に 7 フェーズ | 1 段の中に 6 ステップ + 別モード（Rapid Triage）併設 |
| 段間ゲート | 「全 NG 対応完了」で次段へ | セクション内 1 課題 = 1 AskUserQuestion でゲート。各セクションは順次 | フェーズは順次。Phase 7（自動修正適用）は AskUserQuestion でゲート | ステップは順次。Rapid Triage は分離モード |
| 反復 | 「新規 NG 検出ゼロ」まで反復（明示） | スキル連鎖（design 後に CEO へ）は提案ベース。反復は明示されず | 反復ループ自体は明示されないが Health Score の閾値で判定 | デザインレビューに類似する「FIX TO 10 → 再スコア」が gstack plan-design-review にある |

- 外部事例は「単一スキル内の多段フェーズ」が主で、**レビュアーの役割を切り替えながら 3 段で行う構成は本プロジェクトに固有**。
- gstack は「同一スキル内で人間の介入（AskUserQuestion）を細粒度に挟む」設計のため、段数では 1 段だが対話ターン数では本プロジェクトより多い。
- 「**新規 NG ゼロまで反復**」を明示的にループ化している点は、本プロジェクトの方が外部事例より厳格（外部は閾値到達 or スコア合格で打ち切り）。

#### 示唆

- 「3 段 + 各段で NG ゼロまで反復」という構造は外部にない厳格さを持つ反面、**反復回数の上限が明示されていない**。gstack の「FIX TO 10」のような収束条件側に閾値を置く設計を加味するとループ暴走のリスクを抑えられる。
- 段数を 3 で固定している現状は、軽量な成果物（例: 補足調査）にも全段適用するとオーバーヘッドが大きい可能性がある。**成果物の重要度に応じて段階数を可変にする運用ガイド**は外部事例（gstack の Standard / Rapid 二モード、doc-lint のスコア閾値で出力モード切替）から学べる。

### A.2 役割分担

#### 現状

- Opus = 論理面（整合性・カバレッジ・調査目的整合性・仮説妥当性）
- Sonnet = 実用面（完了条件・命名規則・文書構造・検証パターン具体性）
- 人間 = 自由観点
- 役割は「観点」で分担し、**ドキュメント全体を全レビュアーが見る**（パートを切らない）

#### 外部事例との比較

- **gstack の役割分担はペルソナ駆動**: plan-eng-review = エンジニアリングマネージャー、plan-design-review = シニアプロダクトデザイナー、plan-ceo-review = CEO 視点。各ペルソナに**判断哲学（DRY、明示的 > 巧妙、Dieter Rams、Don Norman 等）が紐付く**。
- doc-lint は単一ペルソナ（QA エンジニア相当）で観点を 7 フェーズに分解。
- borghei contract-review は「契約レビュアー」単一ペルソナでプレイブック参照。

| 観点 | 現プロジェクト | gstack |
|---|---|---|
| 分担軸 | 観点（論理 vs 実用） | ペルソナ（エンジニア vs デザイナー vs CEO） |
| 判断基盤 | 観点リストのみ。判断哲学・参考文献は明示なし | 各ペルソナに哲学＋認知パターン＋参考文献を紐付け |
| モデル特性活用 | あり（Opus = 重判断、Sonnet = 機械チェック寄り） | なし（モデル指定の言及なし） |

#### 示唆

- 「**モデル特性に応じた観点分担**」は外部事例にない本プロジェクト固有の工夫で、Opus / Sonnet のコスト比を踏まえると合理的。
- 一方で、**Opus 担当の「論理整合性」「仮説妥当性」のような抽象観点は、判断基盤（参考文献・判断哲学・代表的な誤りパターン）を明示しないと指摘の質がレビュアーセッション間でブレる**懸念がある。gstack のように「判断基盤を skill 内に書き込む」方向は採れる。
- 観点軸（現状）とペルソナ軸（gstack）はトレードオフではなく組み合わせ可能。例えば「Opus + 計画立案者ペルソナ」「Sonnet + QA 担当ペルソナ」のような複合定義にすると、観点の網羅性とブレ抑制を両立できる。

### A.3 反復・フィードバックループの有無

#### 現状

- セルフ／クロスレビュー段で「新規 NG 検出ゼロまで」反復（明示）
- 段間は「全 NG 対応完了後に次段へ」
- 作業指示者レビュー後は、態度表明（採用 / 却下 / 保留 / 改変）に基づき改訂版を作成

#### 外部事例との比較

- gstack plan-design-review は **「スコア 0–10 → FIX TO 10 → 再スコア」のループ**が明示されている。合格条件は「全パスで 8+」。
- doc-lint は反復明示なし。Health Score（0–100）で PASS/FAIL/PARTIAL の 1 回判定。
- gstack は「Anti-skip rule」で「ゼロ発見時は明示的に "No issues found" と書く」ことを強制。**評価漏れと「指摘なし」の区別が明確**。

#### 示唆

- 本プロジェクトの「新規 NG ゼロまで反復」は強力だが、**「ゼロ件報告」を明示的に書かせる仕組み**（gstack の Anti-skip rule 相当）が雛型上にない。レビュアー Agent が観点をスキップしたのか、見たうえで指摘ゼロだったのかの区別がレビュー報告書から読み取りにくい。
- 「FIX TO 10」のような収束目標値は本プロジェクトに馴染まない（CRITICAL/IMPORTANT 等のラベル区分しか持たない）が、**「IMPORTANT 以上が連続で N 回ゼロになったら反復終了」のような収束条件の数値化**は検討余地がある。

## B. レビュー観点の設計

### B.1 観点の明示度

#### 現状

- 雛型のメタ情報で観点を**短い列挙**として示す（例: 論理整合性・カバレッジ十分性・調査目的との整合性・仮説の妥当性）
- 観点ごとのチェック項目・判断基準・代表アンチパターンは**雛型上で明示されていない**
- ラベル区分（CRITICAL/IMPORTANT/SUGGESTION/POSITIVE）の意味は作業指示者レビュー雛型に明記されているが、Opus / Sonnet レビュー雛型には記載なし（暗黙的に共有）

#### 外部事例との比較

| 観点 | 現プロジェクト | gstack | doc-lint | borghei |
|---|---|---|---|---|
| 形式 | 自由記述型 | 自由記述型（だが認知パターン・参考文献を明示） | チェックリスト型（フェーズごとに具体ルール定義） | チェックリスト型（プレイブック参照） |
| チェック項目 | 観点名のみ | パス名 + 各パスの判断基準を本文に記述 | 「>500 行 = CRITICAL」「H1 数」など定量ルール | プレイブック（references/clause_analysis_guide.md）に分離 |
| 判断基準の所在 | 雛型外（暗黙） | SKILL.md 内本文 | SKILL.md 内本文 | 別ファイルに分離 |

#### 示唆

- 本プロジェクトのレビューは**自由記述型寄り**で、レビュアーの汎用知識に大きく依存している。doc-lint の定量チェック項目（行数・H1 数）や borghei のプレイブック参照のような**「客観的に再現可能なチェック」を一部混ぜる**と、レビュー結果の安定性が上がる。
- 特に Sonnet 担当の「命名規則遵守」「文書構造」はルートおよび個別 CLAUDE.md にルールが書かれているため、**「参照すべき判断基盤」を雛型のメタ情報で明示**すれば、判断ブレをさらに抑えられる（現状の「判断基準とした参照ドキュメント群」コメント欄を必須化する方向）。

### B.2 観点の粒度と網羅性

#### 現状

- 4 観点（論理） + 4 観点（実用） = 計 8 観点
- 観点はやや抽象的（「論理整合性」「文書構造」など）
- ドキュメント種別による観点の出し分けはない（計画書も報告書も同じ雛型を使う）

#### 外部事例との比較

- gstack plan-eng-review は **4 大セクション × 各 3–8 個のサブ観点**（合計 20+）。
- gstack plan-design-review は **7 パス × 各 3–5 個のチェックポイント**。
- doc-lint は **7 フェーズ × 各 3–10 個の具体ルール**。
- borghei contract-review は **6 ステップ × プレイブックの数十項目**。

外部事例は本プロジェクトの 2–3 倍以上の細かさを持つ。

#### 示唆

- 本プロジェクトの観点粒度は**意図的に汎用化**されており、「自然言語ドキュメント全般」に適用できる代わりに、**ドキュメント種別固有の重要観点を取りこぼすリスク**がある（例: 計画書なら「タスク間の前後関係矛盾」、報告書なら「結論と根拠データの一貫性」など）。
- ただし、観点を細分化するとレビューコストが上がるため、**「ドキュメント種別ごとの追加観点リスト」を雛型外に持ち、必要時に組み合わせる**運用が現実的。本プロジェクトでは既に「ハマりどころ.md」「Issue 運用ルール.md」のような分離管理の下地があるため、同様のアプローチで観点パッケージを増やせる。

### B.3 ドキュメント種別への適応性

#### 現状

- 雛型はドキュメント種別非依存（計画書 / 報告書 / 設計書 すべて同一雛型）
- メタ情報の「レビュー対象」欄でファイルパスを示すのみ

#### 外部事例との比較

- gstack は **plan-eng-review / plan-design-review / plan-ceo-review / retro** と**ドキュメント種別ごとに skill を分離**。
- doc-lint は Markdown 全般を対象にした構造監査で、種別非依存。
- borghei は **契約書専用 / NDA 専用 / 雇用契約専用 / リース契約専用**と細分化。

#### 示唆

- 本プロジェクトの「種別非依存・観点ベース」設計は、gstack の「種別ごとに skill 分離」と対極にある。
- 本プロジェクトで扱うドキュメント種別は限定的（計画書・調査報告書・設計書・検証報告書）だが、**それぞれに固有の重要観点が存在する**ため、種別別の観点パッケージ（チェックリスト追加分）を持っておく方が安全。
- 一方、雛型自体を分離するとメンテナンスコストが上がるため、**雛型は共通・観点パッケージ（YAML / Markdown）を別管理**で組み合わせる方式が落としどころとして現実的。

## C. レビュー結果の記録・活用

### C.1 結果フォーマットの構造化度

#### 現状

- メタ情報テーブル（レビュー対象・レビュアー・観点・日付・スコープ外）
- レビュー結果サマリ（ラベル件数表）
- 指摘エントリ単位で固定セクション（問題点 → レビューイ回答 → 修正案 → 作業指示者の態度表明）
- 接頭辞（C/I/S/P, C-/I-/S-/P-, U-C/U-I/...）で出所を区別

#### 外部事例との比較

| 項目 | 現プロジェクト | gstack | doc-lint | borghei |
|---|---|---|---|---|
| メタ情報 | あり（標準テーブル） | Review Log（gstack-review-log コマンドで `~/.gstack/` に永続化） | レポートヘッダ | レポートヘッダ |
| 件数集計 | ラベル別件数表 | セクション別の Required Outputs 一覧 | Health Score + PASS/FAIL/PARTIAL | GREEN/YELLOW/RED 件数 |
| 指摘エントリ構造 | 問題点 / 詳細 / 根拠 / 修正案 / 態度表明 | セクション内に課題列挙 + Completion Summary | フェーズ内に Issue 列挙 | 条項別 GREEN/YELLOW/RED + レッドライン |
| 出力ファイル形式 | Markdown | Markdown + Review Log メタデータ | Markdown レポート + 自動修正スクリプト | Markdown + redline 文書 |

- **指摘エントリ内に「作業指示者の態度表明」テーブルを内蔵する設計は本プロジェクト固有**。外部事例では態度表明と指摘が分離している（gstack は AskUserQuestion で対話的に確認、doc-lint は人間の判断は別管理）。
- 外部事例の方が**スコア（数値）による集約**が明確。本プロジェクトは件数集計のみで、「品質がどの程度か」の数値表現がない。

#### 示唆

- **「指摘 + 態度表明 + レビューイ補足」を 1 箇所に集約する設計は、後述の「作成者コメント → レビュアー修正」フロー（観点 F）にも適合し、本プロジェクトの強み**。
- 数値スコア（Health Score 相当）を導入するかは要検討。本プロジェクトのドキュメントは多様性が高く、機械的スコアリングは難しい。ただし、**「IMPORTANT 以上の件数 / 総ページ数」のような単純比率**は反復収束の判断に使える。

### C.2 作業指示者への情報提示の効率

#### 現状

- 件数サマリでまず全体像を把握 → 個別指摘エントリで詳細確認の 2 段階
- 「作業指示者の態度表明」テーブルが各指摘の末尾にあるため、**読みながら即座に判断を記入できる**
- 作業指示者レビュー雛型には**記入ガイドが埋め込まれている**（接頭辞ルール、関連指摘の参照記法、ラベル区分の意味）

#### 外部事例との比較

- gstack は AskUserQuestion で**1 課題ずつ対話で確認**。情報提示は逐次的（一括レポートではない）。
- doc-lint は**一括レポート**（audit/doc-lint-report.md）。Health Score で全体感を提示してから詳細列挙。
- borghei は**Standard Review（詳細）と Rapid Risk Triage（CRITICAL 3 点以内）の 2 モード**で、状況に応じた粒度切替が可能。

#### 示唆

- 本プロジェクトは**一括レポート方式**で、これは大量指摘を効率的にレビューする場合に適する。
- ただし、CRITICAL が極少数の場合に「**重要指摘だけを最初に読みたい**」というニーズには応えにくい。borghei の Rapid Triage 相当（**サマリ直下に「CRITICAL ハイライト」を 3 点以内で抜粋する欄**）を雛型に追加すると、判断速度が上がる。
- gstack の対話型（AskUserQuestion）は本プロジェクトの「個別レビュー依頼」モードに概念的に近いが、本プロジェクトでは依頼判断がレビュアー Agent に委ねられている。**「対話モードを起動すべき条件」を明示**するとフロー選択がブレない。

### C.3 後続作業への引き継ぎやすさ

#### 現状

- 「態度表明（採用 / 却下 / 保留 / 改変）+ コメント」が指摘エントリ内に残るため、**改訂版作成時に Claude が直接参照可能**
- 作業指示者レビュー雛型に「その他のコメント」欄があり、改訂版作成時のコンテキストとして参照される旨が明記
- ファイル名規約（`<観点名>_<日付YYYY-MM-DD>.md`）で複数回レビューが時系列で残る

#### 外部事例との比較

- gstack は **gstack-review-log で `~/.gstack/` にメタデータ永続化**。後続スキル（design-review → CEO-review）への連鎖時に Review Log を参照する設計。
- doc-lint は **Safe-Fix Script を生成**するため、レビュー結果が直接「修正アクション」になる。
- borghei は **redline 文書（修正提案を反映済みの契約書）を直接生成**。

#### 示唆

- 本プロジェクトの引き継ぎは**「改訂版を Claude に作らせる」前提のテキストベース**。これは柔軟性が高い反面、**「指摘 → 修正版差分」の追跡可能性が改訂版コミットの diff に依存**する。
- doc-lint の Safe-Fix Script や borghei の redline のような**「機械的に適用可能な修正提案」を雛型に組み込む**余地はある。例えば「修正案」セクションに**「適用パッチ（Markdown diff 形式）」**の任意欄を追加すれば、改訂作業の効率と再現性が上がる。
- 既存の Git 運用ルール（ルート CLAUDE.md）と組み合わせれば、**「レビュー指摘 → 改訂コミット → diff レビュー」が 1 サイクルで回る**ため、引き継ぎの基盤は既に整っている。

## D. Claude の役割設計

### D.1 独立性・バイアス排除の仕組み

#### 現状

- Opus / Sonnet を**別 Agent として並列起動**してクロスレビュー実施
- 各レビュアーは「**独立第三者**」と明記
- セルフレビュー → クロスレビューの順で、**作成者 Agent と異なる Agent がレビューを担当**することでバイアス排除を狙う
- code-reviewer agent は本調査では使用しない旨が明記

#### 外部事例との比較

- gstack は**ペルソナベースで独立性を演出**するが、技術的には同一 Claude セッションが複数ペルソナを切り替える設計（モデル分離は明示なし）。
- doc-lint は単一スキル内で実行（独立性の明示的設計はなし）。
- borghei も同様。

**本プロジェクトは「異なるモデル + 異なる Agent」で技術的にも独立性を担保している**点で、外部事例より独立性の設計が強い。

#### 示唆

- 「Opus + Sonnet 並列」は強い独立性を持つ反面、**両者が同じ訓練データに由来する共通バイアス**は排除できない。完全な独立性は人間レビュー（作業指示者レビュー）で担保する設計と理解できる。
- gstack のペルソナ分離（哲学・参考文献の違いを明示）は**論理的な多様性を増す**ため、本プロジェクトでもモデル分離に加えてペルソナ／哲学を明示すると、バイアス排除がさらに強化される。

### D.2 対話性（作業指示者との往復）の設計

#### 現状

- 作業指示者レビューは**雛型記入の往復**（オフライン的）。リアルタイム対話は前提にしない
- 「個別レビュー依頼」モードで、相談ドキュメントまたは GitHub Issue 形式での問いかけが可能
- 作業指示者レビュー雛型の「その他のコメント」欄が自由対話の場

#### 外部事例との比較

- gstack の **AskUserQuestion 中心設計は最も対話的**（1 課題 = 1 質問、複数まとめ禁止）。
- doc-lint は Phase 7 の自動修正適用時のみ AskUserQuestion で確認。
- borghei は対話型ではなくレポート提出型。

| 軸 | 現プロジェクト | gstack | doc-lint | borghei |
|---|---|---|---|---|
| 対話頻度 | 低（雛型記入往復） | 高（1 課題 = 1 質問） | 低（最後に 1 回） | ゼロ（レポート提出のみ） |
| 対話粒度 | 全指摘の態度表明を一括 | 個別課題ごと | 自動修正適用の YES/NO | なし |
| 同期性 | 非同期（記入 → 後で読む） | 同期（即時） | 半同期 | 非同期 |

#### 示唆

- 本プロジェクトは**非同期・一括**設計。これは作業指示者の都合を尊重する一方、**「即座に判断できる軽微な指摘」と「熟考が必要な重大指摘」を一括で扱う**ことになり、後者のレビュー疲労が高まる可能性がある。
- gstack の AskUserQuestion 方式を**個別レビュー依頼モードに限って採用する**（CRITICAL のみ即時対話、IMPORTANT 以下は雛型記入）と、対話コストと熟考時間を両立できる。
- ただし、AskUserQuestion 相当の対話は本プロジェクトの「Claude Code セッション中の対話」で既に実現可能であり、**雛型に組み込むよりも運用ルール（CLAUDE.md）で「CRITICAL 検出時は対話確認後に雛型記入」と書く方が軽量**。

### D.3 自律性と人間判断の分担

#### 現状

- セルフ／クロスレビューは Claude 自律で「新規 NG 検出ゼロ」まで反復
- 作業指示者レビューは「必須対象（計画書 v1.0 / フェーズ完了報告書 / 最終報告書）」のみ
- 個別レビュー依頼の判断は Claude（「作業指示者の判断を仰ぐべき指摘」「手戻り懸念」のいずれかで起動）

#### 外部事例との比較

- gstack は**ほぼ全工程で人間判断を介在**（AskUserQuestion で都度確認）。自律性は低めで人間判断密度が高い。
- doc-lint は**ほぼ全工程で自律実行**（人間介在は最後の自動修正適用のみ）。
- borghei は**完全自律でレポート生成**、人間判断は出力後。

#### 示唆

- 本プロジェクトは**「Claude 自律で品質を担保したうえで、要所で人間判断」**という中間設計。これは**コストと品質のバランスとして合理的**。
- 「個別レビュー依頼の起動条件」が**Claude の主観判断**に依存している点はリスク。**「CRITICAL 検出 N 件以上」「特定キーワード検出時」など客観的トリガ**を補完すると、判断のブレが減る。
- 「判断ミスによる後続工程への大きな手戻り懸念」というトリガは抽象的で、**Claude 側の保守的バイアスで個別レビュー依頼が頻発する**可能性がある。具体的な手戻り基準（「設計の根幹を変える」「スコープを変える」など）を例示すると安定する。

## E. 品質保証の仕組み

### E.1 レビューのレビュー（メタレビュー）

#### 現状

- 多段構成（セルフ → クロス → 人間）自体がメタレビューの役割を果たす
- ただし、**「クロスレビューの質」を評価する明示的な仕組みはない**
- 作業指示者レビューが事実上の最終メタレビュー

#### 外部事例との比較

- gstack は**スキル間連鎖（design-review → CEO-review）で前段レビュー結果を後段が参照**するため、メタレビュー的な機能を持つ。
- vlad-ryzhkov の `output-review` は**他 skill の出力をチェックリストに照らしてレビューするメタ skill**として明示的に存在。
- doc-lint / borghei にはメタレビュー機構なし。

#### 示唆

- 本プロジェクトは**人間の作業指示者がメタレビューを担う**設計で、これは品質的には最高だがコストが高い。
- vlad-ryzhkov の `output-review` 相当の**「クロスレビュー報告書自体をレビューする skill」**は本プロジェクトでも有用な可能性がある。特に「指摘の質（具体性・再現性・根拠の妥当性）」を機械的にチェックする観点は、雛型の `{{プレースホルダ}}` 残存検出など軽量な実装から始められる。

### E.2 収束条件（いつレビューを終えるか）

#### 現状

- セルフ／クロスレビュー: **「新規 NG 検出ゼロ」**（明示）
- 作業指示者レビュー: 全指摘への態度表明完了（暗黙）
- 反復回数の上限は明示されていない

#### 外部事例との比較

- gstack plan-design-review: **「全パスでスコア 8+」**で合格
- doc-lint: **Health Score の閾値で PASS/FAIL/PARTIAL** 判定
- borghei: 1 回のレビューで完結（反復なし）

#### 示唆

- 「新規 NG ゼロ」は理想的だが、**長文ドキュメントでは「何かしら新規指摘が毎回出る」状態に陥り、収束しない**リスクがある。
- 外部事例の**閾値ベース収束**（スコア / 件数）を補完条件として併用すると、実用的な収束保証になる。例: 「**新規 CRITICAL ゼロ + 新規 IMPORTANT が 2 回連続で N 件以下**」など。
- 本プロジェクトの「変更履歴セクション末尾保持」運用は反復履歴の追跡に使えるため、**過去ラウンドの件数推移を見て収束判定**する仕組みも雛型側で支援可能。

### E.3 誤指摘・見落としへの対処

#### 現状

- **誤指摘**: 「作業指示者の態度表明」テーブルで「却下」を選び、コメントに理由を記入
- **見落とし**: 反復による検出 + 作業指示者レビューでの追加指摘
- レビュアーへのフィードバック（「次回はこの観点を強化せよ」など）の機構は雛型上にない

#### 外部事例との比較

- gstack の Anti-skip rule は**「ゼロ件報告の明示化」で見落としを抑制**するが、誤指摘への対処は明示なし。
- doc-lint は機械的チェックのため誤指摘リスクが低い（半面、「文脈を読む指摘」はできない）。
- borghei は**信頼度スコア（HIGH/MEDIUM/LOW）**を付与する設計があり、誤指摘リスクの自己申告に該当。

#### 示唆

- 本プロジェクトでは**指摘の「自信度」「再現性」を表現する欄がない**。borghei の信頼度スコアを参考に、**「指摘の確度（HIGH/MEDIUM/LOW）」を任意欄として雛型に追加**すると、却下判定や反復対象選別がしやすくなる。
- **却下指摘のパターン蓄積** — 却下されたパターンを `improvements/` 配下に蓄積し、後続レビュアーへの judgement input に使う運用が考えられる（既に「improvements/【本紙】要改善点一覧.md」がある下地を活かせる）。
- **見落とし**については、**作業指示者レビューで初めて出た指摘を「Claude レビューでは検出されなかった観点」として記録し、観点定義の改善にフィードバック**する仕組みが、長期的には有効。

## F. 今回追加したプロセス（作成者コメント → レビュアー修正）との対比

### F.1 本プロジェクトの「作成者コメント → レビュアー修正」プロセス

雛型上の構造を見ると、各指摘エントリに「**レビューイからの回答・見解・補足**」セクションが配置されており、**レビュー結果に対して作成者（レビューイ）が応答し、それを踏まえてレビュアーが修正案を確定する**フローが組み込まれている。これは以下の構造で表現される。

```
問題点
  └─ レビューイからの回答・見解・補足  ← 作成者コメント
修正案
  └─ レビューイからの回答・見解・補足  ← 作成者コメント
    └─ 作業指示者の態度表明           ← 最終判断
```

つまり「**レビュアーの一方的指摘 → 作成者の応答 → 修正案 → 最終判断**」という双方向プロセス。

### F.2 外部事例との対比

| 事例 | 類似プロセスの有無 | 詳細 |
|---|---|---|
| gstack plan-eng-review | **部分的にあり** | AskUserQuestion 自体が「作成者（≒ユーザー）からの即時応答」を求める設計。1 課題 = 1 質問の対話形式で、応答に基づいて次の判断を行う。**ただし非同期での「コメント記入欄」は持たない**（同期対話で完結） |
| gstack plan-design-review | **あり（実質的）** | スコア → FIX TO 10 → 再スコアのループは「指摘 → 修正 → 再評価」の双方向プロセスに相当。ただし「修正前にレビューイが反論する余地」は明示されていない |
| doc-lint | **なし** | レビュー結果は一方向。Phase 7 の自動修正適用時のみ AskUserQuestion で同期確認 |
| borghei contract-review | **なし** | レポート + redline 提出型で、作成者（契約書執筆者）の応答を組み込む設計はない |
| vlad-ryzhkov spec-audit / output-review | **なし** | チェックリスト型で一方向 |

### F.3 位置づけの違い・共通点

#### 共通点

- gstack の AskUserQuestion 方式と本プロジェクトの「作成者コメント」欄は、**「レビュアーの判断を作成者の文脈情報で補強する」目的が共通**。レビュアーが見えない経緯・意図を作成者が補足する場として機能する。
- gstack plan-design-review の「FIX TO 10」ループと、本プロジェクトの「新規 NG 検出ゼロまで反復」は、**反復による品質収束という目的が共通**。

#### 違い

| 軸 | 本プロジェクトの方式 | 外部事例の主流 |
|---|---|---|
| 同期性 | 非同期（雛型に書き込む） | 同期（AskUserQuestion）または存在しない |
| 記録性 | 高（レビュー報告書に永続的に残る） | 低（gstack は対話ログとして残るが構造化度は低い）/ 存在しない |
| 作成者の反論権 | 明示的にあり（雛型上に欄あり） | gstack は対話で実質可能、他は事実上なし |
| 改訂作業の所在 | レビュー後に別工程で改訂版作成 | gstack は対話の中で計画を即時更新する設計 |

#### 示唆

- 本プロジェクトの「作成者コメント → レビュアー修正」プロセスは、**外部事例にはほぼ類似がない独自性の高い設計**。特に**「非同期かつ記録性が高い双方向プロセス」**は、長期プロジェクトの判断履歴追跡に有利。
- gstack の同期対話型と比較すると、**判断の即時性は劣るが、文脈再構築のコスト（後で読み返す人にも分かる）は本プロジェクトの方が低い**。
- ただし、**「修正案」セクション後の「レビューイからの回答・見解・補足」がほぼ未活用になりがち**（雛型を見ると 2 箇所に同名セクションがあるが、運用上は問題点側のみ使われやすい）。**修正案への作成者反論の入る余地を運用ルールで明示**するか、雛型側で「修正案は作成者承認後に確定」のフローを書き込むと、双方向性が強化される。
- 本プロジェクトの「個別レビュー依頼」モード（相談ドキュメント / Issue 形式）は、gstack の同期対話に近い性格を持つ。**「作成者コメント → レビュアー修正」プロセスがうまく機能しない場合の escalation 経路**として位置づけられている、と整理可能。

## 総合評価

### 強み

- **多段 + 複数モデル並列** によるバイアス排除と独立性が、外部事例より明確に設計されている
- **指摘 + 作成者コメント + 態度表明** を 1 エントリに集約する構造化が**外部事例にない独自性**を持ち、長期プロジェクトの判断履歴追跡に強い
- 「**新規 NG 検出ゼロまで反復**」という収束条件の明示性が高い
- **接頭辞による出所識別**（C/I/S/P, C-/I-/S-/P-, U-C/U-I/...）で、複数レビュアーの指摘を統合しやすい
- 「作業指示者の態度表明」テーブルが指摘エントリ内に内蔵され、**判断記入の物理的距離が短い**（読みながら判断できる）
- ラベル区分（CRITICAL/IMPORTANT/SUGGESTION/POSITIVE）が**作業指示者レビュー雛型に意味付きで明記**されており、人間記入時の迷いが少ない
- **コードレビュー領域（`code-reviewer` agent）と本調査領域（自然言語ドキュメント）を明示的に分離**しており、適用範囲のブレがない
- **Git 運用ルール / レビュー運用ルール / `improvements/` 蓄積** の組み合わせで、レビュー → 改訂 → 再レビューの足回りが既に整備されている

### 弱み

- **観点が抽象的かつ自由記述型**で、レビュアーの汎用知識依存度が高く、セッション間でのブレ要因になりうる
- **判断基盤（参考文献・判断哲学・代表アンチパターン）が雛型上で明示されていない**（gstack は哲学・参考文献を明示）
- **ドキュメント種別ごとの固有観点が取り込まれていない**（計画書・報告書・設計書を同一雛型で扱う）
- **反復回数の上限が明示されておらず**、ループ暴走リスクがある
- **「指摘ゼロ」と「観点スキップ」の区別ができない**（gstack の Anti-skip rule に相当する仕組みがない）
- **指摘の確度・自信度（HIGH/MEDIUM/LOW）を表現する欄がない**ため、却下判定や反復対象選別に情報が不足
- **レビュー結果のサマリ提示が件数表のみで、CRITICAL ハイライト等の優先閲覧支援がない**（borghei の Rapid Triage に相当する機構がない）
- **クロスレビュー報告書自体の品質を評価するメタレビュー機構がない**（vlad-ryzhkov の `output-review` 相当が不在）

### 優先度の高い改善示唆（観察にとどめ、変更提案には踏み込まない）

優先度の判断基準は「**現プロジェクトの設計思想を維持したまま導入できる軽量さ**」と「**反復・収束品質への寄与度**」の両立。

1. **【高】判断基盤の明示** — 雛型のメタ情報「判断基準とした参照ドキュメント群」コメント欄を必須化し、ルート CLAUDE.md / 個別 CLAUDE.md / `.claude/rules/` 等の参照先をレビュアーに明示する。観点の抽象度を保ったまま、判断ブレを抑制できる。
2. **【高】収束条件の数値化補完** — 「新規 NG 検出ゼロ」に加えて「**IMPORTANT 以上が N 回連続で M 件以下**」のような閾値ベース条件を併用する。長文ドキュメントでの収束保証と反復暴走防止に寄与。
3. **【中】Anti-skip rule 相当の導入** — レビュー結果サマリで**「観点ごとの評価結果（指摘あり / 指摘なし / スコープ外）」を明示**するセクションを雛型に追加する。「指摘ゼロ」と「観点スキップ」の区別が可能になる。
4. **【中】ドキュメント種別ごとの追加観点パッケージ** — 雛型は共通維持しつつ、**「計画書向け追加観点」「フェーズ報告書向け追加観点」を別ファイル管理**して必要時に組み合わせる。「ハマりどころ.md」「Issue 運用ルール.md」と同様の分離管理パターンを踏襲できる。
5. **【中】CRITICAL ハイライト欄の追加** — 件数サマリ直下に **「CRITICAL 抜粋（最大 3 件）」欄**を追加する。borghei Rapid Triage 相当の優先閲覧支援。CRITICAL 件数が多いケースで作業指示者の判断速度が上がる。
6. **【低〜中】指摘の確度欄追加** — 各指摘エントリに**「確度（HIGH/MEDIUM/LOW）」を任意欄**として追加する。却下判定や反復対象選別の根拠情報になる。borghei の信頼度スコア相当。
7. **【低】メタレビュー（クロスレビュー報告書のレビュー）の軽量実装** — 雛型の `{{プレースホルダ}}` 残存検出、件数サマリと本文の整合性チェックなど、機械的に検出できる項目から着手。vlad-ryzhkov `output-review` 相当の最小実装。
8. **【低】「修正案への作成者反論」運用の明確化** — 雛型に既に存在する「修正案後の作成者コメント欄」の用途と、活用すべき場面を運用ルールで明示する。雛型自体の変更は不要で、運用ガイド側で対応可能。
