## 2. 改訂コンセプトそのものへの懸念事項・要方針決定事項・改善提案

§1 で確認した通り、改訂コンセプトは忠実に実装されている。その上で、コンセプトそのものに対して、副作用や追加検討の余地がある点を整理する。本セクションの位置づけは「**コンセプトの根本的な見直しを求めるものではなく、運用に入る前に方針決定しておくべき論点の整理**」である。

なお、`補足_レビューアプローチ相対評価.md` §総合評価で挙げた改善示唆との対応関係（今回コンセプトに含まれていない理由）は、**コンセプト組み立て時に当該調査結果を未読だったためであり、不採用の判断結果ではない**ことが作業指示者から共有されている。本節ではその論点を扱わず、§3 にて整理する。

### 2.1 全体方針（見出し + 箇条書きの強制）

#### 2.1.1 箇条書きへの強制が文脈断片化を招く副作用

- **懸念事項**: 「概要 / 詳細 / 根拠」の 3 点セットを各 1 行で書こうとすると、文脈が断片化して意味が伝わりにくくなる
- **改善提案**: テンプレート内コメントに「各点は箇条書きで複数行展開可」「必要に応じて短い段落説明を許容」を明示する
- **要方針決定**: 「半強制」のレベル感をどこに置くか（厳格な 1 行記述 vs 短文記述の許容）

#### 2.1.2 見出し階層の深さによる視覚的可読性の低下

- **懸念事項**: H5 (`#####`) まで使う設計は GitHub Markdown レンダリング上で太字との視覚的差がほぼ無くなる。PR 上で人間がレビューする際の階層把握が難しくなる
- **トレードオフ**: grep / 範囲読込での扱いやすさを優先するなら現状維持で良い。視覚的可読性は副作用として認識
- **要方針決定**: grep 優先 vs 視覚優先 のどちらを取るか（推奨: 現状の grep 優先設計を維持しつつ、副作用を認識として残す）

### 2.2 冒頭メタ情報

#### 2.2.1 細分化版数の表記書式

- **懸念事項**: 「差戻し時は 0.91, 0.92」というルールは、表記として「0.9 と 1.0 の中間に位置する細分化」が直感的に伝わりにくい。「0.91」は数値として読むと「0.9 より大きい」と誤読される懸念
- **改善提案**: セマンティックバージョニング風の「0.9.1 / 0.9.2」表記への変更
- **要方針決定**: 「0.91 / 0.92」表記を維持するか、「0.9.1 / 0.9.2」に変更するか

#### 2.2.2 件数推移表の列固定の柔軟性

- **懸念事項**: 「0.8 / 0.9 / 1.0」固定 3 列は、差戻し細分化（0.9.1, 0.9.2）が発生したケースに対応できない
- **改善提案**: README に列追加運用ルールを明記する。雛型自体に「必要時に列追加」のコメントを書く案も併存
- **要方針決定**: 雛型を 3 列固定とし運用で行追加か、雛型自体に拡張可ルールをコメントで書くか

#### 2.2.3 「判断基準」セクションの必須化（コンセプトレベル）

- **懸念事項**: コメント内で記載例を示すのは「任意運用」を意味する。コンセプトとして「判断基盤を明示する」を採用するなら、必須欄として位置付けるべき
- **改善提案**: コメントを解除して本文化（必須欄）にする
- **要方針決定**: 「判断基盤の明示」をコンセプトの一部として正式に取り込むか、任意運用に留めるか
- **備考**: §4.1.5 で実装レベルの対応案を別途整理しているが、本論点はコンセプトレベルの方針確認

### 2.3 レビューイ記入箇所の正式化

#### 2.3.1 修正案側のレビューイ補足の活用見込み

- **懸念事項**: 問題点に同意 → 修正案にも全面同意のケースでは、修正案側の補足セクションが形骸化する。前回の試験運用でも修正案側の補足はほぼ未活用だった可能性が高い（実態確認推奨）
- **改善提案**: 修正案側を「任意」とし、コメントで「問題点側で尽きている場合は省略可」と明記
- **要方針決定**: 必須欄として全件埋めさせるか、任意欄として運用するか

#### 2.3.2 問題点側の記入項目の細分化レベル

- **懸念事項**: 「同意の程度 / 同意しない場合の経緯 / 自己判断の意図 / 作業指示者向け補足」と 4 項目に分けているが、実運用では「同意の程度 / 同意しない場合の根拠 / 作業指示者向け補足」の 3 点で十分機能すると思われる（経緯と意図の区別は記入者の主観で揺れやすい）
- **改善提案**: 3 点に集約
- **要方針決定**: 細分化を維持するか、簡素化するか

### 2.4 作業指示者の態度表明

#### 2.4.1 「条件付き採用」と「差戻し」の境界の曖昧さ

- **懸念事項**: 「大きな対応案の修正指示」の "大きな" が運用者の主観に依存する
- **改善提案**: README に例示を置く（例: 「修正案の本質を変える指示は差戻し、細部の調整指示は条件付き採用」）
- **要方針決定**: 例示の追加が必要か、運用者の裁量に委ねるか

#### 2.4.2 「保留」の運用範囲

- **懸念事項**: 新フェーズで「情報収集型保留」は事前解消される設計を踏まえると、態度表明での「保留」は「意思決定型保留」（後続フェーズへ先送り）に絞られるはず。これを明記しないと運用が揺れる
- **改善提案**: README に「保留 = 意思決定型保留に限定」と明記
- **要方針決定**: 「保留」を意思決定型に限定するか、情報収集型保留も残すか（残す場合、新フェーズの意義が薄れる）

#### 2.4.3 「却下」の使用シーンの明確化

- **懸念事項**: 同じく新フェーズで「誤指摘の取り下げ」は事前解消されるため、「却下」は「作業指示者が持つコンテキストにより指摘が無効と判明する」ケースに限られる。実運用上ほぼ使用されない区分として位置付けられる
- **改善提案**: README に「却下」の運用シーンを明記し、運用上ほぼ発生しないことを示唆
- **要方針決定**: 「却下」区分を維持するか、より積極的に削減を検討するか

### 2.5 末尾の変更履歴の表形式化

#### 2.5.1 未到達版を雛型に残すかどうか

- **懸念事項**: 「0.8 / 0.9 / 1.0」を雛型として予め用意する設計は、想定フローの可視化効果がある反面、軽量成果物（作業指示者レビュー不要なケース）では 0.9 / 1.0 行が永遠に空のまま残る
- **改善提案 A**: 雛型は 0.8 行のみとし、フェーズ到達時に行追加（柔軟）
- **改善提案 B**: 現状維持し、未到達行は「（未到達）」等で明示（フロー可視化重視）
- **要方針決定**: A / B どちらを採用するか

### 2.6 改訂コンセプトに含まれていない視点

#### 2.6.1 テンプレート自体のバージョン管理

- **懸念事項**: 既存報告書（旧テンプレート）と新テンプレートの併存をどう扱うか不明。テンプレート自体に「テンプレート v1.0」相当のバージョン記載を持たせるか、README で版管理する設計が将来必要
- **改善提案**: 今回スコープに含めるか、将来課題として認識するかを決定する
- **要方針決定**: テンプレート自体のバージョン管理を導入するタイミング

#### 2.6.2 セルフレビューとの整合

- **懸念事項**: セルフレビュー報告書のテンプレートは未定義（メモリ `reference_review_files.md` に「未定義」と明記）。今回の改訂思想（版数管理、態度表明、レビューイFB）はクロスレビューに固有の要素を含むため、セルフレビューに同じ思想を適用するかは別検討
- **改善提案**: 今回スコープ外とし、将来課題として認識
- **要方針決定**: セルフレビュー報告書のテンプレート整備のタイミング

## 4. 論理整合性テンプレートに対する追加修正・追加内容（提案）

### 4.1 改訂内容に内在する不整合（軽微・必須対応推奨）

#### 4.1.1 IMPORTANT セクションの省略形

- 現状: L131-149 で `{{...}}` プレースホルダのみで詳細フォーマット未記載
- 影響: テンプレートとして単独で完結性が低い。Claude が雛型を埋める際に CRITICAL を参照する暗黙運用が必要
- 対応案 A（推奨）: CRITICAL の構造を IMPORTANT にも複製
- 対応案 B: 省略形を維持し、「IMPORTANT は CRITICAL の構造を参照」と冒頭にコメントで明記
- 推奨理由: ファイル長は増えるが、Claude / レビュアーの双方が雛型単独で完結できるメリットが大きい

#### 4.1.2 SUGGESTION のレビューイ補足の見出し階層

- 現状: SUGGESTION では `#### S1. レビューイからの見解・補足`（H4）。CRITICAL/IMPORTANT は `##### C1. レビューイからの〜`（H5）
- 影響: grep / 範囲抽出の見出し階層が一貫しない
- 検討事項: SUGGESTION は「観点 + 提案」の 2 ブロック構造のため、それぞれにレビューイ補足を分ける（H5 構造）に揃えるか、現状の単一 H4 維持か
- 対応案 A: 現状維持（SUGGESTION は単一の補足で完結する性質）
- 対応案 B: CRITICAL/IMPORTANT と同じ H5 構造に揃える（観点側補足 / 提案側補足）
- 推奨: A（運用上は単一補足で十分なケースが多く、構造の単純さを優先）

#### 4.1.3 POSITIVE の態度区分の整合性

- 現状: L204「（維持 / その他）」
- 影響: 他ラベルの「条件付き採用 / 差戻し」追加と整合がとれていない
- 検討事項: POSITIVE は「肯定的指摘」の性格上、態度区分が他と異なるのは自然。ただし「その他」が曖昧
- 対応案 A: 現状維持
- 対応案 B: 「（同意 / 修正提案あり / 異議あり）」のように具体化
- 推奨: A（POSITIVE は実運用で態度表明をスキップしがち。具体化のメリットが小さい）

#### 4.1.4 「条件付き採用」「差戻し」の意味定義の所在

- 現状: 区分名のみテンプレート上に登場、意味定義なし
- 影響: 作業指示者・Claude の双方が解釈に揺れる可能性
- 対応案: 後述 §6 で示す通り、`README.md` 側に意味定義を記載することを推奨

#### 4.1.5 「判断基準」セクションのコメント運用

- 現状: L25-32 がコメントで囲まれており、実際の記入は任意
- 影響: 「補足_レビューアプローチ相対評価.md」改善示唆 #1（判断基盤の必須化）に対する完全な対応にはなっていない
- 対応案 A: コメント解除し、本文として「以下を埋めてください」と必須化
- 対応案 B: コメント維持（既存形式のまま）
- 推奨: A（必須化することで判断ブレ抑制効果が出る。記載例を残す形にしても良い）

## 5. 実用性テンプレートへの適用方針

### 5.1 そのまま同様に実施すべき項目

論理整合性テンプレートと**完全に同じ構造**を採用すべき項目:

| 項目 | 理由 |
|---|---|
| 「はじめに」セクションへの統一 | クロスレビュー報告書としての構造的統一性 |
| 版番号欄（0.8/0.9/1.0） | レビューフロー全体で版数管理を共通化 |
| 「判断基準」セクション | 判断基盤の明示は実用性レビューでも同様に重要 |
| 版数 × ラベル件数の推移表 | レビューイFB 取り込みフェーズの整合性 |
| 各指摘エントリの詳細構造（問題点 / レビューイ補足 / 修正案 / レビューイ補足 / 態度表明） | レビューイFB フェーズの正式化が両観点で適用される |
| 作業指示者の態度区分（採用 / 条件付き採用 / 差戻し / 保留 / 却下） | 区分はレビュー観点に依存しないため統一 |
| 末尾の変更履歴（表形式・版／日付／内容） | 同上 |
| 接頭辞 `C-/I-/S-/P-`（実用性側）の維持 | README §「設計方針」で識別ルールが定義されており、両観点で互換性あり |

### 5.2 記載を変えるべき項目

論理整合性テンプレートと**記載内容のみ差し替えが必要**な項目:

| 項目 | 論理整合性側の記載 | 実用性側で差し替えるべき内容 |
|---|---|---|
| ファイル冒頭の見出し | `# クロスレビュー報告書 — 論理整合性観点` | `# クロスレビュー報告書 — 実用性観点` |
| レビュアー | `Claude Opus（独立第三者）` | `Claude Sonnet（独立第三者）` |
| レビュー区分 | `論理整合性観点` | `実用性観点` |
| レビュー観点（箇条書き） | 論理整合性 / カバレッジ十分性 / 調査目的との整合性 / 仮説の妥当性 | 完了条件明瞭性 / 命名規則遵守 / 文書構造 / 検証パターン具体性 |
| 判断基準の記載例 | `02.基礎調査 サブタスク 01〜08 各報告書` 等の論理面参照群 | `CLAUDE.md`（命名規則）/ `.claude/rules/coding-standards.md` 等の実用面参照群 |
| 各セクション内のコメント文 | 「論理面で改善余地のあると判断した点」等 | 「実用面で改善余地のあると判断した点」等 |
| 接頭辞 | `C1` / `I1` / `S1` / `P1` | `C-1` / `I-1` / `S-1` / `P-1`（既存実用性テンプレートのハイフン付き接頭辞を維持） |

### 5.3 記載対象外とすべき項目

論理整合性テンプレートの内容のうち、**実用性テンプレートには入れるべきでない**ものは確認した範囲では存在しない。両観点ともクロスレビュー報告書として共通の構造を持つべき。

### 5.4 実用性テンプレート特有の検討項目

実用性レビューには論理整合性レビューに無い性格があり、以下を実用性側でのみ追加検討する余地がある。

#### 5.4.1 「該当箇所」欄の存続判断

- 旧実用性テンプレートには各指摘に `**該当箇所**: {{該当する章節やパス}}` 欄があった
- 旧論理整合性テンプレートには同欄がなかった（「概要・詳細・根拠」内に該当箇所を含めて記述する想定）
- 新論理整合性テンプレートでも該当箇所欄は明示されていない
- 検討事項: 実用性レビューでは「命名規則違反」「文書構造の不整合」など**箇所特定が不可欠な指摘が多い**
- 推奨方針: 実用性テンプレートでは「該当箇所」欄を**問題点セクション内の最初の項目として明示的に追加**する（論理整合性テンプレートには無い、実用性特有の項目）

```markdown
#### C-1. 問題点
* **該当箇所**: {{該当する章節やパス}}
* **概要**: {{...}}
* **詳細**: ...
* **根拠**: ...
```

#### 5.4.2 「修正案」の記述形式

- 実用性レビューでは**コード例・記述例の併記**が頻出（旧テンプレート L36 に「コード例・記述例があれば併記」と明記）
- 論理整合性テンプレートの修正案表は「メリット / デメリット」軸での比較を強制する形式
- 検討事項: 実用性の修正案は「比較案を出す」より「具体的な修正例（コード/記述）を直接示す」のが多い。論理整合性側の表形式を強制すると逆に書きづらい可能性
- 推奨方針: 表形式を**任意**とし、「単一案で十分な場合は箇条書きで案 + 例示」を許容するコメントを追加

#### 5.4.3 検証パターン具体性に関する観点

- 実用性レビュー観点の一つ「検証パターン具体性」は、調査・検証フェーズの報告書に特化している
- 計画書レビュー時には適用範囲が異なる
- 検討事項: 観点が常に 4 つ全て適用されるわけではない
- 推奨方針: テンプレート本体は変更せず、**`README.md` 側に「観点はレビュー対象に応じて取捨選択可」と明記**する

## 6. README.md / 運用ルール側に記載を移すべき項目

テンプレート本体ではなく `README.md`（または `CLAUDE.md` の「レビュー実施ルール」節）に記載するのが適切と判断する項目:

### 6.1 版数定義の運用ルール

- **対象**: 論理整合性テンプレート L37-44 のコメント内記述（版数 0.8/0.9/1.0 の定義）
- **理由**: テンプレートを跨いで共通の運用。各テンプレートにコピーするより一箇所で定義する方が保守性が高い
- **記載先案**: `README.md` の新しいセクション「§ 版数管理」

### 6.2 作業指示者の態度区分の意味定義

- **対象**: 「採用 / 条件付き採用 / 差戻し / 保留 / 却下」の各意味
- **理由**: テンプレート本体には区分名のみ登場し、意味は記載されていない。複数テンプレートで共通の区分のため、README で一元管理が適切
- **記載先案**: `README.md` の新しいセクション「§ 作業指示者の態度区分」
- **記載内容案**:

```markdown
| 態度 | 意味 |
|---|---|
| 採用 | 指摘・修正案を全面的に採用する |
| 条件付き採用 | コメントに記載した条件・対応を前提に採用する |
| 差戻し | Claude への確認事項あり、または条件付き採用とするには対応案の修正幅が大きい場合の差し戻し |
| 保留 | 判断を後続フェーズに先送りする |
| 却下 | 指摘そのものを取り下げさせる |
```

### 6.3 レビューイFB 取り込みフェーズ（0.9 版数）の運用ガイド

- **対象**: 「作成者コメント → レビュアー修正 → 作業指示者レビュー」のフロー全体
- **理由**: テンプレートは記入欄を提供するだけで、運用順序・誰が何を書くかの定義はない
- **記載先案**: `README.md` の「§ 使い方」を拡張、または新しい「§ レビューフロー」を追加
- **記載内容案**:
  - 0.8 版作成（レビュアー）
  - 0.9 版作成（レビュアーがレビューイのFBを取り込み）
  - 1.0 版作成（レビュアーが作業指示者の指摘を取り込み）
  - 各版での件数表更新ルール

### 6.4 観点の取捨選択可ルール

- **対象**: §5.4.3 の「観点はレビュー対象に応じて取捨選択可」
- **理由**: テンプレート本体に書くと観点リストが流動的に見える。運用ルールとして README で記述するのが自然

### 6.5 収束条件の数値化補完（補足相対評価 §総合評価 #2）

- **対象**: 「新規 NG 検出ゼロ」に加える数値閾値
- **理由**: 数値はプロジェクト依存で変動。運用ルール側で柔軟に記述
- **記載先案**: ルート `CLAUDE.md` の「レビュー実施ルール」節 または 個別 `research-for-xxx/CLAUDE.md` の同節
- **検討事項**: テンプレートを共有資産とする一方で、収束条件は調査ごとに調整可能性がある。階層的に「ルートで既定値・個別で上書き」運用が候補

### 6.6 ドキュメント種別ごとの追加観点パッケージ（補足相対評価 §総合評価 #4）

- **対象**: 計画書 / 報告書 / 設計書 ごとの固有観点
- **理由**: テンプレート共通化と種別固有の両立は、別ファイル管理（観点パッケージ）が現実的
- **記載先案**: 今回スコープ外。将来 `.claude/templates/cross-review/observation-packs/` のような別ディレクトリで管理する可能性に言及するに留める

## 7. 作業指示者レビューテンプレートへの波及

論理整合性テンプレートの態度区分変更（採用 / 条件付き採用 / 差戻し / 保留 / 却下）に伴い、`作業指示者レビュー_template.md` の以下の記述が**旧形のまま残っており不整合**:

- L133:
  ```
  各既存レビューの個別指摘への態度表明（採用 / 却下 / 保留 / 改変 + コメント）は、当該指摘エントリの末尾に直接記入する運用。
  ```
  - 「採用 / 却下 / 保留 / 改変」が旧形。**「採用 / 条件付き採用 / 差戻し / 保留 / 却下」に修正が必要**

その他、作業指示者レビューテンプレート自体の構造改訂（はじめに / 版番号 / 判断基準 / 件数推移表 等の取り込み）は要否判断が分かれる:

- 作業指示者レビューは「**人間の自由記入**」が前提のため、論理整合性 / 実用性ほどの構造化は不要との見方もある
- 一方、共通の構造に揃える方が Claude の処理（クロスレビュー結果統合）が一貫する

**推奨方針**: 作業指示者レビューテンプレートは**最小限の修正に留める**:
- L133 の態度区分名のみ修正（必須）
- それ以外の構造改訂は今回スコープ外（人間の記入負荷を増やすデメリットの方が大きいと判断）
