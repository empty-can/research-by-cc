# 先行インプット 01: RAGとAgentic Searchの戦争を 終わらせに来た!!!

- 出典: https://zenn.dev/microsoft/articles/d1aa5068b432f9
- 取得日: 2026-05-01
- 読み方: 精読

## 記事の概観

Microsoft の AI Cloud Solution Architect である Hirosato Gamo 氏が、「RAG は時代遅れ」という SNS 上のインフルエンサー発言に起因する混乱を収束させるために執筆した記事。RAG と Agentic Search は対立概念ではなく異なるアーキテクチャ層に位置するものであり、対象データの性質・規模・タスクに応じた使い分けが本質だと論じる。

## 用語と概念

### RAG (Retrieval-Augmented Generation)
- **狭義**: ベクトル検索を用いた外部データ取得による生成補強（一般的に誤解されている定義）
- **広義**: 「外部データを取得してモデルの生成を補強する」アーキテクチャ全般。Microsoft・AWS・NVIDIA などの主要クラウドベンダーはこの広義の定義を採用しており、ベクトル検索は必須要件ではない
- 記事の主張: RAG をベクトル検索と同一視する理解は誤りであり、「ベクトル検索を用いないRAGも普通に存在する」

### Agentic Search
- **定義**: LLM が推論を伴いながら反復的に検索を実行するアプローチ
- **誤用**: grep/glob コマンドによるファイルシステム探索と同義として使われることが多いが、これは誤り
- RAG の実装手法のひとつとして位置づけられる（対立概念ではない）

### CAG (Context-Augmented Generation)
- 必要な情報をプロンプトのコンテキストに最初から全量ロードしておく手法
- 拡張されたコンテキストウィンドウとプロンプトキャッシュを前提とする
- 小規模データ・フラッグシップモデル・軽いタスクに適する

### Filesystem Exploration RAG
- grep/glob 等のコマンドでファイルシステムを直接探索する RAG 実装
- インデックス構築が不要
- コードベースのような、具体的な文字列・記号パターンが明確なデータに適する

### Vector Search RAG
- テキストをベクトル化してセマンティック類似検索を行う RAG 実装
- 表記が揺れる自然言語ドキュメント群に有効

### 三者の相互関係
```
RAG（広義：外部データ取得による生成補強）
 ├─ CAG（コンテキストへの全量ロード）
 ├─ Vector Search RAG（ベクトル類似検索）
 └─ Filesystem Exploration RAG（コマンド探索）
      └─ Agentic Search は上記の探索を LLM が反復・推論しながら行う実行スタイル
```

## 事実

### 記事が明示する各手法の適用条件

| 手法 | 適する場面 | 適さない場面 |
|---|---|---|
| CAG | フラッグシップモデル使用、数ファイル規模、軽い質問 | 小型モデル、マルチタスク、大規模データ（ノイズ増大） |
| Vector Search RAG | 表記が不安定な自然言語ドキュメント、意味的曖昧性のある検索 | 探索空間が広すぎる場合（破綻リスクあり）、命名規則が一定のデータセット |
| Filesystem Exploration RAG | コードベース、具体的な文字列・記号が判明している場合 | 探索空間が広すぎる場合（破綻リスクあり） |

### Agentic Search のコスト特性（記事の明示的記述）
- **レイテンシ**: 「複数の検索が回る可能性があるということは時間は延びる。吟味の時間含めると更に」
- **トークン消費増大**: 「検索結果の吟味はそれだけ多くのテキストを読み込むことになるため、LLMの消費するコンテキスト量が増加する」
- **後続タスクへのノイズ汚染**: 「消費したトークンをエージェントのコンテキストに残しておくとノイズとなり、後続作業には邪魔でしかなくなる」

### 軽減策として記事が挙げているもの
- 検索処理をサブエージェントとして分離する
- サブエージェントに軽量モデルを使用してコスト削減
- 良質な結果のみをメインエージェントに返す実装

### 著者の明示的推奨・非推奨
- **推奨**: 「対象データの性質・規模・タスクで使い分けることが大事」
- **推奨**: ベクトル検索を用いない RAG の存在を前提として議論すること
- **非推奨**: 「何でもかんでもベクトル検索」
- **非推奨**: コンテキストを剥ぎ取った SNS 上の断片的な比較論に基づく技術選定

### 記事内で言及されているツール・製品・サービス
- Claude Code (Anthropic)
- Azure Search (Microsoft)
- ChatGPT (OpenAI)
- Graph RAG (Microsoft)
- Obsidian
- MCP (Model Context Protocol)

## 観察と示唆

**本調査文脈との関連：**

1. **CAG の位置づけ再考**: Claude の大きなコンテキストウィンドウとプロンプトキャッシュを活かせば、「小規模ファイル数・軽いタスク」に限りトークン効率を保ちつつ RAG レス運用が可能かもしれない。ただし仕様書・ソースコード・脆弱性パッチを大量に扱う本調査の規模感では CAG は主手段にはなりにくいと推定される。

2. **コードベースには Filesystem Exploration RAG が有力**: 本調査のユースケースにはソースコードが含まれるため、ベクトル検索より grep/glob 系の探索の方が精度・速度ともに有利になる可能性がある。ローカル RAG 構築においても、データ種別ごとに手法を使い分けるアーキテクチャ設計が必要と示唆される。

3. **Agentic Search の採用は慎重に**: トークン消費増大・レイテンシ増大・後続タスクへのノイズ汚染という三つのコストが明示されており、本調査の「トークン/コンテキスト消費を抑える」という目的と直接的に対立する。サブエージェント分離アーキテクチャは緩和策として有効だが、設計コストが増す。

4. **RAG の「広義/狭義」問題**: ローカル RAG 調査において「RAG」という語を使う際は、ベクトル DB を伴う実装だけでなく全文検索・ファイルシステム探索も候補として明示的に比較対象に含めるべきである。

5. **MCP の言及**: 記事が MCP (Model Context Protocol) に言及している。Claude Code との連携において MCP ベースのデータアクセス設計が RAG の代替または補完となる可能性を後続で確認すべき。

## 不明・要追跡事項

1. **探索空間が「広すぎる」の定量的基準**: 記事は「探索空間がある程度狭くないと破綻しやすい」と述べるが、ドキュメント数・トークン数の閾値は不明。本調査規模（仕様書・コード・パッチの大量データ）がどの閾値に該当するかは別途調査が必要。

2. **Graph RAG の位置づけ**: 記事内で言及されているが詳細な説明がない。ベクトル検索 RAG の亜種か別カテゴリかが不明。大量の関連ドキュメント（例: 脆弱性パッチと影響コードの関係グラフ）への適用可能性を要確認。

3. **MCP と RAG の関係**: 記事が MCP に言及しているが、Claude Code のツール呼び出しとして MCP 経由のデータアクセスを構成することが、従来型 RAG パイプライン構築と比べてどの程度実用的かは本記事では不明。

4. **軽量モデルの具体的選択肢**: サブエージェントに「軽量モデル」を使う軽減策について、ローカル動作可能なモデルの選択肢（本調査はローカル LLM 構築対象外だが、検索用途限定なら別扱いの可能性）を要確認。

5. **ベクトル DB のローカル OSS 選択肢**: 記事は Azure Search を挙げるが、ローカル動作する OSS ベクトル DB（Qdrant, Chroma, Milvus 等）の優劣比較は記事の対象外。後続調査で要確認。

6. **Filesystem Exploration RAG のスケール限界**: grep/glob ベースのアプローチが「探索空間が広すぎると破綻」するとあるが、コードベース規模（例: 数十万ファイル）での実用性は不明。
