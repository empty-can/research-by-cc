## 事実

### 採用技術スタック

| 構成要素 | 採用技術 |
|----------|---------|
| ベクトル DB | DuckDB（vss 拡張 + HNSW インデックス） |
| 埋め込みモデル | sentence-transformers（複数選択肢、ローカル実行） |
| 検索手法 | コサイン類似度ベースのベクトル検索 |
| Claude Code 統合 | Claude Code スキル（`/rag-index`、`/rag-ask`） |

### 対応埋め込みモデル一覧

| モデル名 | 次元数 | モデルサイズ | 備考 |
|----------|--------|------------|------|
| intfloat/multilingual-e5-small | 384 | 約100MB | デフォルト推奨 |
| cl-nagoya/ruri-v3-30m | 256 | 約120MB | 日本語特化・軽量 |
| cl-nagoya/ruri-v3-310m | 1024 | 約1.2GB | 日本語最高精度 |
| BAAI/bge-m3 | 1024 | 約2.2GB | 多言語対応 |

### DuckDB セットアップコマンド

```python
con = duckdb.connect('rag/mydata.duckdb')
con.execute("INSTALL vss; LOAD vss;")
con.execute("SET hnsw_enable_experimental_persistence = true;")
```

### テーブル定義・インデックス作成 SQL

```sql
CREATE TABLE chunks (
    id VARCHAR PRIMARY KEY,
    source VARCHAR,
    topic VARCHAR,
    page INTEGER,
    content TEXT,
    embedding FLOAT[384],
    created_at TIMESTAMP DEFAULT current_timestamp
);
CREATE INDEX idx_embedding ON chunks USING HNSW (embedding)
WITH (metric = 'cosine');
```

### チャンク分割パラメータ

- チャンクサイズ: 400文字（e5-small）〜 800文字（ruri / bge-m3）
- オーバーラップ: 100文字
- 検索結果上位件数: 5〜N件（自動マージ）

### Claude Code 連携の仕組み

- `/rag-index`: Markdown → チャンク分割 → embedding 生成 → DuckDB 格納
- `/rag-ask`: 質問 → embedding → ベクトル検索 → Claude（クラウド）で回答生成
- 実行例: `/rag-ask dbtのモデル設計のベストプラクティス --source dataengineering`
- 複数 DB ファイルを自動検出し、各 DB 内のメタデータから embedding モデル名を自動取得する機能あり

### ハマりどころ・注意点

| 課題 | 対策 |
|------|------|
| e5 系モデルはプレフィックスが必須 | インデックス時「passage:」、検索時「query:」を付与 |
| チャンク境界で文が途切れる | オーバーラップ 100文字で回避 |
| 同一文書の重複インデックス化 | MD5 ハッシュで既存 ID をスキップ |
| 異なる埋め込みモデルの混在 | メタデータテーブルで整合性チェック |

### DB ファイルの特性

- 単一ファイル（`.duckdb`）で完結
- ローカル完結のため従量課金なし
- Git 管理可能（再構築容易）

## 観察と示唆

- DuckDB + vss 拡張は「追加サーバー不要・単一ファイル」という点でローカル RAG の導入摩擦が低い。Chroma や Qdrant のような別プロセス起動が不要な点は後の比較検討で評価軸に入れる価値がある。
- `hnsw_enable_experimental_persistence = true` は「experimental」であり、安定性リスクが不明。本番相当の用途では要確認。
- 埋め込みモデルを DB ごとにメタデータで管理する設計は、モデル変更時の混在バグ防止として参考になる。
- Claude Code スキルとして `/rag-index` / `/rag-ask` を実装する形式は、Claude Code から呼び出す際の UI 設計の具体例として有用。MCP ではなく「スキル」形式を採用している点は後で深掘り対象（MCP との比較が必要）。
- e5 系モデルのプレフィックス（passage: / query:）は見落としやすい実装上のトラップ。他モデルでも同様の仕様がないか確認が必要。
- 続編（PDF→Markdown 化フロー）は取得対象候補として記録しておく。
