## 2. 調査の目的とスコープ（要点抽出）

### 目的（要約）
Claude Code に大量のファイル群を扱った調査・作業をさせる際、**精度を維持しつつトークン・コンテキスト消費を最小化する仕組み**を、**完全ローカル**かつ **OSS / 商用利用無料製品のみ**で構築する方法を明らかにする。

### 大前提
「LLM でなくてもできることは Claude Code にさせない」を徹底する。データ構造化・取得は専用ツールに任せ、Claude Code には推論・統合の役割に集中させる。

### スコープに含む
- RAG 全般の基礎情報、ローカル RAG 構築事例（オンライン記事・GitHub）の収集
- Claude Code からローカル RAG を利用するための連携方式（CLI、MCP、Skills 等）
- 実際にローカル環境での構築・動作検証
- 埋め込みモデル・リランカーモデル・小型クエリ書き換えモデル等の **「専用ツール」としての** ローカル動作可能なモデル群（生成 LLM ではない）

### スコープに含まない
- 有料サービス型 RAG
- **ローカル LLM の構築や学習に関する情報**
  - 注: 生成 LLM のローカル構築・学習作業のみがスコープ外。埋め込みモデル・リランカーモデル・小型クエリ書き換えモデルは「専用ツール」としてスコープ内（CLAUDE.md 大前提との整合）。
- **特定のローカル LLM が前提で Claude Code への置き換えが不可能な構成**（ただし、構成中の LLM を Claude Code に置換可能であれば調査対象内）
- 信頼性・読み込みコストに難のある SNS 系情報源

## 3. 先行インプットの要約と判明した事実

7 件の先行インプットメモのうち、技術詳細を含むものは **01〜06**（07 は技術詳細なし・参考度低）。以下は事実ベースで読み取れた論点・候補要素のみを記す。観察・示唆は次節へ。

### 3.1 用語整理（インプット 01 由来）

- **RAG（広義）**: 外部データを取得してモデル生成を補強するアーキテクチャ全般。**ベクトル検索は必須要件ではない**。
- **CAG (Context-Augmented Generation)**: 必要情報をプロンプトに全量ロード。小規模データ・軽いタスク向き。
- **Vector Search RAG**: ベクトル類似検索による RAG 実装。表記揺れのある自然言語向き。
- **Filesystem Exploration RAG**: grep / glob 等で直接探索する RAG 実装。コードベース等の文字列・記号パターンが明確なデータ向き。
- **Agentic Search**: LLM が推論を伴って反復検索する実行スタイル。RAG の対立概念ではない。

### 3.2 候補となる構成要素（インプット 02〜06 由来）

#### Claude Code 連携方式
| 方式 | 特徴 | 出所メモ |
|---|---|---|

#### 検索アルゴリズム
- **単純コサイン類似度**: 02, 04, 05
- **ハイブリッド（BM25 + ベクトル + LLM リランキング）**: 03
- **意味検索 + 書誌情報メタデータ照合**: 04
- **チャンク戦略**: 400〜800 文字、オーバーラップ 100 文字（02）

### 3.3 パターン分類（事実から導かれる）

実装事例は次の **構造軸 3 軸** + **評価軸 1 軸** で整理できる。

#### 構造軸（実装上の選択肢の構造）

1. **DB 形態軸**: 単一ファイル DB（DuckDB / sqlite-vec）vs サーバー DB（pgvector / Chroma）
2. **連携方式軸**: 常駐型（MCP / Skills 常駐 HTTP）vs CLI 都度起動型（Skills 都度）vs ハイブリッド
3. **検索アルゴリズム軸**: ベクトル単独 vs ハイブリッド（BM25+ベクトル+リランカー）

#### 評価軸（リソース消費評価のための独立変数）

4. **埋め込み次元軸**: 小型（≦ 384）/ 中型（〜 768）/ 大型（≧ 1024）。ストレージ・速度・精度のトレードオフに直接効く。5.4 の検証対象が両端を含むことを確認する。

  - 採用候補が最低 1 件、除外候補が最低 1 件、根拠付きで明記されていること

##### 04.チャンク分割・インデックス手法

- **完了条件**:
  - データ種別ごと（コード / Markdown / PDF）にチャンクサイズとオーバーラップの推奨値が文献ベースで整理されていること

  - **デファクトスタンダード優先で足切り**: RAGAS（Faithfulness / Answer Relevancy / Context Relevancy / Context Recall）等の既存フレームワークを採用候補として扱い、既存実績をもって採用理由とする
  - 詳細調査は採用候補に対してのみ実施し、それ以外の候補は足切り
  - **ただし**: それら指標やフレームワークが、扱う情報の性質に大きく影響を受けないか、評価に利用を予定している仕組み同士の比較として有効な値が出るものであるかについてはしっかりと確認する
- **アウトプット**:
  - 評価指標確定リスト（項目・定義・計測方法・重み付け・算出式）
  - 採用フレームワーク（RAGAS 等）の選定理由
- **完了条件**:
  - 全評価指標の算出式と重み付けが確定していること
  - 採用フレームワークの選定理由（性質適合性・比較有効性の確認結果含む）が明記されていること

##### 02 以降. `02.検証_有効性_<検証対象名>/` 形式（命名は 04 完了後に確定）

#### 評価指標（ドラフト・最終確定は 05.01）

> Pre-06 由来。「単発クエリトークン効率」「セッション累積コンテキスト圧迫度」を中核指標とし、Claude Code 通信回数削減も含める。

| 指標 | 定義 | 計測方法 |
|---|---|---|
| **単発クエリトークン効率** | 1 質問当たりの入力トークン総量（取得結果＋プロンプト）。RAG 利用時 / 直接ファイル読み込み時 / CAG 時 を比較 | 同一クエリで各方式を実行・トークン計測 |
| **セッション累積コンテキスト圧迫度** | 同一タスク完了までに必要だったクエリ数 × クエリ当たりトークン、および後続タスクへのノイズ汚染（マルチターン累積トークン量）。先行インプット 01 の Agentic Search コスト特性に対応 | セッションログから計測。RAGAS 系 Context Relevancy 等を活用して半定量化 |
| **Claude Code 通信回数削減度** | 同一アウトプットを生成するために要する `Claude Code クライアント ↔ Anthropic API` 間の通信回数の比 | セッションログ・API 呼び出しログから計測 |
| **取得精度（Recall@k）** | 想定正解ドキュメントが上位 k 件に含まれる割合 | テストクエリ + 正解セットを構築し計測 |
| **取得精度（Precision@k）** | 上位 k 件のうち関連あるものの割合 | 同上 |
| **応答速度** | クエリ投入 → Claude Code 応答までの時間 | 計測スクリプト |
| **インデックス構築コスト** | 単位データ量あたりのインデックス時間・ストレージ | 一定規模のサンプルデータで計測 |
| **対照群（Filesystem Exploration / CAG）に対する優位度** | 対照群との精度向上度・トークン削減度の差分 | 同一タスクで実行・比較 |

> **注**: 「ノイズ汚染度」は本表の「セッション累積コンテキスト圧迫度」に統合した（Pre-10 由来：作業指示者回答「成果が期待通り達成された場合、ノイズ汚染も自然と減少する。各構成ごとの差異を定量的に把握できれば十分」）。RAGAS 系 Context Relevancy 等の既存フレームワーク活用は 05.01 で確定。
