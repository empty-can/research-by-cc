## 2. 調査の目的とスコープ（要点抽出）

### 目的（要約）
Claude Code に大量のファイル群を扱った調査・作業をさせる際、**精度を維持しつつトークン・コンテキスト消費を最小化する仕組み**を、**完全ローカル**かつ **OSS / 商用利用無料製品のみ**で構築する方法を明らかにする。

### 大前提
「LLM でなくてもできることは Claude Code にさせない」を徹底する。データ構造化・取得は専用ツールに任せ、Claude Code には推論・統合の役割に集中させる。

### スコープに含む
- RAG 全般の基礎情報、ローカル RAG 構築事例（オンライン記事・GitHub）の収集
- Claude Code からローカル RAG を利用するための連携方式（CLI、MCP、Skills 等）
- 実際にローカル環境での構築・動作検証

### スコープに含まない
- 有料サービス型 RAG
- ローカル LLM 構築（LLM は Claude Code を利用する前提）
- 信頼性・読み込みコストに難のある SNS 系情報源

## 3. 先行インプットの要約と判明した事実

7 件の先行インプットメモのうち、技術詳細を含むものは **01〜06**（07 は技術詳細なし・参考度低）。以下は事実ベースで読み取れた論点・候補要素のみを記す。観察・示唆は次節へ。

### 3.1 用語整理（インプット 01 由来）

- **RAG（広義）**: 外部データを取得してモデル生成を補強するアーキテクチャ全般。**ベクトル検索は必須要件ではない**。
- **CAG (Context-Augmented Generation)**: 必要情報をプロンプトに全量ロード。小規模データ・軽いタスク向き。
- **Vector Search RAG**: ベクトル類似検索による RAG 実装。表記揺れのある自然言語向き。
- **Filesystem Exploration RAG**: grep / glob 等で直接探索する RAG 実装。コードベース等の文字列・記号パターンが明確なデータ向き。
- **Agentic Search**: LLM が推論を伴って反復検索する実行スタイル。RAG の対立概念ではない。

### 3.2 候補となる構成要素（インプット 02〜06 由来）

#### 埋め込みモデル候補
| モデル | 次元 | サイズ | 出所メモ |
|---|---|---|---|
| `intfloat/multilingual-e5-small` | 384 | 約 100〜500 MB | 02, 05 |
| `intfloat/multilingual-e5-large` | 1024 | 大 | 06 |
| `BAAI/bge-m3` | 1024 | 約 2.2 GB | 02, 04 |
| `cl-nagoya/ruri-v3-30m` / `ruri-v3-310m` | 256 / 1024 | 約 120 MB / 1.2 GB | 02 |
| `embedding-gemma-300M-Q8_0` | -（300 MB） | 約 300 MB | 03 |
| `all-MiniLM-L6-v2` | -（小） | 小 | 04（日本語精度に難あり） |

#### ベクトル DB / 検索基盤候補
| 基盤 | 形態 | 出所メモ |
|---|---|---|
| DuckDB + vss 拡張（HNSW） | 単一ファイル DB | 02 |
| sqlite-vec（SQLite） + FTS5 | 単一ファイル DB | 03, 05 |
| PostgreSQL + pgvector | サーバー型（Docker） | 05（MCP 版）, 06 |
| Chroma | サーバー型 | 04 |

#### リランカー候補
| 要素 | 出所メモ |
|---|---|
| `qwen3-reranker-0.6b` による LLM リランキング | 03 |
| R²AG（関連度スコア付与） | 05 |

#### Claude Code 連携方式
| 方式 | 特徴 | 出所メモ |
|---|---|---|
| Skills（`/rag-index`, `/rag-ask` 等） | 常駐不要・CLI 都度起動。実装軽量・初回応答に遅延 | 02, 05 |
| MCP サーバー | 常駐型・低レイテンシ。設計コスト高め | 03, 04, 05, 06 |
| ハイブリッド（管理は CLI / 検索は MCP） | 06 で採用 | 06 |

#### 検索アルゴリズム
- **単純コサイン類似度**: 02, 04, 05
- **ハイブリッド（BM25 + ベクトル + LLM リランキング）**: 03
- **意味検索 + 書誌情報メタデータ照合**: 04
- **チャンク戦略**: 400〜800 文字、オーバーラップ 100 文字（02）

### 3.3 パターン分類（事実から導かれる）

実装事例は次の 3 軸で整理できる:

1. **DB 形態軸**: 単一ファイル DB（DuckDB / sqlite-vec）vs サーバー DB（pgvector / Chroma）
2. **連携方式軸**: Skills（CLI 都度）vs MCP（常駐）vs ハイブリッド
3. **検索アルゴリズム軸**: ベクトル単独 vs ハイブリッド（BM25+ベクトル+リランカー）

### 3.4 確認済みのハマりどころ（事実）

- DuckDB vss の `hnsw_enable_experimental_persistence` は experimental（02）
- e5 系モデルの `passage:` / `query:` プレフィックス必須（02）
- 異なる埋め込みモデルの DB 内混在によるバグ → メタデータ管理で防止（02）
- Skills 版の CLI 都度起動はモデルロードで約 8〜9 秒の遅延が発生（05）
- macOS で sqlite-vec を使うには Homebrew 版 SQLite が必要な場合あり（03）
- `zotero-mcp` の既定モデル `all-MiniLM-L6-v2` は日本語精度が不足（04）

| 指標 | 定義 | 計測方法 |
|---|---|---|
| **トークン削減率** | RAG 利用時 / 直接ファイル読み込み時のトークン消費比 | 同一クエリで両方式実行・トークン計測 |
| **コンテキスト消費削減率** | Claude Code セッションで消費されるコンテキストウィンドウ量の比 | セッションログから計測 |
| **取得精度（Recall@k）** | 想定正解ドキュメントが上位 k 件に含まれる割合 | テストクエリ + 正解セットを構築し計測 |
| **取得精度（Precision@k）** | 上位 k 件のうち関連あるものの割合 | 同上 |
| **応答速度** | クエリ投入 → Claude Code 応答までの時間 | 計測スクリプト |
| **インデックス構築コスト** | 単位データ量あたりのインデックス時間・ストレージ | 一定規模のサンプルデータで計測 |
| **後続タスクへのノイズ汚染度（定性）** | RAG 後の Claude Code 出力品質に対する Agentic Search との比較 | 観察的評価（厳密化は要検討） |

#### サブタスク（命名）
- `01.検証_有効性_<パターン名>/` 形式（04 と接頭辞で区別）
- `99.有効性検証報告/` で統合評価

#### 完了条件
- 各パターンの `検証報告書.md` に上記指標の実測値が記載されている
- 99 にて、推奨構成・除外構成・本調査目的に対する達成度が結論付けられる
