## CRITICAL

### C-1: 02.基礎調査 の各サブタスク（02〜08）に完了条件が未定義

**該当箇所**: `5.2 02.基礎調査` — サブタスク `02.埋め込みモデル比較` 〜 `08.オフライン GitHub リポジトリ調査`

**問題**: `01.RAG パターン分類とユースケース適合性` と `99.最終基礎調査報告` には完了条件が記載されているが、`02〜08` の 7 サブタスクには完了条件が存在しない。これらのサブタスクはそれぞれ固有のアウトプットを持っているにもかかわらず、「調査報告書が揃っていること」という親タスクレベルの完了条件しか判定基準がない。

実際に作業に入った時点で「比較表の何が揃えば完了か」「候補絞り込みはどのレベルまで絞れば完了か」が判定不能になる。

**修正案（例: 02.埋め込みモデル比較）**:

```
完了条件:
- 候補モデルが比較表に 5 件以上列挙されていること
- 各モデルに「多言語対応可否」「ライセンス（商用利用可否）」「モデルサイズ（MB/GB）」「推奨/除外の判定」が記入されていること
- 採用候補（フィジビリティ検証で使用するモデル）が最低 1 件、除外候補が最低 1 件、根拠付きで明記されていること
```

同様の形式で `03〜08` 全サブタスクに完了条件を追記することを推奨する。

### C-2: 05.有効性検証 の検証パターン名が計画書内で未確定のまま、かつ CLAUDE.md のタスク進行状況との整合が取れない

**該当箇所**: `5.5 05.有効性検証` — サブタスク命名、および `research-for-local-RAG-for-cc/CLAUDE.md` のタスク進行状況セクション（行 110〜111）

**問題 (a) — 名前が実質 TBD**:
計画書では `01.検証_有効性_<パターン名>/` のように「パターン名は後で決まる」とだけ示されている。しかし 04 フィジビリティ検証が完了するまで具体名が確定しないことは明らかであり、少なくとも「04 通過後に命名する想定である」という注記がなければ、後続の作業者は「パターンA/B」という仮称を流用してよいのか判断できない。

**問題 (b) — CLAUDE.md とのずれ**:
`CLAUDE.md` のタスク進行状況（行 108〜111）では `05.有効性検証` のサブタスクが `01.検証_有効性_パターンA` / `02.検証_有効性_パターンB` という仮称のままになっている。一方、計画書の 04 フィジビリティ検証パターンには具体名（`DuckDB_Skills` / `sqliteVec_MCP_Hybrid` 等）が付いており、整合していない。

**修正案**:
CLAUDE.md のタスク進行状況の `05.有効性検証` 配下を以下のように更新する:

```markdown
- [ ] 05.有効性検証
  - [ ] （04.フィジビリティ検証 完了後にパターン名を確定し記載）
  - [ ] 99.有効性検証報告
```

また計画書 5.5 のサブタスク命名説明に「04 完了後に具体パターン名を記入する」旨を明示する。

## IMPORTANT

### I-1: 03.ローカル RAG 設計 の完了条件が親タスクに置かれ、サブタスクに存在しない

**該当箇所**: `5.3 03.ローカル RAG 設計` — `完了条件` セクション（`5.3.2` の末尾）

**問題**: セクション 5.3 の完了条件は `5.3.1 01.ユースケース整理` と `5.3.2 02.ローカル RAG 設計` をまとめた親レベルの記述になっているが、サブタスク単位の完了条件（どちらが何を完了させた時点で次のサブタスクに進めるか）が分離されていない。「ユースケース軸が固定され」「各軸の値が…埋まっていること」は `01.ユースケース整理` の完了条件であり、「04 で検証する 3〜N パターンが確定」「05 で測定する有効性指標と閾値が定義」は `02.ローカル RAG 設計` の完了条件のはずだが、混在している。

実際に作業すると、01 が完了して 02 に移行するタイミングが判定できない。

**修正案**: 5.3.1 と 5.3.2 それぞれに完了条件ブロックを追加する。

```
#### 5.3.1 完了条件

#### 5.3.2 完了条件
- 04 で検証するパターンが 3〜N 件確定し、各パターンに構成要素（埋め込みモデル / DB / 検索アルゴリズム / 連携方式）が記載されていること
- TBD4（有効性指標と閾値）が定義されていること
```

### I-2: 04.フィジビリティ検証 の「環境構築可否」完了条件が判定基準として粗い

**該当箇所**: `5.4 04.フィジビリティ検証` — `各パターン共通の検証項目` および `完了条件`

**問題**: 完了条件として「`検証報告書.md` が揃う」「05 へ進めるパターンの選定理由が示されている」とあるが、「何をもってパターンを通過させるか」の基準が示されていない。例えば：
- Docker 起動に成功したが MCP 登録で詰まった → 通過？ 不通過？
- インデックス構築に成功したが検索精度がほぼゼロ → 通過？

「フィジビリティ（実現可能性）」の合否判定基準がなければ、報告書が揃っただけで 05 に進んでよいかどうか実際の判断者が迷う。

**修正案**: 完了条件に以下を追加する。

```
#### 各パターン通過基準（フィジビリティ合格の定義）
以下をすべて満たした場合に「通過」とする:
1. Windows 11（WSL2 含む）で環境構築が完了すること（エラーなく起動できること）
2. 最低 1 件のクエリで結果が返ること（精度不問）
3. Claude Code から当該 RAG にアクセスできること（Skills または MCP 経由で呼び出せること）
いずれか 1 つ以上を満たせない場合は「不通過」とし、不通過理由を検証報告書に記載すること。
```

### I-4: 命名規則違反 — `01.検証_フィジビリティ_FilesystemExploration` がスペースなし英語表記のみ

**該当箇所**: `5.4 04.フィジビリティ検証` — パターン `05.検証_フィジビリティ_FilesystemExploration`

**問題**: ルート `CLAUDE.md` には「同名衝突を避けるため命名は `01.検証_フィジビリティ_<パターン名>/` の形式」と記載されており、パターン名部分のフォーマット上の問題ではないが、他のパターン名（`DuckDB_Skills` / `sqliteVec_MCP_Hybrid` / `pgvector_MCP` / `Chroma_MCP`）は英語の複合語だが `FilesystemExploration` だけ CamelCase で区切り文字がなく、視認性が他パターンと揃っていない。また `CLAUDE.md` のタスク進行状況では `パターンA` / `パターンB` という仮称が使われており、04 配下の具体名と対応が取れていない（C-2 と関連）。

加えて、ルート `CLAUDE.md` の命名規則には「日付はファイル名の末尾に付ける（先頭には付けない）」と規定されているが（ルート CLAUDE.md 第37行付近）、計画書はこれを正しく守っている。しかし `04.フィジビリティ検証` の検証報告書については「`検証報告書.md`」（日付なし）としており、複数回実施する想定がないなら問題ないが、方針を明示しておくべきである。

**修正案**: パターン名の区切り文字を統一する。

```
05.検証_フィジビリティ_Filesystem_Exploration   ← アンダースコアで単語区切り
```

また計画書の冒頭または 5.4 冒頭に「検証報告書は 1 回実施の想定のため日付サフィックスなし」と明記する。

### S-3: セクション 4 の TBD 表と各タスクの完了条件が二重管理になりかねない

**該当箇所**: `4. 仮説と不確定要素`（TBD1〜TBD6） vs 各タスクの完了条件

**問題**: TBD3 は「03.ローカル RAG 設計 / 01.ユースケース整理 で確定」、TBD4 は「03.ローカル RAG 設計 完了時に定義」と書かれているが、5.3 の完了条件にはこれらの TBD 解消が明示されている一方、4 の表の「検証タイミング」表記が微妙にズレている（「01.ユースケース整理」と「03.ローカル RAG 設計 完了時」）。計画書を更新した際に片方だけ直されてズレが生じるリスクがある。
