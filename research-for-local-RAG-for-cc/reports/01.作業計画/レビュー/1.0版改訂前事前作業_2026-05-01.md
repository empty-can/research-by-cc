### Pre-06: 「トークン削減率」と「コンテキスト消費削減率」の仕組み的差異

**関連指摘**: 論理 I4（保留：作業指示者が両者の差異について教示を求めている）

**項目内容**: 作業指示者の質問への回答として、トークン（API 課金単位）とコンテキスト（モデルが受信・保持する入力ウィンドウ）の関係を明確化する。

**区分**: 要ユーザー確認（事前情報提供）

**作業内容（情報提供）**:
作業指示者の理解に対する Claude 側の整理:

- **トークン**: 課金・転送単位。Claude Code クライアント ↔ Anthropic API 間で送受信される入力 / 出力テキストを Anthropic のトークナイザで数えた値。**ローカルプロセスのメモリ消費とは独立**。
- **コンテキスト**: API 呼び出し 1 回ごとにモデルへ渡される入力全量（システムプロンプト＋会話履歴＋ツール定義＋ツール実行結果＋ユーザー入力）。Claude Code が「セッション中保持」する内部状態は、API 呼び出し時に**毎回コンテキストとして送信される**。
- 重要事実:
  - Claude Code セッションのコンテキストは **「ローカルに保持して都度送信」モデル** であり、毎ターンの API 呼び出しで蓄積されたコンテキスト全体が再送される（プロンプトキャッシュにより重複部分は課金軽減されるが、転送・推論対象としてはコンテキスト全量がモデルに渡る）。
  - 単発クエリのトークン数 ≒ 単発 API 呼び出しのコンテキストサイズ（出力分は別計上）。よって**単発比較ではほぼ同義**。
  - 違いが顕在化するのは **マルチターン対話**: コンテキストはターン数に応じて累積し、毎ターン全量がトークンとして再送される。RAG が「不要な情報をコンテキストに残さない」設計なら、累積トークンの増分を抑える効果（つまり「コンテキスト消費削減」≒「累積トークン削減」）が大きい。
  - ノイズ汚染（先行インプット 01）はコンテキスト品質の問題であり、トークン量とは独立した側面（同じトークン数でもノイズが多いと精度が落ちる）。

**暫定結論**: 仕組み的には「コンテキスト＝モデルへの入力」「トークン＝コンテキストの計量単位」であり、**マルチターンでの累積効果**を別軸として明示すれば、「トークン削減率」と「コンテキスト消費削減率」を区別する意味がある。論理 I4 の修正案（単発クエリのトークン効率／セッション累積コンテキスト圧迫度の 2 指標）は技術的に妥当。

**作業指示者への回答希望事項**:
- 上記説明で作業指示者の理解と整合するか。
- 整合する場合、v1.0 改訂で指標を「単発クエリトークン効率」「セッション累積コンテキスト圧迫度（マルチターン累積トークン量＋ノイズ汚染）」の 2 軸に再定義してよいか。

#### 作業指示者からの回答（Pre-06）

**暫定結論**:
- 「ノイズ汚染」を **Context Relevancy（取得した文脈の質問関連度）** + **後続クエリの応答整合性スコア（独自定義）** の組合せで半定量化することが、既存手順の延長線上で実現可能。
