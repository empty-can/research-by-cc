## CRITICAL

### C1. コードベース向け Filesystem Exploration RAG が「保留候補」扱いになっており、調査目的の中核要請と矛盾している

**問題点**:
CLAUDE.md の背景には「リポジトリ配下のソースコードをインプットにした設計書のリバースエンジニアリング」が代表ユースケースとして明記されており、先行インプット 01 は「コードベースには Filesystem Exploration RAG が grep/glob で十分かつベクトル検索よりも適する可能性が高い」と明示している。にもかかわらず、計画書 5.4 ではパターン 05（Filesystem Exploration）を「採否は 03 で判断」の保留候補扱いとし、05.有効性検証の対比対象としても確定していない。

これは論理的に二重に不整合である:
- (a) 計画書自身の H1 仮説（「コードベース系データには grep/glob の方がベクトル検索より精度・速度で有利」）の検証が、必須でない扱いになっている。仮説を立てておきながら検証パターンを必須にしないのは論理破綻。
- (b) 「LLM でなくてもできることは Claude Code にさせない」という大前提に対し、ベクトル系 RAG だけを比較すると「ベクトル検索を組まなくても grep で十分」という結論が出る可能性をそもそも測定できない設計になる。

**修正案**:
- パターン 05（Filesystem Exploration）を「保留候補」から「**必須対比群**」に格上げし、04・05 の両フェーズで全パターン共通の **コントロール（対照群）** として位置付ける。
- 5.4 の検証パターン候補テーブルに「対照群: 05.検証_対照_FilesystemExploration」を新設し、ベクトル系 3〜4 パターンとの精度・トークン削減効果の差分を計測する設計とする。
- 5.5 の有効性指標に「対照群（grep/glob 単独）に対する精度向上度・トークン削減度」を追加。
- H1 仮説の検証タイミングを「04 と 05 の両方」に明記。

**作業指示者の態度表明**:

| 態度 | コメント |
|---|---|
| 条件付き採用 | 修正する前に、「03で判断」という保留候補扱いとした判断の経緯・根拠を確認し、修正案が妥当であることを確認すること。 |

### C2. CAG（Context-Augmented Generation）が比較対象から完全に脱落しており、調査目的の評価基準が片手落ち

**問題点**:
先行インプット 01 は RAG の広義定義に CAG を明示的に含めており、Vector Search RAG / Filesystem Exploration RAG と並ぶ正当な選択肢として位置付けている。本調査の目的は「精度を維持しつつトークン・コンテキスト消費を最小化する仕組み」の解明であり、CAG はこの目的に直接対応する候補（プロンプトキャッシュとの併用でトークン効率を保つ）である。

しかし計画書 3.3 のパターン分類では DB 形態軸・連携方式軸・検索アルゴリズム軸の 3 軸のみで、CAG は事実上の選外となっている。5.4 の検証パターン候補にも CAG（あるいは「RAG なし＋プロンプトキャッシュ運用」）が無い。

これは「ローカル RAG が本当に必要か」という上位の問いに答えられない計画になることを意味する。「RAG が解決策の有力候補」と推定しつつも、データ規模が小さければ CAG で済む可能性は CLAUDE.md でも排除されていない（むしろ「精度を維持しつつトークン消費を抑える」とだけ書かれており手段は限定されていない）。

**修正案**:
- 5.4 の検証パターン候補に「00.検証_対照_CAG」（プロンプトに直接ロード＋プロンプトキャッシュ）を加え、データ規模が小〜中規模の代表ケースで CAG とローカル RAG のトークン消費・応答速度を直接比較する。
- 5.3.1 ユースケース整理の「データ規模」軸で、CAG が成立する閾値（例: トークン数 ≦ 200k）を明示し、ユースケースごとに「CAG で足りるか／RAG が必要か」を最初に判定するゲート条件を設ける。
- 4.（仮説）に「H0: 一定規模以下のデータでは CAG（コンテキスト直接ロード＋プロンプトキャッシュ）が RAG よりトークン効率・精度ともに優れる可能性がある」を追加。

**作業指示者の態度表明**:

|---|---|

### I4. 「トークン削減率」と「コンテキスト消費削減率」が指標としてほぼ同義であり、独立指標として並べる根拠が不明

**問題点**:
5.5 の有効性指標テーブルで:
- トークン削減率: RAG 利用時 / 直接ファイル読み込み時のトークン消費比
- コンテキスト消費削減率: Claude Code セッションで消費されるコンテキストウィンドウ量の比

定義が酷似しており、「同一クエリで両方式実行・トークン計測」と「セッションログから計測」の差も明確に区別されていない。これでは何を比較対象とするか（単一クエリのコスト？セッション全体の累積コスト？）が曖昧で、後段の検証で恣意的に都合のよい値を採用してしまうリスクがある。

**修正案**:
2 つの指標を以下のように再定義し直す:
- **単発クエリのトークン効率**: 1 質問当たりの入力トークン総量（取得結果＋プロンプト）
- **セッション累積コンテキスト圧迫度**: 同一タスク完了までに必要だったクエリ数 × クエリ当たりトークン、および後続タスクへのノイズ汚染（先行インプット 01 で言及された Agentic Search のコスト特性に対応）

後者は単発の比ではなく、**マルチターン対話シナリオでの累積効果**を測るものとして区別すべき。

**作業指示者の態度表明**:

| 態度 | コメント |
|---|---|
| 保留 | Claudeへインプットとして作業指示者が渡した`CLAUDE.md`の記載に起因する指摘。作業指示者の知識不足が原因の可能性もあるが、そのような記載をした作業指示者の意図としては、それぞれ「トークン＝ローカルのClaudeプロセスとオンライン上のモデル(？)の間でやり取りされるデータ」と「コンテキスト＝ローカルのClaudeプロセスがそのセッションで消費するContextサイズ」であり、もし両者が仕組み的に全く同じなのであれば、コストの指標として使用されるのはトークンの方なので「トークン削減率」に統一してよい。逆に、Claudeが読み取ったテキストを咀嚼した結果としてメモリ上に保持しているContext（と作業指示者は理解している）の全量がネットワークの向こうのモデルに送信されるのでなければ、やはり本質的には両者は別ものということになり、トークン数の削減に効果がある工夫と、コンテキストサイズの消費量を抑える効果がある工夫は、両者に正比例の関係があることは自明であるゆえ共通するものが大部分であるとは思うが、どちらかに対してより効果がある工夫は存在する認識。この点について、正確な情報を教示願いたい。 |

### I5. TBD6（ローカル軽量モデルをサブエージェント検索に使う案）の取り扱いがスコープ抵触の判断保留になっている

**問題点**:
TBD6 は「ローカル LLM はスコープ外だが、検索専用なら別扱いか」と書かれており、判断が 02 基礎調査に丸投げされている。しかし、検証パターン 02（sqlite-vec + qwen3-reranker-0.6b）は実質的にローカル LLM（リランカー目的の小型 LLM）を使う構成であり、計画書はそれを採用しつつ TBD6 を未解決のまま並走させている。これは矛盾しており、実装段階で「やはりスコープ外でした」となるリスクがある。

CLAUDE.md の「含まない」節は「LLM としては Claude Code を利用する前提のため、改めて独自のローカル LLM を構築する必要が無いため」と理由を述べており、これは **生成 LLM** をローカル化しないという意味と読める。**埋め込みモデル・リランカーモデル**（=「専用ツール」）はそもそも生成 LLM ではなく、CLAUDE.md の大前提「専用ツールに任せる」に合致するため、スコープ内とすべき。

**修正案**:
- TBD6 を 01 完了時点で **明示判断** する。提案: 「生成 LLM のローカル構築はスコープ外。埋め込みモデル・リランカーモデル・小型クエリ書き換えモデルは『専用ツール』としてスコープ内」と明文化し、CLAUDE.md「含まない」節への注釈追記を依頼者に確認する。
- これにより検証パターン 02 のリランカー採用が論理的に正当化される。

**作業指示者の態度表明**:

| 態度 | コメント |
|---|---|
| 改変 | 特定のLLMが前提になっておりClaude Codeと連携ができない構成は調査対象外にするべきだが、情報源のローカルLLMを Claude Code に置き換えても機能する構成であり、かつローカルRAGあるいはそれに準ずる仕組みの実現について、他の情報源にない有用な情報がある可能性があれば調査対象にすべきである。ここで意図していた調査対象外のスコープを正確に表現するのであれば「ローカルLLMの構築や学習に関する情報」となる。 |

### S3. 5.5 の「ノイズ汚染度」が定性指標のままで定量化方針が無く、結果が主観評価に流れるリスク

表中「後続タスクへのノイズ汚染度（定性）」が「観察的評価（厳密化は要検討）」となっている。しかしこれは先行インプット 01 が Agentic Search の主要コストとして挙げた論点であり、本調査の中核的価値の一つ。定性のまま放置すると「RAG の方がよかった気がする」レベルの結論になる。

**修正案**:
- 「同一タスクを RAG 経由 / 直接読み込み で実行し、後続の追加質問に対する **回答の整合性スコア（事前定義した正解との一致度）** を比較する」など、半定量化できるプロトコルを 03 設計時に決める。
- 完全自動化が無理でも「1〜5 のルーブリック評価を 3 ケース実施し平均」程度には標準化する。

**作業指示者の態度表明**:

| 態度 | コメント |
|---|---|
| 保留 | 修正案に従う方針も取り得るが、「ノイズ汚染」をより厳密に定義できないか、またそれを評価する手順が既に確立されていないかを事前に調査する方が良いのではないかと思われる。見解を求めたい。 |

### S4. パターン分類 3 軸（DB 形態 / 連携方式 / 検索アルゴリズム）に「埋め込みモデル次元数」軸が無く、メモリ・ストレージ評価に反映されない

**問題点**:
3.3 のパターン分類軸には埋め込みモデルの次元数（384 / 1024）が入っていない。しかし先行インプット 03 はストレージ効率（LEANN との比較で 97% 削減）を明示的に課題として挙げており、05 の有効性指標にも「インデックス構築コスト」が入っている。次元数選定は **ストレージ・速度・精度のトレードオフ** に直接効くので独立軸として扱うべき。

**修正案**:
3.3 に第 4 軸「埋め込み次元軸（小型 ≦ 384 / 大型 ≧ 1024）」を追加し、5.4 の検証パターンが両端をカバーするよう確認する（現状ドラフトは概ねカバーしているが、明示することでバランス検証が可能になる）。

## レビュー総評

計画書は「仮説と TBD の明示」「命名規約遵守」「見直しトリガー定義」など方法論面で堅実だが、以下 2 点で **調査目的の核心を取り逃がす** リスクが大きい:

1. **コードベース向け Filesystem Exploration RAG が必須対照群になっていない**（CRITICAL C1）
2. **CAG が比較対象から完全に脱落している**（CRITICAL C2）

この 2 点が修正されないと、本調査は「ベクトル系ローカル RAG の中での最適構成」を選定するに留まり、調査の本来の問い「ローカル RAG は **そもそも** 本ユースケースに必要か／何で代替できるか」に答えない結果になる。02 基礎調査着手前に C1・C2 と I3（規模感の早期確定）を反映した改訂版を作ることを強く推奨する。
