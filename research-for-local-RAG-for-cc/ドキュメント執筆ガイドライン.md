## 0. ガイドラインの位置付けと使い方

### 0.1 ガイドラインとレビュー観点の関係

本ガイドラインは **執筆者がドキュメント作成中に参照する予防チェックリスト** であり、`.claude/templates/cross-review/` のレビュー観点（13 観点）と **対をなす** 関係にあります。

- **執筆段階**（本ガイドライン）: 書く前・書きながら適用する観点
- **レビュー段階**（cross-review テンプレ）: 完成版に対して適用する観点

両者の重複は意図的です。執筆段階で吸収しきれなかった指摘がレビュー段階で発見されることを前提とし、**双方向の品質ループ** を構築します。

### 0.2 適用タイミング

| ドキュメントの段階 | 本ガイドラインの適用箇所 |
|---|---|
| 構造設計（章立て決定） | §1 構造設計編 を全項目適用 |
| 執筆中 | §2 執筆中編 を継続的に意識 |
| 完成直前のセルフチェック | §3 完成前セルフチェック編 を全項目適用 |

### 0.3 観点の出典凡例

各観点の右肩に出典を示します:
- `[doc-coauthoring]`: Anthropic 公式 `anthropics/skills/doc-coauthoring` Skill 由来
- `[internal-comms]`: Anthropic 公式 `anthropics/skills/internal-comms` Skill 由来
- `[Microsoft]`: Microsoft Writing Style Guide（Scannable content 等）由来
- `[Google]`: Google Technical Writing 由来
- `[Minto]`: Minto Pyramid Principle 由来
- `[Diátaxis]`: Diátaxis Framework 由来
- `[academic-paper-reviewer]`: `Imbad0202/academic-research-skills` 由来
- `[作業指示者 §9.2]`: v2 トライアル取りまとめ §9.2 作業指示者記入由来
- `[F02-010]`: バックログ F02-010「レビュー対象成果物の資産性質改善」由来

## 1. 構造設計編（書く前に決めること）

### G1-1. 想定読者像の事前宣言 `[doc-coauthoring]` `[internal-comms]`

ドキュメント冒頭またはメタ情報に、想定読者像を 1〜2 文で明示する。

| 項目 | 例 |
|---|---|
| 想定読者の役割 | 「最終承認権限を持つ人間レビューア」「03 設計フェーズ担当 Claude Agent」 |
| 想定読者の前提知識レベル | 「本プロジェクト全体の文脈を持つ前提」「事前文脈なし、本ファイルのみ参照」 |
| 想定読了時間 | 「10〜20 分」「5 分以内」 |

> **理由**: 想定読者の前提知識レベルが明示されていれば、執筆段階で「どこまで前提を書くべきか」「どこから本題に入れるか」の判断基準が明確になる。レビュー段階での「前提知識の明示不足」指摘も予防できる。

### G1-2. ドキュメント全体構成の可視化（目次・冒頭サマリ・読み方ガイド） `[作業指示者 §9.2]` `[Microsoft]` `[Minto]`

以下の 4 点を必ず満たす:

1. **目次（TOC）の整備** — 章数が 5 を超える、または行数が 100 を超えるドキュメントは目次を必ず置く。各セクション名は **対応するセクションへのリンク** とする
2. **各章の 1 行説明併記** — 目次の各章名の右側に、その章の内容を 1 行で説明する
3. **冒頭サマリ構成** — 報告書系（調査報告書・最終報告書・取りまとめ）は冒頭で「**調査内容 / 調査結果 / 結論・示唆**」のサマリを提示し、その後に各詳細へ繋げる
4. **読者別読み方ガイドの提供（複数読者向けドキュメントのみ）** — 想定読者が複数（例: 承認権限者 / 後続フェーズ Agent / 設計担当者）の場合、各読者がどの章を優先的に読むべきかの動線を **表形式で提示** する

```markdown
良い例（読者別動線表）:
| 想定読者 | 優先読了章 | 読了目安 |
|---|---|---|
| 承認権限者 | §0 冒頭サマリ → §9 GO/NO-GO 整理 | 5〜10 分 |
| 03 設計担当 Agent | §3 採用候補 → §6 命名規則 → §7 引き渡し | 20〜30 分 |
| レビューア | 全章 | 25〜35 分 |
```

> **理由**: ボリュームが大きいドキュメントほど構成把握コストが急増する。冒頭で全体像を把握でき、読者別動線が示されていれば、読者は自分に必要な章だけ読めば判断ができる。認知負荷が大幅に下がる。

### G1-3. 文書モードの自意識（Diátaxis） `[Diátaxis]`

各章を執筆する前に、その章が以下のどのモードかを意識する:

| モード | 性質 | 章末スタンス |
|---|---|---|
| **Tutorial** | 段階的に手を動かして学ぶ | 学習成果としての到達点を明示 |
| **How-to** | 特定の目的を達成する手順 | 完了条件を明示 |
| **Reference** | 仕様・カタログ・参照表 | 網羅性と検索性を優先 |
| **Explanation** | 設計意図・背景・理由づけ | 理解促進を優先 |

> **理由**: 「読者が何を求めて読むか」を一意化することで、不要な脱線・冗長を回避できる。

#### G1-3.1. 複数モード混在ドキュメントの扱い方 `[v2.0 追加]`

計画書・統合報告書のような **本質的に複数モードが混在するドキュメント** では、純粋なモード単一化は不可能。以下の戦略で扱う:

1. **章単位でモードを切り替える** — 1 つの章 = 1 つのモードを基本とし、章レベルではモード混在を避ける
2. **モード切り替え点の明示** — 「ここから設計意図の説明に入る」など、モード切り替えを明示する見出しまたは導入文を置く
3. **読み方ガイド（G1-2 #4）でモード別動線を補完** — 例: 「Reference 章だけ読みたい場合は §3 / §6 へ」など

```markdown
典型的な混在パターン:
- 計画書: §0〜§1（Explanation）→ §2〜§5（How-to + Reference）→ §9（Explanation）
- 統合報告書: §0（Explanation）→ §3〜§7（Reference + Explanation）→ §9（Explanation: GO/NO-GO 判断）
```

> **理由**: 複数モードを章レベルで切り分けると、読者は各章の読み方を即座に判断できる。モード切り替え点が不明だと、Reference を読むつもりで Explanation に巻き込まれる等の認知負荷が発生する。

### G1-4. 内外参照の相互リンク化 `[作業指示者 §9.2]`

ドキュメント内外の参照は **必ず Markdown リンクとして記載** する:

```markdown
良い例:
- 詳細は [§3.2 採用候補](#32-採用候補) を参照
- 関連: [F02-009](improvements/F02-009_クロスレビュー指摘記載ルールとセルフレビュー観点の規定.md)

悪い例:
- 詳細は §3.2 を参照（リンクなし）
- 関連: F02-009（リンクなし）
```

> **理由**: リンクをクリックするだけで参照先へ飛べるため、レビューア・読者の作業コストがほぼゼロになる。手動辿り作業はレビュー効率を著しく圧迫する。

## 2. 執筆中編（書きながら意識すること）

### G2-1. 結論先出し（BLUF / Pyramid） `[Minto]` `[internal-comms]`

各章・各節の冒頭 1〜2 文で **結論または核となる主張** を先に書く。詳細・根拠は後段に置く。

```markdown
良い例:
## 3.1 採用候補
本フェーズの採用候補は BAAI/bge-m3（埋め込み）+ DuckDB+vss（DB）+ ハイブリッド検索の構成。
理由は §3.1.1〜§3.1.3 で述べる。

悪い例:
## 3.1 採用候補
2026 年初頭から複数の候補を比較検討した。BAAI/bge-m3 は…（結論が章末まで出ない）
```

### G2-2. 短文・短段落（3〜7 行） `[Microsoft]` `[Google]`

- **段落長**: 3〜7 行で区切る
- **文長**: 単純に保つ（1 文に複数の節が入りすぎない）
- **箇条書き化**: 列挙構造の文は箇条書き / 表に変換

> **理由**: 長い段落・長文は目が滑りやすく、重要情報を見落とすリスクが上がる。

### G2-3. パターン化された構造（landmark） `[Microsoft]`

同じ種類の情報は **同じ構造（見出しレベル・記述順）** で書き、読者がパターンで処理できるようにする。

```markdown
良い例（採用候補の各エントリで構造を統一）:
### 3.1.1 BAAI/bge-m3
- ライセンス: MIT
- ストレージ要件: 約 2GB
- 採用根拠: 多言語対応、高精度

### 3.1.2 ruri-v3-310m
- ライセンス: Apache 2.0
- ストレージ要件: 約 0.6GB
- 採用根拠: 日本語特化
```

#### G2-3.1. パターン化テンプレート例 `[v2.0 追加]`

頻出するパターンの参考テンプレート:

**採用候補エントリ**:
```markdown
### N.M.K. {候補名}
- **ライセンス**: {ライセンス名・互換性メモ}
- **ストレージ要件**: {サイズ目安}
- **採用根拠**: {技術的根拠・1〜2 文}
- **注意点**: {既知の制約・落とし穴}
- **出典**: {サブタスク N の §X / 引用元へのリンク}
```

**サブタスク報告書サマリ**:
```markdown
### N. {サブタスク名}
- **目的**: {1 文}
- **問い**: {1〜3 件の主要問い}
- **完了条件**: {何が成立すれば完了か}
- **主要発見**: {本フェーズで採用された結論への寄与}
```

**指摘エントリ（クロスレビュー以外で使用する場合）**:
```markdown
### {ID}. {タイトル}
- **該当箇所**: {章節・行番号}
- **問題**: {1〜2 文で要約}
- **根拠**: {引用または典拠リンク}
- **対応案**: {改善案・複数あれば表で}
```

> **理由**: パターン化された構造は「テンプレートで書き始める」ことで初動コストを下げ、書き手間・章間の揺れを防ぐ。テンプレ例を持つことで「最初の 1 件目をどう書くか」の判断負荷も下がる。

#### G2-3.2. 比較項目の表形式の検討（緩いガイドライン） `[v2.0 追加]` `[作業指示者 §3.4.1 (2)]`

> **本項目の強制力について**: 本項目は **「ルール」ではなく「ガイドライン」** であり、**「心がけてほしい」程度の緩い強制力** です。判断基準が状況により曖昧にならざるを得ないため、強い強制力は持たせていません。実装時は読み手にとっての可読性を最優先で判断してください。

複数の対象を **比較する目的** で記載する場合、表形式の採用を検討する:

| 状況 | 推奨表現 |
|---|---|
| 採用候補・ベンチマーク比較等の **比較対象が複数あり、共通項目で比較できる** | 表形式（行 = 対象、列 = 比較項目） |
| 比較対象に該当しない **個別の説明・根拠・注意点** | 表に無理に収めず、表外で箇条書き等で補完 |
| 表形式に収めると一部の情報が欠落・無理が生じる | 箇条書きを優先し、可読性を保つ |

```markdown
良い例（表 + 箇条書きの併用）:
##### 採用候補基本スペック（共通項目は表形式）
| 候補 | 候補順位 | 形態 | スケール目安 | ライセンス |
|---|---|---|---|---|
| DuckDB + vss | 1 | 単一ファイル DB | 数十万〜数百万 | MIT |
| LanceDB | - | 単一ファイル組み込み型 | 数百万〜 | Apache 2.0 |

##### 採用根拠と注意点（個別情報は箇条書き）
- **DuckDB + vss**
  - 採用根拠
    - 単一 `.duckdb` ファイル + 標準 SQL
    - Windows 公式サポート
  - 注意点
    - HNSW のディスク永続化は experimental
- **LanceDB**
  - 採用根拠
    - Arrow ネイティブ・ディスク効率高い
  - 注意点
    - 約 25,600 件未満は自動でフルスキャン
```

> **理由**: 比較項目を表形式にすることで見やすさが向上し、過度な箇条書き化によるドキュメントの縦長化を抑えられる。一方、個別の説明・根拠を無理に表化すると可読性が低下するため、表形式に固執しない。

> **適用タイミング**: 新規執筆時から心がける。既存ドキュメントへの遡及適用は不要。

### G2-4. 前提知識の明示 `[doc-coauthoring]`

ドキュメント執筆中に「これは読者にとって既知か？」を都度問い、暗黙の前提があれば補足する。

| 状況 | 対処 |
|---|---|
| プロジェクト固有の用語 | 初出箇所で 1 行定義を併記 |
| 業界共通用語だが略語 | 初出箇所でフルスペル併記（例: `MCP（Model Context Protocol）`）|
| 引用・参照が前提 | 引用文をその場に残し、参照だけで完結させない |

### G2-5. アクティブボイス・断定の優先 `[internal-comms]` `[Google]`

受動態・婉曲表現が判断を曖昧にしていないかを点検する。

```markdown
良い例:
- 採用する: bge-m3
- 除外する: paraphrase-multilingual（最大 128 トークン制限）

悪い例:
- 採用されるべきと考えられる: bge-m3
- 除外されることが望ましい可能性が高い: paraphrase-multilingual
```

### G2-6. データドリブン（数値・期日・件数） `[internal-comms]`

「効果的」「相当数」のような形容詞は、可能な限り **数値・期日・固有名詞** で置き換える。

```markdown
良い例:
- 02.基礎調査の作業指示者レビューは 2026-05-05 完了、139 指摘収集
- bge-m3 は recall@10 で 91% を達成

悪い例:
- 02.基礎調査のレビューは効果的に完了、相当数の指摘を収集
- bge-m3 は高い精度を達成
```

### G2-7. ジャーゴン判定の手続き化 `[Google]`

略語・専門用語ごとに「想定読者がそのまま読めるか」を判定し、できないなら **定義 or 言い換え** を入れる。

判定手順:
1. その用語を初出時に Google 検索したと仮定し、上位 5 件で意味が即座に取れるか確認
2. 取れない場合は 1 行定義を併記
3. 業界共通用語でも略語は初出フルスペル必須

### G2-8. 箇条書きの記法ルール `[v2.0 追加]` `[作業指示者 §3.4.1 (1)]`

箇条書きで複数の情報を伝える場合（特に伝える情報量が多い場合）、以下のルールに従う:

1. **1 階層目は主題を 1 文で書く**
   - 読み手が箇条書きを目で追ったときに、主題を即座に把握できるようにする
2. **詳細・補足・根拠は階層を下げる**
   - 1 階層目の主題に対する補足情報は、一段下げた箇条として書く（並列の箇条としない）
3. **関連情報は階層構造で表現**
   - 関連する情報を並列の箇条として記載するのではなく、階層を下げて関係性を構造で示す
   - 視覚的に文章の論理構造が把握できる効果

```markdown
良い例（階層構造で関係性を表現）:
- 不同意点の整理
  - 「基準 4 の評価不整合」点は不同意
    - 基準 4 は構築完了後の最低限の動作網羅性確認として必要
      - Pre-15 由来の意図的追加（疎通だけでなく正常パターンも回ることを確認）
    - 「想定通りの結果」が読み手に「精度評価」と誤読される文言は改善余地あり

悪い例（複数情報の詰め込み + 並列化）:
- 「基準 4 の評価不整合」点は不同意。基準 4 は構築完了後の最低限の動作網羅性確認として必要であり、Pre-15 由来の意図的追加（疎通だけでなく正常パターンも回ることを確認）である。ただし「想定通りの結果」が読み手に「精度評価」と誤読される文言は改善余地あり。
```

> **理由**: 1 階層目に複数情報を詰め込むと主題の即時把握が困難になる。階層構造で関係性を表現することで、視覚的に文章の論理構造が把握できる。

> **適用タイミング**: 新規執筆時から適用。既存ドキュメントへの遡及適用は不要（コスト過大のため）。

## 3. 完成前セルフチェック編（出す前に通読チェック）

### G3-1. AI スロップ／前置き句の排除 `[doc-coauthoring]`

完成版を通読し、以下のパターンを **形態素レベルで排除** する:

| 排除対象 | 例 | 対処 |
|---|---|---|
| 中身のない前置き句 | 「近年〜」「重要なのは〜」「以上を踏まえると〜」 | 削除 or 具体的な接続詞に置換 |
| em-dash の連用 | `Aは — Bだが — Cである` | 1 文を 2〜3 文に分割 |
| ハッジ語の頻発 | 「と思われる」「可能性が高い」「と考えられる」 | 断定可能な箇所は断定、不確かな場合のみ残す |
| 単調な文長 | 全文がほぼ同じ長さ | 一部を短文化 or 結合して変化を出す |

> **検出方法**: grep で `近年|重要なのは|以上を踏まえると|と思われる|可能性が高い|と考えられる` を検索し、ヒット箇所を再評価。

### G3-2. 全文「重み検査」（every sentence carries weight） `[doc-coauthoring]`

完成版を通読し、各文に対して以下を問う:

> **「この一文を削除して、情報損失が出るか？」**

- **Yes**: 残す（その文は情報を運んでいる）
- **No**: 削除候補（無くても文書の意味が変わらない）

「No」が一定割合（例: 全文の 10% 超）あれば、冗長過多と判定して圧縮する。

#### G3-2.1. 保険文・誘導文の扱い `[v2.0 追加]`

「保険文」「読者誘導文」は重み検査で「No（削っても情報損失なし）」と判定されがちだが、以下の場合は **残すことを優先** する:

| 残すべき保険文 | 例 | 理由 |
|---|---|---|
| 重要前提の再確認 | 「※本フェーズでは Docker 不可前提下での検証に限定する」 | 削ると後続章で前提誤読のリスク |
| モード切替宣言 | 「ここから採用候補の詳細に入る」 | 削ると章のモード判定が不明瞭になる |
| 警告・注意 | 「※この値は v0.3 以降で変更される可能性がある」 | 削ると安定性誤認のリスク |

判定基準: **「この保険文を削ったとき、想定読者の誤読リスクが増えるか？」が Yes なら残す。**

> **理由**: 重み検査は冗長文の削減が目的だが、保険文は「情報損失」ではなく「誤読リスク低減」を担うため、機械的に削ると本来の目的（読者の認知負荷低減）と逆の結果になる。

#### G3-2.2. G2-3 パターン化構造との競合整理 `[v2.0 追加]`

並列構造（G2-3）を保持すると、各エントリで類似の文言が繰り返され、重み検査では冗長と判定されがち。以下の優先順位で扱う:

1. **G2-3 並列構造を優先** — エントリ単位の構造の揃いは、パターン認識による読み手の負荷軽減効果が大きい
2. **G3-2 重み検査は「並列構造内の各文」ではなく「並列構造そのもの」に対して適用** — 「このエントリ全体は不要か？」を問う形にする
3. **並列構造内の重複が真に問題なら、構造側を簡素化する** — エントリ内のフィールドを削る等で対処（個別文を削るより構造単位で）

> **理由**: G2-3 と G3-2 は両立する観点だが、機械的に重み検査を適用すると並列構造を破壊しがち。優先順位を明示することで判断負荷を下げる。

### G3-3. 冗長／矛盾の二重チェック `[doc-coauthoring]`

通読時に以下を発見・除去:
- 同じ主張の重複（章をまたいで似た主張をしていないか）
- 章をまたぐ矛盾（§3.7 と §4 H1 で同じ仮説について異なる表現になっていないか）
- 同じ事実への異なる表記（「02-07」「02.07」「サブタスク 07」のような表記揺れ）

### G3-4. アンビギュイティ（曖昧表現）の検出 `[doc-coauthoring]`

通読時に以下を点検:
- 主語の省略（誰が・何が の主語が明確か）
- 指示語の連鎖（「この」「それ」が何を指すか即座に分かるか）
- 複数解釈可能な術語（同じ語が章ごとに異なる意味で使われていないか）

### G3-5. 主張の Specificity 三点セット（what / where / evidence） `[academic-paper-reviewer]`

主要主張（H2 直下の結論文や箇条書き）ごとに以下を点検:

| 三点 | 確認内容 |
|---|---|
| **What**: 何を主張しているか | 主張が 1 文で抽出可能か |
| **Where**: どこで根拠が示されているか | 該当節・図表・データへのリンクが付いているか |
| **Evidence**: 反証された場合の影響 | 根拠が崩れたときの影響範囲が把握できるか |

3 点が揃わない主張は、執筆段階で根拠補強または主張削除を検討する。

#### G3-5.1. 計画書段階（証拠未取得段階）における where の扱い `[v2.0 追加]`

計画書執筆時点では実証データが取得されていないため、Where 項目を「§N の表 / 図」のような **既存資産への引用** で満たすことができない。この場合の扱い:

| 計画書の where 表記 | 例 |
|---|---|
| **検証予定の明示** | 「§5.4.3 04-02 検証で実測予定（実測対象: recall@10）」 |
| **典拠先行情報の引用** | 「サブタスク 02 §3.1.1 報告に基づく」 |
| **暫定根拠の明示** | 「先行インプット 04 から推定（実測未）」 |

実証完了後の報告書では「§N の表 / 図」など具体引用が必須。

> **理由**: 計画書段階で「typeA Skill 由来」のような曖昧な引用や、引用なしの主張があると、後続のレビューで「根拠不在」指摘が発生する。検証予定 / 典拠先行情報 / 暫定根拠の 3 区分のいずれかを必ず明示することで、レビューア・承認者の確認負荷が下がる。

### G3-6. 想定読了時間との乖離点検 `[internal-comms]`

文書冒頭で宣言した想定読了時間（G1-1）に対し、文字数・段落数から実測値を概算し、乖離を点検:

- **想定の +50% 以内**: 許容
- **想定の +50% 超**: 要約セクション追加 or 文書分割を検討
- **想定の 2 倍超**: 構造的な見直しが必要

#### G3-6.1. 単位の規定 `[v2.0 追加]`

| 想定読者 | 単位 | 1 分あたり目安 |
|---|---|---|
| **人間（業務文書）** | 日本語文字数（コードブロック・URL を除く本文文字数） | 600〜800 文字 / 分 |
| **人間（読み物）** | 日本語文字数 | 800〜1,000 文字 / 分 |
| **Claude Agent** | トークン数 | 概ね「文字数 ÷ 2.5」程度（処理速度ではなく入力読み込みの観点。実用上は内容理解時間として人間想定の 1/3〜1/5） |

**実測時の文字数定義**:
- 含む: 本文・見出し・表セル内テキスト・箇条書き
- 除く: コードブロック / URL / Markdown 装飾記号（`*`、`#`、`|` 等）

> **理由**: 「文字数」「トークン数」「ワード数」のような単位曖昧さで読了時間判定がブレる。明示的な単位規定により、執筆者間・レビューア間で同じ基準で実測できる。

> **概算ルール**: 想定読者が人間（業務文書）で 10〜20 分想定なら 6,000〜16,000 文字が目安。Claude Agent 向けなら処理時間ではなく **読み込みコスト＝トークン消費** として捉え、トークン数を直接見るほうが実用的。

### G3-7. Devil's Advocate（最強反論の織り込み） `[academic-paper-reviewer]`

主要結論（特に承認判断に影響するもの）について、以下を 1 件ずつ書き残す:

> **「この結論に対する最強の反論は何か？」**

- 反論が **棄却可能** なら: 反論内容と棄却根拠を本文に織り込む
- 反論が **棄却困難** なら: 残存リスクとして承認者に明示

#### G3-7.1. 適用粒度の規定 `[v2.0 追加]`

Devil's Advocate を **どこまで適用するか** の粒度規定:

| 粒度 | 適用対象 | 推奨適用条件 |
|---|---|---|
| **章レベル** | 各章末で「章全体の結論への反論」を 1 件 | 探索的な調査章・整理章で十分 |
| **節レベル** | 主要節（採用候補・GO/NO-GO 判断等）で 1 件 | 統合報告書・改訂提案で推奨 |
| **主張レベル** | 個別の主張（「bge-m3 を採用」「X を除外」等）で 1 件 | **承認判断に直結する主張のみ**（過剰適用は記述コスト増大） |

判断指針:
- 計画書: 主要採用方針（4〜6 件）に対して **節レベル + 主張レベルの折衷**（3〜4 件で十分、Devil's Advocate 章独立化を推奨）
- 統合報告書: 主要結論（GO/NO-GO 判断・採用候補確定等）に対して **節レベル**（5〜8 件）
- 探索的な調査・整理ドキュメント: **章レベル**（章数分のみ）

#### G3-7.2. 再反論深度のガイダンス `[v2.0 追加]`

反論が棄却可能な場合の **棄却根拠の深度**:

| 深度 | 例 | 適用基準 |
|---|---|---|
| **1 段反論** | 反論内容 → 棄却根拠 | 多くの場合これで十分 |
| **2 段反論** | 反論 → 反論への再反論 → 最終棄却根拠 | 想定される反論が複数階層になる場合（例: 「コスト面で不利」→「コスト試算は限定条件下」→「実プロジェクトでは複数条件で検証」） |
| **3 段以上** | 推奨しない | 過剰深掘り・読者の認知負荷増 |

**「最強の反論」の探し方**:
1. 結論を支える主要根拠を 1 つ崩す形で考える
2. 異なる業界・スコープの視点から考える（例: 「Claude Code 用途では不要だが汎用 Agent では必要」）
3. 既知の制約（環境・ライセンス・コスト）を無視できないかを問う

> **理由**: Devil's Advocate を機械的に多用すると本文が反論で埋まる。粒度規定により「どこまで書くか」の判断負荷を下げる。

### G3-8. 図表・コードブロックの self-contained 性 `[doc-coauthoring]`

図に頼らず本文だけで意味が通るか確認:
- 図の内容を本文で 1 文要約
- alt-text を付ける
- コードブロックには言語指定を付ける

### G3-9. iteration の収束基準 `[doc-coauthoring]`

修正を繰り返している場合、3 巡連続で実質的な変更がないなら、**「削れるものはないか」を能動的に問う**（増やす方向の慣性をブレーキ）。

### G3-10. リンクアンカーの動作確認

最後に、ドキュメント内のリンクが実際に機能するか確認:
- 内部アンカー: クリックで該当セクションへ飛ぶか
- 外部リンク: パスが正しいか、ファイル名のタイポがないか
- 日本語見出しのアンカー: GitHub プレビュー / VSCode プレビュー / 他ツールで挙動が揃うか（揃わない場合は明示的な HTML アンカー `<a id="..."></a>` を使う）

#### G3-10.1. アンカー命名規則と静的検証手順 `[v2.0 追加]`

GitHub Flavored Markdown / VSCode / 他レンダラーごとにアンカー生成ルールが異なるため、以下のルールで命名と検証を行う:

**アンカー命名規則**:
- 見出しの記号（`. ` / `/` / `(` / `)` / `:` 等）は省略
- 全角スペース → ハイフン
- 半角スペース → ハイフン
- 大文字 → 小文字（GitHub 仕様）
- 例: `### G3-10. リンクアンカー` → アンカー: `g3-10-リンクアンカー`

**静的検証手順**:
1. ドキュメント内の全 `[...](#...)` 形式リンクを grep で抽出
2. 各リンクの `#` 以降が、対応する見出しから上記命名規則で生成されるアンカーと一致するか目視確認
3. 一致しない場合は明示的な HTML アンカー `<a id="..."></a>` を見出し直前に挿入し、リンクをそのアンカーへ向ける

**外部相対パスの検証**:
- 配置場所が確定していない（`reports/work/` から最終配置先へ移動予定 等）の場合、**最終配置先から相対パス計算** をしてリンクを書く
- 移動前は壊れていることを承知で書き、最終配置時に動作することを優先

> **理由**: Markdown レンダラーのアンカー仕様差は事前検証しないと運用中に壊れる。命名規則を明文化し、配置移動時の整合性を担保する。

### G3-11. 情報欠落チェック（再執筆・改訂時のみ） `[v2.0 追加]` `[§9.3 由来]`

既存版を改訂する場合、または既存版を参考に新規執筆する場合（典拠を別資産から再構築する等）は、**本来必要な情報が欠落していないか** を最終チェックで確認:

| 比較対象 | チェック内容 |
|---|---|
| **既存版（前版）** | 旧版で扱われていた重要情報・データが新版で網羅されているか |
| **典拠（サブタスク報告書 / 計画書 等）** | 典拠で扱われた採用候補・ベンチマーク数値・除外判定・ハマりどころ・Issue 化対象が漏れなく反映されているか |
| **要件定義（CLAUDE.md / 計画書）** | プロジェクト目的・スコープに照らして必要な情報がカバーされているか |

**実施手順**:
1. 前版または典拠から、本来扱うべき情報リスト（採用候補名・主要数値・固有名詞 等）を抽出
2. 新版で各項目が含まれているか機械的に確認（grep 推奨）
3. 含まれていない項目について、意図的削除か漏れかを判断
4. 漏れの場合は本文に補完、意図的削除の場合は変更履歴に明記

> **理由**: 再執筆・改訂時は情報損失リスクが上がる。執筆ガイドラインの予防効果は形式的指摘の削減に強いが、情報欠落は形式以外の問題で発生するため、別の機械的チェックが必要。

> **適用タイミング**: 通常のセルフチェック（G3-1〜G3-10）は新規執筆時にも適用する。G3-11 のみ **再執筆・改訂時の追加観点** として位置付ける。

## 4. ドキュメント種別ごとの追加観点

### 4.1 計画書

- **G1-1 の想定読者像**で「本ドキュメント単独で承認判断ができる」前提か明示
- **G1-2 の冒頭サマリ**で「目的・スコープ・成功条件・打ち切り条件」を提示
- **G1-2 #4 読者別読み方ガイド**で「承認権限者向け動線」を必ず提示（5〜10 分で承認判断到達できる動線）
- **G3-7 Devil's Advocate** を計画前提・採用案ごとに 1 件ずつ実施（Devil's Advocate 章として独立化を推奨）
- **打ち切り条件の独立化** `[v2.0 追加]`: 打ち切り条件は **独立した節**（例: §0.4 / §9.1）として配置し、採用案・成功条件と並列に置く。本文中に散在させない
- **成功条件・打ち切り条件には合格水準・基準値を明示** `[v2.0 追加]`: 「実測値が記録されている」「想定外コストが見積りの 3 倍超」のような **判定不能な定性記述を避け**、定量基準（recall@10 ≥ 0.80 等）または相談トリガー（基準値を超えた時点で作業指示者と相談）として明示
- **読了時間制約のスコープ外** `[v2.0 追加]` `[作業指示者 §3.4.2 (1)]`: 計画書は「全記載内容を時間をかけて十分にレビューする」性質のドキュメントのため、**G3-6 想定読了時間との乖離点検は計画書には適用しない**（= 分量制約は他ドキュメントほど厳格に適用しない）。代わりに以下を重点的に確認する:
  - G1-2 全体構成可視化（特に各セクションの要点把握容易性）
  - G1-3.1 複数モード混在ドキュメントの章単位モード切替
  - 必要情報の網羅性（成功条件・打ち切り条件・スコープ・WBS・成果物・体制・スケジュール・リスク 等）
  - 各セクションの記載順序の理解容易性・妥当性のチェック容易性
  - 判断基準・マイルストーンなど計画遂行に必要な観点・方針の網羅性
- **計画書執筆ガイドライン整備（バックログ）** `[v2.0 追加]`: 計画書固有の詳細ガイドライン（具体的なチェックリスト・記載順序の標準・網羅項目の例示）は [`improvements/F02-011_計画書執筆ガイドライン整備.md`](improvements/F02-011_計画書執筆ガイドライン整備.md) で別途整備予定

### 4.2 調査報告書（フェーズ報告書 / 統合報告書）

- **G1-2 の冒頭サマリ**は「調査内容 / 調査結果 / 結論・示唆」の 3 部構成（作業指示者 §9.2 由来）
- **G3-5 Specificity 三点セット**を採用候補・除外候補の各エントリに必ず適用
- **G3-9 iteration の収束基準** で「報告書のサイズが膨張気味」なら章末 LEARNING / FOLLOW-UP セクションへの切り出しを検討

#### 4.2.1 統合報告書（複数サブタスクの統合）特有の追加観点 `[v2.0 追加]`

統合報告書（最終基礎調査報告等）では、以下の追加観点を必須適用:

1. **用語統一の事前合意** — サブタスク間で揺れる用語（例: 「ハイブリッド検索」/「ハイブリッド RAG」、チャンクサイズ単位の「文字数」/「トークン数」/「非空白文字」）を最初に統一定義する
2. **章間整合性の確認** — 同じ仮説・採用候補・除外候補について複数章で言及する場合、表現を統一する
3. **レイヤー間整合の確認** — 採用候補（§3.1 等）と検索アルゴリズム表（§3.4 等）が同じ候補を扱っているか、レイヤーをまたいで整合しているかを確認
4. **ハマりどころ.md 等の状態同期** `[F02-010]` — 報告書内の「未追記」「未対応」のような **状態言及** が、参照先（ハマりどころ.md 等）の現状と一致しているかを最終チェックで確認。状態が動的に変動する場合は本文側で状態を断定せず、「最新状態は §X 参照」と明記する
5. **GO/NO-GO 判断の明示** — フェーズ承認に関わる統合報告書では、§9 等に「GO を支持する事実」「NO-GO リスク」「次フェーズ方針」の 3 段構造で判断材料を整理する
6. **サブタスク報告書への参照容易性** — 各採用候補・主要結論ごとに、典拠となるサブタスク報告書の該当節へのリンクを付ける（後続フェーズの参照負荷低減）

#### 4.2.2 調査報告書執筆ガイドライン整備（バックログ） `[v2.0 追加]`

調査報告書（フェーズ報告書 / 統合報告書）固有の詳細ガイドライン（具体的なチェックリスト・統合時の標準手順）は [`improvements/F02-012_調査報告書執筆ガイドライン整備.md`](improvements/F02-012_調査報告書執筆ガイドライン整備.md) で別途整備予定。本ガイドラインの §4.2 / §4.2.1 はその起点となる観点列挙。

### 4.3 レビュー報告書（クロスレビュー / 作業指示者レビュー）

- テンプレート（`.claude/templates/cross-review/`）に従う
- **G1-4 内外参照の相互リンク化** は特に重要（指摘ごとの該当箇所への直接リンク）
- **想定読者は事前知識を持つ前提**で書く（前提知識の明示は最小限で良い）

### 4.4 改訂提案・運用考察ドキュメント

## 5. ガイドラインの運用ルール

### 5.1 ガイドラインの参照タイミング

| タイミング | 参照範囲 |
|---|---|
| ドキュメント執筆を開始する直前 | §1 構造設計編（全項目） |
| 章を書き始める直前 | §2 執筆中編（特に G2-1 / G2-3） |
| 章が完成したと判定する直前 | §3 完成前セルフチェック編（全項目） |
| ドキュメント全体が完成したと判定する直前 | §3 全項目 + §4 ドキュメント種別追加観点 |

### 5.2 ガイドライン違反時の扱い

執筆中にガイドライン違反を発見した場合、**その場で修正** を原則とする。修正困難な場合（構造に深く関わる等）は、ドキュメント末尾の「申し送り事項」に記載し、後続のレビューで対応判断を仰ぐ。

### 5.3 ガイドラインの更新ルール

- 本ガイドラインに新たな観点・改善案がある場合、`improvements/F02-010_レビュー対象成果物の資産性質改善.md` を経由して提案する
- レビューでの指摘から「執筆段階で予防可能だった」と判定された項目は、本ガイドラインへの追加候補として起票する

### 5.5 観点 8（Reader-AI フレッシュ読みテスト）の適用判断基準 `[v2.0 追加]` `[§9.3 由来]`

クロスレビューの観点 8（Reader-AI フレッシュ読みテスト）は、対象ドキュメントの **想定読者の前提知識レベル** に応じて適用要否を判断する:

| 想定読者の前提 | 観点 8 の扱い | 判断根拠 |
|---|---|---|
| **事前文脈なし**（外部公開資料・新規参加者向け資料・初出ドキュメント等） | **必須適用** | フレッシュな読者の理解可否を直接検証する以外に検出が難しい |
| **事前文脈あり**（内部継続作業の計画書・統合報告書・特定読者向けレビュー報告書等） | **除外可** | 観点 1 / 5 / 11 / 13 で代替的に検出可能、Reader Agent 起動コスト削減のメリットあり |

判断基準: G1-1 想定読者像で「事前文脈なし、本ファイルのみ参照」と宣言した場合は **観点 8 必須**。

> **除外時の留意点**: 観点 1 / 5 / 11 / 13 で代替的に検出可能だが、**完全代替には至らない**。Reader-AI 固有の検出能力（執筆者の暗黙前提・指示語の連鎖・複数解釈可能な術語等の可読性問題）は他観点では完全には肩代わりできないため、想定読者像を慎重に判断すること。

> **§9.3 トライアルでの実証**: 観点 8 を除外した v3 でも、執筆ガイドライン適用 + 他観点（9 / 10 / 11 / 13）の組み合わせで v2 比 -14% の指摘減少を達成。観点 8 除外は適切な選択でしたが、これは想定読者が事前文脈を持つ前提（02.99 の継続作業）だったため。

### 5.4 執筆者見解レポートの活用 `[v2.0 追加]`

ドキュメント執筆完了時、執筆者は **執筆者見解レポート** を別ファイルとして作成することを推奨する（§9.3 トライアルでの実証済み運用）。レポートの内容:

| セクション | 記載内容 |
|---|---|
| **執筆過程の所感** | ガイドライン適用しやすさ・困難点 |
| **ガイドライン改善案** | 観点単位での具体的改善提案（次版反映候補） |
| **セルフチェック結果サマリ** | G3-1〜G3-11 の各観点遵守状況、情報欠落チェック結果 |
| **構造的差分の自己分析**（再執筆時） | 旧版との章立て変更点、削除箇所、追加箇所、その理由 |
| **典拠評価**（統合報告書時） | サブタスク報告書 N 件の質・量・整合性・統合のしやすさ |

**ファイル名規則**: `<対象成果物名>_執筆者見解_<日付>.md` または同等

**活用方法**:
1. レビューア（クロスレビューを実施する別 Agent）が執筆者見解を参考資料として読み、執筆意図を把握した上でレビューを行う
2. ガイドライン改善案は次版改訂時の入力として活用
3. 構造的差分の自己分析は、改訂レビュー時の作業指示者判断材料となる

> **理由**: 執筆者の意図が見えていれば、レビューア側が「単なる形式指摘」と「設計意図への反論」を区別しやすく、レビュー収束が早まる。執筆ガイドライン改善のフィードバックループを駆動する仕組みでもある。
