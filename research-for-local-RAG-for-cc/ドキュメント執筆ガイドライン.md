## 0. ガイドラインの位置付けと使い方

### 0.1 ガイドラインとレビュー観点の関係

本ガイドラインは **執筆者がドキュメント作成中に参照する予防チェックリスト** であり、`.claude/templates/cross-review/` のレビュー観点（13 観点）と **対をなす** 関係にあります。

- **執筆段階**（本ガイドライン）: 書く前・書きながら適用する観点
- **レビュー段階**（cross-review テンプレ）: 完成版に対して適用する観点

両者の重複は意図的です。執筆段階で吸収しきれなかった指摘がレビュー段階で発見されることを前提とし、**双方向の品質ループ** を構築します。

### 0.2 適用タイミング

| ドキュメントの段階 | 本ガイドラインの適用箇所 |
|---|---|
| 構造設計（章立て決定） | §1 構造設計編 を全項目適用 |
| 執筆中 | §2 執筆中編 を継続的に意識 |
| 完成直前のセルフチェック | §3 完成前セルフチェック編 を全項目適用 |

### 0.3 観点の出典凡例

各観点の右肩に出典を示します:
- `[doc-coauthoring]`: Anthropic 公式 `anthropics/skills/doc-coauthoring` Skill 由来
- `[internal-comms]`: Anthropic 公式 `anthropics/skills/internal-comms` Skill 由来
- `[Microsoft]`: Microsoft Writing Style Guide（Scannable content 等）由来

- `[Diátaxis]`: Diátaxis Framework 由来
- `[academic-paper-reviewer]`: `Imbad0202/academic-research-skills` 由来

## 1. 構造設計編（書く前に決めること）

### G1-1. 想定読者像の事前宣言 `[doc-coauthoring]` `[internal-comms]`

ドキュメント冒頭またはメタ情報に、想定読者像を 1〜2 文で明示する。

| 項目 | 例 |
|---|---|
| 想定読者の役割 | 「最終承認権限を持つ人間レビューア」「03 設計フェーズ担当 Claude Agent」 |
| 想定読者の前提知識レベル | 「本プロジェクト全体の文脈を持つ前提」「事前文脈なし、本ファイルのみ参照」 |
| 想定読了時間 | 「10〜20 分」「5 分以内」 |

> **理由**: 想定読者の前提知識レベルが明示されていれば、執筆段階で「どこまで前提を書くべきか」「どこから本題に入れるか」の判断基準が明確になる。レビュー段階での「前提知識の明示不足」指摘も予防できる。

### G1-2. ドキュメント全体構成の可視化（目次・冒頭サマリ） `[作業指示者 §9.2]` `[Microsoft]` `[Minto]`

以下の 3 点を必ず満たす:

1. **目次（TOC）の整備** — 章数が 5 を超える、または行数が 100 を超えるドキュメントは目次を必ず置く。各セクション名は **対応するセクションへのリンク** とする
2. **各章の 1 行説明併記** — 目次の各章名の右側に、その章の内容を 1 行で説明する
3. **冒頭サマリ構成** — 報告書系（調査報告書・最終報告書・取りまとめ）は冒頭で「**調査内容 / 調査結果 / 結論・示唆**」のサマリを提示し、その後に各詳細へ繋げる

> **理由**: ボリュームが大きいドキュメントほど構成把握コストが急増する。冒頭で全体像を把握できれば、読者は重要箇所に直接アクセスでき、認知負荷が大幅に下がる。

### G1-3. 文書モードの自意識（Diátaxis） `[Diátaxis]`

各章を執筆する前に、その章が以下のどのモードかを意識する:

| モード | 性質 | 章末スタンス |
|---|---|---|
| **Tutorial** | 段階的に手を動かして学ぶ | 学習成果としての到達点を明示 |
| **How-to** | 特定の目的を達成する手順 | 完了条件を明示 |
| **Reference** | 仕様・カタログ・参照表 | 網羅性と検索性を優先 |
| **Explanation** | 設計意図・背景・理由づけ | 理解促進を優先 |

> **理由**: 「読者が何を求めて読むか」を一意化することで、不要な脱線・冗長を回避できる。特に **報告書は Explanation + Reference の混在が多い** ため、章ごとにモードを意識して書き分けると読みやすい。

### G1-4. 内外参照の相互リンク化 `[作業指示者 §9.2]`

ドキュメント内外の参照は **必ず Markdown リンクとして記載** する:

```markdown
良い例:
- 詳細は [§3.2 採用候補](#32-採用候補) を参照
- 関連: [F02-009](improvements/F02-009_クロスレビュー指摘記載ルールとセルフレビュー観点の規定.md)

悪い例:
- 詳細は §3.2 を参照（リンクなし）
- 関連: F02-009（リンクなし）
```

> **理由**: リンクをクリックするだけで参照先へ飛べるため、レビューア・読者の作業コストがほぼゼロになる。手動辿り作業はレビュー効率を著しく圧迫する。

## 2. 執筆中編（書きながら意識すること）

### G2-1. 結論先出し（BLUF / Pyramid） `[Minto]` `[internal-comms]`

各章・各節の冒頭 1〜2 文で **結論または核となる主張** を先に書く。詳細・根拠は後段に置く。

```markdown
良い例:
## 3.1 採用候補
本フェーズの採用候補は BAAI/bge-m3（埋め込み）+ DuckDB+vss（DB）+ ハイブリッド検索の構成。
理由は §3.1.1〜§3.1.3 で述べる。

悪い例:
## 3.1 採用候補
2026 年初頭から複数の候補を比較検討した。BAAI/bge-m3 は…（結論が章末まで出ない）
```

### G2-2. 短文・短段落（3〜7 行） `[Microsoft]` `[Google]`

- **段落長**: 3〜7 行で区切る
- **文長**: 単純に保つ（1 文に複数の節が入りすぎない）
- **箇条書き化**: 列挙構造の文は箇条書き / 表に変換

> **理由**: 長い段落・長文は目が滑りやすく、重要情報を見落とすリスクが上がる。

### G2-3. パターン化された構造（landmark） `[Microsoft]`

同じ種類の情報は **同じ構造（見出しレベル・記述順）** で書き、読者がパターンで処理できるようにする。

```markdown
良い例（採用候補の各エントリで構造を統一）:
### 3.1.1 BAAI/bge-m3
- ライセンス: MIT
- ストレージ要件: 約 2GB
- 採用根拠: 多言語対応、高精度

### 3.1.2 ruri-v3-310m
- ライセンス: Apache 2.0
- ストレージ要件: 約 0.6GB
- 採用根拠: 日本語特化
```

### G2-4. 前提知識の明示 `[doc-coauthoring]`

ドキュメント執筆中に「これは読者にとって既知か？」を都度問い、暗黙の前提があれば補足する。

| 状況 | 対処 |
|---|---|
| プロジェクト固有の用語 | 初出箇所で 1 行定義を併記 |
| 業界共通用語だが略語 | 初出箇所でフルスペル併記（例: `MCP（Model Context Protocol）`）|
| 引用・参照が前提 | 引用文をその場に残し、参照だけで完結させない |

### G2-5. アクティブボイス・断定の優先 `[internal-comms]` `[Google]`

受動態・婉曲表現が判断を曖昧にしていないかを点検する。

```markdown
良い例:
- 採用する: bge-m3
- 除外する: paraphrase-multilingual（最大 128 トークン制限）

悪い例:
- 採用されるべきと考えられる: bge-m3
- 除外されることが望ましい可能性が高い: paraphrase-multilingual
```

### G2-6. データドリブン（数値・期日・件数） `[internal-comms]`

「効果的」「相当数」のような形容詞は、可能な限り **数値・期日・固有名詞** で置き換える。

```markdown
良い例:
- 02.基礎調査の作業指示者レビューは 2026-05-05 完了、139 指摘収集
- bge-m3 は recall@10 で 91% を達成

悪い例:
- 02.基礎調査のレビューは効果的に完了、相当数の指摘を収集
- bge-m3 は高い精度を達成
```

### G2-7. ジャーゴン判定の手続き化 `[Google]`

略語・専門用語ごとに「想定読者がそのまま読めるか」を判定し、できないなら **定義 or 言い換え** を入れる。

判定手順:
1. その用語を初出時に Google 検索したと仮定し、上位 5 件で意味が即座に取れるか確認
2. 取れない場合は 1 行定義を併記
3. 業界共通用語でも略語は初出フルスペル必須

## 3. 完成前セルフチェック編（出す前に通読チェック）

### G3-1. AI スロップ／前置き句の排除 `[doc-coauthoring]`

完成版を通読し、以下のパターンを **形態素レベルで排除** する:

| 排除対象 | 例 | 対処 |
|---|---|---|
| 中身のない前置き句 | 「近年〜」「重要なのは〜」「以上を踏まえると〜」 | 削除 or 具体的な接続詞に置換 |
| em-dash の連用 | `Aは — Bだが — Cである` | 1 文を 2〜3 文に分割 |
| ハッジ語の頻発 | 「と思われる」「可能性が高い」「と考えられる」 | 断定可能な箇所は断定、不確かな場合のみ残す |
| 単調な文長 | 全文がほぼ同じ長さ | 一部を短文化 or 結合して変化を出す |

> **検出方法**: grep で `近年|重要なのは|以上を踏まえると|と思われる|可能性が高い|と考えられる` を検索し、ヒット箇所を再評価。

### G3-2. 全文「重み検査」（every sentence carries weight） `[doc-coauthoring]`

完成版を通読し、各文に対して以下を問う:

> **「この一文を削除して、情報損失が出るか？」**

- **Yes**: 残す（その文は情報を運んでいる）
- **No**: 削除候補（無くても文書の意味が変わらない）

「No」が一定割合（例: 全文の 10% 超）あれば、冗長過多と判定して圧縮する。

### G3-3. 冗長／矛盾の二重チェック `[doc-coauthoring]`

通読時に以下を発見・除去:
- 同じ主張の重複（章をまたいで似た主張をしていないか）
- 章をまたぐ矛盾（§3.7 と §4 H1 で同じ仮説について異なる表現になっていないか）
- 同じ事実への異なる表記（「02-07」「02.07」「サブタスク 07」のような表記揺れ）

### G3-4. アンビギュイティ（曖昧表現）の検出 `[doc-coauthoring]`

通読時に以下を点検:
- 主語の省略（誰が・何が の主語が明確か）
- 指示語の連鎖（「この」「それ」が何を指すか即座に分かるか）
- 複数解釈可能な術語（同じ語が章ごとに異なる意味で使われていないか）

### G3-5. 主張の Specificity 三点セット（what / where / evidence） `[academic-paper-reviewer]`

主要主張（H2 直下の結論文や箇条書き）ごとに以下を点検:

| 三点 | 確認内容 |
|---|---|
| **What**: 何を主張しているか | 主張が 1 文で抽出可能か |
| **Where**: どこで根拠が示されているか | 該当節・図表・データへのリンクが付いているか |
| **Evidence**: 反証された場合の影響 | 根拠が崩れたときの影響範囲が把握できるか |

3 点が揃わない主張は、執筆段階で根拠補強または主張削除を検討する。

### G3-6. 想定読了時間との乖離点検 `[internal-comms]`

文書冒頭で宣言した想定読了時間（G1-1）に対し、文字数・段落数から実測値を概算し、乖離を点検:

- **想定の +50% 以内**: 許容
- **想定の +50% 超**: 要約セクション追加 or 文書分割を検討
- **想定の 2 倍超**: 構造的な見直しが必要

> **概算ルール**: 日本語は 1 分あたり約 600〜800 文字読める想定（読み物 vs 業務文書で変動）。10〜20 分想定なら 6,000〜16,000 文字が目安。

### G3-7. Devil's Advocate（最強反論の織り込み） `[academic-paper-reviewer]`

主要結論（特に承認判断に影響するもの）について、以下を 1 件ずつ書き残す:

> **「この結論に対する最強の反論は何か？」**

- 反論が **棄却可能** なら: 反論内容と棄却根拠を本文に織り込む
- 反論が **棄却困難** なら: 残存リスクとして承認者に明示

### G3-8. 図表・コードブロックの self-contained 性 `[doc-coauthoring]`

図に頼らず本文だけで意味が通るか確認:
- 図の内容を本文で 1 文要約
- alt-text を付ける
- コードブロックには言語指定を付ける

### G3-9. iteration の収束基準 `[doc-coauthoring]`

修正を繰り返している場合、3 巡連続で実質的な変更がないなら、**「削れるものはないか」を能動的に問う**（増やす方向の慣性をブレーキ）。

### G3-10. リンクアンカーの動作確認

最後に、ドキュメント内のリンクが実際に機能するか確認:
- 内部アンカー: クリックで該当セクションへ飛ぶか
- 外部リンク: パスが正しいか、ファイル名のタイポがないか
- 日本語見出しのアンカー: GitHub プレビュー / VSCode プレビュー / 他ツールで挙動が揃うか（揃わない場合は明示的な HTML アンカー `<a id="..."></a>` を使う）

## 4. ドキュメント種別ごとの追加観点

### 4.1 計画書

- **G1-1 の想定読者像**で「本ドキュメント単独で承認判断ができる」前提か明示
- **G1-2 の冒頭サマリ**で「目的・スコープ・成功条件・打ち切り条件」を提示
- **G3-7 Devil's Advocate** を計画前提・採用案ごとに 1 件ずつ実施

### 4.2 調査報告書（フェーズ報告書 / 統合報告書）

- **G1-2 の冒頭サマリ**は「調査内容 / 調査結果 / 結論・示唆」の 3 部構成（作業指示者 §9.2 由来）
- **G3-5 Specificity 三点セット**を採用候補・除外候補の各エントリに必ず適用
- **G3-9 iteration の収束基準** で「報告書のサイズが膨張気味」なら章末 LEARNING / FOLLOW-UP セクションへの切り出しを検討

### 4.3 レビュー報告書（クロスレビュー / 作業指示者レビュー）

- テンプレート（`.claude/templates/cross-review/`）に従う
- **G1-4 内外参照の相互リンク化** は特に重要（指摘ごとの該当箇所への直接リンク）
- **想定読者は事前知識を持つ前提**で書く（前提知識の明示は最小限で良い）

### 4.4 改訂提案・運用考察ドキュメント

- **G3-7 Devil's Advocate** を改訂方針ごとに 1 件ずつ実施
- 改訂量と効果のバランス・実装難易度を明記
- 既存資産への影響範囲を明記

## 5. ガイドラインの運用ルール

### 5.1 ガイドラインの参照タイミング

| タイミング | 参照範囲 |
|---|---|
| ドキュメント執筆を開始する直前 | §1 構造設計編（全項目） |
| 章を書き始める直前 | §2 執筆中編（特に G2-1 / G2-3） |
| 章が完成したと判定する直前 | §3 完成前セルフチェック編（全項目） |
| ドキュメント全体が完成したと判定する直前 | §3 全項目 + §4 ドキュメント種別追加観点 |

### 5.2 ガイドライン違反時の扱い

執筆中にガイドライン違反を発見した場合、**その場で修正** を原則とする。修正困難な場合（構造に深く関わる等）は、ドキュメント末尾の「申し送り事項」に記載し、後続のレビューで対応判断を仰ぐ。

### 5.3 ガイドラインの更新ルール

- 本ガイドラインに新たな観点・改善案がある場合、`improvements/F02-010_レビュー対象成果物の資産性質改善.md` を経由して提案する
- レビューでの指摘から「執筆段階で予防可能だった」と判定された項目は、本ガイドラインへの追加候補として起票する
