## 背景

Claude Code 公式ドキュメントの効率的な参照を目的として、`claude_code_docs_map`・`llms.txt`・`llms-full.txt` の 3 ファイルを調査・比較した結果のまとめ。  
本調査は local RAG for cc プロジェクトの調査活動中（2026-05-09）に実施。

---

## 主要発見サマリ

本調査（2026-05-09）で確認した主要発見:

- Anthropic は llms.txt 仕様を `/llms.txt` + `/llms-full.txt` 両方で **完全準拠** 実装しており、LLM がトップダウンに段階的詳細化できるアーキテクチャを意図的に設計したものと **推測される（強い推測）**
- `docs_map` は llms.txt の代替ではなく、仕様が提供しない **中間粒度**（見出し階層）を補完する独自拡張と推測される（弱い推測）
- `llms-full.txt` により「フェッチ 1 回で全文取得」戦略が成立し、当初課題だった説明精度弱点は **実質解消**
- 残課題は **(a) llms-full.txt の全文サイズ管理** と **(b) HTML/JSX 混在前処理** の 2 点に集約される
- 本プロジェクトにとって、**ローカル RAG 構築はスクレイピング不要・公式提供のみで完結可能** と確認

> **信頼度ラベルの定義**: 本文書で使用する信頼度表記の意味 — 「確認済み」: 直接検証済みの事実 / 「強い推測」: 複数の観察事実に基づく推論 / 「弱い推測」: 消極的根拠のみに基づく推論 / 「推定」: 間接証拠から計算・推定した値 / 「未確認」: 調査範囲外または未実施。

詳細は各観点セクションおよび末尾「結論サマリ」を参照。

## 全体像: 4 階層構造

```
Layer 1: llms.txt        … 全ページカタログ（URL + 1行説明）
Layer 2: docs_map        … 構造マップ（見出し階層、全カテゴリ対応・URL 数は 114/126）
Layer 3: llms-full.txt   … 全文連結コーパス
Layer 4: 個別 .md        … 単一ページ全文
```

**ナビゲーション設計**: llms.txt をハブとするスター型。

- 個別 `.md` → llms.txt（各ページ冒頭の callout）
- `docs_map` → llms.txt（冒頭案内）
- `llms-full.txt` → 個別 URL（各セクションの `Source: URL`）

> **注**: `llms-full.txt` は llms.txt を直接参照しないが、`Source: URL` で個別 `.md` を指し、個別 `.md` の冒頭 callout から llms.txt へ戻る多段経路（`llms-full.txt` → 個別 URL → 個別 `.md` → llms.txt）が成立しており、`llms.txt` は **すべての参照経路の最終ハブ** として機能する。

## 観点 1: llms.txt はフォーマット仕様か、単なる名称か

**結論: フォーマットルールを持つ emerging standard（事実上の準標準）**

- 提唱者: Jeremy Howard（fast.ai）、2024年9月3日
- GitHub ★2,400+、VitePress/Docusaurus プラグイン等のエコシステムが形成済み
- 公式標準ではなくコミュニティ提案だが、仕様は明確に規定されている

**フォーマットルール**:

| 要素 | 必須／任意 | 内容 |
|---|---|---|
| H1 見出し | **必須** | プロジェクト名 |
| blockquote | 任意 | 短い要約 |
| 本文 | 任意 | 詳細情報 |
| H2 区切りのリスト | 任意 | URL + 説明のリンク群（H2 はオプショナル区切りであり、カテゴリ的グルーピングは仕様上保証されない） |

- "Optional" H2 は「スキップ可能コンテンツ」を示す予約語
- 配置場所: サイトルートの `/llms.txt`
- 仕様は `/llms.txt`（短縮版）と `/llms-full.txt`（フルコンテキスト版）の両方提供を推奨
- robots.txt との差別化: robots.txt = クロール時アクセス制御、llms.txt = **推論時**のキュレーション

**Anthropic の実装**: llms.txt 仕様を `/llms.txt` + `/llms-full.txt` 両方含めて完全準拠。さらに各 `.md` ページから llms.txt への callout による循環参照設計が観察できる → **「LLM がトップダウンに段階的詳細化できるアーキテクチャを意図的に設計したものと推測される（強い推測）」**。

> **推測強度の根拠**: 公式の意図表明（公式ブログ・README 等）への参照は本ドキュメントの調査範囲外で未確認だが、(1) llms.txt 仕様への完全準拠、(2) 各 `.md` から llms.txt への callout 配置の一貫性、(3) `llms-full.txt`（フル版）まで提供している点、の 3 点の観察事実から「意図的設計」と判断できるため **強い推測** と位置付ける（観点 2 の「弱い推測」と区別）。

## 観点 2: docs_map は llms.txt の一つか、別物か

**結論: llms.txt 仕様とは別物。「中間粒度の構造情報」を埋める補完ファイル**

llms.txt 仕様との非適合点:

| 要件 | llms.txt 仕様 | docs_map |
|---|---|---|
| 配置場所 | サイトルート `/llms.txt` | `/docs/en/claude_code_docs_map` |
| フォーマット | H1+blockquote+H2リスト | ページごとの見出し階層ツリー |
| 1エントリの情報 | URL + 1行説明 | URL + 全見出し構造 |
| サイズ感 | 数百行（コンテキスト収容前提） | 3,109行 / 78KB |

docs_map は llms.txt/llms-full.txt が提供しない「中間粒度」を担う：

| ファイル | 提供粒度 |
|---|---|
| llms.txt | URL + 1行説明（最も粗い） |
| docs_map | ページごとの見出し階層（中間） |
| llms-full.txt / 個別 .md | 全文（最も細かい） |

仕様に「中間粒度」の標準形式がないため、Anthropic が独自実装した補完層と推測される（**弱い推測**）。

> **推測強度の根拠**: llms.txt 仕様（H1 + blockquote + H2 リスト）に「中間粒度」の標準形式が規定されていないこと **のみ** が判断材料であり、Anthropic 側の独自実装意図に対する直接の観察事実は乏しい。観点 1 の「強い推測」（複数の観察事実に基づく）に対し、本観点は仕様非適合という消極的根拠のみのため **弱い推測** と位置付ける。

> **注**: この粒度分類は「情報の詳細度」軸での 3 段階整理。「取得単位」軸（=全体像の 4 階層構造）では llms-full.txt（全文連結コーパス）と個別 .md（単一ページ取得）は別階層として区別される。両者の本文コンテンツは実質同一（観点 E 参照）。

## 観点 3: 両者の掲載情報の差異が意味するもの

**結論: カテゴリレベルでは 3 ファイルが同一カバレッジ。差異は URL 数（docs_map 114 < llms.txt 126）と中間粒度の有無に集約**

### カバレッジの比較

| カテゴリ | llms.txt | docs_map | llms-full.txt |
|---|---|---|---|
| Agent SDK（28ページ） | ✓ | ✓ | ✓ ※ |
| リファレンス系 | ✓ | ✓ | ✓ ※ |
| whats-new 週次 changelog | ✓ | ✓ | ✓ ※ |
| ガイド・チュートリアル系 | ✓ | ✓ | ✓ ※ |
| **URL 総数** | **126** | **114** | **126** |

> ※ llms-full.txt の掲載ページ数は `Source: URL` 行カウントで 126 件（llms.txt の URL 数と同数）であることを確認済み。個別ページの網羅性は URL カウントから間接確認（1ページ詳細比較は観点 E 参照）。

> **注**: カテゴリレベルでは全 4 カテゴリが docs_map に収録されているが、URL 総数では docs_map 114 件 < llms.txt 126 件で 12 件の差がある。どのページが docs_map に含まれないかは未確認。

### 差異が意味するもの

**1. docs_map は llms.txt の部分集合（URL レベル）**  
カテゴリレベルでは全カテゴリが docs_map に収録されているが、URL 総数は docs_map 114 件 < llms.txt 126 件で 12 件の差がある。`docs_map URL ⊂ llms.txt URL` の関係が成立している可能性が高く、docs_map の冒頭案内（「llms.txt を先に参照せよ」）の設計意図と整合する。どのページが含まれないかは未確認。

**2. メンテナンスパイプラインの独立性（推測）**  
docs_map は「GitHub Actions で自動生成（日次）」と明記。llms.txt / llms-full.txt は別パイプラインで生成されている可能性が高い（観点 D 参照）。URL 数の差（12 件）がパイプラインの設計的意図によるものかバグかは現時点では判断できない。

## 観点 4: 各ファイルは LLM にとって本当に最適な形か

**結論: 各ファイルは「タスクに応じた使い分けが想定された設計」であり、単一最適解ではない**

| ファイル | LLM 最適性の本質 |
|---|---|
| llms.txt | ナビゲーション最適（小サイズ・高被覆・低詳細） |
| docs_map | 構造把握最適（中サイズ・中詳細・全カテゴリ対応） |
| llms-full.txt | 全文摂取最適（大サイズ・全詳細・全被覆） |
| 個別 .md | ピンポイント取得最適（任意サイズ・1ページ単位） |

### 各ファイルの LLM 最適性評価

**llms.txt**:
- ✓ サイズが小さくコンテキスト収容可能
- ✓ `.md` URL でクリーンなマークダウン取得可能
- △ 1行説明では類似ページの判別が困難（例: `hooks.md` vs `hooks-guide.md`）
- ✗ 実質的なカテゴリナビゲーションがない（H2 はあるが、llms.txt 仕様上カテゴリ的グルーピングは保証されず、絞り込みには弱い）
- ✗ ページ間の依存関係が示されない

**docs_map**:
- ✓ 見出し階層でページ内ナビゲーションが精緻化できる
- ✓ セクション分類（Getting started / Agents 等）がある
- ✗ 78KB / 3109行でコンテキストを大きく圧迫（截断リスク）
- ✗ 各ページに説明がなく「なぜそのページか」の判断ができない

**llms-full.txt**:
- ✓ 全文が収録されているため参照漏れがない
- ✓ ページ区切り（`# タイトル` + `Source: URL`）が明確でチャンク化しやすい
- ✗ 推定 MB 級のサイズで直接コンテキスト注入は困難
- ✗ Markdown + HTML/JSX 混在により前処理が必要

## 追加観点

### 観点 A: llms.txt をハブとするスター型ナビゲーションの設計意図解釈

冒頭「全体像: 4 階層構造」のナビゲーション設計（多段経路の最終ハブが llms.txt）を踏まえ、本観点ではその **設計意図** を独立に解釈する。

すべての参照経路（個別 `.md` → llms.txt の callout、`docs_map` → llms.txt の冒頭案内、`llms-full.txt` → 個別 URL → 個別 `.md` → llms.txt）が最終的に llms.txt へ収束する設計は、LLM が「現在地」を見失わないための配慮と解釈できる。どの粒度（カタログ / 構造 / 全文 / 単一ページ）から読み始めても、llms.txt のカタログに戻ることで全体俯瞰を再取得できる構造になっている。

### 観点 B: llms-full.txt が「単一ファイル摂取戦略」を成立させる

llms-full.txt の存在により、「フェッチ 1 回で全ドキュメントを取得する」という戦略が現実的選択肢になった。部分取得ミスのリスクがゼロになり、ローカルキャッシュを 1 ファイル管理で完結できる。

### 観点 C: 3 ファイル構造が RAG アーキテクチャと同型

| RAG コンポーネント | Anthropic Docs での対応 |
|---|---|
| Index / Vector store の素材 | `llms.txt`（URL + サマリ） |
| Document corpus | `llms-full.txt`（全文連結） |
| Chunk metadata | `docs_map`（見出し階層） |
| Source documents | 個別 `.md` ページ |

本プロジェクト（local RAG for cc）にとって、**RAG 構築に必要な素材が公式提供のみで完結**することを意味する重要な発見。

### 観点 D: 3 ファイルのパイプライン独立性と相互検証可能性

#### D-1: 独立パイプライン仮説

3 ファイル（`llms.txt` / `docs_map` / `llms-full.txt`）は独立パイプラインで生成されている可能性が高い（推測）。docs_map は GitHub Actions による日次自動生成と明記されており、llms.txt / llms-full.txt は別パイプラインで生成されている可能性が高い。

> 独立性が成立する場合、各ファイルは互いに **クロスチェック対象** として機能し、後段（D-2）の包含関係チェックを「異常検知」として位置付けられる（同一パイプラインなら単一バグで全ファイル同時崩壊し得るため、包含関係維持自体は異常検知の意味を持たない）。

#### D-2: 包含関係チェック（運用上の品質監視機能）

包含関係チェック自体は独立パイプライン仮説の真偽に関わらず有用だが、D-1 の独立性が成立する場合に「Anthropic 側パイプライン障害の早期検知」としての意味が強まる。

- `llms.txt URL ≈ llms-full.txt セクション URL`（URL 数 126 件で同数を確認済み）
- `docs_map URL ⊂ llms.txt URL`（URL 数は 114 < 126 で推定。URL 単位の照合は未実施）

### 観点 E: llms-full.txt と個別 .md の本文コンテンツは実質同一（確認済み）

overview ページを対象にした直接比較（llms-full.txt の該当セクションを抽出 vs `overview.md` を取得）により、以下を確認:

| 要素 | 個別 .md | llms-full.txt |
|---|---|---|
| Documentation Index callout | あり（サーバー注入） | なし |
| H1 直後の blockquote 説明文 | あり（front matter から注入） | なし |
| 内部リンクのパスプレフィックス | `/en/...` | `/docs/en/...` |
| 本文テキスト・コードサンプル・表 | **同一** | **同一** |

**結論**: 本文コンテンツは実質同一（確認済み）。差異はサーバー注入メタデータ（callout・blockquote）と内部リンクのパスプレフィックスのみ。

この確認により、**llms-full.txt は全 126 ページの個別 .md を結合したものと実質等価** と言える。RAG コーパスとして llms-full.txt を用いれば、個別 .md を 126 回フェッチする手間なく同等の本文コンテンツを取得できる。

## 課題・弱点の再評価

| 以前指摘した弱点 | llms-full.txt による緩和度 |
|---|---|
| docs_map のサイズ過大（78KB） | **緩和なし**（docs_map 自体は不変。ただし代替手段が成立） |
| llms.txt の説明精度不足（1行） | **大幅緩和**（llms-full.txt で全文補完可能） |
| HTML/JSX 混在 | **緩和なし**（llms-full.txt も同様の問題を引き継ぐ） |
| 全文サイズの取り扱い | **やや悪化**（llms-full.txt は MB 級、前処理が必要） |

> **注**: 当初「docs_map の Agent SDK 欠落」として指摘していた弱点は、後の確認で誤認と判明（docs_map にも Agent SDK・リファレンス系・whats-new の全カテゴリが収録されていることを確認済み）。弱点として存在しなかったため上表から除外。

**総括**: 説明精度弱点は llms-full.txt により実質解消。残課題は **(a) llms-full.txt の全文サイズ管理** と **(b) HTML/JSX 混在の前処理** の 2 点に集約される。

## 効果的な活用方法

### 活用方法 1: セッション開始時に llms.txt を必須コンテキスト注入

Claude Code 公式機能を調査する前に llms.txt を参照し、候補ページを特定してから個別フェッチする。サイズが小さく（約 130 エントリ）コンテキストコストが低い。F02-001 で発生した「auto-mode-config.md の発見漏れ」を原理的に防止できる。

### 活用方法 2: 候補数に応じた分岐フェッチ

```
Step 1: llms.txt で候補 URL を絞り込む
Step 2: 候補数で分岐
  1〜3 ページ  → 個別 .md を直接フェッチ
  4〜10 ページ → docs_map で構造把握 → 個別 .md
  11+ ページ  → llms-full.txt 一括取得
```

### 活用方法 3: llms-full.txt をローカル RAG コーパスとして活用

- **チャンク分割**: `# ページタイトル` + `Source: URL` でページ単位一次分割 → 大ページのみ H2/H3 で二次分割
- **メタデータ**: `Source: URL` を保持 + llms.txt サマリを結合して補強
- **更新検出**: whats-new セクションの差分検出 → 変更ページのみ再埋め込み
- **構造補強**: docs_map の見出し階層をチャンクのナビゲーション情報として注入

### 活用方法 4: `.md` 直接 URL の積極活用

特定ページの最新版取得は `https://code.claude.com/docs/en/{page-name}.md` を直接構築してフェッチ。クリーンなマークダウンを確実に取得できる。

### 活用方法 5: whats-new で freshness 確認（知識カットオフ補完）

llms.txt の `whats-new/2026-wXX.md` リンクを参照し、モデルの知識カットオフ後の機能変化を確認する。llms-full.txt にも whats-new セクションが同梱されるため、ローカル corpus 内で常に最新 changelog を参照可能。

### 活用方法 6: 用途別ファイル選択マトリクス

> ※ Agent SDK・hooks・MCP 等の特定機能調査は「特定機能の詳細調査」行を参照（機能依存の特別行は廃止）。

| タスク | 推奨ファイル |
|---|---|

| 特定機能の詳細調査 | 個別 .md（llms.txt で URL 特定後） |

| changelog / 最新機能確認 | llms-full.txt の whats-new セクション |

### 活用方法 7: 3 ファイルのクロスバリデーション

`docs_map URL ⊂ llms.txt URL` および `llms.txt URL ≈ llms-full.txt セクション URL` を定期チェックし、Anthropic 側のパイプライン障害を早期検知する。

### 活用方法 8: コンテキスト予算別の取得戦略

| 予算規模 | 戦略 |
|---|---|
| 小（数千 token） | llms.txt のみ + 必要時に個別 .md |
| 中（数万 token） | llms.txt + docs_map + 個別 .md 数ページ |
| 大（10 万+ token） | llms-full.txt 一括投入 |
| ローカル RAG 利用時 | corpus は llms-full.txt から構築済み、セッション内では検索結果チャンクのみ注入 |

### 活用方法 9: HTML/JSX 前処理パイプラインの集約

**根拠**: 観点 4 / 課題・弱点再評価に基づく。

llms-full.txt と個別 `.md` の双方に残る HTML/JSX 混在問題（残課題 (b)）に対し、ローカル RAG 投入前の **単一の前処理パイプライン**（HTML/JSX 除去 → 純 Markdown 化スクリプト）を構築し、コーパス取得経路によらず常に同じ前処理を経由させる。これにより、ファイル選択（llms-full.txt 一括 vs 個別 .md フェッチ）の違いに依らずコーパス品質が一元管理できる。

### 活用方法 10: docs_map をチャンクメタデータとしてベクトル検索結果に注入

**根拠**: 観点 C / 観点 2 に基づく。

観点 C で示した「docs_map = Chunk metadata」の対応関係を実装に落とし込み、ベクトル検索でヒットしたチャンクに **docs_map から該当ページの見出し階層** を結合してメタ情報として LLM に供給する。LLM はチャンクの「文書内位置」を把握しやすくなり、回答生成時の参照精度が上がる。docs_map のサイズ過大問題（78KB）はインデックス構築時のみ全件読み込み、検索時は該当ページ分だけを抽出することで実運用上の影響を回避できる。

### 活用方法 11: パイプライン整合性ヘルスチェックの自動化

**根拠**: 観点 D（D-2 包含関係チェック）/ 活用方法 7（既存）に基づく。

観点 D の D-2 で提示した相互検証可能性を運用に組み込み、URL 数照合（`llms.txt 126 件` ≈ `llms-full.txt セクション URL 数`、`docs_map URL ⊂ llms.txt URL`）を **cron / CI で日次自動チェック** する仕組みを RAG 構築運用に組み込む。差異が閾値（例: ±2 件）を超えたら Anthropic 側パイプライン障害の可能性として通知。手動チェック（活用方法 7）の自動化版に位置づく。

### 活用方法 12: whats-new 起点のインクリメンタル再埋め込み

**根拠**: 観点 E / 活用方法 5（既存）に基づく。

観点 E で確認した「llms-full.txt と個別 `.md` の本文同一性」を活かし、whats-new セクションで言及された変更ページの URL を抽出 → **対応する個別 `.md` のみを再取得** → 該当チャンクのみ再埋め込み、というインクリメンタル更新フローを構築する。llms-full.txt 全体の再ダウンロード・再埋め込みよりコストが大幅に低く、ローカル RAG コーパスの freshness を低コストで維持できる。

### 活用方法 13: 個別 `.md` の URL パターンを活用したオンデマンド全文補強

**根拠**: 観点 E / 活用方法 4（既存）に基づく。

観点 E で確認した「個別 `.md` には Documentation Index callout や blockquote 説明文が含まれる」差異を逆手に取り、ベクトル検索でヒットしたチャンクの `Source: URL` から `https://code.claude.com/docs/en/{page-name}.md` を自動構築し、**LLM が判断材料として callout / blockquote を必要としたときだけオンデマンド取得** する。llms-full.txt キャッシュの欠落要素（サーバー注入メタデータ）をオンデマンドで補強できる。
