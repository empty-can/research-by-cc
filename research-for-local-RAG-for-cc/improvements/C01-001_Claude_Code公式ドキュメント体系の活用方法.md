# C01-001 Claude Code 公式ドキュメント体系の活用方法

## 1. はじめに

### 1.1 要改善点概要

C01 相談（`consultation/C01-Claude_Code_docs体系分析-20260509/`）にて、Claude Code 公式ドキュメント体系（`llms.txt` / `docs_map` / `llms-full.txt` / 個別 `.md`）の調査・分析・議論を実施。観点 C「3 ファイル構造が RAG アーキテクチャと同型」を含む 13 の活用方法を整理した結果、本プロジェクト（local RAG for cc）の後続フェーズおよび他 research-for-xxx プロジェクトに横断的に適用可能な参照戦略・RAG 構築指針が得られた。

これらの活用方法を **クロージング時の棚卸対象として明示記録** し、本プロジェクト内での正式採用判断（ルート CLAUDE.md / `.claude/rules/` への昇格判断、ローカル RAG 設計への組み込み判断、フェーズごとの参照戦略の規約化判断）を漏れなく実施できる体制を確立する。

## 2. 発生事象の整理

### 2.1 発生事象（ナレッジ識別の経緯）

2026-05-09 の C01 相談で以下を確認・確立:

- **観点 C: 3 ファイル構造が RAG アーキテクチャと同型** — `llms.txt` = Index、`llms-full.txt` = Document corpus、`docs_map` = Chunk metadata、個別 `.md` = Source documents
- **結論サマリ**: 「ローカル RAG 構築はスクレイピング不要・公式提供のみで完結可能」
- **活用方法 1〜13**: セッション開始時の必須注入、候補数別分岐フェッチ、ローカル RAG コーパス活用、`.md` 直接 URL 活用、whats-new による freshness 確認、用途別ファイル選択マトリクス、3 ファイルクロスバリデーション、コンテキスト予算別取得戦略、HTML/JSX 前処理パイプライン集約、docs_map メタデータ注入、パイプライン整合性ヘルスチェック、whats-new 起点インクリメンタル再埋め込み、個別 `.md` URL パターンを活用したオンデマンド全文補強

詳細は `consultation/C01-Claude_Code_docs体系分析-20260509/Claude_Code_docs体系分析.md` を参照。

### 2.2 発生経緯

1. **2026-05-09**: C01 相談着手。`llms.txt` / `docs_map` / `llms-full.txt` / 個別 `.md` の 4 階層構造を分析、論理整合性・実用性の 2 軸クロスレビュー（Round 3 まで実施）を経て本紙 0.9 版完成
2. **2026-05-10**: C01 相談中に、本要改善点として「クロージング時棚卸対象化」を起票

## 3. 採用判断対象

> 本要改善点は「発生事象に対する原因分析・再発防止」型ではなく、「相談で確立されたナレッジの正式採用判断」型のため、雛型 §3 原因分析・§4 同件調査は該当度が低く省略する。代わりに本節で **クロージング時に判断すべき採用候補** を整理する。

### 3.1 採用候補（クロージング時に判断）

| # | 採用候補 | 配置先（採用時） | 期待効果 |
|---|---|---|---|
| A | 活用方法 1「セッション開始時に llms.txt 必須コンテキスト注入」のルール化 | ルート CLAUDE.md または `.claude/rules/` | 公式機能発見漏れ（F02-001 類）の原理的防止 |
| B | 活用方法 2「候補数に応じた分岐フェッチ戦略」のルール化 | 同上 | 不要な大型ファイル取得によるコンテキスト消費抑制 |
| C | 活用方法 3「llms-full.txt をローカル RAG コーパスとして活用」の本プロジェクト設計への組み込み | `reports/03.ローカルRAG設計/` 配下 | 本プロジェクトの主要設計判断材料として直接活用 |
| D | 活用方法 4「`.md` 直接 URL の積極活用」のルール化 | 上記 A/B と同じ場所 | 個別ページ取得時の確実性向上 |
| E | 活用方法 9〜13（実装系活用方法）のフィジビリティ検証対象化 | `reports/04.フィジビリティ検証/` 配下に検証パターンとして追加 | パイプライン整合性チェック・インクリメンタル再埋め込み等の実装可能性確認 |

### 3.2 採用判断の前提

- 各候補の本格採用判断は、後続フェーズ（03〜05）で実証データを蓄積した上でクロージング時に確定する
- 一部候補（A・B 等）は後続フェーズの実作業に先行適用してもよい（実証データ蓄積の機会となる）

## 4. 特記事項/補足事項

- 本要改善点は **C プレフィックス（相談由来）** として起票された最初の要改善点。F プレフィックス（フェーズ振り返り由来）と並列扱い
- C01 相談本紙 v0.9 の 13 活用方法は論理整合性・実用性クロスレビュー Round 3 を経て確立されているため、本要改善点の採用判断において追加検証は基本不要（実装系候補のみフィジビリティ検証対象）
- 関連派生検討: C01 相談の延長として「ローカル文書（ハマりどころ.md 等）への llms.txt スタイル簡易 RAG 適用」「SQL ベース簡易 RAG 構築フロー（SQLite + LIKE + メタデータフィルタ）」が議論中。これらの結論次第で本要改善点の採用候補に追加される可能性あり
