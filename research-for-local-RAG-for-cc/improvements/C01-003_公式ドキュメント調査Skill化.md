# C01-003 公式ドキュメント調査 Skill / Function Calling 化

## 1. はじめに

### 1.1 要改善点概要

C01 相談で確立した「Anthropic 公式ドキュメント調査の手順（暫定ルール）」（ルート CLAUDE.md 参照）は、現時点でローカル DL 済みファイル（`llms.txt` / `llms-full.txt` / `docs_map`）を直接 Grep / Read する手順を CLAUDE.md 本文に記述している。

しかし、本リポジトリでは将来的に以下のインフラ進化が予定されている:

1. **Step 1 (本ブランチでの設計済)**: SQLite + FTS5 trigram ベースの簡易 RAG 構築（別紙_llms.txt思想に基づく簡易RAG構築検討.md 参照）→ ローカルファイル Grep ではなく `sqlite3` クエリで検索する手順に変わる
2. **Step 2 (本調査活動の本来の目的)**: 本格的なベクトル RAG 構築 → MCP サーバ経由の検索に変わる

進化のたびに CLAUDE.md 本文を書き換えるのは非効率かつ事故リスク（CLAUDE.md は全セッション auto-load されるため、文言ミスが全体影響）。**調査手順を Skill / Function Calling として抽象化** し、CLAUDE.md は「公式ドキュメント調査時はこの Skill を使え」という最小記述に留めることで、バックエンド進化に対するスケーラビリティを確保する。

## 2. 発生事象の整理

### 2.1 発生事象（ナレッジ識別の経緯）

2026-05-10、C01 相談中に作業指示者から以下の指摘:

> 一旦別ブランチで追って実装することにした簡易 RAG 構築後や、本調査活動終了後に本格的な構成の RAG ができた際には、ローカルの DL 済みファイルではなく、`sqlite` コマンドを使ったり、RAG にアクセスする MCP サーバーを経由するよう、検索手順も変更になる可能性があります。そのたびにルール（素直に書くとしたら CLAUDE.md？）の文言を修正するのは非効率だと思うので、公式情報を調査する Skill を作成し、その中に、Lazy 条件や具体的な調査手順（該当しない場合には WebFetch を使う）といった内容を記述する、あるいはそれを処理として実装した Function Calling スクリプトを呼ぶことにする、というのが、RAG を含めたナレッジの管理の仕組みの変化に対しても一番スケールする対応ではないか

メインセッション Claude（Opus）も同意。Skill / Function Calling 化により、CLAUDE.md の文言を変えずにバックエンドを進化させられる構造を整備する方針として記録。

### 2.2 発生経緯

1. **2026-05-09**: C01 相談本紙で活用方法 1〜13 を整理（活用方法 1「セッション開始時に llms.txt 必須コンテキスト注入」等）
2. **2026-05-10**: C01-001 起票時、採用候補 A として「llms.txt 必須注入のルール化」を記載
3. **2026-05-10**: 作業指示者から条件記述（lazy / state-conditional）+ Skill 化の提案 → CLAUDE.md 暫定ルール追加と並行で本要改善点を起票

## 3. 採用判断対象

> 本要改善点は「発生事象に対する原因分析・再発防止」型ではなく、「将来の構造改善方針の整理」型のため、雛型 §3 原因分析・§4 同件調査は該当度が低く省略する。代わりに本節で **クロージング時に判断すべき採用候補** を整理する。

### 3.2 採用判断の前提とタイミング

- **本要改善点の本格対処タイミングは、簡易 RAG（SQLite + FTS5）実装完了後** が適切。実装前に Skill 化を進めると、抽象化対象のバックエンドが「ローカルファイル」1 つしかないため、抽象化の有り難みが薄い
- 簡易 RAG 完成後、Skill が「ローカルファイル + sqlite」の 2 バックエンドを抽象化する形で初版作成 → 本格 RAG 完成時に「ローカルファイル + sqlite + MCP」の 3 バックエンドへ拡張、という段階的整備が現実的
- C01-001 採用候補 A（llms.txt 必須注入のルール化）の **HOW（実装方法）** が本要改善点。両者を統合実装するのが経済的

## 4. 特記事項/補足事項

- 本要改善点は、C01-001（WHAT を定義）と C01-002（CLI ツール存在確認の一般原則）の両方と密接に関係する。C01-003 採用時には両者との整合確認が必要
- Skill の auto-invoke 可否は description 品質に依存する。「Anthropic 公式ドキュメントを調査する」「Claude Code の機能を調べる」「Claude API の仕様を確認する」等、複数の意図表現にマッチする description 設計が必要
- 本要改善点の延長として、`Function Calling` スクリプトのライブラリ化（複数公式ドキュメントソース対応）も検討余地あり
