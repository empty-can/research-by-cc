# F02-013 なぜなぜ分析プロセスの改善検討

## 1. はじめに

### 1.1 要改善点概要

5-whys スキル本体（`.claude/skills/5-whys/SKILL.md`）・要改善点別紙雛型（`improvements/【雛型】Fxx-xxx_要改善点名.md`）・なぜなぜ分析を Agent に委任する際のプロンプト構成のいずれにも、(a) 同件調査の **観点抽象化** の手順、(b) 対応策策定前段としての **公式機能・設定の網羅確認** ステップ、(c) 対応案評価軸として **実現可能性 = 網羅性確保** を必須化する仕組み、が組み込まれていない。このため、なぜなぜ分析の品質が担当 Claude（モデル・委任プロンプト・観点設計の判断）の経験値に強く依存し、Sonnet 担当時のみならず Opus 担当時にも品質ばらつきが発生する構造的問題がある。

具体的な発覚事象として、F02-001（background Agent の Write 権限設定漏れ）のなぜなぜ分析実施時に、(1) Sonnet 担当の §4 同件調査が事象具体（Write/Edit 限定）に縛られ抽象化されていなかった、(2) §5 対応案に「実現可能性=網羅性確保」の評価軸が抜けていた、(3) Opus 再実施でも公式機能網羅確認が出発点になっておらず `auto` モードのプラン要件や read-only 既定認識を見落としていた、という 3 つのギャップが連続発覚した。

## 2. 発生事象の整理

### 2.1 発生事象

2026-05-06 に F02-001 / F02-003 のなぜなぜ分析を Agent 並列で実施した際、以下のギャップが連続発覚した:

#### ギャップ 1: §4 同件調査の観点が事象具体に縛られた（F02-001 Sonnet 担当）

- F02-001 別紙の §4 同件調査が「Write/Edit 権限」に範囲を限定して記述されていた
- 根本原因の構造（=「sub-agent / background が permission prompt 経由で実行中復旧できない制約に対する事前 allow 必須」）から逆算すれば「あらゆる権限・ツール・コマンド・MCP 命令」を範囲とすべきだった
- 作業指示者からの確認指摘で発覚

#### ギャップ 2: §5 対応案に実現可能性=網羅性確保の評価軸が抜けていた（F02-001 Sonnet 担当）

- §5 各案の Cons 列が「配置先・運用面の懸念」に留まり、根本対策が依存する「事前列挙の網羅性確保」という本質的実現可能性懸念に踏み込んでいなかった
- 作業指示者からの確認指摘で発覚

#### ギャップ 3: Opus 再実施でも公式機能網羅確認が出発点になっていなかった（F02-001 Opus 担当）

- Opus Agent による §3 品質チェック + §4・§5 再実施でも、**Claude の設定や機能で改善できるか**（公式機能網羅確認）の観点が対応策策定の出発点になっていなかった
- §5 案 3 として `permissionMode` 切替に言及はあったが、プラン要件まで踏まえた `auto` モード利用可否判定や、read-only commands の既定認識（公式 permissions ページ記載）の検出はされていなかった
- 作業指示者の追加指摘と、メインセッションでの公式ドキュメント確認（permissions / permission-modes / sub-agents 各ページ）で初めて浮上

### 2.2 発生経緯

1. **F02-001 別紙作成（2026-05-06、Sonnet Agent）**: 5-whys スキルを適用、別紙雛型に沿って初版作成
2. **作業指示者レビュー (1)**: ギャップ 1 + 2 を指摘
3. **F02-001 別紙の §3 品質チェック + §4・§5 再実施（2026-05-06、Opus Agent）**: 観点抽象化と実現可能性観点追加で更新
4. **作業指示者レビュー (2)**: ギャップ 3 を指摘（Claude の公式機能・設定で改善できるかの確認漏れ）
5. **公式ドキュメント確認（2026-05-06、メインセッション）**: `auto` モード（プラン要件: Max/Team/Enterprise/API のみ、Pro 不可）、read-only commands の既定認識（cd / wc / git show / git blame 等は組み込みで prompt 不要）、`afea8b8` 重複疑義などが浮上
6. **F02-013 起票決定**: なぜなぜ分析プロセス自体の改善検討を本要改善点として分離管理（F02-001 採用案確定とは独立）

## 3. 原因分析

### 3.1 直接原因

以下の複数原因が同時に作用した:

1. **委任プロンプト側の指示不足**: メインセッション（私）が Sonnet / Opus 各 Agent への委任プロンプトで以下を明示指示していなかった
   - 観点抽象化（同件調査範囲を根本原因の構造から逆算する）
   - 公式機能網羅確認を対応策策定の出発点にする
   - 実現可能性 = 網羅性確保を Cons 列の必須評価軸とする

2. **5-whys スキル本体の構造的欠落**:
   - 同件調査の **観点設計** の手順が明示されていない（雛型 §4 と接続するメタ手順がない）
   - 「フェーズ 5: 対策を定義する」に「対策定義の前段としての既存ソリューション網羅確認」ステップが含まれていない
   - 評価軸（即時対応・予防措置・検出メカニズム）に「実現可能性 = 網羅性確保」が含まれていない
   - 落とし穴に「事象具体に範囲を縛る」「公式機能を確認せず独自対策を案出する」が含まれていない

3. **別紙雛型の構造的欠落**:
   - §4 同件調査の説明文が「同件・類件事象を調査する」のみで、観点抽象化を求めていない
   - §5 再発防止策の表形式で Pros/Cons 列に評価軸の必須項目（実現可能性 = 網羅性確保等）が指定されていない
   - §3.1 直接原因の説明文に「複数項目列挙」「仕様事実 vs プロセス事実の分離」を促す記述がない（Opus が F02-001 §3 品質チェックで指摘した構造的弱さ）

4. **§3 で公式ドキュメント参照したことが §5 での「確認済み感」を生んだ可能性**: Why Chain の証拠として公式ドキュメントを引用したことで、Agent 内部で「公式参照は完了」と認識し、§5 の対応策策定で別の角度（プロセス改善・運用工夫）に意識が流れた構造的バイアスがあった可能性

### 5.2 共通の留意事項

- 改善案 A〜E は相互排他ではない。複数案を組み合わせて実装する想定。特に **A + B + C + E は同時実装で相乗効果が期待される**（A が観点設計の型を、B がチェックを、C が雛型での強制を、E が公式機能確認の必須化を提供し、四層で観点設計と対応策策定の品質を担保）
- D は補助的位置付け。A〜C/E のいずれかが本実装される場合に追加すれば足りる
- 採用案の最終決定はクロージング時に再評価する。本要改善点の対処着手時に `/5-whys` を再帰的に適用し、新たな改善案・修正案が浮上する可能性も考慮する

## 6. 特記事項/補足事項

- **クロージング時判断とした理由**: 本調査活動は研究フェーズであり、なぜなぜ分析の実施件数自体が現状フェーズ 02 振り返りで起票された 13 件のみ。実証データが少ない状態で 5-whys スキル / 雛型に踏み込んだ改修を行うと、後続フェーズ（03 設計・04 フィジビリティ・05 有効性検証）でさらに別の改善観点が発覚した場合に再改修が必要になる。クロージングフェーズで全要改善点の分析を一通り実施した上で、共通改善観点を集約して本格対処する方が ROI が高いと作業指示者と合意（2026-05-06）。
- **F02-001 採用案決定時の議論記録（参考）**: F02-001 別紙 §5.2 で確定された採用案（暫定: 検知ベース対処療法継続 / 本格対処: §5.2 多層防御を `.claude/rules/agent-permission-runtime.md` に集約、クロージング時判断）の決定過程で、本要改善点の改善案 A〜E が並行的に識別された。F02-001 採用案と F02-013 改善案は独立だが、F02-013 の改善案 E（公式機能網羅確認の必須化）が将来実装されれば、F02-001 のような事象は分析の出発点で公式機能解決策が検討されるため、現状のような後発検出（メインセッションの WebFetch 確認）に依存しなくなる。
- **改善案 A への作業指示者批評（2026-05-06）の重要性**: 構文テンプレートのスロット（特に発動主体）を適切に埋められるかは未保証という指摘は、改善案 A 単独の有効性を直接否定するものではないが、「テンプレートを提供しても使い方の判断が必要」という構造的限界を示している。この批評は対処着手時に他の改善案との組み合わせ（B/C/E との同時実装）の根拠として再活用する。
- **本要改善点のスコープは「横断」**: 5-whys スキル本体・別紙雛型・委任プロンプトのいずれもワークスペース全体および全 `research-for-xxx/` プロジェクトに影響する。解決策確定後はルート `.claude/skills/` および `.claude/rules/` への配置を維持する（プロジェクト固有 CLAUDE.md には配置しない）。
- **改善案 E への気付き例の追加（2026-05-07）**: F02-001 別紙の作業指示者レビュー過程で、Remote Control 経由のスマホ Claude アプリで Agent permission prompt を承認できる事実が事後判明。これは sub-agent 実行中 prompt 経由復帰不可という仕様制約に対する公式の代替インターフェースであり、F02-001 のなぜなぜ分析時には見落とされていた。**この経緯は改善案 E の必要性を裏付ける具体事例**: 仕様制約として確定した事項に対しても、その制約を回避する公式手段（代替インターフェース・代替ワークフロー・代替運用パターン等）の有無を改めて調査する観点（改善案 E の (d)）が組み込まれていれば、Remote Control の存在は分析時点で対応策選択肢に上がっていた可能性が高い。同観点は本プロジェクトの調査・検証活動全般（特に 04 フィジビリティ検証 / 05 有効性検証で仕様制約に直面する場面）でも有用なため、本要改善点クロージング時判断とは別途、`research-for-local-RAG-for-cc/ハマりどころ.md` §2.9「調査・分析プロセス（仕様制約に直面した際の調査観点等）」にも 2026-05-07 付で記録した（本プロジェクト終了時にルート CLAUDE.md または `.claude/rules/` への昇格を検討）。
