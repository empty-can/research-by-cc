# F02-003 CRITICAL 級欠落のセルフレビュー検出漏れ（H1 多面判定の欠落）

## 1. はじめに

### 1.1 要改善点概要

02.99 最終基礎調査報告 v1.0 において、計画書 §4 で定義された H1 仮説（「コードベース系データには Filesystem Exploration RAG（grep/glob）の方がベクトル検索より精度・速度で有利」）の判定が、サブタスク 07 で得られた定量値（精度・速度・トークン効率の 3 軸）から多面的な結論が導けるにもかかわらず、報告書では「対立軸が補正された」という単一表現に潰されており、**計画書の H1 命題に対する明示的な判定が下されていない状態**で完成・セルフレビュー完了とされた。この CRITICAL 級の欠落（C1）が、後続のクロスレビュー（論理整合性、Opus、2026-05-03）で初めて発覚し、v1.1 改訂・Phase X.5 振り返りまで持ち越された。

## 2. 発生事象の整理

### 2.1 発生事象

2026-05-03 に実施されたクロスレビュー（論理整合性観点、Opus 独立第三者）にて、CRITICAL 指摘 C1 が検出された：

> **C1**: H1 仮説の「現時点ステータス」評価が、計画書の H1 命題に対する判定として未解決のまま残っている

具体内容：

1. 計画書 §4 H1 命題は「コードベース系データには Filesystem Exploration RAG（grep/glob）の方がベクトル検索より精度・速度で有利」という明確な命題
2. 99 報告書 §2.3 / §4 H1 では現時点ステータスを「対立軸が補正された（grep/glob 単独 vs 汎用ベクトルではなく、コードグラフ+シンボル検索 vs 汎用ベクトル）」と単一文で済ませており、H1 そのものに対する判定が下されていない
3. しかし、サブタスク 07 §4 では Codebase-Memory 論文（2026-03）を引用して定量値（file-explorer: 92%、Codebase-Memory: 83%、grep p50 <0.02s、トークン 1/10 等）を報告しており、**精度・速度・トークン効率のそれぞれで異なる結論が導出可能**な状態にあった
4. 計画書 §5.2 完了条件「各仮説（H0〜H5）の現時点の検証状況が整理されていること」に対するカバレッジ欠落が成立

レビューイ（執筆者である Claude Opus 4.7）自身が C1 に対して「全面的に同意する」「多面判定への書き換えは元データから素直に導ける」と回答しており、**追加調査・追加仮定なしに執筆段階で多面判定化できた内容が、セルフレビューでは検出されなかった**ことが確認できる。

C1 修正案として精度面・速度面・トークン効率面・対立軸補正の 4 軸多面判定への書き換えが採用され、v1.1 で対応済み。本要改善点は「なぜ執筆時およびセルフレビューで多面判定欠落を検出できなかったか」を扱う。

## 3. 原因分析

### 3.1 直接原因

H1 多面判定欠落および欠落のセルフレビュー検出漏れを引き起こした直接原因として、以下を識別する：

1. **執筆時の観点抜け（多面判定の網羅性チェック未実施）**
   - サブタスク 07 由来の H1 軸補正という新発見の取り扱いに執筆者の意識が集中し、計画書 §4 H1 命題（精度・速度の優劣判定）に対する判定軸の網羅性が点検されないまま単一表現に潰された
   - 「対立軸が補正された」という表現は新発見のニュアンスを伝える上では適切だが、計画書命題への直接回答としては情報量不足

2. **セルフレビューでの観点不足（計画書命題逆引きチェック未実施）**
   - セルフレビューは「報告書内部の論理整合」「新発見の取り扱い妥当性」が主観点となり、**「計画書で定義された各仮説・命題に対する明示的判定が完結しているか」という逆引きチェックが組み込まれていなかった**
   - 計画書 §5.2 完了条件「各仮説（H0〜H5）の現時点の検証状況が整理されていること」は、報告書内に該当節（§2.3 / §4）が存在することで一見満たされて見えるが、「各仮説命題の判定が完結しているか」までは点検されない構造

3. **観点リスト未整備（仮説判定の多面性チェック観点が明文化されていない）**
   - 02.99 執筆時点（2026-05 初頭）では、ドキュメント執筆ガイドライン（v1.0 / v2.0）も未整備であり、Specificity 三点セット（G3-5）・Devil's Advocate（G3-7）等の予防的セルフチェック観点が存在しなかった
   - 仮に v2.0 が存在していても、「仮説/命題に対する判定軸の網羅性（多面判定の必要性検討）」は v2.0 の G3-X 系のいずれにも明示されていない（後述 §5 参照）

4. **証拠不在ではなく整理漏れであることが見落とされやすい構造**
   - 多面判定の素材（精度・速度・トークン効率の各定量値）はサブタスク 07 報告書内に既に存在し、追加調査は不要だった
   - 「素材は揃っている／整理漏れだけ」という状態は、執筆者から見ると「書ききった」感が出やすく、セルフレビューでも「内容の十分性」より「既記載内容の整合」に意識が向きやすい

### 根本原因

**特定した原因**: 計画書要素（仮説・打ち切り条件・成功条件等）と報告書記述を結びつける **逆引き対応マトリクスを用いた完結性点検プロセス**が、執筆段階・セルフレビュー段階の双方において、ガイドライン／テンプレート／運用ルールのいずれにも整備されていなかった。結果として「素材は揃っているが整理漏れがある」状態が執筆者にもセルフレビューにも検出されず、外部レビュー（クロスレビュー）で初めて発覚した。

**種別**: プロセス（執筆プロセス・セルフレビュープロセスの欠落）／設計（観点リスト・テンプレートの不備）

**確信度**: 高

- 根拠：レビューイ自身が「多面判定への書き換えは元データから素直に導ける」と認めており、追加調査ゼロで対応可能な「整理漏れ」だったことが確定。F02-009（観点規定の未明文化）と F02-010（資産性質改善）も同期間に同根の問題として起票されており、根本原因が体系的な品質ガードの不在にある点で整合する

### 5.2 既に予防されている範囲（執筆ガイドライン v2.0）

執筆ガイドライン v2.0（2026-05-06、§9.3 再執筆トライアル後の改訂版）には、本件と部分的に重なる予防観点が既に存在する：

| ガイドライン観点 | 予防範囲 | 本件との関係 |
|---|---|---|
| **G3-5 Specificity 三点セット**（what / where / evidence） | 主要主張ごとに「what（何を主張）」「where（どこに根拠）」「evidence（反証時の影響）」を点検 | 部分的に予防可能。仮説への判定文が単一文に潰されている場合、「what が複数の判定軸を内包している」状態は検出しやすい。ただし「**判定軸の網羅性**」（多面判定の必要性）までは G3-5 の射程外 |
| **G3-7 Devil's Advocate（最強反論の織り込み）** | 主要結論に対して最強反論を 1 件記述し、棄却根拠または残存リスクを明示 | 部分的に予防可能。「H1 を単一表現で済ませて良いか？」を反論として立てれば多面判定欠落に気づける可能性がある。ただし反論探しの起点が結論側にあるため、「結論記述自体が薄い／単一軸化している」場合には反論を立てにくく、**機能しない可能性が高い** |
| **G3-3 冗長／矛盾の二重チェック** | 報告書内部の冗長／矛盾を点検 | **射程外**。本件は内部矛盾ではなく「計画書命題への回答完結性欠落」のため、G3-3 では検出できない |
| **G3-4 アンビギュイティ検出** | 曖昧表現の検出 | 部分的に予防可能。「対立軸が補正された」という単一文は「補正の内訳が曖昧」とも読めるため、G3-4 で検出される可能性はある。ただし執筆者が「補正＝十分な情報」と認識した場合には機能しない |

→ **本質的な予防には不十分**。G3-5 / G3-7 / G3-4 の組み合わせで「単一文に潰された記述」が検出される可能性はあるが、**仮説/命題の多面判定の網羅性チェック**という観点は v2.0 G3-X 系のいずれにも明示的に存在しない。本件で必要な観点は「**計画書側に立てた命題に対する判定軸の網羅性**」であり、これは執筆ガイドラインに新設すべき観点（§5.1 案 1: G3-12）として位置付けられる。

### 5.3 推奨対応の優先順位と統合案

§5.1 の根本対策案 1 / 2 / 3 はそれぞれ実施場所（執筆ガイドライン／テンプレート／セルフレビュー観点）が異なるが、いずれも **F02-009 / F02-010 / F02-012** の対処と統合実装するのが合理的：

1. **F02-012 着手時**（調査報告書執筆ガイドライン整備）に案 1（G3-12 新設）と案 2（テンプレマトリクス既定化）を実装
2. **F02-009 着手時**（セルフレビュー観点規定）に案 3（観点追加）を実装
3. **クロスレビューテンプレ v3.1 正式化時**に案 4（判断基準明示）を実装し、最後のセーフティネットとして機能させる

これにより、予防（執筆段階）→検出（セルフレビュー段階）→検出（クロスレビュー段階）の三段ガードが成立し、CRITICAL 級欠落が後続工程に持ち越されるリスクを大幅に低減できる。

## 6. 特記事項/補足事項

- 本要改善点は **F02-009 / F02-010 / F02-012 の対処に統合実装する形が最も経済的**。単独実装すると個別整備のオーバーヘッドが大きい
- 本件で C1 が CRITICAL 級として正しく検出できたのは、**外部レビューア（独立第三者 Claude Opus）が計画書を判断基準として独立に参照したから**。同型の問題は単独セルフレビューでは構造的に検出が困難（執筆者と同じ前提・記憶を共有しているため）であり、**クロスレビューでの独立性が品質ガードの最後の砦として機能した実例**として記録に値する
- 02.99 のレビュー実績では同種の判定軸欠落が C1 / I2 / I3 / I4 と複数発生しており（§4.2）、本件は単発の事故ではなく **構造的問題の代表例**。本件対処を起点に、F02-004（類件）・F02-009 / F02-010 / F02-012（対処系）を一体的に進めることで、フェーズ 03 以降の同種問題を予防可能
