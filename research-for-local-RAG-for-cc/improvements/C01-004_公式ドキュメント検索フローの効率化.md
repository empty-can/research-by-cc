## 2. 発生事象の整理

### 2.1 発生事象（実体験から得た知見）

> 本節は、C01 相談中の実運用で得た「llms.txt 活用調査と従来 WebFetch 調査の比較」体感を、既得知見として転記する。クロージング時の本要改善点採用判断の根拠となる実証データ。

#### a. Context 消費・汚染度

| 項目 | WebFetch | llms.txt + ローカル Grep |
|---|---|---|
| 単発取得サイズ | ページ全体（数 KB〜数十 KB が context に丸ごと） | Grep ヒット行 + `-C` 周辺数行のみ（数十バイト〜数 KB） |
| 「無関係コンテンツ」混入 | ページのナビ・フッタ・関連リンク等が markdown 化されて流入 | 検索対象セクションの周辺だけ |
| 失敗時のコスト | 空振り = 全文を context に取り込んだ後に「違った」と気付く | 空振りでも snippet サイズ |

**体感**: 改善は **大きい**。今回 `iam` ページの空振りで Authentication 内容が context に丸ごと入ったが、Grep なら「permissions に該当行ゼロ」で即終了できた。**Context 汚染が劇的に減る** という観点が、最大のメリット。

#### b. 必要情報へのスピード

- **WebFetch path**: URL 推測 → fetch → 内容判断 → 違ったら別 URL 推測 → fetch...（試行錯誤、各回 fetch コストあり）
- **llms.txt path**: Grep でキーワード一致 → 候補ページ判明（数秒）→ 必要なら llms-full.txt or 個別 fetch

**体感**: llms.txt 経由の方が **明確に速い**。今回の permissions 調査では、最初から llms.txt を grep していれば `permissions.md` というドンピシャのページに 1 ステップで到達できていた。WebFetch だと 2-3 ステップ要した。

#### c. 従来見落としていたであろう情報

**実例あり**: 当初 WebFetch で `/iam` と `/settings` を見て満足していたが、後の llms.txt grep で **`permissions.md` という専用ページの存在を発見**。`permissions.md` には:

- pattern syntax の詳細仕様（word boundary `space + *`、`:*` 同義）
- compound command の permission 評価ルール（各サブコマンド独立評価、`&&` `||` `;` `|` 等）
- process wrapper の自動剥離（`timeout` `nice` 等）
- read-only コマンドの組み込みリスト（`ls` `cat` `grep` 等は prompt 不要）

など、`/settings` ページにはなかった重要情報が満載。**「`command -v` がプロンプト発火した理由」も、この詳細仕様を知っていれば即答できた** はずで、`/settings` ページだけ見ていた当初の判断材料は不十分だった。

#### d. 更なる効率化の余地（本要改善点で取り組む 4 戦術）

1. **複数 Grep の並列実行**: 一度のターンで複数パターンを並列 grep すれば、検索ラウンドが減る（今回も多数活用済み、ただしルール化されていない）
2. **llms.txt + docs_map の組み合わせ活用**: llms.txt で「どのページ」を特定後、docs_map で「ページ内のどのセクション」まで絞れる。1 ページが大きい場合に context 節約に効く（今回未活用、次回試したい）
3. **Grep `-C` の微調整**: ヒット行だけだと前後文脈不足、広すぎると汚染。トピックに応じて `-C 2` 〜 `-C 10` を使い分ける運用基準が欲しい
4. **頻出トピックのキャッシュ**: セッション内で同じドキュメントを何度も参照する場合、初回 grep 結果（候補ページ一覧 + 抜粋）をメモしておけば、2 回目以降の grep 自体不要に

## 3. 採用判断対象

> 本要改善点は「即時適用可能な戦術の運用ルール化」型のため、雛型 §3 原因分析・§4 同件調査は該当度が低く省略する。代わりに本節で **クロージング時に判断すべき採用候補** を整理する。

### 3.1 採用候補（クロージング時に判断、ただし手動運用での先行適用は推奨）

| # | 採用候補 | 配置先（採用時） | 期待効果 |
|---|---|---|---|
| A | **複数 Grep 並列実行のルール化**: ルート CLAUDE.md の Agent 活用ガイドライン or 検索手順節に「llms.txt / llms-full.txt 検索時、独立な複数キーワードは並列 Grep を優先する」と明記 | ルート CLAUDE.md または `.claude/rules/search-runtime.md`（path-scoped） | 検索ラウンド削減、トークン削減 |
| B | **llms.txt + docs_map の組み合わせ運用パターン化**: 「llms.txt → ページ特定」「docs_map → ページ内セクション特定」の二段絞り込みフローを運用ガイドラインに記述 | 同上 | 大ページ参照時の context 節約 |
| C | **Grep `-C` 値の運用基準整備**: トピック別の推奨 context 行数（短文回答狙い: `-C 2` / 文脈把握狙い: `-C 5〜10` / コードブロック含む: `-C 15`）の判断基準をガイドライン化 | 同上 | context 汚染と情報不足のバランス最適化 |
| D | **頻出トピックのセッション内キャッシュ運用**: 同セッション内で同じトピックを再参照する場合、初回 Grep 結果（候補ページ + 抜粋）を構造化して保持し、2 回目以降は再 Grep を省略する運用 | 同上 | 重複検索の排除、トークン削減 |
| E | **C01-003（Skill 化）への内蔵**: A〜D の戦術を C01-003 で設計する Skill / Function Calling スクリプトの内部実装に組み込む | C01-003 の Skill / スクリプト | 自動化による一貫した適用 |

### 3.2 採用判断の前提

- **A〜D は本要改善点単独で即時適用可能**。C01-003（Skill 化）の完成を待つ必要なし
- **E は C01-003 と統合実装**: Skill 完成時に内蔵することで手動運用ルールから卒業
- 暫定対処としては、本要改善点の知見をルート CLAUDE.md の暫定ルール節に簡潔に追記しておくのが効果的（A〜D の本格ルール化はクロージング時判断）
