## 調査の目的

Claude Code に、大量の情報（主に大量のファイルに記載されている情報を想定）を扱った調査や作業を、精度を維持したまま、必要最小限のトークン消費・コンテキスト消費で達成するための最適な仕組みを、オンライン上のサービスに頼らず、ローカルにてOSSまたは商用利用無料のプロダクトのみで構築する方法を明らかにすること。

## 背景

### 大前提：私が目指すものの根底となる考え方

Claude Code を活用する環境は「LLMでなくてもできることは、Claude Code にさせない」が徹底されているべきである。

### 現状の課題：本調査のモチベーション

Claude Code は、データを論理的に解釈、構築することに極めて優れたポテンシャルを持っているため、しばしば大量のデータを必要とする以下のような調査を依頼したくなる。
- 膨大な量の仕様書やマニュアルといったドキュメントの、特定の目的に沿った要約
- アナウンスされたものの詳細は秘匿されている（しかしパッチ差分を根気よく分析すれば答えにたどり着くことは可能な）OSSの脆弱性に対する、複数の技術的観点による分析
- リポジトリ配下のソースコードをインプットにした設計書のリバースエンジニアリング

しかし、調査に必要な大量のデータの取得を Claude Code に担当させると、期待する調査のスコープがデータの全量に対して限定的だったとしても、必要なデータの判断をするためにもかなり不要な内容を含んだデータを一度は読み取る必要があり、また読み取りはファイルをテキストデータとして読み込む形であるため、その際に大量のトークン・コンテキストを消費することになる。  

しかし、例に挙げたような調査は、調査対象や調査観点がドメインスペシフィックであることが多く、データの構造化という点に限ってはLLMよりも得意とするツールやデータストアが存在することもしばしばである（プログラムコードの解析などは最たるもの）。  
また、データの内容はドメインスペシフィックでなくとも、データの利用（取得）形態に特定の性質があるのであれば、それを前提としたデータの構造化をすることで十分効果が見込める（例えば、キーワード検索という形でデータにアクセスしたいのであれば、検索対象のドキュメントを全文検索エンジン機能を有効にしたRDBへ事前に投入しておけば、Claude Code が grepコマンドで検索するよりも遥かに高速に答えを得ることができる）。

ここで、本課題の解決方向性を決めるに当たって、大前提に照らすと、**調査対象のデータから調査観点に沿った必要最低限の情報を精度よく Claude Code が取得できる形にするという工程は、その道の専用ツールに任せるべきである** ということになる。

### 課題解決の有力候補：RAG（Retrieval-Augmented Generation：検索拡張生成）

前述の課題を解決できる可能性が高い仕組みとして、RAGが非常に有力な仕組みであると推測している。  
手動検索による事前の簡単な調査で、このRAGは、OSSのライブラリやプロダクトを組み合わせることで、ローカルで構築することが可能そうであることも確認できている。  
しかし、その構築手法やライブラリ・プロダクトの組み合わせには多くの選択肢が存在することが想定され、またRAGに蓄積したいデータのドメインや取得形式の性質によって、最適な組み合わせが変わってくることも十分に考えられるため、[調査の目的](#調査の目的) に記載した内容を達成することが期待される技術として、RAGについての情報を広く収集し、実際にローカル環境で期待通り動作する構成での構築手順まで確立（あるいはオンライン上に手順が存在している場合は、そのフィジビリティを検証）する必要があるため、本ディレクトリにてRAGの情報収集から実際の構築、動作検証までを行うものとする。

## スコープ

### 含む

* オンラインでの情報調査
  * RAGに関する基本情報の収集
    * 補足：RAGに本調査のモチベーションとなった課題を実際に解決できる見込みがあることを確認するため。
  * RAGをローカルで構築した具体的な事例の収集と、採用されている技術・ツール・プロダクトの情報
  * Qiitaなどの技術ブログやオンラインの技術記事などで公開されている、ローカルRAG構築の実例・手順の情報
  * Claude Code からローカルRAGを利用するために必要となる仕組みやツール  
    * 現時点では、CLIタイプのDBクライアントやMCPサーバのようなものがあるだろうと想定
* オフラインでの情報調査
  * GitHubで公開されている、ローカルRAG構築に利用するツールやOSSライブラリ・プロダクト、ローカル起動向けのRAGの実装などのリポジトリ
    * 手動でcloneするので、それらのリポジトリ内のファイルをオフラインで調査

### 含まない

* ベンダーが提供しているような有料サービスとしてのRAGの情報
* RAGだけでなくLLMもローカルで構築する手順が書かれている場合、ローカルLLMの構築に関する情報  
  * LLM としては Claude Code を利用する前提のため、改めて独自のローカルLLMを構築する必要が無いため
* RedditやX（旧Twitter）など、情報の信頼性の低さ、ページの読み込みコストの高さ、低レベルな機械翻訳による情報劣化の可能性が高い特定のサイトの情報

## レビュー実施ルール

本調査における成果物のレビューは以下のルールに従う（作業計画書 v1.0 改訂前事前作業 Pre-24 由来）。

> **クロスレビュー関連ファイルの参照構成（v3.0α-r3 以降）**:
> - `.claude/skills/cross-review/SKILL.md`（Skill 形式、`user-invocable: false` + `paths:` 自動発火）— 概観・使い方・基本ルール（指摘ラベル定義・態度区分・版数管理基本）。レビュー報告書（`**/レビュー/**/*.md`）またはクロスレビュー Skill 配下を読み書きするときに自動ロード。テンプレート 3 種は `templates/` 配下に同梱
> - `.claude/skills/cross-review/references/runtime-rules.md` — SKILL.md から参照される詳細運用仕様（セルフレビュー運用ルール（前半 5 回 / 後半 Opus 3 回・Sonnet 4 回 / レビューイ 3 巡 / Round 3 上限なし）・レビューア確認セクション仕様・指摘記載ルール・判断依頼サマリ運用ルール・件数表運用ルール等）
> - `research-for-local-RAG-for-cc/.claude/skills/writing-guideline/SKILL.md`（Skill 形式、user-invocable: false + paths 自動発火）— 執筆段階の予防的ガイドライン。レビュー時にも判断基準の一貫性確保のため参照
>
> 本節の記載は Level 2（本プロジェクト固有）の上書きとして機能する。サブフォルダ `CLAUDE.md` が存在する場合はそちらが Level 3 として最優先される。`/init` 等で CLAUDE.md を作成する際は、上書きが必要なルールがあれば「レビュー実施ルール」節に明示すること。
>
> **v3.0α 暫定運用中**: テンプレート v3.0α は詳細化途上のリリース。L3 該当項目（指摘記載内容フォーマット移行・除外基準運用詳細・件数表セクション再構成）は運用しながら詰めて v3.1 で正式化する方針。既存資産（02.99 等の過去成果物）は機械的置換せず、新規執筆ドキュメントから v3.0α を適用する。

### レビュー繰り返し
- Claude Code 単独での **セルフレビュー / クロスレビュー** は、**新規 NG 検出がゼロ** になるまで繰り返し実施する
- 多段構成（例: セルフレビュー → 別 Agent クロスレビュー）の場合、**各段で全 NG への対応を完了した状態で次段へ進む**

### 必須レビュー（作業指示者承認を兼ねる）
以下の成果物は **作業指示者によるレビュー** を必須とする:
- 計画書（v1.0 完成時）
- 各フェーズ完了時の報告書
- 最終報告書

### 個別レビューの依頼
以下の場合は、必須レビュー以外でも作業指示者に個別にレビューを依頼する:
- セルフ／クロスレビューで作業指示者の判断を仰ぐべき指摘が検出された場合
- NG が検出されていなくても、判断ミスによる後続工程への大きな手戻り懸念がある場合

レビュー対象は報告書である必要はなく、**相談用ドキュメント** または **GitHub Issue** でも可。判断が必要な事項を分類する場合は **「課題」** という分類名を使用する。

### code-reviewer agent の扱い
ルート `.claude/agents/code-reviewer.md` はコードレビュー用のため、**本調査では使用しない**。
