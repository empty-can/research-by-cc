# 計画書 固有観点

計画書執筆時に共通観点（`common/01〜03`）に加えて適用する追加観点。フェーズ別に整理。

## 1. 構造設計フェーズの追加観点

### 1.1 想定読者像の事前宣言（計画書版）

G1-1 想定読者像で「**本ドキュメント単独で承認判断ができる**」前提か明示する。承認判断に必要な情報が計画書内で完結していることを示す。

### 1.2 冒頭サマリの必須項目

G1-2 冒頭サマリで以下 4 項目を必ず提示:

- **目的**
- **スコープ**
- **成功条件**
- **打ち切り条件**

### 1.3 読者別読み方ガイド: 承認権限者向け動線

G1-2 #4 読者別読み方ガイドで「**承認権限者向け動線**」を必ず提示する（5〜10 分で承認判断到達できる動線）。

```markdown
例:
| 想定読者 | 優先読了章 | 読了目安 |
|---|---|---|
| 承認権限者 | §0 冒頭サマリ → §9 GO/NO-GO 整理 | 5〜10 分 |
```

### 1.4 打ち切り条件の独立化

打ち切り条件は **独立した節**（例: §0.4 / §9.1）として配置し、採用案・成功条件と並列に置く。本文中に散在させない。

> **理由**: 打ち切り条件が本文中に散在していると、承認権限者が「どのリスクが打ち切り対象か」を把握する負荷が増える。独立節に集約することで、判断材料の参照負荷が下がる。

## 2. 執筆中フェーズの追加観点

### 2.1 成功条件・打ち切り条件に合格水準・基準値を明示

「実測値が記録されている」「想定外コストが見積りの 3 倍超」のような **判定不能な定性記述を避け**、定量基準（recall@10 ≥ 0.80 等）または相談トリガー（基準値を超えた時点で作業指示者と相談）として明示。

```markdown
良い例:
- 成功条件: bge-m3 で recall@10 ≥ 0.80 を達成
- 打ち切り条件: ストレージ要件が 10GB を超過した時点で作業指示者と相談

悪い例:
- 成功条件: 十分な精度を達成
- 打ち切り条件: 想定外のコストが発生
```

## 3. 完成前セルフチェックフェーズの追加観点

### 3.1 Devil's Advocate を計画前提・採用案ごとに 1 件

G3-7 Devil's Advocate を計画前提・採用案ごとに 1 件ずつ実施。**Devil's Advocate 章として独立化を推奨**（探索的調査章末への配置よりも、計画書では章独立化の方が承認権限者の参照負荷が下がる）。

### 3.2 読了時間制約のスコープ外 `[作業指示者]`

計画書は「全記載内容を時間をかけて十分にレビューする」性質のドキュメントのため、**G3-6 想定読了時間との乖離点検は計画書には適用しない**（= 分量制約は他ドキュメントほど厳格に適用しない）。代わりに以下を重点的に確認する:

- G1-2 全体構成可視化（特に各セクションの要点把握容易性）
- G1-3.1 複数モード混在ドキュメントの章単位モード切替
- 必要情報の網羅性（成功条件・打ち切り条件・スコープ・WBS・成果物・体制・スケジュール・リスク 等）
- 各セクションの記載順序の理解容易性・妥当性のチェック容易性
- 判断基準・マイルストーンなど計画遂行に必要な観点・方針の網羅性
