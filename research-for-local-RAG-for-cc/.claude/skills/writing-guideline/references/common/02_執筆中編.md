# 執筆中編（書きながら意識すること）

章を書き進めている最中に継続的に意識する観点。全ドキュメント種別共通。種別固有の追加観点は対応する種別ファイルを併読する。

## G2-1. 結論先出し（BLUF / Pyramid） `[Minto]` `[internal-comms]`

各章・各節の冒頭 1〜2 文で **結論または核となる主張** を先に書く。詳細・根拠は後段に置く。

```markdown
良い例:
## 3.1 採用候補
本フェーズの採用候補は BAAI/bge-m3（埋め込み）+ DuckDB+vss（DB）+ ハイブリッド検索の構成。
理由は §3.1.1〜§3.1.3 で述べる。

悪い例:
## 3.1 採用候補
2026 年初頭から複数の候補を比較検討した。BAAI/bge-m3 は…（結論が章末まで出ない）
```

## G2-2. 短文・短段落（3〜7 行） `[Microsoft]` `[Google]`

- **段落長**: 3〜7 行で区切る
- **文長**: 単純に保つ（1 文に複数の節が入りすぎない）
- **箇条書き化**: 列挙構造の文は箇条書き / 表に変換

> **理由**: 長い段落・長文は目が滑りやすく、重要情報を見落とすリスクが上がる。

## G2-3. パターン化された構造（landmark） `[Microsoft]`

同じ種類の情報は **同じ構造（見出しレベル・記述順）** で書き、読者がパターンで処理できるようにする。

```markdown
良い例（採用候補の各エントリで構造を統一）:
### 3.1.1 BAAI/bge-m3
- ライセンス: MIT
- ストレージ要件: 約 2GB
- 採用根拠: 多言語対応、高精度

### 3.1.2 ruri-v3-310m
- ライセンス: Apache 2.0
- ストレージ要件: 約 0.6GB
- 採用根拠: 日本語特化
```

### G2-3.1. パターン化テンプレート例

頻出するパターンの参考テンプレート:

**採用候補エントリ**:
```markdown
### N.M.K. {候補名}
- **ライセンス**: {ライセンス名・互換性メモ}
- **ストレージ要件**: {サイズ目安}
- **採用根拠**: {技術的根拠・1〜2 文}
- **注意点**: {既知の制約・落とし穴}
- **出典**: {サブタスク N の §X / 引用元へのリンク}
```

**サブタスク報告書サマリ**:
```markdown
### N. {サブタスク名}
- **目的**: {1 文}
- **問い**: {1〜3 件の主要問い}
- **完了条件**: {何が成立すれば完了か}
- **主要発見**: {本フェーズで採用された結論への寄与}
```

**指摘エントリ（クロスレビュー以外で使用する場合）**:
```markdown
### {ID}. {タイトル}
- **該当箇所**: {章節・行番号}
- **問題**: {1〜2 文で要約}
- **根拠**: {引用または典拠リンク}
- **対応案**: {改善案・複数あれば表で}
```

> **理由**: パターン化された構造は「テンプレートで書き始める」ことで初動コストを下げ、書き手間・章間の揺れを防ぐ。テンプレ例を持つことで「最初の 1 件目をどう書くか」の判断負荷も下がる。

### G2-3.2. 比較項目の表形式の検討（緩いガイドライン） `[作業指示者]`

> **本項目の強制力について**: 本項目は **「ルール」ではなく「ガイドライン」** であり、**「心がけてほしい」程度の緩い強制力** です。判断基準が状況により曖昧にならざるを得ないため、強い強制力は持たせていません。実装時は読み手にとっての可読性を最優先で判断してください。

複数の対象を **比較する目的** で記載する場合、表形式の採用を検討する:

| 状況 | 推奨表現 |
|---|---|
| 採用候補・ベンチマーク比較等の **比較対象が複数あり、共通項目で比較できる** | 表形式（行 = 対象、列 = 比較項目） |
| 比較対象に該当しない **個別の説明・根拠・注意点** | 表に無理に収めず、表外で箇条書き等で補完 |
| 表形式に収めると一部の情報が欠落・無理が生じる | 箇条書きを優先し、可読性を保つ |

```markdown
良い例（表 + 箇条書きの併用）:
##### 採用候補基本スペック（共通項目は表形式）
| 候補 | 候補順位 | 形態 | スケール目安 | ライセンス |
|---|---|---|---|---|
| DuckDB + vss | 1 | 単一ファイル DB | 数十万〜数百万 | MIT |
| LanceDB | - | 単一ファイル組み込み型 | 数百万〜 | Apache 2.0 |

##### 採用根拠と注意点（個別情報は箇条書き）
- **DuckDB + vss**
  - 採用根拠
    - 単一 `.duckdb` ファイル + 標準 SQL
    - Windows 公式サポート
  - 注意点
    - HNSW のディスク永続化は experimental
- **LanceDB**
  - 採用根拠
    - Arrow ネイティブ・ディスク効率高い
  - 注意点
    - 約 25,600 件未満は自動でフルスキャン
```

> **理由**: 比較項目を表形式にすることで見やすさが向上し、過度な箇条書き化によるドキュメントの縦長化を抑えられる。一方、個別の説明・根拠を無理に表化すると可読性が低下するため、表形式に固執しない。

> **適用タイミング**: 新規執筆時から心がける。既存ドキュメントへの遡及適用は不要。

## G2-4. 前提知識の明示 `[doc-coauthoring]`

ドキュメント執筆中に「これは読者にとって既知か？」を都度問い、暗黙の前提があれば補足する。

| 状況 | 対処 |
|---|---|
| プロジェクト固有の用語 | 初出箇所で 1 行定義を併記 |
| 業界共通用語だが略語 | 初出箇所でフルスペル併記（例: `MCP（Model Context Protocol）`）|
| 引用・参照が前提 | 引用文をその場に残し、参照だけで完結させない |

## G2-5. アクティブボイス・断定の優先 `[internal-comms]` `[Google]`

受動態・婉曲表現が判断を曖昧にしていないかを点検する。

```markdown
良い例:
- 採用する: bge-m3
- 除外する: paraphrase-multilingual（最大 128 トークン制限）

悪い例:
- 採用されるべきと考えられる: bge-m3
- 除外されることが望ましい可能性が高い: paraphrase-multilingual
```

## G2-6. データドリブン（数値・期日・件数） `[internal-comms]`

「効果的」「相当数」のような形容詞は、可能な限り **数値・期日・固有名詞** で置き換える。

```markdown
良い例:
- 02.基礎調査の作業指示者レビューは 2026-05-05 完了、139 指摘収集
- bge-m3 は recall@10 で 91% を達成

悪い例:
- 02.基礎調査のレビューは効果的に完了、相当数の指摘を収集
- bge-m3 は高い精度を達成
```

## G2-7. ジャーゴン判定の手続き化 `[Google]`

略語・専門用語ごとに「想定読者がそのまま読めるか」を判定し、できないなら **定義 or 言い換え** を入れる。

判定手順:
1. その用語を初出時に Google 検索したと仮定し、上位 5 件で意味が即座に取れるか確認
2. 取れない場合は 1 行定義を併記
3. 業界共通用語でも略語は初出フルスペル必須

## G2-8. 箇条書きの記法ルール `[作業指示者]`

箇条書きで複数の情報を伝える場合（特に伝える情報量が多い場合）、以下のルールに従う:

1. **1 階層目は主題を 1 文で書く**
   - 読み手が箇条書きを目で追ったときに、主題を即座に把握できるようにする
2. **詳細・補足・根拠は階層を下げる**
   - 1 階層目の主題に対する補足情報は、一段下げた箇条として書く（並列の箇条としない）
3. **関連情報は階層構造で表現**
   - 関連する情報を並列の箇条として記載するのではなく、階層を下げて関係性を構造で示す
   - 視覚的に文章の論理構造が把握できる効果

```markdown
良い例（階層構造で関係性を表現）:
- 不同意点の整理
  - 「基準 4 の評価不整合」点は不同意
    - 基準 4 は構築完了後の最低限の動作網羅性確認として必要
      - Pre-15 由来の意図的追加（疎通だけでなく正常パターンも回ることを確認）
    - 「想定通りの結果」が読み手に「精度評価」と誤読される文言は改善余地あり

悪い例（複数情報の詰め込み + 並列化）:
- 「基準 4 の評価不整合」点は不同意。基準 4 は構築完了後の最低限の動作網羅性確認として必要であり、Pre-15 由来の意図的追加（疎通だけでなく正常パターンも回ることを確認）である。ただし「想定通りの結果」が読み手に「精度評価」と誤読される文言は改善余地あり。
```

> **理由**: 1 階層目に複数情報を詰め込むと主題の即時把握が困難になる。階層構造で関係性を表現することで、視覚的に文章の論理構造が把握できる。

> **適用タイミング**: 新規執筆時から適用。既存ドキュメントへの遡及適用は不要（コスト過大のため）。
