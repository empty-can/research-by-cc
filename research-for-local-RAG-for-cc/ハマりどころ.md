## 1. 運用ルール

### 1.1 参照ルール

- **各フェーズ作業の開始時に必ず本ファイルを参照する**。
  - 既知のハマりどころに該当しないかを最初に確認する。
  - 該当した場合は、本ファイルに記載された対処法に従って事前に回避する／対策を組み込む。

### 1.2 追記ルール

- **新たに発見したハマりどころは、その作業中または作業終了時に必ず本ファイルへ追記する**。
- 追記タイミング:
  - 発見直後（作業中に新たな対処を要したもの）
  - サブタスク完了時（サブタスク内で何度か遭遇し対処に至ったもの）
  - フェーズ完了時（フェーズ全体を振り返って整理した結果見出したもの）

### 1.3 追記フォーマット

各エントリは以下の形式で記載する:

```markdown
### <連番>. <短いタイトル>

- **トリガ条件**: どのような状況で発生するか（OS / ツール / バージョン / 設定 など）
- **症状**: 具体的に何が起こるか（エラーメッセージ・誤動作・性能劣化 等）
- **対処法**: どう回避・解決するか
- **関連参考資料**: 関連する先行インプット番号・URL・公式ドキュメント等
- **記録元**: 発見されたフェーズ／サブタスク（例: `02.基礎調査/02.埋め込みモデル比較`）
- **記録日**: YYYY-MM-DD
```

末尾の「変更履歴」にも追記日のエントリを追加する。

### 2.1 埋め込みモデル

#### 1. e5 系モデルの `passage:` / `query:` プレフィックス必須

- **トリガ条件**: `intfloat/multilingual-e5-*` 系の埋め込みモデルを利用する場合。
- **症状**: プレフィックスを付与せずに埋め込みを生成すると、想定された精度が出ず、検索結果が劣化する。
- **対処法**: ドキュメント側の埋め込みは `passage: <本文>`、クエリ側は `query: <検索文>` のプレフィックスを付与する。
- **関連参考資料**: 先行インプット 02
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 2. 異なる埋め込みモデルの DB 内混在によるバグ

- **トリガ条件**: 同一ベクトル DB に異なる埋め込みモデルで生成したベクトルを混在保存した場合。
- **症状**: 次元数や埋め込み空間が不一致のため、類似検索が不正な結果を返す（あるいはエラーになる）。
- **対処法**: メタデータとしてモデル名（およびバージョン・次元数）を保存し、検索時にフィルタリングする運用を組み込む。モデル切替時はインデックスを再構築する運用も含めて検討する。
- **関連参考資料**: 先行インプット 02
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 3. `zotero-mcp` の既定モデル `all-MiniLM-L6-v2` は日本語精度が不足

- **トリガ条件**: `zotero-mcp` 等のツールを既定モデルのまま日本語コンテンツに対して使用する場合。
- **症状**: 日本語クエリに対する検索精度が低い。
- **対処法**: 多言語対応モデル（`bge-m3` / `multilingual-e5` 等）または日本語特化モデル（`ruri-v3` 等）に差し替える。
- **関連参考資料**: 先行インプット 04
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 7. ruri-v3 は英語への適用で精度が大幅低下

- **トリガ条件**: `cl-nagoya/ruri-v3-*` 系モデルを日本語以外の言語（英語コード・英語ドキュメント）に適用した場合。
- **症状**: 英語テキストに対する類似度計算の精度が大幅に低下する（日本語特化設計のため）。
- **対処法**: 多言語混在コーパスには ruri-v3 単独使用を避け、`bge-m3` 等の多言語モデルを主軸にするか、ruri-v3 を日本語特化クエリ専用として使い分ける。
- **関連参考資料**: 02.基礎調査/02.埋め込みモデル比較 調査報告書
- **記録元**: 02.基礎調査/02.埋め込みモデル比較
- **記録日**: 2026-05-03

#### 8. bge-m3 の ColBERT モードはメモリ消費が大幅増大

- **トリガ条件**: `BAAI/bge-m3` を ColBERT モード（後期インタラクション）で動作させる場合。
- **症状**: 通常の Dense/Sparse モードと比べてメモリ消費が大幅に増大し、低スペック環境では OOM が発生する可能性がある。
- **対処法**: リソース制約がある環境では Dense + Sparse のハイブリッドに限定し、ColBERT モードはベンチマーク段階でのみ有効化を検討する。
- **関連参考資料**: 02.基礎調査/02.埋め込みモデル比較 調査報告書
- **記録元**: 02.基礎調査/02.埋め込みモデル比較
- **記録日**: 2026-05-03

#### 9. EmbeddingGemma 系モデルはライセンスが商用利用不可

- **トリガ条件**: `google/embedding-gemma-*` または類似の Gemma 系埋め込みモデルを選定する際。
- **症状**: Gemma 独自ライセンス（Gemma Terms of Use）が適用されており、商用利用に制限がある。OSS と誤認して採用すると後のライセンス問題に発展するリスクがある。
- **対処法**: 商用利用可能な MIT / Apache 2.0 ライセンスのモデル（`bge-m3`, `ruri-v3`, `Qwen3-Embedding` 等）を選定する。
- **関連参考資料**: 02.基礎調査/02.埋め込みモデル比較 調査報告書
- **記録元**: 02.基礎調査/02.埋め込みモデル比較
- **記録日**: 2026-05-03

#### 10. Qwen3-Embedding はクエリ側にインストラクションプロンプトが必要

- **トリガ条件**: `Qwen/Qwen3-Embedding-*` 系モデルをクエリ検索に使用する場合。
- **症状**: インストラクション付きエンコードなしでは検索精度が低下する。
- **対処法**: クエリ埋め込み時はタスク別インストラクションプロンプトを先頭に付与する（ドキュメント側には不要。非対称エンコード）。
- **関連参考資料**: 02.基礎調査/02.埋め込みモデル比較 調査報告書
- **記録元**: 02.基礎調査/02.埋め込みモデル比較
- **記録日**: 2026-05-03

### 2.2 ベクトル DB / 検索基盤

#### 4. DuckDB vss の `hnsw_enable_experimental_persistence` は experimental

- **トリガ条件**: DuckDB + vss 拡張で HNSW インデックスを永続化したい場合。
- **症状**: 永続化機能が experimental 扱いのため、将来的な互換性破壊や予期せぬ挙動の可能性がある。
- **対処法**: `hnsw_enable_experimental_persistence` を有効化して使う場合、experimental である旨を運用ドキュメントに明記し、DuckDB / vss のバージョン更新時に動作確認を行う。プロダクション利用時は代替手段（永続化形式の自前管理 等）も検討する。
- **関連参考資料**: 先行インプット 02
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 5. macOS で sqlite-vec を使うには Homebrew 版 SQLite が必要な場合あり

- **トリガ条件**: macOS で `sqlite-vec` 拡張を使う場合（システム同梱の SQLite 利用時）。
- **症状**: ロード時にエラーが発生し、`sqlite-vec` を読み込めない。
- **対処法**: Homebrew で SQLite をインストールし、そちらを利用するように設定する。
- **関連参考資料**: 先行インプット 03
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 11. LanceDB は 25,600 件未満でインデックスが自動作成されずフルスキャンになる

- **トリガ条件**: LanceDB で `create_index()` を明示的に呼び出さずにベクトル検索する場合（データ件数が 25,600 件未満でも発生）。
- **症状**: インデックスが自動作成されず全件フルスキャンになる。件数増加後も再インデックスが必要で、インデックス未作成に気づかないまま運用すると性能劣化が顕在化する。
- **対処法**: `table.create_index("vector")` を明示的に呼び出してインデックスを作成する。本番環境ではインデックス作成ステップを構築フローの必須ステップとして組み込む。
- **関連参考資料**: 02.基礎調査/03.ベクトルDB検索基盤比較 調査報告書
- **記録元**: 02.基礎調査/03.ベクトルDB検索基盤比較
- **記録日**: 2026-05-03

#### 12. sqlite-vec は HNSW インデックス非対応のため大規模時に検索が線形劣化

- **トリガ条件**: `sqlite-vec` を使ってベクトル検索する場合（概ね 100 万件超の規模）。
- **症状**: HNSW 等の近似最近傍インデックスが実装されていないため、件数増加に対して検索時間が線形に増大する。
- **対処法**: 小〜中規模（〜100 万件程度）の利用に限定し、それを超える場合は LanceDB / DuckDB+vss / Chroma 等へ移行する。
- **関連参考資料**: 02.基礎調査/03.ベクトルDB検索基盤比較 調査報告書
- **記録元**: 02.基礎調査/03.ベクトルDB検索基盤比較
- **記録日**: 2026-05-03

#### 13. DuckDB vss は全ベクトルをメモリ展開するため大規模時に RAM が枯渇

- **トリガ条件**: DuckDB+vss 拡張を使って大量のベクトルを検索する場合（1536 次元・数十万件規模以上）。
- **症状**: 1536 次元 × 100 万ベクトルで約 6 GB の RAM を消費する。一般的な開発機（8〜16 GB）では OOM が発生する。
- **対処法**: 埋め込み次元を 768 以下に抑えるか（例: bge-m3 dense モードは 1024 次元）、メタデータフィルタリングで対象件数を削減するか、大規模時は LanceDB / Qdrant 等へ移行する。
- **関連参考資料**: 02.基礎調査/03.ベクトルDB検索基盤比較 調査報告書
- **記録元**: 02.基礎調査/03.ベクトルDB検索基盤比較
- **記録日**: 2026-05-03

### 2.3 連携方式（Skills / MCP / CLI）

#### 6. Skills 版の CLI 都度起動はモデルロードで約 8〜9 秒の遅延が発生

- **トリガ条件**: Claude Code の Skills 経由で埋め込みモデルを CLI 都度起動する形式の RAG を利用する場合。
- **症状**: 1 クエリあたり初回モデルロードで約 8〜9 秒の遅延が発生する。
- **対処法**: 常駐 HTTP サーバー化（Skills 常駐型）または MCP 化することで遅延を回避できる。利用頻度が高いユースケースでは常駐型を選定する。
- **関連参考資料**: 先行インプット 05
- **記録元**: 計画書 v0.x（事前調査）
- **記録日**: 2026-05-01

#### 14. MCP サーバー多数登録時のツール一覧だけで大量トークンを消費する

- **トリガ条件**: Claude Code に複数の MCP サーバー（5 サーバー・58 ツール規模）を登録した状態でセッションを開始する場合。
- **症状**: ツール一覧の読み込みだけで約 55,000 トークンを消費する。通常の利用でセッションのコンテキストを大量に使い込む。
- **対処法**: Claude Code の「Tool Search」機能（`tool_search=true`）を有効化することで動的に絞り込み、最大 85% 程度のトークン削減が可能。ローカル RAG 用 MCP は機能を絞った軽量サーバーを選定することも重要。
- **関連参考資料**: 02.基礎調査/06.ClaudeCode連携方式 調査報告書
- **記録元**: 02.基礎調査/06.ClaudeCode連携方式
- **記録日**: 2026-05-03

#### 27. MCP サーバーの stdio vs Streamable HTTP transport の選択

- **トリガ条件**: MCP サーバーをローカル以外の環境（クラウド・サーバーレス等）にも展開したい場合
- **症状**: stdio transport は Claude Code が自動起動・終了を管理するため運用が簡単だが、サーバーレス環境への展開が不可能。Streamable HTTP transport はサーバーレス環境対応が可能だが、Windows での常駐プロセス管理が別途必要。
- **対処法**: ローカル単独利用なら stdio 一択。将来的なリモート展開を検討する場合のみ Streamable HTTP を選択し、Windows での常駐管理方法（タスクスケジューラ等）を事前に計画する。
- **関連参考資料**: 02.基礎調査/06.ClaudeCode連携方式 調査報告書
- **記録元**: 02.基礎調査/06.ClaudeCode連携方式
- **記録日**: 2026-05-03

### 2.6 チャンク分割・インデックス

#### 15. 日本語・英語混在テキストのトークン数膨張

- **トリガ条件**: `chunk_size=512` 等でチャンクサイズをトークン数で設定した場合
- **症状**: 日本語部分でトークンが想定の 2〜3 倍になり、実際のチャンクが極端に短くなる
- **対処法**: tiktoken（OpenAI）や sentencepiece ベースのトークナイザーで事前に実測してから chunk_size を設定する
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 16. tree-sitter パーサーのバージョン依存

- **トリガ条件**: `tree-sitter-python`, `tree-sitter-typescript` 等の言語バインディングを使用する場合
- **症状**: tree-sitter 本体とのバージョン互換性が厳しく、バージョンミスマッチで parse が失敗する
- **対処法**: インストール時にバージョンを固定する（例: `requirements.txt` で tree-sitter バージョンを明示固定）
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 17. Markdown コードブロック内の誤分割

- **トリガ条件**: RecursiveCharacterTextSplitter 等でセパレータに `"\n"` を含めて Markdown を分割する場合
- **症状**: コードブロック（` ``` ` 〜 ` ``` `）内部の改行で誤分割される
- **対処法**: コードブロックを先に抽出してからテキスト部分のみを分割するか、MarkdownHeaderTextSplitter を使用する
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 18. PDF テキスト抽出の読み取り順序崩れ

- **トリガ条件**: 2 カラムレイアウトの PDF を pymupdf や pdfminer で抽出する場合
- **症状**: 左右カラムが混ざった順序でテキストが取得される
- **対処法**: unstructured + hi-res モデルまたは Azure Document Intelligence でレイアウト解析を適用する
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 19. 重複排除の過剰適用

- **トリガ条件**: コサイン類似度の閾値（例: 0.90）で重複排除を設定した場合
- **症状**: 同じ概念を異なる言い方で説明した文を誤って重複と判定する。特に短いコードコメントやリスト項目で誤排除が起きやすい
- **対処法**: 最小文字数フィルタ（例: 100 文字未満は重複排除スキップ）を設ける
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 20. オーバーラップによるインデックス肥大

- **トリガ条件**: チャンクオーバーラップを 20% より大きく設定した場合
- **症状**: 同一情報が複数チャンクに含まれ、ベクトル検索の結果に重複した情報が返されやすくなる
- **対処法**: オーバーラップは 20% 以下に抑え、検索時の重複排除処理と合わせて設計する
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

#### 21. コードエンティティのドックストリング欠如

- **トリガ条件**: tree-sitter で抽出したコードエンティティにドックストリングがない場合
- **症状**: コンテキストプレフィックスを付けても埋め込み品質が向上しにくい
- **対処法**: 関数シグネチャのみでも付加する価値はあるが、ドックストリング生成の前処理（LLM で補完）も検討する
- **関連参考資料**: 02.基礎調査/04.チャンク分割インデックス手法 調査報告書
- **記録元**: 02.基礎調査/04.チャンク分割インデックス手法
- **記録日**: 2026-05-03

### 2.7 検索アルゴリズム

#### 22. BM25 + 日本語処理の落とし穴（sudachipy 必須）

- **トリガ条件**: `rank_bm25` 等の BM25 ライブラリに日本語テキストをそのまま渡す場合
- **症状**: 文字単位分割になり精度が著しく低下する
- **対処法**: `sudachipy` での前処理が必須。`pip install "AutoRAG[ja]"` または `sudachipy` 単体でインストールする
- **関連参考資料**: 02.基礎調査/05.検索アルゴリズム 調査報告書
- **記録元**: 02.基礎調査/05.検索アルゴリズム
- **記録日**: 2026-05-03

#### 23. RRF の k パラメータの過剰調整

- **トリガ条件**: ハイブリッド検索に RRF（Reciprocal Rank Fusion）を使用する場合
- **症状**: BM25 の精度がベクトル検索より大幅に低い場合に k を大きくするとベクトル側を重視できるが、過度な調整は一般化性を失う
- **対処法**: 特別な理由がなければ k=60（業界標準推奨値）を維持する
- **関連参考資料**: 02.基礎調査/05.検索アルゴリズム 調査報告書
- **記録元**: 02.基礎調査/05.検索アルゴリズム
- **記録日**: 2026-05-03

#### 24. クロスエンコーダーのバッチ処理未使用による遅延

- **トリガ条件**: リランキングで候補を 1 件ずつスコアリングする場合
- **症状**: 遅延が線形増加する
- **対処法**: FlagEmbedding / sentence-transformers のバッチ推論（batch モード）を使う
- **関連参考資料**: 02.基礎調査/05.検索アルゴリズム 調査報告書
- **記録元**: 02.基礎調査/05.検索アルゴリズム
- **記録日**: 2026-05-03

#### 25. リランカーの入力長制限

- **トリガ条件**: `bge-reranker-v2-m3` 等のリランカーに長いチャンクを渡す場合（トークン長上限: 512〜1024）
- **症状**: 上限を超えるチャンクはスコアリングが不正確になる
- **対処法**: チャンキング設計（04.チャンク分割インデックス手法）との整合を取り、チャンクサイズをリランカーの入力長制限以内に収める
- **関連参考資料**: 02.基礎調査/05.検索アルゴリズム 調査報告書
- **記録元**: 02.基礎調査/05.検索アルゴリズム
- **記録日**: 2026-05-03

#### 26. Windows 11 での ONNX 高速化（要検証）

- **トリガ条件**: CPU 環境で FlagEmbedding を使用する場合
- **症状**: `use_fp16=True` による GPU 高速化が使えない CPU 環境では推論速度が遅い
- **対処法**: ONNX Runtime 経由の推論に切り替えると約 1.5〜2x 速度改善が見込める（実環境での検証が必要）
- **関連参考資料**: 02.基礎調査/05.検索アルゴリズム 調査報告書
- **記録元**: 02.基礎調査/05.検索アルゴリズム
- **記録日**: 2026-05-03

### 2.8 コードベース向け RAG

#### 28. コードに対するベクトル埋め込みの「沈黙した失敗」

- **トリガ条件**: 汎用ベクトル埋め込みをコードに適用して関数定義・型参照・依存関係を検索する場合
- **症状**: ベクトル類似度でコード構造の意味が正確に捉えられず、誤ったチャンクが返される。LLM が誤った推論を続けるリスクがある（エラーが発生しないため気づきにくい）
- **対処法**: コード向けには AST チャンキングや構造クエリとの組み合わせが必須
- **関連参考資料**: 02.基礎調査/07.コードベース向けRAG 調査報告書
- **記録元**: 02.基礎調査/07.コードベース向けRAG
- **記録日**: 2026-05-03

#### 29. コードグラフ系 Go ツールの Go 1.26+ 要件

- **トリガ条件**: `codebase-memory-mcp` または `isink17/codegraph` 等のコードグラフ系 Go ツールをインストールする場合
- **症状**: Go 1.26+ が必要だが、2026-05-03 時点の Go 安定版は 1.24.x 系のため、Go >=1.26 環境を別途用意しないとビルドが失敗する
- **対処法**: インストール前に Go 最新バージョンを確認する。プレリリース版 Go の使用が必要な場合は安定版との共存方法を事前に計画する
- **関連参考資料**: 02.基礎調査/07.コードベース向けRAG 調査報告書 / 02.基礎調査/08.オフラインGitHubリポジトリ調査 調査報告書
- **記録元**: 02.基礎調査/07.コードベース向けRAG / 02.基礎調査/08.オフラインGitHubリポジトリ調査
- **記録日**: 2026-05-03

#### 30. AST チャンキングとチャンクサイズの相互作用

- **トリガ条件**: AST チャンキングでチャンク最大サイズを小さく設定した場合
- **症状**: 大きな関数・クラスが 1 チャンクサイズ制限を超えることがあり、構文整合性とのトレードオフが生じる
- **対処法**: チャンクサイズはサブタスク04（チャンク分割・インデックス手法）と整合を取り、大ノードの再帰的分割設定を確認した上で適切な上限値を決める
- **関連参考資料**: 02.基礎調査/07.コードベース向けRAG 調査報告書
- **記録元**: 02.基礎調査/07.コードベース向けRAG
- **記録日**: 2026-05-03

#### 31. ripgrep の Windows パス区切り問題

- **トリガ条件**: MCP サーバー経由で ripgrep にパスを渡す場合（Windows 環境）
- **症状**: バックスラッシュとスラッシュが混在した場合に正しく処理されないことがある
- **対処法**: FastMCP や Go 実装の MCP サーバーはパス正規化を実装していないことがある。MCP サーバー実装でパス正規化処理を組み込むか、スラッシュ統一（`/`）を徹底する
- **関連参考資料**: 02.基礎調査/07.コードベース向けRAG 調査報告書
- **記録元**: 02.基礎調査/07.コードベース向けRAG
- **記録日**: 2026-05-03

#### 32. FastMCP のバージョン間 API 互換性

- **トリガ条件**: FastMCP を使った MCP サーバーを複数参照・利用する場合
- **症状**: FastMCP は活発に更新されており、リポジトリによってバージョンが異なる（例: 最新版を想定するもの、`fastmcp==2.12.0` で固定するもの）。バージョン間の API 互換性に注意が必要
- **対処法**: FastMCP のバージョンを `requirements.txt` で明示固定する。複数の FastMCP 製サーバーを使う場合は共通バージョンに揃える
- **関連参考資料**: 02.基礎調査/08.オフラインGitHubリポジトリ調査 調査報告書
- **記録元**: 02.基礎調査/08.オフラインGitHubリポジトリ調査
- **記録日**: 2026-05-03

#### 33. "ローカル RAG" を謳うリポジトリでも外部サービス必須なものがある

- **トリガ条件**: GitHub でローカル RAG 関連リポジトリを選定する場合
- **症状**: リポジトリ名に "local-RAG" を含んでいても、OpenAI API 等の外部サービスが必須なものがある（例: suwa-sh/local-RAG-backend）
- **対処法**: リポジトリ名だけで完全ローカル性を判断しない。README の dependencies・設定ファイルを確認し、外部 API キーの要否を確認する
- **関連参考資料**: 02.基礎調査/08.オフラインGitHubリポジトリ調査 調査報告書
- **記録元**: 02.基礎調査/08.オフラインGitHubリポジトリ調査
- **記録日**: 2026-05-03

### 2.9 調査・分析プロセス（仕様制約に直面した際の調査観点等）

#### 1. プロダクト仕様の制約に直面した際の調査観点

- **トリガ条件**: なぜなぜ分析や対応策立案で、プロダクトの仕様制約に引っかかった場合
- **症状**: 「仕様として確定 = 変更不能」と判断した時点で思考停止し、制約を回避する公式手段の調査が漏れる
- **対処法**: 制約自体を回避する代替インターフェース・代替ワークフロー・代替運用パターン、または制約の例外条件（プラン要件・モード切替・特定環境下での挙動差異）が公式仕様に明記されていないか、改めて公式情報で再確認する
- **関連参考資料**: F02-001 §3.2 直接原因 #2 / §6 / `improvements/F02-013_*.md` 改善案 E。発生事例: F02-001 で sub-agent の permission 仕様制約を変更不能と整理したが、Remote Control 経由のスマホアプリ承認という公式代替手段を見落としていた（2026-05-07 判明）
- **記録元**: フェーズ 02 振り返り（F02-001 / F02-013 派生）
- **記録日**: 2026-05-07
