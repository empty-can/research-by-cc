## 0. 要約

cc の OTel の変数は、すべてのリポジトリに効いてよいものをユーザ settings の `env` に置き、他のリポジトリに影響しうるものはランチャが起動するプロセスにだけ渡す。Claude が起動する計測用のセッションは、ユーザ settings を読まずに起動する。収集データは本活動の間は自動では消さず、識別属性は受信の時点で鍵付きのハッシュに替える。transcript からは usage と鍵だけを取り込む。受信サーバの常駐、圧縮、内容を記録する変数の 3 件は、判断の節目で作業指示者に諮る。

### 0.3 決めたこと

- 同じ変数をユーザ settings とプロセスの環境変数の両方に置かず、あるセッションでだけ変えるときは `--settings` を使う（[§1.1](#sec-1-1)）

- ユーザ settings の `env` に、有効化・送り先・traces・環境ラベル `lmo.env` の変数を置く（[§1.2](#sec-1-2)）
  - 属性の数の上限と内容の長さの上限は既定のままにする
- 思考案 T2 の経路 (ii)（raw body）は、ランチャ `lmo-launch` で起動したセッションにだけ効かせる（[§1.3](#sec-1-3)）
  - raw body は file モードだけを使い、出力先は `api-bodies\` にする
- 計測用のセッション（probe と Phase 3 の比較実験）は、ユーザ settings を読まずに起動する（[§1.4](#sec-1-4)）
  - `--setting-sources project,local` で起動し、要る設定を `--settings` のファイルで足す。受信は計測ごとに別の番号で待つ
- 受信サーバが止まっていた間の欠けは、取込が transcript と S2 を比べて数える（[§1.6](#sec-1-6)）
- 収集データは、本活動の間は自動では消さない（[§2.1](#sec-2-1)）
  - cc の `cleanupPeriodDays` は延ばさず、取込を 1 日 1 回以上動かして削除より前に取り込む（受信サーバを常駐させる場合。[§2.2](#sec-2-2)）
- 識別属性 5 つを、受信の時点で鍵付きのハッシュに替える（[§2.3](#sec-2-3)）
  - プロンプトの本文は 3 か所に当て、L2 が無効なら受信の時点で落とす
- 補完取込は、transcript から usage と鍵だけを読む（[§2.4](#sec-2-4)）
  - 新しい記録型は読まずに数え、読めない行は 2 種類に分けて数えて飛ばす。取込の記録は `run\ingest\` に置く
- 計画書の既定の案を覆した行は 0 件で、既定の案に足したのは 1 件である（PV-03。本文のマスクの対象に traces の interaction span を足した。[§2.3](#sec-2-3)）

<a id="sec-1-1"></a>
### 1.1 変数の置き場所の規則（EN-01・EN-03）

**決めたこと**

| 置き場所 | 置く変数 | 効く範囲 | 設定する人 |
|---|---|---|---|
| ユーザ settings の `env` | すべてのリポジトリに効いてよい変数（[§1.2](#sec-1-2)）と、内容を記録する変数のうち作業指示者がここと決めたもの（[§3.3](#sec-3-3)） | すべてのセッション（変えた後の起動から） | 作業指示者（Claude が手順を書く） |
| ランチャが起動するプロセスの環境変数 | 他のリポジトリに影響しうる変数（`OTEL_LOG_RAW_API_BODIES` など。[§3.3](#sec-3-3)） | ランチャで起動したセッションだけ | ランチャ（[§1.3](#sec-1-3)） |
| `--settings`（ファイルか JSON の文字列） | ユーザ settings に置いた変数の、あるセッションだけの値 | そのセッションだけ | ランチャ、計測の手順（[§1.4](#sec-1-4)） |
| project・local settings | どの OTel の変数も置かない | — | — |

- 規則 1: 同じ変数をユーザ settings とプロセスの環境変数の両方に置かない
  - settings の `env` の値は、cc を起動したときのプロセスの環境変数（シェルで設定したものなど）の同じ変数を上書きする（docs ed2bfc5 L93882）。両方に置くと、プロセスの環境変数の値は効かない
- 規則 2: ユーザ settings に置いた変数をあるセッションでだけ変えるときは、`--settings` の `env` に書く
  - `--settings` はユーザ・project・local の settings より優先し、書かなかったキーは元のファイルの値のまま残る（docs ed2bfc5 L61168・L65520）
  - ユーザ settings を丸ごと読まずに起動する形は [§1.4](#sec-1-4) にある
- 規則 3: project・local settings には置かない
  - 有効化・送り先・内容を記録する変数と `OTEL_LOG_RAW_API_BODIES` は、そこでは無視される（docs ed2bfc5 L93897〜L93904）
  - `OTEL_RESOURCE_ATTRIBUTES` は project settings でも効き、プロセスの値を丸ごと置き換える（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「第二のゴールへの備え」）。あるリポジトリの project settings がこの変数を持つと、そのリポジトリのセッションでは環境ラベル（[§1.2](#sec-1-2)）が消え、組 B の既定の環境（[H-15](../02.データモデルと集計/設計書.md#sec-6-1) の `store_default`）で補われる
- 手順: ユーザ settings に置くものは、Claude が手順（JSON の断片と、既存の `env` への足し方）を書き、作業指示者が設定する（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意）。変えた後は cc を起動し直す（[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)）

**理由**

- 置き場所の 2 区分は、計画書「有効化と常駐」の回答で決まったことのとおりである。他のリポジトリに影響しうる変数は、ユーザ settings に置かず、起動するプロセスの環境変数で渡す
- 規則 1・2 は、docs の上書きの順に合わせた。合わせないと、ランチャや計測の手順で渡した値が、エラー無しで効かない

**EN-03 の 3 つの制約の当て方**

- EN-03a（`OTEL_LOG_USER_PROMPTS` は L2 の前提）: [§3.3](#sec-3-3) の推奨で、この変数をユーザ settings に置く理由にした
- EN-03b（`OTEL_LOG_ASSISTANT_RESPONSES` の追従）: 応答の本文の扱いは、本環境でも正式リリース物でも明示して設定し、`OTEL_LOG_USER_PROMPTS` に追従させない。値は作業指示者が決める（[§3.3](#sec-3-3)）
  - 理由: 未設定だと `OTEL_LOG_USER_PROMPTS` の値に従う（docs ed2bfc5 L75629）。L2 のために本文の記録を変えると、応答の本文の記録も一緒に変わる
- EN-03c（Windows PowerShell 5.1 で変数が届かなかった件。[1-1 §7](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)）: ランチャを Node.js で書き、PowerShell を通さない。届いたかは取込が確かめる（[§1.3](#sec-1-3)）

<a id="sec-1-2"></a>
### 1.2 ユーザ settings の `env` の中身（EN-01・EN-04・H-16）

**決めたこと**: 次の変数を置く。[引継ぎ資料 v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.1 の基本セットに、traces の 2 つと環境ラベルを足し、プロトコルと送り先を組 A の受け口に合わせた。

| 変数 | 値 | 理由 |
|---|---|---|
| `CLAUDE_CODE_ENABLE_TELEMETRY` | `1` | 有効化（docs ed2bfc5 L75614） |
| `OTEL_METRICS_EXPORTER`・`OTEL_LOGS_EXPORTER` | `otlp` | metrics と logs を受信サーバへ送る |
| `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`・`OTEL_TRACES_EXPORTER` | `1`・`otlp` | traces の有効化（EN-04。docs ed2bfc5 L75670） |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | 組 A の受け口のプロトコル（[H-08](../01.全体構成/設計書.md#sec-7-1)） | cc にプロトコルの既定は無い（docs ed2bfc5 L75617）。traces も共通の設定を使う |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | 組 A の受け口のアドレスと番号（[H-08](../01.全体構成/設計書.md#sec-7-1)）。パスは付けない | 3 つの信号に共通の送り先 |
| `OTEL_RESOURCE_ATTRIBUTES` | `lmo.env=<値>`。値は組 B の [H-15](../02.データモデルと集計/設計書.md#sec-6-1) | 環境の区別（H-16） |
| `OTEL_METRICS_INCLUDE_REPOSITORY` | `true` | リポジトリの単位で分けて見られる（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.1 の「あると望ましい」項目）。`vcs.*` の属性が metrics とイベントに付く |
| `OTEL_METRICS_INCLUDE_ENTRYPOINT` | `true` | `-p` と対話を metrics でも分けられる（[1-1 §3](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-3)） |

設定の形（`<…>` は上の表の値で置き換える）:

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_TRACES_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "<H-08 のプロトコル>",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://<H-08 のアドレス>:<H-08 の番号>",
    "OTEL_RESOURCE_ATTRIBUTES": "lmo.env=<H-15 の値>",
    "OTEL_METRICS_INCLUDE_REPOSITORY": "true",
    "OTEL_METRICS_INCLUDE_ENTRYPOINT": "true"
  }
}
```

- 内容を記録する変数は、[§3.3](#sec-3-3) の決定の後に同じ `env` に足す
- L1 の hook の `hooks`（組 C の [§2.2](../03.作業分類タグ/設計書.md#sec-2-2)）と同じ手順書にまとめ、作業指示者が 1 回で設定できるようにする
- 既定のまま置かない変数
  - 送信の間隔（`OTEL_METRIC_EXPORT_INTERVAL` など）
  - `OTEL_LOGRECORD_ATTRIBUTE_COUNT_LIMIT` などの属性の数の上限。下げると、2.1.310 で加わった `agent_id` などが最初に落ちる（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1) の「有効化と常駐」、[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
  - `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH`（内容の長さの上限。既定 60 KB）。上げると S2 の 1 行が大きくなる（組 A の [§9](../01.全体構成/設計書.md#sec-9) の 7）
  - `OTEL_METRICS_INCLUDE_VERSION`。版は `service.version` で足りる（[1-1 §8](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-8)）

**理由**

- traces を有効にするのは、logs・metrics に出ない API 呼び出しを数えるために span を集計に含めるからである（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）
  - traces を有効にすると、`OTEL_LOG_USER_PROMPTS` が有効なとき interaction span にもプロンプトの本文が入る（docs ed2bfc5 L77301）。そのマスクは [§2.3](#sec-2-3)
- `vcs.*` の属性には、リポジトリの URL と持ち主の名前が入る（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.3）。metrics の系列は、使うリポジトリの数だけ増える。報告書の集計では、リポジトリを「リポジトリ 1」のような番号に置き換えて示す

**環境ラベルのキー（H-16）**: `lmo.env` にする。

- 理由: OTel の semconv の `deployment.environment.name` は配備の段（本番・検証など）を表す名前で、組織の設定が同じキーを使いうる。本活動の固有のキーなら衝突しない
- 書式の制約（空白・カンマなどを使えない。v2.1 R-12）に、組 B の値はかなう
- 置き場所: 本環境と職場（Phase 7）のそれぞれのユーザ settings に、その環境の値で置く
- 別の案: `deployment.environment.name` を使う。長所は規格の名前であること、短所は上の衝突である

<a id="sec-1-3"></a>
### 1.3 ランチャと経路 (ii) の効く範囲（EN-02・EN-03c・H-17）

**決めたこと**

- 思考案 T2 の経路 (ii)（raw body の usage）は、ランチャ `lmo-launch` で起動したセッションにだけ効かせる
  - 日常のセッション（`claude` を直接起動したもの、IDE・Desktop のもの）は、経路 (i) だけ（T1）になる
- ランチャは Node.js のスクリプト `app/bin/lmo-launch.mjs` で、`node app/bin/lmo-launch.mjs <cc の引数>` で起動する。処理の順は次のとおりである
  1. 自分のプロセスの環境変数に、渡す変数を足す。`OTEL_LOG_RAW_API_BODIES` を `file:<出力先>` にし、[§3.3](#sec-3-3) で「ランチャだけ」と決まった変数も足す。ユーザ settings にもある変数は足さない（規則 1）
  2. cc の引数に `--resume`・`--continue`・`--session-id` が無ければ、UUID を作って `--session-id` で渡す（docs ed2bfc5 L61166）。起動の時刻と UUID を `run\launch\<YYYY-MM-DD>.jsonl`（UTC）に 1 行で書く
  3. `claude` を子プロセスとして起動し、標準入出力をそのままつなぐ
- raw body は file モードだけを使い、`=1`（inline）は使わない。出力先（H-17）は `<データの根>\api-bodies\` である
  - cc はそこに要求・応答ごとのファイルと `index.jsonl` を書く（docs ed2bfc5 L76436・L76447・L76458）
  - V-2b の記録の `v2b\` は、これと別に残す
- 届いたかの確かめ（EN-03c）: 取込が、`run\launch\` の UUID と同じ `session_id` の行が `api-bodies\index.jsonl` にあるかを見て、取込の記録（H-12）に書く
  - `--resume` などで既存のセッションを続けた起動は、UUID を作らないので、確かめの対象にしない
  - Phase 3 の初回は、ランチャで 1 セッション起動し、この記録で確かめてから T2 の比較に使う

**理由**

- `OTEL_LOG_RAW_API_BODIES` はユーザ settings に置かない（回答で決まったこと）。プロセスのスコープの変数は、ランチャを通さないセッションには効かない（計画書の EN-02）
- 日常のセッションをランチャに替えると、IDE・Desktop のセッションは替えられず、利用者が起動に別の命令を使うことになる（[計画書 §1.3](../../00.活動計画/活動計画書.md#sec-1-3) の「操作を増やさない」に合わない）
- 本環境では transcript の `requestId` で突合できる（2.1.310 の `-p` で 7 件中 6 件。外れは transcript に出ない compact の 1 件。[1-10 §3.3](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-3-3)）。経路 (ii) が要るのは、T1 で取れないリクエストに限られる
- Node.js で書けば Windows PowerShell 5.1 の件に当たらず、組 A の言語（[組 A §3](../01.全体構成/設計書.md#sec-3)）とそろう
- inline を使わないのは、本文が OTel のイベントに入って S2 の 1 行が大きくなるためである。file モードなら、イベントには本文の代わりにファイルの位置（`body_ref`）だけが入る。組 A が H-17 の後に回した受信の本文の大きさの上限（[組 A §0.3](../01.全体構成/設計書.md#sec-0-3)）は、inline を使わない前提で決められる

**別の案**

| 案 | 長所 | 短所 |
|---|---|---|
| 日常もランチャで起動する（`claude` の名前でランチャを呼ぶ別名を作る） | 経路 (ii) が日常のセッションにも効く | 他のリポジトリの作業でも会話の全体がディスクに書かれ、回答の趣旨に合わない。IDE・Desktop のセッションには効かない |
| ランチャを PowerShell 7 のスクリプトにする | Node.js が無い端末でも動く | 言語が増える。Windows PowerShell 5.1 から起こすと変数が届かない例がある（[1-1 §7](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)） |

職場（Phase 7）で transcript の `requestId` が付かなければ、経路 (ii) の効く範囲を決め直す（[計画書 §7](../../00.活動計画/活動計画書.md#sec-7) #8。割り当て表の G2-03・G2-09。統合）。

<a id="sec-1-4"></a>
### 1.4 計測用のセッションの起動

組 C の申し送り（L1 の hook をユーザ settings に置くと、probe と比較実験のセッションでも L1 が動く。[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）への答えである。

**決めたこと**: Claude が起動する計測用のセッション（probe と Phase 3 の比較実験。`-p` と対話）は、次の形で起動する。日常のセッション（[J-19](../../01.基礎調査/作業指示者裁定待ち事項.md)）の起動は変えない。

```text
claude --setting-sources project,local --settings <計測用の settings ファイル> --permission-mode <固定する mode> --model <完全なモデル ID> …
```

- `--setting-sources project,local` で、ユーザ settings を読まない（docs ed2bfc5 L61167）。ユーザ settings の L1 の hook と OTel の変数が外れる。plugin の有効化も外れる見込みである（下の【推定】の注）
- 計測用の settings ファイルに次を書く。ファイルは plugin の名前を含むので、scratchpad に置き、repo に入れない（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意と同じ扱い）
  - `remoteControlAtStartup` を false にする
  - `enabledPlugins` で、比べる相手の測定（前回の基線）と同じ plugin の集合を true にし、それ以外を false にする
  - `env` に OTel の変数を書き、送り先を下の計測用の受信にする
- 受信は、計測ごとに別の lmo-receiver を起動する。データの根を `probe-<版>\` の下にし、待ち受けの番号を日常の番号と別（例 4319）にする（組 A の [§4](../01.全体構成/設計書.md#sec-4) の `LMO_DATA_DIR`・`LMO_OTLP_PORT`）。日常の lmo-receiver と並べて動かせ、計測のデータが日常の S2 に混ざらない
- L1 を測る条件では、L1 の hook を、probe の作業フォルダの project settings か計測用の settings ファイルの `hooks` に書いて足す
- 切り替えた最初の計測（計画書 Phase 3 の着手前の版の再確認）で、前の起動の仕方（ユーザ settings を読み、`--settings` で plugin を無効にする）の run と並べる。属性集合・`plugin_loaded`・`hook_registered`・`effort` の値が同じかを確かめ、違えばその計測を新しい基線にして、違いを報告書に書く

**理由**

- docs は、settings に書いた hook を 1 つだけ止める手段は無いとする（docs ed2bfc5 L66885）
- ユーザ settings に OTel の変数が入ると、プロセスの環境変数で渡した送り先はユーザ settings の値で上書きされる（[§1.1](#sec-1-1) の規則 1）。ユーザ settings を読まなければ、計測用の送り先が効く
- Phase 1 の probe は、受信スクリプトを 4318 番で動かした（[1-10 §1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-1)）。日常の lmo-receiver が同じ番号で常駐すると、番号がぶつかる

**別の案**

| 案 | 長所 | 短所 |
|---|---|---|
| `--settings` に `disableAllHooks` を書く | ユーザ settings を読んだまま起動できる | probe の作業フォルダの hook と、入れた plugin の Mod も止まり（docs ed2bfc5 L66885・L41962）、hook ありの条件を測れない |
| L1 の hook が特定の環境変数を見て、何もせずに終える | 起動の仕方を変えずに済む | hook のプロセスは起動するので、hook なしの条件にならない |
| 計測用に別の `CLAUDE_CONFIG_DIR` を使う | ユーザの設定の全体から切り離せる | transcript と plugin の置き場所も変わり、認証をやり直すことになる【推定】 |

- 【推定】`--setting-sources` から `user` を外すと、ユーザ settings の `enabledPlugins`・`permissions.defaultMode`・`hooks` も読まれない。docs は SDK の同じ指定を、ファイルの settings の読み込みの選択と書く（docs ed2bfc5 L101470・L101639）。上の最初の計測の並べ方で確かめる
- changelog には、`user` を含まない `--setting-sources` で background の cleanup が `cleanupPeriodDays` を無視して 30 日より古い履歴を消す不具合があり、2.1.101 で直った（docs ed2bfc5 L10894。版の見出しは L10857）。今の基線の版では当たらない
- 日常のセッションの hook なしの基準を取る期間の作り方は、組 C の決めたとおり、Phase 3 の測定の手順で決める

<a id="sec-1-5"></a>
### 1.5 受信サーバの起動（EN-05）

常駐させるかは作業指示者に諮る（[§3.1](#sec-3-1)）。決まるまでは、Phase 3 では作業指示者か Claude が lmo-receiver を手で起動する（起動の形は組 A の [H-05](../01.全体構成/設計書.md#sec-7-1)）。

どの起動の仕方でも、lmo-receiver は待ち受けの番号がすでに使われていたら、動作の記録（`run\`）に残して終える。ログオン時の起動と手動の起動が重なっても、1 つだけ動く。これは組 A の受信サーバの振る舞いに足すもので、段 3 でそろえる。

<a id="sec-1-6"></a>
### 1.6 受信サーバが止まっているとき（EN-06）

**決めたこと**

- cc の側には何も足さない
  - 受信サーバが止まっていても cc の操作は止まらない見込みで、Phase 3 で確かめる（[V-ID 別紙 §2](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の「受信サーバ停止中の cc の挙動」の行）
- 止まっていた間の OTel の記録は欠ける
  - cc が送り直すかは【推定】で、組 A の 503 の扱い（[組 A §9](../01.全体構成/設計書.md#sec-9) の 2）と同じ回に確かめる
- 欠けは取込で数える
  - transcript にあって S2 に無いセッション（`session_id` で比べる）の数と、その最初と最後の時刻を、取込の記録（H-12）に書く
- 欠けたセッションの usage を transcript から集計に足すかは、組 B の集計の正本の規則（[H-26](../02.データモデルと集計/設計書.md#sec-6-1)）に任せ、段 3 でそろえる。足す形は、組 A の縮退運用（[H-25](../01.全体構成/設計書.md#sec-7-1)）と同じになる

**理由**

- [計画書 §5.1](../../00.活動計画/活動計画書.md#sec-5-1) の「受信サーバの停止中にデータが欠落する」の対策（transcript からの遡り取込で補う）に、欠けの大きさを見る手段を足した
- docs は、設定した exporter の失敗を debug log の `[3P telemetry]` の行に出すとする（docs ed2bfc5 L75548）。日常のセッションには debug log が無いので、欠けは取込の側で数える

<a id="sec-2"></a>
## 2. データ保全とプライバシー

[計画書「データ保全とプライバシー」](../../00.活動計画/活動計画書.md#sec-p2-privacy)の行（PV-01〜PV-08b）を決める。収集データの置き場所（データの根）と、本文を記録してよいことは、回答で決まっている。

<a id="sec-2-1"></a>
### 2.1 保持期間とバックアップ（PV-01。圧縮は §3.2）

**決めたこと（本活動の間）**

| データ | 置き場所（組 A の [H-07](../01.全体構成/設計書.md#sec-4) の規則） | 本活動の間 | 消す時 |
|---|---|---|---|
| S2（OTel の生の記録） | `raw\` | 消さない。S1 を作り直す元である | 本活動の終わりか、不要になったとき（回答） |
| S1 | `db\` | 消さない。S2 から作り直せる | 同上 |
| L1 のラベル | 組 C の [H-18](../03.作業分類タグ/設計書.md#sec-4-1) | 消さない | 同上 |
| raw body | `api-bodies\` | 消さない | 同上。ランチャの run ごとに、突合を終えて要らなくなったら消してよい |
| 動作と取込の記録 | `run\` | 消さない（小さい） | 本活動の終わり |
| 既存の `v2b\`・`probe-<版>\` | そのまま | 消さない（回答） | 本活動の終わりか、不要になったとき |

- 自動で消す仕組みは、本活動では作らない
- 本活動の終わりに、消すものの一覧を Claude が作り、作業指示者の確かめの後に消す
- バックアップは自動では取らない。消えると作り直せないもの（S2、L1 のラベル、raw body、組 B の品質の記録と職場の組の単価表、ハッシュの鍵）を、Phase の区切りに作業指示者が外部の記憶装置に写す手順を、Claude が書く（写すかは任意）
  - 写しもクラウド同期の対象のフォルダに置かず、元と同じく本活動の終わりに消す
  - S1 は S2 から作り直せるので写さない

**理由**

- 回答は「本活動が終わったら、または不要になったら削除する」で、期限を決めていない。S2 は、Phase 3〜6 で取込を直すたびに読み直す元である
- 収集データはクラウド同期の対象のフォルダに置かない（回答）。写しにも同じ規則を当てる

**別の案（バックアップ）**: 決まった時刻に別のフォルダへ自動で写す。長所は手間が無いこと、短所は同じ端末の中の写しで端末の故障に効かず、使う容量が倍になることである。

正式リリース物の保持の既定は決めない（[§0.5](#sec-0-5)）。

<a id="sec-2-2"></a>
### 2.2 transcript の保持（cc の側。PV-01 の保持）

**決めたこと**

- `cleanupPeriodDays` は延ばさず、既定の 30 日のままにする（ユーザ settings を変えない）
- 削除より前に取り込む。取込を 1 日 1 回以上動かす（[§2.4](#sec-2-4) の頻度。受信サーバを常駐させる [§3.1](#sec-3-1) の案 2・3 のとき）
- 取込の記録に、最後の取込の時刻と、S2 に届いた `retention_sweep` の `period_days` を書く。最後の取込から 14 日を過ぎたら、lmo-report と取込が警告を出す
- 延ばすことにしたときの条件: cc 2.1.310 以降にする。2.1.309 以前は、非常に大きい値で最近のファイルが消えうる（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D69）。適用値は `retention_sweep` の `period_days` で確かめる（[計画書 §5.1](../../00.活動計画/活動計画書.md#sec-5-1)）

**理由**

- 取込が 1 日 1 回なら、30 日に対して 29 日の余裕がある
- 警告を 14 日にするのは、30 日の半分で、警告から削除まで 16 日が残るためである。取込が止まったことに、削除より前に気付いて直せる
- 延ばすと、すべてのリポジトリの transcript と付随のファイル（file snapshots、tool の結果のファイルなど。docs ed2bfc5 L16161 の一覧）が `~/.claude` に長く残る
- 取込が残すのは transcript の usage と鍵だけ（[§2.4](#sec-2-4)）で、取込の規則の誤りに後から気付くと、30 日より古い transcript からは取り込み直せない。取り込む値は 1 行の中のキーで、規則の誤りの余地は小さい【推定】ので、延ばさない側を選んだ

**別の案**: 本活動の間は延ばす（例 90 日）。長所は、取込を止めた期間や取込の規則の誤りに強いこと、短所は、transcript と付随のファイルが `~/.claude` に長く残ること（上の理由の 3 点目）と、ユーザ settings を変えることである。Phase 3 の取込の試作で規則の誤りが見つかったら、この案に切り替える（[§6](#sec-6) の 6）。

<a id="sec-2-3"></a>
### 2.3 マスクと識別属性（PV-03・PV-04・H-04）

**決めたこと（マスクの規則。H-04）**

| 対象 | 属性（出る所） | 本環境 | 正式リリース物の既定 | 当てる所 |
|---|---|---|---|---|
| 識別属性 | `user.email`・`user.account_uuid`・`user.account_id`・`organization.id`・`user.id`（記録の属性と resource の属性のどちらでも） | 鍵付きのハッシュに替える | 同じ | 受信（S2 に書く前） |
| プロンプトの本文 | `user_prompt` イベントの `prompt`・`prompt_text`、traces の `claude_code.interaction` span の `user_prompt` | 残す | 落とす | 受信。組 C の L2 の切り替え（[組 C §1.7](../03.作業分類タグ/設計書.md#sec-1-7)）が有効なら残し、無効なら `<dropped>` に替える。`prompt_length` は残す |
| 応答の本文、tool の引数と内容、raw body | `assistant_response` の本文、`tool_parameters`・`tool_input`、`tool.output`、`api-bodies\` のファイル | 記録するなら残す（記録するかは [§3.3](#sec-3-3) の変数で決まる） | 変数を無効にするので届かない | — |
| 詳細ベータトレースの本文 | `system_reminders` 属性、`claude_code.system_prompt` イベント | 詳細ベータトレースを使わない（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) R-14）。使うと決めたら、プロンプトの本文と同じ規則に足す | 同じ | 受信 |

- ハッシュは、HMAC-SHA-256 の 16 進の先頭 16 字に `h1:` を付けた値にする
  - 鍵は端末ごとの乱数で、データの根の `config\` に置き、受信サーバの初回の起動で作る
  - 同じ値は同じハッシュになるので、セッションやアカウントの区別は残る
- S1 では、組 B の列（[H-03](../02.データモデルと集計/設計書.md#sec-6-1)）にハッシュの値がそのまま入る。列名と型は組 B のまま変わらない
- 取込の側の差し込み口（組 A の [§2.2](../01.全体構成/設計書.md#sec-2-2)）には、今は何も当てない。取込は transcript の本文を読まない（[§2.4](#sec-2-4)）。transcript に識別属性が入っていたら、受信と同じ規則で替える
- 報告書の集計では、ハッシュの値も識別子として扱い、「アカウント 1」のような番号に置き換えて示す

**理由**

- 識別属性は全レコードに入る（[1-1 §3](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-3)）。集計に要るのは区別だけで、値そのものは要らない
- 受信の時点で替えるのは、S2 を DuckDB で探索した出力にも平文が出ないようにするためである。S2 から S1 を作り直しても、同じ鍵なら同じ値になる
- 鍵付きにするのは、メールアドレスの候補を並べてハッシュと照らす手で、元の値に戻されないようにするためである
- プロンプトの本文は、`OTEL_LOG_USER_PROMPTS` と traces を有効にすると、`user_prompt` の 2 つの属性に加えて interaction span の `user_prompt` 属性にも入る（docs ed2bfc5 L77286〜L77301）。計画書の既定の案は前の 2 つだけを挙げるので、3 つ目を足した
- L2 が無効なときに受信した本文を落とすのは、組 C が組 D に任せた点（組 C の [§1.7](../03.作業分類タグ/設計書.md#sec-1-7)）への答えである。誰かが cc の変数を有効にしても、仕組みの側の設定が無効なら残らない
- PV-04 は計画書の既定の案のままにした

**別の案（識別属性）**

| 案 | 長所 | 短所 |
|---|---|---|
| そのまま残す | 処理が要らない | S2・S1 の探索の出力に平文のメールアドレスが出る |
| S2 は受けたまま、S1 でだけ替える | S2 が受けたままの形になる | S2 を読む探索で平文が出る |
| 落とす | 最も単純 | アカウントの区別ができない（課金の形の違うアカウントを混ぜたとき分けられない） |
| 受信で鍵付きのハッシュに替える（採る） | 上の理由 | 鍵を失うと、それより前の値と結べない（鍵をバックアップの対象にした） |

組 A の S2 の形（[H-06](../01.全体構成/設計書.md#sec-7-1)）は「受けた OTLP の JSON」だが、この規則を当てた後の JSON になる。段 3 でそろえる。

<a id="sec-2-4"></a>
### 2.4 補完取込（PV-05〜PV-08b・H-11・H-12）

**決めたこと（頻度。H-11）**

- lmo-ingest は次のときに動く。同時には 1 つだけ動く（組 A の [§2.1](../01.全体構成/設計書.md#sec-2-1) のロック）
  - lmo-receiver の起動の直後と、その後 1 時間ごと（lmo-receiver が子プロセスとして起こす）
  - lmo-report の集計の前（組 A のとおり）
  - 手動
- 受信サーバを常駐させない場合（[§3.1](#sec-3-1) の案 1）は、受信サーバを起動したとき、lmo-report の前、手動のときにだけ動く
  - 1 日 1 回の取込（[§2.2](#sec-2-2)）は保証されない。14 日の警告も、取込か lmo-report を動かしたときにしか出ない。この弱さを [§3.1](#sec-3-1) の案 1 の短所に入れた
- 1 時間ごとにするのは、S1 を 1 時間以内の新しさに保ち、1 回の取込の量を小さくするためである

**決めたこと（transcript の読み方）**

- 読むファイル: `<cc の設定フォルダ>` の `projects` の下（組 A の [H-09](../01.全体構成/設計書.md#sec-7-1)）で、前回の取込から大きさか更新の時刻が変わったもの
- 変わったファイルは、初めから読み直す。前回の読んだ位置からの続きは使わない
  - 理由: cc は transcript のファイルを削って縮めることがある（`CLAUDE_CODE_TRANSCRIPT_LOCAL_GC`。[1-9 §2](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D58 (c)）
  - 読み直しても、組 B は `request_id` ごとに最後の行を使う（[H-10](../02.データモデルと集計/設計書.md#sec-6-1)）ので、同じリクエストが二重にならない
- 最後の更新から 30 分以内のファイルは「書いている途中」とみなし、末尾の 1 行が読めなくても読めない行に数えず、次の取込で読み直す
  - 理由: 取込は終わったセッションを対象にするのが安全である（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「データモデル」の、異常終了したセッションの項）
  - 30 分は、1 時間ごとの取込の間隔より短く置いた仮の値で、Phase 3 の取込の試作で見直す（[§6](#sec-6) の 7）
  - S2 の当日のファイルの末尾の 1 行も、同じく書いている途中とみなす。閉じた日のファイルの読めない行は、下の種類 1 に数える
- 取り込む値は、組 B の `transcript_usage` の列（H-10）に要るもの（usage、`requestId`、`agentId`、`isSidechain`、`model`、`stop_reason`、時刻など）だけにする。メッセージの本文と tool の入出力は読まない

**決めたこと（新しい記録型。PV-05・PV-06）**

- `api-request`・`api-request-shape`・`api-request-blob`（2.1.300 から。[仕様別紙 §2](../../00.活動計画/【別紙】公式仕様の調査結果.md)）は読まない。型ごとの行数だけを取込の記録に書く
  - 理由: 思考トークンの突合に要らない（[計画書「データ保全とプライバシー」](../../00.活動計画/活動計画書.md#sec-p2-privacy)）。system prompt と tools の全文を含み、ユーザの指示ファイルなどの内容が入りうる【推定】（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「データ保全とプライバシー」）
- PV-06: 読まないので、マスクの範囲は当てない。後で読むと決めたら、system prompt と tools の全文を本文と同じ扱い（本活動では残して本活動の終わりに消し、正式リリース物では取り込まない）にする
- 未知の記録型（知らない `type` の行）も読まず、型の名前ごとの行数を書く

**決めたこと（読めない行。PV-08・PV-08a・PV-08b）**: 計画書の既定の案のとおり、行を飛ばして取込を止めず、件数を取込の記録に書く。

- 種類 1（PV-08a）: `JSON.parse` が例外を出した行
- 種類 2（PV-08b）: 解析はできるが、文字列の値のどれかに孤立したサロゲートが残る行。数え方は [1-9 §5](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-5) の「2.1.308 以前の transcript の読めない行」の行による
- 上の「書いている途中」の末尾の行は、どちらの種類にも数えない

**決めたこと（取込の記録。H-12）**

- 置き場所: `<データの根>\run\ingest\<YYYY-MM-DD>.jsonl`（日付は取込の開始の UTC。組 A の `run\` の下）
- 形: UTF-8、改行は LF、1 回の取込を 1 行の JSON にする。本文を含めない

| 項目 | 中身 |
|---|---|
| `v` | 形の版（初版は 1） |
| `run_id`・`trigger` | 取込の回の ID と、契機（`receiver_start`・`hourly`・`report`・`manual`） |
| `started_at`・`ended_at` | UTC、ISO 8601 |
| `status`・`err` | `ok` か `error`。`err` は例外の種類の名前だけ |
| `s2` | 読んだファイルの数・行数・種類 1 の行数・次に回した末尾の行の数 |
| `transcript` | 見たファイルの数・読み直したファイルの数・行数・種類 1 と種類 2 の行数・書いている途中として次に回したファイルの数・新しい記録型の型ごとの行数・未知の型ごとの行数 |
| `unreadable` | 読めない行のあったファイルごとの、パス・種類・行番号（無かったファイルは載せない） |
| `labels`・`api_bodies` | 読んだファイルの数・行数・読めない行の数 |
| `launch_checks` | ランチャの起動ごとの、`api-bodies\index.jsonl` に行があったか（[§1.3](#sec-1-3)） |
| `otel_gaps` | transcript にあって S2 に無いセッションの数と、その最初と最後の時刻（[§1.6](#sec-1-6)） |
| `retention` | 最後に届いた `retention_sweep` の `period_days` と時刻（[§2.2](#sec-2-2)） |
| `store_bytes` | データの根の直下のフォルダごとの大きさと、transcript の合計の大きさ（[§2.5](#sec-2-5)） |
| `schema_changes` | 組 B の版の検知（[組 B §4.1](../02.データモデルと集計/設計書.md#sec-4-1)）が見つけた変化 |

**理由**: 読めない行を後で直して取り込み直すときに、ファイルと行を引けるようにする。組 B の版の検知と、統合（Phase 3 への引き渡し）が同じ記録を読む。

[進め方 §3](../00.設計の進め方/計画書.md#sec-3) は、読めない transcript の行を段 2 の取込の試作で確かめるとしている。本書は実装と実機の確認をしないので、Phase 3 の取込の試作で確かめる（[§6](#sec-6) の 8）。

<a id="sec-2-5"></a>
### 2.5 保存量の見積もり（PV-07）

**決めたこと**

- 見積もるのは、データの根に溜まる量（S2、S1、raw body、L1 のラベル）である。取込は transcript を写さないので、transcript の大きさは取込の時間に効くだけである
- 方法: Phase 3 の PoC の日常のセッション（cc 2.1.310 以降。取込が対象にする版）で、取込の記録の `store_bytes` を 1 日ごとに読み、2 週間分から 30 日分に延ばして見積もる
- transcript の大きさも同じ期間に数え、取込の読み直しの量の目安にする（2.1.304 から auto mode の `api-request` の記録が小さくなった。[1-9 §3.3](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-3-3)）
- 値は Phase 3 で出す。データの根の 30 日分がディスクの空きの 1 割を超える見込みなら、圧縮（[§3.2](#sec-3-2)）を諮り直す

**理由**: 計画書の既定の案（取込が対象にする版の transcript で見積もる）を、transcript を写さない本書の取込に当てると、溜まる量の主はデータの根の側になる。

## 3. 作業指示者に諮る事項

本節の 3 件は、作業指示者が判断の節目で決める（[進め方 P2-3](../00.設計の進め方/計画書.md#sec-p2-3) の 1〜3）。Claude は決めない。main が [Phase 2 の判断事項のファイル](../作業指示者裁定待ち事項.md)に載せるときの元にするため、各項を単独で読めるように書いた。

<a id="sec-3-1"></a>
### 3.1 受信サーバの常駐（P2-3 の 1。EN-05・S7-03）

**決めること**: 受信サーバ lmo-receiver（組 A の [H-05](../01.全体構成/設計書.md#sec-7-1)）を、使う前に手で起動するか、Windows のログオン時に自動で起動するか。自動にする場合の起動の仕組み。

**選択肢**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1: 手動 | 作業指示者が、cc を使う前に起動する | 端末の設定を変えない | 起動を忘れた間の OTel の記録が欠ける（transcript から補えるのは usage と思考トークンだけ。[§1.6](#sec-1-6)）。受信サーバを起動していない間は取込も 1 時間ごとに動かず、transcript の削除（既定 30 日）より前に取り込む保証が弱くなる（[§2.4](#sec-2-4)）。[計画書 §1.3](../../00.活動計画/活動計画書.md#sec-1-3) の「操作を増やさない」に合わない |
| 2: ログオン時に自動（タスク スケジューラ） | 現在のユーザのログオンを契機に起動するタスクを登録する | 止まったときに起動し直す設定を持てる【推定】。登録の有無を管理の画面で見られ、外しやすい | 既定のタスクの条件（電池で動くときに止める、長く動くと止める など）を外す手順が要る【推定】。登録に管理者の権限が要る場合がある【推定】 |
| 3: ログオン時に自動（スタートアップ フォルダ） | ユーザのスタートアップ フォルダにショートカットを置く | 管理者の権限が要らない。置く・消すだけで済む | 止まったら次のログオンまで起動しない。窓を出さない工夫が要る |

比べて外した仕組みは次の 3 つである。

- レジストリの Run キー: 案 3 と同じ働きで、登録が利用者から見えにくい
- Windows のサービス: 管理者の権限と、サービスにする別の道具が要り、依存が増える（組 A の [§3](../01.全体構成/設計書.md#sec-3)）
- cc の `SessionStart` hook で起こす: hook から background の process を起こすと、tool call が block されうる（[計画書「L1 の hook の既定の書き方」](../../00.活動計画/活動計画書.md#sec-p2-l1-hook)の、background の process の項と同じ理由）

**承認の対象**: 案 1〜3 と、常駐を始める時期。決めないもの: タスクの条件の細かい値と窓を出さない起こし方（Phase 4 の実装で確かめ、手順書で見ていただく）、職場（Phase 7）での起動の仕方（Phase 7 の着手前）。

**Claude の推奨**: 案 2。Phase 3 の PoC は手動で起動し、Phase 4 から常駐させる。案 2 で登録できなければ案 3 にする。

- Phase 4 の完了条件（操作を増やさずにデータが溜まる状態が 1 週間程度続く。[計画書 Phase 4](../../00.活動計画/活動計画書.md#sec-p4)）には、自動の起動が要る
- 止まったときに起動し直せば、欠ける時間を短くできる。欠けの大きさは取込の記録で見る（[§1.6](#sec-1-6)）
- Phase 3 を手動にするのは、PoC の間は受信サーバを何度も直すので、そのたびに登録を直さずに済むためである

**決める時期**: 判断の節目（段 2 の後）。登録と外す手順は Claude が書き、作業指示者が行う（ユーザの環境を変えるため）。裁定が無い間は、どの案でも同じ Phase 3 の手動の起動で進める。

<a id="sec-3-2"></a>
### 3.2 圧縮（P2-3 の 2。PV-01 の一部・S7-05）

**決めること**: 保存ファイル（S2 の閉じた日の JSONL と、raw body）を外部で圧縮する構成（[計画書 §7](../../00.活動計画/活動計画書.md#sec-7) #5）を採るか。採るなら、その手段。本書は「外部で圧縮する構成」を、閉じたファイルを書いた後に丸ごと圧縮する形と読む。

**前提**: 受信サーバは非圧縮の JSONL を追記する（組 A の [H-06](../01.全体構成/設計書.md#sec-7-1)）。書く側で圧縮しないのは、その形式が DuckDB で直接読めないためである（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) R-3。閉じたファイルを後から圧縮する形は、R-3 の対策の形である）。

**選択肢**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1: 圧縮しない | 今の形のまま | 処理が増えない。取込と DuckDB が今の形のまま読める | ディスクの使用量が、圧縮した場合より大きい |
| 2: `node:zlib` の gzip | 取込が読み終えた閉じた日のファイルを `.jsonl.gz` にする | 追加の道具が要らない（Node.js の組み込み。組 A の [§5.2](../01.全体構成/設計書.md#sec-5-2)）。DuckDB は拡張子から圧縮の形を判別して読む（v2.1 R-3） | 取込と探索の読みが遅くなる【推定】。圧縮の処理と、途中で止まったときの扱いが要る |
| 3: 外部の道具（zstd・7-Zip など） | 案 2 と同じことを別の道具で行う | 圧縮率が案 2 より高い【推定】 | 道具を入れる手間と依存が増える（[J-13](../../01.基礎調査/作業指示者裁定待ち事項.md#sec-1)）。Windows には単体の gzip・zstd の命令が標準で無い（v2.1 R-3） |

**承認の対象**: 案 1〜3。決めないもの: 圧縮する時期の値（何日たったファイルを圧縮するか。案 2・3 を採るときに決める）。

**Claude の推奨**: 案 1。外部で圧縮する構成を今は採らず、採る理由が出たら案 2 にする。

- 保存量はまだ見積もっていない（[§2.5](#sec-2-5)。値は Phase 3）。会話の全体を含む raw body はランチャのセッションだけに出る（[§1.3](#sec-1-3)）ので、日常の量は S2 が主になる
- 案 2 は Node.js の組み込みで足りるので、後で採っても依存は増えない
- 案 3 は、依存を少なくする方針（J-13）に合わない
- 見直しの条件: [§2.5](#sec-2-5) の見積もりで、データの根の 30 日分がディスクの空きの 1 割を超える見込みなら、案 2 を諮る

**決める時期**: 判断の節目（段 2 の後）。裁定が無い間は案 1 のまま進める（圧縮しなくても Phase 3 は進む）。

### 3.3 内容を記録する変数の置き場所と、正式リリース物の既定（P2-3 の 3。EN-01・EN-03b・PV-02・S7-02）

**決めること**: 内容を記録する 5 つの変数のそれぞれについて、(a) 本環境の置き場所（ユーザ settings か、ランチャのプロセスだけか）と、(b) 正式リリース物の既定。

**決まっていること**（変えない）

- 取りこぼしの無い仕組みのためなら、どの変数も常時有効にしてよい。他のリポジトリの作業に悪影響を与えうるもの（例 `OTEL_LOG_RAW_API_BODIES`）は、ユーザ settings に置かず、起動するプロセスの環境変数で渡す（[計画書「有効化と常駐」](../../00.活動計画/活動計画書.md#sec-p2-enable)の回答で決まったこと）
- Phase 2 以降の本環境は `OTEL_LOG_USER_PROMPTS=1` にする。正式リリース物で `=0` にすることには問題は無い（[まとめ §5.1 の Q4 の ※2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers)）
- 職場（Phase 7）の変数は、Phase 7 の着手前に決める（[計画書の承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24)の先送りの行）

**Claude の推奨**

| 変数 | 記録されるもの | 本環境の置き場所 | 正式リリース物の既定 |
|---|---|---|---|
| `OTEL_LOG_USER_PROMPTS` | プロンプトの本文（`user_prompt` と、traces の interaction span） | ユーザ settings で有効 | 無効 |
| `OTEL_LOG_ASSISTANT_RESPONSES` | 応答の本文（`assistant_response`） | ユーザ settings で、明示して有効 | 明示して無効 |
| `OTEL_LOG_TOOL_DETAILS` | tool の引数（Bash のコマンドの全体、パス、MCP・skill・agent の名前）と、ユーザ定義の agent と MCP の実名（metrics と `api_request`） | ユーザ settings で有効 | 無効 |
| `OTEL_LOG_TOOL_CONTENT` | tool の出力の内容（ファイルの中身、コマンドの出力、WebFetch の結果。traces の `tool.output`） | ランチャのプロセスだけ（調べる run で有効にする） | 無効 |
| `OTEL_LOG_RAW_API_BODIES` | API の要求と応答の JSON の全体（会話の全体） | ランチャのプロセスだけ（file モード。[§1.3](#sec-1-3)） | 無効 |

記録されるものは docs ed2bfc5 L75628〜L75633・L77286〜L77316 による。

**変数ごとの理由と別の案**

- `OTEL_LOG_USER_PROMPTS`
  - 本環境をユーザ settings にするのは、L2 の前提だからである。ランチャだけにすると、ランチャを通さないセッションでは本文が記録されず、L2 で分類できない（EN-03a）。cc 自身がディスクに書く量は増えない
  - 別の案はランチャだけにすること。長所は他のリポジトリのプロンプトが残らないこと、短所は日常のセッションで L2 が働かず、L1 と L2 を比べられないことである（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の回答の確認 4）
  - 正式リリース物を無効にするのは Q4 の ※2 による。`=0` で動くタグ案は L1 か ① である
- `OTEL_LOG_ASSISTANT_RESPONSES`
  - 本環境を有効にするのは、本活動では情報量の多い案を優先する（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の ※1 の要旨）ためである。応答の本文は、問い② の品質の判定（組 B の [§2.3](../02.データモデルと集計/設計書.md#sec-2-3)）の材料になりうる【推定】
  - 明示するのは EN-03b のとおりで、`OTEL_LOG_USER_PROMPTS` を変えたときに応答の記録が一緒に変わらないようにする（[§1.1](#sec-1-1)）
  - 別の案は、本環境でも明示して無効にすること。長所は S2 の量が減ること、短所は 30 日を過ぎると応答の本文が手元に残らないこと（transcript は消える）である
- `OTEL_LOG_TOOL_DETAILS`（V-5 などの実測の結果を入れた）
  - 有効にすると、ユーザ定義の agent とユーザが設定した MCP の名前が、metrics と `api_request` で実名になる（無効では `custom`）。skill の名前は、公式でない plugin の skill を除き、無効でも実名だった。`skill_activated` だけは、無効だとユーザ定義の skill が `custom_skill` になる
  - metrics の系列は、実名に割れる名前の種類 1 つにつき、cost が 1 本・token が 4 本増えた（モデル 1 つ）。agent 2 種・MCP の tool 2 種・skill 3 種を 1 ターンに 1 つずつ使った run では、32 本が 42 本（+31%）になった。名前がそれぞれ 1 種類の run では 22 本で変わらなかった
  - 系列より大きな差は、`tool_decision`・`tool_result` の `tool_parameters` に、Bash のコマンドの全体（切り詰めない。docs ed2bfc5 L77306）と agent・skill・MCP の名前が付くことである
  - 本環境を有効にするのは、問い②・③ で agent と MCP を実名で分けるためである。系列の増え方は名前の種類に比例する小さなもので、ローカルの S1 には重くない。分類器が block した規則の名前（`classifier_category`）も、この変数が有効なときだけ付く（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
  - 正式リリース物を無効にするのは、他人の端末で、コマンドとパスを既定では残さないためである。無効でも skill の名前は実名で集計できる
  - 正式リリース物の別の案は、有効にして、受信で `tool_parameters`・`tool_input` を落とすこと。長所は agent と MCP を実名で集計でき、コマンドとパスが残らないこと、短所は受信の規則が増え、`claude_code.tool` span の入力由来の属性（`file_path` など。docs ed2bfc5 L77310）の全体が docs から決まらないことである
  - 実測は、無効のときも traces の `claude_code.tool` span に MCP の server・tool の実名が出ると示した（docs の記載と食い違う）。並列に呼んだ MCP の tool は、`api_request` に最後の 1 つの名前しか付かなかった（1 つのリクエストに付く MCP の名前は 1 つ【推定】）
- `OTEL_LOG_TOOL_CONTENT`
  - 本環境をランチャだけにするのは、次の 3 点による
    - 計画書の指標に、tool の出力の内容を使うものが無い。ツール結果の大きさは `tool_result_size_bytes` で取れる（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
    - 内容は 1 属性 60 KB まで入り、traces の 1 回の送信が大きくなる（組 A の [§9](../01.全体構成/設計書.md#sec-9) の 7 の、S2 の 1 行の大きさ）
    - 他のリポジトリで読んだファイル（秘密の値を含む設定ファイルなど）の中身が、S2 に写る
  - 別の案はユーザ settings で有効にすること。長所は情報量が最大になること（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の ※1 の要旨）、短所は上の 3 点である
- `OTEL_LOG_RAW_API_BODIES`
  - 本環境の置き場所は回答で決まっている（ランチャのプロセスだけ）。file モードにする理由は [§1.3](#sec-1-3) にある
  - 正式リリース物を無効にするのは、正式リリース物の思考案が T1 だけなら要らないからである。T2 を残す場合も、ランチャで有効にする（AR-04。統合が設計書の承認時に決める）

**承認の対象**: 上の推奨の表の 5 行 × 2 列（本環境の置き場所と、正式リリース物の既定）。決めないもの: 職場（Phase 7）の変数（Phase 7 の着手前）、正式リリース物で T2 を残すか（AR-04。設計書の承認時）。ユーザ settings に置くものは、Claude が手順を書き、作業指示者が設定する。

**決める時期**: 判断の節目（段 2 の後）。裁定が無い間も Phase 3 の計測は進められる（計測用のセッションは変数を `--settings` で渡す。[§1.4](#sec-1-4)）。日常のセッションの設定は裁定の後に行う。

**V-5 などの実測で残った未確認**: 公式でない plugin のうち marketplace から入れたもの、claude.ai 経由・公式 registry の MCP、モデルと `effort` を振ったときの系列数、対話モードでの名前の出方、職場での名前の出方の 5 件である。どれも推奨を変えない。系列数は、モデルと `effort` の組の数だけ掛けて増える【推定】。

## 7. Devil's Advocate

| 対象 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| 計測用のセッションでユーザ settings を読まない（[§1.4](#sec-1-4)） | ユーザ settings には OTel 以外の設定もあり、読まないと日常の条件から外れ、計測が日常を代表しない | 棄却する。計測用のセッションの役目は、版の間と条件の間の比較で、日常の値は日常のセッション（J-19）で測る。残存リスク: 切り替えの前後で基線が変わる。最初の計測で前の起動の仕方と並べ、違いを基線の変更として残す |
