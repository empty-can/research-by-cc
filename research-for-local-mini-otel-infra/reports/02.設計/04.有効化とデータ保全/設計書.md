## 0. 要約

cc の OTel の変数は、すべてのリポジトリに効いてよいものをユーザ settings の `env` に置き、他のリポジトリに影響しうるものはランチャが起動するプロセスにだけ渡す。Claude が起動する計測用のセッションは、ユーザ settings を読まずに起動する。収集データは本活動の間は自動では消さず、識別属性は受信の時点で鍵付きのハッシュに替える。transcript からは usage と鍵だけを取り込む。作業指示者は判断の節目に 3 件を決めた。受信サーバは常駐させず、起動・停止のスクリプトで手で起こす（J-29）。保存ファイルは圧縮しない（J-30）。内容を記録する変数は、3 つをユーザ settings、2 つをランチャに置き、正式リリース物では 5 つとも無効にする（J-31）。

### 0.3 決めたこと

- 同じ変数をユーザ settings とプロセスの環境変数の両方に置かず、あるセッションでだけ変えるときは `--settings` を使う（[§1.1](#sec-1-1)）
  - ユーザ settings の `env` の値は、プロセスの環境変数の同じ変数を上書きする（docs ed2bfc5 L93882。Claude Desktop app などが起動したセッションでは、起動の環境が設定した変数が先に立つ。L93883）
- ユーザ settings の `env` に、有効化・送り先・traces・環境ラベル `lmo.env` の変数と、内容を記録する変数のうち 3 つ（[§0.4](#sec-0-4)）を置く（[§1.2](#sec-1-2)）
  - 属性の数の上限と内容の長さの上限は既定のままにする
- 思考案 T2 の経路 (ii)（raw body）は、ランチャ `lmo-launch` で起動したセッションにだけ効かせる（[§1.3](#sec-1-3)）
  - raw body は file モードだけを使い、出力先は `api-bodies\` にする
  - ランチャは起動ごとに、渡したセッションの id を `run\launch\` に 1 行で書く。取込が、そのセッションの raw body と transcript が残ったことを確かめ、どちらかが無い起動は T1 と T2 の比較から外す
- 計測用のセッション（probe と Phase 3 の比較実験）は、ユーザ settings を読まずに起動する（[§1.4](#sec-1-4)）
  - `--setting-sources project,local` で起動し、要る設定を `--settings` のファイルで足す。受信は計測ごとに別の番号で待つ
  - セッションの id を計測のデータの根に記録し、日常の取込はその transcript を読まない。Claude Code が起こす対話のセッションは入れ子として扱われ、transcript を残さないので、transcript を使う計測では残させる変数を有効にする
  - hook の記録（L1 のラベル、`SessionStart` の記録）は、起こすプロセスの環境変数でデータの根を渡し、計測のデータの根に書かせる【推定】
- ユーザ settings に置くものの設定の手順は、Phase 3 の着手時に Claude が書き、受信サーバが止まっているときの cc の挙動を確かめてから、`env`、日常の hook なしの基準、`hooks` の順に設定していただく（[§1.7](#sec-1-7)）
  - 手順には、設定が効いたことの確かめと、不具合が出たときの戻し方も書く
- 受信サーバが止まっていた間の欠けは、取込が transcript と OTel の記録（S2 から S1 に入れた行）を比べ、OTel の記録が 1 件も無いセッションを数える（[§1.6](#sec-1-6)）
  - その間のセッションの usage は、transcript から読んだ値で集計に足す
  - セッションの途中で止まった分は、欠けに数えず、補わない
- 収集データは、本活動の間は自動では消さない（[§2.1](#sec-2-1)）
  - cc の `cleanupPeriodDays` は延ばさない。取込は受信サーバを起動するたびに動き、30 日の間に一度は起動すれば削除より前に取り込める【推定】（[§2.2](#sec-2-2)）
- 識別属性 5 つを、受信の時点で鍵付きのハッシュに替える（[§2.3](#sec-2-3)）
  - 鍵は端末ごとの 32 バイトの乱数で、鍵のファイルが読めなければ、受信サーバは新しい鍵を作らずに起動をやめる
  - プロンプトの本文は 3 か所に当て、L2 が無効なら受信の時点で落とす
  - リポジトリの属性 `vcs.*` は平文のまま残し、報告書の集計で番号に置き換える
  - ライブ表示に出してよい項目は、数と区分だけの許可リストにする。本文系、マスクの対象、識別子、利用者が付けた名前を値に持ちうる属性は、マスクの後の通常の経路で見る
- 補完取込は、transcript から usage と鍵だけを読む（[§2.4](#sec-2-4)）
  - 新しい記録型は読まずに数え、読めない行は 2 種類に分けて数えて飛ばす。取込の記録は `run\ingest\` に置く
  - 受信サーバが取込を起こす間隔は、既定 1 時間で、データの根の設定のファイルか、プロセスの環境変数で 5 分〜24 時間の範囲で変えられる。範囲の外の値は既定に戻し、動作の記録に残す。間隔は受信サーバの起動の時刻から数え、前の取込が終わらずロックが取れない回は飛ばす
- 計画書の既定の案を覆した行は 0 件で、既定の案に足したのは 1 件である（PV-03。本文のマスクの対象に traces の interaction span を足した。[§2.3](#sec-2-3)）

## 1. 有効化と常駐

[計画書「有効化と常駐」](../../00.活動計画/活動計画書.md#sec-p2-enable)の行（EN-01〜EN-06）を決める。内容を記録する変数の置き場所と受信サーバの起動の仕方は、作業指示者が決めた（[§3.3](#sec-3-3)・[§3.1](#sec-3-1)）。本節は、それを [§1.2](#sec-1-2)・[§1.3](#sec-1-3)・[§1.5](#sec-1-5) に入れ、ほかを決める。

本書の「データの根」は、収集データを置くフォルダ（Windows の既定は `%LOCALAPPDATA%\local-mini-otel\`。決め方とフォルダの構成は組 A の [§4](../01.全体構成/設計書.md#sec-4)）を指す。

<a id="sec-1-1"></a>
### 1.1 変数の置き場所の規則（EN-01・EN-03）

**決めたこと**

| 置き場所 | 置く変数 | 効く範囲 | 設定する人 |
|---|---|---|---|
| ユーザ settings の `env` | すべてのリポジトリに効いてよい変数と、内容を記録する変数のうち作業指示者がここと決めた 3 つ（[§1.2](#sec-1-2)・[§3.3](#sec-3-3)） | すべてのセッション（変えた後の起動から） | 作業指示者（Claude が手順を書く） |
| ランチャが起動するプロセスの環境変数 | 他のリポジトリに影響しうる変数（`OTEL_LOG_TOOL_CONTENT`・`OTEL_LOG_RAW_API_BODIES`。[§3.3](#sec-3-3)） | ランチャで起動したセッションだけ | ランチャ（[§1.3](#sec-1-3)） |
| `--settings`（ファイルか JSON の文字列） | ユーザ settings に置いた変数の、あるセッションだけの値 | そのセッションだけ | ランチャ、計測の手順（[§1.4](#sec-1-4)） |
| project・local settings | どの OTel の変数も置かない | — | — |

- 規則 1: 同じ変数をユーザ settings とプロセスの環境変数の両方に置かない
  - settings の `env` の値は、cc を起動したときのプロセスの環境変数（シェルで設定したものなど）の同じ変数を上書きする（docs ed2bfc5 L93882）。両方に置くと、プロセスの環境変数の値は効かない
  - ただし、Claude Desktop app や self-hosted environment の runner が起動したセッションでは、起動の環境が設定した変数が先に立ち、その変数には settings の `env` の値が効かない（docs ed2bfc5 L93883）
- 規則 2: ユーザ settings に置いた変数をあるセッションでだけ変えるときは、`--settings` の `env` に書く
  - `--settings` はユーザ・project・local の settings より優先し、書かなかったキーは元のファイルの値のまま残る（docs ed2bfc5 L61168・L65520）
  - ユーザ settings を丸ごと読まずに起動する形は [§1.4](#sec-1-4) にある
- 規則 3: project・local settings には置かない
  - 有効化・送り先・内容を記録する変数と `OTEL_LOG_RAW_API_BODIES` は、そこでは無視される（docs ed2bfc5 L93897〜L93904）
  - `OTEL_RESOURCE_ATTRIBUTES` は project settings でも効き、プロセスの値を丸ごと置き換える（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「第二のゴールへの備え」）。あるリポジトリの project settings がこの変数を持つと、そのリポジトリのセッションでは環境ラベル（[§1.2](#sec-1-2)）が消え、組 B の既定の環境（[H-15](../02.データモデルと集計/設計書.md#sec-6-1) の `store_default`）で補われる
- 手順: ユーザ settings に置くものは、Claude が手順（JSON の断片と、既存の `env` への足し方）を書き、作業指示者が設定する（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意）。変えた後は cc を起動し直す（[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)）。成果物と設定の順序は [§1.7](#sec-1-7) にある

**理由**

- 置き場所の 2 区分は、計画書「有効化と常駐」の回答で決まったことのとおりである。他のリポジトリに影響しうる変数は、ユーザ settings に置かず、起動するプロセスの環境変数で渡す
- 規則 1・2 は、docs の上書きの順に合わせた。合わせないと、ランチャや計測の手順で渡した値が、エラー無しで効かない

**EN-03 の 3 つの制約の当て方**

- EN-03a（`OTEL_LOG_USER_PROMPTS` は L2 の前提）: [§3.3](#sec-3-3) で、この変数をユーザ settings に置く理由にした
- EN-03b（`OTEL_LOG_ASSISTANT_RESPONSES` の追従）: 応答の本文の扱いは、本環境でも正式リリース物でも明示して設定し、`OTEL_LOG_USER_PROMPTS` に追従させない。値は、本環境は有効、正式リリース物は無効である（J-31。[§3.3](#sec-3-3)）
  - 理由: 未設定だと `OTEL_LOG_USER_PROMPTS` の値に従う（docs ed2bfc5 L75629）。L2 のために本文の記録を変えると、応答の本文の記録も一緒に変わる
- EN-03c（Windows PowerShell 5.1 で変数が届かなかった件。[1-1 §7](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)）: ランチャを Node.js で書き、PowerShell を通さない。届いたかは取込が確かめる（[§1.3](#sec-1-3)）

### 1.2 ユーザ settings の `env` の中身（EN-01・EN-04・H-16）

**決めたこと**: 次の変数を置く。[引継ぎ資料 v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.1 の基本セットに、traces の 2 つ、環境ラベル、内容を記録する変数のうちユーザ settings に置く 3 つ（[§3.3](#sec-3-3)。J-31）を足し、プロトコルと送り先を組 A の受け口に合わせた。

| 変数 | 値 | 理由 |
|---|---|---|
| `CLAUDE_CODE_ENABLE_TELEMETRY` | `1` | 有効化（docs ed2bfc5 L75614） |
| `OTEL_METRICS_EXPORTER`・`OTEL_LOGS_EXPORTER` | `otlp` | metrics と logs を受信サーバへ送る |
| `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`・`OTEL_TRACES_EXPORTER` | `1`・`otlp` | traces の有効化（EN-04。docs ed2bfc5 L75670） |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | 組 A の受け口のプロトコル（[H-08](../01.全体構成/設計書.md#sec-7-1)） | cc にプロトコルの既定は無い（docs ed2bfc5 L75617）。traces も共通の設定を使う |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | 組 A の受け口のアドレスと番号（[H-08](../01.全体構成/設計書.md#sec-7-1)）。パスは付けない | 3 つの信号に共通の送り先 |
| `OTEL_RESOURCE_ATTRIBUTES` | `lmo.env=<値>`。値は組 B の [H-15](../02.データモデルと集計/設計書.md#sec-6-1) | 環境の区別（H-16） |
| `OTEL_METRICS_INCLUDE_REPOSITORY` | `true` | リポジトリの単位で分けて見られる（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.1 の「あると望ましい」項目）。`vcs.*` の属性が metrics とイベントに付く |
| `OTEL_METRICS_INCLUDE_ENTRYPOINT` | `true` | `-p` と対話を metrics でも分けられる（[1-1 §3](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-3)） |
| `OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_ASSISTANT_RESPONSES`・`OTEL_LOG_TOOL_DETAILS` | `1` | 内容を記録する変数のうち、本環境でユーザ settings に置く 3 つ（[§3.3](#sec-3-3)）。`OTEL_LOG_ASSISTANT_RESPONSES` は `OTEL_LOG_USER_PROMPTS` に追従させず、明示して書く（EN-03b） |

設定の形（`<…>` は上の表の値で置き換える）:

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_TRACES_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "<H-08 のプロトコル>",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://<H-08 のアドレス>:<H-08 の番号>",
    "OTEL_RESOURCE_ATTRIBUTES": "lmo.env=<H-15 の値>",
    "OTEL_METRICS_INCLUDE_REPOSITORY": "true",
    "OTEL_METRICS_INCLUDE_ENTRYPOINT": "true",
    "OTEL_LOG_USER_PROMPTS": "1",
    "OTEL_LOG_ASSISTANT_RESPONSES": "1",
    "OTEL_LOG_TOOL_DETAILS": "1"
  }
}
```

- 内容を記録する変数のうち `OTEL_LOG_TOOL_CONTENT`・`OTEL_LOG_RAW_API_BODIES` の 2 つは、ここに置かない（ランチャだけ。[§1.3](#sec-1-3)）
- L1 の hook と `SessionStart` の hook の `hooks`（組 C の [§2.2](../03.作業分類タグ/設計書.md#sec-2-2)。スクリプトの置き場所は組 A の [H-27](../01.全体構成/設計書.md#sec-7-1)）と同じ手順にまとめる。設定は `env` と `hooks` の 2 回に分ける（[§1.7](#sec-1-7) の順序）
  - この手順は、ユーザ settings に置くものは Claude が手順を書き作業指示者が設定する、という[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意と J-31 に依る。J-29 の「手順書は作らない」の対象ではない（[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の計画書との関係）
- 既定のまま置かない変数
  - 送信の間隔（`OTEL_METRIC_EXPORT_INTERVAL` など）
  - `OTEL_LOGRECORD_ATTRIBUTE_COUNT_LIMIT` などの属性の数の上限。下げると、2.1.310 で加わった `agent_id` などが最初に落ちる（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1) の「有効化と常駐」、[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
  - `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH`（内容の長さの上限。既定 60 KB）。上げると S2 の 1 行が大きくなる（受信の本文の大きさの上限は組 A の [§2.2](../01.全体構成/設計書.md#sec-2-2)）
  - `OTEL_METRICS_INCLUDE_VERSION`。版は `service.version` で足りる（[1-1 §8](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-8)）

**理由**

- traces を有効にするのは、logs・metrics に出ない API 呼び出しを数えるために span を集計に含めるからである（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）
  - traces を有効にすると、`OTEL_LOG_USER_PROMPTS` が有効なとき interaction span にもプロンプトの本文が入る（docs ed2bfc5 L77301）。そのマスクは [§2.3](#sec-2-3)
- `vcs.*` の属性には、リポジトリの URL と持ち主の名前が入る（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.3）。metrics の系列は、使うリポジトリの数だけ増える。報告書の集計では、リポジトリを「リポジトリ 1」のような番号に置き換えて示す

**環境ラベルのキー（H-16）**: `lmo.env` にする。

- 理由: OTel の semconv の `deployment.environment.name` は配備の段（本番・検証など）を表す名前で、組織の設定が同じキーを使いうる。本活動の固有のキーなら衝突しない
- 書式の制約（空白・カンマなどを使えない。v2.1 R-12）に、組 B の値はかなう
- 置き場所: 本環境と職場（Phase 7）のそれぞれのユーザ settings に、その環境の値で置く
- 別の案: `deployment.environment.name` を使う。長所は規格の名前であること、短所は上の衝突である

### 1.3 ランチャと経路 (ii) の効く範囲（EN-02・EN-03c・H-17）

**決めたこと**

- 思考案 T2 の経路 (ii)（raw body の usage）は、ランチャ `lmo-launch` で起動したセッションにだけ効かせる
  - 日常のセッション（`claude` を直接起動したもの、IDE・Desktop のもの）は、経路 (i) だけ（T1）になる
- ランチャは Node.js のスクリプト `app/bin/lmo-launch.mjs`（名前は組 A の [H-05](../01.全体構成/設計書.md#sec-7-1) の一覧にある）で、`app/bin/` の絶対パスを使い、`node <活動フォルダ>\app\bin\lmo-launch.mjs <cc の引数>` の形で起動する（打つ形と終了コードは組 A の [§2.10](../01.全体構成/設計書.md#sec-2-10)）。今のフォルダを引き継ぎ、そこで cc を起こす。処理の順は次のとおりである
  1. 自分のプロセスの環境変数に、渡す変数を足す。`OTEL_LOG_RAW_API_BODIES` を `file:<出力先>` にし、`OTEL_LOG_TOOL_CONTENT` を有効にする（[§3.3](#sec-3-3) の「ランチャのプロセスだけ」の 2 つ）。transcript を残させる `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` も有効にする（下の「Claude Code が起こすときの transcript」）。ユーザ settings にもある変数は足さない（規則 1）
  2. cc の引数から、セッションの id を決める（下の「セッションの id の決め方」）。ランチャが UUID を作るときは、`--session-id <UUID>` を cc の引数の前に足す（`claude --session-id <UUID> <cc の引数>`。docs ed2bfc5 L61166）
  3. 起動の記録を `<データの根>\run\launch\<YYYY-MM-DD>.jsonl`（日付は起動の UTC）に 1 行で追記する（下の「起動の記録」）
  4. `claude` を子プロセスとして起動し、標準入出力をそのままつなぐ。cc が終わったら、cc の終了コードで終える
- セッションの id の決め方: cc の引数の語（`--` の語より前のもの）を、名前の一致か `<名前>=` で始まるかで見て、次の上から順に最初に当たったものにする
  - `--resume`・`-r`・`--continue`・`-c`・`--from-pr` のどれかがある: 既存のセッションを続ける起動とし、UUID を作らない（docs ed2bfc5 L61118・L61134・L61164）。記録の `session_id` は null
  - `--session-id` がある: 利用者が渡した UUID をそのまま使い、記録する
  - どれも無い: UUID（`node:crypto` の `randomUUID`）を作って渡す
- 起動の記録（`run\launch\` の 1 行。UTF-8、LF、1 行 1 JSON。cc の引数はプロンプトを含みうるので記録しない）

| 項目 | 型 | 中身と例 |
|---|---|---|
| `v` | 数 | 形の版（初版は 1） |
| `ts` | 文字列 | 起動の時刻（UTC、ISO 8601。例 `2026-11-02T01:23:45.678Z`） |
| `session_id` | 文字列か null | cc に渡したセッションの UUID。取込の確かめ（下）が `index.jsonl` の `session_id` と比べる。続ける起動は null |
| `session_source` | 文字列 | `generated`（ランチャが作った）・`user`（利用者が `--session-id` で渡した）・`resume`（続ける起動） |

- 失敗のとき（終了コードの値は組 A の §2.10）
  - 起動の記録を書けない: cc を起こさずに、標準エラーに理由を出して終える。記録の無い T2 の run を作らない
  - `claude` を起こせない（見つからない、起動の例外）: 標準エラーに理由を出して終える。書いた起動の記録には transcript ができず、下の確かめで比較から外れる
- raw body は file モードだけを使い、`=1`（inline）は使わない。出力先（H-17）は `<データの根>\api-bodies\` である
  - cc はそこに要求・応答ごとのファイルと `index.jsonl` を書く（docs ed2bfc5 L76436・L76447・L76458）
  - raw body は受信サーバを通らないので、マスクの規則（[§2.3](#sec-2-3)）は当たらない。保持は [§2.1](#sec-2-1)
  - V-2b の記録の `v2b\` は、これと別に残す
- 届いたかの確かめ（EN-03c）: 取込は、毎回、`run\launch\` の `session_id` のある起動をすべて確かめ、取込の記録（H-12 の `launch_checks`。[§2.4](#sec-2-4)）に書く。確かめのために、`run\launch\` と `api-bodies\index.jsonl` を毎回初めから読む（起動 1 回が 1 行、`index.jsonl` はランチャのセッションの要求 1 件が 1 行で、どちらも小さい）
  - 確かめが済むのは、そのセッションの transcript が書いている途中（[§2.4](#sec-2-4) の 30 分）でなくなった回か、起動から 24 時間を過ぎても transcript が無い回である。済むまでは `pending` に数える。24 時間は、起こしたセッションで最初のやり取りをするまでの時間より十分長く置いた値である
  - 済んだ起動は、`index.jsonl` にそのセッションの行があり、transcript もあれば `ok` に数え、どちらかが無ければ `missing` に入れる。`missing` の起動は T1 と T2 の比較から外す（Phase 3 の比較の手順が `launch_checks` を読む）
  - 続ける起動（`session_id` が null）は確かめない
  - Phase 3 の初回は、ランチャで 1 セッション起動し、そのセッションが `launch_checks` の `ok` に数えられた（`missing` に無い）ことで確かめてから、T1 と T2 の比較に使う
- Claude Code が起こすときの transcript: Claude Code が Bash・PowerShell などのツールからランチャを起こすと、ランチャとランチャが起こす cc は、Claude Code が付けた入れ子の印（`CLAUDE_CODE_CHILD_SESSION`）を受け継ぐ。入れ子の対話のセッションは transcript を残さない（docs ed2bfc5 L63880・L27995。`-p` のセッションは残す）。ランチャは、どの起こされ方でも `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` を有効にし、対話のセッションにも transcript を残させる（docs ed2bfc5 L63958）
  - 作業指示者が自分のターミナルからランチャを起こすときは、入れ子にならず、この変数は効かない【推定】（docs は入れ子のときの働きだけを書く）
  - Claude Code が起こしたランチャのセッションも、作業指示者の `--resume` の一覧と入力の履歴に出る

**理由**

- `OTEL_LOG_RAW_API_BODIES` はユーザ settings に置かない（回答で決まったこと）。プロセスのスコープの変数は、ランチャを通さないセッションには効かない（計画書の EN-02）
- 日常のセッションをランチャに替えると、IDE・Desktop のセッションは替えられず、利用者が起動に別の命令を使うことになる（[計画書 §1.3](../../00.活動計画/活動計画書.md#sec-1-3) の「操作を増やさない」に合わない）
- 本環境では transcript の `requestId` で突合できる（2.1.310 の `-p` で 7 件中 6 件。外れは transcript に出ない compact の 1 件。[1-10 §3.3](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-3-3)）。経路 (ii) が要るのは、T1 で取れないリクエストに限られる
- Node.js で書けば Windows PowerShell 5.1 の件に当たらず、組 A の言語（[組 A §3](../01.全体構成/設計書.md#sec-3)）とそろう
- transcript を残させるのは、ランチャのセッションで T1（transcript の突合）と T2（raw body）を比べるためである。統合の図 2 のとおり、ランチャは作業指示者も Claude Code も起こす
- inline を使わないのは、本文が OTel のイベントに入って S2 の 1 行が大きくなるためである。file モードなら、イベントには本文の代わりにファイルの位置（`body_ref`）だけが入る。受信の本文の大きさの上限（[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)）は、inline を使わないこの前提で置く

**別の案**

| 案 | 長所 | 短所 |
|---|---|---|
| 日常もランチャで起動する（`claude` の名前でランチャを呼ぶ別名を作る） | 経路 (ii) が日常のセッションにも効く | 他のリポジトリの作業でも会話の全体がディスクに書かれ、回答の趣旨に合わない。IDE・Desktop のセッションには効かない |
| ランチャを PowerShell 7 のスクリプトにする | Node.js が無い端末でも動く | 言語が増える。Windows PowerShell 5.1 から起こすと変数が届かない例がある（[1-1 §7](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)） |

職場（Phase 7）で transcript の `requestId` が付かなければ、経路 (ii) の効く範囲を決め直す（[計画書 §7](../../00.活動計画/活動計画書.md#sec-7) #8。割り当て表の G2-03・G2-09。統合）。

<a id="sec-1-4"></a>
### 1.4 計測用のセッションの起動

組 C の申し送り（L1 の hook をユーザ settings に置くと、probe と比較実験のセッションでも L1 が動く。[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）への答えである。

**決めたこと**: Claude が起動する計測用のセッション（probe と Phase 3 の比較実験。`-p` と対話）は、次の形で起動する。日常のセッション（[J-19](../../01.基礎調査/作業指示者裁定待ち事項.md)）の起動は変えない。

```text
claude --setting-sources project,local --settings <計測用の settings ファイル> --permission-mode <固定する mode> --model <完全なモデル ID> …
```

- `--setting-sources project,local` で、ユーザ settings を読まない（docs ed2bfc5 L61167）。ユーザ settings の L1 の hook と OTel の変数が外れる。plugin の有効化も外れる見込みである（下の【推定】の注）
- 計測用の settings ファイルに次を書く。ファイルは plugin の名前を含むので、scratchpad に置き、repo に入れない（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意と同じ扱い）
  - `remoteControlAtStartup` を false にする
  - `enabledPlugins` で、比べる相手の測定（前回の基線）と同じ plugin の集合を true にし、それ以外を false にする
  - `env` に OTel の変数を書き、送り先を下の計測用の受信にする
- 受信は、計測ごとに別の lmo-receiver を起動する。データの根を `probe-<版>\` の下の計測ごとのフォルダにし、待ち受けの番号を日常の番号と別（例 4319）にする（組 A の [§4](../01.全体構成/設計書.md#sec-4) の `LMO_DATA_DIR`・`LMO_OTLP_PORT`）。日常の lmo-receiver と並べて動かせ、計測のデータが日常の S2 に混ざらない
  - 計測ごとのフォルダの名前は `<YYYY-MM-DD>-<計測の名前>`（日付は計測を始めた UTC。計測の名前は ASCII の小文字・数字・ハイフン。例 `probe-<版>\2026-11-02-recheck\`）。組 A の [§4](../01.全体構成/設計書.md#sec-4) の名前の規則に合わせた
- 計測用のセッションはランチャを経ずに、計測の手順（Claude が書く）が上の形で直接起こす。raw body が要る計測（T1 と T2 の比較）では、ランチャの処理の順の 1（[§1.3](#sec-1-3)）と同じ変数を、起こすプロセスの環境変数で渡し、出力先を計測のデータの根の `api-bodies\` にする（ユーザ settings を読まないので、規則 1 の上書きは起きない）
- セッションの記録: 計測の手順は、`--session-id` で UUID を渡して起こし、計測のデータの根の `run\measure\<YYYY-MM-DD>.jsonl`（日付は起動の UTC）に 1 行で書く。`--resume` で続ける計測では、続けた後のセッションの `session_id` が記録に無ければ足す
  - 1 行の項目は、ランチャの起動の記録（[§1.3](#sec-1-3) の表）と同じである。違うのは、書き手が計測の手順であること、`session_source` が `generated` か `resume` で、`resume` の行も続けた後のセッションの `session_id` を持つこと、条件の名前 `condition`（文字列か null。ASCII。例 `hook-on`）を足すことである
  - 日常の取込は、`probe-<版>\` の下の計測ごとのデータの根の `run\measure\` にあるセッションの transcript を読まない（[§1.6](#sec-1-6) の欠けにも、組 B の `transcript_only` の行にも入れない。[§2.4](#sec-2-4)）。そのセッションの L1 のラベルと `SessionStart` の記録も、日常のデータの根にあっても読まない（下の hook の記録の書き先を渡し忘れたときの備え）。除くセッションの集合は、取込のたびに `probe-*\*\run\measure\` のファイルを初めから読んで作る（計測 1 回が数行で小さい）
  - 計測用の取込（計測のデータの根で動く lmo-ingest）は、自分のデータの根の `run\measure\` にあるセッションの transcript だけを読む
- transcript: `-p` の計測用のセッションは transcript を残す。Claude Code がツールから起こす対話の計測用のセッションは、入れ子として扱われ、transcript を残さない（docs ed2bfc5 L63880・L27995。Claude Code が開いたターミナルを経て起こしても同じ）
  - transcript を使う計測（思考トークンの突合、T1 と T2 の比較、サブエージェントの `agentId`）では、起こすプロセスの環境変数で `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` を有効にする（docs ed2bfc5 L63958）。計測用の settings ファイルの `env` に書いて効くかは確かめていないので、プロセスの環境変数で渡す
  - transcript を使わない計測では、transcript が無いことを測定の条件として記録する
- L1 を測る条件では、L1 の hook を、probe の作業フォルダの project settings か計測用の settings ファイルの `hooks` に書いて足す
- hook の記録の書き先: 計測用のセッションを起こすプロセスの環境変数で、`LMO_DATA_DIR` を計測のデータの根にして渡す（`CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` と同じ渡し方）。cc が起こす hook はこの変数を受け継ぎ【推定】、L1 のラベル（組 C の [H-18](../03.作業分類タグ/設計書.md#sec-4-1)）と `SessionStart` の記録（H-28）を、計測のデータの根に書く（データの根の決め方は組 A の [§4](../01.全体構成/設計書.md#sec-4)）
  - 変わるのは書き先だけである。hook の `args` は日常のデータの根の `hooks\` の写しを指してよい。分類の部品と規則のデータは、スクリプトの場所から読む（組 A の [§2.6](../01.全体構成/設計書.md#sec-2-6)）
  - 計測用の settings ファイルの `env` に書いて hook に届くかは確かめていないので、プロセスの環境変数で渡す
  - L1 の Mod 版（Phase 3）の置き場所を決めるときも、計測用のセッションでは計測のデータの根に書く形にする（組 C の H-18）
  - L1 の hook を足した最初の計測用のセッションで、レコードが計測のデータの根にあり、日常のデータの根に無いことを確かめる（[§6](#sec-6) の 13）
- 切り替えた最初の計測（計画書 Phase 3 の着手前の版の再確認）で、前の起動の仕方（ユーザ settings を読み、`--settings` で plugin を無効にする）の run と並べる。属性集合・`plugin_loaded`・`hook_registered`・`effort` の値が同じかを確かめ、違えばその計測を新しい基線にして、違いを報告書に書く。同じ回に、`CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` を有効にした対話の計測用のセッションに transcript が残ることを確かめる。変数を有効にして強制終了したセッションも並べ、transcript の欠けを、入れ子の扱いによるものと強制終了によるものとに分ける（[§6](#sec-6) の 11）

**理由**

- docs は、settings に書いた hook を 1 つだけ止める手段は無いとする（docs ed2bfc5 L66885）
- ユーザ settings に OTel の変数が入ると、プロセスの環境変数で渡した送り先はユーザ settings の値で上書きされる（[§1.1](#sec-1-1) の規則 1）。ユーザ settings を読まなければ、計測用の送り先が効く
- Phase 1 の probe は、受信スクリプトを 4318 番で動かした（[1-10 §1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-1)）。日常の lmo-receiver が同じ番号で動いていると、番号がぶつかる
- セッションの記録で分けるのは、transcript の置き場所（cc の設定フォルダの `projects`）が日常と同じで、データの根を分けても transcript は分かれないためである。記録が無いと、日常の取込は計測のセッションを受信サーバが止まっていた間のセッションとして数え、計測用の取込は日常のセッションを集計に足す。セッションの id で分ければ、計測を行う作業フォルダに依らない
- hook の記録の書き先を渡すのは、hook の記録の置き場所がデータの根で決まり、書く側に計測のデータの根を渡せば分かれるためである。渡さないと、計測のプロンプトの L1 のレコードが日常のデータの根に書かれ、計測の S1 に入らない。日常の取込で除かなければ、日常の `l1_hook_record` に入って、J-12 の判定と見直しのきっかけ（[組 C §1.1](../03.作業分類タグ/設計書.md#sec-1-1)）に混ざる
- 対話の計測で transcript を残させるのは、Phase 3 の比較実験の思考トークンと T1・T2 の比較が transcript に依るためである。Phase 1 の i3・i4（Claude が新しい窓で起動した対話。[1-1 §1](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-1)）に transcript が無かったことも、入れ子の扱いで説明できる【推定】（[1-2 §3.1](../../01.基礎調査/02.思考トークン取得経路/調査報告書.md#sec-3-1)）

**別の案**

| 案 | 長所 | 短所 |
|---|---|---|
| `--settings` に `disableAllHooks` を書く | ユーザ settings を読んだまま起動できる | probe の作業フォルダの hook と、入れた plugin の Mod も止まり（docs ed2bfc5 L66885・L41962）、hook ありの条件を測れない |
| L1 の hook が特定の環境変数を見て、何もせずに終える | 起動の仕方を変えずに済む | hook のプロセスは起動するので、hook なしの条件にならない |
| 計測用に別の `CLAUDE_CONFIG_DIR` を使う | ユーザの設定の全体から切り離せ、transcript も日常と分かれる | transcript と plugin の置き場所も変わり、認証をやり直すことになる【推定】 |
| 計測のセッションを、作業フォルダ（`projects` の下のフォルダ）で日常の取込から除く | 起動の手順を変えない | 計測を日常の作業フォルダで行うと除けない |

- 【推定】`--setting-sources` から `user` を外すと、ユーザ settings の `enabledPlugins`・`permissions.defaultMode`・`hooks` も読まれない。docs は SDK の同じ指定を、ファイルの settings の読み込みの選択と書く（docs ed2bfc5 L101470・L101639）。上の最初の計測の並べ方で確かめる
- changelog には、`user` を含まない `--setting-sources` で background の cleanup が `cleanupPeriodDays` を無視して 30 日より古い履歴を消す不具合があり、2.1.101 で直った（docs ed2bfc5 L10894。版の見出しは L10857）。今の基線の版では当たらない
- 日常のセッションの hook なしの基準を取る期間の作り方は、組 C の決めたとおり、Phase 3 の測定の手順で決める

<a id="sec-1-5"></a>
### 1.5 受信サーバの起動（EN-05）

**決めたこと**: 受信サーバ lmo-receiver は常駐させず、作業指示者か Claude Code が、cc を使う前に起動・停止のスクリプト lmo-ctl の `start` で起こし、`stop` で止める（J-29。[§3.1](#sec-3-1)）。名前と起動の形は組 A の [H-05](../01.全体構成/設計書.md#sec-7-1)、lmo-ctl の振る舞いは[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) にある。

- lmo-receiver は、待ち受けの番号がすでに使われていたら、受信サーバの動作の記録（項目の名前と書くファイルは組 A の [§2.9](../01.全体構成/設計書.md#sec-2-9)）に残して終える。`start` を重ねて打っても、1 つだけ動く（受信サーバの振る舞いは組 A の [§2.1](../01.全体構成/設計書.md#sec-2-1)・[§2.2](../01.全体構成/設計書.md#sec-2-2)）
- 起動していない間の欠けは [§1.6](#sec-1-6)、取込の頻度は [§2.4](#sec-2-4)、transcript の削除より前に取り込むことは [§2.2](#sec-2-2) にある

<a id="sec-1-6"></a>
### 1.6 受信サーバが止まっているとき（EN-06）

**決めたこと**

- cc の側には何も足さない
  - 受信サーバが止まっていても cc の操作は止まらない見込みで、Phase 3 で確かめる（[V-ID 別紙 §2](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の「受信サーバ停止中の cc の挙動」の行）
- 止まっていた間の OTel の記録は欠ける
  - cc が送り直すかは【推定】で、組 A の 503 の扱い（[組 A §9](../01.全体構成/設計書.md#sec-9) の 2）と同じ回に確かめる
- 欠けは取込で数える（欠けの数え方の正本は本節）
  - 比べる範囲: その回に読んだ transcript のセッションごとに、S1 の OTel の元の表（S2 から入れた表。その回に読んだ S2 の行を入れた後に比べる）に同じ `session_id` の行が 1 件も無いものを欠けとする。計測用のセッション（[§1.4](#sec-1-4) の記録）と、書いている途中のファイル（[§2.4](#sec-2-4) の 30 分）のセッションは比べない（書いている途中のセッションは、OTel の記録が送信の間隔の分だけ遅れて届きうるため）
  - 取込の記録（H-12 の `otel_gaps`。[§2.4](#sec-2-4)）に、欠けたセッションの数、`session_id` の一覧、transcript の最初と最後の時刻を書く。`session_id` は本文でなく、後で `transcript_only` の行と結ぶのに使う
  - 同じセッションは、transcript が変わった回ごとに数え直す。`otel_gaps` はその回に見た欠けで、回をまたいで足すと二重になる。期間の欠けの数は、S1 の `transcript_only` の行のセッションで数える（組 B の [H-26](../02.データモデルと集計/設計書.md#sec-6-1)）
- 欠けたセッションの usage は、取込が transcript から読んだ値（[§2.4](#sec-2-4)）で集計に足す
  - 足すのは OTel の記録にそのセッションが 1 件も無い場合に限り、二重に数えない。行の形は組 B の集計の正本の規則（[H-26](../02.データモデルと集計/設計書.md#sec-6-1)）にある
  - 組 A の縮退運用（[H-25](../01.全体構成/設計書.md#sec-7-1)）と同じ形である
- セッションの途中で受信サーバが止まった分（OTel の記録が 1 件以上あるセッションの一部の欠け）は、欠けに数えず、補わない。そのセッションは OTel の記録で集計し、止まっていた間のリクエストは集計に入らない。途中の欠けの大きさは Phase 3 で確かめる（[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 6）

**理由**

- [計画書 §5.1](../../00.活動計画/活動計画書.md#sec-5-1) の「受信サーバの停止中にデータが欠落する」の対策（transcript からの遡り取込で補う）に、欠けの大きさを見る手段を足した
- docs は、設定した exporter の失敗を debug log の `[3P telemetry]` の行に出すとする（docs ed2bfc5 L75548）。日常のセッションには debug log が無いので、欠けは取込の側で数える
- 途中の欠けを数えないのは、組 B の結合の規則（H-26）が transcript から足す行をセッションの単位（`transcript_only`）でだけ作り、途中の欠けを補う行を持たないためである。Phase 3 で途中の欠けが大きいと分かったら、数える規則を足す（統合 §8 の 6 の崩れたときの直し）

<a id="sec-1-7"></a>
### 1.7 設定の手順（作業指示者向け）

ユーザ settings に置くもの（[§1.2](#sec-1-2) の `env` と、組 C の [§2.2](../03.作業分類タグ/設計書.md#sec-2-2) の `hooks`）は、Claude が手順を書き、作業指示者が設定する（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意、J-31）。J-29 の「手順書は作らない」は起動・停止のスクリプトのことで、この手順は対象ではない（[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の計画書との関係）。下の成果物・時期・順序は、実用性のクロスレビューの I5 の修正案 1 で、[作業指示者の態度表明（採用。2026-10-27）](../レビュー/クロスレビュー_Phase2設計_実用性_2026-10-27.md#i5-作業指示者の態度表明)で決まった。

**決めたこと**

- 成果物: 作業指示者向けの設定の手順を、Phase 3 の報告書のフォルダ（`reports/03.PoC/` の下）に別紙として置く（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3) の成果物）
  - 手順には、JSON の断片と、既存の設定への足し方を書く。値は設計の値（組 A の H-08 の受け口、組 B の H-15 の環境ラベル）を指す
  - 作業指示者の環境だけの値（データの根を展開した絶対パスなど）は、手順を渡すときに作業指示者に確かめて埋め、repo に置かない
- 時期: Phase 3 の着手時（版の再確認の後）に、Claude が書く
- 順序（手順に書く）
  1. ユーザ settings を変える前に、受信サーバが止まっているときの cc の挙動を、計測用のセッション（[§1.4](#sec-1-4) の形で、送り先を受信していない番号にする）で確かめる（[§6](#sec-6) の 2）。cc の操作が止まるなら、設定せずに作業指示者に諮る
  2. `env` を先に設定し、日常のセッションの hook なしの基準を取ってから、`hooks` を設定する。基準を取る期間の作り方は、Phase 3 の測定の手順で決める（[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）
  3. 設定を変えた後は、開いている cc のセッションを起動し直す（変えた後の起動から効く。[§1.1](#sec-1-1)）
- 設定が効いたことの確かめ（手順に書く。Claude が行う）
  - `env` の後: 受信サーバを起動し、順序の 3 で起動し直した日常のセッションでプロンプトを 1 つ送ってから 1 分以上待つ（metrics の送信の間隔の既定は 60 秒。docs ed2bfc5 L75626）。Claude が次を確かめる
    - その日の `raw\logs\`・`raw\metrics\`・`raw\traces\`（組 A の [H-06](../01.全体構成/設計書.md#sec-7-1)）に、そのセッションの行がある（traces が届くことを含む）
    - その行の resource の属性に `lmo.env` がある
    - 受信サーバの動作の記録（組 A の [§2.9](../01.全体構成/設計書.md#sec-2-9)）で、その間に 400・413・415・503 の応答が増えていない
    - マスクの確かめ（[§2.3](#sec-2-3) の「確かめ方」の日常の初回）を同じ回に行う
  - `hooks` の後: 日常のセッションでプロンプトを 1 つ送った後、日常のデータの根の `labels\`（組 C の [H-18](../03.作業分類タグ/設計書.md#sec-4-1)）にそのプロンプトのレコードがあり、`session-start\`（H-28）にそのセッションの記録があることを確かめる
  - 確かめられなければ、作業指示者に知らせ、下の戻し方で戻すかを諮る
- 戻し方（手順に書く。外すのは作業指示者）
  - 手順に、足したキーの一覧（[§1.2](#sec-1-2) の表の変数と、`hooks` の L1 と `SessionStart` の項）と、外す JSON の断片を書く
  - cc の起動や操作が遅くなる・止まる、他のリポジトリの作業で OTel や hook の誤りが出る、などの不具合が出たら、`env` の足したキーを外す（hook だけの不具合なら `hooks` の項だけを外す）。外した後は、開いている cc のセッションを起動し直す
  - 外した日時と理由は、Claude が Phase 3 の報告書に書く。外した後のセッションは OTel の記録が無いので、取込が欠け（[§1.6](#sec-1-6)）に数え、transcript の usage で足す。報告書の日時で、受信サーバの停止による欠けと分けて読む

**理由**

- 順序の 1: ユーザ settings の `env` はすべてのリポジトリのセッションに効き、手動の起動（J-29）では、受信サーバが止まっている時間が普通にある。確かめる前に設定すると、全リポジトリの作業に影響しうる。計測用のセッションなら、ユーザ settings を変えずに確かめられる
- 順序の 2: L1 の hook を日常のセッションに入れると、日常の hook なしの基準（J-12 の判定で上乗せを測る元）が取れなくなる
- 手順を Phase 3 の着手時に置くのは、日常のセッションの測定（J-12 の判定、計画書 Phase 3 の確認観点）がユーザ settings の設定を前提にするためである
- 確かめと戻し方を手順に入れるのは、ユーザ settings の誤りがエラー無しで効かないこと（[§1.1](#sec-1-1) の理由）と、すべてのリポジトリの作業に及ぶ不具合に、設定の直後に気付いて戻せるようにするためである

**別の案**: 手順を Phase 4 の利用手順に入れる。長所は計画書の成果物を変えないこと、短所は Phase 3 の前半に手順が無く、基準を取り損ねうることである。

## 2. データ保全とプライバシー

<a id="sec-2-1"></a>
### 2.1 保持期間とバックアップ（PV-01。圧縮は §3.2）

**決めたこと（本活動の間）**

| `SessionStart` の記録、品質の記録 | `session-start\`（組 C の [H-28](../03.作業分類タグ/設計書.md#sec-4-1)）、`quality\`（組 A の [H-30](../01.全体構成/設計書.md#sec-7-1)） | 消さない | 同上 |
| raw body | `api-bodies\` | 消さない | 同上。ランチャの run ごとに、突合を終えて要らなくなったら消してよい |

| 動作と取込の記録 | `run\` | 消さない（小さい） | 本活動の終わり |

- 自動で消す仕組みは、本活動では作らない
- 本活動の終わりに、消すものの一覧を Claude が作り、作業指示者の確かめの後に消す
- バックアップは自動では取らない。消えると作り直せないもの（S2、L1 のラベルと `SessionStart` の記録、raw body、組 B の品質の記録と職場の組の単価表、ハッシュの鍵）を、Phase の区切りに作業指示者が外部の記憶装置に写す手順を、Claude が書く（写すかは任意）
  - 設定のファイル `lmo-settings.json` も写す。作り直せるが、失うと既定に戻り、L2 が無効になって受信がプロンプトの本文を落とす（[§2.3](#sec-2-3)）
  - 写しもクラウド同期の対象のフォルダに置かず、元と同じく本活動の終わりに消す
  - S1 は S2 から作り直せるので写さない

**理由**

- 回答は「本活動が終わったら、または不要になったら削除する」で、期限を決めていない。S2 は、Phase 3〜6 で取込を直すたびに読み直す元である
- 収集データはクラウド同期の対象のフォルダに置かない（回答）。写しにも同じ規則を当てる

**別の案（バックアップ）**: 決まった時刻に別のフォルダへ自動で写す。長所は手間が無いこと、短所は同じ端末の中の写しで端末の故障に効かず、使う容量が倍になることである。

正式リリース物の保持の既定は決めない（[§0.5](#sec-0-5)）。

<a id="sec-2-2"></a>
### 2.2 transcript の保持（cc の側。PV-01 の保持）

**決めたこと**

- `cleanupPeriodDays` は延ばさず、既定の 30 日のままにする（ユーザ settings を変えない）
- 削除より前に取り込む。取込は、受信サーバを起動するたびと、動いている間の取込の間隔（既定 1 時間）ごとに動く（[§2.4](#sec-2-4) の頻度）
  - 受信サーバは手動で起動する（J-29。[§1.5](#sec-1-5)）ので、1 日 1 回の取込は保証されない。30 日の間に一度は受信サーバを起動すれば、削除より前に取り込める【推定】（[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 2）
- 取込の記録に、最後の取込の時刻と、S2 に届いた `retention_sweep` の `period_days` を書く。最後の取込から 14 日を過ぎたら、lmo-ctl の `start` と lmo-report が警告を出す。どちらも、取込を起こす前の最後の取込の時刻で判定する
- 延ばすことにしたときの条件: cc 2.1.310 以降にする。2.1.309 以前は、非常に大きい値で最近のファイルが消えうる（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D69）。適用値は `retention_sweep` の `period_days` で確かめる（[計画書 §5.1](../../00.活動計画/活動計画書.md#sec-5-1)）

**理由**

- 取込は受信サーバの起動の直後に動く。受信サーバは cc を使う前に起動するので、起動した日には、その日までの transcript が取り込まれる
- 警告の役目は、受信サーバを起動しているのに取込が止まっている（失敗が続く）ことに、削除より前に気付いて直すことである。14 日は 30 日の半分で、警告から削除まで 16 日が残る
  - lmo-ctl の `start` も lmo-report も打たない期間には、警告は出ない。起動しない期間が 30 日を超えたことに気付くのは次の起動のときで、30 日を過ぎた分は消えている（残存リスク。[§7](#sec-7)）。気付く手段は Phase 4 で検討する（[統合 §6.3](../99.設計まとめ/設計書.md#sec-6-3)）
- 警告を lmo-ctl の `start` で出すのは、受信サーバを起動するときに作業指示者か Claude Code が目にするためである
- 延ばすと、すべてのリポジトリの transcript と付随のファイル（file snapshots、tool の結果のファイルなど。docs ed2bfc5 L16161 の一覧）が `~/.claude` に長く残る
- 取込が残すのは transcript の usage と鍵だけ（[§2.4](#sec-2-4)）で、取込の規則の誤りに後から気付くと、30 日より古い transcript からは取り込み直せない。取り込む値は 1 行の中のキーで、規則の誤りの余地は小さい【推定】ので、延ばさない側を選んだ

**別の案**: 本活動の間は延ばす（例 90 日）。長所は、取込を止めた期間や取込の規則の誤りに強いこと、短所は、transcript と付随のファイルが `~/.claude` に長く残ること（上の理由の 4 点目）と、ユーザ settings を変えることである。次のときは、この案に切り替える。

- Phase 3 の取込の試作で規則の誤りが見つかったとき（[§6](#sec-6) の 5）
- 受信サーバを 30 日の間に一度も起動しない期間が出たとき（[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 2）

<a id="sec-2-3"></a>
### 2.3 マスクと識別属性（PV-03・PV-04・H-04・H-32）

**決めたこと（マスクの規則。H-04）**

| 対象 | 属性（出る所） | 本環境 | 正式リリース物の既定 | 当てる所 |
|---|---|---|---|---|
| 識別属性 | `user.email`・`user.account_uuid`・`user.account_id`・`organization.id`・`user.id`（記録の属性と resource の属性のどちらでも） | 鍵付きのハッシュに替える | 同じ | 受信（S2 に書く前） |
| プロンプトの本文 | `user_prompt` イベントの `prompt`・`prompt_text`、traces の `claude_code.interaction` span の `user_prompt` | 残す（本環境は L2 の切り替えを有効にする。H-31） | 落とす | 受信。組 C の L2 の切り替え（[組 C §1.7](../03.作業分類タグ/設計書.md#sec-1-7)。設定の置き場所は H-31）が有効なら残し、無効なら `<dropped>` に替える。`prompt_length` は残す |
| 応答の本文、tool の引数と内容、raw body | `assistant_response` の本文、`tool_parameters`・`tool_input`、`tool.output`、`api-bodies\` のファイル | 記録するなら残す（記録するかは [§3.3](#sec-3-3) の変数で決まる） | 変数を無効にするので届かない | — |
| 詳細ベータトレースの本文 | `system_reminders` 属性、`claude_code.system_prompt` イベント | 詳細ベータトレースを使わない（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) R-14）。使うと決めたら、プロンプトの本文と同じ規則に足す | 同じ | 受信 |
| リポジトリの属性 | `vcs.repository.url.full`・`vcs.owner.name`・`vcs.repository.name`・`vcs.provider.name`（metrics とイベントの属性。`OTEL_METRICS_INCLUDE_REPOSITORY` が有効なとき。[§1.2](#sec-1-2)。docs ed2bfc5 L76098） | 平文のまま S2 と S1 の `attrs_json` に残す（保存の形は組 B の [§1.8](../02.データモデルと集計/設計書.md#sec-1-8)）。報告書の集計では「リポジトリ 1」のような番号に置き換える | 同じ（変数を有効にしたときだけ届く） | 報告書を作るとき（番号への置き換え） |

- 当てる位置（受けた OTLP の JSON）
  - 識別属性: resource の属性（3 つの信号の `resource.attributes`）と、記録の属性（logs の `logRecords[].attributes`、metrics のデータ点の `dataPoints[].attributes`（`sum`・`gauge`・`histogram` などの下）、traces の `spans[].attributes` と `spans[].events[].attributes`）のどこにあっても当てる
  - プロンプトの本文: logs の `logRecords[].attributes`（`user_prompt` イベント）と、traces の `spans[].attributes`（interaction span）に当てる
  - 識別属性の値が文字列でないときは、ハッシュを当てずに `<dropped>` に替え、件数を受信サーバの動作の記録（組 A の [§2.9](../01.全体構成/設計書.md#sec-2-9)）に残す。プロンプトの本文は、値の型に依らず上の表の規則による
- ハッシュは、HMAC-SHA-256 の 16 進の先頭 16 字に `h1:` を付けた値にする
  - 同じ値は同じハッシュになるので、セッションやアカウントの区別は残る
  - 先頭 16 字（64 ビット）で足りる: ハッシュに替える値は、1 つの端末で使う利用者・アカウント・組織の識別子で、種類が少ない。64 ビットなら 1 万種類でも、2 つが同じハッシュになる確率は 1,000 億分の 1 より小さい（誕生日の近似で、種類の数 n に対して n² / 2^65）
- 鍵: 端末ごとの 32 バイトの乱数（`node:crypto` の `randomBytes`。HMAC-SHA-256 の出力と同じ長さ）を、16 進 64 字の 1 行で、データの根の `config\` の下の鍵のファイルに置く
  - 鍵を読み、ハッシュを計算する関数は、`app/lib/` の 1 つの部品に置く（置き場所の規則は組 A の [§2.6](../01.全体構成/設計書.md#sec-2-6)）。受信サーバが使い、取込が使うことにしたとき（[§6](#sec-6) の 9）も同じ部品で同じ鍵を読む
  - 受信サーバは、待ち受けを始めた後、要求の処理を始める前に鍵を読む。鍵のファイルが無いときだけ、鍵を作って書く（一時のファイルに書いてから名前を替える）。番号の衝突で終える 2 つ目の受信サーバは、鍵に触れない
  - 鍵のファイルがあるのに読めない、または形が違う（16 進 64 字の 1 行でない）ときは、新しい鍵を作らず、受信サーバの動作の記録（組 A の §2.9）に残して起動をやめる（終了コードは組 A の [§2.10](../01.全体構成/設計書.md#sec-2-10)、`start` の表示は[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）。直すときは、鍵のファイルをバックアップ（[§2.1](#sec-2-1)）から戻す
  - 計測ごとのデータの根（[§1.4](#sec-1-4)）には別の鍵ができ、ハッシュの値は日常と合わない。計測の比べ方は識別属性を使わない
- S1 では、組 B の列（[H-03](../02.データモデルと集計/設計書.md#sec-6-1)）にハッシュの値がそのまま入る。列名と型は組 B のまま変わらない
- 取込の側の差し込み口（組 A の [§2.2](../01.全体構成/設計書.md#sec-2-2)）には、今は何も当てない。取込は transcript の本文を読まない（[§2.4](#sec-2-4)）。transcript に識別属性が入っていたら、受信と同じ規則で替える
- 報告書の集計では、ハッシュの値も識別子として扱い、「アカウント 1」のような番号に置き換えて示す

**理由**

- 識別属性は全レコードに入る（[1-1 §3](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-3)）。集計に要るのは区別だけで、値そのものは要らない
- 受信の時点で替えるのは、S2 を DuckDB で探索した出力にも平文が出ないようにするためである。S2 から S1 を作り直しても、同じ鍵なら同じ値になる
- 鍵付きにするのは、メールアドレスの候補を並べてハッシュと照らす手で、元の値に戻されないようにするためである
- 鍵のファイルが読めないときに新しい鍵を作らないのは、作るとそれより前のハッシュの値と結べなくなり、気付かないまま集計の区別が分かれるためである。起動をやめれば、lmo-ctl の `start` の表示で気付ける。直すまでの間の OTel の記録は欠けるが、usage は取込が transcript から補う（[§1.6](#sec-1-6)）ので、新しい鍵で受け続けるより失うものが小さい
- `vcs.*` をハッシュに替えないのは、識別属性 5 つが集計で区別にだけ使われるのに対し、`vcs.*` はどのリポジトリの作業かを探索で読むために有効にした（[§1.2](#sec-1-2)）からである。`vcs.owner.name` には個人のアカウント名も入りうるので、報告書の集計では番号に置き換え、ライブ表示にも出さない（下の許可リストの条件 4）
- プロンプトの本文は、`OTEL_LOG_USER_PROMPTS` と traces を有効にすると、`user_prompt` の 2 つの属性に加えて interaction span の `user_prompt` 属性にも入る（docs ed2bfc5 L77286〜L77301）。計画書の既定の案は前の 2 つだけを挙げるので、3 つ目を足した
- L2 が無効なときに受信した本文を落とすのは、組 C が組 D に任せた点（組 C の [§1.7](../03.作業分類タグ/設計書.md#sec-1-7)）への答えである。誰かが cc の変数を有効にしても、仕組みの側の設定が無効なら残らない
- PV-04 は計画書の既定の案のままにした

**別の案（識別属性）**

| 案 | 長所 | 短所 |
|---|---|---|
| そのまま残す | 処理が要らない | S2・S1 の探索の出力に平文のメールアドレスが出る |
| S2 は受けたまま、S1 でだけ替える | S2 が受けたままの形になる | S2 を読む探索で平文が出る |
| 落とす | 最も単純 | アカウントの区別ができない（課金の形の違うアカウントを混ぜたとき分けられない） |
| 受信で鍵付きのハッシュに替える（採る） | 上の理由 | 鍵を失うと、それより前の値と結べない（鍵をバックアップの対象にした） |

S2 の 1 行の `body`（組 A の [H-06](../01.全体構成/設計書.md#sec-7-1)）は、この規則を当てた後の OTLP の JSON である。

**決めたこと（ライブ表示に出してよい項目。許可リスト。H-32）**

ライブ表示（経路は組 A の [§2.7](../01.全体構成/設計書.md#sec-2-7)、項目の形は組 B の [§1.12](../02.データモデルと集計/設計書.md#sec-1-12)）に出してよいのは、次の 4 つのすべてに当たる項目だけにする。当たらない項目は、マスクの後の通常の経路（S2 → 取込 → S1）で見る。

| # | 条件 | 当たらない例（通常の経路で見る） |
|---|---|---|
| 1 | 値が数（トークン数、所要時間、metrics の値など）か区分である。区分は、組 B §1.12 の列に値の一覧か形（正規表現）を決め、合わない値を決めた値（多くの列は `other`）に替えて出す | 本文系（プロンプト、応答、tool の引数と内容、raw body、system prompt）、エラーの文、ファイルのパス、コマンドの文字列 |
| 2 | 上のマスクの規則（H-04）の対象でない | 識別属性 5 つ（ハッシュに替えた後の値も）、プロンプトの本文の 3 か所 |
| 3 | 1 つのセッション・プロンプト・リクエスト・呼び出しを指す識別子でない | `session.id`・`prompt.id`・`request_id`・`client_request_id`・`agent_id`・`tool_use_id` |
| 4 | 利用者が付けた名前を値に持ちうる属性でない | `query_source`（サブエージェントの名前が入る。[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性)）、`skill.name`・`agent.name`、tool と MCP のサーバの名前、`vcs.*`（リポジトリと持ち主の名前） |

- 出してよい項目は、組 B §1.12 の列だけである。列を足すときは、先に上の 4 つに当てる
- 抜き出す元は、上のマスクの規則を当てた後の JSON である（組 A §2.7）
- セッションを分けて見るときは、`session.id` の代わりに、受信サーバが振る番号（組 B §1.12 の `session_seq`）を使う
- 本環境と正式リリース物で同じ規則にする

**理由（許可リスト）**

- 出してよいかは、マスクと同じくデータの性質で決まるので、規則をマスクの規則の側に置く。許可リストの形にするのは、版で増える属性（組 A の [§2.2](../01.全体構成/設計書.md#sec-2-2)）が、確かめる前にライブ表示に出ないようにするためである
- 数と区分だけなら、作業の中身はライブ表示に出ない。区分の値を一覧か形に限るのは、`model` などの区分の属性にも、環境によってはクラウドの提供元のリソースの名前のような、識別子を含む値が入りうるためである【推定】（[§6](#sec-6) の 16）
- 識別子を出さないのは、ライブ表示の画面を人に見せたり写したりしたときに、セッションやリクエストを特定する値が出ないようにするためである。セッションの区別は、受信サーバの中だけの番号で足りる

**確かめ方（Phase 3。マスクと許可リスト）**: 結果は Phase 3 の報告書に書き、合わなければ受信サーバを直してから日常の受信に使う（[§6](#sec-6) の 15）。

- 受信サーバを作ったとき（Claude。作った OTLP/HTTP の JSON の要求を受信サーバに送る試験）
  - 識別属性 5 つを、resource・logs の記録・metrics のデータ点・span・span のイベントの各位置に置いた要求: S2 の行で、どの位置の値も `h1:` で始まり、同じ値は同じハッシュになる
  - 文字列でない値の識別属性を置いた要求: `<dropped>` になり、件数が受信サーバの動作の記録（組 A の §2.9）に入る
  - プロンプトの本文 3 か所を持つ要求を、L2 の切り替えを無効（設定のファイルかキーが無い）にして送る: 3 か所とも `<dropped>` になり、`prompt_length` は残る。有効にして送ると、本文が残る
  - 鍵のファイルを形の違う中身にして起動する: 新しい鍵を作らず、起動をやめ、記録に残る
  - ライブ表示を購読して上の要求を送る: 配られた項目が組 B §1.12 の列だけで、識別子・本文・マスクの対象・`vcs.*` が無く、区分の列の一覧か形の外の値は決めた値（`other` など）に替わっている
- 日常の初回（[§1.7](#sec-1-7) の `env` の後の確かめと同じ回。Claude）: その日の S2 のすべての行で、識別属性 5 つの値が `h1:` で始まるか `<dropped>` であることを数える。本環境は L2 を有効にするので、本文が残ることも見る

### 2.4 補完取込（PV-05〜PV-08b・H-11・H-12）

**決めたこと（頻度。H-11）**

- lmo-ingest は次の契機で動く（括弧は取込の記録の `trigger` の値）。同時には 1 つだけ動く（ロックと 1 回の流れは組 A の [§2.8](../01.全体構成/設計書.md#sec-2-8)。起こすときの引数と手動の打つ形は組 A の [§2.10](../01.全体構成/設計書.md#sec-2-10)）
  - lmo-receiver の起動の直後（`receiver_start`）と、動いている間の取込の間隔（既定 1 時間。下の設定）ごと（`interval`）。lmo-receiver が子プロセスとして起こす
  - lmo-report の集計の前（`report`）
  - 手動（`manual`）と、手動の作り直し（`rebuild`。組 A の §2.8）
- ロックが取れないとき
  - `receiver_start` と `interval` は、その回を飛ばし、飛ばしたことを受信サーバの動作の記録（組 A の [§2.9](../01.全体構成/設計書.md#sec-2-9)）に残す（次の間隔で動く）。起動の直後の回も飛ばすのは、動いている取込（`report` か手動）が同じ範囲を読み、飛ばしても次の間隔まで遅れるだけだからである
  - `report`・`manual`・`rebuild` は、動いている取込が終わるのを待ってから動く（待つ間の取り直しの間隔と表示は組 A の §2.8）
- 取込が失敗した回（`status: error`）の後の動き（次の回の読み直し、lmo-receiver が次の間隔で起こすこと）と知らせ方は、組 A の §2.8 にある
- 受信サーバは手動で起動する（J-29。[§1.5](#sec-1-5)）ので、起動していない間は、lmo-report の前と手動のときにだけ動く。削除より前に取り込むことの扱いは [§2.2](#sec-2-2) にある
- 既定を 1 時間にするのは、S1 を 1 時間以内の新しさに保ち、1 回の取込の量を小さくするためである。受信から数秒で見たい数と区分は、ライブ表示（組 A の [§2.7](../01.全体構成/設計書.md#sec-2-7)）で見る。取込の間隔は、ライブ表示に出ない値（本文系、transcript から入る思考トークンなど）の新しさを決める

**決めたこと（取込の間隔の設定）**

| 項目 | 決めたこと |
|---|---|
| 単位と既定 | 分の整数。既定は 60 |
| 永続の値 | `<データの根>\config\lmo-settings.json`（組 C の H-31 の L2 の切り替えと同じファイル）のキー `ingest_interval_min`。例: 30 分にするなら、ファイルの JSON のオブジェクトに `"ingest_interval_min": 30` を足す |
| 一時の上書き | 環境変数 `LMO_INGEST_INTERVAL_MIN`。lmo-ctl の `start` を打つプロセスに渡すと、lmo-ctl が起こす lmo-receiver が受け継ぐ。ユーザ settings の `env` には置かない（cc のセッションが読む変数でなく、すべてのリポジトリのセッションに渡ってしまう。[§1.1](#sec-1-1)） |

| 範囲 | 5 分以上、1,440 分（24 時間）以下。下限は【推定】で、Phase 3 で取込の所要を測って見直す（[§6](#sec-6) の 14） |

**理由（取込の間隔の範囲）**

- 下限 5 分【推定】: 取込が動いている時間を全体の 1 割以下に保つため、下限を「ふだんの取込の所要の最大 × 10」以上にする。ふだんの取込（初回の取込を除く）の所要は未測定で、30 秒に収まると見て 5 分にした。Phase 3 で取込の記録の `started_at`・`ended_at` から所要を測り、所要の最大 × 10 が 5 分を超えたら下限を上げる。下限より短くしてもロックで取込は重ならないが、取込がほぼ切れ目なく動き、lmo-report の待ちが増える
- 書いている途中の 30 分（下の transcript の読み方）とは食い違わない。間隔を 30 分より短くすると、書いている途中のファイルを次の取込で読み直す回数が増える。読み直しは初めから行うので、長いセッションの transcript ほど取込の所要が延びる。その所要は、下限の見直しで測る取込の所要に入る
- 上限 24 時間: 最後の取込から 14 日で出す警告（[§2.2](#sec-2-2)）は、受信サーバが動いているのに取込が止まっていることに気付くためのものなので、間隔はそれより十分に短くする。24 時間なら、受信サーバが動いている間の S1 は 1 日以内の新しさを保ち、1 回の取込の量は 1 日分で、初回の取込（transcript の 30 日分）より小さい
- 範囲の外の値で受信サーバを止めず既定に戻すのは、設定の誤りで取込が動かなくなり、transcript の削除より前の取込を逃すことを避けるためである。記録と lmo-ctl の表示で気付ける
- 時計の起点を起動の時刻に固定するのは、取込の時刻が前の取込の所要に依らず決まり、取込の記録の `started_at` の並びから間隔どおりに動いているかを読めるためである。前の取込の終わりから数えると、取込が長引くたびに間隔が延びる
- 永続の値をデータの根に置くのは、端末ごとの運用の値で、repo の `app/config/`（公開の単価表など、端末に依らないデータ）に置くと、ほかの端末と作業ツリーに及ぶためである。L2 の切り替えと同じファイルにして、作業指示者が直す設定のファイルを 1 つにする

**決めたこと（transcript の読み方）**

- 読むファイル: `<cc の設定フォルダ>` の `projects` の下（組 A の [H-09](../01.全体構成/設計書.md#sec-7-1)）で、前回の取込で残した大きさか更新の時刻（組 A の [§2.8](../01.全体構成/設計書.md#sec-2-8) の読んだ位置。`state\`）から、どちらかが変わったもの
  - 計測用のセッション（[§1.4](#sec-1-4) の `run\measure\` の記録にあるもの）の transcript は、日常の取込では読まない。計測用の取込では、自分のデータの根の記録にあるものだけを読む
  - 日常のデータの根の `labels\`・`session-start\` にある、同じセッションのファイル（名前が `<session_id>.jsonl`）も、日常の取込では読まない。§1.4 で計測のデータの根に書かせるので、日常のデータの根に来るのは書き先を渡し忘れたときだけである
- 変わったファイルは、初めから読み直す。transcript では、読んだ位置のうち大きさと更新の時刻だけを使い、読み終えた位置からの続きは使わない
  - 理由: cc は transcript のファイルを削って縮めることがある（`CLAUDE_CODE_TRANSCRIPT_LOCAL_GC`。[1-9 §2](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D58 (c)）

- 最後の更新から 30 分以内のファイルは「書いている途中」とみなし、末尾の 1 行が読めなくても読めない行に数えず、次の取込で読み直す。次の回に変わっていなくても読み直すよう、そのファイルの読んだ位置（大きさと更新の時刻）は更新しない
  - 理由: 取込は終わったセッションを対象にするのが安全である（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「データモデル」の、異常終了したセッションの項）

  - S2 などの追記だけのファイル（組 A の §2.8）の、改行で終わらない末尾の行も、ファイルの最後の更新から 30 分以内なら同じく書いている途中とみなす。30 分を過ぎた末尾の行は、下の種類 1 に数える
- 取り込む値は、組 B の `transcript_usage` の列（H-10）に要るもの（cache 書き込みの TTL 別の内訳を含む usage、`requestId`、`agentId`、`isSidechain`、`model`、`effort`、`stop_reason`、時刻など）だけにする。メッセージの本文と tool の入出力は読まない
  - サブエージェントの `meta.json` からは、呼び出しの鍵の `toolUseId` だけを読む（組 B の `subagent_invocation`。H-10）。`meta.json` に本文に当たる項目があるかは確かめていない。主線の transcript の `toolUseResult.agentId` でも結べる（[1-6 §5.3](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-5-3)）が、`toolUseResult` は tool の結果を含むので使わない
  - OTel の記録が 1 件も無いセッション（[§1.6](#sec-1-6) の欠け）の usage は、この値から集計の行を作る（組 B の [H-26](../02.データモデルと集計/設計書.md#sec-6-1)）

**決めたこと（取込の記録。H-12）**

- キーの名前は ASCII の小文字とアンダースコアにし、入れ子の項目はオブジェクトにする。数は件数、大きさはバイト数、時刻は UTC の ISO 8601 である

| `transcript` | オブジェクト | `files_seen`（見たファイルの数）・`files_read`（読み直したファイルの数）・`lines`・`unparsable`（種類 1）・`lone_surrogate`（種類 2）・`deferred_files`（書いている途中として次に回したファイルの数）・`new_types`（新しい記録型の型ごとの行数。例 `{"api-request": 12}`）・`unknown_types`（未知の型ごとの行数。同じ形）・`measure_skipped`（計測用のセッションとして読まなかったファイルの数） |
| `unreadable` | 配列 | 読めない行のあったファイルごとに 1 つ。`source`（`s2`・`transcript`・`labels`・`session_start`・`quality`・`api_bodies`）・`file`（`<根>:<相対パス>`）・`kind`（1 か 2）・`byte_offsets`（読めない行の先頭のバイト位置の配列）。`file` とバイト位置の形は、定義の別紙 [§1.7](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-7) のファイルの位置の列（`#` の前と後ろ）と同じである。無かったファイルは載せない |
| `labels`・`session_start`・`quality`・`api_bodies` | オブジェクト | `files`・`lines`・`unparsable`（L1 のラベル、`SessionStart` の記録、品質の記録、raw body の `index.jsonl`）。`labels`・`session_start` には `measure_skipped`（計測用のセッションとして読まなかったファイルの数）も持つ |
| `launch_checks` | オブジェクト | ランチャの起動の確かめ（[§1.3](#sec-1-3)）。`launches`（`session_id` のある起動の数）・`pending`（確かめが済まない数）・`ok`（`index.jsonl` の行と transcript の両方があった数）・`missing`（確かめが済んで、どちらかが無かった起動の配列。1 つは `session_id`・`ts`（起動の時刻）・`index`・`transcript`（それぞれ、あったか。真偽値）） |
| `otel_gaps` | オブジェクト | 欠け（[§1.6](#sec-1-6)）。`sessions`（数）・`session_ids`（配列）・`first_ts`・`last_ts`（欠けたセッションの transcript の最初と最後の時刻。欠けが無ければ null） |
| `retention` | オブジェクトか null | 最後に届いた `retention_sweep` の `period_days` と、その記録の時刻 `ts`（[§2.2](#sec-2-2)）。届いていなければ null |
| `store_bytes` | オブジェクト | `data_root`（データの根の直下のフォルダの名前ごとの大きさ。例 `{"raw": 123456, "db": 7890}`）・`transcripts`（transcript の合計の大きさ）（[§2.5](#sec-2-5)） |
| `schema_changes` | 配列 | 組 B の版の検知（[組 B §4.1](../02.データモデルと集計/設計書.md#sec-4-1)）が見つけた変化。1 件の中身は組 B §4.1 |

**理由**: 読めない行を後で直して取り込み直すときに、ファイルと行の位置を引けるようにする。位置をバイト位置にするのは、続きから読む取込は行の先頭のバイト位置を知っていて、行の番号はファイルの初めから数え直さないと出ないためである（定義の別紙 §1.7 と同じ）。組 B の版の検知と、統合（Phase 3 への引き渡し）が同じ記録を読む。

読めない transcript の行は、Phase 3 の取込の試作で確かめる（[進め方 §3](../00.設計の進め方/計画書.md#sec-3)、[§6](#sec-6) の 7）。本書は実装と実機の確認をしない。

<a id="sec-2-5"></a>
### 2.5 保存量の見積もり（PV-07）

**決めたこと**

- 見積もるのは、データの根に溜まる量（S2、S1、raw body、L1 のラベル）である。取込は transcript を写さないので、transcript の大きさは取込の時間に効くだけである
- 方法: Phase 3 の PoC の日常のセッション（cc 2.1.310 以降。取込が対象にする版）で、取込の記録の `store_bytes` を 1 日ごとに読み、2 週間分から 30 日分に延ばして見積もる
- transcript の大きさも同じ期間に数え、取込の読み直しの量の目安にする（2.1.304 から auto mode の `api-request` の記録が小さくなった。[1-9 §3.3](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-3-3)）
- 値は Phase 3 で出す。データの根の 30 日分がディスクの空きの 1 割を超える見込みなら、圧縮（[§3.2](#sec-3-2)）を諮り直す

**理由**: 計画書の既定の案（取込が対象にする版の transcript で見積もる）を、transcript を写さない本書の取込に当てると、溜まる量の主はデータの根の側になる。

<a id="sec-3-1"></a>
### 3.1 受信サーバの常駐（P2-3 の 1。EN-05・S7-03）

**決めたこと**: 受信サーバ lmo-receiver（組 A の [H-05](../01.全体構成/設計書.md#sec-7-1)）は常駐させず、作業指示者か Claude Code が、使う前に手で起動する（案 1: 手動）。起動と停止には、作業指示者と Claude Code が実行するスクリプト lmo-ctl を作る（振る舞いは[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）。手順書は作らない。

**理由**: 作業指示者の裁定である（[判断事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-29）。裁定は、作業指示者と Claude Code が実行する起動・停止のスクリプトの作成だけで十分とし、手順書を要らないとした。

手動の起動に合わせた決めごとは、次の節にある。

- 起動していない間の OTel の記録の欠けと、その間のセッションの usage の補い: [§1.6](#sec-1-6)
- transcript の削除より前に取り込むこと（`cleanupPeriodDays` を延ばさない）: [§2.2](#sec-2-2)
- 取込の頻度: [§2.4](#sec-2-4)
- 計画書の「操作を増やさない」との関係: [統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の「計画書との関係」

**選択肢**（裁定の材料。採ったのは案 1）

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1: 手動 | 作業指示者が、cc を使う前に起動する | 端末の設定を変えない | 起動を忘れた間の OTel の記録が欠ける（transcript から補えるのは usage と思考トークンだけ。[§1.6](#sec-1-6)）。受信サーバを起動していない間は取込も 1 時間ごとに動かず、transcript の削除（既定 30 日）より前に取り込む保証が弱くなる（[§2.4](#sec-2-4)）。[計画書 §1.3](../../00.活動計画/活動計画書.md#sec-1-3) の「操作を増やさない」に合わない |
| 2: ログオン時に自動（タスク スケジューラ） | 現在のユーザのログオンを契機に起動するタスクを登録する | 止まったときに起動し直す設定を持てる【推定】。登録の有無を管理の画面で見られ、外しやすい | 既定のタスクの条件（電池で動くときに止める、長く動くと止める など）を外す手順が要る【推定】。登録に管理者の権限が要る場合がある【推定】 |
| 3: ログオン時に自動（スタートアップ フォルダ） | ユーザのスタートアップ フォルダにショートカットを置く | 管理者の権限が要らない。置く・消すだけで済む | 止まったら次のログオンまで起動しない。窓を出さない工夫が要る |

比べて外した仕組みは次の 3 つである。

- レジストリの Run キー: 案 3 と同じ働きで、登録が利用者から見えにくい
- Windows のサービス: 管理者の権限と、サービスにする別の道具が要り、依存が増える（組 A の [§3](../01.全体構成/設計書.md#sec-3)）
- cc の `SessionStart` hook で起こす: hook から background の process を起こすと、tool call が block されうる（[計画書「L1 の hook の既定の書き方」](../../00.活動計画/活動計画書.md#sec-p2-l1-hook)の、background の process の項と同じ理由）

**採らなかった Claude の推奨**: 案 2。Phase 3 の PoC は手動で起動し、Phase 4 から常駐させる。案 2 で登録できなければ案 3 にする。

- Phase 4 の完了条件（操作を増やさずにデータが溜まる状態が 1 週間程度続く。[計画書 Phase 4](../../00.活動計画/活動計画書.md#sec-p4)）には、自動の起動が要る
- 止まったときに起動し直せば、欠ける時間を短くできる。欠けの大きさは取込の記録で見る（[§1.6](#sec-1-6)）
- Phase 3 を手動にするのは、PoC の間は受信サーバを何度も直すので、そのたびに登録を直さずに済むためである

**決めないもの**: 職場（Phase 7）での起動の仕方（Phase 7 の着手前）。lmo-ctl が受信サーバを窓を出さずに起こす仕方は、lmo-ctl の実装で決める（[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 1）。

<a id="sec-3-2"></a>
### 3.2 圧縮（P2-3 の 2。PV-01 の一部・S7-05）

**決めたこと**: 保存ファイル（S2 の閉じた日の JSONL と、raw body）を外部で圧縮する構成（[計画書 §7](../../00.活動計画/活動計画書.md#sec-7) #5）を採らない（案 1: 圧縮しない）。本書は「外部で圧縮する構成」を、閉じたファイルを書いた後に丸ごと圧縮する形と読む。

**理由**: 作業指示者の裁定である（[判断事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-30）。裁定は、Claude の推奨（案 1。外部で圧縮する構成を今は採らず、採る理由が出たら案 2 にする）と同じである。推奨の理由は次のとおりである。

- 保存量はまだ見積もっていない（[§2.5](#sec-2-5)。値は Phase 3）。会話の全体を含む raw body はランチャのセッションだけに出る（[§1.3](#sec-1-3)）ので、日常の量は S2 が主になる
- 案 2 は Node.js の組み込みで足りるので、後で採っても依存は増えない
- 案 3 は、依存を少なくする方針（J-13）に合わない

**見直しの条件**: [§2.5](#sec-2-5) の見積もりで、データの根の 30 日分がディスクの空きの 1 割を超える見込みなら、案 2 を諮る。

**前提**: 受信サーバは非圧縮の JSONL を追記する（組 A の [H-06](../01.全体構成/設計書.md#sec-7-1)）。書く側で圧縮しないのは、その形式が DuckDB で直接読めないためである（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) R-3。閉じたファイルを後から圧縮する形は、R-3 の対策の形である）。

**選択肢**（裁定の材料。採ったのは案 1）

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1: 圧縮しない | 今の形のまま | 処理が増えない。取込と DuckDB が今の形のまま読める | ディスクの使用量が、圧縮した場合より大きい |
| 2: `node:zlib` の gzip | 取込が読み終えた閉じた日のファイルを `.jsonl.gz` にする | 追加の道具が要らない（Node.js の組み込み。組 A の [§5.2](../01.全体構成/設計書.md#sec-5-2)）。DuckDB は拡張子から圧縮の形を判別して読む（v2.1 R-3） | 取込と探索の読みが遅くなる【推定】。圧縮の処理と、途中で止まったときの扱いが要る |
| 3: 外部の道具（zstd・7-Zip など） | 案 2 と同じことを別の道具で行う | 圧縮率が案 2 より高い【推定】 | 道具を入れる手間と依存が増える（[J-13](../../01.基礎調査/作業指示者裁定待ち事項.md#sec-1)）。Windows には単体の gzip・zstd の命令が標準で無い（v2.1 R-3） |

**決めないもの**: 圧縮する時期の値（何日たったファイルを圧縮するか。案 2・3 を採るときに決める）。

<a id="sec-3-3"></a>
### 3.3 内容を記録する変数の置き場所と、正式リリース物の既定（P2-3 の 3。EN-01・EN-03b・PV-02・S7-02）

**決めたこと**: 内容を記録する 5 つの変数のそれぞれについて、(a) 本環境の置き場所（ユーザ settings か、ランチャのプロセスだけか）と、(b) 正式リリース物の既定を、次の表のとおりにする。

| 変数 | 記録されるもの | 本環境の置き場所 | 正式リリース物の既定 |
|---|---|---|---|
| `OTEL_LOG_USER_PROMPTS` | プロンプトの本文（`user_prompt` と、traces の interaction span） | ユーザ settings で有効 | 無効 |
| `OTEL_LOG_ASSISTANT_RESPONSES` | 応答の本文（`assistant_response`） | ユーザ settings で、明示して有効 | 明示して無効 |
| `OTEL_LOG_TOOL_DETAILS` | tool の引数（Bash のコマンドの全体、パス、MCP・skill・agent の名前）と、ユーザ定義の agent と MCP の実名（metrics と `api_request`） | ユーザ settings で有効 | 無効 |
| `OTEL_LOG_TOOL_CONTENT` | tool の出力の内容（ファイルの中身、コマンドの出力、WebFetch の結果。traces の `tool.output`） | ランチャのプロセスだけ（調べる run で有効にする） | 無効 |
| `OTEL_LOG_RAW_API_BODIES` | API の要求と応答の JSON の全体（会話の全体） | ランチャのプロセスだけ（file モード。[§1.3](#sec-1-3)） | 無効 |

記録されるものは docs ed2bfc5 L75628〜L75633・L77286〜L77316 による。

- 本環境のユーザ settings への足し方は [§1.2](#sec-1-2)、ランチャが足す変数は [§1.3](#sec-1-3) にある
- ユーザ settings に置くものは、Claude が手順を書き、作業指示者が設定する

**理由**: 作業指示者の裁定である（[判断事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-31）。上の表は Claude の推奨の表で、裁定はそれを 5 行 × 2 列のとおりに承認した。変数ごとの理由は下にある。

**決まっていること**（変えない）

- 取りこぼしの無い仕組みのためなら、どの変数も常時有効にしてよい。他のリポジトリの作業に悪影響を与えうるもの（例 `OTEL_LOG_RAW_API_BODIES`）は、ユーザ settings に置かず、起動するプロセスの環境変数で渡す（[計画書「有効化と常駐」](../../00.活動計画/活動計画書.md#sec-p2-enable)の回答で決まったこと）
- Phase 2 以降の本環境は `OTEL_LOG_USER_PROMPTS=1` にする。正式リリース物で `=0` にすることには問題は無い（[まとめ §5.1 の Q4 の ※2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers)）
- 職場（Phase 7）の変数は、Phase 7 の着手前に決める（[計画書の承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24)の先送りの行）

**変数ごとの理由と別の案**

- `OTEL_LOG_USER_PROMPTS`
  - 本環境をユーザ settings にするのは、L2 の前提だからである。ランチャだけにすると、ランチャを通さないセッションでは本文が記録されず、L2 で分類できない（EN-03a）。cc 自身がディスクに書く量は増えない
  - 別の案はランチャだけにすること。長所は他のリポジトリのプロンプトが残らないこと、短所は日常のセッションで L2 が働かず、L1 と L2 を比べられないことである（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の回答の確認 4）
  - 正式リリース物を無効にするのは Q4 の ※2 による。`=0` で動くタグ案は L1 か ① である
- `OTEL_LOG_ASSISTANT_RESPONSES`
  - 本環境を有効にするのは、本活動では情報量の多い案を優先する（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の ※1 の要旨）ためである
  - 明示するのは EN-03b のとおりで、`OTEL_LOG_USER_PROMPTS` を変えたときに応答の記録が一緒に変わらないようにする（[§1.1](#sec-1-1)）
  - 正式リリース物を無効にするのは、他人の端末で、応答の本文（コード・パス・秘密の値を含みうる）を既定では残さないためである。無効も明示するのは、利用者が L2 のために `OTEL_LOG_USER_PROMPTS` を有効にしても、応答の記録が一緒に有効にならないようにするためである（EN-03b）
  - 別の案は、本環境でも明示して無効にすること。長所は S2 の量が減ること、短所は 30 日を過ぎると応答の本文が手元に残らないこと（transcript は消える）である
- `OTEL_LOG_TOOL_DETAILS`（V-5 などの実測の結果は [1-3 §5.1](../../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-5-1)）
  - 有効にすると、ユーザ定義の agent とユーザが設定した MCP の名前が、metrics と `api_request` で実名になる（無効では `custom`）。skill の名前は、公式でない plugin の skill を除き、無効でも実名だった。`skill_activated` だけは、無効だとユーザ定義の skill が `custom_skill` になる
  - metrics の系列は、実名に割れる名前の種類 1 つにつき、cost が 1 本・token が 4 本増えた（モデル 1 つ）。agent 2 種・MCP の tool 2 種・skill 3 種を 1 ターンに 1 つずつ使った run では、32 本が 42 本（+31%）になった。名前がそれぞれ 1 種類の run では 22 本で変わらなかった
  - 系列より大きな差は、`tool_decision`・`tool_result` の `tool_parameters` に、Bash のコマンドの全体（切り詰めない。docs ed2bfc5 L77306）と agent・skill・MCP の名前が付くことである
  - 本環境を有効にするのは、問い②・③ で agent と MCP を実名で分けるためである。系列の増え方は名前の種類に比例する小さなもので、ローカルの S1 には重くない。分類器が block した規則の名前（`classifier_category`）も、この変数が有効なときだけ付く（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
  - 正式リリース物を無効にするのは、他人の端末で、コマンドとパスを既定では残さないためである。無効でも skill の名前は実名で集計できる
  - 正式リリース物の別の案は、有効にして、受信で `tool_parameters`・`tool_input` を落とすこと。長所は agent と MCP を実名で集計でき、コマンドとパスが残らないこと、短所は受信の規則が増え、`claude_code.tool` span の入力由来の属性（`file_path` など。docs ed2bfc5 L77310）の全体が docs から決まらないことである
  - 実測は、無効のときも traces の `claude_code.tool` span に MCP の server・tool の実名が出ると示した（docs の記載と食い違う。[1-3 §5.1 の表](../../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-5-1-docs)、[仕様別紙](../../00.活動計画/【別紙】公式仕様の調査結果.md) §3）。並列に呼んだ MCP の tool は、`api_request` に最後の 1 つの名前しか付かなかった（1 つのリクエストに付く MCP の名前は 1 つ【推定】）
- `OTEL_LOG_TOOL_CONTENT`
  - 本環境をランチャだけにするのは、次の 3 点による
    - 計画書の指標に、tool の出力の内容を使うものが無い。ツール結果の大きさは `tool_result_size_bytes` で取れる（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md)）
    - 内容は 1 属性 60 KB まで入り、traces の 1 回の送信が大きくなる（S2 の 1 行の大きさ。受信の本文の大きさの上限は組 A の [§2.2](../01.全体構成/設計書.md#sec-2-2)）
    - 他のリポジトリで読んだファイル（秘密の値を含む設定ファイルなど）の中身が、S2 に写る
  - 正式リリース物を無効にするのは、上の 1 点目と 3 点目と同じく、計画書の指標に使わず、他人の端末で読んだファイルの中身とコマンドの出力を残さないためである
  - 別の案はユーザ settings で有効にすること。長所は情報量が最大になること（[まとめ §5.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers) の ※1 の要旨）、短所は上の 3 点である
- `OTEL_LOG_RAW_API_BODIES`
  - 本環境の置き場所は回答で決まっている（ランチャのプロセスだけ）。file モードにする理由は [§1.3](#sec-1-3) にある
  - 正式リリース物を無効にするのは、正式リリース物の思考案が T1 だけなら要らないからである。T2 を残す場合も、ランチャで有効にする（T2 を残すかは下の「決めないもの」）

**決めないもの**: 正式リリース物で T2 を残すか（AR-04。[統合 §4](../99.設計まとめ/設計書.md#sec-4) の J-35 として、設計書の承認時に決める）。職場（Phase 7）の変数は、上の「決まっていること」のとおり Phase 7 の着手前に決める。

**V-5 などの実測で残った未確認**: 5 件ある（[1-3 §5.1](../../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-5-1) の「確かめられなかった点」の表）。どれも決めたことを変えない。系列数は、モデルと `effort` の組の数だけ掛けて増える【推定】。

## 7. Devil's Advocate

| 対象 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| 計測用のセッションでユーザ settings を読まない（[§1.4](#sec-1-4)） | ユーザ settings には OTel 以外の設定もあり、読まないと日常の条件から外れ、計測が日常を代表しない | 棄却する。計測用のセッションの役目は、版の間と条件の間の比較で、日常の値は日常のセッション（J-19）で測る。残存リスク: 切り替えの前後で基線が変わる。最初の計測で前の起動の仕方と並べ、違いを基線の変更として残す |
| 識別属性を受信でハッシュに替える（[§2.3](#sec-2-3)） | 1 人で使う端末の中のデータで、平文でも外に出ない。受けたものを S2 にそのまま残す組 A の原則を崩す | 棄却する。探索の出力を報告書に貼る経路で平文が出る事故を防ぐ。S1 の作り直しは同じ鍵で成り立ち、組 A は受信に差し込み口を置いている。組 A の S2 が残すのは、版で増える属性とイベントを選ばない形で、マスクの規則は S2 に書く前に当てる（[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)）。残存リスク: 鍵を失うと前後の値が結べない（鍵をバックアップの対象にした） |
| `cleanupPeriodDays` を延ばさない（[§2.2](#sec-2-2)） | 取込の規則の誤りに気付いたとき、30 日より古い transcript から取り込み直せない | 残存リスク。とくに Phase 3 で取込の規則を確かめるまでの期間に当たる。Phase 3 で誤りが見つかったら延ばす案に切り替え、それまでに取り込んだ値は S1 に残る。受信サーバを手で起動する（J-29）ので、起動しない期間が 30 日を超えうる。超えたことに気付くのは次の起動のときで、そのときに延ばす案に切り替える（[§2.2](#sec-2-2)）。気付く手段は Phase 4 で検討する（[統合 §6.3](../99.設計まとめ/設計書.md#sec-6-3)） |
| 取込の間隔を設定で変えられるようにする（[§2.4](#sec-2-4)） | 変えられる値は誤りの元で、既定の 1 時間で足りる。受信から数秒の値はライブ表示で見られる | 棄却する。ライブ表示に出ない値（本文系、思考トークン）の新しさを、作業に合わせて変える手段が要る。範囲の外の値は既定に戻し、記録と lmo-ctl の表示で知らせるので、誤りで取込は止まらない。残存リスク: 下限の 5 分は【推定】で、取込が重いと短い間隔で切れ目なく動く（[§6](#sec-6) の 14） |
| ライブ表示を許可リストにする（[§2.3](#sec-2-3)） | 1 人で使う端末のループバックの画面で、本文を出しても外には出ない。許可リストに無い値はライブで見られない | 棄却する。画面は人に見せたり写したりしうるので、本文と識別子は、マスクの後の通常の経路で見る。許可リストの外の値は、取込の後に S1 で見られる。残存リスク: 版で増えた数の属性は、組 B §1.12 に列を足すまでライブに出ない |
| 経路 (ii) をランチャだけにする（[§1.3](#sec-1-3)） | T2 の目的は T1 で取れないリクエストを補うことで、日常のセッションこそ補いたい | 棄却する。本環境では transcript の `requestId` で突合でき、補う対象が小さい。raw body をユーザ settings に置かないことは回答で決まっている。残存リスク: 職場で `requestId` が付かなければ決め直す（Phase 7） |
