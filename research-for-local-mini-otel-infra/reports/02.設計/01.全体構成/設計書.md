<a id="sec-0"></a>
## 0. 要約

受信 → 保存 → 補完取込 → 集計 → UI を、受信サーバ 1 つと、都度起動する取込・集計などのコマンドに分ける。受信サーバは作業指示者か Claude Code が手で起動・停止し（J-29）、受けた記録にマスクの規則を当てて生の JSONL（保存案 S2）に足す。SQLite（保存案 S1）には取込だけが書く。実装言語は Node.js で、npm パッケージを使わない（J-34 の裁定）。

<a id="sec-0-1"></a>
### 0.1 決めたこと

- プロセスの構成（AR-01）: 起動してから止めるまで動き続けるのは、受信サーバ `lmo-receiver` の 1 つにする。取込 `lmo-ingest`、集計 `lmo-report`、起動・停止 `lmo-ctl`、ランチャ `lmo-launch`（組 D）、品質の記録 `lmo-judge` は都度起動のコマンドにし、UI は Phase 5 で別のプロセスにする（[§2.1](#sec-2-1)）
- 受信サーバ: 127.0.0.1 の 4318 番で `http/json` だけを受け、受けた本文の大きさの上限は 64 MB にする（[§2.2](#sec-2-2)）
- 保存の書き手（AR-01）: S2 は受信サーバだけが、S1 は取込だけが書く。DuckDB のデータベースファイル（`.duckdb`）は持たず、DuckDB は外部のファイルを読むだけにする（[§2.3](#sec-2-3)）
- traces の受け口（AR-01a）: 同じ受信サーバが `/v1/traces` も受け、span を S2 に残す（[§2.4](#sec-2-4)）
- UI の仮置き（AR-01b）: UI は S1 と S2 を読むだけの別のプロセスにし、画面案 D1・D2 のどちらもつなげる（[§2.5](#sec-2-5)）
- コードの置き場所: 活動フォルダの `app/` の下に置く。hook のスクリプトは、データの根の `hooks\` に写したものをユーザ settings が指す（[§2.6](#sec-2-6)）
- パス（AR-05）: データの根（収集したデータを置くフォルダ。Windows の既定は `%LOCALAPPDATA%\local-mini-otel\`）と cc の設定フォルダを、変数と OS の既定から決め、コードにパスを埋め込まない（[§4](#sec-4)）
- 組 A が正本の受け渡し 8 件（H-05〜H-09・H-25・H-27・H-30）の値（[§7.1](#sec-7-1)）

## 1. 構成の全体像

受信は、起動している間動き続ける 1 つのプロセスが S2 に残し、S1 への正規化と OTel の外の記録の取込は、都度起動する 1 つのプロセスがまとめて行う。構成とデータの流れの図は[統合 §1.2 の図 2](../99.設計まとめ/設計書.md#sec-1-2) にある。

| コンポーネント | 担う処理 | プロセス | 書く所 | 読む所 |
|---|---|---|---|---|
| 受信 | OTLP/HTTP を受け、検査し、マスクの規則を当てて S2 に追記する。取込を子プロセスで起こす | lmo-receiver（起動から停止まで動く） | S2、`run\` | `config\` のハッシュの鍵（初回の起動で作る。[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)） |
| 保存 | S2 への追記（受信が行う）と、S2 から S1 への正規化（取込が行う） | lmo-receiver・lmo-ingest | S2・S1 | S2 |
| 補完取込 | transcript と OTel の外の記録（L1 のラベル、`SessionStart` の記録、raw body のファイル、品質の記録）を S1 に入れ、突合し、集計の正本の表を作る | lmo-ingest（都度起動） | S1、`state\`、`run\` | S2、transcript、[§4](#sec-4) の OTel の外の記録、単価表 |
| 集計 | S1 の SQL で指標を出す（Phase 3 は CLI の出力） | lmo-report（都度起動） | 標準出力 | S1 |
| UI | 画面（Phase 5） | Phase 5 で決める | — | S1、S2 |
| 起動・停止 | 受信サーバを起こし、止める | lmo-ctl（都度起動） | — | `run\` |
| ランチャ | 調べる run の cc を、プロセスの環境変数を足して起こす（組 D） | lmo-launch（都度起動） | `run\` | — |
| 品質の記録 | 作業指示者の判定を 1 件 1 行で足す | lmo-judge（都度起動） | `quality\` | — |

## 2. コンポーネントとプロセスの構成

[計画書 Phase 2「全体構成」](../../00.活動計画/活動計画書.md#sec-p2-arch)の 1 点目（AR-01）とその子の 2 点（AR-01a・AR-01b）を決める。

<a id="sec-2-1"></a>
### 2.1 プロセスの分け方（AR-01）

**決めたこと**: 起動してから止めるまで動き続けるのは受信サーバ 1 つにし、取込と集計を都度起動のコマンドにする（下の案 P1）。本節と [§10](#sec-10) の「常駐」は、起動している間は待ち受け続けるプロセスのことで、ログオン時の自動の起動を指さない（受信サーバの起動は手動。[J-29](../作業指示者裁定待ち事項.md#sec-1)）。

- プロセスの名前は、`lmo-`（local-mini-otel の略）に役目を続けた形にする（H-05。値は [§7.1](#sec-7-1)）
- 受信サーバは、作業指示者か Claude Code が起動・停止のコマンド `lmo-ctl` の `start`・`stop` で起こし、止める。手順書は作らない。`lmo-ctl` の振る舞いは [統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) にある
- 受信サーバは、起動の直後と、その後 1 時間ごとに、取込を子プロセスとして起こす（頻度の正本は組 D の H-11。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）。取込は単独でも起動でき、lmo-report の集計の前と手動でも動く
- 取込は同時に 1 つだけ動く。`state\` のロックで、子プロセスの起動と単独の起動が重ならないようにする
- lmo-report は、集計の前に取込を呼ぶ。見る時点の S1 に、それまでの受信が入る
- ランチャ `lmo-launch` は[組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3) で、品質の記録のコマンド `lmo-judge` は H-30（[§7.1](#sec-7-1)）で決めた。どちらも都度起動のコマンドである

**理由**

- 常駐の処理を「JSON を読み、マスクの規則を当てて 1 行足す」だけにすると、常駐のプロセスが失敗する箇所が少ない。スキーマ（組 B）を直しても、受信サーバを止めずに済む
- S1 は S2 から作り直せる。正規化の誤りに後から気付いても、取込を流し直せば直る（[まとめ §3.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-1) の S1 の短所「取り直せない」を、2 層で消す）
- 取込が受信サーバに依らないので、ループバック宛ての送信が止められた環境でも、取込と集計だけで回せる（縮退運用。[§5.3](#sec-5-3)）
- S1 の書き手が 1 つになり、SQLite の書き込みの待ちが生じない。読み手は WAL で同時に読める（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3)）

**別の案**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| P1（採る） | 常駐は受信だけ。取込と集計は都度起動 | 上の理由 | S1 は、取込を走らせるまで新しい受信を含まない（集計の前に取込を呼んで補う） |
| P2 | 1 つの常駐プロセスに、受信・取込・集計の問い合わせ口をまとめる | 起動と停止の管理が 1 つで済む。S1 がすぐ新しくなる | 取込や集計の不具合で受信が止まる。縮退運用でも受信の部分を起動する。DuckDB を使う問い合わせは、受信のプロセスに持たせることになる（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3) の回避策） |
| P3 | 受信サーバが S2 と S1 の両方に書き、取込は transcript だけを扱う | S1 がすぐ新しくなる | 受信の処理が大きくなる。S1 の書き手が 2 つになる。スキーマを直すたびに受信サーバを止める |

<a id="sec-2-2"></a>
### 2.2 受信サーバ（AR-01 の受信）

**決めたこと**

- 受け口は 127.0.0.1 の 4318 番で、`/v1/logs`・`/v1/metrics`・`/v1/traces` を受ける。プロトコルは `http/json` だけを受ける（H-08。値は [§7.1](#sec-7-1)）
  - `localhost` でなく `127.0.0.1` と書く。送信先の変数（組 D）も同じ書き方にそろえる
  - ループバックのアドレスにだけ待ち受け、ほかの端末からは受けない（本活動は個人ローカル用。[計画書 §1.4](../../00.活動計画/活動計画書.md#sec-1-4)）
- 検査と応答
  - `Content-Type` が JSON でない要求（protobuf など）は、415 で返す
  - `Content-Encoding` が gzip・deflate・br なら、`node:zlib` で展開してから読む
  - JSON として読めない本文は 400 で返し、件数を動作の記録（`run\`）に残す
  - S2 に書けたら 200 を返し、書けなかったら 503 を返す
  - 本文の大きさに上限を置き、超えた要求は 413 で返す。上限は受信サーバのメモリを守るためだけに置き、初めの値は 64 MB にする
  - S2 に書いた行のうち、16 MB（DuckDB の `maximum_object_size` の既定。[1-4 §5](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-5) の #28）を超えた行の数を、動作の記録（`run\`）に残す。その行のある日のファイルを DuckDB で読むときは、読む側の上限を上げる
  - 上限の値は、Phase 3 で S2 の行の大きさの最大を測って見直す（[§9](#sec-9) の 7）
- S2 への書き方: 1 要求（送り手からの 1 回の HTTP の送信。以下も「要求」と書く）を 1 行にし、1 回の同期の追記で書く。行の形は H-06（[§7.1](#sec-7-1)）
- 版で増える属性とイベント: `event.name` や属性を選ばず、S2 に残す。S1 の列に持つかは組 B（H-02）
- マスク: 受信サーバは、S2 に書く前に、組 D のマスクの規則（H-04。[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）を当てる。取込の側にも、S1 に書く前に記録を変える処理を 1 か所置く。そこには、組 D §2.3 のとおり今は何も当てない
- 起動と停止
  - 待ち受けの番号がすでに使われていたら、動作の記録（`run\`）に残して終える。2 つ起動しても、1 つだけ動く
  - 待ち受けを始めたら、自分のプロセス番号を `run\lmo-receiver.pid` に書き、止まるときに消す。`lmo-ctl` の `stop` はこの番号のプロセスを止める
  - 起動の直後と 1 時間ごとに取込を子プロセスで起こす（[§2.1](#sec-2-1)）

**理由**

- `http/json` なら `JSON.parse` で足り、protobuf の解読が要らない（[1-4 §4.2](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-2)。1-1 の数十行の受信スクリプトで 3 つの信号を受けた）。OTLP の JSON は 64 ビットの整数を文字列で表すので、`JSON.parse` で読み直しても桁は落ちない（同じ節）
- 4318 番は OTLP/HTTP の慣例の番号で、docs の例の送信先と同じである（docs ed2bfc5 L75677 の `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` の例）。Phase 1 の probe は 127.0.0.1:4318 で受けた（[1-10 §1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-1)）
- `localhost` は IPv6 の `::1` に解決されることがあり、127.0.0.1 で待つ受信サーバに届かなくなりうる【推定】。両側を同じアドレスで書けば、名前の解決に依らない
- 今の cc は非圧縮で送る（cc 2.1.283 の実測。[1-4 §4.1](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-1)）。展開の処理は、利用者が圧縮を指定した場合に備えて置く（1-1 の受信スクリプトも gzip・deflate・br に対応した）
- OTLP の仕様は、503 を送り手が再送してよい応答にしている【推定】（一次資料は Phase 3 の実装の前に確かめる）。cc の送り手が再送するかも【推定】で、Phase 3 で確かめる（受信サーバが止まっているときの cc の挙動は組 D の EN-06）
- Node.js は 1 つのスレッドでイベントを処理するので、同期の追記なら、同時に届いた 2 セッションの要求の行が混ざらない。書きかけで止まった末尾の行は、読む側が読めない行として数える（数え方は組 D の H-11。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）
- 行の順は受信の順で、記録の起きた順ではない。`event.sequence` はプロセスごとの連番なので、並べ替えは `event.timestamp` で行う（v2.1 R-4。[1-4 §4.4](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-4)）
- 版でイベントの種類と属性が増える（2.1.307 の `safety_event`、2.1.310 の `agent_id` など）。S2 は属性とイベントを選ばずに残すので、増えた属性も残る（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1) の「全体構成」の行）
- 本文の上限をメモリを守るためだけに置くのは、raw body を file モードだけで出し（[組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3)）、本文が OTel のイベントに入らないためである。16 MB を超える行は DuckDB の側の上限を上げれば読めるが、受信で断るとその記録が欠ける
- 番号の衝突で終えるのは、手動の起動が重なっても、待ち受ける受信サーバを 1 つに保つためである。プロセス番号のファイルは、`lmo-ctl` が止める相手を知るために置く

**別の案（S2 の 1 行の単位）**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1 要求 1 行（採る） | 受けた要求の本文を、マスクの規則を当てた後、1 行にする | 受けた形（入れ子の構造）を変えずに残し、S1 を作り直す元にできる。受信の処理が小さい | DuckDB で読むと、`resourceLogs` → `scopeLogs` → `logRecords` の入れ子を展開する SQL が要る（[引継ぎ資料 v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.5 のひな形で書ける）。1 行が大きくなりうる（[§9](#sec-9) の 7） |
| 1 レコード 1 行 | 受信サーバが、logRecord・span・データ点ごとに 1 行に分け、resource の属性を各行に写す | DuckDB の SQL が平らになる | 受信の処理が大きくなる。受けた形から変えるので、分け方の誤りを後から直せない |

### 2.3 保存の書き手と読み手（AR-01 の保存）

**決めたこと**

| 保存 | 形 | 書き手 | 読み手 |
|---|---|---|---|
| S2 | 日別の JSONL（H-06） | lmo-receiver だけ | lmo-ingest、DuckDB CLI |
| S1 | SQLite（`node:sqlite`、WAL）。スキーマは組 B | lmo-ingest だけ | lmo-report、UI、DuckDB CLI |
| DuckDB のデータベースファイル（`.duckdb`） | 持たない。DuckDB はメモリ上のデータベースで開き、S2 と S1 を読むだけにする | — | — |

- S1 のファイルは `db\telemetry.sqlite` である
- S1 の表は、すべて lmo-ingest が作る。元の表のほか、集計の正本の表 `usage_record`、見なし費用、ラベルの表 `prompt_label`（L2 の事後分類を含む）、品質の記録の表 `quality_judgement` も作る。表と規則は組 B（[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-26）
- lmo-report と UI は S1 を読むだけで、表を作らない
- 単価表（組 B の H-23）を直したら、取込を流し直して見なし費用を作り直す

**理由**

- DuckDB は、同じ `.duckdb` ファイルを別のプロセスから同時に読み書きできない（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3)）。`.duckdb` を持たなければ、受信・取込・UI を別のプロセスにしても、この制約に当たらない
- S1 の書き手を 1 つにすれば、S1 への書き込みの順が取込の中で決まる

**残る未確認**: 受信サーバが追記している当日の JSONL を、別のプロセスの DuckDB で読めるか（見込み）。Phase 3 で、[V-ID 別紙 §2](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の「書き込み中の JSONL を別プロセスの DuckDB で読めるか」の行で確かめる。読めなければ、DuckDB では閉じた前日までのファイルだけを読み、当日分は S1 で見る（[まとめ §3.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-1) の残存リスクの対策と同じ）。

<a id="sec-2-4"></a>
### 2.4 traces の受け口（AR-01a）

**決めたこと**: 受信サーバは、logs・metrics と同じ受け口で `/v1/traces` も受け、span を S2 の `raw\traces\` に残す。span を S1 のどの表に入れるかと、集計の正本と結合の規則は、組 B が決める（[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-02・H-26）。

**理由**

- logs・metrics に出ない API 呼び出し（ターン終了後の `side_query`、自前の auto mode の分類器のリクエスト）は、traces の span にだけ出る（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「分析指標」）。費用の集計に span を含める（[計画書 Phase 2「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）ので、受けて残す
- span を受けて残しておけば、集計の正本を traces と logs のどちらにしても足りる（[1-4 §6](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-6) の traces の注記）
- traces は beta 機能で、版で形が変わりうる。生のまま S2 に残せば、形が変わっても取込を直して読み直せる

送信側の traces の有効化（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` と `OTEL_TRACES_EXPORTER`）は組 D（EN-04。[組 D §1.2](../04.有効化とデータ保全/設計書.md#sec-1-2)）が決める。traces は、送信先とプロトコルに共通の OTLP の設定を使う（docs ed2bfc5 L75670）ので、受信サーバも受け口も分けない。

### 2.5 UI の仮置き（AR-01b）

**決めたこと**: UI は受信サーバと別のプロセスにし、S1（SQLite）と S2（JSONL）を読むだけにする。受信サーバには問い合わせ口を持たせない。

- 方式（D1 / D2）とプロセスの名前は、Phase 5 の着手時に決める（[計画書 Phase 5](../../00.活動計画/活動計画書.md#sec-p5)）
- それまでは画面を作らず、DuckDB の SQL で直接集計する（探索期。[まとめ §3.2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-2)）
- Phase 3 の簡易集計は、lmo-report の CLI の出力で行う（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3)）

**理由**

- D1（自作 Node.js）は、S1 を `node:sqlite` で、S2 を DuckDB CLI の子プロセスで読める（[1-5 §7](../../01.基礎調査/05.ダッシュボード方式/調査報告書.md#sec-7) の決め手 3）
- D2（Observable Framework）は、DuckDB・SQLite を Wasm 経由で読める（[まとめ §3.2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-2)）
- どちらも読むだけなので、S1 の WAL と `.duckdb` を持たない構成（[§2.3](#sec-2-3)）の下で、受信と取込を止めずに読める

**画面案の依存**: D1 は、可視化ライブラリを使えばその npm パッケージに依る。D2 は npm パッケージで、ビルドの道具を含むので、間接の依存は D1 より多い【推定】（[1-7 §6.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-6-1)）。Phase 5 で画面案を選ぶときに、依存の多さを比べる軸に入れる（[J-13](../../01.基礎調査/作業指示者裁定待ち事項.md#sec-1) の推奨）。

### 2.6 コードの置き場所

割り当て表の行には無いが、[活動 CLAUDE.md](../../../CLAUDE.md) の成果物の配置が「配置の確定は Phase 2」とするので、ここで決める。

**決めたこと**: 実装コードは活動フォルダの `app/` に置く。収集したデータは `app/` に置かず、データの根（[§4](#sec-4)）に置く。

| フォルダ | 置くもの |
|---|---|
| `app/bin/` | コマンドごとの起動スクリプト。H-05 の名前ごとに `<名前>.mjs`（`lmo-receiver.mjs`・`lmo-ingest.mjs`・`lmo-report.mjs`・`lmo-ctl.mjs`・`lmo-launch.mjs`・`lmo-judge.mjs`） |
| `app/lib/` | 共通の部品（パスの決め方、S2 の行の読み書き、分類の部品など） |
| `app/hooks/` | hook のスクリプトの元（`l1-tag.mjs`・`session-start.mjs`。H-27） |
| `app/` の下のほかのフォルダ | repo に置いてよいデータ。置き場所はそのデータの正本の組が決める（公開の料金の単価表は `app/config/price-tables/`。[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-23。分類体系と規則のデータは `app/config/taxonomy/`。[組 C §1.1](../03.作業分類タグ/設計書.md#sec-1-1)） |

hook のスクリプトは、元を `app/hooks/` に置き、ユーザ settings が指すのはデータの根の `hooks\` に写したものにする（H-27）。

- 写すのは、hook が実行時に読むもの全部（`app/hooks/` のスクリプト、`app/lib/` の分類の部品、分類体系と規則のデータ）で、写した先のファイルの名前は元と同じにする
- 写すのは Claude で、hook を直したら写し直す
- ユーザ settings の hook の `args` には、写しの絶対パスを、変数を展開した形で書く（settings に書く形は[組 C §2.2](../03.作業分類タグ/設計書.md#sec-2-2)）

**理由**

- 計画書の Phase 3・Phase 4 の成果物は `app/` の下である（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3)）。起動スクリプトの名前をコマンドの名前（H-05）と同じにすれば、名前からファイルを一意に指せる
- hook を写しから動かすのは、ユーザ settings が repo の作業ツリーを直接指すと、ほかのブランチを checkout したときにファイルが無くなり、hook が黙って失敗してラベルが欠けるためである（[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）

### 3.2 承認の対象、推奨、条件に当たったとき

**承認の対象**: 実装言語（案 1 / 案 2）と依存の方針。案 1 では、npm パッケージを使わないことを原則にする。

**条件に当たったとき**（J-34 の条件）: Phase 3 以降の実装で、受信・保存・取込・集計に npm パッケージが 1 つでも要る見込みが出たら、その時点で、パッケージの中身を添えて作業指示者に諮り、実装方針（Node.js のままか、言語を変えるか）を変えるかを検討する。添える中身と条件の対象は [統合 §2.3](../99.設計まとめ/設計書.md#sec-2-3) にある。諮って使うと決めたパッケージは、[§3.3](#sec-3-3) の一覧に足す。

決めないもの: UI の依存（画面案を選ぶ Phase 5 の着手時）、L1 の実装手段（組 C が command hook に決めた。[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）、DuckDB の版（Phase 3 で決める）。

**Claude の推奨**: 案 1（裁定と同じ）。

- 案 1 では npm パッケージを 0 にできる【推定】（[§9](#sec-9) の 4）。作業指示者がパッチを当てたい対象（第三者のライブラリ）が、収集の経路（受信と取込）に残らない。案 2 では、JSON と SQLite でライブラリが要る見込みで、パッチの対象がかえって増える【推定】
- 第一のゴールの PoC（Phase 3）を、実測済みの受信スクリプトから始められる
- 受信の処理は小さいので、Node.js 自体が職場で使えなくなった場合に、Java に書き移す費用は小さい（この判断は後で戻せる）

**決める時期**: 判断の節目（段 2 の後。[進め方 P2-2](../00.設計の進め方/計画書.md#sec-p2-2)）で、2026-10-27 に決まった。

## 4. 環境に依存しないパス（AR-05）

**決めたこと**: プロセスが使うパスは、次の 2 つの根から `node:path` で組み立てる。コードに絶対パスと区切り文字を埋め込まない。

| 根 | 決め方（上から順に、最初に当たったもの） | 根拠 |
|---|---|---|
| データの根 | (1) 変数 `LMO_DATA_DIR`<br>(2) Windows では `%LOCALAPPDATA%\local-mini-otel\`<br>(3) それ以外（WSL・Docker）では `$XDG_DATA_HOME/local-mini-otel/`、その変数が無ければ `~/.local/share/local-mini-otel/` | (2) は[計画書 Phase 2「データ保全とプライバシー」](../../00.活動計画/活動計画書.md#sec-p2-privacy)の「回答で決まったこと」の置き場所 |
| cc の設定フォルダ | (1) 変数 `CLAUDE_CONFIG_DIR`<br>(2) `~/.claude` | docs ed2bfc5 L64088（設定フォルダを変え、セッションの履歴もその下に置く）。transcript はその下の `projects` にある（[1-6 §2.1](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-2-1)） |

- 受け口のアドレスと番号も、変数 `LMO_OTLP_HOST`・`LMO_OTLP_PORT` で変えられるようにし、既定は H-08 の値にする
- ファイル名とフォルダ名の日付は、UTC の `YYYY-MM-DD` にする。端末のタイムゾーンで名前が変わらず、レコードの時刻（ISO 8601）の日付の部分と同じ形になる
- データの根を変数で変えるときも、クラウド同期の対象のフォルダと、ネットワーク上のフォルダには置かない。SQLite の WAL は、同じ端末のプロセスの間でしか効かない（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3)）
- 既存のフォルダ（`v2b\`、`probe-<版>\`）は動かさない。`v2b\` は作業指示者の回答で決まった置き場所である（[計画書 承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24) の Q2・Q3 の行）

**理由**

- 第三のゴール（WSL + Docker）では、データの根と cc の設定フォルダの場所が Windows と違う。変数と OS の既定から決めれば、コードを直さずに動く（[計画書 Phase 2「全体構成」](../../00.活動計画/活動計画書.md#sec-p2-arch)の最後の点）
- cc の設定フォルダは `CLAUDE_CONFIG_DIR` で変えられる。`~/.claude` を決め打ちにすると、変えている環境で transcript を見つけられない
- 受け口のアドレスを変えられれば、Docker のコンテナの中で待ち受ける場合にも、コードを直さずに済む【推定】

**フォルダの構成**（H-07）

```text
<データの根>\
├── raw\                 S2。信号ごとのフォルダに日別の JSONL（H-06）。lmo-receiver が書く
│   ├── logs\
│   ├── metrics\
│   └── traces\
├── db\                  S1。telemetry.sqlite（WAL の付随ファイルを含む）。lmo-ingest が書く
├── state\               取込の読んだ位置と、取込を 1 つに限るロック。lmo-ingest が書く
├── run\                 各プロセスの動作の記録（起動・停止・受信の件数・エラー）
│   ├── ingest\          取込の記録（H-12。組 D）
│   ├── launch\          ランチャの起動の記録（組 D）
│   └── lmo-receiver.pid 受信サーバのプロセス番号（動いている間だけある）
├── api-bodies\          raw body の出力先（H-17。組 D）。cc が書く
├── config\              ハッシュの鍵（H-04。組 D）と、職場の組の単価表の price-tables\（H-23。組 B）
├── labels\              L1 のラベル（H-18。下の形は組 C）。L1 の hook が書く
├── session-start\       SessionStart の記録（H-28。組 C）。SessionStart の hook が書く
├── quality\             品質の記録（H-30）。lmo-judge が書く
├── hooks\               hook のスクリプトの写し（H-27）。Claude が写す
├── v2b\                 既存。V-2b の記録（消さない）
└── probe-<版>\          既存。probe の記録
```

図は、データの根の直下に、記録の種類ごとに 1 つのフォルダと、設定（`config\`）と hook の写し（`hooks\`）を置く形を示す。

- 根の直下には、記録の種類ごとに 1 つのフォルダを置く。記録でないものは、設定（`config\`）と hook の写し（`hooks\`。[§2.6](#sec-2-6)）だけにする
- 新しく作るフォルダの名前は ASCII の小文字・数字・ハイフンにする（WSL・Docker と DuckDB の glob で扱いやすい）。既存の `probe-<版>\` は、版の点を含むまま残す
- 括弧に H のあるフォルダの下の形（ファイルの名前と中身の形）は、その受け渡しの正本の節にある（H-06・H-27・H-30 は [§7.1](#sec-7-1)、ほかは組 B〜D）。hook の所要時間（H-19）は L1 のラベルのレコードに入る

## 5. 第二のゴールへの備え（組 A の分）

[計画書 Phase 2「第二のゴールへの備え」](../../00.活動計画/活動計画書.md#sec-p2-goal2)の 6 点のうち、組 A の構成に関わる 3 点である。どれも統合の行（[割り当て表 §1](../99.設計まとめ/【別紙】割り当て表.md#sec-1) の G2-04〜G2-06）で、組ごとの決めごとと照らして決めたことは[統合 §5](../99.設計まとめ/設計書.md#sec-5) にある。本節は、組 A の構成での形を書く。

<a id="sec-5-1"></a>
### 5.1 少ない依存（G2-04 に関わる）

[§3](#sec-3) の案 1（J-34）で、収集の経路（受信と取込）の依存は Node.js だけになる。DuckDB CLI は探索と UI の側にだけ入るので、職場で DuckDB が使えなくなっても、受信と取込は止まらない。

<a id="sec-5-2"></a>
### 5.2 Git Bash に依らない起動（G2-05 に関わる）

組 A のプロセスは、どれも `node` に起動スクリプトを渡して起動する。sh のスクリプトと、Git Bash の道具（`tar`・`gzip` など）に依らない。圧縮が要るときは `node:zlib` を使える（[1-4 §5](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-5) の #18）。受信サーバは手動で起動し、起動・停止のコマンド lmo-ctl も `node` で起動する（J-29。[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）。L1 の hook と `SessionStart` の hook は、exec 形式で `node` を起こす（[組 C §2.1](../03.作業分類タグ/設計書.md#sec-2-1)）。

<a id="sec-5-3"></a>
### 5.3 縮退運用の構成（H-25。G2-06 に関わる）

**決めたこと**（構成）: ループバック宛ての送信が届かない環境では、lmo-receiver を起動せず、lmo-ingest と lmo-report だけで回す。lmo-ingest は transcript と L1 のラベルから S1 を作り、lmo-report は S1 から集計する。切り替えは「受信サーバを起動しない」ことだけで、ほかのプロセスとフォルダは変わらない。

- S1 の `usage_record` に、transcript の usage だけから作る行を足す。行の種類の値と作れる列は組 B が決める（[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-26）。受信サーバを止めていた間のセッションを補う規則と同じで、S2 にそのセッションが 1 件も無いときに限るので、二重に数えない
- 欠けるもの: OTel にだけある記録（metrics、traces の span、`api_request` の属性のうち transcript に無いもの）。出せる指標と欠ける指標は[統合 §5](../99.設計まとめ/設計書.md#sec-5) にある
- 縮退運用は用意する（G2-06。統合 §5）。切り替えるか（G2-07）は Phase 7 の結果で決める

**理由**: 取込は受信サーバに依らずに動く（[§2.1](#sec-2-1)）ので、部品を足さずに縮退運用の形になる。

## 10. Devil's Advocate

| 対象 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| 常駐は受信だけ（[§2.1](#sec-2-1) の P1） | 取込を走らせるまで S1 が古く、当日の集計がすぐ出ない。1 つの常駐にまとめれば、S1 はいつも新しい | 棄却する。lmo-report は集計の前に取込を呼ぶので、見る時点の S1 は新しい。分析は数週間の単位（[計画書 Phase 6](../../00.活動計画/活動計画書.md#sec-p6)）で、秒の単位の新しさは要らない。残存リスク: 自動で更新する画面を Phase 5 で作るなら、取込の頻度（組 D）を短くする |
| 実装言語（[§3](#sec-3) の案 1。J-34） | Node.js 自体に脆弱性が出て職場で禁止されたら、受信も取込も止まる。Java なら、パッチを当てて使い続けられる | 残存リスク。cc 本体も Node.js 製である（[1-7 §6.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-6-1)）ので、その場合は cc も止まりうる【推定】。受信は小さく保ち、Java に書き移す費用を小さくする（[§3.2](#sec-3-2)） |
| S2 の 1 行を 1 要求にする（H-06） | 1 レコード 1 行にすれば、DuckDB の SQL で入れ子を展開せずに済み、探索が楽になる | 棄却する。S2 の役目は、受けた形のまま残し、S1 を作り直せることである。日常の集計は S1 で行う。残存リスク: 探索期に S2 を直接読む SQL には、入れ子の展開が要る |
| hook を写しから動かす（[§2.6](#sec-2-6)。H-27） | 写しは repo の外にあり、hook を直した後に写し直すのを忘れると、古い hook が黙って動き続ける。repo の作業ツリーを直接指せば、写し直しが要らない | 棄却する。作業ツリーを直接指すと、ほかのブランチを checkout したときに hook が黙って失敗する（[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）。レコードに `hook_ver`・`rules_ver` が入る（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1) の H-18）ので、古い写しで付いたラベルは後から見分けられる。残存リスク: 写し直しは手作業で、気付くまでの間のラベルは古い規則による |
| `.duckdb` を持たない（[§2.3](#sec-2-3)） | DuckDB に取り込んだデータベースの方が、毎回 JSONL を読むより集計が速い | 残存リスク。日常の集計は S1（SQLite）で行い、DuckDB は探索に使うので、速さは Phase 3 の量で見る。遅ければ、探索用の写しの `.duckdb` を別の名前で作る（受信と取込はその写しに触れない） |
