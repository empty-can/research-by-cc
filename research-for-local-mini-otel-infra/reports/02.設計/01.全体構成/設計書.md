## 0. 要約

受信 → 保存 → 補完取込 → 集計 → UI を、受信サーバ 1 つと、都度起動する取込・集計などのコマンドに分ける。受信サーバは作業指示者か Claude Code が手で起動・停止し（J-29）、受けた記録にマスクの規則を当てて生の JSONL（保存案 S2）に足す。SQLite（保存案 S1）には取込だけが書く。実装言語は Node.js で、npm パッケージを使わない（J-34 の裁定）。

<a id="sec-0-1"></a>
### 0.1 決めたこと

- プロセスの構成（AR-01）: 起動してから止めるまで動き続けるのは、受信サーバ `lmo-receiver` の 1 つにする。取込 `lmo-ingest`、集計 `lmo-report`、起動・停止 `lmo-ctl`、ランチャ `lmo-launch`（組 D）、品質の記録 `lmo-judge` は都度起動のコマンドにし、UI は Phase 5 で別のプロセスにする（[§2.1](#sec-2-1)）
- 受信サーバ: 127.0.0.1 の 4318 番で `http/json` だけを受け（アドレスを変えるときもループバックに限る）、受けた本文の大きさの上限は 64 MB にする。`Host` のヘッダが待ち受けのアドレスと番号でない要求は断る。受けた要求はマスクの後に書き手 1 つの列に並べ、S2 に非同期で追記し、書けてから 200 を返す（[§2.2](#sec-2-2)）
- 取込の起こし方: 受信の知らせでは起こさず、受信サーバの起動の直後と取込の間隔（既定 1 時間）ごと、lmo-report の集計の前、lmo-judge の一覧の前、手動で動かす（[§2.1](#sec-2-1)）
- ライブ表示: 受信サーバが、S2 に書けた要求から許可リストの項目（数と区分）だけを抜き出して配り、UI が購読する。ライブの値は S1 に書かない（[§2.7](#sec-2-7)）
- 保存の書き手（AR-01）: S2 は受信サーバだけが、S1 は取込だけが書く。DuckDB のデータベースファイル（`.duckdb`）は持たず、DuckDB は外部のファイルを読むだけにする（[§2.3](#sec-2-3)）
- traces の受け口（AR-01a）: 同じ受信サーバが `/v1/traces` も受け、span を S2 に残す（[§2.4](#sec-2-4)）
- UI の仮置き（AR-01b）: UI は別のプロセスにし、S1 を主に読む。S2 の生のファイルは直接読まず、S2 にしか無い情報は取込で DB に取り込んでから読む。ライブ表示は受信サーバの配り口を購読する。画面案 D1・D2 のどちらもつなげる（[§2.5](#sec-2-5)）
- 取込の振る舞い: lmo-ingest はロックで 1 つだけ動き、前回からの新しい行と変わったファイルを読み、1 回の書き込みを 1 つのトランザクションで確定してから読んだ位置を更新する。作り直しでは、元のファイルが無い行を残す（[§2.8](#sec-2-8)）
- 受信サーバの動作の記録: lmo-receiver が `run\receiver\` の日別のファイルに、起動・毎時の件数・取込の終わりなどを 1 行 1 JSON で書く（[§2.9](#sec-2-9)）
- コマンドの引数と終了コード: lmo-ctl・lmo-ingest・lmo-report・lmo-judge の終了コードを、0（成功）・1（失敗）・2（使い方の誤り）・3（lmo-ingest は取込を飛ばした、lmo-report と lmo-judge は取込の失敗）にそろえる（[§2.10](#sec-2-10)）
- コードの置き場所: 活動フォルダの `app/` の下に置く。hook のスクリプトは、データの根の `hooks\` に写したものをユーザ settings が指す（[§2.6](#sec-2-6)）
- パス（AR-05）: データの根（収集したデータを置くフォルダ。Windows の既定は `%LOCALAPPDATA%\local-mini-otel\`）と cc の設定フォルダを、変数と OS の既定から決め、コードにパスを埋め込まない（[§4](#sec-4)）
- 組 A が正本の受け渡し 9 件（H-05〜H-09・H-25・H-27・H-30・H-34）の値（[§7.1](#sec-7-1)）

## 2. コンポーネントとプロセスの構成

[計画書 Phase 2「全体構成」](../../00.活動計画/活動計画書.md#sec-p2-arch)の 1 点目（AR-01）とその子の 2 点（AR-01a・AR-01b）を決める。

<a id="sec-2-1"></a>
### 2.1 プロセスの分け方（AR-01）

**決めたこと**: 起動してから止めるまで動き続けるのは受信サーバ 1 つにし、取込と集計を都度起動のコマンドにする（下の案 P1）。本節と [§10](#sec-10) の「常駐」は、起動している間は待ち受け続けるプロセスのことで、ログオン時の自動の起動を指さない（受信サーバの起動は手動。[J-29](../作業指示者裁定待ち事項.md#sec-1)）。

- プロセスの名前は、`lmo-`（local-mini-otel の略）に役目を続けた形にする（H-05。値は [§7.1](#sec-7-1)）
- 受信サーバは、作業指示者か Claude Code が起動・停止のコマンド `lmo-ctl` の `start`・`stop` で起こし、止める。手順書は作らない。`lmo-ctl` の振る舞いは [統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) にある
- 受信サーバは、起動の直後と、その後は取込の間隔（既定 1 時間。設定で変えられる）ごとに、取込を子プロセスとして起こす（頻度と間隔の設定の正本は組 D の H-11。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)。起こし方は [§2.8](#sec-2-8)）。取込は単独でも起動でき、lmo-report の集計の前、lmo-judge の一覧の前、手動でも動く
- 取込は同時に 1 つだけ動く（ロックは [§2.8](#sec-2-8)）
- lmo-report は、集計の前に取込を子プロセスとして起こし、終わってから集計する（[§2.8](#sec-2-8)）。見る時点の S1 に、それまでの受信が入る。lmo-judge も、判定する作業の一覧を出す前に同じく起こす
- 取込は、受信の知らせ（S2 に行を書けたこと）では起こさない。S2 の行が S1 に入るのは上の契機の取込のときで、S1 の書き手は lmo-ingest だけである。受信から数秒で見たい値は、許可リストの項目だけをライブ表示で見る（[§2.7](#sec-2-7)）
- ランチャ `lmo-launch` は[組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3) で、品質の記録のコマンド `lmo-judge` は H-30（[§7.1](#sec-7-1)）で決めた。どちらも都度起動のコマンドである

**理由**

- 常駐の処理を「JSON を読み、マスクの規則を当てて列から 1 行足す」ことと、許可リストの項目を配ること（[§2.7](#sec-2-7)）だけにすると、常駐のプロセスが失敗する箇所が少ない。スキーマ（組 B）を直しても、受信サーバを止めずに済む
- S1 は S2 から作り直せる（transcript と raw body から作る行は、元のファイルが消えるまでに限る。[§2.8](#sec-2-8)）。正規化の誤りに後から気付いても、取込の作り直しで直る（[まとめ §3.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-1) の S1 の短所「取り直せない」を、2 層で消す）
- 取込が受信サーバに依らないので、ループバック宛ての送信が止められた環境でも、取込と集計だけで回せる（縮退運用。[§5.3](#sec-5-3)）
- S1 の書き手が 1 つになり、SQLite の書き込みの待ちが生じない。読み手は WAL で同時に読める（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3)）
- 取込を受信の知らせで起こさないのは、ライブ表示に出さない値（本文系とマスクが要りうる属性。[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）を、受信から数秒で S1 に入れる用が無いためである。知らせで起こすと要求ごとに S1 に書くことになる。`node:sqlite` の読み書きの API（`DatabaseSync`・`StatementSync`）は同期なので（本環境の Node.js v24.14.0 で確かめた。2026-10-29）、受信を止めないよう、書く処理を別のプロセスか `worker_threads` に分けて常駐させることになり、常駐の処理が大きくなる。今の都度起動の子プロセスなら、同期の API は受信のイベントの処理を止めない

**別の案**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| P1（採る） | 常駐は受信だけ。取込と集計は都度起動 | 上の理由 | S1 は、取込を走らせるまで新しい受信を含まない（集計の前に取込を呼んで補う） |
| P2 | 1 つの常駐プロセスに、受信・取込・集計の問い合わせ口をまとめる | 起動と停止の管理が 1 つで済む。S1 がすぐ新しくなる | 取込や集計の不具合で受信が止まる。縮退運用でも受信の部分を起動する。DuckDB を使う問い合わせは、受信のプロセスに持たせることになる（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3) の回避策） |
| P3 | 受信サーバが S2 と S1 の両方に書き、取込は transcript だけを扱う | S1 がすぐ新しくなる | 受信の処理が大きくなる。S1 の書き手が 2 つになる。スキーマを直すたびに受信サーバを止める |

**別の案（S2 から S1 への取込の起こし方）**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 契機ごとに起こす（採る） | 起動の直後、取込の間隔ごと、lmo-report の前、lmo-judge の前、手動 | 上の理由 | S1 は、最大で取込の間隔の分だけ古い（ライブ表示と、lmo-report の前の取込で補う） |
| 受け手を別のプロセスで常駐させる | 受信サーバが S2 に書けたら常駐の取込のプロセスに知らせ、そのプロセスが S1 に書く | S1 がすぐ新しくなる。取込の不具合で受信は止まらない | 常駐のプロセスが 2 つになり、lmo-ctl の起動・停止（J-29）が 2 つを扱う。単独の取込（lmo-report の前、手動、縮退運用）とロックを分け合う |
| 受け手を受信サーバの `worker_threads` にする | 受信サーバの中の worker が知らせを受けて S1 に書く | プロセスが増えない。知らせをプロセスの中で渡せる | worker の不具合とメモリの増えが受信サーバに及ぶ。単独の取込とロックを分け合うのは同じ |

受け手にすると決め直すとき（例: Phase 5 の UI に、許可リストの外の値を数秒の新しさで出す要件が出たとき）は、表の受け手の 2 つの案から試作で選ぶ。比べる材料は、受け手の有無での受信の 1 要求あたりの処理の時間、受信サーバのメモリの増え、取込の不具合を起こしたときに受信が続くか、単独の取込がロックで待つ時間である。

<a id="sec-2-2"></a>
### 2.2 受信サーバ（AR-01 の受信）

**決めたこと**

- 受け口は 127.0.0.1 の 4318 番で、`/v1/logs`・`/v1/metrics`・`/v1/traces` を受ける。プロトコルは `http/json` だけを受ける（H-08。値は [§7.1](#sec-7-1)）
  - `localhost` でなく `127.0.0.1` と書く。送信先の変数（組 D）も同じ書き方にそろえる
  - ループバックのアドレスにだけ待ち受け、ほかの端末からは受けない（本活動は個人ローカル用。[計画書 §1.4](../../00.活動計画/活動計画書.md#sec-1-4)）。変数でアドレスを変えるときも、ループバックのアドレスに限る（[§4](#sec-4)）
  - 同じ待ち受けに、ライブ表示の配り口 `GET /lmo/live` を置く（[§2.7](#sec-2-7)）
- 検査と応答（`/v1/*` の 3 つのパスへの要求に当てる。ライブの配り口の扱いは [§2.7](#sec-2-7)）
  - 要求の `Host` のヘッダが待ち受けのアドレスと番号（既定は `127.0.0.1:4318`。IPv6 の `::1` で待つときは `[::1]:4318` の形）でない要求は、ほかの検査の前に 403 で返し、件数を動作の記録（[§2.9](#sec-2-9) の `bad_host`）に残す。配り口と同じ確かめである（[§2.7](#sec-2-7)）
    - cc の要求の `Host` は、送信先の変数（組 D）に書いたアドレスと番号になり、この確かめを通る【推定】。Phase 3 で、受信サーバを作ったときの試験（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の確かめ方）で確かめる。通らないと分かったら、`/v1/*` には当てず、当てない理由（害の大きさの見方）を下の理由に書く
  - `Content-Type` が JSON でない要求（protobuf など）は、415 で返す
  - `Content-Encoding` が gzip・deflate・br なら、`node:zlib` で展開してから読む
  - JSON として読めない本文は 400 で返し、件数を動作の記録（[§2.9](#sec-2-9)）に残す
  - S2 に書けたら 200 を返し、書けなかったら 503 を返す（書き方は下の「S2 への書き方」）。200 の本文は `{}`（OTLP/HTTP の JSON の成功の応答【推定】。部分成功の応答は使わない）で、`Content-Type: application/json` を付ける
  - 本文の大きさに上限を置き、超えた要求は 413 で返す。上限は受信サーバのメモリを守るためだけに置き、初めの値は 64 MB にする
  - S2 に書いた行のうち、16 MB（DuckDB の `maximum_object_size` の既定。[1-4 §5](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-5) の #28）を超えた行の数を、動作の記録（§2.9）に残す。その行のある日のファイルを DuckDB で読むときは、読む側の上限を上げる
  - 上限の値は、Phase 3 で S2 の行の大きさの最大を測って見直す（[§9](#sec-9) の 7）
- ほかのパスとメソッド: `/v1/*` の 3 つと `/lmo/live` のほかのパスへの要求は 404、`/v1/*` の 3 つのパスへの POST でない要求は 405 で返し、それぞれの件数を動作の記録（§2.9）に残す
- S2 への書き方: 1 要求（送り手からの 1 回の HTTP の送信。以下も「要求」と書く）を 1 行にし、書き手 1 つの列（キュー）から非同期で追記する。行の形は H-06（[§7.1](#sec-7-1)）
  - 受信サーバは、本文を読み、検査し、マスクの規則（H-04）を当ててから、行を列の末尾に並べる。`received_at` は列に並べた時刻にし、行を書く日付のファイルもこの時刻で決める
  - マスクの処理が例外を出したら、その要求を S2 に書かずに 500 を返し、件数を動作の記録（§2.9）の毎時の行に入れる。本文と例外の文は記録しない
  - 書き手は 1 つで、列の先頭の行を 1 つずつ追記する。1 行の追記が返ってから次の行に移り、2 つの追記を同時に走らせない
  - 書き手は、日のファイルを開いて最初の 1 行を書くときだけ、ファイルの終わりを確かめる。終わりが改行でなければ（前の受信サーバが追記の途中で止まった）、行の前に改行を足して同じ書き込みに含める（L1 の hook の [組 C §2.3](../03.作業分類タグ/設計書.md#sec-2-3) の 5 と同じ決め）。その後は自分が行の単位で書くので、確かめない
  - その要求の行の追記が返ったら 200 を返す。追記が失敗したら 503 を返し、件数を動作の記録（§2.9）に残して、書き手は列の次の行に移る。「書けた」は OS への書き込みが返ったことで、ディスクへの同期（fsync）は待たない
  - 追記を待つ間も、ほかの要求を受け、読み、マスクして列に並べる
  - 列の上限は、件数 1,000 と、並んでいる行の大きさの合計 128 MB にする【推定】（[§9](#sec-9) の 10）。並べるとどちらかを超える要求は、並べずに 503 を返し、件数を動作の記録（§2.9）に残す。列が空なら、大きさに依らず 1 件は並べる
  - 毎時の区切りで（取込の間隔とは別）、列の長さと大きさの最大と、要求ごとの処理の時間の中央値と最大を、動作の記録（§2.9）に残す（上限とライブ表示の負荷を Phase 3 で見直す材料）
  - 受信サーバを止めたときに列に残っていた行は、書かれない。その要求には 200 を返していないので、送り手からは、受信サーバが止まっていた間と同じに見える（[組 D §1.6](../04.有効化とデータ保全/設計書.md#sec-1-6)）
- 版で増える属性とイベント: `event.name` や属性を選ばず、S2 に残す。S1 の列に持つかは組 B（H-02）
- マスク: 受信サーバは、S2 に書く前に、組 D のマスクの規則（H-04。[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）を当てる。取込の側にも、S1 に書く前に記録を変える処理を 1 か所置く。そこには、組 D §2.3 のとおり今は何も当てない
- 起動と停止
  - 待ち受けの番号がすでに使われていたら、動作の記録（§2.9）に残して終える。2 つ起動しても、1 つだけ動く
  - 待ち受けを始めたら、自分のプロセス番号と待ち受けの番号を `run\lmo-receiver.pid` に書く。自分で止まるときは消す。どの応答にも、自分のプロセス番号をヘッダ（`x-lmo-receiver-pid`）で付ける
  - `lmo-ctl` の `stop` は、待ち受けの番号に要求を 1 つ送り、応答のヘッダの番号が番号のファイルの番号と同じときだけ、そのプロセスを止める。止めた後、待ち受けの番号が接続を断るのを確かめてから、番号のファイルを消す（Windows で Node.js から別のプロセスを止めると強制終了になり、受信サーバは自分で消せない【推定】。[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 1）。接続を断られたら（待ち受けている受信サーバが無い）、止めずに番号のファイルだけを消す。接続できたが上限の時間の内に応答が来ない（応えない受信サーバ）ときは、止めずに番号のファイルを残す（振る舞いの正本は[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）
  - `lmo-ctl` の `start` は、番号のファイルが残っていたら同じ確かめを行い、接続を断られたら、古いファイルとして消してから起こす
  - 起動の直後と取込の間隔ごとに、取込を子プロセスで起こす（[§2.1](#sec-2-1)・[§2.8](#sec-2-8)）

**理由**

- `http/json` なら `JSON.parse` で足り、protobuf の解読が要らない（[1-4 §4.2](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-2)。1-1 の数十行の受信スクリプトで 3 つの信号を受けた）。OTLP の JSON は 64 ビットの整数を文字列で表すので、`JSON.parse` で読み直しても桁は落ちない（同じ節）
- 4318 番は OTLP/HTTP の慣例の番号で、docs の例の送信先と同じである（docs ed2bfc5 L75677 の `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` の例）。Phase 1 の probe は 127.0.0.1:4318 で受けた（[1-10 §1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-1)）
- `localhost` は IPv6 の `::1` に解決されることがあり、127.0.0.1 で待つ受信サーバに届かなくなりうる【推定】。両側を同じアドレスで書けば、名前の解決に依らない
- `/v1/*` にも `Host` を確かめるのは、DNS rebinding（ほかのサイトが自分の名前を 127.0.0.1 に向け直す手）で、ブラウザで開いたほかのサイトのページが作った記録が S2 と S1 に入るのを断つためである。名前を向け直した後は同じ origin の要求になり、`Content-Type: application/json` の POST を事前の確かめの要求なしに送れる【推定】。入った値は集計とライブ表示に混ざり、後で Claude Code が S1 や S2 を引くときにも読まれる
- 今の cc は非圧縮で送る（cc 2.1.283 の実測。[1-4 §4.1](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-1)）。展開の処理は、利用者が圧縮を指定した場合に備えて置く（1-1 の受信スクリプトも gzip・deflate・br に対応した）
- OTLP の仕様は、503 を送り手が再送してよい応答にし、成功の応答の本文を空の JSON のオブジェクトでよいとしている【推定】（一次資料は Phase 3 の実装の前に確かめる）。cc の送り手が再送するかも【推定】で、Phase 3 で確かめる（受信サーバが止まっているときの cc の挙動は組 D の EN-06）
- 書き手を 1 つにして列から 1 行ずつ追記するので、同時に走る追記が無く、同時に届いた 2 セッションの要求の行が混ざらない。書きかけで止まった末尾の行は、読む側が読めない行として数える（数え方は組 D の H-11。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）。最初の 1 行の前に改行を足すのは、強制終了の後に同じ日に起動し直したとき、200 を返した次の行が書きかけの行とつながって読めなくなるのを防ぐためである
- 追記を非同期にするのは、書き込みを待つ間も受信を止めないためである。同期の追記では、ディスクが遅いとき（ほかのプログラムの読み書きなど）に、受信サーバのイベントの処理が止まり、ほかのセッションの要求も待たされる
- 200 を書けた後に返すのは、「200 は S2 に保存済み」を保ち、200 を受けた送り手の記録を失わないためである。fsync を待たないのは、待って守れるのが端末の電源が落ちたときの末尾の行だけで、1 要求ごとにディスクへの同期の待ちが加わるためである
- マスクの例外に 503 でなく 500 を返すのは、送り直されても同じ本文で同じ失敗になるためである。本文と例外の文を記録しないのは、マスクの前の値（識別属性の平文を含みうる）を残さないためである
- 列の上限は、受信サーバのメモリを守るために置く。上限を超えた要求に 503 を返すのは、書けなかったときと同じく、送り手が送り直してよい応答だからである（上の 503 の理由と同じ【推定】）。`received_at` を列に並べた時刻にするのは、行の順と時刻の順をそろえ、日付が変わる時刻の前後で前日のファイルに後から書かないためである
- 行の順は受信の順で、記録の起きた順ではない。`event.sequence` はプロセスごとの連番なので、並べ替えは `event.timestamp` で行う（v2.1 R-4。[1-4 §4.4](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-4-4)）
- 版でイベントの種類と属性が増える（2.1.307 の `safety_event`、2.1.310 の `agent_id` など）。S2 は属性とイベントを選ばずに残すので、増えた属性も残る（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1) の「全体構成」の行）
- 本文の上限をメモリを守るためだけに置くのは、raw body を file モードだけで出し（[組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3)）、本文が OTel のイベントに入らないためである。16 MB を超える行は DuckDB の側の上限を上げれば読めるが、受信で断るとその記録が欠ける
- 番号の衝突で終えるのは、手動の起動が重なっても、待ち受ける受信サーバを 1 つに保つためである。プロセス番号のファイルは、`lmo-ctl` が止める相手を知るために置く。応答のヘッダで確かめるのは、受信サーバが落ちてファイルが残り、その番号が別のプロセスに使われていたときに、そのプロセスを止めないためである

**別の案（S2 の 1 行の単位）**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1 要求 1 行（採る） | 受けた要求の本文を、マスクの規則を当てた後、1 行にする | 受けた形（入れ子の構造）を変えずに残し、S1 を作り直す元にできる。受信の処理が小さい | DuckDB で読むと、`resourceLogs` → `scopeLogs` → `logRecords` の入れ子を展開する SQL が要る（[引継ぎ資料 v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.5 のひな形で書ける）。1 行が大きくなりうる（[§9](#sec-9) の 7） |
| 1 レコード 1 行 | 受信サーバが、logRecord・span・データ点ごとに 1 行に分け、resource の属性を各行に写す | DuckDB の SQL が平らになる | 受信の処理が大きくなる。受けた形から変えるので、分け方の誤りを後から直せない |

**別の案（S2 への追記の仕方）**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 書き手 1 つの列で非同期に追記し、書けてから 200（採る） | 上のとおり | 上の理由 | 列の上限と、上限を超えたときの応答を持つ。強制で止めると列に残った行は書かれない（200 を返していないので、送り手からの見え方は止まっていた間と同じ） |
| 同期の追記 | 1 要求ごとに同期の追記で書き、書けてから 200 | 列が要らず、書き方が最も単純。Node.js は 1 つのスレッドでイベントを処理するので、行は混ざらない | 追記の間、受信サーバのイベントの処理が止まり、ディスクが遅いとほかの要求を受けられない |
| 列に並べたら 200 | 列に並べた時点で 200 を返し、追記は後で行う | 応答が速い | 書けなかった記録にも 200 を返し、送り手が送り直さない。「200 は保存済み」が崩れる |

- S1 の書き手を 1 つにすれば、S1 への書き込みの順が取込の中で決まる
- lmo-report の最初の版を確認観点に当たる集計に絞るのは、Phase 3 の合否をこの集計で見るためで、指標の全体（問い①〜③）を作ると Phase 3 が膨らむ

**残る未確認**: 受信サーバが追記している当日の JSONL を、別のプロセスの DuckDB で読めるか（見込み）。Phase 3 で、[V-ID 別紙 §2](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の「書き込み中の JSONL を別プロセスの DuckDB で読めるか」の行で確かめる。読めなければ、DuckDB では閉じた前日までのファイルだけを読み、当日分は S1 で見る（[まとめ §3.1](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-1) の残存リスクの対策と同じ）。

<a id="sec-2-4"></a>
### 2.4 traces の受け口（AR-01a）

**決めたこと**: 受信サーバは、logs・metrics と同じ受け口で `/v1/traces` も受け、span を S2 の `raw\traces\` に残す。span を S1 のどの表に入れるかと、集計の正本と結合の規則は、組 B が決める（[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-02・H-26）。

**理由**

- logs・metrics に出ない API 呼び出し（ターン終了後の `side_query`、自前の auto mode の分類器のリクエスト）は、traces の span にだけ出る（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「分析指標」）。費用の集計に span を含める（[計画書 Phase 2「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）ので、受けて残す
- span を受けて残しておけば、集計の正本を traces と logs のどちらにしても足りる（[1-4 §6](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-6) の traces の注記）
- traces は beta 機能で、版で形が変わりうる。生のまま S2 に残せば、形が変わっても取込を直して読み直せる

送信側の traces の有効化（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` と `OTEL_TRACES_EXPORTER`）は組 D（EN-04。[組 D §1.2](../04.有効化とデータ保全/設計書.md#sec-1-2)）が決める。traces は、送信先とプロトコルに共通の OTLP の設定を使う（docs ed2bfc5 L75670）ので、受信サーバも受け口も分けない。

<a id="sec-2-5"></a>
### 2.5 UI の仮置き（AR-01b）

**決めたこと**: UI は受信サーバと別のプロセスにし、S1（SQLite）を主に読む（読み先は [§2.3](#sec-2-3) の表）。UI は読むだけで、S2（生の JSONL）を直接読まない。受信サーバには集計の問い合わせ口を持たせない。ライブ表示は、受信サーバの配り口を購読する（[§2.7](#sec-2-7)）。

- S2 にしか無い情報を画面に出すときは、取込（lmo-ingest）で DB に取り込んでから読む。取り込み先は S1 を第一とし、S1 と別の DB（DuckDB のファイルなど）にするかは Phase 5 で決める（`.duckdb` を持たない今の理由は [§2.3](#sec-2-3)）。どの情報を足すかは、Phase 5 で画面の要件から決める。材料は、S1 に入れない S2 の中身の一覧（span の event など。[組 B §1.1](../02.データモデルと集計/設計書.md#sec-1-1)）である
- 方式（D1 / D2）とプロセスの名前は、Phase 5 の着手時に決める（[計画書 Phase 5](../../00.活動計画/活動計画書.md#sec-p5)）
- それまでは画面を作らず、DuckDB の SQL で直接集計する（探索期。[まとめ §3.2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-2)）
- Phase 3 の簡易集計は、lmo-report の CLI の出力で行う（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3)）

**理由**

- S1 を主に読むのは、S1 が集計に向いた形で、生の JSONL を読むより効率がよいためである。S2 にしか無い情報も取り込んでから読むのは同じ理由で、画面を出すたびに生の JSONL を展開しない。S2 を直接読むのが lmo-ingest と探索だけなので、S2 の形（H-06）が変わっても、UI は直さずに済む
- D1（自作 Node.js）は、S1 を `node:sqlite` で読める。DuckDB のファイルを足すなら、DuckDB CLI の子プロセスで読める（[1-5 §7](../../01.基礎調査/05.ダッシュボード方式/調査報告書.md#sec-7) の決め手 3）
- D2（Observable Framework）は、SQLite・DuckDB を Wasm 経由で読める（[まとめ §3.2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-2)）
- どちらも読むだけなので、S1 の WAL の下で、受信と取込を止めずに読める（[§2.3](#sec-2-3)）

**画面案の依存**: D1 は、可視化ライブラリを使えばその npm パッケージに依る。D2 は npm パッケージで、ビルドの道具を含むので、間接の依存は D1 より多い【推定】（[1-7 §6.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-6-1)）。Phase 5 で画面案を選ぶときに、依存の多さを比べる軸に入れる（[J-13](../../01.基礎調査/作業指示者裁定待ち事項.md#sec-1) の推奨）。

### 2.6 コードの置き場所

割り当て表の行には無いが、[活動 CLAUDE.md](../../../CLAUDE.md) の成果物の配置が「配置の確定は Phase 2」とするので、ここで決める。

**決めたこと**: 実装コードは活動フォルダの `app/` に置く。収集したデータは `app/` に置かず、データの根（[§4](#sec-4)）に置く。

| フォルダ | 置くもの |
|---|---|
| `app/bin/` | コマンドごとの起動スクリプト。H-05 の名前ごとに `<名前>.mjs`（`lmo-receiver.mjs`・`lmo-ingest.mjs`・`lmo-report.mjs`・`lmo-ctl.mjs`・`lmo-launch.mjs`・`lmo-judge.mjs`） |
| `app/lib/` | 共通の部品（パスの決め方、S2 の行の読み書き、分類の部品など） |
| `app/hooks/` | hook のスクリプトの元（`l1-tag.mjs`・`session-start.mjs`。H-27） |
| `app/` の下のほかのフォルダ | repo に置いてよいデータ。置き場所はそのデータの正本の組が決める（公開の料金の単価表は `app/config/price-tables/`。[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-23。分類体系と規則のデータは `app/config/taxonomy/`。[組 C §1.1](../03.作業分類タグ/設計書.md#sec-1-1)。端末に依らないデータの表のファイルは `app/config/` の直下（`query-source-map.json` など）。[定義の別紙 §1.1](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-1)） |

コマンドは、`app/bin/` の絶対パスで起動する（打つ形は H-05）。スクリプトは自分の場所（`import.meta.url`）から `app/` を求め、今のフォルダに依らずに動く。ランチャは今のフォルダを引き継ぎ、そこで cc を起こす（[組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3)）。

hook のスクリプトは、元を `app/hooks/` に置き、ユーザ settings が指すのはデータの根の `hooks\` に写したものにする（H-27）。

- 写すのは、hook が実行時に読むもの全部（`app/hooks/` のスクリプト、`app/lib/` の分類の部品、`app/config/taxonomy/` の分類体系と規則のデータ）である。`app/` の下のフォルダの構成を保って写し（`hooks\hooks\l1-tag.mjs`・`hooks\lib\`・`hooks\config\taxonomy\taxonomy.json`）、ファイルの名前も元と同じにする。スクリプトの相対の読み込み（例 `../lib/`）が、元と写しで同じに動く
- 写すのは Claude で、hook を直したら写し直す。写した後に、写しの各ファイルが元と同じ（ハッシュが同じ）ことを確かめる。写す手順をスクリプトにする（H-05 にコマンドを足す）かは、Phase 3 で写す回数を見て決める
- ユーザ settings の hook の `args` には、写しの絶対パスを、変数を展開した形で書く（settings に書く形は[組 C §2.2](../03.作業分類タグ/設計書.md#sec-2-2)）

**理由**

- 計画書の Phase 3・Phase 4 の成果物は `app/` の下である（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3)）。起動スクリプトの名前をコマンドの名前（H-05）と同じにすれば、名前からファイルを一意に指せる
- 絶対パスで起動するのは、ランチャと、Claude Code が打つ lmo-ctl・lmo-report が、活動フォルダでない作業フォルダ（他のリポジトリ）から打たれるためである
- hook を写しから動かすのは、ユーザ settings が repo の作業ツリーを直接指すと、ほかのブランチを checkout したときにファイルが無くなり、hook が黙って失敗してラベルが欠けるためである（[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）

<a id="sec-2-7"></a>
### 2.7 ライブ表示の経路

受信から数秒で見たい値を UI に出す経路をここで決める。出してよい項目の規則は[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の許可リスト（H-32）、項目の形は[組 B §1.12](../02.データモデルと集計/設計書.md#sec-1-12)（H-33）にある。

**決めたこと**: 受信サーバが、S2 に書けた要求から許可リストの項目だけを抜き出し、プロセスの中で配る（pub/sub）。UI は受信サーバの配り口を購読する。ライブの値は S1 に書かない。

- 配り口: 受信と同じ待ち受け（H-08 のアドレスと番号）の `GET /lmo/live` で、Server-Sent Events（`Content-Type: text/event-stream`）で配る。1 件を 1 つの `data:` の行の JSON にする（形は組 B §1.12）
- 抜き出す時点と元: 要求の行を S2 に書けて 200 を返した後に、マスクの規則（H-04）を当てた後の JSON から抜き出す。S2 に書けなかった要求と、列の上限で断った要求（[§2.2](#sec-2-2)）は配らない
- 購読が 1 つも無いときは、抜き出さない。ただし、`session.id` から `session_seq` への対応だけは持つ。番号は、購読の有無に依らず、受信サーバの起動から、S2 に書けた要求の中の `claude_code.api_request` の記録の `session.id` が初めて現れた順に振る（[組 B §1.12](../02.データモデルと集計/設計書.md#sec-1-12)）。購読が無い間は、その記録から `session.id` だけを拾う
- 購読の数の上限は 4 にし、超えた購読は 503 で断る。購読への送りの溜まり（書き出せずに残っている量）が 1 MB を超えたら、その購読を切る（UI は繋ぎ直す）。15 秒ごとに SSE の注釈の行を送り、繋がりを保つ。3 つの値で足りることは【推定】で、確かめる時期は [§9](#sec-9) の 14 にある
- 繋いだときは、過去の項目を送らず、受信サーバの起動の時刻と取込の間隔を 1 件だけ送る。それより前の値は S1 で見る
- 配り口は、要求の `Host` のヘッダが待ち受けのアドレスと番号（既定は `127.0.0.1:4318`）のときだけ応じ、ほかは 403 で断る（`/v1/*` と同じ確かめ。[§2.2](#sec-2-2)）。CORS のヘッダは付けない。UI の方式と origin を決める Phase 5 で、その origin 1 つだけを許す形にする
- 守りが働いた数は、動作の記録の `hourly` に残す（[§2.9](#sec-2-9)。`live_bad_host`: 配り口の 403、`live_full`: 購読の上限で断った 503、`live_dropped`: 送りの溜まりで切った購読）。守りが働くかは、Phase 3 で受信サーバを作ったときの試験で確かめる（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の確かめ方）
- 受信サーバを止めると、配りも止まる。UI は、繋がらない間は S1 の値だけを出し、受信サーバが動いていないことを出す
- 作る時期: 配り口は Phase 3 の受信サーバに入れ、scratchpad の試しの購読のスクリプトで負荷を測る。購読して画面に出すのは Phase 5 の UI である

**負荷**（受信の 1 要求あたりに足す処理）: 購読があるときは、マスクした後の JSON を 1 回たどって許可リストの項目を拾い、1 件 数百バイトの JSON にして、購読の数だけ書き出す。購読が無いときは、`claude_code.api_request` の記録の `session.id` を拾って番号の対応を持つだけである。たどる量はマスクと同じ程度で、ふだんの要求（数 KB〜数百 KB）では 1 ms に届かない【推定】。Phase 3 で、購読 0 と 1 のときの要求ごとの処理の時間（[§2.9](#sec-2-9) の動作の記録）を比べる（[§9](#sec-9) の 11）。

**理由**

- 全部をライブにしない。本文系とマスクが要りうる属性は、マスク → S2 → 取込 → S1 の通常の経路で入り、ライブ表示に出すのは、データの性質でも処理の負荷でも支障の無い数と区分だけにする（規則は組 D §2.3）
- S2 に書けた後に配るので、ライブに出た値は S2 にもある。ライブにだけ出て保存されない値は無い
- S1 に書かないので、S1 の書き手は lmo-ingest だけのままである（[§2.3](#sec-2-3)）。ライブの値と S1 の値の関係（ライブは速報で、正は S1）は組 B §1.12 にある
- プロセスの中で配るので、ディスクへの書き込みも、常駐のプロセスも増えない。`node:http` と `node:events` で書け、npm パッケージは要らない（J-34）
- 購読が無い間も `session_seq` の対応を持つのは、同じ受信サーバの中では、ブラウザを開き直して購読し直しても、同じセッションが同じ番号になるためである。購読の始まりから振ると、繋ぎ直すたびに番号の意味が変わる。振る元を S2 に書けた要求の `claude_code.api_request` の記録に限るのは、番号を出す項目が `api_request` だけで（組 B §1.12）、配るのも S2 に書けた要求だけだからである。購読の有無で振る元を変えないので、番号の順の意味も変わらない
- 配り口を受信と同じ待ち受けに置くのは、ループバックの待ち受けを 1 つに保つためである。`Host` を確かめるのは、ブラウザで開いたほかのサイトが、自分の名前を 127.0.0.1 に向け直して配り口を読む手（DNS rebinding）を断つためである。CORS のヘッダを付けないのも、ほかのサイトのページから読ませないためである
- 受信サーバは手動で起動する（J-29）。受信サーバが止まっている間は cc の送信も届かないので、ライブ表示も受信サーバが動いている間だけで足りる

**別の案（ライブの値の渡し方）**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 受信サーバが配り、UI が購読する（採る） | 上のとおり | 上の理由 | 受信サーバに配り口と購読の扱いが加わる（購読が無ければ、`session.id` の番号の対応を持つだけ）。UI が繋ぎ直す間の速報は欠ける（正は S1 にある） |
| 取込の受け手がライブ用の小さな表を S1 に書く | 受信サーバが項目を常駐の受け手に知らせ、受け手が S1 の表に書き、UI は S1 だけを読む | UI の読み先が S1 だけになる。繋ぎ直しで欠けない | 要求ごとに S1 に書き、常駐の受け手が要る（[§2.1](#sec-2-1) の別の案の短所）。S1 の書き手が 2 つになるか、lmo-ingest を常駐にする |
| 受信サーバがライブ用のファイルに書き、UI が読む | データの根の下のファイルに項目を足し、UI が末尾を読む | 配り口が要らない。繋ぎ直しで欠けない | 要求ごとのディスクへの書き込みと、そのファイルの保持の規則が要る。UI が読む間隔の分だけ遅れる |

<a id="sec-2-8"></a>
### 2.8 取込（lmo-ingest）の振る舞い

lmo-ingest の 1 回の動きを決める。契機と頻度、ロックが取れないときの契機ごとの動きは組 D の H-11、取込の記録の項目は組 D の H-12（どちらも[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）、派生の表と列の作る順と範囲、遅れて届く記録の扱いは[組 B §1.1](../02.データモデルと集計/設計書.md#sec-1-1) にある。

**決めたこと（起こし方）**

- どの契機でも、`node <活動フォルダ>\app\bin\lmo-ingest.mjs` を別のプロセスとして起こし、契機を引数で渡す（引数は [§2.10](#sec-2-10)）
  - lmo-receiver は子プロセスとして起こし、終わりを待たずに受信を続ける。子が終わったら、動作の記録に書く（[§2.9](#sec-2-9)）
  - lmo-report も子プロセスとして起こし、終わってから集計する。子の標準エラー（ロックを待つ間の表示など）は、そのまま lmo-report の標準エラーに通す
  - lmo-judge も、判定する作業の一覧を出す前に子プロセスとして起こし（`--trigger judge`）、終わってから一覧を出す。子の標準エラーの通し方は lmo-report と同じである
  - 手動の取込は、作業指示者か Claude Code が打つ。下の作り直しも手動の取込である

**決めたこと（1 回の流れ）**

1. ロックを取る（下の「ロック」）
2. 設定のファイルを読む（L2 の切り替え。組 C の H-31。[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1)）
3. 分類体系のデータ（repo の `app/config/taxonomy/taxonomy.json`。形は[組 C §1.1](../03.作業分類タグ/設計書.md#sec-1-1)）を読む。読めなければ、その回の取込を失敗にする（下の「異常のとき」）
4. 源（S2、transcript、[§4](#sec-4) の OTel の外の記録）ごとに、読むファイルと読み始める位置を決める（下の「読んだ位置」）。日常の取込では、あわせて、計測用のセッションを除く集合（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の H-11）を作り、日常のデータの根の除く一覧（`state\measure-sessions.json`）に無いセッションを「新しく入ったセッション」とする
5. 読んだ記録を取込の側の差し込み口（[§2.2](#sec-2-2) のマスク。今は何も当てない）に通し、元の表に入れる（表と列は[定義の別紙 §1](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1)）。S1 に入れない S2 の中身（span の event（OTLP の `spans[].events[]`）・link・`status` など。一覧は[組 B §1.1](../02.データモデルと集計/設計書.md#sec-1-1)）は読み飛ばす（S2 にだけ残る）
6. 4 で新しく入ったセッションがあれば、その行を日常の S1 の元の表と派生の表から消す（消したセッションの数は取込の記録の `transcript.measure_removed`）。そのうえで派生の表と列を作る（順と範囲は組 B §1.1。新しく入ったセッションも、変わったセッションとして作り直す範囲に入る。L2 の事後分類と、旧い版の区分に対応表を当てるときに、3 で読んだ分類体系のデータを使う）
7. S1 への書き込みを確定する（下の「書き込みの単位」）
8. 読んだ位置を更新する。4 で新しく入ったセッションを除く一覧に足す（一覧からは消さない）
9. 取込の記録（H-12）を書く
10. ロックのファイルを消す

**決めたこと（読んだ位置）**

- 置き場所は `<データの根>\state\ingest-positions.json` である。源のファイルごとに、パス（データの根か cc の設定フォルダからの相対）、大きさ、更新の時刻、読み終えた位置を持つ
- 続きから読むファイル（下の「読み方」の 1 つ目）の読み終えた位置は、最後に読んだ改行の後ろのバイト位置である。改行で終わらない末尾は、ファイルの最後の更新から 30 分以内なら書いている途中として位置に含めず、次の回に読む。30 分を過ぎていれば読めない行に数え、位置をファイルの終わりにする（30 分と数え方は組 D §2.4）
- 読み方は源で分ける
  - 追記だけのファイルのうち S1 の元の表に入れるもの（S2 の日別のファイル、L1 のラベル、`SessionStart` の記録、品質の記録）は、前の位置の続きから読む。大きさが前の位置より小さくなったファイルは、そのファイルから入れた元の表の行を消して、初めから読み直す
  - ランチャの起動の記録（`run\launch\`）、`api-bodies\index.jsonl`、計測用のセッションの記録（`run\measure\`）は、取込のたびに初めから読む。使い方（ランチャの確かめ、計測用のセッションの除外）と、日常の取込と計測用の取込で読む `run\measure\` の範囲は、組 D の [§1.3](../04.有効化とデータ保全/設計書.md#sec-1-3)・[§1.4](../04.有効化とデータ保全/設計書.md#sec-1-4) にある
    - ランチャの起動の確かめは、確かめが済んでいない（`pending` の。`launch_check` に行の無い）起動だけを確かめる。済んだ起動の結果は S1 の `launch_check`（[定義の別紙 §1.1](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-1)）に 1 行で残し、後の回で変えない（判定の規則は組 D §1.3）。その回に済んだ数と `pending` の数は、取込の記録の `launch_checks` に書く（項目は組 D §2.4 の H-12）
    - `index.jsonl` の行が指す raw body のファイルは、まだ読んでいないものだけを読み、読んだファイルを読んだ位置に残す。指すファイルが無いか JSON として読めないときは、その行の時刻（`timestamp`）から 30 分以内なら次の回に回し（読んだ位置に残さない）、過ぎたら読めないファイルとして取込の記録の `unreadable`（`source` は `api_body_file`。組 D §2.4 の H-12）に数え、読んだ位置に残す。次の回に回したファイルの数は、取込の記録の `api_bodies.deferred_body_files` である。30 分は、組 D §2.4 の書いている途中と同じ線である。消したファイルから前に入れた行は、作り直しでも残す（下の「通常と作り直し」）。作り直しでは、元の表に行が残っているファイル（突合の後に消したもの）を読めないファイルに数えない
  - transcript とサブエージェントの `meta.json` は、大きさか更新の時刻が前回から変わったものを、初めから読み直す（transcript の読み方の正本は組 D §2.4）
  - 単価表など、記録でないファイルは毎回全体を読む
- 位置のファイルと除く一覧は、一時のファイルに書いてから名前を替える。書きかけのファイルを残さない

**決めたこと（ロック）**

- ロックは `<データの根>\state\ingest.lock` で、ファイルが無いときだけ作る形（排他の作成）で取る。中身は JSON で、`pid`（プロセス番号）、`acquired_at`（取った時刻。UTC、ISO 8601）、`trigger`（契機）を持つ
- 終わるときは、成功でも失敗でもロックを消す
- ロックがあるときは、`pid` の番号のプロセスがあるかで、持ち主が居るかを見る
  - 居なければ（強制終了で残ったロック）、ロックを消して取り直し、取込の記録の `stale_lock_removed` を真にする
  - 居れば、組 D §2.4 の契機ごとの動きのとおり、飛ばすか待つ。飛ばすときは、取込の記録を書かずに終了コード 3 で終える（[§2.10](#sec-2-10)。飛ばした回は lmo-receiver が動作の記録に書く）
- 待つときは 1 秒ごとに取り直す。待ち始めと、その後 30 秒ごとに、ロックの契機と取った時刻を標準エラーに出す
- 待つ上限は置かない。初回の取込（transcript の 30 日分）の所要が未測定で、上限を決める材料が無いためである。Phase 3 で初回とふだんの取込の所要を測り、上限を置くかを決める（[§9](#sec-9) の 12）
- プロセス番号が別のプロセスに使い回されると、残ったロックの持ち主が居るとみなされる。その間、間隔ごとの取込は飛び、lmo-report・lmo-judge の前と手動の取込は待ち続ける。待っている表示の取った時刻が古いことで気付き、作業指示者か Claude Code がロックのファイルを消す

**決めたこと（書き込みの単位）**

- 1 回の取込の S1 への書き込み（元の表、派生の表と列）を、1 つのトランザクションにする。確定した後に、読んだ位置を更新する
- 確定と位置の更新の間で落ちたら、次の回に同じ行を読み直す。元の表の一意の鍵（定義の別紙 §1）で、同じ行は二重に入らない
- 1 つのトランザクションの大きさ（初回の取込の 30 日分）で、メモリと WAL のファイルの大きさに困らないことは【推定】である（[§9](#sec-9) の 12。作り直しの大きさは下の「通常と作り直し」）

**決めたこと（通常と作り直し）**

- 通常: 上の読んだ位置に従って、新しい行と変わったファイルを読む。lmo-receiver・lmo-report・lmo-judge が起こす取込と、引数なしの手動の取込は通常である
- 作り直し（`--rebuild`）: 単価表（組 B の H-23）・データの表・取込の規則を直したときに、作業指示者か Claude Code が打つ。前の読んだ位置を使わずに、残っているファイルを初めから読み、S1 の行を消して作り直す。ただし、元のファイルが残っていない行は消さずに残す
  - 残すのは、次の 2 つの種類の元の表の行のうち、元のファイルが無いものである
    - 元のファイルの位置（`source_ref`）を持つ元の表（`transcript_usage`・`subagent_invocation`・`raw_body_usage`・`l1_hook_record`。[定義の別紙 §1.1](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-1)）。`source_ref` の指すファイルの有無で見分ける
    - S2 から作る元の表（[定義の別紙 §1.2](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-2) の共通の列を持つ 9 つと、共通の列を持たない `session_identity`）。共通の列を持つ表は、`s2_ref` の指す S2 のファイルの有無で見分ける。`session_identity` の見分け方は定義の別紙 §1 にある
  - 本活動の間に当たるのは、cc が既定の 30 日で消した transcript と、消してよいとした raw body から作った行である（[組 D §2.2](../04.有効化とデータ保全/設計書.md#sec-2-2)・[§2.1](../04.有効化とデータ保全/設計書.md#sec-2-1)）。S2、L1 のラベル、`SessionStart` の記録、品質の記録は、本活動の間は消さない（組 D §2.1）ので、そこから作る行は読み直しになる
  - ランチャの起動の確かめの結果 `launch_check` の行は、元のファイルの有無に依らず、すべて残す（元のファイルの無い行と同じ扱い）。作り直しの後も、`pending` の起動だけを確かめる
  - ほかの元の表の行は消して、残っているファイルから読み直す
  - 計測用のセッションの除く一覧（`state\measure-sessions.json`）は、作り直しでも消さずに使う。前の読んだ位置（`state\ingest-positions.json`）だけを使わない
  - 集計の正本 `usage_record` と派生の列（見なし費用、`prompt_label` のラベル、L2 の事後分類）は、残した行と読み直した行から作り直す（組 B §1.1）。残した行の元のファイルは無く、読み直さないので、同じ行が二重にならない
  - 作り直しも 1 つのトランザクションで行い、確定の後に読んだ位置のファイルを置き換える。途中で失敗したら、S1 と読んだ位置は作り直しの前のままである。本活動の間の S2 の全体を読む作り直しの大きさは【推定】である（[§9](#sec-9) の 13）

**決めたこと（異常のとき）**

- 取込が失敗したら（例外、S1 に書けない、分類体系のデータを読めない）、トランザクションを戻し、読んだ位置を変えずに、取込の記録に `status` を `error` として `err` を書き、終了コード 1 で終える。次の契機の取込が、確定した位置の続きから読み直す
- 取込の記録も書けないとき（ディスクが一杯など）は、標準エラーに出して終了コード 1 で終える
- S1 のファイル（`db\telemetry.sqlite`）が無いか開けないとき
  - 開けないとき（ファイルはある）と、無いのに読んだ位置（`state\ingest-positions.json`）が残っているときは、表を新しく作らずに取込を失敗にする（取込の記録の `status` は `error`、終了コード 1）。作り直しを促す文（下の戻し方）を標準エラーに出す。lmo-ctl の `start` は、最後の取込の失敗の警告で知らせる（[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の警告の 2）
  - 無くて、読んだ位置も無いときは、初回の取込として表を作る
  - 戻し方は 2 つある。どちらも、受信サーバを lmo-ctl の `stop` で止め、取込が動いていない（ロックのファイル `state\ingest.lock` が無い）ことを確かめてから行う。受信サーバは、戻し終えてから（(2) では作り直しが終わってから）`start` で起こす
    - (1) 写した S1（`db\`）と読んだ位置（`state\ingest-positions.json`）を一緒に戻す（写し方は[組 D §2.1](../04.有効化とデータ保全/設計書.md#sec-2-1) のバックアップ）。除く一覧（`state\measure-sessions.json`）は、写した後に足したセッションも持つ今のものを残す。ただし、`state\` も失っていたとき（今のものが無いとき、または、その後の初回の取込が今のものを作り直したとき）は、写しの一覧を戻す
    - (2) `db\` の中身と `state\ingest-positions.json` を退けて、作り直し（`--rebuild`）を打つ。除く一覧は退けない
  - S1 が無いまま打った作り直しは、取込の記録に `rebuild_without_s1` を真で残す（項目は組 D §2.4 の H-12）。S1 にだけ残っていた行（元のファイルが消えた行と `launch_check`）が戻らなかった印である
- 知らせ方
  - lmo-receiver は、起こした取込の終わりを動作の記録に書き（[§2.9](#sec-2-9) の `ingest_exit`。ロックで飛ばした回は `ingest_skipped`）、次の間隔でふだんどおり起こす。取込の失敗が続いても、受信は止めない
  - lmo-report は、集計の前に自分が起こした取込が失敗したら、標準エラーに警告を出し、S1 の今の内容で集計を出して、終了コード 3 で終える。lmo-report は動作の記録に書かない
  - lmo-judge は、一覧の前に自分が起こした取込が失敗したら、lmo-report と同じく、標準エラーに警告を出し、S1 の今の内容で一覧を出す。終了コードは 3 である（[§2.10](#sec-2-10)）
  - lmo-ctl の `start` は、最後の取込の記録が `error` なら警告を出す（[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）
  - 手動の取込は、終了コードと標準エラーで、打った人に知らせる

**理由**

- どの契機でも取込を別のプロセスにするのは、S1 に書くプロセスを lmo-ingest だけに保つためである（[§2.3](#sec-2-3)）。lmo-receiver が取込の終わりを待たないのは、受信を止めないためである（[§2.1](#sec-2-1)）
- lmo-judge が一覧の前に取込を起こすのは、受信サーバが止まっていて間隔の取込が動かないときも、直前に終えた作業が一覧に出るためである。作業指示者が手動の取込を先に打つ手間が無く、lmo-report と動きがそろう
- ロックを、ファイルが無いときだけ作る形にするのは、プロセスをまたいで効き、`node:fs` だけで書けるためである。持ち主の居ないロックを消すのは、強制終了で残ったロックのために以後の取込が動かなくなるのを避けるためである
- 1 回の書き込みを 1 つのトランザクションにし、確定の後に位置を更新するのは、途中で落ちても S1 と読んだ位置が食い違わないためである。読み手（lmo-report・lmo-judge・UI）は WAL の下で確定の前の状態を読み、取込の途中の状態を見ない
- 追記だけのファイルを続きから読むのは、新しい行が位置で決まるためである。transcript を初めから読むのは、cc がファイルを削って縮めることがあるためである（組 D §2.4）。ランチャと計測用のセッションの記録と `index.jsonl` を毎回初めから読むのは、確かめが済んでいない起動と、除く集合に新しく入ったセッションを見つけるのに、毎回すべての起動とセッションを見る必要があり、どれも小さいためである（組 D §1.3・§1.4）
- 済んだ起動の確かめの結果を変えないのは、cc が transcript を消した後（既定 30 日）や、突合の後に raw body を消した後に、`ok` だった起動が `missing` に変わらないためである。T1 と T2 を比べる手順は `launch_check` を読む（組 D §1.3）
- 除く集合に新しく入ったセッションの行を消すのは、計測用のセッションの記録が日常の取込より後に書かれたときに、それまでに入った行を日常の S1 に残さないためである（[組 B §3.1](../02.データモデルと集計/設計書.md#sec-3-1) の「日常の S1 には作らない」）。除く一覧を `state\` に持って消さないのは、計測のデータの根を消した後も、除く集合が変わらないためである
- raw body の本文のファイルにも 30 分の線を置くのは、cc が `index.jsonl` の行と本文のファイルを書く順が docs に無く（docs ed2bfc5 L76447）、書く前か書きかけのファイルを読んだことにすると、その要求の経路 (ii) の値が後の回にも入らないためである
- S1 が無いのに読んだ位置が残っているときに表を新しく作らないのは、続きから読む取込が前の位置より後の行だけを入れ、黙って欠けた S1 ができるためである。読んだ位置と S1 は 1 組で意味を持つ
- 戻し方の (1) で除く一覧を写しのものに戻さないのは、写した後に一覧に足し、その後に計測のデータの根を消したセッションを、除く集合から外さないためである。`state\` も失っていたときに写しの一覧を戻すのは、初回の取込が作り直した一覧は根が残る計測用のセッションだけを持つためである（根が残るセッションは、次の取込が一覧に足し直す）。戻す・退ける前に受信サーバを止めるのは、受信サーバが起こす取込が、戻しかけの S1 を開くことと、(2) で作り直しの前に初回の取込として表を作ること（作り直しの `rebuild_without_s1` が真にならない）を避けるためである
- 作り直しを 1 つの動き方にするのは、取込の規則を直すたびに要る操作を、1 つの形にそろえるためである。元のファイルが消えた行を残すのは、ほかに元の無い記録を失わないためである。見分けを `source_ref`・`s2_ref` の指すファイルの有無にするのは、元の表ごとに元のファイルが決まっていて、行ごとに機械で判定できるためである
- OTel の元の表も残すのは、S1 の元の表から派生の表と列を作り直せることを、正式リリース物の保存の構成（J-35。[§6](#sec-6)）のどの案でも保つためである。保存を S1 だけにして S2 のファイルを消しても、OTel の元の表の行は残る
- 取込の失敗で受信を止めないのは、S2 に残った受信の記録を、次の取込で S1 に入れられるためである

**別の案**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1 回を 1 つのトランザクションにする（採る） | 上のとおり | 上の理由 | 初回の取込のトランザクションが大きい（[§9](#sec-9) の 12）。失敗すると、その回の全体を次の回に読み直す |
| 源のファイルごとに確定する | ファイルごとに元の表への書き込みを確定し、位置を更新する。派生の表と列は回の最後にまとめて作る | トランザクションが小さく、失敗しても進んだ分が残る | 元の表と派生の表がずれた状態を、読み手が見る。派生を作る前に落ちた回の扱い（どのセッションを作り直すか）を別に持つ |
| lmo-report が取込の部品を同じプロセスで呼ぶ | lmo-report の中で取込をしてから集計する | プロセスを起こさずに済む | S1 に書くプロセスが 2 種類になり、ロックと書き込みの規則を 2 か所で守る |

<a id="sec-2-9"></a>
### 2.9 受信サーバの動作の記録

**決めたこと**

- 置き場所は `<データの根>\run\receiver\<YYYY-MM-DD>.jsonl`（日付は書いた時刻の UTC）である。書くのは lmo-receiver だけである。取込は取込の記録（H-12）に書き、lmo-report・lmo-judge・lmo-ctl は動作の記録に書かずに、標準出力と標準エラーに出す（[§2.10](#sec-2-10)）
- 形: UTF-8、改行は LF、1 件を 1 行の JSON にする（取込の記録と同じ形）。本文、識別属性の値、例外の文は書かない
- 書くのは下の表のときだけで、数が少ないので、1 行ずつ同期の追記で書く
  - 日のファイルを開いて最初の 1 行を書くときは、S2 と同じく、ファイルの終わりが改行でなければ、行の前に改行を足して同じ書き込みに含める（[§2.2](#sec-2-2) の S2 への書き方）
  - 追記が失敗しても（ディスクが一杯など）、受信サーバは止めずに続ける。書けなかった行の数を数え、次に書けた `hourly` の行の `record_write_failed` に入れて 0 に戻す。`hourly` より先にほかの行が書けても、0 に戻さない
- どの行も、`v`（形の版。初版は 1）、`ts`（書いた時刻。UTC、ISO 8601）、`kind`、`pid`（lmo-receiver のプロセス番号）を持つ

| `kind` | 書くとき | 項目（共通の 4 つのほか） |
|---|---|---|
| `start` | 待ち受けを始め、鍵を読んだとき（鍵のファイルが無ければ作った後） | `host`・`port`（待ち受けのアドレスと番号）<br>`key_created`（その起動で鍵のファイルを作ったか。真偽値。[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）<br>`ingest_interval_min`（使う取込の間隔）と `ingest_interval_source`（`env`・`file`・`default`）。既定に戻したときは、`ingest_interval_rejected`（元の値を文字列にした先頭 32 字）と `ingest_interval_reason`（`not_integer`・`below_min`・`above_max`。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）<br>`l2_enabled`（使う L2 の切り替えの値）。設定のファイルを使えなかったときは `settings_issue`（`unreadable`: JSON として読めないか、オブジェクトでない。`not_boolean`: `l2_enabled` が真偽値でない。組 C の H-31） |
| `port_in_use` | 待ち受けの番号がすでに使われていて、終えるとき（[組 D §1.5](../04.有効化とデータ保全/設計書.md#sec-1-5)） | `host`・`port` |
| `host_not_loopback` | `LMO_OTLP_HOST` の値がループバックのアドレスでなく、起動をやめるとき（[§4](#sec-4)） | `host`（変数の値を文字列にした先頭 64 字） |
| `key_unreadable` | ハッシュの鍵のファイルがあるのに、読めないか形が違い、起動をやめるとき（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)） | `reason`（`read_error`・`bad_format`） |
| `hourly` | 毎時の区切り（UTC の正時）と、自分で止まるとき | `from`・`to`（区間）<br>`signals`: 信号（`logs`・`metrics`・`traces`）ごとに、`requests`（受けた要求の数）、応答ごとの数（`ok`: 200、`bad_json`: 400、`bad_host`: 403 の `Host` が待ち受けのアドレスと番号でないもの、`too_large`: 413、`bad_type`: 415、`mask_error`: 500、`write_failed`: 503 の書けなかったもの、`queue_full`: 503 の列の上限で断ったもの）、`body_bytes_max`（展開した後の本文の大きさの最大）、`over_16mb_lines`（16 MB を超えた行の数）<br>`not_found`（404）・`bad_method`（405）の数<br>`queue_len_max`・`queue_bytes_max`（列の長さと大きさの最大）<br>`proc_ms_p50`・`proc_ms_max`（要求ごとの処理の時間の中央値と最大。受けてから、応答を返してライブの配りを終えるまで）<br>`live_subscribers_max`（ライブの購読の数の最大）<br>`live_bad_host`（配り口で `Host` が合わずに断った 403 の数）・`live_full`（購読の上限で断った 503 の数）・`live_dropped`（送りの溜まりで切った購読の数）（[§2.7](#sec-2-7)）<br>`id_attr_dropped`（文字列でない識別属性を `<dropped>` に替えた数。組 D §2.3）<br>`record_write_failed`（前に書けた `hourly` の行より後に、書けなかった動作の記録の行の数） |
| `ingest_skipped` | 起こした取込が、ロックを取れずに飛ばしたとき（終了コード 3） | `trigger`（`receiver_start`・`interval`） |
| `ingest_exit` | 起こした取込が終わったとき（飛ばした回を除く） | `trigger`、`started_at`・`ended_at`、`code`（終了コード。[§2.10](#sec-2-10)） |
| `stop` | 自分で止まるとき（コンソールでの Ctrl+C など）。先に、その区間の `hourly` を書く | なし |

- 起動の順は、受け口のアドレスを確かめる（[§4](#sec-4)）→ 待ち受けを始める → 鍵を読む（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）→ `start` を書く → 要求の処理を始める、である。`LMO_OTLP_HOST` がループバックのアドレスでないときは `host_not_loopback` を、番号の衝突で待ち受けを始められないときは `port_in_use` を、鍵が読めないときは `key_unreadable` を書き、`start` を書かずに終える
- 受けた要求が 0 の区間も `hourly` を書く。受信サーバが動いていたことが分かる
- lmo-ctl の `stop` は受信サーバを強制終了する【推定】（[§2.2](#sec-2-2)、[統合 §8](../99.設計まとめ/設計書.md#sec-8) の 1）ので、`stop` の行と、その区間の `hourly` の行は書かれない。Phase 3 の確かめで区間の数を使う run は、正時の `hourly` の行が書かれた後に止める
- 毎時に区切るのは、Phase 3 で列の上限とライブ表示の負荷を見直す粒度にするためで、取込の間隔とは別である

**理由**

- 要求ごとに書かず毎時の数にまとめるのは、書く回数を受信の数に依らず小さく保ち、受信の処理に書き込みを足さないためである
- 取込の記録と同じ形の日別のファイルにするのは、読む側（lmo-ctl の `start`、Phase 3 の確かめ）が同じ読み方で読めるためである
- 動作の記録を書けなくても受信サーバを止めないのは、動作の記録は受信の付随の記録で、S2 に書ければ受けた記録は残るためである。書けなかった間があったことは、次に書けた `hourly` の行で分かる
- 本文・識別属性の値・例外の文を書かないのは、動作の記録を、本文を含む S2 と分けて扱えるようにするためである（Phase 3 の確かめの結果に写すときなど）

### 2.10 コマンドの引数と終了コード

**決めたこと**: 打つ形は `node <活動フォルダ>\app\bin\<名前>.mjs <引数>`（H-05。[§7.1](#sec-7-1)）で、引数と終了コードは下の表のとおりにする。

| コマンド | 打つ形と引数 | 終了コード | 振る舞いの正本 |
|---|---|---|---|
| lmo-ctl | `start`・`stop` のどちらか 1 つ | 0: `start` で、起こした受信サーバの待ち受けを確かめたか、受信サーバがすでに動いていた（警告があっても 0）。`stop` で受信サーバを止めたか、受信サーバが動いていなかった（待ち受けの番号が接続を断るか、ヘッダ `x-lmo-receiver-pid` の無い応答）<br>1: `start` で、待ち受けの番号に応答があるが、番号のファイルの受信サーバと確かめられない（応答にヘッダが無い、ヘッダの番号が番号のファイルと違う、番号のファイルが無い）か、起こした受信サーバを上限の時間までに確かめられない（番号の衝突、鍵が読めない、`LMO_OTLP_HOST` がループバックのアドレスでない、すぐ落ちた、待ち受けを始められない）。`stop` で、ヘッダの番号が番号のファイルと違うか番号のファイルが無いので止めないか、止めた後も上限の時間まで待ち受けの番号が接続を断らない。`start`・`stop` とも、待ち受けの番号に接続できたが上限の時間の内に応答が来ない（応えない受信サーバ。止めずに番号のファイルを残す）。表示する理由と上限の時間は統合 §2.1<br>2: 使い方の誤り（引数が無いときを含む） | [統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) |
| lmo-ingest | 引数なし: 手動の通常の取込（`trigger` は `manual`）<br>`--trigger <契機>`: lmo-receiver・lmo-report・lmo-judge が付ける（契機は `receiver_start`・`interval`・`report`・`judge`）<br>`--rebuild`: 作り直し（`trigger` は `rebuild`）<br>`--trigger` と `--rebuild` は一緒に付けない | 0: 済んだ<br>1: 失敗（分類体系のデータを読めないときを含む。取込の記録の `status` は `error`）<br>2: 使い方の誤り<br>3: ロックが取れず、飛ばした（飛ばす契機は組 D §2.4） | [§2.8](#sec-2-8) |
| lmo-report | `--since <YYYY-MM-DD>`・`--until <YYYY-MM-DD>`（どちらも任意。UTC の日付で、両端を含む。無ければ全期間）。集計は `usage_record` の `event_ts` の日付で、取込の記録から出す数（欠け、読めない行）は取込の開始の日付で絞る。出力の時刻は UTC で出し、`UTC` と添える（引数と同じ時間帯） | 0: 出した<br>1: 失敗（集計を出せない）<br>2: 使い方の誤り<br>3: 集計の前に起こした取込が失敗し、S1 の今の内容で出した | [§2.3](#sec-2-3)（最初の版の出力）、[§2.8](#sec-2-8)（取込を待つ間の表示と、取込の失敗） |
| lmo-launch | cc の引数をそのまま続ける（ランチャが足す引数は組 D §1.3） | cc の終了コードをそのまま返す。cc を起こせないときと、起動の記録を書けないときは 1（区別は標準エラーの文で行う） | [組 D §1.3](../04.有効化とデータ保全/設計書.md#sec-1-3) |
| lmo-receiver | 引数を持たない（lmo-ctl の `start` が起こす。設定は環境変数と設定のファイル。[§4](#sec-4)・組 D §2.4・組 C の H-31） | 1: 起動をやめた（番号の衝突、鍵のファイルが読めない、`LMO_OTLP_HOST` がループバックのアドレスでない。[§2.9](#sec-2-9)）。lmo-ctl の `stop` で止めたときは強制終了なので、終了コードを使わない | [§2.2](#sec-2-2) |
| lmo-judge | 引数は Phase 4 の実装で決める。どの引数でも、判定する作業の一覧を出す前に取込を子プロセスで起こす（`--trigger judge`）。一覧の時刻は UTC で出し、`UTC` と添える | 0: 済んだ<br>1: 失敗（S1 を読めない、品質の記録に書けない）<br>2: 使い方の誤り<br>3: 一覧の前に起こした取込が失敗し、S1 の今の内容で一覧を出した | [§7.1](#sec-7-1) の H-30、[§2.8](#sec-2-8)（取込を待つ間の表示と、取込の失敗） |

- 標準出力には結果だけを出し、警告と誤りは標準エラーに出す。警告と誤りの文には、本文と識別子の値を入れない（結果に出す一覧の中身は、各コマンドの正本の節にある）
- 使い方の誤りのときは、使い方を標準エラーに出す

**理由**: 終了コードを 0〜3 にそろえると、呼ぶ側（lmo-receiver・lmo-report・lmo-judge・Claude Code）が、成功・失敗・使い方の誤り・飛ばした（lmo-report と lmo-judge では取込の失敗）を、標準エラーの文を読まずに分けられる。出力の時刻を UTC で出すのは、引数（`--since`・`--until`）とファイル名の日付と同じ時間帯にそろえ、読み替えの規則を 1 つにするためである。lmo-launch が cc の終了コードを返すのは、ランチャを経ても cc を打ったときと同じに扱えるためである。

### 3.2 承認の対象、推奨、条件に当たったとき

**承認の対象**: 実装言語（案 1 / 案 2）と依存の方針。案 1 では、npm パッケージを使わないことを原則にする。

**条件に当たったとき**（J-34 の条件）: Phase 3 以降の実装で、受信・保存・取込・集計に npm パッケージが 1 つでも要る見込みが出たら（起動・停止・ランチャ・品質の記録のコマンドも、Claude が決めたこととして同じに扱う）、その時点で、パッケージの中身を添えて作業指示者に諮り、実装方針（Node.js のままか、言語を変えるか）を変えるかを検討する。添える中身と条件の対象は [統合 §2.3](../99.設計まとめ/設計書.md#sec-2-3) にある。諮って使うと決めたパッケージは、[§3.3](#sec-3-3) の一覧に足す。

**Claude の推奨**: 案 1（裁定と同じ）。

- 案 1 では npm パッケージを 0 にできる【推定】（[§9](#sec-9) の 4）。作業指示者がパッチを当てたい対象（第三者のライブラリ）が、収集の経路（受信と取込）に残らない。案 2 では、JSON と SQLite でライブラリが要る見込みで、パッチの対象がかえって増える【推定】

<a id="sec-4"></a>
## 4. 環境に依存しないパス（AR-05）

**決めたこと**: プロセスが使うパスは、次の 2 つの根から `node:path` で組み立てる。コードに絶対パスと区切り文字を埋め込まない。

| 根 | 決め方（上から順に、最初に当たったもの） | 根拠 |
|---|---|---|
| データの根 | (1) 変数 `LMO_DATA_DIR`<br>(2) Windows では `%LOCALAPPDATA%\local-mini-otel\`<br>(3) それ以外（WSL・Docker）では `$XDG_DATA_HOME/local-mini-otel/`、その変数が無ければ `~/.local/share/local-mini-otel/` | (2) は[計画書 Phase 2「データ保全とプライバシー」](../../00.活動計画/活動計画書.md#sec-p2-privacy)の「回答で決まったこと」の置き場所 |
| cc の設定フォルダ | (1) 変数 `CLAUDE_CONFIG_DIR`<br>(2) `~/.claude` | docs ed2bfc5 L64088（設定フォルダを変え、セッションの履歴もその下に置く）。transcript はその下の `projects` にある（[1-6 §2.1](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-2-1)） |

- 受け口のアドレスと番号も、変数 `LMO_OTLP_HOST`・`LMO_OTLP_PORT` で変えられるようにし、既定は H-08 の値にする
  - `LMO_OTLP_HOST` は、本活動ではループバックのアドレス（IPv4 の `127.0.0.0/8` と IPv6 の `::1`。名前は受けない）だけを受ける。ほかの値なら、受信サーバは動作の記録に `host_not_loopback` を書いて起動をやめる（[§2.9](#sec-2-9)）
  - Docker で外に開く形（第三のゴール）は、そのときに `Host` の確かめ（[§2.2](#sec-2-2)・[§2.7](#sec-2-7)）とあわせて決める
- ファイル名とフォルダ名の日付は、UTC の `YYYY-MM-DD` にする。端末のタイムゾーンで名前が変わらず、レコードの時刻（ISO 8601）の日付の部分と同じ形になる
- データの根を変数で変えるときも、クラウド同期の対象のフォルダと、ネットワーク上のフォルダには置かない。SQLite の WAL は、同じ端末のプロセスの間でしか効かない（[1-4 §3.3](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-3-3)）
- 既存のフォルダ（`v2b\`、`probe-<版>\`）は動かさない。`v2b\` は作業指示者の回答で決まった置き場所である（[計画書 承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24) の Q2・Q3 の行）

**理由**

- 第三のゴール（WSL + Docker）では、データの根と cc の設定フォルダの場所が Windows と違う。変数と OS の既定から決めれば、コードを直さずに動く（[計画書 Phase 2「全体構成」](../../00.活動計画/活動計画書.md#sec-p2-arch)の最後の点）
- cc の設定フォルダは `CLAUDE_CONFIG_DIR` で変えられる。`~/.claude` を決め打ちにすると、変えている環境で transcript を見つけられない
- アドレスをループバックに限るのは、変数 1 つの誤り（例 `0.0.0.0`）で、受け口とライブの配り口がほかの端末に開くのを防ぐためである（[§2.2](#sec-2-2) のループバックの決めごと）。開くと、配り口の `Host` の確かめは、ほかの端末がそのアドレスの名前で送れば通る。Docker のコンテナの中で待ち受ける形は、外から別の名前で届き、今の `Host` の確かめと合わない【推定】ので、第三のゴールで決める。変数は H-08 の受け渡しの値（変数で変えられる）として残す

**フォルダの構成**（H-07）

```text
<データの根>\
├── raw\                 S2。信号ごとのフォルダに日別の JSONL（H-06）。lmo-receiver が書く
│   ├── logs\
│   ├── metrics\
│   └── traces\
├── db\                  S1。telemetry.sqlite（WAL の付随ファイルを含む）。lmo-ingest が書く
├── state\               取込の読んだ位置、ロック、計測用のセッションを除く一覧 measure-sessions.json（§2.8、組 D §2.4）。lmo-ingest が書く
├── run\                 各プロセスの記録。下のフォルダごとに書き手が分かれる
│   ├── receiver\        受信サーバの動作の記録（H-34。§2.9）。lmo-receiver が書く
│   ├── ingest\          取込の記録（H-12。組 D）
│   ├── launch\          ランチャの起動の記録（組 D）
│   ├── measure\         計測用のセッションの記録（組 D。計測ごとのデータの根にだけある）
│   └── lmo-receiver.pid 受信サーバのプロセス番号と待ち受けの番号（lmo-ctl の stop か、自分で止まる受信サーバが消す）
├── api-bodies\          raw body の出力先（H-17。組 D）。cc が書く
├── config\              ハッシュの鍵（H-04。組 D）、職場の組の単価表の price-tables\（H-23。組 B）、L2 の切り替えの設定（H-31。組 C）と取込の間隔（同じファイル。組 D）、データの表のうち端末ごとのもの（env-config.json と、ゲートウェイの別名の model-alias.json。組 B）
├── labels\              L1 のラベル（H-18。下の形は組 C）。L1 の hook が書く
├── session-start\       SessionStart の記録（H-28。組 C）。SessionStart の hook が書く
├── quality\             品質の記録（H-30）。lmo-judge が書く
├── hooks\               hook のスクリプトの写し（H-27）。app\ の下の構成を保つ。Claude が写す
├── v2b\                 既存。V-2b の記録（消さない）
└── probe-<版>\          既存。probe の記録。計測ごとのデータの根もこの下に置く（組 D）
```

図は、データの根の直下に、記録の種類ごとに 1 つのフォルダと、設定（`config\`）と hook の写し（`hooks\`）を置く形を示す。

- 根の直下には、記録の種類ごとに 1 つのフォルダを置く。記録でないものは、設定（`config\`）と hook の写し（`hooks\`。[§2.6](#sec-2-6)）だけにする
- データの表のファイルは、端末や職場ごとに値が違うもの（`env-config.json`、ゲートウェイの別名の `model-alias.json`）をデータの根の `config\` に、端末に依らないもの（`query-source-map.json`、公開のモデル名の規則の `model-alias.json` など）を repo の `app/config/` に置く（§2.6 の規則。ファイルの一覧は[定義の別紙 §1.1](../02.データモデルと集計/【別紙】スキーマと指標の定義.md#sec-1-1)）
- 新しく作るフォルダの名前は ASCII の小文字・数字・ハイフンにする（WSL・Docker と DuckDB の glob で扱いやすい）。既存の `probe-<版>\` は、版の点を含むまま残す
- 括弧に H のあるフォルダの下の形（ファイルの名前と中身の形）は、その受け渡しの正本の節にある（H-06・H-27・H-30・H-34 は [§7.1](#sec-7-1)、ほかは組 B〜D）。hook の所要時間（H-19）は L1 のラベルのレコードに入る

## 5. 第二のゴールへの備え（組 A の分）

[計画書 Phase 2「第二のゴールへの備え」](../../00.活動計画/活動計画書.md#sec-p2-goal2)の 6 点のうち、組 A の構成に関わる 3 点である。どれも統合の行（[割り当て表 §1](../99.設計まとめ/【別紙】割り当て表.md#sec-1) の G2-04〜G2-06）で、組ごとの決めごとと照らして決めたことは[統合 §5](../99.設計まとめ/設計書.md#sec-5) にある。本節は、組 A の構成での形を書く。

<a id="sec-5-1"></a>
### 5.1 少ない依存（G2-04 に関わる）

[§3](#sec-3) の案 1（J-34）で、収集の経路（受信と取込）の依存は Node.js だけになる。DuckDB CLI は探索と UI の側（UI は、Phase 5 で読み先に DuckDB のファイルを足した場合）にだけ入るので、職場で DuckDB が使えなくなっても、受信と取込は止まらない。

<a id="sec-5-2"></a>
### 5.2 Git Bash に依らない起動（G2-05 に関わる）

組 A のプロセスは、どれも `node` に起動スクリプトを渡して起動する。sh のスクリプトと、Git Bash の道具（`tar`・`gzip` など）に依らない。圧縮が要るときは `node:zlib` を使える（[1-4 §5](../../01.基礎調査/04.受信・保存コンポーネント/調査報告書.md#sec-5) の #18）。受信サーバは手動で起動し、起動・停止のコマンド lmo-ctl も `node` で起動する（J-29。[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）。L1 の hook と `SessionStart` の hook は、exec 形式で `node` を起こす（[組 C §2.1](../03.作業分類タグ/設計書.md#sec-2-1)）。

<a id="sec-5-3"></a>
### 5.3 縮退運用の構成（H-25。G2-06 に関わる）

**決めたこと**（構成）: ループバック宛ての送信が届かない環境では、lmo-receiver を起動せず、lmo-ingest と lmo-report だけで回す。lmo-ingest は transcript と L1 のラベルから S1 を作り、lmo-report は S1 から集計する。切り替えは「受信サーバを起動しない」ことだけで、ほかのプロセスとフォルダは変わらない。

- S1 の `usage_record` に、transcript の usage だけから作る行を足す。行の種類の値と作れる列は組 B が決める（[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-26）。受信サーバを止めていた間のセッションを補う規則と同じで、S2 にそのセッションが 1 件も無いときに限るので、二重に数えない
- 欠けるもの: OTel にだけある記録（metrics、traces の span、`api_request` の属性のうち transcript に無いもの）。出せる指標と欠ける指標は[統合 §5](../99.設計まとめ/設計書.md#sec-5) にある
- 縮退運用は用意する（G2-06。統合 §5）。切り替えるか（G2-07）は Phase 7 の結果で決める

**理由**: 取込は受信サーバに依らずに動く（[§2.1](#sec-2-1)）ので、部品を足さずに縮退運用の形になる。

## 10. Devil's Advocate

| 対象 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| 常駐は受信だけ（[§2.1](#sec-2-1) の P1） | 取込を走らせるまで S1 が古く、当日の集計がすぐ出ない。1 つの常駐にまとめれば、S1 はいつも新しい | 棄却する。lmo-report は集計の前に取込を呼ぶので、見る時点の S1 は新しい。分析は数週間の単位（[計画書 Phase 6](../../00.活動計画/活動計画書.md#sec-p6)）で、秒の単位の新しさは要らない。数と区分は、ライブ表示（[§2.7](#sec-2-7)）で受信から数秒で見られる。残存リスク: ライブ表示に出ない値（本文系、transcript から入る思考トークンなど）は、取込の間隔（既定 1 時間。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の設定で 5 分まで縮められる）の分だけ遅れる |
| S2 への追記を書き手 1 つの列で非同期にする（[§2.2](#sec-2-2)） | 同期の追記なら列も上限も要らず、Node.js の 1 つのスレッドの処理で行は混ざらない。ふだんの要求は小さく、書き込みはすぐ終わる | 棄却する。ディスクが遅いときに、同期の追記は受信サーバのイベントの処理を止め、ほかのセッションの要求も待たせる。列は書き手 1 つと上限だけの小さな仕組みで、200 は書けた後に返すので、保存の意味は変わらない。残存リスク: 列の上限の値は【推定】（[§9](#sec-9) の 10） |
| ライブ表示を受信サーバが配る（[§2.7](#sec-2-7)） | 常駐の処理を小さく保つ方針（[§2.1](#sec-2-1)）に反し、配りの不具合で受信が止まりうる。速報と S1 の 2 つの値が並び、見る人が取り違える | 棄却する。購読が無ければ `session.id` の番号の対応を持つだけで、配りは S2 に書けた後で、送りの溜まった購読は切るので、受信の応答を待たせない。速報は S1 に書かず、UI では速報と分かる形で出す（[組 B §1.12](../02.データモデルと集計/設計書.md#sec-1-12)）。配り口の守り（`Host` の確かめ、CORS のヘッダを付けないこと、購読の上限、送りの溜まり）は、Phase 3 の試験で確かめる（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の確かめ方）。残存リスク: 配りの負荷と守りの値は【推定】（[§9](#sec-9) の 11・14） |
| 実装言語（[§3](#sec-3) の案 1。J-34） | Node.js 自体に脆弱性が出て職場で禁止されたら、受信も取込も止まる。Java なら、パッチを当てて使い続けられる | 残存リスク。cc 本体も Node.js 製である（[1-7 §6.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-6-1)）ので、その場合は cc も止まりうる【推定】。受信は小さく保ち、Java に書き移す費用を小さくする（[§3.2](#sec-3-2)） |
| S2 の 1 行を 1 要求にする（H-06） | 1 レコード 1 行にすれば、DuckDB の SQL で入れ子を展開せずに済み、探索が楽になる | 棄却する。S2 の役目は、受けた形のまま残し、S1 を作り直せることである。日常の集計は S1 で行う。残存リスク: 探索期に S2 を直接読む SQL には、入れ子の展開が要る |
| hook を写しから動かす（[§2.6](#sec-2-6)。H-27） | 写しは repo の外にあり、hook を直した後に写し直すのを忘れると、古い hook が黙って動き続ける。repo の作業ツリーを直接指せば、写し直しが要らない | 棄却する。作業ツリーを直接指すと、ほかのブランチを checkout したときに hook が黙って失敗する（[組 C §1.2](../03.作業分類タグ/設計書.md#sec-1-2)）。レコードに `hook_ver`・`rules_ver` が入る（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1) の H-18）ので、古い写しで付いたラベルは後から見分けられる。残存リスク: 写し直しは手作業で、気付くまでの間のラベルは古い規則による |
| `.duckdb` を持たない（[§2.3](#sec-2-3)） | DuckDB に取り込んだデータベースの方が、毎回 JSONL を読むより集計が速い | 残存リスク。日常の集計は S1（SQLite）で行い、DuckDB は探索に使うので、速さは Phase 3 の量で見る。遅ければ、探索用の写しの `.duckdb` を別の名前で作る（受信と取込はその写しに触れない） |
| 1 回の取込を 1 つのトランザクションにする（[§2.8](#sec-2-8)） | 初回の取込（transcript の 30 日分）を 1 つのトランザクションにすると、WAL のファイルが大きくなり、途中で失敗すると全部を読み直す。源のファイルごとに確定すれば、進んだ分が残る | 棄却する。失敗しても、次の契機で確定した位置から読み直すだけで、記録は失わない。ファイルごとに確定すると、元の表と派生の表がずれた状態を読み手が見て、派生を作る前に落ちた回の扱いを別に持つことになる。残存リスク: 大きさは【推定】（[§9](#sec-9) の 12・13） |
| 計測用のセッションの除く一覧を `state\` に持つ（[§2.8](#sec-2-8)） | S1 が残って `state\` だけを失うと、S1 は開けるので取込は失敗にならず、読んだ位置も無いので初めから読み直し、除く一覧を根が残る計測用のセッションだけで作り直す。計測のデータの根を消したセッションは除く集合から外れ、その transcript が残っている間（30 日）は日常の S1 に入る | 残存リスク。`state\` はバックアップの対象で（[組 D §2.1](../04.有効化とデータ保全/設計書.md#sec-2-1)）、受信サーバを止めて写しから除く一覧を戻せる（戻す前に取込が動いていたら、入った行は一覧を戻しても消えないので、戻した後に作り直しを打つ）。起きるのは、写しも無く、計測のデータの根も消しているときだけである |
| マスクの例外に 500 を返し、S2 に書かない（[§2.2](#sec-2-2)） | 例外を出した要求も、マスクを当てずに S2 に残せば、後でマスクを直して取り込める。500 では、その要求の記録が失われる | 棄却する。マスクを当てずに残すと、識別属性の平文が S2 に入り、S2 を受信で替える理由（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）が崩れる。例外の数は毎時の行（[§2.9](#sec-2-9) の `mask_error`）に出るので、マスクを直す契機は残る。残存リスク: 直すまでの間、その形の要求の記録は欠ける |
| `/v1/*` にも `Host` の確かめを当てる（[§2.2](#sec-2-2)） | cc の要求の `Host` が待ち受けのアドレスと番号と合わなければ（実装の誤り、cc の版での変化）、すべての記録が 403 で断られる。403 は送り直してよい応答でない【推定】（503 と同じく OTLP の仕様の一次資料で確かめる。[§9](#sec-9) の 2）ので、記録が欠ける。ブラウザのページから記録を作られる害より、この欠けの方が大きい | 棄却する。Phase 3 で、cc の要求が通ることと別の名前の要求が断られることを試験で確かめ、合わなければ直すまで日常の受信に使わない（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の確かめ方）。合わないと分かれば `/v1/*` には当てない（§2.2）。断った数は `hourly` の `bad_host` に出て、最後に書かれた `hourly` の行の区間にも cc が送っていれば、lmo-ctl の `start` が警告する（[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の警告の 9）。残存リスク: cc の版で送る `Host` の形が変わると、次に lmo-ctl の `start` を打って警告を見るまで、その間の記録が欠ける（usage は、OTel の記録が 1 件も無いセッションに限って、取込が transcript から補う。[組 D §1.6](../04.有効化とデータ保全/設計書.md#sec-1-6)）。警告の 9 が読むのは最後に書かれた `hourly` の行の `bad_host` だけなので、ほかのサイトのページからの `/v1/*` への要求は、その区間に来たときだけ気付ける。配り口で断った読み取りの試み（`live_bad_host` など）は警告しない（警告の限りは[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1) の理由の 9） |
