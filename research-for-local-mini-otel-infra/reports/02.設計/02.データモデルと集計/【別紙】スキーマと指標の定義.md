- 形: UTF-8 の JSON のオブジェクト 1 つで、`table`（表の名前）、`table_version`（直した日。`YYYY-MM-DD`）、`rows`（行の配列。キーは表の列の名前）を持つ。単価表だけは [§4.1](#sec-4-1) の形にする
- ファイルが無いときは、行の無い表として扱う（例: `env_config` が無ければ、見なし費用は `no_price_set` になる）。JSON として読めないときと、行に要る列が無いときは、その回の取込を失敗にする（組 A §2.8 の異常のとき。取込の記録の `err` は例外の種類）。誤った表で S1 を作らないためである
- ファイルを直したら、取込の作り直し（`--rebuild`）を打つ（設計書 [§1.1](設計書.md#sec-1-1)）。通常の取込は、変わったセッションの行だけを新しい表で作り直す
- repo とデータの根の分け方は、単価表（H-23）と同じである。端末ごとの期間を持つもの（`env_config`）と、職場の構成に当たるもの（ゲートウェイの別名）はデータの根に、どの端末でも同じ公開の規則は repo に置く

### 1.2 共通の列

OTel から作る元の表（`otel_log_event`・`api_request`・`user_prompt`・`assistant_response`・`tool_event`・`compaction`・`otel_span`・`llm_span`・`metric_point`）に共通の列である。型の揃っていない属性（`duration_ms` などがイベントで int と string に分かれる。[1-1 §4.2](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-4-2)）は、取込のときに INTEGER にそろえる。

| 列 | 型 | 中身 |
|---|---|---|
| `rec_id` | INTEGER | 行の通し番号（S1 の中だけの鍵） |
| `session_id` | TEXT | `session.id` |
| `prompt_id` | TEXT（NULL 可） | `prompt.id`（付く記録だけ） |
| `event_ts` | TEXT | `event.timestamp`（span は開始の時刻）。UTC、ISO 8601。並べ替えはこの列で行う（`event.sequence` はプロセス単位の連番。[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2)） |
| `event_seq` | INTEGER（NULL 可） | `event.sequence` |
| `cc_version` | TEXT（NULL 可） | `service.version`。`service.name` が cc でない行は NULL（受け渡し H-24） |
| `cc_version_num` | INTEGER（NULL 可） | major × 1,000,000 ＋ minor × 1,000 ＋ patch |
| `service_name` | TEXT | `service.name` |
| `host_version` | TEXT（NULL 可） | `service.name` が cc でない行の `service.version` |
| `env_label` | TEXT | `anthropic`・`llm_gateway`・`unknown`（受け渡し H-15） |
| `env_label_source` | TEXT | `resource`・`store_default` |
| `received_at` | TEXT | 受信の時刻（S2 の行の `received_at`。組 A の H-06） |
| `s2_ref` | TEXT | S2 の行（1 要求）の位置。形は [§1.7](#sec-1-7) のファイルの位置の列 |
| `rec_idx` | INTEGER | S2 の 1 行の中の記録の順番（0 から）。logs は `resourceLogs[].scopeLogs[].logRecords[]`、traces は `resourceSpans[].scopeSpans[].spans[]`、metrics は `resourceMetrics[].scopeMetrics[].metrics[]` の下のデータ点（`sum`・`gauge`・`histogram` などの `dataPoints[]`）を、JSON の並びの順に通して数える |
| `attrs_json` | TEXT | 属性全体の JSON。識別属性と本文の属性は除く（設計書 [§1.1](設計書.md#sec-1-1)） |

### 1.7 表の型と一意の鍵

**ファイルの位置の列**（`s2_ref`・`source_ref`）: `<根>:<相対パス>#<バイト位置>` の形の TEXT にする。

- 根は `data`（データの根）か `cc`（cc の設定フォルダ）である。どちらも[組 A §4](../01.全体構成/設計書.md#sec-4) の決め方で求める
- 相対パスは根からのパスで、区切りは `/` にする
- バイト位置は、その行の先頭の、ファイルの初めからのバイト数（10 進）である。1 つのファイルを 1 件として読むもの（サブエージェントの `meta.json`、raw body の本文のファイル）は `0` にする
- 例: `data:raw/logs/2026-11-02.jsonl#20480`、`cc:projects/<フォルダ>/<session_id>.jsonl#1536`
- ファイルのパスは、最後の `#` より前を取り出し、根を置き換えて得る。取込は、縮んだファイルの行を消すときと、作り直しで元のファイルの有無を見るとき（組 A §2.8）に、この形でファイルを引く
- 行の番号でなくバイト位置にするのは、続きから読む取込（組 A §2.8 の読んだ位置）が、行の先頭のバイト位置を数え直さずに知っているためである

**入れ方の共通の規則**

- 続きから読むファイル（S2、L1 のラベル、`SessionStart` の記録、品質の記録）の行は、一意の鍵が同じ行がすでにあれば入れずに飛ばす。確定の後で読んだ位置を更新する前に落ちた回の読み直しで、同じ行が二重に入らない（組 A §2.8 の書き込みの単位）。この飛ばしは、取込の記録の重複の数（H-12 の `s2` の `duplicates`）に数えない
- ファイルが縮んで初めから読み直すとき（組 A §2.8）と、初めから読み直すファイル（transcript、`meta.json`）を読むときは、先にそのファイルから入れた行（ファイルの位置の列の、`#` より前が同じ行）を消してから入れる
- 作り直し（`--rebuild`）で残す行は、ファイルの位置の列の指すファイルが無い行である（組 A §2.8）。`launch_check` はファイルの位置の列を持たず、作り直しでも行を消さない。済んだ起動の結果を、transcript や raw body の `index.jsonl` の行が消えた後も変えないためである（組 D §1.3）
- `session_identity` は、1 つのセッションの記録が複数の S2 のファイルにまたがるので、ファイルの位置を持たない。取込のたびと作り直しで、行を消さずに上書きする（識別属性の列は新しく読んだ値、`first_seen_at` は古い方、`last_seen_at` は新しい方）。S2 のファイルが無くなったセッションの行は、読む記録が無いのでそのまま残る。これが、作り直しで `session_identity` の行を残す見分け方である

**表ごとの鍵と型**: 下の「TEXT でない列」に無い列は TEXT である。一意の鍵の列、`s2_ref`・`source_ref`、`received_at` は NULL を許さない。ほかの列は、属性やキーが無いときに NULL にする。

|---|---|---|---|

### 4.5 計算

1 行の見なし費用は、次のとおりに計算する。まず `total_input_tokens` と行の `band_threshold_tokens` でプロンプトの長さの区分を決め、(`price_set`, `model_key`, `prompt_length_band`, `speed`) で単価の行を引く。同じ鍵の行が複数の版で並ぶときは、要求の `event_ts` の UTC の日付以前で `effective_from` が最も新しい行を使う。

```text
cost_calc_usd =
  ( input_tokens       × usd_per_mtok_input
  + output_tokens      × usd_per_mtok_output
  + cache_read_tokens  × usd_per_mtok_cache_read
  + cache 書き込みの費用 ) ÷ 1,000,000
  × data residency の倍率（inference_geo が us の行と、環境の設定で US だけの推論の期間とした行。それ以外と不明は掛けない）

cache 書き込みの費用 =
  内訳があるとき:  cache_creation_5m_tokens × usd_per_mtok_cache_write_5m
                  + cache_creation_1h_tokens × usd_per_mtok_cache_write_1h        cost_basis = ttl_breakdown
  内訳が無いとき:  cache_creation_tokens × 既定の TTL の cache 書き込みの単価       cost_basis = ttl_default
```

- 内訳が 2 つとも 0 で `cache_creation_tokens` が正の行は、「内訳が無いとき」として計算する（API の応答が内訳を返さないとき。設計書 [§1.9](設計書.md#sec-1-9)）
- 区分は、`total_input_tokens` が `band_threshold_tokens` 以下なら `le_threshold`、超えれば `gt_threshold` である。区分の無いモデルは `all`
- 既定の TTL は、`billing_form` と `ttl_request_class` で決まる（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性) の cache 書き込みの既定の TTL）。定額の契約の枠内の主の会話は 1 時間、それ以外は 5 分である。利用枠の中でサーバーが決める一部の補助の要求は 1 時間だが、行では見分けられないので 5 分で計算する。`ttl_request_class` が `unknown` の行も 5 分で計算し、注記する
- `transcript_only` の行は、transcript の usage の値で同じ式を当て、`cost_basis` を `transcript_ttl_breakdown`・`transcript_ttl_default` にする（[§1.3](#sec-1-3)）
- 1 回ごとの料金は行の式に入れず、`server_tool_use_json` の `call_key` の回数 × 1 回の単価を `cost_per_call_usd` に入れ、`cost_calc_usd` に足す（[§4.2](#sec-4-2)。回数のキーが transcript にあると確かめてから。設計書 §2.6 の MT-07f）
- 単価が見つからない行は `cost_calc_usd` を NULL にし、`cost_status` を `unpriced_model`・`unpriced_key`・`no_price_set` のどれかにする（[§1.3](#sec-1-3)）

## 7. 品質の記録

問い② の品質の指標（作業指示者の判定。設計書 [§2.3](設計書.md#sec-2-3)、J-33）の記録の列と鍵である（受け渡し H-35 の正本）。コマンド `lmo-judge` が 1 件 1 行の JSONL に足していき（入れ方と置き場所は受け渡し H-30。[組 A §7.1](../01.全体構成/設計書.md#sec-7-1)）、lmo-ingest が S1 の `quality_judgement` に読み込む。JSONL の 1 行は、下の表の列を持つ。S1 の行は、これに `source_ref`（[§1.7](#sec-1-7)）を足す。

- 判定し直しと直しは、前の行を書き換えずに、新しい行を後に足す。同じ作業（`session_id`・`prompt_id_first`・`prompt_id_last` が同じ。NULL どうしは同じとみなす）の行のうち、`judged_at` が最新の行を使う（同じ時刻なら、後に書いた行）。行は消さない
- 後から足せること、判定の無い作業を分母から外すこと、作業分類への結び方は設計書 §2.3 にある

| 列 | 型 | 中身 |
|---|---|---|
| `judgement_id` | TEXT | 行の id。行ごとに一意で、lmo-judge が付ける（`node:crypto` の `randomUUID`） |
| `judged_at` | TEXT | 判定の時刻（UTC、ISO 8601、ミリ秒まで） |
| `session_id` | TEXT | 判定した作業のセッション |
| `prompt_id_first`・`prompt_id_last` | TEXT（NULL 可） | 作業がセッションの一部のとき、最初と最後のプロンプト |
| `work_ref` | TEXT（NULL 可） | 作業の参照（成果物のパスやコミットなど。手元の記録だけで使う） |
| `verdict` | TEXT | `as_is`（そのまま使えた）・`fixed`（直して使えた）・`unusable`（使えなかった） |
| `rubric_version` | TEXT | 判定の尺度の版。整数の文字列で、初めの値は `1`（設計書 §2.3 の今の 3 段階の値と言葉が `1` に当たる）。lmo-judge が、自分のコードに定数で持つ今の版を書き、作業指示者は入れない。3 段階の値か言葉を変えたときに、Claude がその定数と設計書 §2.3 を一緒に直して版を 1 つ上げる（変えるのは作業指示者の決め）。3 段階の境の文（設計書 §2.3 の決めないもの）を Phase 4 で初めて書いたときと、後で変えたときも、同じく 1 つ上げる。それより前の判定と分けて数えるためである |
| `note` | TEXT（NULL 可） | 注記 |

JSONL の 1 行の例（値は仮のもの）:

```json
{"judgement_id":"<judgement_id>","judged_at":"2026-11-10T09:15:30.123Z","session_id":"<session_id>","prompt_id_first":"<prompt_id>","prompt_id_last":"<prompt_id>","work_ref":"<成果物のパスかコミット>","verdict":"fixed","rubric_version":"1","note":"<注記>"}
```

## 8. 使用量の上限の記録

**`plan_usage_snapshot`**（設計書 [§1.11](設計書.md#sec-1-11)）: Mod で `$.session.usage()` を記録したときに値が入る。日常では埋めない（受け渡し H-29）。1 行が 時点 × 上限の種類である。中身は docs による（[1-1 §10](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-10)。実機では確かめていない）。

- Mod の記録の項目と書き先、それを読む経路（計測用の取込だけが読む）は、受け渡し H-29（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1)）にある
- 記録 1 回は、`rateLimits` の要素ごとに 1 行にする。`snapshot_at` は記録の `ts`、`context_*` は `context` の値、`limit_*` は要素の `kind`・`percentUsed`・`resetsAt` から写す。`rateLimits` が空の記録は、`limit_kind` を `none`、ほかの `limit_*` を NULL にした 1 行にする。S1 の行は `source_ref`（[§1.7](#sec-1-7)）を持ち、一意の鍵は (`source_ref`, `limit_kind`) である

| 列 | 型 | 中身 |
|---|---|---|
| `snapshot_at` | TEXT | 記録の時刻（`session.measure` の時点） |
| `session_id`・`prompt_id` | TEXT（`prompt_id` は NULL 可） | 記録したセッションと、分かればプロンプト |
| `cc_version` | TEXT | 版 |
| `context_tokens`・`context_window`・`context_percent` | INTEGER・INTEGER・REAL | 文脈の使用量 |
| `limit_kind` | TEXT | 上限の種類（`rateLimits` の `kind`） |
| `limit_percent_used` | REAL | 上限の使用率 |
| `limit_resets_at` | TEXT | 上限が戻る時刻 |

上限はアカウント全体のものなので、同時に動くセッションがある区間の増えは、セッションに振り分けない（[§3](#sec-3) の指標 14）。

## 9. system prompt の版の表

**`system_prompt_default`**（設計書 [§2.5](設計書.md#sec-2-5)）: `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` が未設定の期間に、モデルから既定の system prompt の版を引くデータの表である。ファイルは [§1.1](#sec-1-1) のデータの表のファイルにある。

| 列 | 中身 |
|---|---|
| `model_key` | 単価表と同じ正規化したモデルの名前（[§4.4](#sec-4-4)） |
| `default_variant` | `full`（完全版）・`short`（短縮版） |
| `basis` | 根拠。`docs`（docs の文が直に当たるモデル。名前を挙げたモデルと、同じ系統のより新しいモデル）・`estimated`（名前を挙げたモデルの系統に無いモデルに、docs の「より新しいモデル」を当てた【推定】） |
| `note` | 注記 |

初めの行は次のとおりである（docs の env-vars の `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` の行。docs f43c40d L64062。[1-8 §7.2](../../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) の D16、[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)）。実装のときに、単価表の `model_key` の名前で行を作る。

| モデル | `default_variant` | `basis` |
|---|---|---|
| Haiku 4.5・Sonnet 5・Opus 4.7 と、それより前の同じ系統のモデル | `full` | `docs` |
| Haiku 5.5・Sonnet 5.5・Opus 5.5 | `short` | `docs` |
| Fable 5.1 など、上の 3 つの系統に無い新しいモデル | `short` | `estimated` |

- 表に無いモデルの行は、`system_prompt_variant` を `unknown` にする
- 未設定のときも、実験かサーバの設定で短縮版が選ばれうる（同じ docs の `0` の説明）。`full` の行は、その場合に外れる【推定】。確かめ方は設計書 [§7](設計書.md#sec-7) の 19
