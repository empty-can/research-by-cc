## 1. データモデル

<a id="sec-1-1"></a>
### 1.1 粒度と表の構成（DM-00）

**決めたこと**

- S1 に 2 種類の表を置く
  - 元の表: 受けた記録を種類ごとに正規化した表（`otel_log_event`・`api_request`・`llm_span`・`transcript_usage` など）
  - 集計の正本の表 `usage_record`: 1 行が API リクエスト 1 件。[§3](#sec-3) の規則で、元の表から作る
- `usage_record` から、プロンプト（`prompt_id`）、セッション（`session_id`）、作業分類（`label_l1`・`label_l2`）、サブエージェントの個体（`subagent_key`）へ集約する
- 識別属性（`user.email`・`user.account_uuid`・`user.account_id`・`organization.id`・`user.id`）と本文の属性（`prompt`・`prompt_text`、応答の本文）は、属性全体を入れる `attrs_json` から抜き、それぞれ 1 つの表（`session_identity`・`user_prompt`・`assistant_response`）にだけ置く
- サブエージェントの個体の鍵 `subagent_key` は、(`session_id`, `agent_id`) にする。`agent_id` は次の順に取る
  - 2.1.310 以降は `api_request` の `agent_id`
  - 2.1.309 以前は、結合できた span の `agent_id`
  - それも無ければ、transcript の `agentId`（サブエージェントのファイルの id。`request_id` で結ぶ）
- サブエージェントの呼び出し（親の Agent tool の呼び出し）への結び付けは、補完取込でサブエージェントの `meta.json` の `toolUseId` を読み、`agent_tool_use_id` の列に持つ。OTel の Agent の `tool_result` の `tool_use_id` と同じ値で結べる。取込が `meta.json` から読むのは `toolUseId` だけである（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）
- L1 の hook のレコード（組 C の H-18）は、元の表 `l1_hook_record` に 1 件 1 行で入れる。項目は、H-18 の項目からレコードの形の版 `v` を除いたもの（規則の結果 `category`、`rule_id`、`cmd`、`hook_ms`、`impl`、`permission_mode`、版など。`v` は取込が読み分けに使う）で、ラベルのファイルの位置を `source_ref` に持つ。`prompt_label` の L1 の列は、この表から組 C の順（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1) の H-20）で作る
- 表と列の全体は定義の別紙 [§1](【別紙】スキーマと指標の定義.md#sec-1) にある
- S1 の表は、どれも lmo-ingest（受け渡し H-09。[組 A §7.1](../01.全体構成/設計書.md#sec-7-1)）が作る。`usage_record` と派生の列（見なし費用、`prompt_label` のラベル、L2 の事後分類）の計算と、品質の記録の読み込みも lmo-ingest が行い、lmo-report と UI は読むだけである。S1 のファイルは、データの根の `db\` に置かれる（[組 A §4](../01.全体構成/設計書.md#sec-4)）
- 単価表と写し方の表（データの表）を直したときは、取込を流し直して、派生の列と `usage_record` を作り直す

**理由**

- 計画書は粒度を API リクエスト単位と決めている。トークン 4 種・`model`・`effort`・費用がそろう最小の単位である
- 元の表と正本の表を分けると、結合の規則を直したときに、受信をやり直さずに正本だけを作り直せる
- hook のレコードを元の表に置くのも同じ理由で、TG-09 の判定規則が決まったときに、過去の分の最終のラベルを S1 の中で付け直せる。組 C の見直しのきっかけ（規則の結果が `none` の割合）と J-12 の判定（`hook_ms` を実装手段と permission mode の組で数える）も、S1 で `prompt_id` によって OTel の記録と結んで出せる
- 正本と派生の列を lmo-ingest が作るのは、S1 の書き手を 1 つにする組 A の構成（[組 A §2.3](../01.全体構成/設計書.md#sec-2-3)）に合わせ、lmo-report と UI が同じ値を読むためである
- 識別属性と本文を 1 か所にまとめるのは、S1 の中でそれらの値を持つ所を 1 つに絞り、消すときと、マスクの規則（受け渡し H-04）を変えたときに直す所を 1 つにするためである。規則は受信（S2 に書く前）で当たるので、S1 には替えた後の値が入る（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）
- `agent_id` は、2.1.310 から logs のサブエージェントのイベントにも付く（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66）。この取り元の順は計画書 v2.5 の案（P2）に依る
- `agent_id` の一意性は、Phase 1 の残作業で確かめた（[1-6 §5.3](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-5-3)。2026-10-26、cc 2.1.310 の `-p` の 1 run）。同じセッションで、組み込みのサブエージェントの 1 つの型を 4 回（並列 2・順 2）呼び、4 回の呼び出しは 4 個の別の値になり、transcript の `agentId`・OTel の `agent_id`・span の `agent_id` の 3 つは、呼び出しごとに同じ値だった。`meta.json` の `toolUseId` は、Agent の `tool_result` の `tool_use_id` と 4 件中 4 件、1 対 1 で一致した
- 一意を確かめたのは 1 セッションの中だけなので、`agent_id` 単体でなく `session_id` と組にする

**確かめていないこと**: 別のセッションの間の重複、入れ子（`parent_agent_id`）、fork subagent、span の `agent_id` の `acompact-` の形の値、バックグラウンドで動くサブエージェント。2.1.309 以前の transcript で `agentId` とファイルの id が同じ値であることは【推定】である。Phase 3 の比較実験の記録で、`session_id` ごとに `agent_id` の重複が無いことを数える（[§7](#sec-7) の 1）。

### 1.2 `query_source` の体系（DM-01）

**決めたこと**

- 生の値を、それぞれ元の名前の列に残す。イベントの `query_source`、span の `query_source_safe`、metrics の `query_source`（3 分類）である
- 派生の列を 2 つ持つ
  - `query_source_class`（`main`・`subagent`・`auxiliary`・`unknown`）: metrics の 3 分類にそろえる
  - `ttl_request_class`（`main_conversation`・`other`・`unknown`）: cache 書き込みの既定の TTL を選ぶ要求の区分
- 生の値から派生の列への写し方は、コードに埋めず、データの表 `query_source_map` で持つ（定義の別紙 [§2](【別紙】スキーマと指標の定義.md#sec-2)）。表に無い値は `unknown` にして件数を数え、表に行を足す

**理由**

- 値の体系が metrics とイベントで違う（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性)）。metrics の値と比べて検算するには、イベント側を同じ 3 分類に寄せる列が要る
- span の `query_source` は詳細ベータトレースのときだけ出る（v2.1 の R-14）ので、span は `query_source_safe` で見る
- `ttl_request_class` を 3 分類と別に持つのは、TTL の区分が 3 分類と一致しないためである。主の会話の区分には、一緒に走る補助の要求も入る（仕様別紙 §1 の cache 書き込みの既定の TTL）。TTL 別の内訳がある行（2.1.300 以降の `api_request`）は内訳を使うので、この列が効くのは内訳の無い行だけである

**未確認**: 生の値ごとの 3 分類と TTL の区分は、本活動の文書で一覧を確かめておらず、【推定】で置いた。Phase 3 で、同じ期間の metrics の `query_source` 別のトークン数と、イベントを 3 分類に寄せた合計を比べて確かめる。

### 1.3 v2.1 の R-6・R-9・R-14（DM-02）

**決めたこと**: 既定の案のまま、次のとおりにする。

- R-6: トークン 4 種と TTL 別の 2 つは別の列で持つ。合算した列は総入力（[§1.5](#sec-1-5)）だけにし、費用は種類ごとの単価を掛けて足す
- R-9: セッション数を分母にする集計では、metrics の `session.count` の `start_type` が `agents_view` の行を除く。`resume`・`continue` は数え、`start_type` の列で分けられるようにする
- R-14: 詳細ベータトレースは使わない。span の要求の出どころは `query_source_safe` で見る

**理由**: [v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) の R-6・R-9・R-14 のとおりである。R-9 で `resume`・`continue` を数えて列を残すのは、v2.1 が「分析の目的に応じて決める」とした所で、問い① で resume をまたぐ比較をするときに分けられるようにするためである。

<a id="sec-1-4"></a>
### 1.4 列名と対応表（DM-03）

**決めたこと**

- 物理列は cc の元の名前にする。属性名のドットはアンダースコアにする（例: `prompt.id` は `prompt_id`）
- GenAI semconv の名前は論理対応表 `semconv_map`（定義の別紙 [§6](【別紙】スキーマと指標の定義.md#sec-6)）で持ち、外へ出すときのビューと出力の名前に使う
- 意味の違う属性は semconv の列に寄せない。`input_tokens`（キャッシュ分を含まない）と `agent_id`（semconv の `gen_ai.agent.id` と意味が違う）は cc 固有の列のままにする

**理由**: J-1 の裁定（GenAI semconv を参照語彙・対応表に使う。[計画書の承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24) の J-1 の行）と [1-7 §9](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9) のとおりである。ドットをアンダースコアにするのは、SQLite の列名に引用符を要らなくするためで、名前の対応は機械的に戻せる。

<a id="sec-1-5"></a>
### 1.5 総入力の派生列（DM-04）

**決めたこと**: `usage_record` に派生列 `total_input_tokens`（= `input_tokens` ＋ `cache_read_tokens` ＋ `cache_creation_tokens`）を持つ。cc の生の値の列とは混ぜない。画面と出力の名前には「キャッシュ込み」「キャッシュ除く」を付ける。

**理由**: cc の `input_tokens` はキャッシュの読み書き分を含まず、semconv の `gen_ai.usage.input_tokens` は含む（[1-7 §7.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-7-1)）。計算した値と生の値を同じ列に置くと、二重の加算か過小な数えになる（[1-7 §9](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9)）。

<a id="sec-1-6"></a>
### 1.6 effort と model（DM-05）

**決めたこと**

- サブエージェントを含め、`effort`・`model` は `api_request` の値を正とする（結合できなかった span は span の値）。agent の frontmatter から推定しない（既定の案）
- `effort` の無い行は、既定の effort で埋めずに NULL のまま持ち、集計では「effort なし」として別に数える
  - 無い理由は 2 つある。model が effort を受けない場合（Haiku 4.5 など）と、ゲートウェイの effort の再試行の後の場合【推定】である
  - 前者は `model` の列で見分けられる
- `model` は、生の値の列と、単価表に結ぶために正規化した `model_key`（[§2.6](#sec-2-6)）を並べて持つ。比較と再現には完全なモデル ID を使う

**理由**

- 呼び出しごとの `effort` と、Mod による model の上書きがある（[計画書「データモデル」](../../00.活動計画/活動計画書.md#sec-p2-model)）
- docs は `api_request` の `effort` を「effort を送らないときは付かない」と書き、ゲートウェイが effort を拒否すると、cc が終わるまで、そのモデルへの要求に effort を付けない（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D67）。既定の effort で埋めると、作業分類 × モデル × effort の集計で別の水準に数えてしまう。この扱いは計画書 v2.5 の案（P3）に依る
- エイリアスの解決先は版で変わる（[まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「データモデル」のモデルの解決先）

<a id="sec-1-7"></a>
### 1.7 `session.id` と `gen_ai.conversation.id`（DM-06）

**決めたこと**: cc の値に寄せる。`session_id` は `session.id` のまま持ち、`gen_ai.conversation.id` の名前に写さない。span の `gen_ai.conversation.id` は、span の表に元の値のまま持つ。論理対応表では「メインの span だけ同じ値」と注記する。

**理由**: サブエージェントの span の `gen_ai.conversation.id` はそのサブエージェントの `agent_id` と同じ値で、`session.id` を写すと cc 自身の値と食い違う（[1-7 §9](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9)、[付録 A.3](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-a-3)）。

**別の案**: `session.id` を対応表で `gen_ai.conversation.id` に写す。

- 長所: logs のイベントも semconv の名前で外へ出せる
- 短所: サブエージェントの span で cc の値と食い違い、外のツールで span と logs を同じ会話の名前で並べると、別の会話に見える

**未確認**: `--resume` と compact の前後で `session.id` が変わるか（[1-7 §10](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-10)）。Phase 3 で確かめる。

<a id="sec-1-8"></a>
### 1.8 版で増える属性とイベント（DM-07）

**決めたこと**

- 受信・保存は、知らない `event.name` も落とさずに保存する（既定の案）
  - S1 では、logs のイベントをすべて `otel_log_event`（共通の列と、属性全体の `attrs_json`）に入れ、既知のイベントは種類ごとの表にも写す
  - span は `otel_span`、metrics は `metric_point` に、同じく `attrs_json` を付けて入れる
  - 既知かどうかは、データの表 `known_event` で見る
- 既知のイベントに版で加わった属性は、`attrs_json` に残し、集計に要るときに固定の列に上げる（上げる手順は [§4.2](#sec-4-2)）
- `vcs.*` の属性（本環境の設定で metrics とイベントに付く。[組 D §1.2](../04.有効化とデータ保全/設計書.md#sec-1-2)）は、列にせず `attrs_json` に残す。計画書の指標にリポジトリ別が無く、値にリポジトリの URL と持ち主の名前が入る（[v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §5.3）ためである。報告書では、リポジトリを番号に置き換えて示す（組 D §1.2）
- 2.1.310 で加わった次の 3 つは、今から固定の列にする。2.1.309 以前の行では NULL である。この 3 つは計画書 v2.5 の案（P2）に依る
  - サブエージェントのイベントの `agent_id`・`parent_agent_id`
  - `tool_result`・`tool_decision` の `request_id`

**理由**

- イベントと属性は版で増える。例は、2.1.307 の `safety_event`（[1-9 §2](../../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D56）と、2.1.310 の 3 つの属性（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66）である。`attrs_json` があれば、取込を直さずに後から集計に足せる
- 3 つを今から固定の列にするのは、問い② の個体別の集計と、問い③ のリクエスト単位の集計に使うためである（[§2.1](#sec-2-1)）

**別の案**（計画書の[承認と保留](../../00.活動計画/活動計画書.md#sec-approval)の「新しく決めること」にある）: 既知のイベントだけを保存する。

- 長所: スキーマが固定で済む
- 短所: 取込を直すまで、版で増えたイベントが残らない

<a id="sec-1-9"></a>
### 1.9 TTL 別の cache 書き込み（DM-08。MT-07a と同じ決めごと）

**決めたこと**: 使う。

- 内訳のある行（2.1.300 以降の `api_request`）は、`cache_creation_5m_tokens` と `cache_creation_1h_tokens` に、それぞれの TTL の単価を掛ける
- 内訳の無い行（2.1.300 より前の `api_request` と、結合できなかった span）は、`ttl_request_class` と課金の形（[§2.6](#sec-2-6) の環境の設定）で決まる既定の TTL の単価で計算する。そう計算したことを `cost_basis` の列に `ttl_default` と残す
- OTel の記録の無いセッションの行（`transcript_only`。[§3.1](#sec-3-1)）は、transcript の usage の内訳で同じく計算し、内訳が無ければ既定の TTL で計算する。`cost_basis` は `transcript_ttl_breakdown`・`transcript_ttl_default` にする（定義の別紙 [§1.3](【別紙】スキーマと指標の定義.md#sec-1-3)）

**理由**: 単価は TTL で違い、2.1.302 の実機では内訳の和が `cache_creation_tokens` と一致した（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性)）。職場の費用を見積もるときに、内訳を合計して職場の TTL の単価で掛け直すのにも要る（[§2.6](#sec-2-6) の MT-07g）。

**別の案**: 内訳を使わず、全行を既定の TTL で計算する。

- 長所: 計算が 1 通りで済む
- 短所: 実際の TTL が既定と違う行（`promptCacheTtl` などの設定や、利用枠を超えて usage credits を使った分）で、費用がずれる

<a id="sec-1-10"></a>
### 1.10 アイドル時の compaction（DM-09）

**決めたこと**: 分ける。`compaction` イベントに派生の列 `compact_kind` を付ける。

- `trigger` が `manual` の行は `manual`
- `trigger` が `auto` の行のうち、同じセッションの直前の `main` の要求から 50 分以上空いた行は `auto_idle`【推定】
- それ以外の `auto` の行は `auto`、判定に使う要求が無い行は `unknown`

**理由**

- 問い① は、利用者が `/compact` と `/clear` をどう使い分けるかを問う。アイドル時の compaction は利用者の選択ではなく、混ぜると compact の費用が利用者の選択以上に大きく出る
- `trigger` ではどちらも `auto` で見分けられず（仕様別紙 §1 の対話のアイドル時の compaction）、ほかに見分ける属性も本活動の文書に無い。docs の条件（端末では最後の要求から約 54 分の時点、VS Code の拡張と desktop app では次のメッセージが 1 時間以上後のとき）から、空いた時間で見分ける。50 分は、この 2 つの時間より短く置いた
- VS Code と desktop app でも動くことは 2.1.310 の docs で分かった（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D70）。この材料は計画書 v2.5 の案（P2）に依る

**未確認**: 実機では観測していない。Phase 3 で観測できなければ「未観測」と記録し（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3) の完了条件）、規則は観測したときに確かめる。

**別の案**: 分けない。

- 長所: 推定の規則が要らない
- 短所: 上の混ざりが残る

<a id="sec-1-11"></a>
### 1.11 Mod の記録（DM-10）

**決めたこと**

- `turn.step` は使わない
- `turn.complete` は使わない
- `$.session.usage()`（`session.measure` の時点で取る、文脈の使用率とプランの上限の割合）は、データモデルに表 `plan_usage_snapshot` を持つ（定義の別紙 [§8](【別紙】スキーマと指標の定義.md#sec-8)）。値が入るのは Mod で記録するときだけである
  - 日常では埋めない。Phase 3 で Mod で記録して中身を確かめ、日常で埋めるかは Phase 4 に進むかの判断のときに決まる（受け渡し H-29。[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1)）

**理由**

- `turn.step` を使う理由だった、サブエージェントの個体をリクエスト単位で分けることは、2.1.310 以降は OTel の `agent_id` で足りる（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66。計画書 v2.5 の案（P2）に依る）。また、`turn.step` と OTel を結ぶ鍵はプロンプト単位の `prompt_id` だけで、リクエスト単位の照合は docs で保証されない（[1-1 §10](../../01.基礎調査/01.実データ確認/調査報告書.md#sec-10)）
- `turn.complete` の turn ごとの合計は、`usage_record` を `prompt_id`（サブエージェントは `subagent_key`）で集約すれば出る
- 計画書は、本環境では費用より精度・時間・使用量の上限の消費を主に比べるとする（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics) の見なし費用の「比べ方」）。使用量の上限の割合は OTel に無く、`$.session.usage()` だけが持つ

**限り**

- 上限はアカウント全体のものなので、同時に動くセッションがあると、割合の増えをセッションに振り分けられない【推定】
- 日常で埋めない間は、使用量の上限の消費を見なし費用で代える。代わりの量であり、上限の割合と同じではない

**別の案**: Mod の記録を使わず、表も持たない。

- 長所: Mod に依らない
- 短所: 使用量の上限の消費を直接測る経路が無くなる

<a id="sec-2"></a>
## 2. 分析指標

<a id="sec-2-1"></a>
### 2.1 指標の一覧（MT-00）

**決めたこと**: 指標は定義の別紙 [§3](【別紙】スキーマと指標の定義.md#sec-3) の表のとおりとする。どの指標も、件数（標本の数）を添え、効く版の区切り（[§4.3](#sec-4-3)）をまたがないように出す。主なものは次のとおりである。

- 作業分類 × モデル × effort ごとの、プロンプトあたりのトークン（4 種と総入力）・見なし費用・所要時間
- 思考トークン比率（思考トークンの値が確定した行だけ）とキャッシュヒット率
- 問い① 用: compact の前後の総入力と費用、compact の要求自身の費用（`compact_kind` 別）、`/clear` の前後（[§2.4](#sec-2-4)）
- 問い② 用: サブエージェント比率（トークン・費用）を、型（`agent_name`）ごとと個体（`subagent_key`。2.1.310 以降）ごとに出す。品質の指標は [§2.3](#sec-2-3)（作業指示者の判定）
- 問い③ 用: ツール結果のサイズを tool ごとに出す。2.1.310 以降は `request_id` で API リクエストに結び、それより前はプロンプトの単位で結ぶ
- 使用量の上限の消費（`plan_usage_snapshot` に値があるとき。[§1.11](#sec-1-11)）

**理由**: 計画書の指標の例と、問い①〜③ の材料をそろえた。問い② の個体別と問い③ のリクエスト単位は、2.1.310 で加わった属性に依る（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1)）。この 2 つは計画書 v2.5 の案（P3）に依る。

**呼び出しとの結び付き**: 個体（`subagent_key`）は呼び出し 1 回と 1 対 1 で（[§1.1](#sec-1-1)）、問い② の個体別の指標は、親の Agent tool の呼び出し（`agent_tool_use_id`）ごとにも出せる。

<a id="sec-2-2"></a>
### 2.2 input 系の定義（MT-01〜MT-03）

**決めたこと**: キャッシュヒット率（MT-01）と総入力（MT-02）は、計画書の式のまま使う。期間やセッションで集約するときは、合計の比（cache_read の合計を総入力の合計で割る）にする（MT-03 の案のまま）。

**理由**: 合計の比は、トークン量で重み付けた値になる。リクエストごとの比の平均は、分類器や補助の要求のような小さな要求の比に引かれる。[1-7 §10](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-10) の「キャッシュヒット率の集約」は、これで閉じる。

**別の案**: リクエストごとの比を平均する。

- 長所: 1 件の要求の典型の値を示す
- 短所: 上の偏りが出る

<a id="sec-2-3"></a>
### 2.3 問い② の品質の指標（MT-04。作業指示者が決めた）

**決めたこと**: 問い②（オーケストレーションと、Opus から Sonnet への移譲で、品質を保ったままどこまでコストを下げられるか）の「品質を保った」は、A（作業指示者の判定）だけで測る。

- 作業（セッションか、プロンプトの範囲）の終わりに、作業指示者が 3 段階（そのまま使えた / 直して使えた / 使えなかった）で判定する。全部ではなく、比べたい作業（移譲した作業と、しなかった同じ種類の作業）を抜き取る
- 判定は、作業分類ごとに集計して出す
- 判定はテレメトリの外の記録で、表 `quality_judgement` に持つ（下の「記録の形」）
- 手戻りの代理指標（B）は採らないので、分類体系に「修正依頼」の区分も、区分と別の印も作らない

決めないもの: 「保った」とする基準の値（Phase 6 の着手時に、集まった件数を見て決める）と、判定する作業の選び方と記録の打ち方の細部（Phase 4 の実装で決める）。

**理由**

- 作業指示者の裁定による（[判断事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-33。案 A）
- 品質はテレメトリでは測れない（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）ので、テレメトリの外の記録が要る。A の判定は作業の後から作れないので、記録の形を、データを集め始める前（日常の運用の Phase 4 の前）にデータモデルに入れておく（[進め方 §8](../00.設計の進め方/計画書.md#sec-8) の P2-3 の行）
- 作業分類ごとに出すのは、作業品質への影響が作業の種類で違いうる（v2.1 の仮説 H-2）ためである

**選択肢と Claude の推奨**（判断の材料として示したもの。裁定の記録として残す。採ったのは A だけである）

| 案 | 中身 | 長所 | 短所 | テレメトリの外の記録 |
|---|---|---|---|---|
| A: 作業指示者の判定 | 作業（セッションか、プロンプトの範囲）の終わりに、作業指示者が 3 段階（そのまま使えた / 直して使えた / 使えなかった）で記録する。全部ではなく、比べたい作業（移譲した作業と、しなかった同じ種類の作業）を抜き取る | 作業指示者が品質と考えるものを直接測る。作業の種類に依らず使える | 抜き取った作業ごとに、3 段階から 1 つを選んで記録する手間が要る。主観で、記録した作業だけが標本になる | 要る（`quality_judgement`） |
| B: 手戻りの代理指標 | 同じ作業の中の修正依頼のプロンプトの数、tool の呼び出しの拒否・差し戻し（`tool_decision`・`safety_event`）、同じ作業のやり直しを、テレメトリとラベルから数える | 全件で自動に取れ、過去のデータにも当てられる。記録の手間が要らない | 品質そのものでなく、代わりの量である。手戻りが少ないのは作業が易しいためかもしれない。修正依頼を見分ける精度は、L1 のルール分類か L2 の事後分類の精度に依る | 要らない（分類体系に「修正依頼」の区分が要る。組 C） |
| C: 既にある検査の結果 | レビュー（セルフチェックの巡回ごとの指摘の数、クロスレビューの CRITICAL・IMPORTANT の数）と、テスト・lint の合否を、作業に結ぶ | 記録の手間が増えにくく、比べやすい数がある | レビューかテストを通る作業に限られる。指摘の数は文書の大きさとレビュアーのモデルに左右される。レビューの結果をセッションに結ぶ手間が要る | 要る（`quality_judgement` に検査の結果として入れる） |
| D: 対照実験 | 同じ課題を条件（移譲する / しない）を変えて実行し、作業指示者がどちらの条件かを知らずに比べる | 移譲で品質が保たれたかを、条件の差として最も直接に示す | 費用と時間が掛かり、課題の数が限られる。日常のデータには当てられない | 要る（実験の条件と結果の記録） |

**Claude の推奨**（採らなかった案）: A（抜き取り）と B の組み合わせ。

- 問い② の答えは、作業指示者が移譲を決めるための目安である。作業指示者の判断に効く品質の定義は、作業指示者自身の判定（A）である
- A だけでは標本が少ないので、全件で取れる B を傾向の見張りに使い、A と B の向きが合うかも見る
- C は、レビューの結果をセッションに結ぶ手間が大きい。D は、Phase 6 の着手時に、問い① の対照実験とあわせて実施するかを決める（[計画書 Phase 6](../../00.活動計画/活動計画書.md#sec-p6) の補足）
- 作業品質への影響は作業の種類で違いうる（v2.1 の仮説 H-2）ので、どの案でも作業分類ごとに出す

**記録の形**: 表 `quality_judgement` に 1 件 1 行で持つ。鍵は `session_id` と、プロンプトの範囲（`prompt_id_first`・`prompt_id_last`）である。判定の値と、判定の尺度の版を持つ。記録はコマンド `lmo-judge` が JSONL に足し、lmo-ingest が S1 に読み込む（入れ方の正本は受け渡し H-30。[組 A §7.1](../01.全体構成/設計書.md#sec-7-1)）。列は定義の別紙 [§7](【別紙】スキーマと指標の定義.md#sec-7) にある。

### 2.4 `/clear` の前後のセッションの結び付け（MT-05）

**決めたこと**

- `SessionStart` hook が `source` に `clear` を受けたとき、新しい `session_id`・作業フォルダ・時刻を記録する
- 同じ作業フォルダで直前に終わったセッションと、時刻の隣接で結ぶ（見込み。Phase 3 で確かめる）
- 結果は表 `session_link` に、`link_kind` を `clear`、`method` を `hook_time` として持つ。hook の記録が無い期間は時刻の隣接だけで結び、`method` を `time_only` にする
- hook の書き方と置き場所、記録のファイルの置き場所は、受け渡し H-28（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1)）による。lmo-ingest が記録を読み、表 `session_start_record`（定義の別紙 [§1.1](【別紙】スキーマと指標の定義.md#sec-1-1)）に入れる

**理由**: `/clear` 専用のイベントは無く、`/clear` で `session.id` が新しくなる（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性)）。前のセッションの id を hook の入力で受け取れるかは、本活動の文書で確かめていない。どちらの場合も結べるよう、時刻と作業フォルダで結ぶ形にした。

<a id="sec-2-5"></a>
### 2.5 system prompt の交絡（MT-06）

**決めたこと**

- 比較実験では `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` を固定し、その値を実験の条件として記録する
- 日常のデータには、派生の列 `system_prompt_variant`（完全版 / 短縮版）を付ける。変数が未設定のときに model で決まる版を、データの表で引く。モデル間の比較では、交絡として注記する
- 変数を設定した期間は、環境の設定 `env_config`（[§2.6](#sec-2-6)）に期間で残し、その期間は設定に従って版を付ける

**理由**: 変数が未設定のとき、モデルの世代で既定の system prompt が違う（[仕様別紙 §4](../../00.活動計画/【別紙】公式仕様の調査結果.md)、[1-8 §7.3.3](../../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）。テレメトリには変数の値が出ないので、日常のデータでは設定の記録から付ける。

<a id="sec-2-6"></a>
### 2.6 見なし費用（MT-07〜MT-07h）

**MT-07 見なし費用で集計する**: 既定の案のまま。`usage_record` に、見なし費用 `cost_calc_usd` と cc の値 `cost_usd`（`api_request` のある行だけ）を並べて持ち、集計の費用には `cost_calc_usd` を使う。

**MT-07b 理由**: `cost_usd` は、cc が Anthropic の料金で換算した推定値である。本環境（定額の契約）では実費ではなく、Bedrock 環境の請求とも単価の組が違う（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)）。この行は決める事項ではなく MT-07 の根拠で、根拠として採る。

**MT-07a 計算**: `api_request` のトークン 4 種（cache 書き込みは TTL 別。[§1.9](#sec-1-9)）に単価を掛けて足す。単価の行は、単価の組・`model_key`・プロンプトの長さの区分・`speed` で引き、行にある 5 種のトークンの単価を掛ける。式は定義の別紙 [§4](【別紙】スキーマと指標の定義.md#sec-4) にある。

**MT-07c 単価表の形**

- コードに埋めず、データ（JSON）で持つ
- 行のキーは、単価の組 × モデル × プロンプトの長さの区分 × `speed` である。プロンプトの長さの区分は、段階単価のあるモデル（今は Haiku 5.5 だけ）では 2 区分、ほかのモデルでは 1 区分である
- 行の値は、5 種のトークン（入力・出力・cache 書き込み 5 分・cache 書き込み 1 時間・cache 読み）の単価である。cache の単価は入力の単価からの倍率で導かず、値で持つ（cache 読みの倍率はモデルで違い、出典の間でも値が違った。[§2.7](#sec-2-7)）
- 行ごとに、出典の URL、取得日、効き始めの日を持つ。改定は行を足して残し、古い行は消さない（過去の期間を当時の単価で計算し直せる）
- 列は定義の別紙 [§4](【別紙】スキーマと指標の定義.md#sec-4) にある。値は本書に持たない。Anthropic の組の値の正本は [V-11(b) の別紙](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-11(b)確認結果.md) の #24 の行で、実装のときに表のファイルに写す

**MT-07d 設計で決める 4 点**

1. 単価の組をレコードに当てる鍵: 環境ラベル `env_label`（受け渡し H-15）から、環境の設定 `env_config` で単価の組と課金の形（定額の契約の枠内 / API キー・クラウド提供元）を引く。要求の区分は `ttl_request_class`（[§1.2](#sec-1-2)）を使う。利用枠を超えて usage credits を使った分は行ごとに区別できないので、注記する
2. `model` と表のモデルの結び付け: データの表 `model_alias` で、`model` の生の値を `model_key` に写す。完全一致、日付の後置きを外した一致、ゲートウェイの別名の行の順に引く
3. 表に無いモデル: `cost_calc_usd` を NULL、`cost_status` を `unpriced_model` にする。件数を数え、費用に含めずに注記する（既定の案のまま）。モデルはあるが `speed` かプロンプトの長さの区分の行が無いとき（`fast` の行を足す前の fast mode の要求など）は、`unpriced_key` にして同じく数える
4. 表の保存形式と置き場所: JSON のファイルで、公開の料金の組は repo、職場の組はデータの根（`%LOCALAPPDATA%\local-mini-otel\`）の下に置く（受け渡し H-23。[§6.1](#sec-6-1)）

**MT-07e 単価の値**: Anthropic の単価は、単価の出典確認（[§2.7](#sec-2-7)）で確かめた。値の正本は [V-11(b) の別紙](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-11(b)確認結果.md) の #24 の行で、Phase 3 の検算までに表のファイルに写す。fast mode の行は、`fast` の要求が記録に出た時点で、同じ出典から足す。職場の実単価は、確かめ方を Phase 7 の着手前に作業指示者と決める（計画書の[承認と保留](../../00.活動計画/活動計画書.md#sec-approval-v24)の先送りの行）。それまで職場の組は空で、職場の費用の見積もりは出さない。職場の組織が managed settings の `modelPricing` を配っていれば、職場の `cost_usd` はその単価での換算になり、実単価の手がかりになる【推定】（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)。配っているかは Phase 7 で確かめる）。

**MT-07f 費用に効くほかの要素**: 表に持つ形を決めた（定義の別紙 [§4](【別紙】スキーマと指標の定義.md#sec-4) の調整の行）。

- 長いコンテキストの段階単価: プロンプトの長さの区分で持つ。区分は、その要求の入力系のトークンの合計（`total_input_tokens`）が境目以下か、超えるかで決める。境目の値は V-11(b) の別紙の #24 の行にある。今は Haiku 5.5 だけに区分がある
- fast mode: キーの `speed` で持ち、`api_request` の `speed` で行ごとに当てる
- data residency の料金の倍率: 調整の行で持つ。要求に `inference_geo` が付けば、その値が `us` の行に倍率を掛ける。`inference_geo` が OTel の `api_request` に載るかは未確認で、載らない間は倍率を掛けずに計算して注記する。作業指示者が US だけの推論を使う期間を環境の設定に書いた場合は、その期間の行に掛ける
- web search などの 1 回ごとの料金: トークンの単価表に入れず、回数 × 1 回の単価の調整の行で持つ。回数は transcript の usage の `server_tool_use` から数える案で、そのキーが transcript にあるかは【推定】である。確かめるまでは集計の漏れとして注記する
- batch の割引: 持たない。cc の通常の使い方で batch の要求が出る記述は読んだ範囲に無く、本環境の記録にも出ない【推定】

**MT-07g 比べ方**

- モデル間の比較は、比率でも示す。基準は、比べる組に Haiku 系があれば最新の Haiku、無ければ組の中で最も安いモデルとする
- 職場の費用の見積もりは、職場の実単価が分かってから出す。そのときは、cache 書き込みを TTL 別の内訳の合計 × 職場の TTL の単価で計算し直す。見積もりの表には、前提（ゲートウェイの先でプロンプトキャッシュが効くこと、職場の TTL は 5 分の見込み【推定】）を出す（[計画書「分析指標」](../../00.活動計画/活動計画書.md#sec-p2-metrics)の比べ方）

**MT-07h 検算**

- Phase 3 で、Anthropic の単価の組で計算した見なし費用を、リクエストごとに `cost_usd_micros` と比べる
- 合格は、100 万分の 1 ドルの単位で差が ±1 以内とする。これは計画書の「丸めの差を除く」の初期の値である。単価の出典確認では、この幅で Sonnet 5.5 と Haiku 5.5 の `api_request` 25 件が全件一致した（[§2.7](#sec-2-7)）。ほかのモデルと Haiku 5.5 の上の区分は、Phase 3 で確かめる
- ずれた行は、次の順に調べる。`speed`（fast mode）、`inference_geo`（data residency）、`modelPricing`（`-p` の結果の `costBasis` が `list` 以外か）、`model` の別名（`model_alias` の引き当て）、Haiku 5.5 の区分である。fast mode・data residency・1 回ごとの料金は `cost_usd` に含まれるか分からない（【未確認】）ので、その要素でずれた行は、要素を記録して比べる対象から外し、見なし費用の漏れとして注記する（[計画書 Phase 3](../../00.活動計画/活動計画書.md#sec-p3) の見なし費用の検算）
- 検算できるのは `cost_usd` を持つ `api_request` だけである。span にだけ出る要求（自前の分類器の Sonnet 5 など）の費用は、検算できないまま単価表で出す

<a id="sec-3"></a>
## 3. 集計の正本と二重計上の除き方

<a id="sec-3-1"></a>
### 3.1 正本の選び方（DD-00）

**決めたこと**: logs の `api_request` を正本にし、logs に無い span だけを足す。

**理由**

- 作業分類の鍵の `prompt.id`、`cost_usd`、TTL 別の内訳、`skill.name`・`agent.name` は、`api_request` にあり span に無い（[仕様別紙 §1](../../00.活動計画/【別紙】公式仕様の調査結果.md#1-取れるシグナルと属性)、[1-7 付録 A.1](../../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-a-1)）
- traces は beta 機能で、span の `query_source` は詳細ベータトレースのときだけ出る（v2.1 の R-14）。イベントを主軸にする方が、版の変化に強い
- span を正本にしても、作業分類と費用の検算には `api_request` との結合が要り、鍵の欠けへの弱さは変わらない

**別の案**: traces の span を正本にする。

- 長所: logs に出ない呼び出しも含め、すべての要求が 1 つの信号にそろう
- 短所: 上の属性が無い。結合できなかった span には、作業分類も費用の検算も付かない。traces の形が版で変わると、正本の数え方が揺れる

**足したこと（span の無いセッション）**: traces の span を 1 件も受けていないセッション（traces を有効にする前のデータ、traces の exporter を設定していない環境）は、`api_request` だけで数え、`record_kind` を `logs_only_session` にする。計画書の既定の案は、span のあるセッションを前提にしている。span の無いセッションで、結合できなかった `api_request` を足さない規則をそのまま当てると、そのセッションが 0 件になるためである。既定の案は覆していない。

**足したこと（OTel の記録の無いセッション）**: S2 にそのセッションの記録が 1 件も無いセッションは、transcript の usage（`transcript_usage`。[§3.3](#sec-3-3)）だけから `usage_record` の行を作り、`record_kind` を `transcript_only` にする。

- 当たるのは、受信サーバが止まっていた間のセッション（取込の記録の `otel_gaps`。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）と、縮退運用（受け渡し H-25。[組 A §7.1](../01.全体構成/設計書.md#sec-7-1)）のセッションである。S2 に 1 件でも記録のあるセッションには作らないので、二重に数えない
- 計測用のセッション（[組 D §1.4](../04.有効化とデータ保全/設計書.md#sec-1-4) の `run\measure\` の記録にあるもの）は、日常の S1 には作らない。計測は計測のデータの根の S1 で数え、その取込は記録にあるセッションの transcript だけを読む
- 作れる列: トークン 4 種、TTL 別の内訳、思考トークン、`model`、`effort`（2.1.237 以降。[1-6 §3.2](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-3-2)）、サブエージェントの個体、見なし費用（`cost_basis` に transcript から計算したことを残す）
- 欠ける列: 作業分類（transcript に `prompt_id` に当たるキーが無い。未確認。[§7](#sec-7) の 16）、`cost_usd`、`skill_name`・`agent_name` などの logs の属性。列ごとの値は定義の別紙 [§1.3](【別紙】スキーマと指標の定義.md#sec-1-3)
- 足す理由: 計画書の既定の案は OTel の記録のあるセッションを前提にしている。手動の起動（J-29。[統合 §2.1](../99.設計まとめ/設計書.md#sec-2-1)）では受信サーバを止めている間も cc は動き、その間のセッションは OTel の記録が欠ける。transcript の usage で数えれば、トークンと見なし費用の集計からそのセッションが抜けない。縮退運用でも同じ規則で数えられ、部品を足さずに済む（[統合 §5](../99.設計まとめ/設計書.md#sec-5)）。既定の案は覆していない

**鍵の欠けに耐える範囲**: 鍵が欠けても、件数・トークン数・`model` は span で数えられる。作業分類と `cost_usd` は、結合できた要求に限られる（[計画書「集計の正本と二重計上の除き方」](../../00.活動計画/活動計画書.md#sec-p2-dedupe)）。第二のゴールへの備えの G2-02 は、この範囲で決めた（[統合 §5](../99.設計まとめ/設計書.md#sec-5)）。

<a id="sec-3-2"></a>
### 3.2 突き合わせの規則（DD-01〜DD-05）

**決めたこと**: 計画書の既定の案のまま、次のとおりにする。

- DD-01: 1 段目に、`api_request` と span を、`client_request_id` の値が一致するもので結合する
- DD-02: 2 段目に、1 段目で結合できなかったものを、`request_id` の値が一致するもので結合する。`client_request_id` が片側にしか無いものと、両側で値が合わないものも、ここで試す
- DD-03: 結合できた組は 1 件と数え、`record_kind` を `joined` にする。span に無い logs の属性（`prompt_id`・`skill_name`・`agent_name`・`cost_usd` など）を付け、使った鍵を `join_key` に残す
- DD-04: 結合できなかった span は 1 件と数え、`record_kind` を `span_only` にする。費用は単価表から出す（[§2.8](#sec-2-8) の MT-11）。作業分類は `unclassified_kind` の列で 2 つに分ける（値は [§6.1](#sec-6-1) の H-21）
  - `query_source_safe` が、logs に出ないと分かっている種類の表 `no_logs_query_source` にある span（本環境で観測した `auto_mode`・`agent_classifier`）は、「未分類（logs に出ない呼び出し）」
  - それ以外は「未分類（突き合わせ不可）」
- DD-05: 結合できなかった `api_request` の行は、件数・トークン・費用に足さない。行数を、結合できなかった span のうち logs に出ない種類を除いた数と比べる（[§3.4](#sec-3-4) の記録）
- `agent_id` は鍵に足さない（[1-10 §5.1](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-5-1)）

**理由**: 鍵は環境ごとではなく、リクエストごとに選ぶ。同じ環境でも、non-streaming fallback で再試行したリクエストには `client_request_id` が付かない（[計画書「集計の正本と二重計上の除き方」](../../00.活動計画/活動計画書.md#sec-p2-dedupe)）。logs に出ない種類の観測値は、[V-ID 別紙 §2](../../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表にある。

**足したこと**（同じ記録の重複）: 同じ記録が 2 回届いた場合は、正本を作る前に 1 件にする。logs は (`session_id`, `event_name`, `event_seq`, `event_ts`)、span は `span_id` が同じものを重複とみなす。OTLP の送信の再試行で同じ記録が届きうる【推定】ためである。Phase 3 で、重複が起きるかを数える（取込の記録の `s2` の、重複として除いた行の数。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）。

<a id="sec-3-3"></a>
### 3.3 transcript との突合（受け渡し H-10）

**決めたこと**

- 補完取込が作る `transcript_usage` を、`request_id` で `usage_record` に結び、`thinking_tokens` と `thinking_status` を付ける
- transcript は 1 リクエストが複数行に分かれ、確定値は最終行にある。`request_id` ごとに最後の行を使う
- `thinking_status` の値
  - `final`: 最終行の値がある
  - `unconfirmed`: 最終行の `stop_reason` が null【推定】
  - `not_in_transcript`: transcript に出ない要求（compact など）
  - `no_key`: `request_id` が無い
- サブエージェントの transcript の `agentId` は `transcript_agent_id` の列に持ち、2.1.309 以前の `subagent_key` の取り元にする（[§1.1](#sec-1-1)）
- `transcript_usage` は、OTel の記録の無いセッションの `usage_record` の行（`transcript_only`。[§3.1](#sec-3-1)）の元にもする。そのために、行の時刻と版、`effort`、`speed`、TTL 別の cache 書き込みの内訳も持つ

**理由**: [まとめ §2](../../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「データモデル」の transcript の項と、[1-2 §6](../../01.基礎調査/02.思考トークン取得経路/調査報告書.md#sec-6) による。transcript の `assistant` レコードは、`version`・`timestamp`・`effort`（2.1.237 以降）と、`speed` を含む usage を持つ（[1-6 §3.2](../../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-3-2)）。TTL 別の内訳は usage の `cache_creation` にある（[計画書 Phase 7](../../00.活動計画/活動計画書.md#sec-p7) の V-10 の行）。補完取込のコンポーネントの置き方は組 A（H-09。[組 A §7.1](../01.全体構成/設計書.md#sec-7-1)）、取込の頻度と読めない行は組 D（H-11。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）による。

## 4. バージョン追従

<a id="sec-4-1"></a>
### 4.1 検知の仕組み（VR-01）

**決めたこと**

- 取込のたびに、(`cc_version`, 信号, 名前) ごとの属性のキーと型の集合を、表 `schema_observation` に足す
- 新しい `cc_version` が来たら、直前の版の集合と比べる。加わった・消えた・型の変わったキーと、知らない `event.name`・span の名前を、取込の記録（受け渡し H-12。[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4)）に出す
- transcript も、記録型ごとのキーの集合を同じ表に持つ（信号の列は `transcript`）

**理由**: 2.1.310 の `agent_id` の追加は changelog に無く、docs の差分と実機の属性集合の比較で見つかった（[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66）。日常のデータで集合を比べれば、probe を回す前に変化に気付ける。

<a id="sec-4-2"></a>
### 4.2 差分確認の手順と担当（VR-02。MT-12 を含む）

**決めたこと**: 担当は Claude で、[§4.1](#sec-4-1) が新しい版を検知したときと、作業指示者が版を上げると知らせたときに行う。手順は、[1-8 §1](../../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-1) の差分の取り方に、[1-8 §7.1](../../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-1) の docs のページ別の差分を合わせた形である。

1. changelog の範囲の全行を読む
2. ローカル docs を、ページ別に語の差分で前の版と比べる。足りない所はオンラインのページで補う
3. 実機の属性集合を前の版と比べる（`schema_observation` か probe）
4. traces の span の名前と、集計に使う属性（トークン数、`model`、`query_source_safe`、`client_request_id`・`request_id`）を確かめる（MT-12）
5. GenAI semconv の breaking・deprecation の断片を見る（[§4.4](#sec-4-4)）
6. 集計に効く変化があれば、版の区切りの表に行を足し（[§4.3](#sec-4-3)）、固定の列に上げる属性を決める（[§1.8](#sec-1-8)）
7. 結果を新しい番号の報告書に書く。活動中は `reports/01.基礎調査/` の下に置く（[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意）

**理由**: docs だけでは拾えない変化がある。例は、2.1.310 の `agent_id`（D66）と、changelog に名前の無い `gen_ai.operation.name`（[1-8 §8.3.1](../../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-1)）である。本活動の後の保守の流れは、計画書「バージョン追従」の備忘のとおり、別に作る。

<a id="sec-4-3"></a>
### 4.3 版をまたぐ集計の区切り（VR-03）

**決めたこと**

- 元の表と `usage_record` のすべてに、`cc_version` と、大小を比べられる整数の `cc_version_num` を持つ（値の決め方は [§6.1](#sec-6-1) の H-24）

- 区切る版の一覧は計画書「[バージョン追従](../../00.活動計画/活動計画書.md#sec-p2-version)」と 1-8・1-9 にあり、本書には写さない。2.1.310（`agent_id`・tool のイベントの `request_id` が出始め、"Prompt is too long" の後の compaction が直った。[1-10 §2](../../01.基礎調査/10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66・D70）を加えるのは、計画書 v2.5 の案（P4）に依る

**理由**: 記録される値・記録の完全性・記録される属性が変わった版がある（[計画書「バージョン追従」](../../00.活動計画/活動計画書.md#sec-p2-version)）。区切りをデータの表で持つと、版が増えても集計のコードを直さずに済む。

## 8. Devil's Advocate

| 対象 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| logs の `api_request` を正本にすること（[§3.1](#sec-3-1)） | span を正本にすれば、logs に出ない呼び出しを含めて 1 つの信号で数えられ、結合の規則も要らない | 棄却する。span には `prompt.id`・`cost_usd`・TTL 別の内訳が無く、作業分類と費用の検算には結合が要る。結合の規則は、どちらを正本にしても要る。残存リスク: 職場で鍵が付かないと、結合できた組が減り、作業分類の付く範囲が狭まる（G2-10。Phase 7 の結果で決める） |
| 見なし費用を単価表のデータで計算すること（[§2.6](#sec-2-6)） | 単価表の保守が要り、表が古いと費用がずれる。`cost_usd` をそのまま使えば保守が要らない | 棄却する。既定の案（MT-07）は計画書で承認済みで、`cost_usd` は span に無く、職場の実単価にも合わない。行ごとに出典と取得日を持たせ、Phase 3 の検算でずれを見つける。残存リスク: 改定を見落とした期間の費用がずれる。行の `retrieved_at` で表の古さが分かるので、分析の報告には、使った単価表の版（`price_table_version`）と取得日を書く |
| サブエージェントの個体の鍵を (`session_id`, `agent_id`) にすること（[§1.1](#sec-1-1)） | 一意を確かめたのは 1 セッションの 4 回（同じ型 1 つ）だけで、入れ子・fork・別のセッションで値が重なれば、問い② の個体別の集計が誤る | 棄却する。鍵に `session_id` を含めるので、別のセッションの間の重なりは効かない。残存リスク: 入れ子・fork・span の `agent_id` の `acompact-` の形の値での付き方は確かめていない。Phase 3 の記録で `session_id` ごとの重複を数え、重複が出たら呼び出しの `agent_tool_use_id` を鍵に足す |
