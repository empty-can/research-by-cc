## 0. 要約

- 構成: 本活動の仕組みは、受信サーバ lmo-receiver 1 つと、都度起動のコマンド（取込、集計、起動・停止、ランチャ、品質の記録）で作る（[§1](#sec-1)）。受信サーバは常駐させず、作業指示者か Claude Code が起動・停止のスクリプト lmo-ctl で起こす（J-29。[§2.1](#sec-2-1)）
- 割り当て表の統合の行: 第二のゴールへの備えのうち Phase 2 で決める行を決めた（[§5](#sec-5)）。正式リリース物の保存と思考は、設計書の承認のときに J-35 として諮る（[§4](#sec-4)）。第二のゴールへの備えの残りは、Phase 7 の結果で決める（[§6.1](#sec-6-1)。行ごとの状態は [§7](#sec-7)）
- 裁定（J-29〜J-34）: 全体への反映を [§2](#sec-2) に書き、組の設計書にも入れた。裁定を変える必要は出なかった

<a id="sec-0-1"></a>
### 0.1 目的とスコープ

- 目的: 作業指示者が、組 A〜D の設計書とあわせて設計を承認できるようにする
- 対象
  - 全体像と組の間のつながり（[§1](#sec-1)・[§3](#sec-3)）
  - 統合の 12 行（正式リリース物の構成と第二のゴールへの備え。AR-03・AR-04・G2-01〜G2-10。[割り当て表 §1](【別紙】割り当て表.md#sec-1)）
  - 裁定（J-29〜J-34）の全体への反映と、組の間の受け渡しの食い違いのそろえ
  - Phase 3・Phase 7 の結果を待つ 5 つと、Phase 3 への引き渡し（[進め方 §2.1](../00.設計の進め方/計画書.md#sec-2-1) の統合の行）
- 対象外
  - 組の行の決めごとの詳細（正本は組の設計書）と、計画書 v2.5 の案（別に作り、設計書と同じ回に承認を受ける）
  - 実装と実機の確認（Phase 3 から）

<a id="sec-0-2"></a>
### 0.2 成功条件と打ち切り条件

- 成功条件
  - 統合の 12 行が、決めた / 作業指示者に諮る / 決めない（理由と時期）のどれかになっている（[§7](#sec-7)）
  - J-35 に、選択肢ごとの長所と短所、承認の対象、推奨、決める時期がそろっている（[§4](#sec-4)）
  - 結果を待つ 5 つに、仮置き、決める時期、決まったときに直す範囲が書かれている（[§6.1](#sec-6-1)）
  - [§3.2](#sec-3-2) のそろえを組の設計書に入れ、照合で受け渡しの食い違いが 0 件になる
- 打ち切り条件: [進め方 §0.3](../00.設計の進め方/計画書.md#sec-0-3) のとおり。本書の執筆では当たらなかった

<a id="sec-0-3"></a>
### 0.3 決めたこと

- 受信と保存の流れ（[§1.2](#sec-1-2)）
  - 受信サーバは、受けた要求をマスクの後に書き手 1 つの列に並べ、S2 に非同期で追記し、書けてから 200 を返す
  - 取込は、受信サーバの起動の直後と取込の間隔ごと（既定 1 時間。5 分〜24 時間で設定でき、下限の 5 分は【推定】。[§2.1](#sec-2-1) の警告の 3、[§8](#sec-8) の 8）、lmo-report と lmo-judge の前、手動で動き、S1 に書く唯一の書き手である
  - UI のライブ表示は、受信サーバが配る許可リストの項目（数・区分・時刻）だけを速報として出す。正は S1 である（[§1.6](#sec-1-6)）
- 組の間の食い違い 39 件をそろえ、組の設計書に入れた（寄せ方は [§3.2](#sec-3-2)）
- 縮退運用（transcript の取込だけで回す形）は用意する（G2-06。[§5](#sec-5)）

#### 1.2.1 図の要約と凡例

- 図 2 が示すもの
  - cc の OTel の送信が、受信サーバと S2 を通って S1 に入る流れ
  - UI が S1 を主に読み、受信サーバからライブの速報（許可リストの項目）を受ける形

- 凡例: 実線は操作とデータの流れ、点線はプロセスが別のプロセスを起こす・止める所である
  - 点線の例: lmo-report は集計の前に、lmo-judge は判定する作業の一覧の前に、取込を子プロセスで起こす（[組 A §2.8](../01.全体構成/設計書.md#sec-2-8)）
- 操作する人は、cc・lmo-ctl・ランチャ・lmo-report・lmo-judge・手動の取込を起こし、DuckDB CLI で探索し、UI を見る。ほかのプロセスは、図の点線の元が起こす

#### 1.2.2 図に描けない決まり

- 操作する人が Claude Code のとき: その Claude Code も、cc のセッションとして OTel を送る
- マスク: 受信サーバは、S2 に足す前に、`user.email` などの識別属性 5 つを鍵付きのハッシュに替え、プロンプトの本文は L2 の切り替えが無効なら `<dropped>` に替える（規則は[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)）

- DuckDB CLI: 作業指示者が手で打つ探索で、`.duckdb` のファイルを持たずにメモリ上で S1 と S2 を読む（[組 A §2.3](../01.全体構成/設計書.md#sec-2-3)）

#### 1.2.3 まだ決めていないこと

UI の方式（図 1）と、S1 と別の DB（DuckDB のファイルなど）を持ち UI がそれを読むかは、Phase 5 で決める。別の DB を持つと決まったら、図に足す（[§6.3](#sec-6-3) の Phase 5 の行、[組 A §2.5](../01.全体構成/設計書.md#sec-2-5)）。

#### 1.2.4 図に描かないもの

- 計測用のセッション: Claude が起こす probe と Phase 3 の比較実験のセッションで、ユーザ settings を読まずに起こす。別の受信サーバとデータの根で動く（[組 D §1.4](../04.有効化とデータ保全/設計書.md#sec-1-4)）

#### 1.2.5 ほかの節への案内

- 図にある記録と、設定のファイル・単価表などの図に無いファイルの中身: [§1.4](#sec-1-4) の一覧
- 図の操作の打つ形と引数: [§1.5](#sec-1-5)

```mermaid

  participant CTL as lmo-ctl
  participant RCV as lmo-receiver
  participant CC as cc の各セッション（送る側）

  participant REP as lmo-report
  OP->>CTL: start
  CTL->>RCV: 窓を出さずに起こす

  CTL-->>OP: 起動した（取込の間隔と、§2.1 の警告）
  RCV->>ING: 起動の直後に取込を起こす
  ING->>S1: S2 と transcript などを読み、正規化して書く

  UI->>RCV: ライブの配り口を購読する

  CC->>RCV: OTLP の送信
  RCV->>S2: マスクの後、列から 1 要求を 1 行で追記
  RCV-->>CC: 書けたら 200（書けない・列が満ちたら 503）

    RCV-->>UI: 許可リストの項目（ライブの速報）

  REP->>ING: 集計の前に取込を起こす

  OP->>CTL: stop
  CTL->>RCV: プロセス番号を確かめてから止める
```

図 3 は、受信サーバを起動してから止めるまでに、受信・取込・ライブ表示・集計がどの順で動くかを示す。200 は S2 に書けてから返し、ライブの速報はその後に配る。

- 取込は、変わったセッションについて、`usage_record` と派生の列を作り直す（[組 B §1.1](../02.データモデルと集計/設計書.md#sec-1-1)）
  - 元の表: 受けた記録を種類ごとに正規化した表
  - 変わったセッション: その回の取込で、元の表に行が入ったか行が消えた（縮んだファイルの読み直し）セッションと、計測用のセッションを除く一覧（[§1.4](#sec-1-4) の取込の状態）にその回に新しく入ったセッション
  - `usage_record`: 1 行が API リクエスト 1 件の集計の正本の表で、元の表から作る
  - 派生の列: 見なし費用（トークン数 × 単価表。[組 B §2.6](../02.データモデルと集計/設計書.md#sec-2-6)）、`prompt_label` のラベル、L2 の事後分類
- L1 の hook は `UserPromptSubmit` のときにラベルを書き、取込は S2 と同じ回にそれを読む（[組 C §4.1](../03.作業分類タグ/設計書.md#sec-4-1) の H-18、[組 A §2.8](../01.全体構成/設計書.md#sec-2-8)）

### 1.4 記録と設定のファイルの一覧

プロセスと hook が書き、読むファイルと、cc が読む設定の入口である。

- 「置き場所」は、repo・計測のデータの根・cc の設定フォルダ・scratchpad と断った行のほかは、データの根の下のフォルダである。データの根は、変数 `LMO_DATA_DIR` の値、無ければ Windows では `%LOCALAPPDATA%\local-mini-otel\` である（[組 A §4](../01.全体構成/設計書.md#sec-4) のフォルダの構成）
- 「中身の正本」は、ファイルの名前と中身の形を書いた節である
- 「機微」は、本文・識別子・利用者の付けた名前・利用統計の実数（件数・大きさ・使用率。報告書での扱いは[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の制約）が入りうるかで、扱いは正本の節にある。`session_id` などの識別子はほとんどの行にあるので、列には行に固有のもの（`cmd`・`cwd`・`work_ref`・`note`・ファイルのパスなど）を書く
- 「保持と消し方」は本活動の間の扱いで、正本は[組 D §2.1](../04.有効化とデータ保全/設計書.md#sec-2-1)（バックアップの対象かを含む）と [§2.2](../04.有効化とデータ保全/設計書.md#sec-2-2)（transcript）である。「消さない」は、本活動の終わりか不要になったときに、Claude が作る一覧を作業指示者が確かめてから消す

### 1.6 UI とライブ表示

UI の画面は Phase 5 から作る（Phase 3 は Claude の試しの購読だけ）。UI の方式と依存など、Phase 5 で決めることは [§6.3](#sec-6-3) の Phase 5 の行にある。

**読み先**（[組 A §2.3](../01.全体構成/設計書.md#sec-2-3) の表・[§2.5](../01.全体構成/設計書.md#sec-2-5)）

- UI は S1 を主に読み、S2 を直接読まない。S2 にしか無い情報は、取込で DB（S1 を第一とする）に入れてから読む
- UI は DuckDB CLI を使わない

**ライブ表示**（経路は[組 A §2.7](../01.全体構成/設計書.md#sec-2-7)、形は[組 B §1.12](../02.データモデルと集計/設計書.md#sec-1-12)、規則は[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の許可リスト）

- 出すもの: 受信サーバが配る許可リストの項目（数・区分・時刻）だけを速報として出す。保存せず、正は S1 である
- 見える項目: API 呼び出し 1 件ごとのモデル・effort・トークン 4 種・環境ラベルなど。作業分類と思考トークンは、取込の後に S1 で見る
- 許可リストの 4 条件
  1. 値が数・区分・形を決めた UTC の時刻のどれかであること
  2. マスクの規則の対象でないこと
  3. cc が付けた識別子でないこと（受信サーバが起動ごとに振り、外の記録と結べない番号は出してよい）
  4. 利用者が付けた名前を値に持ちうる属性でないこと
- 区分の値
  - 一覧か形に合わなければ、決めた値（多くの列は `other`）に替えて出す
  - `model` などの区分にも、環境によっては識別子を含む値が入りうる【推定】ので、形に合って通るゲートウェイの別名の扱いは、Phase 7 の着手時に値の形を見て決める（[組 D §6](../04.有効化とデータ保全/設計書.md#sec-6) の 16）

**`cmd` と `cwd` の出し方**（[組 C §1.5](../03.作業分類タグ/設計書.md#sec-1-5) の `cmd`、[§4.1](../03.作業分類タグ/設計書.md#sec-4-1) の H-28 の `cwd`）

- 手元の出力（lmo-report、UI、S1 の探索）: S1 に平文で持ち、出してよい（UI については、Phase 5 で出し方を決めるまでの扱い）
- ライブ表示: 出さない（許可リストの条件 4）
- 報告書: `cmd` は名前を出さず区分ごとの数だけを出し（手元の出力を写すときは名前を外す）、`cwd` は番号に置き換える

S1 を読む画面に識別子などを出すかを Phase 5 で決める材料は、上の許可リストの 4 条件、報告書での番号への置き換え（組 D §2.3）、`cmd` と `cwd` の出し方である。

### 2.1 J-29: 受信サーバを常駐させない

**決めたこと**

- 起動・停止のスクリプトは、Node.js の 1 本（`app/bin/lmo-ctl.mjs`）にする
  - 作業指示者も Claude Code も、`lmo-ctl` の `start` と `stop` を同じ形で打つ（打つ形・引数・終了コードは [§1.5](#sec-1-5)）
  - 引数が無いときは、使い方を表示する。手順書は作らない（J-29 の裁定）
  - 受信サーバが動いているかだけを見る引数は持たない。`start` が兼ねる（下の `start` の 2）
- lmo-receiver は、次の 2 つの振る舞いを持つ（[組 A §2.1](../01.全体構成/設計書.md#sec-2-1)・[§2.2](../01.全体構成/設計書.md#sec-2-2)）
  - 待ち受けの番号がすでに使われていたら、記録して終える（[組 D §1.5](../04.有効化とデータ保全/設計書.md#sec-1-5)）
  - 起動の直後と取込の間隔ごとに、取込を子プロセスで起こす（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の頻度と間隔の設定）
- transcript の保持の決めごと（`cleanupPeriodDays` を延ばさない。[組 D §2.2](../04.有効化とデータ保全/設計書.md#sec-2-2)）は保つ
  - 受信サーバを止めていた間のセッションは、次に起動したときの取込で transcript から数えて補う（[§3.2](#sec-3-2) の 20）。その間も cc の操作が止まらないことは Phase 3 で確かめる（[組 D §1.6](../04.有効化とデータ保全/設計書.md#sec-1-6)）
- タスク スケジューラの操作「プログラムの開始」から lmo-ctl の `start` を起動しても受信サーバが動き続けるかは、Phase 4 で確かめる。起動の方針は手動のままである（[§6.3](#sec-6-3)）

**`start` の振る舞い**

- 本節の「番号のファイル」は `run\lmo-receiver.pid`、「動作の記録」は `run\receiver\` である（どちらも[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)・[§2.9](../01.全体構成/設計書.md#sec-2-9)）
- 本節の「ヘッダ」は、lmo-receiver がどの応答にも付ける、自分のプロセス番号のヘッダ `x-lmo-receiver-pid` である（[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)）
- 動作の記録と取込の記録は日別のファイルなので、読む行は最新の日付のファイルから遡って探す

| 順 | 動き |
|---|---|
| 1 | 取込の記録（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の H-12）の最後の行と、動作の記録の最後の `hourly` の行を読む（下の警告の 1・2・6・9 に使う） |
| 2 | 待ち受けの番号に要求を 1 つ送り、応答を待つ（待つ上限は 5 と同じ 10 秒）<br>・応答のヘッダのプロセス番号が番号のファイルの番号と同じなら、受信サーバはすでに動いているので起こさない。そのプロセス番号と、その受信サーバが使っている取込の間隔（動作の記録の、そのプロセス番号の起動の行）を表示し、警告を出して成功で終える |
| 3 | 次のときは、起こさずに失敗で終える。<br>・応答はあるが 2 に当たらない（ヘッダが無い、ヘッダのプロセス番号が番号のファイルと違う、番号のファイルが無い）: 待ち受けの番号を使っている相手（ヘッダがあればそのプロセス番号）を表示する<br>・接続できたが、上限の内に応答が来ない（応えない受信サーバ）: 番号のファイルを残し、そのファイルのプロセス番号（ファイルがあれば）と、応えないことを表示する。止め方は下の「応えない受信サーバの止め方」 |
| 4 | 接続を断られたら（待ち受けている受信サーバが無い）、残っている番号のファイルを古いものとして消し、lmo-receiver を窓を出さずに子プロセスとして起こして、cc や起こしたシェルと独立に動かす（[§8](#sec-8) の 1）。窓を出さずに起こす仕方は、lmo-ctl の実装で決める（[組 D §3.1](../04.有効化とデータ保全/設計書.md#sec-3-1) の決めないもの） |
| 5 | 0.5 秒ごとに待ち受けの番号に要求を送り、応答のヘッダのプロセス番号が起こした子の番号と同じになったら、起動したとみなす。待つ上限は 10 秒【推定】（[§8](#sec-8) の 7） |
| 6 | 起動したら、プロセス番号、待ち受けのアドレスと番号、使う取込の間隔とその出どころを表示し、警告を出して成功で終える（表示の文言は Phase 3 で決める）<br>・間隔は受信サーバと同じ部品で求める（[組 A §7.2](../01.全体構成/設計書.md#sec-7-2) の H-11）<br>・出どころは、環境変数 `LMO_INGEST_INTERVAL_MIN`、設定のファイルのキー `ingest_interval_min`、既定（60 分）のうち、この順で最初に当たったものである（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の取込の間隔の設定） |

上限までに起動したとみなせないときは、次のとおりに理由を読んで表示し、失敗で終える。

| 子の様子 | 表示する理由 |
|---|---|
| 終わっていて、動作の記録の子のプロセス番号の最後の行が `port_in_use`（待ち受けの番号の衝突）か `key_unreadable`（鍵が読めない）。行の種類は組 A §2.9 | そのこと。鍵が読めないときは、鍵のファイルをバックアップから戻すことを添える（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3)） |
| 終わっていて、動作の記録の子のプロセス番号の最後の行が `host_not_loopback`（`LMO_OTLP_HOST` がループバックのアドレスでない） | そのことと、変数の値（行の `host`）。変数を外すか、ループバックのアドレスにしてから `start` を打ち直すことを添える（[組 A §4](../01.全体構成/設計書.md#sec-4)） |
| 終わっていて、動作の記録に子の行が無い | 起こした受信サーバがすぐ落ちたこと（子の終了コードを添える） |
| 動いたまま、上限を過ぎた | 待ち受けを始められなかったこと。子は止める |

**応えない受信サーバの止め方**（`start` の 3 か `stop` が、応えないことを表示したとき。作業指示者か Claude Code が行う）

lmo-ctl はそのプロセスを止めない（下の理由）。

1. 番号のファイルが無かったときは、待ち受けの番号を使うプロセスの番号を OS の道具（例 `netstat -ano`）で探す
2. その番号のプロセスが lmo-receiver（`app\bin\lmo-receiver.mjs` を動かす node）であることを、OS の道具（タスク マネージャーの詳細のコマンド ラインなど）で確かめる
3. そのプロセスを止める（例 `taskkill /PID <番号> /F`）
4. `start` を打つ。待ち受けの番号は接続を断るので、`start` は番号のファイルを古いものとして消して起こす（`start` の 4）

**警告**（`start` は、起こしたときも、すでに動いていたときも出す。標準エラーに出し、警告があっても成功で終える）

| 2 | 最後の取込が失敗した（`status` が `error`。失敗の扱いは[組 A §2.8](../01.全体構成/設計書.md#sec-2-8) の異常のとき） | 同上 |

**`stop` の振る舞い**: 待ち受けの番号に要求を 1 つ送り、応答で分ける（応答を待つ上限は `start` と同じ 10 秒）。

| 応答 | 動き |
|---|---|
| 接続を断られたか、ヘッダの無い応答 | 受信サーバは動いていないことを表示して成功で終える（ヘッダの無い応答なら、ほかのプログラムがその番号を使っていることも出す）。残っている番号のファイルは消す |
| ヘッダのプロセス番号が番号のファイルの番号と同じ | そのプロセスを止める（[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)）。止めた後、待ち受けの番号が接続を断るのを `start` と同じ上限まで待つ<br>・断ったら: 番号のファイルを消し、止めたプロセス番号を表示して成功で終える（表示の文言は Phase 3 で決める）<br>・断らなければ: 番号のファイルを残し、止められなかったことを表示して失敗で終える |
| ヘッダのプロセス番号が番号のファイルの番号と違うか、番号のファイルが無い | 止めずに、ヘッダのプロセス番号を表示して失敗で終える |
| 接続できたが、上限の内に応答が来ない（応えない受信サーバ） | 止めずに番号のファイルを残し、そのファイルのプロセス番号（ファイルがあれば）と、応えないことを表示して失敗で終える。止め方は上の「応えない受信サーバの止め方」 |

- 止め方は Windows では強制終了になる【推定】（[§8](#sec-8) の 1）ので、受信サーバは、止まる区間の毎時の行と停止の行を動作の記録に書かない（[組 A §2.9](../01.全体構成/設計書.md#sec-2-9)）
- 止め方を強制終了のままにするか、止まる要求を送る形にするかは、Phase 3 の試作で Claude が決め、PoC 報告書に書く（[【別紙】Phase 3 で確かめる事柄](【別紙】Phase3で確かめる事柄.md#sec-1)）。材料は次のとおりである
  - 強制終了のまま
    - 止まる区間の毎時の行と停止の行が書かれない
    - 列に並んで書き終わっていない要求には 200 を返していないので、送り手が送り直す【推定】（[組 A §2.2](../01.全体構成/設計書.md#sec-2-2)・[§9](../01.全体構成/設計書.md#sec-9) の 2）
    - 追記の途中で止まると、その日のファイルの末尾に書きかけの行が残りうる。起動し直した後の最初の行は、書き手が日のファイルを開いて最初の 1 行を書くときに、ファイルの終わりが改行でなければ行の前に改行を足す決め（組 A §2.2 の S2 への書き方）で守る
    - 受信サーバに止まる口が要らない
  - 止まる要求を送る形
    - 受信サーバが新しい要求を 503（送り直してよい応答）で断り、列を書き終え、毎時の行と停止の行を書いてから止まる
    - 待ち受けはループバックだけなので、ほかの端末からは止められない
    - ブラウザのページから送られないよう、ライブの配り口と同じ `Host` の確かめを当て（[組 A §2.7](../01.全体構成/設計書.md#sec-2-7)）、同じ `Host` の試験をその口にも当てる（[組 D §2.3](../04.有効化とデータ保全/設計書.md#sec-2-3) の確かめ方）
    - 列を書き終えるのを待つ上限が要り（初めの値は `start` と同じ 10 秒）、過ぎたら強制終了に切り替える

**理由**

- 裁定は手動の起動で、スクリプトと手順書の扱いまで決めている
- Node.js で書けば、Git Bash にも PowerShell の版にも依らず（G2-05）、J-34 の言語とそろう
- 手動の起動でも、transcript の削除（既定 30 日）より前に取り込める【推定】（[§8](#sec-8) の 2）
  - 取込は受信サーバの起動の直後に動くので、30 日の間に一度は受信サーバを起動すれば取り込める。作業指示者は cc を使う前に起動するので、この条件はふだん満たされる
  - 起動しない期間が続いたことに気付く手段は、Phase 4 で検討する（[§6.3](#sec-6-3)）
- 動いているかの確かめを `start` が兼ねるのは、引数を 2 つに保つためである。すでに動いていれば何もせずに表示だけをするので、確かめたいときに `start` を打ってよい
- 起動を確かめる上限を置くのは、起こした受信サーバが待ち受けを始められないときに、lmo-ctl が返らなくなるのを避けるためである。10 秒は、鍵の読み込みを含む起動の所要に余裕を見た値で、Phase 3 で起動の所要を見て直す
- 確かめられないときに動作の記録を読むのは、lmo-receiver が起動をやめた理由を動作の記録に書き（組 A §2.9）、lmo-ctl は子を窓を出さずに起こすので、子の標準エラーを読めないためである
- 番号のファイルと合わない相手と、応えない受信サーバを止めないのは、番号の使い回しで、ほかのプロセスを止めないためである（組 A §2.2 の理由と同じ）。応えない相手は、応答のヘッダで番号を確かめられない
- 番号のファイルを消すのを、受信サーバが待ち受けていないと分かったとき（接続を断られた、ヘッダの無い応答）と、止めた後に接続を断るのを確かめたときに限るのは、応えない受信サーバや止められなかった受信サーバの番号を残し、止める手掛かりを失わないためである
- 警告の 1 は、受信サーバを起動しているのに取込が止まっている（失敗が続く）ことに、transcript が既定の 30 日で消える前に気付くためである。この警告は、lmo-ctl の `start`・lmo-report・lmo-judge のどれも打たない期間には出ない。14 日は 30 日の半分である（[組 D §2.2](../04.有効化とデータ保全/設計書.md#sec-2-2)）
- 警告の 6〜9 は、ふだん目にしない異常に、受信サーバを起動するときに気付くためである
  - 6: 受信サーバが起こした取込の標準エラーは見る人がいない（[組 D §2.4](../04.有効化とデータ保全/設計書.md#sec-2-4) の H-12 の `settings_issue`）
  - 7: 鍵を失った後の起動は、受信サーバが止めずに続ける（組 D §2.3）ので、ハッシュの値が前と結べなくなった日に気付く手段がほかに無い
  - 8: ドライブが一杯になると、受信の 503 も取込の失敗も記録に書けない（組 A §2.8・§2.9）ので、一杯になる前に知らせる。7 日分は、作業指示者が写すか消すかを決めるまでの余裕として置いた値で、Phase 3 の見積もりの後に直す
  - 9: cc の版で送る `Host` の形が変わって `/v1/*` の要求が断られ続けている間に、動作の記録を開かずに気付ける（最後に書かれた `hourly` の行の区間にも cc が送っていれば、その行に出る）
    - 読むのはその 1 行の `bad_host` だけなので、ほかのサイトのページからの `/v1/*` への要求は、その区間に来たときだけ気付ける
    - 配り口で断った読み取りの試み（`live_bad_host` など）は警告しないので、動作の記録で見る

**計画書との関係**: 計画書 v2.5 の案は、次の 2 つを直した（[計画書 v2.5 の承認依頼書](../../00.活動計画/【別紙】計画書v2.5承認依頼書.md)）。

- [§1.3](../../00.活動計画/活動計画書.md#sec-1-3) の成功基準と [Phase 4](../../00.活動計画/活動計画書.md#sec-p4) の完了条件の「操作を増やさずに」を、「受信サーバの起動のほかに操作を増やさずに」にした
- Phase 4 の作業の「受信・保存の常駐化」を、受信サーバの起動・停止のスクリプトにした

**手順書の範囲**: ユーザ settings の `env` と `hooks` の設定の手順（[組 D §1.7](../04.有効化とデータ保全/設計書.md#sec-1-7)）は、J-29 の「手順書は作らない」の対象ではない。理由: その手順は、ユーザ settings に置くものは Claude が手順を書き作業指示者が設定するという[活動の CLAUDE.md](../../../CLAUDE.md) の作業時の注意と、J-31 に依る。

### 2.2 J-32 の注記: 還流先は仮説

作業指示者の注記のとおり、作業分類の区分の還流先（「モデル選定原則」の表と check-model の判定基準）は仮説で作られ、本仕組みの定量評価で見直す対象である。

- そこで、区分を還流先の行に合わせて固定しない。還流先が改訂されたら、区分と行の対応も分類体系の見直しのきっかけにする（組 C §1.1 の見直しのきっかけにある）
- Phase 6 の反映案は、今の還流先を正解として比べず、改訂案として出す（[計画書 Phase 6](../../00.活動計画/活動計画書.md#sec-p6) のとおり）

**今の区分**（[組 C §1.1](../03.作業分類タグ/設計書.md#sec-1-1)）

- 区分（案 A）は、作業の性質で分けた 8 区分（初版。代表は `review`（レビュー）・`impl`（実装・デバッグ）・`research`（調査））を、4 つの群（判断・実装・読み書き・操作）にまとめたものである
- 区分は、還流先の行に当てて置いた。`verify`（実機検証・計測）と `writing`（執筆・反映）は当たる行が無く、Phase 6 で行を足す候補である

### 2.3 J-34 の条件: npm パッケージが要ると分かったとき

- 条件: Phase 3 以降の実装で npm パッケージが 1 つでも要る見込みが出たら、その時点で、パッケージの中身（依存の数、保守の状態、脆弱性への備え）を添えて作業指示者に諮り、実装方針（Node.js のままか、言語を変えるか）を変えるかを検討する
- 対象: J-34 の承認が及ぶ受信・保存・取込・集計
  - DuckDB CLI は npm パッケージでなく、数に入らない（[組 A §3.3](../01.全体構成/設計書.md#sec-3-3)）
  - UI の依存は J-34 の決めないもの（Phase 5 で決める。[§6.3](#sec-6-3)）
- 起動・停止（lmo-ctl）、ランチャ（lmo-launch）、品質の記録（lmo-judge）のコマンドにも、Claude が決めたこととして同じ扱い（npm パッケージを使わず、要る見込みが出たら足す前に諮る）を当てる
  - この 3 つは J-34 の材料（組 A v0.1）に無かったが、lmo-ctl は受信サーバを起こすので、依存に脆弱性が出ると受信サーバを起こせなくなる（J-13 の作業指示者の観点）
  - 裁定の対象は広げていない

## 3. 組の間のつながり

**Claude の推奨**: 保存は S1 だけ（S2 は一時置き場）、思考は「T1 で設計し、T2 は V-2b の後に決める」。保存の推奨は、S2 を長く残す利点が小さいという【推定】に依り、正式リリース物で S1 のバックアップを決めることを条件とする。

- S1 だけと 2 層の差のうち、S1 だけを推す理由は次の 2 つである
  - ディスクの量: 他人の端末に長く残るのは S1 だけになる。J-30 で圧縮しないので、S2 の分の差がそのまま残る（量は Phase 3 で見積もる。[組 D §2.5](../04.有効化とデータ保全/設計書.md#sec-2-5)）
  - S2 を長く残す利点（いつでも作り直せる）は小さい【推定】（[§8](#sec-8) の 4）。S1 にも記録の全属性が残る（知らない `event.name` も `attrs_json` に入れる。[組 B §6.1](../02.データモデルと集計/設計書.md#sec-6-1) の H-02。S1 に入れないのは span の event などで、一覧は組 B §1.1）ので、派生の列と集計の正本の表は S1 の中で作り直せる（作り直しで OTel の元の表の行を残す。[組 A §2.8](../01.全体構成/設計書.md#sec-2-8)）。S2 が要るのは、S1 に入れる前の段（読み込みと重複の除き方）の誤りを直すときと、S1 のファイルを失った・壊れたときである。前者は一時置き場の日数の間はでき、後者には S1 のバックアップで備える。transcript と raw body から入れた行は、どちらの案でも元のファイルが消えた後は S1 にしか残らないので、S1 のバックアップはどちらの案でも要る
- 依存の差は前提に依る。2 層を本活動の形のまま（探索が S2 を DuckDB で読む）配るなら、S1 だけの方が依存が少ない。2 層でも探索を S1 だけにすれば、差は無い。依存を少なくする考え方は J-13・J-34 による（J-34 が決めたのは受信・保存・取込・集計の npm パッケージの原則で、UI の依存は Phase 5 で決める）
- 生の記録を長く残さないことは、理由にしない。S1 だけにすると、利用者が tool の内容の記録（`OTEL_LOG_TOOL_CONTENT`）を有効にした場合に、S2 にだけ残る tool の出力の内容を長く残さない差があるが、正式リリース物の既定は無効（J-31）なので理由にしない。ほかの属性の種類は S1 と同じで（本環境の設定では、リポジトリの URL と持ち主の名前の `vcs.*` も S1 の `attrs_json` に残る。[組 B §1.8](../02.データモデルと集計/設計書.md#sec-1-8)）、S1 だけにして減るのはその写しの 1 つである
- 思考は T1 で設計する。計画書の既定の案と Claude の推奨（まとめ §3.3）のとおりで、正式リリース物の既定は内容を記録する変数を 5 つとも無効にする（J-31）ので、raw body を既定で有効にしない T1 と合う。T2 を足すかは、応答のボディに usage が入るか（V-2b）が分かってから決める

**残存リスク**: cc は版ごとに属性と形が変わる。取込の誤りに一時置き場の日数の後で気付くと、生の記録から作り直せない。誤りに気付く機会は Phase 3〜Phase 6 の本活動の中にあり、作り直しが度々要るなら、推奨を 2 層に改める（[§8](#sec-8) の 4、[§9](#sec-9)）。S1 のバックアップの形を決めずに配ると、S1 のファイルを失ったときに戻す元が無い。

**決める時期**: 設計書の承認時（[進め方 P2-3](../00.設計の進め方/計画書.md#sec-p2-3) の 7）。裁定が無い場合も本活動の作業は止まらない。正式リリース物の設計に入るまでに決まっていればよい。
