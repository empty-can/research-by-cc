- **調査結果**
  - **変わらなかったこと**: 本活動が依存する属性の削除・改名・型の変化は無かった（changelog・docs・2.1.309 の実機の 3 点で確認）。属性集合は 2.1.302 のクリーンの run と同じで、加わったのは新しいイベント `claude_code.safety_event` だけだった。`prompt_id` の結合（8/8）と transcript の突合（38 件中 37 件。外れは compact の 1 件）も 2.1.302 と同じ形で、GO の根拠は保たれた（[§3.1](#sec-3-1)・[§3.3](#sec-3-3)・[§3.6](#sec-3-6)）
  - **変わったこと**: (1) `claude_code.safety_event` が加わった（2.1.307。D56）。tool call を止めたしくみを `category` で見分けられ、`tool_decision` と `tool_use_id` で結べる。(2) サブエージェントの transcript の usage と stop reason が確定値になった（2.1.307。D57。実機ではカスタムサブエージェントの 6 件中 6 件）。(3) transcript の `api-request` の記録が、1 件あたり約 6 KB から約 1.6 KB に縮んだ（実機は 2.1.309。【推定】changelog 2.1.304 の変更による。D58）。(4) custom `ANTHROPIC_BASE_URL` の背後で tool search が既定でオンになった。2.1.304 には、ゲートウェイが tool search を拒否すると全リクエストが失敗する退行があった（2.1.305 で修正。D59）。(5) PowerShell で動く hook が、exit 2 で block するようになった（2.1.309。D60）。(6) docs は、mode を設定していない `-p` を v2.1.302 以降は常に Manual（`default`）で起動すると書き、1-8 D47 の docs と changelog の食い違いが解消した。実機でも、ユーザ settings を読まない `-p` は `default` で起動した。対話は、インストール・更新の直後の最初のセッションが表と違う mode で起動しうるという docs の注記が消え、mode を設定しなければ provider に依らず auto（auto mode が使えなければ Manual）で起動する。職場のゲートウェイの背後で auto mode が使えるかは、docs では決まらない（D64）
  - **Phase 1 の記述の修正**: 崩れた事実は無かった。版を付けて読む記述を 9 件洗い出した（[§4](#sec-4)）。そのうち「サブエージェントの思考トークンは約 2/3 しか取れない」（1-2）は、2.1.306 以前に記録した transcript での評価として読む。2.1.309 で確かめたのはカスタムサブエージェントだけで、組み込みの general-purpose は確かめていないので、崩れたとは判定しなかった
- **判断事項への影響**: 推奨・既定・選択肢を変える J・Q は無く、新しい J も作らない。J-18 は、基線の版の句（事項の欄の「現時点では 2.1.302」と、既定の欄の版の句）が 2.1.309 になる。あわせて、職場の確認で cc の版を記録し、2.1.304 なら 2.1.305 以降にしてから測ること（ゲートウェイが tool search を拒否するとき全リクエストが失敗する退行。D59）を、手順の注意として計画書 Phase 7 と裁定待ち事項 §3 の J-18 に書く。職場の版の下限（第 2 の問い）は先送りのままで、規則にしない。J-16 の `--permission-mode` を明示する方針は変わらない。根拠の文のうち、docs と changelog の食い違いは解消した（D64）。J-3（Mods）・J-26（職場の接続の形）・J-12（hook の待ち時間の基準）の推奨は変わらず、材料が D63・D59 で増えただけである。回答済みの Q の判断の材料（まとめ §5.1 の Q の表、§3 の各案の長所・短所の表）は、作業指示者が読んだときのままにする
- **結論・示唆**: 本活動が依存する属性は 2.1.309 でも使える。Phase 2 の設計では次の 3 点を考えに入れる。受信・保存で知らない `event.name` を落とさない（`safety_event`。D56）、transcript の取込で読めない行を 2 種類に分けて数え、飛ばして件数を記録に残す（JSON として解析できない行と、2.1.308 以前の絵文字の途中で切れた行。D58）、L1 はスクリプトが自分で終える経路では終了コード 0 で終え、どの失敗でも終了コード 2 にならない作りにする（PowerShell の hook も 2.1.309 以降は exit 2 で止める。D60）。職場（Phase 7）の確認には、tool search の拒否と、OTel の設定がどこから来るかの記録を足す（server-managed settings の不具合 D61 は、ゲートウェイの背後では server-managed settings が止まるので職場に当たらない。docs。[§5](#sec-5)）

### 3.5 `-p` の起動時の permission mode

cf8ad11 の docs は、v2.1.302 以降、permission mode を設定していない `claude -p` と Agent SDK は Manual mode（設定上は `default`）で起動すると書く（L75467）。[1-8 D47](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) は「本環境では、`--model haiku`（Haiku 5.5）の `-p` は auto のまま動いた」とした。これを切り分けた。

- qk 系の起動時の mode: `tool_decision` の `permission_mode` は qk2・qk2b・qk2c の全件で `auto`、UserPromptSubmit の hook の入力の `permission_mode` は 8 件中 8 件で `auto` だった。Haiku 5.5・Sonnet 5.5 の run に `permission_mode_changed` は無い。Haiku 4.5 の run（s3・s3b）は、auto で起動してから default に落ちている
- 本環境は、ユーザ settings の `permissions.defaultMode` の設定により、mode を与えている（値は書かない）
- ユーザ settings を読まない起動（`--setting-sources project,local`。OTel の変数はプロセスの環境で渡したので届いた）:

| run | 設定 | 起動時の mode（`tool_decision` の `permission_mode`） | `permission_mode_changed` | `classifier_verdict` |
|---|---|---|---|---|
| v309-nouser-ha | ユーザ settings を読まない | `default` | 無し | 無し（Bash の `wc -l` は `accept`・`config`） |
| v309-nouser-dm | ユーザ settings を読まず、ユーザ settings の `permissions.defaultMode` のキーだけを写したファイルを `--settings` で渡す | `auto` | 無し | `allow` |

- 結論: 本環境の `-p` が auto で動いたのは、ユーザ settings の `permissions.defaultMode` の設定による。ほかのユーザ settings を外したまま、このキーだけを戻すと auto に戻る。mode を設定していない `-p` は、docs のとおり `default`（Manual）で起動した。1-8 D47 の「auto のまま動いた」は、docs と食い違うのではなく、mode を設定で与えた run の観測だった（1-8 §7.3.3 の記述と同じ）
- effort は、ユーザ settings を読まない nouser-ha でも `medium` だった。Haiku 5.5 の `medium` は、ユーザ settings が無くてもこの値になる（1 run）
- 限り: 各 1 run、cc 2.1.309、Anthropic API に直接つなぐ環境。nouser の 2 run は、plugin・モデル・effort などのユーザ settings もすべて外れる
