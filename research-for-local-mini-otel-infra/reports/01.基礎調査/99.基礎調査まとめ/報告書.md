  - 職場の cc の接続の形の回答（J-26）を受けて、LLM ゲートウェイ環境（職場の cc が社内ゲートウェイにつなぐ形に依る事柄の呼び名）で docs から決まることと決まらないことを整理した（[仕様別紙 §5](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5)）
- **調査結果**
  - モデル・effort・トークン・コストと、問い①〜③ のコスト側のデータは OTel で取れる。問い②の「品質」の指標と、`/clear` 前後のセッションの結び付けは未確認（[§1.1](#sec-1-1)）
  - 思考トークンは transcript との突合で、本環境のメインスレッドでは取れた。サブエージェントは 9 件中 3 件が取れず（2.1.306 以前に記録した transcript での値。2.1.307 で直った不具合に当たる【推定】。[1-9 §3.4](../09.cc2.1.304差分の確認/調査報告書.md#sec-3-4)）、compact 等の補助リクエストは取れない
  - 作業分類は、ネイティブ属性と、本文を保存しない hook 分類、または本文の事後分類で付けられる
  - cc は `http/json`（非圧縮）で送信し、数十行の Node.js で受信できた
  - GenAI semconv は Phase 2 の列名の対応表として使い、OpenInference・Phoenix は部品として使わない（[§1.2](#sec-1-2)）
  - 本活動が依存する属性は、最新の基線の cc 2.1.310 でも使える（2.1.304〜2.1.310 で削除・改名は無かった）。加わったのは、イベントの `safety_event`（2.1.307）と、属性の `agent_id`（サブエージェントのイベント）・`request_id`（tool のイベント）（どちらも 2.1.310）で、Q・J の推奨・選択肢を変えるものは無かった（[1-9 の要約](../09.cc2.1.304差分の確認/調査報告書.md#sec-0)、[1-10 の要約](../10.cc2.1.310差分の確認/調査報告書.md#sec-0)）。hook と Mod の上乗せは、2.1.287・2.1.296・2.1.302 の測定ではどれも 0.5 秒未満で、大小は版とモードで入れ替わる（[§1.3](#sec-1-3)）
  - 職場の cc は Anthropic 形式で社内 LLM ゲートウェイ（LiteLLM）につなぎ、cc の Bedrock モードは使わない（J-26）。transcript の `requestId` が付くかなどは docs では決まらない（[§1.3 の職場の接続の形](#sec-1-3-1018)）
- **結論・示唆**
  - 4 分野とも候補を 2 案に絞り、Q1 で承認いただいた（[§1](#sec-1)）。1-7〜1-10 と職場の接続の形（J-26）を受けても、候補は変えていない。本活動の中では、排他でない案を両方作る。保存は S1 と S2 の 2 層、思考は T1 と T2、タグは L1 と L2 である（[§5.1 の回答を受けて決まったこと](#sec-5-1-answers)）
  - Phase 1 を条件付きで完了とし、内容記録のフラグを要する残作業を Phase 2 と並行して進める（Q5 で承認。[§4](#sec-4)・[§5](#sec-5)）。環境変数は、内容を記録するものを含めて常時有効にしてよい（他のリポジトリに悪影響を与えうるものを除く）。変数ごとの置き場所（ユーザ settings かプロセスのスコープか）は Phase 2 で決める（Q2・Q3）
  - ゴールを 3 段に分けた（J-27）。職場環境で確かめる事項は第二のゴール（Phase 7）で確かめ、Phase 2 の着手を止めない。第一のゴールの設計には、第二のゴールへの備え（データの環境のラベル、突き合わせの鍵の欠けに耐える集計、思考案 T2 を残すこと、npm の依存を少なくすること）を含める（[§2](#sec-2) の「第二のゴールへの備え」、[§4.3](#sec-4-3)）

GenAI semconv は Phase 2 の参照語彙・対応表として採用し、OpenInference・Phoenix は実装部品として採用しない。候補（S1/S2・D1/D2・T1/T2・L1/L2）は変えない。Issue #4 の 2 つの前提は、どちらも一次資料と合わなかったので、訂正したうえで判断した（J-1、[1-7 §1.3](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-1-3)）。GenAI semconv は全体が Development 段階でリリースタグが無く、OpenInference は GenAI semconv の実装ではない Arize 独自の規約である。cc は span で GenAI semconv の属性の一部を出すが、トークン数の `gen_ai.usage.*` は 2.1.309 でも出さない（版ごとの属性は [1-7 §2.4](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-2-4) と [§2](#sec-2) の「データモデル」の 2.1.300）ので、Phase 2 では列名を cc の元の名前とし、semconv 名は対応表で持つ（[1-7 §5](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-5)・[§9](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9)）。Phoenix は traces しか受けず、cc の `http/json` を受け付けないので、候補に加えない（J-2、[§3.2](#sec-3-2)）。この結論は J-1 で条件付きで承認いただいた（2026-10-24）。条件は、本活動の後も OpenInference と Phoenix の成熟度を定期的に確かめることが漏れないよう備忘を書くことで、備忘は計画書 Phase 2「[バージョン追従](../../00.活動計画/活動計画書.md#sec-p2-version)」にある。

## 2. Phase 2 の設計に効く事実（設計項目別）

計画書 [Phase 2](../../00.活動計画/活動計画書.md#sec-p2) の設計項目ごとに並べる。

**全体構成**

- cc は `http/json` で送信でき、数十行の Node.js で受信できた（[1-1 §1](../01.実データ確認/調査報告書.md#sec-1)）。送信は非圧縮だった（全 203 リクエストで `Content-Encoding` 無し。[1-4 §4.1](../04.受信・保存コンポーネント/調査報告書.md#sec-4-1)）
  - (A) の最大の懸念だった実装負荷（protobuf のデコード）は、`http/json` を選べば生じない。1-1 で使った受信スクリプトが、そのまま PoC の出発点になる
  - (A) は、logs・metrics に加えて traces も受け、span を保存する。logs・metrics に出ず、traces の span にだけ出る API 呼び出しがあるためである（下の「分析指標」、[1-4 §6](../04.受信・保存コンポーネント/調査報告書.md#sec-6)）

  - 受信と集計・表示を別プロセスにするなら、SQLite の WAL モード（書き込み中でも別のプロセスから読める方式）を使うか、DuckDB には外部ファイル（JSONL）を読ませる
  - 後者で、書き込み中の JSONL を別プロセスの DuckDB が読めることは見込みで、未検証（Phase 3 で確認。[【別紙】V-ID別状況とPhase3実測項目 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2)）

**分析指標**

- OTel の logs（`api_request`）と metrics に出ない API 呼び出しがある。debug log には、起動時の `quota_check` とターン終了後の `side_query` が各 1 回あった（2.1.287・2.1.296 とも）。logs・metrics だけでは全 API 呼び出しを数えられず、`cost_usd` の合計は実際より小さくなりうる。ターン終了後の `side_query` は、traces には `claude_code.llm_request` span（`query_source_safe=agent_classifier`、Haiku、トークン数付き）として出ていた（Remote Control に接続した対話 run だけ）。`quota_check` は traces にも無く、課金・トークン量は未確認で、Phase 3 で件数の差を測る（[1-8 §7.3.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)）
- auto mode の分類器は、Claude Code が実行しようとする操作（Bash のコマンドや外部への通信など）を、確認なしで許可してよいかを実行前に判定する。判定は、本体のリクエストに同乗するサーバー側チェック（課金されない）か、別の呼び出しの自前の分類器リクエスト（アカウントの種類によっては課金される）で行う。自前の分類器リクエストも、logs（`api_request`）と metrics（`token.usage`）には出ず、traces の `claude_code.llm_request` span（`query_source_safe=auto_mode`、モデルは Sonnet 5、トークン数付き）には出た（C-6b、各 2 回）。1 回あたり入力 90・出力 9 トークンに加え、約 4.6 万トークンのキャッシュがあった（1 回目は書き込み、2 回目は読み込み。n=2、1 種類の操作だけ）。logs・metrics から外す理由は docs に書かれていない（Agent SDK の使用量 `modelUsage` は分類器を除くと明記している）。サーバー側チェックが効いていれば、判定は本体のリクエストに同乗し、本体のリクエストは logs・traces の両方に出る。このため、traces の span を集計に含めれば、サーバー側チェックの有無によらず漏れない見込みである（確かめたのは、直接接続で debug log を取った run に出た呼び出しの種類までで、直接接続の観測からの推定）。traces の取得に致命的な欠点は無いので、作業指示者はこの件を本活動にとって致命的ではないと判断した（J-21、J-23 は取り下げ。[1-8 §7.3.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)・[§8.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-3)）
- 2.1.307 から、tool call を止めた・確認に回した・差し戻したときに、イベント `claude_code.safety_event` が出る。止めたしくみ（規則・分類器・hook・sandbox など）を `category` で見分けられ、同じ呼び出しの `tool_decision` と `tool_use_id` で結べる。`tool_decision` は残る。分類器の block と判定なしの拒否（R6）は、`tool_decision` の `classifier_verdict` に加えて、`category` の `auto_mode_block` と `auto_mode_no_verdict` でも見られる（実機では未観測）。規則に当たった拒否は、`reason_type` では拾えないことがあるので `category` で拾う。`-p` の既定の拒否では出ない。【推定】受信・保存は、知らない `event.name` を落とさずに保存する作りにする（[1-9 §3.2](../09.cc2.1.304差分の確認/調査報告書.md#sec-3-2)、[§2](../09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D56）
- Phase 2 で決めること（計画書 Phase 2「分析指標」）
  - (1) 集計の正本と二重計上の除き方: 本体のリクエストは logs の `api_request` と traces の span の両方に出るので、両方を足すと二重に数える。traces の span を正本にするか、logs の `api_request` を正本にして logs に無い span を足すかを決める。後者の既定の規則（`client_request_id`、次に `request_id` で結合する 2 段の結合と、結合できなかった span・`api_request` の行の数え方）は、計画書 Phase 2 の[「集計の正本と二重計上の除き方」](../../00.活動計画/活動計画書.md#sec-p2-dedupe)にある。この規則で鍵の欠けに耐えるのは、件数・トークン数・model など span にある属性の集計までである。作業分類（`prompt.id` による）と `cost_usd` は結合できたリクエストに限られ、span が届かなかったリクエストは数えられない。Phase 3 の受信データの記録（鍵ごとの一致の割合など）は、[V-ID 別紙 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の、logs・metrics に出ない API 呼び出しの行にある
  - (2) span には `cost_usd` が無いので、単価から計算する。分類器のリクエストは Sonnet 5 で、キャッシュ書き込みが大きい（Sonnet 5 は client-side の分類器の既定のモデル。2.1.302 から `CLAUDE_CODE_AUTO_MODE_MODEL` で選べる。[1-8 §8.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-4)）。費用の計算の既定の案（見なし費用）は、計画書 Phase 2「[分析指標](../../00.活動計画/活動計画書.md#sec-p2-metrics)」にある
  - (3) traces は beta 機能なので、版ごとに形を確かめる
  - (4) 起動時の `quota_check` だけは、どの信号にも出ない漏れとして注記する（セッションごとに 1 回で、トークン量は不明）
- 単価: Haiku 5.5 の単価は changelog 2.1.293 にだけ書かれており（100K トークン超のプロンプトは高い段階単価）、料金ページでの出典確認と、`cost_usd` が段階単価を反映するかの確認が残る。出典確認の対象には、Sonnet 5 の単価と、TTL 別（5 分・1 時間）の cache 書き込みの単価も入る（V-11(b) #24、J-17。[§6.2](#sec-6-2)）
- system prompt の交絡: `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` が未設定のとき、Haiku 4.5・Sonnet 5・Opus 4.7 の世代までは完全版、それより新しいモデルは短縮版の system prompt を使う（docs で明記）。モデル間で入力・キャッシュ書き込みのトークンを比べると、system prompt の差が交絡する。比較実験では変数を固定するか、交絡として注記する（[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）

**有効化と常駐**

- 思考トークン: transcript の `requestId` が付かなければ、思考案 T1 は職場では成り立たない。T1 を採っても T2 を残す（J-27。計画書 §7 #8）。思考トークンの内訳がゲートウェイ経由で返るかも未確認である（計画書 §2.2）
- モデルの解決先: 職場の cc は Anthropic 形式でゲートウェイにつなぐので、`haiku` は本環境と同じく Haiku 5.5 に解決し、その ID でゲートウェイに渡る見込みである（職場の settings に `ANTHROPIC_DEFAULT_*_MODEL` などがあればそれに従う）。どの Bedrock のモデルが答えるかはゲートウェイの対応付けで決まり、cc からは見えない（J-26）
- ゲートウェイの背後の tool search: 2.1.304 から、custom `ANTHROPIC_BASE_URL` の背後で tool search が既定でオンになり、リクエストに tool search のフィールドが入る。2.1.304 には、ゲートウェイがそれを拒否するとき、全リクエストが失敗する退行がある。2.1.305 以降は拒否の後に tool search 抜きで再試行し、拒否されたリクエストもゲートウェイに見える。職場の確認では cc の版を記録し、2.1.304 なら 2.1.305 以降にしてから測る（計画書 Phase 7 の手順の注意。職場の版の下限は J-18 の第 2 の問いで先送り）。OTel への出方は docs に無い（[1-9 §2](../09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D59。確かめる項目は [1-9 §5](../09.cc2.1.304差分の確認/調査報告書.md#sec-5)）
- 起動時の permission mode: docs では、v2.1.302 以降、mode を設定していない `-p` は `default` で起動する（feature flag を取得しないときに auto で起動しえたのは v2.1.302 より前）。職場の cc が 2.1.302 以降なら、settings に `permissions.defaultMode` が無い限り、職場の `-p` も `default` で起動する（[1-9 §2](../09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D64）。測定の `-p` では `--permission-mode` を明示する（J-16）
- アイドル時の compaction: 【推定】職場では動かない可能性がある。ゲートウェイの credential で認証するなら（分岐 T・K）、要求に subscription の login が付かず、cc が既定で 1 時間の prompt cache TTL を求めるのは subscription のときだけなので（docs）、1 時間 TTL の条件に当たらない。認証が `ANTHROPIC_AUTH_TOKEN` だけ（分岐 T）なら、feature flag も取得しない（docs。J-26）
- 識別属性: `user.id` と `session.id` だけになる見込みで、これも認証の方法で分かれる（claude.ai のログインのまま使う分岐 L なら `user.email` 等も付く見込み。[【別紙】V-11(b)確認結果](【別紙】V-11(b)確認結果.md) #5、仕様別紙 §5）
- auto mode の分類器: 職場では、社内 LLM ゲートウェイの管理チームの指示で pre-release 機能を止める変数を設定し、サーバー側チェックの変数は設定していない（作業指示者による、2026-10-12）。docs では、この組み合わせではサーバー側チェックを依頼しない（`auto-mode-classifier-billing`、llm-gateway-protocol の「Disable pre-release capabilities」）。例外は、Claude Code を組み込むホストが `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` を設定している場合である。したがって職場の分類器は、自前のリクエスト（課金される）で動いている見込みである。最初から自前の分類器なら、途中の切り替えの通知は出ず、「課金の通知を見たことが無い」と矛盾しない。traces の span を集計に含めれば漏れない見込み（上の「分析指標」）なので、職場がサーバー側チェックを効かせているかは確かめない（J-23 は取り下げ）。課金の通知が出たら Enter で続行する（J-22 で裁定済み）。gateway が応答を途中で切る、または結果を書き換えると、通知の代わりに判定なしの拒否（その操作は実行されない）になり、判定なしが 10 回続くとターンが止まる（docs。職場では未確認）
- Mods と command hook の可否: managed settings の `allowManagedModsOnly` は利用者の Mod を止めるが、settings hook と plugin の command hook は動き続ける。command hook まで止めるのは `allowManagedHooksOnly`（組織が配布していない hook を止める）と `disableAllHooks` で、タグ案 L1 が成り立たないのはこの 2 つが効いている場合に絞れる（[仕様別紙 §5](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5)、[1-8 §4.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)・[§7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）。managed settings の `strictPluginOnlyCustomization` が hook をロックしても、L1 は plugin の hook（marketplace から入れる形）なら動く。settings hook の L1 と、skills のフォルダに置いた plugin は動かない（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)、[1-9 §2](../09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D63）。L1 を Mod で作って配る場合は、次の条件も加わる（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)、[1-8 §4.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-1)・[§7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) の D18）
  - 組織が managed settings で有効にした plugin でも、cache にコピーされる plugin（GitHub・git・URL・npm の source）の Mod は利用者の Mod に数えられ、`allowManagedModsOnly` で拒否され、`allowManagedHooksOnly` では読み込まれない。組織の Mod に数えられるのは、マシン上のフォルダの marketplace からその場で読み込む plugin の Mod だけである
  - LLM ゲートウェイ（`ANTHROPIC_BASE_URL` と `ANTHROPIC_AUTH_TOKEN`）で Anthropic のアカウントを持たない人の Mod が off のままだった不具合は、2.1.290 で直った。職場で Mod を使うなら 2.1.290 以降が要る（Mod を採る前提の 2.1.293 以降に含まれる）
  - Mod の `$.http.fetch` が拒否されるのは、組織の policy が WebFetch を許さない場合だけである（2.1.288 以降）。nonessential traffic を止める変数が止めるのは、組み込み Mod と、セッションの Anthropic の credential を載せた `$.http.fetch` だけである
- Git Bash: L1 の hook を既定の書き方（上の「作業分類タグ」）にすれば、Git Bash の有無に依らない。Phase 7 では、この書き方の L1 の試作の hook が職場で動くことで既定を確かめ（[V-ID 別紙 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2-l1-hook)）、Git Bash は入っているかを記録するだけにする（cc が Git Bash を使うかは確かめない）。この記録は、Phase 2 の設計担当が既定を覆して shell 形式の Bash 用の hook を選ぶときの材料にする
- ループバック宛て送信: セキュリティ製品等が `localhost` / `127.0.0.1` 宛ての OTLP 送信を止める可能性がある（作業指示者の指摘による懸念。未確認）。止められた場合に transcript の取込だけで回す構成（縮退運用）にしておくかは、Phase 2 で決める
- OTel の設定の配り方: server-managed settings で配った設定が、初回のサインインの直後などのセッションで無視される不具合は、2.1.304 で直った（それより前の版では起きうる。いつの版からかは changelog に無い。[1-9 §2](../09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D61）。ただし職場は custom `ANTHROPIC_BASE_URL` のゲートウェイの背後で、docs では server-managed settings が止まる（ファイルの managed settings は効く）ので、この不具合は職場に当たらない（職場では未確認）。職場で OTel の設定がどこから来るか（user settings か managed settings のファイルか）は Phase 7 で記録し、受信の確認の読み方に使う
- 依存: 採用した構成の npm パッケージに脆弱性が出ると、修正版が出るまで職場環境で使えなくなりうる（[§4.2](#sec-4-2)）ので、依存を少なくする（J-13）。本活動では保存を 2 層で作るので、S2 の DuckDB には依存する（[回答を受けて決まったこと](#sec-5-1-answers)）。職場では任意の版の Node.js を使える（J-24）ので、保存案 S1 の `node:sqlite`（Node 22.13 以降）の前提は職場でも満たせる

### 3.3 思考トークンの経路

思考トークンの数は OTel に出ないので、別の経路で取る。経路 (i) は、transcript の usage を OTel の `request_id` で突合する。経路 (ii) は、`OTEL_LOG_RAW_API_BODIES` で記録した応答ボディの usage を使う（[1-2 §5](../02.思考トークン取得経路/調査報告書.md#sec-5)）。

| 思考案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| **T1** | 経路 (i) だけ | 内容記録のフラグを有効にしなくてよく、応答ボディをディスクに残さない。本環境では、メインスレッドのほぼ全件と、サブエージェントの約 2/3 の思考トークンを取れる | compact・タイトル生成等の補助リクエストと、サブエージェントの約 1/3（9 件中 3 件）は取れず、「不明」として集計する。LLM ゲートウェイ環境で transcript に `requestId` が付かなければ成り立たない（付くかは Phase 7 で確かめる） |
| **T2** | 経路 (i) を主にし、(i) で取れないリクエストだけ (ii) で補う | ほぼ全件を取れる見込み。LLM ゲートウェイ環境で (i) が成り立たない場合の備えになる | フラグは全リクエストに効くので、補うためだけに全リクエストのボディ（会話履歴全体）がディスクに残る。保存量が大きい。常時の有効化の判断（計画書 §7 #2）が要る。応答ボディに usage が入ることは実測していない |

Claude の推奨は T1 である。V-2b で経路 (ii) を短期間だけ有効にして取れない分の思考トークンの量を測り、その結果で T2 に進むかを決める（1-2 §5 の所見）。分析の主眼は作業分類 × モデル × effort ごとの思考トークンの比率で、取れない分の大半は補助リクエストなので、比率への影響は小さい見込みである。サブエージェントの取れない分は、問い②（サブエージェントへの移譲）の分析に影響しうる。経路 (ii) を主にする案（1-2 の T3）は、T2 と同じ短所に加えて、transcript の取込を思考トークンの目的で使わなくなるので、候補から外した。本活動では T1 と T2 を両方作る（[回答を受けて決まったこと](#sec-5-1-answers)）。

**最強の反論と残存リスク**

| 結論 | 最強の反論 | 棄却根拠 / 残存リスク |
|---|---|---|
| 思考案 T1 / T2 に絞る | (1) サブエージェントの欠損は 9 件中 3 件の小サンプルで、実運用の欠損率は大きく異なり得る。(2) LLM ゲートウェイ環境では、transcript の `requestId` が付くかがゲートウェイの返す応答ヘッダで決まり、docs では決まらない（J-26）。付かなければ経路 (i) が成り立たない | 残存リスク。(1) は V-2b で欠損量を測ってから決める。(2) は第二のゴールの Phase 7 で確かめ、備えとして T2 を残す（J-27、[1-2 §5](../02.思考トークン取得経路/調査報告書.md#sec-5)） |
