- **調査内容**: Phase 1 の 8 項目を調べた

  - 1-7 は GitHub Issue #4 への対応で、生成 AI 向けの規格（OTel GenAI semconv・OpenInference）を一次資料で読んだ。1-8 は、cc の版（2.1.287・2.1.296・2.1.302）ごとに docs・changelog の差分を洗い出し、実機で再実測した
  - 職場の cc の接続の形の回答（J-26）を受けて、LLM ゲートウェイ環境（職場の cc が社内ゲートウェイにつなぐ形に依る事柄の呼び名）で docs から決まることと決まらないことを整理した（[仕様別紙 §5](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5)）
- **調査結果**
  - モデル・effort・トークン・コストと、問い①〜③ のコスト側のデータは OTel で取れる。問い②の「品質」の指標と、`/clear` 前後のセッションの結び付けは未確認（[§1.1](#sec-1-1)）

  - 作業分類は、ネイティブ属性と、本文を保存しない hook 分類、または本文の事後分類で付けられる
  - cc は `http/json`（非圧縮）で送信し、数十行の Node.js で受信できた
  - GenAI semconv は Phase 2 の列名の対応表として使い、OpenInference・Phoenix は部品として使わない（[§1.2](#sec-1-2)）
  - 本活動が依存する属性は、最新の基線の cc 2.1.302 でも使える。hook と Mod の上乗せは、2.1.287・2.1.296・2.1.302 の測定ではどれも 0.5 秒未満で、大小は版とモードで入れ替わる（[§1.3](#sec-1-3)）
  - 職場の cc は Anthropic 形式で社内 LLM ゲートウェイ（LiteLLM）につなぎ、cc の Bedrock モードは使わない（J-26）。transcript の `requestId` が付くか、`-p` の起動 mode などは docs では決まらない（[§1.3 の職場の接続の形](#sec-1-3-1018)）
- **結論・示唆**
  - 4 分野とも候補を 2 案に絞った（[§1](#sec-1)）。1-7・1-8 と職場の接続の形（J-26）を受けても、候補は変えていない
  - Phase 1 を条件付きで完了とし、内容記録のフラグを要する残作業を Phase 2 と並行して進めることを提案する（[§4](#sec-4)・[§5](#sec-5) Q5）
  - ゴールを 3 段に分けた（J-27）。職場環境で確かめる事項は第二のゴール（Phase 7）で確かめ、Phase 2 の着手を止めない。第一のゴールの設計には、第二のゴールへの備え（データの環境のラベル、突き合わせの鍵の欠けに耐える集計、思考案 T2 を残すこと、npm の依存を少なくすること）を含める（[§2](#sec-2) の「第二のゴールへの備え」、[§4.3](#sec-4-3)）

### 1.2 Issue #4 の結論（1-7）

GenAI semconv は Phase 2 の参照語彙・対応表として採用し、OpenInference・Phoenix は実装部品として採用しない。候補（S1/S2・D1/D2・T1/T2・L1/L2）は変えない。Issue #4 の 2 つの前提は、どちらも一次資料と合わなかったので、訂正したうえで判断した（J-1、[1-7 §1.3](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-1-3)）。GenAI semconv は全体が Development 段階でリリースタグが無く、OpenInference は GenAI semconv の実装ではない Arize 独自の規約である。cc は span で GenAI semconv の属性を出している（2.1.296 までは 5 つ。2.1.300 から `gen_ai.provider.name`・`gen_ai.tool.name`・`gen_ai.conversation.id` が加わり（2.1.302 の実機では `gen_ai.operation.name` も出た。出始めた版は確かめていない）、トークン数の `gen_ai.usage.*` は 2.1.302 でも出ない。[1-7 §2.4](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-2-4)）ので、Phase 2 では列名を cc の元の名前とし、semconv 名は対応表で持つ（[1-7 §5](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-5)・[§9](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9)。2.1.302 でも変えない）。Phoenix は traces しか受けず、cc の `http/json` を受け付けないので、候補に加えない（J-2、[§3.2](#sec-3-2)）。

### 1.3 cc の版の再確認（1-8）

本活動が依存する属性・値の体系は、2.1.287・2.1.296・2.1.302 のどの版でも 1-1・1-2 と同じで、GO の根拠（既存の属性、`prompt_id` と OTel の `prompt.id` の結合、transcript の突合）は保たれた。版ごとの事実は次のとおりである。hook と Mod の測定値の一覧は [1-3 §2.1 の版・モード別の表](../03.作業分類タグ方式/調査報告書.md#sec-2-1)、Phase 1 の文書の誤りの一覧は [1-8 §7.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-4) にある。

**2.1.287**（[1-8 §2〜§6](../08.cc2.1.287差分の確認/調査報告書.md#sec-2)）

- **属性**: 削除・改名は無く、追加は `user_prompt` の `prompt_text`（`prompt` の複製）だけだった。内容記録のフラグが OFF なら伏せ字になる（[1-8 §3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-3-1)）

**職場の接続の形と docs 2026-10-18 の差分**

- **接続の形（J-26）**: 職場の cc は、`ANTHROPIC_BASE_URL` で社内 LLM ゲートウェイ（LiteLLM）を指す Anthropic 形式でつなぎ、cc の Bedrock モード（`CLAUDE_CODE_USE_BEDROCK` で cc 自身が Bedrock の API の形で要求を送る設定）は使わない。ゲートウェイの先は Amazon Bedrock である。docs は、この形の cc はゲートウェイを Claude API として扱い、上流を知らないと書く。職場は third-party provider（docs の語。provider ごとの変数でつなぐ接続で、docs の例は Bedrock・Claude Platform on AWS・Agent Platform・Foundry）に当たらない見込みである
- **docs で決まる事柄**: Remote Control は使えない（理由は `ANTHROPIC_BASE_URL` が Anthropic 以外のホストを指すことで、Bedrock ではない）。`traceparent` は既定でゲートウェイに送らない。transcript の `requestId` は OTel の `request_id` と同じ値である

- **docs の差分（2026-10-18 取得版）**: 1 つ目は、`UserPromptSubmit` hook が、skill・カスタム slash command を打ったプロンプト（例: `/deploy staging`）では、展開した中身ではなく、打ったままの行を受け取ることである。2 つ目は、Git Bash の無い Windows で、`onFailure` を書かない shell 形式の `PreToolUse`・`PermissionRequest` の command hook が失敗すると、ツール呼び出しを止めうることである。L1 が使う `UserPromptSubmit` は 2 つ目に入らないので、fail-open の方針は変わらない（どちらも [§2](#sec-2) の「作業分類タグ」）
- **候補と推奨**: J-26 と docs 2026-10-18 の差分を受けても、GO の根拠、候補、Q1〜Q5 の推奨は変わらない

## 2. Phase 2 の設計に効く事実（設計項目別）

計画書 [Phase 2](../../00.活動計画/活動計画書.md#sec-p2) の設計項目ごとに並べる。

**全体構成**

- cc は `http/json` で送信でき、数十行の Node.js で受信できた。送信は非圧縮だった（全 203 リクエストで `Content-Encoding` 無し）（[1-1 §1](../01.実データ確認/調査報告書.md#sec-1)、[1-4](../04.受信・保存コンポーネント/調査報告書.md) §4.1）
  - (A) の最大の懸念だった実装負荷（protobuf のデコード）は、`http/json` を選べば生じない。1-1 で使った受信スクリプトが、そのまま PoC の出発点になる
- DuckDB は、同じ `.duckdb` ファイルを別プロセスから同時に読み書きできない（[1-4](../04.受信・保存コンポーネント/調査報告書.md) §3.3）
  - 受信と集計・表示を別プロセスにするなら、SQLite の WAL モード（書き込み中でも別のプロセスから読める方式）を使うか、DuckDB には外部ファイル（JSONL）を読ませる
  - 後者で、書き込み中の JSONL を別プロセスの DuckDB が読めることは見込みで、未検証（Phase 3 で確認。[【別紙】V-ID別状況とPhase3実測項目 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2)）

**データモデル**

- 型が統一されていない。`duration_ms` などが、イベントによって int と string に分かれる。取込時に正規化する（[1-1 §4.2](../01.実データ確認/調査報告書.md#sec-4-2)）
- `query_source` の値の体系が、イベントと metrics で違う（[1-1 §5](../01.実データ確認/調査報告書.md#sec-5)）
  - 対話モードでは、補助リクエスト（タイトル生成・入力候補の生成・compact など、利用者の指示に直接対応しないリクエスト）が毎回出る
  - 対話モードでは、アイドル時の compaction で、放置しただけで compact のリクエストが増えうる（changelog では 2.1.299 の項で追加。v2.1.290 は設定キー `idleCompaction` が効く版）。docs では、対話の端末、1 時間の prompt cache TTL、Anthropic から feature flag を取得できること、閾値（既定 200K トークン）以上、約 54 分の放置の 5 つがそろうと既定で動く。`compaction` イベントは `trigger=auto`、そのリクエストは `query_source=compact` である。`-p` では動かない。docs と changelog の記載で、実機では未観測（[1-1 §5](../01.実データ確認/調査報告書.md#sec-5)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D49）。LLM ゲートウェイ環境での見込みは下の「第二のゴールへの備え」
- transcript は 1 リクエストが複数行に分かれ、確定値は最終行にある。サブエージェントでは、最終行も未確定のことがある（[1-2 §3.2](../02.思考トークン取得経路/調査報告書.md#sec-3-2)）
- 異常終了したセッションでは transcript が残らない場合がある。強制終了した対話セッションで観測した（2.1.283 の 2 セッション、2.1.287 の 1 セッション、2.1.296 の 12 セッションのすべて。原因は未確定）。取込は、終了したセッションを対象にするのが安全である（[1-2 §3.1](../02.思考トークン取得経路/調査報告書.md#sec-3-1)、[1-8 §7.3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-1)）
- レコードの並べ替えは `event.timestamp` で行う。`event.sequence` はプロセス単位の連番で、セッションをまたぐ並べ替えには使えない。どの保存構成でも同じ（v2.1 R-4、[1-4](../04.受信・保存コンポーネント/調査報告書.md) §4.4）

- cc 2.1.287 より前は、resume・compaction の後にフォルダの CLAUDE.md が二重に付く不具合などがあった（2.1.285〜2.1.287 で修正）。2.1.287 より前の compact 後・resume 後の入力トークンは、本来より大きい可能性がある。問い①で compact の前後を比べるときは、`service.version` で 2.1.287 の前後を区切る（[1-8 §2.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-1) D10）
- 2.1.288 以降にも、`service.version` で区切るべき版がある（changelog。[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)・[§8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2)。2.1.300〜2.1.302 の属性ごとの最低版は [1-8 §8.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-4) の表の 4）

- `UserPromptSubmit` hook を Node.js の command hook で書くと、hook 単体の所要時間は、2.1.283・2.1.287 の `-p` を中心とする 11 回で 130〜370 ms、2.1.296 の `-p` で 130〜191 ms、2.1.302 の `-p` で 134〜160 ms だった。対話モードは、2.1.283 の 6 回中 2 回（初回プロンプト）が 2.1〜2.8 秒で、原因は未特定である。2.1.287 の対話モードは 383〜495 ms、2.1.296 は 183〜249 ms（Remote Control の有無を含む）、2.1.302 は 251〜300 ms（Remote Control を切った状態）で、2 秒超は出なかった（版・モード別の値は [1-3 §2.1 の表](../03.作業分類タグ方式/調査報告書.md#sec-2-1)、[1-8 §4.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-3)・[§7.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2)・[§8.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-2)）。この値（`hook_execution_complete` の `total_duration_ms`）は、同じ event でマッチした全 hook（並列に走る）の経過時間である（docs 2.1.295 で明記）。他の `UserPromptSubmit` hook がある環境では、L1 の hook 単体の時間としては読めない
- 日常のセッションの hook なしの基準値は、有効な plugin の構成で変わる。本環境では、ユーザ設定で有効な plugin のうち 2 つが command hook を登録しており、日常に近い条件の対話モードでは、llm_request の開始までが、それらを無効にした条件より約 450 ms 長かった（2.1.302。[§1.3](#sec-1-3)）。上の `total_duration_ms` もこれらの hook を含むので、hook ごとの時間は debug log の行で分ける。同じイベントの hook は並列に走るので、L1 の command hook の上乗せは既存の plugin の hook に隠れうる【推定】が、Mod は plugin を有効にしたままでも隠れなかった。日常のセッションには debug log が無いので、L1 の hook 自身の時間は hook が自分で記録する（Phase 2 で設計する）（J-12・J-25、[1-8 §8.3.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)）

- `user_prompt` イベントと `UserPromptSubmit` hook は、cc が自分で始めたターンでも発火する（docs 2.1.295）。`user_prompt` の件数は人間のプロンプト数ではない。タグ案 L1 での扱いは J-15 で裁定待ちで、自動開始ターンに `prompt_id` が付くかは Phase 3 で確かめる（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)・[§4](../03.作業分類タグ方式/調査報告書.md#sec-4)）
- 2.1.299 から、`UserPromptSubmit` hook は skill・カスタム slash command の展開の前に動く（changelog）。hook は、展開した中身ではなく、打ったままの行（例: `/deploy staging`）を受け取る（docs 2026-10-18 取得版）。したがって L1 のルール分類は、展開前のプロンプト（`/skill名 引数` の形）を見る。command の名前・引数で分けるなら、UserPromptExpansion hook（入力に `command_name`・`command_args` がある。docs）を使えるので、Phase 2 の作業分類タグの検討材料にする（案）。利点は command の名前でラベルを書けることで、費用は hook が 1 つ増えることである。この hook が動くのは、利用者が打った command が展開される経路だけである（モデルが Skill tool を呼ぶ経路は `PreToolUse` を通る。docs）。Phase 3 で確かめるのは、skill・slash command を使うターンの `prompt_id` の一致と上乗せで、hook の入力の形は記録だけする。同じ版から、skill の frontmatter に書いた `UserPromptSubmit` hook は、その skill を呼んだ次のプロンプトから動く。L1 の hook は skill の frontmatter に置かない（置くと、その skill を呼んだプロンプトにラベルが付かない。[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D44）

- L1 の hook は失敗しても利用者のプロンプトを止めない作り（fail-open）にし、command hook に `onFailure: "block"`（2.1.295。docs 2.1.296 で明記）は付けない。Mod は `.catch` で失敗時に素通しにする（[1-3 §4](../03.作業分類タグ方式/調査報告書.md#sec-4)）。ただし 2.1.299 から、cc は、plugin の hook との受け渡しに失敗したとき、その hook が止めうる操作を通さずに拒否する（changelog）。この対象にプロンプトが入るかは未確認である。【推定】入るなら、受け渡しの失敗はプロンプトの拒否になり、Mod の `.catch`（hook の関数の失敗を扱う）では防げない。L1 を plugin（Mod を含む）で配る場合に Phase 3 で確かめる（J-3、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D46）
- hook の失敗の扱い（docs 2026-10-18 取得版。[仕様別紙 §3](../../00.活動計画/【別紙】公式仕様の調査結果.md)）: command hook の `onFailure` を書かないときの扱いは、多くの event で `"continue"` と同じである。例外は Git Bash の無い Windows の shell 形式の `PreToolUse`・`PermissionRequest` の command hook で、失敗するとツール呼び出しを止めうる。L1 が使う `UserPromptSubmit` は例外に入らないので、fail-open の方針は変わらない。ただし、`shell` を書かない shell 形式の hook は、Git Bash が無いと PowerShell で動く（以前の docs からある記述）。【推定】Git Bash の無い Windows では、Bash 用に書いた L1 の hook は動かず、fail-open なのでラベルが黙って欠ける。L1 の hook の既定の書き方（exec 形式か `"shell": "powershell"` で書き、`"onFailure": "continue"` を明示する）は[計画書 Phase 2](../../00.活動計画/活動計画書.md#sec-p2-l1-hook) にある。docs が exec 形式を勧めるのは 1 つの `.exe` を動かす hook で、`.cmd`・`.bat` は含まない。既定は Git Bash の有無に依らないので、Phase 2 の決定は職場の確認の結果を待たない（職場での確かめ方は「第二のゴールへの備え」）
- L1 の hook は background の process を起こさない作りにする。docs（2026-10-17 取得）に「background の process を起こす hook」の節が加わり、判断を出した後に stdout・stderr を閉じない background の process を起こすと、tool call が block されるとしている（[1-3 §4](../03.作業分類タグ方式/調査報告書.md#sec-4)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D46）
- 失敗した hook の stderr と終了コードは、cc 2.1.284 以降 debug log に出る。本文を扱う hook は、stderr に本文を出さない作りにする（[1-8 §2.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-1) D11、計画書 §5）

**分析指標**

- OTel の logs（`api_request`）と metrics に出ない API 呼び出しがある。debug log には、起動時の `quota_check` とターン終了後の `side_query` が各 1 回あった（2.1.287・2.1.296 とも）。logs・metrics だけでは全 API 呼び出しを数えられず、`cost_usd` の合計は実際より小さくなりうる。ターン終了後の `side_query` は、traces には `claude_code.llm_request` span（`query_source_safe=agent_classifier`、Haiku、トークン数付き）として出ていた（Remote Control に接続した対話 run だけ）。`quota_check` は traces にも無く、課金・トークン量は未確認で、Phase 3 で件数の差を測る（[1-8 §7.3.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)）
- auto mode の自前の分類器リクエストも、logs（`api_request`）と metrics（`token.usage`）には出ず、traces の `claude_code.llm_request` span（`query_source_safe=auto_mode`、モデルは Sonnet 5、トークン数付き）には出た（C-6b、各 2 回）。1 回あたり入力 90・出力 9 トークンに加え、約 4.6 万トークンのキャッシュがあった（1 回目は書き込み、2 回目は読み込み。n=2、1 種類の操作だけ）。logs・metrics から外す理由は docs に書かれていない（Agent SDK の使用量 `modelUsage` は分類器を除くと明記している）。サーバー側チェックが効いていれば、判定は本体のリクエストに同乗し、本体のリクエストは logs・traces の両方に出る。このため、traces の span を集計に含めれば、サーバー側チェックの有無によらず漏れない見込みである（確かめたのは、直接接続で debug log を取った run に出た呼び出しの種類までで、直接接続の観測からの推定）。traces の取得に致命的な欠点は無いので、作業指示者はこの件を本活動にとって致命的ではないと判断した（J-21、J-23 は取り下げ。[1-8 §7.3.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)・[§8.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-3)）
- Phase 2 で決めること（計画書 Phase 2「分析指標」）
  - (1) 集計の正本と二重計上の除き方（規則は計画書 Phase 2 の[「集計の正本と二重計上の除き方」](../../00.活動計画/活動計画書.md#sec-p2-dedupe)）: 本体のリクエストは logs の `api_request` と traces の span の両方に出るので、両方を足すと二重に数える。traces の span を正本にするか、logs の `api_request` を正本にして logs に無い span だけを足すかを決める。後者の突き合わせの鍵は、環境ごとではなく、リクエストごとに選ぶ（`client_request_id`、無ければ `request_id`）。突き合わせできなかった `api_request` の行（鍵が無い、片側にしか無い、値が合わない）は足さず、span を数える。リクエストごとにするのは、non-streaming fallback で再試行したリクエストには、直接接続でも `client_request_id` が付かない（docs）ためである。Phase 3 の受信データの記録では、鍵が両側にあり、値が一致した割合を見る（[V-ID 別紙 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の、logs・metrics に出ない API 呼び出しの行）
  - (2) span には `cost_usd` が無いので、単価から計算する。分類器のリクエストは Sonnet 5 で、キャッシュ書き込みが大きい（Sonnet 5 は client-side の分類器の既定のモデル）
  - (3) traces は beta 機能なので、版ごとに形を確かめる
  - (4) 起動時の `quota_check` だけは、どの信号にも出ない漏れとして注記する（セッションごとに 1 回で、トークン量は不明）
- 単価: Haiku 5.5 の単価は changelog 2.1.293 にだけ書かれており（100K トークン超のプロンプトは高い段階単価）、料金ページでの出典確認と、`cost_usd` が段階単価を反映するかの確認が残る。出典確認の対象には、Sonnet 5 の単価と、TTL 別（5 分・1 時間）の cache 書き込みの単価も入れた（V-11(b) #24、J-17。[§6.2](#sec-6-2)）
- system prompt の交絡: `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` が未設定のとき、Haiku 4.5・Sonnet 5・Opus 4.7 の世代までは完全版、それより新しいモデルは短縮版の system prompt を使う（docs で明記）。モデル間で入力・キャッシュ書き込みのトークンを比べると、system prompt の差が交絡する。比較実験では変数を固定するか、交絡として注記する（[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）

**第二のゴールへの備え**

LLM ゲートウェイ環境の差の一覧と認証の方法の分岐は[仕様別紙 §5](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5)、Phase 7 で確かめる項目と手順は [V-ID 別紙 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の職場の表にある。第一のゴールの設計に効く事実を次に挙げる。

- 環境の区別: プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` は、プロセス環境変数の値を丸ごと置き換える。環境の区別（Anthropic 環境 / LLM ゲートウェイ環境）にこの変数を使う場合、どこで設定するかを一か所に決める（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)）
- 突き合わせの鍵: `request_id`・`client_request_id`（と transcript の `requestId`）が LLM ゲートウェイ環境で付くかは、docs では決まらない（J-26）。`requestId` は OTel の `request_id` と同じ値で、応答の `request-id` ヘッダ、無ければ `x-amzn-requestid` ヘッダから取り、どちらも無ければ付かない（docs）。したがって職場で付くかは、ゲートウェイ（LiteLLM）が返すヘッダで決まる。本環境の記録に混在する Bedrock 形式のモデル ID の行（2,063 件）では全件欠けていた（[1-6](../06.ローカルファイル棚卸し/調査報告書.md) §3.7）。ただし、付くかは行のモデル名の形では決まらないので、この観測を職場に当てる根拠は無い（本環境の行が欠けた理由は調べていない）。鍵が欠けても集計できるよう、上の「分析指標」の (1) の規則で span を数える
- 思考トークン: transcript の `requestId` が付かなければ、思考案 T1 は職場では成り立たない。T1 を採っても T2 を残す（J-27。計画書 §7 #8）。思考トークンの内訳がゲートウェイ経由で返るかも未確認である（計画書 §2.2）
- モデルの解決先: 職場の cc は Anthropic 形式でゲートウェイにつなぐので、`haiku` は本環境と同じく Haiku 5.5 に解決し、その ID でゲートウェイに渡る見込みである（職場の settings に `ANTHROPIC_DEFAULT_*_MODEL` などがあればそれに従う）。どの Bedrock のモデルが答えるかはゲートウェイの対応付けで決まり、cc からは見えない（J-26）
- 起動時の permission mode: 職場の `-p` の起動 mode は、認証の方法（分岐 T では feature flag を取得しない）で分かれ、docs では決まらず、本環境と食い違いうる（[仕様別紙 §5 の認証の方法の分岐](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5-auth)）。測定の `-p` で `--permission-mode` を明示すれば、この差は生じない（J-16）
- アイドル時の compaction: 【推定】職場では動かない可能性がある。ゲートウェイの credential で認証するなら（分岐 T・K）、要求に subscription の login が付かず、cc が既定で 1 時間の prompt cache TTL を求めるのは subscription のときだけなので（docs）、1 時間 TTL の条件に当たらない。認証が `ANTHROPIC_AUTH_TOKEN` だけ（分岐 T）なら、feature flag も取得しない（docs。J-26）
- 識別属性: `user.id` と `session.id` だけになる見込みで、これも認証の方法で分かれる（claude.ai のログインのまま使う分岐 L なら `user.email` 等も付く見込み。[【別紙】V-11(b)確認結果](【別紙】V-11(b)確認結果.md) #5、仕様別紙 §5）
- auto mode の分類器: 職場では、社内 LLM ゲートウェイの管理チームの指示で pre-release 機能を止める変数を設定し、サーバー側チェックの変数は設定していない（作業指示者による、2026-10-12）。docs では、この組み合わせではサーバー側チェックを依頼しない（`auto-mode-classifier-billing`、llm-gateway-protocol の「Disable pre-release capabilities」）。例外は、Claude Code を組み込むホストが `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` を設定している場合である。したがって職場の分類器は、自前のリクエスト（課金される）で動いている見込みである。最初から自前の分類器なら、途中の切り替えの通知は出ず、「課金の通知を見たことが無い」と矛盾しない。traces の span を集計に含めれば漏れない見込みで（上の「分析指標」）、職場がサーバー側チェックを効かせているかは確かめない（J-23 は取り下げ）。課金の通知が出たら Enter で続行する（J-22 で裁定済み）。gateway が応答を途中で切る、または結果を書き換えると、通知の代わりに判定なしの拒否（その操作は実行されない）になり、判定なしが 10 回続くとターンが止まる（docs。職場では未確認）
- Mods と command hook の可否: managed settings の `allowManagedModsOnly`（組み込み plugin の option で、トップレベルのキーではない）は、利用者の Mod を読み込むが拒否し、hook を動かさない。settings hook と、plugin の `hooks/hooks.json` の command hook は動き続ける。command hook まで止めるのは `allowManagedHooksOnly`（組織が配布していない hook を止める）と `disableAllHooks` で、タグ案 L1 が成り立たないのはこの 2 つが効いている場合に絞れる（[仕様別紙 §5](../../00.活動計画/【別紙】公式仕様の調査結果.md#sec-5)、[1-8 §4.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)・[§7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）
- Git Bash: L1 の hook を既定の書き方（上の「作業分類タグ」）にすれば、Git Bash の有無に依らない。Phase 7 では、この書き方の L1 の試作の hook が職場で動くことで既定を確かめ（hook の仕様は [V-ID 別紙 §2 の L1 の試作の hook](【別紙】V-ID別状況とPhase3実測項目.md#sec-2-l1-hook)）、Git Bash は入っているかを記録するだけにする。cc が Git Bash を使うかは確かめない（既定は Git Bash に依らないので、既定の確認にも Phase 2 の決定にも効かない）。この記録は、Phase 2 の設計担当が既定を覆して shell 形式の Bash 用の hook を選ぶときの材料にする
- ループバック宛て送信: セキュリティ製品等が `localhost` / `127.0.0.1` 宛ての OTLP 送信を止める可能性がある（作業指示者の指摘による懸念。未確認）。止められた場合に transcript の取込だけで回す構成（縮退運用）にしておくかは、Phase 2 で決める
- 依存: 採用した構成の npm パッケージに脆弱性が出ると、修正版が出るまで職場環境で使えなくなりうる（[§4.2](#sec-4-2)）ので、依存を少なくする（J-13）。職場では任意の版の Node.js を使える（J-24）ので、保存案 S1 の `node:sqlite`（Node 22.13 以降）の前提は職場でも満たせる
