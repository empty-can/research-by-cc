## 2. Phase 2 の設計に効く事実（設計項目別）

計画書 Phase 2 の設計項目ごとに並べる。

**全体構成**

- cc は `http/json` で送信でき、数十行の Node.js で受信できた。送信は非圧縮だった（全 203 リクエストで `Content-Encoding` 無し）（[1-1 §1](../01.実データ確認/調査報告書.md#sec-1)、[1-4](../04.受信・保存コンポーネント/調査報告書.md) §4.1）
  - (A) の最大の懸念だった実装負荷（protobuf のデコード）は、`http/json` を選べば生じない。1-1 で使った受信スクリプトが、そのまま PoC の出発点になる
- DuckDB は、同じ `.duckdb` ファイルを別プロセスから同時に読み書きできない（[1-4](../04.受信・保存コンポーネント/調査報告書.md) §3.3）
  - 受信と集計・表示を別プロセスにするなら、SQLite の WAL モード（書き込み中でも別のプロセスから読める方式）を使うか、DuckDB には外部ファイル（JSONL）を読ませる
  - 後者で、書き込み中の JSONL を別プロセスの DuckDB が読めることは見込みで、未検証（Phase 3 で確認。[【別紙】V-ID別状況とPhase3実測項目 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2)）

**データモデル**

- 型が統一されていない。`duration_ms` などが、イベントによって int と string に分かれる。取込時に正規化する（[1-1 §4.2](../01.実データ確認/調査報告書.md#sec-4-2)）
- `query_source` の値の体系が、イベントと metrics で違う（[1-1 §5](../01.実データ確認/調査報告書.md#sec-5)）
  - 対話モードでは、補助リクエスト（タイトル生成・入力候補の生成・compact など、利用者の指示に直接対応しないリクエスト）が毎回出る
- transcript は 1 リクエストが複数行に分かれ、確定値は最終行にある。サブエージェントでは、最終行も未確定のことがある（[1-2 §3.2](../02.思考トークン取得経路/調査報告書.md#sec-3-2)）
- 異常終了したセッションでは transcript が残らない場合がある（2 セッションで観測。原因は未確定）。取込は、終了したセッションを対象にするのが安全である（[1-2 §3.1](../02.思考トークン取得経路/調査報告書.md#sec-3-1)）
- レコードの並べ替えは `event.timestamp` で行う。`event.sequence` はプロセス単位の連番で、セッションをまたぐ並べ替えには使えない。どの保存構成でも同じ（v2.1 R-4、[1-4](../04.受信・保存コンポーネント/調査報告書.md) §4.4）
- サブエージェントの個体は、api_request イベントでは区別できない。trace の `agent_id` と transcript の `agentId`（ファイル名 `agent-<id>.jsonl`）で区別できる（[1-1 §6](../01.実データ確認/調査報告書.md#sec-6)、[1-6](../06.ローカルファイル棚卸し/調査報告書.md) §3.5）。`agentId` の一意性は未確認（[§6.2](#sec-6-2)）

**データ保全とプライバシー**

- 利用者のメールアドレス・アカウント ID が全レコードに入る。保存時に落とすかハッシュ化するかを決める（[1-1 §3](../01.実データ確認/調査報告書.md#sec-3)）

**有効化と常駐・両環境への対応**

- プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` は、プロセス環境変数の値を丸ごと置き換える。環境の区別（本環境 / 職場環境）にこの変数を使う場合、どこで設定するかを一か所に決める（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)）
- Windows PowerShell 5.1 からスクリプトで環境変数を設定して cc を起動すると、OTel の設定が届かなかった（[1-1 §7](../01.実データ確認/調査報告書.md#sec-7)）
  - 本番の有効化はユーザ settings の `env` で行う（計画書 §2 #6）ので、影響を受けない。影響するのは起動ランチャでラベルを付ける候補 ③ だけで、③ はタグ案 L1 / L2 のどちらにも含まれない

**作業分類タグ**

- `UserPromptSubmit` hook を Node.js で書くと、プロンプトごとに 2 秒程度待つ。hook を使うタグ案 L1 では軽量な実装にする（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)）

## 3. 受信・保存（1-4）とダッシュボード（1-5）の絞り込み

受信・保存は (A) Node.js の自作受信に絞り、保存の構成で保存案 S1 / S2 を残す。ダッシュボードは画面案 D1 / D2 を残す。以下の絞り込みは本書の評価である（1-4・1-5 は採否を判定していない）。

<a id="sec-3-1"></a>
### 3.1 受信・保存

| 候補 | 評価 | 判定 |
|---|---|---|
| (A) Node.js の自作 OTLP/HTTP 受信 | `http/json` なら実装が小さい（実証済み）。Node.js だけで動き、職場環境へ持ち込みやすい。保存形式を自由に選べる | **採用候補** |
| (B) `otelcol-contrib.exe` + file exporter + DuckDB | 外部バイナリが 2 つ増える。file exporter は alpha で、再起動時のデータ保持（V-6）が未文書化 | 外す。(A) で受信して生 JSONL を書けば、(B) と同じ「生 JSONL + DuckDB」を作れ、(B) を選ぶ利点が残らない（本書の評価） |
| (C) VictoriaMetrics / VictoriaLogs | 分析の主軸であるイベントは VictoriaLogs（LogsQL）側になり、SQL で探索できない。バイナリが 2 系統になる。OTLP の json 受信は未確認 | 外す |

(A) の保存の構成で 2 案に絞る。

| 保存案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| **S1** | 受信 → 正規化して SQLite（`node:sqlite`、WAL モード）に保存 | ネイティブビルドが不要（Node 22.13 以降）。受信中でもダッシュボードから読める。型の正規化・個人情報の除去を取込時に済ませられる | 生のレコードを残さないと、スキーマの誤りに後から気付いても取り直せない。`node:sqlite` は Node v24 でも experimental。Node 22.13 未満では使えず、`better-sqlite3`（ネイティブアドオン）が要る。探索期に DuckDB（SQLite 拡張）で集計する場合は、S2 と同じく DuckDB の導入が要る |
| **S2** | 受信 → 生の JSONL を日別ファイルに追記 → DuckDB（CLI または `duckdb -json` の子プロセス）で集計 | 生データが残る（v2.1 要件 R5・計画書 §7 #4 の解釈 A と整合）。集計の切り口を SQL ですぐ変えられる | DuckDB の導入が要る。生の JSONL にメールアドレス・アカウント ID が残る。型の正規化・個人情報の除去を集計のたびに行う。書き込み中の JSONL を別プロセスの DuckDB で読めるかは未検証（1-4 で (B) について挙げた残存リスクと同じ） |

S1 と S2 は排他ではない。「生 JSONL を保存し（S2）、そこから SQLite に正規化して取り込む（S1）」の 2 層にもできる。どちらを主にするか、2 層にするかを Phase 2 で決める。

<a id="sec-3-2"></a>
### 3.2 ダッシュボード

| 画面案 | 長所 | 短所 |
|---|---|---|
| **D1 自作 Node.js** | レイアウトを設定ファイル化でき、Claude Code に改修を任せやすい。S1・S2 のどちらにもつなげる | 画面・部品をすべて自作・保守する |
| **D2 Observable Framework**（Markdown でページを書く静的サイト生成ツール） | Markdown でページを管理でき、DuckDB / SQLite を Wasm（ブラウザ内で動く実行形式）経由で読める（ネイティブビルド不要） | 静的サイト生成が前提で、データ更新の反映方法（再ビルド等）を決める必要がある。職場環境での動作は未検証 |

外した候補と理由（典拠は [1-5](../05.ダッシュボード方式/調査報告書.md) §3・§7）:

| 候補 | 外す理由 |
|---|---|
| Grafana | 保存案 S2 では、DuckDB 用プラグインが Linux 専用で Windows から接続できない。保存案 S1 では、SQLite データソースプラグインの Windows 対応が未確認であり、Grafana サーバという外部サービスが 1 つ増える（S1 の場合の理由は本書の評価。見込み）。なお、レイアウトの変更と Claude Code への委任は、1-5 の評価では可能である。D1・D2 で要件を満たせない場合に再検討する |
| Evidence.dev | D2 と同種の候補だが、製品がホスト型へ方向転換中で、ローカルの DuckDB 接続は旧来の経路になっている。継続性に懸念がある |
| Metabase | レイアウトのコード管理は有償版のみ。Java 25 の持ち込みが職場環境で可能か不明 |
| Apache Superset | docs が Windows ネイティブの導入を対象外としている |
| DuckDB UI | チャート作成機能が無い（探索期の SQL 実行には使える） |
| Rill | Windows では WSL が必要で、本活動の制約と両立しない |

探索期（見る指標が固まるまで）は、ダッシュボードを作らず DuckDB の SQL で直接集計する（v2.1 §3.1 の考え方）。保存案 S1 でも、DuckDB の SQLite 拡張で SQLite ファイルを読める見込み（Phase 3 で確認）。定常期の画面を D1 / D2 から選ぶ時期は、計画書の改訂で決める（[§5.3](#sec-5-3)）。

## 4. GO/NO-GO 整理

Phase 1 を条件付きで完了とし、Phase 2（設計）に進むことを提案する。NO-GO リスクはいずれも、Phase 2 の設計、Phase 3 の PoC、または Phase 2 と並行する Phase 1 の残作業で扱える。

<a id="sec-4-1"></a>
### 4.1 GO を支持する事実

- [§1](#sec-1) の 6 項目とも、Phase 2 の設計に必要な判定が出た。4 分野とも候補を 2 案に絞った
- 受信は `http/json` + Node.js で成立した（実測）
- V-11(b) の 33 項目の確認結果を別紙に記録した（未確認 7 件には理由と確認時期を付けた）

<a id="sec-4-2"></a>
### 4.2 NO-GO リスク

- 計画書 §7 #2（内容記録のフラグ）が未判断で、思考案（T1 / T2）とタグ案（L1 / L2）が確定していない（[§5](#sec-5) Q2〜Q4）
- サブエージェントの思考トークンの欠損量が不明（V-2b 待ち）
- 問い②の品質の指標と、問い①の `/clear` 前後の結び付けが未設計（[§1.1](#sec-1-1)）
- 職場環境の不明点（本環境では確かめられない。Phase 3 で作業指示者が確認する）
  - **Node.js の版**: 22.13 未満なら保存案 S1 の `node:sqlite` が使えない。1-5 は Node 18 の可能性を挙げている（ルート `CLAUDE.md` の「Node.js v18+」を下限とした仮定。実際の版は未確認）
  - **Bedrock 経由の transcript の `requestId`**: 本環境の記録に混在する Bedrock 形式のモデル ID の行（2,063 件）では、全件欠けていた（[1-6](../06.ローカルファイル棚卸し/調査報告書.md) §3.7）。職場環境で同じなら、思考案 T1 は職場環境では成り立たない
  - **ループバック宛て送信のブロック**: セキュリティ製品等が `localhost` / `127.0.0.1` 宛ての OTLP 送信を止める可能性（作業指示者の指摘による懸念。本調査では未確認）
  - **思考トークンの内訳**: Bedrock・社内プロキシ経由でも返るか（計画書 §2.2）
- hook の待ち時間が未測定（タグ案 L1 を採る場合）

<a id="sec-4-3"></a>
### 4.3 次フェーズ方針

- Phase 2 は、どの案にも共通する部分から着手する
  - 受信 (A) の構成
  - データモデルの API リクエスト単位の粒度、型の正規化、個人情報の扱い
- Phase 1 の残作業（V-2b 等。[§6.2](#sec-6-2)）は、§5 の判断を受けて Phase 2 と並行して行う。思考案 T1 / T2 は V-2b の結果で、Phase 2 の中で確定する
- 職場環境のリスクは、計画書 v1.3 でリスク表に加え、Phase 3 の職場環境確認手順書に入れる（[§5.3](#sec-5-3)）
