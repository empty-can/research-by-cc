### 1.2 Issue #4 の結論（1-7）

GenAI semconv は Phase 2 の参照語彙・対応表として採用し、OpenInference・Phoenix は実装部品として採用しない。候補（S1/S2・D1/D2・T1/T2・L1/L2）は変えない。Issue #4 の 2 つの前提は、どちらも一次資料と合わなかったので、訂正したうえで判断した（J-1、[1-7 §1.3](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-1-3)）。GenAI semconv は全体が Development 段階でリリースタグが無く、OpenInference は GenAI semconv の実装ではない Arize 独自の規約である。cc は span で GenAI semconv の属性を出している（2.1.296 までは 5 つ。2.1.300 から `gen_ai.provider.name`・`gen_ai.tool.name`・`gen_ai.conversation.id` が加わり（2.1.302 の実機では `gen_ai.operation.name` も出た。出始めた版は確かめていない）、トークン数の `gen_ai.usage.*` は 2.1.302 でも出ない。[1-7 §2.4](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-2-4)）ので、Phase 2 では列名を cc の元の名前とし、semconv 名は対応表で持つ（[1-7 §5](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-5)・[§9](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-9)。2.1.302 でも変えない）。Phoenix は traces しか受けず、cc の `http/json` を受け付けないので、候補に加えない（J-2、[§3.2](#sec-3-2)）。

## 2. Phase 2 の設計に効く事実（設計項目別）

計画書 Phase 2 の設計項目ごとに並べる。

**全体構成**

- cc は `http/json` で送信でき、数十行の Node.js で受信できた。送信は非圧縮だった（全 203 リクエストで `Content-Encoding` 無し）（[1-1 §1](../01.実データ確認/調査報告書.md#sec-1)、[1-4](../04.受信・保存コンポーネント/調査報告書.md) §4.1）
  - (A) の最大の懸念だった実装負荷（protobuf のデコード）は、`http/json` を選べば生じない。1-1 で使った受信スクリプトが、そのまま PoC の出発点になる
- DuckDB は、同じ `.duckdb` ファイルを別プロセスから同時に読み書きできない（[1-4](../04.受信・保存コンポーネント/調査報告書.md) §3.3）
  - 受信と集計・表示を別プロセスにするなら、SQLite の WAL モード（書き込み中でも別のプロセスから読める方式）を使うか、DuckDB には外部ファイル（JSONL）を読ませる
  - 後者で、書き込み中の JSONL を別プロセスの DuckDB が読めることは見込みで、未検証（Phase 3 で確認。[【別紙】V-ID別状況とPhase3実測項目 §2](【別紙】V-ID別状況とPhase3実測項目.md#sec-2)）

**データモデル**

- 型が統一されていない。`duration_ms` などが、イベントによって int と string に分かれる。取込時に正規化する（[1-1 §4.2](../01.実データ確認/調査報告書.md#sec-4-2)）
- `query_source` の値の体系が、イベントと metrics で違う（[1-1 §5](../01.実データ確認/調査報告書.md#sec-5)）
  - 対話モードでは、補助リクエスト（タイトル生成・入力候補の生成・compact など、利用者の指示に直接対応しないリクエスト）が毎回出る
  - 対話モードでは、アイドル時の compaction（v2.1.290 以降は既定で有効。200K トークン以上の会話を、最後の要求から約 54 分放置すると compact する。`compaction` イベントは `trigger=auto`、そのリクエストは `query_source=compact`）で、放置しただけで compact のリクエストが増えうる。`-p` では動かない。docs と changelog の記載で、実機では未観測（[1-1 §5](../01.実データ確認/調査報告書.md#sec-5)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D49）
- transcript は 1 リクエストが複数行に分かれ、確定値は最終行にある。サブエージェントでは、最終行も未確定のことがある（[1-2 §3.2](../02.思考トークン取得経路/調査報告書.md#sec-3-2)）

**有効化と常駐・両環境への対応**

- プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` は、プロセス環境変数の値を丸ごと置き換える。環境の区別（本環境 / 職場環境）にこの変数を使う場合、どこで設定するかを一か所に決める（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)）
- Windows PowerShell 5.1 からスクリプトで環境変数を設定して cc を起動すると、OTel の設定が届かなかった（[1-1 §7](../01.実データ確認/調査報告書.md#sec-7)）
  - 本番の有効化はユーザ settings の `env` で行う（計画書 §2 #6）ので、影響を受けない。影響するのは起動ランチャでラベルを付ける候補 ③ だけで、③ はタグ案 L1 / L2 のどちらにも含まれない
- 2.1.302 から、permission mode を指定しない `-p` は、third-party provider のとき、テレメトリを無効にしているとき、インストール直後のときに default で起動する（changelog）。本環境では、2.1.302 でも `haiku` エイリアスの解決先（Haiku 5.5）の `-p` は auto のまま動いた。【推定】職場（社内 LLM ゲートウェイ＋Bedrock）は third-party provider に当たるので、職場の `-p` の起動 mode は本環境と食い違いうる。測定の `-p` は `--permission-mode` を明示する（J-16、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D47）
- 2.1.300 から、api.anthropic.com への大きいリクエストは、テレメトリを無効にしていても gzip で送る（`CLAUDE_CODE_GZIP_REQUEST_BODIES=0` で止める。changelog）。対象は API へのリクエストで、上の「全体構成」の OTel の送信（非圧縮）の観測とは対象が違う。【推定】proxy で raw body を取る経路を使うなら、展開が要る。【推定】OTel の受信には関係しない（[1-2 §4](../02.思考トークン取得経路/調査報告書.md#sec-4)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D51）

- 日常のセッションの hook なしの基準値は、有効な plugin の構成で変わる。本環境では、ユーザ設定で有効な plugin のうち 2 つが command hook を登録しており（2.1.296 の測定の後に増えた 4 つの plugin の一部）、日常に近い条件（plugin は有効のまま、Remote Control を切る、hook なし）の対話モードでは、llm_request の開始までが、増えた plugin を無効にした条件より約 450 ms 長かった（2.1.302）。上の `total_duration_ms` もこれらの hook を含むので、hook ごとの時間は debug log の行で分ける。J-12 の判定の組に plugin の構成（command hook を登録する plugin の有無）を足した（J-25、[1-8 §8.3.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)）
- hook の代わりに Claude Mods（2.1.287）の `classic.UserPromptSubmit` も使える。`prompt_id` は `-p`・対話モードとも OTel と結合できた（2.1.287・2.1.296 とも各 3 回。2.1.302 は `-p` で Mod 18 回・command hook 15 回、対話モードで各 3 回）。llm_request の開始までの上乗せは、2.1.287 では両モードとも Mod が小さかったが、2.1.296・2.1.302 の `-p` では command hook の方が小さい（各 n=3。原因（組み込み Mod の `prompt.context`。C-3c で確認）と比較材料は [§1.3](#sec-1-3)、[1-3 §2.1 の版・モード別の表](../03.作業分類タグ方式/調査報告書.md#sec-2-1)）。2.1.302 は、`-p`（Haiku 4.5 を明示した対照）で command hook +134 ms・Mod +201 ms、対話モード（Remote Control を切った状態）で command hook +270 ms・Mod +94 ms で、2.1.296 と同じ向きだった（対話モードは Mod の方が小さい。組み込み Mod を無効にすると `-p` の Mod の上乗せが消えることも同じ。[1-8 §8.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-2)）。Mod を採るなら 2.1.293 以降が前提になる。職場の managed settings で、Mod も command hook も止められうる（[§4.2](#sec-4-2)）。比較の一覧は [1-8 §4.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)・[§7.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2)
- `user_prompt` イベントと `UserPromptSubmit` hook は、cc が自分で始めたターン（scheduled task（`/loop` の各回を含む）、background subagent の起動元への報告、他セッションからのメッセージ）でも発火する（docs 2.1.295）。`user_prompt` の件数は人間のプロンプト数ではない。タグ案 L1 での扱いは J-15 で裁定待ちで、自動開始ターンに `prompt_id` が付くかは Phase 3 で確かめる（[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)・[§4](../03.作業分類タグ方式/調査報告書.md#sec-4)）
- 2.1.299 から、`UserPromptSubmit` hook は skill・カスタム slash command の展開の前に動く（changelog）。【推定】L1 のルール分類は、展開前のプロンプト（`/skill名 引数` の形）を見る。skill・slash command を使うターンの hook 入力と `prompt_id` の一致は Phase 3 で確かめる。同じ版から、skill の frontmatter に書いた `UserPromptSubmit` hook は、その skill を呼んだ次のプロンプトから動く。L1 の hook は skill の frontmatter に置かない（置くと、その skill を呼んだプロンプトにラベルが付かない。[1-3 §2](../03.作業分類タグ方式/調査報告書.md#sec-2)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D44）
- Mod の hook の変更（changelog）: 2.1.299 から、`turn.start` はサブエージェントのターンでも発火する（`agentId` で区別する。メインループのターンには `agentId` が無い。J-15 の判定規則の材料）。2.1.300 で `prompt.change` hook が加わった（[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D45）
- L1 の hook は失敗しても利用者のプロンプトを止めない作り（fail-open）にし、command hook に `onFailure: "block"`（2.1.295。docs 2.1.296 で明記）は付けない。Mod は `.catch` で失敗時に素通しにする（[1-3 §4](../03.作業分類タグ方式/調査報告書.md#sec-4)）。ただし 2.1.299 から、cc は、plugin の hook との受け渡しに失敗したとき、その hook が止めうる操作を通さずに拒否する（changelog）。この対象にプロンプトが入るかは未確認である。【推定】入るなら、受け渡しの失敗はプロンプトの拒否になり、Mod の `.catch`（hook の関数の失敗を扱う）では防げない。L1 を plugin（Mod を含む）で配る場合に Phase 3 で確かめる（J-3、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D46）
- L1 の hook は background の process を起こさない作りにする。docs（2026-10-17 取得）に「background の process を起こす hook」の節が加わり、判断を出した後に stdout・stderr を閉じない background の process を起こすと、tool call が block されるとしている（[1-3 §4](../03.作業分類タグ方式/調査報告書.md#sec-4)、[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D46）
- 失敗した hook の stderr と終了コードは、cc 2.1.284 以降 debug log に出る。本文を扱う hook は、stderr に本文を出さない作りにする（[1-8 §2.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-1) D11、計画書 §5）

## 3. 受信・保存（1-4）とダッシュボード（1-5）の絞り込み

受信・保存は (A) Node.js の自作受信に絞り、保存の構成で保存案 S1 / S2 を残す。ダッシュボードは画面案 D1 / D2 を残す。以下の絞り込みは本書の評価である（1-4・1-5 は採否を判定していない）。

### 3.1 受信・保存

| 候補 | 評価 | 判定 |
|---|---|---|
| (A) Node.js の自作 OTLP/HTTP 受信 | `http/json` なら実装が小さい（実証済み）。Node.js だけで動き、職場環境へ持ち込みやすい。保存形式を自由に選べる | **採用候補** |

| (C) VictoriaMetrics / VictoriaLogs | 分析の主軸であるイベントは VictoriaLogs（LogsQL）側になり、SQL で探索できない。バイナリが 2 系統になる。OTLP の json 受信は未確認 | 外す |

(A) の保存の構成で 2 案に絞る。

| 保存案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| **S1** | 受信 → 正規化して SQLite（`node:sqlite`、WAL モード）に保存 | ネイティブビルドが不要（Node 22.13 以降）。受信中でもダッシュボードから読める。型の正規化・個人情報の除去を取込時に済ませられる | 生のレコードを残さないと、スキーマの誤りに後から気付いても取り直せない。`node:sqlite` は Node v24 でも experimental。Node 22.13 未満では使えず、`better-sqlite3`（ネイティブアドオン）が要る。探索期に DuckDB（SQLite 拡張）で集計する場合は、S2 と同じく DuckDB の導入が要る |

S1 と S2 は排他ではない。「生 JSONL を保存し（S2）、そこから SQLite に正規化して取り込む（S1）」の 2 層にもできる。どちらを主にするか、2 層にするかを Phase 2 で決める。

**Q2 の補足（2026-10-10 追記）**

- v0.8 までの「Q2 は影響が無い」は誤りだった。根拠にしていた「本環境は first-party・テレメトリ有効なので、`-p` の auto mode での起動（2.1.285）の条件に当たらない」は、組み込みの既定については正しい。しかし本環境は、ユーザ settings（`~/.claude/settings.json`）の `permissions.defaultMode` の設定により、`-p` も auto mode で起動する（[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）。probe はユーザ settings を変えていない
- 2.1.287 でも、`-p` の Haiku 4.5 の run 10 件すべてが、起動直後に `permission_mode_changed`（auto から default へ。`auto_gate_denied`）を出していた（OTel で確認）。Haiku 4.5 が auto mode に対応しないため default に落ち、見えにくかった。2.1.296 では `haiku` が auto 対応の Haiku 5.5 に解決するので、`-p` も auto のまま動く。版上げで生じた誤りではないが、版上げで実際の挙動に効くようになった。command hook の入力の `permission_mode` も同じことを示す（2.1.287 の Sonnet 5.5 の `-p` でも `auto`。1-8 §7.3.3）
- このため、推奨の条件に「`--permission-mode default` を明示する」を足した。auto mode のままだと、ツール 1 回の許可判定に約 300 ms かかり（default の Haiku 4.5 では十数 ms。n=1）、分類器のリクエストは `api_request` に現れず（2026-10-12 の C-6b。自前のリクエストにした場合は traces の span には出る）、raw body での見え方は未確認なので、V-2b の条件を固定する。推奨（有効にする）と、承認しない場合の進め方は変えない
