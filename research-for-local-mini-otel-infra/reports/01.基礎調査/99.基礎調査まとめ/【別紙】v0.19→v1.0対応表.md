# 【別紙】v0.19→v1.0 対応表 — 基礎調査まとめ報告書

[まとめ報告書](報告書.md)を v0.19 から v1.0 に書き直したときの、旧版の節・段落・表の行ごとの行き先である。レビューの道具として置く。v0.19 は git の履歴（コミット 28f1ca2）で読める。§2 の「v0.19 の位置」の括弧の数字は、v0.19 の行番号である。

<a id="sec-1"></a>
## 1. v0.19 からの変更の要点

- ゴールを 3 段に分ける裁定（J-27）を反映した。職場環境の確認を、Phase 3 から第二のゴールの Phase 7 へ移した（§0・§1・§3.3・§4・§5・§6）
- 意味を変えた箇所は次の 5 つで、どれも J-27・J-24・実用性 S7 による
  - Q5 の残作業の範囲から、職場環境の確認を外した（§5.1 の表の Q5 の質問の欄。§6.2 の行の職場の分は表の下に分け、表は 10 行のまま）
  - 職場の Node.js の版の不明点（§4.2）とお願い（§5.2）を、J-24 の回答（職場では任意の版の Node.js を使える）で消した
  - §2 の突き合わせの鍵の規則を、計画書 v2.0 の「集計の正本と二重計上の除き方」の参照にし、2 段の結合（`client_request_id`、残りを `request_id`）と、結合できなかった側ごとの扱い（span は 1 件と数えて作業分類を「未分類（突き合わせ不可）」にし、`api_request` の行は足さずに行数だけ記録する）の形にした。鍵の欠けに耐える範囲（件数・トークン数・model まで）も書いた（実用性 S7。同日のクロスレビュー Round 2 の論理整合性 S1・実用性 I2 で、規則の形と限界を足した）
  - 「第二のゴール」の語を、v2.0 の意味（LLM ゲートウェイ環境）だけで使う。§3.3 の「第二のゴール（WSL + Docker）」は第三のゴールにした
  - 第一のゴールの設計に、第二のゴールへの備えを含めることを書いた（§0・§2・§4.3）
- 日付ごとの補足（§1.3 の 2.1.296・2.1.302 の追補と 2026-10-18 の補足、§5.1 の Q1〜Q5 の補足）を、今の時点の文に畳んだ。いつ何を変えたかは[【別紙】改訂履歴](【別紙】改訂履歴.md)に移した
- §1.3 を、版ごとの事実（2.1.287・2.1.296・2.1.302）と、職場の接続の形と docs 2026-10-18 の差分（アンカー `sec-1-3-1018`）にした。版ごとの測定値は、1-3 §2.1 の表と 1-8 に寄せ、2.1.302 の値だけを残した
- §2 の項目の名前を、計画書 Phase 2 の 8 つの設計項目にそろえた。「有効化と常駐・両環境への対応」を「有効化と常駐」と「第二のゴールへの備え」に分け、「分析指標」と「バージョン追従」を立てた。`service.version` で区切る版の一覧は「データモデル」に残した（計画書の「バージョン追従」が「データモデル」を参照しているため）
- §4.2 を、第一のゴールのリスクと、第二のゴールのリスク・不明点（1 行ずつ）に分けた
- §5.1 の表の質問・選択肢・推奨・承認しない場合の進め方・回答の列は、Q5 の範囲のほか変えていない。表から「（10-03 補足あり）」などの印と、Q2 の推奨の中の「10-10 追加。」を外し、Q5 の推奨の「計画書 v1.3」を「計画書 v2.0」にした（版の付け替えで、意味は変えていない）
- 候補、GO の根拠、Q1〜Q5 の推奨は変えていない。アンカー（`sec-0`〜`sec-6-4`、`sec-1-3-1018` の 24 個）、Q・J・V-ID・案のラベルも変えていない
