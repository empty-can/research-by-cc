## 2. Phase 3 で実測する項目

個別報告書と V-11(b) の別紙から集約した。v0.2 で [1-8 §6](../08.cc2.1.287差分の確認/調査報告書.md#sec-6) の未確認事項を、v0.6 で cc 2.1.296 の追補の未確認事項（[1-8 §7.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-5)）を、v0.8 で docs 2.1.296 の反映（1-8 §7 の「2026-10-12 追記」）を、v0.13 で cc 2.1.302 の再確認（[1-8 §8](../08.cc2.1.287差分の確認/調査報告書.md#sec-8)）を、v0.15 で職場の接続の形の回答（J-26）と docs 2026-10-18 取得版の差分を加えた。計画書 Phase 3 の確認観点（受信サーバが止まっていても cc の操作に影響しないか、2 セッション同時で欠落しないか等）に加えて行う。

- Phase 3 の測定は、Phase 3 着手時点の最新の基線の版以降（基線は本活動の文書で確かめた cc の版で、計画書 §2 冒頭にある。2026-10-17 時点では cc 2.1.302）で行うことを提案する（[裁定待ち事項](../作業指示者裁定待ち事項.md#sec-1) J-18 で裁定待ち）。下限は Phase 3 着手時点で一度だけ決め、Phase 3 の途中の反映では上げない（途中で上げると、先に測った値が新しい下限を下回り、判定に使えなくなる）。Phase 3 着手の前に、基線の版に回帰が見つかったら、下限を自動では上げず、作業指示者に諮る。この提案は 2026-10-17 に見直したもので、v0.12 までは「cc 2.1.293 以降」（v0.5 までは 2.1.287 以降）としていた。見直した理由は、Phase 3 で測る項目に、2.1.300〜2.1.302 で入った属性を使うものがあることである。span の `gen_ai.provider.name` と `api_request` の `cache_creation_5m_tokens`・`cache_creation_1h_tokens` は 2.1.300、`tool_decision` の `classifier_verdict`・`permission_mode` は 2.1.301、`classifier_category` の欠落の修正は 2.1.302 で入った。span の `gen_ai.operation.name` は、2.1.296 では出ず、2.1.302 では出た（changelog に名前が無く、出始めた版は確かめていない）。2.1.293 の下限では、それらが出ない版を許してしまう。属性ごとの最低版は [1-8 §8.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-4) の表の 4 にある。下限は本環境の測定に課す。職場環境では確認時の cc の版を記録し、下限未満なら、その版で測った値は本環境の値と比べず、職場の中の比較に限る（managed settings のキーと拒否の行の確認は版に依らないので、そのまま行う）。作業指示者の情報（2026-10-12）では、職場の cc は起動ランチャーで常に最新版に更新している。旧提案（2.1.293 以降）の理由は、2.1.288 の OTel の値の修正（`-p` の `claude_code.tool.blocked_on_user` の source・decision が `unknown` になる不具合と、未回答の permission ask で `tool_decision` が出ない不具合）、2.1.288〜2.1.290 の transcript の回帰（終了時に最後のメッセージが失われうる。2.1.291 で修正）、2.1.287〜2.1.292 の Mod の不具合（worker の再起動中に `classic.*` hook が飛ばされる。2.1.293 で修正）である。hook と Mod の上乗せは版で動く（2.1.296 の `-p` では Mod の方が大きくなった）ので、測定では `service.version` を必ず記録し、hook と Mod の比較は同じ版の値どうしで行う
- 版の検知: cc の自動更新は止めない（更新は利用者の操作なしに起き、次の起動で効く）。測定の前後で `claude --version` を記録する。`service.version` が前のセッションと変わった最初のセッションを「版上げ直後」とみなし、測定の途中で版が変わったら、変わった後のセッションをその比較から除く。職場環境でも同じく、確認のたびに cc の版を記録し、前回と違えば最初のセッションを測定に使わない
- Phase 1 の 1-1〜1-6 は 2.1.283 の実測で、2.1.287 での再確認の結果は [1-8 §3](../08.cc2.1.287差分の確認/調査報告書.md#sec-3)、2.1.296 での再確認の結果は [1-8 §7.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3) にある
- モデルは完全な ID で指定し、エイリアス（`haiku` 等）では指定しない。2.1.293 から、Anthropic API の `haiku` は Haiku 5.5（`claude-haiku-5-5`）に解決し、過去の実測の Haiku 4.5（`claude-haiku-4-5-20251001`）とは違う。基準モデルは、版をまたぐ継続比較（属性集合・遅延・突合）は Haiku 4.5、auto mode が有効なまま動く条件（auto mode の比較を含む）の基準は Haiku 5.5、と用途で分ける案である（[裁定待ち事項](../作業指示者裁定待ち事項.md#sec-1) J-14 で裁定待ち）
- 測定の注意（[1-8 §7.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-1)・[§7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）
  - permission mode は `--permission-mode` で明示して固定する（比較実験の値は、auto mode の行の案のとおり `default`）。本環境はユーザ settings の `permissions.defaultMode` の設定により、対話モードも `-p` も auto で起動する（組み込みの既定ではない。2.1.296・2.1.302 の本環境の実機の事実）。2.1.302 は、third-party provider・テレメトリ無効・インストール直後のとき、permission mode を指定しない `-p` を default で起動する（[1-8 §8.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-4) の表の 1）。職場は third-party provider に当たらない見込みだが（J-26）、認証の方法によっては feature flag を取得しないので、職場の `-p` の起動 mode は docs では決まらず、本環境と食い違いうる（職場の表の起動時の permission mode の行）。J-12 の判定に使う日常のセッションは固定せず、mode を記録する（hook の行）
  - `-p` は 2.1.292 から、main が起動した background コマンドと `/loop` の wakeup を待ち、結果を受けてもう 1 ターン走る。計測用の `-p` では background コマンドを使わない（ターン数と `api_request` の件数が増えうる）
  - Git Bash から `-p "/compact"` などのスラッシュコマンドを渡すときは `MSYS_NO_PATHCONV=1` を付ける（付けないとパスに変換される）
  - Claude が起動する対話モードの計測用のセッション（probe と比較実験）は、Remote Control を切って行い、各 run の Remote Control の有無を記録する（2026-10-10 の作業指示者の指示。J-12 の判定に使う日常のセッションは切らない。[裁定待ち事項](../作業指示者裁定待ち事項.md#sec-2) J-19）。切り方: `remoteControlAtStartup` を false にする 1 キーだけの JSON ファイルを作り、そのパスを `--settings` に渡す（JSON の文字列を直接渡すと、シェルごとの引用符の扱いが要る）。確かめ方: debug log に、Remote Control の接続を示す行（接頭辞 `[remote-bridge]`・`[bridge:repl]`・`[bridge]`）が 0 件であること。`--plugin-dir` を使う実行では、ファイル識別の行にも「bridge」の語が出るので、接頭辞で判定する（[1-8 §7.3.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)）。`-p` は Remote Control に接続しない。LLM ゲートウェイ環境では、`ANTHROPIC_BASE_URL` が Anthropic 以外のホストを指すので Remote Control は使えない（docs。J-26）。この項目は本環境だけ
  - probe と Phase 3 の比較実験での plugin の扱い（v0.14 で追加。[裁定待ち事項](../作業指示者裁定待ち事項.md#sec-2) J-25）。規則: plugin の構成を、比べる相手の測定（前回の基線）と同じにする。前回の測定の後にユーザ設定で有効になった plugin は、hook を登録しないものも含めて無効にする（2.1.302 の測定では、2.1.296 の後に増えた 4 つすべて）。手順: `--settings` に渡す JSON ファイルの `enabledPlugins` で、それらの plugin を false にする。Remote Control を切る設定（`remoteControlAtStartup` を false）と同じファイルにしてよい。ファイルは plugin の名前を含むので、repo には置かず、repo の外の作業用フォルダに置く。確認: OTel の `plugin_loaded` にそれらの plugin が出ないこと、`hook_registered` が probe の作業フォルダの hook だけになること（[1-8 §8.3.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)）。対象: Claude が起動する計測用のセッション（probe と Phase 3 の比較実験）。日常のセッション（J-19）は対象外で、無効にせず、plugin の構成を記録する（hook の行の (3)〜(4)）
- 「判定の目安」は、手順書の作成担当が基準を独自に決めずに済むよう、Claude が置いた案である（v0.4。クロスレビュー 実用 I3）。Phase 2 の設計で変わり得る。合否を置かず値を記録するだけの項目は「記録のみ」と書いた
- 起こし方を決めていない項目（R6 の block・ask、R12 の `classifier_category`、plugin の hook の受け渡しの失敗、`error.type`、`retention_sweep` など日常利用の中で観測する項目。v0.14 で追加）は、Phase 3 の期間内に観測できなければ、「未観測（起こらなかった条件）」と記録して閉じてよい。閉じた項目は Phase 3 の完了判定に残さず、日常利用で後に観測できたときに追記する
- hook の待ち時間の基準（タグ案 L1 から L2、または ① だけへの切替の基準）は作業指示者の判断事項で、暫定値を [作業指示者裁定待ち事項](../作業指示者裁定待ち事項.md) J-12 に記録した
