## 0. サマリ

- **調査内容**: 1-1 の実測で受信した api_request イベント 38 件を、同じセッションの transcript と `request_id` で突き合わせた。経路 (ii)（応答ボディ）は、計画書 §7 #2 の判断待ちのため実施していない
- **調査結果**
  - メインスレッドは、transcript が残っていた 19 件すべてで突合でき、トークン数が一致し、`thinking_tokens` があった。内訳は `-p` 実行 18 件、対話モード 1 件（対話モードの残り 2 件は transcript が作られていなかった）（[§3.1](#sec-3-1)）
  - サブエージェントは 9 件すべて突合できたが、3 件は transcript の usage が未確定のままで、思考トークンを取れなかった（[§3.2](#sec-3-2)）
  - compact・タイトル生成などの補助リクエスト 8 件は transcript に記録されない（[§3.1](#sec-3-1)）
  - `thinking_tokens ≤ output_tokens` は値がある 25 件すべてで成立し、思考分が `output_tokens` に含まれることと矛盾しない（[§3.3](#sec-3-3)）
- **結論・示唆**: 本環境では経路 (i) を主線にできる（職場環境の Bedrock 経由では突合の鍵が欠ける可能性がある。[§5](#sec-5)）。サブエージェントの欠損の大きさと `output_tokens` の内訳の確定には V-2b が要るため、`OTEL_LOG_RAW_API_BODIES` を短期間だけ有効にすることを提案する（[§5](#sec-5)）

## 1. 目的と方法

計画書 §2.1 の経路 (i)（transcript 突合）と (ii)（応答ボディ）がどの程度成り立つかを確かめ、どちらを主にするかの判断材料をそろえる。

- (i): 1-1 の実測で受信した api_request イベント（38 件）と、同じセッションの transcript（`~/.claude/projects/<フォルダ>/<session>.jsonl` と `<session>/subagents/agent-<id>.jsonl`）を、`request_id` と `requestId` で突き合わせた
- (ii): `OTEL_LOG_RAW_API_BODIES` の有効化は、計画書 §7 #2 の判断が必要なため実施していない

<a id="sec-3"></a>
## 3. 経路 (i) transcript 突合の詳細

<a id="sec-3-1"></a>
### 3.1 突合率（query_source 別）

| query_source | OTel の件数 | 突合できた件数 | 出力トークンが一致 | `thinking_tokens` あり |
|---|---|---|---|---|
| `sdk`（`-p` のメイン） | 18 | 18 | 18 | 18 |
| `repl_main_thread`（対話モードのメイン） | 3 | 1 | 1 | 1 |
| `agent:builtin:general-purpose` | 5 | 5 | 3 | 3 |
| `agent:custom` | 4 | 4 | 3 | 3 |
| `compact` | 1 | 0 | — | — |
| `generate_session_title` | 6 | 0 | — | — |
| `prompt_suggestion` | 1 | 0 | — | — |

- `repl_main_thread` の未突合 2 件は、Claude が 35 秒後に強制終了した対話セッション（[1-1](../01.実データ確認/調査報告書.md#sec-1) の i3 / i4）のもの。**この 2 セッションは transcript ファイル自体が作られていなかった**。正常に終了した対話セッション（i5）は突合できた。原因は確定していない（2 セッションでの観測）。1 リクエストが複数行に分けて書かれること（3.2）から、書き出しはセッション終了時の一括ではない可能性もある。日常の対話モードでの突合率は Phase 3 で確認する
- 入力系トークン（input / cache_read / cache_creation）は、突合できた 28 件すべてで一致した

<a id="sec-3-2"></a>
### 3.2 transcript の記録形式で注意する点

- **1 リクエストが複数行になる**: 応答の content block ごとに assistant 行が書かれ、同じ `requestId` が複数行に現れる（1-6 の過去分の集計では約 80% の行が重複）
- **最終行だけが確定値**: 先頭の行の `output_tokens` は途中の値で、`thinking_tokens` を持たない。確定した usage は、同じ `requestId` の最後の行にある。突合では最後の行を使う必要がある
- **サブエージェントでは最終行も未確定のことがある**: サブエージェントの 9 件中 3 件で、最後の行の usage が途中の値のままだった。いずれもツール呼び出し（Bash、サブエージェントの結果返却）で終わるリクエストだった。この 3 件の OTel 側の `output_tokens` は 53〜455 で、transcript 側（1〜5）と大きく異なる

<a id="sec-3-3"></a>
### 3.3 `output_tokens` に思考分が含まれるか（V-2a）

- 値がある全件で `thinking_tokens ≤ output_tokens` が成り立つ
- 応答の本文がごく短いリクエストで、`output_tokens` と `thinking_tokens` の差が本文の長さ程度になっている（例: Haiku が「OK」とだけ答えたリクエストで、`output_tokens=149`、`thinking_tokens=143`）
- OTel の `output_tokens` と transcript の `output_tokens` は、確定値どうしでは一致する

以上から、「OTel の `output_tokens` は思考トークンを含む」ことと矛盾しない。確定には V-2b（生の応答の usage の確認）が要る。

<a id="sec-3-4"></a>
### 3.4 過去分の扱い（1-6 の結果から）

- `thinking_tokens` は cc 2.1.237 以降の transcript にしか無い。同じバージョン内でも 60〜78% の行にしか無い（先頭行が途中の値であることによる。3.2）
- transcript は既定 30 日で削除される。過去分から思考トークンを復元できる範囲は限られる

<a id="sec-4"></a>
## 4. 経路 (ii) 応答ボディ

未実施（計画書 §7 #2 の判断待ち）。3 章の結果から、(ii) で補える可能性があるのは次の範囲に限られる。

- 経路 (i) で取れない補助リクエスト（compact 等）と、サブエージェントの usage が未確定のリクエスト
- docs によれば、file モード（`OTEL_LOG_RAW_API_BODIES=file:<dir>`）の `index.jsonl` には `query_source` と `request_id` があるため、突合はできる見込み

一方で、(ii) には次の懸念がある（計画書 §2.1）。

- 会話履歴全体がディスクに残る
- 保存量が大きい
- 過去のターンの思考本文が伏せられる

<a id="sec-5"></a>
## 5. 判断材料（計画書 §7 #2 と経路の選択）

記号 T1〜T3 は思考トークンの経路の組み合わせを表す（v0.3 で「案 A〜C」から改名。受信・保存の候補 (A)(B)(C) とは無関係）。「取れる範囲」は本環境（Anthropic 直接契約）の実測に基づく。

| 思考案 | 内容 | 思考トークンを取れる範囲 | 懸念 |
|---|---|---|---|
| T1. (i) のみ | transcript の最終行を突合する | 本環境では、メインスレッドのほぼ全件（`-p` 18 件・対話モード 1 件で確認）、サブエージェントの約 2/3。compact・タイトル生成等は取れない | 取れない分の扱い（「不明」として集計する等）を Phase 2 で決める。職場環境（Bedrock 経由）では transcript の `requestId` が欠ける可能性がある（[1-6 §3.7](../06.ローカルファイル棚卸し/調査報告書.md#sec-3-7)）。欠ける場合、職場環境では思考トークンを突合できない |
| T2. (i) を主、(ii) を補助 | (i) で取れないリクエストだけ応答ボディで補う | ほぼ全件の見込み | 補助のためだけに全リクエストのボディが保存される（フラグは全リクエストに効く）。§7 #2 の判断が要る |
| T3. (ii) を主 | 応答ボディの usage を使う | ほぼ全件の見込み | T2 と同じ懸念に加え、transcript の取込を思考トークンの目的では使わなくなる |

- 分析の主眼は、作業分類 × モデル × effort ごとの思考トークン比率である。取れない分の大半は補助リクエスト（compact・タイトル生成）で、作業分類ごとの比率への影響は小さい見込み
- サブエージェントの約 1/3 が取れないことは、問い②（サブエージェントへの移譲）の分析に影響し得る。V-2b を実施すれば、影響の大きさ（取れない分の思考トークン量）を見積もれる

**Claude の所見**: T1 を主線にし、V-2b だけは短期間に限って (ii) を有効にして実施するのが妥当と考える。V-2b では次の 2 点を見る。

- `output_tokens` に思考分が含まれることの確定
- サブエージェントの未確定分で、思考トークンがどの程度欠けるか

T2 に進むかは、その結果を見て決める。判断は作業指示者に委ねる（§7 #2）。`OTEL_LOG_RAW_API_BODIES` の短期有効化が承認されない場合は、T1 のまま進め、サブエージェントの未確定分と補助リクエストの思考トークンを「不明」として集計する（[§6](#sec-6)）。

**最強の反論と残存リスク**

- 反論: サブエージェントの未確定 3 件（9 件中）はサンプルが小さい。実運用での欠損率は大きく異なり得るので、T1 で足りるとは言えない
  - この反論は現時点で棄却できない（残存リスク）
  - V-2b でサブエージェントを含む複数のリクエストを流し、欠損する思考トークンの量を測る。その結果で T1 / T2 を決める
- 反論: T1 の評価は本環境の実測だけに基づく。1-6 は、本環境の記録に混在する Bedrock 形式のモデル ID の行（2,063 件）で `requestId` が全件欠けていたと報告している。職場環境で同じなら、職場環境では T1 が成り立たない
  - この反論は現時点で棄却できない（残存リスク）
  - Phase 3 の職場環境確認で、transcript に `requestId` が残るかを確かめる。残らない場合の扱い（T2 に進む、別の鍵を探す、職場環境の思考トークンは「不明」とする）は計画書 §7 #8 と合わせて判断する

<a id="sec-6"></a>
## 6. Phase 2 への示唆

- 取込では、同じ `requestId` の最後の行を採る。サブエージェントでは、最後の行の `output_tokens` が OTel と一致しない場合は「未確定」として扱い、思考トークンを「不明」とする
- 異常終了したセッションでは transcript が残らない場合がある（2 セッションで観測。原因は未確定）。取込は、終了したセッションを対象にするのが安全である
- 補助リクエスト（`compact`・`generate_session_title`・`prompt_suggestion`）の思考トークンは、(i) では「不明」とする
- 突合は次の鍵で行う
  - メイン: セッションごとの transcript ファイル
  - サブエージェント: `subagents/agent-<id>.jsonl`（trace の `agent_id` と一致。[1-1 §6](../01.実データ確認/調査報告書.md#sec-6)）
