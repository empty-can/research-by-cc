<a id="sec-3-2"></a>
### 3.2 transcript の記録形式で注意する点

- **1 リクエストが複数行になる**: 応答の content block ごとに assistant 行が書かれ、同じ `requestId` が複数行に現れる（1-6 の過去分の集計では約 80% の行が重複）
- **最終行だけが確定値**: 先頭の行の `output_tokens` は途中の値で、`thinking_tokens` を持たない。確定した usage は、同じ `requestId` の最後の行にある。突合では最後の行を使う必要がある
- **サブエージェントでは最終行も未確定のことがある**: サブエージェントの 9 件中 3 件で、最後の行の usage が途中の値のままだった。いずれもツール呼び出し（Bash、サブエージェントの結果返却）で終わるリクエストだった。この 3 件の OTel 側の `output_tokens` は 53〜455 で、transcript 側（1〜5）と大きく異なる
- **件数がずれる新しい要因（2.1.288 以降）**: 応答の途中で API がタイムアウトしたとき、非対話セッション（`-p`・SDK）とサブエージェントは、届いた部分応答から続行する。thinking だけで終わった応答は再試行する（changelog 2.1.288）。このため `api_request` と transcript の件数が一致しなくなりうる。再試行が `api_request` にどう出るか（`attempt` 等）は未確認で、長い対話の突合で確かめる（Phase 3）。`attempt` は docs 2.1.296 で、streaming の失敗の後に Claude Code がリクエストを出し直すたびに 1 から数え直す定義になった。そのため、`attempt` が 1 でも出し直しが無かったとは言えない（2026-10-19 追記。[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) D31）。changelog 2.1.288 は、直前の応答が usage 0 のときの不具合も直しており、usage が 0 の応答が存在することが分かる。transcript での記録の形は未確認である。この項は docs・changelog に基づく。2.1.296 の `-p` 実行でも未突合は compact の 1 件だけだった（[§3.1](#sec-3-1)）が、タイムアウト時の挙動は実測していない

<a id="sec-3-3"></a>
### 3.3 `output_tokens` に思考分が含まれるか（V-2a）

- 値がある全件で `thinking_tokens ≤ output_tokens` が成り立つ
- 応答の本文がごく短いリクエストで、`output_tokens` と `thinking_tokens` の差が本文の長さ程度になっている（例: Haiku 4.5 が「OK」とだけ答えたリクエストで、`output_tokens=149`、`thinking_tokens=143`）
- OTel の `output_tokens` と transcript の `output_tokens` は、確定値どうしでは一致する

以上から、「OTel の `output_tokens` は思考トークンを含む」ことと矛盾しない。確定には V-2b（生の応答の usage の確認）が要る。

<a id="sec-3-4"></a>
### 3.4 過去分の扱い（1-6 の結果から）

- `thinking_tokens` は cc 2.1.237 以降の transcript にしか無い。同じバージョン内でも 60〜78% の行にしか無い（先頭行が途中の値であることによる。3.2）

<a id="sec-3-5"></a>
### 3.5 cc 2.1.300 以降の transcript の変更（2026-10-17 追記。cc 2.1.302）

changelog と 2.1.302 の実機（2026-10-17）に基づく。詳細は [1-8 §8](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-4)。

- **新しい記録型**: 2.1.300 から、API リクエストごとの system prompt・tools・parameters が transcript に記録される（changelog 2.1.300）。実機では、新しい記録型 `api-request`（リクエスト 1 件ごとの記録。parameters と、下の 2 つへの参照）・`api-request-shape`（system prompt と tools の全文）・`api-request-blob`（メッセージ本文の実体）が加わり、assistant の行に `requestRef`、user の行に `toolDenialKind` が加わった。同じ `shapeHash` の `api-request-shape` は、セッションの中で 1 回だけ書かれる。既存の記録型は残り、削除は無かった
- **突合のキー**: assistant の `requestId` は変わらない。`requestRef` は新しい `api-request` との対応を示す追加のキーで、`request_id` の突合には使わない
- **サイズ**: 短い `-p` の run では、transcript のファイルが 1 ファイルあたり約 95〜180 KB 増え、2.1.296 の約 1.5〜2 倍になった（1-8 §8.3.4）。長いセッションでは `api-request-shape` の重複排除が効くので、リクエスト数に比例して増えるとは限らない（未確認）
- **機微性**: system prompt には、ユーザの指示ファイル等の内容が含まれうる【推定】。transcript を取り込み・保存・共有するときの扱いが、2.1.296 より重くなる（[1-6](../06.ローカルファイル棚卸し/調査報告書.md) も参照）
- **応答の記録ではない**: 新しく記録されるのは API リクエストの側（system prompt・tools・parameters）で、応答の usage ではない。思考トークンは従来どおり assistant の行の usage から取るので、経路 (ii)（応答ボディ）の代わりにはならない
- **周辺の修正**: 2.1.299 で、@ で指した PDF の bytes が transcript に残らなくなった。2.1.300 で、resume と compaction 周りの記録が欠ける不具合が直った（クラッシュで途切れた最終行の直後の記録が失われる、`-p`・SDK の resume で直近のメッセージと compaction の要約が失われる）（changelog 2.1.299・2.1.300）。本書の突合は resume を使わない
- **cache creation**: 2.1.300 から OTel の `api_request` に `cache_creation_5m_tokens`・`cache_creation_1h_tokens` が付く。突合で一致を確かめているのは従来の合算の値で、transcript の usage 側に同じ内訳があるかは確かめていない

（2026-10-17 追記。cc 2.1.300 以降）api.anthropic.com への大きいリクエストは、テレメトリを切っていても gzip で送られる（`CLAUDE_CODE_GZIP_REQUEST_BODIES=0` で止める。changelog 2.1.300）。proxy で raw body を取る経路を選ぶ場合は、展開が要る【推定】。`OTEL_LOG_RAW_API_BODIES` には関係しない【推定】。LLM ゲートウェイ環境の要求は `ANTHROPIC_BASE_URL` の社内のゲートウェイ宛てなので、「api.anthropic.com 宛て」の記述は当たらない（2026-10-18 に改めた。J-26）。この経路は実測していない。

## 5. 判断材料（計画書 §7 #2 と経路の選択）

記号 T1〜T3 は思考トークンの経路の組み合わせを表す（v0.3 で「案 A〜C」から改名。受信・保存の候補 (A)(B)(C) とは無関係）。「取れる範囲」は本環境（Anthropic 直接契約）の実測に基づく。

| 思考案 | 内容 | 思考トークンを取れる範囲 | 懸念 |
|---|---|---|---|
| T1. (i) のみ | transcript の最終行を突合する | 本環境では、メインスレッドのほぼ全件（`-p` 18 件・対話モード 1 件で確認）、サブエージェントの約 2/3。compact・タイトル生成等は取れない | 取れない分の扱い（「不明」として集計する等）を Phase 2 で決める。LLM ゲートウェイ環境で transcript に `requestId` が残るかは不明である。docs では、transcript の `requestId` は OTel の `request_id` と同じ値で、取得元（応答の `request-id` か `x-amzn-requestid` のヘッダ）も同じなので、ゲートウェイがどちらのヘッダを返すかで決まる。Phase 3 で確かめる（2026-10-18 に改めた。J-26。本環境に混ざっていた Bedrock 形式の行の観測は [1-6 §3.7](../06.ローカルファイル棚卸し/調査報告書.md#sec-3-7)）。欠ける場合、LLM ゲートウェイ環境では思考トークンを突合できない |
| T2. (i) を主、(ii) を補助 | (i) で取れないリクエストだけ応答ボディで補う | ほぼ全件の見込み | 補助のためだけに全リクエストのボディが保存される（フラグは全リクエストに効く）。§7 #2 の判断が要る |
| T3. (ii) を主 | 応答ボディの usage を使う | ほぼ全件の見込み | T2 と同じ懸念に加え、transcript の取込を思考トークンの目的では使わなくなる |

- 上の表の「取れる範囲」は cc 2.1.283・2.1.287 の実測に基づく。2.1.296・2.1.302 の `-p` 実測（[§3.1](#sec-3-1)）でも、メインスレッドは全件取れ、compact は取れず、サブエージェントに確定前の usage が残る例があり、範囲は変わらない（2026-10-17 追記）
- 分析の主眼は、作業分類 × モデル × effort ごとの思考トークン比率である。取れない分の大半は補助リクエスト（compact・タイトル生成）で、作業分類ごとの比率への影響は小さい見込み
- サブエージェントの約 1/3 が取れないことは、問い②（サブエージェントへの移譲）の分析に影響し得る。V-2b を実施すれば、影響の大きさ（取れない分の思考トークン量）を見積もれる
- GenAI semconv には思考トークンの属性 `gen_ai.usage.reasoning.output_tokens` があるが、cc は OTel ではこの値を出さない。そのため T1 の経路（transcript の突合）は変わらない（[1-7 §7.2](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-7-2)）
- Claude Mods の usage にも思考トークンの項目は無く（docs 2026-10-19 取得版）、Mod は経路 (i)・(ii) のどちらの代わりにもならない（【推定】。2026-10-19 追記。詳細は [§6](#sec-6)）

**Claude の所見**: T1 を主線にし、V-2b だけは短期間に限って (ii) を有効にして実施するのが妥当と考える。V-2b では次の 2 点を見る。

- `output_tokens` に思考分が含まれることの確定
- サブエージェントの未確定分で、思考トークンがどの程度欠けるか

cc 2.1.302 でもこの所見は変わらない（2026-10-17 追記）。2.1.300 から transcript に API リクエストの system prompt・tools・parameters が記録されるようになったが（[§3.5](#sec-3-5)）、記録されるのはリクエストの側で応答ではない。経路 (i) で取れない補助リクエストや、サブエージェントの未確定分の思考トークンは、transcript の新しい記録では補えない。そのため T1 の範囲も、T2 が補う範囲も変わらず、推奨も変えない。変わるのは、取込が読む transcript のサイズと機微性である（[§6](#sec-6)）。

T2 に進むかは、その結果を見て決める。判断は作業指示者に委ねる（§7 #2）。`OTEL_LOG_RAW_API_BODIES` の短期有効化が承認されない場合は、T1 のまま進め、サブエージェントの未確定分と補助リクエストの思考トークンを「不明」として集計する（[§6](#sec-6)）。

**最強の反論と残存リスク**

- 反論: サブエージェントの未確定 3 件（9 件中）はサンプルが小さい。実運用での欠損率は大きく異なり得るので、T1 で足りるとは言えない
  - この反論は現時点で棄却できない（残存リスク）
  - V-2b でサブエージェントを含む複数のリクエストを流し、欠損する思考トークンの量を測る。その結果で T1 / T2 を決める
- 反論: T1 の評価は本環境の実測だけに基づく。1-6 は、本環境の記録に混在する Bedrock 形式のモデル ID の行（2,063 件）で `requestId` が全件欠けていたと報告している。職場の cc は `ANTHROPIC_BASE_URL` で社内のゲートウェイにつなぎ、cc の Bedrock モードを使わないので、この行が LLM ゲートウェイ環境の transcript と同じ形かは分からない。LLM ゲートウェイ環境で `requestId` が残らなければ、そこでは T1 が成り立たない（2026-10-18 に改めた。J-26）
  - この反論は現時点で棄却できない（残存リスク）
  - Phase 3 の職場環境確認で、transcript に `requestId` が残るかを、OTel の `api_request` に `request_id` が付くかと合わせて確かめる（同じ値で、取得元も同じ。docs。2026-10-18 に改めた。J-26）。残らない場合の扱い（T2 に進む、別の鍵を探す、LLM ゲートウェイ環境の思考トークンは「不明」とする）は計画書 §7 #8 と合わせて判断する

## 6. Phase 2 への示唆

- 取込では、同じ `requestId` の最後の行を採る。サブエージェントでは、最後の行の `output_tokens` が OTel と一致しない場合は「未確定」として扱い、思考トークンを「不明」とする
- 異常終了したセッションでは transcript が残らない場合がある。強制終了した対話セッションでは、観測した 2.1.283・2.1.287・2.1.296 のどの版でも transcript が作られなかった（原因は未確定。2.1.302 では確かめていない。[§3.1](#sec-3-1)。2026-10-19 に改めた）。取込は、終了したセッションを対象にするのが安全である
- 補助リクエスト（`compact`・`generate_session_title`・`prompt_suggestion`）の思考トークンは、(i) では「不明」とする
- `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC=1`（2.1.287、opt-in）は設定しない。`-p`／SDK のセッションで transcript が 5 MB を超えると、compaction のたびにそれ以前の履歴を削るので、T1 の突合の前提（`request_id` ごとの最終行が transcript に残ること）を壊す。起動する環境の環境変数で設定するもので、settings の `env` では有効にならない（docs）
- 2.1.288〜2.1.290 の transcript は、終了時にセッションの最後のメッセージが失われうる回帰があった（2.1.291 で修正）。この版で作られた transcript と突合するときは、末尾のリクエストが欠けうる
- Haiku 5.5 は思考を off にできない（常時 adaptive。docs 2.1.295）。2.1.293 以降、Anthropic API では `haiku` がこのモデルに解決するので、`haiku` で probe するときは、思考トークンが出る前提で見る。本書の実測のうち `haiku` で動かした分は Haiku 4.5 のものなので、比べるときはモデルを明記する
- advisor など API 側で実行された tool call は、Mod の `turn.step` の `result.serverToolUses`（2.1.290）に、id・name・input・開始・終了つきで出る。`tool.call`／`tool.check` の hook は発火しない。advisor の呼び出しが OTel と transcript でどう見えるかは未確認である。advisor の呼び出しを分けて見たくなった場合の経路の候補で、必要になったときだけ検討する
- Claude Mods の活用余地（2026-10-19 追記。docs 2026-10-19 取得版の Mods の events・reference・API・test のページ）: 思考トークンについては無い
  - `turn.step` の結果の `result.usage` に docs が挙げる項目は、Claude API が報告するトークン数 4 種（`input_tokens`・`output_tokens`・`cache_read_input_tokens`・`cache_creation_input_tokens`）と、答えた `model` で、思考トークンの項目は無い。`$.model.complete` の usage の例（test のページ）も 4 種だけである。`turn.complete` の `e.usage` は turn のトークン合計である。思考分が `output_tokens` に入っているかは、Mods の docs では決まらない
  - `turn.step` の stream の各片は `{ kind, index, text }` の形で、docs の例は `kind: 'text'` だけである。思考の片が stream に流れるかは docs に無い
  - `$.session.messages()` は transcript を `{ role, text, toolUses }` の配列で返し、最新の 4,096 件までである。usage・`requestId`・思考は項目に無い（transcript の取込の観点は [1-6 §6](../06.ローカルファイル棚卸し/調査報告書.md#sec-6)）
  - `session.append` は、会話が保存する行（プロンプト、応答の block、tool の結果、通知）ごとに、保存の前に発火する。changelog 2.1.295 に、実際のセッションが残す thinking block を消す `session.append` hook が `claude plugin test` で通っていた不具合の修正があり、行に thinking block が入りうる。行に usage があるかは docs では決まらない
  - 【推定】以上から、Mod は経路 (i)（transcript 突合）の代わりにも、経路 (ii)（応答ボディ）の代わりにもならない。Mod の usage の 4 種は、OTel の `api_request` にすでにある値と同じ種類である。そのため、[§5](#sec-5) の T1〜T3 に Mod の経路は足していない
- cc 2.1.300 以降の transcript（2026-10-17 追記。[§3.5](#sec-3-5)）についての Phase 2 への申し送り。設計は Phase 2 で決める
  - 2.1.302 の実機では、思考トークンの突合に必要なのは assistant の行の `requestId` と usage で、新しい記録型は不要だった。取込がこれらの記録型を読むかは、Phase 2 で判断する
  - system prompt と tools の全文は、ユーザの指示ファイル等の内容を含みうる【推定】。取込先に持ち込むかは、機微性とサイズを見て Phase 2 で判断する
  - 記録の形は 2.1.300 で変わった。取込が未知の記録型に遭遇したときの扱いも、Phase 2 の設計項目である
- 突合は次の鍵で行う
  - メイン: セッションごとの transcript ファイル
  - サブエージェント: `subagents/agent-<id>.jsonl`（trace の `agent_id` と一致。[1-1 §6](../01.実データ確認/調査報告書.md#sec-6)）。2.1.300 以降は、span の `gen_ai.conversation.id` も、メインの span では `session.id`、サブエージェントの span では `agent_id` と同じ値になる（2.1.302 の実機。2026-10-19 追記。[1-8 §8.3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-1)）
  - fork subagent（2026-10-19 追記。[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) D50・[§8.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-5)）: cc 2.1.302 から、`-p` でも fork subagent が既定で有効になった。サブエージェントを使う `-p` の実行では、span と `api_request` の形が変わりうる。fork を使う実行でのサブエージェントの突合は確かめていない
