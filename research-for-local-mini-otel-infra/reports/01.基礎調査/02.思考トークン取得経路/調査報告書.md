### 3.2 transcript の記録形式で注意する点

- **1 リクエストが複数行になる**: 応答の content block ごとに assistant 行が書かれ、同じ `requestId` が複数行に現れる（1-6 の過去分の集計では約 80% の行が重複）
- **最終行だけが確定値**: 先頭の行の `output_tokens` は途中の値で、`thinking_tokens` を持たない。確定した usage は、同じ `requestId` の最後の行にある。突合では最後の行を使う必要がある
- **サブエージェントでは最終行も未確定のことがある**: サブエージェントの 9 件中 3 件で、最後の行の usage が途中の値のままだった。いずれもツール呼び出し（Bash、サブエージェントの結果返却）で終わるリクエストだった。この 3 件の OTel 側の `output_tokens` は 53〜455 で、transcript 側（1〜5）と大きく異なる
  - 2026-10-23 追記: この現象は、changelog 2.1.307 で直った不具合（サブエージェントの transcript が、streaming の応答で usage を仮の値、stop reason を空で記録していた）に当たる【推定】。cc 2.1.309 の `-p` 実機では、同じ種類（ツール呼び出しで終わる）のサブエージェントのリクエスト 6 件すべてで、最後の行の usage が OTel と一致し、`stop_reason` も空でなかった（2.1.302 は同じ方法で 4 件中 2 件が未確定。[1-9 §3.4](../09.cc2.1.304差分の確認/調査報告書.md#sec-3-4)、D57）。2.1.309 で確かめたのはカスタムサブエージェントだけだった。組み込みの general-purpose・fork subagent・対話は、V-2b（cc 2.1.316・2.1.317）で確かめ、未確定の usage は無かった（[§4.1](#sec-4-1)）。2.1.306 以前に記録した transcript では残りうる
- **件数がずれる新しい要因（2.1.288 以降）**: 応答の途中で API がタイムアウトしたとき、非対話セッション（`-p`・SDK）とサブエージェントは、届いた部分応答から続行する。thinking だけで終わった応答は再試行する（changelog 2.1.288）。このため `api_request` と transcript の件数が一致しなくなりうる。再試行が `api_request` にどう出るか（`attempt` 等）は未確認で、長い対話の突合で確かめる（Phase 3）。`attempt` は docs 2.1.296 で、streaming の失敗の後に Claude Code がリクエストを出し直すたびに 1 から数え直す定義になった。そのため、`attempt` が 1 でも出し直しが無かったとは言えない（2026-10-19 追記。[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) D31）。changelog 2.1.288 は、直前の応答が usage 0 のときの不具合も直しており、usage が 0 の応答が存在することが分かる。transcript での記録の形は未確認である。この項は docs・changelog に基づく。2.1.296 の `-p` 実行でも未突合は compact の 1 件だけだった（[§3.1](#sec-3-1)）が、タイムアウト時の挙動は実測していない

<a id="sec-3-3"></a>
### 3.3 `output_tokens` に思考分が含まれるか（V-2a）

- 値がある全件で `thinking_tokens ≤ output_tokens` が成り立つ
- 応答の本文がごく短いリクエストで、`output_tokens` と `thinking_tokens` の差が本文の長さ程度になっている（例: Haiku 4.5 が「OK」とだけ答えたリクエストで、`output_tokens=149`、`thinking_tokens=143`）
- OTel の `output_tokens` と transcript の `output_tokens` は、確定値どうしでは一致する

以上から、「OTel の `output_tokens` は思考トークンを含む」ことと矛盾しない。V-2b（生の応答の usage の確認）で、含まれることを確かめた。根拠は、API の応答そのものが、思考トークンの数を `output_tokens` の内訳（`usage.output_tokens_details.thinking_tokens`）として返すことである。レスポンスボディのある 902 リクエストすべてで `thinking_tokens` は `output_tokens` 以下で、OTel と比べられる 900 件すべてで、ボディの `output_tokens` は OTel の `output_tokens` と一致した（[§4.1](#sec-4-1)）。

### 3.5 cc 2.1.300 以降の transcript の変更（2026-10-17 追記。cc 2.1.302）

changelog と 2.1.302 の実機（2026-10-17）に基づく。詳細は [1-8 §8](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-4)。2026-10-23 追記の部分は、changelog 2.1.304〜2.1.309 と 2.1.309 の実機による。

- **新しい記録型**: 2.1.300 から、API リクエストごとの system prompt・tools・parameters が transcript に記録される（changelog 2.1.300）。実機では、新しい記録型 `api-request`（リクエスト 1 件ごとの記録。parameters と、下の 2 つへの参照）・`api-request-shape`（system prompt と tools の全文）・`api-request-blob`（メッセージ本文の実体）が加わり、assistant の行に `requestRef`、user の行に `toolDenialKind` が加わった。同じ `shapeHash` の `api-request-shape` は、セッションの中で 1 回だけ書かれる。既存の記録型は残り、削除は無かった。2.1.309 の実機では、記録型の集合は同じで、`user` の記録（Bash のツール結果を持つもの）に `sandboxed`（boolean）のキーが加わった（changelog に記載は無い。2026-10-23 追記）
- **突合のキー**: assistant の `requestId` は変わらない。`requestRef` は新しい `api-request` との対応を示す追加のキーで、`request_id` の突合には使わない
- **サイズ**: 短い `-p` の run では、transcript のファイルが 1 ファイルあたり約 95〜180 KB 増え、2.1.296 の約 1.5〜2 倍になった（1-8 §8.3.4）。長いセッションでは `api-request-shape` の重複排除が効くので、リクエスト数に比例して増えるとは限らない（未確認）。2026-10-23 追記: 2.1.304 で、auto mode の安全の分類器の context をリクエストごとに保存しなくなった（changelog）。2.1.309 の実機では、auto mode の `api-request` の記録から `params.safeguards` のキーが消え、1 件あたり約 6 KB から約 1.6 KB になった（changelog のこの項目に当たるかは【推定】）。ただし attachment が増え、短い `-p` の run の 1 ファイルあたりの大きさはほぼ同じか少し大きかった。長い auto mode のセッションでは、リクエスト数に比例して小さくなる方向に効く【推定】（[1-9 §3.3](../09.cc2.1.304差分の確認/調査報告書.md#sec-3-3)、D58）
- **機微性**: system prompt には、ユーザの指示ファイル等の内容が含まれうる【推定】。transcript を取り込み・保存・共有するときの扱いが、2.1.296 より重くなる（[1-6](../06.ローカルファイル棚卸し/調査報告書.md) も参照）
- **応答の記録ではない**: 新しく記録されるのは API リクエストの側（system prompt・tools・parameters）で、応答の usage ではない。思考トークンは従来どおり assistant の行の usage から取るので、経路 (ii)（応答ボディ）の代わりにはならない
- **周辺の修正**: 2.1.299 で、@ で指した PDF の bytes が transcript に残らなくなった。2.1.300 で、resume と compaction 周りの記録が欠ける不具合が直った（クラッシュで途切れた最終行の直後の記録が失われる、`-p`・SDK の resume で直近のメッセージと compaction の要約が失われる）（changelog 2.1.299・2.1.300）。本書の突合は resume を使わない
- **cache creation**: 2.1.300 から OTel の `api_request` に `cache_creation_5m_tokens`・`cache_creation_1h_tokens` が付く。突合で一致を確かめているのは従来の合算の値で、transcript の usage 側に同じ内訳があるかは確かめていない

## 5. 判断材料（計画書 §7 #2 と経路の選択）

記号 T1〜T3 は思考トークンの経路の組み合わせを表す（v0.3 で「案 A〜C」から改名。受信・保存の候補 (A)(B)(C) とは無関係）。「取れる範囲」は本環境（Anthropic 直接契約）の実測に基づく。

| 思考案 | 内容 | 思考トークンを取れる範囲 | 懸念 |
|---|---|---|---|
| T1. (i) のみ | transcript の最終行を突合する | 本環境では、メインスレッドのほぼ全件（`-p` 18 件・対話モード 1 件で確認）、サブエージェントの約 2/3。compact・タイトル生成等は取れない | 取れない分の扱い（「不明」として集計する等）を Phase 2 で決める。LLM ゲートウェイ環境で transcript に `requestId` が残るかは不明である。docs では、transcript の `requestId` は OTel の `request_id` と同じ値で、取得元（応答の `request-id` か `x-amzn-requestid` のヘッダ）も同じなので、ゲートウェイがどちらのヘッダを返すかで決まる。Phase 3 で確かめる（2026-10-18 に改めた。J-26。本環境に混ざっていた Bedrock 形式の行の観測は [1-6 §3.7](../06.ローカルファイル棚卸し/調査報告書.md#sec-3-7)）。欠ける場合、LLM ゲートウェイ環境では思考トークンを突合できない |
| T2. (i) を主、(ii) を補助 | (i) で取れないリクエストだけ応答ボディで補う | ほぼ全件の見込み | 補助のためだけに全リクエストのボディが保存される（フラグは全リクエストに効く）。§7 #2 の判断が要る |
| T3. (ii) を主 | 応答ボディの usage を使う | ほぼ全件の見込み | T2 と同じ懸念に加え、transcript の取込を思考トークンの目的では使わなくなる |

- 上の表の「取れる範囲」は cc 2.1.283・2.1.287 の実測に基づく。2.1.296・2.1.302 の `-p` 実測（[§3.1](#sec-3-1)）でも、メインスレッドは全件取れ、compact は取れず、サブエージェントに確定前の usage が残る例があり、範囲は変わらない（2026-10-17 追記）
- サブエージェントの「約 2/3」は、2.1.306 以前に記録した transcript での評価として読む。未確定の usage は 2.1.307 で直った不具合に当たる【推定】（[§3.2](#sec-3-2)）。V-2b（cc 2.1.316・2.1.317）では、元の 9 件のうち 5 件を占めた組み込みの general-purpose を含め、fork subagent・対話・background のサブエージェント 448 件すべてが取れた（[§4.1](#sec-4-1)）。表の評価を変えないのは、2.1.306 以前に記録した transcript と、確かめていない長いセッション・自動 compact が残るためである
- 分析の主眼は、作業分類 × モデル × effort ごとの思考トークン比率である。取れない分の大半は補助リクエスト（compact・タイトル生成）で、作業分類ごとの比率への影響は小さい見込み

**Claude の所見**: T1 を主線にするのが妥当と考える。V-2b は、短期間に限って (ii) を有効にして行った。見たのは次の 2 点である。

- `output_tokens` に思考分が含まれることの確定
- サブエージェントの未確定分で、思考トークンがどの程度欠けるか

cc 2.1.302 でもこの所見は変わらない（2026-10-17 追記）。2.1.300 から transcript に API リクエストの system prompt・tools・parameters が記録されるようになったが（[§3.5](#sec-3-5)）、記録されるのはリクエストの側で応答ではない。経路 (i) で取れない補助リクエストや、サブエージェントの未確定分の思考トークンは、transcript の新しい記録では補えない。そのため T1 の範囲も、T2 が補う範囲も変わらず、推奨も変えない。変わるのは、取込が読む transcript のサイズと機微性である（[§6](#sec-6)）。

V-2b を行った（[§4.1](#sec-4-1)）。1 点目は確かめた。2 点目は、903 リクエスト（cc 2.1.316 の 309 件、2.1.317 の 594 件）のうち、transcript の usage で取れなかったのが 115 件で、すべて補助のリクエスト（compact 6、タイトル生成 5、入力候補生成 24、background のサブエージェントの進み具合のラベル 79、離席の後の要約 1）だった。主とサブエージェントは、どの起動の形・モデル・`effort` でも全件取れた（サブエージェントは 448 件。入れ子、background、多ターンの対話、`/compact` の後、約 21 分動いた background のサブエージェントを含む）。サブエージェントの欠けが残るのは、2.1.306 以前に記録した transcript と、確かめていない長いセッション・自動 compact である。2.1.316・2.1.317 で欠けが無かったのは、2.1.307 で直った不具合に当たるため【推定】である（[§3.2](#sec-3-2)）。T1 を主線にする推奨は変えない。
