## 0. サマリ

- **調査内容**: cc の OTel テレメトリ（logs・metrics・traces）を、自作の受信スクリプトで本環境の実セッションから受け取った。属性の有無・型・格納位置を docs と照合した。対象は `-p` 実行 12 パターンと対話モード 5 セッション
- **調査結果**
  - 集計の主軸（`model`・`effort`・トークン 4 種・`cost_usd`・`skill.name`・`agent.name`）は、api_request イベントにリクエスト単位でそろう（[§4.1](#sec-4-1)）
  - 問い①〜③ のコスト側のデータ（compaction、`/clear`、サブエージェント別、ツール別）は取れる。問い②の「品質」の指標と、`/clear` 前後のセッションの結び付けは本調査の範囲外で未確認（[§2](#sec-2)）
  - docs との差異は無い。`app.version`・`app.entrypoint` が既定で付かないことも、フラグ（`OTEL_METRICS_INCLUDE_VERSION` / `OTEL_METRICS_INCLUDE_ENTRYPOINT`）を有効にすると metrics だけでなくイベント・span にも付くことも、docs どおりである（[§3](#sec-3)）
  - 取込で扱う点が 2 つある。属性の型がイベント間で不統一（[§4.2](#sec-4-2)）。メールアドレス・アカウント ID が全レコードに入る（[§3](#sec-3)）
  - 作業指示者の Windows PowerShell 5.1 から直接起動すると、環境変数が cc に届かなかった（[§7](#sec-7)）
- **結論・示唆**: api_request イベントを集計の主軸にする。取込時に、型の正規化・個人情報の扱い・`query_source` の対応付けを行う（[§9](#sec-9)）

## 1. 目的と方法

主な属性が docs どおりに届くか、値の型と格納位置、問い①〜③ に要るデータが取れるかを実測で確かめる。

- **受信**: Node.js で数十行の OTLP/HTTP 受信スクリプトを作り、受け取ったリクエストをそのまま JSONL に書き出した。スクリプトと受信データは repo 外（Claude の scratchpad）に置き、コミットしない
- **有効化**: ユーザ settings は変更せず、実測用の cc プロセスにだけ環境変数を渡した（`CLAUDE_CODE_ENABLE_TELEMETRY=1`、3 シグナルとも `otlp`、`OTEL_EXPORTER_OTLP_PROTOCOL=http/json`、`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`、`OTEL_RESOURCE_ATTRIBUTES=probe.run=<実行名>`）。内容記録のフラグ（`OTEL_LOG_USER_PROMPTS` 等）は OFF
- **用語**: OTLP は OpenTelemetry Protocol（テレメトリの送信形式）。delta は、metrics の値を前回送信からの増分で送る方式（temporality の一種）
- **実行パターン**: 検証用フォルダに、プロジェクト skill（`probe-skill`）とカスタムサブエージェント（`probe-agent`、Haiku 4.5）を置いて実行した

| 実行名 | 起動 | 内容 |
|---|---|---|
| smoke1 / r5 / r8 | `-p`、Haiku 4.5 | 最小の応答。r5 はセッション名（`-n`）付き、r8 は `OTEL_METRICS_INCLUDE_VERSION=true` |
| r1 / r2 | `-p`、Opus high / Sonnet low | ファイルを読んで推論する同じプロンプト |
| r3 | `-p`、Sonnet medium | `probe-skill` → カスタムサブエージェントを起動 |
| r4 | `-p`、Sonnet medium | 組み込みサブエージェント（general-purpose）を起動 |
| r6b / r7b | `-p --resume`（r1 のセッション） | `/compact`、`/clear` |
| r9 | `-p`、console exporter | 出力先の確認 |
| r10 / r11 | `-p` | プロジェクト設定・hook の確認（1-3 で使用）、skill 実行後の次のプロンプト |
| i3 / i4 | 対話モード（Claude が新しいウィンドウで起動し、35 秒後に終了） | 対話モードでの値の確認 |
| i1 / i2 / i5 | 対話モード（作業指示者が起動） | 起動方法による差（7 章） |

r1〜r4 は 4 セッションを同時に実行した（2 セッション同時の見え方の確認を兼ねる）。

- 注: `--model sonnet` の解決先は、cc 2.1.284 以降 Sonnet 5.5（`claude-sonnet-5-5`）に変わった。本書の Sonnet の実行は `claude-sonnet-5` に解決されている。比較を再現するときは、完全なモデル ID で指定する（[1-8 §3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-3-2)）
- 注: 本書の実測で `haiku` を指定した実行は、すべて Haiku 4.5（`claude-haiku-4-5-20251001`）に解決されていた。cc 2.1.293 から、Anthropic API の `haiku` エイリアスは Haiku 5.5（`claude-haiku-5-5`）に解決する。2.1.296 の実機では、`--model haiku` のほか、サブエージェントの `model: haiku` と、裏で動くセッションタイトル生成・入力候補生成も Haiku 5.5 になった。Bedrock など Anthropic API 以外では、docs 上 `haiku` は Haiku 4.5 のままである。比較を再現するときは、`haiku` もエイリアスではなく完全なモデル ID で指定する（[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）

## 2. 結果の要約

| 観点 | 結果 |
|---|---|
| 集計の主軸（`model`・`effort`・トークン 4 種・`cost_usd`） | api_request イベントと metrics の両方に届く。メイン / サブエージェント / compact を区別できる |
| `effort` | effort に対応するモデルでは付く。Haiku 4.5 では付かない（docs どおり）。Haiku 5.5 は対応し、付く（2.1.296 の実機で確認。[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)） |
| `skill.name` | skill 実行中の api_request と metrics に、ユーザ定義 skill の名前がそのまま付く。起動したサブエージェントのリクエストにも引き継がれる |
| cc のバージョン | リソース属性 `service.version` に常に入る。`app.version` は既定では付かない（docs どおり。opt-in で既定 false）。フラグを有効にするとイベントにも付く（docs の標準属性の節どおり。[§3](#sec-3)） |
| 問い① のデータ | `compaction` イベント（前後のトークン数）、`/clear` の `user_prompt`（`command_name=clear`）が取れる。ただし `/clear` の後はセッション ID が変わる（[§7](#sec-7)）。前後のコストを比べるには 2 つのセッションを結び付ける方法が要り、未確認 |
| 問い② のデータ | サブエージェント別（`agent.name`・`query_source`）のトークン・コスト、`subagent_completed` が取れる。「品質を保ったまま」の品質はテレメトリでは測れず、本調査の範囲外 |
| 問い③ のデータ | ツール別の件数・所要時間・入出力サイズ（`tool_result`）、サブエージェント・skill 別のトークンが取れる |
| 2 セッション同時 | 4 セッション同時でも欠落なし。全レコードに `session.id` が付き、metrics は delta なので加算で集計できる |

**2.1.287 での再確認**: cc 2.1.287 での再実測の結果は [1-8 §3](../08.cc2.1.287差分の確認/調査報告書.md#sec-3) にある。本活動が依存する属性の削除・改名は無く、追加は `user_prompt` の `prompt_text`（内容記録フラグ OFF では `<REDACTED>`）だけだった。対話モードの既定が auto mode になった後も、単純な操作では分類器のリクエストは `api_request` に現れなかった。

## 3. リソース属性と標準属性

- **リソース属性**（`resource.attributes`）: `service.name`（`claude-code`）、`service.version`（`2.1.283`）、`os.type`、`os.version`、`host.arch`、および `OTEL_RESOURCE_ATTRIBUTES` で与えたキー
  - `OTEL_RESOURCE_ATTRIBUTES` で与えたキーは、リソース属性に加えて、各イベント・metrics のデータポイント・span の属性にも複製される
- **標準属性**（各レコードの属性）: `user.id`、`session.id`、`organization.id`、`user.email`、`user.account_uuid`、`user.account_id`、`terminal.type`
  - **利用者のメールアドレスとアカウント ID が全レコードに入る**。保存・共有の設計（Phase 2「データ保全とプライバシー」）で扱いを決める必要がある
  - `app.version`・`app.entrypoint` は、既定ではイベントにも metrics にも付かなかった。docs も両属性を opt-in（`OTEL_METRICS_INCLUDE_VERSION` / `OTEL_METRICS_INCLUDE_ENTRYPOINT`、既定 false）としており、docs どおりである（[1-8 §5.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-5-1)）
  - フラグを有効にしたときの付き先も docs どおりである。docs の変数表は「metrics に付ける」とだけ説明しているが、標準属性の節は両属性を「全 metrics・イベントが共有する標準属性」に挙げ、「全 span が標準属性を持つ」としている（docs の中で書き方が揺れている）
    - `OTEL_METRICS_INCLUDE_VERSION=true` では、`app.version` が metrics だけでなくイベントにも付いた（r8）
    - `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` では、`app.entrypoint` がイベント・metrics・span に付き、値は `-p` で `sdk-cli` だった（2.1.287 で確認。[1-8 §3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-3-1)）。本調査（2.1.283）ではこのフラグを設定していない
  - 起動経路は transcript の `entrypoint`（`cli` / `sdk-cli`）でも分かる

### 4.1 api_request

|---|---|---|
| `model` | string | `claude-opus-5-5`、`claude-sonnet-5`、`claude-haiku-4-5-20251001` |
| `input_tokens` / `output_tokens` / `cache_read_tokens` / `cache_creation_tokens` | int | 4 種が別々に入る |
| `cost_usd` / `cost_usd_micros` | double / int | API 換算の推定値 |
| `duration_ms` / `ttft_ms` | int | |
| `request_id` | string | `req_…`。transcript の `requestId` と一致（[1-2 §3](../02.思考トークン取得経路/調査報告書.md#sec-3)） |
| `client_request_id` | string | 本環境では付く |
| `prompt.id` | string | 同じプロンプトから派生したリクエスト（サブエージェント・compact を含む）で共通 |
| `effort` | string | `low` / `medium` / `high`。Haiku 4.5 では付かない（Haiku 5.5 では付く） |
| `speed` | string | `normal`（docs どおり。metrics では fast mode 以外は付かない） |
| `query_source` | string | 5 章の表 |
| `agent.name` | string | 組み込みは `general-purpose` 等そのまま、ユーザ定義は `custom`（フラグ OFF 時。表の下の注） |
| `skill.name` | string | skill 実行中のみ。ユーザ定義 skill でも名前がそのまま付く。third-party の plugin の skill は既定で `"third-party"` になる。公式マーケットプレイスの plugin の skill は名前がそのまま出る（docs の記載。[1-8 §2.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-2)。本調査は project skill のみ観測） |

- 注: `input_tokens` は、キャッシュの読み書き分（`cache_read_tokens`・`cache_creation_tokens`）を含まない（docs に明記。[1-7 §7.1](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-7-1)）
- 注: `agent.name=custom` は、内容記録フラグ OFF 時の値である。docs には、`OTEL_LOG_TOOL_DETAILS=1` では実名になると書かれている（[1-8 §2.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-2)）。実機では未確認（[1-8 §6](../08.cc2.1.287差分の確認/調査報告書.md#sec-6)）。§6 の metrics の `agent.name` も同じ

### 4.2 その他のイベント

| イベント | 主な属性 | 備考 |
|---|---|---|
| `user_prompt` | `prompt.id`、`prompt_length`（**string**）、`command_name`・`command_source`（スラッシュコマンド時） | 本文は `<REDACTED>`。cc が自分で始めたターンでも出る（表の下の注） |
| `assistant_response` | `request_id`、`model`、`query_source`、`response_length` | 本文は `<REDACTED>`（`OTEL_LOG_ASSISTANT_RESPONSES=1` で記録される） |
| `tool_decision` / `tool_result` | `tool_name`、`tool_source`、`success`、`duration_ms`、`tool_input_size_bytes`、`tool_result_size_bytes` | `tool_result` の数値は**すべて string** |
| `skill_activated` | `skill.name`、`invocation_trigger`、`skill.source` | ユーザ定義 skill は `skill.name=custom_skill` に丸められる（api_request 側は丸められない） |
| `subagent_completed` | `agent_type`、`agent.source`、`is_built_in`、`is_async`、`total_tokens`、`total_tool_uses`、`duration_ms`、`model`、`final_model`、`model_swapped` | `total_tokens` は最後の 1 リクエスト分だけ（docs どおり。実測で一致） |
| `compaction` | `trigger`、`success`、`duration_ms`、`pre_tokens`、`post_tokens`、`precompute_reuse` | 数値は**すべて string** |
| `hook_registered` / `hook_execution_start` / `hook_execution_complete` | `hook_event`、`hook_source`、`num_success`、`total_duration_ms` 等 | hook を設定したセッションで出る（`-p`・対話モードとも） |
| `permission_mode_changed` | `from_mode`、`to_mode`、`trigger` | |
| `managed_settings_resolved` | `managed_settings.sources`（空配列）等 | 起動ごとに出る |
| `plugin_loaded` / `mcp_server_connection` | | 起動ごとに出る |

- `user_prompt` は、人間が打ったプロンプトだけでなく、cc が自分で始めたターンでも出る。docs（2.1.295）が挙げるのは、scheduled task（`/loop` の各回を含む）、background subagent の起動元への報告、他セッションからのメッセージである。このため、`user_prompt` の件数は人間のプロンプト数ではない。区別するフィールドは docs に無い。changelog に対応する行が無く、既存の挙動を docs に書き足したものと推測する【推測】。自動開始ターンに `prompt.id` が付くか、`api_request` の `prompt.id` と一致するかは未確認で、Phase 3 で確かめる（[1-8 §7.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-5)）

**型の不統一**: 同じ意味の属性でも、イベントによって型が異なる（例: `duration_ms` は api_request では int、`tool_result`・`compaction`・`mcp_server_connection` では string）。取込時に型を正規化する必要がある。

## 6. metrics と traces

**metrics**（今回の操作で出たもの）

| metric | 種類 | temporality | 値の型 | 主な属性 |
|---|---|---|---|---|
| `claude_code.session.count` | sum | delta | asDouble | `start_type`（`fresh` / `resume`） |
| `claude_code.cost.usage` | sum | delta | asDouble | `model`、`query_source`、`effort`、`agent.name`、`skill.name` |
| `claude_code.token.usage` | sum | delta | asDouble | 上記 + `type`（`input` / `output` / `cacheRead` / `cacheCreation`） |
| `claude_code.active_time.total` | sum | delta | asDouble | `type`（`cli`） |

**traces**（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`）: `claude_code.interaction`、`claude_code.llm_request`、`claude_code.tool`、`claude_code.tool.execution`、`claude_code.tool.blocked_on_user` の 5 種。`llm_request` にはトークン 4 種、`effort`、`request_id`、`stop_reason`、サブエージェントの `agent_id` が付く。`agent_id` は transcript のサブエージェントファイル名（`agent-<id>.jsonl`）と一致した。

span には GenAI semconv の属性も 5 つ付いていた。`llm_request` に `gen_ai.system`・`gen_ai.request.model`・`gen_ai.response.id`・`gen_ai.response.finish_reasons`、`tool` 系の span に `gen_ai.tool.call.id` である。2.1.283 の受信データにあったが、v0.3 までは記載が漏れていた。規格との対応は [1-7 §2.4](../07.生成AIオブザーバビリティ規格/調査報告書.md#sec-2-4) を参照。

## 7. その他の確認事項

- **console exporter**（V-11(b) #22）: 出力先は **stdout**。形式は JSON ではなく JavaScript のオブジェクト表記で、`-p` の応答と同じストリームに混ざる。機械処理には向かないため、1-1 以降は OTLP 受信を使う
- **`-p --resume` でのスラッシュコマンド**（#22）: `/compact`・`/clear` とも実行できた。ただし Git Bash から実行すると `/compact` が Windows のパスに変換されるため、`MSYS_NO_PATHCONV=1` が要る
- **`/clear`**（V-8、#3）: 専用イベントは無く、`user_prompt` に `command_name=clear` が付く。対話モードでは `SessionStart` hook に `source=clear` が渡る。`-p --resume "/clear"` は新しいセッション ID を返した
- **セッション名**（#11）: `-n` で付けた名前はどのシグナルにも載らなかった（`-p` で確認）
- **`retention_sweep`**（#9）: `-p`・対話モードのどちらでも出なかった。docs 上は保持期間の掃除が走ったときに出るイベントで、短いセッションでは走らない見込み。`cleanupPeriodDays` の実効値は 1-6 で確認済み
- **トークン単価**（#24）: Haiku 4.5 の 1 リクエストで、`cost_usd` を単価から検算した。キャッシュ作成を 1 時間 TTL の単価（入力単価の 2 倍）で計算すると一致した。ただし検算に使った単価は Claude の知識によるもので、料金ページでの出典確認は未実施。出典確認と他モデルの単価確認は、Phase 2 のコスト集計設計の前に行う
  - 他モデルの確認対象には Haiku 5.5（`claude-haiku-5-5`）が加わる。2.1.293 以降、Anthropic API では `haiku` がこのモデルに解決する。単価は changelog 2.1.293 にだけ「$0.10/$0.50 per Mtok、100K 超のプロンプトは $0.50/$2.50」とあり、docs は「100K 超で高くなる」とだけ書く。料金ページでの出典確認は未了である。`cost_usd` と `claude_code.cost.usage` が 100K 超の段階単価を反映するかも未確認で、100K 超のプロンプトを流して Phase 3 で確かめる
- **`/usage`**（問い② の補助、対話モード）: セッション単位のモデル別トークン・コストとキャッシュの状況に加え、直近 24 時間 / 1 週間の「利用量に寄与した要因」を表示する。要因は、サブエージェントの多いセッション、長時間セッション、150k を超えるコンテキスト、並列セッション、skill・サブエージェント別の割合。ローカルのセッションから算出した概算で、テレメトリとは独立した検算・仮説出しの材料になる
- **起動方法による差**: 環境変数を設定して `claude` を起動するスクリプトを、作業指示者のシェルから実行した結果は次のとおり。デバッグログ（`--debug-file`）の `isTelemetryEnabled` で確認した

  | 起動の仕方 | 結果 |
  |---|---|
  | Windows PowerShell 5.1 のウィンドウでスクリプトを直接実行（`& "<スクリプト>"`） | cc に `CLAUDE_CODE_ENABLE_TELEMETRY` が届かず、送信されない。スクリプト終了後のシェルにも変数が残っていなかった |
  | 同じウィンドウから PowerShell 7 経由で実行（`& "C:\Program Files\PowerShell\7\pwsh.exe" -File "<スクリプト>"`） | 届き、送信される |

  - 5.1 の内部で何が起きているかは特定できていない。Claude（cc の子プロセス）から 5.1 で同じスクリプトを実行した場合は変数が設定されたため、作業指示者のシェルでだけ起きる
  - 本番の有効化はユーザ settings の `env` で行う方針（計画書 §2 #6）なので、影響するのは起動ランチャを使う候補 ③（1-3）に限られる。候補 ③ を採る場合は PowerShell 7 経由の起動を前提とし、職場環境の PowerShell の版を Phase 3 で確認する

## 9. Phase 2 への示唆

- 集計の主軸は api_request イベントとする。リクエスト単位で `request_id`・`prompt.id`・`effort`・`skill.name`・`agent.name` がそろう。metrics は検算と長期の推移に使う
- `query_source` はイベントと metrics で値の体系が違う（5 章）。イベントの値から metrics の区分（main / subagent / auxiliary）へ対応付ける表を持つ
- 取込時に型を正規化する（4.2）
- メールアドレス・アカウント ID は、保存時に落とすかハッシュ化するかを決める
- 対話モードで毎回出るタイトル生成・入力候補生成のリクエストは、作業分類とは別に「付帯コスト」として集計する
- モデルをまたいでトークン数や費用を比べるときは、system prompt の長さの差が交絡する。`CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` が未設定のとき、Haiku 4.5・Sonnet 5・Opus 4.7 とそれ以前の同系統のモデルは完全版、それより新しいモデル（Sonnet 5.5・Opus 5.5・Haiku 5.5 等）は短縮版の system prompt を使う（docs 2.1.295 の明記）。入力・キャッシュ書き込みのトークンを比べる実験では、この変数を `0` か `1` に固定するか、交絡として注記する

**最強の反論と残存リスク**

- 反論: 実測の大半は `-p` の短いセッションで、日常の長い対話セッションの挙動を代表していない
  - 対話モードに固有の値（`query_source`、補助リクエスト）は i3〜i5 で確認し、`-p` との差を [§5](#sec-5) に記録した
  - 自動 compact・リトライ・長時間セッションでの `retention_sweep` は未観測である（残存リスク）。Phase 3 の PoC で日常利用のセッションを流して確認する
