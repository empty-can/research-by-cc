## 0. サマリ

- **調査内容**: cc の OTel テレメトリ（logs・metrics・traces）を、自作の受信スクリプトで本環境の実セッションから受け取った。属性の有無・型・格納位置を docs と照合した。対象は `-p` 実行 12 パターンと対話モード 5 セッション
- **調査結果**
  - 集計の主軸（`model`・`effort`・トークン 4 種・`cost_usd`・`skill.name`・`agent.name`）は、api_request イベントにリクエスト単位でそろう（[§4.1](#sec-4-1)）。ただし、logs（api_request）と metrics に出ない API 呼び出しがある（2026-10-19 追記。[§9](#sec-9)）
  - 問い①〜③ のコスト側のデータ（compaction、`/clear`、サブエージェント別、ツール別）は取れる。問い②の「品質」の指標と、`/clear` 前後のセッションの結び付けは本調査の範囲外で未確認（[§2](#sec-2)）
  - docs との差異は無い。`app.version`・`app.entrypoint` が既定で付かないことも、フラグ（`OTEL_METRICS_INCLUDE_VERSION` / `OTEL_METRICS_INCLUDE_ENTRYPOINT`）を有効にすると metrics だけでなくイベント・span にも付くことも、docs どおりである（[§3](#sec-3)）
  - 取込で扱う点が 2 つある。属性の型がイベント間で不統一（[§4.2](#sec-4-2)）。メールアドレス・アカウント ID が全レコードに入る（[§3](#sec-3)）
  - 作業指示者の Windows PowerShell 5.1 から直接起動すると、環境変数が cc に届かなかった（[§7](#sec-7)）
- **結論・示唆**: 集計に使う属性は api_request イベントにそろう。logs・metrics に出ない API 呼び出しがあり、その一部は traces の span にだけ出るので、集計の正本（api_request か traces の span か）は本書では決めず、計画書 Phase 2 に任せる（2026-10-19 に改めた）。取込時に、型の正規化・個人情報の扱い・`query_source` の対応付けを行う（[§9](#sec-9)）。Claude Mods で取れる値（サブエージェントのリクエスト単位の usage、turn ごとの合計、文脈の使用率とプランの上限の割合）と注意は [§10](#sec-10) に置いた（2026-10-19 追記。採るかは Phase 2 で決める）

## 1. 目的と方法

主な属性が docs どおりに届くか、値の型と格納位置、問い①〜③ に要るデータが取れるかを実測で確かめる。

- **受信**: Node.js で数十行の OTLP/HTTP 受信スクリプトを作り、受け取ったリクエストをそのまま JSONL に書き出した。スクリプトと受信データは repo 外（Claude の scratchpad）に置き、コミットしない
- **有効化**: ユーザ settings は変更せず、実測用の cc プロセスにだけ環境変数を渡した（`CLAUDE_CODE_ENABLE_TELEMETRY=1`、3 シグナルとも `otlp`、`OTEL_EXPORTER_OTLP_PROTOCOL=http/json`、`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`、`OTEL_RESOURCE_ATTRIBUTES=probe.run=<実行名>`）。内容記録のフラグ（`OTEL_LOG_USER_PROMPTS` 等）は OFF
- **用語**: OTLP は OpenTelemetry Protocol（テレメトリの送信形式）。delta は、metrics の値を前回送信からの増分で送る方式（temporality の一種）
- **実行パターン**: 検証用フォルダに、プロジェクト skill（`probe-skill`）とカスタムサブエージェント（`probe-agent`、Haiku 4.5）を置いて実行した

| 実行名 | 起動 | 内容 |
|---|---|---|
| smoke1 / r5 / r8 | `-p`、Haiku 4.5 | 最小の応答。r5 はセッション名（`-n`）付き、r8 は `OTEL_METRICS_INCLUDE_VERSION=true` |
| r1 / r2 | `-p`、Opus high / Sonnet low | ファイルを読んで推論する同じプロンプト |
| r3 | `-p`、Sonnet medium | `probe-skill` → カスタムサブエージェントを起動 |
| r4 | `-p`、Sonnet medium | 組み込みサブエージェント（general-purpose）を起動 |
| r6b / r7b | `-p --resume`（r1 のセッション） | `/compact`、`/clear` |
| r9 | `-p`、console exporter | 出力先の確認 |
| r10 / r11 | `-p` | プロジェクト設定・hook の確認（1-3 で使用）、skill 実行後の次のプロンプト |
| i3 / i4 | 対話モード（Claude が新しいウィンドウで起動し、35 秒後に終了） | 対話モードでの値の確認 |
| i1 / i2 / i5 | 対話モード（作業指示者が起動） | 起動方法による差（7 章） |

r1〜r4 は 4 セッションを同時に実行した（2 セッション同時の見え方の確認を兼ねる）。

## 3. リソース属性と標準属性

- **リソース属性**（`resource.attributes`）: `service.name`（`claude-code`）、`service.version`（`2.1.283`）、`os.type`、`os.version`、`host.arch`、および `OTEL_RESOURCE_ATTRIBUTES` で与えたキー
  - `OTEL_RESOURCE_ATTRIBUTES` で与えたキーは、リソース属性に加えて、各イベント・metrics のデータポイント・span の属性にも複製される
- **標準属性**（各レコードの属性）: `user.id`、`session.id`、`organization.id`、`user.email`、`user.account_uuid`、`user.account_id`、`terminal.type`
  - **利用者のメールアドレスとアカウント ID が全レコードに入る**。保存・共有の設計（Phase 2「データ保全とプライバシー」）で扱いを決める必要がある
  - `app.version`・`app.entrypoint` は、既定ではイベントにも metrics にも付かなかった。docs も両属性を opt-in（`OTEL_METRICS_INCLUDE_VERSION` / `OTEL_METRICS_INCLUDE_ENTRYPOINT`、既定 false）としており、docs どおりである（[1-8 §5.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-5-1)）
  - フラグを有効にしたときの付き先も docs どおりである。docs の変数表は「metrics に付ける」とだけ説明しているが、標準属性の節は両属性を「全 metrics・イベントが共有する標準属性」に挙げ、「全 span が標準属性を持つ」としている（docs の中で書き方が揺れている）
    - `OTEL_METRICS_INCLUDE_VERSION=true` では、`app.version` が metrics だけでなくイベントにも付いた（r8）
    - `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` では、`app.entrypoint` がイベント・metrics・span に付き、値は `-p` で `sdk-cli` だった（2.1.287 で確認。[1-8 §3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-3-1)）。本調査（2.1.283）ではこのフラグを設定していない
  - 起動経路は transcript の `entrypoint`（`cli` / `sdk-cli`）でも分かる

## 10. Mod の活用余地（2026-10-19 追記）

Claude Mods（plugin の hooks module。仕組みと管理は [1-8 §4.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-1)）の docs から、本書の集計の対象（モデル・effort・トークン・サブエージェント）に効く項目を拾った。典拠は docs 2026-10-19 取得版の Mods のページ（events・reference・API・test）、hooks のページと changelog で、実機では確かめていない。Mod を採るかどうかは Phase 2 で決める（本書では決めない）。タグ付け（L1）を command hook と Mod のどちらで書くかの比べる表は、[1-3 の「L1 の実装手段の比較（command hook と Mod）」](../03.作業分類タグ方式/調査報告書.md#sec-4-l1-impl)にある。

**リクエスト単位の usage とサブエージェントの個体（`turn.step`）**

- `turn.step` は、Claude Code がモデルへリクエストを 1 件送る直前に発火する（tool call のある turn では複数回）。サブエージェントのリクエストでは `e.agentId` が付く。hook の結果の `result.usage` は、Claude API がそのリクエストについて報告するトークン数 4 種（`input_tokens`・`output_tokens`・`cache_read_input_tokens`・`cache_creation_input_tokens`）と、答えた `model` を持つ（docs の events のページ。docs は `result.usage` の項目として、トークン数 4 種と `model` を並べて書く。型定義では確かめていない）。docs の例は、usage の無い結果を除いている
- 活用余地: `turn.step` の `e.agentId` と usage を Mod で記録すれば、api_request の `agent.name`（種類の名前）では分からないサブエージェントの個体を、traces を使わずにリクエスト単位で分ける材料になる。（2026-10-26 追記。cc 2.1.310）2.1.310 からは `api_request` にもサブエージェントの `agent_id` が付くので、個体をリクエスト単位で分けることは OTel で足りる（[1-10 §2](../10.cc2.1.310差分の確認/調査報告書.md#sec-2) の D66）
- ただし、OTel のレコードと結び付ける鍵は、プロンプト単位の `prompt_id` だけである。docs に出る Mod の turn イベントの項目には、`request_id`・`prompt.id`・`session.id` に当たるものが無く、`turnId` と OTel の `prompt.id` の関係も docs に無い。`prompt_id` は settings hook の共通の入力の項目で、OTel の `prompt.id` と同じ値である（最初のユーザ入力までは無い。hooks の docs）。Mod では、`classic.*` の `e`（settings hook の stdin と同じ JSON）で受ける。【推定】Mod の中で `classic.UserPromptSubmit` の `prompt_id` を覚えて同じプロンプトの `turn.step` の記録に付け、そのプロンプトの中を順序・時刻・モデル・トークン数で `api_request` と照合することになる。この照合は docs で保証されておらず、`classic.UserPromptSubmit` と `turn.start` の発火の順序も docs では決まらない
- `e.agentId` が、settings hook の入力の `agent_id`、traces の span の `agent_id`、transcript の `subagents/agent-<id>.jsonl` と同じ値かは docs に無い（changelog 2.1.289 に「plugin hook のイベントをまたいで 1 つの agent id」とあるだけ）。render site の `e.requestId` は描画の単位の id で、API リクエストの `request_id` ではない。（2026-10-26 追記。cc 2.1.310）OTel のイベントの `agent_id`（2.1.310 から `api_request`・tool のイベントなどに付く）、traces の span の `agent_id`、transcript のサブエージェントのファイルの id は、2.1.310 の `-p` で同じ値だった（サブエージェント 1 つ。[1-10 §3.2](../10.cc2.1.310差分の確認/調査報告書.md#sec-3-2)）。Mod の `e.agentId` と settings hook の入力の `agent_id` がこれらと同じ値かは、確かめていないまま残る
- `turn.step` が、compact・セッションタイトルの生成・入力候補の生成・auto mode の分類器・side query のリクエストでも発火するかは docs に無い（docs の turn は「1 つのプロンプトへの答えとして Claude がすること全体」）。[§9](#sec-9) の logs・metrics に出ない API 呼び出しを Mod で拾えるかは、ここで決まる

**turn ごとの合計（`turn.complete`）**

- `turn.complete` は turn の終わりに発火し、ユーザが中断した turn でも発火する（そのとき `e.isAborted` が true）。`e.usage` は turn のトークン合計、`e.durationMs` は所要時間である。サブエージェントの turn でも `e.agentId` 付きで発火する。`turn.start`（2.1.299 からサブエージェントの turn でも発火）の `e.turnId` が、3 つの turn イベントに共通の鍵になる
- 活用余地: OTel の `subagent_completed.total_tokens` は最後の 1 リクエスト分だけ（[§4.2](#sec-4-2)）なので、サブエージェントの turn 単位の合計を補える見込みである（【推定】。`e.usage` がどのリクエストを足した値か、サブエージェントの 1 回の起動が 1 turn かは docs では決まらない）

**OTel に無い値（`$.session.usage()`）**

- `$.session.usage()` は `{ startedAt, context, rateLimits, cost }` を返す。`context` は文脈の `tokens`・`window`・`percent`、`rateLimits` はプランの上限ごとの `{ kind, percentUsed, resetsAt }` の配列である（docs の reference のページ）。Monitoring の docs には、文脈の使用率とプランの上限の割合に当たる属性が無い。`cost` の中身と `startedAt` の単位は docs では決まらない
- `session.measure` は、各 turn の後と、プランの上限の使用率が変わったときに発火する
- 活用余地: 文脈の使用率とプランの上限の割合を、OTel とは別の記録として取れる。集計に加えるかは Phase 2 で決める

**注意（Mod を入れた環境の値）**

- モデルと effort: `turn.step` の hook は、そのリクエストのモデルと effort を書き換えられ（`next({ ...e, model })`・`next({ ...e, effort })`）、モデルを呼ばずに答えることもできる。Mod を入れた環境では、`api_request` の `model`・`effort` の出どころに Mod が加わる（`api_request` の値が書き換え後になることは【推定】。[§4.1](#sec-4-1) の注の `agent.spawn` と同じ種類）
- prompt cache: `prompt.section`・`prompt.context`・`skill.prompt` の hook が返す文がリクエストの間で変わると、prompt cache が無効になる（docs）。【推定】Mod を入れた環境では、`cache_creation_tokens`・`cache_read_tokens` が Mod（組み込み Mod を含む）の有無と構成で動きうる。cache のトークン数を比べる実験では、Mod の構成をそろえるか、交絡として注記する（[§9](#sec-9) の system prompt の交絡と同じ種類。[1-8 §7.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2) の C-3c の `prompt.context` も同じ場所の話）
- Mod 自身のリクエスト: `$.model.complete`・`$.model.fork` はセッションの credential で送られ、利用者のプラン・API キー・クラウドの provider に課金される。`$.model.complete` の結果には usage（cache の 2 項目を含む）がある。このリクエストが OTel の `api_request` に出るか、`query_source` が何になるかは docs に無い
- Mod が足す tool: `$.tool.register` で Mod が足した tool は、Claude には `mcp__`・plugin の名前・`__`・登録した名前をつないだ名前で見える。OTel の `tool_result` の `tool_name`・`tool_source` にどう出るかは docs に無い
- 版: LLM ゲートウェイ（`ANTHROPIC_BASE_URL` と `ANTHROPIC_AUTH_TOKEN`）で Claude に届き、Anthropic のアカウントを持たない人には Mod が off のままだった不具合が、2.1.290 で直った（changelog）。auto mode でサブエージェントが報告を返すときに `turn.complete` の answer が空になる不具合と、`turn.step` の結果に、応答途中のモデルの fallback で捨てた tool call が残る不具合も 2.1.290 で直った。LLM ゲートウェイ環境（計画書 v2.0 の Phase 7）で Mod を使うなら 2.1.290 以降が要る（1-8 が Mod を採る前提とする 2.1.293 以降に含まれる）

**確かめる時期**（同日のクロスレビュー Round 2 で追記）

- 上の「docs に無い」「docs では決まらない」の点は、Mod を採る場合に Phase 3 の PoC で確かめる。項目・確かめ方・合格の条件は [1-8 §8.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-5) の表に置く
  - `turn.step` が、compact・セッションタイトルの生成・入力候補の生成・auto mode の分類器・side query のリクエストでも発火するか
  - `turn.step` の記録と `api_request` の照合（`classic.UserPromptSubmit` と `turn.start` の発火の順序を含む）
  - `e.agentId` が、settings hook の入力・traces の span・transcript の `agent_id` と同じ値か
  - `turn.complete` の `e.usage` がどのリクエストを足した値か、サブエージェントの 1 回の起動が 1 turn か
  - Mod 自身の `$.model.complete` のリクエストが `api_request` に出るか、`query_source` が何になるか
  - `$.tool.register` で足した tool が、`tool_result` の `tool_name`・`tool_source` にどう出るか
  - `result.usage` の `model` の位置（型定義で確かめる）
  - `$.session.usage()` の `cost` の中身と `startedAt` の単位
- 職場（LLM ゲートウェイ環境）で Mod が読み込まれるかは、Phase 7 で確かめる（1-8 §8.5 の表）
