## 0. サマリ

- **調査内容**: 作業分類タグの付与方式の候補 ①〜⑤ について、前提と制約を実測で確かめ、計画書の 10 列の比較表で整理した
- **調査結果**
  - ネイティブ属性（①）の `skill.name` は、ユーザ定義 skill でも名前がそのまま付き、skill が起動したサブエージェントにも引き継がれる（[§2](#sec-2)）
  - `UserPromptSubmit` hook の入力の `prompt_id` は、OTel の `prompt.id` と 7 件すべてで一致した。hook 方式（②）は成立する。cc 2.1.287 の Claude Mods でも同じ結合ができ、cc 2.1.296 でも command hook・Mod とも `-p`・対話モードの各 3 回で一致した。cc 2.1.302 でも、`-p`（command hook 15 回・Mod 18 回）と対話モード（各 3 回）のすべてで一致した。cc 2.1.309 の `-p` でも、command hook の 8 回すべてで一致した（Mod と対話モードは確かめていない。[§2](#sec-2)）
  - `UserPromptSubmit` hook は、cc が自分で始めたターン（scheduled task など）でも発火する（docs 2.1.295 で明記）。hook の入力と OTel の `user_prompt` には区別するフィールドが docs に無く、タグ案 L1 での扱いは、ラベル「自動」を付けて残すと裁定された（J-15、2026-10-24。[§2](#sec-2)・[§4](#sec-4)）。Mod の `session.receive` の `e.origin.kind`（`task-notification`・`scheduled-trigger` など）は、判定の材料になる（docs 2026-10-19 取得版。2026-10-19 追記）
  - cc 2.1.299 から、`UserPromptSubmit` hook は skill・カスタム slash command の展開の前に動く。L1 のルール分類が受け取るプロンプトは、展開した中身ではなく打ったままの行（`/skill名 引数` の形）になる（docs 2026-10-18 で確かめた）。Phase 3 で確かめるのは、そのターンの `prompt_id` の一致と上乗せである（[§2](#sec-2)）
  - 本環境の日常に近い条件（plugin は有効のまま、Remote Control は切った）では、ユーザ設定で有効な plugin の hook だけで、hook なしの対話モードの llm_request の開始までが平均 593 ms になっていた。それらの plugin を無効にした場合より約 450 ms 長い（cc 2.1.302。[§2.1](#sec-2-1)）
  - hook 入力にはプロンプト本文があるため、本文を保存せずに hook の中で分類する形（④'）も作れる（[§3](#sec-3)）
  - Mod の活用余地（2026-10-19 追記。docs 2026-10-19 取得版）: 【推定】L2 の本文の記録は、OTel の代わりに Mod で書き出しても作れる（本文は OTel の経路に入らないが、この形では L2 も hook を使い、hook の待ちが乗る）。Mod は、失敗した hook を既定で飛ばして処理を続ける（fail-open）。Mod から OTel のレコードに属性を足す API は無い（[§2](#sec-2)・[§4](#sec-4)）
  - プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` はプロセス環境変数を丸ごと置き換えるため、③ と ⑤ は併用できない（[§2](#sec-2)）
- **結論・示唆**: タグ案 L1「① + ④'（hook でルール分類。本文を保存しない）」とタグ案 L2「① + ④（`OTEL_LOG_USER_PROMPTS=1` で本文を記録し事後分類。hook なし）」の 2 案に絞る（L2 の「hook なし」は OTel で本文を記録する場合。Mod で書き出す形は §4 の注）。どちらにするかは、計画書 §7 #2（本文の記録）の判断と合わせて決める（[§4](#sec-4)）。L1 の command hook と Mod の上乗せの大小は cc の版とモードで入れ替わるが、2.1.287・2.1.296・2.1.302 の測定ではどれも 0.5 秒未満で、この絞り込みは変わらない（2.1.302 の向きは 2.1.296 と同じ。[§2.1 の版・モード別の表](#sec-2-1)）

## 1. 目的と方法

「どの作業か」を後から集計するためのラベルの付け方を、計画書の候補 ①〜⑤ で比べる。前提と制約は、1-1 と同じ受信環境で実測して確かめた。内容記録のフラグ（`OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_TOOL_DETAILS`）は OFF のまま（§7 #2 の判断待ち）。

実測したこと:

- `skill.name`・`agent.name`・`command_name` の値と有効範囲（1-1 の r3・r4・r6b・r7b・r11）
- 検証用フォルダのプロジェクト設定（`.claude/settings.json`）での確認（r10）
  - `env` に `OTEL_RESOURCE_ATTRIBUTES`・`OTEL_METRICS_INCLUDE_VERSION` を書いた場合の効き方と、プロセス環境変数との優先関係
  - `SessionStart`・`UserPromptSubmit` hook の入力（ID 系の値とキー名だけを記録し、本文は記録していない）

## 3. 候補の比較

候補の定義（計画書 1-3）:

- ① ネイティブ属性（`skill.name`・`command_name`・`workflow.name` 等）のみ
- ② `UserPromptSubmit` hook でラベルを別ファイルに書き、`prompt_id` で突合
- ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
- ④ プロンプト本文の事後分類（ルール / LLM）
- ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル

④ の前提は計画書では `OTEL_LOG_USER_PROMPTS=1` としている。ただし実測で、hook 入力に本文があることが分かった。そのため、④ を hook の中で実行する形（④'）も比較に加える。

| 候補 | 長所 | 短所 | 前提事項 | 制約 | 分類精度 | 導入負荷 | 維持負荷 | 機微情報 | その他 |
|---|---|---|---|---|---|---|---|---|---|
| ① ネイティブ属性のみ | 追加の仕組みが要らない。過去の OTel データにもそのまま使える | skill・サブエージェントを使わない自由入力の作業は分類できない | skill・コマンド・サブエージェントを使う運用 | ユーザ定義サブエージェントは `custom` に丸められる（docs ではフラグで実名になる。実機は未確認） | skill 経由の作業は高い。それ以外は分類不能 | なし | 低（cc の属性の変更への追従のみ） | 記録しない | 他の候補と常に併用できる |
| ② hook でラベル | プロンプト単位でラベルを付けられる。OTel の設定に依存しない | hook のラベル付けの規則を用意する必要がある。プロンプトごとに待ち時間が増える（llm_request の開始までの上乗せは、Node.js の command hook で `-p` 約 130〜150 ms（2.1.287・2.1.296・2.1.302）、対話モード約 440 ms（2.1.287）・約 211 ms（2.1.296）・約 270 ms（2.1.302。どちらも Remote Control なし）。[§2.1 の版・モード別の表](#sec-2-1)）。自動開始ターン（scheduled task 等）でも発火するので、人間以外のプロンプトにもラベルが付く（§2） | `UserPromptSubmit` hook の `prompt_id` が OTel の `prompt.id` と一致すること（人間が入力したプロンプトで確認済み。自動開始ターンと、skill・slash command を使うターンは未確認） | ラベルは OTel の外（別ファイル）にあり、取込時に突合が要る | 規則次第。キーワード・コマンド等の単純な規則なら中 | 中（hook スクリプトと保存先） | 中（規則の見直し） | 本文を hook 内で読むが、ラベルだけを保存すれば記録しない | 実装手段は command hook（PowerShell / 起動の速い実行形式にする余地がある。PowerShell で書く場合の文字コードの注意は §4）のほか、cc 2.1.287 の Claude Mods も使える（Mod を採るなら 2.1.293 以降。§2） |
| ③ 起動ランチャ | セッション単位のラベルが全シグナルに直接付く。突合が要らない | 起動時にラベルを選ぶ操作が増える。1 セッションで複数の作業をすると分類が粗くなる | 環境変数を設定してから cc を起動する手段（PowerShell 7 経由） | ⑤ と同時に使うとプロジェクト設定側で上書きされる。PowerShell 5.1 から直接起動すると効かない（1-1） | 起動時の選択が正しければ高い。セッション内で作業が変わると下がる | 低〜中（ランチャ） | 低 | 記録しない | 「操作を増やさない」（計画書 §1.3）と相反する |
| ④ 本文の事後分類（`OTEL_LOG_USER_PROMPTS=1`） | 過去に遡って分類し直せる。分類体系を後から変えられる | プロンプト本文がテレメトリとしてディスクに残る | `OTEL_LOG_USER_PROMPTS=1`（§7 #2） | 本文の保存に伴う管理（保存先・保持期間） | LLM で分類すれば高い見込み | 中（分類処理） | 中（分類体系・プロンプトの見直し） | 本文を記録する（2.1.287 以降は `prompt` と `prompt_text` の 2 か所）。自動開始ターンの本文（タスク通知・他セッションのメッセージ）も記録される | LLM で分類する場合はそのコストがかかる |

## 4. 組み合わせの考察

- ① は常に併用できる。skill・サブエージェント経由の作業はこれで分類でき、追加コストが無い
- 自由入力の作業の分類には、② / ④' / ④ のいずれかが要る。本文を保存しない方針なら ④'（hook でルール分類）、分類し直しを重視するなら ④ になる
- ③ は「操作を増やさない」という成功基準と相反し、⑤ とも排他である。優先度は低い
- ⑤ で得られる「どのリポジトリの作業か」の情報は、`cwd`（hook 入力）や transcript のフォルダ名からも取れる。⑤ を使う必要は薄い見込み
