## 0. サマリ

- **調査内容**: 作業分類タグの付与方式の候補 ①〜⑤ について、前提と制約を実測で確かめ、計画書の 10 列の比較表で整理した
- **調査結果**
  - ネイティブ属性（①）の `skill.name` は、ユーザ定義 skill でも名前がそのまま付き、skill が起動したサブエージェントにも引き継がれる（[§2](#sec-2)）
  - `UserPromptSubmit` hook の入力の `prompt_id` は、OTel の `prompt.id` と 7 件すべてで一致した。hook 方式（②）は成立する。cc 2.1.287 の Claude Mods でも同じ結合ができ、cc 2.1.296 でも command hook・Mod とも `-p`・対話モードの各 3 回で一致した（[§2](#sec-2)）
  - `UserPromptSubmit` hook は、cc が自分で始めたターン（scheduled task など）でも発火する（docs 2.1.295 で明記）。区別するフィールドは docs に無く、タグ案 L1 での扱いは裁定待ち（J-15。[§2](#sec-2)・[§4](#sec-4)）
  - hook 入力にはプロンプト本文があるため、本文を保存せずに hook の中で分類する形（④'）も作れる（[§3](#sec-3)）
  - プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` はプロセス環境変数を丸ごと置き換えるため、③ と ⑤ は併用できない（[§2](#sec-2)）
- **結論・示唆**: タグ案 L1「① + ④'（hook でルール分類。本文を保存しない）」とタグ案 L2「① + ④（`OTEL_LOG_USER_PROMPTS=1` で本文を記録し事後分類。hook なし）」の 2 案に絞る。どちらにするかは、計画書 §7 #2（本文の記録）の判断と合わせて決める（[§4](#sec-4)）。L1 の command hook と Mod の待ち時間の大小は cc の版とモードで入れ替わるが、どれも 0.5 秒未満で、この絞り込みは変わらない（[§2 の版・モード別の表](#sec-2-1)）

<a id="sec-1"></a>
## 1. 目的と方法

「どの作業か」を後から集計するためのラベルの付け方を、計画書の候補 ①〜⑤ で比べる。前提と制約は、1-1 と同じ受信環境で実測して確かめた。内容記録のフラグ（`OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_TOOL_DETAILS`）は OFF のまま（§7 #2 の判断待ち）。

実測したこと:

- `skill.name`・`agent.name`・`command_name` の値と有効範囲（1-1 の r3・r4・r6b・r7b・r11）
- 検証用フォルダのプロジェクト設定（`.claude/settings.json`）での確認（r10）
  - `env` に `OTEL_RESOURCE_ATTRIBUTES`・`OTEL_METRICS_INCLUDE_VERSION` を書いた場合の効き方と、プロセス環境変数との優先関係
  - `SessionStart`・`UserPromptSubmit` hook の入力（ID 系の値とキー名だけを記録し、本文は記録していない）

<a id="sec-2-1"></a>
**hook と Mod の上乗せ（版・モード別）**

llm_request の開始までの上乗せ（interaction span の開始から最初の llm_request span の開始までの時間の、同じ条件の hook なしとの差）。単位は ms、各 n=3 の平均。2.1.287 は [1-8 §4.4](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)、2.1.296 は [1-8 §7.3.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2)。

| 版・モード（モデル） | hook なし | command hook の上乗せ | Mod の上乗せ | 上乗せが小さい方 |
|---|---|---|---|---|
| 2.1.287 `-p`（Haiku 4.5。auto から default に落ちた後） | 135 | +152 | +31 | Mod |
| 2.1.296 `-p`（Haiku 5.5。auto のまま） | 293 | +155 | +204 | command hook |
| 2.1.296 `-p`（Haiku 4.5 を明示した補足 run） | 115 | — | +195 | — |
| 2.1.287 対話（Haiku 4.5、Remote Control あり） | 121 | +439 | +297 | Mod |
| 2.1.296 対話（Haiku 5.5、Remote Control あり） | 111 | +235 | +160 | Mod |
| 2.1.296 対話（Haiku 5.5、Remote Control なし） | 108 | +211 | +110 | Mod |

- モデルの表記: Haiku 4.5 は `claude-haiku-4-5-20251001`、Haiku 5.5 は `claude-haiku-5-5`。2.1.293 から、Anthropic API の `--model haiku` は Haiku 5.5 に解決する（[1-8 §7.3.3](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）
- `-p` では、2.1.296 で大小が逆転した。Haiku 4.5 を明示しても Mod の上乗せは +195 ms なので、モデルや permission mode の差ではなく版の差である。原因の手がかり: Mod の処理そのものは 30.6 ms だった。Mod を読み込むと、組み込み Mod `cc-plugin-agents-md` の `prompt.context`（238 ms）がプロンプト受付後の待ち経路に入っていた。hook なしでは、同じ処理が起動時に済んでいた【推測、debug n=1】。2.1.296 では、組み込み Mod が購読するイベントの構成も 2.1.287 から変わっている
- 対話モードでは、2.1.296 で両方とも縮み、Mod の方が小さいままだった。ただし対話の版間比較は、モデル（Haiku 4.5→5.5）と permission mode（2.1.287 は default に落ちた後、2.1.296 は auto のまま）も違う。上乗せは同じ条件の hook なしとの差なので条件差の多くは相殺されるが、対話では Haiku 4.5 を明示した補足 run をしていないので、版の差だけを分けてはいない
- Remote Control: ユーザ設定 `remoteControlAtStartup: true` のため、2.1.287・2.1.296 の対話の計測は、どちらも Remote Control に接続した状態だった。版間比較は「Remote Control あり」の行どうしで行う。接続しない場合は、command hook の上乗せが約 24 ms、Mod の上乗せが約 50 ms 小さかった
- どの値も 0.5 秒未満で、2 秒超はどの条件でも出なかった。上乗せは版（組み込み Mod の構成）で動くので、Phase 3 の測定値は測った版でしか使えない

<a id="sec-3"></a>
## 3. 候補の比較

候補の定義（計画書 1-3）:

- ① ネイティブ属性（`skill.name`・`command_name`・`workflow.name` 等）のみ
- ② `UserPromptSubmit` hook でラベルを別ファイルに書き、`prompt_id` で突合
- ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
- ④ プロンプト本文の事後分類（ルール / LLM）
- ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル

④ の前提は計画書では `OTEL_LOG_USER_PROMPTS=1` としている。ただし実測で、hook 入力に本文があることが分かった。そのため、④ を hook の中で実行する形（④'）も比較に加える。

| 候補 | 長所 | 短所 | 前提事項 | 制約 | 分類精度 | 導入負荷 | 維持負荷 | 機微情報 | その他 |
|---|---|---|---|---|---|---|---|---|---|
| ① ネイティブ属性のみ | 追加の仕組みが要らない。過去の OTel データにもそのまま使える | skill・サブエージェントを使わない自由入力の作業は分類できない | skill・コマンド・サブエージェントを使う運用 | ユーザ定義サブエージェントは `custom` に丸められる（docs ではフラグで実名になる。実機は未確認） | skill 経由の作業は高い。それ以外は分類不能 | なし | 低（cc の属性の変更への追従のみ） | 記録しない | 他の候補と常に併用できる |
| ② hook でラベル | プロンプト単位でラベルを付けられる。OTel の設定に依存しない | hook のラベル付けの規則を用意する必要がある。プロンプトごとに待ち時間が増える（llm_request の開始までの上乗せは、Node.js の command hook で `-p` 約 150 ms（2.1.287・2.1.296 とも）、対話モード約 440 ms（2.1.287）・約 235 ms（2.1.296）。[§2 の版・モード別の表](#sec-2-1)）。自動開始ターン（scheduled task 等）でも発火するので、人間以外のプロンプトにもラベルが付く（§2） | `UserPromptSubmit` hook の `prompt_id` が OTel の `prompt.id` と一致すること（人間が入力したプロンプトで確認済み。自動開始ターンは未確認） | ラベルは OTel の外（別ファイル）にあり、取込時に突合が要る | 規則次第。キーワード・コマンド等の単純な規則なら中 | 中（hook スクリプトと保存先） | 中（規則の見直し） | 本文を hook 内で読むが、ラベルだけを保存すれば記録しない | 実装手段は command hook（PowerShell / 起動の速い実行形式にする余地がある）のほか、cc 2.1.287 の Claude Mods も使える（Mod を採るなら 2.1.293 以降。§2） |
| ③ 起動ランチャ | セッション単位のラベルが全シグナルに直接付く。突合が要らない | 起動時にラベルを選ぶ操作が増える。1 セッションで複数の作業をすると分類が粗くなる | 環境変数を設定してから cc を起動する手段（PowerShell 7 経由） | ⑤ と同時に使うとプロジェクト設定側で上書きされる。PowerShell 5.1 から直接起動すると効かない（1-1） | 起動時の選択が正しければ高い。セッション内で作業が変わると下がる | 低〜中（ランチャ） | 低 | 記録しない | 「操作を増やさない」（計画書 §1.3）と相反する |

## 4. 組み合わせの考察

- ① は常に併用できる。skill・サブエージェント経由の作業はこれで分類でき、追加コストが無い
- 自由入力の作業の分類には、② / ④' / ④ のいずれかが要る。本文を保存しない方針なら ④'（hook でルール分類）、分類し直しを重視するなら ④ になる
- ③ は「操作を増やさない」という成功基準と相反し、⑤ とも排他である。優先度は低い
- ⑤ で得られる「どのリポジトリの作業か」の情報は、`cwd`（hook 入力）や transcript のフォルダ名からも取れる。⑤ を使う必要は薄い見込み

**2 案への絞り込み（案）**

記号 L1 / L2 はタグ方式の組み合わせを表す（v0.3 で「案 1 / 案 2」から改名）。

| タグ案 | 構成 | 本文の記録 | hook | 特徴 |
|---|---|---|---|---|
| L1 | ① + ④'（hook でルール分類し、ラベルだけ保存） | しない | 使う | プライバシー面で安全。分類精度はルールの作り込み次第で、分類し直しはできない。llm_request の開始までの上乗せの大小は、cc の版とモードで入れ替わる。2.1.287 では `-p`・対話モードとも Mod が command hook より小さかった。2.1.296 では、対話モードは Mod が小さいままで、`-p` では command hook が小さい（どれも 0.5 秒未満。[§2 の版・モード別の表](#sec-2-1)）。実装手段（command hook か Mod か）は Phase 2 で決める |
| L2 | ① + ④（`OTEL_LOG_USER_PROMPTS=1` で本文を記録し、事後分類） | する | 使わない | 分類体系を後から変えられる。本文の保存を許容する判断（§7 #2）が要る。hook の待ち時間は生じない |

- 注: L2 で本文を記録すると、2.1.287 以降は `user_prompt` の `prompt` と `prompt_text` の 2 か所に入る。マスク・削除・保存量の見積もりは両方に適用する（[1-8 §2.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-2-1)）。docs 2.1.295 には `prompt_text` が正式に載り、collector で `prompt` と `prompt_text` の両方を消す例も載った（[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）。L2 では、自動開始ターンの本文（タスク通知・他セッションのメッセージ）も記録対象になる
- 注: L1 の ④' を command hook と Claude Mods のどちらで実装するかは、Phase 2 で決める。L1 / L2 への絞り込みは変えない（[1-8 §4](../08.cc2.1.287差分の確認/調査報告書.md#sec-4)）。Mod で実装するなら 2.1.293 以降が前提になる（2.1.287〜2.1.292 は、worker の再起動中に `classic.*` hook が飛ばされ、ラベルが黙って欠ける不具合があった。§2）
- 注（自動開始ターン）: `UserPromptSubmit` hook は cc が自分で始めたターンでも発火するので、L1 のラベルには人間以外のプロンプトが混ざる（§2）。扱いは[裁定待ち事項](../作業指示者裁定待ち事項.md#sec-1) J-15 で裁定待ちである。Claude の推奨は、ラベル「自動」を付けて残すこと（除外すると、OTel 側に残るラベルの無いプロンプトを hook の失敗による未付与と区別できない）。自動開始ターンかどうかの判定規則は、docs に区別するフィールドが無いので、Phase 3 で hook 入力の `prompt` の形と `prompt_id` の有無を確かめてから決める
- 注（失敗時の扱い）: L1 の hook は、失敗しても利用者のプロンプトを止めない作り（fail-open）にする。command hook に `onFailure: "block"`（2.1.295 で追加。docs 未反映。hook が起動しない・タイムアウト・想定外の終了コードのときに操作を止める設定）は付けない。Mod で実装する場合は `.catch` で失敗時に素通しにする（`claude plugin validate` が、`.catch` の無い gating hook として `classic.UserPromptSubmit` を警告する。[1-8 §7.3.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-1)）

L2 に hook（②）を足さない理由: ② が保存する `prompt_id`・コマンド名は、OTel の `user_prompt` イベントにもある（[1-1 §4.2](../01.実データ確認/調査報告書.md#sec-4-2)）。L2 で ② が新たに足すのは `cwd` 程度で、これは transcript のフォルダ名からも取れる。② の長所「OTel の設定に依存しない」も、OTel の設定（本文の記録）を前提にする L2 では効かない（v0.3 で案 2 から ② を外した）。

どちらの案も選ばない場合（本文を記録せず、hook も使わない）は ① だけになり、skill・サブエージェントを使わない自由入力の作業は「未分類」として集計する。

**最強の反論と残存リスク**

- 反論: L1 の hook は 1 プロンプトごとに待ち時間を足すので、成功基準「操作を増やさない」（計画書 §1.3）と実質的に相反する
  - 測った範囲では、待ち時間は 0.5 秒未満だった。llm_request の開始までの上乗せは、2.1.287 では `-p` で command hook 約 150 ms・Mod 約 30 ms、対話モードで command hook 約 440 ms・Mod 約 300 ms だった。2.1.296 では `-p` で command hook 約 155 ms・Mod 約 200 ms（Mod の方が大きい）、対話モードで command hook 約 235 ms・Mod 約 160 ms（Remote Control に接続した状態）だった。どちらが小さいかは版とモードで入れ替わる（各 n=3。[§2 の版・モード別の表](#sec-2-1)）
  - 残存リスク: command hook の対話モードの 6 回中 2 回（2.1.283 の i3・i4。初回プロンプト）は 2.1〜2.8 秒で、原因を特定していない。同じ起動のしかたの 2.1.287 の 3 回と、2.1.296 の対話モード（Remote Control に接続した状態・接続しない状態の各 3 回）では再現しなかった。標本は各 3 回と小さく、日常の長いセッションは測っていない。上乗せは版で動くので、Phase 3 で使う版で測り直す必要がある
  - Phase 3 の PoC で、対話モードと日常のセッションで同じ指標を測る。許容できなければ L2（hook なし）に寄せるか、① だけで運用する。「許容」の基準は作業指示者の判断事項で、暫定値（上乗せの中央値が 1 秒以下で、かつ、上乗せが 2 秒を超えるプロンプトが 1 割以下）を[裁定待ち事項](../作業指示者裁定待ち事項.md) J-12 に置いた（2.1.296 の値でも暫定値は変えていない）。測り方と標本数（モデル切替直後のプロンプトの扱い、hook の合算、Remote Control の有無の記録を含む）は [【別紙】V-ID別状況とPhase3実測項目 §2](../99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) にある
