## 0. サマリ

- **調査内容**: `~/.claude` 配下に実在するファイル・ディレクトリを実地確認し、公式 docs の「Application data」節と突き合わせた。transcript は Read で開かず、Node.js ストリーム集計スクリプトで全件処理した（[§1](#sec-1)）。
- **調査結果**
  - ファイル一覧は docs の分類（自動削除／保持／独自ルール）と概ね一致する。ただし `security/`（容量が大きい）等、docs に対応項目のない独自ディレクトリも存在する（[§2](#sec-2)）
  - `assistant` レコードの基本 4 トークン種・`uuid`/`parentUuid`/`isSidechain`/`sessionId` は観測全バージョン（2.1.150〜2.1.283）で出現率 100%。`thinking_tokens` は cc 2.1.237 以降のみフィールドが存在し、行単位では 60〜78%（記録形式起因。確定値は同一 `requestId` の最終行にある）（[§3.2](#sec-3-2)、[§3.4](#sec-3-4)）
  - `requestId` は同一値が複数行にまたがる（1 対 N、79.7% が重複）ため、突合設計は 1 対 1 を前提にできない（[§3.6](#sec-3-6)）
  - `agentId` は `isSidechain: true` の行と全件で一致し、OTel が持たない subagent 単位識別の補助候補になる（[§3.5](#sec-3-5)）
  - V-11(b) #4（managed settings）・#9（`cleanupPeriodDays`）はいずれも「一致」（[§5](#sec-5)）
- **結論・示唆**: transcript 突合（経路 (i)）は主線として成立するが、`requestId` の 1 対 N 関係と `thinking_tokens` のバージョン依存を前提にした設計が要る。cc 2.1.300 以降の transcript には API リクエストごとの system prompt・tools・parameters が入り、サイズも増える（短い `-p` の run で約 1.5〜2 倍）ので、取り込み・保存・公開の扱いを 2.1.296 以前より慎重にする必要がある（[§3.4](#sec-3-4)・[§6](#sec-6)）。Phase 2 の材料として `agentId` の併用と `stats-cache.json` の検算源としての活用を提案する（[§6](#sec-6)）。取り込み対象の判定自体は本調査の範囲外である。

## 1. 目的と方法

- **目的**: Phase 1 の調査項目 1-6（計画書 §4「Phase 1」表）として、`~/.claude`（本環境では `C:\Users\<user>\.claude`）配下に実在するファイル・ディレクトリを棚卸しし、①テレメトリと突き合わせる鍵（`session_id`・`request_id`・`prompt_id`・`uuid` 等）を持つか、②保存期間・形式が安定しているか、③既存 transcript の過去分から model / usage / thinking_tokens / skill 等をどこまで復元できるかを明らかにする。あくまで OTel を補う位置付けであり、本調査自体は「何を取り込むか」を決めない（計画書 §7 #4）。
- **方法**:
  - `~/.claude` 直下を実地確認し、公式 docs の「Application data」節（`llms-full.txt` 内 `# Explore the .claude directory` 章、`## Application data` 以下）の記載と突き合わせた。
  - 各ファイルの中身は `head` / Node.js ワンライナーでキー名（`Object.keys`）のみを確認し、値は本文性の低いメタ情報（バージョン文字列・件数・真偽値・タイムスタンプ等）に限って読んだ。プロンプト本文・ツール出力・API キー等の値は本報告書に転記していない。
  - transcript（`projects/*/*.jsonl` と subagent 分）は Read で開かず、Node.js（v24.14.0）のストリーム集計スクリプトで全件集計した。スクリプトは本 repo 外の scratchpad（`...\scratchpad\1-6\`）に置き、repo にはコミットしない。
  - installation・ダウンロード・`~/.claude` 配下の変更・削除、settings の変更は行っていない。
- **注記**: 本調査中もこのセッション自身が `~/.claude` 配下（transcript・history.jsonl 等）に書き込み続けているため、件数・サイズは数分単位でわずかに変動する。以下の数値は計測時点のスナップショットである。

## 6. Phase 2 に向けた材料

**有力候補（2 つ以内）**:

1. **transcript 突合（経路 (i)）に `agentId` を追加する**: 現行の設計方針（v2.1 §2.1 の経路 (i)、`request_id` による突合）に加えて、transcript の `agentId` フィールドを subagent 単位の補助鍵として使う。OTel 側は `agent_id` を持たない（スパンのみ・beta）ため、同型サブエージェントの並列実行を区別する唯一の手段になり得る（2026-10-26 追記。OTel 側に `agent_id` が無いのは 2.1.309 までで、2.1.310 以降の分は OTel のイベントの `agent_id` でも区別できる。`agentId` が唯一の手段になるのは 2.1.309 以前の分である。§3.5 の注記）。決め手: `isSidechain: true` と `agentId` の出現が全件で一致しており（[§3.5](#sec-3-5)）、追加のパース負荷なしに拾えるフィールドであること。懸念: 値の一意性・再利用性（同一セッション内で同じ subagent を複数回呼んだ場合に値がどう変わるか）は未検証。
2. **`stats-cache.json` を軽量な検算源として併用する**: 日別×モデル別のトークン集計（`dailyModelTokens`）とモデル別累計（`modelUsage`）を、OTel/transcript から算出した集計の整合性チェック（サニティチェック）に使う（[§2.2](#sec-2-2)）。決め手: 大きな transcript 群を読まずに済む小さい既存集計であり、`/usage` という cc 標準機能の裏付けデータであるため形式変更のリスクが相対的に低い。懸念: `effort`・skill・thinking トークンの内訳がなく、`lastComputedDate` が毎回最新とは限らない（今回は 5 日遅れ）ため、主集計には使えない。

**最強の反論と残存リスク**: 上記 2 候補は、1 利用者・約 1 か月分（件数は書かない。J-28）の transcript から見出したものであり、利用の偏り（使った skill・subagent の種類）の影響を受け得る（v0.4 で「1 セッション分」の誤記を訂正）。特に候補 1 の `agentId` は値の一意性（同一セッション内で同じ subagent を複数回呼んだ場合に値が変わるか）を検証しておらず、変わらない場合は補助鍵として機能しない。この反論は現時点で棄却できず、Phase 2 の設計判断前に追加検証することを残存リスクとして申し送る。

**その他の懸念**:

- `usage.output_tokens_details.thinking_tokens` はバージョン依存（2.1.237 以降）であり、行単位では 60〜78% しか出現しない（記録形式による。確定値は同じ `requestId` の最終行。[1-2 §3.2](../02.思考トークン取得経路/調査報告書.md#sec-3-2)）ため、過去分をそのまま思考トークン比率の分母に使うと、対象外の呼び出しを「思考なし」と誤判定するリスクがある。フィールド不在（バージョン起因）と値 0（実際に思考なし）を区別する設計が要る。
- `requestId` は 1 対 N（同一値が複数行にまたがる）が既定であるため、突合ロジックは「1 リクエスト = 1 行」を前提にできない。
- 2.1.288 から、応答の途中で API がタイムアウトすると、非対話セッションとサブエージェントは部分応答から続行し、thinking だけの応答は再試行する。これも `api_request` と transcript の件数がずれる要因になる（[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) D21）。突合ロジックは、上の 1 対 N と合わせて、この件数のずれも前提にする
