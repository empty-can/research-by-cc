## 0. サマリ

- **調査内容**: `~/.claude` 配下に実在するファイル・ディレクトリを実地確認し、公式 docs の「Application data」節と突き合わせた。transcript（316 ファイル、215.6 MB、57,860 行）は Read で開かず、Node.js ストリーム集計スクリプトで全件処理した（[§1](#sec-1)）。
- **調査結果**
  - ファイル一覧は docs の分類（自動削除／保持／独自ルール）と概ね一致する。ただし `security/`（301 MB）等、docs に対応項目のない独自ディレクトリも存在する（[§2](#sec-2)）
  - `assistant` レコードの基本 4 トークン種・`uuid`/`parentUuid`/`isSidechain`/`sessionId` は観測全バージョン（2.1.150〜2.1.283）で出現率 100%。`thinking_tokens` は cc 2.1.237 以降のみフィールドが存在し、行単位では 60〜78%（記録形式起因。確定値は同一 `requestId` の最終行にある）（[§3.2](#sec-3-2)、[§3.4](#sec-3-4)）
  - `requestId` は同一値が複数行にまたがる（1 対 N、79.7% が重複）ため、突合設計は 1 対 1 を前提にできない（[§3.6](#sec-3-6)）
  - `agentId` は `isSidechain: true` の行と完全一致（19,947/19,947）し、OTel が持たない subagent 単位識別の補助候補になる（[§3.5](#sec-3-5)）
  - V-11(b) #4（managed settings）・#9（`cleanupPeriodDays`）はいずれも「一致」（[§5](#sec-5)）
- **結論・示唆**: transcript 突合（経路 (i)）は主線として成立するが、`requestId` の 1 対 N 関係と `thinking_tokens` のバージョン依存を前提にした設計が要る。Phase 2 の材料として `agentId` の併用と `stats-cache.json` の検算源としての活用を提案する（[§6](#sec-6)）。取り込み対象の判定自体は本調査の範囲外である。

## 1. 目的と方法

- **目的**: Phase 1 の調査項目 1-6（計画書 §4「Phase 1」表）として、`~/.claude`（本環境では `C:\Users\<user>\.claude`）配下に実在するファイル・ディレクトリを棚卸しし、①テレメトリと突き合わせる鍵（`session_id`・`request_id`・`prompt_id`・`uuid` 等）を持つか、②保存期間・形式が安定しているか、③既存 transcript の過去分から model / usage / thinking_tokens / skill 等をどこまで復元できるかを明らかにする。あくまで OTel を補う位置付けであり、本調査自体は「何を取り込むか」を決めない（計画書 §7 #4）。
- **方法**:
  - `~/.claude` 直下を実地確認し、公式 docs の「Application data」節（`llms-full.txt` 内 `# Explore the .claude directory` 章、`## Application data` 以下）の記載と突き合わせた。
  - 各ファイルの中身は `head` / Node.js ワンライナーでキー名（`Object.keys`）のみを確認し、値は本文性の低いメタ情報（バージョン文字列・件数・真偽値・タイムスタンプ等）に限って読んだ。プロンプト本文・ツール出力・API キー等の値は本報告書に転記していない。
  - transcript（`projects/*/*.jsonl` と subagent 分）は Read で開かず、Node.js（v24.14.0）のストリーム集計スクリプトで全件集計した。スクリプトは本 repo 外の scratchpad（`...\scratchpad\1-6\`）に置き、repo にはコミットしない。
  - installation・ダウンロード・`~/.claude` 配下の変更・削除、settings の変更は行っていない。
- **注記**: 本調査中もこのセッション自身が `~/.claude` 配下（transcript・history.jsonl 等）に書き込み続けているため、件数・サイズは数分単位でわずかに変動する。以下の数値は計測時点のスナップショットである。

### 3.3 思考トークンの整合性チェック（V-2a 相当）

4. `attributionSkill` / `attributionAgent` / `agentId` はバージョンごとの出現率の差が大きいが、これは**フィールドの有無ではなく、そのバージョンで実際に skill/subagent をどれだけ使ったかという利用実績の差**であり、形式不安定の証拠ではない（例: 2.1.237 で `attributionSkill` が 0.4% しかないのは、そのバージョンで動いたセッションが skill をほとんど使わなかったため）。
5. `perTurnEffort` は 2.1.263 以前には一切出現せず、2.1.273 以降でのみ 100% 出現する。**直近数バージョンで新規追加されたフィールド**とみられ、計画書 §5「バージョンアップで属性が変わる」リスクの transcript 版の実例である。

### 3.5 `agentId` による subagent 識別（OTel にない情報の補完候補）

- `isSidechain: true` の行は 19,947 件あり、`agentId` フィールドの出現数（19,947 件）と**完全に一致**する。すなわち `agentId` は subagent（sidechain）の行にのみ付与され、メインスレッドの行には付かない。
- 仕様別紙 §1 は「`agent_id` は無い（スパンのみ）ので、同型サブエージェントの並列実行は区別できない」と OTel 側の制約を記す。transcript の `agentId` はこの制約を補える可能性がある候補である（同一 `subagent_type` を並列実行した場合に個体を区別できるかは、今回は確認していない。値そのものを比較する追加調査が必要）。

### 3.6 同一 `requestId` の重複（ストリーミング分割の実態）

- ファイル内で同一 `requestId` を持つグループは 8,872 件。うち 7,067 件（79.7%）が 2 行以上にまたがる。
- これは 1 回の API 応答が「テキストブロック」「tool_use ブロック」等、複数の `assistant` 型レコードに分かれて記録されるためとみられる（見込み。API 応答の内部構造までは今回未確認）。OTel の `api_request` イベントと transcript を `request_id` で突合する設計では、**1 対 1 ではなく 1 対 N の関係になる前提**で集計ロジックを組む必要がある。

### #4 managed settings の有無

### #9 `cleanupPeriodDays` の設定値と最古 transcript の日付

- **結果: 一致**
- **根拠**:
  - `~/.claude/settings.json`（ユーザ設定）・本 repo の `.claude/settings.json`（プロジェクト設定）のいずれにも `cleanupPeriodDays` キーは設定されていない。docs の既定値（30 日、最小 1、`0` は検証エラー）がそのまま適用される状態である。
  - 実測では、**主セッションの transcript（`projects/<project>/<session>.jsonl`、211 件）は全件が 2026-08-28（＝調査日 2026-09-27 の 30 日前）以降の mtime を持ち、30 日を超えて残っている主セッションは 0 件**であった。既定 30 日が実際に効いていることと整合する。
  - 一方、subagent transcript（`.../subagents/*.jsonl`）の中には mtime が 2026-08-20（38 日前）のものが存在した。個別に確認したところ、当該ファイルの親セッション（同じディレクトリの `<session>.jsonl`）自体の mtime は 2026-09-26 と新しく、docs の「subagent transcript は親セッションの transcript が消える時に一緒に削除される」という記載と整合する（親が生きている限り、古い subagent ファイルだけが単独で残ることは仕様どおりの挙動であり、`cleanupPeriodDays` の不整合ではない）。
  - `.last-cleanup`（2026-09-27T12:54:54.542Z）の存在から、当日中に retention sweep が少なくとも 1 回実行されたことが分かる。sweep が実際にどの `period_days` で走ったか（`retention_sweep` イベントの `period_days` / `used_default`）を OTel 側で裏付ける作業は、担当を 1-1 とする計画書の役割分担どおり本調査では行っていない。

## 6. Phase 2 に向けた材料

**有力候補（2 つ以内）**:

1. **transcript 突合（経路 (i)）に `agentId` を追加する**: 現行の設計方針（v2.1 §2.1 の経路 (i)、`request_id` による突合）に加えて、transcript の `agentId` フィールドを subagent 単位の補助鍵として使う。OTel 側は `agent_id` を持たない（スパンのみ・beta）ため、同型サブエージェントの並列実行を区別する唯一の手段になり得る。決め手: `isSidechain: true` と `agentId` の出現が完全一致しており（19,947/19,947、[§3.5](#sec-3-5)）、追加のパース負荷なしに拾えるフィールドであること。懸念: 値の一意性・再利用性（同一セッション内で同じ subagent を複数回呼んだ場合に値がどう変わるか）は未検証。
2. **`stats-cache.json` を軽量な検算源として併用する**: 日別×モデル別のトークン集計（`dailyModelTokens`）とモデル別累計（`modelUsage`）を、OTel/transcript から算出した集計の整合性チェック（サニティチェック）に使う（[§2.2](#sec-2-2)）。決め手: 215 MB の transcript を読まずに済む 12.8 KB の既存集計であり、`/usage` という cc 標準機能の裏付けデータであるため形式変更のリスクが相対的に低い。懸念: `effort`・skill・thinking トークンの内訳がなく、`lastComputedDate` が毎回最新とは限らない（今回は 5 日遅れ）ため、主集計には使えない。

**最強の反論と残存リスク**: 上記 2 候補は、1 利用者・約 1 か月分（316 ファイル、主セッション 211 件）の transcript から見出したものであり、利用の偏り（使った skill・subagent の種類）の影響を受け得る（v0.4 で「1 セッション分」の誤記を訂正）。特に候補 1 の `agentId` は値の一意性（同一セッション内で同じ subagent を複数回呼んだ場合に値が変わるか）を検証しておらず、変わらない場合は補助鍵として機能しない。この反論は現時点で棄却できず、Phase 2 の設計判断前に追加検証することを残存リスクとして申し送る。

**その他の懸念**:

- `usage.output_tokens_details.thinking_tokens` はバージョン依存（2.1.237 以降）であり、行単位では 60〜78% しか出現しない（記録形式による。確定値は同じ `requestId` の最終行。[1-2 §3.2](../02.思考トークン取得経路/調査報告書.md#sec-3-2)）ため、過去分をそのまま思考トークン比率の分母に使うと、対象外の呼び出しを「思考なし」と誤判定するリスクがある。フィールド不在（バージョン起因）と値 0（実際に思考なし）を区別する設計が要る。
- `requestId` は 1 対 N（同一値が複数行にまたがる）が既定であるため、突合ロジックは「1 リクエスト = 1 行」を前提にできない。
- `security/`（301 MB、うち大半が `agent-sdk-venv` という Python 仮想環境）は docs の Application data 表に対応項目がなく、sweep 対象かどうか不明。今後の設計で `~/.claude` 全体をバックアップ・複製する運用を検討する場合、このディレクトリの扱い（除外するか等)を別途確認したほうがよい。
