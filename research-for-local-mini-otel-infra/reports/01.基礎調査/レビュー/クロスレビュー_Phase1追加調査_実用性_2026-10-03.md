### I2. hook と Mod の比較材料が分散し、測定点・条件・管理停止の扱いが揃っていない

**観点**: 検証パターン具体性（副: 文書構造）

#### I2. 問題点

* **概要**: Phase 2 が command hook と Mod を選ぶための材料が 5 か所に分かれ、比較の軸と測定条件が揃っていない。さらに、職場環境の確認項目が Mod 側だけに偏っている。
* **問題点**:
  1. 比較材料の所在: 仕組み・API・管理（08 §4.1）、遅延の 3 値（08 §4.3）、03 表の ② 行、99 §3.3 と Q4 補足、別紙 §2、計画書 §5 の行。比較軸（実行形態、言語、遅延、`prompt_id` 結合、本文へのアクセス、保存先への書き込み手段、管理による停止条件、対話モードでの確認状況）を 1 表にした箇所が無い。
  2. 「待ち時間」の測定点が混在している。130〜370 ms は `hook_execution_complete` の `total_duration_ms`（hook 単体の所要時間）、135 / 287 / 166 ms は interaction span の開始から最初の `llm_request` span の開始までの遅延（hook の有無による差）である。03 の ② 行と 99 §3.3 は両方を同じ文脈に並べており、「Mod は hook より約 120 ms 小さい」（J-3）が、どの測定点の差かが文面から取れない。差で見ると hook は約 150 ms 増（287−135）、Mod は約 30 ms 増（166−135）である。
  3. 比較条件が非対称な可能性がある【推測】。08 §4.3 の表は command hook を「`UserPromptSubmit` と `SessionStart` の 2 つ」と書き、Mod は `classic.UserPromptSubmit` の 1 本である。測定区間は interaction 開始以降で `SessionStart` の影響は小さいと見込めるが、本数を揃えた比較ではない。標本は各 3 回、`-p` のみ、Haiku のみである。
  4. 管理による停止が両方向にあるのに、職場環境の確認項目は Mod だけである。08 §4.1 は、`allowManagedModsOnly` は利用者持ち込みの Mod を止めるが利用者の settings hook は動き続ける、`allowManagedHooksOnly` は利用者の settings hook も止める、`disableAllHooks` は全 Mod・全 hook を止める、と書く。別紙 §2 の職場環境表は「Claude Mods が managed settings（`allowManagedModsOnly` 等）で止められていないか」だけで、command hook が使えるか（L1 の代替手段が成立するか）を確かめる項目が無い。
* **影響**:
  1. Phase 2 の設計担当が比較表を一から作ることになり、各所の数値の測定点の取り違えが起き得る。
  2. 職場環境で `allowManagedHooksOnly` や `disableAllHooks` が設定されていると、Mod も command hook も使えず、L1 が成り立たない。この場合の判断（L2 または ① のみ）が Phase 3 の結果を待つことになり、確認項目に無いと見落とされる。
* **詳細**:
  1. 別紙 §2 は hook の待ち時間の行で測定点を併記しているが、「Mod の対話モードでの確認」「managed settings」は別の行に分かれている。
  2. 計画書 §5 の Mod の行は「設定によっては利用者の settings hook も止まる」と書くが、対応する Phase 3 の確認項目（Phase 3「手順書に含めるもの」）は Mod の可否だけである。
* **根拠**:
  1. 08 §4.1（管理の 4 キー）、§4.3（測定条件と 3 値、実測 3 の `total_duration_ms`）。
  2. 03 §2 の ② 行・Mods 行、99 §3.3 の L1 / L2 行、J-3、別紙 §2 の職場環境表、計画書 §5 と Phase 3。
