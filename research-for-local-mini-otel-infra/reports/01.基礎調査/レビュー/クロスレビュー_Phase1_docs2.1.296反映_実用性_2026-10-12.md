### I1. 職場の分類器の確認の手順が、`/status` を見る時点、通知への応答、通知が出ない場合の読み方、拒否で終わる結果を欠く

**観点**: 検証パターン具体性（副: 完了条件明瞭性）
**作業指示者判断**: 要（後続作業をブロックしない。既定は修正案 1）。要るのは、職場の cc で課金の通知が出たときに Enter（以後その session の分類器リクエストが課金されて続行）で進めてよいかである。通知は最初の対象の操作を保留するので、手順書にどちらかを書いておく必要がある

**該当箇所**: 計画書 L210（Phase 3 職場の確認「auto mode の分類器」）、V-ID 別紙 L79（職場環境の表の新しい行）、1-8 L706（§7.5 の「職場の確認」）、1-8 L457（D33）

#### I1. 問題点

* **概要**: 計画書 L210 と V-ID 別紙 L79 は、職場の cc が自前の分類器リクエストに落ちるかを、「`/status` の Auto mode server 行を記録する」「分類器が働く操作の前後で `api_request` の件数と `query_source` を比べる」「課金の通知が出たかを記録する」で確かめる。作業指示者本人が職場で実施する手順だが、docs の挙動に照らすと、次の 5 点が書かれておらず、結果が読み違えられるか、手順の途中で止まる。
* **問題点**:
  1. `/status` を見る時点: V-ID 別紙 L79 は、auto mode のセッションで `/status` を実行し、その後に操作を行う順序に読める。docs（auto-mode-classifier-billing）は、行が `Enabled` なのは「サーバーのチェックが判定している間」で、自前に落ちた後は `Disabled` になると書く。permission-modes は、自前への切り替えが「セッションの残りで確定した時点」で通知を出すと書く。起動直後に `Enabled` と出ても、最初の対象の操作の後に `Disabled` になりうる（推測。docs は起動直後の表示を書いていない）。操作の後にも `/status` を見ないと、`Enabled` を誤って記録する。
  2. 通知への応答: 通知は、対話では最初の対象の操作を保留する。Enter で続行（以後その session は自前の分類器リクエストで、課金される）、Esc または Ctrl+C でその操作を実行せずターンを止める（docs）。手順書にどちらを押すかが無いと、作業指示者が職場アカウントの費用に関わる選択を手順なしですることになる。`-p` では stderr に出る（stream-json では `system` の warning）が、これも記録の取り方が書かれていない。
  3. 通知が出ないときの読み方: gateway が特定できて通知が gateway を名指しした場合、承認すると「その端末で 24 時間」通知が再表示されない（docs）。2 回目以降の確認で通知が出なくても、サーバー側チェックに戻ったとは限らない。記録する値の「通知の有無」は、それだけでは判定にならない。判定は `/status` の行（操作の後）と `api_request` の増減を主にし、通知は補助にする必要がある。
  4. 第 3 の結果（拒否で終わる）: docs は、自前への切り替えとは別に、「gateway が応答を短くする、結果の形を書き換える」ときは、通知の代わりに「サーバーが判定を返さなかった」拒否になり、判定なしの応答が 10 回続くとターンが止まると書く（permission-modes L339 付近、errors の "The server returned no safety verdict"）。社内ゲートウェイ越しでは、1-8 D33 が挙げた「要求・結果を落とす」より、こちらが起きる可能性もある。計画書 L210・V-ID 別紙 L79 の記録する値に、この拒否の有無が無い。
  5. 前提の確認が無い: 職場の分類器を見るには、auto mode で起動している必要がある。auto mode は対応モデルだけで、管理者は `disableAutoMode`（managed settings）で止められる（docs の permission-modes。ローカル版 L17329 付近）。止まっていると Manual で起動し、`/status` に行が無いかもしれない。この「auto で起動しなかった」ときの記録（起動時の mode、モデル ID、`disableAutoMode` の有無）は、V-ID 別紙 L78 の別の行にモデル ID と `defaultMode` はあるが、`disableAutoMode` は文書のどこにも無い（`grep -rn disableAutoMode` で 0 件）。さらに「分類器が働く操作」の例が「作業フォルダ外への書き込みやシェルコマンド等」で、読み取り専用のシェルコマンドは、自前の分類器では既定許可でスキップされ、サーバー側チェックでは review を待つ（permission-modes）。同じ操作でも結果が変わるので、操作を「読み取り専用でないシェルコマンド」のように 1 つに決めたい。
  また、受信した `api_request` の件数を数える前提は、職場でループバック宛て送信が通る場合に限る。計画書 L206 は、ブロックされた場合の代替を Phase 2 で決めるとしている。ブロックされた場合の、この項目の代替（`/status` の行と通知だけで判定する、など）が書かれていない。
* **影響**:
  1. 職場の確認の結果が、`Enabled` の誤記録や「通知なし」の誤読で、「サーバー側チェックに乗る」という誤った結論になる。Phase 4 の見積もり（`cost_usd` の合計が実際より小さくなりうる）の前提が崩れる。
