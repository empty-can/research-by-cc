# 調査報告書 執筆者見解（1-5 ダッシュボード方式、2026-09-27）

対象成果物: [調査報告書.md](調査報告書.md)（v0.1 → v0.2）。本見解は `writing-guideline` Skill（`releases/執筆ガイドライン/.claude/skills/writing-guideline/SKILL.md`）に沿った改訂を実施した際の記録。レビューア（クロスレビューを実施する別 Agent）が執筆意図を把握した上でレビューに入るための参考資料として作成する。

## 1. 執筆過程の所感

- v0.1 は机上調査の事実収集を主目的に書いたため、構造は「調査目的 → 比較表 → 決め手」の直線的な順序のみで、想定読者・全体構成の可視化・内部参照のリンク化といった **読み手の負荷を下げる仕掛けが欠けていた**。ガイドラインを後から当てると、これらは「事実・判断を変えずに追加できる純粋な構造改善」であり、改訂の切り分けがしやすかった。
- 最も工数を要したのは **内部参照のリンク化（G1-4）** だった。§3 の注記が§4・§5・§7 から計 26 回引用されており、各引用を該当する注記へのアンカーリンクに変換する作業は、目視での逐次編集ではなく Python スクリプトによる正規表現一括変換 + 変換後のリンク整合性の機械検証（アンカー定義とリンク先の突合）で行った。約 100 件のリンクを人手で 1 件ずつ検証するのは非現実的なため、**「機械的に生成し、機械的に検証する」** 方針を取った。
- G3-10（リンクアンカーの動作確認）は、GitHub/VSCode でのアンカー生成規則の差異（英数字は小文字化・句読点除去等）に依存させると壊れるリスクが高いと判断し、章見出し・注記のすべてに **明示的な HTML アンカー（`<a id="secN">` / `<a id="noteN">`）** を付与する方式に統一した。これにより、レンダラー依存のスラッグ生成規則を一切当てにせず、プログラムで「リンク先アンカーがすべて実在するか」「重複アンカーがないか」を確認できる状態にできた。
- 外部資料（活動計画書・引継ぎ資料 v2.1・仕様別紙）への参照は、本文中の全出現箇所を深いアンカー付きリンクにする案と、代表箇所だけをファイルリンクにする案を比較し、後者を採った。理由は、外部文書側の見出しアンカーを個別に検証する時間的余裕がなく、G3-10 の「動作確認」を満たせない形でリンクを増やすことは避けたかったため。

## 2. ガイドライン改善案

- **G1-4（内外参照の相互リンク化）に「大量の同一注記への逆参照がある場合の効率的な変換手順」の補足があるとよい**。本件では機械的な正規表現変換 + プログラムによるリンク整合性検証という手順を自己判断で編み出したが、同種のドキュメント（比較表 + 番号付き注記形式）は他の調査報告書でも頻出するパターンであり、ガイドライン側に「注記アンカー化 → 一括正規表現変換 → リンク先存在チェックのスクリプト例」を用意しておくと、次回以降の再現性が上がる。
- **G3-10.1（アンカー命名規則と静的検証手順）に「明示的 HTML アンカーで統一する」選択肢を明記してほしい**。現状の記載は「レンダラーごとのスラッグ生成規則に従い、一致しない場合だけ明示的アンカーを使う」という順序だが、本件のように内部参照数が多いドキュメントでは、**最初から全見出し・全注記を明示的アンカーで統一する方が、検証コストも保守コストも低い**。この判断基準（参照密度が高い場合は明示的アンカー方式を第一選択にする）をガイドラインに追記する価値がある。
- **G3-7（Devil's Advocate）の粒度規定は、「採否の判定をしない」調査報告書での適用粒度に触れていない**。今回は GO/NO-GO 判定がない探索的調査だったため「章レベル・章数分のみ」を適用したが、「判定をしない」ことを明言している報告書での Devil's Advocate の狙い（結論そのものではなく、結論を導いた事実確認プロセスの限界を明示する）は、既存の粒度表（§7.1）だけでは読み取りにくかった。「判定なし報告書」というカテゴリを明示的に加えると判断が速まる。
