### 0.3 冒頭サマリ

**調査内容**: 活動計画書 Phase 1 の調査項目 1-5「ダッシュボード方式」として、cc の OTel テレメトリを可視化する方式を机上調査で比較した。自作 Node.js ダッシュボードを有力候補としつつ、Grafana、および軽量 OSS 6 候補（Evidence.dev・Metabase・Apache Superset・DuckDB UI・Observable Framework・Rill）を、活動計画書が指定する 7 つの比較軸で比較した。あわせて V-11(b) #29（Prometheus の OTLP 受信・delta 機能フラグ・保持期間）を確認した。インストール・実行は行わず、公式ドキュメント・GitHub 等での存在確認にとどめている（[§1](#sec-1)）。

**調査結果**: 最大の発見は、DuckDB 用 Grafana データソースプラグインが Linux/glibc 前提で **Windows ネイティブでは動かない**ことである（[§3 注 12](#note-12)）。これにより Grafana の実力は保存側（1-4）の選択に強く条件付けられる（[§7](#sec-7) 決め手 1）。また Rill は公式に WSL 導入が前提とされており、本活動の「WSL 不使用」制約と両立しない（[§3 注 30](#note-30)）。自作 Node.js と Observable Framework は、Windows ネイティブ対応・DuckDB 接続・コードによるレイアウト管理のいずれでも安定して高評価だった（[§7](#sec-7) 決め手 3・4）。V-11(b) #29 は現行 Prometheus 3.15.0 の docs と全項目一致した（[§6](#sec-6)）。

**結論・示唆**: 本調査単独では候補を 2 案に絞り切れない。ダッシュボード方式の優劣は保存側（1-4）の結論に依存するため、[§7](#sec-7) は「保存側が (A)(B)（DuckDB 系）に決まる場合」と「保存側が (C)（VictoriaMetrics/VictoriaLogs）に決まる場合」で条件分岐する結論を示す。1-4 と本調査を突き合わせる際は、この条件分岐表を起点にすることを推奨する。採否そのものの判定は作業指示者と Phase 2 の設計判断に委ねる。

## 1. 目的と方法

- **目的**: Phase 1 の調査項目 1-5（計画書 §4「Phase 1」表）として、cc の OTel テレメトリを可視化するダッシュボード方式を机上調査で比較する。作業指示者はレイアウトを度々変えたくなる見込みがあり、Node.js の自作ダッシュボードが有力候補（活動計画書 §1.4）。本調査はその有力候補と OSS を比較する。
- **調査日**: 2026-09-27。基線は cc 2.1.283、docs 2026-09-27 取得版（活動計画書 §2 冒頭）。
- **方法**: 机上調査（インストール・実行はしない。存在確認まで。計画書 1-5 の方法「自作 Node.js ダッシュボードと Grafana（Windows 版）等の OSS を比べる」に従う）。公式ドキュメント・GitHub・プラグインページを調査した。出典 URL のない記述は「見込み」と明記する。
- **採否の判定はしない**。事実収集と比較表まで行い、[§7](#sec-7) に「2 案以内に絞るなら何が決め手になるか」を書く。
- **前提の確認**（活動計画書・仕様別紙・引継ぎ資料 v2.1 から）: v2.1 §4.1 により、リクエスト単位のトークン内訳・コスト・`prompt.id` は **イベント側だけ**にある。メトリクス側（Prometheus/VictoriaMetrics が主に扱う領域）はリクエスト単位に分解できない集計済みカウンタである。そのため「メトリクスだけ」の経路では、見たいもの（作業分類 × モデル × effort ごとの詳細、高コストのプロンプト・セッションのランキングと明細）を再現できない。本調査での「Prometheus」「VictoriaMetrics」は、産出量（分母）や時系列の可視化としては候補になるが、トークン・コストの主表示はイベント側データ（DuckDB 上の JSONL、または VictoriaLogs 上のログ）を経由する前提で評価する。

## 2. 候補の概要

比較対象は、活動計画書が指定する自作 Node.js ダッシュボードと Grafana に加え、軽量 OSS の候補として活動計画書が例示する Evidence.dev・Metabase・Apache Superset・DuckDB UI・Observable Framework、および同種の候補として Rill を加えた計 8 候補とする（「その他の軽量 OSS」は 6 候補で、活動計画書の「候補は 4〜6 に抑える」の上限内）。

| # | 候補 | 一言 |
|---|---|---|
| 1 | 自作 Node.js ダッシュボード | 軽量サーバ + Chart.js / ECharts / Observable Plot / Vega-Lite 等。部品を設定ファイル化する構成を想定 |
| 2 | Grafana（+ データソースプラグイン） | 汎用可視化 OSS。DuckDB・SQLite・Prometheus・VictoriaMetrics/VictoriaLogs 等のデータソースと組み合わせる |
| 3 | Evidence.dev | Markdown + SQL を静的サイトにコンパイルする BI-as-code。現行の既定構成はホスト型「Evidence Studio」（ClickHouse）へ移行中で、ローカル DuckDB 接続は legacy 扱い（後述） |
| 4 | Metabase | Java jar で動く汎用 BI。GUI 中心、DuckDB は非公式ドライバ経由 |
| 5 | Apache Superset | Python 製の汎用 BI。Windows ネイティブでの導入難易度を確認する（活動計画書の指示） |
| 6 | DuckDB UI（`duckdb -ui`） | DuckDB CLI 同梱の SQL ノートブック + 自動プロファイラ。チャート作成機能は無い（後述） |
| 7 | Observable Framework | Markdown + データローダーで作る静的サイト生成ツール。Observable Plot / D3 を使う |
| 8 | Rill | DuckDB（または ClickHouse）を OLAP エンジンとする BI-as-code。YAML でダッシュボード定義。**Windows はネイティブ非対応で WSL 必須のため、本活動の制約と矛盾する（後述）** |

各候補の詳細な事実は [§3](#sec-3) の比較表に集約する。

**注記（根拠と詳細）**

<a id="note-1"></a>
1. 自作 Node: パネル定義を JSON/JS 設定オブジェクトとして持たせれば、レイアウト変更はファイル編集で完結する。Chart.js・Apache ECharts は単一の JSON 相当の「option」オブジェクトでチャートを定義でき（Chart.js は MIT、ECharts は Apache-2.0）、Vega-Lite は仕様そのものが JSON ドキュメントで「a concise, declarative JSON syntax」と明記されている（BSD-3-Clause）。Observable Plot（ISC）はマーク配列が JS オブジェクト寄りで、純粋な静的 JSON 化はやや劣る見込み（確度: Chart.js/ECharts/Vega-Lite は confirmed、Observable Plot の相対評価は likely）。出典: https://www.chartjs.org/docs/latest/getting-started/usage.html 、https://echarts.apache.org 、https://vega.github.io/vega-lite/docs/ 、各 GitHub の LICENSE。
<a id="note-2"></a>
2. SQL をどこに書くかは自作次第で完全に自由（ファイル・CLI・API 経由のどれでも可）。
<a id="note-3"></a>
3. Node.js は本活動の前提環境に既にある。管理者権限は不要（ユーザー権限で `node server.js` を起動できる）。
<a id="note-4"></a>
4. (A)(B) はいずれも DuckDB/JSONL/SQLite ベースであり、Node から直接クエリできる。
<a id="note-5"></a>
5. (C)（VictoriaMetrics/VictoriaLogs）は PromQL/LogsQL の HTTP API を自前で呼ぶコードが必要になる見込み。
<a id="note-6"></a>
6. DuckDB へのアクセス経路は 2 通りある。(i) `@duckdb/node-api`（Node ネイティブバインディング）は win32-x64 のプリビルドが npm 上に存在する（confirmed: https://www.npmjs.com/package/@duckdb/node-bindings-win32-x64 の `os: win32` `cpu: x64`）が、`engines` フィールドの記載がなく Node 18 対応は明記されていない（未確認・見込み）。(ii) DuckDB CLI（`duckdb.exe`）は「a single, dependency-free executable」で Windows 向けに事前ビルド配布されており、`-json` オプションで結果を JSON 出力できる（confirmed: https://duckdb.org/docs/stable/clients/cli/overview ）。Node から `child_process` 経由でこの exe を呼べば、Node バインディングのコンパイル・バージョン依存を完全に回避できる。これは (B) が前提とする収集用バイナリと同じ実行系である。SQLite 側は、Node 18 では組み込み `node:sqlite`（Node ≥22.5 で導入。confirmed: https://nodejs.org/api/sqlite.html ）が使えないため `better-sqlite3` に頼ることになるが、この npm パッケージは Windows 向けプリビルドを同梱しつつも、環境によっては `node-gyp rebuild` が誤って走り失敗する報告がある（見込みリスク。1-4 での実機確認を推奨）。出典: https://github.com/WiseLibs/better-sqlite3/issues/1516 （`gypfile:false` でも Windows で `node-gyp`/Python 呼び出しが発生する報告）。
<a id="note-7"></a>
7. 受信・保存・集計・表示のすべてを自前実装するため、cc のバージョンアップへの追従や不具合対応もすべて自前になる。
<a id="note-8"></a>
8. コードベース全体が repo で管理できるため、Claude Code によるレビュー・改修が最もしやすい候補。
<a id="note-9"></a>
9. Grafana はダッシュボードをファイルからプロビジョニングできる。`provisioning/dashboards/` 配下の YAML でパスを指定し、`updateIntervalSeconds` が 10 秒以下ならファイルシステムを監視して自動反映、10 秒超ならポーリングする（confirmed: https://grafana.com/docs/grafana/latest/administration/provisioning/ 「After Grafana provisions your dashboards, it checks the filesystem for changes and updates dashboards as needed」）。ダッシュボード JSON の編集は GUI なしで完結する。
<a id="note-9b"></a>

## 4. 探索期 / 定常期で分ける案の検討

引継ぎ資料 v2.1 §3.1・§3.2 は、保存側（1-4 の対象）について「探索期は DuckDB の SQL で切り口をすぐ変えられる」「定常期は指標が固まったら Prometheus + Grafana を追加する（temporality を cumulative に切り替える）」という 2 段階の方針を示している。本項目（1-5・ダッシュボード方式）の観点では、この 2 段階方針を含め、次の 3 つの分け方を比較する。記号 E1〜E3 は本節だけで使う（まとめ報告書の保存案 S1 / S2・思考案 T1 / T2・タグ案 L1 / L2 とは無関係。v0.3 で「案 A〜C」から改名）。

| 分け方 | 探索期 | 定常期 | 長所 | 短所 |
|---|---|---|---|---|
| E1. v2.1 の 2 段階案（ツールを切り替える） | 専用ダッシュボードなし。DuckDB CLI / DuckDB UI 等で SQL を都度実行 | Prometheus + Grafana を追加し、固まった指標をパネル化 | 探索期のコストが低い（SQL を書くだけ）。定常期は運用向けの見た目が整う | 指標が固まった判断が要る。移行時に「同じ集計を Grafana パネルに書き直す」作業が発生する。[§3](#sec-3) のとおり Grafana から DuckDB への直接接続は Windows で不可に近く、定常期に Prometheus（メトリクス）だけでは見たいもの（プロンプト単位の明細等）を再現できない |
| E2. 自作 Node ダッシュボード 1 本で両期をまかなう | 設定ファイルに一時的なクエリ・パネルを追加して確認 | 同じ仕組みの中で、安定したパネルを正式な設定として整理し直す | ツールを切り替えない。パネル定義がすべて repo 管理下にあり、Claude Code に改修を任せやすい（[§3 注8](#note-8)） | 探索期の「とりあえず SQL を試す」体験は自作次第で、専用 SQL ノートブックほど軽快にならない可能性がある。実装・保守の負荷は自作側に集中する（[§3 注7](#note-7)） |
| E3. SQL ファイル自体がダッシュボードになるツール 1 本でまかなう（Evidence.dev / Observable Framework） | Markdown+SQL ファイルを追加すればそれがページになる | 同じファイルをそのまま残す・整理する。「探索用ファイル」を「正式なページ」に格上げする作業の限界コストが小さい見込み | 探索と定常の境目がほぼ消える。SQL を書く行為自体が成果物になる | ツールの学習コスト。Evidence.dev はホスト型 Studio への方向転換中で legacy 経路の継続性に注意（[§3 注22](#note-22)・[注23](#note-23)）。両ツールとも保存側 (C) VictoriaMetrics/VictoriaLogs との相性は限定的（[§5](#sec-5)） |

E1 は v2.1 が既に採用している考え方だが、本調査で判明した「Grafana → DuckDB の Windows 向け経路がほぼ塞がっている」という事実（[§3 注12](#note-12)）により、定常期に Grafana を使う場合は保存側の選択（1-4）が (C) VictoriaMetrics/VictoriaLogs であることが前提になりやすい。E2・E3 は、作業指示者の「レイアウトを度々変えたくなる見込み」という前提（活動計画書 §1.4）に対し、ツール切り替えという追加の意思決定点を発生させない点で優位がある見込みだが、判定は本調査の範囲外とする（[§7](#sec-7) で決め手として扱う）。

**補足（DuckDB UI・Rill の位置付け）**: DuckDB UI は SQL ノートブック + 自動プロファイラであり、チャート作成機能を公式には持たない（[§3 注24](#note-24)）。そのため「探索期の使い捨てクエリ実行」には適するが、そのまま定常期の「見る画面」には育たない見込みで、E1 の探索期側の道具（DuckDB CLI 等）と同格に位置付けられる。Rill は本活動の環境制約（Windows ネイティブ・WSL 不使用）と両立しないため、探索期・定常期のいずれの案にも組み込めない（[§3 注30](#note-30)）。

## 5. 保存側候補 (A)(B)(C) との組み合わせ表

保存側候補は活動計画書 §1・1-4 の定義に従う: (A) Node 自作受信 + SQLite/DuckDB、(B) otelcol-contrib + JSONL + DuckDB、(C) VictoriaMetrics/VictoriaLogs。**前提の再確認（[§1](#sec-1)）**: (A)(B) は DuckDB 経由でイベント（`api_request` 等）の生データにアクセスできるため、見たいものの全項目に対応できる。(C) は VictoriaMetrics（メトリクス）だけでは対応できず、VictoriaLogs（ログ）側にイベント相当のデータを入れる設計が前提になる（1-4 の検討事項）。

| ダッシュボード候補 | (A) Node自作+SQLite/DuckDB | (B) otelcol+JSONL+DuckDB | (C) VictoriaMetrics/VictoriaLogs |
|---|---|---|---|
| 1. 自作 Node.js | 可・Node バインディングまたは `duckdb.exe -json` 経由で直接クエリ（[§3 注6](#note-6)） | 可・同上（JSONL を DuckDB 経由で読む） | 見込み・VM/VL の HTTP API（PromQL/LogsQL）を自前実装すれば可 |
| 2. Grafana | 不可に近い（DuckDB プラグインが Linux/glibc 限定）／見込みで SQLite プラグイン経由なら可（[§3 注12](#note-12)） | 同左（DuckDB プラグインが Windows 非対応のため、JSONL を DuckDB で読む経路は事実上不可。SQLite へ ETL すれば SQLite プラグインで可） | 見込み・公式プラグインはカタログにあるが Windows 対応は未確認 |
| 3. Evidence.dev | 可・legacy `@evidence-dev/duckdb` コネクタで DuckDB ファイルに接続（[§3 注22](#note-22)） | 可・同上（JSONL は事前に DuckDB へ取り込む前提） | 不可・専用コネクタなし |
| 4. Metabase | 可（SQLite 標準／DuckDB は非公式ドライバ、[§3 注16](#note-16)） | 可（同上。JSONL は事前に DuckDB ファイル化する前提） | 不可・Metabase は SQL 系 BI で時系列 DB 用のコネクタを持たない |
| 5. Superset | 可（`duckdb-engine`／SQLite 標準、[§3 注19](#note-19)） | 可（同上） | 不可・公式コネクタなし |
| 6. DuckDB UI | 可・DuckDB ネイティブ、ファイルを直接 `ATTACH`（[§3 注24](#note-24)・[注25](#note-25)） | 可・同上 | 不可 |
| 7. Observable Framework | 可・DuckDB-Wasm でファイルを直接アタッチ、またはデータローダーで DuckDB CLI を呼び出す（[§3 注28](#note-28)） | 可・同上 | 見込み・データローダーから VM/VL の HTTP API を呼べば可 |
| 8. Rill | 評価保留（本体が WSL 前提のため。[§3 注30](#note-30)） | 評価保留 | 評価保留 |

## 7. 2 案以内に絞るための決め手と懸念

採否の判定はしないが、Phase 2 の設計判断（活動計画書 Phase 1 完了条件「候補が 2 案以内に絞られている」）に向けて、決め手になり得る事実と懸念を挙げる。

**決め手になり得る事実**

1. **Grafana の実力は、保存側（1-4）の選択に強く条件付けられる。** Grafana 自体はファイルプロビジョニングでダッシュボード JSON をコード管理でき（[§3 注9](#note-9)）、Windows ネイティブでも導入できる（[§3 注11](#note-11)）という長所がある。しかし本調査で判明した最大の事実は、公式・非公式を問わず DuckDB 用 Grafana データソースプラグインが Linux/glibc 前提で Windows 非対応であること（[§3 注12](#note-12)）。したがって Grafana を採る場合、(A)(B) の DuckDB ファイルへ直接つなぐ経路は事実上なく、①SQLite データソースプラグイン経由に迂回する（Windows 対応は見込みどまり）か、②保存側を (C) VictoriaMetrics/VictoriaLogs に決め、公式プラグイン（Windows 対応は未確認）経由でつなぐ、のどちらかを選ぶ必要がある。「Grafana を採るなら保存側は事実上 (C) 寄りになる」という依存関係が、1-4 との整合を取る際の最重要事項である。
2. **見たいもの（プロンプト単位の明細・ランキング）はイベント側データが必要で、メトリクス専用の経路では作れない（[§1](#sec-1)）。** Prometheus・VictoriaMetrics はメトリクス（産出量や集計値）の可視化には向くが、本調査の想定画面（期間サマリ、クロス集計、推移、高コストのプロンプト・セッションのランキングと明細）のうち後者 2 つは、イベント（`api_request` 等）に基づく必要がある。VictoriaLogs（ログ）側にイベント相当データを入れる設計であれば (C) でも成立し得るが、これは 1-4 の検討事項であり、1-5 の時点では「Grafana + Prometheus だけ」では見たいものの一部が欠落する、という制約として持ち越す。
3. **自作 Node.js は、レイアウト変更・接続性・Claude Code への委任しやすさのすべてで安定して高評価だが、保守負荷のすべてを自分で引き受ける。** DuckDB へは Node バインディング（Windows プリビルドあり、Node 18 対応は見込み）と `duckdb.exe -json` の子プロセス呼び出し（バインディング不要・Node 版数非依存）の 2 経路があり、後者は職場環境（Node 18 の可能性）でも安定して動く見込みが高い（[§3 注6](#note-6)）。可視化ライブラリ（Chart.js・ECharts・Vega-Lite）はいずれも JSON 設定オブジェクトでチャートを定義でき、レイアウトの設定ファイル化と相性がよい（[§3 注1](#note-1)）。
4. **Observable Framework は、自作に近い柔軟性を持ちながら枠組みが用意されている「中間案」になり得る。** Windows ネイティブ対応（Node 18 対応を明記。[§3 注29](#note-29)）、DuckDB/SQLite への接続が Wasm 経由でネイティブバインディング不要（[§3 注28](#note-28)）、Markdown ファイルでのレイアウト管理（Claude Code に任せやすい）という組み合わせは、自作の「全部自分で作る」負荷と、既製 BI ツールの「コード管理しにくい」弱点の中間に位置する。
5. **Evidence.dev は同種の候補だが、製品自体がホスト型 Studio へ方向転換中という懸念がある。** ローカル DuckDB 接続（legacy 経路）は現時点で維持されているが、公式ドキュメントの主要動線ではなくなりつつあり、将来的な継続性に不確実性がある（[§3 注22](#note-22)・[注23](#note-23)）。
6. **Metabase・Superset は、いずれも「DuckDB/SQLite への接続はできるが、レイアウトのコード管理は弱い（Metabase は有償版のみ）か公式外（Superset は YAML エクスポートが OSS で使えるが GUI が既定）」という共通の弱点を持つ。** Metabase はさらに Java 25 という比較的新しいランタイムの持ち込みが職場環境で可能かという懸念がある（[§3 注15](#note-15)）。Superset は Windows ネイティブ導入が公式に非対応とは書かれていないものの、docs が対象外としている（[§3 注18](#note-18)）。
7. **DuckDB UI・Rill は、いずれも「ダッシュボード」としては候補から外れる。** DuckDB UI はチャート作成機能を持たない SQL ノートブックであり（[§3 注24](#note-24)）、Rill は Windows で WSL を必須とし本活動の制約と両立しない（[§3 注30](#note-30)）。

**懸念（未確認のまま残る事項）**

- Grafana + SQLite プラグイン経由、または Grafana + VictoriaMetrics/VictoriaLogs 公式プラグイン経由の Windows 対応は、いずれも「未確認」にとどまる。2 案に絞る前に、少なくとも一方は実機で確認する価値がある。
- 自作・Observable Framework とも、Node 18（職場環境で使われる可能性がある版。職場環境の実際の版は未確認で、ルート `CLAUDE.md` の環境特性「Node.js v18+」を下限として仮定した。v0.3 で出典を追記）での DuckDB 接続（Node バインディングまたは Wasm）の実際の動作は未検証（机上調査の範囲外）。
- Evidence.dev の新 CLI がオフライン・ローカル DuckDB だけで動くか（Studio アカウント不要か）は未確認。
- DuckDB UI の初回起動時のネットワークアクセス（`ui.duckdb.org`）が、職場環境のネットワークポリシーで許可されるかは未確認。

**1-5 単独では 2 案に絞れない — 1-4（保存側）の結論が先行する**

本調査で最も大きな決め手（決め手 1）は、Grafana の実力が保存側の選択に強く条件付けられるという事実である。そのため、ダッシュボード方式の絞り込みは保存側の選択に応じて次のように条件分岐する。

- **保存側が (A)(B)（DuckDB 系）に決まる場合**: Grafana は Windows ネイティブでは DuckDB への直接接続経路がほぼ塞がっており（決め手 1）、候補から実質的に外れる。残る候補は「自作 Node.js」「Observable Framework」（いずれも DuckDB への接続に Windows 対応の確証がある）と、継続性への懸念付きで「Evidence.dev」になる。
- **保存側が (C)（VictoriaMetrics/VictoriaLogs）に決まる場合**: Grafana の公式データソースプラグインが候補に戻るが、Windows 対応は未確認のままであり、実機確認が要る（懸念参照）。「自作 Node.js」「Observable Framework」も VM/VL の HTTP API を自前実装すれば対応できる。

したがって、本項目（1-5）の結論は「保存側の決定を待って、その条件下で候補を絞る」というかたちにとどめる。1-4 と 1-5 を突き合わせる際は、この条件分岐表を出発点にすることを推奨する。判定そのものは作業指示者と Phase 2 の設計判断に委ねる。

**Devil's Advocate（本章の結論への最強の反論）**: 本章は保存側を (A)(B) と (C) の二分法で条件分岐しているが、実際には「保存は DuckDB（(A)(B)）で行いつつ、Grafana 用に一部データを SQLite へ ETL する」ような中間構成もあり得る。この場合、保存側が (A)(B) に決まっても Grafana が完全には候補から外れない可能性がある。

- **棄却根拠**: この中間構成は決め手 1（[§3 注12](#note-12)）で「SQLite データソースプラグイン経由に迂回する」候補として既に言及済みであり、条件分岐の対象外ではなく「保存側が (A)(B) の場合に残る候補」の一部として扱っている。反論は棄却できるが、SQLite プラグインの Windows 対応が「見込み」にとどまる点（懸念の 1 件目）は残存リスクとして明示済みである。
