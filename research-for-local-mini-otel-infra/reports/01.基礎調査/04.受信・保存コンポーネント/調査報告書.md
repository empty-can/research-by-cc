## 0. サマリ

- **調査内容**: Phase 1 の 1-4 として、cc の OTel テレメトリを Windows ネイティブ・Docker 不要で受信・保存する 3 候補 — (A) Node.js 自作 OTLP/HTTP 受信 + SQLite/DuckDB、(B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB、(C) VictoriaMetrics/VictoriaLogs の単体バイナリ — を机上で比較した。あわせて V-11(b) の担当分 9 項目（#12、14、15、17、18、19、26、27、28）を確認した
- **調査結果**
  - DuckDB は「`.duckdb` 形式のファイル」に対して単一書き込みプロセス制限を持つ。受信プロセスと別プロセスのダッシュボードが同じ DuckDB ファイルを同時に読み書きすることはできない（[§3.3](#sec-3-3)）。SQLite（WAL）はこの制限を持たない
  - V-11(b) #19 は**差異あり**: VictoriaMetrics は v1.132.0 以降、delta temporality の値をそのまま保存できる。引継ぎ資料 v2.1 が前提としていた「delta は破棄される」という記載は現行バージョンでは当てはまらない（[§5](#sec-5)）
  - `node:sqlite` は Node.js 組み込みで追加の native ビルドツールが不要。本活動の基線 Node v24.14.0 で利用できるが、release candidate 化は v25.7.0 以降で、現時点ではまだ experimental 表示が残る（[§3.4](#sec-3-4)）
  - cc が `http/json` で送信でき、Node.js の数十行の受信スクリプトで 3 シグナルとも受信できることは、1-1 の実測で裏付けられている。(A) の実装負荷が低いという結論は、机上の推定から実測付きの結論に格上げできる（[§4.2](#sec-4-2)）
  - 4 セッションを同時に `-p` 実行しても欠落は無かった（1-1 実測。cc 2.1.283）。cc 側の送信は複数セッション同時でも問題を起こさないことが裏付けられたが、(B)(C) 固有の受信コンポーネントでの同時受信は未検証のまま残る（[§4.4](#sec-4-4)）
  - 2026-10-19 追記: logs・metrics に出ず、traces の span にだけ出る API 呼び出しがある。費用の集計には traces の span も含めるので、(A) は traces も受けて保存する（集計の正本は計画書 Phase 2 で決めるが、受け口はその決定を待たずに作れる。[§6](#sec-6) の注記）
- **結論・示唆**: 本報告書は採否の判定を行わない。[§6](#sec-6) に、2 案以内へ絞り込むための決め手候補・懸念・Phase 3 で実測すべき点を整理した。Phase 2 の設計判断はこれらの事実を入力に行う

## 1. 目的と方法

Phase 1 基礎調査の項目 1-4（[計画書](../../00.活動計画/活動計画書.md) §4）として、cc の OTel テレメトリを Windows ネイティブ・Docker 不要で受信・保存する構成の候補を机上で比較する。判定したいことは、導入・常駐の手軽さ、集計クエリの書きやすさ、UI との相性、データ消失への強さ、OTLP プロトコル対応である（計画書 1-4「方法」）。

- **調査日**: 2026-09-27（机上調査。実機での確認は Phase 3）
- **対象**:
  - (A) Node.js の自作 OTLP/HTTP 受信 + SQLite（`better-sqlite3` / `node:sqlite`）または DuckDB（`@duckdb/node-api`）
  - (B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB（引継ぎ資料 v2.1 の採用構成）
  - (C) VictoriaMetrics（メトリクス）/ VictoriaLogs（ログ）の単体バイナリ
- **禁止事項の遵守**: インストール・ダウンロード・実行は行っていない。ローカルでの確認は `node --version`、`where tar`、`where duckdb` の**存在確認のみ**（下記）。他はすべて公式ドキュメント・GitHub Releases・npm レジストリの参照
- **採否の判定はしない**。事実収集と比較表、および [§6](#sec-6) の「決め手」の記述にとどめる

<a id="sec-2"></a>
## 2. 各候補の概要

<a id="sec-2-a"></a>
### (A) Node.js 自作 OTLP/HTTP 受信 + SQLite / DuckDB

```
Claude Code
  └─ OTLP/HTTP (http/json または http/protobuf) → 127.0.0.1:<port>
       └─ Node.js プロセス（自作）
            ├─ /v1/logs    を受信 → パース → INSERT
            ├─ /v1/metrics を受信 → パース → INSERT
            └─ traces      を受信 → パース → INSERT（2026-10-19 追記）
                 └─ SQLite（better-sqlite3 / node:sqlite）
                    または DuckDB（@duckdb/node-api）に永続化
```

受信・パース・保存を 1 プロセスにまとめる自作構成。traces の受け口は 2026-10-19 に足した（費用の集計に traces の span も含めるため。[§6](#sec-6) の注記）。保存先を SQLite にするか DuckDB にするかで、後述のとおり UI との相性が変わる。

<a id="sec-2-b"></a>
### (B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB

引継ぎ資料 v2.1 §3 の採用構成そのもの（再掲）。

```
Claude Code
  └─ OTLP (http/protobuf 等) → 127.0.0.1:4318
       └─ otelcol-contrib.exe
            ├─ logs    → file exporter → otel-logs.jsonl
            └─ metrics → file exporter → otel-metrics.jsonl
                 └─ DuckDB（CLI または他プロセス）が JSONL を read_json で読む
```

受信・変換は otelcol-contrib、保存はプレーンな JSONL ファイル、集計は別プロセスの DuckDB、と役割が分かれる。

<a id="sec-2-c"></a>
### (C) VictoriaMetrics / VictoriaLogs の単体バイナリ

```
Claude Code
  └─ OTLP metrics → VictoriaMetrics（単体バイナリ。/opentelemetry/v1/metrics）
  └─ OTLP logs    → VictoriaLogs（単体バイナリ。/insert/opentelemetry/v1/logs）
```

メトリクスとログで別々の単体バイナリが要る（2 プロセス構成）。cc の分析の主軸は `api_request` などの **log イベント**であり（[引継ぎ資料 v2.1](../../00.活動計画/handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md) §4.1「トークンとコストの分析では、イベントのデータが主になる」）、この構成では **VictoriaLogs（LogsQL）が集計の主役**になる。VictoriaMetrics（MetricsQL）は産出量など補助指標向け。traces（beta）に対応する VictoriaMetrics ファミリー製品（VictoriaTraces 等）は本調査では確認していない。2026-10-19 追記: 「主軸は log イベント」は引継ぎ資料 v2.1 の前提である。集計の正本は計画書 Phase 2 で決め、traces の span も集計に含める（[§6](#sec-6) の決め手の 1 点目と traces の注記）。

### 3.1 導入・常駐

| **(A)-SQLite**（`node:sqlite` または `better-sqlite3`） | Node.js は導入済み前提。追加は npm パッケージのみ | 不要（npm install はユーザ権限で完結する見込み。社内プロキシで npm レジストリが許可されているかは別途要確認） | 現在ユーザのタスクスケジューラで「ログオン時」トリガーを自分のタスクとして作る分には管理者権限は不要（既定でバッチジョブとしてのログオン権が付与される）[D21]。真の Windows Service 化（`sc.exe create` 等）は管理者権限が要る[D20] |

| **(B)** otelcol-contrib + DuckDB | `otelcol-contrib_<ver>_windows_amd64.tar.gz`（展開して直接実行するポータブル版）と `_windows_x64.msi`（インストーラ）の両方が GitHub Releases に存在（v0.161.0 で確認）[D7] | tar.gz を展開して直接実行するだけなら管理者権限は不要と見込む（公式の Windows 導入ページはこの実行方法の権限要否を明記していないが、非システムディレクトリへの実行ファイル配置と非特権ポートへの bind は一般に管理者権限を要さない）[D22]。`.msi` は Collector を Windows Service として登録するインストーラであり[D22]、サービス登録・`sc.exe create` は管理者権限のあるプロンプトが要る[D20] | tar.gz 版なら (A) と同じ非管理者の常駐手段（タスクスケジューラ）が使える。`.msi` は Windows Service として登録される前提の配布形態[D22] |
| **(C)** VictoriaMetrics + VictoriaLogs | VictoriaMetrics・VictoriaLogs とも `*-windows-amd64-<ver>.zip` が GitHub Releases に存在（VM v1.152.0、VL v1.51.1 で確認）[D8][D9] | (B) の tar.gz と同様、zip を展開して直接実行するだけなら不要と見込む。正規 Windows Service 化は (B) と同様に管理者権限が要る見込み | 同上。(A)(B) と同じ非管理者の常駐手段（タスクスケジューラ）が使える見込み |

### 3.2 プロトコル・シグナルの受け方（詳細は [§4](#sec-4) も参照）

| | OTLP プロトコル対応 | metrics / logs / traces の受け方 | temporality（delta/cumulative）の扱い |
|---|---|---|---|
| **(A)-SQLite** / **(A)-DuckDB**（保存先の違いはこの軸に影響しない） | 自作次第。`http/json` を選べば JSON パースのみで済む。`http/protobuf` を選ぶ場合は自前でデコーダが要る（[§4](#sec-4)）。実際に cc を `http/json` で送信させ、Node.js の数十行の受信スクリプトで 3 シグナルとも受信できることは [1-1 報告書](../01.実データ確認/調査報告書.md#sec-1) の実測で確認済み | 自作でエンドポイントを分けて実装する必要がある（`/v1/metrics`、`/v1/logs`。cc の設定例にもこのパスが出てくる[D1]）。柔軟だが実装量が増える。traces も受ける（2026-10-19 追記。[§6](#sec-6) の注記） | 自作なので delta を素直に加算していく実装にできる（cc既定の delta のまま扱える。仕様別紙 §4） |
| **(B)** | Collector の OTLP receiver は `http/json` と `http/protobuf` の両方をネイティブに受け付ける（受信側の実装負荷はどちらでも同じ） | file exporter のパイプラインを metrics 用・logs 用に分けて設定するだけで済む（v2.1 §5.4 の設定例どおり）。traces（beta）を使う場合も pipeline を追加するだけ | file exporter はそのまま JSON 化するだけなので delta のまま記録され、集計時に加算すればよい |
| **(C)** | VictoriaMetrics の OTLP metrics 受信エンドポイント（`/opentelemetry/v1/metrics`）は、ドキュメントの記載が protobuf エンコードのリクエストを前提にしている[D10]。`http/json` でも受け付けるかは未確認。VictoriaLogs の OTLP ログ受信が `http/json`/`http/protobuf` のどちらに対応するかも未確認 | metrics は VictoriaMetrics、logs は VictoriaLogs と**別バイナリ**で受ける。リソース属性は既定で VictoriaLogs の「ログストリームのフィールド」として扱われる（`VL-Stream-Fields` ヘッダで変更可）[D11]。traces に対応する専用バイナリは本調査では未確認 | VictoriaMetrics は **v1.132.0 以降、delta temporality の値をそのまま保存する**（`sum_over_time()` / `rate_over_sum()` で集計）とドキュメントに明記されている[D10]。現行の最新版（v1.152.0）はこれを含む。[§5](#sec-5) V-11(b) #19 で詳述 |

<a id="sec-3-3"></a>
### 3.3 保存・集計・UI との相性

| | 集計クエリの書きやすさ | 受信プロセスとダッシュボード（読み手）プロセスの同時アクセス | UI との相性 | データ消失への強さ（再起動・異常終了） | 保存容量・保持期限 | 圧縮 |
|---|---|---|---|---|---|---|
| **(A)-SQLite** | SQL（SQLite 方言）。ウィンドウ関数等は使えるが、JSON 型の柔軟な扱いは DuckDB ほど強くない | **○**。SQLite の WAL モードは「書き込み側と読み取り側が互いをブロックせず並行して動作でき、これは同一ホスト上の別プロセス間でも成立する」と公式ドキュメントに明記されている（ネットワークファイルシステム越しでは不可）[D-sqlite]。受信プロセスが書き込み、別プロセスのダッシュボードが読む、という構成に素直に対応する | 自作 Node ダッシュボードとの相性が良い。別プロセス構成でも WAL の恩恵を受けられる | 自作コードの実装次第。SQLite はトランザクションコミット後は永続化される一般的な設計 | 運用者が明示的に削除しない限り、SQLite ファイルは自然には縮まない（保持期限＝TTL に相当する機能はない） | 自作なので任意（Node の `zlib` で `.gz` を作れる。追加ソフト不要） |
| **(A)-DuckDB** | SQL（DuckDB 方言）。`GROUP BY` の書き換えだけで集計の切り口をすぐ変えられる（v2.1 §3.1 の想定どおり） | **✕（要注意）**。DuckDB の公式ドキュメントは「read-write 接続と read-only 接続を、複数プロセスにまたがって同時に同じデータベースファイルに接続することはできない」と明記している[D4]。自作の受信プロセスが `.duckdb` ファイルを read-write で開いている間、**別プロセスのダッシュボードが同じファイルを読むことはできない**。回避には、受信プロセス自身にクエリ用の HTTP API を持たせる、または定期的にファイルを閉じる／エクスポートする設計が要る | 上記の制約を設計で回避する必要がある（受信プロセスに問い合わせ API を持たせる等） | 自作コードの実装次第（DuckDB も同様にトランザクションコミット後は永続化される一般的な設計） | 同上（保持期限に相当する機能はない。[§5](#sec-5) #12） | 同上 |
| **(B)** | (A)-DuckDB と同じ SQL の書きやすさ。ただし JSONL の入れ子構造（`resourceLogs[] → scopeLogs[] → logRecords[]`）を毎回展開するクエリが要る（引継ぎ資料 v2.1 §5.5 のひな形） | **○（見込み）**。DuckDB の単一書き込みプロセス制限は、公式ドキュメントの記載範囲が「`.duckdb` 形式のデータベースファイル」であり[D4]、file exporter が書き出す **プレーンな JSONL テキストファイルを `read_json()` で読む用途はこの記載の対象外**である（本調査の推論であり、ドキュメントに明記された記述ではない **見込み**）。複数の DuckDB プロセス（CLI・スクリプト）が同じ JSONL を同時に読み取ることが制約されないという判断も同じく見込みであり、書き込み中の行を読むと不完全な行を拾う可能性がある点を含め未検証（[§6 最強の反論](#sec-6-devil) 参照） | 自作ダッシュボードから DuckDB の `read_json` を都度実行するだけでよく、上記の制限（見込み）の影響を受けない。v2.1 の想定構成どおり | file exporter は `append: false` が既定であり、`rotation` を設定しないと**再起動のたびにファイルが切り詰められる**（v2.1 R-1、fileexporter README で確認済み[D6]）。`rotation` 設定時に再起動してもデータが残るかは README に記載がなく未検証（V-6、[§5](#sec-5) #27 参照）。また v2.1 **R-4**「`event.sequence` は Claude Code のプロセスごとに数えられ、セッションをまたぐ並べ替えのキーには使えない」ため、JSONL の行の並び自体もイベント発生順とは限らない。集計・突合では `event.timestamp` で並べ替える必要がある（並べ替えの単位は「ファイル内の行順」ではなく「タイムスタンプ」である点に注意） | DuckDB のドキュメント・機能一覧には保持期限（TTL）に相当する機能の記載がない（[§5](#sec-5) #12。「ない」という消極的確認であり、積極的に明記された記述ではない） | ローテーション済みファイルを外部で `.gz`/`.zst` に圧縮すれば DuckDB がそのまま読める（拡張子で自動判別。[§5](#sec-5) #28）。Collector 自身の `compression` 設定は使えない（v2.1 R-3、[§5](#sec-5) #17） |
| **(C)** | メトリクスは MetricsQL（PromQL のスーパーセット）[D10]、ログは LogsQL[D11]。いずれも専用クエリ言語で、SQL の `GROUP BY` のような書き方に馴染みがある人には学習コストがある | ○。VM/VL 自体がサーバプロセスとして常駐し、HTTP 経由で複数クライアント（vmui・API 呼び出し）から同時にクエリされる設計 | Grafana と組み合わせる場合は相性が良い（PromQL 互換の MetricsQL、Grafana の VictoriaLogs データソースあり）。「レイアウトを度々変えたい」という本活動の要件（計画書 §1.4）に対しては、自作 UI をこの上に作るなら結局 API 呼び出しのラッパーが要る | VM/VL は自身のディスク上のストレージエンジンを持ち、通常の TSDB/ログストアと同様のクラッシュリカバリの仕組みを備えている見込み（本調査では詳細未確認） | VictoriaMetrics には `-retentionPeriod`（既定 1 か月＝31 日、単体構成の既定）が明記されている[D-vmretention]。VictoriaLogs にも同様の保持期間設定がある設計思想と見られるが、既定値は本調査で個別確認していない（見込み）。**放置すると既定の保持期間で自動的にデータが消える**ため、長期保持したい場合は明示的に期間を延ばす設定が要る（DuckDB/JSONL 側にはこの自動削除の心配がない代わりに、自分で容量管理をする必要がある） | VM/VL は内部で独自の圧縮ストレージ形式を持つ見込み（詳細未確認） |

## 4. OTLP プロトコルの比較

<a id="sec-4-1"></a>
### 4.1 cc 側の対応

cc 公式ドキュメントは次のとおり明記している（`code.claude.com/docs/en/monitoring-usage`、ローカル DL 版 L86669）[D1]:

> `OTEL_EXPORTER_OTLP_PROTOCOL` … Claude Code has no default protocol, so set this or the signal-specific protocol variable for each `otlp` exporter you enable. Values: `grpc`, `http/json`, `http/protobuf`

すなわち **cc には既定プロトコルが無く**、`grpc` / `http/json` / `http/protobuf` のいずれかを明示指定する必要がある（仕様別紙 §4 の記載と一致）。signal ごとに `OTEL_EXPORTER_OTLP_METRICS_PROTOCOL`（L86672 付近。既定エンドポイント例 `http://localhost:4318/v1/metrics`）、`OTEL_EXPORTER_OTLP_LOGS_PROTOCOL`（L86674 付近。既定エンドポイント例 `http://localhost:4318/v1/logs`）等で個別上書きも可能[D1]。(A) が自作エンドポイントを `/v1/metrics`・`/v1/logs` に置くのはこのデフォルトパスに合わせるものである。

なお `OTEL_EXPORTER_OTLP_COMPRESSION`（送信時の圧縮）に相当する cc 固有の変数は、ローカル DL 済み docs 全文を検索した限り記載が見つからなかった。OpenTelemetry 仕様側の既定値は「明示指定なし（no value）」であり、どちらの値をとるかは各言語 SDK の実装依存とされている[D-otelspec]。cc（Node.js 製）の OTel SDK がどちらを既定にしているかは docs に明記がない。**実測（v0.3 で追記）**: 1-1 の受信スクリプトが記録した全 203 リクエスト（logs 118・metrics 62・traces 23）は、いずれも `Content-Encoding` ヘッダが無く、`application/json` の非圧縮だった（cc 2.1.283、`OTEL_EXPORTER_OTLP_COMPRESSION` 未指定）。既定では (A) の受信コードに解凍処理は要らない。ただし利用者が圧縮を指定した場合に備え、`Content-Encoding` を見て解凍する処理を入れておくと安全である（1-1 の受信スクリプトは gzip・deflate・br に対応済み）。

2026-10-19 追記: cc 2.1.300 から、Anthropic の API への大きいリクエストは、テレメトリを無効にしていても gzip で送られる（[1-8 §8.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) D51。changelog 2.1.300）。これは API へのリクエスト本体の話で、OTLP の送信の圧縮とは別である（1-8 は、テレメトリを無効にしたときの挙動（D51 ほか）を OTel の export とは別の話とし、D51 の反映先を 1-2 §4 にしている）。上の非圧縮の記述は変わらない。

<a id="sec-4-2"></a>
### 4.2 各候補の対応と (A) の実装負荷

| 観点 | (A) Node.js 自作 | (B) otelcol-contrib | (C) VictoriaMetrics / VictoriaLogs |
|---|---|---|---|
| `http/json` 対応 | 自作すれば対応でき、実装は単純。ただし OTLP の JSON マッピングでは 64bit 整数（`intValue` 等）が**文字列として**表現される（protobuf の proto3 JSON マッピング仕様。int64/uint64/fixed64 系は JSON では文字列にする、と明記されている[D16]）。パース時に数値へキャストする処理が要る | ネイティブ対応（receiver 側の実装は Collector に内蔵済み） | VictoriaLogs のログ受信は OTLP の標準的な receiver 実装に準じると見込む（未確認）。VictoriaMetrics の metrics 受信はドキュメント上 protobuf 前提の記載で、`http/json` 対応の可否は未確認[D10] |
| `http/protobuf` 対応 | 自作の場合、`opentelemetry-proto` の `.proto` 定義を `protobufjs` 等でコンパイルしてデコードする実装が要る。`@opentelemetry/otlp-transformer`（npm、"Transform OpenTelemetry SDK data into OTLP"、v0.222.0 確認[D15]）は OTel SDK からエクスポートする側（エンコード）を主目的としたパッケージであり、受信側のデコード用途への転用は追加の検証が要る（未確認）。実装負荷は `http/json` より明確に高い | ネイティブ対応（同上） | VictoriaMetrics の OTLP metrics エンドポイントは protobuf エンコードのリクエストを前提とした記載[D10] |
| `grpc` 対応 | 自作する場合、HTTP/2 + protobuf の実装が要り、`http/*` より大幅に負荷が高い。採用する理由が薄い | ネイティブ対応 | 未確認（本調査の対象外。VM/VL は通常 HTTP ベースの受信エンドポイントを主にすると見込む） |
| 結論（(A) の実装負荷） | **`http/json` を選べば、自作受信サーバはおおむね「HTTP サーバ + `JSON.parse` + 数値キャスト」で足りる**。`http/protobuf` を選ぶ場合は protobuf デコードライブラリの導入・スキーマ管理が追加で要る。仕様別紙 §4 の「`http/json` を選べば protobuf のデコードが不要になり、Node.js で受信サーバを自作しやすい」という記載と一致する。**この結論は机上の記載だけでなく、[1-1 報告書](../01.実データ確認/調査報告書.md#sec-1) の実測でも裏付けられている**: cc を `OTEL_EXPORTER_OTLP_PROTOCOL=http/json` で起動し、Node.js で数十行の OTLP/HTTP 受信スクリプトを書くだけで、metrics・logs・traces の 3 シグナルとも受信できた | 該当なし（プロトコル選択による実装負荷の差はほぼ無い。Collector が両方とも内蔵で処理する） | (C) を直接受信先にする場合、少なくとも VictoriaMetrics 側は protobuf 前提の可能性が高く、(A) のような「json で実装を楽にする」余地が薄い（未確認だが、ドキュメントの記載傾向からは protobuf 志向） |

<a id="sec-4-3"></a>
### 4.3 受信サーバ停止中の cc 側の挙動（仕組み上の記述。実測は Phase 3）

cc の変更履歴には、テレメトリのエクスポート失敗はデバッグログに `[3P telemetry] OTEL diag error` として記録され、Anthropic 自身の運用テレメトリ（`[Anthropic telemetry]`）とは区別される、という記載がある（ローカル DL 版 L5631 付近）[D1]。これは失敗が **デバッグログに記録されるだけ** であることを示しており、対話セッションの動作自体を止めるとは docs に明記されていない。一般的な OpenTelemetry SDK のエクスポータ設計（バッチ・非同期送信、失敗時はリトライまたは破棄してキューを進める）に基づけば、受信サーバが落ちていても cc の操作自体はブロックされないと見込む（実測は Phase 3 の PoC 観点。1-1 の実測では受信サーバを停止するケースは扱っていない）。

<a id="sec-4-4"></a>
### 4.4 2 セッション同時受信の仕組み上の記述と実測

cc の各セッションは別プロセス・別 OTel エクスポータとして動作し、同一の OTLP エンドポイント（例: `127.0.0.1:4318`）へそれぞれ独立に push する。(A)(B)(C) いずれも、受信側は通常の HTTP サーバ（Collector・VM/VL・自作サーバのいずれも）であり、複数クライアントからの同時接続を受け付けるのが通常の実装であるため、2 セッションが同じポートに同時送信すること自体は仕組み上の障害にはならない（見込み）。

**この点は cc 側の送信挙動として [1-1 報告書](../01.実データ確認/調査報告書.md#sec-2) の実測（cc 2.1.283）で裏付けられている**: 4 セッションを同時に `-p` 実行しても欠落は無く、全レコードに `session.id` が付いた。ただし 1-1 の受信スクリプトは自作の簡易実装であり、(B)(C) の受信コンポーネント（otelcol-contrib・VictoriaMetrics/VictoriaLogs）自体が複数クライアントからの同時接続をどう扱うかは、この実測では検証されていない。cc 側が複数セッションを問題なく送信することは確認できたが、**受信側の実装ごとの同時受信耐性は Phase 3 で個別に確認する必要がある**。

セッションを区別する軸は `session.id`（メトリクス・イベント双方にある。仕様別紙 §1）であり、これを使えば受信後にどのセッションのデータかを弁別できる。ただし v2.1 **R-4** のとおり `event.sequence` は「Claude Code のプロセスごと」に採番されるため、**2 セッション（＝2 プロセス）が同時に送信した場合、`event.sequence` はセッションをまたいだ順序の手がかりにならない**（セッション内の順序保証にしかならない）。並べ替えは `event.sequence` ではなく `event.timestamp` で行う必要がある点は (A)(B)(C) いずれの保存先でも共通の注意点である。

これと対照的に、**pull 型の `prometheus` exporter は各セッションがポート 9464 を占有するため、複数セッションを同時に起動すると衝突する**（仕様別紙 §4）。本比較の (A)(B)(C) はいずれも push 型（OTLP export）を前提としており、この衝突は生じない。

## 5. V-11(b) 担当分（#12, #14, #15, #17, #18, #19, #26, #27, #28）の確認結果

判定は「一致 / 差異あり / 未確認（実機要）」の 3 区分。

| # | 確認すること | 結果 | 根拠・理由 |
|---|---|---|---|
| 12 | DuckDB に保持期限の概念がないこと | 一致（消極的確認） | DuckDB の公式ドキュメント（JSON 読み込み・接続関連ページ）には TTL・自動削除に相当する機能の記載がない。「ないと明記された記述」ではなく、「機能一覧に存在しない」ことをもって一致とした[D3][D4]。VictoriaMetrics/VictoriaLogs には明示の保持期間設定があるのと対照的（[§3.3](#sec-3-3)） |
| 14 | `read_json_auto` のサンプリングの挙動と `sample_size=-1` の効果 | 一致 | DuckDB 公式ドキュメントに「`sample_size` の既定値は 20480、`-1` を指定するとファイル全体を走査する」との記載を確認した[D3]。ただしサンプリングがファイル先頭から行われるかどうかはドキュメントに明記がなく、そこは未確認のまま残る |
| 15 | 圧縮したファイルと圧縮していないファイルを混在させて読めるか | 未確認（実機要） | `compression` オプションはファイル拡張子から自動判別されると明記されている（`t.json.gz` → gzip、`t.json` → none）が[D3]、1 回の `read_json`/glob 呼び出しで **圧縮ファイルと非圧縮ファイルが混在する場合**にそれぞれ個別に自動判別されるかを明記した記述は見つからなかった。理屈上は「ファイルごとに拡張子で判別」という仕組みなら混在も動きそうだが、明記がないため実機確認が要る |

## 6. 決め手と懸念・Phase 3 実測点

判定は行わないが、絞り込みの材料になる事実は以下のとおり。

**決め手になり得る事実**

- **cc の分析対象の主軸は log イベント（`api_request` 等）であり、metrics は補助**（引継ぎ資料 v2.1 §4.1）。この観点では、ログ専用の受信・保存の作りやすさ・クエリの書きやすさが評価の中心になるべきで、(C) では VictoriaLogs（LogsQL）が主役になる一方、(A)(B) では DuckDB / SQLite の SQL がそのまま主役になる。2026-10-19 追記: 集計の正本（`api_request` か traces の span か）は、計画書 Phase 2 で決める（[1-1 §9](../01.実データ確認/調査報告書.md#sec-9)）。どちらを正本にしても traces の span は集計に含め（作業指示者の 2026-10-12 の判断）、受信の構成としては traces も受ける（下の traces の注記）。span を正本にする場合は、span の保存とクエリの書きやすさも評価の中心に入る
- **DuckDB は「`.duckdb` 形式のファイル」に対しては単一書き込みプロセス制限がある**（複数プロセスにまたがる read-write／read-only 同時接続はできない、と公式ドキュメントに明記）[D4]。(A) を「受信プロセスが DuckDB に直接書き込む」設計にすると、別プロセスのダッシュボードが同時に読めない制約に当たる。(B) は「file exporter がプレーンテキストの JSONL に書き、DuckDB は外部ファイルとして `read_json` で読むだけ」なので、この制限が及ぶ対象（`.duckdb` データベースファイル）には該当しない（見込み。[§3.3](#sec-3-3) に記載のとおり未検証）。**(A) で DuckDB を保存先にするなら、受信プロセス自身にクエリ API を持たせるか、SQLite（WAL。公式ドキュメントで別プロセス間の同時読み書きが明記されている[D-sqlite]）を選ぶ必要がある**
- **`node:sqlite` は Node.js 組み込みで、追加の native ビルドツールが不要**（Node 22.13/23.4 以降フラグ無しで利用可、本活動の基線 Node v24.14.0 は満たす。ただし v25.7.0 で release candidate になるまでは experimental 表示が残る）[D12]。職場環境への持ち込みやすさの観点で、npm の native addon（`better-sqlite3` や DuckDB の Node バインディング）よりリスクが低い
- **VictoriaMetrics は v1.132.0 以降、delta temporality をそのまま保存できる**ため、v2.1 が前提としていた「delta は破棄される」という懸念は現行版では当てはまらない（[§5](#sec-5) #19）。(C) を積極的に採らない理由としてこの点を挙げるのは、現行バージョンでは根拠が薄い
- **(B) の file exporter は alpha 安定度であり、`rotation` 設定時の再起動後の挙動が未文書化**（[§5](#sec-5) #27、V-6 は実機要）。ここが (B) 最大の未解決リスクである。なお v2.1 **R-4**（`event.sequence` はプロセス単位で、セッションをまたぐ並べ替えのキーには使えない）は (B) 固有ではなく、どの保存構成でも `event.timestamp` で並べ替える必要がある（[§4.4](#sec-4-4)、まとめ報告書 §2。v0.3 で「(B) 固有」の記述を訂正）
- **(A) の実装負荷は `http/json` を選べば低い、という結論は 1-1 の実測で裏付けられている**（[§4.2](#sec-4-2)）。あわせて、cc 側は 4 セッション同時実行でも送信の欠落が無いことが実測済みであり（[§4.4](#sec-4-4)）、(A) の自作受信サーバを検討する際の「同時送信への耐性」に関する不安要素は cc 側については軽減されている

**懸念点**

- (A) は実装量そのものが最も多い（受信・パース・保存をすべて自作）。特に `http/protobuf` を選ぶと protobuf デコードの実装が追加で要る（[§4.2](#sec-4-2)）
- (C) は metrics 用・logs 用に別バイナリが要り、2 系統の運用（起動・監視・クエリ言語の学習）が発生する。VictoriaMetrics の OTLP metrics 受信が protobuf 前提である可能性が高く、(A) のような「json で楽をする」余地が薄い（未確認）
- (B) は otelcol-contrib・DuckDB という 2 つの外部バイナリの導入・保守が要り、file exporter の alpha 安定度がバージョンアップ時の設定崩れリスクになる

- 送る経路: Mod の `$.http.fetch(url, init)` は `http`・`https` で送れ、応答の本文を読み終えてから結果（`status`・`ok`・`headers`・`text`）を返す（docs の mods の API）。これを使えば、Mod が作るレコード（タグ案 L1 のラベル、`turn.step` が渡すリクエストごとの usage など）を、(A) の受信サーバへ JSON で送る形が作れる【推定】。受信側には、OTLP とは別の入口を用意することになる【推定】
- 上限: 送る本文は 4 MiB（文字数で数え、超えると reject）、応答の本文は 4 MiB（先頭の 4 MiB だけを読む。`Content-Length` の header が超える大きさを示すと reject）、1 回の呼び出し（redirect と本文を含む）は 30 秒、redirect は 5 回まで（docs の mods の reference の Limits）。別の origin への redirect では、`accept`・`accept-language`・`content-type`・`user-agent` 以外の header を落とす
- docs に無いこと: localhost・127.0.0.1 宛ての扱い（[1-8 §6](../08.cc2.1.287差分の確認/調査報告書.md#sec-6) の未確認事項のまま）。受信サーバに接続できないときに `$.http.fetch` が reject するか、どんな値を返すか（reject と書かれているのは、送る本文が上限を超えたときと、応答の `Content-Length` が上限を超えたときだけ）。受信サーバが止まっているときの再送・キュー。どれも docs では決まらない。Mod を採る場合に Phase 3 の PoC で確かめる（確かめ方と合格の条件は [1-8 §8.5](../08.cc2.1.287差分の確認/調査報告書.md#sec-8-5) の表。下の「Phase 3 で実測すべき点」にも置いた）
- 失敗の扱い: hook の中の例外を `catch` しないと hook の失敗として扱われ、`next` を呼ぶ前なら、その hook は飛ばされて次の handler が代わりに動く（docs の mods の events「Handle a hook that fails」）。送れなかったレコードは、黙って欠けうる【推定】
- 止まる条件（要約。正は [1-8 §4.1](../08.cc2.1.287差分の確認/調査報告書.md#sec-4-1) の「`$.http.fetch` を止める条件」）: 組織の policy が WebFetch を許さない場合だけ、すべての Mod の `$.http.fetch` が拒否される（2.1.288 以降）。Claude Code がこの policy を取りに行くのは、claude.ai の Team・Enterprise でサインインし LLM gateway を経由しないセッションと、plan を判定できないセッションである。web fetch を無効にする変数や deny rule では止まらない。nonessential traffic を止める変数が止めるのは、組み込み Mod と、セッションの Anthropic の credential を載せた fetch だけである（L1 のラベルの送信は credential を載せない【推定】）。どの条件も `$.process.run` で起動した program の通信には効かない。確かめ方は `/status`（セッションの外では `claude doctor`）の `Organization policy` の行である（docs 2026-10-19 取得版）
  - 結論（【推定】）: LLM ゲートウェイ環境は LLM gateway を経由するので、この policy による拒否の条件に当たらない見込みである。plan を判定できないセッションに当たらないかは docs では決まらないので、計画書 v2.0 の Phase 7 で `/status` の `Organization policy` の行を見て確かめる（1-8 §8.5 の表）
  - 組織は、自前の policy Mod で、ほかの Mod の `http.fetch` の呼び出しを拒否することもできる（docs の mods の API）。職場でこれが L1 の Mod の送信を止めうる【推定】
- LLM ゲートウェイ環境（計画書 v2.0 の Phase 7）: 2.1.290 より前は、LLM gateway（`ANTHROPIC_BASE_URL` と `ANTHROPIC_AUTH_TOKEN`）で Claude に届き、Anthropic のアカウントを持たない人の Mod は off のままだった（changelog 2.1.290。[1-8 §7.2](../08.cc2.1.287差分の確認/調査報告書.md#sec-7-2) D18 の 2026-10-19 追記）。1-8 が Mod を採る前提とする 2.1.293 以降は、この修正を含む
- タグ案 L1 を command hook と Mod のどちらで書くかの材料は、1-3 の「[L1 の実装手段の比較（command hook と Mod）](../03.作業分類タグ方式/調査報告書.md#sec-4-l1-impl)」の表にまとめてある（同日のクロスレビュー Round 2 で追記）

<a id="sec-6-devil"></a>
**最強の反論と残存リスク**

- **反論**: (B) で「DuckDB の単一書き込みプロセス制限は `read_json()` による外部ファイル読み込みには及ばない」という [§3.3](#sec-3-3)・[§6](#sec-6) の判断は、DuckDB 公式ドキュメントの「Concurrency」ページを読んだ上での推論であり、そのページ自体が `read_json()` のような外部ファイルスキャン関数を明示的に対象外と述べているわけではない。DuckDB の内部実装が、`read_json()` 実行時にも何らかのファイルロックや mmap を伴う可能性はゼロではない
  - **棄却できるか**: 部分的に棄却できる。DuckDB の Concurrency ページの記載範囲は一貫して「database file」（`.duckdb` 形式の永続化ファイル）についてであり、JSON/CSV/Parquet 等の外部ファイルを都度スキャンする `read_json()`・`read_csv()` 系関数はそもそも DuckDB 自身のトランザクション管理下のファイルではない。これは一般的な OLAP エンジンの設計（外部ファイルはテーブルではなくスキャン対象）から妥当性が高い推論だが、**ドキュメントに明記された記述ではない**ため完全な棄却はできない
  - **残存リスク**: (B) を採用候補として残す場合、Phase 3 で「otelcol-contrib が書き込み中の JSONL ファイルを、別プロセスの DuckDB CLI が同時に `read_json` で読めるか」を実機で確認する（[§6 Phase 3 実測点](#sec-6)に記載済み）
- **反論**: VictoriaMetrics の delta temporality 対応（v1.132.0 以降）が確認できたのは公式ドキュメントの記載のみであり、実際に cc の `claude_code.token.usage`（sum, delta）のような属性付きメトリクスを送った場合に、ドキュメント記載どおりに保存されるとは限らない
  - **棄却できるか**: 棄却困難。ドキュメントの記載は一般的な delta temporality の扱いについてのものであり、cc 固有の属性の組み合わせ（`model`・`effort`・`query_source` 等の高カーディナリティなラベル）でも同様に動くかは未検証
  - **残存リスク**: (C) を候補に残す場合、Phase 3 で cc の実際のメトリクスを VictoriaMetrics に送り、`sum_over_time()` で意図した値が集計できるかを確認する必要がある（下記 Phase 3 実測点に追加）
