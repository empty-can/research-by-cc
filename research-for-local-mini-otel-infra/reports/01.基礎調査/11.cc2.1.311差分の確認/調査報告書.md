## 要約

- **調査内容**: cc 2.1.311（2026-10-26 公開）の changelog の 92 行すべてと、1-10 の docs（ed2bfc5）から、2026-10-27 15:00 に取り込まれたローカル docs（f43c40d）までの差分を確かめた。f43c40d も、14:11 に取ったオンラインの llms-full.txt も 2.1.311 の changelog を含まないので、オンラインの changelog と、関わるページ 13 本を取って補った（[§1](#sec-1)）。本活動に関わる項目に、差分の番号 D72〜D79 を付けた（[§2](#sec-2)。以下の「D」はこの番号）。cc 2.1.311 の `-p` の 3 run（1-10 の qk1〜qk3 に当たる）で、属性集合と events を 2.1.310 と比べた（[§3](#sec-3)。費用は約 0.12 USD）
- **調査結果**
  - **変わらなかったこと**: OTel の属性集合（25 種・455 組）、events と span の種類、`query_source`・モデル・effort、plugin の構成、`agent_id`・tool のイベントの `request_id` の値の一致、`prompt_id` の結合（3 件中 3 件）、transcript の突合（7 件中 6 件。外れは compact の 1 件）、hook の入力のキーは、2.1.310 と同じだった（[§3](#sec-3)）。monitoring-usage と settings のページは ed2bfc5 と語が同じで、changelog 2.1.311 にも OTel の出力の変更は無い
  - **変わったこと**
    - (1) 対話の端末の `ultrathink` が、Anthropic の API 経由の Opus 5.5・Sonnet 5.5・Haiku 5.5・Fable 5.1 で、そのターンの要求を `xhigh` の effort で送るようになった。動いている途中に打つと、そのターンの残りを上げる。ローカル docs（ed2bfc5・f43c40d）は、`ultrathink` では API に送る effort は変わらないと書いていた（D72）
    - (2) 後置きが効かないモデル（docs では 1M の窓が既定のモデル）で、モデル名と ID から `[1m]` の後置きを外すようになった。【推定】OTel の `model` の文字列が版で変わり、単価表に結ぶ規則に効く（D73）
    - (3) compaction で、要約の無い応答の後にもう 1 回要約を求めるようになった。標準の窓のセッションが 200K token を超えると止まっていた不具合が直り、compact して続くようになった（D74）
    - (4) transcript: `-p` と SDK のセッションが message の順を違えて保存したり、取り消された message を残したりしていた不具合が直った。実機で新しい記録型 `tools-used` が出た（changelog・docs に無い）。docs は、transcript が読み込んだ指示ファイル（CLAUDE.md など）も持ちうると書くようになった（D75）
    - (5) auto mode で自分の shell を待つ background agent が、起きるたびにメインの会話のターンを始めていた不具合が直った（D76）
    - (6) docs に、組み込みの guard（docs の名前は `sec-default@builtin`）が読み込まれる所では、利用者の Mod の `classic.*` の hook（`classic.UserPromptSubmit` を含む）が動かないことが足された。guard は、その端末に managed settings があるときと、docs が挙げる組織向けのプランの `/login` で動くセッションで読み込まれる（D77）
  - **反映候補**: 崩れた事実は無い。Phase 1 の文書と設計書が【推定】（仕様別紙は「見込み」）としていた、transcript とリクエストにユーザの指示ファイルの内容が入りうることは、docs で裏付けられた。反映候補は、Phase 1 の文書に 16 件、設計書に 13 件、計画書 v2.5 の案に 8 件ある（[§4](#sec-4)）
  - **反映の状態**: 37 件とも 2026-10-27 に各文書へ反映した。設計書で覆した決めごとは無い（組 B の MT-07d の引く順に、`[1m]` の後置きを外す段を足した。#21）。#19 は数え方を変えず、今の定義のまま、1 つのプロンプトが要求の入る組のそれぞれの分母に入ることを注記した。計画書の 8 件は v2.5 の案に入れ、承認の回には、[計画書の v2.5 の小節](../../00.活動計画/活動計画書.md#sec-approval-v25)の「1-11 の Pn」の項を見る
- **判断事項への影響**: 今回、作業指示者に求める判断は無い。推奨・既定・選択肢を変える J は無く、新しい J も作らない。J-18 は、基線の版の句が 2.1.311 になる。J-15 の判定規則（TG-09）の材料に、2.1.310 以前の auto mode のセッションの、background agent が起きるたびのターンが加わる（D76）。J-12 の基準を超えたときに諮る「hook の改善（Mod にするなど）」は、guard が読み込まれる環境（職場など）では成り立たない場合がある（D77）。J-26 の材料に、ゲートウェイの背後で `ultrathink` が effort を上げるかは docs に無いことと、"Connection dropped" の文が加わる（D72・D78）
- **結論・示唆**: 本活動が依存する属性は 2.1.311 でも使える。影響のある設計書の節は組 B（データモデルと集計）に多い（[§5.1](#sec-5-1)）。次の 4 点を、設計書と計画書 v2.5 の案に入れる候補とした（今の状態は上の「反映の状態」）。職場（Phase 7）の確認には、`ultrathink` がゲートウェイの背後で effort を上げるかと、guard の有無を足す（[§5.2](#sec-5-2)）
  - 区切る版に 2.1.311 を足す（`effort` の付き方、`model` の文字列【推定】、compaction の件数、`-p`・SDK の transcript の順序が変わる）
  - 1 つのプロンプトの要求は、2.1.311 より前から複数のモデル・effort の組に入りうる（サブエージェントのモデルと `effort`、skill の `effort`。動いている途中の `/effort` も【推定】）。2.1.311 以降は、`ultrathink` を途中で打ったときも入りうる【推定】。定義の別紙の「プロンプトあたり」の分母の扱いを書く（D72）
  - `model` を単価表に結ぶ引き方に、`[1m]` の後置きを外した一致を足す（D73）
  - transcript の「`request_id` ごとに最後の行」は、2.1.310 以前の `-p`・SDK の transcript で崩れうる【推定】ので、Phase 3 の取込の試作で確かめる（D75）
