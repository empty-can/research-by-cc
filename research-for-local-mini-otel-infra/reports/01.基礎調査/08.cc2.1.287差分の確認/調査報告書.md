## 1. 目的と方法

Phase 1 の報告書は cc 2.1.283 時点の docs と実測に依拠している。その後 cc 2.1.287 までに仕様が変わったので、既存文書のどこが古くなったかを特定し、実測で確かめる。§1〜§6 の範囲は 2.1.287 までである。2.1.288〜2.1.296 の分は、同じ手順で [§7](#sec-7) に追補した。

- **基線**: docs の 2026-09-27 15:00 取得版（ローカル docs リポジトリ `C:\cc-workspace\LLMs` の commit 4b44c61）。計画書 §2 と仕様別紙が基線にしている版
  - この版にした理由: 計画書 §2 冒頭は、1-1〜1-6 がこの版の docs に依拠したとしている（1-6 の環境欄も同じ）。v0.1 は引継ぎ資料 v2.1 が使った 2026-09-26 15:00 取得版（commit df1f117）を基線にしていた
  - D3・D4 の記述は 09-26 版にもある。D5〜D7 は 09-27 版で初めて現れる。Phase 1 の文書が依拠した 09-27 版に照らすと、D3〜D7 はいずれも既存文書の誤り・記載漏れに当たる
- **比較先**: 同リポジトリの 2026-10-02 15:00 取得版（commit 9b8bb3e）

  - 有効化: ユーザ settings は変更せず、実測用の cc プロセスにだけ環境変数を渡した
  - 内容記録のフラグ（`OTEL_LOG_*`）はすべて OFF。計画書 §7 #2 の判断待ちのため
  - q1〜q3 では `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` と `OTEL_METRICS_INCLUDE_VERSION=true` を付けた

## 4. Claude Mods の事実と実測

Mods は 2.1.287 で加わった、plugin の中で動く JS/TS の hook である。`classic.UserPromptSubmit` の Mod は OTel の `prompt.id` と結合でき、2.1.287 では `-p` と対話モードの両方で、llm_request の開始までの上乗せが command hook より小さかった。2.1.296 の `-p` では大小が逆になった（[§7.3.2](#sec-7-3-2)）。標本は各 3 回と小さい。command hook との比較は [§4.4](#sec-4-4) の表に集約した。

<a id="sec-4-1"></a>
### 4.1 仕組み・API・管理（docs の記載）

- **位置付け**: plugin の hooks module（`register(on, options)` をエクスポートする ES module）。cc のプロセス内で動き、インストール済みの Mod は 1 本のワーカースレッドを共有する。別プロセスを起動する command hook とは実行形態が異なる
  - 言語は JS / TS で、ビルド不要。Node.js API とタイマーのグローバルは無く、外部へは Mods API を通して触る
  - 端末 CLI・Desktop の Code タブ・VS Code 拡張・`claude -p`・Agent SDK で動く
- **主なイベント**: hook は `($, e, next)` を受ける middleware で、観測・書き換え・応答ができる
  - `prompt.submit`: プロンプト送信時。本文（`e.text`）の読み取り・書き換え・破棄
  - `turn.start` / `turn.step` / `turn.complete`: turn の開始、モデルへの各リクエスト、終了。`turn.complete` は turn のトークン合計（`e.usage`）を持つ
  - `classic.<settings hook のイベント名>`: settings hook と同じイベントを、stdin の JSON と同じ `e` で受ける
- **API**: ファイル（`$.fs`、1 ファイル 4 MiB まで）、HTTP（`$.http.fetch`）、タイマー（`$.clock`）、モデル（`$.model.complete` 等。利用者のプラン・API キーで課金）、プロセス（`$.process.run`、既定 30 秒）。hook 自身の実行時間は 10 秒まで
  - OTel の属性・span を書き換える API は無い。`$.telemetry` は cc 本体か組み込みの Mod が呼んだときだけ送信される
  - Mods はサンドボックス化されず、利用者と同じ権限で動く
- **管理**: 既定で有効（端末は 2.1.287 以降、Desktop 同梱の cc は 2.1.286 以降。docs 2.1.295）。組織は managed settings で止められる
  - `allowManagedModsOnly`: managed settings のトップレベルのキーではない。組み込みの guard の option として、`pluginConfigs."cc-plugin-sec-default@builtin".options.allowManagedModsOnly` に置く。利用者が持ち込む Mod は読み込まれるが拒否され、hook が動かない。利用者の settings hook と、plugin の `hooks/hooks.json` の command hook は動き続ける
  - `allowManagedHooksOnly`: 利用者の settings hook も止まる（managed settings が force-enable した plugin の hook は動く）。`disableAllHooks`: 全 Mod・全 hook を停止。`disableSideloadFlags`: `--plugin-dir` を拒否
    - 2026-10-19 補足（docs 2026-10-19 取得版。settings-reference の「What runs under `allowManagedHooksOnly`」、plugins/mods の admin）: 上の括弧は command hook（plugin の `hooks/hooks.json`）について正しい。force-enable した plugin の Mod が読み込まれるのは、組織の Mod に数えられる場合（managed settings がマシン上のフォルダの marketplace を絶対パスで指し、plugin をそこから相対パスでその場で読み込む場合）だけである。GitHub・git・URL・npm の source から cache にコピーされる plugin の Mod は、managed settings で有効にしても利用者の Mod に数えられ、`allowManagedModsOnly` では拒否され、`allowManagedHooksOnly` では読み込まれない。職場でタグ案 L1 を Mod として配る場合の条件になる
  - `$.http.fetch` を止める条件（2026-10-19 に改めた。docs 2026-10-19 取得版の plugins/mods の admin「Network policy covers `$.http.fetch`」と、tools-reference の「WebFetch availability」）
    - 組織の policy が WebFetch を許さないと、すべての Mod の `$.http.fetch` が拒否される。Claude Code がこの policy を起動時に取るのは、claude.ai の Team・Enterprise でサインインし、LLM gateway を経由しないセッションなどである
    - `CLAUDE_CODE_DISABLE_WEB_FETCH` や `WebFetch` の deny rule（managed settings を含む）では、Mod の `$.http.fetch` は止まらない
    - `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` が止めるのは、組み込み Mod と、セッションの Anthropic の credential を載せた `$.http.fetch` だけである。2.1.288 より前は、すべての Mod の `$.http.fetch` を止めた
    - どの条件も、Mod が `$.process.run` で起動した program の通信には効かない
    - v0.14 までは「組織が web fetch か nonessential traffic を無効にしていると拒否される」と書いていた。nonessential traffic の部分は 2.1.288 より前の挙動で、2.1.288 以降には当たらない。web fetch の部分は、上の 1 点目（組織の policy）に限られる
  - v0.4 までは `allowManagedModsOnly` をトップレベルのキーのように書き、意味を「全て不許可」としていた。置き場所は 2026-10-02 取得の docs から同じで、版上げとは無関係の Phase 1 の誤りである（docs に正しく書かれていた。一覧は [§7.4](#sec-7-4)）。意味は docs 2.1.295 が「拒否され、hook が動かない。plugin の `hooks/hooks.json` は動く」と書き直した（[§7.2](#sec-7-2) D17）
- **型定義の記述**: cc に同梱の plugin-authoring の型定義（hook 入力の基底型）は、`prompt_id` を「OTel イベントの `prompt.id` 属性と同じ値で、hook の出力を OTel イベントとプロンプト単位で結合できる」と説明している

### 4.4 command hook と Mod の比較

タグ案 L1 の実装手段（command hook か Mod か）を Phase 2 で選ぶための材料を、この表に集約する。ほかの文書はこの表を参照する。左の 2 列の測定値は 2.1.287（Haiku 4.5）のもの。右端の列に、2.1.296 での値と変化を置いた（v0.5 で追加）。

| 観点 | command hook（Node.js。値は 2.1.287） | Mod（`classic.UserPromptSubmit`。値は 2.1.287） | 2.1.296 での値・変化（[§7.3](#sec-7-3)） |
|---|---|---|---|
| 実行形態・言語 | プロンプトごとに別プロセスを起動する。言語は任意（測定は Node.js） | cc のプロセス内のワーカースレッドで動く JS / TS。Node.js API は無く、Mods API を使う（[§4.1](#sec-4-1)） | 同じ。`-p` でも Mod がワーカーで動くことを確かめた。`-p` で `--plugin-dir` に型ファイルを書かなくなった（2.1.295 の修正） |
| `prompt_id` の結合 | OTel の `prompt.id` と一致（1-1 の 7 プロンプト。1-3 §2） | 一致（`-p` 3 回、対話モード 3 回。[§4.2](#sec-4-2)） | command hook・Mod とも、`-p`・対話モードの各 3 回で一致（[§7.3.1](#sec-7-3-1)） |
| 上乗せ（測定点 A の hook なしとの差。平均） | `-p` 約 150 ms、対話モード 約 440 ms | `-p` 約 30 ms、対話モード 約 300 ms | `-p`（Haiku 4.5 を明示した対照。2.1.287 と同じモデル・permission mode）: command hook 約 135 ms・Mod 約 198 ms。`-p`（`haiku` エイリアスの解決先の Haiku 5.5）: 約 155 ms・約 204 ms。対話モード: 約 235 ms・約 160 ms（Remote Control なしで約 211 ms・約 110 ms）。**`-p` ではどちらの条件でも command hook の方が小さい**（[§7.3.2](#sec-7-3-2)） |

| 管理による停止 | managed settings の `allowManagedHooksOnly`（利用者の settings hook を止める）、`disableAllHooks`。`allowManagedModsOnly` では止まらない（settings hook と plugin の `hooks/hooks.json` は動く） | `allowManagedModsOnly`（`pluginConfigs."cc-plugin-sec-default@builtin".options` の下に置く。利用者の Mod を拒否）、`allowManagedHooksOnly`、`disableAllHooks`、`disableSideloadFlags`（`--plugin-dir` を拒否） | 同じ（docs 2.1.295 で `allowManagedModsOnly` の意味が明確になった。[§4.1](#sec-4-1)）。Mod を採るなら 2.1.293 以降が前提（[§7.2](#sec-7-2) D18） |

- 2.1.287 では、測定点 A の上乗せは `-p` と対話モードのどちらでも Mod が command hook より小さかった（各 n=3、Haiku 4.5）

- 大小は版とモードで入れ替わる。上乗せは組み込み Mod の構成しだいで版ごとに変わるので、Phase 2 の比較と Phase 3 の判定は、同じ版の値どうしで行う。2.1.287・2.1.296 のどの条件でも、上乗せは 0.5 秒未満だった（測定点 A は 2.1.283 では測っていない。2.1.283 の対話モードでは、hook 単体（測定点 B）が 2.1〜2.8 秒の回が 2 回あり、原因は未特定）
- command hook は `UserPromptSubmit` と `SessionStart` の 2 つ、Mod は 1 つで、本数がそろっていない。【推測】`SessionStart` は interaction span の開始より前に走るので、測定点 A への影響は小さい
- 職場環境では、managed settings で Mod だけでなく command hook も止められうる。ただし `allowManagedModsOnly` だけなら、command hook（settings hook と plugin の `hooks/hooks.json`）は動き続ける。タグ案 L1 が成り立たないのは、`allowManagedHooksOnly` か `disableAllHooks` で command hook も止められている場合に絞れる（Phase 3 の職場環境確認で確かめる。[§6](#sec-6)）

Mods をタグ付けの手段に採るかの判断は、1-3 の改訂と Phase 2 に委ねる。

**Remote Control の影響**

- 2.1.287・2.1.296 の対話モードの計測は、どちらも Remote Control に接続した状態だった（[§7.3.4](#sec-7-3-4)）。条件はそろっているので、版間比較は有効である
- Remote Control を切ると、hook なしはほぼ同じ（111 → 108 ms）で、上乗せは command hook が 24 ms（ばらつきの範囲）、Mod が 50 ms 小さくなった。対話モードの順位（hook なし < Mod < command hook）と、上乗せがどれも 0.5 秒未満であることは変わらない。【推測、n=3】Remote Control の起動処理が、ワーカー上の Mod の初回の処理と重なっていた可能性がある
- どの値を引くか: 版間比較は、Remote Control ありの行どうしで行う。J-12 の判定は、日常のセッション（Remote Control は普段どおり接続した状態）をそのまま測って行う。Remote Control の有無・モデル・permission mode を記録して条件ごとに集計し、上乗せは同じ条件の hook なしの中央値から求める。Remote Control を切った計測用のセッションの値は、参照値として並べる（J-19）

**結論**

- J-3 の推奨（Mods を加える。hook か Mod かは Phase 2 で決める）と、Q4 の推奨（L1）は変わらない。2.1.287・2.1.296 のどの条件でも、上乗せは 0.5 秒未満だった
- ただし「両モードとも Mod が小さい」は、版しだいで成り立たない。上乗せは版（組み込み Mod の構成）で動くので、Phase 3 の測定値は測った版でしか使えない（J-18）
- J-12 の暫定値（上乗せの中央値 1 秒以下、上乗せが 2 秒を超えるプロンプト 1 割以下）は変えない。根拠に 2.1.296 の値を並べ、測り方の注記（`/model` で切り替えた直後のプロンプトは判定から除いて別に集計する、測定点 B は同じ event でマッチした全 hook の経過時間（D22）、Remote Control の有無・モデル・permission mode を記録して条件ごとに集計する）を足した（[裁定待ち事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-12）

#### 7.3.4 その他の観測（blocked_on_user、logs・metrics に出ない API 呼び出し、Remote Control）

- **`claude_code.tool.blocked_on_user`（`-p`）**: 2.1.287 では source・decision が `unknown` だった。2.1.296 では `config`・`accept` になり、拒否も `reject`・`config` で記録された。2.1.288 の修正（D19）を実機で確かめた。対話モードは両版とも `config`・`accept`。span の種類（interaction、llm_request、tool、tool.blocked_on_user、tool.execution）は両版で同じ
- **logs・metrics に出ない API 呼び出し**（2.1.287・2.1.296 とも）: debug log には、OTel の logs（`api_request`）と metrics に出ない API 呼び出しがある。起動時の `quota_check` と、ターン終了後の `side_query` が各 1 回である。ターン終了後の `side_query` は auto mode の判定とは時刻が合わず、auto mode の分類器の呼び出しではない。logs・metrics だけでは全 API 呼び出しを数えられず、`cost_usd` の合計は実際より小さくなりうる（[§7.5](#sec-7-5)）。2026-10-12 の C-6b では、自前の分類器リクエストも同じ `side_query` として debug log に出て、logs・metrics には出なかった（次の項目）
  - traces での見え方（2026-10-12 追記。当初は traces を見ていなかった）: ターン終了後の `side_query` は、traces には `claude_code.llm_request` span（`query_source_safe=agent_classifier`、`llm_request.context=standalone`、トークン数付き）として出ていた。モデルは、2.1.287 では Haiku 4.5、2.1.296 では Haiku 5.5 だった。debug log のリクエスト ID と span の `client_request_id` は、2.1.287 の 15 run、2.1.296 の 12 run のすべてで一致した。この span は Remote Control に接続した対話 run にだけあり、Remote Control を切った 2.1.296 の 13 run（Remote Control なしの ih・imm・in の 9 回と、C-6b の 4 回）には、span も debug log の `side_query` も無かった。何を判定しているか、Remote Control との因果は確かめていない。`quota_check` は traces にも見当たらない。したがって、traces の span を集計すれば、本環境で debug log を取った run に現れた呼び出し（`side_query`・`generate_session_title`・`repl_main_thread`・`prompt_suggestion`・`sdk`）は数えられ、`quota_check` だけが残る。分類器が拒否する操作、複数段階の判定、compaction、サブエージェントを debug log 付きで観測した run は無い。`quota_check` の課金とトークン量は未確認である（セッションごとに 1 回。トークン量は不明）
- **分類器のモデル呼び出し**: 2.1.296 の i6〜i8 でも、`api_request` に現れなかった（`query_source` は `generate_session_title`・`repl_main_thread`・`prompt_suggestion` だけ）。Haiku 5.5 では `--model haiku` の対話も auto のまま動くので、分類器が働く場面は増える
  - 用語（2026-10-12 追記）: 分類器は、auto mode で Claude Code が実行しようとする操作（Bash のコマンドや外部への通信など）を、確認なしで許可してよいかを実行前に判定する仕組みで、読み取りの既定許可や作業フォルダ内の書き込みの近道で決まる操作では呼ばれない。判定の方法は、本体のモデルリクエストに同乗するサーバー側チェック（課金されない）と、別の呼び出しとして Sonnet 5 を使う自前の分類器リクエスト（アカウントの種類によっては課金される）の 2 つである
  - 2026-10-12 追記（D33。J-21）: docs の permission-modes の「Server-side classifier review」節（節そのものは基線の docs からある）によると、auto mode では、Claude Code が自前の分類器リクエストを送る代わりに、セッション自身のモデルリクエストの中でサーバーにチェックを依頼できる（課金されない）。直接接続では、Anthropic の展開に応じて依頼する（docs）。i6〜i8 の観測（i7・i8 は分類器を使わずに決まった）はそのまま正しい
  - C-6b（2026-10-12）: 分類器が呼ばれる操作で、見え方を確かめた。条件は cc 2.1.296、対話モード（auto mode）、`--model claude-sonnet-5-5`、Remote Control なしで、Bash で外部への curl を実行させる操作を、(a) 既定と (b) `CLAUDE_CODE_AUTO_MODE_SERVER=0`（その cc プロセスにだけ設定）で各 2 回、交互に行った
    - (a) 既定: `api_request` の `query_source` は `generate_session_title`・`repl_main_thread`・`prompt_suggestion` だけで、debug log にも分類器用のリクエストや分類器の行は無かった。docs の「チェックはセッション自身のモデルリクエストに同乗する」と矛盾しないが、サーバー側でチェックしたことを直接示す行も無い。同乗したとは断定せず、別のリクエストは出なかった、とだけ言える
    - (b) `=0`: debug log では、判定 1 回ごとに Claude Code 自前の分類器リクエストが出た（モデルは Sonnet 5、debug log の source は `side_query`）。OTel の logs（`api_request`）にも metrics（`claude_code.token.usage`）にも現れず、logs の `query_source` の新しい値も無かった。一方、traces には、判定ごとに `claude_code.llm_request` span が 1 本出ていた（`query_source_safe=auto_mode`、モデルは Sonnet 5、親 span は `claude_code.tool.blocked_on_user`）。debug log のリクエスト ID・時刻と、span の `client_request_id`・時刻は 2 回とも一致した。span にはトークン数が入っていた（1 回あたり入力 90・出力 9 トークン。ほかに約 4.6 万トークンのキャッシュがあり、1 回目は書き込み、2 回目は読み込みだった。debug log では伏せ字）。当初は traces を見ておらず、「OTel に出ない」「トークン数は取れなかった」と書いていた（2026-10-12 に訂正。[§7.4](#sec-7-4)）。許可判定の時間（`permissionDecisionMs`）は、(a) の 0.3〜0.5 秒に対し約 2.3 秒だった
    - 意味: R6 の確かめ方（分類器がモデルを呼ぶ操作で `query_source` の新しい値を待つ）は、logs・metrics では使えない（どちらの条件でも分類器のリクエストが `api_request` に出ない）。traces では、自前の分類器リクエストが `query_source_safe=auto_mode` の span として出るので使える。自前の分類器リクエストは、上の「logs・metrics に出ない API 呼び出し」と同じ系統で、debug log の source では、ターン終了後の `side_query` と区別できない（debug log で数えるなら `classifier_request_` で始まる行を使う。traces なら `query_source_safe` の `auto_mode` と `agent_classifier` で分けられる）。職場でサーバー側チェックが落ちると、課金される分類器リクエストは logs・metrics の集計から漏れる。本活動の受信は traces も受けるので、traces の span を集計に含めれば漏れない見込みである（職場は、直接接続の C-6b からの推定）。サーバー側チェックが効いていれば、判定は本体のリクエストに同乗し、本体のリクエストは logs・traces の両方に出るので、サーバー側チェックの有無によらない見込みである。traces の取得に致命的な欠点は無いので、作業指示者はこの件を本活動にとって致命的ではないと判断した（2026-10-12）。ただし traces は beta 機能（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`）で、版によって形が変わりうる。logs・metrics から外す理由は docs に書かれていない（Agent SDK の使用量 `modelUsage` は、分類器を除くと docs に明記している）
    - 制約: 各条件 2 回、1 種類の操作（外部への curl）だけ。分類器が拒否する操作や、判定が複数の段階に進む場合は確かめていない。本環境の `/status` の Auto mode server 行は見ていない。2.1.296 で測った結果で、版で変わりうる
  - 職場（社内 LLM ゲートウェイ＋Bedrock）では、gateway が要求や結果を素通ししないと、Claude Code 自前の分類器リクエストに切り替わり、アカウントの種類によってはトークン使用量として課金される（docs）。C-6b のとおりなら、その分は logs・metrics に出ず、traces の span には出る（職場では同じ形で traces に出ると見込む。直接接続の観測からの推定）。traces を集計に含めれば漏れない見込みなので、職場がサーバー側チェックを効かせているか（分類器の状態）は確かめない（作業指示者の判断、2026-10-12。J-23 は取り下げ）。職場の確認は、課金の通知への応答と、受信確認で traces に `llm_request` span が届くことだけで、[§7.5](#sec-7-5) の職場の確認に置いた（通知が出たら Enter で続行する。J-22 で裁定済み）
- **Remote Control**: ユーザ settings の `remoteControlAtStartup` の設定により、対話セッションは起動時に Remote Control に接続する。対話モードの計測は 2.1.287（§4.3 実測 4）・2.1.296 とも、接続した状態だった（debug log で確認）。遅延への影響は [§7.3.2](#sec-7-3-2)
  - 切り方: `remoteControlAtStartup` を false にする 1 キーだけの JSON ファイルを作り、そのパスを `--settings` に渡した（JSON の文字列を直接渡すと、シェルごとの引用符の扱いが要る）
  - 切れたことの確かめ方: debug log に、Remote Control の接続を示す行（接頭辞 `[remote-bridge]`・`[bridge:repl]`・`[bridge]`）が 0 件であること（切った 9 回は、すべて 0 件だった）。`--plugin-dir` を使う実行では、ファイル識別の行にも「bridge」の語が出るので、語ではなく接頭辞で判定する
  - Remote Control に接続した ih・imm では、6 回中 5 回で generate_session_title の `api_request` が 2 回出た。切った 9 回では、すべて 1 回だった。ターン終了後の `side_query`（traces の `agent_classifier` の span）も、接続した run にだけ出た（2026-10-12 に traces で確認。上の「logs・metrics に出ない API 呼び出し」）。因果は確かめていないが、コスト集計では、Remote Control の有無で裏のリクエスト数が変わりうる
  - 今後の動作検証は、Remote Control を切って行う（作業指示者の指示、2026-10-10）。この指示は Claude が起動する計測用のセッション（probe と Phase 3 の比較実験）に当てはめ、J-12 の判定に使う日常のセッションは切らずに測ると解釈した（J-19）。LLM ゲートウェイ環境では、Remote Control はそもそも使えない。理由は Bedrock ではなく、`ANTHROPIC_BASE_URL` が Anthropic 以外のホストを指すことである。ゲートウェイの credential（`ANTHROPIC_AUTH_TOKEN`・`ANTHROPIC_API_KEY`・`apiKeyHelper`）が有効な間も使えない（docs。2026-10-18 に改めた。J-26）

#### 8.3.3 auto mode の分類器の新しい属性

2.1.301 から、OTel の `tool_decision` イベントに `permission_mode` と `classifier_verdict` が付く（D39）。

- **`-p` での付き方**: 2.1.302 の `-p` の run（q1〜q3・p302-*・p302k-*）で、`permission_mode` は `auto` が 29 件、`default` が 34 件（うち拒否 1 件）だった。`classifier_verdict` は、auto mode の Bash・Agent などの判定に `allow` で付き（21 件）、Read・Glob・Skill（読み取りなどの既定の許可で決まる操作）には付かなかった。default mode では付かない。観測した値は `allow` だけである
- **C-6b の再実行**: 条件は cc 2.1.302、対話モード（auto mode）、`--model claude-sonnet-5-5`、クリーン、Remote Control なしで、Bash で外部への curl を 1 回実行させる操作を、(a) 既定と (b) `CLAUDE_CODE_AUTO_MODE_SERVER=0` で各 2 回、交互に行った（§7.3.4 の C-6b と同じプロンプト）

| 項目 | (a) 既定 | (b) `CLAUDE_CODE_AUTO_MODE_SERVER=0` | 2.1.296 の C-6b |
|---|---|---|---|
| `api_request` の `query_source` | `generate_session_title`・`repl_main_thread`（2 件）・`prompt_suggestion` | 同じ。新しい値は無い | 同じ種類 |
| traces の `query_source_safe=auto_mode` の `llm_request` span | 無い | 判定ごとに 1 本（モデルは Sonnet 5、トークン数付き） | (b) だけにあった（同じ） |
| traces の `agent_classifier` の span | 無い | 無い | 無い（2.1.296 では、Remote Control に接続した run だけにあった） |
| `tool_decision` | Bash、`permission_mode=auto`、`classifier_verdict=allow`（source は `config`、decision は `accept`） | 同じ値 | `permission_mode`・`classifier_verdict` の属性が無かった |
| `classifier_category` | 付かない | 付かない | — |
| 許可判定の時間（`permissionDecisionMs`、debug log） | 285 / 280 ms | 2,476 / 2,146 ms | (a) 474 / 330 ms、(b) 2,346 / 2,334 ms |

- **意味**: `classifier_verdict` は、分類器が判定したことを logs で示す。ただし (a) と (b) で値が同じなので、サーバー側チェックか、Claude Code 自前の分類器リクエストかは、`classifier_verdict` では区別できない。自前のリクエストが出たか（費用の漏れの有無）は、従来どおり traces の `query_source_safe=auto_mode` の span で見る
  - J-23 の取り下げの判断（logs と traces を集計に含めれば、分類器のリクエストは漏れない見込み。[§7.3.4](#sec-7-3-4)）の根拠は変わらない。判定の有無を logs でも確かめられる分、確かめやすくなった。(b) では判定 1 件に span が 1 本だったので、自前に落ちたセッションでは、判定の数と span の数を突き合わせて span の欠けを見つけられる（直接接続、各 n=2）
  - 【推定】職場でも、分類器が自前に落ちても落ちなくても、判定したことは logs の `classifier_verdict` で、自前に落ちたかは traces で分かる（直接接続の観測からの推定。社内 LLM ゲートウェイ＋Bedrock の経路で `classifier_verdict` が付くかは確かめていない）
- **R6 の確かめ方**: 分類器の別の `api_request` が出ない点は 2.1.296 と同じ（既定でも自前でも出ない）。2.1.301 以降は、`tool_decision` の `classifier_verdict` で分類器の判定を logs で見分けられる。§7.5 の R6 の行の確かめ方（traces の span、debug log の `classifier_request_` で始まる行）に、この経路が加わる
- **`classifier_category`**（分類器が block したときに合致した組み込みの規則の名前。changelog 2.1.301 では `OTEL_LOG_TOOL_DETAILS=1` のときだけ。docs の本文には無い）: block される操作をせず、`OTEL_LOG_*` のフラグも OFF なので、観測していない。2.1.301 では多くの block で欠けていた（2.1.302 で修正。D40）
- **分類器のモデル**: 2.1.302 から、client-side の分類器のモデルを `CLAUDE_CODE_AUTO_MODE_MODEL` で選べる（サーバー側の分類器には効かない。D48）。変数を設定しない (b) では、自前の分類器リクエストのモデルは Sonnet 5 だった。§3.4・§7.3.4 の「分類器は Sonnet 5」は、client-side の分類器の既定として読む（[§8.4](#sec-8-4)）

#### 8.3.4 transcript

2.1.300 から、ローカルの transcript に、API リクエストごとの system prompt・tools・parameters が記録される（D43）。2.1.296 と 2.1.302 の同じ種類の `-p` の run（q1〜q3 と qk1〜qk3、lat-a と p302k-a、lat-b と p302k-b）の、メインスレッドの transcript を比べた。

| 記録型 | キー | 内容 |
|---|---|---|
| `api-request`（新規） | `type`・`id`・`timestamp`・`version`・`sessionId`・`querySource`・`shapeHash`・`params`・`keep`・`tail`・`cacheControl`・`requestDigest`・`base` | リクエスト 1 件ごと。`params` のキーは `model`・`betas`・`max_tokens`・`thinking`・`context_management` |
| `api-request-shape`（新規） | `type`・`timestamp`・`version`・`sessionId`・`shapeHash`・`shape` | `shape` のキーは `system`（text ブロックの配列）と `tools`（`name`・`description`・`input_schema`・`eager_input_streaming`）。同じ `shapeHash` は、セッションの中で 1 回だけ書かれる |
| `api-request-blob`（新規） | `type`・`hash`・`sessionId`・`message` | メッセージ本文の実体（`hash` で参照する） |
| `assistant`（既存） | `requestRef` が加わった | `api-request` との対応 |
| `user`（既存） | `toolDenialKind` が加わった（拒否があった run だけ） | — |

- 既存の記録型は残り、削除は無い。突合に使う assistant の `requestId` も変わらない
- サイズ（transcript の 1 ファイルあたりの平均 / 一意な requestId あたり）:

| 比較 | 2.1.296 | 2.1.302 | 新しい記録型の量（2.1.302、ファイルの合計） |
|---|---|---|---|
| q1〜q3 相当（2 ファイル） | 約 202 KB / 約 81 KB | 約 297 KB / 約 149 KB | shape 104 KB、blob 79 KB、api-request 24 KB |
| lat-a 相当（Haiku 4.5 を明示、3 ファイル） | 約 190 KB / 約 81 KB | 約 372 KB / 約 159 KB | shape 266 KB、blob 96 KB、api-request 9 KB |
| lat-b 相当（command hook あり、3 ファイル） | 約 190 KB / 約 95 KB | 約 370 KB / 約 159 KB | lat-a 相当とほぼ同じ |

- 短い `-p` の run では、1 ファイルあたり約 95〜180 KB 増え、1 ファイルあたりで約 1.5〜2 倍、一意な requestId あたりで約 1.7〜2 倍になった。大きいのは shape（system と tools。セッションに 1 回）と blob で、リクエスト単位の `api-request` は小さい（1 件あたり約 1.3〜6 KB）
- lat-a 相当では、既存の attachment も 533 → 697 KB（ファイルの合計）に増えた。利用できる skill の一覧などの環境の差と見ているが、仕様差かは判定していない
- 【推定】長い会話では shape の重複排除が効くので、増分はリクエスト数に比例しては増えない（確かめていない）
- **突合**: thinking tokens と request_id の突合は、引き続き成り立った。2.1.302 の `-p` の全 run（クリーンと、ユーザ環境の plugin を有効にした run の両方）で、`api_request` 122 件中 120 件が request_id で一致し、外れは compact の 2 件（transcript に出ない。2.1.296 と同じ）、transcript だけにあるリクエストは 0 件だった。メインスレッドは入力・キャッシュ系トークンとも全件一致し、`thinking_tokens` を持つ全件で `thinking_tokens ≤ output_tokens` が成り立った。サブエージェントには、未確定の usage が残る例が q2・qk2 で各 1 件あった（2.1.296 と同じ性質）。`thinking_tokens` は Haiku 4.5・Haiku 5.5・Sonnet 5.5 のどれでも出た
- **含意**: transcript は、system prompt（【推定】ユーザの指示ファイルなどの内容を含みうる）と tools の定義を含むので、取込・保存・公開の扱いが 2.1.296 より重くなる。サイズの見積もりも変わる。本書には記録型とキー名までを書き、値は書かない
- そのほかの transcript の変更（changelog。実機では試していない）: @ で指した PDF の bytes を残さない（2.1.299）。resume・compaction の後に記録が欠ける不具合の修正（2.1.300）
- 強制終了した対話セッションの transcript（R5）は、2.1.302 では確かめていない

#### 8.3.5 ユーザ環境の plugin（測定条件の変化）

2.1.296 の測定の後に、ユーザ設定で有効な plugin が 4 つ増え、うち 2 つが command hook（`UserPromptSubmit`・`PreToolUse`・`PostToolUse`・`Stop` など）を登録していた。本書では plugin の名前は書かない。

- **素の run への影響**: 2.1.296 と同じ手順で測ると、hook なしの条件にも、各イベントでこれらの hook が走った（`UserPromptSubmit` は約 260〜330 ms、`PreToolUse`・`PostToolUse`・`Stop` は各約 230〜280 ms）。`-p` の測定点 A の hook なしは、クリーンに比べ、Haiku 4.5 を明示して 112 → 411 ms、Haiku 5.5 で 278 → 567 ms に増えた。この条件では、hook なしの基準そのものが成り立たない
- plugin を有効のままにした `-p` の値（参考。ユーザ環境の plugin の hook が混入しているので、2.1.296 との比較にも、hook と Mod の比較にも使わない。単位は ms、各 n=3 の平均。command hook の見かけの上乗せは +29 ms・−1 ms に縮んだ）:

| 条件 | hook なし | command hook（見かけの上乗せ） | Mod（見かけの上乗せ） |
|---|---|---|---|
| `-p`（Haiku 4.5 を明示） | 411 | 440（+29） | 568（+157） |
| `-p`（Haiku 4.5 を明示。`cc-plugin-agents-md` 無効） | 404 | — | 424（+20） |
| `-p`（Haiku 5.5） | 567 | 566（−1） | 710（+143） |

- **対話の日常に近い条件**: plugin は有効のまま、Remote Control を切り、hook なしで測ると（inr、3 回）、測定点 A は 730 / 521 / 528 ms（平均 593 ms）で、クリーン（145 ms）より約 450 ms 長かった。plugin の `UserPromptSubmit` の hook は 605 / 378 / 402 ms、`Stop` の hook は 349 / 311 / 299 ms かかった（OTel の `hook_execution_complete`）。Remote Control を切っているので、日常のセッション（J-19。Remote Control も普段のまま）の値ではない。日常のセッションの値は Phase 3 で測る
- **測り方**: 2.1.296 との比較には、増えた 4 つの plugin を `--settings` に渡すファイルの `enabledPlugins` で false にし、そのプロセスだけ無効にした値（クリーン）を使った。ユーザ設定は変えていない。無効になったことは OTel の `plugin_loaded` で確かめた。`hook_registered` は、probe の作業フォルダの hook（2 件）だけになった
- **plugin による属性**: plugin を有効にした run だけに、`hook_registered` の `plugin.name`・`plugin_id_hash` と、`plugin_loaded` の `plugin.version` が出た（[§8.3.1](#sec-8-3-1)）
- **J-12 に関わる事実**: 日常のセッションの hook なしの基準値は、有効な plugin の構成で変わる。本環境では、増えた 4 つの plugin（うち 2 つが command hook を登録）の有無で、対話の hook なしが約 450 ms 違った。OTel の `hook_execution_complete.total_duration_ms` は同じイベントの全 hook の経過時間（D22）なので、plugin の hook がある環境では、L1 の hook 単体の時間として読めない。hook ごとの時間は debug log の行（D28）で分けられるが、その行は debug を有効にしたセッション（`--debug-file` を付けて起動するなど）にしか出ない。J-12 の条件の扱い（判定の組と、L1 の hook 自身の時間の測り方）は、[裁定待ち事項](../作業指示者裁定待ち事項.md)で決める
- docs では、同じイベントにマッチした hook は並列に走る。【推定】そのため、L1 の command hook の上乗せは、既存の plugin の command hook より短ければ、見かけ上ほとんど増えない。`-p` で command hook の見かけの上乗せが +29 ms・−1 ms に縮んだことは、この推定と合う。Mod は、plugin を有効のままでも見かけの上乗せが +157 ms・+143 ms で、隠れなかった（クリーンの +201 ms・+185 ms からの縮み方が小さい）。【推定】command hook で隠れる分だけ、L1 の hook 自身の時間は見かけの上乗せより長い。職場の plugin の構成が本環境と違えば、本環境で隠れた L1 の hook の時間が、職場ではそのまま上乗せに出うる。Phase 3 で測る
- 最初の run だけ遅い傾向があった（クリーンの対話の hook なしの 1 回目は 219 ms、日常に近い条件の 1 回目は 730 ms）。理由は確かめていない
