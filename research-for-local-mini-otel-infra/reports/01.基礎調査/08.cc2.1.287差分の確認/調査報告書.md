## 0. サマリ

- **調査内容**: Phase 1 の基線（計画書と同じ docs 2026-09-27 版、cc 2.1.283）から cc 2.1.287 までの公式 docs・changelog の差分を洗い出し、既存文書 55 箇所への影響を棚卸しした。差分に関わる事実は cc 2.1.287 で再実測した
- **調査結果**
  - 本活動に関わる項目は 12 件（D1〜D12）。基線の後の docs の変更は 7 件で、OTel の属性を直接変えたのは 2.1.287 の `user_prompt.prompt_text` の追加だけだった（[§2.1](#sec-2-1)）
  - 残る 5 件（D3〜D7）は基線の docs にすでに書かれており、Phase 1 の文書の誤り・記載漏れだった（[§2.2](#sec-2-2)）
  - 2.1.287 の実測で、属性の削除・改名は無かった。`prompt_text` は内容記録フラグ OFF で伏せ字になる（[§3.1](#sec-3-1)）
  - 既存文書に誤りが 3 件あった。1-1 の `app.version`・`app.entrypoint` の「docs と差異」判定、仕様別紙の「agent は `custom` に丸められ区別できない」、まとめ §5.3 の反映項目である。いずれも基線の docs で既に正しく書かれていた。2026-10-03 に各文書で訂正した（[§5.1](#sec-5-1)）
  - 1-3 の「hook の待ち時間 2.1〜2.8 秒」は、2.1.283 の対話モードの 2 回（i3・i4）の値で、一般化しすぎだった。`-p` では 130〜370 ms。対話モードは 2.1.287 で 3 回を追加で測り、2 秒超は出なかった（対話モードの command hook は 6 回中 2 回が 2 秒超。原因は未特定）（[§4.3](#sec-4-3)）
  - Claude Mods（2.1.287）の `classic.UserPromptSubmit` で受け取った `prompt_id` は、`-p` と対話モードの各 3 回とも OTel の `prompt.id` と一致した（[§4.2](#sec-4-2)）。llm_request の開始までの上乗せは、両モードとも Mod が command hook より小さかった（[§4.4](#sec-4-4)）
- **結論・示唆**: 本活動が依存する属性は 2.1.287 でも使える。既存文書は誤り 3 件の訂正と差分の追記で足り、2026-10-03 に反映した（反映状況は [§5.2](#sec-5-2)）。Mods をタグ付けの手段に採るかは、本書では判断しない。1-3 の改訂と Phase 2 に委ねる

## 1. 目的と方法

Phase 1 の報告書は cc 2.1.283 時点の docs と実測に依拠している。その後 cc 2.1.287 までに仕様が変わったので、既存文書のどこが古くなったかを特定し、実測で確かめる。

- **基線**: docs の 2026-09-27 15:00 取得版（ローカル docs リポジトリ `C:\cc-workspace\LLMs` の commit 4b44c61）。計画書 §2 と仕様別紙が基線にしている版
  - この版にした理由: 計画書 §2 冒頭は、1-1〜1-6 がこの版の docs に依拠したとしている（1-6 の環境欄も同じ）。v0.1 は引継ぎ資料 v2.1 が使った 2026-09-26 15:00 取得版（commit df1f117）を基線にしていた
  - D3・D4 の記述は 09-26 版にもある。D5〜D7 は 09-27 版で初めて現れる。Phase 1 の文書が依拠した 09-27 版に照らすと、D3〜D7 はいずれも既存文書の誤り・記載漏れに当たる
- **比較先**: 同リポジトリの 2026-10-02 15:00 取得版（commit 9b8bb3e）
- **補完**: ローカル版には 2.1.287 がまだ載っていなかった。2.1.287 の分は、公式 `https://code.claude.com/docs/llms-full.txt` を curl で取得した版（取得時刻 2026-10-02T19:28:54Z）、`monitoring-usage` ページ（2026-10-03 取得）、`changelog` ページで補った
- **差分の取り方**: 基線と比較先の `llms-full.txt` を、OTel・hook・transcript・permission 等のキーワードで照合した。補完分は changelog の 2.1.284〜2.1.287 と Monitoring ページを読んだ。各項目は基線の `llms-full.txt` でも grep し、基線にすでにある記述は docs の変更から外した。既存文書への影響は、同じキーワード群で各文書を grep して棚卸しした
- **再実測の条件**: 1-1 と同じ自作の OTLP/HTTP 受信スクリプトを使った。手順・スクリプト・受信データは scratchpad に置き、コミットしない
  - 有効化: ユーザ settings は変更せず、実測用の cc プロセスにだけ環境変数を渡した
  - 内容記録のフラグ（`OTEL_LOG_*`）はすべて OFF。計画書 §7 #2 の判断待ちのため
  - q1〜q3 では `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` と `OTEL_METRICS_INCLUDE_VERSION=true` を付けた

<a id="sec-4"></a>
## 4. Claude Mods の事実と実測

Mods は 2.1.287 で加わった、plugin の中で動く JS/TS の hook である。`classic.UserPromptSubmit` の Mod は OTel の `prompt.id` と結合でき、`-p` と対話モードの両方で、llm_request の開始までの上乗せが command hook より小さかった。標本は各 3 回と小さい。command hook との比較は [§4.4](#sec-4-4) の表に集約した。

<a id="sec-4-1"></a>
### 4.1 仕組み・API・管理（docs の記載）

- **位置付け**: plugin の hooks module（`register(on, options)` をエクスポートする ES module）。cc のプロセス内で動き、インストール済みの Mod は 1 本のワーカースレッドを共有する。別プロセスを起動する command hook とは実行形態が異なる
  - 言語は JS / TS で、ビルド不要。Node.js API とタイマーのグローバルは無く、外部へは Mods API を通して触る
  - 端末 CLI・Desktop の Code タブ・VS Code 拡張・`claude -p`・Agent SDK で動く
- **主なイベント**: hook は `($, e, next)` を受ける middleware で、観測・書き換え・応答ができる
  - `prompt.submit`: プロンプト送信時。本文（`e.text`）の読み取り・書き換え・破棄
  - `turn.start` / `turn.step` / `turn.complete`: turn の開始、モデルへの各リクエスト、終了。`turn.complete` は turn のトークン合計（`e.usage`）を持つ
  - `classic.<settings hook のイベント名>`: settings hook と同じイベントを、stdin の JSON と同じ `e` で受ける
- **API**: ファイル（`$.fs`、1 ファイル 4 MiB まで）、HTTP（`$.http.fetch`）、タイマー（`$.clock`）、モデル（`$.model.complete` 等。利用者のプラン・API キーで課金）、プロセス（`$.process.run`、既定 30 秒）。hook 自身の実行時間は 10 秒まで
  - OTel の属性・span を書き換える API は無い。`$.telemetry` は cc 本体か組み込みの Mod が呼んだときだけ送信される
  - Mods はサンドボックス化されず、利用者と同じ権限で動く
- **管理**: 2.1.287 以降、既定で有効。組織は managed settings で止められる
  - `allowManagedModsOnly`: 利用者が持ち込む Mod を全て不許可。利用者の settings hook は動き続ける
  - `allowManagedHooksOnly`: 利用者の settings hook も止まる。`disableAllHooks`: 全 Mod・全 hook を停止。`disableSideloadFlags`: `--plugin-dir` を拒否
  - `$.http.fetch` は、組織が web fetch か nonessential traffic を無効にしていると拒否される
- **型定義の記述**: cc に同梱の plugin-authoring の型定義（hook 入力の基底型）は、`prompt_id` を「OTel イベントの `prompt.id` 属性と同じ値で、hook の出力を OTel イベントとプロンプト単位で結合できる」と説明している

<a id="sec-4-2"></a>
### 4.2 実測 1: `prompt_id` の結合

`classic.UserPromptSubmit` でプロンプトをルール分類し、`prompt_id`・`session_id`・ラベル等を 1 プロンプト 1 ファイルで書き出す Mod を作った。本文は保存しない。`claude plugin validate` を通し、`claude -p --plugin-dir` で読み込んだ。

- lat-c1〜c3 の 3 回とも、Mod が書いた `prompt_id` は OTel の `user_prompt` の `prompt.id` と一致した
- 対話モード（imm1〜imm3、`--plugin-dir` で読み込み。[§4.3](#sec-4-3) 実測 4）でも、3 回とも一致した
- `-p` では、入力の `source` が null だった。型定義上、段階的に提供中の項目で省略され得る
- 記録の時刻が `{}` になったのは、probe 側の `await` 漏れである（`$.clock.now()` は Promise を返す）。cc の挙動ではない

### 4.4 command hook と Mod の比較

タグ案 L1 の実装手段（command hook か Mod か）を Phase 2 で選ぶための材料を、この表に集約する。ほかの文書はこの表を参照する。

| 観点 | command hook（Node.js） | Mod（`classic.UserPromptSubmit`） |
|---|---|---|
| 実行形態・言語 | プロンプトごとに別プロセスを起動する。言語は任意（測定は Node.js） | cc のプロセス内のワーカースレッドで動く JS / TS。Node.js API は無く、Mods API を使う（[§4.1](#sec-4-1)） |
| `prompt_id` の結合 | OTel の `prompt.id` と一致（1-1 の 7 プロンプト。1-3 §2） | 一致（`-p` 3 回、対話モード 3 回。[§4.2](#sec-4-2)） |
| 上乗せ（測定点 A の hook なしとの差。平均） | `-p` 約 150 ms、対話モード 約 440 ms | `-p` 約 30 ms、対話モード 約 300 ms |
| hook 単体の所要時間（測定点 B） | `-p` を中心とする 11 回（1-1 の i3・i4 以外の 5 回と今回の `-p` 6 回。対話モードは i5 だけ）で 130〜370 ms。2.1.287 の対話モード 3 回で 383〜495 ms。2.1.283 の対話モードの 2 回が 2.1〜2.8 秒 | 対話モード 約 296 ms（1 回） |
| 2 秒超の観測 | 対話モードの 6 回中 2 回（2.1.283 の i3・i4。原因未特定）。それ以外の 11 回では 0 回 | なし（測定点 A の 6 回） |
| 本文の扱い | hook 入力の `prompt` で読める | `e`（hook 入力と同じ内容）で読める |
| ラベルの書き出し | 任意のファイル操作 | `$.fs`（1 ファイル 4 MiB まで）、`$.http.fetch` |
| 管理による停止 | managed settings の `allowManagedHooksOnly`（利用者の settings hook を止める）、`disableAllHooks` | `allowManagedModsOnly`、`allowManagedHooksOnly`、`disableAllHooks`、`disableSideloadFlags`（`--plugin-dir` を拒否） |
| 未確認 | 日常の長いセッションでの値 | 日常の長いセッション、Desktop・VS Code での値。`$.http.fetch` のローカル宛先（[§6](#sec-6)） |

- 測定点 A の上乗せは、`-p` と対話モードのどちらでも Mod が command hook より小さかった。どちらも各 n=3、Haiku だけの値である
- command hook は `UserPromptSubmit` と `SessionStart` の 2 つ、Mod は 1 つで、本数がそろっていない。【推測】`SessionStart` は interaction span の開始より前に走るので、測定点 A への影響は小さい
- 職場環境では、managed settings で Mod だけでなく command hook も止められうる。両方が止められていればタグ案 L1 は成り立たない（Phase 3 の職場環境確認で確かめる。[§6](#sec-6)）

Mods をタグ付けの手段に採るかの判断は、1-3 の改訂と Phase 2 に委ねる。

**最強の反論と残存リスク**

- 反論: 再実測は `-p` の短い実行と、各 3 回の小標本が中心で、Mods の遅延の優位や「属性の削除なし」を一般化できない
  - 属性集合の比較は、1-1 と同じ実行パターン（skill・サブエージェント・compact を含む）で行った。【推測】依存する属性の有無は、標本数より実行パターンで決まるので、`-p` でも判定できる
  - 遅延の比較と Mod の挙動は、対話モードでは短い実行の各 3 回だけを確かめた。日常の長いセッションでは未確認である（残存リスク）。Phase 3 の PoC で、同じ指標で測り直す
  - command hook の 2 秒超（2.1.283 の対話モードの 2 回）は、同じ起動のしかたの 2.1.287 の 3 回で再現せず、原因も特定していない（残存リスク）
- 反論: docs の基線と比較先の照合はキーワード検索によるため、拾えていない差分があり得る
  - 2.1.284〜2.1.287 の changelog は、OpenTelemetry・telemetry を含む項目を全件確認した。docs 本文の未検出の差分は残存リスクとして残る。計画書の基線（実測時点と再確認時点の 2 段）に新しい再確認時点を加えるときも、同じ手順で差分を確かめる
