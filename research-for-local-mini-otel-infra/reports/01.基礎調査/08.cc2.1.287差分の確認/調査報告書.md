## 0. サマリ

- **調査内容**: Phase 1 の基線（計画書と同じ docs 2026-09-27 版、cc 2.1.283）から cc 2.1.287 までの公式 docs・changelog の差分を洗い出し、既存文書 55 箇所への影響を棚卸しした。差分に関わる事実は cc 2.1.287 で再実測した
- **調査結果**
  - 本活動に関わる項目は 12 件（D1〜D12）。基線の後の docs の変更は 7 件で、OTel の属性を直接変えたのは 2.1.287 の `user_prompt.prompt_text` の追加だけだった（[§2.1](#sec-2-1)）
  - 残る 5 件（D3〜D7）は基線の docs にすでに書かれており、Phase 1 の文書の誤り・記載漏れだった（[§2.2](#sec-2-2)）
  - 2.1.287 の実測で、属性の削除・改名は無かった。`prompt_text` は内容記録フラグ OFF で伏せ字になる（[§3.1](#sec-3-1)）
  - 既存文書に誤りが 3 件あった。1-1 の `app.version`・`app.entrypoint` の「docs と差異」判定、仕様別紙の「agent は `custom` に丸められ区別できない」、まとめ §5.3 の反映項目である。いずれも基線の docs で既に正しく書かれていた。2026-10-03 に各文書で訂正した（[§5.1](#sec-5-1)。2.1.296 の追補で見つけたものを含む Phase 1 の誤りの一覧は [§7.4](#sec-7-4)）
  - 1-3 の「hook の待ち時間 2.1〜2.8 秒」は、2.1.283 の対話モードの 2 回（i3・i4）の値で、一般化しすぎだった。`-p` では 130〜370 ms。対話モードは 2.1.287 で 3 回を追加で測り、2 秒超は出なかった（対話モードの command hook は 6 回中 2 回が 2 秒超。原因は未特定）（[§4.3](#sec-4-3)）
  - Claude Mods（2.1.287）の `classic.UserPromptSubmit` で受け取った `prompt_id` は、`-p` と対話モードの各 3 回とも OTel の `prompt.id` と一致した（[§4.2](#sec-4-2)）。llm_request の開始までの上乗せは、2.1.287 では両モードとも Mod が command hook より小さかった（[§4.4](#sec-4-4)。2.1.296 の `-p` では逆。[§7.3.2](#sec-7-3-2)）
- **2.1.296 追補（[§7](#sec-7)、2026-10-10）**: docs 2.1.295・changelog 2.1.288〜2.1.295・cc 2.1.296 の実機で確かめ直した。依存する属性の削除・改名・追加は無く、`prompt_id` の結合と transcript の突合も同じだった（[§7.3.1](#sec-7-3-1)）
  - `-p` では Mod の上乗せが command hook を上回り、2.1.287 と大小が逆転した。モデルと permission mode を 2.1.287 とそろえた対照（Haiku 4.5 を明示し、3 条件を同じバッチで各 3 回）で command hook +135 ms・Mod +198 ms（2.1.287 は +152 ms・+31 ms）だったので、版の差である。`haiku` エイリアスの解決先（Haiku 5.5）でも +155 ms・+204 ms と同じ向き。対話モードは両方とも縮み、Mod が小さいまま。2.1.287・2.1.296 の測定では、どの上乗せも 0.5 秒未満で、J-3・Q4 の推奨は変わらない（[§7.3.2](#sec-7-3-2)）
  - `haiku` は 2.1.293 から Haiku 5.5 に解決し、auto mode のまま動く。本書 §3・§4 の「Haiku」は Haiku 4.5 である。docs は、cc が自分で始めたターンでも `user_prompt` と UserPromptSubmit が発火すると明記した（[§7.2](#sec-7-2)・[§7.3.3](#sec-7-3-3)）
  - 本環境はユーザ settings で `-p` も auto mode で起動しており、§5.3 の「Q2 は影響なし」は誤りだった。訂正した（[§7.3.3](#sec-7-3-3)）
- **docs 2.1.296 の反映（2026-10-12）**: 2.1.296 の changelog を含む docs で確かめ直し、§7 の事実で崩れたものは無かった（[§7.2](#sec-7-2) D28〜D36）。`-p` の Mod の上乗せは、組み込み Mod `cc-plugin-agents-md` をセッション単位で無効にすると消え（+174 ms → −8 ms。C-3c、n=3）、§7.3.2 の推測を確かめた（[§7.3.2](#sec-7-3-2)）
  - auto mode の分類器のチェックは、基線の docs から、セッション自身のモデルリクエストの中でサーバーが行える（無料）と書かれていた。Phase 1 はこれを見落としていた（J-21）。職場では、gateway が要求・結果を素通ししないと Claude Code 自前の分類器リクエストに切り替わり、トークン使用量として課金される。確認は Phase 3 の職場の項目に加えた（[§7.3.4](#sec-7-3-4)・[§7.5](#sec-7-5)）
- **結論・示唆**: 本活動が依存する属性は 2.1.287・2.1.296 でも使える。既存文書は、誤りの訂正と差分の追記で足りた。2.1.287 までの分は 2026-10-03 に（反映状況は [§5.2](#sec-5-2)）、2.1.296 の追補の分は 2026-10-10 に、docs 2.1.296 の分は 2026-10-12 に反映した（[§7.4](#sec-7-4)。Phase 1 の誤りの一覧も §7.4）。Mods をタグ付けの手段に採るかは、本書では判断しない。1-3 の改訂と Phase 2 に委ねる

## 1. 目的と方法

Phase 1 の報告書は cc 2.1.283 時点の docs と実測に依拠している。その後 cc 2.1.287 までに仕様が変わったので、既存文書のどこが古くなったかを特定し、実測で確かめる。§1〜§6 の範囲は 2.1.287 までである。2.1.288〜2.1.296 の分は、同じ手順で [§7](#sec-7) に追補した。

- **基線**: docs の 2026-09-27 15:00 取得版（ローカル docs リポジトリ `C:\cc-workspace\LLMs` の commit 4b44c61）。計画書 §2 と仕様別紙が基線にしている版
  - この版にした理由: 計画書 §2 冒頭は、1-1〜1-6 がこの版の docs に依拠したとしている（1-6 の環境欄も同じ）。v0.1 は引継ぎ資料 v2.1 が使った 2026-09-26 15:00 取得版（commit df1f117）を基線にしていた
  - D3・D4 の記述は 09-26 版にもある。D5〜D7 は 09-27 版で初めて現れる。Phase 1 の文書が依拠した 09-27 版に照らすと、D3〜D7 はいずれも既存文書の誤り・記載漏れに当たる
- **比較先**: 同リポジトリの 2026-10-02 15:00 取得版（commit 9b8bb3e）
- **補完**: ローカル版には 2.1.287 がまだ載っていなかった。2.1.287 の分は、公式 `https://code.claude.com/docs/llms-full.txt` を curl で取得した版（取得時刻 2026-10-02T19:28:54Z）、`monitoring-usage` ページ（2026-10-03 取得）、`changelog` ページで補った
- **3 段目の比較点（§7）**: docs は 2026-10-10 に curl で取得した版（2.1.295 時点。ローカル docs リポジトリの commit f7270cc（10-09）と同一）、changelog は 2.1.288〜2.1.295、実機は cc 2.1.296。この時点で 2.1.296 の changelog は未公開で範囲外だった。2026-10-12 に、公開済みの 2.1.296 の changelog を含む docs で 4 段目として確かめた（[§7.1](#sec-7-1)）
- **差分の取り方**: 基線と比較先の `llms-full.txt` を、OTel・hook・transcript・permission 等のキーワードで照合した。補完分は changelog の 2.1.284〜2.1.287 と Monitoring ページを読んだ。各項目は基線の `llms-full.txt` でも grep し、基線にすでにある記述は docs の変更から外した。既存文書への影響は、同じキーワード群で各文書を grep して棚卸しした
- **再実測の条件**: 1-1 と同じ自作の OTLP/HTTP 受信スクリプトを使った。手順・スクリプト・受信データは scratchpad に置き、コミットしない
  - 有効化: ユーザ settings は変更せず、実測用の cc プロセスにだけ環境変数を渡した
  - 内容記録のフラグ（`OTEL_LOG_*`）はすべて OFF。計画書 §7 #2 の判断待ちのため
  - q1〜q3 では `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` と `OTEL_METRICS_INCLUDE_VERSION=true` を付けた

| 実行名 | 起動 | 内容 |
|---|---|---|
| q1-smoke | `-p`、Haiku 4.5 | 最小の応答 |

## 4. Claude Mods の事実と実測

Mods は 2.1.287 で加わった、plugin の中で動く JS/TS の hook である。`classic.UserPromptSubmit` の Mod は OTel の `prompt.id` と結合でき、2.1.287 では `-p` と対話モードの両方で、llm_request の開始までの上乗せが command hook より小さかった。2.1.296 の `-p` では大小が逆になった（[§7.3.2](#sec-7-3-2)）。標本は各 3 回と小さい。command hook との比較は [§4.4](#sec-4-4) の表に集約した。

<a id="sec-4-1"></a>
### 4.1 仕組み・API・管理（docs の記載）

- **位置付け**: plugin の hooks module（`register(on, options)` をエクスポートする ES module）。cc のプロセス内で動き、インストール済みの Mod は 1 本のワーカースレッドを共有する。別プロセスを起動する command hook とは実行形態が異なる
  - 言語は JS / TS で、ビルド不要。Node.js API とタイマーのグローバルは無く、外部へは Mods API を通して触る
  - 端末 CLI・Desktop の Code タブ・VS Code 拡張・`claude -p`・Agent SDK で動く
- **主なイベント**: hook は `($, e, next)` を受ける middleware で、観測・書き換え・応答ができる
  - `prompt.submit`: プロンプト送信時。本文（`e.text`）の読み取り・書き換え・破棄
  - `turn.start` / `turn.step` / `turn.complete`: turn の開始、モデルへの各リクエスト、終了。`turn.complete` は turn のトークン合計（`e.usage`）を持つ
  - `classic.<settings hook のイベント名>`: settings hook と同じイベントを、stdin の JSON と同じ `e` で受ける
- **API**: ファイル（`$.fs`、1 ファイル 4 MiB まで）、HTTP（`$.http.fetch`）、タイマー（`$.clock`）、モデル（`$.model.complete` 等。利用者のプラン・API キーで課金）、プロセス（`$.process.run`、既定 30 秒）。hook 自身の実行時間は 10 秒まで
  - OTel の属性・span を書き換える API は無い。`$.telemetry` は cc 本体か組み込みの Mod が呼んだときだけ送信される
  - Mods はサンドボックス化されず、利用者と同じ権限で動く
- **管理**: 既定で有効（端末は 2.1.287 以降、Desktop 同梱の cc は 2.1.286 以降。docs 2.1.295）。組織は managed settings で止められる
  - `allowManagedModsOnly`: managed settings のトップレベルのキーではない。組み込みの guard の option として、`pluginConfigs."cc-plugin-sec-default@builtin".options.allowManagedModsOnly` に置く。利用者が持ち込む Mod は読み込まれるが拒否され、hook が動かない。利用者の settings hook と、plugin の `hooks/hooks.json` の command hook は動き続ける
  - `allowManagedHooksOnly`: 利用者の settings hook も止まる（managed settings が force-enable した plugin の hook は動く）。`disableAllHooks`: 全 Mod・全 hook を停止。`disableSideloadFlags`: `--plugin-dir` を拒否
  - `$.http.fetch` は、組織が web fetch か nonessential traffic を無効にしていると拒否される
  - v0.4 までは `allowManagedModsOnly` をトップレベルのキーのように書き、意味を「全て不許可」としていた。置き場所は 2026-10-02 取得の docs から同じで、版上げとは無関係の Phase 1 の誤りである（docs に正しく書かれていた。一覧は [§7.4](#sec-7-4)）。意味は docs 2.1.295 が「拒否され、hook が動かない。plugin の `hooks/hooks.json` は動く」と書き直した（[§7.2](#sec-7-2) D17）
- **型定義の記述**: cc に同梱の plugin-authoring の型定義（hook 入力の基底型）は、`prompt_id` を「OTel イベントの `prompt.id` 属性と同じ値で、hook の出力を OTel イベントとプロンプト単位で結合できる」と説明している

### 4.2 実測 1: `prompt_id` の結合

`classic.UserPromptSubmit` でプロンプトをルール分類し、`prompt_id`・`session_id`・ラベル等を 1 プロンプト 1 ファイルで書き出す Mod を作った。本文は保存しない。`claude plugin validate` を通し、`claude -p --plugin-dir` で読み込んだ。

タグ案 L1 の実装手段（command hook か Mod か）を Phase 2 で選ぶための材料を、この表に集約する。ほかの文書はこの表を参照する。左の 2 列の測定値は 2.1.287（Haiku 4.5）のもの。右端の列に、2.1.296 での値と変化を置いた（v0.5 で追加）。

- 大小は版とモードで入れ替わる。上乗せは組み込み Mod の構成しだいで版ごとに変わるので、Phase 2 の比較と Phase 3 の判定は、同じ版の値どうしで行う。2.1.287・2.1.296 のどの条件でも、上乗せは 0.5 秒未満だった（測定点 A は 2.1.283 では測っていない。2.1.283 の対話モードでは、hook 単体（測定点 B）が 2.1〜2.8 秒の回が 2 回あり、原因は未特定）
- command hook は `UserPromptSubmit` と `SessionStart` の 2 つ、Mod は 1 つで、本数がそろっていない。【推測】`SessionStart` は interaction span の開始より前に走るので、測定点 A への影響は小さい
- 職場環境では、managed settings で Mod だけでなく command hook も止められうる。ただし `allowManagedModsOnly` だけなら、command hook（settings hook と plugin の `hooks/hooks.json`）は動き続ける。タグ案 L1 が成り立たないのは、`allowManagedHooksOnly` か `disableAllHooks` で command hook も止められている場合に絞れる（Phase 3 の職場環境確認で確かめる。[§6](#sec-6)）

Mods をタグ付けの手段に採るかの判断は、1-3 の改訂と Phase 2 に委ねる。

  - 設計への意味（Phase 2 の材料。J-3 の推奨は変えない）: AGENTS.md を使わない環境では、`cc-plugin-agents-md` を無効にすれば、`-p` の Mod の上乗せはほぼ無くなる。ただし AGENTS.md の読み込みも止まるので、無効化を既定の対策にはしない。職場で AGENTS.md を使うかは未確認。組み込み Mod の構成は版で変わるので、この結果も測った版でしか使えない
- `-p` の hook なしは、Haiku 5.5 で 293 ms と、2.1.287（135 ms）より増えた。版の差ではない（同じ 2.1.296 で Haiku 4.5 を明示すると 115 ms）。Haiku 5.5 で `-p` の hook なしだけが増えた理由は確かめていない（対話モードの hook なしは 121 → 111 ms で、増えていない。[§7.5](#sec-7-5)）。`-p` の版間比較は C-3b の行で行うので、この増加は比較に入らない

**対話モード**

- command hook・Mod とも上乗せが縮み（+439 → +235 ms、+297 → +160 ms）、Mod の方が小さいままだった。2 秒超はどの条件でも出なかった（最大は Remote Control ありの 1 回の `SessionStart` の 709 ms）
- ただし、対話モードの版間比較は、モデル（Haiku 4.5 → Haiku 5.5）と permission mode（2.1.287 は default に落ちた後、2.1.296 は auto のまま）も違う。上乗せは同じ条件の hook なしとの差なので、条件差の多くは相殺される。それでも、対話モードでは Haiku 4.5 を明示した補足の実行をしていないので、版の差だけを分けてはいない
- 2.1.288 の「最初のリクエストとモデル切替直後のリクエストは最大 1.5 秒待つ」（D23）は、新しいウィンドウの初回プロンプトでは出なかった（hook なし 105〜114 ms）。【推測】「新しい環境」は、新しい設定ディレクトリやインストール直後を指す

**測定点 B（hook 単体の所要時間）**

| 指標 | 2.1.287 | 2.1.296 |
|---|---|---|
| command hook の `UserPromptSubmit` の `total_duration_ms`（`-p`） | 132〜365 ms（6 回） | 130〜191 ms（6 回）。Haiku 4.5 を明示した C-3b では 141〜162 ms（3 回） |
| 同（対話モード） | 383〜495 ms | 204〜249 ms（Remote Control なしで 183〜224 ms） |
| Mod の所要時間（debug log、対話モード） | 262〜296 ms（3 回） | 121〜196 ms（3 回。Remote Control なしで 103〜112 ms） |

- 2026-10-12 追記: 2.1.296 から、command hook の所要時間も debug log に出る（D28。docs 2.1.296 で明記）。Remote Control に接続した対話の 3 回で、`UserPromptSubmit` の debug log の値は、OTel の `total_duration_ms` と 2 ms 以内で一致した（`SessionStart` は 1 回で、debug log 706 ms・OTel 709 ms）。debug log は hook ごとに 1 行出るので、測定点 B の補助に使える（ほかの hook がある環境で、L1 の hook の時間を分けて読める見込み）

**Remote Control の影響**

- 2.1.287・2.1.296 の対話モードの計測は、どちらも Remote Control に接続した状態だった（[§7.3.4](#sec-7-3-4)）。条件はそろっているので、版間比較は有効である
- Remote Control を切ると、hook なしはほぼ同じ（111 → 108 ms）で、上乗せは command hook が 24 ms（ばらつきの範囲）、Mod が 50 ms 小さくなった。対話モードの順位（hook なし < Mod < command hook）と、上乗せがどれも 0.5 秒未満であることは変わらない。【推測、n=3】Remote Control の起動処理が、ワーカー上の Mod の初回の処理と重なっていた可能性がある
- どの値を引くか: 版間比較は、Remote Control ありの行どうしで行う。J-12 の判定は、日常のセッション（Remote Control は普段どおり接続した状態）をそのまま測って行う。Remote Control の有無・モデル・permission mode を記録して条件ごとに集計し、上乗せは同じ条件の hook なしの中央値から求める。Remote Control を切った計測用のセッションの値は、参照値として並べる（J-19）

**結論**

- J-3 の推奨（Mods を加える。hook か Mod かは Phase 2 で決める）と、Q4 の推奨（L1）は変わらない。2.1.287・2.1.296 のどの条件でも、上乗せは 0.5 秒未満だった
- ただし「両モードとも Mod が小さい」は、版しだいで成り立たない。上乗せは版（組み込み Mod の構成）で動くので、Phase 3 の測定値は測った版でしか使えない（J-18）
- J-12 の暫定値（上乗せの中央値 1 秒以下、上乗せが 2 秒を超えるプロンプト 1 割以下）は変えない。根拠に 2.1.296 の値を並べ、測り方の注記（`/model` で切り替えた直後のプロンプトは判定から除いて別に集計する、測定点 B は同じ event でマッチした全 hook の経過時間（D22）、Remote Control の有無・モデル・permission mode を記録して条件ごとに集計する）を足した（[裁定待ち事項 §1](../作業指示者裁定待ち事項.md#sec-1) の J-12）

- §3.4 の「対話モードの既定 auto mode」の観測も、この設定の下のものである

#### 7.3.4 その他の観測（blocked_on_user、OTel に出ない API 呼び出し、Remote Control）

- **`claude_code.tool.blocked_on_user`（`-p`）**: 2.1.287 では source・decision が `unknown` だった。2.1.296 では `config`・`accept` になり、拒否も `reject`・`config` で記録された。2.1.288 の修正（D19）を実機で確かめた。対話モードは両版とも `config`・`accept`。span の種類（interaction、llm_request、tool、tool.blocked_on_user、tool.execution）は両版で同じ

  - 2026-10-12 追記（D33。J-21）: docs の permission-modes の「Server-side classifier review」節（基線の docs からある）によると、auto mode では、Claude Code が自前の分類器リクエストを送る代わりに、セッション自身のモデルリクエストの中でサーバーにチェックを依頼できる（無料）。本環境は Anthropic API への直接接続なので、分類器が呼ばれても、チェックはセッション自身のモデルリクエストに乗り、別の `api_request` は出ない見込みである（docs による。実機では未確認）。i6〜i8 の観測（i7・i8 は分類器を使わずに決まった）はそのまま正しいが、「分類器がモデルを呼ぶ操作で `query_source` の新しい値を待つ」という R6 の確かめ方は、本環境では成り立たない。2.1.296 の 12 回の実行の debug log には、サーバー側チェックの依頼の有無を示す行は見当たらなかった。本環境の `/status` の Auto mode server 行は確かめていない

- **Remote Control**: ユーザ settings の `remoteControlAtStartup` の設定により、対話セッションは起動時に Remote Control に接続する。対話モードの計測は 2.1.287（§4.3 実測 4）・2.1.296 とも、接続した状態だった（debug log で確認）。遅延への影響は [§7.3.2](#sec-7-3-2)

  - 今後の動作検証は、Remote Control を切って行う（作業指示者の指示、2026-10-10）。この指示は Claude が起動する計測用のセッション（probe と Phase 3 の比較実験）に当てはめ、J-12 の判定に使う日常のセッションは切らずに測ると解釈した（J-19）。職場環境（Amazon Bedrock）では、Remote Control はそもそも使えない（docs）
