# 調査報告書（1-8 cc 2.1.287 までの仕様差分と再確認）執筆者見解

対象: [調査報告書.md](調査報告書.md)（v0.2）。執筆ガイドライン（`releases/執筆ガイドライン/.claude/skills/writing-guideline/`）に沿って執筆した報告書についての執筆者見解。レビューア（クロスレビューを実施する別 Agent）向けの参考資料。本書は報告書の本文から読み取れる範囲で書いており、本文に無い経緯は補っていない。

## 1. 執筆過程の所感

### 1.1 執筆時の判断

- **「docs の変更」と「基線の時点からあった誤り・記載漏れ」を分けた**。差分の調査を始めると、基線の docs にすでに書かれていた事項が「新しい差分」に見えてしまう。基線の `llms-full.txt` を各項目で grep して判定し、7 件（D1・D2・D8〜D12）と 5 件（D3〜D7）に分けた。理由は、前者は仕様変更への追従、後者は Phase 1 の文書の補正で、反映の意味が違うためである（[§2.1](調査報告書.md#sec-2-1)、[§2.2](調査報告書.md#sec-2-2)）
- **誤りの訂正を、独立した節（§5.1）に切り出した**。既存文書の誤り 3 件と hook の待ち時間の訂正は、作業指示者が最初に判断する項目である。文書・節ごとの反映先の一覧（§5.2）に埋もれないように分けた
- **実測の結果を R1〜R12 の表で一覧にした**。確認済み・一部確認・未確認が混在するため、章を追って読まなくても状況がわかる形にした。未確認は理由と確認の時期を §6 に集約した
- **Mods を採るかの判断は、本書では行わなかった**。実測（`prompt_id` の一致、遅延の比較）は示したが、標本が各 3 回で、対話モードは未確認である。判断は 1-3 の改訂に委ねると明記した
- **既存文書の反映は、本書では行わなかった**。本書は反映先と処置の一覧までにとどめ、反映は別の担当が行う。作業指示者が反映前に訂正案を確認できるようにするためである
- **「最強の反論」を 2 件置いた**。標本が小さいことと、キーワード検索による照合の取りこぼしである。どちらも本書の弱点として自分で見つけたものを先に書いた

### 1.2 迷った点

- **v0.1 から v0.2 への変更は、基線の取り方だけ**。変更履歴のとおり、v0.2 で基線を計画書と同じ 2026-09-27 版に合わせた。これにより D1〜D12 の「基線にあったか」の判定が計画書と一致する。ただし判定の基準が変わったので、項目の再分類が正しいかを見てほしい
- **棚卸し 55 箇所の件数の扱い**。内訳（誤り 3、不足 18、表現の更新 11、再確認要 10、影響なし 13）を §5 の冒頭に書いた。D3〜D7 に当たる 23 箇所を「基線の変更では変わらない」と注記したが、この注記が読者に伝わるかに自信がない
- **D8・D10・D11 の版の食い違い**。棚卸しの作業メモと changelog で版が異なる箇所があり、changelog を正とした（§2.1 の注記）。どの版が正かの確認は changelog の記載に頼っており、実機での確認はしていない
- **hook の待ち時間「2.1〜2.8 秒」の原因**。1-1 の i3・i4 の 2 回に限った値で、どちらも新しいウィンドウでの最初のプロンプトだった。原因は特定できず、【推測】として Node.js の初回起動やウイルス対策ソフトの走査を挙げた。追加の測定はしていない
- **`app.entrypoint` の値の扱い**。実測では `sdk-cli`（`-p`）が出た。docs の変数表との差（イベントと span にも付く）は事実として書いたが、まとめ §5.3 の訂正文案で値の例（`cli` / `sdk-cli` 等）まで書いてよいかは迷った
- **自作の受信スクリプトと受信データをコミットしない**扱い。再現手順は scratchpad にあるため、報告書だけでは第三者が再現しにくい。収集データを公開しない制約を優先した

### 1.3 ガイドラインの適用しやすさ

- 本書は差分の洗い出しと棚卸しが主で、結論が「訂正と追記で足りる」という性格を持つ。表が中心になるため、G2 系の「結論先出し」は節の冒頭 1〜2 文で満たす形を選んだ
- ガイドラインに、差分調査（版が変わったときの再確認）型の観点が無い。基線・比較先・補完の 3 版を明示する書き方は、1-4 の運用に倣いつつ本書で整えた

## 2. レビュアーに特に見てほしい点

1. **「基線の時点からあった」の判定（D3〜D7）**。基線の `llms-full.txt` を grep しての判定であり、記述の有無の読み違いがあると、既存文書の誤りの認定（§5.1）が揺らぐ。特に D3（`custom` の置き換え規則）と D4（`app.version`・`app.entrypoint`）の判定根拠を確認してほしい
2. **誤り 3 件の訂正の妥当性（§5.1）**。1-1 の「docs と差異」判定、仕様別紙の「区別できない」、まとめ §5.3 の反映項目。訂正後の記述が、実測と docs の両方に整合しているか
3. **hook の待ち時間の訂正（§4.3・§5.1）**。「2.1〜2.8 秒」を「対話モードの 2 回だけの値」と結論づけた根拠が、観測値の並べ方で足りるか。原因を【推測】にとどめた判断が適切か
4. **Mods の実測の読み方（§4.2・§4.3）**。標本 n=3 で「Mod が command hook より遅延が小さかった」と書いた表現の強さ。傾向として扱うと注記したが、サマリ・結論側の書き方が強すぎないか
5. **属性集合の比較（§3.1）の網羅性**。「削除・改名なし」の判定が、1-1 と同じ実行パターンの範囲に限られる点。`-p` の短い実行が中心であることの影響
6. **キーワード検索による差分の拾い漏れ（§6）**。docs 本文の未検出の差分は残存リスクとして書いたが、棚卸しの 55 箇所の分類（誤り・不足・表現・再確認・影響なし）に取りこぼしが無いか
7. **未確認事項の置き場（§6）**。R3・R9・R7・R11・R12 等を Phase 3 や Q3 の判断後に回した判断が、計画書の工程と整合しているか
