## 0. サマリ

- **調査内容**: Issue #4 が挙げた OTel GenAI semantic conventions（以下 GenAI semconv）と Arize-ai/openinference（以下 OpenInference）を一次資料で読んだ。cc の実 span（1-1 で記録した 86 span）を OpenInference の変換層に通した。そのうえで、本活動の要件に照らして Phase 1 に反映する価値を判断した
- **調査結果**
  - Issue の 2 つの前提は、どちらも一次資料と合わない（[§1](#sec-1)）
    - GenAI semconv は全体が Development 段階で、リポジトリにリリースタグが 1 つも無い。「成立した規格」ではなく、成立途上のデファクトである
    - OpenInference は Arize 独自の「complementary」な規約で、GenAI semconv の実装ではない。両者を収束させる公式の計画も無い。ただし、両者を橋渡しする変換層はある
  - cc はすでに span で GenAI semconv の属性を 5 つ出している。cc の公式 docs にも、GenAI semconv との対応を説明する節が新しく設けられた（[§2.4](#sec-2-4)）
  - OpenInference の JS 変換層は cc の span を誤分類し、トークン数を 1 つも引き継がない（[§3.3](#sec-3-3)）。Phoenix は traces しか受けず、cc の `http/json` を拒否する（[§4](#sec-4)）
- **結論・示唆**（[§5](#sec-5)）
  - (a) GenAI semconv を、Phase 2 のスキーマ設計の参照語彙と対応表として使う: **価値あり・採用**。物理列は cc の元の名前を主にし、semconv 名は論理対応表（[付録 A](#sec-a)）として持つ
  - (b) OpenInference・Phoenix を実装部品として使う: **不採用**。Phase 1 の候補（保存案 S1/S2・画面案 D1/D2・思考案 T1/T2・タグ案 L1/L2）は変えない
  - 言語の観点（[§6](#sec-6)）: (a) の使い方なら OpenInference への依存はゼロで、脆弱性で利用禁止になる懸念はこの用途では生じない。Java・Go には、パッチを当てて使い続ける対象がそもそも無い

<a id="sec-2"></a>
## 2. OTel GenAI semconv の要点

GenAI semconv は、生成 AI の呼び出し・エージェント・ツール実行を OTel の span・metric・event で表す規約である。本活動に効くのは、トークン属性の定義と Anthropic 固有の算出規則で、cc はその一部をすでに出している。

<a id="sec-2-1"></a>
### 2.1 位置付けと変更の頻度

- 本体の semantic-conventions から専用リポジトリに分離された。本体の `CHANGELOG.md` の v1.42.0 の節に「Move Generative AI semantic conventions to a dedicated repository (#3696)」とある
- 版は dev チャネル専用の `X.Y.Z-dev` で、次に切る予定の版は `1.42.0-dev`（`schema_url`）。本体 semconv v1.44.0 に依存する（`semantic-conventions-genai:model/manifest.yaml`、`RELEASING.md`）
- 本体側の 2026 Roadmap（semantic-conventions#3330）でも、GenAI の安定化は「[Unconfirmed] Stabilize conventions: GenAI (core set)」に置かれている
- 直近の breaking の例
  - `gen_ai.client.token.usage`（Histogram）の廃止（#374）。後継は、種別ごとの Counter `gen_ai.client.inference.usage.*` と、分布を表す Histogram
  - `gen_ai.usage.cache_creation.input_tokens` から `gen_ai.usage.cache_write.input_tokens` への改名（#440）
  - `invoke_agent` span からの属性削除（#469、#289、#322、#242）
- `gen_ai.system` は、本体 semconv v1.37.0 で `gen_ai.provider.name` に改名された（#2046）。GenAI リポジトリには `gen_ai.system` の定義が無い

<a id="sec-2-2"></a>
### 2.2 構成（本活動に関わる範囲）

| 種類 | 主なもの | 本活動との関係 |
|---|---|---|
| span | Inference（`chat {gen_ai.request.model}`）、`execute_tool`、`invoke_agent`、`invoke_workflow`、skill 系 ほか | cc の `claude_code.llm_request` は Inference、`claude_code.tool` は `execute_tool` に近い |
| トークン属性 | `gen_ai.usage.input_tokens`、`output_tokens`、`cache_read.input_tokens`、`cache_write.input_tokens`、`reasoning.output_tokens` | 意味の違いに注意（[§7](#sec-7)） |
| metric | `gen_ai.client.operation.duration`（Histogram、秒）、`gen_ai.client.inference.usage.*`（Counter、属性 `gen_ai.token.modality` が必須） | cc の `claude_code.token.usage` は 1 metric ＋ `type` 属性で、構造が違う |
| 内容の記録 | `gen_ai.input.messages` ほか（Opt-In）。既定では記録しない（SHOULD NOT capture by default） | cc の方針（内容記録は既定 OFF）と一致する |
| エージェント | `gen_ai.agent.id` はホスト型エージェントの安定 ID で、プロセス内の一時 ID は NOT RECOMMENDED | cc の `agent_id`（サブエージェントの実行単位の ID）とは意味が違う |

典拠は `semantic-conventions-genai:docs/gen-ai/` の各ページと `model/gen-ai/registry.yaml`。cost（費用）に当たる属性は GenAI semconv に無い。

<a id="sec-2-3"></a>
### 2.3 Anthropic 固有の規約

`semantic-conventions-genai:docs/gen-ai/anthropic.md`（Status: Development）がある。

- Inference span の `gen_ai.provider.name` は `"anthropic"`（MUST）
- トークンの算出規則: Anthropic の `input_tokens` はキャッシュ分を含まない。`gen_ai.usage.input_tokens` は `input_tokens + cache_read_input_tokens + cache_write_input_tokens` で求める（MUST）
- `gen_ai.request.reasoning.level` は Anthropic の `output_config.effort` に対応し、値は送った文字列をそのまま入れる。cc の `effort` 属性がこれに当たる

<a id="sec-2-4"></a>
### 2.4 cc の準拠状況

cc は span で、GenAI semconv の属性を 5 つ出している（cc の Monitoring docs の span 属性表。1-1 の実データでも確認）。

| cc が出す属性 | 内容 | 現行の semconv での扱い |
|---|---|---|
| `gen_ai.system` | 常に `anthropic` | 旧名。現行は `gen_ai.provider.name` |
| `gen_ai.request.model` | `model` と同じ値 | 同名 |
| `gen_ai.response.id` | `request_id` と同じ値 | 同名 |
| `gen_ai.response.finish_reasons` | `stop_reason` を配列にしたもの | 同名 |
| `gen_ai.tool.call.id` | `tool_use_id` と同じ値 | 同名 |

cc が出さないもの: `gen_ai.operation.name`（span で Required）、`gen_ai.provider.name`（同）、`gen_ai.usage.*`。トークン数は cc 独自の名前（`input_tokens` 等）で出る。

cc の Monitoring docs には、「Map input tokens to OpenTelemetry GenAI semantic conventions」節が新しく設けられた。本活動が定期的に取り込んでいる docs（llms-full.txt、2026-10-02 取り込み分まで）には無く、2026-10-03 取得の Monitoring ページにある。この節は次のことを書いている。

- cc は `gen_ai.usage.*` を設定しない
- cc の `input_tokens` はキャッシュ分を含まない。GenAI semconv の総入力にするには、`input_tokens`・`cache_read_tokens`・`cache_creation_tokens` を足す
- `cache_creation_tokens` は `gen_ai.usage.cache_write.input_tokens` に対応する。旧版の規約の名前（`cache_creation`）もあるので、受け側が期待する名前を使う

<a id="sec-3"></a>
## 3. OpenInference と変換層の要点

OpenInference は OTel の span と OTLP の上に載る、GenAI semconv と並行した規約である。cc の span を OpenInference の変換層に通すと、トークンが落ち、span の種別が誤分類される。

<a id="sec-3-1"></a>
### 3.1 属性体系

| 区分 | 属性 | 要点 |
|---|---|---|
| span 種別 | `openinference.span.kind` | 全 span で必須。`LLM` / `AGENT` / `CHAIN` / `TOOL` / `RETRIEVER` ほか |
| モデル | `llm.model_name`、`llm.system`、`llm.provider` | |
| トークン | `llm.token_count.prompt` / `completion` / `total`、`prompt_details.cache_read` / `cache_write`、`completion_details.reasoning` | キャッシュ分は `prompt` の内数。Anthropic の `input_tokens` は、キャッシュ分を足し戻して `prompt` に入れる |
| コスト | `llm.cost.*` | GenAI semconv に無い独自属性 |
| セッション | `session.id`、`user.id` | cc は同じ名前で出している |

典拠は `openinference:spec/semantic_conventions.md`。秘匿の設定（`OPENINFERENCE_HIDE_*`）は計装する側の機能で、cc の span には効かない。

<a id="sec-3-2"></a>
### 3.2 cc 本体には計装パッケージを使えない

OpenInference の Anthropic 用・Claude Agent SDK 用の計装は、計装を入れたプロセスの中のライブラリ呼び出しにパッチを当てる方式である（`openinference:js/packages/openinference-instrumentation-claude-agent-sdk/` ほか）。Agent SDK は `claude` CLI を子プロセスとして起動する。このため、対話型の cc が出す API 呼び出しは捕捉できない。本活動では、cc 自身が出す OTLP を受けるしかない。

<a id="sec-3-3"></a>
### 3.3 cc の span を JS 変換層に通した結果

`@arizeai/openinference-genai` 0.4.0 の変換関数に、1-1 で記録した 86 span を入力した（実行済み）。変換関数は `gen_ai.*` だけを読む（`openinference:js/packages/openinference-genai/src/attributes.ts`）。

| cc の span（件数） | 入力された `gen_ai.*` | 判定された種別 | 判定 |
|---|---|---|---|
| `claude_code.llm_request`（36） | `system`、`request.model`、`response.id`、`response.finish_reasons` | LLM ×36 | 正しい。ただしトークン数は空 |
| `claude_code.interaction`（17） | なし | LLM ×17 | **誤分類**（種別の既定値が LLM） |
| `claude_code.tool.blocked_on_user`（11） | なし | LLM ×11 | **誤分類** |
| `claude_code.tool`（11） | `tool.call.id` | TOOL ×11 | **重複**（1 回のツール実行が TOOL ×2 になる） |
| `claude_code.tool.execution`（11） | `tool.call.id` | TOOL ×11 | **重複**（同上） |

- 引き継がれるもの: `gen_ai.request.model` → `llm.model_name`、`gen_ai.response.finish_reasons` → `llm.finish_reason`（`end_turn` のまま）、`gen_ai.tool.call.id` → `tool_call.id`、`session.id`
- 落ちるもの
  - cc 独自のトークン属性（`input_tokens`・`output_tokens`・`cache_read_tokens`・`cache_creation_tokens`）はすべて落ちる
  - 旧名の `gen_ai.system` は読まれず、`llm.system`・`llm.provider` が空になる
  - `tool_name` は `gen_ai.tool.name` ではないため、`tool.name` が空になる
- 影響: interaction と blocked_on_user が LLM として数えられ、LLM 呼び出しの件数とトークン集計が汚れる

<a id="sec-4"></a>
## 4. Phoenix の評価と除外

Phoenix（Arize の OTLP 受信・閲覧ツール）は、保存案・画面案の候補に加えない。除外の軸は、04・05 報告書と同じ「Windows ネイティブ」「依存の重さ」「受けられる信号」である。

| 軸 | Phoenix の事実 | 典拠 |
|---|---|---|
| 受けられる信号 | **traces だけ**。gRPC は trace のサービスだけを登録し、HTTP にも metrics・logs の受け口が無い。本活動の集計の主軸である `api_request` イベント（logs）と metrics を受けられない | `phoenix:src/phoenix/server/grpc_server.py`、`src/phoenix/server/api/routers/v1/` |
| 受信の形式 | HTTP の `POST /v1/traces` は `application/x-protobuf` だけを受け付け、JSON は 415 を返す。1-1 で使った cc の `http/json` はそのままでは拒否される | `phoenix:src/phoenix/server/api/routers/v1/traces.py` |
| Windows ネイティブ・Docker 不要 | Docker なしでも `pip install arize-phoenix` や `uvx arize-phoenix serve` で起動する手順はある。ただし単体バイナリは無く、Python 3.11〜3.14 の実行環境が要る。Windows での動作は未確認 | `phoenix:README.md`、`pyproject.toml` |
| 依存の重さ | Python 製で直接依存が 54 件（sqlalchemy、grpcio、openinference-* ほか）。Node.js だけで動く S1/S2 に比べ、持ち込む実行環境と依存が大幅に増える | `phoenix:pyproject.toml` |
| ライセンス | Elastic License 2.0（ELv2）。OSI 承認のライセンスではない。改変版には改変した旨の明示が要る | `phoenix:LICENSE` |

Phoenix 上での cc の span の見え方は、コードから予測しただけで、起動して確かめていない【推測】。

- `llm_request` は LLM になる。旧名 `gen_ai.system` から `llm.provider` は付くが、トークン欄は空になる
- `tool` と `tool.execution` は TOOL が 2 個ずつ並ぶ
- `interaction` と `blocked_on_user` は合成の対象外になり、種別が UNKNOWN になる

**最強の反論と残存リスク**

- 反論: traces だけを Phoenix に分岐させれば、UI を作らずに span の木構造を見られる。cc は traces だけプロトコルと送信先を変えられる（`OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf`、traces 用の endpoint 指定。cc の Monitoring docs）
  - 本活動の目的はトークンとコストの集計で、Phoenix ではトークン欄が空、interaction が UNKNOWN になる【推測】。cc 独自のトークン属性を写す前処理を別途作る必要があり、S1/S2 の代わりにならない
  - 職場の managed settings で `OTEL_EXPORTER_OTLP_PROTOCOL` が設定されている場合、signal 別のプロトコル指定は削除される（cc の docs）。分岐が職場環境で使えない可能性がある
  - 残存リスク: 表示の予測は未検証である。画面案 D1・D2 で要件を満たせない場合に限り、Phoenix を起動して確かめる

<a id="sec-5"></a>
## 5. 反映する価値の判断

「反映する価値」は、参照語彙として使うか（a）と、実装部品として使うか（b）の 2 軸に分けると結論が分かれる。(a) は採用、(b) は不採用とする。

<a id="sec-5-1"></a>
### 5.1 (a) GenAI semconv を参照語彙・対応表として使う: 価値あり・採用

採用する理由は 2 つ。

- cc が span で GenAI 属性を 5 つ出している（[§2.4](#sec-2-4)）。そのうち `gen_ai.system` は旧名で、現行は `gen_ai.provider.name` である
- cc の公式 docs が、GenAI semconv との対応節を新しく設けた（[§2.4](#sec-2-4)）。cc の出力名が今後 semconv に寄る可能性があり、対応を先に持っておくと追随しやすい【推測】

設計の方針は、物理列を cc の元の名前にし、semconv 名は論理対応表（[付録 A](#sec-a)）として持つことである。総入力の派生値・改名の alias 表・commit での固定を含め、詳細は [§9](#sec-9) に置く。

Phase 1 への反映は、本書と付録 A の追加にとどめる。1-1〜1-6 の結論と、まとめ報告書の候補は変えない。

**最強の反論と残存リスク**

- 反論: GenAI semconv は Development のまま breaking が続いている。参照語彙にしても、改名のたびに対応表を直す手間が増えるだけではないか
  - 物理列は cc の元の名前なので、semconv の改名は保存データに波及しない。影響は対応表と alias 表の更新に閉じる
  - semconv を commit で固定し、`changelog.d/` の breaking 断片を確認する運用にすれば、追随のコストを見積もれる（[§9](#sec-9)）
  - 残存リスク: cc 側の出力名が変わる場合（`gen_ai.system` が `gen_ai.provider.name` に変わる、`gen_ai.usage.*` を出し始める等）は、取込の処理を直す必要がある。cc の版を上げるたびに、属性集合の差分を確かめる（2.1.283 → 2.1.287 では、本活動が依存する属性の削除・改名は無かった）

<a id="sec-5-2"></a>
### 5.2 (b) OpenInference・Phoenix を実装部品として使う: 不採用

- JS の変換層は cc の span を誤分類する。interaction と blocked_on_user を LLM にし、ツール実行を TOOL ×2 にし、cc 独自名のトークンをすべて落とす（[§3.3](#sec-3-3)）
- Phoenix は traces しか受けない。HTTP は protobuf だけで、cc の `http/json` は 415 で拒否される（[§4](#sec-4)）
- Phoenix は Python 製で直接依存が 54 件、ライセンスは ELv2 である（[§4](#sec-4)）
- 計装パッケージは対話型の cc に適用できない（[§3.2](#sec-3-2)）

Phase 1 の候補（S1/S2・D1/D2・T1/T2・L1/L2）は変えない。Phoenix は除外候補として扱う。まとめ報告書 [§3.2](../99.基礎調査まとめ/報告書.md#sec-3-2) の除外一覧と同じ形で書くと、次のようになる。

| 候補 | 外す理由 |
|---|---|
| Phoenix | traces しか受けず、集計の主軸の `api_request` イベントと metrics を受けられない。HTTP は protobuf だけ。単体バイナリが無く、Python 3.11〜3.14 と 54 件の直接依存が要る。ライセンスは ELv2。cc の span はトークン欄が空になる見込み【推測】。D1・D2 で要件を満たせない場合に再検討する |

最強の反論（Phoenix を traces の参考ビューアとして並走させる案）と残存リスクは [§4](#sec-4) に置いた。

<a id="sec-6"></a>
## 6. 実装言語の観点への回答

結論: [§5](#sec-5) の方針（語彙だけ借り、変換は自作）なら、OpenInference への依存はゼロになる。言語の選択は OpenInference と無関係になり、受信機（Node.js）と作業分類タグ（Mods なら JS/TS）に合わせて JS で書くのが自然である。

| 作業指示者の観点 | 回答 |
|---|---|
| Python / JS / Go の利点: 候補スタックとの相性が良い | JS については成り立つ。受信機（S1/S2）は Node.js で、自作の変換・対応表も JS で書ける。作業分類タグを cc の Mods（2.1.287）で実装する場合、Mod は cc のプロセス内で動く JavaScript / TypeScript の関数なので、言語は JS/TS に固定される（cc の Mods docs） |
| Python / JS / Go の欠点: 依存パッケージの脆弱性で利用禁止になりうる | この用途では生じない。OpenInference のパッケージを取り込まないため、その脆弱性で止まる経路が無い。なお、S1/S2 の依存（DuckDB 等）の脆弱性は本書の対象外で、別途の論点である |
| Java の利点: OSS 側に独自パッチを当てて使い続けられる | パッチを当てる対象が無い。OpenInference の Java には Anthropic / Claude 向けの計装も GenAI 変換も無い。計装は langchain4j・springAI・annotation・adk-java の 4 個だけである（`openinference:java/`） |
| Java の欠点: 候補スタックとの相性が劣るかもしれない | 受信機を Node.js とする現在の候補では、Java を使う場面が無い。Java を選ぶかは、OpenInference と無関係に「受信機を Java で書くか」という論点になる【推測】 |

Go も同じで、OpenInference の Go には `anthropic-sdk-go` 用（0.1.0）と `openai-go` 用（0.1.0）の計装しか無く、GenAI 変換層が無い（`openinference:go/`）。Java・Go のどちらでも、パッチを当てて使い続ける対象がそもそも無い。

<a id="sec-7"></a>
## 7. トークンの意味の違い

cc と GenAI semconv では、input トークンの意味が違う。thinking トークンは、OTel 上では cc から取れないが、transcript の経路（思考案 T1）で取れる。

<a id="sec-7-1"></a>
### 7.1 input トークン

| | キャッシュ分を含むか | 典拠 |
|---|---|---|
| cc の `input_tokens`（span・`api_request` イベント）、`claude_code.token.usage` の `type=input` | 含まない（API の usage の値そのまま） | cc の Monitoring docs |
| GenAI semconv の `gen_ai.usage.input_tokens` | 含む（"SHOULD include all types of input tokens, including cached tokens"） | `semantic-conventions-genai:model/gen-ai/registry.yaml` |
| OpenInference の `llm.token_count.prompt` | 含む（キャッシュ分を足し戻す） | `openinference:spec/semantic_conventions.md` |

cc の docs も、3 種（`input_tokens`・`cache_read_tokens`・`cache_creation_tokens`）を足して換算するよう書いている。cc の `input_tokens` を semconv の `input_tokens` の列に名前だけ替えて入れると、総入力を過小に数える。

<a id="sec-7-2"></a>
### 7.2 thinking（reasoning）トークン

- GenAI semconv には `gen_ai.usage.reasoning.output_tokens` がある。extended thinking を含む出力トークンで、`output_tokens` の内数である
- cc は OTel でこの値を出さない。「thinking トークンは cc から取れない」は OTel 上の話で、cc 全体の話ではない
- 取得経路は思考案 T1（transcript の `thinking_tokens` を `request_id` で突合）である（[1-2 §5](../02.思考トークン取得経路/調査報告書.md#sec-5)）
  - cc 2.1.287 の再実測: `-p` 実行の `api_request` 25 件のうち 24 件を突合できた。残る 1 件は compact で、transcript に出ない（1-2 と同じ）
  - `thinking_tokens ≤ output_tokens` は、2.1.287 でも全件成立した。思考分が `output_tokens` に含まれることと矛盾しない（[1-2 §3.3](../02.思考トークン取得経路/調査報告書.md#sec-3-3)）
- semconv の `reasoning.output_tokens` に対応づける列は NULL 許容にする。サブエージェントの未確定分・補助リクエスト・compact は取れないためである

<a id="sec-8"></a>
## 8. MCP の扱い

MCP（Model Context Protocol）の仕様には、リクエストの `_meta` に `traceparent` を載せてトレース文脈を伝える規定がある（SEP-414、2025 年）。2026-09-26〜10-02 の MCP 仕様の差分は表の整形だけで、内容の変更は無い。本活動の目的は cc のトークン・コストの分析で、MCP サーバ側のトレースと結合する用途はスコープ外とする。cc が MCP 呼び出しに `traceparent` を載せるかは確認していない。

<a id="sec-9"></a>
## 9. Phase 2 への示唆

[付録 A](#sec-a) の対応表を、Phase 2 のスキーマ設計の入力にする。改名に追随する運用と、総入力の派生値を設計項目に加える。

- **対応表の使い方**
  - 物理列は cc の元の名前（`input_tokens`、`cache_read_tokens`、`cache_creation_tokens`、`output_tokens`、`ttft_ms`、`effort` 等）にする
  - semconv 名は、付録 A を元にした論理対応表として持つ。外部へ出す場合や他のツールと突き合わせる場合に、ビューや出力時の名前として使う
  - 意味が違う属性は同じ列に寄せない。`agent_id` は semconv の `gen_ai.agent.id`（ホスト型の安定 ID）と意味が違うので、cc 固有の列にする
  - `session.id` を `gen_ai.conversation.id` 相当とみなすかは設計判断として残す。`--resume` と compact との関係は未確認である
- **改名に追随する運用**
  - 取込層に alias 表を持ち、新旧どちらの名前も受ける（`gen_ai.system` → `gen_ai.provider.name`、`cache_creation` → `cache_write`）。`gen_ai.system` は保存時に provider として正規化する
  - 参照する semconv は commit（e07f4eb）で固定する。cc の版を上げるときに、`changelog.d/` の breaking・deprecation 断片と、cc の Monitoring docs の対応節を確認する
- **総入力の派生値**
  - 総入力 = `input_tokens + cache_read_tokens + cache_creation_tokens` を派生値として計算する。metrics では `type` の `input`・`cacheRead`・`cacheCreation` を足す
  - ダッシュボードの列名に「キャッシュ込み」「キャッシュ除く」を明記し、cc の `input_tokens` と取り違えない
  - 計算した値と cc の生の値を同じ列に混在させない（二重加算や過小評価の原因になる）
- **thinking トークン**: semconv の `reasoning.output_tokens` に対応づける列を、T1 の取込結果で埋める。NULL 許容にし、`output_tokens` から差し引く計算は書かない
