## 1. ゴール

**背景**: cc の費用対効果を高めたい。ステータスラインで見られるモデル・コンテキストサイズ・総トークン量だけでは、effort や作業の性質ごとのトークン消費（思考トークンを含む）が分からない。そこで、これらを cc の OTel テレメトリで収集・分析できるようにする。

### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

あわせて、次の 3 つの問いに分析で答える（v2.1 §1.2）。答えは、右列のルート資産の改訂案として出す。還流先のない分析はしない。

| # | 分析で答える問い | 分析結果の還流先（ルート資産） |
|---|---|---|
| ① | `/compact` と `/clear` をどう使い分けるとコストを抑えられるか | compact / clear の運用指針（ルート `CLAUDE.md`、または `pre-compact` skill） |
| ② | Skill・workflow・カスタムサブエージェントによるオーケストレーション（Opus から Sonnet への移譲を含む）で、品質を保ったままどこまでコストを下げられるか | ルート `CLAUDE.md` の「Agent 活用ガイドライン」、`orchestrate` skill |
| ③ | どの作業・agent・ツールがコストのボトルネックか | 「モデル選定原則」表、`check-model` skill |

### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript など `~/.claude` 配下のファイルから別経路で取り込み、テレメトリと突合する。何を取り込むかは 1-6 の棚卸しを受けて Phase 2 で決める |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

いずれも本環境と職場環境の両方で動くものとする（§1.4）。

### 1.3 成功基準（活動全体）

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- 本環境と職場環境で同じ仕組みが動き、両方のデータを同じ観点で集計できる。どちらの環境のデータかを区別できる（区別の方法は Phase 2 で決める。合算して分析するかは §7 #7）
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ読込 / キャッシュ作成 / **思考**トークンと推定コストを集計できる。メインとサブエージェントを分けて集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる
- 問い①〜③ のそれぞれについて、還流先資産の改訂案を根拠データ付きで提示できる。データが足りない問いは「結論保留・継続観測」と明示する

### 1.4 前提・制約とスコープ

- **第一のゴール（本計画 Phase 0〜6 の対象）**: Windows ネイティブ・Docker 不要の最小構成。**第二のゴール**: WSL + Docker 環境への対応。次の活動で扱う
- **対象環境**
  - 本環境: Anthropic 直接契約のアカウント。Windows 11 ネイティブ（Docker / WSL は使わない）
  - 職場環境: cc → 社内 LLM ゲートウェイ（LiteLLM 等。`ANTHROPIC_BEDROCK_BASE_URL` / `ANTHROPIC_BASE_URL` で指定）→ Amazon Bedrock。Windows。OTel 設定（ユーザ settings の `env`）は作業指示者が変更できる。実機確認は Phase 3 で作業指示者が行う
- 受信サーバ・データシンク等は、ローカルで起動できる OSS を積極的に使ってよい
- 分析 UI は、レイアウトを度々変えたくなる見込みがあるため、Node.js の自作ダッシュボードを有力候補とする（OSS との比較は 1-5）
- **スコープ外**: チーム・組織単位の集中収集（本活動は個人ローカル用）、クラウド・SaaS の監視基盤（Datadog 等）への送信

## 2. 公式仕様の調査結果と、計画への影響

基線は cc 2.1.283、Node.js v24.14.0、docs 2026-09-27 15:00 取得版。以下は docs 上の事実で、実機との一致は Phase 1（職場環境の分は Phase 3）で確認する（対象一覧は v2.1 §8.5 V-11(b)。本書には転記しない）。「見込み」は docs に明記がない推定を示す。Phase 0 の transcript 実測は cc 2.1.282 時点。属性・イベントの詳細は仕様別紙を参照する。

| # | 事実（docs） | 計画への影響 | 確認 |
|---|---|---|---|
| 1 | トークン・コストは metrics と `api_request` イベントに出て、`model`・`effort`・`skill.name` 等が付く。cc のバージョンは `service.version` で取れる（仕様別紙 §1） | 集計の主軸にする。バージョン変化の検知にも使う | 1-1 |
| 2 | 思考トークンは OTel で分離されない（`output_tokens` に含まれる見込み）。transcript の usage に数があり、`request_id` で突合できる（仕様別紙 §2） | 補完取込（§1.2 #2）が要る。経路は §2.1 の表から 1-2 で選ぶ | 1-2 |
| 3 | 作業の性質を表す属性は無い。ユーザ定義の agent 名は `"custom"` に丸められる（仕様別紙 §3） | タグ付け方式を 1-3 で比較し、Phase 2 で決める | 1-3 |
| 4 | `/clear` 専用のイベントは無い。`compaction`・`subagent_completed`・tool 系イベントは出る（仕様別紙 §1） | 問い①〜③ のデータは取れる見込み | 1-1 |
| 5 | prometheus exporter はセッションごとにポートが衝突する。OTLP のプロトコルには既定値が無い（仕様別紙 §4） | push 型の OTLP を主線にする。プロトコル（`http/json` / `http/protobuf`）は 1-4 で比べる | 1-4 |
| 6 | OTel 変数はユーザ settings の `env` で効き、変更後は再起動が要る（仕様別紙 §4） | 有効化の手順は Phase 2 で決める | — |
| 7 | 職場環境では識別属性・`request_id` の取得元などに差がある（仕様別紙 §5）。加えて §2.2 の 2 点が不明 | Phase 3 で作業指示者が確認する | Phase 3 |

### 2.1 思考トークンの取得経路（1-2 で選ぶ）

| 経路 | 内容 | 利点 | 懸念 |
|---|---|---|---|
| (i) transcript 突合 | transcript の usage を取り込み、`request_id` で OTel の `api_request` と突合する | 内容記録フラグが不要。過去分にも使える | transcript 形式は cc 内部仕様でバージョンごとに変わり得る。取込の仕組みと頻度を決める必要がある（§5） |
| (ii) 応答ボディ | `OTEL_LOG_RAW_API_BODIES` の応答ボディの usage を使う | OTel の設定だけで完結する | 会話履歴全体がディスクに残る（プライバシー・容量。§7 #2・#4 と連動）。usage が含まれることは未実測 |

v2.1 は (i) を主、(ii) を補助としている。

### 2.2 職場環境の不明点（Phase 3 で確認）

- 思考トークンの内訳（usage の `output_tokens_details.thinking_tokens`）が、Bedrock・社内プロキシ経由でも返るか、transcript に残るか
- 社内プロキシが usage・応答ヘッダ・ストリームを改変しないか

### Phase 1: 基礎調査・フィジビリティ確認

Phase 2 の設計判断に必要な事実を、机上調査と本環境での実測で揃える。職場環境で差が出る項目は docs で確認するにとどめる（実機確認は Phase 3）。「V-ID」列は、v2.1 §8.2 の検証項目のうち各調査で扱うもの。

| # | 調査項目 | 判定したいこと | V-ID |
|---|---|---|---|
| 1-1 | 実際に届くデータの確認 | 主な属性（`effort`・`skill.name`・`query_source`・`service.version`）が docs どおり届くか。値の型と格納位置。問い①〜③ に要るデータが取れるか | V-1、V-3、V-4、V-8、V-9 |
| 1-2 | 思考トークンの取得経路 | 経路 (i)(ii)（§2.1）がどの程度成立するか。`output_tokens` に思考分が含まれるか。どちらを主にするか | V-2a、V-2b |
| 1-3 | 作業分類タグの付与方式 | 候補 ①〜⑤ をどう組み合わせるか（精度・手間・プライバシー） | V-5、V-7、V-12 |
| 1-4 | 受信・保存コンポーネント | 導入・常駐の手軽さ、集計クエリの書きやすさ、UI との相性、データ消失への強さ。OTLP のプロトコル | V-6、V-13 |
| 1-5 | ダッシュボード方式 | 「頻繁にレイアウトを変えたい」要件への適合度。探索期（指標が未確定）と定常期で方式を分けるか | — |
| 1-6 | `~/.claude` 配下のローカルファイルの棚卸し | どのファイルに何が残るか。テレメトリと突き合わせる鍵（`session_id`・`request_id` 等）を持つか。保存期間と形式は安定しているか。既存 transcript の過去分を基準データとして使えるか（あくまで補助。主線は OTel） | — |

**方法**

- 1-1: `console` exporter か簡易受信で実セッションを流し、metrics / events / traces を記録する（手順は v2.1 §8.1。出力先は V-11(b) #22 で最初に確かめる）。delta の挙動、2 セッション同時の見え方、`/usage` の利用量内訳（問い②の補助）も見る
- 1-2: 同じセッションで (i)(ii) を比べる。(i) は突合率をメイン / サブエージェント / compact / リトライ別に測り、`thinking_tokens ≤ output_tokens` を確かめる（V-2a）。(ii) で確定する（V-2b。§7 #2 の判断後）
- 1-3: 次の候補を比べる。前提と制約の裏付けとして、`skill.name` の有効範囲、`agent.name` の値、`OTEL_RESOURCE_ATTRIBUTES` の読み込み時期（③⑤ の前提）を確かめる
  - ① ネイティブ属性（`skill.name`・`command_name`・`workflow.name` 等）のみ
  - ② `UserPromptSubmit` hook でラベルを別ファイルに書き、hook 入力の `prompt_id` で突合
  - ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
  - ④ プロンプト本文の事後分類（ルール / LLM。`OTEL_LOG_USER_PROMPTS=1` が前提）
  - ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル
  - 比較結果は次の列の表で整理する（列名: 記載する内容）
    - 候補: ①〜⑤、または組み合わせ
    - 長所: 他の候補ではできず、この候補ならできること
    - 短所: 他の候補ならできるが、この候補ではできないこと
    - 前提事項: この候補が成り立つために必要な条件
    - 制約: この候補を採ると受け入れる必要がある制限
    - 分類精度: 作業の性質をどこまで正しく分けられるか
    - 導入負荷: 仕組みを用意するための作業量
    - 維持負荷: 分類体系の見直しや cc の更新への追従に要る作業量
    - 機微情報: プロンプト本文などの機微な情報を記録・処理するか
    - その他: 上のいずれにも当てはまらない事項
- 1-4: Windows ネイティブ・Docker 不要のものに限り、(A) Node.js の自作 OTLP/HTTP 受信 + SQLite / DuckDB、(B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB（v2.1 §3 の構成）、(C) VictoriaMetrics / VictoriaLogs の単体バイナリを比べる。(B) は v2.1 R-1・R-3・R-4、V-6・V-13 の注意点（再起動時の消失、圧縮、並べ替えキー、Windows のパス表記。v2.1 §5.4・§6）を評価に含める
- 1-5: 自作 Node.js ダッシュボードと Grafana（Windows 版）等の OSS を比べる。探索期は DuckDB の SQL で集計の切り口をすぐ変えられる、という v2.1 §3.1 の考え方も比較軸に入れる
- 1-6: `~/.claude` 配下のファイル（transcript、サブエージェントの transcript、プロンプト履歴、設定、デバッグログ等。実在と内容は着手時に確かめる）ごとに、取得・算出できる情報、突合の鍵、保存期間、機微情報の有無を表にする。テレメトリとして扱えない情報も対象に含める。あわせて、既存 transcript（約 217MB）から model / usage / thinking_tokens / skill 等をどこまで復元できるかを確かめる

- **成果物**: `reports/01.基礎調査/…/調査報告書.md`（項目ごとに分けるかは着手時に決める）
- **完了条件**: 1-1〜1-6 の判定が出そろい、Phase 2 の設計判断に必要な候補が 2 案以内に絞られている。v2.1 §8.5（V-11(b)）の各項目について、確認結果（一致 / 差異あり / 対象外とその理由）が記録されている。V-11(b) は 1-1〜1-6 で横断的に確認し、担当の 1-x は着手時に割り当てる
- **主なリスク**: 文書と実際の出力の差。バージョンアップで属性が変わること

### Phase 3: PoC（エンドツーエンド疎通）

- **作業**: 最小の受信 → 保存 → transcript 突合 → 簡易集計（CLI かスクリプト出力で可）を実装し、実セッションで一通り流す
- **確認観点**: `effort` 別・`model` 別の集計が出るか、思考トークンが突合されるか、2 セッションを同時に動かしても欠落しないか、受信サーバが止まっていても cc の操作に影響しないか
- **職場環境の確認ステップ（PoC の後半）**: 本環境で PoC が通った後、Claude Code が確認手順書を用意し、作業指示者本人が職場環境で実施する（Claude Code は職場環境で検証しない）。Phase 4 の実装に入る前に、職場環境の差が設計に影響しないかを確かめるため、ここに置く
  - 手順書に含めるもの: v2.1 V-10、§2.2 の不明点、既知の差（仕様別紙 §5）、PoC を職場環境で動かす手順と記録様式
  - 結果は作業指示者が記録様式に書き、Claude Code が PoC 報告書に取りまとめる。設計の変更が要る場合は Phase 2 へ戻す
- **成果物**: `app/` 配下の PoC コード、`reports/03.PoC/…/PoC報告書.md`、同フォルダの職場環境確認手順書（確認結果を含む）
- **完了条件**: 本環境で確認観点を満たし、職場環境の確認結果がそろっている。満たさない場合は Phase 2 へ戻す判断材料をそろえる

### Phase 4: 収集基盤の実装

- **作業**: PoC を日常運用に耐える形にする。受信・保存の常駐化、transcript 取込の自動化、タグ付けの仕組み（hook / ランチャ等）、形式変化の検知、ログ・エラー処理
- **成果物**: `app/` 配下の実装、利用手順（導入・起動・停止・トラブル時の対応）
- **完了条件**: 日常の cc 利用で操作を増やさずにデータが溜まる状態が 1 週間程度継続する（職場環境での継続は作業指示者が確認する）

### Phase 5: ダッシュボードの実装

- **作業**: 1-5（ダッシュボード方式の比較）で選んだ方式で分析画面を作る。レイアウトを変えやすい構成（部品の設定ファイル化など）を優先する
- **想定画面**: 期間サマリ、作業分類 × モデル × effort のクロス集計、トークン内訳（思考比率を含む）の推移、高コストのプロンプト・セッションのランキングと明細
- **成果物**: ダッシュボード、画面仕様メモ
- **完了条件**: 作業指示者が画面をレビューし、分析に使える状態と判断する

### Phase 6: 運用・分析・フィードバック

- **作業**: 一定期間（目安 2〜4 週間）データを蓄積してから分析する。「トークンを消費しやすい作業」の特定、作業分類ごとの推奨モデル × effort の導出、問い①〜③ の分析。仮説 H-1〜H-3（v2.1 §4.5）を出発点とし、トークン数とコストの両方で比べる
- **成果物**:
  - `reports/06.分析/…/分析報告書.md`
  - **推奨モデル × effort 表（改訂案）** と、ルート `CLAUDE.md` の「モデル選定原則」・`check-model` skill への反映案
  - 問い①〜③ の還流先資産（§1.1 の表）への反映案
- **完了条件**: 反映案を作業指示者が承認する（反映自体は main 側の横断作業として別途実施）
- **補足**: サンプル数が少ない分類・問いは結論を保留し、継続観測の対象として明記する。問い①の比較には対照実験（effort を固定して `/compact` と `/clear` を比べる等）が要る可能性があり、実施するかは Phase 6 着手時に決める

## 5. 横断的なリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| cc のバージョンアップで OTel 属性・transcript 形式が変わる（例: v2.1.222 の `mcp_server.name` の意味変更） | 集計の欠落・誤り | 環境基線（`service.version`）を記録する。取込時に想定外の形式を検知して警告する（Phase 2 で設計） |
| transcript と OTel の突合が一部成立しない | 思考トークンの欠落 | 1-2 で成立率を実測し、欠落分の扱い（除外 / 推定）を設計で決める |
| 作業分類タグの付与漏れ・揺れ | 分析精度の低下 | 付与方式を複数組み合わせる。「未分類」を明示的に集計して漏れを見える化する |
| プロンプト本文などの機微情報が保存される | 情報漏えい | 保存先を repo 外にする。本文の記録は既定 OFF とし、有効化は作業指示者の判断で行う |
| 受信サーバの停止中にデータが欠落する | 連続性の低下 | cc 側は送信失敗しても操作に影響しないことを PoC で確認する。transcript からの遡り取込で補う |
| `cost_usd` が API 料金換算の推定値である | サブスクリプション利用時の実コストとずれる。職場環境では Bedrock の実請求ともずれる | 分析では「API 換算コスト」と明記し、比較の相対指標として扱う |
| transcript は cc が既定 30 日（`cleanupPeriodDays`）で削除する。OTel と違い、こちらから取り込まない限り手元に残らない（v2.1 R-13） | 取込が削除に間に合わないと、思考トークンの突合・遡り取込が欠落する | 削除より前に定期的に取り込み、自前の保存先に永続化する（取込の仕組みと頻度は Phase 2 で決める）。`cleanupPeriodDays` の延長は補助策とし、適用値は `retention_sweep` イベントの `period_days` で確かめる（職場環境では管理者設定で短い可能性がある） |
