## 1. ゴール

**背景**: cc の費用対効果を高めたい。ステータスラインで見られるモデル・コンテキストサイズ・総トークン量だけでは、effort や作業の性質ごとのトークン消費（思考トークンを含む）が分からない。そこで、これらを cc の OTel テレメトリで収集・分析できるようにする。

### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

あわせて、次の 3 つの問いに分析で答える（v2.1 §1.2）。答えは、右列のルート資産の改訂案として出す。還流先のない分析はしない。

| # | 分析で答える問い | 分析結果の還流先（ルート資産） |
|---|---|---|
| ① | `/compact` と `/clear` をどう使い分けるとコストを抑えられるか | compact / clear の運用指針（ルート `CLAUDE.md`、または `pre-compact` skill） |
| ② | Skill・workflow・カスタムサブエージェントによるオーケストレーション（Opus から Sonnet への移譲を含む）で、品質を保ったままどこまでコストを下げられるか | ルート `CLAUDE.md` の「Agent 活用ガイドライン」、`orchestrate` skill |
| ③ | どの作業・agent・ツールがコストのボトルネックか | 「モデル選定原則」表、`check-model` skill |

### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript など `~/.claude` 配下のファイルから別経路で取り込み、テレメトリと突合する。何を取り込むかは 1-6 の棚卸しを受けて Phase 2 で決める |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

いずれも本環境と職場環境の両方で動くものとする（§1.4）。

### 1.3 成功基準（活動全体）

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- 本環境と職場環境で同じ仕組みが動き、両方のデータを同じ観点で集計できる。どちらの環境のデータかを区別できる（区別の方法は Phase 2 で決める。合算して分析するかは §7 #7）
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ読込 / キャッシュ作成 / **思考**トークンと推定コストを集計できる。メインとサブエージェントを分けて集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる
- 問い①〜③ のそれぞれについて、還流先資産の改訂案を根拠データ付きで提示できる。データが足りない問いは「結論保留・継続観測」と明示する

### 1.4 前提・制約とスコープ

- **第一のゴール（本計画 Phase 0〜6 の対象）**: Windows ネイティブ・Docker 不要の最小構成。**第二のゴール**: WSL + Docker 環境への対応。次の活動で扱う
- **対象環境**
  - 本環境: Anthropic 直接契約のアカウント。Windows 11 ネイティブ（Docker / WSL は使わない）
  - 職場環境: cc → 社内 LLM ゲートウェイ（LiteLLM 等。`ANTHROPIC_BEDROCK_BASE_URL` / `ANTHROPIC_BASE_URL` で指定）→ Amazon Bedrock。Windows。OTel 設定（ユーザ settings の `env`）は作業指示者が変更できる。実機確認は Phase 3 で作業指示者が行う
- 受信サーバ・データシンク等は、ローカルで起動できる OSS を積極的に使ってよい
- 分析 UI は、レイアウトを度々変えたくなる見込みがあるため、Node.js の自作ダッシュボードを有力候補とする（OSS との比較は 1-5）
- **スコープ外**: チーム・組織単位の集中収集（本活動は個人ローカル用）、クラウド・SaaS の監視基盤（Datadog 等）への送信

### 2.2 職場環境の不明点（Phase 3 で確認）

- 思考トークンの内訳（usage の `output_tokens_details.thinking_tokens`）が、Bedrock・社内プロキシ経由でも返るか、transcript に残るか
- 社内プロキシが usage・応答ヘッダ・ストリームを改変しないか
- セキュリティ製品等が `localhost` / `127.0.0.1` 宛ての OTLP 送信を止めないか（作業指示者の指摘による懸念。Phase 1 では未確認。[まとめ報告書 §4.2](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-4-2)）
- 職場環境の Node.js の版。保存に `node:sqlite` を使う構成は Node 22.13 以降が前提になる（同上）
- Bedrock 経由の transcript に `requestId` が残るか。本環境の記録にある Bedrock 形式のモデル ID の行では全件欠けていた。職場環境でも欠けるなら、§2.1 の経路 (i) は職場環境では成り立たない（同上、[1-6 §3.7](../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-3-7)）
- Claude Mods（cc 2.1.287 で加わった、plugin 内で cc のプロセスと同居して動く JS/TS の hook）が、職場の managed settings で止められていないか。Mod を止める `allowManagedModsOnly` は managed settings のトップレベルのキーではなく、組み込み plugin の option として `pluginConfigs."cc-plugin-sec-default@builtin".options.allowManagedModsOnly` に置く。これが有効だと、利用者の Mod は読み込まれるが拒否され、hook が動かない。settings の command hook と、plugin の `hooks/hooks.json` の command hook は動き続ける（docs 2.1.295 時点の記述。置き場所は以前の docs から同じ）。command hook まで止まるのは `allowManagedHooksOnly`（組織が配布していない hook を止める）か `disableAllHooks` の場合で、そのときは候補 ②（hook でラベル）は職場環境では成り立たない（[1-8 §4.1](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-4-1)・[§4.4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)・[§7.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）
- auto mode の分類器のリクエストが、社内ゲートウェイの経由でもサーバー側のチェックに乗るか。分類器は、auto mode で実行しようとする操作を確認なしで許可してよいかを実行前に判定する仕組みである。docs では、分類器のチェックはセッション自身のモデルリクエストの中でサーバーが行い、課金されない（Bedrock や LLM gateway の経由でも、cc 2.1.278 以降は既定で依頼する）。ゲートウェイが要求や結果を素通ししないと、Claude Code 自前の分類器リクエストに切り替わり、アカウントの種類によってはトークン使用量として課金される。本環境で `CLAUDE_CODE_AUTO_MODE_SERVER=0` にして自前のリクエストを出させると、そのリクエストは OTel の `api_request` にも `token.usage` にも出なかった（2026-10-12 の C-6b、各 2 回）。職場で自前に落ちると、OTel だけではコストを過小評価する（裁定待ち事項 J-21 で報告、通知への応答は J-22 で裁定済み。[1-8 §7.3.4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)）

既知の差として、permission mode が未設定のとき、third-party provider（職場環境）では対話型も `-p` も auto mode で起動する（`-p` は cc 2.1.285 以降。[1-8 §2.1](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-2-1)）。ただし docs（2.1.295 時点）では、auto mode に対応するのは Sonnet 5 以降・Opus 4.7 以降・Haiku 5.5（cc 2.1.293 以降）・Fable のモデルだけで、それ以外のモデルは Manual で起動する。モデルのエイリアスの解決先も環境で違う。Bedrock では `haiku` が Haiku 4.5、`sonnet` が Sonnet 4.5、`opus` が Opus 5.5 に解決する。本環境（Anthropic API）では、`haiku` は cc 2.1.293 以降 Haiku 5.5（`claude-haiku-5-5`）に、`sonnet` は Sonnet 5.5 に解決する（[1-8 §7.3.3](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）。職場環境は社内ゲートウェイを経由するため、指定したモデルと起動時の permission mode は Phase 3 で確かめる。本環境でも対話型は cc 2.1.284 以降、既定で auto mode になる。加えて本環境では、ユーザ settings の `permissions.defaultMode` の設定により、`-p` も auto mode で起動する（組み込みの既定によるものではない。裁定待ち事項 J-16 で報告）。cc 2.1.287 の `-p` の実測では、auto mode に対応しない Haiku 4.5 が起動直後に default に落ちていたため見えにくかった。cc 2.1.296 の実機では、Haiku 5.5 の `-p` は auto mode のまま動いた。このため、V-2b 等の検証の `-p` では `--permission-mode default` を明示する (承認待ち: Q2)。確認手順書での扱いは Phase 3 に書く。

- 1-3: 次の候補を比べる。前提と制約の裏付けとして、`skill.name` の有効範囲、`agent.name` の値、`OTEL_RESOURCE_ATTRIBUTES` の読み込み時期（③⑤ の前提）を確かめる
  - ① ネイティブ属性（`skill.name`・`command_name`・`workflow.name` 等）のみ

  - ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
  - ④ プロンプト本文の事後分類（ルール / LLM。`OTEL_LOG_USER_PROMPTS=1` が前提）
  - ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル
  - 比較結果は次の列の表で整理する（列名: 記載する内容）
    - 候補: ①〜⑤、または組み合わせ
    - 長所: 他の候補ではできず、この候補ならできること
    - 短所: 他の候補ならできるが、この候補ではできないこと
    - 前提事項: この候補が成り立つために必要な条件
    - 制約: この候補を採ると受け入れる必要がある制限
    - 分類精度: 作業の性質をどこまで正しく分けられるか
    - 導入負荷: 仕組みを用意するための作業量
    - 維持負荷: 分類体系の見直しや cc の更新への追従に要る作業量
    - 機微情報: プロンプト本文などの機微な情報を記録・処理するか

- 1-4: Windows ネイティブ・Docker 不要のものに限り、(A) Node.js の自作 OTLP/HTTP 受信 + SQLite / DuckDB、(B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB（v2.1 §3 の構成）、(C) VictoriaMetrics / VictoriaLogs の単体バイナリを比べる。(B) は v2.1 R-1・R-3・R-4、V-6・V-13 の注意点（再起動時の消失、圧縮、並べ替えキー、Windows のパス表記。v2.1 §5.4・§6）を評価に含める

- **作業**: PoC を日常運用に耐える形にする。受信・保存の常駐化、transcript 取込の自動化、タグ付けの仕組み（hook / Claude Mods / ランチャ等。hook と Mod のどちらにするかは Phase 2 で決める）、形式変化の検知、ログ・エラー処理
- **成果物**: `app/` 配下の実装、利用手順（導入・起動・停止・トラブル時の対応）
- **完了条件**: 日常の cc 利用で操作を増やさずにデータが溜まる状態が 1 週間程度継続する（職場環境での継続は作業指示者が確認する）

### Phase 5: ダッシュボードの実装

- **作業**: 1-5（ダッシュボード方式の比較）で選んだ方式で分析画面を作る（方式を選ぶ時期は、候補の絞り込みの結果を受けて決める (保留: Q1 の回答待ち)）。レイアウトを変えやすい構成（部品の設定ファイル化など）を優先する
- **想定画面**: 期間サマリ、作業分類 × モデル × effort のクロス集計、トークン内訳（思考比率を含む）の推移、高コストのプロンプト・セッションのランキングと明細
- **成果物**: ダッシュボード、画面仕様メモ
- **完了条件**: 作業指示者が画面をレビューし、分析に使える状態と判断する

### Phase 6: 運用・分析・フィードバック

- **作業**: 一定期間（目安 2〜4 週間）データを蓄積してから分析する。「トークンを消費しやすい作業」の特定、作業分類ごとの推奨モデル × effort の導出、問い①〜③ の分析。仮説 H-1〜H-3（v2.1 §4.5）を出発点とし、トークン数とコストの両方で比べる
- **成果物**:

  - **推奨モデル × effort 表（改訂案）** と、ルート `CLAUDE.md` の「モデル選定原則」・`check-model` skill への反映案
  - 問い①〜③ の還流先資産（§1.1 の表）への反映案
- **完了条件**: 反映案を作業指示者が承認する（反映自体は main 側の横断作業として別途実施）
