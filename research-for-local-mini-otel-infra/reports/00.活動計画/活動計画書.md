## 1. ゴール

**背景**: cc の費用対効果を高めたい。ステータスラインで見られるモデル・コンテキストサイズ・総トークン量だけでは、effort や作業の性質ごとのトークン消費（思考トークンを含む）が分からない。そこで、これらを cc の OTel テレメトリで収集・分析できるようにする。

### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

あわせて、次の 3 つの問いに分析で答える（v2.1 §1.2）。答えは、右列のルート資産の改訂案として出す。還流先のない分析はしない。

| # | 分析で答える問い | 分析結果の還流先（ルート資産） |
|---|---|---|
| ① | `/compact` と `/clear` をどう使い分けるとコストを抑えられるか | compact / clear の運用指針（ルート `CLAUDE.md`、または `pre-compact` skill） |
| ② | Skill・workflow・カスタムサブエージェントによるオーケストレーション（Opus から Sonnet への移譲を含む）で、品質を保ったままどこまでコストを下げられるか | ルート `CLAUDE.md` の「Agent 活用ガイドライン」、`orchestrate` skill |
| ③ | どの作業・agent・ツールがコストのボトルネックか | 「モデル選定原則」表、`check-model` skill |

### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript など `~/.claude` 配下のファイルから別経路で取り込み、テレメトリと突合する。何を取り込むかは 1-6 の棚卸しを受けて Phase 2 で決める |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

いずれも Anthropic 環境と LLM ゲートウェイ環境の両方で動くものとする（§1.4）。

### 1.3 成功基準（活動全体）

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- Anthropic 環境と LLM ゲートウェイ環境で同じ仕組みが動き、両方のデータを同じ観点で集計できる。どちらの環境のデータかを区別できる（区別の方法は Phase 2 で決める。合算して分析するかは §7 #7）
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ読込 / キャッシュ作成 / **思考**トークンと推定コストを集計できる。メインとサブエージェントを分けて集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる
- 問い①〜③ のそれぞれについて、還流先資産の改訂案を根拠データ付きで提示できる。データが足りない問いは「結論保留・継続観測」と明示する

### 1.4 前提・制約とスコープ

- **第一のゴール（本計画 Phase 0〜6 の対象）**: Windows ネイティブ・Docker 不要の最小構成。**第二のゴール**: WSL + Docker 環境への対応。次の活動で扱う
- **対象環境**
  - 本環境: Anthropic 直接契約のアカウント。Windows 11 ネイティブ（Docker / WSL は使わない）。職場環境と並べて呼ぶときは「Anthropic 環境」と書く
  - 職場環境: cc → 社内 LLM ゲートウェイ（LiteLLM。`ANTHROPIC_BASE_URL` で指定する Anthropic 形式の接続で、cc の Bedrock モードは使わない。2026-10-18 の作業指示者の回答）→ Amazon Bedrock。Windows。OTel 設定（ユーザ settings の `env`）は作業指示者が変更できる。実機確認は Phase 3 で作業指示者が行う
  - 職場環境の呼び分け: 職場環境の性質のうち、cc から見た接続の形に依る事柄を「LLM ゲートウェイ環境」、ゲートウェイが LiteLLM であることに依る事柄を「LiteLLM 環境」、ゲートウェイの先の Amazon Bedrock に依る事柄（実請求、提供されるモデルなど）を「Bedrock 環境」と書く。本環境と並べて呼ぶときは「LLM ゲートウェイ環境」と書く。職場の PC・社内の管理・作業指示者が確かめる場としての意味では「職場環境」と書く。cc の Bedrock モード（third-party provider）を前提にした記述は、2026-10-18 の回答を受けて見直す（見直しは別の作業）
- 受信サーバ・データシンク等は、ローカルで起動できる OSS を積極的に使ってよい
- 分析 UI は、レイアウトを度々変えたくなる見込みがあるため、Node.js の自作ダッシュボードを有力候補とする（OSS との比較は 1-5）
- **スコープ外**: チーム・組織単位の集中収集（本活動は個人ローカル用）、クラウド・SaaS の監視基盤（Datadog 等）への送信

### 2.2 職場環境の不明点（Phase 3 で確認）

- 思考トークンの内訳（usage の `output_tokens_details.thinking_tokens`）が、Bedrock・社内プロキシ経由でも返るか、transcript に残るか
- 社内プロキシが usage・応答ヘッダ・ストリームを改変しないか
- セキュリティ製品等が `localhost` / `127.0.0.1` 宛ての OTLP 送信を止めないか（作業指示者の指摘による懸念。Phase 1 では未確認。[まとめ報告書 §4.2](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-4-2)）
- 職場環境の Node.js の版。保存に `node:sqlite` を使う構成は Node 22.13 以降が前提になる（同上）
- Bedrock 経由の transcript に `requestId` が残るか。本環境の記録にある Bedrock 形式のモデル ID の行では全件欠けていた。職場環境でも欠けるなら、§2.1 の経路 (i) は職場環境では成り立たない（同上、[1-6 §3.7](../01.基礎調査/06.ローカルファイル棚卸し/調査報告書.md#sec-3-7)）
- Claude Mods（cc 2.1.287 で加わった、plugin 内で cc のプロセスと同居して動く JS/TS の hook）が、職場の managed settings で止められていないか。Mod を止める `allowManagedModsOnly` は managed settings のトップレベルのキーではなく、組み込み plugin の option として `pluginConfigs."cc-plugin-sec-default@builtin".options.allowManagedModsOnly` に置く。これが有効だと、利用者の Mod は読み込まれるが拒否され、hook が動かない。settings の command hook と、plugin の `hooks/hooks.json` の command hook は動き続ける（docs 2.1.295 時点の記述。置き場所は以前の docs から同じ）。command hook まで止まるのは `allowManagedHooksOnly`（組織が配布していない hook を止める）か `disableAllHooks` の場合で、そのときは候補 ②（hook でラベル）は職場環境では成り立たない（[1-8 §4.1](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-4-1)・[§4.4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-4-4)・[§7.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)）
- auto mode の分類器のリクエストが、社内ゲートウェイの経由でもサーバー側のチェックに乗るか。分類器は、auto mode で実行しようとする操作を確認なしで許可してよいかを実行前に判定する仕組みである。docs では、分類器のチェックはセッション自身のモデルリクエストの中でサーバーが行い、課金されない（Bedrock や LLM gateway の経由でも、cc 2.1.278 以降は既定で依頼する）。ゲートウェイが要求や結果を素通ししないと、Claude Code 自前の分類器リクエストに切り替わり、アカウントの種類によってはトークン使用量として課金される。本環境で `CLAUDE_CODE_AUTO_MODE_SERVER=0` にして自前のリクエストを出させると、そのリクエストは OTel の logs（`api_request`）と metrics（`token.usage`）には出なかったが、traces の `claude_code.llm_request` span（`query_source_safe=auto_mode`、トークン数付き）には出た（2026-10-12 の C-6b、各 2 回。当初は traces を見落として「OTel に出ない」と書いた）。logs・metrics だけで集計すると分類器の分が漏れるが、traces の span を集計に含めれば、サーバー側チェックの有無によらず漏れない（効いていれば判定は本体のリクエストに同乗し、本体のリクエストは logs・traces の両方に出る。効いていなければ自前のリクエストが traces の span に出る）。ただしこれは、確かめた範囲（直接接続で、debug log を取った run に出た呼び出しの種類まで。C-6b は各 2 回・操作 1 種類）からの推定である。職場（ゲートウェイ＋Bedrock）でも同じ形で traces に出ると見込む。traces の取得に致命的な欠点は無いので、分類器の件は本活動にとって致命的ではなく、職場がサーバー側チェックを効かせているか（分類器の状態）は Phase 3 で確かめない（作業指示者の判断、2026-10-12。職場では、受信確認で traces に `llm_request` span が届くことを確かめ、判定の有無を下の `classifier_verdict` で記録する。集計の扱いは Phase 2「分析指標」。裁定待ち事項 J-21 で報告、通知への応答は J-22 で裁定済み、J-23 は取り下げ。[1-8 §7.3.4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-4)）。cc 2.1.301 からは、分類器が判定したことを logs の `tool_decision` の `classifier_verdict` でも見分けられる（cc 2.1.302 の実機では、サーバー側チェックでも自前のリクエストでも同じ値で、自前に落ちたかの区別には使えなかった）。費用を数えるのは引き続き traces の span なので、上の判断の根拠は変わらない（[1-8 §8.3.3](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-3)）

既知の差として、permission mode が未設定のとき、third-party provider（職場環境が当たる見込み）では対話型も `-p` も auto mode で起動する（`-p` は cc 2.1.285〜2.1.301。[1-8 §2.1](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-2-1)）。cc 2.1.302 からは、permission mode を指定しない `-p` は third-party provider では default で起動する（changelog。docs の表とは食い違うので changelog を正とする。仕様別紙 §5、[1-8 §8.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D47）。このため職場の `-p` の起動 mode は、本環境と食い違いうる。また docs（2.1.295 時点）では、auto mode に対応するのは Sonnet 5 以降・Opus 4.7 以降・Haiku 5.5（cc 2.1.293 以降）・Fable のモデルだけで、それ以外のモデルは Manual で起動する。モデルのエイリアスの解決先も環境で違う。Bedrock では `haiku` が Haiku 4.5、`sonnet` が Sonnet 4.5、`opus` が Opus 5.5 に解決する。本環境（Anthropic API）では、`haiku` は cc 2.1.293 以降 Haiku 5.5（`claude-haiku-5-5`）に、`sonnet` は Sonnet 5.5 に解決する（[1-8 §7.3.3](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-3)）。職場環境は社内ゲートウェイを経由するため、指定したモデルと起動時の permission mode は Phase 3 で確かめる。本環境でも対話型は cc 2.1.284 以降、既定で auto mode になる。加えて本環境では、ユーザ settings の `permissions.defaultMode` の設定により、`-p` も auto mode で起動する（組み込みの既定によるものではない。裁定待ち事項 J-16 で報告）。cc 2.1.287 の `-p` の実測では、auto mode に対応しない Haiku 4.5 が起動直後に default に落ちていたため見えにくかった。cc 2.1.296 の実機では、Haiku 5.5 の `-p` は auto mode のまま動いた（cc 2.1.302 でも同じ）。このため、V-2b 等の検証の `-p` では `--permission-mode default` を明示する (承認待ち: Q2)。permission mode を明示すれば、cc 2.1.302 の `-p` の起動 mode の変更による本環境と職場の差は、測定に入らない（裁定待ち事項 J-16）。確認手順書での扱いは Phase 3 に書く。

    - auto mode の分類器（§2.2）: 確かめるのは、課金の通知への応答と、分類器のリクエストが traces の span に出るかである。職場がサーバー側チェックを効かせているか（`/status` の Auto mode server 行、`CLAUDE_CODE_AUTO_MODE_SERVER=1` の試行）は確かめない。traces を集計に含めれば、サーバー側チェックの有無によらず分類器の分は漏れない見込み（直接接続の観測からの推定）だからである（作業指示者の判断、2026-10-12。裁定待ち事項 J-23 は取り下げ）。手順: auto mode で起動したこと（起動時の mode、モデル ID、managed settings の `disableAutoMode`）を確かめ、auto で起動しなかったらその旨を記録して終える。debug log を付けて起動し、分類器が呼ばれる操作（外部への通信など、読み取り専用でないシェルコマンド 1 つ）を行う。課金の通知が出たら Enter で続行する（裁定待ち事項 J-22 で裁定済み。docs の `auto-mode-classifier-billing`）。通知の有無、判定なしの拒否の有無、debug log で分類器が呼ばれたかを記録する。自前の分類器リクエストは logs（`api_request`）と metrics には出ず、traces の span には出る（本環境の C-6b）。ループバック宛ての送信が届く場合は、操作の前後の `api_request` と traces の span（`query_source_safe=auto_mode` の有無）、logs の `tool_decision` の `classifier_verdict`・`permission_mode`（cc 2.1.301 以降の属性。`classifier_verdict` は分類器が判定したかを示す。職場の cc が 2.1.301 未満なら付かない）も記録する。職場で traces が届くかと、span の `request_id`（と `client_request_id`）の有無は、上のループバック宛て送信の項目で確かめる（[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2)、[1-8 §7.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-5)）
    - plugin の構成と L1 の hook の時間（タグ案 L1 を採る場合。記録だけの項目）: ループバック宛ての送信が届く場合に、hook を登録する plugin の集合（`plugin_loaded`・`hook_registered`）と、L1 の試作の hook が自分で記録する所要時間を記録する。plugin の構成が本環境と違うと、本環境で隠れた L1 の hook の時間が、職場ではそのまま上乗せに出うるためである（§5）。どちらも PoC の受信データと L1 の hook の記録に入るので、記録の取り出しで職場の手作業が増えるのは、受信データの提出（記録様式の手順）の範囲に限られる。ほかに、下の L1 の試作の hook の導入と取り外しがある。PoC 報告書には plugin の名前を書かない。L1 の試作の hook は、PoC の成果物（plugin、または settings に書く command hook）として作業指示者が職場の環境に入れる。入れ方と外し方は職場環境確認手順書に書く
  - 各確認項目の判定の目安・測り方・標本数（職場環境の項目は確認する場所と記録する値）は、[【別紙】V-ID別状況とPhase3実測項目 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の案を出発点にする。タグ案 L1 の hook の待ち時間の判定は、上の「測定の条件」の J-12 の判定のとおり
    - 候補 ③（起動ランチャ）を採る場合だけ、PowerShell の版。本環境では Windows PowerShell 5.1 のスクリプトで環境変数を設定して起動すると、OTel の設定が届かなかった（[1-1 §7](../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)）
  - 結果は作業指示者が記録様式に書き、Claude Code が PoC 報告書に取りまとめる。設計の変更が要る場合は Phase 2 へ戻す
- **成果物**: `app/` 配下の PoC コード、`reports/03.PoC/…/PoC報告書.md`、同フォルダの職場環境確認手順書（確認結果を含む）
- **完了条件**: 本環境で確認観点を満たし、職場環境の確認結果がそろっている。起こし方を決めていない項目（plugin の hook の受け渡しの失敗、アイドル時の compaction など）は、期間内に観測できなければ「未観測」と記録して閉じてよい（V-ID 別紙 §2）。満たさない場合は Phase 2 へ戻す判断材料をそろえる
