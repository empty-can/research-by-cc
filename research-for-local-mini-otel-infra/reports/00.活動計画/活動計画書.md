    - 長所: 組織が managed settings の `strictPluginOnlyCustomization`（hook などの種類を、plugin と managed settings のものに限る設定）でどれかの種類をロックしても、plugin の hook は動く（別の案では、エラー無しで読み込まれない）
    - 短所: marketplace を用意して入れる手順が要る。組織が `strictKnownMarketplaces`（plugin を入れてよい marketplace の allowlist）を置いていれば、その marketplace が許されている必要がある（別の案では、フォルダを置くだけで済む）

費用を見なし費用で集計する既定の案（Phase 2「[分析指標](#sec-p2-metrics)」。作業指示者の発言（2026-10-24）を受けた。別の案に長所と短所を添えた）:

- 費用は、API リクエストごとのトークン数と単価表から計算する見なし費用で集計し、`cost_usd` は検算と参考に残す。単価表は、単価の組（Anthropic の API の料金と、職場の実単価（分かってから足す。下の表の先送りの行））× モデル × トークンの種類で持つ。本環境では、費用より精度・時間・使用量の上限の消費を主に比べ、見なし費用は、職場の実単価が分かってから職場の費用の見積もりに使う。別の案は、`cost_usd` をそのまま費用にすること（v2.3 までの §5.1・§5.2 の対策の「API 換算コスト」）
  - 長所: 職場の実単価が分かれば、その組を表に足して、職場の費用を見積もれる。`cost_usd` の無い span の費用も同じ表で計算できる。単価が改定されたとき、過去の期間を計算し直せる
  - 短所: 単価表の保守（改定への追従と出典の確認）が要る。表に無い要素は計算できない（別の案は、実装も保守も要らず cc の計算に任せられるが、換算は Anthropic の料金による。managed settings の `modelPricing` が配られていればその料金によるが、`overrides` の行の単価では TTL 別の cache 書き込みを 1 つの単価で扱う。仕様別紙 §5）
- 既定の案の中身（見なし費用を採る場合に決まること。別の案は置いていない。TTL の扱いは docs の既定の TTL から、検算の基準は計算の正しさから決まり、4 点は Phase 2 で決めることの列挙であるため）
  - cache 書き込みの TTL: TTL 別の内訳を使わない場合と内訳の無い行は、その行の課金の形（定額の契約の枠内か、API キー・クラウド提供元か）と要求の区分（主の会話か、サブエージェントなどそれ以外か）での既定の TTL（主の会話は、定額の契約の枠内では 1 時間、API キー・クラウド提供元では 5 分。それ以外は、一部の補助の要求を除いて 5 分。仕様別紙 §1）の単価で計算し、注記する。本環境の記録から職場の費用を見積もるときは、cache 書き込みを職場の TTL（`promptCacheTtl`（主の会話の cache の TTL を選ぶ設定）などを設定していなければ 5 分の見込み【推定】。Phase 7 の V-10 の行で確かめる）の単価で計算し直す
  - Phase 2 の設計で決める 4 点: 単価の組と課金の形をレコードに当てる鍵（環境の区別。要求の区分は `query_source` から付ける）、`model` と表のモデルの結び付け、表に無いモデルの扱い（未計算として件数を数え、注記する）、表の保存形式と置き場所
  - 検算（[Phase 3](#sec-p3)）: Anthropic の単価の組で計算した見なし費用と `cost_usd` が、リクエストごとに一致する（丸めの差を除く）ことを合格の基準の既定の案にする。ずれたら、ずれる要素を特定して記録し、単価表か計算を直す。表で直せないずれ（トークン数から計算できない料金など）は、要素を記録して検算の比べる対象から外し、見なし費用の漏れとして注記する

<a id="sec-1"></a>
## 1. ゴール

**背景**: cc の費用対効果を高めたい。ステータスラインで見られるモデル・コンテキストサイズ・総トークン量だけでは、effort や作業の性質ごとのトークン消費（思考トークンを含む）が分からない。そこで、これらを cc の OTel テレメトリで収集・分析できるようにする。

<a id="sec-1-1"></a>
### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

あわせて、次の 3 つの問いに分析で答える（v2.1 §1.2）。答えは、右列のルート資産の改訂案として出す。還流先のない分析はしない。

| # | 分析で答える問い | 分析結果の還流先（ルート資産） |
|---|---|---|
| ① | `/compact` と `/clear` をどう使い分けるとコストを抑えられるか | compact / clear の運用指針（ルート `CLAUDE.md`、または `pre-compact` skill） |
| ② | Skill・workflow・カスタムサブエージェントによるオーケストレーション（Opus から Sonnet への移譲を含む）で、品質を保ったままどこまでコストを下げられるか | ルート `CLAUDE.md` の「Agent 活用ガイドライン」、`orchestrate` skill |
| ③ | どの作業・agent・ツールがコストのボトルネックか | 「モデル選定原則」表、`check-model` skill |

<a id="sec-1-2"></a>
### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript など `~/.claude` 配下のファイルから別経路で取り込み、テレメトリと突合する。何を取り込むかは 1-6 の棚卸しを受けて Phase 2 で決める |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

いずれも、第一のゴールで本環境に作り、第二のゴールで LLM ゲートウェイ環境に広げる（§1.4）。

<a id="sec-1-3"></a>
### 1.3 成功基準

成功基準は、ゴールの段（§1.4）ごとに書く。

**第一のゴール（本環境）**

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ読込 / キャッシュ作成 / **思考**トークンと推定コストを集計できる。メインとサブエージェントを分けて集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる
- 問い①〜③ のそれぞれについて、還流先資産の改訂案を根拠データ付きで提示できる。データが足りない問いは「結論保留・継続観測」と明示する

**第二のゴール（LLM ゲートウェイ環境）**

- 第一のゴールの仕組みが LLM ゲートウェイ環境でも動き、両方の環境のデータを同じ観点で集計できる。どちらの環境のデータかを区別できる（区別の方法は Phase 2 で決める。合算して分析するかは §7 #7）

<a id="sec-1-4"></a>

|---|---|---|---|
| 第一のゴール | 本環境（Anthropic 環境） | Phase 0〜6 | Windows ネイティブ・Docker 不要の最小構成で、仕組みを作る |
| 第二のゴール | 職場環境（LiteLLM + Amazon Bedrock。LLM ゲートウェイ環境） | Phase 7 | 第一のゴールの仕組みを職場環境で動かし、差を吸収する |

- **本活動の中と正式リリース物**: 本活動の中（作業指示者以外へ配布できる品質になるまでの試行錯誤）では、取得できる情報量の多い案を優先し、案同士が排他でなければ両方で動作検証・構築する。正式リリース物（作業指示者以外へ配布できる品質にした版）の構成と既定の設定は、これと別に決める（Q1 の回答の ※1 の要旨。[まとめ §5.1](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers)）

  - ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
  - ④ プロンプト本文の事後分類（ルール / LLM。`OTEL_LOG_USER_PROMPTS=1` が前提）
  - ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル
  - 比較結果は次の列の表で整理する（列名: 記載する内容）

    - 長所: 他の候補ではできず、この候補ならできること
    - 短所: 他の候補ならできるが、この候補ではできないこと
    - 前提事項: この候補が成り立つために必要な条件

    - 導入負荷: 仕組みを用意するための作業量
    - 維持負荷: 分類体系の見直しや cc の更新への追従に要る作業量

    - その他: 上のいずれにも当てはまらない事項

<a id="sec-p2-arch"></a>
#### 全体構成

**回答で決まったこと**

- 保存は、本活動では生の JSONL（保存案 S2）と、そこから正規化した SQLite（S1）の 2 層にする（§1.4）。S2 を作るので、DuckDB への依存が入る

**Phase 2 で決める**

- 受信 → 保存 → 補完取込 → 集計 → UI のコンポーネント構成とプロセス構成（1 プロセスにまとめるか分けるか）
  - 受信は logs・metrics に加えて traces も受け、span を保存する（logs・metrics に出ない API 呼び出しを集計に含めるため。「分析指標」）
  - UI は、画面案 D1 / D2 のどちらもつなげる形で仮置きにする（方式は Phase 5 の着手時に選ぶ）
- 実装言語と依存の最小化（Node.js のまま依存を減らすか、受信・保存を Java で書くか。J-13）。依存パッケージの一覧（DuckDB を含む）を設計書に載せる
- 正式リリース物の保存の構成（S1 だけ・S2 だけ・2 層。[まとめ §3.1](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-1)）
- 正式リリース物の思考案（T1 だけか、T2 も残すか。V-2b の結果で決める。[まとめ §3.3](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-3-3)）。設計の承認までに V-2b が終わらなければ、正式リリース物は T1（Claude の推奨）で設計し、T2 を足すかは V-2b の結果が出た時点で決める（既定の案）。本活動では T1 と T2 を両方作るので、どちらの場合も本活動の作業は止まらない
- 第三のゴール（WSL + Docker）で作り直しにならないよう、設定や保存先のパスを環境に依存させない

<a id="sec-p2-model"></a>
#### データモデル

**Phase 2 で決める**

分析用スキーマを決める。粒度は API リクエスト単位を基本とし、プロンプト・セッション・作業分類へ集約する。既定の案は次のとおりである。

- metrics とイベントの `query_source` の値の体系の違いを吸収する
- v2.1 R-6（トークン 4 種は別々に集計）、v2.1 R-9（`agents_view` を除外）、v2.1 R-14（詳細ベータトレースは使わない）を反映する
- 列名は cc の元の名前（`input_tokens`・`cache_read_tokens` 等）を主とし、GenAI semconv の名前は対応表で持つ
- 総入力（下の「分析指標」の定義）は派生値として、cc の生の値とは別の列に持つ（`input_tokens` はキャッシュの読み書き分を含まない）
- サブエージェントの `effort`・`model` は `api_request` の値を正とし、agent の frontmatter から推定しない（呼び出しごとの `effort` と Mod による model の上書きがある）

次の 5 点を決める。

- `session.id` を対応表で `gen_ai.conversation.id` に写すか、cc の値に寄せるか（サブエージェントの span では値が違う）
- 版で増える属性とイベント: 既知のものだけを固定の列にするか、未知のものも残すか。イベントは版で増える（2.1.307 で `claude_code.safety_event` が加わった。[1-9 §2](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D56）ので、受信・保存は知らない `event.name` も落とさずに保存する（既定の案）
- TTL 別の cache 書き込み（`cache_creation_5m_tokens`・`cache_creation_1h_tokens`）を使い、TTL 別の単価で費用を計算するか
- 問い① の compact の集計で、アイドル時の compaction（放置による compact）を分けるか
- Mod の記録を使うか: `turn.step`（API リクエストごとの `e.agentId` と usage。サブエージェントの個体をリクエスト単位で分ける材料）、`turn.complete`（turn ごとの合計）、`$.session.usage()`（文脈の使用率とプランの上限の割合。OTel に無い）。OTel と結ぶ鍵は、プロンプト単位の `prompt_id` だけである（[1-1 §10](../01.基礎調査/01.実データ確認/調査報告書.md#sec-10)）

1-7 の未確認事項（`ttft_ms` の測定点など）と設計判断は 1-7 §10 にある。

<a id="sec-p2-tag"></a>
#### 作業分類タグ

**回答で決まったこと**（§7 #6）

- 本活動では、タグ案 L1 と L2 を両方作り、本環境で両方動かす。目的は本活動中の動作検証で集める情報を最大にすることで、どちらを推奨するかの裁定とは別である。J-12・J-15 は、L1 の動きに関わる裁定である（2026-10-24 に裁定済み）
- Phase 2 以降の本環境では、`OTEL_LOG_USER_PROMPTS=1` にする（L2）
- 正式リリース物の設計書と既定の設定で `OTEL_LOG_USER_PROMPTS=0` にすることには問題は無い（※2）。`=0` で動くタグ案は L1 か ① だけで、Claude の推奨は L1 である
- L2 は、デバッグモードのような位置づけか、非公開の機能として作る（※2）

**Phase 2 で決める**

- 分類体系（初期のカテゴリ一覧）、ラベルが付かなかった場合（付与漏れ）と、どの分類にも当てはまらない場合（該当分類なし）の扱い、分類体系の見直し手順
- L2 のデバッグモード（※2）で何を切り替えるか: 本文の記録（`OTEL_LOG_USER_PROMPTS`）、事後分類の実行、L2 のラベルの集計への出力のどれを含めるか。本環境では `OTEL_LOG_USER_PROMPTS=1` にするので、本環境で切り替えの対象に残るのは後の 2 つである
- L1 と L2 のラベルの持ち方（既定の案: 本活動では両方を並べて比べるので、別の列で持つ。「[データモデル](#sec-p2-model)」）
- 候補 ② の実装手段（command hook か Claude Mods か）: 比べるときは、command hook も組み込み Mod の状態と plugin の構成をそろえて測る（`-p` の Mod の上乗せは、組み込み Mod の有効・無効で分かれる。C-3c）。plugin で配る場合は、同じ名前の plugin を重ねない（D32）
- cc が自分で始めたターン（scheduled task、background subagent の報告、他セッションからのメッセージ）: ラベル「自動」を付けて残す。判定できないターンには `unknown` を付け、人間のプロンプトと同じ規則では分類しない（J-15 の裁定）
- hook の書き方: 既定の案は下の「[L1 の hook の既定の書き方](#sec-p2-l1-hook)」
- skill・カスタム slash command を使うターン: L1 のルール分類は、hook が受け取る打ったままの行（`/skill名 引数` の形）を見る。command の名前・引数で分けるために `UserPromptExpansion` hook を材料に足すかを決める。利点は、hook の側で command の名前でラベルを書けることである。費用は、利用者が command を打った経路のプロンプトで hook が 1 つ増えることで、所要時間が J-12 の基準に入り、失敗の扱いも 1 つ増える（モデルが Skill ツールを呼ぶ経路では、この hook は動かない）。hook 入力の `prompt_id` の一致は Phase 3 で確かめる
- タグ付けの hook 自身の所要時間を記録する仕組みと記録の仕方: 日常のセッションには hook ごとの時間を示す debug log の行が無いためで、Phase 3 の J-12 の判定に使う

**Phase 3 の結果で決める**

- cc が自分で始めたターンの判定規則: Phase 3 で hook 入力と `user_prompt` の中身（`prompt_id` が付くか、`prompt.id` と一致するか）を確かめてから決める。Mod を使う場合は、`turn.start` の `agentId` と、`session.receive` の `e.origin.kind`（`task-notification`・`scheduled-trigger`・`peer` など）も判定の材料にする（[1-3 §4](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-4)）

<a id="sec-p2-metrics"></a>
#### 分析指標

**Phase 2 で決める**

指標の例は、作業分類 × モデル × effort ごとのプロンプトあたりトークン・コスト、思考トークン比率、キャッシュヒット率、所要時間である。問い①〜③ 用に、compact 前後の input 系トークンとコスト、サブエージェント比率、ツール結果のサイズも扱う。input 系の定義は次のとおりとする（イベントでは `input_tokens`・`cache_read_tokens`・`cache_creation_tokens`、metrics では `type` の `input`・`cacheRead`・`cacheCreation` を使う）。

- キャッシュヒット率 = cache_read /（input ＋ cache_read ＋ cache_creation）
- 総入力 = input ＋ cache_read ＋ cache_creation
- 期間やセッションで集約するときは、合計の比（cache_read の合計を総入力の合計で割る）とする（案）

問い①・② のために、次の 2 つも設計する。

- 問い② の品質の指標: 何をもって「品質を保った」とするか。テレメトリでは測れない
- 問い① の `/clear` 前後のセッションの結び付け: `/clear` の後はセッション ID が変わる。`SessionStart` hook の `source=clear` と時刻の隣接が候補（見込み。Phase 3 で確認）

モデル間の比較とコストの集計では、次の点を扱う。

- system prompt の交絡: モデルの世代で既定の system prompt が違う。比較実験では `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` を固定するか、交絡として注記する
- 見なし費用: 費用は、API リクエストごとのトークン数と単価表から計算する見なし費用で集計し、`cost_usd` は検算と参考に残す（既定の案。別の案との比較は[承認と保留](#sec-approval)の「新しく決めること」）
  - 計算: `api_request` の `input_tokens`・`output_tokens`・`cache_read_tokens`・`cache_creation_tokens` に、`model` と `speed`（fast mode かどうか。仕様別紙 §1）で選んだ単価を掛ける。cache 書き込みの TTL 別の内訳（`cache_creation_5m_tokens`・`cache_creation_1h_tokens`。仕様別紙 §1）を使う場合は、その TTL の単価で計算する（使うかは「[データモデル](#sec-p2-model)」で決める）。内訳を使わない場合と、内訳の無い行（2.1.300 より前の版の行など）は、その行の課金の形と要求の区分（主の会話か、それ以外か）での既定の TTL（仕様別紙 §1）の単価で計算し、そう計算したことを注記する（既定の案）。logs と結合できなかった span も、span のトークン数から同じ表で計算する（下の「span の費用」）
  - 理由: `cost_usd` は、cc が Anthropic の料金で換算した推定値である（managed settings の `modelPricing` が配られていれば、その料金で換算する。仕様別紙 §5）。本環境（定額の契約）では実費ではなく、Bedrock 環境の請求とも単価の組が違う（[§5.1](#sec-5-1)・[§5.2](#sec-5-2) の `cost_usd` の行）
  - 単価表: コードに埋めず、データとして持つ。行は、単価の組（Anthropic の API の料金と、職場の実単価（分かってから足す。承認と保留の表の先送りの行））× モデル × トークンの種類（入力・出力・cache read・cache write の 5 分と 1 時間）である。行ごとに出典と確かめた日を持ち、改定は版を足して残す（過去の期間を当時の単価で計算し直せる）
  - 設計で決める 4 点: 単価の組をレコードに当てる鍵（環境の区別。職場の `model` は Anthropic の形の ID になる見込みで、ゲートウェイの先の推論プロファイルなどを読み取れないので、職場の組は設定で与える。課金の形（定額の契約の枠内か、API キー・クラウド提供元か。TTL 別の内訳の無い行の既定の TTL を選ぶのに要る）も同じ設定で与え、要求の区分（主の会話か、それ以外か）は `query_source` から付ける。利用枠を超えて usage credits を使った分は行ごとに区別できないので、注記する）、`model` と表のモデルの結び付け（日付付きの ID やゲートウェイの別名などの正規化）、表に無いモデルの扱い（未計算として件数を数え、費用に含めずに注記する）、表の保存形式と置き場所
  - 単価の値: Anthropic の単価は、下の「単価の出典確認」のときに、表に載せるモデルの分を料金ページで確かめ、Phase 3 の検算までに表に入れる
    - 職場の実単価: 契約によって公開の料金と違う（作業指示者の情報、2026-10-24）ので、ゲートウェイの記録などで確かめる。確かめ方は Phase 7 の着手前に作業指示者と決める（承認と保留の表の先送りの行）。それまで、単価表は Anthropic の単価の組だけで進め、職場の費用の見積もりは出さない
    - 職場の組織が managed settings の `modelPricing` を配っていれば、職場の `cost_usd` は組織が設定した単価での換算になり（仕様別紙 §5）、職場の実単価の手がかりになる【推定】（組織の単価が実単価と同じかは分からない。配っているかは Phase 7 のモデル名の渡り方の行で確かめる）
  - 費用に効くほかの要素: 単価の出典確認のときに、長いコンテキストの段階単価、fast mode の単価、data residency の料金の倍率、web search などの 1 回ごとの料金などを洗い出し（仕様別紙 §5 の `cost_usd` の行）、表に持つ。表に持てない要素は、集計の漏れとして注記する
  - 比べ方: モデル間の比較は、比率（例: Haiku を 1 とした倍率）でも示す。本環境では、費用より精度・時間・使用量の上限の消費を主に比べ、見なし費用は、職場の実単価が分かってから職場の費用の見積もりに使う。cache read の割合が費用を大きく左右するので、職場の費用の見積もりには、ゲートウェイの先でプロンプトキャッシュが効くかを前提として明示する。職場でプロンプトキャッシュが効いているかは、[Phase 7](#sec-p7) の確かめることの表の V-10 の行（`cache_read_tokens` が 0 でない `api_request` があるか）で見る
    - cache 書き込みの TTL: 既定の TTL は課金の形と要求の区分で違う（主の会話は、定額の契約の枠内では 1 時間、API キー・クラウド提供元と、使用量の上限を超えて usage credits を使う分では 5 分。それ以外の要求は、サーバーが決める一部の補助の要求を除いて、どちらでも 5 分。仕様別紙 §1）。職場（ゲートウェイの先が Bedrock）は、`promptCacheTtl` などを設定していなければ 5 分の見込み【推定】（認証の方法が仕様別紙 §5 の分岐 T・K の場合。分岐 L なら主の会話は 1 時間になりうる。Phase 7 の V-10 の行で確かめる）。本環境の記録から職場の費用を見積もるときは、cache 書き込みを職場の TTL の単価で計算し直す（TTL 別の内訳を合計して掛け直す）。TTL が短いと cache の切れ方も変わるので、本環境の cache read・write の量は職場の量の目安にとどまる【推定】
  - 検算: Anthropic の単価の組で計算した見なし費用を `cost_usd`（整数の `cost_usd_micros` もある）と比べ、計算を確かめる。Phase 3 で、下の「単価の出典確認」の、`cost_usd` が段階単価と TTL 別の単価を反映するかの確認と同じ回に行う。合格の基準は、[Phase 3](#sec-p3) の見なし費用の検算にある
- 単価の出典確認: コスト集計の設計の前に、料金ページで出典を確かめる。対象は、Haiku 5.5 の単価、Sonnet 5.5 の cache read の単価、Sonnet 5 の単価、TTL 別（5 分・1 時間）の cache 書き込みの単価の 4 つである（J-17）。見なし費用の単価表に載せる単価と、費用に効くほかの要素も、このときに確かめる（上の「見なし費用」）。`cost_usd` が段階単価と TTL 別の単価を反映するかは Phase 3 で確かめる
- logs・metrics に出ない API 呼び出し（起動時の `quota_check`、ターン終了後の `side_query`、自前の auto mode の分類器リクエスト）: logs・metrics だけでは全 API 呼び出しを数えられないので、traces の `llm_request` span を集計に含める（traces の有効化は「有効化と常駐」）。含めれば `quota_check` 以外は漏れない見込みである（確かめた範囲は 1-8 §7.3.4）
- 集計の正本と二重計上の除き方: 下の「[集計の正本と二重計上の除き方](#sec-p2-dedupe)」
- span の費用: span には `cost_usd` が無いので、logs と結合できなかった span（span だけに出るリクエストを含む）の費用は、見なし費用と同じ単価表で、span のトークン数から計算する（自前の分類器リクエストは既定で Sonnet 5 で、キャッシュ書き込みが大きい）
- traces の版ごとの確認: traces は beta 機能で、版によって形が変わりうる。cc の版を上げたら、span の名前と、集計に使う属性（トークン数、model、`query_source_safe`、`client_request_id`・`request_id`）を確かめる（「バージョン追従」の差分確認の手順に含める）
- `quota_check` の漏れ: どの信号（logs・metrics・traces）にも出ないので、集計の漏れとして注記する（セッションごとに 1 回で、トークン量は不明）。課金・トークン量への影響は Phase 3 で確かめる

<a id="sec-p2-enable"></a>
#### 有効化と常駐

**回答で決まったこと**

- 取りこぼしの無い仕組みのためなら、どの環境変数も常時有効にしてよい。内容を記録する 5 つの変数（`OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_ASSISTANT_RESPONSES`・`OTEL_LOG_TOOL_DETAILS`・`OTEL_LOG_TOOL_CONTENT`・`OTEL_LOG_RAW_API_BODIES`）はその例である（応答の本文も）
- 他のリポジトリの作業に悪影響を与えうるもの（例: `OTEL_LOG_RAW_API_BODIES` は、リクエストごとに会話履歴の全体をディスクに書く）は、ユーザ settings に置かず、起動するプロセスの環境変数（ランチャ・スクリプト）で渡す

**Phase 2 で決める**

- ユーザ settings の `env` の中身（v2.1 §5.1 を下敷きにする。属性の数の上限を下げる場合の注意は仕様別紙 §4）と、プロセスのスコープで渡す変数の分け方。5 つの変数と exporter の変数は project / local settings では無視される（docs）ので、置き場所はユーザ settings（すべてのリポジトリに効く）か、プロセスのスコープになる。ユーザ settings に置くものは、Claude が手順を書き、作業指示者が設定する
- プロセスのスコープで渡す変数は、ランチャを通さずに起動したセッションには効かない。思考案 T2 の経路 (ii) を日常のセッションのどこまでに効かせるかを、「操作を増やさない」（§1.3）とあわせて決める
- 変数の置き場所を決めるときは、上の T2 のほかに次の制約を当てる
  - `OTEL_LOG_USER_PROMPTS` は L2 の前提である。プロセスのスコープに置くと、ランチャを通さずに起動したセッションでは本文が記録されず、L2 で分類できない
  - `OTEL_LOG_ASSISTANT_RESPONSES` は、未設定なら `OTEL_LOG_USER_PROMPTS` の値に従う（docs）。正式リリース物の既定を決めるときは、応答の本文の扱いを `OTEL_LOG_USER_PROMPTS` と別に明示するかも決める
  - Windows PowerShell 5.1 のスクリプトで環境変数を設定して cc を起動すると、OTel の設定が届かなかった（PowerShell 7 経由では届いた。[1-1 §7](../01.基礎調査/01.実データ確認/調査報告書.md#sec-7)）。ランチャ・スクリプトで渡す変数は、届いたことを確かめてから使う（[まとめ報告書 §2](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-2) の「有効化と常駐」）
- traces の有効化（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` と traces の exporter の設定）: 集計に traces の span を含める（「分析指標」）ので、`env` に入れる。v2.1 §5.1 の基本セットは metrics と logs の exporter だけで、traces を含まない。traces を有効にした設定と届いた span は、[1-1 §1](../01.基礎調査/01.実データ確認/調査報告書.md#sec-1)・[§6](../01.基礎調査/01.実データ確認/調査報告書.md#sec-6) にある
- 受信サーバの起動方法（手動 / ログオン時の自動起動。§7 #3）
- 受信サーバが止まっているときの cc 側の挙動

<a id="sec-p2-privacy"></a>
#### データ保全とプライバシー

**回答で決まったこと**

- 収集したデータ（OTel の受信の記録、raw body の file モードの出力、検証の記録）は、repo の外の `%LOCALAPPDATA%\local-mini-otel\` の下に置く。毎回同じ場所にし、クラウド同期の対象のフォルダには置かない。repo にはコミットしない
- 本活動では、プロンプト本文と応答の本文を記録してよい。記録したものは、本活動が終わったら、または不要になったら削除する
- 正式リリース物の既定の設定で、本文の記録を OFF（`OTEL_LOG_USER_PROMPTS=0`）にすることには問題は無い（Q4 の回答の ※2）

**Phase 2 で決める**

- 保持期間、圧縮（§7 #5）、バックアップ
- `OTEL_LOG_USER_PROMPTS` 以外の内容を記録する変数の、正式リリース物の既定

既定の案は次のとおりである。

- 本文のマスク・削除・保存量の見積もりは、`user_prompt` イベントの `prompt` と `prompt_text` の 2 つに当てる（OTel Collector で本文を消すときも、両方の属性を指定する。docs には `attributes` processor の例 `attributes/drop-prompt-text` がある）
- 詳細ベータトレースは使わない（v2.1 R-14）。使うことにした場合は、本文を含む `system_reminders` 属性と `claude_code.system_prompt` イベントもマスク対象に加える

補完取込の対象の transcript は、cc 2.1.300 から、API リクエストごとの system prompt・tools・parameters を新しい記録型で含む。2.1.308 以前の transcript には、長い tool 出力のプレビューが絵文字の途中で切れ、`jq` で読めない行が入りうる（2.1.309 で直った。[1-9 §2](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D58）。次の 4 点を決める。

- 新しい記録型を読むか（system prompt・tools の全文を取り込むか。思考トークンの突合には要らない）
- 取り込む場合のマスクの範囲
- 保存量の見積もり: 取込が対象にする版の transcript で見積もる（2.1.304 から、auto mode の `api-request` の記録が小さくなった。[1-9 §3.3](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-3-3)）
- 取込が未知の記録型や読めない行に出会ったときの扱い。読めない行は、次の 2 種類を数え、どちらも行を飛ばして取込を止めず、件数を取込の記録に残すのを既定の案にする（記録の置き場所は Phase 2 で決める）
  - JSON として解析できない行
  - 2.1.308 以前の transcript の、長い tool 出力のプレビューが絵文字の途中で切れた行（孤立したサロゲートのエスケープを含む行）。Node.js の `JSON.parse` では読めてしまうので、解析した文字列に孤立したサロゲートが残るかを別に調べて数える（数え方は [1-9 §5](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-5)）

<a id="sec-p2-version"></a>
#### バージョン追従

**Phase 2 で決める**

- cc の属性・transcript 形式が変わったときに検知する仕組み（`service.version` を使う）
- 版を上げるときの docs・changelog の差分確認の手順と担当: 手順は [1-8 §1](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-1) の「差分の取り方」と同じ形にする。docs だけでなく changelog を読み、実機の属性集合を前の版と比べる（docs の span の属性の表は、cc 2.1.300 で加わった属性を載せていない）。traces の span の名前と集計に使う属性も、この手順で確かめる（「分析指標」）
- 版をまたぐ集計の区切り: 記録される値・記録の完全性・記録される属性が変わった版があるので、版をまたいで集計するときは `service.version` で区切る。区切る版（2.1.287・2.1.288・2.1.291・2.1.293・2.1.299〜2.1.302・2.1.304・2.1.306・2.1.307・2.1.309。2.1.304 以降は [1-9 §2](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D56〜D58・D62）と各版の変更は、まとめ報告書 §2 の「データモデル」と 1-8・1-9 にある。compact の前後を比べるとき（問い①）は、2.1.287 の前後で区切る（それより前は、resume・compaction の後にフォルダの CLAUDE.md が二重に付く不具合があり、入力トークンが本来より大きく出ている可能性がある）

#### L1 の hook の既定の書き方

タグ案 L1 のタグ付けの hook（`UserPromptSubmit`）は、次の書き方を既定の案とする。Phase 2 の設計担当はこの既定を覆してよい。既定は Git Bash の有無に依らないので、Phase 2 は Phase 3・Phase 7 の結果を待たずに決められる。

- exec 形式（`command` と `args`）か `"shell": "powershell"` で書き、Git Bash の有無に依らないようにする。exec 形式を docs が勧めるのは、1 つの `.exe` を動かす hook の場合である（`.cmd`・`.bat` は含まない）
- PowerShell で書く場合は、スクリプトを UTF-8 + BOM で保存し、標準入力を UTF-8 として読む（本環境の Windows PowerShell 5.1・PowerShell 7 の実測。cc が hook を起動したときは未確認で、PowerShell の hook を採る場合に Phase 3 で確かめる。[1-3 §4](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-4)）
- スクリプトが自分で終える経路は、終了コード 0 で終える（例外を捕まえて 0 を返し、失敗の処理に終了コード 2 を使わない）。`UserPromptSubmit` の hook が終了コード 2 で終わると、プロンプトが Claude に届かない。PowerShell で動く hook が終了コード 2 で止めない不具合は 2.1.309 で直ったので、2.1.309 以降は PowerShell の hook もそうなる（それより前の版では止めないことがありうる。いつの版からかは changelog に無い。changelog 2.1.309、docs。[1-9 §2](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D60）。2 を使わなければ、版で挙動が変わらない。PowerShell で書く場合は、どの失敗（スクリプトが見つからない・例外・タイムアウト）でも終了コードが 2 にならず、プロンプトが Claude に届くことを、Phase 3 の L1 の試作の hook で確かめる（[1-9 §5](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-5)）
- `"onFailure": "continue"` を明示し、fail-open の意図を設定に残す。`onFailure` が扱う失敗は、起動できない・0 と 2 以外の終了コード・タイムアウトなどで、終了コード 2 には効かない（docs）ので、上の終了コード 0 の作りの代わりにはならない。`"onFailure": "block"` は付けない（ラベル付けの失敗などで、利用者のプロンプト・操作を止めない）。docs が PowerShell の guard hook に勧める `"onFailure": "block"` は、失敗で止める hook 向けで、L1 には当たらない
- ラベルは `prompt_id` をキーにして書き、同じ `prompt_id` の後の書き込みが前を上書きする形か、集計で重複を除く形にする（2.1.308 以前の対話では、ctrl+enter で同じプロンプトの hook がやり直されえた。changelog 2.1.309。D63）
- Mod で実装する場合は、`.catch` を付けない。Mod は、`.catch` の無い hook が失敗すると飛ばして進む（fail-open）。`.catch` は失敗時に止める側の手段である（docs。[1-3 §4](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-4)）。plugin（Mod を含む）で配る場合は、受け渡しの失敗による拒否がプロンプトに及ぶかを Phase 3 で確かめる（Mod の既定の素通しも `.catch` も hook の関数の失敗を扱うもので、受け渡しの失敗は防げない。settings に書く command hook には及ばない見込み）
- background の process を起こさない（起こすと tool call が block されうる。docs）
- skill の frontmatter に置かない（そこに書いた hook は、その skill を呼んだ次のプロンプトから動くので、その skill を呼んだプロンプトにラベルが付かない）
- plugin で配る場合は、marketplace から入れる形にし、skills のフォルダ（`~/.claude/skills/`・`.claude/skills/`）に plugin を置かない。managed settings の `strictPluginOnlyCustomization` がどれかの種類をロックすると、skills のフォルダの plugin は hook・Mod ごと、エラー無しで読み込まれない（`strictKnownMarketplaces` の allowlist に skills のフォルダが無いときも同じ）。`hooks` をロックすると、settings に書く command hook も動かず、plugin の hook は動く（docs。[1-3 §2](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-2)。ロックの下で skills のフォルダの plugin が読み込まれないことは、1-9 の D63 の docs の差分にもある）

docs の根拠（`onFailure` の扱い、終了コード 2、Git Bash の無い Windows の例外と直し方）は仕様別紙 §3 に、変更の版は [1-8 §8.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D44・D46 と [1-9 §2](../01.基礎調査/09.cc2.1.304差分の確認/調査報告書.md#sec-2) の D60・D63 にある。この書き方の試作の hook が職場で動くかは、Phase 7 で確かめる（試作の hook の仕様は [V-ID 別紙 §2 の職場の表の前](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2-l1-hook)）。

<a id="sec-p2-dedupe"></a>
#### 集計の正本と二重計上の除き方

本体のリクエストは、logs の `api_request` と traces の `llm_request` span の両方に出る。両方を足すと二重に数えるので、Phase 2 は集計の正本を決める。選択肢は、traces の span を正本にするか、logs の `api_request` を正本にして logs に無い span だけを足すかである。

後者を採る場合の突き合わせの規則（既定の案）は次のとおりである。鍵は環境ごとではなく、リクエストごとに選ぶ。同じ環境の中でも鍵の付かないリクエストがあるためである（non-streaming fallback で再試行したリクエストには、直接接続でも `client_request_id` が付かない。docs の Monitoring ページの「Event correlation attributes」の表の `client_request_id` の行）。

- 1 段目: `api_request` と span を、`client_request_id` の値が一致するもので結合する
- 2 段目: 1 段目で結合できなかったものを、`request_id`（span と `api_request` に同名の属性がある）の値が一致するもので結合する。`client_request_id` が片側にしか無いものや、両側にあっても値が合わないものも、ここで `request_id` を試す
- 結合できた組: 1 件と数え、span に無い logs の属性（作業分類の鍵の `prompt.id`、`skill.name`・`agent.name`、`cost_usd` など）を付ける
- 結合できなかった span: 1 件と数え、費用は見なし費用の単価表から出す（logs の属性は付かない。「分析指標」の span の費用）。作業分類は、logs に出ないと分かっている種類（ターン終了後の `side_query`、自前の auto mode の分類器のリクエストなど。「分析指標」の logs・metrics に出ない API 呼び出し）を「未分類（logs に出ない呼び出し）」とし、鍵の欠けで結合できなかった span とは別に数える。それ以外は「未分類（突き合わせ不可）」にする。種類は `query_source_safe` で見分ける（本環境で観測した値は、自前の分類器のリクエストが `auto_mode`、ターン終了後の `side_query` が `agent_classifier` である。[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の、分類器の行と logs・metrics に出ない API 呼び出しの件数の行）
- 結合できなかった `api_request` の行: 件数・トークン・費用に足さず（同じリクエストの span と二重に数えるおそれがあるため）、行数を、結合できなかった span のうち logs に出ないと分かっている種類を除いた数と比べる（span が届かなかったリクエストがあるかを見る材料にする）

この規則で鍵の欠けに耐えるのは、件数・トークン数・model など span にある属性の集計までである。作業分類（`prompt.id` による）と `cost_usd` は、結合できたリクエストに限られる。span が届かなかったリクエストは、この規則ではどこにも数えられない（結合できなかった `api_request` の行数として記録だけする）。span と `api_request` の属性の違いは、[1-7 付録 A.1](../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-a-1) と仕様別紙 §1 にある。

Phase 2 はこの規則までを決める（Phase 3・Phase 7 の結果を待たない）。どの鍵がどれだけのリクエストに使えるかは、受信データの記録で見る。記録の定義は Phase 3（本環境）と Phase 7（職場）で同じで、次のとおりである。

- 分母: 受信した `api_request` の行数
- 鍵ごと（`client_request_id`・`request_id`）の、両側にあり値が一致した行の割合
- どちらかの鍵で結合できた行の割合
- 結合できなかった span の数（受信した span の数に対する割合）。logs に出ないと分かっている種類を除いて数え、除いた数は `query_source_safe` 別に記録する

Phase 7 では、あわせて鍵ごとの、鍵がある件数と無い件数も記録する。LLM ゲートウェイ環境で鍵が付くかは、docs では決まらない（仕様別紙 §5）。職場の件数は手元の記録にだけ残し、報告書には割合か「有・一部・無」で書く。

- **測定の条件**
  - 版の再確認: Phase 3 着手の前に、その時点の最新の cc で版の再確認（1-8・1-9 の追補にあたる。次の番号の報告書に書く）を行い、§2 冒頭の基線を更新する。下の版の下限は、この基線で決まる
  - 版の下限: 測定に使う cc の版の下限は、Phase 3 着手時点の最新の基線の版（§2 冒頭）以降とする（J-18 の裁定。現時点では 2.1.309）。下限は Phase 3 着手時点で一度だけ決め、Phase 3 の途中の反映では上げない（途中で上げると、先に測った値が新しい下限を下回り、判定に使えなくなる）。決めた下限は、PoC 報告書と J-18 に記録する。着手の前に基線の版に回帰が見つかったら（changelog と、着手前の再確認の報告書で確かめる）、下限を自動では上げず、作業指示者に諮る。Phase 3 の途中で、下限より新しい版の属性が要る項目ができたら、その項目にだけ最低版を課す。下限を置く理由と、選択肢との比較は J-18 にある
  - 版ごとの比較: すべての測定で `service.version` を記録する。hook と Mod の上乗せは版で変わり、cc は自動更新で Phase 3 の中でも上がりうる（[1-8 §7.3.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2)・[§8.3.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-2)）。このため、比較は `service.version` ごとに同じ版の値どうしで行い、測定値は測った版でだけ使う
  - 版上げ直後: 版を上げた直後の最初のセッションは測定に使わない。このセッションでは、feature flag で有効になる機能が欠けることがある（flag はそのセッションの中で取得され、次のセッションから効く。docs の「First session after an install or upgrade」）。使った場合は、J-12 の判定の組のキーの permission mode を、hook の入力か `tool_decision`（2.1.301 以降）の `permission_mode` で記録し（`permission_mode_changed` は mode が変わったときだけ出る）、flag で有効になる機能のうち測定に効くもの（アイドル時の compaction など）と Mod の読み込みで、条件がそろっているかを確かめる（[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の版上げ直後の行）
  - 版の検知: cc の自動更新は止めない（更新は次の起動で効く）。測定の前後で `claude --version` を記録する。`service.version` が前のセッションと変わった最初のセッションを「版上げ直後」とみなし、測定の途中で版が変わったら、変わった後のセッションをその比較から除く
  - モデル: エイリアス（`haiku`・`sonnet`）ではなく、完全なモデル ID で指定して記録する（エイリアスの解決先は版で変わる）。基準モデルは用途で分ける。cc 2.1.283・2.1.287 からの継続比較（属性集合・遅延・突合）は Haiku 4.5（`claude-haiku-4-5-20251001`）、auto mode が有効なまま動く条件（auto mode の比較を含む）の基準は Haiku 5.5（`claude-haiku-5-5`）を使う（J-14 の裁定）
  - Remote Control: Claude が起動する対話の計測用のセッション（比較実験）は、Remote Control を切って起動する（切り方と確かめ方は、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の測定の注意と、活動の `CLAUDE.md` の作業時の注意にある）。本環境のユーザ設定は、起動時に Remote Control に接続するためである。J-12 の判定に使う日常のセッションは切らずにそのまま測り、Remote Control の有無・モデル・permission mode・plugin の構成（hook（command hook・Mod）を登録する plugin の集合。OTel の `plugin_loaded` と `hook_registered` で観測する）をプロンプトごとに記録して、条件ごとに集計する。計測用のセッションの値は参照値として並べる（J-19）
  - plugin の構成: Claude が起動する計測用のセッション（probe と比較実験。`-p` と対話）では、plugin の構成を、比べる相手の測定（前回の基線。Phase 3 では着手前の版の再確認の測定）と同じにし、その後に有効になった plugin を、そのプロセスだけ無効にする。前回の基線の plugin の集合は、その測定の `plugin_loaded` の記録（repo の外）から取る。有効なままだと、hook なしの条件にもその plugin の hook が走って版の間の比較ができず、同じ版の中で hook と Mod を比べるときも、並列に走る plugin の hook で command hook の上乗せが隠れる（[1-8 §8.3.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)、J-25）。無効にする手順と確かめ方は、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の測定の注意と、活動の `CLAUDE.md` の作業時の注意にある。日常のセッション（J-19）は無効にせず、上のとおり plugin の構成を記録する
  - J-12 の判定: タグ案 L1 の hook の待ち時間を「許容できる」とする基準は、J-12 の暫定値を使う。判定は、「モデル × permission mode × Remote Control の有無 × plugin の構成（hook を登録する plugin の集合。有無の 2 値ではない）」の組のうち、標本が最も多い組（日常の主な条件）で行い、ほかの組は参考値とする。上乗せに加えて、L1 の hook 自身の所要時間にも同じ基準を当てる（理由は §5.1 の plugin の構成の行）。L1 の hook 自身の所要時間は、日常のセッションでは hook が自分で記録した値（Phase 2「作業分類タグ」）を使う。自分で記録した時間はプロセスの起動を含まないので、計測用のセッションで debug log の hook ごとの行との差を測って記録し、判定では、自分で記録した時間にその差（中央値）を足した値を使う（[1-8 §8.3.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)）。判定が決めるのは、L1 を正式リリース物の既定と職場（Phase 7）の候補にしてよいかである。基準を超えたら、hook の改善（Mod にするなど）か、① だけにするかを諮る。本環境では、基準を超えても L1・L2 とも動かし続ける（本活動中の動作検証で集める情報を最大にするため。確認 4。[まとめ §5.1](../01.基礎調査/99.基礎調査まとめ/報告書.md#sec-5-1-answers)）
- **受信データの記録**: 突き合わせの規則を確かめるため、[集計の正本と二重計上の除き方](#sec-p2-dedupe)の記録の定義の値を取る。記録の仕方は、V-ID 別紙 §2 の本環境の表の、logs・metrics に出ない API 呼び出しの件数の行にある
- **見なし費用の検算**: Anthropic の単価の組で計算した見なし費用を、リクエストごとに `cost_usd`（`cost_usd_micros`）と比べる（Phase 2「[分析指標](#sec-p2-metrics)」の見なし費用）。合格の基準の既定の案は、リクエストごとに一致すること（丸めの差を除く）である。ずれたら、ずれる要素（段階単価・TTL 別の単価・fast mode・`modelPricing`・data residency の料金の倍率（応答の `inference_geo`）・web search などの 1 回ごとの料金（SDK の費用の推定には入る。`cost_usd` にも入る見込み【推定】）。仕様別紙 §5）を特定して記録し、単価表か計算を直す。表で直せないずれ（トークン数から計算できない料金など）は、要素を記録して、その分を検算の比べる対象から外し、見なし費用の漏れとして注記する（「分析指標」の、表に持てない要素の注記と同じ扱い）。手順と記録は [V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の「見なし費用の検算」の行にある。職場の費用の見積もりは、職場の実単価が分かるまで出さない（確かめ方は Phase 7 の着手前に決める。承認と保留の表の先送りの行）
- **判定の目安**: 各確認項目の判定の目安・測り方・標本数は、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の案を出発点にする。タグ案 L1 の hook の待ち時間の判定は、上の「測定の条件」の J-12 の判定のとおりとする
- **成果物**: `app/` 配下の PoC コード、`reports/03.PoC/…/PoC報告書.md`
- **完了条件**: 本環境で確認観点を満たす。L1 の hook の待ち時間の判定（J-12）で、主な組の標本が足りなければ測定期間を延ばし、延ばしても足りなければ、自動では判定せず測定値を添えて諮る（J-12 の暫定値）。基準を超えた場合の扱いは、上の「測定の条件」の J-12 の判定のとおりとする。起こし方を決めていない項目（plugin の hook の受け渡しの失敗、アイドル時の compaction など）は、期間内に観測できなければ「未観測」と記録して閉じてよい（V-ID 別紙 §2）。満たさない場合は Phase 2 へ戻す判断材料をそろえる

- **結果の取りまとめ**: 結果は作業指示者が記録様式に書き、Claude Code が報告書に取りまとめる。記録様式と、件数を手元の記録にだけ残す規則は V-ID 別紙 §2 にある。plugin の構成と L1 の hook の時間は、PoC の受信データと L1 の hook の記録に入る。このため、この 2 つの記録で職場の手作業が増えるのは、受信データの提出と、L1 の試作の hook の導入と取り外しに限られる。受信データの提出の形（何を、どの形で渡すか）は、Phase 7 の手順書で記録様式（V-ID 別紙 §2）とあわせて決め、件数を手元の記録にだけ残す規則に合う形にする。報告書には plugin の名前を書かない
- **差の吸収**: 確認の結果で、Phase 2 の備え（環境ラベル、突き合わせの鍵、思考案 T2、縮退運用）を調整し、要れば Phase 2〜5 の成果物を直す。設計の変更が要る場合は Phase 2 へ戻す。§7 #7・#8 を判断いただく
- **成果物**: `reports/07.職場環境対応/…`（案。職場環境確認手順書と確認結果、報告書）と、差の吸収の修正。フォルダは今は作らない
- **完了条件**: 職場の日常の利用で、操作を増やさずにデータが溜まる状態が 1 週間程度続く（作業指示者が確かめる）。両方の環境のデータを同じ観点で集計でき（作業分類は、鍵で結合できた範囲。鍵が付かない場合の扱いは、Phase 2「[第二のゴールへの備え](#sec-p2-goal2)」の Phase 7 の結果で決める項目による）、どちらの環境のデータかを区別できる
- **打ち切りの条件**: 職場で動かせないと判断する条件を、Phase 7 の着手前に作業指示者と決める
