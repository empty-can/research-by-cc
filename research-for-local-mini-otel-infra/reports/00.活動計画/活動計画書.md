<a id="sec-1"></a>
## 1. ゴール

**背景**: cc の費用対効果を高めたい。ステータスラインで見られるモデル・コンテキストサイズ・総トークン量だけでは、effort や作業の性質ごとのトークン消費（思考トークンを含む）が分からない。そこで、これらを cc の OTel テレメトリで収集・分析できるようにする。

<a id="sec-1-1"></a>
### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

あわせて、次の 3 つの問いに分析で答える（v2.1 §1.2）。答えは、右列のルート資産の改訂案として出す。還流先のない分析はしない。

| # | 分析で答える問い | 分析結果の還流先（ルート資産） |
|---|---|---|
| ① | `/compact` と `/clear` をどう使い分けるとコストを抑えられるか | compact / clear の運用指針（ルート `CLAUDE.md`、または `pre-compact` skill） |
| ② | Skill・workflow・カスタムサブエージェントによるオーケストレーション（Opus から Sonnet への移譲を含む）で、品質を保ったままどこまでコストを下げられるか | ルート `CLAUDE.md` の「Agent 活用ガイドライン」、`orchestrate` skill |
| ③ | どの作業・agent・ツールがコストのボトルネックか | 「モデル選定原則」表、`check-model` skill |

<a id="sec-1-2"></a>
### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript など `~/.claude` 配下のファイルから別経路で取り込み、テレメトリと突合する。何を取り込むかは 1-6 の棚卸しを受けて Phase 2 で決める |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

いずれも、第一のゴールで本環境に作り、第二のゴールで LLM ゲートウェイ環境に広げる（§1.4）。

<a id="sec-1-3"></a>
### 1.3 成功基準

**第一のゴール（本環境）**

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ読込 / キャッシュ作成 / **思考**トークンと推定コストを集計できる。メインとサブエージェントを分けて集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる
- 問い①〜③ のそれぞれについて、還流先資産の改訂案を根拠データ付きで提示できる。データが足りない問いは「結論保留・継続観測」と明示する

**第二のゴール（LLM ゲートウェイ環境）**

- 第一のゴールの仕組みが LLM ゲートウェイ環境でも動き、両方の環境のデータを同じ観点で集計できる。どちらの環境のデータかを区別できる（区別の方法は Phase 2 で決める。合算して分析するかは §7 #7）

<a id="sec-1-4"></a>
### 1.4 前提・制約とスコープ

ゴールは次の 3 段に分ける（J-27）。

| 段 | 対象環境 | 扱う Phase | 要点 |
|---|---|---|---|
| 第一のゴール | 本環境（Anthropic 環境） | Phase 0〜6 | Windows ネイティブ・Docker 不要の最小構成で、仕組みを作る |
| 第二のゴール | 職場環境（LiteLLM + Amazon Bedrock。LLM ゲートウェイ環境） | Phase 7 | 第一のゴールの仕組みを職場環境で動かし、差を吸収する |
| 第三のゴール | WSL + Docker 環境 | 次の活動 | WSL + Docker 環境に対応する |

段は直列に進める。第一のゴールの設計には、第二のゴールへの備えを含める（Phase 2「第二のゴールへの備え」）。

- **対象環境**
  - 本環境: Anthropic 直接契約のアカウント。Windows 11 ネイティブ（Docker / WSL は使わない）。職場環境と並べて呼ぶときは「Anthropic 環境」と書く
  - 職場環境: cc → 社内 LLM ゲートウェイ（LiteLLM。`ANTHROPIC_BASE_URL` で指定する Anthropic 形式の接続で、cc の Bedrock モードは使わない。J-26）→ Amazon Bedrock。Windows。OTel 設定（ユーザ settings の `env`）は作業指示者が変更できる。実機確認は Phase 7 で作業指示者が行う
  - 職場環境の呼び分け: 職場環境の性質のうち、cc から見た接続の形に依る事柄を「LLM ゲートウェイ環境」、ゲートウェイが LiteLLM であることに依る事柄を「LiteLLM 環境」、ゲートウェイの先の Amazon Bedrock に依る事柄（実請求、提供されるモデルなど）を「Bedrock 環境」と書く。本環境と並べて呼ぶときは「LLM ゲートウェイ環境」と書く。職場の PC・社内の管理・作業指示者が確かめる場としての意味では「職場環境」と書く。cc はこの形のゲートウェイを Claude API として扱い、ゲートウェイの先を知らない（docs）ので、本書は cc の Bedrock モード（third-party provider）の docs の差を LLM ゲートウェイ環境に当てない（J-26）。ゲートウェイへの認証の方法は未確認で、Phase 7 の職場環境の確認の最初に確かめる（認証の方法で結論が分かれる項目は仕様別紙 §5）
- 受信サーバ・データシンク等は、ローカルで起動できる OSS を積極的に使ってよい
- 分析 UI は、レイアウトを度々変えたくなる見込みがあるため、Node.js の自作ダッシュボードを有力候補とする（OSS との比較は 1-5）
- **スコープ外**: チーム・組織単位の集中収集（本活動は個人ローカル用）、クラウド・SaaS の監視基盤（Datadog 等）への送信

### 2.1 思考トークンの取得経路（1-2 で選ぶ）

| 経路 | 内容 | 利点 | 懸念 |
|---|---|---|---|
| (i) transcript 突合 | transcript の usage を取り込み、`request_id` で OTel の `api_request` と突合する | 内容記録フラグが不要。過去分にも使える | transcript 形式は cc 内部仕様でバージョンごとに変わり得る。取込の仕組みと頻度を決める必要がある（§5.1） |

v2.1 は (i) を主、(ii) を補助としている。

### 2.2 職場環境の不明点（Phase 7 で確認）

職場環境の不明点は、第二のゴールの Phase 7 で作業指示者が確かめる。不明点は、ゲートウェイへの認証の方法、思考トークンの内訳、社内プロキシによる改変、ループバック宛て送信の可否、transcript の `requestId`、Claude Mods と command hook の可否、Git Bash の有無、auto mode の分類器のリクエストの扱いである。確かめ方とその結果で決まることは [Phase 7](#sec-p7) に、docs の差と認証の方法の分岐は[仕様別紙 §5](【別紙】公式仕様の調査結果.md#sec-5) にある。

**方法**

- 1-1: `console` exporter か簡易受信で実セッションを流し、metrics / events / traces を記録する（手順は v2.1 §8.1。出力先は V-11(b) #22 で最初に確かめる）。delta の挙動、2 セッション同時の見え方、`/usage` の利用量内訳（問い②の補助）も見る
- 1-2: 同じセッションで (i)(ii) を比べる。(i) は突合率をメイン / サブエージェント / compact / リトライ別に測り、`thinking_tokens ≤ output_tokens` を確かめる（V-2a）。(ii) で確定する（V-2b。§7 #2 の判断後）
- 1-3: 次の候補を比べる。前提と制約の裏付けとして、`skill.name` の有効範囲、`agent.name` の値、`OTEL_RESOURCE_ATTRIBUTES` の読み込み時期（③⑤ の前提）を確かめる
  - ① ネイティブ属性（`skill.name`・`command_name`・`workflow.name` 等）のみ
  - ② `UserPromptSubmit` hook でラベルを別ファイルに書き、hook 入力の `prompt_id` で突合。手段は command hook のほか、Claude Mods（cc 2.1.287 で加わった、plugin 内で cc のプロセスと同居して動く JS/TS の hook）の `classic.UserPromptSubmit` も候補にする（[1-8 §4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-4)）。hook と Mod のどちらにするかは Phase 2 で決める
  - ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位のラベル
  - ④ プロンプト本文の事後分類（ルール / LLM。`OTEL_LOG_USER_PROMPTS=1` が前提）
  - ⑤ プロジェクト設定の `OTEL_RESOURCE_ATTRIBUTES` でリポジトリ単位のラベル
  - 比較結果は次の列の表で整理する（列名: 記載する内容）
    - 候補: ①〜⑤、または組み合わせ
    - 長所: 他の候補ではできず、この候補ならできること
    - 短所: 他の候補ならできるが、この候補ではできないこと
    - 前提事項: この候補が成り立つために必要な条件
    - 制約: この候補を採ると受け入れる必要がある制限
    - 分類精度: 作業の性質をどこまで正しく分けられるか
    - 導入負荷: 仕組みを用意するための作業量
    - 維持負荷: 分類体系の見直しや cc の更新への追従に要る作業量
    - 機微情報: プロンプト本文などの機微な情報を記録・処理するか
    - その他: 上のいずれにも当てはまらない事項
- 1-4: Windows ネイティブ・Docker 不要のものに限り、(A) Node.js の自作 OTLP/HTTP 受信 + SQLite / DuckDB、(B) `otelcol-contrib.exe` + file exporter（JSONL）+ DuckDB（v2.1 §3 の構成）、(C) VictoriaMetrics / VictoriaLogs の単体バイナリを比べる。(B) は v2.1 R-1・R-3・R-4、V-6・V-13 の注意点（再起動時の消失、圧縮、並べ替えキー、Windows のパス表記。v2.1 §5.4・§6）を評価に含める
- 1-5: 自作 Node.js ダッシュボードと Grafana（Windows 版）等の OSS を比べる。探索期は DuckDB の SQL で集計の切り口をすぐ変えられる、という v2.1 §3.1 の考え方も比較軸に入れる
- 1-6: `~/.claude` 配下のファイル（transcript、サブエージェントの transcript、プロンプト履歴、設定、デバッグログ等。実在と内容は着手時に確かめる）ごとに、取得・算出できる情報、突合の鍵、保存期間、機微情報の有無を表にする。テレメトリとして扱えない情報も対象に含める。あわせて、既存 transcript（約 217MB）から model / usage / thinking_tokens / skill 等をどこまで復元できるかを確かめる
- 1-7: GenAI semconv・OpenInference の一次資料を読み、cc の span を OpenInference の変換層に通して、反映する価値を判断する
- 1-8: 基線の段（§2 冒頭）ごとに docs・changelog の差分を洗い出し、差分に関わる事実をその段の cc で再実測する（cc 2.1.287・2.1.296・2.1.302）

- **成果物**: `reports/01.基礎調査/…/調査報告書.md`（項目ごとに分けるかは着手時に決める）
- **完了条件**: 1-1〜1-8 の判定が出そろい、Phase 2 の設計判断に必要な候補が 2 案以内に絞られている (承認待ち: Q1)。v2.1 §8.5（V-11(b)）の各項目について、確認結果（一致 / 差異あり / 対象外とその理由）が記録されている。V-11(b) は 1-1〜1-6 で横断的に確認し、担当の 1-x は着手時に割り当てる

<a id="sec-p2-l1-hook"></a>
#### L1 の hook の既定の書き方

タグ案 L1 のタグ付けの hook（`UserPromptSubmit`）は、次の書き方を既定の案とする。Phase 2 の設計担当はこの既定を覆してよい。既定は Git Bash の有無に依らないので、Phase 2 は Phase 3・Phase 7 の結果を待たずに決められる。

- exec 形式（`command` と `args`）か `"shell": "powershell"` で書き、Git Bash の有無に依らないようにする。exec 形式を docs が勧めるのは、1 つの `.exe` を動かす hook の場合である（`.cmd`・`.bat` は含まない）
- `"onFailure": "continue"` を明示し、fail-open の意図を設定に残す。`"onFailure": "block"` は付けない（ラベル付けの失敗などで、利用者のプロンプト・操作を止めない）
- Mod で実装する場合は、`.catch` で失敗時に素通しにする。plugin（Mod を含む）で配る場合は、受け渡しの失敗による拒否がプロンプトに及ぶかを Phase 3 で確かめる（及ぶなら `.catch` では素通しにできない見込み。settings に書く command hook には及ばない見込み）
- background の process を起こさない（起こすと tool call が block されうる。docs）
- skill の frontmatter に置かない（そこに書いた hook は、その skill を呼んだ次のプロンプトから動くので、その skill を呼んだプロンプトにラベルが付かない）

docs の根拠（`onFailure` の扱い、Git Bash の無い Windows の例外と直し方）は仕様別紙 §3 に、変更の版は [1-8 §8.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-2) の D44・D46 にある。この書き方の試作の hook が職場で動くかは、Phase 7 で確かめる（試作の hook の仕様は [V-ID 別紙 §2 の職場の表の前](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2-l1-hook)）。

<a id="sec-p2-dedupe"></a>
#### 集計の正本と二重計上の除き方

本体のリクエストは、logs の `api_request` と traces の `llm_request` span の両方に出る。両方を足すと二重に数えるので、Phase 2 は集計の正本を決める。選択肢は、traces の span を正本にするか、logs の `api_request` を正本にして logs に無い span だけを足すかである。

後者を採る場合の突き合わせの規則（既定の案）は次のとおりで、鍵は環境ごとではなく、リクエストごとに選ぶ。同じ環境の中でも鍵の付かないリクエストがあるためである（non-streaming fallback で再試行したリクエストには、直接接続でも `client_request_id` が付かない。docs）。

- `client_request_id` が `api_request` と span の両側にあるリクエストは、それで突き合わせる
- そうでないリクエストは、`request_id`（span と `api_request` に同名の属性がある）が両側にあれば、それで突き合わせる
- 突き合わせできなかった `api_request` の行（鍵が無い、片側にしか無い、値が合わない）は足さず、span を数える（その分は traces を正本にする。二重に数えないため）

Phase 2 はこの規則までを決める（Phase 3・Phase 7 の結果を待たない）。どの鍵がどれだけのリクエストに使えるかは、受信データの記録で見る。Phase 3（本環境）では、鍵が `api_request` と span の両側にあり、値が一致した割合を記録する。Phase 7（職場）では、鍵ごとの、鍵がある件数と無い件数に加えて、同じ割合を記録する。職場の件数は手元の記録にだけ残し、報告書には割合か「有・一部・無」で書く。LLM ゲートウェイ環境で鍵が付くかは、docs では決まらない（仕様別紙 §5）。

- **成果物**: `reports/02.設計/…/設計書.md`
- **完了条件**: 作業指示者が設計を承認する

### Phase 3: PoC（本環境でのエンドツーエンド疎通）

- **作業**: 最小の受信 → 保存 → transcript 突合 → 簡易集計（CLI かスクリプト出力で可）を実装し、実セッションで一通り流す。タグ案 L1 を採る場合は、自分の所要時間を記録する L1 の試作の hook も用意する（J-12 の判定に使う。記録の仕方は Phase 2「作業分類タグ」で決める）

  - 版の再確認: Phase 3 着手の前に、その時点の最新の cc で版の再確認（1-8 の追補にあたる。次の番号の報告書に書く）を行い、§2 冒頭の基線を更新する。下の版の下限は、この基線で決まる (承認待ち: J-18)
  - 版の下限: 測定に使う cc の版の下限は、Phase 3 着手時点の最新の基線の版（§2 冒頭）以降とする（現時点では 2.1.302）。下限は Phase 3 着手時点で一度だけ決め、Phase 3 の途中の反映では上げない（途中で上げると、先に測った値が新しい下限を下回り、判定に使えなくなる）。決めた下限は、Phase 3 の手順書と J-18 に記録する。着手の前に基線の版に回帰が見つかったら（changelog と、着手前の再確認の報告書で確かめる）、下限を自動では上げず、作業指示者に諮る。Phase 3 の途中で、下限より新しい版の属性が要る項目ができたら、その項目にだけ最低版を課す (承認待ち: J-18)。下限を置く理由と、選択肢との比較は J-18 にある
  - 版ごとの比較: すべての測定で `service.version` を記録する。hook と Mod の上乗せは版で変わり、cc は自動更新で Phase 3 の中でも上がりうる（[1-8 §7.3.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-3-2)・[§8.3.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-2)）。このため、比較は `service.version` ごとに同じ版の値どうしで行い、測定値は測った版でだけ使う
  - 版上げ直後: 版を上げた直後の最初のセッションは測定に使わない。このセッションは feature flag を取得する前に permission mode を決めることがあり、docs の組み込みの既定の表と違う mode で始まりうる。使った場合は、hook の入力か `tool_decision`（2.1.301 以降）の `permission_mode` で mode を確かめる（`permission_mode_changed` は mode が変わったときだけ出る）

  - モデル: エイリアス（`haiku`・`sonnet`）ではなく、完全なモデル ID で指定して記録する（エイリアスの解決先は版で変わる）。基準モデルは用途で分ける。cc 2.1.283・2.1.287 からの継続比較（属性集合・遅延・突合）は Haiku 4.5（`claude-haiku-4-5-20251001`）、auto mode が有効なまま動く条件（auto mode の比較を含む）の基準は Haiku 5.5（`claude-haiku-5-5`）を使う (承認待ち: J-14)
  - Remote Control: Claude が起動する対話の計測用のセッション（比較実験）は、Remote Control を切って起動する（`remoteControlAtStartup` を false にする JSON ファイルを `--settings` に渡す。切れたことは、debug log に Remote Control の接続を示す行が無いことで確かめる）。本環境のユーザ設定は、起動時に Remote Control に接続するためである。J-12 の判定に使う日常のセッションは切らずにそのまま測り、Remote Control の有無・モデル・permission mode・plugin の構成（hook（command hook・Mod）を登録する plugin の集合。OTel の `plugin_loaded` と `hook_registered` で観測する）をプロンプトごとに記録して、条件ごとに集計する。計測用のセッションの値は参照値として並べる（J-19）
  - plugin の構成: Claude が起動する計測用のセッション（probe と比較実験。`-p` と対話）では、plugin の構成を、比べる相手の測定（前回の基線。Phase 3 では着手前の版の再確認の測定）と同じにし、その後に有効になった plugin を、そのプロセスだけ無効にする。前回の基線の plugin の集合は、その測定の `plugin_loaded` の記録（repo の外）から取る。有効なままだと、hook なしの条件にもその plugin の hook が走って版の間の比較ができず、同じ版の中で hook と Mod を比べるときも、並列に走る plugin の hook で command hook の上乗せが隠れる（[1-8 §8.3.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)、J-25）。無効にする手順と確かめ方は、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の測定の注意と、活動の `CLAUDE.md` の作業時の注意にある。日常のセッション（J-19）は無効にせず、上のとおり plugin の構成を記録する
  - J-12 の判定: タグ案 L1 の hook の待ち時間を「許容できる」とする基準は、J-12 の暫定値を使う。判定は、「モデル × permission mode × Remote Control の有無 × plugin の構成（hook を登録する plugin の集合。有無の 2 値ではない）」の組のうち、標本が最も多い組（日常の主な条件）で行い、ほかの組は参考値とする。上乗せに加えて、L1 の hook 自身の所要時間にも同じ基準を当てる（理由は §5.1 の plugin の構成の行）。L1 の hook 自身の所要時間は、日常のセッションでは hook が自分で記録した値（Phase 2「作業分類タグ」）を使う。自分で記録した時間はプロセスの起動を含まないので、計測用のセッションで debug log の hook ごとの行との差を測って記録し、判定では、自分で記録した時間にその差（中央値）を足した値を使う（[1-8 §8.3.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)）
- **受信データの記録**: 突き合わせの鍵（`client_request_id`・`request_id`）が `api_request` と span の両側にあり、値が一致した割合を記録する（[集計の正本と二重計上の除き方](#sec-p2-dedupe)の規則の確かめ）。記録の仕方は、V-ID 別紙 §2 の本環境の表の、logs・metrics に出ない API 呼び出しの件数の行にある
- **判定の目安**: 各確認項目の判定の目安・測り方・標本数は、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の本環境の表の案を出発点にする。タグ案 L1 の hook の待ち時間の判定は、上の「測定の条件」の J-12 の判定のとおりとする
- **成果物**: `app/` 配下の PoC コード、`reports/03.PoC/…/PoC報告書.md`
- **完了条件**: 本環境で確認観点を満たす。起こし方を決めていない項目（plugin の hook の受け渡しの失敗、アイドル時の compaction など）は、期間内に観測できなければ「未観測」と記録して閉じてよい（V-ID 別紙 §2）。満たさない場合は Phase 2 へ戻す判断材料をそろえる

### Phase 7: 職場環境の確認と差の吸収（第二のゴール）

- **入力**: 仕様別紙 §5（docs の差と、認証の方法の分岐）、[V-ID 別紙 §2](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2) の職場の表（11 行。実施の順）、職場に入れる L1 の試作の hook の仕様（[V-ID 別紙 §2 の職場の表の前](../01.基礎調査/99.基礎調査まとめ/【別紙】V-ID別状況とPhase3実測項目.md#sec-2-l1-hook)）、Phase 3 の PoC、[1-8 §8.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-5) などの未確認事項
- **先に分かれば知らせていただくこと**（任意。いつでもよい）: ループバック宛て送信の短い試験、ゲートウェイへの認証の方法（仕様別紙 §5 の分岐 T・K・L）、Git Bash の有無。届いたら、その時点で Phase 2「第二のゴールへの備え」の判断に使う
- **職場環境確認手順書に含めるもの**: v2.1 V-10、仕様別紙 §5 の差、PoC を職場環境で動かす手順と記録様式、下の「測定の条件」と「確かめること」、L1 の試作の hook の入れ方と外し方。試作の hook は、PoC の成果物（plugin、または settings に書く command hook）として作業指示者が職場の環境に入れる
- **測定の条件**
  - cc の版を記録する。Phase 3 の版の下限未満なら、その版で測った値は本環境の値と比べず、職場の中の比較に限る（managed settings のキーと拒否の行の確認は、版に依らないのでそのまま行う）。職場の cc の版上げを依頼するかは作業指示者が決める。職場にも下限を課すか（J-18 の第 2 の問い）は、Phase 7 の着手前に諮る
  - 確認のたびに cc の版を記録し、前回と違えば最初のセッションを測定に使わない
  - permission mode を明示して固定する（`--permission-mode` か `permissions.defaultMode`）。明示すれば、`-p` の起動時の mode の本環境と職場の差は測定に入らない（J-16）
  - モデルは完全なモデル ID で指定する。職場で通るモデル ID はゲートウェイの routing（LiteLLM 環境）で決まり、本環境の ID が通るとは限らない。そこで手順書では ID の欄を空欄にし、作業指示者が職場の PC 上の写しにだけ、職場で通る ID を入れて実行する。ID を入れた写しは repo に戻さない。記録するのは ID の種類（Anthropic の ID か、ゲートウェイの別名か）だけである
  - Remote Control は使えない（`ANTHROPIC_BASE_URL` が Anthropic 以外のホストを指す間は、cc が Remote Control を off にする。ゲートウェイの credential が有効な間も使えない。docs。J-26）
- **確かめること**: 実施の順は V-ID 別紙 §2 の職場の表の行の順とし、下の表もその順に並べる。並べ方の原則は 3 つある。`/status` の記録を最初にする（記録だけで、受信サーバは要らない）。確かめる項目の最初は、ループバック宛て送信にする（届かなければ受信を前提にする項目が成り立たないので、早く見つける）。L1 の試作の hook を入れる行（Mods の行）を、それを使う起動時の permission mode の行より前に置く。各行の手順と記録する値は、V-ID 別紙 §2 の対応する行にある。Node.js の版は確かめない（J-24 の回答で、職場では任意の版を使える）

| 確かめること | その結果で決まること |

- **結果の取りまとめ**: 結果は作業指示者が記録様式に書き、Claude Code が報告書に取りまとめる。記録様式と、件数を手元の記録にだけ残す規則は V-ID 別紙 §2 にある。plugin の構成と L1 の hook の時間は、PoC の受信データと L1 の hook の記録に入る。このため、この 2 つの記録で職場の手作業が増えるのは、受信データの提出（記録様式の手順）と、L1 の試作の hook の導入と取り外しに限られる。報告書には plugin の名前を書かない
- **差の吸収**: 確認の結果で、Phase 2 の備え（環境ラベル、突き合わせの鍵、思考案 T2、縮退運用）を調整し、要れば Phase 2〜5 の成果物を直す。設計の変更が要る場合は Phase 2 へ戻す。§7 #7・#8 を判断いただく
- **成果物**: `reports/07.職場環境対応/…`（案。職場環境確認手順書と確認結果、報告書）と、差の吸収の修正。フォルダは今は作らない
- **完了条件**: 職場の日常の利用で、操作を増やさずにデータが溜まる状態が 1 週間程度続く（作業指示者が確かめる）。両方の環境のデータを同じ観点で集計できる

## 5. 横断的なリスクと対策

### 5.1 第一のゴールのリスク

| リスク | 影響 | 対策 |

| cc のバージョンアップで OTel 属性・transcript 形式が変わる（例: v2.1.222 の `mcp_server.name` の意味変更） | 集計の欠落・誤り | 環境基線（`service.version`）を記録する。取込時に想定外の形式を検知して警告する（Phase 2 で設計）。版をまたぐ比較は `service.version` で区切る（Phase 2「バージョン追従」） |

| 作業分類タグの付与漏れ・揺れ | 分析精度の低下 | 付与方式を複数組み合わせる。「未分類」を明示的に集計して漏れを見える化する |
| プロンプト本文などの機微情報が保存される | 情報漏えい | 保存先を repo 外にする。本文の記録は既定 OFF とし、有効化は作業指示者の判断で行う。記録する場合は `prompt` と `prompt_text` の両方をマスクする（Phase 2「データ保全とプライバシー」）。transcript は cc 2.1.300 から system prompt と tools の全文を含む（[1-8 §8.3.4](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-4)）ので、補完取込での扱いも同じ設計項目で決める |
| 失敗した hook の stderr と終了コードが debug log に出る（cc 2.1.284 以降。[1-8 §2.3](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-2-3)） | プロンプト本文を扱う hook が失敗すると、本文の一部が debug log に残り得る | hook は stderr に本文を出さない作りにする（Phase 2 で設計）。debug log を機微情報として扱う |
| Mod の不具合で、ラベルが黙って欠ける（worker の再起動中に `classic.*` hook が飛ばされる不具合は 2.1.293 で、アップグレード後の最初のセッションで Mod が読み込まれない不具合は 2.1.289 で直った。[1-8 §7.2](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-7-2)） | タグ付けを Mod で実装した場合、その間のプロンプトにラベルが付かず、hook の失敗による付与漏れと見分けにくい | Mod を採る場合は cc 2.1.293 以降を前提にする。Phase 3 で、日常のセッションでの worker の再起動回数と、その前後のラベルの欠けを確かめる。付与漏れは `service.version` と並べて集計する |
| 日常のセッションの hook なしの基準値が、ユーザ環境で有効な plugin の構成で変わる（本環境の対話で約 450 ms。[1-8 §8.3.5](../01.基礎調査/08.cc2.1.287差分の確認/調査報告書.md#sec-8-3-5)、J-25） | 構成の違うプロンプトを混ぜると、タグ案 L1 の hook の上乗せを誤って判定する。plugin の hook がある本環境では、L1 の command hook の上乗せが隠れうる見込みである | J-12 の判定の組に plugin の構成（hook を登録する plugin の集合）を含め、L1 の hook 自身の所要時間にも同じ基準を当てる。計測用のセッションは、plugin の構成を前回の基線にそろえる（いずれも Phase 3） |
| GenAI semconv は全体が Development 段階で、破壊的な改名が続いている（[1-7 §1.3](../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-1-3)） | 対応表・取込の名前の対応が古くなる | 列名は cc の元の名前で持ち、改名の影響を対応表に閉じる。参照する semconv を commit で固定し、cc の版を上げるときに確認する（[1-7 §5.1](../01.基礎調査/07.生成AIオブザーバビリティ規格/調査報告書.md#sec-5-1)・§9） |
| 受信サーバの停止中にデータが欠落する | 連続性の低下 | cc 側は送信失敗しても操作に影響しないことを PoC で確認する。transcript からの遡り取込で補う |
| `cost_usd` が API 料金換算の推定値である | サブスクリプション利用時の実コストとずれる | 分析では「API 換算コスト」と明記し、比較の相対指標として扱う |
| transcript は cc が既定 30 日（`cleanupPeriodDays`）で削除する。OTel と違い、こちらから取り込まない限り手元に残らない（v2.1 R-13） | 取込が削除に間に合わないと、思考トークンの突合・遡り取込が欠落する | 削除より前に定期的に取り込み、自前の保存先に永続化する（取込の仕組みと頻度は Phase 2 で決める）。`cleanupPeriodDays` の延長は補助策とし、適用値は `retention_sweep` イベントの `period_days` で確かめる |

## 6. 作業の進め方

- 各 Phase の終わりに作業指示者のレビューを受け、承認後に次 Phase へ進む

- モデル選定: 調査の実測・集計は Sonnet、設計判断・分析結論・計画改訂は Opus を基本とする（ルート CLAUDE.md の原則どおり）
