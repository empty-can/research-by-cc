## 1. ゴール

### 1.1 最終ゴール

cc の利用実績から **「作業の性質 → 推奨モデル × 推奨 effort」** を導き、ルート `CLAUDE.md` の「モデル選定原則」表と `check-model` skill の判定基準を**データに基づいて改訂する**。

### 1.2 そのために作るもの

| # | 構成要素 | 役割 |
|---|---|---|
| 1 | 受信・保存 | cc の OTel シグナルを Windows ローカルで受けて保存する |
| 2 | 補完データ取込 | OTel に無い情報（思考トークン等）を transcript から取り込み、突合する |
| 3 | 作業分類タグ | 「どの作業か」を後から集計できるようにラベルを付ける |
| 4 | ダッシュボード | 作業分類 × モデル × effort でトークン・コストを可視化する |

### 1.3 成功基準（活動全体）

- 日常の cc 利用で、操作を増やさずにテレメトリが自動で溜まる
- 作業分類 × モデル × effort ごとに、入力 / 出力 / キャッシュ / **思考**トークンと推定コストを集計できる
- 推奨モデル × effort 表（改訂案）を、根拠データ付きで作業指示者に提示できる

## 2. 公式仕様の調査結果と、計画への影響

Phase 0 で公式 docs（cc 2.1.282 時点）と既存 transcript を確認した。背景の期待とそのままでは合わない点があるため、先に整理する。

### 2.1 取れるもの（OTel ネイティブ）

| シグナル | 主なデータ | 分析上の意味 |
|---|---|---|
| metrics `claude_code.token.usage` | `type`=input / output / cacheRead / cacheCreation、`model`、`effort`、`query_source`（main / subagent / auxiliary）、`skill.name`、`agent.name` | 集計の主軸になる |
| metrics `claude_code.cost.usage` | 上と同じ属性で USD 推定値 | コスト軸 |
| events `api_request` | リクエスト単位のトークン 4 種、`cost_usd`、`duration_ms`、`effort`、`request_id`、`prompt.id` | 明細の主軸。`prompt.id` で 1 プロンプト分をまとめられる |
| events `user_prompt` | `prompt_length`、`command_name`、（任意）プロンプト本文 | 作業分類の手がかり |
| events `tool_result` / `skill_activated` / `subagent_completed` など | ツール・skill・subagent の実行状況 | 作業分類の手がかり |
| traces（beta） | `llm_request` span の `ttft_ms` / `stop_reason` / `agent_id`、親子関係 | 任意拡張。beta のため必達にしない |

### 2.2 背景の期待と合わない点

**(a) 思考トークンは OTel では分離されない**

- OTel のトークン数は output_tokens に思考分を含めた値で、思考分だけを取り出す属性は無い（公式: "Thinking tokens are billed as output tokens"）
- 生の API ボディを出す `OTEL_LOG_RAW_API_BODIES` でも、思考の本文は必ず伏せられる
- **ただし API 応答の usage には思考トークン数がある**。本セッションの transcript で `message.usage.output_tokens_details.thinking_tokens` を実測で確認した（思考の本文は空で、トークン数のみ）。同じエントリに `requestId` があることも確認した
- この usage は API 応答をそのまま保存したものなので、取得経路は 2 つ考えられる。どちらを主にするかは Phase 1-2 で決める

| 経路 | 内容 | 利点 | 懸念 |
|---|---|---|---|
| (i) transcript 突合 | transcript の usage を取り込み、`request_id` で OTel の `api_request` と突合する | 実測で成立を確認済み。過去分にも使える | 公式に「transcript 形式は cc 内部仕様でバージョンごとに変わり得る」とされている |
| (ii) 応答ボディのイベント | `OTEL_LOG_RAW_API_BODIES` の `api_response_body` イベントに含まれる usage を使う（思考の本文は伏せられるが、usage は伏せられない見込み） | OTel の送信経路だけで完結する | 会話履歴全体を含むボディが出る（プライバシー・容量）。usage が含まれることは未実測 |

**(b) 「作業の内容・性質の分類」を表す属性は OTel に無い**

- ネイティブに使える代理指標: `skill.name`（ユーザ定義 skill も名前がそのまま出る）、`command_name`、`query_source`、`effort`、`workflow.name`
- `agent.name` は、ユーザ定義 agent だと `"custom"` に丸められる（例: 自作の `cve-investigator` 等は区別できない）
- `OTEL_RESOURCE_ATTRIBUTES` は起動時に固定され、セッション途中でタグを変えられない
- → **タグ付け方式を Phase 1 で比較し、Phase 2 で決める**。候補は §4 Phase 1 の 1-3 を参照

### 2.3 構成上の制約・注意点

- cc には OTLP プロトコルの既定値が無く、明示指定が必要。`http/json` を選べば protobuf のデコードが不要になり、Node.js で受信サーバを自作しやすい
- `prometheus` exporter は各セッションがポート 9464 を占有するため、複数セッションを同時に起動すると衝突する → **push 型の OTLP を主線にする**
- metrics の temporality の既定は `delta`（前回送信からの増分）。自作で保存する場合は受け取った値を足し合わせるだけで済むため、**既定の `delta` のまま使う**（`cumulative` に変える必要はない）
- OTel 変数はユーザ settings（`~/.claude/settings.json`）の `env` で設定でき、起動方法に関係なく効く。一部（`OTEL_LOG_RAW_API_BODIES` 等）は project / local settings では無視される
- 設定値は起動時に読み込まれるため、変更後は cc の再起動が必要

## 4. 各フェーズの詳細

### Phase 0: 活動計画（本フェーズ）

- **作業**: 公式仕様の確認、transcript の実測（思考トークン数の有無）、全フェーズ構成の策定
- **成果物**: 本書、`research-for-local-mini-otel-infra/CLAUDE.md`
- **完了条件**: 作業指示者が本計画を承認する

### Phase 1: 基礎調査・フィジビリティ確認

Phase 2 の設計判断に必要な事実を、机上調査と実測で揃える。

| # | 調査項目 | 方法 | 判定したいこと |
|---|---|---|---|
| 1-1 | 実際に届くデータの確認 | `console` exporter、または簡易受信で実セッションを 1 本流し、metrics / events / traces の中身を記録する | `effort` / `skill.name` / `query_source` 等が文書どおり届くか。delta の挙動、同時に 2 セッション動かした場合の見え方 |
| 1-2 | 思考トークンの取得経路 | §2.2(a) の 2 経路を同じセッションで比べる。(i) `api_request` の `request_id` と transcript の `requestId` の突合率 (ii) `OTEL_LOG_RAW_API_BODIES=file:<dir>` の応答ボディに `thinking_tokens` が入るか | 各経路がどの程度成立するか（subagent・compact・リトライ時を含む）。どちらを主にするか（(ii) はプライバシーの判断＝§7 の 2 と連動） |
| 1-3 | 作業分類タグの付与方式の比較 | 候補を比べる: ①ネイティブ属性（`skill.name` 等）のみ ② `UserPromptSubmit` hook で分類ラベルを別ファイルに書き `prompt.id` / セッションと時刻で突合 ③ 起動ランチャで `OTEL_RESOURCE_ATTRIBUTES` にセッション単位の作業種別を入れる ④ プロンプト本文（`OTEL_LOG_USER_PROMPTS=1`）の事後分類（ルール / LLM） | 精度・手間・プライバシーの兼ね合いで、どの組み合わせにするか |
| 1-4 | 受信・保存コンポーネントの候補比較 | Windows ネイティブで Docker 不要のものに限って比較する。例: (A) Node.js の自作 OTLP/HTTP 受信 + SQLite / DuckDB (B) `otelcol-contrib.exe` + file exporter + 取込処理 (C) VictoriaMetrics / VictoriaLogs の単体バイナリ | 導入・常駐の手軽さ、集計クエリの書きやすさ、UI との相性 |
| 1-5 | ダッシュボード方式の比較 | 自作 Node.js ダッシュボードと、Grafana（Windows 版）等の OSS を比べる | 作業指示者の「頻繁にレイアウトを変えたい」要件への適合度 |
| 1-6 | 既存 transcript の遡り取込 | 既存 transcript（約 217MB）から model / usage / thinking_tokens / skill 等をどこまで復元できるかを確認する | 過去分を基準データとして使えるか（あくまで補助。主線は OTel） |

- **成果物**: `reports/01.基礎調査/…/調査報告書.md`（項目ごとに分けるかは着手時に決める）
- **完了条件**: 1-1〜1-6 の判定が出そろい、Phase 2 の設計判断に必要な候補が 2 案以内に絞られている
- **主なリスク**: 文書と実際の出力の差。バージョンアップで属性が変わること

### Phase 2: 設計

| 設計項目 | 内容 |
|---|---|
| 全体構成 | 受信 → 保存 → 補完取込 → 集計 → UI のコンポーネント構成とプロセス構成（1 プロセスにまとめるか分けるか） |
| データモデル | 分析用スキーマ。粒度は API リクエスト単位を基本とし、プロンプト・セッション・作業分類へ集約する |
| 作業分類タグ | Phase 1-3 の結果を受けた方式、分類体系（初期のカテゴリ一覧）、付与漏れ時の扱い |
| 分析指標 | 例: 作業分類 × モデル × effort ごとのプロンプトあたりトークン・コスト、思考トークン比率、キャッシュヒット率、所要時間 |
| 有効化と常駐 | ユーザ settings の `env` の中身、受信サーバの起動方法（手動 / ログオン時の自動起動）、受信サーバが止まっているときの cc 側の挙動 |
| データ保全とプライバシー | 保存先（repo 外）、保持期間、プロンプト本文を記録するかどうか、バックアップ |
| バージョン追従 | cc の属性・transcript 形式が変わったときに検知する仕組み |

- **成果物**: `reports/02.設計/…/設計書.md`
- **完了条件**: 作業指示者が設計を承認する

### Phase 3: PoC（エンドツーエンド疎通）

- **作業**: 最小の受信 → 保存 → transcript 突合 → 簡易集計（CLI かスクリプト出力で可）を実装し、実セッションで一通り流す
- **確認観点**: `effort` 別・`model` 別の集計が出るか、思考トークンが突合されるか、2 セッションを同時に動かしても欠落しないか、受信サーバが止まっていても cc の操作に影響しないか
- **成果物**: `app/` 配下の PoC コード、`reports/03.PoC/…/PoC報告書.md`
- **完了条件**: 確認観点を満たす。満たさない場合は Phase 2 へ戻す判断材料をそろえる

### Phase 4: 収集基盤の実装

- **作業**: PoC を日常運用に耐える形にする。受信・保存の常駐化、transcript 取込の自動化、タグ付けの仕組み（hook / ランチャ等）、形式変化の検知、ログ・エラー処理
- **成果物**: `app/` 配下の実装、利用手順（導入・起動・停止・トラブル時の対応）
- **完了条件**: 日常の cc 利用で操作を増やさずにデータが溜まる状態が 1 週間程度継続する

### Phase 5: ダッシュボードの実装

- **作業**: Phase 1-5 で選んだ方式で分析画面を作る。レイアウトを変えやすい構成（部品の設定ファイル化など）を優先する
- **想定画面**: 期間サマリ、作業分類 × モデル × effort のクロス集計、トークン内訳（思考比率を含む）の推移、高コストのプロンプト・セッションのランキングと明細
- **成果物**: ダッシュボード、画面仕様メモ
- **完了条件**: 作業指示者が画面をレビューし、分析に使える状態と判断する

### Phase 6: 運用・分析・フィードバック

- **作業**: 一定期間（目安 2〜4 週間）データを蓄積してから分析する。「トークンを消費しやすい作業」の特定、作業分類ごとの推奨モデル × effort の導出
- **成果物**:
  - `reports/06.分析/…/分析報告書.md`
  - **推奨モデル × effort 表（改訂案）** と、ルート `CLAUDE.md` の「モデル選定原則」・`check-model` skill への反映案
- **完了条件**: 反映案を作業指示者が承認する（反映自体は main 側の横断作業として別途実施）
- **補足**: サンプル数が少ない分類は結論を保留し、継続観測の対象として明記する

## 5. 横断的なリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| cc のバージョンアップで OTel 属性・transcript 形式が変わる | 集計の欠落・誤り | 環境基線（cc のバージョン）を記録する。取込時に想定外の形式を検知して警告する（Phase 2 で設計） |
| transcript と OTel の突合が一部成立しない | 思考トークンの欠落 | Phase 1-2 で成立率を実測し、欠落分の扱い（除外 / 推定）を設計で決める |
| 作業分類タグの付与漏れ・揺れ | 分析精度の低下 | 付与方式を複数組み合わせる。「未分類」を明示的に集計して漏れを見える化する |
| プロンプト本文などの機微情報が保存される | 情報漏えい | 保存先を repo 外にする。本文の記録は既定 OFF とし、有効化は作業指示者の判断で行う |
| 受信サーバの停止中にデータが欠落する | 連続性の低下 | cc 側は送信失敗しても操作に影響しないことを PoC で確認する。transcript からの遡り取込で補う |
| `cost_usd` が API 料金換算の推定値である | サブスクリプション利用時の実コストとずれる | 分析では「API 換算コスト」と明記し、比較の相対指標として扱う |
