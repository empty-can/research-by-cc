# 【別紙】公式仕様の調査結果 — 活動計画書

[活動計画書](活動計画書.md) §2 の要点表の裏付けとなる、OTel の属性・イベントと構成上の制約の詳細。計画書では「仕様別紙 §n」として参照する。

基線は cc 2.1.283、公式 docs 2026-09-27 15:00 取得版（`C:\cc-workspace\LLMs\official-llms-txts\code.claude.com\docs\llms-full.txt`）。以下は docs 上の事実で、実機での確認は Phase 1（職場環境の分は Phase 3）で行う。「見込み」は docs に明記がない推定を示す。出典の詳細は [引継ぎ資料 v2.1](handover-report_by_chat-claude/claude-code-otel-telemetry-design-brief-v2.1.md)（以下「v2.1」）の各節。

## 1. 取れるシグナルと属性

| シグナル | 主なデータ | 分析上の意味 | v2.1 参照 |
|---|---|---|---|
| metrics `claude_code.token.usage` / `cost.usage` | `type`=input / output / cacheRead / cacheCreation、USD 推定値、`model`、`effort`、`query_source`、`skill.name`、`agent.name` | 集計の主軸。`query_source` は `main` / `subagent` / `auxiliary` の 3 分類で、イベントとは値の体系が違う | §4.7、§4.8 |
| events `api_request` | リクエスト単位のトークン 4 種、`cost_usd`、`duration_ms`、`effort`、`request_id`、`prompt.id`、`query_source`（`repl_main_thread` / `compact` / サブエージェント名の生の値） | 明細の主軸。`prompt.id` で 1 プロンプト分をまとめる。`agent_id` は無い（スパンのみ）ので、同型サブエージェントの並列実行は区別できない | §4.2、§4.8 |
| resource `service.version` / `service.name` | cc のバージョン（設定不要で全シグナルに付く）。Desktop の Code タブでは Desktop のバージョンになるため `service.name` で区別する | バージョン別の集計、形式変化の検知 | §2.4 |
| events `user_prompt` | `prompt_length`、`command_name`（組み込みコマンド名は既定でそのまま出る）、（任意）プロンプト本文 | 作業分類の手がかり。`/compact`・`/clear` の実行時点の検出（問い①） | §4.5 |
| events `compaction` | `trigger`（auto / manual）、`pre_tokens` / `post_tokens`（概数）、`duration_ms`、`success` | 問い①。圧縮自体の API 呼び出しは `api_request` の `query_source="compact"` | §4.5 |
| events `subagent_completed` | 型別のツール使用数・実行時間、`model` / `final_model` / `model_swapped` | 問い②。`total_tokens` は最後の 1 リクエスト分だけなので、トークン集計には使わない（metrics を `query_source="subagent"` で絞る） | §4.8 |
| events `tool_result` / `skill_activated` など | ツール結果・入力のサイズ（`tool_result_size_bytes` 等）、skill・hook の実行状況 | 問い③、作業分類の手がかり | §4.6 |
| traces（beta） | `llm_request` span の `ttft_ms` / `stop_reason` / `agent_id`、親子関係 | 任意拡張。beta のため必達にしない。詳細ベータトレースは送信先が切り替わる（v2.1 R-14） | R-14 |

- `/clear` 専用のイベントは無い。`/clear` で `session.id` が新しくなる。`/clear` の実行時に `user_prompt` が出るかは docs に明記がない（V-8）。出ない場合は `SessionStart` hook の `source`（`clear` / `compact`）で区切りを記録する（v2.1 §4.5）
- サブエージェントも自身のリクエストを送ってプランの利用量を消費する。`/usage` などの利用量内訳でサブエージェントの割合が見られる（costs / sub-agents ページ。問い②の補助）

## 2. 思考トークン

- `api_request` にも metrics にも、思考トークンだけを示す属性は無い
- `api_request.output_tokens` に思考分が含まれるかは docs に明記がなく、**含まれる見込み**（課金上は output として扱われる）。1-2 で V-2a（transcript 突合）→ V-2b（応答ボディ）の順に確かめる
- 生の API ボディを出す `OTEL_LOG_RAW_API_BODIES` でも、思考の本文は必ず伏せられる
- transcript の `message.usage.output_tokens_details.thinking_tokens` に思考トークン数がある（思考の本文は空で、トークン数のみ。Phase 0 に cc 2.1.282 で実測）。同じエントリの `requestId` は OTel の `request_id` と同じ値（docs 明記）。`request_id` は API が返したときだけ付くので、突合できない行が出る前提で集計する
- 取得経路（transcript 突合 / 応答ボディ）の比較は計画書 §2.1

## 3. 作業分類に使える属性

- ネイティブに使える代理指標: `skill.name`、`command_name`、`query_source`、`effort`、`workflow.name`
- `skill.name` は、`api_request` と token / cost metrics ではユーザ定義 skill も元の名前で出る。`skill_activated` イベントでは、ユーザ定義 skill も `"custom_skill"` に置き換わる（`OTEL_LOG_TOOL_DETAILS=1` で元の名前）。skill の終了後も `skill.name` が付き続けるかは docs に記述がない（V-12）
- `agent.name` は、ユーザ定義 agent だと `"custom"` に丸められる（例: 自作の `cve-investigator` 等は区別できない）。`subagent_completed` の `agent_type` も同じ規則
- `OTEL_RESOURCE_ATTRIBUTES` は起動時に固定される**見込み**（docs に明記なし。OTel の一般的な仕組みからの推定。1-3 で確認）。プロジェクト設定でも有効なので、リポジトリ単位の固定ラベルには使える
- hook 入力の `prompt_id` は OTel の `prompt.id` と一致する（v2.1.196 以降。最初のプロンプトより前は無い）。hook でラベルを書き出す方式は、時刻ではなく `prompt_id` で突合できる

## 4. 構成・設定上の制約

- cc には OTLP プロトコルの既定値が無く、明示指定が必要。`http/json` を選べば protobuf のデコードが不要になり、Node.js で受信サーバを自作しやすい（v2.1 は `http/protobuf`）
- `prometheus` exporter は各セッションがポート 9464 を占有するため、複数セッションを同時に起動すると衝突する
- metrics の temporality の既定は `delta`（前回送信からの増分）。自作で保存する場合は受け取った値を足し合わせるだけで済むため、既定の `delta` のまま使える
- OTel 変数はユーザ settings（`~/.claude/settings.json`）の `env` で設定でき、起動方法に関係なく効く。project / local settings で無視されるのは、有効化・送信先・内容記録の変数に限られる（cc 2.1.282 以降）。`OTEL_RESOURCE_ATTRIBUTES` と送信間隔などは有効（v2.1 R-2）
- 設定値は起動時に読み込まれるため、変更後は cc の再起動が必要
- `OTEL_LOG_TOOL_CONTENT=1` は、cc 2.1.283 から MCP ツール・WebFetch・WebSearch の結果も `tool.output` span event に記録する（計画書 §7 #2 の判断材料）

## 5. 職場環境で差が出る点

職場環境は、cc → 社内 LLM ゲートウェイ（LiteLLM 等の社内プロキシ。`ANTHROPIC_BEDROCK_BASE_URL` / `ANTHROPIC_BASE_URL` で指定）→ Amazon Bedrock の経路で使う。docs で確定している差は次のとおり（詳細は v2.1 §9.1〜§9.6）。不明な 2 点（思考トークンの内訳、社内プロキシによる改変）は計画書 §2.2。

| 項目 | 職場環境での差 |
|---|---|
| 利用者の識別属性 | `user.id` と `session.id` しか埋まらない |
| `client_request_id` | 付かない（対応付けには `request_id` を使う） |
| `request_id` の取得元 | `request-id` ヘッダの無い応答（Bedrock など）では `x-amzn-requestid` の値が入る（2026-09-27 版 docs の Event correlation attributes で明記。v2.1 §9.3 では【要確認】のまま） |
| `internal_error` イベント | 出ない |
| トレースのコンテキスト | `traceparent` はサードパーティのプロバイダには送られない（独自プロキシへは `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1`） |
| `cost_usd` | Anthropic の料金による換算で、Bedrock の実請求とはずれる（計画書 §5） |

- 補助的なデータ源: cc 2.1.283 から、`CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` で opt-in すると `x-claude-code-prompt-id` ヘッダ（1 つのプロンプトに属するリクエストで共通の UUID）がゲートウェイに送られる。社内プロキシのログをプロンプト単位で集計する補助に使えるが、ゲートウェイは社内管理のため本活動の主線にはしない
