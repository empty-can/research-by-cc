- GenAI semconv（OTel の生成 AI 向け semantic conventions）との対応: cc は `gen_ai.usage.*` を出さない（cc 2.1.309 でも出ない。トークン数は引き続き独自名の属性から取る）。`cache_read_tokens` は `gen_ai.usage.cache_read.input_tokens`、`cache_creation_tokens` は `gen_ai.usage.cache_write.input_tokens` に対応する。semconv の `gen_ai.usage.input_tokens` はキャッシュ分を含むので、cc の 3 種（`input_tokens`・`cache_read_tokens`・`cache_creation_tokens`）の合計に当たる（1-8 §2.1 D1、1-7 §7.1）。span の `gen_ai.*` 5 属性は実測時点の docs にもあった（1-8 §2.2）。docs の span の属性の表は、2026-10-23 取得版（cf8ad11）とオンラインのページでもこの 5 属性のままである（1-9 §3.1）
- span の GenAI 属性は、cc 2.1.296 までは表の 5 つだけだった（2.1.283・2.1.287・2.1.296 の実機）。cc 2.1.300 から、`gen_ai.provider.name`（値は `anthropic`。interaction・llm_request・tool・tool.blocked_on_user・tool.execution の 5 種の span）、`gen_ai.tool.name`（tool span。既存の `tool_name` と同じ値）、`gen_ai.conversation.id`（5 種の span）が加わった（changelog 2.1.300 と 2.1.302 の実機）。`gen_ai.operation.name`（interaction は `invoke_agent`、tool は `execute_tool`。llm_request には付かない）は、2.1.296 では出ず、2.1.302 では出た（changelog に名前が無く、出始めた版は確かめていない）。changelog 2.1.300 にある `error.type` は、エラーの無い run だけで、観測していない。`gen_ai.system` は 2.1.302 でも `gen_ai.provider.name` と並んで出る。`gen_ai.conversation.id` は、2.1.302 の実機で、メインの span では `session.id` と同じ値、サブエージェントの span ではそのサブエージェントの `agent_id` と同じ値だった（`session.id` を対応表で写すときの扱いは計画書 Phase 2「データモデル」）。logs のイベントと metrics には `gen_ai.*` は付かない（1-8 §8.3.1、1-7 §2.4）
- docs（2026-10-18 取得版）の Monitoring ページの `claude_code.llm_request` span の属性の表には、`prompt.id`（docs は events に付く属性として挙げる）・`skill.name`・`agent.name` が無く、`model`・`effort`・トークン 4 種・`request_id`・`client_request_id` はある（`cost_usd` も span に無い。1-7 付録 A.1。logs と結合できなかった span の扱いは計画書 Phase 2「集計の正本と二重計上の除き方」）
- `api_request` には cc 2.1.300 から、cache 書き込みのトークン数の TTL 別の内訳 `cache_creation_5m_tokens`・`cache_creation_1h_tokens`（int）が付く（changelog 2.1.300）。2.1.302 の実機では全件に付き、2 つの和は `cache_creation_tokens` と一致した。docs は、metrics の `token.usage` の `cacheCreation` を 5 分と 1 時間の書き込みの合算と明記している（metrics では分けられない）。単価が TTL で違う場合の費用の計算に使える（1-8 §8.2 D38）。この 2 つは、docs の `api_request` の属性の一覧には無く、changelog 2.1.300 の項にだけある（docs cf8ad11 L3083。5536db3 も同じ）
- `api_request` の費用の属性: `cost_usd` は USD の推定値で、100 万分の 1 ドル単位の整数の推定値 `cost_usd_micros` も付く。`speed` は、fast mode だったかを `fast` / `normal` で示す。metrics の `cost.usage`・`token.usage` の `speed` は、fast mode のときだけ `fast` が付き、それ以外は無い（docs cf8ad11 の Monitoring ページ。`api_request` は L74023〜L74045、metrics は L73883・L73902。5536db3 にも同じ記述がある）。cc がどの料金で換算するかは §5 の `cost_usd` の行にある。トークン 4 種・`model`・`speed` は、計画書 Phase 2「分析指標」の見なし費用の計算に使う
- cache 書き込みの既定の TTL は、課金の形と要求の区分で決まる。主の会話（対話のターン、`-p` の実行、Agent SDK のターンと、それと一緒に走る補助の要求）は、定額の契約（Claude の subscription）の利用枠の中では 1 時間、usage credits・API キー・クラウド提供元では 5 分である。それ以外の要求（サブエージェント、workflow、compaction、セッションのタイトルなど）は、どちらでも 5 分である（利用枠の中では、サーバーが決める一部の補助の要求だけ 1 時間）。利用枠を超えて usage credits を使うと、主の会話も 5 分になる。TTL は `promptCacheTtl`・`CLAUDE_CODE_PROMPT_CACHE_TTL`（主の会話）と `subagentPromptCacheTtl`・`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`（それ以外）で選べる（docs cf8ad11 の prompt caching のページの「Which TTL each request gets」L42013〜L42027 と「Choose the TTL yourself」L42029〜L42034。5536db3 にも同じ記述がある）。TTL を選ぶ制御が重なると、`FORCE_PROMPT_CACHING_5M=1`（両方の区分を 5 分）、区分の環境変数、区分の設定、サブエージェントの frontmatter の `cacheTtl`、`ENABLE_PROMPT_CACHING_1H=1`（両方の区分を 1 時間。API キー・Bedrock などで 1 時間を選ぶ変数。changelog L10288）、区分の既定、の順に最初に当たったものを使う（L42038〜L42045）。主の会話の cache 書き込みの TTL は、`claude -p "hello" --output-format json` の `usage.cache_creation` の `ephemeral_1h_input_tokens`・`ephemeral_5m_input_tokens` で確かめられる（L42049）。transcript の usage の `cache_creation` にも同じ 2 つのキーがある（本環境の transcript（2026-10-24 の最新のファイル）で、キーの名前だけ確かめた）。ゲートウェイの背後で 1 時間にするには、ゲートウェイが `anthropic-beta` ヘッダを転送する必要があり、Bedrock では 1 時間の TTL が使えるかがモデルで違う（L42051〜L42055）。職場（ゲートウェイの credential）は、設定していなければ 5 分になる見込みである（下の対話のアイドル時の compaction の箇条と同じ理由。認証の方法が分岐 L なら、主の会話は 1 時間になりうる。§5 の認証の方法の分岐）。計画書 Phase 2「分析指標」の見なし費用は、TTL 別の内訳を使わない場合と内訳の無い行を、この既定の TTL の単価で計算する
- `tool_decision` イベントには cc 2.1.301 から `permission_mode` と `classifier_verdict` が付き、auto mode の分類器が判定した操作を、permission の規則による判定と見分けられる（changelog 2.1.301）。2.1.302 の実機では、auto mode の Bash 等の判定に `allow` が付き、読み取り等の既定の許可で決まる操作（Read・Glob・Skill）と default mode では付かなかった。サーバー側チェックでも自前の分類器リクエストでも同じ値なので、自前に落ちたかは traces の span で見る（§5、1-8 §8.3.3）。分類器が block したときに合致した組み込みの規則の名前を入れる `classifier_category`（`OTEL_LOG_TOOL_DETAILS=1` のときだけ）も 2.1.301 で加わり、多くの block で欠けていた不具合が 2.1.302 で直った（block される操作を試しておらず、未観測。1-8 §8.2 D40）。2.1.307 からは、分類器の block を `safety_event` の `category`（`auto_mode_block`・`auto_mode_no_verdict`）でも見られる（上の表。実機では未観測）。docs は、`tool_decision` の `source: "config"` の出どころに分類器の判定を含めるので、`config` を「規則による判定」と読む集計は分類器の判定を含む。`classifier_category` は、オンラインの docs では、2.1.302 以降、サーバー側の分類器の review が決めた block にも付く（cf8ad11 は、Claude Code が自分で分類器のリクエストを送ったときを条件に挙げる。1-9 D56）
- サブエージェントの `agent_id`・`parent_agent_id` と、tool のイベントの `request_id`（cc 2.1.310 以降。docs は「v2.1.310 以降」と書き、changelog 2.1.310 には記載が無い。1-10 D66）: `agent_id` は、イベントを出したサブエージェントの ID で、サブエージェントの API と tool のイベント、`assistant_response`、`subagent_completed` に付く。メインのセッションと in-process の teammate のイベントには付かない。サブエージェントの span の `agent_id` は、この値と同じか、先頭の `a` の後にラベルを足した値（`acompact-` で始まる形）になる。`parent_agent_id` は、そのサブエージェントを起動した（か最後に resume した）agent の `agent_id` で、それがメインのセッションなら付かない。`tool_result`・`tool_decision` の `request_id` は、その tool の呼び出しを含んだ API の応答の `request_id` で、その応答に request ID が無いときと、どの API の応答にも含まれない呼び出しでは付かない。2.1.310 の実機（`-p`。サブエージェント 1 つ）では、`agent_id` の値が span の `agent_id` と transcript のサブエージェントのファイルの id と一致し、tool のイベントの `request_id` は同じ run の `api_request` の `request_id` と一致した。並列・入れ子のサブエージェントと対話モードは確かめていない（1-10 §3.2・§5.3）。2.1.309 以前の行には付かないので、版で区切って扱う（列に持つかは計画書 Phase 2「データモデル」で決める）。職場で `request_id` が付くかは、`api_request` と同じくヘッダ次第である（§5 の `request_id` の取得元の行）
- 対話のアイドル時の compaction（changelog では 2.1.299 の項で追加。settings のキー `idleCompaction` と `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` が効くのは v2.1.290 以降）は、docs の 6 つの条件（対話の端末のセッション（2.1.310 時点の docs では、VS Code の拡張と desktop app も。この箇条の後ろ）、`autoCompactEnabled` が on であること、1 時間の prompt cache の TTL、Anthropic から feature flag を取得できること、会話が閾値（既定 200K token）以上、最後の要求から約 54 分の時点で端末が起きていること）がそろうと既定で動く。条件の一覧は 2026-10-24 の取得版（ローカル docs の commit 5536db3）から 6 つで、それより前の取得版は `autoCompactEnabled` を除く 5 つだった（auto-compact を切るとアイドル時の compaction も止まることは、それより前の docs の本文にもある。1-10 D70）。2.1.310 時点の docs（ed2bfc5）では、端末の対話に加えて、VS Code の拡張の chat panel と desktop app の Code タブでも、Anthropic が選んだアカウントでは動く。そこでは、次のメッセージが最後の要求から 1 時間以上後のときだけ、用意した要約で compact する（1-10 D70）。`compaction` イベントの `trigger` は `auto`、そのリクエストは `query_source=compact` で、長い会話を放置しただけで増えうる。実機では観測していない。LLM ゲートウェイ環境では、ゲートウェイの credential（`ANTHROPIC_AUTH_TOKEN`・`ANTHROPIC_API_KEY`・`apiKeyHelper`）で認証するなら、動かない見込みである（J-26）。cc が自分から 1 時間の TTL を求めるのは Claude の subscription の利用の中だけで、ゲートウェイの credential による利用はそれに当たらない見込みなので、TTL は既定で 5 分になる（1 時間にするには、`promptCacheTtl` を設定し、ゲートウェイがその `anthropic-beta` を転送し、Bedrock の上流のモデルが 1 時間に対応している必要がある。docs）。認証が `ANTHROPIC_AUTH_TOKEN` だけなら、feature flag を取得する credential も無い（docs）。職場の認証の方法は未確認である（[§5 の「認証の方法の分岐」](#sec-5-auth)。1-8 §8.2 D49）
- `api_request` の `attempt` は、初回を含む試行の数で、streaming の失敗の後に Claude Code がリクエストを出し直すたびに 1 から数え直す（docs 2.1.296 時点で定義が書き直された。以前は「試行の総数（1 なら再試行なし）」。1-8 §7.2 D31）。`attempt` が 1 でも、出し直しが無かったとは言えない
- `claude_code.at_mention` は、プロンプトを 1 回読み込むごとに、`mention_type` が `agent` のものと `mcp_resource` のものを、それぞれ最大 100 件まで記録する（changelog 2.1.293。docs 2.1.296 時点で明記。1-8 §7.2 D30）。件数の集計には使わない
- `/clear` 専用のイベントは無い。`/clear` で `session.id` が新しくなる。`/clear` の実行時に `user_prompt` が出るかは docs に明記がない（V-8）。出ない場合は `SessionStart` hook の `source`（`clear` / `compact`）で区切りを記録する（v2.1 §4.5）
- サブエージェントも自身のリクエストを送ってプランの利用量を消費する。`/usage` などの利用量内訳でサブエージェントの割合が見られる（costs / sub-agents ページ。問い②の補助）

## 2. 思考トークン

- `api_request` にも metrics にも、思考トークンだけを示す属性は無い
- `api_request.output_tokens` に思考分が含まれるかは docs に明記がなく、**含まれる見込み**（課金上は output として扱われる）。1-2 で V-2a（transcript 突合）→ V-2b（応答ボディ）の順に確かめる
- 生の API ボディを出す `OTEL_LOG_RAW_API_BODIES` でも、思考の本文は必ず伏せられる
- transcript の `message.usage.output_tokens_details.thinking_tokens` に思考トークン数がある（思考の本文は空で、トークン数のみ。Phase 0 に cc 2.1.282 で実測）。同じエントリの `requestId` は OTel の `request_id` と同じ値（docs 明記）。`request_id` は API が返したときだけ付くので、突合できない行が出る前提で集計する

## 3. 作業分類に使える属性

- ネイティブに使える代理指標: `skill.name`、`command_name`、`query_source`、`effort`、`workflow.name`
- `skill.name` は、`api_request` と token / cost metrics ではユーザ定義 skill も元の名前で出る。`skill_activated` イベントでは、ユーザ定義 skill も `"custom_skill"` に置き換わる（`OTEL_LOG_TOOL_DETAILS=1` で元の名前）。third-party plugin の skill は既定で `"third-party"` になる。skill の終了後も `skill.name` が付き続けるかは docs に記述がない（V-12）
- `agent.name` は、既定ではユーザ定義 agent だと `"custom"` に置き換わる。`OTEL_LOG_TOOL_DETAILS=1` で実名になり、v2.1.273 以降は metrics と `api_request` / `api_error` / `api_refusal` でも実名になる。`subagent_completed` の `agent_type` も同じ規則（1-8 §2.2 D3）。cc 2.1.310 の実機（`-p`）で、metrics・`api_request`・`subagent_completed` がこの規則どおりであることを確かめた（`api_error`・`api_refusal` は確かめていない。[1-3 §5.1](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-5-1)）
- `plugin.name`・`mcp_server.name`（ユーザ設定の MCP server は既定で `"custom"`）・`mcp_tool.name` も、同じフラグで実名になる
  - 実機（cc 2.1.310 の `-p`）では、フラグが無効でも traces の `claude_code.tool` span にユーザ設定の MCP の server・tool の実名が出て（docs と食い違う）、並列に呼んだ MCP の tool の名前は 1 つのリクエストに 1 つしか付かなかった（docs に無い。[1-3 §5.1](../01.基礎調査/03.作業分類タグ方式/調査報告書.md#sec-5-1-docs)）
- `OTEL_RESOURCE_ATTRIBUTES` は起動時に固定される**見込み**（docs に明記なし。OTel の一般的な仕組みからの推定。1-3 で確認）。プロジェクト設定でも有効なので、リポジトリ単位の固定ラベルには使える
- hook 入力の `prompt_id` は OTel の `prompt.id` と一致する（v2.1.196 以降。最初のプロンプトより前は無い）。hook でラベルを書き出す方式は、時刻ではなく `prompt_id` で突合できる。cc が自分で始めたターン（§1 の `user_prompt` の行）で `prompt_id` が付くかは docs に書かれていない（Phase 3 で確かめる）
- command・HTTP hook の `onFailure: "block"`（cc 2.1.295 以降）は、hook の失敗（起動しない、想定外の終了コード、HTTP の 2xx 以外、タイムアウトなど）を、その event での終了コード 2 と同じ扱い（`PermissionRequest` では拒否）にする。`Stop` 系と background の hook（`async`・`asyncRewake`）には効かない。`onFailure` を書かないときは、多くの event で `"continue"` と同じく操作が進む。例外は Git Bash の無い Windows の `PreToolUse`・`PermissionRequest` の command hook（`shell` を書かない shell 形式。cc 2.1.309 からは `"shell": "powershell"` の hook も。次の項）で、書かなくても、失敗するとツール呼び出しを止めうる（docs 2026-10-18 取得版。docs 2.1.296 時点では「既定は `"continue"`」と明記されていた（1-8 §7.2 D29）が、command hook の `onFailure` の行と「Block the action when a hook fails」の節からこの語が消えた。HTTP hook の `onFailure` の行には「`"continue"`, the default」が残っていて、docs の中で書き方がそろっていない）。`shell` を書かない shell 形式の hook が Git Bash の無い Windows で PowerShell で動くこと（`shell` の既定）は、以前の docs からある。Bash 用の script は、そのままでは動かないことがある。docs 2026-10-18 取得版で変わったのは、上の `onFailure` の既定の語の削除と例外の注、その直し方を挙げる「Failed hooks on Windows without Git Bash」の節である。節の直し方のうち、Git Bash の有無に依らずに動かす書き方は 2 つある。hook が 1 つの `.exe` を動かすなら exec 形式（`command` に実行ファイル、`args` に引数。`args` があると `shell` は無視される）、PowerShell 用の script なら `"shell": "powershell"` で書く。Windows の exec 形式は、`command` が `.exe` などの実行ファイルに解決する必要があり、npm・npx などの `.cmd`・`.bat` の shim はそのままでは起動できない（`node` にスクリプトのパスを渡す形にする。docs の exec 形式の節）。Bash 用の script のまま使うなら、Git for Windows を入れる（入っていても cc が見つけない場所なら `CLAUDE_CODE_GIT_BASH_PATH` で指す）。タグ付けの hook（タグ案 L1 の `UserPromptSubmit`）は上の例外に入らないので、`"onFailure": "block"` を付けずに fail-open で使う方針は変わらない（計画書 Phase 2「L1 の hook の既定の書き方」）
- PowerShell で動く hook（cc 2.1.309。changelog とオンラインの hooks ページ。1-9 D60）: hook のプログラムが終了コード 2 で終わると止める（止めない不具合が 2.1.309 で直った。それより前の版では止めないことがあり、いつの版からか、`powershell.exe` の exec 形式も当たるかは changelog に無い。changelog は event を限っていない）。`UserPromptSubmit` の終了コード 2 はプロンプトを止め、Claude に届かない（docs の event 別の表。shell による例外は書いていない）。`onFailure` が扱う失敗は、起動できない、0 と 2 以外の終了コード、HTTP の 2xx 以外、タイムアウト、出力の不正で、終了コード 2 は失敗に入らないので、`onFailure` は終了コード 2 に効かない。Git for Windows の無い Windows で、`"shell": "powershell"` の `PreToolUse`・`PermissionRequest` の hook が失敗しても通していた不具合も直った（上の例外に入る）。オンラインの hooks ページは、失敗で止める PowerShell の hook（guard hook）に、`"onFailure": "block"` と `"shell": "powershell"` を付けるよう勧める（`onFailure` を書かないと、Git for Windows を入れて Git Bash が見つかった後は、失敗で止めなくなるため）。この勧めは失敗で止める hook のもので、L1 には当たらない。L1 は、どの失敗（スクリプトが見つからない・例外・タイムアウト）でも終了コードが 2 にならない作りにし、スクリプトが自分で終える経路は 0 で終える（起動できない・0 と 2 以外の終了コード・タイムアウトは失敗で、`"onFailure": "continue"` なら止めない。計画書 Phase 2「[L1 の hook の既定の書き方](活動計画書.md#sec-p2-l1-hook)」）。PowerShell で動く `UserPromptSubmit` の hook が終了コード 2 でプロンプトを止めることは、実機では確かめていない（L1 の PowerShell の試作の hook を作るときに、Phase 3 で確かめる。1-9 §5）
- PowerShell で動く hook の、引用符で囲んだ文字列だけの command（2.1.310 時点の docs と changelog。1-10 D68）: PowerShell は、引用符付きのパスなど、引用符で囲んだ文字列だけの command を、実行せずにその文字列として出力する（docs の hooks の「PowerShell started no program」。2026-10-25 の取得版から）。docs の直し方は、`.ps1`・`.cmd`・`.bat` や変数を含むパスの `.exe` を動かすなら `"shell": "powershell"` のまま引用符付きのパスの前に `&` を置き、`$` を含まないパスの `.exe` 1 つなら内側の引用符を外して exec 形式にする、である。Git Bash の無い Windows で、この形の command の `PreToolUse`・`PermissionRequest` の hook が tool call を通していた不具合は、2.1.310 で直った（changelog）
- command hook は、cc 2.1.296 以降、終了時に所要時間を debug log に hook ごとに 1 行出す（docs 2.1.296 時点。1-8 §7.2 D28）。OTel の `hook_execution_complete.total_duration_ms` は同じ event の全 hook の経過時間なので、hook ごとの時間はこちらで見る。この行は debug を有効にしたセッション（`--debug-file` を付けて起動するなど）にしか出ないので、日常のセッションでは使えない（1-8 §8.3.5）
- `plugin_loaded` の `has_hooks` は、hooks module（Mod）を持つ plugin（組み込みの plugin を含む）で false になる不具合が、cc 2.1.299 で直った（changelog。1-8 §8.2 D41）。2.1.299 より前のデータでは、`has_hooks` を hooks module の有無の根拠にしない（計画書 Phase 3 で、plugin の構成を `plugin_loaded`・`hook_registered` で記録する）

## 4. 構成・設定上の制約

- cc には OTLP プロトコルの既定値が無く、明示指定が必要。`http/json` を選べば protobuf のデコードが不要になり、Node.js で受信サーバを自作しやすい（v2.1 は `http/protobuf`）
- `prometheus` exporter は各セッションがポート 9464 を占有するため、複数セッションを同時に起動すると衝突する
- metrics の temporality の既定は `delta`（前回送信からの増分）。自作で保存する場合は受け取った値を足し合わせるだけで済むため、既定の `delta` のまま使える
- OTel 変数はユーザ settings（`~/.claude/settings.json`）の `env` で設定でき、起動方法に関係なく効く。project / local settings で無視されるのは、有効化・送信先・内容記録の変数に限られる（cc 2.1.282 以降）。`OTEL_RESOURCE_ATTRIBUTES` と送信間隔などは有効（v2.1 R-2）
- 設定値は起動時に読み込まれるため、変更後は cc の再起動が必要
- `OTEL_LOG_TOOL_CONTENT=1` は、cc 2.1.283 から MCP ツール・WebFetch・WebSearch の結果も `tool.output` span event（`claude_code.tool` span に付く）に記録する。外部から取ったページ全文等も span に残る。`tool_result` イベントには結果の本文を持つ属性が無い（1-8 §2.2 D5。計画書 §7 #2 の判断材料）

- `OTEL_LOGRECORD_ATTRIBUTE_COUNT_LIMIT` で属性の数の上限を下げていると、cc 2.1.301 では新しい属性に押し出されて `tool_use_id`・`tool_source`・`tool_parameters` が落ちた（2.1.302 で修正。changelog。1-8 §8.2 D40）。上限を下げるなら、2.1.302 以降にするか、落ちる属性を確かめる。cc 2.1.310 からは、上限を `tool_decision` の属性の数より下げたとき、SDK が先に落とす順が `parent_agent_id` → `agent_id` → `request_id` → `permission_mode` → `classifier_category` → `classifier_verdict` になった（docs。1-10 D66）。上限を下げると、2.1.310 で加わった 3 つ（§1 の表の下）が最初に落ちる

## 5. 職場環境で差が出る点

職場環境は、cc → 社内 LLM ゲートウェイ（LiteLLM。`ANTHROPIC_BASE_URL` で指定する Anthropic 形式の接続で、cc の Bedrock モードは使わない。2026-10-18 の作業指示者の回答）→ Amazon Bedrock の経路で使う。cc はこの形のゲートウェイを Claude API として扱い、ゲートウェイの先（Bedrock）を知らない（docs。裁定待ち事項 J-26）。このため cc の Bedrock モードの docs の差（Bedrock の model ID など）は当たらず、職場は third-party provider に当たらない見込みである（docs の third-party provider の列挙に入らない）。差は `ANTHROPIC_BASE_URL` のゲートウェイについての docs の条件で決まる。その条件から見た差は次の表のとおりで、docs で決まらない行は Phase 7 で確かめる（v2.1 §9.1〜§9.6 はデプロイ形態ごとの整理で、多くは third-party provider が対象）。ただし docs の列挙は例示で、ゲートウェイを通すときは機能の可否をゲートウェイの先の provider に合わせるという note もあるので、表の見込みは Phase 7 で確かめる前提で使う。識別属性などの項目は、ゲートウェイへの認証の方法で結論が分かれる。職場の認証の方法は未確認で、分岐は表の下の「[認証の方法の分岐](#sec-5-auth)」にまとめた。不明点（認証の方法、思考トークンの内訳、社内プロキシによる改変、ループバック宛て送信の可否、transcript の `requestId`、Claude Mods の可否、Git Bash の有無、auto mode の分類器のチェックがゲートウェイ経由でもサーバー側に乗るか、ゲートウェイが tool search などの要求のフィールドを拒否するか）は計画書 Phase 7。職場環境の確認は第二のゴール（LLM ゲートウェイ環境への対応）で行う。呼び名は計画書 §1.4。

**認証の方法の分岐**: 職場がどれに当たるかは未確認である。Phase 7 の職場の確認の最初に、`/status` の Status タブで確かめる。見るのは、`Anthropic base URL` の行があるか（ゲートウェイを指しているか）と、`Auth token`・`API key`・`Login method` のどの行が、どの変数を名指しして出るか（どの credential が有効か）である（docs）。記録するのは、`Anthropic base URL` の行の有無と、使われている行に出る変数の名前（または `apiKeyHelper`・`Login method` の別）だけで、値と画面の写し（貼り付け・撮影）は残さない。

| 分岐 | 職場の設定 | docs の扱い | `/status` での見え方 |
|---|---|---|---|
| T | `ANTHROPIC_AUTH_TOKEN` だけ（API key なし） | 要求はこの credential を運び、claude.ai のログインの代わりになる。feature flag を取得する credential が無い | `Auth token` の行が `ANTHROPIC_AUTH_TOKEN` を名指しし、`API key` の行が無い（`Login method` の行が並んでもよい） |
| K | `ANTHROPIC_API_KEY` か `apiKeyHelper`（`ANTHROPIC_AUTH_TOKEN` との併用を含む） | 要求はこの credential を運ぶ。feature flag を取得できるかは書いていない | `API key` の行が `ANTHROPIC_API_KEY` か `apiKeyHelper` を名指しし、not in use の印が無い（`Auth token` の行が並んでもよい） |
| L | 資格情報の変数なし（保存済みの claude.ai のログインのまま） | 要求はゲートウェイを通るが、有効な credential は claude.ai のログインのままで、subscription の利用上限と課金が当たる | `Login method` の行が claude.ai のアカウントを示し、T・K の変数を名指しする行が無いか、あっても not in use の印が付く |

- 次の場合は分岐を決めない

- 「不明」のときは、下の表の項目の読み方を保留し（結果は記録しておく）、分岐に依らない項目（`client_request_id`・`request_id` の有無など）は進める
