## 1. 取れるシグナルと属性

- GenAI semconv（OTel の生成 AI 向け semantic conventions）との対応: cc は `gen_ai.usage.*` を出さない（cc 2.1.302 でも出ない。トークン数は引き続き独自名の属性から取る）。`cache_read_tokens` は `gen_ai.usage.cache_read.input_tokens`、`cache_creation_tokens` は `gen_ai.usage.cache_write.input_tokens` に対応する。semconv の `gen_ai.usage.input_tokens` はキャッシュ分を含むので、cc の 3 種（`input_tokens`・`cache_read_tokens`・`cache_creation_tokens`）の合計に当たる（1-8 §2.1 D1、1-7 §7.1）。span の `gen_ai.*` 5 属性は実測時点の docs にもあった（1-8 §2.2）。docs の span の属性の表は、2026-10-17 取得版でもこの 5 属性のままである
- span の GenAI 属性は、cc 2.1.296 までは表の 5 つだけだった（2.1.283・2.1.287・2.1.296 の実機）。cc 2.1.300 から、`gen_ai.provider.name`（値は `anthropic`。interaction・llm_request・tool・tool.blocked_on_user・tool.execution の 5 種の span）、`gen_ai.tool.name`（tool span。既存の `tool_name` と同じ値）、`gen_ai.conversation.id`（5 種の span）が加わった（changelog 2.1.300 と 2.1.302 の実機）。`gen_ai.operation.name`（interaction は `invoke_agent`、tool は `execute_tool`。llm_request には付かない）は、2.1.296 では出ず、2.1.302 では出た（changelog に名前が無く、出始めた版は確かめていない）。changelog 2.1.300 にある `error.type` は、エラーの無い run だけで、観測していない。`gen_ai.system` は 2.1.302 でも `gen_ai.provider.name` と並んで出る。`gen_ai.conversation.id` は、2.1.302 の実機で、メインの span では `session.id` と同じ値、サブエージェントの span ではそのサブエージェントの `agent_id` と同じ値だった（`session.id` を対応表で写すときの扱いは計画書 Phase 2「データモデル」）。logs のイベントと metrics には `gen_ai.*` は付かない（1-8 §8.3.1、1-7 §2.4）
- `api_request` には cc 2.1.300 から、cache 書き込みのトークン数の TTL 別の内訳 `cache_creation_5m_tokens`・`cache_creation_1h_tokens`（int）が付く（changelog 2.1.300）。2.1.302 の実機では全件に付き、2 つの和は `cache_creation_tokens` と一致した。docs は、metrics の `token.usage` の `cacheCreation` を 5 分と 1 時間の書き込みの合算と明記している（metrics では分けられない）。単価が TTL で違う場合の費用の計算に使える（1-8 §8.2 D38）
- `tool_decision` イベントには cc 2.1.301 から `permission_mode` と `classifier_verdict` が付き、auto mode の分類器が判定した操作を、permission の規則による判定と見分けられる（changelog 2.1.301）。2.1.302 の実機では、auto mode の Bash 等の判定に `allow` が付き、読み取り等の既定の許可で決まる操作（Read・Glob・Skill）と default mode では付かなかった。サーバー側チェックでも自前の分類器リクエストでも同じ値なので、自前に落ちたかは traces の span で見る（§5、1-8 §8.3.3）。分類器が block したときに合致した組み込みの規則の名前を入れる `classifier_category`（`OTEL_LOG_TOOL_DETAILS=1` のときだけ）も 2.1.301 で加わり、多くの block で欠けていた不具合が 2.1.302 で直った（block される操作を試しておらず、未観測。1-8 §8.2 D40）
- 対話のアイドル時の compaction（changelog では 2.1.299 の項で追加。settings のキー `idleCompaction` と `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` が効くのは v2.1.290 以降）は、docs の 5 つの条件（対話の端末のセッション、1 時間の prompt cache の TTL、Anthropic から feature flag を取得できること、会話が閾値（既定 200K token）以上、最後の要求から約 54 分の時点で端末が起きていること）がそろうと既定で動く。`compaction` イベントの `trigger` は `auto`、そのリクエストは `query_source=compact` で、長い会話を放置しただけで増えうる。実機では観測していない。職場環境は feature flag の取得や 1 時間 TTL の条件に当たらず、動かない可能性があると見込む（1-8 §8.2 D49）
- `api_request` の `attempt` は、初回を含む試行の数で、streaming の失敗の後に Claude Code がリクエストを出し直すたびに 1 から数え直す（docs 2.1.296 時点で定義が書き直された。以前は「試行の総数（1 なら再試行なし）」。1-8 §7.2 D31）。`attempt` が 1 でも、出し直しが無かったとは言えない
- `claude_code.at_mention` は、プロンプトを 1 回読み込むごとに、`mention_type` が `agent` のものと `mcp_resource` のものを、それぞれ最大 100 件まで記録する（changelog 2.1.293。docs 2.1.296 時点で明記。1-8 §7.2 D30）。件数の集計には使わない
- `/clear` 専用のイベントは無い。`/clear` で `session.id` が新しくなる。`/clear` の実行時に `user_prompt` が出るかは docs に明記がない（V-8）。出ない場合は `SessionStart` hook の `source`（`clear` / `compact`）で区切りを記録する（v2.1 §4.5）
- サブエージェントも自身のリクエストを送ってプランの利用量を消費する。`/usage` などの利用量内訳でサブエージェントの割合が見られる（costs / sub-agents ページ。問い②の補助）

## 2. 思考トークン

- `api_request` にも metrics にも、思考トークンだけを示す属性は無い
- `api_request.output_tokens` に思考分が含まれるかは docs に明記がなく、**含まれる見込み**（課金上は output として扱われる）。1-2 で V-2a（transcript 突合）→ V-2b（応答ボディ）の順に確かめる
- 生の API ボディを出す `OTEL_LOG_RAW_API_BODIES` でも、思考の本文は必ず伏せられる
- transcript の `message.usage.output_tokens_details.thinking_tokens` に思考トークン数がある（思考の本文は空で、トークン数のみ。Phase 0 に cc 2.1.282 で実測）。同じエントリの `requestId` は OTel の `request_id` と同じ値（docs 明記）。`request_id` は API が返したときだけ付くので、突合できない行が出る前提で集計する
- transcript には cc 2.1.300 から、API リクエストごとの system prompt・tools・parameters が、新しい記録型 `api-request`・`api-request-shape`・`api-request-blob` で記録される（changelog 2.1.300。assistant の行に `requestRef` が付く。system と tools の全文が入る shape は、セッションの中で 1 回だけ書かれる）。2.1.302 の実機では、短い `-p` の run でファイルのサイズが約 1.5〜2 倍になった。記録されるのはリクエストの側で、応答の usage ではないので、思考トークン数の取り方は変わらない（`thinking_tokens` と `requestId` の突合は 2.1.302 でも成り立ち、新しい記録型は要らなかった）。system prompt にはユーザの指示ファイル等の内容が入りうる見込みで、取込の扱いは計画書 Phase 2「データ保全とプライバシー」で決める（1-8 §8.3.4）
- 取得経路（transcript 突合 / 応答ボディ）の比較は計画書 §2.1

## 3. 作業分類に使える属性

- ネイティブに使える代理指標: `skill.name`、`command_name`、`query_source`、`effort`、`workflow.name`
- `skill.name` は、`api_request` と token / cost metrics ではユーザ定義 skill も元の名前で出る。`skill_activated` イベントでは、ユーザ定義 skill も `"custom_skill"` に置き換わる（`OTEL_LOG_TOOL_DETAILS=1` で元の名前）。third-party plugin の skill は既定で `"third-party"` になる。skill の終了後も `skill.name` が付き続けるかは docs に記述がない（V-12）
- `agent.name` は、既定ではユーザ定義 agent だと `"custom"` に置き換わる。`OTEL_LOG_TOOL_DETAILS=1` で実名になり、v2.1.273 以降は metrics と `api_request` / `api_error` / `api_refusal` でも実名になる。`subagent_completed` の `agent_type` も同じ規則。実機での確認は、計画書 §7 #2 の判断後に行う（1-8 §2.2 D3・§6）
- `plugin.name`・`mcp_server.name`（ユーザ設定の MCP server は既定で `"custom"`）・`mcp_tool.name` も、同じフラグで実名になる
- `OTEL_RESOURCE_ATTRIBUTES` は起動時に固定される**見込み**（docs に明記なし。OTel の一般的な仕組みからの推定。1-3 で確認）。プロジェクト設定でも有効なので、リポジトリ単位の固定ラベルには使える
- hook 入力の `prompt_id` は OTel の `prompt.id` と一致する（v2.1.196 以降。最初のプロンプトより前は無い）。hook でラベルを書き出す方式は、時刻ではなく `prompt_id` で突合できる。cc が自分で始めたターン（§1 の `user_prompt` の行）で `prompt_id` が付くかは docs に書かれていない（Phase 3 で確かめる）
- command・HTTP hook の `onFailure: "block"`（cc 2.1.295 以降）は、hook の失敗（起動しない、想定外の終了コード、HTTP の 2xx 以外、タイムアウトなど）を、その event での終了コード 2 と同じ扱い（`PermissionRequest` では拒否）にする。`Stop` 系と background の hook（`async`・`asyncRewake`）には効かない。既定は `"continue"`（docs 2.1.296 時点で明記。1-8 §7.2 D29）。タグ付けの hook には付けない（計画書 Phase 2「作業分類タグ」）
- command hook は、cc 2.1.296 以降、終了時に所要時間を debug log に hook ごとに 1 行出す（docs 2.1.296 時点。1-8 §7.2 D28）。OTel の `hook_execution_complete.total_duration_ms` は同じ event の全 hook の経過時間なので、hook ごとの時間はこちらで見る。この行は debug を有効にしたセッション（`--debug-file` を付けて起動するなど）にしか出ないので、日常のセッションでは使えない（1-8 §8.3.5）
- `plugin_loaded` の `has_hooks` は、hooks module（Mod）を持つ plugin（組み込みの plugin を含む）で false になる不具合が、cc 2.1.299 で直った（changelog。1-8 §8.2 D41）。2.1.299 より前のデータでは、`has_hooks` を hooks module の有無の根拠にしない（計画書 Phase 3 で、plugin の構成を `plugin_loaded`・`hook_registered` で記録する）

## 4. 構成・設定上の制約

- cc には OTLP プロトコルの既定値が無く、明示指定が必要。`http/json` を選べば protobuf のデコードが不要になり、Node.js で受信サーバを自作しやすい（v2.1 は `http/protobuf`）
- `prometheus` exporter は各セッションがポート 9464 を占有するため、複数セッションを同時に起動すると衝突する
- metrics の temporality の既定は `delta`（前回送信からの増分）。自作で保存する場合は受け取った値を足し合わせるだけで済むため、既定の `delta` のまま使える
- OTel 変数はユーザ settings（`~/.claude/settings.json`）の `env` で設定でき、起動方法に関係なく効く。project / local settings で無視されるのは、有効化・送信先・内容記録の変数に限られる（cc 2.1.282 以降）。`OTEL_RESOURCE_ATTRIBUTES` と送信間隔などは有効（v2.1 R-2）
- 設定値は起動時に読み込まれるため、変更後は cc の再起動が必要
- `OTEL_LOG_TOOL_CONTENT=1` は、cc 2.1.283 から MCP ツール・WebFetch・WebSearch の結果も `tool.output` span event（`claude_code.tool` span に付く）に記録する。外部から取ったページ全文等も span に残る。`tool_result` イベントには結果の本文を持つ属性が無い（1-8 §2.2 D5。計画書 §7 #2 の判断材料）
- `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` が未設定のとき、Haiku 4.5・Sonnet 5・Opus 4.7 とそれ以前の同系統のモデルは完全版の system prompt を、それより新しいモデル（Haiku 5.5・Sonnet 5.5・Opus 5.5 等）は短縮版を使う（docs 2.1.295 時点で明記。changelog に対応する行は無い。1-8 §7.2）。モデル間で入力・キャッシュ書き込みのトークンを比べると、system prompt の差が交ざる。比較実験ではこの変数を `0` か `1` に固定するか、交絡として注記する（計画書 Phase 2「分析指標」）
- `OTEL_LOGRECORD_ATTRIBUTE_COUNT_LIMIT` で属性の数の上限を下げていると、cc 2.1.301 では新しい属性に押し出されて `tool_use_id`・`tool_source`・`tool_parameters` が落ちた（2.1.302 で修正。changelog。1-8 §8.2 D40）。上限を下げるなら、2.1.302 以降にするか、落ちる属性を確かめる

## 5. 職場環境で差が出る点

職場環境は、cc → 社内 LLM ゲートウェイ（LiteLLM 等の社内プロキシ。`ANTHROPIC_BEDROCK_BASE_URL` / `ANTHROPIC_BASE_URL` で指定）→ Amazon Bedrock の経路で使う。docs で確定している差は次のとおり（詳細は v2.1 §9.1〜§9.6）。不明点（思考トークンの内訳、社内プロキシによる改変、ループバック宛て送信の可否、Node.js の版、transcript の `requestId`、Claude Mods の可否、auto mode の分類器のチェックがゲートウェイ経由でもサーバー側に乗るか）は計画書 §2.2。

| 項目 | 職場環境での差 |
|---|---|
| 利用者の識別属性 | `user.id` と `session.id` しか埋まらない |
| `client_request_id` | 付かない（対応付けには `request_id` を使う） |
| `request_id` の取得元 | v2.1.282 以降、`request-id` ヘッダの無い応答（Bedrock など）では `x-amzn-requestid` の値が入る（2026-09-27 版 docs の Event correlation attributes で明記。v2.1 §9.3 では【要確認】のまま）。`request_id` は `api_request` / `api_error` / `api_refusal` / `assistant_response` / `api_response_body` に付き、`llm_request` span の同名属性と一致する（1-8 §2.2 D7）。Bedrock 形式の transcript で `requestId` が欠ける問題は、これでは解消しない |
| `internal_error` イベント | 出ない |
| トレースのコンテキスト | `traceparent` はサードパーティのプロバイダには送られない（独自プロキシへは `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1`） |
