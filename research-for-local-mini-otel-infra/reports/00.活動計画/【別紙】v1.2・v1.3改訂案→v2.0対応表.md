## 1. v1.2 からの変更の要点

**構成（J-27）**

- ゴールを 3 段に分けた。第一は本環境で仕組みを作る（Phase 0〜6）、第二は職場環境（LLM ゲートウェイ環境）への対応（Phase 7）、第三は WSL + Docker 環境への対応（次の活動）である。段は直列に進める
- Phase 7「職場環境の確認と差の吸収」を足した。v1.2 で Phase 3 の後半にあった職場環境の確認と手順書、Phase 4 の職場での継続の確認は、Phase 7 に移った。Phase 3 は本環境だけになった
- 成功基準を段ごとに分けた。§7 #7（両環境のデータを合算するか）と #8（職場で思考トークンの内訳が取れない場合）の時期は Phase 7 になった
- Phase 2 の「両環境への対応」を「第二のゴールへの備え」に置き換えた。環境ラベル、突き合わせの鍵の欠けに耐える集計、思考案 T2 を残すこと、npm の依存を少なくすること、Git Bash に依らない hook、縮退運用を、第一のゴールの設計に含める
- §5 のリスクを、第一のゴール（§5.1）と第二のゴール（§5.2）に分けた
- 冒頭に「承認と保留」を置いた。J-7 で承認いただく対象、Q・J に依存する箇所の表、第二のゴールへ先送りにした問い（J-18 の第 2 の問い）がある

**職場環境の前提（J-24・J-26）**

- 職場の cc は `ANTHROPIC_BASE_URL` で LiteLLM を指す Anthropic 形式でつなぎ、cc の Bedrock モードは使わない（J-26）。§1.4 に呼び分け（Anthropic 環境・LLM ゲートウェイ環境・LiteLLM 環境・Bedrock 環境）を置いた
- 職場の不明点は、v1.2 の 2 点（思考トークンの内訳、社内プロキシの改変）から 8 点になった。確かめる項目は 11 行で（V-ID 別紙 §2 の職場の表）、ゲートウェイへの認証の方法を最初に確かめる
- 職場の Node.js の版は前提にしない（J-24）

**Phase 1（1-7・1-8）**

- 調査項目に 1-7（生成 AI オブザーバビリティ規格。Issue #4）と 1-8（cc 2.1.287〜2.1.302 の仕様差分）を足し、8 項目にした
- §2 の基線を、cc 2.1.283 の 1 段から 5 段にした（cc 2.1.287・2.1.296・2.1.302 の再確認。docs は 2026-10-18 取得版まで）。どの段でも、本活動が依存する属性の削除・改名は無い
- 完了条件に Q1 の承認を、完了の扱いに Q5（条件付きで完了とするか）を結び付けた

**Phase 2 の設計項目（主な追加）**

- 全体構成: 実装言語と依存の最小化（J-13）
- データモデル: 列名は cc の名前を主とし、GenAI semconv の名前は対応表で持つ（J-1）。総入力を派生の列にする。サブエージェントの `effort`・`model` は `api_request` の値を正とする。決める 4 点（`gen_ai.conversation.id`、版で増える属性、TTL 別の cache 書き込み、アイドル時の compaction）
- 作業分類タグ: Claude Mods を L1 の実装手段の候補に加えた（J-3）。cc が自分で始めたターン（J-15）、L1 の hook の既定の書き方（fail-open、Git Bash に依らない）、skill・slash command のターン、hook 自身の所要時間の記録
- 分析指標: input 系の定義、問い② の品質の指標と問い① の `/clear` 前後の結び付け、system prompt の交絡、単価の出典確認（J-17）、traces の span を集計に含めること、集計の正本と二重計上の除き方、span の費用、`quota_check` の漏れ
- データ保全とプライバシー: `prompt_text` もマスクすること、transcript の新しい記録型の扱い
- バージョン追従: 差分確認の手順、版をまたぐ集計の区切り

**Phase 3 の測定の条件（本環境）**

- 版の再確認と版の下限（J-18）、版上げ直後の扱いと版の検知、基準モデル（J-14）、Remote Control を切る計測用のセッション（J-19）、plugin の構成（J-25）、J-12 の判定、受信データの鍵が一致した割合
- 作業に、自分の所要時間を記録する L1 の試作の hook を足した（J-12 の判定に使う）

**§5・§7**

- §5.1 に、hook の stderr、Mod の不具合、plugin の構成による基準値の変化、GenAI semconv の改名の行を足した
- §5.2 に、ループバック宛て送信、Mods・command hook の制限、transcript の `requestId`、Git Bash、職場の plugin の構成、依存パッケージの脆弱性、`cost_usd`、transcript の保存期間の行を置いた
- §7 #2 に判断材料の 3 点を足した

**変わらないもの**

- 最終ゴール、問い①〜③、作るものの 4 つ、スコープ外
- Phase 0 の作業と成果物。Phase 4〜6 は小さな追加だけである（Phase 4 のタグ付けの手段に Claude Mods、Phase 5 の方式を選ぶ時期に Q1 の印、Phase 6 は本環境のデータで分析し、LLM ゲートウェイ環境のデータを足すかは §7 #7 と Phase 7 で決める）
- §7 #1〜#6 の事項、Q1〜Q5・J の質問・選択肢・推奨

**意味を変えた箇所**（J-27 と実用性 S7 による。ほかは意味を変えていない）

- 職場環境の確認を、Phase 3 から Phase 7 へ移した
- Q5 の残作業の範囲から、職場環境の確認を外した（Q5 の質問の欄の残作業の範囲だけを変え、選択肢・推奨は変えていない）
- 「両環境で動く」前提の文を、第一のゴールの備え（Phase 2「第二のゴールへの備え」）と第二のゴールの作業（Phase 7）に分けた。Mods が止められていた場合の代替と、指定したモデル ID と `api_request` の `model` がずれた場合の扱いを決める場は、Phase 2 から Phase 7 の差の吸収になった
- 集計の突き合わせの規則に、実用性 S7 の直しを入れた。突き合わせできなかった `api_request` の行（鍵が無い、片側にしか無い、値が合わない）は足さず、span を数える。鍵を選ぶ条件は「`client_request_id` があるか」から「`client_request_id` が両側にあるか」にした（片側にしか無いときは `request_id` を試す）。Phase 3・Phase 7 の受信データの記録に、鍵が両側にあり値が一致した割合を足した
- J-24 の回答で、職場の Node.js の版の不明点・リスク・お願いを消した
- J-18 の第 2 の問い（職場にも版の下限を課すか）は、第二のゴールへ先送りにした。職場の版の扱いの文には `(承認待ち: J-18)` を付けず、Phase 7 の着手前に諮る

**用語「第二のゴール」の意味の変わり目**: v1.3 改訂案までと、凍結した文書（1-1〜1-8、過去のクロスレビュー報告書）の「第二のゴール」は、WSL + Docker 環境への対応を指す。v2.0 では WSL + Docker は第三のゴールで、第二のゴールは LLM ゲートウェイ環境への対応である。v2.0 は v2.0 の意味だけを使う。
