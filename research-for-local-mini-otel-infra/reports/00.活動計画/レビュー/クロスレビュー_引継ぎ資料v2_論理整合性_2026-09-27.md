#### I1. 問題点
* **概要**: 思考トークンの内訳は「生のレスポンスボディ（`OTEL_LOG_RAW_API_BODIES`）を読むことになる【推測】」としか書かれていない。Claude Code の transcript からも取得でき、OTel イベントと `request_id` で結合できるが、この経路が扱われていない。
* **問題点**:
  1. 内訳の取得手段が、会話履歴全体を記録する内容記録フラグ（§7.1）の一択になっている
  2. V-2（R3 の確認）と §10 手順 2 が「承認を得たうえで」に依存しており、承認待ちの間は R3 を確かめられない構成になっている
  3. R-13 では transcript を「OTel を補う用途」と位置付けているのに、R3 の補完手段としての使い道が書かれていない
* **影響**:
  1. 思考トークン内訳の取得のためだけに、プライバシー影響の大きいフラグを有効にする設計判断を誘発する
  2. 必須要件 R3 の検証が不必要に後回しになる（§10 手順 2 は「後回しにしてよい」としている）
  3. effort と思考量の関係（§1.1 一次目的）の分析開始が遅れる
* **詳細**:
  1. Phase 0 の実測（cc 2.1.282）では、transcript の assistant エントリの `message.usage.output_tokens_details.thinking_tokens` に思考トークン数が入っており、同じエントリに `requestId` もある

  3. 同じ usage ブロックの `output_tokens` と `thinking_tokens` を並べれば、V-2 の前半（`output_tokens` に思考分が含まれるか）の確認材料にもなる。transcript の `output_tokens` と `api_request.output_tokens` を `requestId` で突き合わせれば、OTel 側の値が API usage と一致するかも確かめられる
* **根拠**:
  1. 作業指示者提供の Phase 0 実測事実（本レビューの判断基準 2）
  2. llms-full.txt L86351〜L86354（"`request_id` on the API events, persisted as `requestId` on the transcript's assistant entries"）。同 L86351 は transcript 形式が内部仕様でバージョン依存であることも明記

##### I1. レビューア確認: 修正案（0.9）
