# CLAUDE.md — research-for-local-mini-otel-infra

## 調査の目的

Claude Code（以下 cc）の OpenTelemetry テレメトリを、**Windows ローカルで完結する最小構成**で受信・蓄積・可視化する仕組みを構築する。

背景・ゴール・問い①〜③・前提・スコープ・フェーズ構成は `reports/00.活動計画/活動計画書.md`（以下「計画書」）を正本とする。最終的な効用は、分析結果をルート資産（「モデル選定原則」、`check-model` skill 等）へ還流させることであり、**分析そのものを目的化しない**（計画書 §1）。

## 作業時の制約

- **Windows ネイティブ・Docker 不要**で動く構成にする。WSL + Docker 前提の構成は本活動では作らない（第三のゴールとして次の活動で扱う。計画書 §1.4）
- ゴールは 3 段で、直列に進める（裁定待ち事項 J-27）。仕組みは第一のゴール（計画書 Phase 0〜6）で本環境（Anthropic 環境）に作り、第二のゴール（Phase 7）で LLM ゲートウェイ環境（社内のゲートウェイの先は Amazon Bedrock。呼び分けは計画書 §1.4）に広げる。第一のゴールの設計には、第二のゴールへの備えを含める（計画書 Phase 2「第二のゴールへの備え」）。**Claude Code は職場環境で検証しない**（確認手順書を用意し、作業指示者が実施する。計画書 Phase 7）
- 収集データを外部の SaaS・クラウドへ送らない。**収集データ（プロンプト本文等を含み得る）はコミットしない**
- 報告書（公開リポジトリに載る）には、`~/.claude` 配下のファイルの種類とキー名までを書く。認証情報・鍵のファイル名、利用統計の実数、識別子（メールアドレス・アカウント ID・request_id 等）の値は書かない
- 仕様は cc のバージョンに依存する。基線（cc と docs の版）は計画書 §2 冒頭。ただし今の基線は、1-10 で上げた cc 2.1.310・docs ed2bfc5（2026-10-26 取得）で、計画書 §2 への反映は v2.5 の案として設計書と同じ回に承認を受ける（Phase 2 の進め方の P2-4）

## 作業時の注意

- OTel の仕様に関わる作業の前に `reports/00.活動計画/【別紙】公式仕様の調査結果.md`（仕様別紙）を読む。「見込み」とある項目は事実として扱わない
- OTel の変数はユーザ settings（`~/.claude/settings.json`）の `env` に設定する。project / local settings では、有効化・送信先・内容記録の変数が無視される
  - 内容を記録する変数（`OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_ASSISTANT_RESPONSES`・`OTEL_LOG_TOOL_DETAILS`・`OTEL_LOG_TOOL_CONTENT`・`OTEL_LOG_RAW_API_BODIES`）は、取りこぼしの無い仕組みのためなら常時有効にしてよい（応答の本文も、設計・開発に寄与するなら残してよい。不要になったら消す）。ただし、他のリポジトリの作業に悪影響を与えうるもの（例: `OTEL_LOG_RAW_API_BODIES` はリクエストごとに会話履歴の全体をディスクに書く）は、ユーザ settings に置かず、調査・検証のランチャやスクリプトの中でプロセスのスコープで渡す。どれをどちらに置くかは Phase 2 の設計で決める。ユーザ settings に置くものは、Claude が手順を書き、作業指示者が設定する（2026-10-19 の作業指示者の回答）
- 収集したデータ（OTel の受信の記録、raw body の file モードの出力、検証の記録）は、repo の外の `%LOCALAPPDATA%\local-mini-otel\` の下に置く。毎回同じ場所にし、セッションごとに変わる scratchpad には置かない。V-2b の記録は `v2b\` に置き、V-2b の完了後も消さずに残す（2026-10-19 の作業指示者の回答）。repo にはコミットしない。クラウド同期（OneDrive 等）の対象のフォルダには置かない
- transcript（`~/.claude/projects/*/*.jsonl`）は cc が既定 30 日で削除する。取込の仕組みができるまでは、分析に使う transcript が残っていることを前提にしない
- 実機検証で Claude が起動する対話セッション（probe と Phase 3 の比較実験）は、Remote Control を切って起動する（`remoteControlAtStartup` を false にする JSON ファイルを `--settings` に渡す。ユーザ設定は起動時に接続するため、切らないと計測の条件が変わる。1-8 §7.3.4）。J-12 の判定に使う日常のセッションは切らない（裁定待ち事項 J-19）
- Claude が起動する計測用のセッション（probe と Phase 3 の比較実験。`-p` と対話）では、plugin の構成を、比べる相手の測定（前回の基線）と同じにする。前回の測定の後に有効になった plugin を、hook を登録しないものも含めて、`--settings` に渡す JSON ファイルの `enabledPlugins` で false にし、そのプロセスだけ無効にする（ユーザ設定は変えない。2.1.302 の再確認では、増えた 4 つをすべて無効にした）。Remote Control を切る設定と同じファイルにしてよい。ファイルは plugin の名前を含むので、repo に置かず scratchpad に置く。無効になったことは、OTel の `plugin_loaded` にそれらの plugin が出ないことと、`hook_registered` が probe の作業フォルダの hook だけになることで確かめる。有効なままだと、hook なしの条件にもその hook が走り、版の間の比較ができない。日常のセッション（J-19）は無効にせず、plugin の構成を記録する（1-8 §8.3.5、裁定待ち事項 J-25）。報告書には plugin の名前を書かない
- cc の版の追補は、1-8 に §9 として足さず、`reports/01.基礎調査/` の下に新しい番号のフォルダ（例: `09.cc<版>差分の確認/調査報告書.md`）を作って書く（1-8 は §8 までで約 10 万字になったため。2026-10-17 のクロスレビュー 人間読み手 U-I3。作業指示者の態度表明で確かめる）
- 古い文書の読み替え（J-27）: 計画書 v1.3 改訂案までの文書と、書き直していない文書（1-1〜1-8 の報告書、過去のレビュー報告書）では、「第二のゴール」は WSL + Docker 環境（計画書 v2.0 の第三のゴール）を、「Phase 3 の職場環境（の）確認」は計画書 v2.0 の Phase 7 の確認を指す。これらの文書は直さない
- クロスレビューの「作業指示者+人間読み手」の観点のレビュアーには、作業指示者が読む部分と変更点だけを読ませる。作業指示者が読む部分は、まとめ報告書の §0・§3・§5、裁定待ち事項の冒頭〜§2、計画書の「承認と保留」、対応表の別紙 §1、ブロック指摘一覧の「態度表明の区分」など、その回の作業指示者の読む道に入る箇所である。変更点は、その回の差分である。文書の全文は読ませない（2026-10-19 の作業指示者の指示。クロスレビューの所要時間を短くするため。共通の cross-review skill への反映は別の作業）
- 生きている文書（計画書・まとめ報告書・裁定待ち事項・別紙）を改訂・スリム化するときは、[`.claude/rules/living-doc-slimming.md`](.claude/rules/living-doc-slimming.md) に従う。本文は今の状態だけにし、主旨・方針・結論が途中で変わった経緯だけを追記だけの別紙へ移す（根拠は移さない）。追記だけの別紙はクロスレビューしない（2026-10-20 の作業指示者の指示）
- 作業指示者に判断を仰ぐ事項（まとめ報告書の Q、裁定待ち事項の J）には、選択肢ごとの長所と短所、承認の対象（何を承認し、何を決めないか）、Claude の推奨と決める時期（推奨を出していないならその旨）を、判断事項の表から 1 リンクで届く所にそろえて置く。参照は「1-2 §5」のような略記だけにせずリンクにする（2026-10-19、作業指示者が Q1〜Q4 を判断できなかったことを受けて）
- 本活動フォルダのテキストファイルの改行は LF にそろえる。例外は PowerShell のファイル（`.ps1`・`.psm1`・`.psd1`。UTF-8 + BOM + CRLF）と `.bat`（CP932 + CRLF・BOM なし。`.cmd` は使わない）で、`.gitattributes` が拡張子ごとに改行を決める（`.claude/rules/win-file-encoding.md` の規約に合わせた）。Markdown 等は書き込みの後に CR が 0 であることを確かめる（2026-10-19 に、CRLF だった 1-7・1-8 とレビュー報告書 3 本を LF にした。作業指示者の指示）
  - 文字コードの規約の正本（`win-file-encoding` の rule・skill・hook）は develop にある（2026-10-19、0e4c4a8）。本ブランチには、develop の 2 コミットを `git cherry-pick -x` で取り込んだ（2026-10-23。作業指示者の判断。報告書が引くコミットのハッシュを保つため、rebase はしない）。`.ps1`・`.bat` を扱うときは `.claude/rules/win-file-encoding.md` と hook に従う（hook は Python 3.10 以上が `python` として PATH に要る）
