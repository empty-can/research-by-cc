## 3. CRITICAL（全件、メインが独立に再現を確認）

### CR-1: 素の日本語 Windows で fail-closed が fail-open になる

**Python は Windows でパイプ出力に ANSI コードページ（日本語環境では cp932）を使う**。hook が返す block JSON の理由文には、**まさに拒否対象である CP932 外の文字（`⚠` 等）**が含まれるため、**拒否が発動する場面でだけ `UnicodeEncodeError` が起きて JSON が途中で切れ、exit 1（＝非ブロッキング）になる**。`.bat` の書き戻し拒否が Claude に届かず素通りする。

- **なぜ実装者の検証で出なかったか**: 開発機に **User 環境変数 `PYTHONIOENCODING=utf-8`** が設定されていた。外すと `sys.stdout.encoding` は `cp932`（レジストリの ACP も 932）。
- **これは 3 度目の同型事故**: ①`chcp` が共有コンソールを壊した ②Claude Code の PowerShell ツールが UTF-8 コンソールを張るため既定環境を測れなかった ③今回の `PYTHONIOENCODING`。**計測器が測定対象を汚染する**。
- 修正: 両 hook で `sys.stdout` / `sys.stderr` を UTF-8 へ `reconfigure`。

### CR-2: `.origin` サイドカー経由の任意パス書き込み

影（`*.utf8.txt`）と `.origin` は **deny 対象外**なので自由に書ける。`.origin` に任意パスを書いて影を保存すると、hook がそのパスへ CP932 で書き込む。**`.bat` ですらないプロジェクト外のファイルを上書きできることを実測**。**「ハードなガードは `permissions.deny`」という設計宣言を hook 自身が迂回路にしていた**。

- 修正: 書き戻し前に (1) 原本が `.bat` であること (2) **その影の写像先であること**（`shadow_for(src) == shadow`）(3) **原本が影を作った後に変更されていないこと**（sha256 照合）を検査する。サイドカーは `{"origin", "sha256"}` の JSON へ。

### CR-3: ミラー段だけが fail-open で、壊れた plugin が push される

`publish-plugin` の 7 点の防御（レビューで**全て機能することを実測確認**）の**谷間にあるミラー段（step 5）だけ失敗検査が無い**。しかも **PowerShell の `New-Item -ItemType Directory -Force` は、対象がファイルだと `$ErrorActionPreference='Stop'` でも例外を投げず `$null` を返す**（実測）。その結果、削除とコピーが意図と違う動きをし、**`.claude-plugin/` 階層が消えた plugin が commit・push され「✓ publish 完了」が表示される**。

- 修正: 両版に「配布先がディレクトリか」の事前検査・各手順の失敗検査・**出口の件数照合**を追加。**`publish-share` にも同じ穴があったため横展開**（片肺を作らない）。

### CR-4: 配布物に虚偽の安全宣言（`.ini`）

rule / SKILL.md / README の 3 文書が「`.reg` / `.ini` は `permissions.deny` で R/W を禁止している」と断定していたが、**`settings.json` に `.ini` の deny は存在しない**。**保護があると信じさせる誤情報が全利用先へ配布される**。

- 判断: **`.ini` を実際に deny すると `tox.ini` / `pytest.ini` / `mypy.ini` まで遮断されて通常開発が壊れる**（UTF-8 が正しい `.ini` が広く存在する）。よって**文書側を「規定しない・deny もしない」に訂正**した。

## 5. レビューアが実測で追認した点（POSITIVE 抜粋）

- **技術的主張は中核が全て正しい**: BOM 付き `.bat` が cmd.exe で 1 行目を壊す／PS 5.1 は BOM 無し UTF-8 を CP932 誤読（`.Length` 9）・PS 7 は CP932 を誤読（8）で**両対応は UTF-8+BOM のみ**／**「CP932 の後続バイトに 0x0A・0x0D は現れない」を全 Unicode 符号点で総当たり検証**／`Write` は BOM も CRLF も保持しないが `Edit` は保持する。
- **拡張子ベース化による保護後退ゼロ**（全 49 追跡ファイルの `check-attr` を develop と機械比較）。配布先シミュレーション合格。機微情報・マシン固有パスの混入ゼロ。
- **`publish-plugin` の 7 点の防御は実測で全て機能**し、bash と PS の終了コードが 7 シナリオで完全一致（過去 2 度 CRITICAL を生んだ「片肺」がガード層には無い）。
- **`check-ignore` を `-z` + bytes で叩く実装**が Windows の text-mode CRLF 混入を正しく回避している。

## 7. 教訓

1. **計測器が測定対象を汚染する事故が 3 度目**（`chcp` / PowerShell ツールのコンソール / `PYTHONIOENCODING`）。**「素の環境」を測るには、自分の環境変数と、自分が使っているツールが張る設定を疑う**。`PYTHONIOENCODING` / `PYTHONUTF8` / コンソールのコードページ / `core.autocrlf` は、いずれも**開発機でだけ症状を隠す**。
2. **「hook で守る」は保証にならない**（実行環境が欠けると fail-open する）。公式 docs も「ハードな許可/拒否は permission システムで行え」と明記している。**hook は利便性、permission がガード**という二層は正しかったが、**その hook 自身が deny の迂回路を作っていた**（CR-2）ことに実装者は気づけなかった。
3. **path-scoped rule は「読んだ時」にしか効かない**。**新規作成の導線は無条件ロードの `CLAUDE.md` に置くしかない**。
4. **成果物の種別ごとにレビューアを分けたのは有効**だった。3 レーンの CRITICAL は互いに重複せず、Python の可搬性・シェルの破壊的操作・文書と実装の乖離という**それぞれの専門でしか出ない指摘**が得られた。
