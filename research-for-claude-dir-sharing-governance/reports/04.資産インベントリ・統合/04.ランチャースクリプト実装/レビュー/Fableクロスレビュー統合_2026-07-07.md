## 3. CRITICAL（検証済み・リリース前提）

### CR-1 配布先セーフティネット（.gitignore / .gitattributes）が payload に乗らず、Windows 利用者で `.sh` 系が CRLF 破損・個人実体が無防備
**統合元**: 論理C1 ／ 実用I9 ／ 作業U-C1（3観点全到達）
**私の検証（CONFIRMED）**:
- C-BDC（`C:\cc-workspace\basic_dot_claude`）実物: **`.gitattributes` は存在しない**。`.gitignore` は4行（`settings.local.json` / `CLAUDE.local.md` 系のみ）で、`option-settings.{sh,ps1}` / `custom.env` / `*.env` の除外が**無い**。
- publish-share.sh 実物 L37 `git archive "$REF" .claude | tar -x`／L51-54 は keep-list（`.git`/`.gitignore`/`README.md`/`LICENSE`）を残し他を rm→`cp -R "$tmp/.claude/." "$SHARE_BODY/"`。C-BDK ルートの `.gitattributes` は `.claude/` 外のため **archive に乗らず、C-BDC へ直コミットしても keep-list 外＝次回 publish で消える**。
- 帰結（実害）: (1) C-BDC に eol 属性が無いと、`core.autocrlf=true`（Git for Windows 既定）の clone で `setup-environment.sh` 等が CRLF 化 → `start_claude_code.sh`（`set -euo pipefail`）が source 時に `$'\r'` で**初回起動から中断**。(2) 利用者が `.claude`（=C-BDC submodule）内に作る `custom.env`/`option-settings.*` はどの `.gitignore` にも守られず、submodule 内の安易な `git add .` で**共有リポへ commit される経路が開いたまま**。F1 は開発リポ側の網の再建だったが、消費者側の網は最初から無い。

**対応レーン**: 設計判断=本セッション（payload 搬送方式の確定）／実装=C-BDK 移管
**修正案**: C-BDK に **`.claude/.gitignore`**（`option-settings.sh`/`option-settings.ps1`/`custom.env`）と **`.claude/.gitattributes`**（`/launcher/*.sh text eol=lf`・`/launcher/*.ps1 text eol=crlf` 等、パスは `.claude/` 相対）を追加。cp -R により C-BDC ルートへ `.gitignore`/`.gitattributes` として正しく着地し、以後 payload 正本に一元化。`start_claude_code.*` 用の eol 属性は Phase 4a の C-BCP ルートレールに同梱（`/start_claude_code.ps1 text eol=crlf`・`.sh text eol=lf`）。Phase 5 の security-review チェックに「配布先3リポで `git check-attr`/`check-ignore` 確認」を追加。

## 8. Fable 5 試行の評価

> **モデル前提の訂正（2026-07-08）**: 本節は当初 Fable 5 を「軽量モデル」と誤記していたが、これは無検証の憶測で誤り。公式 docs（Claude Code v2.1.170）では Fable 5 は **Mythos-class ＝一般提供モデル中で最高性能・1M context 既定**であり Opus 4.8 より上位。以下は「Fable は最上位モデル」という正しい前提での評価。

- **精度**: 事実系指摘はほぼ正確（誤検知は 21 指摘中 U-I7 の1件のみ）。作業指示者観点の agent は配布先リポ実物・publish-share/check-assets 参照実装・git index まで自発的に読み、**最も深い CRITICAL（U-C1/U-C2）を実物典拠付きで**挙げた ―― 最上位モデルに委任した結果として妥当な高品質。
- **カバレッジ**: 3観点が独立に同一核心へ到達し、かつ観点固有の指摘（実用＝実装バグ、作業＝配布先/README、論理＝ドクトリン矛盾）も分化しており、観点分担が機能した。
- **限界**: (1) U-I7 の誤検知は Glob の取りこぼしに起因。**ツールの取りこぼしはモデルの性能序列と独立に起こり得る事象**であり「軽量ゆえ」ではない（当初の因果帰属は誤り）。(2) 指摘の最終的な影響度・採否の見極めはメイン検証で補正した（例: IM-6 の重要度、IM-11 の追認）。
