## 2. IMPORTANT

### F1 root `.gitattributes` の `/.claude/**` 指定が `.claude/.gitattributes` に上書きされて効かない ―― かつコメントが優先関係を誤って説明している
**典拠（実測）**: `.gitattributes` は**深い階層が優先**する。統合ツリーで実行:

```
git check-attr text eol -- .claude/skills/win-file-encoding/scripts/convert_encoding.py
  → text: auto  eol: lf      ← .claude/.gitattributes の「* text=auto eol=lf」が効いている
                                （root の「/.claude/skills/**/*.py text eol=lf」＝text は set のはず）
```

root `.gitattributes` は `/.claude/launcher/*`（5 行）と `/.claude/skills/**`（2 行）を持つが、**`.claude/.gitattributes` が存在する限りこれらは効かない**。にもかかわらず root のコメントは「本ファイルは開発リポ内でのみ**有効**」「配布先向けは `.claude/.gitattributes` が担う。**両者は別物なので片方だけ直さないこと**」と書いており、実態（**上書き関係**であって併存ではない）と食い違う。
**帰結**: 将来 launcher の改行方針を変えようとした保守者が root を編集し、**効かないのに「直したつもり」になる**。これは Round 1〜3 で 3 度繰り返した「片側だけ修正」を**構造的に誘発する罠**である。
**原因**: 私の Round 3 修正（R3-B で `* text=auto eol=lf` を追加）が、それまで生きていた root の `/.claude/skills/**` を無効化した。**自分の修正が何を無効化するかを確認しなかった。**
**修正案**: root `.gitattributes` のコメントを実態（`.claude/` 配下は `.claude/.gitattributes` が優先。root の `/.claude/**` 行は同ファイルを持たない ref のための保険）に訂正する。**⚠ root `.gitattributes` は CR-c 対策で両ブランチが byte-identical にしてある。片方だけ編集すると add/add コンフリクトが復活するため、必ず両ブランチへ同一内容で入れること。**

### ⚠ 対応中に、自分で IM-2 をそのまま再発させた（記録）

**F10 / F11 の実装で、Round 2 の IM-2（「`check-assets` の検査が working tree で恒常 FAIL する」）を再現してしまった。**

新検査（2-e / 2-f）を書いたとき、走査対象を `find "$SHARE/.claude"` で列挙した。その結果、**gitignored で payload には乗らない `.claude/work/` 配下まで検査対象になり、作業ツリーに対して FAIL 24 件・exit 1** を出した ―― README が案内する `check-assets.sh .` が常時赤くなる、まさに「ゲートのオオカミ少年化」である。

**原因**: 二層基準を「既存の検査項目」にしか適用せず、**新しく足した検査に適用し忘れた**。「層で基準を変える」という設計判断が、検査項目ごとに手書きされているため、追加時に落ちる。
**修正**: 走査対象の列挙自体を二層基準にした（`payload_files()` / `Get-PayloadFiles`）。git 層は `ls-files`（追跡分だけが payload に乗る）、非 git 層は `find`（実体が全て配布される）。
**教訓**: **ゲートに検査を足すときは、必ず「作業ツリーに対して実行して exit 0 になるか」を確認する。** 実行して初めて気づいた（コードを読むだけでは気づかなかった）。
