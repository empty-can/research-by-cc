## 要旨(2nd)

L1〜L63 の再整理版は 1st 時点と比べ、以下が大きな差分。

* (a) 利用禁止が「正式通達ではなく現場・マネジメント層の暫定判断」であること
* (b) 説得相手が同部署内に閉じ正式承認プロセス不要であること
* (c) 目的が「ロジックの確立」「ファクト収集の仕組みの確立」「実適用による活用促進」の 3 段構成で明示されたこと
* (d) 事前収集と定義事項のアウトラインが粗いまま並列で並んでいること

これにより 1st 見解の前提（情報セキュリティ所管部署＝外部の正式審査主体、というモデル）は **部分的に外れる**ため、計画書策定前に「説得相手・完了条件・継続運用の主体」の 3 点を作業指示者と再握りすべき。  
再整理版自体は計画書を「書き始める」には不足ではないが、**ゴールの粒度がぶれたまま着手するとフェーズ分割が空中戦になる**ため、書き始める前に下記を最低限確定したい。

### B. 計画書 v1.0 着手前に作業指示者と合意すべき事項（優先順）

以下は **着手前合意必須**。順番は計画書のフェーズ分割への影響度順:

1. **本活動の DoD（Definition of Done）の確定**  
   特に、**L38「実適用」が本活動内かどうか** がフェーズ数（5±1 フェーズ程度の差）に直結するため最初に握る。
   * 候補
     * (i) 「審査基準＋仕組み」が揃った時点
     * (ii) 同部署内マネジメントの納得が取れた時点
     * (iii) 1 本目の MCP サーバを実適用で通した時点
     * (iv) N 本適用してフロー安定化を確認した時点  
2. **「同部署内マネジメント層」を具体化**  
   これにより成果物のフォーマット・粒度・実例の必要性が決まる。
   1. ロール
   2. 人数
   3. 立場
   4. 既存の判断スタイル（資料を読み込む派か、実例ベース派か）
3. **対象 MCP サーバのスコープ**  
  **最初の実適用対象を 1 本仮置きできるかどうか** が事前収集の重さを大きく変える。
   * (a) 利用したい具体サーバが既にあるか
   * (b) 公式・OSS・自作の混在か
   * (c) 言語・ランタイム範囲（Node/Python/Go/Rust 等）
4. **「ロジック」と「ファクト収集の仕組み」の依存関係**  
   **L32 のロジックが先か、L35 の仕組みが先か、並走か**  
     * ロジック先行が自然だが、Claude Code を使ったレビューの実現性が分からないと基準粒度が決められないため、**スパイク（試行検証）フェーズの要否** を確認。
5. **継続運用主体**  
   L37「継続的にウォッチする仕組み」を構築するなら、**運用主体（誰が定期実行・結果判定・新版審査をするか）** が決まらないと仕組みの自動化粒度が決まらない。  
   本活動は仕組み構築までで運用は別活動か、を握る。
6. **本活動の期限・工数の上限の有無**  
   無制限なら長期活動として組めるが、四半期マイルストーン等があるなら最初から MVP 思考でフェーズを切る必要がある。

### D. 事前収集（L48〜L52）への補強提案

各項目に **打ち切り基準** を付けることを推奨。  
打ち切り基準が無いと事前収集フェーズが無限化し、計画自体が破綻するリスクが高い。

#### 打ち切り基準の例

1. 「世間の動き」「公開ナレッジ」系（L48・L52）  
   以下を当たって追加 1 ソースで新情報がほぼ出なくなったら打ち切り
   * 主要 3〜5 ソース（OWASP LLM Top 10
   * Invariant Labs
   * Anthropic 公式の MCP ガイダンス
   * 主要 SAST ベンダのレポート
   * GitHub Advisory Database の MCP タグ等）
2. 「事例」（L49）
   * 5〜10 件で類型化し、類似事例が続いたら打ち切り
3. 「実装言語＋ツール」（L50）
   * TypeScript/Python の 2 言語に絞って各言語 SAST/依存スキャナを 2〜3 ツール特定したら打ち切り
   * 他言語は実適用対象が出てから追加調査
4. 「検出すべき脆弱性種類」（L51）  
  以下 の 3 ソース突合で確定
   * OWASP LLM Top 10
   * CWE 主要カテゴリ
   * MCP 特有脅威モデル  
     * prompt injection 経由のツール乱用
     * tool description poisoning
     * 認証情報
     * *FS/network アクセス境界

### F. 推奨フェーズ構成（仮）

B 群が握れた前提での暫定案。計画書 v1.0 内で詳細化する想定:

1. **Phase 1: 活動憲章整備**  
  本見解 B 群を反映した計画書 v1.0 の作成・合意
2. **Phase 2: 事前情報収集**  
  D の打ち切り基準付きで実施
3. **Phase 3: 審査ロジック・基準ドラフト作成**
4. **Phase 4: レビュー実施仕組みのスパイク**  
  Claude Code を使った半自動レビューの実現性検証（小規模 MCP 1 本で試行）
5. **Phase 5: 仕組み本構築＋基準のリファイン**  
  Phase 4 の知見でロジック・基準を更新
6. **Phase 6: 実適用（1〜N 本）**  
  DoD 次第で本活動内 or 別活動
7. **Phase 7: 継続運用への移行設計**  
  DoD 次第で本活動内 or 別活動

Phase 4 の **スパイク先行** が肝。  
基準の粒度を Claude Code の実現可能範囲と整合させないと「立派な基準は作れたが運用できない」になる。
