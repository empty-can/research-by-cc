## 要旨(5th)

4th への作業指示者の回答（[Opus見解と返答(4th).md](Opus見解と返答(4th).md) の「作業指示者からの返答・補足」各節）と、参考資料 [【参考資料】MCPサーバの脆弱性に関する事前質問(Google AIへのお試し問合せ).md](<../../【参考資料】MCPサーバの脆弱性に関する事前質問(Google AIへのお試し問合せ).md>) を踏まえて、以下を確認:

* **本活動のスコープ境界が大幅に明確化** — A2-1〜A2-5 の各カテゴリに対する「責任範囲内 / 範囲外」の判断が示され、計画書 v1.0 のスコープ定義に直接反映可能
* **Phase 0 試行結果の質が高い** — 参考資料の Google AI 回答は CVE 番号特定 / OSS ツール選定 / OWASP 参照まで含み、Phase 0b の実行可能性と得られる情報の質が実証された
* **打ち切り基準は「事前情報収集を進めながら設定」する方針で合意** — 4th の A3-1 (1)〜(4) への返答で示された「ある程度情報が見えてから基準設定」を Phase 0 運用に組み込む
* **Phase 0c の方針が「広く浅く」に確定** — 4th の A3-2 への返答で「重要な観点・トピックの欠落リスクを避ける」ことを優先

結論として、**スコープ境界の文書化 + Phase 0 質問リスト確定 + Phase 0c 運用ルール詳細化** の 3 点を 5th で整理すれば、Phase 0a 完了の握り直し → Phase 0b 着手が可能。

## スコープ境界の整理（A2 への返答受け）(5th)

4th の A2-1〜A2-5 への作業指示者の返答を踏まえ、本活動のスコープ境界を以下のように整理。**この整理は計画書 v1.0 のスコープ定義（含む / 含まない）の主たる素材になる**。

### 含む（本活動の責任範囲）

| カテゴリ | 含む理由 | 具体的な検査対象 |
|---|---|---|
| **A2-1 依存ライブラリの脆弱性** | MCP サーバ側の脆弱性として無視できない | `requirements.txt` / `package.json` の依存関係スキャン |
| **A2-1 コンテナイメージの脆弱性（条件付き）** | Docker イメージとしてのみ公開されている MCP サーバを利用する場合に必須 | ベースイメージスキャン（Trivy 等） |
| **A2-2 設定ファイル静的解析** | Git リポジトリに含まれているためコードインスペクションで検出可能 | `.json` / `.yaml` 設定ファイル + デフォルト値レビュー |
| **A2-2 環境変数の取扱い（実装観点）** | ログ出力周りのコードインスペクションで一部検知可能 | ロガー設定 + 機密情報マスキング処理 |
| **A2-3 Supply Chain 攻撃** | 認識されていなかった観点として 4th で追加採用 | パッケージ署名検証、SBOM 取得、メンテナ確認 |
| **A2 補足: 動作検証（必要な場合のみ）** | 「本当に必要なのであれば」MCP サーバ起動・実行を伴う検証を実施する方針 | Phase 3 のスパイク内で要否判断 |

### 含まない（本活動のスコープ外）

| カテゴリ | スコープ外とする理由 | 代替的なリスク管理方針 |
|---|---|---|
| **A2-1 OS/ランタイム自体の脆弱性** | MCP サーバ専用でないランタイムは「MCP サーバとは別」と整理可能。MCP サーバ専用ランタイムのみ例外 | 既存の OS パッチ管理運用に委ねる |
| **A2-1 コンテナイメージスキャン（非 Docker MCP）** | Docker を使わず直接インストール可能な MCP は Docker を使わないことで責任を回避 | 利用ガイドラインで「Docker 使用しない」を推奨 |
| **A2-2 デフォルト設定の脆弱性（運用観点）** | 概念的に「利用時の注意事項」へ集約 | 「利用手順」「利用時の注意事項」アウトプットに反映 |
| **A2-4 MCP プロトコル仕様自体の脆弱性** | MCP プロトコル策定団体の責任範囲 | 団体公開情報の継続ウォッチ |
| **A2-4 クライアント（Claude Code 等）側の不備** | MCP サーバの利用を否定する材料になりづらい | LLM への事前ルールインプット（例: 取得データ内のリンク・スクリプトの実行前確認） |
| **A2-5 メモリダンプ経由の漏洩** | ローカル出力されるメモリダンプが外部漏洩経路を持たなければ実害なし | 環境のセキュリティ運用に委ねる |
| **A2-5 異常パターン下の挙動（情報漏洩に繋がらないもの）** | 情報漏洩に繋がらない範囲は本活動の目的（情報漏洩防止）と無関係 | リソース枯渇等は別観点で扱う |

### 含むが扱い保留（Phase 0 で詳細確認）

| カテゴリ | 保留理由 | Phase 0 で確認すること |
|---|---|---|
| **A2-5 タイミング攻撃** | 判断するためにはタイミング攻撃の知識獲得が必要 | 質問リスト Q5/Q6 等の回答に含めて知識獲得 |

`★ Insight ─────────────────────────────────────`

- スコープを「含む / 含まない / 保留」の 3 段階で整理する構造は、計画書 v1.0 のスコープ定義節にそのまま転用可能。Opus 1st の活動憲章観点（スコープ・スコープ外の明示）に対する具体的な答えになっている
- 「含まない」項目について **代替的なリスク管理方針** を併記するのは、説得相手（チームリーダー / マネージャー / 事業責任者）への説明資料としても効く。「無視している」のではなく「別の場所で管理されている」と説明できる構造

### Phase 0 への 4 つの示唆

#### S-1. 質問リストの精度は実用に耐える

参考資料の質問は本活動の質問リスト Q1〜Q6 とほぼ同等の構成で、**回答の質も Phase 0 の目的（計画書 v1.0 のインプット獲得）を満たすレベル**。質問リストへの大幅な再設計は不要。

#### S-2. 推奨追加質問 Q7 の必要性は緩和される

4th で推奨した Q7（既存業界デファクトのチェックリスト・基準・ガイドライン）について、参考資料で既に **OWASP Top 10 for LLM / MCP Security Vulnerability Database / Awesome MCP** が言及されているため、**Q7 は単独質問ではなく既存 Q5/Q6 の文面充実で取り込む方針**が適切。これは [4th 返答の A1-2 節](Opus見解と返答(4th).md)で作業指示者が既に示した方針（「既存の Q に組み込めるものは Q 文面の充実化で取り込む」）と整合。

#### S-3. Q8 は単独質問として残す価値あり

4th で推奨した Q8（インシデント対応規約）は参考資料でカバーされていないため、**Phase 6（継続運用）の設計精度向上のためには単独質問として残すか、Q5/Q6 の文面に「インシデント対応規約・脆弱性開示プロセス」を含める形で取り込む**。

#### S-4. Phase 3 のスパイク対象が既に絞れる状態

参考資料の F-4 で **Semgrep + Trivy + Gitleaks + Bandit / ESLint** という具体的な OSS ツール候補が出揃った。**これは Phase 0 で得るべき情報のうち、ツール特定の部分はほぼ完了している**ことを意味し、Phase 0c で深掘りすべきは:

- 各ツールの MCP 特化ルール / カスタムルールの書き方
- 各ツールの実運用上の精度・偽陽性率
- ツール間の連携・出力フォーマット統合方法

に絞り込める。

## Phase 0c の運用ルール詳細化（A3-2 への返答受け）(5th)

4th の A3-2 への返答で、Phase 0c の打ち切り基準は **「広く浅く」運用** に確定しました。これを具体的な作業ルールに落とすと:

### Phase 0c の作業ルール

| 項目 | ルール |
|---|---|
| **対象範囲** | LLM 各サービス（13 種）の回答に含まれる公開ナレッジを **全件カバー対象** とする |
| **1 件あたりの調査深度の上限** | 各公開ナレッジの **概要 + 主要セクション** を確認するに留める。全文精読しない |
| **深掘り対象への昇格条件** | 主要セクション確認時点で「本活動の重要観点（A2 含む / 保留に該当）」が出現した場合のみ深掘り対象に昇格 |
| **重複処理** | 複数 LLM の回答に同一情報源が出現した場合、初回のみ確認し以降はスキップ（ただし「複数 LLM が言及した」事実はメモする = 信頼性の指標） |
| **打ち切り判定** | 全件カバー後、「Claude Code が把握済みの観点を超える新観点が出現しない」状態で打ち切り |

### 想定される作業量

参考資料の F-1 で 5 件程度の事例 + F-4 で 4〜6 種のツール + F-5 で 4 つの情報集積地が言及されているため、LLM 13 サービスからの回答を統合した場合、**ユニークな公開ナレッジは 30〜50 件程度** になることが想定されます。これに対し:

- 概要 + 主要セクション確認 = 1 件あたり 3〜5 分
- 全 30〜50 件で 1.5〜4 時間
- 深掘り対象昇格は 5〜10 件程度を想定 = 1 件あたり 15〜30 分 = 1〜5 時間
- **合計 3〜9 時間**

これは Claude Code セッション 1〜2 回で完結できる規模です。

`★ Insight ─────────────────────────────────────`

- Phase 0c の作業量見積もりが具体化されたことで、**Phase 1（計画書 v1.0 作成）への着手タイミングが現実的に予測可能** になった。3〜9 時間 = 1〜2 セッションで Phase 0c が完結すれば、その後 Phase 1 に入れる
- 「全件カバーするが各件は浅く」という運用は、4th の A3-1 で作業指示者が示した「実際にある程度情報収集を行ってから打ち切り基準を見極める」という考え方とも整合。Phase 0c の前半（最初の 5〜10 件）で情報の性質を見極め、後半は機械的に処理という流れが自然
