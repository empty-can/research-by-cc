## 本ドキュメントについて

[01.活動の概要.md](../../01.活動の概要.md)ファイル作成前に、同様の内容の超ドラフト版に対してもらった、Opusの見解。  

実質的に「活動の概要」に対する最初にもらったOpusからの見解だが、インプットにしてもらった「活動の概要」に関する内容が非常に粗かったため、[01.活動の概要.md](../../01.活動の概要.md)として改めて書き起こした内容に関するOpusからの見解を、改めて同ドキュメント内に記載してもらっており、そちらは2nd呼称している。

内容的に2ndと重複していたり、[01.活動の概要.md](../../01.活動の概要.md)に記載した内容に完全に対応していないなど、基本的に活動計画の策定には不要な内容がほとんどであるが、Opusの提案（後述）から、活動計画の初版（1.0版）がfixするまでは過去経緯情報としての有用性もあるため、別紙として残すこととする。

### Opusからの、過去見解の廃棄可否についての提案

**結論**: 廃棄推奨  
ただし即削除ではなく、計画書 v1.0 確定後に削除する運用を推奨）

**理由**:

* **2nd で 1st の主要観点はすべてカバー済み**  
  継承すべき観点は上記「継承」節に明記しており、1st 全文を残しておく必要は低い
* **1st は前提が一部ずれている**  
  説得相手モデルが異なるため、計画書策定時に 1st を直接参照すると判断ミスを誘発するリスク
* **本ファイルは「計画書策定のインプット」である**  
  インプット文書に古い見解が混在していると、計画書執筆 Agent が混乱する可能性

ただし以下の理由で **即時削除ではなく猶予を置く** ことを推奨:

* 計画書 v1.0 のレビュー時に、2nd の見解と 1st の見解の差分を作業指示者が突合したい場面が出る可能性
* Git 履歴で復元可能だが、レビュー中の頻繁な参照には不向き

**推奨運用**:  
計画書 v1.0 が作業指示者承認を得た時点で L65 以降を削除し、コミットメッセージに「1st 見解は計画書 v1.0 確定により役目を終えたため削除、Git 履歴 (commit `<hash>`) で参照可」と記載する。

## Claude からの  全体総括（Opus の見解）1st

> **注意事項**
> 本件会は、セッション開始直後のインプットに対するものである。
> 一方で、本ドキュメントの前半に記述した内容は以降に改めて再整理・清書した内容であり、本セクションで記載しているOpusの見解のインプットと内容や情報量が異なっていることに留意

### 要旨(1st)

「(1) 要件定義書的なもの / (2) 関連情報の事前収集」という当初の認識は 合致 しています。ただし (1) は「要件定義書」より活動憲章 / プロジェクトチャーターと捉えると性質が明確になります（成果物の機能要件ではなく、活動そのもののスコープ・完了条件を定義するものであるため）。

これに加え、計画書精度のために (3)〜(5) を追加で押さえることを推奨 します。

### 推奨内容 (1st)

#### (1) 活動憲章(1st)

最低限押さえるべき項目:

* 背景・経緯  
  なぜ今やるのか（特定の MCP 利用要望が起点か、組織方針の先回りか）
* 目的とゴール
  「情報セキュリティ所管部署からの利用許諾」が真のゴールか、「インスペクション仕組みの確立」が真のゴールか（後者は前者の手段）
* スコープ  
  対象 MCP サーバの範囲（公式 / OSS / 自作 / 全部）、対象言語・ランタイム、レビュー対象は MCPサーバ実装のみか依存ライブラリまで含むか
* スコープ外の明示  
  動的解析・ペネトレーションテスト・実環境での挙動検証 等を含めるか含めないか
* 完了条件（Definition of Done）  
  審査基準ドキュメントが揃った」で完了か、「所管部署の承認が取れた」で完了か、「最初の MCP サーバ 1本を実際に審査通過させた」で完了か
* 関係者・承認者  
  情報セキュリティ所管部署のどのロールがレビュー・承認するか、活動指示者の決裁範囲
* 制約条件  
  期限、工数、利用可能ツールの制限（本環境で MCP 不可など）
* 想定リスク・前提  
  所管部署が求める基準が後から変わる可能性、組織内に類似活動がある可能性

#### (2) 事前収集の対象(1st)

「ざっくり」の中身を、計画書の精度に効く順に仕分け:

* 既存の社内ルール・先行事例
* 情報セキュリティ所管部署の既存審査基準（OSS 利用申請、外部 SaaS 利用申請等）
  * インスペクション基準のベースに流用できる
  * 過去に同種の利用許諾を取った先行事例（フォーマット・粒度・所要期間の参考）
* MCP サーバそのものの技術的理解
  * MCP プロトコル仕様（Anthropic 公式ドキュメント、modelcontextprotocol.io）
  * 主要な MCP サーバ実装の構成パターン（stdio / SSE / HTTP、認証有無、外部 API 連携の典型）
  * MCP 特有の脅威モデル — prompt injection 経由のツール乱用、tool description poisoning、認証情報の取扱い、ローカルFS / network アクセスの境界
* 既存の脆弱性インスペクション手法・基準
  * OWASP（特に LLM Top 10、ASVS）、CWE、SAST ツールの観点
  * サプライチェーン系（SLSA、依存ライブラリ脆弱性スキャン）
  * 既に公開されている MCP セキュリティ解析記事・先行研究（Invariant Labs 等）
* インスペクション実施手段の現実性確認
  * 本環境で使える解析ツール（SAST、依存スキャナ）
  * Claude Code をインスペクション実施者として使う場合の運用設計（プロンプト・チェックリスト化方法）
* 対象 MCP サーバの候補
  * 最初の検証対象として何を据えるか（許諾を取りたい具体サーバがあるなら、そのリポジトリの規模・言語感を見ておく）

#### (3) 成果物の一覧と最終形イメージ（追加推奨）(1st)

* 「審査基準書」「観点・チェックリスト」「実施プロセス定義書」「成果物フォーマット（インスペクションレポート雛形）」をどの粒度で作るか、所管部署に何をどの形で提出するか
* 計画書の 「フェーズ分割」と「フェーズ完了条件」が成果物単位で決まるため、ここが曖昧だと計画が組めない

#### (4) 所管部署との合意プロセス設計（追加推奨）(1st)

* いつ・どの段階で所管部署に持ち込むか（基準ドラフト時点か、実例 1 本通した時点か）
* 早期に方向性をすり合わせないと、終盤で基準のちゃぶ台返しが起きるリスク
* これは計画書の 「マイルストーン」に直結

#### (5) 判定の運用モデルの方向性仮説（追加推奨）(1st)

* 「インスペクション実施者は誰か（情シス / 利用部門 / Claude Code を使った半自動）」「判定の最終承認者は誰か」「却下時の救済プロセスはあるか」
* 仕組みの利用者像が決まらないと、チェックリストの粒度（専門家向け / 非専門家向け）が決められない

### まとめ（Opus 結論）(1st)

* (1)(2) の認識は概ね合致。(1) は「活動憲章」と捉えると性質が明確
* 追加で 成果物像・所管部署との合意プロセス・運用モデルの仮説 の 3 点を計画書着手前に整理することを推奨
* 特に 完了条件（DoD）と所管部署の関与タイミング はフェーズ分割の骨格を決めるので、計画書 v1.0を書く前に作業指示者と握っておく価値が高い
