## 活動概要

本活動は、MCPサーバに対して、脆弱性（特に、構築環境の個人情報や機密情報の漏洩に繋がるようなもの）の潜在有無を確認し、安全に利用できるものかどうかを判別するための調査フローと判断基準を確立する活動である。

### 背景

昨今、MCPサーバの脆弱性や、外部とデータをやり取りするという性質から、認証情報やMCPサーバ実行環境の内部情報といった、機密情報の漏洩が問題視され始めており、安全性を証明することができないMCPサーバの利用が禁止される事例も発生している。

脆弱性をチェックする製品は既に世の中に多く存在するが、一般的に、高機能なプロダクトはエンタープライズ向け、逆に無料で利用できるOSSツールはチェックの仕組みに起因する検出ルールの柔軟性やスコープに限界があることが多い。

よって、ソースコードのインスペクションを中心とした高度な脆弱性検出を低コストで実現する最有力な手段はLLM(具体的にはClaude Code)を活用した仕組みを構築することだが、MCPサーバが利用できない制約下では、LLMを活用したとしても実現できる作業が大幅に制限されてしまう。

このように、MCPサーバの安全性を効率的かつ高精度で説明できるファクトを積み上げるために活用したいMCPサーバの安全性を先に証明しないといけないというジレンマに陥っている状態である。

### 補足の背景情報

背景にある、MCPサーバの利用禁止は、まだ所管部署からの正式な通達としてなされたものではなく、Claude Codeを利用している現場の責任者・マネジメント層による、先行的・リスク回避優先的な暫定的判断である。
よって、同じ部署に所属する現場責任者やマネジメント層に対して説明し納得してもらえればよく、正式で厳格な社内承認プロセスを通す必要はない。

## 本活動のモチベーション

MCPサーバの安全性の証明のためにMCPサーバを活用できないのであれば、それ以外の手段（主にOSSのツールやプロダクトが中心になると想定）でMCPサーバの安全性を証明するための説明ロジックと、ファクトを収集する仕組みが必要である。

しかし、MCPサーバの安全性が注目され始めたこと自体が最近のことであり、世の中的にも同様の活動が始まったくらいのフェーズであると推察され、前述のロジックや仕組みを確立する活動が必要であろうと思われたため、本活動を実施することとした。

## 本活動の目的

前述のとおり、本活動の目的は以下のとおりである。

1. 利用したいMCPサーバの安全性を説明するためのロジックの確立
    * どのような基準をクリア（＝どのような脆弱性が存在しないことを確認）できれば安全と、説得力と自信をもって言えるかの整理
    * MCPサーバを安全に利用するために順守するべきルールや手順の整備
2. 利用したいMCPサーバの安全性を保障するファクト収集の手順・仕組みの確立
    * 存在しないことの確認が求められる脆弱性の存在確認を行う仕組みの設計と構築
    * MCPサーバの安全性を継続的にウォッチする（＝バージョンアップに伴うデグレードを即検知できる）仕組みの設計と構築
3. 本活動の成果を有用なMCPサーバから順に適用し、安全であることを証明してMCPサーバの活用を促進、LLMを活用した活動の生産性を更に向上させる

上記 1〜3 を達成するため、本活動は **コードインスペクション活動**（実装不備による脆弱性の検知）と **ガイドライン・チェックリスト整備活動**（クライアント側設定・運用層でのリスク緩和）を **二層防御として並行進行** させる構成をとる。詳細は[フェーズ構成](#フェーズ構成)節および [`CLAUDE.md`](../../CLAUDE.md) の「活動構成（コードインスペクション活動とガイドライン活動の並行進行）」節を参照。

## スコープ

4th 見解 A2-1〜A2-5 への作業指示者返答および 5th 見解の整理結果に基づき、本活動のスコープを「含む / 含まない / 含むが扱い保留」の 3 段階で確定する。

### 含む（本活動の責任範囲）

| カテゴリ | 含む理由 | 具体的な検査対象 |
|---|---|---|
| 依存ライブラリの脆弱性 | MCPサーバ側の脆弱性として無視できない | `requirements.txt` / `package.json` の依存関係スキャン |
| コンテナイメージの脆弱性（条件付き） | Docker イメージとしてのみ公開されている MCP サーバを利用する場合に必須 | ベースイメージスキャン（Trivy 等） |
| 設定ファイル静的解析 | Git リポジトリに含まれているためコードインスペクションで検出可能 | `.json` / `.yaml` 設定ファイル + デフォルト値レビュー |
| 環境変数の取扱い（実装観点） | ログ出力周りのコードインスペクションで一部検知可能 | ロガー設定 + 機密情報マスキング処理 |
| Supply Chain 攻撃 | 4th 見解で新たに採用された観点 | パッケージ署名検証、SBOM 取得、メンテナ確認 |
| 「利用手順」「利用時の注意事項」アウトプット | デフォルト設定の運用観点・Supply Chain 観点を集約する形で本活動成果物に含める（5th 返答で確定）。専用の調査活動は行わず、設定解析と Supply Chain 調査のアウトプットを再利用 | 利用ガイドライン文書 |
| クライアント（Claude Code 等）側を含む LLM への事前ルール | 外部リソースへのアクセスが多くの MCP サーバの主要前提機能であるため、`CLAUDE.md` やルール文言として LLM へ指示する形で本活動アウトプットに含める。専用調査は不要で、脆弱性成立の知識獲得時点でルール制定可能 | LLM 向けルール定型文言 |
| 動作検証（必要な場合のみ） | 「本当に必要なのであれば」MCPサーバ起動・実行を伴う検証を実施する方針 | Phase 3 のスパイク内で要否判断 |

### 含まない（本活動のスコープ外）

「含まない」項目には代替的なリスク管理方針を併記し、「無視している」のではなく「別の場所で管理されている」と説明できる構造とする。

| カテゴリ | スコープ外とする理由 | 代替的なリスク管理方針 |
|---|---|---|
| OS / ランタイム自体の脆弱性 | MCP サーバ専用でないランタイムは「MCP サーバとは別」と整理可能 | 既存の OS パッチ管理運用に委ねる |
| コンテナイメージスキャン（非 Docker 利用時） | Docker を使わず直接インストール可能な MCP は Docker を使わないことで責任を回避 | 利用ガイドラインで「Docker を使用しない」を推奨 |
| MCP プロトコル仕様自体の脆弱性 | MCP プロトコル策定団体の責任範囲 | 団体公開情報の継続ウォッチ |
| メモリダンプ経由の漏洩 | ローカル出力されるメモリダンプが外部漏洩経路を持たなければ実害なし | 環境のセキュリティ運用に委ねる |
| 異常パターン下の挙動（情報漏洩に繋がらないもの） | 本活動の目的（情報漏洩防止）と無関係 | リソース枯渇等は別観点で扱う |

> **v1.3 補足**: 上表「含む」のうち「『利用手順』『利用時の注意事項』アウトプット」および「クライアント（Claude Code 等）側を含む LLM への事前ルール」は、**ガイドライン・チェックリスト整備活動の中核成果物**として位置付ける。コードインスペクション活動の成果物ではなく、二層防御のガイドライン系列側で主に産出される。

### 含むが扱い保留（Phase 0 で詳細確認）

| カテゴリ | 保留理由 | Phase 0 で確認すること |
|---|---|---|
| タイミング攻撃 | 判断するためにはタイミング攻撃の知識獲得が必要 | 質問項目票 Q5 / Q6 等の回答に含めて知識獲得 |

### 対象 MCP サーバの範囲

- **対象**: 公式 または OSS として公開されている MCP サーバ（自作は含まない）
- **具体サーバ**: 利用したい具体サーバが既に存在する
- **言語・ランタイム範囲**: 対象 MCP サーバの実装言語次第であり、Phase 0（事前情報収集）および Phase 2（正式情報収集）の結果を踏まえて確定する

## 関係者一覧

3rd 見解の Q1 補足および 4th 見解の関係者像整理に基づき、本活動の関係者を「立場 × ロール」で以下のように整理する。

| 関係者 | 立場 | 主なロール |
|---|---|---|
| 作業指示者 | 作業指示者本人 | 利用者 / 一次レビュアー / 一次承認者 |
| Claude Code | 実行ツール | 成果物の主たる作成者 |
| チームメンバー | 作業指示者と同等 | 利用者 / 技術的レビュアー（決定権なし） |
| チームリーダー | チームリーダー | 説得対象者 / 二次レビュアー（想定） |
| グループマネージャー | グループマネージャー | 説得対象者 / 上位レビュアー（想定） |
| 事業責任者 | 事業責任者 | 最終説得対象者 / 最終承認者（想定） |

- 各立場の人数は **各立場 1〜2 人** を想定。
- 説得対象者の判断スタイルは **資料を読み込む派と実例ベース派の両方** を含むが、説明資料は **要点を的確かつ端的に説明したフォーマット** が好まれる。
- レビューの 2 段構造（技術的妥当性はチームメンバー、運用・組織レイヤはチームリーダー以上）が成立する想定で、Phase 5「実適用」での説明前にチームメンバーレビューを通すことで説明資料の品質を担保する。

## 完了条件（DoD）

本活動の Definition of Done は **「(iii) と (iv) の中間」 = 対象 MCP 全本数で安定化 = Phase 5 完了** とする（2nd 見解 B-1 の選択肢に対する作業指示者返答に基づく）。

- 確認したい MCP サーバが複数あるため、(iii)「1 本目を実適用で通した時点」では不足。
- (iv)「N 本適用してフロー安定化を確認した時点」のうち「フロー安定化」は、本活動においては **利用したい MCP に限って安定化できればよく、MCP サーバ全般への汎用化は努力目標**。
- **Phase 6（継続運用への移行設計）は努力目標**。Phase 5 完了時点で利用可否の判断（喫緊のニーズ）は達成できるため。

## 制約条件

| 区分 | 制約 |
|---|---|
| 必達期限 | 必達期限なし（個人的なモチベーションで実施する活動）。ただしチームの Claude Code 活用の生産性向上に直結するため **Phase 5 までは早期達成が望ましい**。**Phase 6 は時間をかけてよい** |
| 工数の上限 | 上限は存在しない |
| MCP 利用制約 | 本活動の実行環境では MCP サーバは一切利用できない（情報セキュリティ保護上の制約により正式に認められていない）。Phase 0b（複数 LLM・ChatGPT サービスへの同一質問）も MCP 経由ではなく作業指示者主体で実施 |
| 継続運用主体 | 対象 MCP の脆弱性をチェックするプロジェクトを Git リポジトリとして作成し、定期パイプライン実行で継続的な定期チェックを実現。**人的継続運用主体は不要** |
| 実適用判定の堅牢性 | 1 本でも妥当と言える仕組みであることを、(a) チェックインプットの信頼性（信頼できる組織が提供する情報・業界デファクトのチェックツール・実績ある手順の利用）、(b) チェック方式（ソースコード全量インスペクション）の 2 点で保証する |

## 想定リスク

計画書 v1.0 作成時に詳細化する想定だが、現時点で識別済みのリスクは以下:

| リスク | 影響 | 暫定対応方針 |
|---|---|---|
| 審査基準が後から外部から覆される | チェックリスト・ロジックの再構築 | 信頼できる組織が提供する情報・業界デファクト基準（OWASP / CWE / MITRE / Anthropic 公式 等）への準拠で覆されにくくする |
| 対象 MCP がアップデートで仕様変更 | 既存判定結果の再評価が必要 | Phase 6 の継続運用パイプラインによる再チェックで吸収（ただし Phase 6 は努力目標） |
| Claude Code 自体の更新で再評価必要 | 仕組み自体の妥当性再検証 | 仕組みの依存箇所を Claude Code バージョンと紐づけて記録 |
| MCP プロトコル仕様自体の脆弱性発覚 | 個別実装の安全性が無効化される | スコープ外として MCP プロトコル策定団体の公開情報を継続ウォッチ |
| Claude Code 利用コストの上限が突如設定される | 本活動の継続実行が困難になる | 本活動を可能な限り早期に進める |

## Phase 0（事前情報整理）の運用ルール詳細

| サブフェーズ | 内容 | 主担当 |

### Phase 0b の 3 ステップワークフロー

質問項目票の精度を Google AI 正式試行で自己検証してから残サービスへ展開する形を採る。

1. **Phase 0b-1（Google AI 正式試行）**: 確定版質問項目票 Q1〜Q3 + Q5 + Q6 を Google AI に投入し、回答を取得
2. **Q4 の整理**: Google AI 正式回答を受けて作業指示者が必要な追加質問を整理し、質問項目票の Q4 に正式記入（**質問票の凍結確定**）

## 本活動の活動計画立案に当たって

できるだけ具体的で無駄や手戻りリスクの少ない活動計画を立てるために、Phase 0（事前情報整理）の出発点として以下を整理した。本節の 2 リストは活動計画立案の起点メモであり、各論の確定事項は本紙の前節までを参照する。

### 事前にざっくりと収集すべき情報

1. MCPサーバの脆弱性についての世間の動きや公開情報の有無の調査
2. 現実に検知されているMCPサーバの脆弱性の事例情報の調査
3. MCPサーバの主要な実装言語と、それらに対応しているツールの存在状況の調査
4. 安全と宣言するために検知すべき公算の高い脆弱性の種類と調査難易度
5. 既に一般に公開されているMCPサーバの脆弱性や安全性に関するナレッジの存在有無

これらは Phase 0 の質問項目票（Q1〜Q6）に取り込み済みであり、複数 LLM・ChatGPT サービスへの同一質問運用で網羅する。

### 定義するべき事項

1. 活動のゴール（＝必達の成果物）
    * MCPサーバが安全と判定するためのロジックと基準（≒観点）とチェックリスト
    * MCPサーバのソースコードレビューによる脆弱性の調査・判定の仕組み
      * 特に構築環境の個人情報・機密情報漏洩に繋がるもの
    * 構築した仕組みの実適用結果
2. ゴールに向けて実施するべき活動のブレイクダウンとフェーズ（＝工程）分割
3. 各フェーズの目的、ゴール、およびフェーズ中断判断の条件
    * ただしフェーズ中断判断の条件は設けるべきと思われる場合のみ定義

これらは本紙の「[完了条件（DoD）](#完了条件dod)」「[フェーズ構成](#フェーズ構成)」「[成果物の最小品質基準](#成果物の最小品質基準)」節で確定済み。各論の詳細化は Phase 1（計画書 v1.0 作成）で実施する。
