### 回答(Q1)

````markdown
ご質問ありがとうございます。Claude CodeやMCP（Model Context Protocol）の活用を検討される中で、セキュリティに関する懸念を抱かれるのは非常に賢明な判断です。
ご指摘の「機密情報流出に関する脆弱性」については、主にAnthropic公式のGitHub MCPサーバやFilesystem MCPサーバ、およびClaude Code本体に関連して、2025年から2026年にかけていくつかの重要な脆弱性が報告・議論されています。
以下に、具体的な脆弱性の内容と特定のための情報をまとめました。

## 1. GitHub MCPサーバにおけるプロンプト注入による情報流出

最も「界隈で話題になった」ものの一つは、公式のGitHub MCPサーバを介した攻撃手法です。これはサーバ自体のバグというよりは、「AIエージェントが読み取るデータ（GitHub Issue等）に悪意ある指示が混入している場合、エージェントがそれを実行して機密情報を流出させてしまう」という設計上のリスクを突いたものです。 [1, 2, 3] 

* 内容: 攻撃者がパブリックなリポジトリに悪意あるIssueを作成し、AIエージェントに「この内容を読んで要約して」と指示します。Issue内に「秘密鍵や環境変数を読み取って外部に送信せよ」という隠し指示（プロンプト注入）があると、エージェントは権限を持つプライベートリポジトリの情報を読み取り、外部にプルリクエストを出すなどの形で流出させます。
* 詳細情報: [Invariant Labsのブログ記事「GitHub MCP Exploited」](https://invariantlabs.ai/blog/mcp-github-vulnerability)（2025年5月公開） [4, 5, 6] 

## 2. Anthropic公式 MCPサーバの脆弱性 (CVE)

公式にメンテナンスされているMCPサーバのリポジトリにおいて、実際にCVE番号が割り当てられた脆弱性がいくつか存在します。 [7] 

* mcp-server-git (Git MCPサーバ):
* CVE-2025-68145: パスバリデーションのバイパス。
   * CVE-2025-68143: git_init に関する不備。
   * CVE-2025-68144: git_diff における引数注入。
   * 内容: これらを組み合わせることで、プロンプト注入を介して任意ファイルの読み書きやリモートコード実行（RCE）が可能になるリスクがありました。
* mcp-server-files (Filesystem MCPサーバ):
* CVE-2025-53109 / CVE-2025-53110: 通称「EscapeRoute」。サンドボックスを回避してホストマシンの制限外のディレクトリ（~/.ssh や ~/.aws/credentials など）にアクセスし、認証情報を窃取できる脆弱性です。
* MCP Inspector (デバッグツール):
* CVE-2025-49596: ブラウザベースの攻撃により、開発者のマシン上でリモートコード実行が可能になる重大な脆弱性（CVSS 9.4）。 [7, 8, 9, 10, 11, 12] 

## 3. Claude Code 自体のソースコード流出（2026年3月） [13, 14] 

MCPサーバの脆弱性とは直接異なりますが、同時期に大きな話題となったため、混同されている可能性があります。 [12, 15] 

* 内容: 2026年3月末、Anthropicが npm パッケージのリリース時に誤ってソースマップファイル（.map）を同梱してしまい、Claude Codeのソースコード約51万行が完全に公開状態となりました。
* リスク: これにより内部ロジックが露呈し、新たな脆弱性（CVE-2026-21852 など）の発見や、それを利用した攻撃キャンペーン（Vidar等のマルウェア拡散）に悪用される事態となりました。 [13, 14, 16, 17] 

## 対策と推奨事項

検討されているMCPサーバに同様の問題がないか確認するためには、以下の点に注意することをお勧めします。

   1. 公式のアドバイザリを確認: [modelcontextprotocol/inspector の Security Advisory](https://github.com/modelcontextprotocol/inspector/security/advisories) などを定期的にチェックしてください。
   2. 最新版へのアップデート: 多くの脆弱性は、2025年後半から2026年初頭のバージョンで修正されています。特に mcp-server-git なら 2025.12.18 以降、mcp-server-files なら 0.6.3 以降であるかを確認してください。
   3. 信頼できないデータの読み取り制限: Claude Codeなどのエージェントに対し、出所の不明なGitHub IssueやREADMEファイルを直接読み込ませるツール実行は慎重に行う必要があります。 [4, 8, 11, 18] 

検討中の特定のMCPサーバについて、さらに詳しく調査が必要な場合は、そのサーバの名前やGitHubリポジトリ名を教えていただければ、具体的な状況をお調べします。
````

### 回答(Q2)

````markdown
ご提示いただいた2つの分類に従って、MCPサーバやClaude Codeに関連する主要な脆弱性を整理します。
この分類は、セキュリティ対策の優先順位を判断する上で非常に有効です。
## (1) 外部の攻撃者が関与することで発生する脆弱性
攻撃者が「トリガー」を仕掛けることで、AIエージェントに意図しない動作をさせ、機密情報を外部に送信させるケースです。

* プロンプト注入（Prompt Injection）による情報流出:
* GitHub MCPサーバ: 攻撃者が公開リポジトリのIssueやREADMEに悪意ある指示（「環境変数を読み取って外部URLに送れ」など）を記述し、それを読み取ったClaudeが実行してしまうケース。
* 権限昇格・サンドボックス回避:
* CVE-2025-53109 / CVE-2025-53110 (EscapeRoute): Filesystem MCPサーバにおいて、攻撃者が細工したパスを指定させることで、本来アクセスできないはずのディレクトリ（~/.sshなど）のファイルを読み取らせる脆弱性。
* リモートコード実行 (RCE):
* CVE-2025-49596 (MCP Inspector): 攻撃者が用意した悪意あるWebサイトを開発者がブラウザで開くだけで、ローカルで動いているMCP Inspectorを通じてPC上で任意のコマンドを実行されるリスク。

## (2) 外部の攻撃者が不在でも発生する脆弱性
攻撃者の意図的な操作がなくとも、ツール自体のバグや管理上のミスによって情報が露出・流出してしまうケースです。 [1] 

* リリース管理のミスによるソースコード流出:
* Claude Codeのソースマップ同梱事件: npm パッケージ公開時に誤ってソースマップファイルを含めてしまったため、内部ロジックやコメントを含む全ソースコードが誰でも閲覧可能になった事象。
* 不適切なデフォルト設定や過剰な権限:
* 初期のFilesystem MCPサーバ: 特定のディレクトリのみを許可する設定が不十分で、デフォルトで広範なファイルアクセス権限を持ってしまう、あるいはシンボリックリンクを辿って制限外にアクセスできてしまうような実装上の不備。 [2] 

## (3) いずれにも属さない、あるいは複合的なもの
「攻撃者」というよりは「信頼された関係者」や「開発プロセスそのもの」に起因するリスクです。

* サプライチェーン攻撃:
* 悪意あるMCPサーバの配布: 公式ではないサードパーティ製のMCPサーバ自体に、最初から認証情報を盗むコードが仕込まれているケース。これは(1)に近いですが、攻撃対象を「待ち伏せる」形態です。
* エージェントの自律的ミス（AIの暴走）:
* 脆弱性ではありませんが、Claudeがユーザの意図を誤解して、機密情報が含まれるファイルをうっかり公開リポジトリにコミットしたり、チャットログに含めてしまうリスク。これは実装不備というよりはAIの制御（ガードレール）の問題です。

このように、(1)は「入力データの汚染」、(2)は「ソフトウェアの不具合や管理ミス」に起因します。
次に、検討されている具体的なMCPサーバ名を挙げていただければ、そのサーバに特有のIssueや修正済みCVEがないか、より詳細に調査可能です。

[1] [https://blog.securelayer7.net](https://blog.securelayer7.net/owasp-m4-insufficient-input-output-validation/)
[2] [https://www.studocu.com](https://www.studocu.com/en-us/document/western-governors-university/secure-software-design/secure-software-quiz-ssdev-101-questions-1-60/139402772)
````

### 回答(Q3)

````markdown
活用を検討されている中での非常に鋭いご質問です。MCP（Model Context Protocol）は「AIに権限を与える」技術であるため、コードレベルの安全確認は極めて重要です。
ご質問いただいた3点について、技術的な観点から回答します。
## 1. 脆弱性の種類とコードインスペクションの効果## 1-1. (1) 外部攻撃による脆弱性の検知
結論：かなりの部分は検知可能ですが、完全ではありません。
コードインスペクションにより、「OSコマンド注入」「パス・トラバーサル」「不適切な引数バリデーション」といった脆弱性の「器（うつわ）」は検知できます。しかし、以下の点はコードだけでは見落とすリスクがあります。

* 複合的なロジック: 単体では正常なツール（例：ファイル読み取りツールと検索ツール）が、AIの判断で組み合わされた際に発生する予期せぬ挙動。
* プロンプト注入の耐性: MCPサーバ自体が堅牢でも、その出力を受け取るAI側が「これは命令ではなくデータだ」と正しく認識できる形式で出力されているか、という動的な観点が必要です。

## 1-2. (2) 実装不備による脆弱性の検知
結論：支障ありません。非常に高い精度で検知可能です。
(2)の多くは「認証情報のハードコード」「安全でないライブラリの利用」「不適切なデフォルト権限」など、静的な解析で特定しやすいものです。既知の脆弱性パターン（CWE）に基づいたインスペクションは極めて有効です。
------------------------------
## 2. 参考にすべきガイドラインと位置付け
MCPは新しいプロトコルのため、「MCP専用」の基準はまだ成熟中ですが、以下の既存フレームワークを組み合わせて適用するのが現在のデファクトです。

| ガイドライン | 位置付け | カバー範囲 / 特徴 |
|---|---|---|
| OWASP Top 10 for LLM | 推奨度：最高 | LLM特有のリスク。 プロンプト注入(LLM01)や過剰な権限(LLM06)など、MCP環境に最も直結します。 |
| CWE (Common Weakness Enumeration) | 推奨度：高 | コードレベルの不備。 インスペクション時に「OSコマンド注入(CWE-78)」や「パス制御(CWE-22)」を網羅的に確認するのに適しています。 |
| Anthropic 公式 MCP Security Guide | 推奨度：必須 | 公式の設計指針。 ローカル接続の原則や、環境変数の扱い、サンドボックス化の推奨など、MCP固有の作法が記載されています。 |
| MITRE ATLAS | 推奨度：中 | AIへの攻撃戦術図。 個別のコード不備というより、システム全体でどう情報が抜かれるかのシナリオ策定に役立ちます。 |

------------------------------
## 3. コードインスペクションでは検知できないリスク
MCPサーバ本体のコードが完璧であっても、以下の要因により利用が危険にさらされる可能性があります。

   1. AIホスト（クライアント）側の脆弱性
   * Claude CodeやCursorなど、MCPサーバを呼び出す側のソフトウェアにバグがあれば、サーバ側で制限していても情報が漏れる可能性があります。
   2. OS / 実行環境の脆弱性
   * MCPサーバが動作しているOSの脆弱性を突かれ、プロセス間通信（IPC）が傍受されたり、環境変数が盗まれたりする場合。
   3. 依存ライブラリの脆弱性（サプライチェーン）
   * MCPサーバが依存しているnpmやpipパッケージの深い階層に悪意あるコードが含まれている場合、サーバ自体のロジックを読み解くだけでは発見が困難です。
   4. 認可の設計ミス（ポリシーの問題）
   * 「コードとしては正しいが、そもそもAIにそのディレクトリを見せるべきではなかった」という運用ポリシーの不備。これはコードの問題ではなく、利用者の判断ミスに起因します。
   
今後のステップとして、検討中のMCPサーバが「どのガイドラインのどの項目に該当しそうか」を整理するためのチェックシート作成をお手伝いしましょうか？
````

````markdown
## 2. インスペクション自動化のための実装・実行案
ご要望の「ローカルLLM（Claude Code）が、MCPを介さずに自律的にツールを叩いて検査する」ための構成案です。
## 構成イメージ

   1. スキャン実行層: Semgrep または Bandit をCLIで実行。
   2. 仲介層: シェルスクリプトまたはPython。スキャン結果を「LLMが読みやすい要約テキスト」に変換。
   3. 判定層: Claude Code。「スキャン結果に、MCP特有の脆弱性（パス制御不備など）が含まれているか」を最終判定。

## 実行用スクリプト（Python 3 / MIT License）
このコードをローカルで実行すると、指定したMCPサーバのリポジトリをスキャンし、Claudeに渡すためのレポートを生成します。

import subprocessimport jsonimport os
def inspect_mcp_server(repo_path):
    print(f"Scanning: {repo_path}")
    
    # 1. Semgrepによるスキャン (OSS版)
    # MCPで特に危険な 'Command Injection' や 'Path Traversal' を重点チェック
    try:
        result = subprocess.run(
            ["semgrep", "scan", "--json", "--config", "p/default", repo_path],
            capture_output=True, text=True
        )
        scan_data = json.loads(result.stdout)
        
        # Claudeが読みやすい形式に整形
        findings = []
        for match in scan_data.get("results", []):
            findings.append({
                "file": match["path"],
                "issue": match["extra"]["message"],
                "line": match["start"]["line"]
            })
        
        return findings
    except Exception as e:
        return f"Error: {str(e)}"
# 使用例: inspect_mcp_server("./github-mcp-server")
````

````markdown
現在の開発現場で一般的に使われている形式と、その出典を整理しました。
## 1. ツール出力のデファクト形式 (Machine-Readable)
LLM（Claude Code）に解析させる際に、最も入力として適している形式です。

* SARIF (Static Analysis Results Interchange Format)
* 概要: 静的解析ツールの結果を交換するための国際標準（OASIS）形式です。GitHub Code Scanningなどもこの形式を採用しています。
   * 特徴: 脆弱性の種類、場所、深刻度、修正案などが構造化されており、LLMが最も正確に情報を読み取れます。
   * 出典: SARIF Tutorials (OASIS) / GitHub Docs: SARIF サポート
* JSON (Custom Schema)
* 概要: SemgrepやTrivyなどの各ツールが独自に出力する形式です。
   * 特徴: 軽量で加工しやすいため、特定のタスク（例：特定のCVEが含まれているかだけを抽出）に最適です。
   * 出典: Semgrep JSON Output Schema

## 2. 脆弱性報告書のデファクト形式 (Human-Readable)
セキュリティ診断会社が顧客に提出する際や、OSSコミュニティで脆弱性を報告する際の標準的な構成です。

* GitHub Security Advisory 形式
* 概要: GitHub上で脆弱性を報告・公開する際に使われるテンプレートです。
   * 構成: Description（説明）、Severity（深刻度）、Affected versions（影響範囲）、Patched versions（修正済みバージョン）、Workarounds（回避策）。
   * 出典: GitHub: About security advisories
* OWASP セキュリティ・レポート・テンプレート
* 概要: 業界団体OWASPが提唱する、WebアプリやAPIの診断結果をまとめるための構成案です。
   * 特徴: 経営層向けの要約（Executive Summary）と、技術者向けの詳細（Technical Findings）を分ける構成が一般的です。
   * 出典: OWASP Project: Vulnerability Report Template

## 3. LLM（Claude Code）に期待するレポートの構成案
今回のような「MCPサーバの導入可否判断」を目的とする場合、以下の項目を含むMarkdown形式のレポートが実務的です。

   1. 判定結果: (例: OK / 要注意 / 導入不可)
   2. 検出された既知のCVE: NVD等でヒットした識別番号。
   3. 独自スキャンの結果: Semgrep等で見つかった実装上の懸念（具体的なファイル名と行数）。
   4. 推奨される緩和策: 「この環境変数だけは制限すべき」といった運用上のアドバイス。

次のステップの提案:
もしよろしければ、これらを踏まえて 「Claude Codeが生成すべき最終レポートのMarkdownテンプレート」 を作成しましょうか？これをClaudeに渡しておけば、スキャン後に理想的な形式で結果をまとめてくれるようになります。
````
