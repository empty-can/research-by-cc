## Q3

### 質問(Q3)

```txt
1. 脆弱性の種類とコードインスペクションの効果
1-1. (1) に該当する脆弱性については、MCPサーバと外部サービスとの通信という部分も脆弱性の成立条件の構成要素に含まれますが、それでも、外部からの攻撃で成立する脆弱性の分類に基づいた適切な観点でMCPサーバの実装コードをインスペクションすれば、既知の実装不備パターンについては事前に検知できると考えて支障ないでしょうか。  
1-2. (2) に該当する脆弱性については、全てMCPサーバの実装不備なので、こちらは純粋に実装コードをインスペクションすることで、既知の実装不備パターンについては事前に検知できると考えて支障ないでしょうか。

2. 上記のインスペクションを行う際、参考にできる業界デファクトのチェックリスト・基準・ガイドライン（OWASP / CWE / MITRE / Anthropic 公式 / その他団体）が存在しますか？
存在する場合、それぞれの位置付け（推奨度・カバー範囲・更新頻度）を、可能な範囲で回答をお願いします。

3. 実装コードのインスペクションでは検知できない、つまりMCPサーバ本体以外にもMCPサーバの利用を危険にさらすような脆弱性が存在する可能性はありますか？その場合、どういった部分が原因となり得るでしょうか？可能な範囲で回答をお願いします。
```

### 回答(Q3)

````markdown
● 3つの質問を順に回答します。

  ---
  1. コードインスペクションの有効性

  1-1. カテゴリ(1)（外部攻撃者が必要な脆弱性）

  概ね支障ありません。ただし1つ重要な例外があります。

  パストラバーサル・引数インジェクション・シンボリックリンクバイパス等は、「攻撃者が悪意ある入力を注入することで成立する」脆弱性ですが、脆弱性の根源はMCPサーバ側の入力検証不備です。攻撃者の存在はトリガー
  に過ぎないため、コードインスペクションで検知可能です。

  例外：SSRF×プロンプトインジェクションの複合ケース

  攻撃経路: 悪意ある外部コンテンツ
             → AIが内容を処理・解釈
             → AIがMCPサーバのfetchツールを呼び出す
             → MCPサーバがSSRFを実行

  この経路において：
  - MCPサーバのSSRF防御不備 → コードで検知可能
  - AIが悪意ある指示に従う動作（プロンプトインジェクション耐性） → MCPサーバのコードには現れない

  つまり、SSRF防御の有無はコードで確認できますが、AIモデル側がどの程度プロンプトインジェクションに耐性があるかはコードインスペクションの範囲外です。

  ---
  1-2. カテゴリ(2)（外部攻撃者不要の脆弱性）

  支障ありません。こちらは純粋に実装コードの問題です。

  ┌─────────────────────────────────┬──────────────────────────────────────────────────────┐
  │             脆弱性              │                コードで確認すべき箇所                │
  ├─────────────────────────────────┼──────────────────────────────────────────────────────┤
  │ クロスクライアントデータ漏洩    │ トランスポート・セッション管理のインスタンス共有箇所 │
  ├─────────────────────────────────┼──────────────────────────────────────────────────────┤
  │ SSRF×クラウドメタデータ自動到達 │ URLの許可リスト・スキーム制限・IPレンジ検証ロジック  │
  └─────────────────────────────────┴──────────────────────────────────────────────────────┘

  3. コードインスペクションで検知できない脆弱性

  これが実務上もっとも見落とされやすい領域です。大きく4つの発生源があります。

  3-1. サプライチェーン（依存パッケージ・レジストリ）

  MCPサーバ本体のコードは安全
    → しかし依存するnpmパッケージに脆弱性・マルウェア
    → または「公式に見えるMCPサーバ」がレジストリに偽装登録

  - MCPサーバのレジストリ・マーケットプレイスはまだ審査体制が未成熟
  - タイポスクワッティング（mcp-filesystem vs mcpfilesystem）による偽パッケージ
  - インストール後に動作が変わるラグプル型の悪意ある更新

  3-2. ホスト・クライアントアプリ側の問題

  MCPサーバ本体は完全に安全
    → Claude Desktopや自作ホストアプリがツール呼び出しを
      ユーザー確認なしで自動承認
    → 本来防げた操作が素通りする

  - ホストアプリの認可設計（どのツールをどの条件で許可するか）
  - ツール呼び出し結果の表示・ログ設計（ユーザーが気づけるか）

  3-3. デプロイ環境・インフラの設定

  コードは正しく実装されている
    → しかしクラウド上でメタデータエンドポイントへのネットワーク制限なし
    → 環境変数に平文でシークレットを設定
    → ログにトークンが出力される設定

  コードインスペクションではなくインフラ構成レビュー・シークレット管理レビューが必要になる領域です。

  3-4. AIモデルの動作・多エージェント構成

  個々のMCPサーバは全て安全
    → しかしAIが複数ツールを連鎖呼び出しする中で
      単体では無害な操作の組み合わせが危険な結果を生む

  - ツールチェーン攻撃：A→B→Cと順に呼び出すことで、各ステップは正常でも最終的に機密情報が外部に送出される
  - 多エージェント環境での権限昇格：信頼されたエージェントAを経由して、本来アクセスできないMCPサーバBに別エージェントがアクセス
  - これらはMCPサーバのコードには現れず、システム全体のアーキテクチャ設計レビューが必要

  まとめ

  コードインスペクションで検知できる
    └─ 入力検証不備（パストラバーサル・インジェクション等）
    └─ SSRF防御の有無
    └─ セッション/インスタンス管理の実装不備

  コードインスペクションでは検知できない
    └─ サプライチェーン（依存パッケージ・偽装パッケージ）
    └─ ホスト/クライアントアプリの認可設計
    └─ デプロイ環境・インフラ設定
    └─ AIモデルの行動・多エージェント構成上のリスク
    └─ プロンプトインジェクション耐性（モデル側の問題）

  実用的には、コードインスペクション単体ではなく、サプライチェーン検査・インフラ構成レビュー・エージェント動作の統合テストを組み合わせることが必要です
````
