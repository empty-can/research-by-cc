  - **(1) 外部攻撃者の関与が必要なタイプ**: 実装不備は存在するが、攻撃者が能動的にトリガー（悪意あるリポジトリ提供 / 悪意ある MCP サーバ運用 /
  悪意ある入力送信 等）しない限り情報流出は顕在化しない
  - **(2) 外部攻撃者の関与が不要なタイプ**:
  通常運用しているだけで情報流出が起こりうる実装不備（プレーンテキスト保存・テナント越境・意図せぬログ出力・テレメトリ送信 等）

  なお、本回答は **追加 WebSearch を併用** して情報を裏取りしています。

  ---

  ### (1) 外部攻撃者の関与が必要なタイプ

  |---|---|---|
  | **CVE-2025-59536 / CVE-2026-21852** | Claude Code (project files / MCP / Hooks / env) | 攻撃者が悪意ある repo

  | **CVE-2025-49596** | MCP Inspector | 攻撃者が悪意ある Web ページを用意、被害者が MCP Inspector 稼働中にそれを訪問 |

  - 攻撃の起点は **「悪意あるコンテンツとの接触」** という外因
  - 防御策は「**未検証の外部成果物（repo / MCP サーバ / プロンプト入力源）を信頼しない**」+「修正版へのアップデート」
  - 実装不備自体は修正済み、または修正リリースが提供されている

  ### (2) 外部攻撃者の関与が不要なタイプ

  該当事案は **少数** ですが、存在します。実装不備により **通常運用しているだけで** 情報流出が起こり得るタイプです。

  | 事案 | 対象 | 流出メカニズム |
  |---|---|---|
  | **Asana MCP データリーク事案**（2025-06） | Asana MCP インテグレーション | バグにより一部顧客の情報が **他テナントの MCP
  インスタンスへ漏出**。攻撃者不在で発生。Asana 側は MCP インテグレーションを 2 週間オフラインにして修正対応 |
  | **MCP サーバの OAuth トークン / API キー平文保存（一般リスク）** | 多数の MCP サーバ実装（個別 CVE 化されていないものも多い） | 多くの MCP サーバが
  OAuth トークン・API キーを
  **平文または不十分な保護でローカル設定ファイル等に保存**。バックアップ・誤同期・共有ファイルシステム経由で受動的に漏出しうる。Trend Micro / Hadrian
  等の研究レポートで指摘 |

  **この分類の共通特徴**:
  - 攻撃の起点は **「実装が前提とする境界の自然な逸脱」**（テナント境界の混線、保存場所の権限境界の弱さ）
  - 防御策は「**ベンダ側の修正待ち**」または「**自前で平文保存を避ける構成**」（OS のキーチェーン / シークレットマネージャ連携など）
  - 「攻撃者が悪意を持って何かをしなくても、ある日気づくと漏れていた」が成立しうる

  **重要な補足**:
  - 個別 CVE が割り振られていない事案も多く、Asana の例は **インシデント報告** ベース（CVE 番号は確認できず）。
  - 「平文保存」リスクは MCP プロトコル仕様自体ではなく、**個別 MCP サーバ実装の品質依存**。導入検討する MCP サーバ個別に確認が必要。

  ### (3) 上記のいずれにも完全には属さないもの（境界事例）

  「外部攻撃者の関与」の定義によって分類が揺れる、ハイブリッド事例があります。

  #### 3-A. 「内部の意図せぬ第三者」を介する事例

  | 事案 | 該当の難しさ |
  |---|---|
  | **Supabase × Cursor Agent インシデント**（2025 年中盤） | サポートチケットに紛れた悪意ある SQL 命令を Cursor
  エージェントが実行し、トークンが**公開サポートスレッドに露出**。「攻撃者」はサポートチケット投稿者だが、**SaaS 通常ユーザの正当な操作経路**
  経由で実現する点が (1) と (2) の中間 |
  | **Cross-server context contamination**（複数 MCP サーバ間のコンテキスト汚染） | 利用者自身が正当に選んだ複数 MCP サーバ間で、LLM が **サーバ A
  から得た秘匿情報をサーバ B へ無自覚に渡す**。攻撃者不在でも漏出しうるが、漏出先となる「より低信頼な MCP
  サーバ」の存在が前提（=広義の攻撃者は介在）。authzed のタイムライン記事や Composio の解説でこの設計問題が指摘されている |

  #### 3-B. プロトコル設計レベルの問題（CVE 化されにくいもの）

  - **Tool poisoning / hidden instructions in tool descriptions**: MCP の Tool description 自体に LLM 向けの隠し指示を埋め込む手法。Tool
  提供者の意図次第で「正規 MCP サーバなのに利用者の不利益動作を引き起こす」設計上の問題。攻撃者の定義次第で (1) または (2) の中間
  - **過剰な permission scope の付与**: MCP サーバが要求する権限が不必要に広く、結果としてエージェントが秘匿情報にアクセス可能になる設計問題。これは「実
  装不備」というより「設計選択」の問題で、伝統的な CVE の枠に入りにくい

  ## 1. 脆弱性の種類とコードインスペクションの効果

  ### 1-1. (1) 外部攻撃者の関与が必要なタイプ → コードインスペクションで検知可能か？

  **結論: 既知の実装不備パターンについては、概ね検知可能。ただし重要な留保あり。**

  #### 検知可能な理由

  (1) に該当する CVE の大多数は、伝統的な **CWE（Common Weakness Enumeration）にマッピング可能な実装パターン** に起因しています：

  | 既知 CVE 例 | マッピングされる CWE | 静的解析・コードレビューで検知しやすい |
  |---|---|---|
  | CVE-2025-6514 (mcp-remote) | CWE-78 (OS Command Injection) | ◎ |
  | CVE-2025-49596 (MCP Inspector) | CWE-78, CWE-352 (CSRF 類似) | ◎ |
  | CVE-2025-53109/53110 (Filesystem MCP) | CWE-22 (Path Traversal) | ◎ |
  | CVE-2025-53967 (Figma MCP) | CWE-306 (Missing Authentication) | ◎ |
  | CVE-2025-54136 (MCPoison) | CWE-367 (TOCTOU) | △ |
  | CVE-2025-59536 / CVE-2026-21852 | CWE-94 / CWE-200 系 | ○ |

  SAST ツール（Semgrep / CodeQL / Bandit 等）や、CWE ベースのチェックリストによる手動レビューで、これら**「既知パターン」は事前に検知できます**。

  #### 重要な留保 4 点

  しかし、「(1) に該当する脆弱性 ＝ 全部コードインスペクションで防げる」と単純化するのは危険です：

  1. **MCP サーバ単体ではなく依存ライブラリ起因の不備**: mcp-remote の `open()` 関数の使い方は MCP
  サーバ自身のコードだが、依存パッケージ側に脆弱性がある場合は **依存も含めた検査（SCA: Software Composition Analysis）** が別途必要
  2. **「想定する攻撃者」のモデル化が抜けると検知できない**: 例えば「OAuth
  認可エンドポイントのレスポンスが攻撃者制御下にある」というシナリオを想定していないと、レスポンス値の `open()`
  渡しは「ただのリンク起動処理」に見えてしまう。**MCP 特有の脅威モデル**を持って臨まないと、汎用 SAST はこの種の脆弱性を見落とす
  3. **時系列依存（TOCTOU 系）の検出は静的解析の苦手領域**: MCPoison
  のような「設定承認時点と実行時点で値が異なりうる」設計上の問題は、動的なフロー解析や脅威モデリングが必要
  4. **MCP プロトコル特有のセマンティクス**: Tool description に隠し命令を埋め込む手法（tool
  poisoning）等、**コードの構文ではなく文字列の意味内容が問題** になるケースは、伝統的なコード検査では検知困難

  **まとめ**: 「**既知の実装不備パターンに、MCP 特有の脅威モデルを掛け合わせた観点でインスペクションすれば、(1)
  の多くは事前検知可能**」が現実的な答え。汎用 SAST だけでは不十分で、MCP 専用のルールセット（後述の OWASP MCP Top 10 等）と組み合わせる必要があります。

  ---

  ### 1-2. (2) 外部攻撃者の関与が不要なタイプ → コードインスペクションで検知可能か？

  **結論: 純粋に MCP サーバ実装の問題であれば検知可能。ただし「インスペクション可能であること」自体が前提となる点に注意。**

  #### 検知可能な理由

  (2) の代表パターンは以下のように、いずれも**コード上の特定パターンとして表出します**：

  | パターン | 検知方法 |
  |---|---|
  | 平文での credential 保存 | `fs.writeFileSync` 等で `~/.config/*.json` に token 系を書き出す箇所の grep / SAST |
  | OS 標準シークレットストア未使用 | macOS Keychain / Windows Credential Manager / libsecret 等の呼び出しが存在しないことを検査 |
  | 過剰なログ出力 | logger 呼び出しで credential / token / API key 系変数を含む箇所の検査 |
  | テナント分離欠落 | リクエスト処理で tenant_id / user_id がアクセス制御の述語に含まれているかの検査 |
  | 平文での外部送信 | HTTP（HTTPS でない）通信先、不要なテレメトリ送信先の検査 |

  これらは **静的解析で十分検出可能なパターン** であり、(1) よりむしろ「機械的に潰しやすい」とすら言えます。

  #### 重要な留保 3 点

  ただし、(2) を「全て」インスペクションで検知できる、と言うには以下の留保が必要：

  1. **クラウドホスト型 MCP サーバはそもそもインスペクション不可能**: Asana MCP
  データリーク事案のように、**実装コードがベンダ側に閉じている場合**、利用者はソースコードを見ることができない。この場合、(2)
  の検知は「ベンダの脆弱性開示・SOC 2 等の第三者監査・契約上のセキュリティ条項」に依存する
  2. **テナント分離バグは「設計レベル」で表出することが多い**:
  コード上の単純なパターンマッチでは検出が難しく、**データフロー解析・スレッドモデル解析・状態共有箇所の網羅レビュー**
  が必要。特に並行処理由来のレース条件は静的解析の苦手領域
  3. **「設定で変わる挙動」はコード単体では判定できない**: 例えば「verbose ログモード有効時のみ credential が漏れる」「デバッグビルドのみ telemetry
  送信」のような設定依存挙動は、コードだけでなく **デフォルト設定 + ドキュメント記載の運用前提** までセットで検査する必要がある

  **まとめ**: 「**MCP サーバが OSS で実装をインスペクション可能、かつパターンマッチに加えてデータフロー・設定の両面を見るレビュー体制があれば、(2)
  の既知パターンの大半は検知可能**」が現実的な答え。

  ## 3. コードインスペクションで検知できない領域

  **結論: 多数存在します。** MCP セキュリティは「MCP
  サーバ本体のコード品質」だけでは閉じず、システム全体の信頼鎖が成立しないと安全にならない構造です。代表的なものを以下に整理します。

  ### 3-A. MCP サーバ「外側」の構成要素由来

  | 原因領域 | 具体例 |
  |---|---|
  | **MCP ホスト（クライアント）側の脆弱性** | Claude Code / Cursor / Claude Desktop 自体の脆弱性（CVE-2025-54136 MCPoison、CVE-2025-59536 等）。**MCP
  サーバを完璧に実装しても、クライアント側の TOFU バグで侵害される** |
  | **設定ファイル（mcp.json / claude_desktop_config.json）の不備** | 平文 API キー埋め込み、過剰権限設定、未承認 MCP
  サーバの混入。**コードではなく構成データの問題** |
  | **OS / 環境変数経由のリーク** | CVE-2026-21852 の `ANTHROPIC_BASE_URL` 上書きのように、環境変数を信頼することで漏洩。MCP
  サーバ実装は正しくても、ホスト OS の env 取り扱いに起因 |
  | **ネットワーク層** | TLS 設定不備（古い TLS、自己署名証明書の無条件受け入れ）、ファイアウォール不備によるリモート MCP の意図せぬ公開 |
  | **デプロイメント / コンテナ** | Docker image の secret 埋め込み、Kubernetes secret の不適切な mount、CI/CD ログでの token 露出 |

  ### 3-B. サプライチェーン由来

  | 原因領域 | 具体例 |
  |---|---|
  | **パッケージ名 typosquatting** | 公式は `@modelcontextprotocol/*`、非公式の `@mcp/*` `@anthropic-ai/*` 等の偽装パッケージが過去発生 |
  | **MCP サーバの「乗っ取り」** | npm パッケージのメンテナアカウント乗っ取り、依存先での悪意ある更新（CVE 化されない事案も多い） |
  | **rug pull**（リリース後変更） |
  初回リリースは安全だが、後続バージョンで悪意あるコードを混入。コードレビューは「レビュー時点のスナップショット」しか保証しない |
  | **transitive dependency** | 直接依存ではない孫依存に脆弱性。SCA ツールが必須 |

  ### 3-C. LLM / プロンプト層由来

  | 原因領域 | 具体例 |
  |---|---|
  | **Tool poisoning** | Tool 説明文に LLM
  向け隠し命令を埋め込む。**コードとしては正しいが、文字列の意味内容が攻撃ペイロード**。コードインスペクションでは「ただの説明文」にしか見えない |
  | **Prompt injection (indirect)** | MCP サーバが取得してくる外部データ（Web ページ、ファイル内容等）に隠された命令を LLM が実行。MCP
  サーバは「データを返しただけ」で実装不備はない |
  | **Memory / context poisoning** | エージェントの長期記憶や会話履歴に毒を仕込み、後続セッションで悪影響。MCP サーバ単体の問題ではない |
  | **Confused deputy** | 利用者の権限で動く MCP サーバが、攻撃者の意図を実行してしまう構造。MCP サーバ実装は正しくても認可モデル設計の問題 |

  ### 3-D. マルチ MCP・エージェント間相互作用由来

  | 原因領域 | 具体例 |
  |---|---|
  | **Tool shadowing / cross-server contamination** | 信頼できる MCP サーバ A から得た秘匿情報を、低信頼な MCP サーバ B
  にエージェントが渡してしまう。個々の MCP サーバを単独レビューしても発見できない |
  | **権限の組み合わせ問題** | 個別には無害な権限が、組み合わさると危険になる（例: ファイル読み取り権 + 外部送信権 = 任意ファイル流出） |
  | **Inter-agent communication** | 複数エージェントが連携する系での通信途中での改ざん・盗聴。OWASP Agentic Top 10 2026 でも独立項目として扱われている |

  ### 3-E. 運用・人間要因由来

  | 原因領域 | 具体例 |
  |---|---|
  | **ユーザの過剰承認** | 「全 MCP サーバを auto-approve」設定、警告ダイアログを盲目的に承認 |
  | **MCP サーバの不適切な権限付与** | 必要以上のスコープを持つ OAuth トークンを発行 |
  | **インシデント検知体制の欠落** | 異常な MCP サーバ呼び出しパターンを監視していないため、侵害が長期化 |
  | **ベンダ側のクラウド型 MCP の信頼性** | コードを見られないクラウド MCP サーバ（Asana 事案）に対しては、ベンダの SOC 2 / ISO 27001
  等の第三者監査に依存するしかない |

  ### 3-F. クライアント（Claude Code 等）と MCP の境界での問題

  | 原因領域 | 具体例 |
  |---|---|
  | **MCP プロトコル自体の設計選択** | STDIO 経由の設定→コマンド実行直結という設計が CVE-2025-49596 等の根本原因。これは個別 MCP
  サーバ実装の問題ではなく **プロトコル / SDK レベル** の問題 |
  | **承認 UI / UX の不備** | 「このツールは何をするか」がユーザに伝わらない承認ダイアログ。Tool poisoning が成立しやすい |

  ---

  ### 全体まとめ

  - **コードインスペクションは必要だが、必要十分ではない**。(1)(2) いずれも「既知パターン」は検知可能だが、「MCP
  サーバ実装コードのみ」では捉えられない攻撃面が広く存在する
  - 実用的な評価戦略は **「コードインスペクション（pattern-based +
  threat-modeled）」+「設定・運用レビュー」+「ホスト/クライアント側レビュー」+「サプライチェーン追跡」+「ランタイム監視」** の多層防御
  - 業界デファクトとしては **OWASP MCP Top 10 + OWASP "Practical Guide" 2 種** を起点に据えるのが現時点で最も妥当

  ## 4. タイミング攻撃・サイドチャネル攻撃の MCP 文脈での扱い

  ### 4-1. MCP サーバの脅威モデルにおいて、現実的な脅威となり得るか？

  **結論: 現時点では「現実的脅威の優先順位は低い」。ただしゼロではなく、特定シナリオでは検討対象になる。**

  #### 優先順位が低い理由

  - 現在の MCP 関連 CVE は **RCE / credential exfiltration / path traversal / prompt injection / tool poisoning**
  といった「高インパクト・低コスト」攻撃が圧倒的多数。攻撃者にとって側チャネル探索は ROI が低い
  - OWASP MCP Top 10 / OWASP Top 10 for Agentic Applications 2026 / OWASP GenAI
  各種ガイドのいずれも、**サイドチャネル攻撃を独立カテゴリとして取り上げていない**
  - WebSearch 結果でも MCP 文脈での timing/side-channel 攻撃の **具体事例・CVE はほぼ見当たらない**

  #### それでも検討対象になりうるシナリオ

  | シナリオ | 想定脅威 |
  |---|---|
  | **リモート MCP サーバが認証処理で文字列比較に通常の `==` を使う** | 認証 token の正規 vs 不正での比較時間差を観測し、token
  をブルートフォースで特定（典型的 timing attack） |
  | **マルチテナント SaaS の MCP インテグレーション** | 別テナントのデータ存在有無をレスポンス時間差で推測（**Asana 事案のような cross-tenant 問題の
  sub-pattern**） |
  | **MCP サーバが外部 API 呼び出しキャッシュを共有実装** | キャッシュヒット/ミスの時間差で他ユーザのクエリ内容を推測 |
  | **LLM 推論時間自体が input に依存する場合** | プロンプトのトークン数推定 → indirect info leak。これは MCP よりも LLM provider 側の問題 |
  | **共有ホスト型 MCP サーバの CPU / メモリ使用** | 同一インスタンス上の別テナントの活動を統計的に観測（cloud co-tenancy 攻撃の応用） |

  #### 結論の補強

  「MCP セキュリティで側チャネルを最優先で対策する必要はない」が、「**リモート MCP サーバ実装で認証 token を扱う場合は constant-time comparison
  を使う**」程度の防御は最小限の良いプラクティスとして取り入れるべきです。完全に無視するのは推奨できません。

  ### 4-2. 検知に有効なツール・手法

  **MCP 専用のサイドチャネル検査ツールは存在しない**ため、汎用ツールを応用する形になります。

  | ツール / 手法 | ライセンス | 観点 | URL |
  |---|---|---|---|
  | **ct-verif** | MIT | C/LLVM 向けの **constant-time 検証ツール**。暗号実装の timing leak 検証で標準的 |
  <https://github.com/imdea-software/verifying-constant-time> |
  | **MicroWalk** | OSS | 動的解析でメモリアクセス / 命令フローの input 依存性を検出。**サイドチャネル leak 自動検出** |
  <https://github.com/microwalk-project/Microwalk> |
  | **dudect** | OSS | timing leak を統計的に検出する dynamic test。**実装言語非依存** | <https://github.com/oreparaz/dudect> |
  | **Semgrep カスタムルール** | LGPL-2.1 | **`==` / `!=` での token 比較を検出し、`crypto.timingSafeEqual` / `hmac.compare_digest` への置換を強制**
  する pattern を書くことが現実的 | <https://semgrep.dev/> |
  | **手動コードレビュー観点** | — | (a) 認証 token 比較は constant-time 関数を使っているか、(b)
  エラーメッセージで「ユーザ不在」と「パスワード誤り」を区別していないか、(c) cache 実装が tenant scope を持つか、(d) レスポンス時間に input
  が影響しうるか — をチェックリスト化 | — |

  **実用的なアドバイス**:
  - インスペクション体制が成熟するまでは「**Semgrep カスタムルールで `==` / `!=` 系の token 比較を機械的に検出して constant-time
  に置換させる**」程度を最低限のラインに据えるのが現実的
  - 本格的な側チャネル分析（ct-verif / MicroWalk / dudect）は **暗号実装を MCP サーバが自前で書いている場合に限定**
  して適用すれば十分。標準ライブラリ（OS / 言語標準 crypto）を使っているなら検査対象としての優先度は低い

  ---

  ### 全体まとめ

  - **インスペクション自動化**: MCP-Scan + Semgrep（カスタムルール）+ CodeQL + OSV-Scanner + gitleaks を Claude Code
  から直接実行する構成が現実的かつ高精度
  - **セキュア実装例**: 単一の decisive な「これが正解」テンプレートは未確立。SDK 公式リファレンス + Anthropic mcp-builder skill + OWASP guides
  の組み合わせ参照が現状ベスト
  - **脆弱性開示プロセス**: CVD（CERT/CC 慣習）+ GHSA + CSAF をベースに、MCP 領域では OX Security 等が大規模 coordinated disclosure の先例を作っている
  - **サイドチャネル**: MCP の脅威モデルでは優先度低だが、リモート MCP の認証 token 扱いには constant-time
  比較を最低ラインで適用すべき。本格的検査は専用暗号実装にスコープを絞る
