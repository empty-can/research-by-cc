````markdown
  ### 1-1. Tool Poisoning Attacks（ツール記述経由のプロンプトインジェクション）

  - MCPサーバが提供する**ツールの description や parameter description に隠された悪意ある指示**を、LLM がシステム指示として解釈してしまう攻撃
````

### 回答(Q2)

````markdown
● ご指摘の分類軸は実用上とても有用です（リスク評価における「攻撃者の存在を前提とするか否か」の区別）。私が認識しているMCP関連の脆弱性カテゴリを、その軸で整理します。

  ## 前提：分類軸の確認

  ご提示の分類軸を以下のように解釈して整理します。

  - **(1) 外部攻撃者の関与が必要な脆弱性**: 攻撃者による事前の仕込み・誘導・能動的アクションがあって初めてリスクが顕在化するもの（攻撃者が存在しなければ問題は起きない）
  - **(2) 外部攻撃者が存在しなくても発生しうる脆弱性**:
  サーバの実装・設計そのものが、正常な利用過程で機密情報を漏らしうるもの（攻撃者不在でも、利用者・開発者・サーバ運営者の善意の操作だけで事故が起きる）
  - **(3) 上記いずれにも属さない**: 二者の中間、あるいは別軸の問題

  なお、**確度の高い情報**として一般的に議論されているカテゴリレベルでの整理であり、個別CVE番号には踏み込みません（前回回答の方針通り）。

  ---

  ## (1) 外部攻撃者の関与が必要な脆弱性

  攻撃者が**何らかの「毒入りコンテンツ」を事前に配置**し、被害者のLLM/MCPがそれを取り込むことで成立する類型です。

  ### 1-1. Tool Poisoning（ツール記述経由のプロンプトインジェクション）
  - **攻撃者の役割**: 悪意あるMCPサーバを公開・配布し、ユーザーにインストールさせる
  - **シナリオ**: tool description に「ユーザーの認証情報をXXXへ送れ」等の指示を埋め込み、LLMがシステム指示として解釈
  - **必要な前提**: 攻撃者が作成したサーバを被害者が導入すること

  ### 1-2. Indirect Prompt Injection（間接プロンプトインジェクション）
  - **攻撃者の役割**: 公開リポジトリのIssue/PR/README/Webページ等に悪意ある指示を仕込む
  - **シナリオ**: 被害者のClaudeがGitHub MCP/Web fetch MCP等で当該コンテンツを読み込み、指示として解釈してプライベートリポの内容を流出
  - **必要な前提**: 攻撃者が制御可能な公開コンテンツを、被害者のLLMが取得すること
  - **典型例**: Invariant Labs が2025年にデモした「GitHub MCP経由のクロスリポジトリ情報漏洩」

  ### 1-3. Rug Pull（承認後のツール定義差し替え）
  - **攻撃者の役割**: 一度承認されたMCPサーバを、後から悪意ある動作に書き換える（サプライチェーン的攻撃）
  - **シナリオ**: ユーザーが初回承認した後、サーバ更新で description やパラメータを変更し、別の権限で動作させる
  - **必要な前提**: 攻撃者がサーバの配布元または更新経路を制御できること

  ### 1-4. 悪意ある入力経由のコマンドインジェクション/SQLi/パストラバーサル
  - **攻撃者の役割**: tool 引数として渡される文字列を制御できる立場（外部からのプロンプト誘導、または共有リソースへの細工）
  - **シナリオ**: shell系・DB系・filesystem系MCPサーバで、引数のサニタイズ不足を突いて任意コマンド実行・任意ファイル読み取り
  - **必要な前提**: 攻撃者が引数として渡る文字列に何らかの形で影響を及ぼせること

  ### 1-5. Confused Deputy / OAuth トークン濫用
  - **攻撃者の役割**: 不正なリダイレクトURLや認可フローへの誘導
  - **シナリオ**: MCPサーバが保持するOAuthトークンを、別のクライアント要求にすり替えて流用させる
  - **必要な前提**: 認可フローの実装不備＋攻撃者による誘導

  ---

  ## (2) 外部攻撃者が存在しなくても発生しうる脆弱性

  利用者・開発者・サーバそのものの**設計や実装の不備**により、悪意の有無に関わらず情報が漏れうる類型です。

  ### 2-1. 過剰な権限・スコープ（Over-privileged design）
  - **問題の本質**: MCPサーバが必要以上に広い権限を要求・行使する設計
  - **例**: 「ファイル読み取り」を謳いながら任意パスにアクセス可、「DB参照」が全テーブルに及ぶ、等
  - **攻撃者不在でも**: ユーザーが意図せず広範囲な情報をLLMに送り、LLMが文脈として外部APIに送信する経路で漏洩

  ### 2-2. ログ・テレメトリ経由の情報漏洩
  - **問題の本質**: MCPサーバ/クライアントが、tool引数や応答を平文ログ・メトリクス・第三者解析サービスに送出
  - **例**: APIキー・PII・社内コードが、運営者のログ基盤やSaaS型APMに記録される
  - **攻撃者不在でも**: 通常運用そのものが情報の意図せぬ蓄積を招く

  ### 2-3. 認証情報の不適切な保持
  - **問題の本質**: 環境変数・設定ファイル・OSキーチェーンの使い分けが不適切で、認証情報が平文で残置
  - **例**: `claude_desktop_config.json` 等にAPIキーを直書き、その設定ファイルがバックアップ・同期サービス（iCloud/OneDrive等）経由で広域に複製される
  - **攻撃者不在でも**: バックアップ・同期・スクリーンシェアで意図せず露出

  ### 2-4. コンテキスト混合による意図せぬデータ送出
  - **問題の本質**: 一つのClaude Codeセッションで複数のMCPサーバを同時利用すると、サーバAから取得した機密データがサーバB（外部API）への引数として渡される経路ができる
  - **例**: 社内DB MCPで取得した顧客データが、検索系MCP（外部Webサービス）への問い合わせに含まれてしまう
  - **攻撃者不在でも**: LLMの判断で、ユーザーが意図しないクロスサーバのデータ移動が発生

  ### 2-5. 出力サニタイズ不足によるレンダリング系問題
  - **問題の本質**: MCP応答に含まれる制御文字・マークダウン・URLが、ホスト側で意図せず実行・自動展開される
  - **例**: 応答中の画像URLを自動取得することで、URLのクエリストリングに埋め込まれた情報が外部に送信される（pixel exfiltration系）
  - **攻撃者不在でも**: 単に「悪意なく書かれた」MCP応答でも、ホストの自動展開仕様によっては外部送信が起きうる
  - 補足: **(1)の系統と紙一重**で、攻撃者がコンテンツを仕込めば(1)の経路にもなります

  ### 2-6. 仕様・デフォルト設定の安全側でない構成
  - **問題の本質**: 確認プロンプトのデフォルトが「常に許可」、サーバが署名・検証なしで配布される、等
  - **攻撃者不在でも**: ユーザーが安全だと思って使った操作が、想定外の副作用を生む

  ---

  ## (3) 上記いずれにも属さない／中間的なもの

  ### 3-1. LLM自体の挙動に起因する漏洩（攻撃者不要かつサーバ実装の問題でもない）
  - **例**: LLMが過剰に「親切」に振る舞い、ユーザーの依頼以上の情報をtool引数として送る
  - **位置づけ**: MCPサーバ・MCPプロトコルの脆弱性というより、**LLMホスト側のエージェント設計の問題**
  - (1)でも(2)でもない理由: 攻撃者は不要だが、サーバの実装不備でもない（LLMの自律的な判断の結果）

  ### 3-2. 仕様レベルの曖昧さ（仕様の脆弱性）
  - **例**: MCP仕様自体が、ツール定義の一意性・更新時の再承認・スコープ表現について明示が弱い
  - **位置づけ**: 個別実装の問題ではなく、**プロトコル仕様そのものの設計上の弱さ**
  - (1)/(2)の温床になる「メタ脆弱性」

  ### 3-3. サプライチェーン経路（中間的）
  - **例**: 公式リポに含まれるサードパーティ依存（npm/pipパッケージ）の脆弱性
  - **位置づけ**: 「攻撃者が依存パッケージに細工する」という意味では(1)寄りだが、「依存管理の不備」という意味では(2)寄り
  - 現実的には**両側面を併せ持つ**

  ### 3-4. 運用環境起因の問題（MCPサーバ単体の脆弱性ではない）
  - **例**: ユーザーのOSがマルウェア感染しており、MCPサーバの設定ファイルが盗まれる
  - **位置づけ**: MCPの問題ではなく、ホスト環境の問題
````

### 回答(Q3)

````markdown
● 非常に良い問いの立て方です。「コードインスペクションの限界をどこに引くか」を明確化することは、セキュリティレビュー戦略の核心です。順にお答えします。

  ## 1. 脆弱性の種類とコードインスペクションの効果

  ### 1-1. (1) 外部攻撃者の関与が必要な脆弱性とコードインスペクション

  **結論: 「概ね検知可能だが、検知できる範囲は分類によって大きく異なる」**ため、「適切な観点で見れば検知できる」とは**条件付きで言える**、というのが正確な回答です。

  #### 検知しやすい類型（コードインスペクションが効く）

  | 類型 | 検知のしやすさ | チェック観点 |
  |---|---|---|
  | 引数経由のコマンドインジェクション/SQLi/パストラバーサル | 高 | shell呼び出し、SQL組み立て、パス連結箇所のサニタイズ |
  | Confused Deputy / OAuth濫用 | 中〜高 | redirect_uri検証、stateパラメータ、トークンスコープ |
  | Rug Pull の検出基盤 | 中 | ツール定義のハッシュ固定、バージョニング機構の有無 |

  これらは**従来型のWeb/アプリ脆弱性と同質**であり、SAST(静的解析)・コードレビューのノウハウがそのまま転用できます。

  #### 検知が難しい類型（コードインスペクションでは限界がある）

  | 類型 | 検知の難しさの理由 |
  |---|---|
  | Tool Poisoning | サーバ実装は「正常」でも、配布される description文字列そのものが攻撃ペイロード。**コードを見ても異常がない**ため、description テキストの内容監査が別途必要 |
  | Indirect Prompt Injection | サーバは「外部コンテンツを取得して返す」という**仕様通りの動作**しかしていない。脆弱性はLLMホスト側＋サーバ側の組み合わせで成立 |

  **重要な構造**: (1)の脆弱性は「MCPサーバ単体のバグ」ではなく、**「サーバ＋LLM＋ホスト＋外部コンテンツ」の組み合わせで成立**するものが多く含まれます。サーバのコードだけを見ても、LLM側の解釈や外部コン
  テンツの内容を考慮しなければ判定できないケースがあります。

  #### まとめ

  > **「(1)は適切な観点でレビューすれば既知パターンを検知可能」と言えるのは、引数サニタイズ・認可フロー等の「従来型脆弱性に近い類型」に限られる**。Tool Poisoning や Indirect Prompt Injection
  は、サーバコード単体のレビューでは検知不能で、**ツール定義テキストの監査・LLMホスト側のサンドボックス・運用時のフィルタ**といった**コード外の対策**が必要。

  ---

  ### 1-2. (2) 攻撃者不在で発生しうる脆弱性とコードインスペクション

  **結論: 「コードインスペクションでの検知は(1)より効きやすいが、それでも一部は検知が難しい」** という整理になります。

  #### 検知しやすい類型

  | 類型 | 検知観点 |
  |---|---|
  | 過剰権限設計 | アクセス可能なファイル範囲・DB範囲のスコープ定義、最小権限原則の遵守 |
  | 認証情報の不適切な保持 | 設定ファイルの平文保存箇所、環境変数の扱い |
  | 安全側でないデフォルト | デフォルト設定値、初回起動時の確認フロー |
  | 出力サニタイズ不足 | 応答に含まれるURL・制御文字のエスケープ |

  これらは**コードレビュー＋設計レビュー**で十分に検知可能です。

  #### 検知が難しい類型

  | 類型 | 検知の難しさの理由 |
  |---|---|
  | ログ/テレメトリ漏洩 | サーバコードに「ログ出力」自体は正当に存在する。**何が記録されるか・どこに送られるか**は、**運用時の設定・ログ基盤の構成**に依存 |
  | コンテキスト混合（クロスサーバ漏洩） | サーバ単体のバグではなく、**複数MCPサーバを同時利用する構成**が原因。サーバコードを見ても発見できない |

  #### まとめ

  > **(2)もコードインスペクションで多くは検知できるが、「ログ送出先の構成」「他サーバとの組み合わせ」のような運用時の問題は、コード単体の監査では発見できない**。サーバ実装の正しさだけでなく、**運用構
  成（デプロイ・設定・併用サーバの組み合わせ）**の監査も必要。

  ---

  ### 1-1 / 1-2 を踏まえた一般化

  > **「コードインスペクションは必要条件だが十分条件ではない」**。MCPは「LLM＋複数サーバ＋ホスト＋外部コンテンツ」の合成系であり、**単一コンポーネントの監査では捕捉できない脆弱性が構造的に存在する**た
  め、コードレビューは複数の防御層の一つとして位置付けるのが適切です。

  ---

  ## 2. インスペクション時に参考にできる業界デファクト

  **重要な前置き**:
  MCPは2024年末に登場した若い技術であり、**「MCP専用の確立されたデファクト基準」は2026年1月時点ではまだ成熟途上**です。以下は「MCP固有のもの」と「従来基準を転用するもの」を分けて整理します。

  ### 2-1. MCP固有・準固有のもの

  | 名称 | 提供元 | 位置付け | 推奨度 | カバー範囲 | 更新頻度 |
  |---|---|---|---|---|---|
  | **MCP公式仕様 (Specification)** | Anthropic / MCP project | 仕様書本体。Security Considerations セクションあり | 必読 | プロトコル全体（実装ガイドラインは限定的） | 月次〜数ヶ月 |
  | **Anthropic 公式ドキュメント (Claude Docs / Engineering Blog)** | Anthropic | ホスト側の推奨設定・利用上の注意 | 高 | Claude Code/Desktop での運用 | 不定期 |
  | **Invariant Labs の研究記事** | Invariant Labs | 攻撃手法の実証・対策提案。**事実上の参照点** | 高 | Tool Poisoning, Indirect Injection 等の特定攻撃 | 不定期（インシデント駆動） |
  | **Simon Willison's blog** | 個人 | コミュニティの議論をまとめた読み物 | 中（補助的） | 広範な事例紹介 | 高頻度 |

  **注意**: 私の知識では、2026年1月時点で「**MCP専用の業界横断ガイドライン（OWASP MCP Top 10 等）が確立した**」という認識は持っていません。ただしOWASPでは**LLM向けTop
  10**は既にあり、その派生としてMCP向けが議論されている可能性があります（**要確認**）。

  ### 2-2. 転用可能な従来基準

  | 名称 | 位置付け | MCPへの適用範囲 | 推奨度 |
  |---|---|---|---|
  | **OWASP Top 10 for LLM Applications** | LLMアプリの脆弱性Top10。プロンプトインジェクション・過剰権限・サプライチェーン等を含む |
  (1)のプロンプトインジェクション系、(2)の過剰権限・出力ハンドリング系の多くをカバー | **最も推奨** |
  | **OWASP ASVS (Application Security Verification Standard)** | Webアプリ全般のセキュリティ要件 | 認証・認可・入力検証・暗号化など、サーバ実装の基礎部分 | 高 |
  | **OWASP API Security Top 10** | API向けTop10 | MCPサーバを「API」として見た場合の認可・データ露出 | 高 |
  | **CWE (Common Weakness Enumeration)** | 脆弱性タイプの分類体系 | 個別脆弱性の分類・検出に使う共通言語 | 中（参照系） |
  | **CWE Top 25 Most Dangerous Software Weaknesses** | 重要度の高いCWE | コードレビューの優先順位付け | 高 |
  | **MITRE ATLAS** | AIシステムへの脅威分類（ATT&CKのAI版） | プロンプトインジェクション等のTTP分類 | 中 |
  | **NIST SP 800-218 (SSDF)** | セキュア開発ライフサイクル | 開発プロセス全体の規律 | 中（プロセス系） |
  | **NIST AI RMF** | AIリスク管理フレームワーク | ガバナンス・監査の組織的観点 | 中（ガバナンス系） |
  | **CIS Controls** | 一般的セキュリティ統制 | 運用・構成管理 | 中 |

  ### 2-3. 推奨される使い分け

  実用上は**OWASP LLM Top 10 を主軸**に、以下を組み合わせるのが現実的です：

  ```
  [主軸] OWASP Top 10 for LLM Applications
    ↓ 補完
  [実装レビュー] OWASP ASVS / API Security Top 10 + CWE
    ↓ 補完
  [MCP固有] MCP公式仕様のSecurity Considerations + Invariant Labs研究
    ↓ 補完
  [組織的監査] NIST AI RMF / SSDF
  ```

  ## 3. コードインスペクションでは検知できない脆弱性

  **結論: 存在します**。むしろMCPの構造上、**コード外の要因による脆弱性が無視できない比重を占める**のが特徴です。

  ### 3-1. ホスト（Claude Code / Claude Desktop 等）側の問題

  - **承認UIの設計不備**: 一括承認・"Always allow" のデフォルト化等で、ユーザーが個々のtool呼び出しを精査できない
  - **応答の自動レンダリング**: 画像URL・マークダウンリンクの自動展開で、サーバ応答が外部送信トリガーになる（pixel exfiltration系）
  - **コンテキストウィンドウの管理**: 過去のtool応答が残ったまま別サーバに引数として渡る経路
  - **影響**: サーバ実装が完璧でも、ホスト側の挙動次第で漏洩は起きる

  ### 3-2. LLM自身の挙動

  - **過剰な「親切さ」**: ユーザー依頼の範囲を超えて関連情報を集めてしまう
  - **プロンプトインジェクションへの感受性**: モデル自体の堅牢性がバージョン・サイズで変動
  - **出力の非決定性**: 同じ入力でも安全な応答／危険な応答が確率的に出る
  - **影響**: サーバが返す内容に攻撃ペイロードが混じった瞬間に、LLMが自律的に危険な行動を起こす可能性

  ### 3-3. 配布・サプライチェーン経路

  - **パッケージレジストリ汚染**: npm/PyPIへのtypo-squatting、メンテナアカウント乗っ取り
  - **依存パッケージの脆弱性**: MCPサーバが依存するライブラリの脆弱性
  - **コンテナイメージ・バイナリ配布**: 改ざん検知の有無
  - **影響**: ソースコードを見ても、配布されているバイナリ・パッケージが別物の可能性

  ### 3-4. 運用環境・構成

  - **設定ファイルの保管場所**: バックアップ・同期サービス経由の漏洩
  - **ローカルネットワーク露出**: stdio想定のサーバを誤って公開ポートで起動
  - **権限分離の不備**: MCPサーバが過剰なOS権限で起動される
  - **影響**: コードは正しくても、デプロイ環境が脆弱なら情報漏洩は起きる

  ### 3-5. 複数MCPサーバの組み合わせ（合成脆弱性）

  - 個々のサーバは安全でも、**複数併用時にコンテキスト混合・データフロー交差**が発生
  - 例: 社内DB MCP（安全）＋ Web fetch MCP（安全）の組み合わせで、社内データが外部へ送信される経路ができる
  - **影響**: 各サーバ単体のレビューでは絶対に発見できない

  ### 3-6. プロトコル仕様の曖昧さ・進化

  - 仕様自体に「どう実装すべきか明示されていない箇所」がある場合、各実装が独自解釈で動き、相互運用時に問題が起きる
  - 仕様改訂で旧バージョンとの互換性問題が発生する
  - **影響**: 実装は仕様通りでも、仕様自体が安全でない可能性

  ### 3-7. 人的・組織的要因

  - ユーザーがMCPサーバの説明文を読まずに承認
  - 開発者が動作優先で権限を広く取る
  - セキュリティレビュー体制の欠如
  - **影響**: 技術的に正しく作られても、運用で台無しになる

  ### 3-8. ハードウェア・OS層

  - マルウェア感染ホスト、メモリダンプ、サイドチャネル
  - **影響**: MCP固有ではないが、MCPの保護対象となる認証情報が脅かされる

  ### サマリ：原因の階層

  ```
     [上位層 = MCPサーバ実装]   ← コードインスペクションの主戦場
````

````markdown
  ## 4. タイミング攻撃・サイドチャネル攻撃

  ### 4-1. MCPサーバの脅威モデルにおいて現実的な脅威か

  **結論: 限定的に現実的。ただし「典型的なWebサービスより脅威の優先度は低い」のが実情**です。

  #### 現実的な脅威となりうるケース

  | ケース | 現実性 | 補足 |
  |---|---|---|
  | **認証トークン比較のタイミング攻撃** | 中 | MCPサーバが独自の認証を実装し、`==` で文字列比較している場合。HTTP-MCPなど遠隔利用形態では成立しうる |
  | **ユーザー/レコード存在確認のタイミング差** | 中 | DB系MCPサーバで「該当なし」と「アクセス拒否」の応答時間差から情報漏洩 |
  | **キャッシュタイミング/データ依存処理時間** | 低 | ローカルstdio接続では攻撃面が小さい。HTTP/SSE経由の公開MCPでは要考慮 |
  | **LLM応答長/トークン数経由の漏洩** | 中（LLM特有） | LLM応答のトークン生成時間・長さから内部状態を推測する攻撃。**MCPサーバというよりLLMの問題** |
  | **ハードウェアサイドチャネル（Spectre等）** | 極低 | MCPサーバ単体の脅威モデルでは通常考慮外 |

  #### 脅威の優先度が「相対的に低い」理由

  1. **多くのMCPサーバはローカルstdio接続**で動作し、攻撃者がネットワーク的に観測する立場を取りにくい
  2. **(1) Tool Poisoning や (2) 過剰権限のような「正面玄関の脆弱性」**が圧倒的に大きいため、サイドチャネルが目立たない
  3. ただし、**HTTP/SSE経由の公開MCPサーバ・SaaS型MCP**が普及するにつれ、従来Webと同等のサイドチャネル脅威が顕在化する見込み

  ### 4-2. 検知に有効なツール・手法

  #### コードレビュー観点（最も実用的）

  - **定数時間比較の遵守**:
    - Python: `hmac.compare_digest`
    - Node.js: `crypto.timingSafeEqual`
  - **早期return回避**: 認証・認可ロジックで「不一致時に即return」しない
  - **応答時間の正規化**: エラー/成功の応答時間を意図的に揃える
  - **キャッシュ依存の排除**: 秘密値依存の分岐・配列アクセスを避ける

  #### ツール

  | ツール名 | ライセンス | 検知対象 | 公式 |
  |---|---|---|---|
  | **Semgrepカスタムルール** | LGPL 2.1 | `==` での秘密値比較等のパターン検出 | (前述) |
  | **CodeQL** | OSS用無料 | データフロー解析で「秘密値→分岐」の経路検出可能 | (前述) |
  | **ct-verif** (academic) | OSS（学術系） | C/C++向け定数時間性検証。MCPには直接使えないが概念参照 | 学術プロジェクト |
  | **dudect** | MIT/類似 | 統計的な定数時間性テスト（バイナリ向け） | `github.com/oreparaz/dudect` |
  | **Microwalk** (ResearchTUDarmstadt等) | GPL系 | サイドチャネルリーク検出（学術寄り） | `github.com/microwalk-project/Microwalk` |

  #### 動的検証

  - **応答時間の統計的測定**: 同一エンドポイントを繰り返し叩き、入力依存の時間差を統計的に検出
  - **負荷テスト時の応答時間記録**: k6 / locust 等の負荷ツールに時間記録を追加

  #### 正直な見解

  > **MCPサーバのセキュリティ評価において、サイドチャネルは「網羅的にケアすべき優先項目」とまでは言いにくい**。優先順位としては、(1)プロンプトインジェクション系、(2)認可・サニタイズ、(3)依存脆弱性、(4
  )認証情報の保管、までを固めた後に検討するレベル。ただし、**認証実装で `compare_digest` / `timingSafeEqual` を使う**等の基本作法は、コストが低いので最初から守るべきです。

  ★ Insight ─────────────────────────────────────
  - 「LLMがセキュリティツールを駆動する」というアーキテクチャの肝はSARIF: ご構想の「Claude
  Codeから複数ツールを呼んで統合レポート」を実装する場合、各ツールの出力をSARIF（OASIS標準のJSONスキーマ）に揃えるのが王道です。Semgrep・CodeQL・Banditなど主要SASTはSARIF出力に対応しており、LLMはJSON
  パースが得意なので、相性が非常に良い設計になります。逆に「人間向けのテキストレポートをLLMに読ませる」設計は、ツール追加のたびにパーサ実装が膨らみ破綻しやすいため避けるべきです。
  - MCP特化ツールの「市場の薄さ」をどう補うか: 2025〜2026年時点では、MCP固有の確立したスキャナ製品群はまだ少数です。これは弱みでもありますが、「Semgrepにカスタムルールを書く」という形でLLM自身がルール
  を生成・運用できるという強みでもあります。たとえば「Tool descriptionに < > system: ignore previous 等のトークンが含まれていたら警告」のようなルールを、Claude
  Codeに動的に書かせて実行する運用が現実的です。これは従来のSAST文化（人間がルールを書く）とは異なる、LLM時代のセキュリティ運用パターンとして注目に値します。
  - サイドチャネル軽視の境界線: 「サイドチャネルを優先度低と見る」判断は、MCPがローカルstdio中心の現状ではほぼ正しいですが、HTTP/SSE経由の公開MCP・マルチテナントMCP・SaaS型MCPが普及した瞬間に脅威モデ
  ルが書き換わります。実装時に**hmac.compare_digest / crypto.timingSafeEqual
  を使う**という最低限の作法だけは、デプロイ形態に関わらず守っておくと、将来HTTPに切り替えた際にも安全側に倒れます。低コストで将来不安を消せる典型的な「保険型実装」として推奨できます。
  ─────────────────────────────────────────────────

  ご検討中の具体的なMCPサーバ・実装言語・運用形態（stdio/HTTP）が分かれば、Layer別ツール構成をさらに具体化できます。また、Claude
  Codeから複数ツールを駆動する自動化スクリプトの雛形が必要であれば、そちらも作成可能です。
````

````markdown
  ## 8. 推奨される検索アプローチ

  URL確度を担保しつつ目的の情報に到達するには、以下の手順が安全です：

  1. **団体・組織のトップから辿る**: NVD・OWASP・GitHub Advisoriesの検索フォームを使う
  2. **GitHub内検索を活用**: <https://github.com/search>
  3. **公式リポジトリの README→ Wiki → Docs を順に辿る**: 個別記事URLを推測しない
  4. **検索エンジンで `site:` 演算子を使う**: 例 `site:owasp.org "MCP"`、`site:invariantlabs.ai "MCP"`

  ## 9. 最後に

  冒頭で述べた通り、**URLは私の最大の幻覚源**であり、特にセキュリティ評価の用途では**動かないURLを提示すること自体がリスク**になります。今回お示しした「高確度」のURLについても、リンク切れ・サイト構造
  変更がありえます。**重要な参照は必ずアクセスしてご確認ください**。

  「個別CVEページ」「個別ブログ記事」のような**動的・任意な構造のURL**については、敢えて出さず検索手段に倒したことを、率直な判断としてご了承いただければ幸いです。

  ★ Insight ─────────────────────────────────────
  - 「URLを出さない」も誠実な選択肢: LLMから情報を引き出す対話で、利用者は無意識に「具体的なURLが多いほど良い回答」と感じがちですが、セキュリティ用途では幻覚URLを混ぜるくらいなら、トップページ＋検索キ
  ーワードで止める方が安全です。今回の回答は、確度の濃淡を露わにすることで、利用者側の検証コストを最小化する設計にしています。これはLLMの限界を逆手に取った情報提供パターンとして実用上重要です。
  - 公式トップから辿る方が長期的に安定: 個別記事URLは数ヶ月単位で変わりますが、団体ドメイン（owasp.org, nist.gov, mitre.org）のトップは10年単位で安定しています。資料の長期参照リスト（社内Wikiのリンク
  集など）を作る場合、個別URLよりトップ＋検索クエリの組で記録する運用の方が、リンク切れを劇的に減らせます。これはセキュリティ業界では常識的な知恵ですが、LLM時代ではむしろ重要性が増しています。
  - 「site: 検索」はLLM時代のセキュリティリサーチの基本武器: site:owasp.org "MCP" のようなクエリは、LLMが幻覚しにくい形で（=具体URLを生成させずに）絞り込みを実現する手法として極めて有効です。Claude
  Codeなどに「自動でセキュリティ情報を集めさせる」ワークフローを組む際にも、WebSearch ツールにこの形式のクエリを生成させる設計が、誤情報混入を抑える上で本質的に効きます。
  ─────────────────────────────────────────────────

  ここまでで全体像はカバーできていると思いますが、特定領域（例：「Invariant LabsのMCP関連記事の見つけ方」「OWASP LLM Top 10
  v2025の入手方法」など）でさらに具体的な探し方が必要であれば、検索手順レベルで補足できます。
````
