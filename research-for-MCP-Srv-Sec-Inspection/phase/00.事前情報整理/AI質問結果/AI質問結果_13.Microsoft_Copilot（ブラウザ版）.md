### 質問(Q3)

```txt
1. 脆弱性の種類とコードインスペクションの効果

2. 上記のインスペクションを行う際、参考にできる業界デファクトのチェックリスト・基準・ガイドライン（OWASP / CWE / MITRE / Anthropic 公式 / その他団体）が存在しますか？

```

### 回答(Q3)

````markdown
**要点：既知のMCP/Claude Code周辺脆弱性は「(1) 外部攻撃者の関与で発動するもの」と「(2) 外部攻撃者がいなくても発生するもの」の両方が存在します。コードインスペクションで多くを検出可能ですが、運用・構成・サプライチェーン由来のリスクは別途評価が必要です。**   [Qiita](https://qiita.com/keitah/items/eeae1d26c1a81035ab1f)  [National Security Agency](https://www.nsa.gov/Portals/75/documents/Cybersecurity/CSI_MCP_SECURITY.pdf)

| **分類** | **コード検査で検出可能か** | **主要指標（短文）** | **代表例** |
|---|---:|---|---|
| **(1) 外部攻撃者関与型** | **多くは検出可能だが環境依存** | 外部入力の検証欠如・リポジトリやツール記述の信頼不足 | CVE‑2026‑40068（Trust bypass via git worktree）.   [Github](https://github.com/anthropics/claude-code/security/advisories/GHSA-q5hj-mxqh-vv77) |
| **(2) ローカル実装型** | **コード検査で検出可能** | 設定ファイル検証不足・共有パスの不適切利用 | 設定読み込みでの権限昇格やファイル書込脆弱性（実例多数）。   [app.opencve.io](https://app.opencve.io/cve/CVE-2026-40068)  [modelcontextprotocol.io](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) |
| **その他** | **コード検査だけでは不十分** | サプライチェーン・運用ミス・認証設定ミス | 未認証公開や静的クライアントIDによるConfused Deputy等。   [Qiita](https://qiita.com/keitah/items/eeae1d26c1a81035ab1f)  [National Security Agency](https://www.nsa.gov/Portals/75/documents/Cybersecurity/CSI_MCP_SECURITY.pdf) |

### 回答（要点）
1-1. **(1) はコードインスペクションで多くの既知パターンを検出可能**だが、検出には「ツール説明文の自然言語検査」「リポジトリメタデータ検証」「ランタイムパス解決ロジックのレビュー」が必要。   [Qiita](https://qiita.com/keitah/items/eeae1d26c1a81035ab1f)  
1-2. **(2) は原則コードレビューで検出可能**（設定検証・ファイルI/O・権限管理・セッション分離などを重点的に見る）。   [modelcontextprotocol.io](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)  
2. 参考基準：**OWASP MCPガイド（推奨度高）・CWE/MITRE（分類）・Anthropic公式ドキュメント（実装例）・NSA/OWASP勧告（運用注意）**。OWASPは実務向けでカバー広く更新頻度高め。   [Qiita](https://qiita.com/keitah/items/eeae1d26c1a81035ab1f)  [Anthropic](https://www.anthropic.com/news/model-context-protocol)  [CWE - Common Weakness Enumeration](https://cwe.mitre.org/)  
3. コード検査で検出できないリスク：**公開設定ミス・認証欠如・サプライチェーン改竄・運用ログ改竄・ネットワーク露出**。これらは構成監査・SBOM・ランタイム検査・ペネトレーションで補う必要があります。   [septimlabs.com](https://septimlabs.com/ja/blog/mcp-server-vulnerability-checklist-2026)  [Practical DevSecOps](https://www.practical-devsecops.com/mcp-security-checklist/)

必要なら、あなたの候補MCPサーバ名を教えてください。該当リポジトリ／Issue／CVEをURL付きで掘って提示します。
````

### 自動化アーキテクチャ（LLM に実行させる流れ）
1. **収集**：リポジトリをローカルにクローン → SBOM 生成（pip‑audit / trivy）。  
2. **静的解析**：Semgrep/Globstar + Bandit を実行（カスタムルールをLLMが生成・チューニング）。  
3. **依存性チェック**：pip‑audit / trivy で既知CVE を検出。  
4. **動的/環境検査**：ローカルでの権限分離テスト・symlink/TOCTOU チェック・マニフェスト署名検証を自動化（LLM が手順生成）。  
5. **レポート化**：LLM が検出結果を統合し、優先度付き修正案を出力。

### タイミング攻撃／副チャネルについて
- **現実性**：MCP サーバの脅威モデルでは、**攻撃者が精密なネットワーク計測や同一ホストでの観測権限を持つ場合に現実的**。MCP が外部リクエストを仲介しレスポンス差を返す設計だとリスクが高まる。  
- **検知手法**：静的解析では検出困難。対策は**定数時間実装・差分テスト（差分応答検査）・負荷下での統計的応答分析・フォレンジック計測（タイムスタンプ分布）**。専門ツールは少なく、差分フェンシングやフォーマル検証・ランタイム計測を組み合わせるのが実務的です。
