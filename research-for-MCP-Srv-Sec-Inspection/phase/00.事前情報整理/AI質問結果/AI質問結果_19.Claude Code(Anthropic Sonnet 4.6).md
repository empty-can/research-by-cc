  ## MCP 脆弱性の分類（2025〜2026年報告分）

  ---

  ### 前提: 分類軸の定義

  | 分類 | 判定基準 |
  |---|---|
  | **(1) 攻撃者関与型** |
  攻撃者が**実行時に能動的に関与**（不正リクエスト送信・悪意あるサーバー接続・細工ファイル配置等）することで初めて機密情報の流出リスクが生じる |
  | **(2) 構造的流出型** | 攻撃者が**存在しなくても**、設計・実装・設定の不備によって機密情報が流出し得る |
  | **(3) どちらにも属さない** | 実行時には攻撃者が不在だが、**事前の仕込み**（サプライチェーン汚染・プロンプト埋め込み等）が前提となるハイブリッド型 |

  ## (1) 攻撃者関与型

  攻撃者が実行時に直接介入することで初めてリスクが顕在化する実装不備。

  ### CVE-2025-49596 — MCP Inspector（Anthropic 公式）
  - **攻撃手法**: 認証なしの Inspector ↔ Proxy 間エンドポイントに攻撃者が細工した HTTP リクエストを送信
  - **流出情報**: 開発者ワークステーション上のファイルシステム・API キー・環境変数
  - **修正バージョン**: 0.14.1 以上
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-49596)

  ### CVE-2025-6514 — mcp-remote（Anthropic 公式）
  - **攻撃手法**: 攻撃者が悪意ある MCP サーバーを立て、OAuth の `authorization_endpoint` に OS コマンドを注入
  - **流出情報**: クライアント側の API キー・SSH 鍵・認証情報（Cloudflare / Hugging Face / Auth0 連携含む）
  - **影響規模**: 累計 437,000+ ダウンロード
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-6514)

  ### CVE-2025-68143 / 68144 / 68145 — mcp-server-git（Anthropic 公式）
  - **攻撃手法**: 攻撃者が細工した `.git/config` ファイルを配置し、パス検証バイパス・`git_init`・`git_diff` 引数インジェクションを連鎖させて RCE
  - **GitHub Advisory**: [一覧](https://github.com/modelcontextprotocol/servers/security/advisories)

  ### CVE-2026-0755 — gemini-mcp-tool
  - **攻撃手法**: ネットワーク越しに `execAsync` メソッドへ未検証入力を送信し、認証なしで OS コマンド実行
  - **流出情報**: サービスアカウント権限内の全リソース
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-0755)（CVSS 9.8）

  ### CVE-2026-23744 — MCPJam Inspector
  - **攻撃手法**: 未認証エンドポイントへ細工した HTTP リクエストを送信し、任意の MCP サーバーをインストール・実行
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-23744)（CVSS 9.8）

  ### CVE-2026-33032 — nginx-ui
  - **攻撃手法**: MCP メッセージエンドポイントが認証なしでコマンド実行を受け付けるため、攻撃者が直接 nginx 設定変更・サービス制御を実行
  - **影響**: 公開状態の 2,600 件以上のインスタンスが対象
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-33032)（CVSS 9.8）

  ### CVE-2025-59163 / CVE-2025-66414 / 66416 — DNS リバインディング（複数 SDK）

  エンドポイントに到達、RCE チェーンへ

  ### CVE-2025-53355 — Kubernetes MCP

  ## (2) 構造的流出型

  攻撃者が存在しなくても、アーキテクチャ・設計・実装の不備によって機密情報が漏洩し得る。

  ### CVE-2026-25536 — MCP TypeScript SDK（最新: 2026年2月）
  - **不備内容**: `StreamableHTTPServerTransport` で 1 つの `McpServer` インスタンスを複数クライアントで共有すると、A クライアントへのレスポンスが B
  クライアントに漏洩（レースコンディション）
  - **影響バージョン**: v1.10.0〜1.25.3（修正: v1.26.0）
  - **流出情報**: 他クライアントの会話内容・処理結果
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-25536)（CVSS 7.1）

  ### CVE-2025-53109 / 53110 — Anthropic Filesystem MCP Server
  - **不備内容**: 許可ディレクトリ内のシンボリックリンクを適切に解決せず、許可範囲外のファイルにアクセスできる
  - **流出情報**: ホスト上の秘密鍵・認証情報ファイル（攻撃者不在でもシンボリックリンクが既に存在していれば流出）
  - [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-53109)（CVSS 7.3）

  ### Session ID の URL 露出（MCP 仕様設計上の問題）
  - **不備内容**: HTTP+SSE トランスポートでセッション ID が URL
  クエリパラメーターに含まれるため、サーバーログ・リファラーヘッダー・プロキシログに自動的に記録される
  - **流出情報**: セッショントークン（攻撃者なしでもインフラ内部で流出）

  ### 過剰スコープの認証トークン（設計上の問題）
  - **不備内容**: `files:*`・`db:*`・`admin:*` 等の過剰なスコープを持つトークンが通常の API 呼び出し・ログ記録・エラーレポートを通じて露出
  - **流出情報**: 本来不要な範囲のリソースへのアクセス権

  ### 認証情報のプレーンテキスト保存（設定不備）
  - **不備内容**: MCP サーバーの設定ファイルやプロセス環境変数に API
  キーや認証情報がそのまま記録されており、同一ホスト上の任意のプロセスから読み取り可能
  - **流出情報**: API キー・DB パスワード等（攻撃者なしでも同ホストの他プロセス・ログから流出）

  ### Confused Deputy（OAuth 設定不備）
  - **不備内容**: MCP サーバーがユーザーの代理で動作する際、本来のユーザー権限より広い OAuth
  スコープで処理を行うことで、正常な操作中に過剰なデータにアクセス・処理してしまう

  ## (3) どちらにも属さない（ハイブリッド型）

  実行時には攻撃者が不在で自動的に発動するが、事前に悪意ある「仕込み」が必要なもの。
  実装不備というよりは **設計思想・エコシステムの信頼モデルの問題** といえる。

  ### ツールポイズニング / プロンプトインジェクション経由の情報窃取
  - **仕組み**: 攻撃者が MCP サーバーのツール説明文・Jira チケット・GitHub Issue・Google ドキュメント等に隠し命令を埋め込む。AI
  がそのコンテンツを処理する瞬間に自動的に認証情報を外部送信
  - **実例**: Cursor + Jira のゼロクリック攻撃（CVE-2025-54136、通称 MCPoison）— Jira チケットを開くだけで JWT トークン・認証情報が外部流出
  - **特徴**: 攻撃者は「仕込み時」だけ存在すれば足りる。実行時は被害者の通常操作のみ

  ### ラグプル（Rug Pull）/ サイレントなツール定義書き換え
  - **仕組み**: 初回審査・承認済みの MCP サーバーが、後から悪意ある定義に差し替えられる（WhatsApp MCP 事例等）。以降は正常な操作を通じて機密情報が漏洩
  - **特徴**: 承認時点では正当だが、事後の「仕込み」によって (2) 構造的流出型と同等の挙動になる

  ### サプライチェーン汚染（悪意あるパッケージ配布）
  - **仕組み**: 攻撃者が正規 MCP サーバーを偽装したパッケージを npm / PyPI / GitHub
  等に公開。インストール後は攻撃者不在で認証情報・ブラウザパスワード・API キー・ウォレット情報を収集（StealC マルウェア埋め込み事例等）
  - **実例**: 偽 Oura MCP プロジェクト（2026年2月）、偽 Postmark MCP サーバー（2025年9月）
  - **特徴**: 「実装の脆弱性」ではなく「正規品に見せた悪意ある実装」そのもの

  ### クロスサーバーツールシャドウイング
  - **仕組み**: 攻撃者が正規ツールと同名のツールを持つ悪意ある MCP
  サーバーを共存インストールさせる。接続順・優先度によって正規ツールが乗っ取られ、以降は正常な操作で情報流出

  | CVE-2026-0755（gemini-mcp-tool） | ユーザー入力を直接システムコールに渡す | execAsync への未検証変数（CWE-78） |

  **注意点**: (1) の脆弱性の中には「**MCP クライアント側**」のコードに起因するものが含まれます。
  たとえば mcp-remote の CVE-2025-6514 は MCP サーバーではなく OAuth クライアント側の実装不備です。
  「MCP サーバーのコードのみ」をインスペクションしても検知できない場合があるため、
  **MCP サーバー + クライアント（SDK 含む）の双方がインスペクション対象**になります。

  ---

  ### 1-2. (2) 構造的流出型 ← コードインスペクションで検知できるか

  **結論: 検知できる。(1) よりも純粋に静的検知に向いている。**

  (2) の脆弱性は「外部刺激なしに動作の結果として漏洩が起きる」設計・実装不備なので、
  コードを読めば直接確認できます：

  | CVE / 問題 | コードで確認できる不備 |
  |---|---|
  | CVE-2026-25536（TypeScript SDK） | McpServer インスタンスを複数クライアントで共有する実装 → レスポンスが混在する設計（CWE-362） |
  | CVE-2025-53109/53110（Filesystem MCP） | symlink を follow する前に canonicalize していない → 境界外アクセス（CWE-59） |
  | Session ID の URL 露出 | セッション ID をクエリパラメーターに乗せている実装 |
  | 過剰スコープトークン | OAuth スコープ要求がワイルドカードや過剰権限になっている実装 |
  | 認証情報のプレーンテキスト保存 | 設定ファイル・環境変数・ログ出力に平文でシークレットが書かれている |

  ただし一部の「構造的問題」（例: Confused Deputy の OAuth フロー設計）は、
  **コード単体を読むだけでは「設計意図通りかどうか」が判断しにくい**ことがあります。
  この場合は設計仕様書との照合が必要になります。

  ## 3. コードインスペクションでは検知できない脆弱性・リスク

  コードが完全にクリーンであっても、以下の要因によって MCP サーバー活用が危険にさらされる可能性があります。

  ---

  ### (A) プロンプトインジェクション（データ駆動の攻撃）

  - **原因**: 攻撃者が Jira チケット・GitHub Issue・Web ページ・ドキュメント等に
    隠し命令（自然言語の指示）を埋め込む。MCP サーバーのコードは正常だが、
    AI モデルがその「データ」を「命令」として解釈・実行する
  - **コードで何もわからない理由**: コードは正しくデータを受け取り正しく AI に渡しているだけ。
    「コードの欠陥」ではなく「モデルの判断プロセス」を悪用する攻撃
  - **例**: Cursor + Jira の MCPoison（CVE-2025-54136）— Jira チケットを開くだけで JWT が流出
  - **対策方向**: ランタイムの出力監視・サンドボックス・ユーザー確認ステップの挿入

  ---

  ### (B) サプライチェーン汚染（依存パッケージ・レジストリの問題）

  - **原因**: MCP サーバー本体のコードは正常でも、
    ① 依存パッケージが悪意ある版に差し替えられている（npm/PyPI への不正公開）
    ② タイポスクワッティング（類似名の偽パッケージ）のインストール
    ③ 正規パッケージに対するシークレットスキャン未実施
  - **コードで何もわからない理由**: インスペクション対象のファイルは「正常な依存宣言」にしか見えない
  - **例**: 偽 Oura MCP（StealC マルウェア）、偽 Postmark MCP、Smithery ビルド時の認証情報流出
  - **対策方向**: SBOM（Software Bill of Materials）作成・依存パッケージのハッシュ固定・
    SCA ツール（Dependabot 等）

  ---

  ### (C) ラグプル・ツール定義の事後書き換え

  - **原因**: インスペクション時点では正常な MCP サーバーが、
    デプロイ後にツール説明文・スキーマ・エンドポイントを悪意ある内容に変更する
  - **コードで何もわからない理由**: スナップショット時点では問題なし。
    時間経過後の変更はコードスキャンでは検知不可
  - **対策方向**: ツール定義の SHA-256 ハッシュをピン留め・
    定期的な再検証・変更検知アラート

  ---

  ### (D) MCP クライアント側・IDE の実装問題

  - **原因**: MCP サーバーとやり取りする Claude Code / Cursor / Windsurf 等の
    クライアント側に脆弱性があれば、サーバーコードが完璧でも被害を受ける
  - **例**: CVE-2025-59944（Cursor の大文字小文字バイパス）、
    CVE-2026-30615（Windsurf のゼロクリック RCE）
  - **コードで何もわからない理由**: MCP サーバーの実装コードには現れない

  ---

  ### (E) 実行環境・インフラ起因のリスク

  - **原因**:
    - サーバーが `0.0.0.0` にバインドされている（コード上は正しくても設定ファイル次第）
    - Docker コンテナの特権設定・ネットワーク設定の不備
    - OS / コンテナランタイムの既知 CVE（例: Docker サンドボックス脱出 CVE-2025-53372）
    - クラウドメタデータエンドポイントへのアクセス制御欠如（SSRF 経由で IAM 資格情報取得）
  - **コードで何もわからない理由**: デプロイ設定・インフラ構成の問題であり、
    ソースコードには出現しない

  ---

  ### (F) DNS リバインディング（ネットワーク層の攻撃）

  - **原因**: コードが「IPアドレスを検証してから接続する」正しい実装であっても、
    DNS 解決のタイミング差（TOCTOU: Time of Check / Time of Use）を突かれると
    バリデーション時は安全な IP、実際の接続時は内部 IP に変わる
  - **コードで何もわからない理由**: コードロジックは正しく、ネットワーク層で発生する

  ---

  ### (G) クロスサーバーツールシャドウイング（マルチサーバー構成の問題）

  - **原因**: 個々の MCP サーバーは完全にクリーンでも、
    悪意あるサーバーが同名のツールを登録することで呼び出しを横取りする
  - **コードで何もわからない理由**: 各サーバーのコードを単独でスキャンしても、
    「複数サーバーが共存したときの挙動」は見えない

  ---

  ### コードインスペクション外のリスク: まとめ

  | リスク領域 | 原因の所在 | 対策の方向性 |
  |---|---|---|
  | プロンプトインジェクション | 処理するデータ（モデルの判断） | 出力監視・サンドボックス |
  | サプライチェーン汚染 | 外部依存パッケージ | SCA・SBOM・ハッシュ固定 |
  | ラグプル | 時間軸の変化（デプロイ後） | ツール定義ピン留め・変更検知 |
  | クライアント側脆弱性 | MCP クライアント実装 | クライアント含む総合テスト |
  | インフラ設定 | デプロイ構成・OS | IaC スキャン・設定レビュー |
  | DNS リバインディング | ネットワーク層 | エグレスプロキシ・IP 固定 |
  | クロスサーバー干渉 | 複数サーバー構成 | 統合テスト・ツール名衝突検査 |

  ---
  機能不全の実態と対策

  前回調査で判明した通り、MCP
  CVEの多くでリードタイム≤0日（開示前パッチ未完）という実態がある。個人開発者が多数を占めるMCPエコシステムでは、CVDが機能しないケースが多い。

  実践的な対策:
  - 利用するMCPサーバはGitHub Security Advisory有無とSECURITY.md有無を選定基準に含める
  - 個人開発者製のMCPサーバを本番利用する場合は、フォークして自社でパッチ管理する体制も検討
  - 公式MCP Servers（github.com/modelcontextprotocol/servers）はAnthropicがメンテする組織リポジトリのため相対的に応答性が高い

  2. 検知に有効なツール・手法

  静的解析では検知できないため、以下のアプローチを組み合わせる。

  コード修正による根本対策（最優先）

  # Python: タイミングセーフな比較（hmac.compare_digest）
  import hmac

  def verify_token(provided: str, expected: str) -> bool:
      return hmac.compare_digest(provided.encode(), expected.encode())

  // TypeScript/Node.js: crypto.timingSafeEqual
  import { timingSafeEqual } from 'crypto';

  function verifyToken(provided: string, expected: string): boolean {
    const a = Buffer.from(provided);
    const b = Buffer.from(expected);
    if (a.length !== b.length) return false;
    return timingSafeEqual(a, b);
  }

  標準ライブラリの定数時間比較関数（hmac.compare_digest / crypto.timingSafeEqual）の使用が唯一の実践的な対策。
