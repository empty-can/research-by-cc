### 0.2 本ドキュメントの位置付け

本ドキュメントは、本活動「MCP Server セキュリティレビューの仕組み確立」の Phase 0c（公開ナレッジ分析）を、**Claude Code 主体で自走進行するための運用設計** を定める。

**本来的に Phase に縛られない汎用的な性質** を持つ運用設計だが、Phase 0c の特性（事実情報ベース・人間判断少なめ）を前提に組み立てているため、初回は Phase 0c 配下に配置する。Phase 0c で運用が確立できれば、後続フェーズでも参照可能な設計とする。

**運用ルール上の親ファイル**: 本ファイルは `phase/00.事前情報整理/03.Phase0c/CLAUDE.md` の運用ルール（目次運用・ファイルサイズ閾値・版管理）に準じて作成・更新する。

## 1. 運用設計の前提

### 1.1 委任スタイルの統一

メインセッションは作業指示者との対話と Agent コントロールに集中し、**実作業は全て Agent に委任** する。シングル Agent タスクでも同様（メインセッション直接処理は禁止）。

```
作業指示者 <-(対話)-> メインセッションのモデル <-(作業指示/アウトプット)-> Agent
```

**意義**:

| 観点 | 効果 |
|---|---|
| 自走率の測定 | 「メインセッション直接処理」と「Agent 委任」が混在しないため、自走実績の積み上げが純粋に測れる |
| バイアス低減 | メインセッションは判断レイヤーに専念し、実作業のバイアス（特定モデルの癖等）を最小化 |
| スケーラビリティ | 委任先 Agent の数や並列度を変えるだけで作業規模を調整できる |

### 1.2 段階的拡張原則

全タスクで **最小構成（1 Agent）から開始** し、効果測定後に段階的に Agent 数・並列度を拡張する。

**意義**:

| 観点 | 効果 |
|---|---|
| 過剰投資の回避 | シングル Agent で十分な品質が出るタスクで不要な並列化を避ける |
| ベースラインの確保 | シングル → マルチへの拡張効果を測定するためのベースラインデータを得る |
| 失敗時のリカバリー | 最小構成で問題が見つかった場合、拡張前に修正できる |

### 1.3 収束ロジック

議論モードは **既存クロスレビュー流（収束上限 + 不収束時の作業指示者エスカレーション）** を踏襲。新規プラグイン採用時もこの機構を必須要件とする。

**収束ロジックの構成要素**:

| 要素 | 内容 |
|---|---|
| 議論ラウンド上限 | クロスレビュー流の「前半 5 回 / 後半 Opus 3 回・Sonnet 4 回 / レビューイ 3 巡」に準じた上限値を採用 |
| 不収束時の対応 | 上限到達時は議論を打ち切り、作業指示者に判断を仰ぐ |
| 部分合意の取り扱い | 完全合意できなくても部分合意が成立した範囲は採用可（残りは作業指示者判断） |

### 1.4 ハイブリッド方針（自走 + チェックポイント）

完全自走ではなく、**Phase 0c の活動をいくつかのステップに分け、各ステップ完了時に作業指示者がレビューする** ハイブリッド方針を採用する。

| 局面 | 自走 / 確認 |
|---|---|
| 議論プロセス・素案生成 | **完全自走** |
| 信頼性スコア軸の確定・採用判定の確定 | **作業指示者承認**（短時間で済む形式に整える） |
| 個別ナレッジの裏取り・整理 | **完全自走** |
| Phase 0c 着手前準備 7 項目のうち #1〜#4（裏取りルール設計）| **要相談**（運用ルール変更の性質を持つため） |

## 2. 運用設計テーブル

Phase 0c の各タスクに対する運用モード・使用資産・スモールスタート構成・チェックポイントを以下にまとめる。

| Phase 0c タスク | 運用モード | 使用資産 | スモールスタート構成 | チェックポイント |
|---|---|---|---|---|
| 着手前準備 #5 / #6 / #7（索引整備・差分比較） | 協調分担 | `/orchestrate` パターン A（Agent ツール直接呼び出しで実装） | 初回は **1 Agent 単独** → 出力品質確認 → 2 Agent 並列に拡張 | 各準備項目完了時 |
| 着手前準備 #1〜#4（裏取りルール設計） | 議論 + 作業指示者承認 | 新規プラグイン候補 or クロスレビュー流運用 | **2 Agent 議論** から開始 → ルール案の妥当性・議論ラウンド数で評価 | ルール案合意時 + 最終承認時 |
| 公開ナレッジ全件カバー | 協調分担（並列） | `/orchestrate` パターン A（Agent ツール直接呼び出しで実装） | **5 件単位のバッチ**、初回バッチは 1 Agent → 効果確認後並列化 | バッチ毎 |
| 信頼性スコア軸設計 | 議論 | 新規プラグイン候補 or クロスレビュー流運用 | **2 Agent 議論** で軸候補抽出 → 議論ラウンド数・収束品質を測定 | 軸案合意時 + 確定時 |
| 二軸分類軸設計 | 議論 | 新規プラグイン候補 or クロスレビュー流運用 | 信頼性スコア軸設計と同じ | 軸案合意時 + 確定時 |
| 個別ナレッジ整理 | 協調分担 | `/orchestrate` パターン A（Agent ツール直接呼び出しで実装） | 1 件単位を 1 Agent で実施 → 並列化 | バッチ毎 |
| 重複処理（同一情報源の言及 LLM 集合化） | 分担 → 統合 | `/orchestrate` パターン B（Agent ツール直接呼び出しで実装） | 分担: 1 Agent ずつ並列 / 統合: **別 Agent 1 名** がメインセッション制御下で実施（メインセッション直接処理ではない） | 統合結果確認時 |

## 3. スモールスタート→拡張の効果測定軸

各タスクで「拡張すべきか」を判断するための測定軸とその目安:

| 測定軸 | 拡張判断のしきい値（目安） | 拡張しない判断（目安） |
|---|---|---|
| **出力品質** | シングル Agent では網羅性・正確性に不足が観察される場合 | シングル Agent で十分な品質が出る → 拡張不要（過剰投資の回避） |
| **所要時間** | 並列化で 50% 以上の時間短縮が見込める場合 | 並列化のセットアップ時間が短縮効果を上回る |
| **観点の網羅性** | 議論モードで「シングルだと特定観点を見落とす」が観察された場合 | シングル Agent で必要観点をすべてカバーできている |
| **コスト感（参考軸）** | 契約レート上限に十分余裕がある場合は積極拡張可 | 上限間近の場合は段階拡張のペースを落とす |

## 4. 既存資産との関係

### 4.1 既存資産一覧

本活動で利用可能なマルチ Agent 関連の既存資産:

| 既存資産 | 種別 | 機能 |
|---|---|---|
| `/orchestrate` skill | Skill | 複数 sub-agent の並列・順次協調（パターン A / B / C）。**メインセッションで呼ぶ前提** |
| `code-reviewer` agent | Agent | git diff ベースのレビュー専門 Agent（Sonnet 固定） |
| クロスレビュー運用 | テンプレート + ルール | レビュー報告書の標準フォーマット + 運用ルール（`.claude/templates/cross-review/` + `.claude/rules/cross-review-runtime.md`） |

### 4.2 新規プラグインによる補強範囲

新規プラグインを採用する場合の評価軸: **`/orchestrate` skill + クロスレビューでは実現できない部分** を明示できることを採用基準とする。実現できるなら新規プラグインは不要。

**新規プラグインで補強したい領域（暫定）**:

| 領域 | 期待する機能 |
|---|---|
| 議論モード（Multi-agent debate） | Six Thinking Hats / Devil's Advocate / Delphi method 等のフレームワークに基づく議論進行 |
| 合意形成 | 投票 / 加重投票 / 第 3 者裁定 Agent 等の収束ロジック |
| 議論ログの構造化保存 | Agent 間の議論プロセスを追跡可能な形でローカル保存 |

公開プラグインの探索は別セッションで並行実施中。結果が戻り次第、本ドキュメントに採用判定を追記する。

### 4.3 `/orchestrate` skill 自己呼び出しの制約と対応

`.claude/skills/orchestrate/SKILL.md` には `disable-model-invocation: true` が設定されており、Claude Code から Skill ツール経由での自動呼び出しは **不可**（ユーザが手動で `/orchestrate` と入力する必要あり）。

**対応**: メインセッションは Skill 経由ではなく、**Agent ツールを直接呼び出してパターン A / B / C を実装** する。`/orchestrate` の SKILL.md ドキュメントはパターン定義の参照資料として活用する。

**意義**: 既存の `disable-model-invocation: true` 制約を尊重しつつ、Phase 0c 自走運用を実現できる。

### 5.2 不収束時のエスカレーション

議論モードで収束ロジックの上限に達しても合意できない場合の対応:

1. **議論を打ち切る**: ラウンド上限到達時点で議論プロセスを停止
2. **議論ログをサマリ化**: メインセッションが議論内容を要約し、争点を明示
3. **作業指示者に判断を仰ぐ**: 争点と各 Agent の主張、メインセッションの推奨を提示
4. **作業指示者判断を反映して再開**: 判断後、議論の続行 or 採択 / 不採択を確定

このエスカレーションは **例外運用** であり、頻発する場合は議論フレームワーク自体の見直し（収束ロジックの強化等）を検討する。
