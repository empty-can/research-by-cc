### §1.2 脆弱性の本質

**攻撃前提条件**

| 前提 | 詳細 |
|---|---|
| Prompt Injection 能力 | 攻撃者が Untrusted コンテンツを Claude Code のコンテキストウィンドウに挿入できること（例: 悪意ある Web ページ閲覧・悪意ある git リポジトリクローン等） |
| Claude Code 実行環境 | サンドボックスが有効な状態で Claude Code が動作中 |

**攻撃経路**

1. プロンプトインジェクション等を通じて、サンドボックス内プロセスにシンボリックリンク作成を誘導（例: `/workspace/link -> /etc/passwd`）
2. Claude Code の非サンドボックス化プロセスが該当パスに書き込みを試行
3. シンボリックリンクが追跡され、ワークスペース外の任意のパスへ書き込みが発生
4. 結果として任意ファイル上書き・潜在的コード実行（RCE 連鎖）が可能

**根本原因**

- **直接原因（CWE-61）**: サンドボックスがワークスペース外を指すシンボリックリンクの作成を検知・ブロックしない
- **間接原因（CWE-22）**: 非サンドボックスプロセスがシンボリックリンク先のパスを検証せず追跡する
- **設計上の問題**: サンドボックスと非サンドボックスプロセス間の信頼境界が適切に実装されていない

**影響**

- サンドボックス脱出（コンテナ・プロセス境界を超えた任意ファイル書き込み）
- 潜在的な RCE（書き込み先に応じてシェル設定・認証情報・実行ファイルの改ざん）
- CVSS v3.1 が 10.0 となった理由: S:C（スコープ変更）= サンドボックスの境界を超えるため、S の変更が成立

### §1.4 軸分類の精緻化

**既存の暫定分類（07 §4.2）**: A3 / B1

| 軸 | 暫定分類 | 裏取り後評価 | 根拠 |
|---|---|---|---|
| **軸 A（検知軸）** | A3 | **A3 妥当・確認** | 根本原因はサンドボックスと非サンドボックスプロセス間の「信頼境界設計」。どのファイルがシンボリックリンクを作成する可能性があるかはコードを読んでも判断困難。SAST では「シンボリックリンク作成コード」は検出できても、それがサンドボックス内の悪意ある誘導によって生じるかは静的解析では判断不可。ただし、「非サンドボックスプロセスがシンボリックリンク追跡をチェックせずに書き込んでいる」コード箇所は A1/A2 の観点で部分的に検知可能 |
| **軸 B（攻撃分類）** | B1 | **B1 妥当・確認** | 攻撃結果はサンドボックス脱出 + 任意書き込み + 潜在的 RCE。CWE-22/61 = コード実装不備系の典型。プロンプトインジェクションが攻撃の「入口」だが、脆弱性の本質は B1（コード実装不備による境界突破）であり B2 ではない |

**精緻化提案**

- **A3 確定**: 信頼境界設計の不備が本質であり、コード単体では「この設計が安全か」は判断困難。A3 を維持する
- **補足**: ただし「非サンドボックスプロセスがパス書き込み前にシンボリックリンク解決を行っているか」という **A1 レベルのチェックポイント** も存在する。Phase 1 でソースコードをレビューする際は、この部分（ファイルシステム操作前の `fs.realpath` / symlink チェックの有無）を確認する価値はある
- **B1 確定**: 変更提案なし

### §1.5 Phase 1 インスペクション観点への示唆

MCP サーバーのソースコードレビューでこの種の脆弱性を検知しようとする場合に確認すべき観点:

1. **ファイル書き込み前のシンボリックリンク解決チェックの有無**: ファイル書き込み（`fs.writeFile` / `open()` / `Path.write_text()` 等）の前に `fs.realpath()` または `os.path.realpath()` でリンク先を解決し、許可されたベースディレクトリ配下であることを確認するコードがあるかを確認する。これがなければ symlink following 脆弱性の候補となる
2. **サンドボックス／許可パス境界の実装確認**: 「許可ディレクトリ外を指すシンボリックリンクを作成しようとした場合にブロックする」ロジックがサンドボックス処理（例: chroot / seccomp / 独自ホワイトリスト）に含まれているか確認する
3. **ファイルシステム操作の TOCTOU（Time-of-Check to Time-of-Use）**: パスの正規化と実際の書き込みの間に symlink 差し替えが可能なウィンドウがないか確認する
4. **プロンプトインジェクション経路の特定**: MCP サーバーが外部入力（URL 取得結果・ファイル内容・ユーザー入力）をツール引数に渡す箇所で、ファイルシステム操作につながるパスが制御可能かを確認する（B2 側の入口チェック）

### §2.2 脆弱性の本質

**攻撃前提条件**

| 前提 | 詳細 |
|---|---|
| 認証済みアカウント | LibreChat に登録済みのユーザーアカウントが必要（ユーザー登録がオープンな場合は事実上認証不要に近い） |
| API アクセス | HTTP 経由で `/api/mcp/servers` エンドポイントにアクセス可能 |

**攻撃経路**

1. 認証トークンを取得（ユーザー登録 → ログイン）
2. `/api/mcp/servers` エンドポイントに POST リクエストで MCP サーバー設定を送信
3. `StdioClientTransport` を利用する設定で `command` フィールドに任意のシェルコマンドを指定
4. LibreChat がコマンド「検査」時に stdio コマンドを root 権限でコンテナ内実行
5. 任意コマンドがコンテナ内 root で実行される

**根本原因**

3 つの不備が組み合わさって成立する:

1. **入力検証欠如（CWE-285 の主因）**: `StdioClientTransport` が `command` パラメータを直接 OS コマンドとして実行し、値の検証・ホワイトリスト制限を行わない
2. **デフォルト設定の危険性**: MCP サーバー作成権限が全ユーザーに対してデフォルトで有効
3. **実行権限過剰**: コンテナ内の root 権限でコマンドが実行される（最小権限原則違反）

**パッチ内容（コミット 211b39f3）**

- `MCPServerUserInputSchema` から stdio オプションを削除（API 経由の stdio 設定を完全無効化）
- stdio 設定送信時に HTTP 400 エラーを返すよう変更
- "Stdio allows arbitrary command execution" という理由を明記し、管理者が YAML ファイル経由でのみ設定可能とするよう制限

**影響**

- コンテナ内 root での任意コマンド実行（完全な機密性・完全性・可用性の侵害）
- スコープ変更（S:C）: コンテナ外への影響が理論的に可能

### §2.4 軸分類の精緻化

**既存の暫定分類（07 §4.2）**: 07 §4.2 には CVE-2026-22252 の個別エントリなし（LibreChat STDIO として統合カテゴリに含まれる可能性があるが、明示的な分類は未記載）。§1.1 の CVE テーブルでは「LibreChat STDIO」として言及のみ。

| 軸 | 新規分類 | 根拠 |
|---|---|---|
| **軸 A（検知軸）** | **A1** | `StdioClientTransport` の `command` パラメータが入力検証なしで OS 実行されていることは、コードを読むだけで即座に特定可能。SAST ツール（Bandit / Semgrep）の「コマンドインジェクション」ルールでも検知できる可能性が高い。入力をそのままサブプロセス実行に渡すパターンは静的解析の得意領域 |
| **軸 B（攻撃分類）** | **B1** | 認証済みユーザーによる API 経由の任意コマンド実行。MCP stdio コマンドの入力検証不備 = コード実装不備。B6（過剰権限）の要素も存在するが、攻撃の本質は「任意コマンド実行 = B1」と判定する |

**精緻化提案**

- A1/B1 で新規分類する（07 §4.2 への追記が必要）
- 付記: B6（コンテナ内 root 実行 = 過剰権限）の要素もあり、「A1/B1+B6」とすることも可能。しかし B6 は結果として生じる影響増幅要因であり、脆弱性の本質は B1 と判断する
- 既存の統合カテゴリ「LibreChat STDIO」が A1/B1 相当であることが本裏取りで確認された

### §2.5 Phase 1 インスペクション観点への示唆

MCP サーバーのソースコードレビューでこの種の脆弱性を検知しようとする場合に確認すべき観点:

1. **stdio コマンドの入力検証の有無**: `StdioClientTransport`（または類似の STDIO プロセス起動クラス）が受け取る `command` / `args` パラメータにホワイトリスト・バリデーションが実装されているか確認する。`child_process.spawn()` / `subprocess.Popen()` 等への直接渡しがあれば要注意
2. **API エンドポイントの認可チェック**: MCP サーバー設定を登録・更新するエンドポイントに対して、「一般ユーザー vs 管理者」の権限分離が実装されているか確認する。管理者のみが stdio 設定を変更できる設計かを確認する
3. **stdio vs SSE/HTTP の設定可能範囲**: ユーザーが API 経由で指定できるトランスポート種別に制限があるか確認する。stdio は任意コマンド実行を内包するため、API 経由の設定を許可する設計は根本的なリスクを持つ
4. **コンテナ・プロセスの実行権限**: コマンドが実行されるプロセスの UID/GID を確認する。root での実行設計は被害範囲を最大化するため、最小権限の観点でフラグを立てる

| 認証不要 | PR:N（特権不要）= 認証・ログイン一切不要 |
| ユーザー操作不要 | UI:N = 被害者の操作を必要としない |

**攻撃経路**

```
攻撃者 → HTTP POST /api/mcp/connect
         {"serverConfig":{"command":"<任意コマンド>","args":[...],"env":{}},"serverId":"<任意>"}
         → MCPJam が command + args を検証なしで spawn()
         → 任意コマンド実行
```

実証された PoC:
```
curl http://[ターゲット]:6274/api/mcp/connect \
  --header "Content-Type: application/json" \
  --data '{"serverConfig":{"command":"cmd.exe","args":["/c","calc"],"env":{}},"serverId":"mytest"}'
```

**根本原因**

2 つの設計不備が組み合わさって成立:

1. **認証の欠如（CWE-306 の主因）**: `/api/mcp/connect` エンドポイントに認証・認可チェックが一切存在しない
2. **デフォルトバインドの危険性**: サーバーが `0.0.0.0`（全インターフェース）にバインドされており、ローカル以外からもアクセス可能。「Docker 運用向け設計」がセキュリティ上の欠陥に

**パッチ内容（コミット e6b9cf9）**

- `server/index.ts` の `hostname: "0.0.0.0"` → `hostname: "127.0.0.1"` に変更
- Sentry 関連コードの削除（関係なし）
- 「Fix port vuln」というコミットメッセージが修正意図を示す

> **パッチの限界**: バインドアドレスを `127.0.0.1` に変更したのみで、入力検証・認証機構の追加は行われていない。同一ホスト上で別プロセスが動いている場合（例: 悪意ある MCP サーバーが同ホストで動作している場合）、ローカルホスト経由での攻撃は引き続き可能である点に注意が必要。

**影響**

- ネットワーク経由の完全な任意コマンド実行（RCE）
- 機密性・完全性・可用性すべてへの高影響（C:H/I:H/A:H）
- S:U（スコープ変更なし）= MCPJam 自体のプロセス権限の範囲内。CVE-2026-39861 と異なりスコープは変化しないが、CVSS が 9.8 である理由は PR:N（認証不要）

### §3.4 軸分類の精緻化

**既存の暫定分類（07 §4.2）**: A2 / B1

| 軸 | 暫定分類 | 裏取り後評価 | 根拠 |
|---|---|---|---|
| **軸 A（検知軸）** | A2 | **A2 妥当・確認** | 「認証なしでコマンドを受け付けるエンドポイント」はコードを読めば構造的に確認できる（A1 相当のコードパターンが存在する）。ただし「このエンドポイントが外部からアクセス可能か」は `hostname` の設定値（`0.0.0.0` vs `127.0.0.1`）という実行時設定に依存し、コードレビューだけでは「疑い」までしか到達できない。A2 が適切 |
| **軸 B（攻撃分類）** | B1 | **B1 妥当・確認** | `/api/mcp/connect` への入力検証なし + 直接コマンド実行 = コード実装不備系の典型。RCE として B1 が適切。CWE-306（認証欠如）が主因だが、攻撃の結果は B1（RCE）|

**精緻化提案**

- A2/B1 を維持する
- 補足: パッチがバインドアドレス変更のみである点は A2 の根拠を強化する（コード変更だけでは不十分で、設定・デプロイ環境も考慮が必要）
- A1 の追加提案（却下理由）: 入力検証コードの不在は A1 観点で読める部分もあるが、外部アクセス可否はランタイム依存のため A1 には分類しない

### §3.5 Phase 1 インスペクション観点への示唆

MCP サーバーのソースコードレビューでこの種の脆弱性を検知しようとする場合に確認すべき観点:

1. **HTTP サーバーのバインドアドレス確認**: サーバーが `0.0.0.0`（全インターフェース）または `localhost`（`127.0.0.1`）のどちらにバインドされているかをコードと設定ファイルの双方で確認する。`0.0.0.0` バインドは「Docker 向け」「LAN 内利用向け」等の理由で存在することが多く、意図的なものでもネットワーク環境次第で脆弱になる
2. **コマンド実行エンドポイントの認証確認**: HTTP API がシェルコマンド・スクリプト実行・プロセス起動を行うエンドポイントに対して、認証・認可ミドルウェアが適用されているかを確認する。MCP 開発ツール系は「ローカル専用」前提で認証を省略しがちな設計パターンが存在する
3. **`command` / `args` フィールドのサニタイズ確認**: HTTP リクエストから受け取った JSON の `command` / `args` / `env` フィールドをそのままサブプロセス実行に渡すコードパターン（`child_process.spawn(command, args)` 相当）を検索し、入力検証の有無を確認する
4. **エンドポイント一覧の棚卸し**: Express / Fastify / Hono 等の route 定義をコードで確認し、認証ミドルウェアが適用されていないエンドポイントを列挙する。`router.post('/mcp/connect', handler)` のような登録で認証が先行していなければ要注意

### §4.1 軸分類の分布と確定結果

| CVE | 暫定分類（07 §4.2） | 裏取り後確定分類 | 変更有無 |
|---|---|---|---|

**軸 B の分布**: 3 件全て **B1（RCE/コマンドインジェクション/パストラバーサル）**

**軸 A の分布**:
- A1（SAST 検知可能）: 1 件（CVE-2026-22252）

この分布は「CVSS スコア順に A3 > A2 > A1 で難易度が対応している」という合理的な傾向を示す。最高深刻度（CVSS 10.0）の CVE-2026-39861 が A3 であることは、設計レベルの問題が最も深刻な結果を生みやすいという仮説と一致する。

### §4.2 Phase 1 優先度の根拠

3 件が Phase 1 最優先とされる理由を裏取り結果から補強する:

| 観点 | CVE-2026-39861 | CVE-2026-22252 | CVE-2026-23744 |
|---|---|---|---|
| **CVSS スコア** | 10.0（Perfect Score） | 9.9 | 9.8 |
| **攻撃前提の緩さ** | プロンプトインジェクション能力が必要 | 認証済みユーザーで十分（登録制なら誰でも） | 認証不要・ネットワーク到達のみ |
| **影響範囲** | サンドボックス脱出（境界突破） | コンテナ内 root 実行 | ホスト上の任意コマンド実行 |
| **PoC の存在** | 詳細な攻撃手順が GHSA に記載 | API エンドポイントと手順が判明 | curl コマンド 1 行の PoC が公開済み |

| **MCP サーバー評価への関連性** | Claude Code 自体の脆弱性（間接的関連） | MCP STDIO の設計パターン問題（直接関連） | MCP 開発ツールの脆弱性（直接関連） |

**Phase 1 でのインスペクション焦点**:
- CVE-2026-22252 型: stdio コマンド受付エンドポイントの入力検証・認可確認（A1 = SAST 検知可能）
- CVE-2026-23744 型: HTTP エンドポイントの認証有無・バインドアドレス確認（A2 = コードレビューで疑い特定可）
