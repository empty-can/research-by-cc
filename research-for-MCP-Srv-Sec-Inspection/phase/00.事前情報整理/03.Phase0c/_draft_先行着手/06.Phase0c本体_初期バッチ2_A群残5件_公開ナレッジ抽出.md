## §4 二軸分類

### §4.1 二軸定義（Batch 1から継承）

Batch 1で定義した二軸定義を変更なく継承する。

**軸A: コードインスペクションによる検知可能性**

| 区分 | 定義 |
|---|---|
| A1 | 静的解析（SAST）で検知可能なコード実装不備（ハードコード秘密情報・インジェクション可能入力検証不足・既知脆弱ライブラリ依存等） |
| A2 | 実行時・動的テストが必要な脆弱性（SSRF実証・PI実際動作・エージェント実行パス確認等）。コードレビューで「疑い」まで到達可能 |
| A3 | 設計・アーキテクチャレベルの問題。コード単体では判断不可（信頼境界設計・権限設計・ツール組合せ問題等） |

**軸B: 攻撃・リスクカテゴリ**

| 区分 | 定義 |
|---|---|
| B1 | プロンプトインジェクション（PI）/ ツールポイズニング |
| B2 | SSRF / アウトバウンド通信悪用 |
| B3 | パストラバーサル / 任意ファイルアクセス |
| B4 | RCE（Remote Code Execution）/ コマンドインジェクション |
| B5 | 秘密情報漏洩 / 認証・認可不備 |
| B6 | サプライチェーン攻撃 / 悪意あるMCPサーバー |

## §5 所感・考察

### §5.1 CVEハルシネーション検出

**Batch 2の2026年CVE群について**:

Batch 2では14件のCVEが言及されたが、そのうち10件が2026年CVEである（2026-21852 / 2026-27825 / 2026-23744 / 2026-30615 / 2026-40068 / 2026-35603 / 2026-39861 / 2026-35020 / 2026-25723 / 2026-7812）。作業時点（2026-05-28）は2026年中であるため「未来年CVE」とは言えないが、CVEの採番・公開タイムラグを考慮すると、2026年後半採番のCVEが既に公開されていることは状況として注意が必要。

**ハルシネーション疑いの根拠**: 単一AI言及 + 詳細不明 + NVD未確認（疑義フラグ付与基準）。

**NVD確認済みCVEの扱い**: CVE-2026-23744は複数AI言及かつ#14がNVD URLを明示。現時点では最も信頼性の高い2026年CVEとして扱う。

**Batch 1との比較**: Batch 1では CVE-2026-27735が単一AI言及のハルシネーション疑い判定。Batch 2では同様の単一AI言及2026年CVEが複数（7件）あり、疑義フラグ付与が重要。

### §5.2 Web検索バイアス

**#10 Google Gemini 3 Flash（Web検索なし）の際立った差異**:

Batch 2の5件のうち #10のみがWeb検索を行わなかった。その結果:
- CVE番号を一切提供しなかった（「精度懸念のため提供を避ける」と明示）
- ガイドライン・ツール言及は5件中最も保守的
- ただし学習データ由来の具体的な実装事例（GitHub MCP PR #143）を提供できた

**Web検索有4件の傾向**:
- #01/#13/#14/#21はいずれもCVEを複数提供（ただし2026年CVEの割合が高い）
- Web検索のタイムラグ・インデックス差異が各AIの取得情報に差を生む
- #13（Bing）と#14/#21（Google系）で重複しない2026年CVEが多く出現 → 検索エンジン差異の可能性

### §5.3 学習データ深度

**#10の保守的アプローチの評価**:

CVE提供拒否は一見情報量が少ないように見えるが、実態は「過剰断定を避けた正確性重視の対応」である。Q3での「ほぼ全ての実装不備について、事前に検知可能です」という過剰断定（後に自己訂正）との対比から、#10はモデルとして精度と断定のバランスを調整中であることが伺える。

**#14 OpenAI ChatGPTの分析深度**:

#14はバッチ2の中で最も深い分析的知見を提供した。"trusted-but-malicious"概念・ケイパビリティ合成問題・LLMアウェア脅威モデリングの必要性は他AIが明示しなかった視点。Web検索併用かつ学習データの深度が高いことが背景と推察。
