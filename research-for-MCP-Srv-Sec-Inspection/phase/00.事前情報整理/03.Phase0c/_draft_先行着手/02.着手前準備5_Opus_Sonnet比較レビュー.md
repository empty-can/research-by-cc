## 2. Opus 版の優位点

### 2.1 #16 直接観察による完全性

Sonnet 版は #16（25,030 tokens で Read 上限超過）を **分割読込せず間接情報のみ** で扱った:

> Sonnet 版 §1 照合: "本索引作成時に #16 は上限超過により全文読込できなかった。事前確認では「有（Insight ブロック観察）」とされており、矛盾なし。"

> Sonnet 版 §6.3: "#16 は 25,030 tokens でファイルが読込上限を超過しており、本索引作成時に詳細内容を確認できなかった。Phase 0c で #16 の詳細内容を確認する際は必ず分割読込が必要。"

Opus 版は #16 の Q1 (Explore agent 自発実行・GHSA 6 + CVE 5 提示)・Q5/Q6 (Insight ブロック多数)・質問者所感（行 815-819）・レビュア所感（行 821-866）まで具体内容を抽出している。

指示文では「長いファイルは offset/limit で分割読込してもよい」と明示していたため、**Sonnet は判断ミス**（分割読込を試行すべきだった）。

### 2.2 構造化された結論の導出

Opus 版は単なる事実列挙にとどまらず、**マトリクス的視点で構造化された結論** を出している:

- **「Opus は経由先に敏感、Sonnet は安定」**（§6.4）
  - 根拠: 16/19 (Sonnet 4.6) は両経由先で Web 検索積極、18/20 (Opus 4.7) は経由先で正反対
- **「同 Plugin でもベースモデル個性が反映される」**（§5.1）
  - 16 (Sonnet 4.6): 具体テクニック・実用 ROI 指針（例: `== token` Semgrep ルール 1 本で ROI 最大）
  - 18 (Opus 4.7): メタ的・運用論的・設計判断的（例: SARIF 統合方針、stdio→HTTP 保険型実装）

Sonnet 版にはこれらの構造的結論が出ていない（事実列挙と表形式整理が中心）。

### 2.3 補足観察の精度

- 17 (Bedrock Opus 4.5) の Q0 表組みが ASCII art 風（罫線文字 `┌─┐│├┤`）であることから **Plugin ON の蓋然性が高い** と推論（§1 補足観察）
- 15 (Bedrock Sonnet 4.5) の Q0 はプレーン Markdown のため **Plugin 状況証拠としては中立** と判定（§5.3）

Sonnet 版は 15/17 を「未確認」のまま留めるのみで、Q0 表現スタイルからの推論には至っていない。

## 3. Sonnet 版の優位点

### 3.1 表形式整理の視認性

§6 クロス分析の比較表は Sonnet 版の方が読みやすい:

- §6.1 (#18 vs #20) で「比較軸 | #18 | #20」の 3 列表
- §6.3 (#16 vs #19) で同様の表（ただし #16 側が「不明」のため情報量は限定）

Opus 版にも比較表はあるが、Sonnet 版の方が観点を表内に揃える整理が秀逸。

### 3.2 CVE 番号レベルでの列挙

Sonnet 版は各 AI の具体 CVE 提示を本文中で列挙:
- 19 Q1: CVE-2025-49596 / CVE-2025-6514 / CVE-2025-53109/53110 / CVE-2025-68143〜145 / CVE-2026-0755 / CVE-2026-25536 / CVE-2026-33032
- 20 Q1: CVE-2025-59536 / CVE-2026-21852 / CVE-2025-6514

Opus 版は「13 件超を網羅」「20 回超」のように **件数** で済ませており、Phase 0c で CVE 単位の裏取りをする際の検索効率は Sonnet 版がやや良い。

ただし索引の目的は「該当箇所のファイル + セクション pointer」なので、列挙が薄くても **pointer から逆引きできれば実用上は問題ない**。

### 3.3 Q1-Q6 実施状況の精密把握

Sonnet 版は §0 表で **Q4 スキップ理由** まで記載:
- #07: "Q4 はスキップ：回答ボリューム・質に追加質問なし"
- #18: "Q4 はスキップ：理由「詳細すぎて疑問が浮かばないパターン」"

Opus 版は Q4 スキップに言及していない。Phase 0c で「Q4 系の質問項目はそもそも追加質問されにくい」傾向を扱う際には Sonnet 版が役立つ。

### 3.4 Phase 0c 着手前準備 #6 への接続提案

Sonnet 版 §6.1 末尾:

> "経由先によって Web 検索利用の有無が決定されるため、「具体 CVE・URL の取得」が目的なら Anthropic 純正経由が確実。Bedrock 経由は検索を促す追加指示が有効か否かの確認が必要（#19 の Q1 には WebFetch/WebSearch 利用を明示許可する文言があり、#18 の Q1 にはない）。"

**「Q1 質問文に明示許可を含めるか」が決定要因** という観点は、後続タスク B（着手前準備 #6: 経由先・バージョン差分比較ペア明示）への直接的な接続。Opus 版にはこの観点なし。

## 4. 総合評価

**Opus 版を主とし、Sonnet 版を補強素材として併用**することを推奨する。

理由:

1. **完全性で決定的な差**: Opus は #16 を含め全件直接観察、Sonnet は #16 を間接情報で代替（指示違反に近い判断ミス）
2. **構造化結論の有無**: 「Opus は経由先に敏感、Sonnet は安定」「同 Plugin でもベースモデル個性が反映」等は Opus のみ
3. **所要時間も Opus が優位**（4:20 vs 7:10）

ただし Sonnet 版の以下の要素は **Opus 版に取り込む価値あり**:
- §0 の Q4 スキップ詳細
- §6.1 末尾の Phase 0c 着手前準備 #6 への接続提案（明示許可文言の有無）
- CVE 番号レベルの具体列挙（後で必要になった際の参照素材）

**スモールスタート→拡張の総括**:

- 並行作業 A での Opus/Sonnet 並列比較により、両モデルの **得意領域の境界線が判明**:

  - **Sonnet 優位**: 表形式整理・列挙的網羅・コスト効率
- **以降のタスクでは「初回 Opus/Sonnet 並列比較」は原則不要**。タスク性質から推奨モデルを選定し、単独実行する
- **例外**: 「観点重視 + 構造化が必要かつ列挙的網羅も必要」な混合タスクが出てきた場合のみ、再度並列比較を検討
