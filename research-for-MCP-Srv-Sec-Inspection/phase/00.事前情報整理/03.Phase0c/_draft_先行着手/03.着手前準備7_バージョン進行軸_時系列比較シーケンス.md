## 1. 設計方針

### 1.1 交絡変数の扱い

本シーケンスでは「バージョン進行」を主軸に置くが、Claude 系 7 種の構成は **以下 4 軸が交絡** している:

| 交絡軸 | 値域 | バージョン進行への影響 |
|---|---|---|
| ベースモデル | Sonnet / Opus | 同バージョンでもモデル特性で挙動が異なる |
| 経由先 | Bedrock 直接 API / CC+Bedrock / CC+Anthropic 純正 | Plugin 環境・Web 検索可否を支配 |
| Plugin 環境 | 有 / 無 / 適用外 / 未確認 | 体裁差（Insight ブロック有無）を生む |
| 学習時点 | 2024-08 〜 2026-01 | バージョンと相関するが厳密に一致しない |

このため、純粋な「バージョン進行効果」を抽出するには **他軸を揃えたシーケンス** を組む必要がある。本ドキュメントでは:

- **同経由先で揃えるシーケンス**（バージョン進行を見やすい構成）
- **経由先を変える代わりにバージョンを揃えるシーケンス**（バージョン横断比較の補正用）

の双方を提示する。

### 1.2 Q1-Q6 未実施 2 件（#15, #17）の扱い

並行作業 A 索引 §0 表のとおり、**#15（Sonnet 4.5 CC+Bedrock）と #17（Opus 4.5 CC+Bedrock）は Q1-Q6 未実施**。本シーケンスでは:

- **シーケンス本体からは一旦除外**（Q0 のみで挙動評価は不可能）
- ただし **Q0 観点（学習時点・MCP 知識解像度・Plugin 状況証拠）** は補助情報として併記
- Q1-Q6 が後日実施された場合、本シーケンスを増補する形で組み込む想定（§6 で補完計画を明示）

### 1.3 4.5 → 4.6 → 4.7 のうち各バージョンが揃わない箇所の補完策

7 種構成の制約上、以下の欠落がある:

|---|---|

| Opus 系列の 4.6 が存在しない | (a) Sonnet 4.6 で代替する横断シーケンスを §4 で提示 / (b) Opus 4.5 と Opus 4.7 を直接比較する場合、4.6 のギャップを「8 ヶ月相当の学習時点差」として明示 |

**バージョン進行で観察される変化**:

### 2.3 シーケンス利用時の注意

- **S-A は経由先・Plugin・Web 検索可否が同時に変化** するため、「4.5 → 4.6 でのバージョン進行効果」と「Bedrock 直 API → CC 経由への環境変更効果」が **分離不能**。観察結果は「合成効果」として扱う

## 4. ベースモデル横断のシーケンス（Sonnet vs Opus の同バージョン比較）

バージョン軸で欠落する箇所（Sonnet の 4.7 / Opus の 4.6）を補正するためのシーケンス。

### 4.1 シーケンス定義

#### シーケンス X-A: 同 4.6 で Sonnet 系列の最先端 vs Opus 4.7 で代替

```
[基準] Sonnet 4.6 (#19 CC+Anthropic / 2025-08 / Q1-Q6 完了)
  ↓ ベースモデル差 + バージョン進行差（4.6 → 4.7）+ 学習時点差（2025-08 → 2026-01）
[代替先] Opus 4.7 (#20 CC+Anthropic / 2026-01 / Q1-Q6 完了)
```

**用途**: Sonnet 系列の 4.7 が存在しないため、Opus 4.7 (#20) を代替として参照する。**経由先（CC+Anthropic 純正）を揃えることで、Plugin 環境・Web 検索可否の交絡を除去**。残る交絡は「ベースモデル差 + バージョン差 + 学習時点差」の合成。

#### シーケンス X-B: 同 4.6 で Sonnet vs Opus 4.7（CC+Bedrock 揃え）

```
[基準] Sonnet 4.6 (#16 CC+Bedrock / 2025-08 / Q1-Q6 完了)
  ↓ ベースモデル差 + バージョン進行差（4.6 → 4.7）+ 学習時点差（2025-08 → 2026-01）
[代替先] Opus 4.7 (#18 CC+Bedrock / 2026-01 / Q1-Q6 完了)
```

**用途**: X-A の Bedrock 経由版。Plugin 環境（両者とも ON）を揃えることで、X-A と異なる軸で Sonnet/Opus 差を観察可能。

#### シーケンス X-C: 同経由先での Sonnet vs Opus 比較（経由先固定・最先端世代）

```
CC+Bedrock 経由 / 最先端世代:
  Sonnet 4.6 (#16) vs Opus 4.7 (#18)
  → 「Bedrock 経由で Plugin ON 環境下、両モデルの差」

CC+Anthropic 純正 / 最先端世代:
  Sonnet 4.6 (#19) vs Opus 4.7 (#20)
  → 「Anthropic 純正で Plugin OFF 環境下、両モデルの差」
```

**用途**: 並行作業 A §6.4 末尾の構造的結論「**Sonnet 系は両経由先で Web 検索積極、Opus 系は経由先で正反対。Opus は経由先に敏感、Sonnet は安定**」を再現観察するためのシーケンス。

### 4.2 比較観点

シーケンス X-A / X-B の主要観点:

| 観点 | Sonnet 4.6 | Opus 4.7 | 差の出処（推定） |
|---|---|---|---|
| **MCP 個別 CVE 提示** | #19: 22+ 件のパッチ状況追跡 / #16: GHSA 6 + CVE 5 | #20: 13+ 件 + Sources / #18: 意図的回避 | バージョン差・モデル差・経由先差の合成 |
| **Web 検索積極性** | #19: 自発 + 明示指示で 20 回超 / #16: Explore agent 自発 | #20: 自発複数回 / #18: 回避 | **経由先差が支配的**（並行作業 A §6.4 末尾） |
| **文体傾向** | 具体・列挙的・調査ログ的 | メタ的・設計判断的（Bedrock 側で顕著） | モデル差 |
| **学習時点差** | 2025-08 | 2026-01（約 5 ヶ月新しい） | バージョン進行（実年月の進化） |
| **Insight ブロック** | #16: 具体テクニック・ROI 指針 / #19: 皆無 | #18: メタ的・運用論的 / #20: 皆無 | **Plugin 環境差が支配的**、同 Plugin 下でモデル個性が反映 |

### 4.3 シーケンス利用時の注意

- **X-A / X-B はバージョン差・モデル差・学習時点差が同時に混入** するため、純粋なバージョン進行効果の抽出は不可能。**「Sonnet 系列の 4.7 欠落を Opus 4.7 で代替する場合の補正用」** として位置付ける
- **X-C の Bedrock 側（#16 vs #18）と Anthropic 純正側（#19 vs #20）の差** は、Sonnet 版索引 §6.1 末尾の論点「**Q1 質問文に WebFetch/WebSearch の明示許可文言を含めるか** が経由先差を決める要因」と連動する。明示許可の有無を観察軸に追加することで、経由先差の構造をより精密に把握できる
- **同 4.7 でも経由先で挙動が両極化**（#18 抑制 vs #20 積極）は、「Opus は経由先に敏感、Sonnet は安定」の構造的結論を支える観察。X-C 全体を Phase 0c の「経由先差が回答性質を支配する事例」として再利用可能

## 5. Phase 0c 本体での利用方法

並行作業 A 索引（Opus 版）§7 と整合させた利用シナリオを提示する。

### 5.1 シナリオ A: 「同一質問への回答の経年変化」を可視化

**用途**: Phase 0c で「MCP セキュリティ知識が時系列でどう更新されたか」を示す素材として、特定の質問（例: Q1 - 既知 CVE 提示）について複数バージョンの回答を並べる。

**推奨シーケンス**: S-A（Sonnet 4.5 → 4.6）

- **Q1 系列での回答変化例**:
  - #07 (Sonnet 4.5 / 2024-08): 「学習時点制約により具体 CVE 不可」と拒否 → 調査手順案内のみ
  - #16 (Sonnet 4.6 / 2025-08, CC+Bedrock): Explore agent で具体 GHSA 6 + CVE 5 を網羅提示
  - #19 (Sonnet 4.6 / 2025-08, CC+Anthropic): WebSearch 多用、NVD 個別 CVE ページまで深掘り、CVE-2025-49596 / CVE-2025-6514 等 8 件超を URL 付きで提示

**観察される進化軸**: 学習時点の前進（2024-08 → 2025-08）+ Web 検索機能の獲得 + MCP エコシステムの成熟（4.6 期で具体 CVE が大量公表されている）

**補強**: S-B（Sonnet 4.5 → 4.6、CC+Bedrock 揃え）は #15 Q1-Q6 補完後に最終形へ。現状は Q0 解像度比較のみ。

### 5.2 シナリオ B: 「信頼性スコア」算出時の系統重複検出

**用途**: Phase 0c で各 AI 回答に「信頼性スコア」を割り当てる際、**同系統（同バージョン / 同経由先 / 同 Plugin 環境）の回答が重複してカウントされないよう** にする。

**推奨参照**: 4 軸マトリクス（並行作業 A 索引 §1）+ 本シーケンス §2 〜 §4

- **重複検出ルール（暫定案）**:
  - 同バージョン・同経由先の 2 件はスコア算出時に重み 0.5 ずつとする
  - 例: #18 (Opus 4.7 CC+Bedrock) と #20 (Opus 4.7 CC+Anthropic) は同バージョンだが経由先違いで挙動が正反対なので **独立した観察として重み 1.0 ずつ** カウント
  - 例: #16 (Sonnet 4.6 CC+Bedrock) と #19 (Sonnet 4.6 CC+Anthropic) は同バージョンで挙動が両者とも積極的なため、**情報源の独立性に応じて重み調整**（CVE 提示の独立性が高ければ 1.0 ずつ、依拠元が重複していれば 0.5 ずつ）

**観察される構造**: 並行作業 A §6.4 末尾の構造的結論「Opus は経由先に敏感、Sonnet は安定」を踏まえると、**Sonnet 系列は経由先差で挙動が大きく変わらないため重複検出が必要**、**Opus 系列は経由先差で挙動が両極化するため独立扱い** という方針が成立する。

### 5.3 シナリオ C: 「バージョン進化で何が学べるか」を Phase 0c 報告書で示す

**用途**: Phase 0c の最終報告書で「Claude モデル進化により MCP セキュリティ知識・回答傾向がどう改善したか」を示す節を作る場合の素材。

- **時系列マトリクス例（簡略）**:
