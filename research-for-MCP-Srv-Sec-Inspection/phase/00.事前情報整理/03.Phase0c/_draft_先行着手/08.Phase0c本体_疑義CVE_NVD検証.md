### §0.3 凡例

| 記号 | 意味 |
|---|---|
| **実在確認済** | NVD / GitHub Advisory に対象エントリが存在し、概要・影響製品・CVSS を取得できた |
| **NVD 未登録** | WebFetch で「CVE Not Found」/ 404 / RESERVED 状態を確認。存在しない可能性が高い |
| **詳細不一致** | NVD に存在するが、AI 言及内容（製品名・脆弱性種別・CVSS 等）が実際と有意に乖離 |
| **WebFetch エラー** | タイムアウト・リダイレクト等で WebFetch が結果を返せなかった（再試行またはフォールバック実施） |
| **★WebSearch 代替** | WebFetch が拒否された場合、WebSearch でフォールバック確認したもの |

## §5 裏取りプロセス上の論点

### §5.1 検証コスト感

- **全 25 件の WebFetch 所要時間**: 開始 02:50:46 → 終了 02:52:52 = **約 2 分間**
- **1 件あたりの平均**: 約 5 秒（WebFetch 並列実行で効率化）
- **並列実行の効果**: 5 件ずつ並列 WebFetch を 4〜5 ラウンド実施。直列実行なら 25 件 × 5 秒 = 約 2 分。今回は並列化により 2 分以内に完了
- **評価**: 25 件規模の CVE 裏取りは 2〜3 分で完了できる。100 件規模でも 10 分程度と見込まれ、フェーズ作業のコスト比率として許容範囲

### §5.2 WebFetch エラー時の対応

- **Tenable TRA-2026-27**: WebFetch が「Permission Denied」で拒否された。WebSearch でフォールバックしてタイトル・概要・タイムラインを確認。存在確認には十分
- **再試行不要だったケース**: NVD / GitHub Advisory は全件 WebFetch が成功。リダイレクトや 404 は発生しなかった
- **推奨対応**: Tenable / ベンダー固有セキュリティページは WebSearch フォールバックをデフォルト戦略にする。NVD / GitHub Advisory は WebFetch が安定

### §5.3 NVD に存在しない事例の判定難しさ

- **今回は全件存在していたため発生しなかった**が、存在しない場合の判定は以下が難しい:
  - NVD の「CVE Not Found」表示は確認できるが、「採番されたが RESERVED 状態」vs「そもそも存在しない」の区別が難しい
  - CVE-2026-53355 は RESERVED 状態（NVD 未登録）を確認できた（§1 #25 の CVE-2025-53355 とは別 ID）
- **対応案**: NVD 未登録の場合は GitHub Advisory、CVE Program（cveawg.mitre.org）、vendor advisory を追加確認する

### §5.4 「2026 年 CVE = ハルシネーション疑い」仮説の再評価

- **検証前の仮説**: 2026 年 CVE は採番・公開タイムラグを考慮すると疑義が高い
- **検証結果**: バッチ 2 の 2026 年 CVE 10 件が全件実在。2026 年 5 月時点で 2026 年 CVE が公開済みであることは十分ありえる（実際に 1〜5 月公開のものが多かった）
- **学び**: 「年号が近い = 疑義」より「単一 AI 言及 + 詳細が曖昧 = 疑義」の方がハルシネーション検出に有効な指標。年号単独での疑義フラグは感度が高すぎる（偽陽性が多い）

### §5.5 将来的な Skill / Hook 化の要件

- **入力**: CVE / GHSA 識別子の一覧（Markdown テーブルから抽出）
- **処理**: NVD WebFetch（並列）→ GHSA WebFetch（並列）→ 存在確認 + CVSS/公開日/概要の抽出
- **出力**: 識別子ごとの判定結果テーブル（実在/未登録/エラー）
- **実装上の課題**:
  - NVD の HTML 構造変化への対応
  - WebFetch の並列数制限（今回は 5 件並列が安定）
  - Tenable 等ベンダー固有ページの拒否対応（WebSearch フォールバック自動化）
  - RESERVED 状態の CVE と「存在しない CVE」の区別ロジック
- **推奨実装形態**: Hook（フェーズ完了前の自動検証）より Skill（必要時に手動呼び出し）が適切。信頼性判断はメインセッションが行うべきで、Skill は純粋な実在確認データ収集に留める
