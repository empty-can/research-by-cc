- **本環境では MCP サーバは一切利用できない**（情報セキュリティ保護上の制約により、組織として正式に認められていない）。

## 調査の目的

MCP Server の脆弱性（特に、構築環境の個人情報や機密情報の漏洩に繋がるようなもの）を、MCP Server のソースコードのレビューによって調査・判定するための仕組みを調査・確立すること。

## 背景

### 本実行環境における現状の MCP サーバ利用制約

本リポジトリの実行環境（および利用者の所属組織の業務環境）では、**情報セキュリティ保護上の制約により、MCP サーバの利用が現状正式には認められておらず、一切セットアップされていない**。

この制約は MCP サーバの仕組み自体（Claude Code とサードパーティ製サーバ間の双方向通信、サーバ側コードの任意実行性、トークン・認証情報・ローカルファイルへのアクセス可能性）が、構築環境の個人情報や機密情報の漏洩経路となる潜在リスクを持つことに起因する。

### 本ブランチが達成しようとしているゴール

情報セキュリティ所管部署に対して、以下を満たした上で MCP サーバの利用許諾を得られるようにすること:

1. **しっかりとした審査基準を設けた上で**、
2. **対象 MCP サーバのソースコードレビュー（インスペクション）を実施し**、
3. **充分な確認を行ったものに限って利用する**

という運用フローを確立し、それによって「利用にリスクは無い」と **説得力と自信を持って所管部署に回答・説明できる状態** を目指す。

そのために本調査では以下を整備する:
- MCP サーバのソースコードレビューによる脆弱性（特に構築環境の個人情報・機密情報漏洩に繋がるもの）の調査・判定の仕組み
- 判定基準・観点・チェックリスト
- 実施プロセスと成果物フォーマット

## 活動構成（コードインスペクション活動とガイドライン活動の並行進行）

### 背景と動機

本ブランチ `feature/MCP-Srv-Sec-Inspection` は当初コードインスペクション活動を主軸として発足した。Phase 0b-2 完了段階で「ガイドライン・チェックリスト整備活動」を併走させる方針に拡張した。

両活動は「MCP サーバ安全利用フローの確立」という共通ゴールに対する **二層防御** の関係にある:

- **コードインスペクション活動**: MCP サーバ本体の実装不備による情報漏洩系脆弱性を検知（EscapeRoute / mcp-server-git CVE / Atlassian MCP RCE / mcp-remote RCE / 引数注入等）
- **ガイドライン・チェックリスト活動**: クライアント側設定・運用層での情報漏洩リスク緩和（プロンプトインジェクション / 過剰権限 / Whispering Secrets / MCP Inspector RCE / 間接プロンプトインジェクション等）

既知 MCP 脆弱性事例の量的多数派は「ガイドライン整備で塞げる」ことが Phase 0b-1（Google AI モード Q1〜Q6）+ 参考資料 + Claude 学習済み知識から確認されている。一方コードインスペクションでしか検知できない実装不備系は影響度が大きい（任意ファイル読取・RCE）ため、両者は補完関係にある。

### ブランチ・フォルダ構造

- **共通親ブランチ**: `feature/MCP-Srv-Sec-Inspection`（本ブランチ）。活動完了まで main にマージしない方針

- **サブブランチ開始タイミング**: Phase 01（計画書 v1.0 策定）は共通親ブランチで実施。Phase 02 以降からサブブランチ運用を開始する想定

## 成果物配置ルール（本調査適用版）

本調査では、ルート CLAUDE.md「成果物は `research-for-xxx/reports/<タスク名>/<フェーズ名>/` に置く」節の **代わりに本ルールを適用する**。

### 活動の構成要素

```
活動テーマ（= research-for-* ブランチ） ─1:N─ フェーズ ─1:N─ タスク ─1:N─ 作業
```

### フォルダ階層

```
research-for-MCP-Srv-Sec-Inspection/
└── phase/
    ├── 01.<フェーズ名>/
    │   ├── 01.<タスク名>/
    │   │   └── （タスク配下の作業ファイル・サブフォルダ群、構成は任意）
    │   └── 02.<タスク名>/
    └── 02.<フェーズ名>/
```

- 直下のサブフォルダ名は `phase/`（ルート CLAUDE.md の `reports/` の代替）
- 直下から **フェーズ → タスク → 作業** の順で階層化する（ルート CLAUDE.md の記述は実態と順序が逆になっているが、本調査ではフェーズが先）
- タスク配下の構成（さらにサブフォルダを切るか、ファイル直置きか等）は **任意**

### 命名規則

ルート CLAUDE.md「フォルダ・ファイル命名規則」節を継承する:

- 順序を示したい場合は数値プレフィックスを先頭に付ける（例: `01.<フェーズ名>/`、`01.<タスク名>/`）
- 日付はファイル名の末尾に付ける（`YYYY-MM-DD`）
- 日付付与は同内容を複数回実施する場合のみ（レビュー報告書の複数回実施等）。それ以外はファイル内変更履歴で表現
- 親タスク違いで同名作業が出る場合は、親タスク識別子を接頭辞に含める

### 「reports」ではなく「phase」とした理由

各フェーズ・タスクで生成されるファイルはレポート（計画書や報告書の類）に限らず、検証スクリプト・調査メモ・素材ファイル等を含むため、より実態に即した命名にしている。
