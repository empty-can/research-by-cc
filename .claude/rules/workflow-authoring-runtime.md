# Dynamic Workflow 実装時の運用ルール

Workflow ツール用のスクリプト（`.claude/workflows/*.js` および配布物の `workflows/*.js`）を読み書きする際に自動ロードされる path-scoped rule。**実運用で踏んだ失敗から得た知見のみを記録する**（公式仕様の再掲はしない。仕様は Workflow ツールの description が正）。

各項目には「いつ・何を踏んだか」を残す。再現条件が分からない知見は対処法だけ書いても使えないため。

---

## 1. resume のキャッシュ粒度は「プロンプト文字列の同一性」である

`resumeFromRunId` は `(prompt, opts)` が不変な `agent()` 呼び出しをキャッシュから返す。ここから 3 つの帰結が出る。

### 1.1 データフローが表現されていないパイプラインでは resume も正しく効かない

ステージ間のデータ依存を**プロンプトに埋め込んでいない**と、上流を再実行しても下流のプロンプト文字列が変わらず、キャッシュヒットして再走しない。

> **実例（2026-07-29 / cve-triage）**: 調査単位 C が失敗し再実行したが、単位 D のプロンプトが A と B しか受け取らない実装だったため、C を振り直しても D はキャッシュ再生され、C の成果が D に届かなかった。`unitPromptD(cveId, unitB, unitA)` に `unitC` を追加する修正が必要になった。

**教訓**: 「ステージ N の出力がステージ N+1 の判断に影響するなら、その出力をステージ N+1 のプロンプトに入れる」。これは調査精度の問題であると同時に、**再実行の正しさの問題**でもある。順序依存（`parallel` の完了待ち）とデータ依存は別物であり、前者だけでは resume は機能しない。

### 1.2 全エージェント共通の前文を変更すると、キャッシュが全滅する

`target` / `goal` / `notes` のような**全エージェントのプロンプトに埋め込まれる値**を変えると、1 体も再利用できなくなる。

> **実例（2026-07-29 / cve-triage）**: 失敗対策の注意書きを `notes` に追記して resume したところ、`preamble()` 経由で全プロンプトが変化し、意図した 16 体ではなく**27 体全部が再走する**状態になった。起動直後に気づいて `TaskStop` し、`notes` を戻して再実行した。

**教訓**: resume の直前に args を「ついでに改善」しない。プロンプト改善は次回の新規実行に回す。どうしても両立させたいなら、共通前文ではなく**再走させたいステージのプロンプトにだけ**差分を入れる。

### 1.3 失敗したエージェントにはキャッシュが無いので、resume すれば必ず再走する

`null` を返して終わったエージェントは journal に result を持たないため、resume 時は自動的に再実行される。**中断（abort）を選んでも部分成果は捨てられない** — 成功済みのエージェントはキャッシュから返るため。「中断すると成功分を捨てることになる」というのは誤った直感である。

## 2. エラーハンドリング

### 2.1 ランタイムの StructuredOutput リトライは同一コンテキスト内で行われる

スキーマ検証に失敗した場合、ランタイムは同一エージェント・同一コンテキストで最大 5 回振り直す（`StructuredOutput retry cap (5) exceeded` で打ち切り）。**壊れた出力パターンはコンテキストに残るため、5 回とも同じ壊れ方を再現しうる。**

> **実例（2026-07-29 / cve-triage）**: 調査自体は完走していたエージェントが、成果物を JSON に載せる段階で `<parameter name="claim">` というツール呼び出しの XML 記法を JSON 文字列に混入させ、5 回とも同じ壊し方をして結果を返さず終了した。

**教訓**: スキーマ整形の失敗は確率的だが、**同一コンテキスト内の再試行では回復しにくい**。回復させたいなら、ワークフロー層で**新規コンテキストのエージェントを立て直す**リトライを実装する。ランタイム任せにしない。

```js
async function agentWithRetry(prompt, opts) {
  const first = await agent(prompt, opts)
  if (first) return first
  log(opts.label + ': 結果を返さなかった — 新規コンテキストで1回だけ再試行する')
  return await agent(prompt, { ...opts, label: opts.label + '(retry)' })
}
```

### 2.2 欠損を握り潰さず、続行するか中断するかを設計判断として明示する

失敗したステージの結果を `null` のまま下流に渡すとクラッシュし、黙って空を渡すと「調査したが何も無かった」と誤読される。取りうる選択肢は 2 つで、**どちらを選んだかをコードに明示する**。

- **プレースホルダで続行**: 「再実行が必要」という情報を構造に残して先へ進む。下流が劣化入力で走るリスクを負う
- **中断**: 当該アイテムの下流ステージを実行せず、理由つきで返却値に載せる。トークンを節約でき、汚染も起きない

**劣化入力を受けた下流が「劣化を正しく扱えるか」は確率的**であり、設計として当てにすべきではない。汚染リスクとやり直しコストを天秤にかけ、**やり直しコストの方が安いなら中断を選ぶ**（1.3 のとおり部分成果は失われない）。

### 2.3 欠損は返却値のトップレベルで可視化する

欠損の事実を成果物本文（`summary` の文字列など）に埋め込むだけでは、呼び出し元が気づけない。`abortedItems` / `degradedItems` のような**専用フィールドをトップレベルに置き**、呼び出し元向けの next-steps にも点検指示を含める。

## 3. args の受け取り

呼び出し側から `args` が**オブジェクトではなく JSON 文字列として渡ってくる場合がある**。文字列をそのまま単一フィールド扱いする実装だと、原因の読み取れないエラーで即死する。

> **実例（2026-07-29 / cve-triage）**: `if (typeof input === 'string') input = { cves: input }` が JSON 文字列全体を CVE ID リストとして扱い、`CVE ID の形式が不正: {"CVES":...}` というエラーになった。

```js
let input = args
if (typeof input === 'string') {
  const raw = input.trim()
  if (raw.startsWith('{')) {
    try { input = JSON.parse(raw) } catch (e) {
      throw new Error('args が JSON 文字列として渡されましたが解析できません: ' + e.message)
    }
  } else {
    input = { cves: raw }   // 単一値のショートハンドとして扱う場合
  }
}
```

## 4. 開発中の反復

### 4.1 `Workflow({name})` はセッション開始時のレジストリを参照する

`.claude/workflows/*.js` を編集しても、**同一セッション中は `name` 指定で再読み込みされない**。編集内容を反映して実行するには `scriptPath` で実ファイルを直接指定する。

> **実例（2026-07-29）**: 修正後に `name` 指定で起動したところ、生成された実行スクリプトに修正が入っておらず同じエラーで落ちた。`scriptPath` 指定に切り替えて解決。

### 4.2 `node --check` は async IIFE でラップして通す

ワークフロースクリプトはトップレベル `return` を含み、`export const meta` を持つ。そのままでは `node --check` が「Illegal return statement」で落ちる。**構文チェック自体は必ず実施する**（テキストレビュー2巡が構文エラーを見逃した実績がある）。

```bash
{ echo '(async () => {'; sed 's/^export const meta/const meta/' "$f"; echo '})()'; } > /tmp/chk.mjs
node --check /tmp/chk.mjs
```

### 4.3 配布物と導入コピーの二重管理に注意する

配布用のスクリプトと、実際に実行される `.claude/workflows/` 配下のコピーが別ファイルになっている構成では、**片方だけ直すと実行結果が変わらない**。編集後に `diff -q` で同一性を確認する。

## 5. 規模とコスト

- 1 ワークフロー内の同時実行数は **`min(16, CPU コア数 - 2)`**。8 コアの端末では 6 体で、超過分は自動キューイングされる（失敗ではない）。**「N 体同時起動で端末がパンクする」という心配は不要**だが、その分**待ち時間は直列化される**
- 予定エージェント数が 25 体を超えるとタスクパネルに「Large workflow」警告が出る（通知のみ。実行は止まらない）
- 大量アイテムを扱う場合、**アイテム単位でバッチ分割して順次実行する**方が、メインセッションのコンテキスト消費と失敗時のやり直し範囲を抑えられる。1 回の返却値が数百 KB になると、呼び出し元がそれを読むだけで大きなコストになる

---

## 6. 返却値の読み取り

返却値が大きい場合、タスク通知に載るのは先頭だけで残りは truncate される。**全体はタスクの output ファイルに保存されている**ため、必要な部分だけをスクリプトで抽出して読む。全文を Read すると呼び出し元のコンテキストを浪費する。

```js
// output ファイルは { summary, agentCount, logs, result, ... } でラップされている
const wrapped = JSON.parse(fs.readFileSync(outputPath, 'utf8'))
const d = typeof wrapped.result === 'string' ? JSON.parse(wrapped.result) : wrapped.result
```

`journal.jsonl` には完了したエージェント 1 体につき 1 行の `{"type":"result",...}` が記録される。**失敗したエージェントは result 行を持たない**ため、「started はあるが result が無い」ものが失敗候補になる。実行中に生死を判定したい場合は、各 `agent-*.jsonl` の更新時刻を比較する（兄弟が毎秒書いている中で数分間無更新なら停止している）。
