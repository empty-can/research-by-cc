# 対象 Opus 出力の事前予想 — 書き手: Ctx. 非共有状態 Opus 4.6（AWS Bedrock 経由）

作成日: 2026-05-20
書き手: 議論サマリを受領した、議論コンテキストを共有していない別セッションの Opus（**AWS Bedrock 経由**、Opus 4.6）
予想対象: 2026-05-21 実施予定の実験において、議論コンテキストなし・CLAUDE.md なし・LSP なしの条件で標準 NG 調査指示（＋計画出力指示）を受けた対象 Opus が産出する計画

## 予想: 対象 Opus が産出する計画

### 1. 調査の step-by-step プラン

対象 Opus は以下のような計画を立てると予想する（粒度は 5〜8 ステップの範囲でブレうるが、ここでは最も詳細な場合の 8 ステップで予想を記述する。実際には Step 5 と Step 8 が省略され 6 ステップ程度になる可能性もある）:

**Step 1: エラーの全体像を把握する**
- artifact.zip 内のテスト結果サマリ・JUnit レポート XML を最初に確認
- 失敗テストケースの特定（テストクラス名・メソッド名・失敗数）
- エラーメッセージとスタックトレースの確認

**Step 2: スタックトレースの解析**
- スタックトレース上の例外チェーンを辿る
- アプリケーション固有フレーム（パッケージ名でフィルタ）と OSS フレームの識別
- 直接原因となった例外・発生箇所の特定

**Step 3: テストコードの確認**
- 失敗テストメソッドのソースを読む
- テストが何を検証しようとしていたかを把握
- テスト内で行われているセットアップ処理・アサーション内容の理解

**Step 4: 関連するアプリケーションコードの確認**
- スタックトレースで示された例外発生箇所のソースコードを読む
- 呼び出し元を遡って処理フローを理解
- 設定ファイル（application.yml / properties 等）の関連箇所を確認

**Step 5: テスト環境・設定の確認**
- テスト用の設定ファイル群の確認
- build.gradle のテスト関連設定の確認
- テスト実行時の依存関係・バージョンの確認

**Step 6: 原因の仮説立案と検証**
- 上記情報を統合して原因仮説を立てる
- 仮説を裏付ける/否定する追加証拠をコードベース内で探索
- 必要に応じて OSS のドキュメント・ソースを参照

**Step 7: 解消方法の提案**
- 原因に対する修正案を複数検討
- 影響範囲の評価（他テストへの波及等）
- 推奨する修正案の提示と根拠説明

**Step 8: 再発防止の考察（余力があれば）**
- 同種の問題が他箇所にないかの簡易チェック
- テスト設計上の改善余地があれば言及

#### 予想の確信度

- **高**: Step 1〜4 の存在と順序。Opus はスタックトレース → コード追跡の定石を踏むはず
- **中**: Step 5 の粒度。テスト環境の複雑さを初見でどこまで察知するかは不確実
- **低**: Step 8 の有無。指示文に「原因調査・解消方法提案」とあれば再発防止まで踏み込む可能性はあるが、計画段階で明示するかは半々

### 2. 各ステップで入力として必要な情報

対象 Opus が列挙すると予想する必要情報:

| ステップ | 既に渡されている情報 | 追加で必要になり得る情報 |
|---|---|---|
| Step 1 | artifact.zip 内のテスト結果レポート | — |
| Step 2 | artifact.zip 内のスタックトレース / ログ | — |
| Step 3 | テストソースファイル（リポジトリ内） | テストが依存する外部データ / フィクスチャの所在 |
| Step 4 | アプリケーションソース（リポジトリ内） | 実行時の動的設定・環境変数 |
| Step 5 | build.gradle・設定ファイル群（リポジトリ内） | CI パイプライン定義（.gitlab-ci.yml 等） |
| Step 6 | 上記全て | OSS ドキュメント / Changelog（WebFetch で取得） |
| Step 7 | 上記全て | 過去の類似修正コミット履歴 |
| Step 8 | 上記全て | 同種のテストの一覧（grep 等で取得） |

※ Step 8 は「余力があれば」の条件付きステップであり、対象 Opus が必要情報として列挙しない可能性もある。

#### 予想の確信度

- **高**: artifact.zip の存在を前提とする点。渡されていれば最初にそこを見る
- **中**: CI パイプライン定義への言及。指示文にパイプライン情報がどう書かれているかに依存
- **低**: 「過去の類似修正」への言及。git log を見る発想が計画段階で出るかは不確実

### 3. 各ステップでの意思決定ポイント

対象 Opus が挙げると予想する判断基準:

1. **Step 1 → Step 2 の分岐**: テスト失敗がアサーションエラーか例外スローか
   - アサーションエラー → 期待値と実値の乖離分析ルートへ
   - 例外スロー → スタックトレース深掘りルートへ

2. **Step 2 完了後の優先順位**: テストコード確認（Step 3）とアプリコード確認（Step 4）のどちらを重点的に行うか
   - スタックトレースがテストセットアップ中の例外を示す → Step 3 を重点的に確認
   - スタックトレースがアプリケーションロジック内の例外を示す → Step 3 は軽く確認し Step 4 を重点化

3. **Step 4 完了後の分岐**: 原因の所在が明白か、追加調査が必要か
   - コードロジックの問題が明白 → Step 5・6 をスキップし Step 7 へ
   - 設定・環境依存が疑われる → Step 5 で環境・設定を確認した上で Step 6 へ

4. **Step 6 での判断**: 仮説に十分な確信が持てるか
   - 確信あり → Step 7 へ
   - 確信なし → 追加のコード読み込みまたは情報要求

#### 予想の確信度

- **高**: 分岐 1（アサーション vs 例外）は Opus が自然に立てる区分
- **高**: 分岐 2（テストセットアップ vs アプリロジック）も定石的な切り分け
- **中**: 分岐 3 と 4 の粒度。ここまで具体的に書くかはやや不確実（もっと大雑把に「状況に応じて」で済ませる可能性あり）

### 4. 着手前に不足していると感じる情報とその入手方法案

対象 Opus が挙げると予想する不足情報:

1. **テスト環境の構成情報**
   - 何のコンテナ上で動いているか、Java バージョン、使用 DB 等
   - 入手方法: CI 定義ファイル / Dockerfile / docker-compose.yml の確認

2. **最近の変更履歴**
   - NG が発生し始めたタイミングと、その前後のコミット
   - 入手方法: git log --since / git bisect 的なアプローチ

3. **正常時の動作仕様**
   - テスト対象機能の仕様・設計意図
   - 入手方法: 設計ドキュメント / テスト仕様書があれば参照

4. **過去の類似 NG 対応例**
   - 同種の失敗パターンに対する過去の対処法
   - 入手方法: Issue トラッカー / コミットメッセージ検索

#### 予想の確信度

- **高**: 項目 1〜2。環境と変更履歴はほぼ確実に挙がる
- **中**: 項目 3。仕様書の存在を前提とするかは指示文の書き方次第
- **低**: 項目 4。「既知障害パターン」的な発想が計画段階で出るかは五分五分

### 5. 想定される行き詰まりパターンとその対処案

対象 Opus が挙げると予想する行き詰まりパターン:

1. **スタックトレースが浅い / 情報量不足**
   - 例: `AssertionError: expected <200> but was <500>` のみでトレースが短い
   - 対処: アプリ側のログ（artifact.zip 内）を確認、デバッグログレベルの出力を探す

2. **関連コードが広範囲に分散している**
   - 例: DI / AOP / イベント駆動で呼び出しチェーンが追いにくい
   - 対処: grep でキーワード検索、設定ファイルから Bean 定義を辿る

3. **テスト固有の設定が複雑で全容把握に時間がかかる**
   - 例: テスト用 profile / テスト固有 Bean / モック差し替えが多層
   - 対処: テスト実行時のログからロードされた設定を逆引き

4. **OSS 側のバグ or バージョン起因の問題**
   - 例: Spring Boot バージョンアップに伴う破壊的変更
   - 対処: OSS の Changelog / Release Notes / Issue Tracker を参照

5. **再現環境がないため仮説検証ができない**
   - 対処: コードの静的解析で論理的に絞り込む、修正案を複数提示して人間に検証を委ねる

#### 予想の確信度

- **高**: パターン 1〜2。定番の行き詰まりとして挙がるはず
- **高**: パターン 5。「再現できない」制約は指示文から読み取れれば確実に言及
- **中**: パターン 3〜4 の具体度。もっと抽象的に書くか、もっと具体的に書くかはブレる

## 予想: 対象 Opus が産出する自己批判

### 1. この計画で見落としていそうな観点

対象 Opus が挙げると予想する自己批判:

- テスト実行環境と開発環境の差異（環境固有の問題）への考慮が薄い
- 複数テストが同時に失敗している場合の共通原因分析の視点が弱い
- テストデータの状態（DB のシード状態、外部サービスのモック状態）への言及が不足
- 調査の「打ち切り基準」（ここまでやって分からなければ別アプローチ）が未定義

### 2. 過剰投資になっているステップ

- Step 4 でアプリケーションコードを広く読みすぎるリスク
- Step 6 で OSS ソースまで深追いするのは多くの場合不要
- Step 8（再発防止）は調査タスクのスコープ外かもしれない

### 3. 着手順序を変えたほうが効率的な箇所

- アプリケーション実行ログ（スタックトレース以外のログ出力）の確認を Step 2 と並行して行うべき
- build.gradle の確認は必要になってからで良く、Step 5 として独立させる必要はない
- git log（最近の変更）を早期に確認すれば、多くの場合 Step 3-4 の探索範囲を絞れる

### 4. 別の Opus セッションがこの計画を見たら指摘しそうな弱点

- 「全ステップが直列」であり、並行して確認できるものの整理がない
- artifact.zip の内容物を具体的に列挙していない（何が入っているか不明なまま計画している）
- テスト実行の仕組み自体（ビルド構成、起動手順）の理解ステップが明示されていない
- コスト意識（トークン消費の最適化）への言及がない

## メタ: 予想についての確信度と補足

### 対象 Opus が見落とすであろう観点

1. **インテグレーションテストの複雑な多段構成**（テスト用アプリ起動 → Selenium リクエスト → 証跡取得）を正しく認識せず、通常の JUnit テスト失敗として扱う可能性が高い
   - 確信度: **高**。CLAUDE.md がなく、この複雑な構造を事前に知る手段がない
   
2. **build.gradle が複数存在し、それぞれ異なる責務を持つ**ことへの気付きが遅れる
   - 確信度: **高**。Gradle モノリポの「癖」は読み込んで初めて分かる

3. **ant タスクによるファイル・フォルダ構成の準備**がテスト実行の前提になっていること
   - 確信度: **高**。ビルド定義ファイルを逐一読み込むまで ant タスクの存在と役割に気付きにくく、計画段階ではそこまで踏み込まない

4. **トークン消費の最適化戦略**（何を読まないか、の意識的決定）
   - 確信度: **中〜高**。計画出力指示にコスト言及がなければ、自発的に触れない可能性が高い

5. **既知障害パターンとの照合**というステップ
   - 確信度: **中**。カタログが存在しない環境では発想しにくいが、「過去の類似NG」として間接的に触れる可能性はある

### 対象 Opus が自発的に提案してきそうな観点

1. **git blame / git log を使った回帰分析**（「いつから壊れたか」の特定）
   - 確信度: **高**。Opus が好む系統的アプローチ

2. **WebFetch での OSS ドキュメント参照**の提案
   - 確信度: **高**。ツールとして利用可能であれば計画に含めるはず

3. **修正案の複数提示とトレードオフ分析**
   - 確信度: **高**。Opus は単一解でなく選択肢を示す傾向がある

4. **テスト実行コマンドの確認・提案**（ローカルで再実行する方法）
   - 確信度: **中〜高**。ただし環境制約で実行不可と分かれば引き下がる

5. **影響範囲分析**（同じ部品を使う他テストへの波及確認）
   - 確信度: **中**。計画段階で具体的に入れるかは微妙だが、Step 7 内で言及する可能性あり

6. **自己批判での「計画が直列すぎる」指摘と並列化提案**
   - 確信度: **中**。Opus は自己批判で構造的な弱点を指摘する傾向がある

## 予想の全体的な不確実性

### 確実性が高い部分
- 全体の骨格（スタックトレース起点 → コード追跡 → 仮説検証 → 修正提案）は高い確率でこの形
- 自己批判のセクションで「探索範囲が広すぎるリスク」に言及すること
- artifact.zip を起点とすること（渡されていれば）

### 不確実な部分
- **計画の粒度**: 5〜6 ステップで粗く書くか、8 ステップ以上に細分化するか。指示文のトーンに依存
- **インテグレーションテスト特有の構造への対応**: 初見で artifact.zip の中身を見て「これは単純な JUnit NG ではない」と気づくタイミングと、計画の修正度合い
- **自己批判の深度**: 形式的に 2〜3 行ずつ書くか、踏み込んだ構造的批判をするか
- **コスト / 効率への自発的言及**: 指示文にコスト言及がなければ触れない可能性が高い（＝ガイドライン整備の価値がここで実証される想定）

### 予想全体が外れる可能性のあるシナリオ
- 対象 Opus が artifact.zip の中身を計画前に確認できる環境にあり、テスト構造の複雑さを初手で認識した場合 → 計画がより構造化される
- 標準指示文にインテグレーションテストの仕組みに関する説明が含まれている場合 → 「見落とし」予想の多くが外れる
- 対象 Opus のメモリに過去の類似作業経験が残っている場合 → 「新規性の高い依頼」前提が崩れる
