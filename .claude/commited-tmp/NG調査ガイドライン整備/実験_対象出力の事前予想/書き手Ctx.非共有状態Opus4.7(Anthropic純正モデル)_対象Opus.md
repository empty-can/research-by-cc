# NG 調査計画事前予想 — コンテキスト非共有 Opus による予想

作成日: 2026-05-20
作成モデル: 議論サマリのみを受領した、元議論セッションを共有していない別セッションの Opus（**Anthropic 純正モデル**、Opus 4.7）
位置付け: 議論サマリ §7.2 の依頼に従い、**議論サマリも元議論も持たない別セッションの Opus**（2026-05-21 実施の対象 Opus）が、標準 NG 調査指示文 + §6.3 の追加指示を受け取った場合に出力するであろう計画を予想したもの。§7.3 の留意点に従い、議論で設計したガイドライン案の存在に過度に引きずられないよう注意した。

---

## 0. 予想の前提と書き方

- 対象 Opus は、本リポジトリの慣習・モノリポ固有の癖・運用環境制約（コンテナ再現不可、LSP 未導入、CLAUDE.md 不在）の **いずれも事前に知らない** 想定で予想する
- 対象 Opus は標準的な「Java / Spring Boot のテスト失敗調査」の発想を、Java / Spring / Selenium の一般知識を背景に展開すると想定する
- 出力は §6.3 のフォーマット（ステップ計画 / 必要情報 / 意思決定ポイント / 不足情報 / 行き詰まりパターン + 自己批判）に沿った構造になると予想する
- 各観点の末尾に **自信レベル（高 / 中 / 低）** を付す

---

## 1. 全体構造に関する予想

対象 Opus は、最初に受領した情報（標準指示文・artifact.zip・参照ファイル一覧）の内容物確認を軽く行った後、**「証跡を起点とした逆向き解析」を基軸** に置いた線形のステップ計画を提示する公算が高い。

ステップ数は **6〜9 個** の範囲に収まり、最初に「入力情報の取り込み・分類」を、最後に「修正方針提示」を置く構造を取ると予想する。各ステップに対して入力情報・判定基準・不足情報を順に列挙する形式になる。

自信レベル: **中**（Opus はフォーマット要求に忠実に従う一方、ステップ粒度には個体差が出やすい）

---

## 2. ステップ計画（予想）

対象 Opus は概ね以下の流れを提示すると予想する。

### Step 1: 入力情報の確認と分類

- artifact.zip を展開して内容物を一覧化
- ファイル種別ごとに分類（テストレポート XML、サーバ側ログ、Selenium スクリーンショット、ジャーナル等）
- 「参照ファイル一覧」と artifact 内容の対応付け

自信レベル: **高**

### Step 2: NG テストケースの特定

- テストレポート（surefire / failsafe 形式の XML を想定する公算大）から失敗テストを抽出
- テストクラス名・メソッド名を確定
- 失敗時のアサーションメッセージ・例外型を控える

自信レベル: **高**

### Step 3: スタックトレース解析

- トップフレームから順に、ユーザコード（Java 部品）に到達する最初のフレームを特定
- "Caused by" チェーンを辿り、根因例外を特定
- 例外型から想定される失敗カテゴリ（NPE / 接続失敗 / シリアライズ失敗 / タイムアウト等）を分類

自信レベル: **高**

### Step 4: 該当テスト用アプリ側コードの精読

- テスト用アプリの起動設定（テスト用 build.gradle、application.yml/properties 等）
- 失敗箇所周辺の対象部品ソース
- 関連する Bean 定義・DI 設定

自信レベル: **中**（対象 Opus が「テスト用アプリ側」と「クライアント側」を明確に分けたステップとして提示するかは、artifact 内のフォルダ命名や指示文の表現次第で揺れる。両者を混在させた単一ステップに丸めてくる可能性もある）

### Step 5: テストクライアント側コードの精読

- Selenium driver を使うクライアント側の JUnit テストコード
- リクエスト送信ロジックと期待値定義
- ブラウザ操作・待機戦略（暗黙待ち / 明示待ちの有無）

自信レベル: **中**（Selenium クライアントが JUnit プラットフォーム経由で動くという「やや独特な」構成を、対象 Opus が正しく把握できるかは artifact 内ヒントの濃度に依存）

### Step 6: ログ・ジャーナル横断確認

- サーバ側ログから例外発生前後のエントリを抽出
- ジャーナル（systemd journal を想定するか、独自概念と捉えるかは Opus 次第）からプロセス起動・終了状況を確認
- Selenium スクリーンショットを失敗時点の UI 状態確認に使用

自信レベル: **中**（ジャーナルが何を指すかの解釈で振れやすい）

### Step 7: 仮説形成

- 上記から原因仮説を 2〜3 個列挙し、各仮説の整合性スコアを暗黙に付与
- 各仮説に対する「追加で確認すべき情報」を列挙

自信レベル: **高**

### Step 8: 修正方針提示

- 最有力仮説に対する修正案（コード変更 / 設定変更 / テスト側変更のいずれかを判定）
- 影響範囲の見積もり
- リグレッションリスクの簡潔な注記

自信レベル: **中**（指示文が「原因特定」までを求めているのか「修正提案」までを求めているのかで分岐する）

## 3. 各ステップの必要情報に関する予想

対象 Opus は、以下のパターンで必要情報を整理すると予想する。

- 「**既に渡されているもの**」: artifact.zip、対象部品のソースアクセス、テスト用 / クライアント側 build.gradle へのアクセス
- 「**追加で必要かもしれないもの**」として挙がりやすい項目:
  - 過去の類似 NG の有無（**ただし対象 Opus は記憶機構を信頼せず、ユーザに問う形を取る公算が高い**）
  - リポジトリ全体のモジュール構成図
  - 当該テストの直近の Pass 履歴（最後に通ったのはいつか、その間の関連変更）
  - 対象部品のバージョンと、依存している Spring Boot のバージョン
  - インテグレーションテストの実行ログ全文（artifact に部分しか含まれない場合）

自信レベル: **中**（上記項目すべてを挙げるとは限らない。特に「リポジトリ全体のモジュール構成図」は省略される公算がある。Opus は「既に渡された情報で進められそうなら進む」傾向があるため）

---

## 4. 意思決定ポイントに関する予想

対象 Opus は、以下のような分岐ポイントを列挙すると予想する。

1. **Step 3 の後**: スタックトレースがユーザコードに到達しているか否か。到達していれば Step 4 へ、フレームワーク内で完結していれば OSS 内挙動の理解（Spring Boot ドキュメント参照）へ
2. **Step 5 の後**: クライアント側に明らかな問題（待機不足 / セレクタ不整合）があるか否か。あればクライアント側修正方針へ、なければサーバ側深掘りへ
3. **Step 6 の後**: ログ・ジャーナルから「テスト用アプリが正常に起動していたか」が確認できているか。起動失敗ならビルド・起動フェーズの調査へ、起動成功なら振る舞いの調査へ
4. **Step 7 の後**: 仮説に有意な差があるか。なければ「再現を試みる」ルートを提案する公算が高い（**ここでローカル再現が不可能であることへの認識が抜ける可能性が高い**）

自信レベル: **中**（分岐の粒度はモデルがどの程度先回りするかで変わる）

---

## 5. 不足情報とその入手方法に関する予想

対象 Opus が挙げるであろう項目:

- **テスト用アプリのコンテナ環境定義**（Dockerfile / compose 定義 / ant タスクの中身）— 「リポジトリ内検索で取得可能」と回答する想定
- **当該 NG の発生頻度**（毎回失敗か / 間欠失敗か）— 「ユーザに問い合わせ」または「過去のパイプライン結果参照」と提案
- **テスト対象部品の責務に関する高水準ドキュメント** — 「README / Javadoc 参照」と提案
- **Spring Boot 固有挙動の公式情報** — 「公式 docs を WebFetch」と提案

**逆に対象 Opus が挙げそうにない項目**:

- 「再現環境が利用可能か」自体への明示的問い合わせ（**コンテナがあるのが当たり前と仮定する公算が高い**）
- 「LSP が利用可能か」への問い合わせ（**そもそも LSP 利用を前提に置かない**）
- 「CLAUDE.md・`.claude/rules/` 配下に既存ガイドはあるか」への確認（**対象 Opus がメタ情報を最初に探す挙動を取らない場合、この観点自体が抜け落ちる**）

自信レベル: **高**（特に後者の「挙げそうにない」観点は、設計議論を経た側からは見えやすいが、コンテキストなしでは盲点になりやすい）

## 6. 想定される行き詰まりパターンと対処案に関する予想

対象 Opus は以下を挙げる公算が高い。

1. **スタックトレースがフレームワーク内で完結し、ユーザコード由来かが見えない**
   - 対処案: OSS ソース / docs を読みに行く、リフレクション・AOP 経由の呼び出しを疑う
2. **Selenium スクリーンショット時点で異常状態が読み取れない**
   - 対処案: 画像の前後フレームを比較、テスト用アプリ側のログと時刻で突き合わせ
3. **テスト用アプリ起動失敗で本体テストが走っていない**
   - 対処案: ant タスク・build.gradle の起動フェーズログを精査
4. **間欠失敗で再現が困難**
   - 対処案: タイミング系の問題（並行性 / 非同期境界 / 待機不足）を疑う

**対象 Opus が挙げ損ねる公算が高いパターン**:

- **「該当 OSS のソース全文読み込みでトークンを浪費する」**（自分自身がはまるパターンへの気付きは弱い）
- **「artifact.zip 内に大量の正常ログが含まれて読み込みコストが膨らむ」**（コスト観点で先回りする発想が出るかは個体差大）
- **「テストクライアントとテスト用アプリのコードを混同して、誤った場所を修正提案する」**（artifact 内のフォルダ命名や指示文の表現次第で発生確率が変動するが、対象 Opus 側でこのリスクへの言及があるかは別問題）

自信レベル: **中**（行き詰まりパターンの列挙は典型例に偏る傾向があり、対象 Opus がどこまで網羅するかは個体差が大きい）

## 7. 自己批判パートに関する予想

対象 Opus は §6.3 後段で求められた自己批判 4 項目に対して、以下のような内容を返すと予想する。

### 7.1 見落としていそうな観点（自己批判 1 項目目）

**対象 Opus が自身の計画への自己批判として挙げると予想する観点**:

- 「テストフレームワークそのもののバージョン差異・既知バグ確認が抜けている」
- 「先行する Pass 履歴との diff（git log）から原因特定する経路を最初に置くべきだった」
- 「テストデータ依存（外部リソース・テストフィクスチャ）の観点が薄い」

**一方、議論コンテキスト側で重要と判断されている以下の観点には、対象 Opus は自己批判でも到達しない公算が高い**（書き手の補足的観察）:

- ローカル再現が不可能という前提
- モノリポ独自慣習の存在
- 既知 NG カタログという仕組みの不在
- トークン消費そのものを設計目標とすべきという発想

### 7.2 過剰投資になっているステップ（自己批判 2 項目目）

**対象 Opus が挙げると予想する観点**:

- 「Step 4〜5 のコード精読範囲が広くなり過ぎる懸念」を自分から挙げる公算は **中**
- 「Step 6 のログ全文読みが効率悪い」と挙げる公算は **中〜高**（Opus は自分のトークン消費に対しある程度自覚的）

### 7.3 着手順序の見直し（自己批判 3 項目目）

**対象 Opus が挙げると予想する観点**:

- 「先にテストクラスのアサーション内容を見てから artifact 全展開する方が無駄が少ない」と気付く公算は **中**
- 「git log の確認を Step 1.5 として前倒しすべき」と気付く公算は **中〜低**（自然発想では出にくい）

### 7.4 別 Opus セッションが指摘しそうな弱点（自己批判 4 項目目）

**対象 Opus が挙げると予想する観点**:

- 「仮説形成の判断基準が暗黙的すぎる」
- 「修正提案の影響範囲評価が浅い」
- 「ユーザへの問い合わせ判断基準が無く、無限に自走する余地がある」

### 7.5 自己批判パート全体への自信レベル

自信レベル: **中**（自己批判 4 項目それぞれの深さはランタイムの揺らぎが大きく、上記 7.1〜7.4 で挙げた内容のうちどれが実際に出力されるかは確率的）

## 8. 総合的な見立て

### 8.1 対象 Opus が自発的に提案してきそうな観点（議論側から見て価値があるもの）

- **git log / blame を用いた直近変更との突き合わせ**: 議論サマリでは明示的に取り上げていないが、Opus は自然と提案する公算が高い
- **OSS バージョン差異・既知バグの確認経路**: GitHub Issues / リリースノートへのアクセス提案
- **テストフィクスチャ・テストデータの観点**: 議論側で薄い領域
- **間欠失敗 vs 決定的失敗の切り分けを早期に行う発想**: 議論側でも明示的に出していない

### 8.2 対象 Opus が見落とすであろう観点（議論側で重要と判断したもの）

- **ローカル再現不可能という制約**: 対象 Opus は「再現を試みる」ステップを当然のように入れる公算が高い
- **モノリポ固有の癖の存在**: 標準的な Java プロジェクト構成として扱う
- **OSS ソース読み込みのコスト感**: 「必要なら全部読む」前提で計画する
- **LSP プラグインを利用する選択肢**: そもそも触れない（議論時点で未導入のため、見落としても結果は同じだが、選択肢として言及するかが論点）
- **既存ガイドライン（CLAUDE.md / `.claude/rules/`）の確認を最初に行う発想**: 触れない公算が高い（議論時点で未整備のため、たとえ確認に行っても何も見つからないが、確認に行く発想自体があるかが論点）
- **artifact 読み込みの優先順位付け**: 「全展開して中身を確認」の粒度に留まる

### 8.3 全体としての自信

- 出力フォーマット遵守を予想する自信: **高**
- ステップ計画の骨子を予想する自信: **高**
- 各ステップの粒度を予想する自信: **中**
- 自己批判の深さを予想する自信: **中**
- 「議論側で重要と判断した観点を対象 Opus はおおむねカバーしない」という予想への自信: **中〜高**

## 9. 比較観測時の注目ポイント（実験当日の検証用）

- 対象 Opus が「再現を試みる」ステップを置くか / コンテナ環境の有無を最初に確認するか
- 「既存の CLAUDE.md / ガイドライン確認」を最初に置くか
- artifact 内容の選択的読み込み戦略を自発的に提案するか
- ローカル LSP・grep 等の使い分けに言及するか
- git log / blame を計画に組み込むか
- 過剰投資への自己批判で「OSS ソース全文読み」「artifact 全展開」に言及するか
- モノリポ固有性への言及があるか
- 上記のいずれにも触れない場合、それはガイドライン整備の独自価値を裏付ける材料となる

---

## 10. 予想外の挙動が起きるとしたらどこか

- **対象 Opus が想定外に丁寧で、最初にメタ情報（CLAUDE.md 等）を探しに行く**: 発生可能性は中程度。Opus にはコンテキスト把握を先行させる挙動が見られる場面があり、その方向に振れる可能性は否定できない
- **対象 Opus が逆に薄く、ステップ計画を 3〜4 個で済ませてくる**: 発生可能性は低〜中程度。指示文末尾の項目数（5 項目 + 自己批判 4 項目）に引っ張られて密度は確保されると予想
- **対象 Opus が「指示文末尾の 5 項目」と「自己批判 4 項目」を統合せず、別ブロックで返してくる**: 発生可能性は高い。両者を順番に分けて記述する構造を取る公算が高い
