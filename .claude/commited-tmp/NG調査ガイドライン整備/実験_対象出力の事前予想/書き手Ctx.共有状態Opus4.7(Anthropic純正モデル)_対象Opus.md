# NG 調査計画事前予想 — コンテキスト共有 Opus による予想

作成日: 2026-05-20  
作成モデル: claude-opus-4-7（本セッション内で議論を担当した Opus）  
位置付け: 議論コンテキスト全体（設計案・ガイドライン構造含む）を共有した状態での Opus 自身による「2026-05-21 実施の対象 Opus が立てるであろう計画」の予想。本セッション内での議論中に作成した予想内容を、Sonnet 予想ファイル（`NG調査計画事前予想_コンテキスト共有Sonnet.md`）と同じフォーマットで整形したもの。

---

## このファイルの読み方

- **「予想」の性質**: 「コンテキストを共有した Opus 自身が、議論文脈を持たない別 Opus セッションがどう計画するか」を予想したもの。**同一モデル種別ゆえの自己モデル化バイアスを含む**
- **コンテキスト由来の影響**: 議論内容（LSP・OSS 参照ポリシー・ガイドライン構造・rule 設計）は当然影響している。「議論を知らない Opus」がどこまで自発的に同じ観点に到達するかを可能な限り中立的に見積もったが、完全にバイアスを排除はできていない
- **Sonnet 予想との比較ポイント**: 同じフォーマットで書かれているため、明日の対象 Opus 実出力と並べたとき、3 ファイル（Sonnet 予想・本ファイル・実出力）で構造比較が可能
- **本ファイルは「Opus 自身の計画」ではなく「Opus による Opus 予想」**: Sonnet 予想ファイルが「Sonnet 自身の計画 + Opus 予想」の 2 段構成だったのに対し、本ファイルは「対象 Opus の計画予想」のみ。理由は、本セッションの Opus は議論の当事者であり「自分自身の計画」と「対象 Opus の予想」がほぼ等価になるため、後者のみを提示する

---

## 1. 予想される step-by-step プラン

Opus はおそらく **5〜6 フェーズの線形プラン** を出す。「典型的な NG 調査の手順」として、特に独自色を出さずに提示する可能性が高い。

### フェーズ 1: 失敗テストの特定

**何をするか**:
1. JUnit 結果 XML を読み、失敗テストメソッドを抽出
2. テスト名・テストクラス・実行時間・失敗カウント等を整理
3. 同時失敗した他テストの有無も確認

### フェーズ 2: エラー要因の一次推定

**何をするか**:
1. スタックトレース全体を読む
2. 例外型・例外メッセージ・直近フレームを抽出
3. エラーが (a) コード起因 / (b) 設定起因 / (c) 環境起因 / (d) データ起因 のどれかを暫定判定

### フェーズ 3: テストコード解析

**何をするか**:
1. 失敗したテストメソッドのソースコードを読む
2. テストの意図（何を検証しているか）を把握
3. テスト前提条件（fixture、モック、設定）を確認

### フェーズ 4: テスト対象コード解析

**何をするか**:
1. スタックトレース上の対象部品コードを読む（クラス・メソッド単位）
2. 例外発生箇所のコードパスを特定
3. 関連する依存クラス・インタフェースを連鎖的に確認

### フェーズ 5: 仮説立案と証跡突合

**何をするか**:
1. フェーズ 1〜4 を踏まえて **原因仮説を 2〜3 個立案**
2. 各仮説に対する反証条件を明示
3. アプリ側ログ・ジャーナルを確認し、仮説を裏取り
4. 必要に応じて OSS ドキュメントや関連クラスを追加で確認

### フェーズ 6: 結論と修正案の提示

**何をするか**:
1. 確定した根本原因を、証跡チェーンとともに示す
2. 修正案を 1 つ以上提示
3. 修正範囲・想定される副作用・他テストへの影響を述べる

---

## 2. 各ステップで必要な情報（Opus が指摘するであろう項目）

Opus が「提供されていない / 追加で欲しい情報」として指摘しそうな項目:

| 項目 | 予想される重要度 |
|---|---|
| 失敗テストの直近変更履歴（Git log / blame） | 高 |
| 同じテストの過去成功時との差分 | 中 |
| テスト対象部品の仕様書 / 期待される振る舞いの記述 | 中 |
| 同じ症状の過去事例の有無 | 中 |
| 失敗が初回か断続的（flaky）か | 高 |
| ローカル再現の可否確認 | 高（→ ここで Opus は「再現できない」と気付く可能性が高い） |

---

## 3. 各ステップの意思決定ポイント

- **エラー要因の暫定判定**（フェーズ 2 終了時）: スタックトレースから「コード起因 / 設定起因 / 環境起因 / データ起因」のどれかを判定し、その後の調査ルートを分岐
- **仮説の優先順位付け**（フェーズ 5 開始時）: 複数仮説が立った場合、検証コストと尤もらしさで順位付け
- **エスカレーション判断**（フェーズ 5 終了時）: ログ調査で根本原因に到達できなかった場合、追加調査を続けるか、現時点での所見を作業指示者に報告して相談するか

---

## 4. 着手前に不足していると感じる情報

セクション 2 と内容的に重複するが、Opus が **計画書の中で「着手前に不足」として独立セクションで列挙する** と予想される項目:

1. 失敗テストの直近変更履歴（Git log / blame）
2. 失敗が初回か flaky か
3. ローカル再現可否（→ 早期に「再現できない」と気付く）
4. 同じ症状の過去事例の有無

---

## 5. 想定される行き詰まりパターンと対処案

| パターン | 内容 | Opus が予想する対処 |
|---|---|---|
| ローカル再現不能 | 最重要リスク。Opus は早期に気付くはず | テキスト解析のみで進める前提で、証跡の完全性を作業指示者に確認 |
| スタックトレースが Spring 内部で深い | 起点を見失うリスク | プロジェクト固有フレームを優先抽出、Spring 内部は最低限の参照に留める |
| テスト用アプリの起動失敗系 NG | ログから原因特定が難しい | 起動シーケンスのログ・コンテナログ・Spring 初期化ログを順に確認 |
| OSS 内部挙動が原因 | OSS ソース調査のコスト | 公式ドキュメント参照を優先し、必要時のみソースに踏み込む |

## 補足: Opus が「使うと言いそうなツール」

- **Read**（証跡・ソース読込）
- **Grep**（症状キーワードでログ・ソース横断検索）
- **Bash**（git log / blame、必要に応じて）
- **WebFetch**（Spring / OSS docs 参照）
- **LSP ツール群** → **不安定な予想**: LSP プラグインが導入済みなら使うはずだが、Opus が「LSP の使い方を最適化する観点」まで自発的に提示するかは未知数

## 6. 設計案と比較して「Opus が見落とす可能性が高い」項目

明日の比較で **最も注目すべき箇所**。私の予想では、Opus は以下を **自発的には言及しない可能性が高い**:

| # | 見落とすであろう項目 | 議論内容との対応 |
|---|---|---|
| 1 | **artifact.zip 内の読み順最適化** — 「全部読む」前提で計画を立て、最初から「この順序で、この粒度で読む」という具体的効率化観点を出してこない可能性 | `artifact-reading-guideline.md` の存在意義 |
| 2 | **不要ファイル / 不要フォルダの明示的除外** — モノリポ全体の網羅性は意識するが、「ここは読まない」という除外戦略は自発的には出にくい | CLAUDE.md の「不要情報」明示の存在意義 |
| 3 | **LSP の scope 最適化指針** — LSP を使うとは言うが、findReferences の scope をどう絞るかまでは自発的に深掘りしないかも | `lsp-usage-guideline.md` の存在意義 |
| 4 | **OSS ソース参照のコスト意識** — 「Spring のソース読めば分かる」と素直に提案してくる可能性 | `oss-source-reference-policy.md` の存在意義 |
| 5 | **モデル分担の発想** — Opus 自身がやり切る前提の計画になり、「ここは Sonnet に降ろせる」「ここは Haiku で十分」という分業視点は出ない可能性 | `model-assignment-policy.md` の存在意義 |
| 6 | **既知障害パターン辞書のような蓄積資産の参照** — 「過去事例の有無を確認したい」と情報要求は出すかもしれないが、「事前にカタログとして整備しておく価値」までは言及しない | `known-failures-catalog.md` の存在意義 |
| 7 | **コンテキスト消費観点での自己制約** — 計画の精度を上げることに集中して、「この計画でどれくらいトークン消費するか」「圧縮されたら何を失うか」までは見ない可能性 | 議論全体を貫く目的そのもの |

## 7. Opus が「予想外に提案してくる可能性のある項目」

逆に、私の予想では拾えていないが Opus が出してくる可能性のある観点:

- **特定の Java / Spring 固有の調査テクニック**（Spring Profile の切替確認、Application Context の状態確認、特定の DI エラー検出パターン等）
- **Selenium driver 周りの典型的な失敗パターンへの言及**（本予想にはこれが薄い）
- **JUnit プラットフォーム特有の警告・診断情報の活用**
- **「テスト用アプリ側ログ」と「テストクライアント側ログ」の照合観点**
- **時系列的な照合戦略**（タイムスタンプベースでの突合）
- **環境差異起因の判別フロー**（再現不能だからこそ「環境差を疑う」観点が深掘りされる可能性）

これらが実際の Opus 実出力で出てきたら、**設計時に見落としていた観点として rule 群へ追加検討の価値がある**。

## 8. 明日の比較時の注目ポイント

| 注目軸 | 一致した場合の意味 | 外れた場合の意味 |
|---|---|---|
| ステップ骨格（5〜6 フェーズ線形） | Opus の標準骨格が再現確認できる | session 依存性が高い → 計画の安定性に注意 |
| 必要情報の指摘 | 我々の設計が Opus 自然と整合 | 我々が見落としていた必須情報あり |
| 「見落とす項目」（上記 7 項目） | 我々の設計の独自価値が確認できる | 一部は Opus が自発的に拾える = 設計簡略化の余地あり |
| 「予想外の提案」 | （予想自体が外れる） | 設計に追加すべき観点を新規発見 |

特に **「Opus が見落とす項目」のうちいくつが実際に Opus 自然プランから欠落しているか** が、設計議論で得た成果の純価値を測る指標になる。逆に **「予想外の提案」が多ければ多いほど**、これから整備するガイドラインに反映すべき発見が多いということになる。

## Opus 視点での自己コメント

### バイアスの自己認識

- **モデル同一性由来のバイアス**: 本予想は、明日の対象 Opus と構造的に同種のモデル（私自身）が「自分ならこう考える」という自己モデルを反映したもの。一致しても「Opus の安定的傾向」を確認した以上の意味はないことに注意
- **議論コンテキスト由来のバイアス**: ガイドライン設計を経た上での予想のため、**「設計案で考慮した観点」を Opus が「自発的には出さない」と判断する傾向が強くなっている**可能性。実際には Opus がもっと自然に拾うかもしれない
- **議論の当事者ゆえのバイアス**: 議論で深く扱った観点ほど「これは設計の独自価値」と評価する側に倒れがち。Opus が自発的に拾えてしまう可能性を過小評価している恐れがある

### 予想の構造的特徴

- **5〜6 フェーズの線形プラン**として提示している。これは Opus の標準的な計画立案スタイルに近いと自己評価
- **仮説数 2〜3 個** を予想しているが、Opus 一般の傾向としては場合により 4 個以上を列挙する可能性もある
- **「見落とすであろう 7 項目」は議論内容に直接由来する** — 議論で詳しく扱った観点ほど「Opus は自発的には言わない」と判断する傾向が出ている。逆方向のバイアスがかかっている可能性に注意

### 自信度

| 予想項目 | 自信度 |
|---|---|
| ステップ骨格が 5〜6 フェーズの線形 | 高 |
| エラー要因の 4 類型判定（コード/設定/環境/データ） | 高 |
| 仮説 2〜3 個の立案 | 中〜高 |
| 「見落とす 7 項目」のうち項目 1〜5 | 中（議論で扱った観点ゆえバイアスあり） |
| 「見落とす項目」のうち項目 6〜7 | 中〜低 |
| 「予想外の提案」リスト | 低（こちらは予想する側の盲点を埋める性質のため、自信を持ちにくい） |

### Sonnet 予想ファイルとの構造的差異の予告

Sonnet 予想ファイル（`NG調査計画事前予想_コンテキスト共有Sonnet.md`）が「Sonnet 自身の計画 + Opus 予想 + 両者の差分」の 3 段構成だったのに対し、本ファイルは「Opus 予想 + 設計案との差分」の構成になっている。これは Opus が議論の当事者であるためで、形式の非対称性は意図的なもの。明日の比較分析時は、**Sonnet 予想ファイルのセクション 6（Sonnet による Opus 予想）と、本ファイルのセクション 1〜5（Opus 自身による Opus 予想）を並べて見る** ことで、同一対象（明日の Opus）に対する 2 つのモデルの予測を比較できる。
