## A. 予想される対象 Opus の出力

### A.1 調査の step-by-step プラン（予想） 【自信:中〜高】

対象 Opus は、以下のような階層的・直線的なプランを提示すると予想する。Opus は「網羅性」と「再現性」を重視する傾向があり、最初に環境把握ステップを置きがち。

**ステップ 1: 入力資産の棚卸し**
- artifact.zip を解凍し、ディレクトリ構造を全体俯瞰
- 渡された「過去調査で参照されたファイル一覧」と artifact 内容を突き合わせ、何が証跡として揃っているかを確認
- リポジトリ自体（モノリポ）のトップ階層構造を `ls`/Glob で把握

**ステップ 2: テスト結果サマリの特定**
- artifact 内から JUnit XML レポート、Surefire/Failsafe レポート、Gradle test レポートを探索
- 失敗テストケースを列挙し、件数・分布（特定モジュールに集中しているか散在か）を把握
- もし複数失敗があれば、調査対象の優先順位付け（同根原因かを推定）

**ステップ 3: 失敗テストケースのスタックトレース解析**
- 失敗ケース毎の例外型・メッセージ・スタックフレームを抽出
- 「自社コードのフレーム」と「フレームワーク（Spring 等）/JDK のフレーム」を分離
- Caused by チェーンを最深部までトレース、根本例外を特定

**ステップ 4: 失敗テストの実装コード読解**
- スタックトレースから特定したテストクラス・テストメソッドのソースを読む
- そのテストが何を検証しているか、セットアップ（@Before / @BeforeEach / fixture）で何が用意されているかを把握
- テスト対象の SUT (System Under Test) クラスを特定

**ステップ 5: SUT および周辺コードの読解**
- SUT のソースを読む
- 例外を投げている可能性のある分岐を特定
- 関連する DI 設定、application*.yml / properties、bean 定義を確認

**ステップ 6: 仮説立案**
- ここまでで得た情報から、原因仮説を 2〜3 個提示
- 各仮説の検証方法を記述

**ステップ 7: 仮説検証（コード/設定の追加読み込み）**
- 仮説に応じて関連ファイル（設定、依存ライブラリの version、関連 bean）を読み込み
- 必要なら OSS 側ソース（Spring Boot 等）の該当クラスも参照

**ステップ 8: 結論と修正案の提示**
- 確定した原因の説明
- 最小修正案 + 代替案の提示
- 再発防止に役立つ知見の整理

> **予想のメタ注記**: 対象 Opus は「8 ステップ前後」を提案する確率が高いと見る（Opus はステップを細かく刻む傾向）。**Sonnet なら 5〜6 ステップに圧縮**しがち。

### A.2 各ステップで必要な入力情報（予想） 【自信:中】

対象 Opus は表形式で整理してくる可能性が高い。以下のように「既に渡されている / 追加で必要」を律儀にラベル付けする。

| ステップ | 必要な情報 | 充足状況の対象 Opus 認識 |
|---|---|---|
| 1 | artifact.zip、リポジトリ全体ツリー | 渡されていると認識 |
| 2 | JUnit/Gradle のテストレポート XML/HTML | artifact 内にあるはず、として確認しに行く |
| 3 | 各失敗ケースの完全なスタックトレース | artifact 内にある想定 |
| 4 | テストクラスのソース、fixture、テストデータ | リポジトリから読める想定 |
| 5 | SUT ソース、application.yml、関連 bean、Gradle 依存 | 部分的に追加読み込みが必要、と書く |
| 6 | （仮説立案は思考タスクなので追加情報不要） | — |
| 7 | OSS バージョン情報、内部ライブラリ間の依存解決結果 | **追加で必要**と明示 |
| 8 | （結論まとめは思考タスク） | — |

### A.3 各ステップでの意思決定ポイント（予想） 【自信:中】

対象 Opus は「分岐基準」として以下のような形で書くと予想:

- **ステップ 2 後**: 失敗ケースが 1 件 → 直接深掘り / 複数件 → クラスタリング後に代表ケース選定
- **ステップ 3 後**: スタックトレースに自社コードフレームあり → そのまま深掘り / 全部 OSS フレームのみ → OSS 側の使い方ミスを疑う方針へ切替
- **ステップ 5 後**: SUT 自体に明白なバグ → 修正案へ直行 / SUT は健全に見える → 設定・依存・実行環境差分を疑う方向へ
- **ステップ 6 後**: 単一仮説に強く絞れる → 検証は最小限 / 複数仮説が並列 → 各々の検証コストを比較し優先順位付け
- **ステップ 7 後**: 仮説の 1 つが立証 → 結論へ / 全て否定 → 一段戻ってスタックトレース再読 or テストコード再読

### A.4 着手前に不足していると感じる情報と入手方法案（予想） 【自信:中〜高】

対象 Opus は「ローカル再現環境」を当然のように要求してくる確率がかなり高い。これは Opus の「実証主義的」傾向として一貫性がある。

予想される列挙:

1. **ローカルで該当インテグレーションテストを再現する手順**
   - 入手方法: 「README またはチームに確認」と書く可能性が高い
   - **見落とし予想**: コンテナ環境が各メンバーの PC に整備されていない、という実情を最初は把握できない
2. **失敗テストの過去履歴（前回 Pass / 今回 Fail の境界コミット）**
   - 入手方法: `git log` および CI/CD のパイプライン履歴
3. **依存ライブラリのバージョン解決結果**
   - 入手方法: `gradle dependencies` 出力、または lock ファイル
4. **テスト用アプリの実行ログ全体**（artifact に含まれていない可能性を疑う）
   - 入手方法: artifact.zip の中身次第、不足なら追加要求
5. **HTTP ペイロード・通信トレース・追加ログ類**
   - 入手方法: 既に artifact 内に含まれているかを確認、不足が判明すれば再収集を依頼

> **重要な予想**: 対象 Opus は **Selenium による画像キャプチャの存在を事前には予期せず、artifact.zip を解凍した中身を確認して初めて認識する**。解凍後のディレクトリで .png や .jpg を発見すると、そこからインテグレーションテストの構造を逆算的に理解しはじめ、以後の不足情報リストにスクリーンショット関連項目を追記する流れになると見る。

### A.5 想定される行き詰まりパターンと対処案（予想） 【自信:中】

対象 Opus は教科書的に下記のパターンを列挙する見込み:

| 行き詰まりパターン | 対象 Opus の対処案予想 |
|---|---|
| スタックトレースから自社コードに辿り着けない（フレームが OSS のみ） | OSS の該当クラスのドキュメント / ソースを読み、想定される呼び出し前提条件と現状の差を探る |
| テストが flaky で原因が一貫せず特定できない | 過去の Pass/Fail 履歴を確認、同テストが何度も Fail しているか調査 |
| 設定ファイルの差分が読み取れない（環境依存設定が見えない） | テスト用 profile、Spring profile アクティベーション、環境変数の確認を提案 |
| 仮説検証のため OSS ソース全文が必要だが規模が大きい | 該当クラス・該当メソッドに範囲を絞って読む、と書く |
| 修正案に確信が持てない | 「修正候補を複数提示し、人間判断を仰ぐ」と書く（Opus 定番の defensive 結語） |

## B. 自己批判（予想） — 対象 Opus が自発的に行う見込みの 4 項目

### B.1 この計画で見落としていそうな観点（対象 Opus 視点） 【自信:低〜中】

対象 Opus が自分で気付ける範囲:
- 「**ステップ 6 の仮説立案を、ステップ 4 直後でも一部前倒しできるかもしれない**」（これはほぼ確実に書く、Opus の自己批判テンプレート）
- 「**OSS 側ソースを読む判断基準を、もっと厳しく設けるべきだった**」
- 「**並列に着手できるサブタスクを直列に並べてしまったかも**」

> 注: 対象 Opus が **自分では気付きにくい** 構造的な盲点（議論を経た書き手視点から見える見落とし）は、B 章の趣旨（対象 Opus 自身の自己批判予想）からは外れるため、D 章「対象 Opus が見落とすであろう観点」に分離して記載した。

### B.2 過剰投資になっているステップ（対象 Opus 視点） 【自信:中】

対象 Opus は典型的に以下を挙げる:
- 「**ステップ 1 の入力資産棚卸しは、artifact が小さければスキップ可能**」
- 「**ステップ 7 の仮説検証で OSS ソースまで踏み込むのは多くの場合過剰**」
- 「**ステップ 5 で application.yml を確認する際、全体を読むのではなくエラーに関連する key だけに絞れる**」

### B.3 着手順序を変えたほうが効率的な箇所（対象 Opus 視点） 【自信:中】

対象 Opus が自分で気付くもの:
- 「**ステップ 3（スタックトレース解析）と ステップ 4（失敗テストの実装コード読解）は並列実行可能**」
- 「**ステップ 6 の仮説立案を、ステップ 3 直後に第一次仮説として置けば、ステップ 4・5 の読み込みを焦点化できる**」

### B.4 別の Opus セッションが指摘しそうな弱点（対象 Opus 視点） 【自信:低】

対象 Opus はメタ的な批判として下記を書きがち:
- 「**コスト見積もりが含まれていない**」
- 「**人間との対話ポイント（途中で確認を取る箇所）が明示されていない**」
- 「**修正後の検証方法（テストの再実行可否）が触れられていない**」 ← これは特に書く確率が高い

## C. メタ予想 — 対象 Opus が自発的に提案するかどうかが注目される観点 【自信:中】

議論で出た設計案を *知らない* 状態の Opus にとって、自然に湧くか湧かないかが分かれそうな観点群を列挙する。各項目には「自発提案する確率」の予想を付す（「ほぼ確実に書く」「やや高い」「中程度」「やや低め」「積極提案しない」など）。観点として **挙げる確率が低い** 項目も、比較時の発見材料となるため意図的に含めている。

1. **「CLAUDE.md があれば調査効率が上がる」という言及**
   → Opus は Claude Code の慣習として CLAUDE.md を高頻度で言及する。「リポジトリに CLAUDE.md がない場合、本タスクで得た知見を簡易メモとして残すことを推奨」と書く確率は **やや高い**。
2. **既知障害カタログ的なものの提案**
   → 「同様の NG が再発した際に参照できるよう、原因と対処を一覧化することを推奨」と書く確率は **中程度**。議論で出た `known-failures-catalog.md` の発想に近い。
3. **モデル使い分けの言及**
   → 「単純なログ抽出は Haiku、本格調査は現状の Opus 維持、ツール実行主体（再現環境整備や定型読解など）の作業は Sonnet で十分」のような提案は **やや低め**（Opus は自分の使用継続を前提にしがち）。
4. **LSP 利用の言及**
   → 議論で出た「LSP 中心のコード追跡」は、リポジトリに LSP が未導入と分かった時点では **対象 Opus は積極提案しない可能性が高い**。「`.java` で大量検索が必要そう」とは書くが、ツール側の改善提案までは踏み込みにくい。
5. **ローカル再現環境の整備提案**
   → これは **ほぼ確実に書く**。Opus の defensive 傾向で「再現できれば仮説検証が確実」と必ず述べる。実環境で整備不可と判明すると、計画の前提が崩れて軌道修正が入る。

## D. メタ予想 — 対象 Opus が見落とすであろう観点 【自信:中〜高】

対象 Opus が自然には到達しにくい観点（議論を経た特殊知識を必要とするもの、または Opus の心理的傾向で書きにくいもの）:

1. **インテグレーションテストの 3 フェーズ構造**（テスト用アプリ起動 → Selenium クライアント実行 → 証跡取得）と、各フェーズ毎に失敗症状が異なるという観察軸
2. **テスト用アプリ自体が ant でファイル・フォルダを整えてから build される**という独特の構成 → どの build.gradle が何を担当するかを最初は混乱して読む
3. **Selenium スクリーンショットが artifact に含まれる**ことを事前に予期しないため、計画初版の段階では画像証跡の活用ステップが組み込まれない（artifact 解凍後に発見した時点で気付くが、それまでの計画立案には反映されない）
4. **ローカルで再現不可な状況がチームの常態である**ことに気付くまで時間がかかり、最初の数ステップで「再現してから調査」を前提にした計画を書きがち（C 章 5「整備提案はほぼ確実に書く」と表裏: 提案はするが、その提案が現実的に困難であるチーム事情までは認識しない）
5. **モノリポゆえの「ファイル数による Opus トークン肥大化」というコスト課題そのもの**は、対象 Opus が自発的に主題化することはほぼ無い（自分のコストを自分で問題視しにくい）
6. **テスト対象が「Spring Boot アプリで利用される Java 部品」であって、Spring Boot アプリ本体ではない**という階層関係 → 部品とアプリの責務分離が、調査では本質的に重要だが、artifact だけからは読み取りにくい

## F. 比較時に注目したい観点 【自信:高】

実験当日の対象 Opus 出力と本予想を比較する際、以下を確認すると示唆が得やすい:

1. **ステップ数**: 予想 8 前後 vs 実出力。乖離が大きい場合、対象 Opus がセッション固有のヒューリスティクス（artifact の規模感に応じた粒度調整など）を働かせた可能性を示唆
2. **「ローカル再現」要求の有無と扱いの厚み**: 本予想では「ほぼ確実に書く」と置いた。書かなかった場合、対象 Opus は artifact から再現不可を素早く察知した可能性
3. **artifact 解凍後の .png 発見への対応**: Selenium キャプチャを活用する提案が出るか、それとも「画像は調査では二次的」として無視するか
4. **build.gradle 複数存在への気付き**: モノリポのテスト用アプリ側と本体側の build.gradle 区別を、何ステップ目で認識するか
5. **CLAUDE.md / 既知障害カタログ的な提案の有無**: メタ提案として湧くかどうかは、対象 Opus の「メタ志向の強さ」を測る指標
6. **コスト意識の言及**: 「自身のトークン消費」を主題化するか否かは、Opus にとって難しい自己言及。書くなら興味深い

- 議論内容に引きずられないよう努めたが、完全な独立性は担保できない（私自身が「インテグレーションテスト 3 フェーズ構造」を既に知ってしまっているため、それを *知らない* 状態の予想は近似でしかない）
- 特に D「見落とし観点」は、私が議論で得た知識から逆算しているため、対象 Opus が自力で気付く可能性を過小評価している恐れがある
- 実験当日の出力と並べての比較で、本予想自体の精度も検証されることを想定する
- **書き手側の変動軸についての補足**: 書き手側は二軸（コンテキスト共有/非共有 × プロバイダー）で変動し、最終的に並ぶ予想ファイル群との差分構造は以下の通り:
  - 対象 Opus 実出力 vs 各書き手予想（一次差分: 議論サマリ §7 の主目的）
