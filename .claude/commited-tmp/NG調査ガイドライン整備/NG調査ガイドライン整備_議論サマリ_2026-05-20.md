# Claude Code NG 調査ガイドライン整備 — 議論サマリと実験プロトコル

2026-05-19〜2026-05-20 にかけて行われた、Claude Code でのインテグレーションテスト NG 調査の効率化に関する設計議論のサマリ。別セッション（Sonnet または Opus）で、2026-05-21 に実施予定の実験において、対象 Opus が産出する計画を予想してもらうための前提情報として用いる。

---

## 1. 背景と目的

### 1.1 利用環境

- ある Java 部品開発チームが、Claude Code を用いたソフトウェア開発支援を活用し始めた段階（運用開始 1〜2 ヶ月）
- 対象リポジトリ: Java 部品（Spring Boot ベースのアプリケーションで利用される）のモノリポジトリ
- 対象作業: 自動テストの失敗（以下「NG」）の原因調査・解消方法提案

### 1.2 現状の課題

- NG 調査の指示を Claude Code（Opus）に出すと、**異常にトークンを消費する**
- 想定される直接原因: モノリポゆえのファイル数・フォルダ数・階層の多さ。NG 原因特定のために多くのソースコード・設定ファイルを読み込むことになる
- 結果として、コスト面で実用継続が難しくなっている

### 1.3 議論のゴール

- NG 調査の効率化に向けた施策を、コスト対効果が高い順に整理し、当面の取り組み方針を決める
- 具体的な成果物: CLAUDE.md と `.claude/rules/` 配下のガイドライン群の設計と段階的整備計画

## 2. 対象環境の特性

### 2.1 リポジトリ構造

- Gradle ベースのモノリポジトリ
- 多数のサブプロジェクトで構成
- 一般的なモノリポと比較して **非常に癖のある作り**（独自色が強い慣習・構成を含む）
- 通常の Gradle ビルド・ユニットテストは正常に実行可能

### 2.2 インテグレーションテストの仕組み（重要）

NG 調査の対象となるテストは、ユニットテストとは大きく異なる **複雑な独自インテグレーションテスト** である:

1. **テスト用アプリ起動フェーズ**: テスト用に起動したコンテナ上で、テスト対象の部品を実際に使った疑似アプリケーション（テスト用アプリ）を、ant タスクでファイル・フォルダ構成を整えた上で、インテグレーションテスト専用の build.gradle でビルド・起動
2. **テストリクエスト送信フェーズ**: 起動したテスト用アプリへ、テストケースに沿ったリクエストを送信するための **Selenium driver を使った JUnit プラットフォーム動作のクライアントコード** を、専用の build.gradle で実行（ユニットテストと類似の動作形式）
3. **証跡取得フェーズ**: テスト送信完了後にテスト用アプリを停止、ログ・ジャーナルを取得。テスト中に Selenium がキャプチャした画像スクリーンショットと合わせて、パイプライン成果物（artifact.zip）として保存
4. 全テストケースが終わるまで 1〜3 を繰り返し

この仕組み全体は **GitLab パイプラインで実行される前提** で組まれており、テスト実行〜結果レポート出力〜証跡取得まで自動化されている。

### 2.3 Claude Code 実行環境の制約

- 各メンバーのローカル PC では、上記インテグレーションテストを実行するためのコンテナ環境が **基本的に整備されていない**
- 結果として、Claude Code は **NG を再現できない状態で原因調査を行う**
- 調査の実態（推定）: スタックトレース等のエラー証跡、NG 発生テストケースのテストコードと設定ファイル（アプリ側 / クライアント側両方）、対象部品のソース、利用 OSS（Spring Boot 等）のドキュメント・ソース、これらを **テキスト的に解析する作業がほとんど**

### 2.4 現状のドキュメント整備状況

- CLAUDE.md がリポジトリ内に存在しない（Claude Code の活用開始から日が浅いため、まだ整備されていない）
- LSP プラグイン（jdtls 等）は未導入。導入予定

## 3. 設計したドキュメント体系

### 3.1 役割分担の基本方針

**LSP プラグイン（特に jdtls）と CLAUDE.md / `.claude/rules/` の役割分担**:

- **LSP**: コード追跡（go to definition / find references / type hierarchy 等）。Anthropic 公式は「grep + 複数ファイル読み込み」の置き換えとして LSP プラグインを位置付けている
- **CLAUDE.md**: リポジトリ構造のナビゲーション情報（モジュール一覧、横断機能、build.gradle 群の責務、モノリポ固有の癖、`.claude/rules/` 配下への目次）
- **`.claude/rules/*.md`**: NG 調査の進め方ガイドライン群。`paths:` frontmatter で条件付きロード可能（Anthropic 公式機能）

### 3.2 想定する `.claude/rules/` 配下のファイル群

| ファイル名 | 主な内容 | ロード方式（暫定） |
|---|---|---|
| `integration-test-investigation-overview.md` | NG 調査全体フローの骨格、各フェーズで参照する rule へのリンク | 常時ロード |
| `artifact-reading-guideline.md` | artifact.zip の構造、最初に読むべき順序、選択的読み込み指針 | 条件付き（artifact 系パス） |
| `stacktrace-analysis-guideline.md` | スタックトレースの効率的読み方、優先フレーム判定 | 条件付き（.log / トレース系拡張子） |
| `lsp-usage-guideline.md` | LSP 各コマンドの使い分け、scope 最適化、findReferences 暴走防止 | 常時ロード |
| `known-failures-catalog.md` | 既知の障害パターン辞書（症状→原因→対処）。最初は空、運用で蓄積 | 常時ロード |
| `oss-source-reference-policy.md` | OSS 情報は LSP hover を最優先、公式 docs、最終手段でソース全文 | 常時ロード |
| `model-assignment-policy.md` | 各サブタスクへの推奨モデル（Opus / Sonnet / Haiku）と判断基準 | 常時ロード |

### 3.3 CLAUDE.md に残す内容（rule に切り出さないもの）

- モジュール一覧と一行説明
- 主要な横断機能マップ
- build.gradle 群の責務マッピング（テスト用アプリ側 / テストクライアント側 / 部品本体側）
- モノリポ固有の癖の暫定リスト
- `.claude/rules/` 配下ファイルの目次（ロード条件付き）

## 4. 段階的な整備計画

**Phase 1（着手 1〜3 日目、人間単独で書ける土台）**:
- CLAUDE.md 初版
- `integration-test-investigation-overview.md` 骨格
- `known-failures-catalog.md`（空テンプレート）
- `oss-source-reference-policy.md`

**Phase 2（4〜10 日目、Claude との対話で精度を高める）**:
- `artifact-reading-guideline.md`（実調査を通じた振り返りベース）
- `stacktrace-analysis-guideline.md`（代表的トレース複数種に対する解析対話）

**Phase 3（LSP プラグイン導入後）**:
- `lsp-usage-guideline.md`（LSP を使った実調査経験ベース）

**Phase 4（運用継続フェーズ）**:
- `known-failures-catalog.md` への継続的追記
- 全 rule の継続的 refine

## 5. モデル分担方針

- **ガイドライン整備期間**: Opus が実作業を担当（書き出し・自己批判・refine）
- **本格運用期**: Sonnet を主担当、推論深度が必要な場面で Opus にエスカレーション
- **単純検索系（OSS docs の WebFetch 等）**: 場合により Haiku
- **Opus が書いたガイドラインは Sonnet で動作検証** するステップを Phase 2 以降に組み込む（モデル間ギャップの検出）
- 具体的なモデル割り当ては、Opus に判断基準（コスト / 性能 / フォールバック / 作業規模）を整理させて `model-assignment-policy.md` に明文化する

## 6. 2026-05-21 実施予定の実験

### 6.1 実験の目的

本議論で設計したガイドライン体系を実環境に適用する前に、**Opus が標準的な NG 調査依頼を素のまま受けたら、どんな計画を立てるか** を観測する。設計議論で得た想定と Opus の自然発想の差分から、(a) 設計案の独自価値の検証、(b) 設計案で見落としていた観点の発見、を目指す。

### 6.2 実施条件

- 既に原因特定済みの過去 NG 案件の証跡一式（artifact.zip、対象 Opus が参照したファイル一覧）を投入
- 既に運用で使用されている標準の NG 調査指示文を使用
- 当方（実験実施者）の環境では、過去 NG 調査経験の蓄積（Claude メモリ等）が少ないため、対象 Opus にとって新規性の高い依頼として処理される想定

### 6.3 対象 Opus に渡す指示の構造

標準指示文の末尾に、以下の指示を追加する:

> ただし、**今回は調査を実際には開始しないでください**。まず以下を文書として出力してください:
> 1. 調査の step-by-step プラン（各ステップで何をするか）
> 2. 各ステップで入力として必要な情報（既に渡されているか、追加で必要か）
> 3. 各ステップでの意思決定ポイント（次のステップに進むか別ルートを取るかの判断基準）
> 4. 着手前に不足していると感じる情報とその入手方法案
> 5. 想定される行き詰まりパターンとその対処案
>
> 出力後、以下の自己批判も実施してください:
> 1. この計画で見落としていそうな観点
> 2. 過剰投資になっているステップ
> 3. 着手順序を変えたほうが効率的な箇所
> 4. 別の Opus セッションがこの計画を見たら指摘しそうな弱点

### 6.4 比較の構造

実験では、以下の観測点を比較する想定:

1. **対象 Opus の実出力**（本実験の主データ、2026-05-21 に取得）
2. **当方（人間、議論参加者）の事前予想**（議論コンテキストありでの予想。実験実施前に作成）
3. **議論セッション内で対象モデル（Opus）が出した事前予想**（既に作成済み。**本サマリには意図的に含めない、別セッション予想を汚染しないため**）
4. **本サマリを受け取った別セッションでの予想**（本サマリの主用途。Sonnet / Opus 双方で実施想定）

これらの差分から、**ガイドライン整備で何を補強すべきか** を多角的に評価する。

## 7. このサマリを受け取った別セッションへの依頼

### 7.1 セッションが Sonnet の場合

以下の 3 点を出力してください:

1. **あなた（Sonnet）自身がこの NG 調査タスクを依頼された場合に立てる計画**（6.3 の指示構造と同じフォーマット: ステップ計画 / 必要情報 / 意思決定ポイント / 不足情報 / 行き詰まりパターン）
2. **同じ指示文と入力を Opus が受け取った場合に立てるであろう計画** の予想（同じフォーマット）
3. **自身の計画と Opus 予想の主要な差** 3〜5 点と、その差が生じる理由（モデル特性 / 推論深度 / 自信の置き方の違い等）

### 7.2 セッションが Opus の場合

以下を出力してください:

- **同じ指示文と入力を、本サマリの議論文脈を持たない別セッションの Opus が受け取った場合に立てる計画** の予想（2026-05-21 実施の対象 Opus 実出力に対する予想）
- 出力フォーマット: 6.3 に示した指示構造に対応（ステップ計画 / 必要情報 / 意思決定ポイント / 不足情報 / 行き詰まりパターン + 自己批判）

### 7.3 共通の留意点

- **予想は本サマリの議論内容に過度に引きずられないよう、「議論を知らない Opus がどう自然に発想するか」の視点で書く**
- **本サマリは設計案を含むが、実験当日の対象 Opus はそれを持たずに着手する**。よって予想時には、設計案の存在を意識しすぎないこと
- 予想とともに、「**どこで自信が高く、どこで自信が低いか**」を明示すると、後の比較精度が上がる
- 予想項目に「**実験当日の対象 Opus が見落とすであろう観点**」と「**逆に対象 Opus が自発的に提案してきそうな観点**」を含めると、比較で発見が得やすい

## 8. 補足: 本サマリの位置付け

- 本サマリは、議論コンテキスト無しでは作成困難な前提情報を、別セッションに最小限で渡すことを目的としている
- 本サマリには **議論セッション内で対象モデル（Opus）が既に出力した事前予想は含めていない**。これは別セッション予想の純度を保つための意図的な除外
- 本サマリの読み手が予想を作成した後、議論セッション内の事前予想と並べての比較が予定されている
