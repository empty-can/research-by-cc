  LSP が「テスト NG 調査」の文脈で特に効く理由

  自動テスト NG の調査で典型的に発生する探索は、おおむね次の流れです:

  1. テスト失敗時の例外/メッセージ → スタックトレースの メソッド名 から実装に辿る
  2. 当該メソッドの 呼び出し元/呼び出し先 を確認して影響範囲を絞る
  3. 関連クラスの 型・契約（インタフェース実装関係） を確認して期待挙動と差分を切り分ける

  これは LSP の go to definition / find references / type hierarchy / workspace symbol がほぼ 1:1 で答える領域です。Anthropic 公式が言う「a single 'go to definition' call replaces what might otherwise be a grep followed by

  2. ビルド設定（pom.xml / build.gradle）由来の問題 — 依存解決、テストランナー設定、プロファイル切替などが原因の NG は、LSP では追えません（XML LSP が無いのもここに効いてきます）。

  - 複数のビルドツールが混在（Maven + Gradle、または build script なしの素の Java ディレクトリ）するケース: jdtls の自動判定が外れて部分的な解析しかできないことがある
  - ビルドが通らない状態のリポジトリ: jdtls の解析能力が大きく劣化する

  - 代替手段の俯瞰 — lemminx（XML 用 LSP、Spring・XSD 認識あり）を .lsp.json で独自プラグイン化する選択肢が存在します。Claude Code 公式 docs :30888-30891 に「公式 LSP プラグインに無い言語は .lsp.json
  で自作できる」旨が明記されており、技術的にはハードルは低い。Skill 自作 vs LSP 自作プラグインのどちらが ROI 高いか は、上記の「実際の XML
  解釈ニーズ」の中身に依存します。構造的なナビゲーション（要素間ジャンプ、参照解決）が中心なら LSP のほうが向き、ドメイン特化の要約（「この Bean 定義に関わる依存関係を最小限で抽出」など）なら Skill のほうが向きます。

  1-a. オートコンパクション発火による振り返り精度低下への対策

  懸念は妥当で、特に「Context 消費に直接影響した作業前半」が真っ先に圧縮対象になるため、振り返りには致命的です。対策案を順に:

  PreCompact hook の活用は有効です

  Claude Code には PreCompact という hook イベントが存在し、自動コンパクション・手動 /compact の両方で発火します。ここで Skill / スクリプトを発火させ、現セッションのトリアージレポート（読み込んだファイル一覧 / NG 関連の暫定仮説 / 寄与度が低かったと感じる読み込み）を .md ファイルに書き出す設計は機能します。本リポジトリにも pre-compact Skill がすでに存在しており（メモリ最新化・未コミット変更確認・保留タスク整理）、同じ枠組みを「NG調査用の振り返りファイル出力」用途に拡張する形で展開可能です。

  ただし PreCompact だけに頼らない方が安全

  PreCompact は コンパクション直前 に走るため、その時点で Claude のコンテキストはすでに膨らみきっています。書き出すレポートの品質も多少劣化することが想定されます。より精度を保ちやすい補完策 を 2 つ:

  - 定期スナップショット方式 — 調査が一段進むたび（例: 「テスト ID 特定 → スタックトレース解析 → 怪しい呼び出し経路特定」の各節目）に Claude に短い進捗 .md を更新させる。Hook ではなく 明示的な作業ステップとして CLAUDE.md / Skill に組み込む ほうが、コンパクション圧縮の影響を受けにくい。
  - 「不要だった読み込み」を発生直後にマーキング — 調査の途中で Claude が「この Read は当たりではなかった」と判断した時点で、その情報を専用の log ファイルに追記させる Skill を用意。事後の振り返りに依存しないので、コンパクションが発生しても情報が失われない。

  実装容易性とコスト効率を踏まえると、PreCompact hook + 定期スナップショット の二段構え がバランスが良いです。事後質問のテンプレートに依存する設計より頑健になります。

  1-b. 振り返り質問テンプレートのレビュー

  提示された 2 つはどちらも 良い質問形式 です。配布前に微調整するなら:

  - 「ログ ○○ 行のうち寄与した行は何行か？」: 数字だけ返ってきても検証ができないので、「寄与した行範囲を <file>:<L 開始>-<L 終了> 形式で列挙してください」と出力フォーマットを縛ると、後で実ログと突き合わせ可能になります。
  - 「多用したツール・コマンド上位 3 つを減らすための事前情報 3 つを提供形態込みで挙げてください」: 良い形式です。さらに「提供形態の選択肢」を明示しておくと回答ブレが減ります。  
    例: — 以下の 4 択から選ばせる。  
      * (a) CLAUDE.md への記述
      * (b) 専用 Skill 化
      * (c) 事前生成のインデックスファイル
      * (d) Subagent ブリーフィングテンプレへの追加

  テンプレ全体のサイズ: 質問は 3〜5 個に絞る ほうが、回答者（Claude）も実施者（メンバー）も継続できます。「全部聞きたい」気持ちは抑えて、最も改善示唆につながる質問のみ を残すのがコツです。回答品質ベースで定期見直し（月 1 回など）するルールを併設すると、テンプレートが陳腐化しません。

● ご提示の整理は おおむね妥当ですが、各セクションで補足したい観点があります。順に。

  1. 何の地図を — 補足したい項目

  ご提示の必須①②と「迷い項目」の整理は方向として正しいです。ただ、LSP の効きを最大化する観点で、追加で必須に近い情報があります。

  追加で「必須①」相当として書いてほしい項目

  - テスト実行コマンド — 全テスト・単一テスト・モジュール単位テストそれぞれの実行 syntax（Gradle 特有の癖を含む）。これが無いと Claude は試行錯誤で gradlew の正しい呼び出し方を探す段階でトークンを消費します。
  - NG 調査の入口情報 — テスト実行時のレポート出力先（build/reports/tests/ 等）、ログ出力先、Spring 関連の追加ログ出力場所。「失敗したらまずここを見ろ」という最初の数手の指示。
  - モジュール間の依存・呼び出し関係の高位俯瞰 — 「モジュール A は B を呼ぶ、B は C を呼ぶ」程度の関係図。これは LSP の findReferences を 広すぎる範囲に投げない ための前提知識として効きます。LSP は個別のシンボル解決はできますが、「どのモジュールにスコープすべきか」という判断は CLAUDE.md 側のナビゲーション知識に依存します。
  - テストの命名規約 — *Test, *IT, *Spec などの分類規約があれば明記。Claude のテスト探索のキーワード選定精度が直接上がります。
  - モノリポ固有の癖 — ご自身でも「非常に癖のある作り」と認識されている部分。Claude が毎セッション再発見していると想定される事項を書き出すと、最も投資効率が高い項目になるはずです（前回の「振り返り質問テンプレ」のアウトプット先がここ）。

  「必須②」（除外情報）について

  ご提示のリストは妥当です。ただ補足を 2 点:

  - .git, .idea などの汎用メタフォルダは Claude が既に避ける傾向がある ため、わざわざ書く必要性は低いです。書くなら monorepo 固有で「うっかり見られると無駄が発生する」もの（テスト環境構成スクリプト、CI 設定、自動生成物の出力先など）に絞るほうが、CLAUDE.md のサイズ規律を保てます。
  - 「除外」より「なぜ除外か」を書く ほうが効果的です。Claude は「helpful になろうとする」傾向があるため、「除外」とだけ書くと、判断に迷ったときに consult してしまうことがあります。「これは X の理由で NG 調査に絶対に寄与しないので、絶対に読まない」という強めの表現と理由付けがあると、迷いが減ります。

  「迷い項目」（補足ドキュメント）について

  「条件付き必須」として記載する のがおすすめです。「常に読まなくてよい、ただし NG が X 系（外部仕様起因の挙動差異など）の場合は最初に Y を読め」という トリガー条件付きで書いておくと、無条件にロードされてトークンを食うことなく、必要なときだけ Claude が consult する形になります。

  2. どの粒度で

  「機能単位のパッケージ程度の粒度」という見立ては妥当です。さらに refine するなら:

  推奨粒度: 「サブモジュール + 横断機能」のハイブリッド

  - 基本単位はサブモジュール — 名前と一行説明（「これは何をするモジュールか」+「主要な責務」）
  - 横断機能は別ブロックで列挙 — ご指摘の「複数モジュールを横断する機能」は、サブモジュール一覧の中で表現しきれないので、別に 「主要な横断機能 → 関わるモジュール / パッケージ」のマッピング を持つ
  - パッケージレベルまで降りるのは、横断機能と「特に間違えやすい構造」の場合のみ — 全パッケージを羅列するのはトークンの無駄。LSP が補完できる粒度（個別クラス・メソッド）には踏み込まないのが鉄則

  判断基準は「LSP に渡す前段階で Claude が判断できる粒度か」

  CLAUDE.md の粒度のゴールは「Claude が LSP を呼ぶときに、どのスコープに対して呼ぶべきか判断できる」レベルです。それより細かいことは LSP が答えてくれるので CLAUDE.md には不要。それより粗いと LSP の呼び出しスコープが広すぎて結果が膨大になります。サブモジュール + 横断機能 は、ちょうどこのスイートスポットに来ます。

  3. どこに置くか — ルート直下 1 ファイル運用の現実性

  Git 操作と untracked ファイルの実挙動について（先に事実訂正を 1 つ）

  ▎ Git 操作によってファイルシステム上から消えるべきフォルダの中に Git 追跡対象外のファイルが存在すると(恐らく)Git 操作が失敗する？

  **正確には「失敗しない」が「綺麗にならない」**です。Git は untracked ファイルを保護 するため、ブランチ切替先にフォルダが存在しない場合でも、untracked ファイル（と、それを含むフォルダ）は 物理的に残ったまま になります。Git 操作自体は成功します。

  ただし、これが起きると次の問題が出ます:
  - 切替先ブランチには本来存在しないはずのフォルダが残り、見た目が混乱する
  - 切り戻すと untracked CLAUDE.md は元の場所に再度認識されるが、間にあったブランチでの作業中もそのフォルダ・ファイルが見えてしまう

  つまり「失敗する」ではなく「ノイズが残る」が正しい認識です。それでもサブフォルダに置く運用は煩雑なので、ルート直下 1 ファイル運用を当面採用する判断自体は妥当です。

  ルート直下 1 ファイルでも効果は十分に出ます

  サブモジュール単位の CLAUDE.md を持てないことのデメリットは「全サブモジュールの情報が常時ロードされてトークンを食う」点です。これを緩和する設計テクニックがあります。

  設計テクニック 1: 「インデックス + 章ファイル」構造

  - ルート CLAUDE.md は短いインデックスに徹する — モジュール一覧（一行説明）、横断機能マップ、調査入口、共通規約のみ
  - モジュール固有の深い情報は別ファイルに切り出す — 例えば .claude/docs/module-X.md（untracked、ルート直下 .claude/ 内なのでブランチ切替の影響を受けにくい）
  - ルート CLAUDE.md は「モジュール X の詳細は .claude/docs/module-X.md を参照」と書くだけ

  このやり方なら、毎セッションのロード量は最小に抑えつつ、必要なときだけ Claude が章ファイルを Read します。ルートだけで完結する 1 ファイル運用」ではなく「ルート 1 ファイル + .claude/docs/ 配下の untracked サポート群」というハイブリッド にすると、Git操作の懸念も回避できます（.claude/ フォルダはブランチ間で安定的に存在することを Claude Code 自身が想定しているため）。

  設計テクニック 2: CLAUDE.md は「読む順序」を明示する

  ナビゲーション地図として機能させるなら、書き方として次のような明示が効きます:

  - 「最初に読むセクション」と「条件付きで読むセクション」を明示 — Claude に「全部読むな、まずこのセクションを読め」と指示する
  - 意思決定ツリー風の記述 — 「NG が テスト ID + class.method 形式で特定できているなら X 節へ。スタックトレースが主たる手がかりなら Y 節へ」のような分岐記述
  - LSP の呼び方ヒント — 「findReferences は必ずモジュール X のスコープに絞ること（広域では結果が爆発する）」のような、LSP を効かせるための具体指示

  LSP プラグインの能力を持っていても、Claude がそれをどの粒度で呼ぶべきかを CLAUDE.md が誘導しないと、結果膨大 → 二次検索 → コンテキスト枯渇のパターンに陥ります。「LSP の使い方ガイドそのもの」を CLAUDE.md に書く のが、ナビゲーション地図のもう一つの本質的役割です。

  設計テクニック 3: 段階的に育てる前提を最初から組む

  ご提示の通り、当面は untracked 運用が現実的です。**「初版で完璧を目指さない」**を明示的にデザインに組み込むなら:

  - 「現状判明していない仕様・規約」セクションを設けて、空欄のまま置く — 振り返り質問で出てきた示唆を、ここに段階的に追記する場所として最初から確保
  - 「直近で変更された / 揺れている領域」セクション — 過渡的に揺れている情報を、安定情報と分けて管理。Git 管理に昇格する際は、揺れているセクションを抜く判断ができる

  結論: ルート 1 ファイル運用 + .claude/docs/ 補助の組み合わせを推奨

  整理すると、現実的な配置戦略は:

  - ルート直下に CLAUDE.md — インデックス + 調査入口 + LSP 利用ガイド + 既知の癖。トークン規律を意識した短さ
  - .claude/docs/ 配下に untracked のサポート章ファイル — モジュール固有の深い情報、横断機能の詳細、調査チェックリスト等。.claude/ はブランチ切替に対して比較的安定的に扱われる

  この構成なら、Git 操作の懸念を回避しつつ、ナビゲーション地図としての効力を最大化できます。

そして、Claude Codeが起動される通常メンバーのローカル環境では、コンテナを起動するための環境は基本的に整っていません。

よって、Claude CodeはNG解消を指示された際に、ユニットテストのNG解消の場合とは異なり、自分でNGを再現させながらの調査作業はできない状況です。  
ここからは、NG解消の指示を受けたClaude Codeが、NGの原因を特定し解消方法を提示するまでに実際に行っている作業を確認していないため断言できませんが、恐らくスタックトレースなどのエラー証跡と、NGが発生したテストケースのテストコードと設定ファイル（テストアプリ側、テストクライアント側両方）、そして部品のソースコードと部品が利用しているOSS（Spring Bootなど）のドキュメントやソースコードをテキスト的に解析するという作業がほとんどであると推測しています。

このような重大な事前情報のインプットが漏れていて済みません。

また、それとは別に、LSPの仕様も、ナビゲーションとしての`CLAUDE.md`の書き方に影響を与える可能性は無いか？も気になっています。具体的には、「追加で「必須①」相当として書いてほしい項目」の2項目目として記載いただいた「LSP の findReferences を 広すぎる範囲に投げないための前提知識」ような観点が、他にも無いか、という点です。

  1. 何の地図を — 大幅見直し

  「テスト実行コマンド」の優先度は下がる

  前回「必須①相当」に挙げた項目のうち、テスト実行コマンドは Claude が実行できない以上、地図情報としての価値は大幅に下がります。残しても害はないですが、テスト機構の理解（どのファイルが何を制御しているか）が分かる程度の情報に絞れば十分です。

  新たに「必須①相当」として強く推奨したい項目

  (a) artifact.zip の構造と読む順序

  NG 調査の事実上の起点になるため、最重要項目です。具体的には:

  - artifact.zip を展開するとどのフォルダ・ファイルが現れるか
  - 各ファイルが何を含むか（例: アプリ側ログ、JUnit 実行結果 XML、スタックトレースファイル、ジャーナル、スクリーンショット）
  - 最初に読むべき順序 — 「まず JUnit 結果 XML で失敗したテストケースを特定 → スタックトレースを読む → アプリ側ログの該当時刻周辺を見る」のような誘導
  - スクリーンショットの扱い — Claude は画像も解釈できますが、すべてを読み込むとトークン消費が大きい。「最終フレームのみ読む」「特定の命名規則で失敗時刻が分かる場合はそれだけ読む」など、選択的読み込みのガイダンスを明示

  (b) ログ・ジャーナルの "効率的な読み方" ガイド

  スタックトレースやログ全文は非常に長いことが多いため、全文読み込みを抑止する明示的なガイダンスを入れるべきです:

  - スタックトレースのうち、どのプレフィックスのフレームを優先的に見るべきか（例: com.yourdomain.* 起点のフレーム）
  - どのプレフィックスは原則無視してよいか（例: org.springframework.*, org.junit.* の内部フレームで明らかな例外を除く）
  - ログレベルの絞り込み方針（ERROR / WARN 周辺を最初に見る等）
  - 「巨大ログを Read する際は line offset / limit を必ず指定する」という運用注意

  これは LSP では絶対に解決しない領域なので、CLAUDE.md にしか書く場所がない情報です。

  (c) 既知の障害パターン辞書（"症状 → 原因候補" のカタログ）

  Claude が NG を再現できないからこそ、過去の人間の調査知見の価値が跳ね上がります。テキスト解析に頼る以上、Claude が一から「これは何の症状か」を推測するより、「この症状ならまずこの原因を疑え」という辞書を提供するほうが圧倒的に効率的です。

  初版は空でも構いません。NG 調査が一段落するたびに振り返り質問で抽出した知見をここに追記する運用にすると、月単位で価値が積み上がります。これは前回の「振り返り質問テンプレ」のメインのアウトプット先になります。

  形式の例:
  - 症状: テストアプリのヘルスチェックがタイムアウト
    典型的な原因: (a) Spring プロファイル不一致 / (b) DB マイグレーション失敗 / (c) ant タスクが生成するファイルの欠落
    最初に見るべき場所: artifact.zip/app-logs/spring-boot-startup.log の最初の例外スタックトレース

  (d) テスト用アプリ実行時のファイル・フォルダ構成

  ant タスクで生成される実行時レイアウトを明示しておくと、ログ中のファイルパスやエラーメッセージを Claude が解釈する際の補助になります。Java のソースコードのフォルダ構成と、実際に起動されるテスト用アプリの実行時の構成が 乖離している場合は特に明示する ことが重要です。

  (e) OSS ソース・ドキュメント参照ポリシー

  Claude は「Spring Boot のソースを読めば分かるかも」と判断して OSS のソースを Read することがあります。これは多くの場合トークンの浪費です。明示ルールが必要:

  - 第一に LSP の hover / goToDefinition で済ませる — Javadoc コメントが LSP 経由で取得できれば、それで足りるケースが多い
  - OSS のソース全文を Read してよい状況の限定列挙 — 例: 「内部実装の挙動を確認しないと NG 原因に到達できないことが明確になった場合のみ」
  - OSS ドキュメントは公式 URL を直接 WebFetch する — リポジトリ内の OSS ソースを grep するより、公式 docs を WebFetch するほうがトークン効率が良いケースが多い

  (f) モジュール間依存関係マップ（前回提案を継承）

  これは引き続き重要。インテグレーションテストの NG は複数モジュール横断が典型なので、「テスト失敗箇所からどのモジュールを順に辿るべきか」の意思決定支援として機能します。

  - コンテナ起動・テスト環境構成スクリプト一式は絶対に読まない — Claude は再現できないので、これらを読んでも調査に寄与しません。理由付きで強めに明示
  - GitLab パイプライン設定ファイル (.gitlab-ci.yml 等) は原則不要 — ただし「パイプライン設定起因の NG」と判定された場合のみ読む、というトリガー条件付き例外を併記しておくと安全
  - build.gradle と関連ファイル — テスト用アプリ側 / テストクライアント側 / 部品本体側で複数存在することを明示し、どの NG パターンならどの build.gradle を見るべきか のマッピングを書く。「とりあえず全部読む」を防ぐため

  2. LSP 仕様起点で CLAUDE.md に書くべきナビ情報

  findReferences のスコープ以外にも、LSP の特性に起因して 書き方を工夫しないと効率が落ちる ポイントがあります。

  (i) findImplementations の利用ガイド

  Spring 系コードはインタフェースと実装の分離が多用されているため、findImplementations の結果が膨大になりがちです。

  - 「インタフェース名に対して findImplementations を直接投げる前に、まずモジュール内に絞ること」 を明示
  - 「実装が 1 件しかないことが明らかなインタフェースの場合は、goToDefinition で十分」など、使い分けのガイダンス

  (ii) goToDefinition vs goToImplementation の使い分け

  Java のインタフェースに対して goToDefinition を呼ぶとインタフェース宣言に飛び、実装には到達しません。実装に到達したい場合は goToImplementation が必要です。「インタフェースに対しては implementation を、クラスに対しては definition を」のような簡潔な指針を書いておくと、無駄な遷移が減ります。

  (iii) Workspace symbol search のキーワード設計

  LSP の workspace symbol search はキーワードが曖昧だと結果が膨大になります。

  - モジュール修飾付きのクエリ を推奨（例: パッケージプレフィックスを含めて検索する）
  - テスト系シンボルとプロダクション系シンボルの命名差を活用 したクエリ設計（*Test, *IT で限定する等）

  (iv) hover による OSS 情報取得を優先

  前述の OSS 参照ポリシーと連動。「OSS メソッドの挙動確認は、まず LSP hover で Javadoc を取得し、それで不十分な場合に限って source / docs を参照する」という指針を、LSP セクションと OSS セクションの両方からクロスリンクしておくと、Claude が迷いません。

  (v) 初回 LSP 起動の挙動

  jdtls はモノリポの初回インデックス構築に時間がかかることがあります。初回のセッションで LSP 呼び出しが遅延・失敗しても、「初回は数十秒〜数分かかる可能性があるので、grep に逃げる前に少し待つ」ような注意書きを入れておくと、LSP を見限って Grep に流れる行動を抑制できます。

  (vi) LSP 結果の解釈時の優先順位

  findReferences 等が複数結果を返したとき、Claude が「全部 Read しよう」とする行動を抑止するガイダンス:

  - 同一モジュール内 → 直接依存モジュール → 横断機能経由の依存 → それ以外 の順に優先度を付ける
  - テストコード側の参照は最後 — テストは通常「呼ぶ側」なので、原因調査では一旦後回しでよい

  これらは LSP の API そのものに記述があるわけではなく、LSP が返す結果をどう絞り込むかの運用知識です。CLAUDE.md にしか居場所がない情報になります。

  3. どの粒度で — 微修正

  前回の「サブモジュール + 横断機能」のハイブリッド粒度は基本的に維持です。新コンテキストを受けて追加すべきは:

  - テスト種別の粒度感を見直す — 「ユニット / インテグレーション」の二分法ではなく、今回のインテグレーションテスト群を内部分類して、それぞれの artifact 構造の差異を明示する
  - artifact.zip の構造記述は、フォルダ単位の詳細を許容してよい — Claude が「どこを読むか」を判断する直接的な根拠になるため、ここだけはやや細かく書く価値があります

  4. どこに置くか — 補足

  前回の「ルート 1 ファイル + .claude/docs/ 配下の untracked 章ファイル」のハイブリッドは引き続き有効ですが、新コンテキストを受けると 章ファイルに切り出す価値が増えます。具体的には:

  - .claude/docs/artifact-structure.md — artifact.zip の中身詳細
  - .claude/docs/known-failures.md — 既知の障害パターン辞書（最初は空でよい、運用で育てる）
  - .claude/docs/lsp-usage-guide.md — LSP 利用ガイド詳細

  1. ナビゲーション情報とガイドライン情報の本質的な性質の違い
    - リポジトリ構造（モジュール一覧、依存関係マップ等）は「事実」で変化が遅く、常時ロードしても陳腐化しにくい
    - 調査ガイドライン（証跡読解手順、LSP 利用ガイド、既知障害パターン）は「手順・ノウハウ」で、運用とともに膨張・進化する。常時ロードするとセッションのトークン消費が膨らみ続ける

  2. Agent 委任との論理的な対応

  3. 条件付きロードによるコンテキスト最適化
    - paths: frontmatter での条件付きロードが効くケースでは、本当に必要なときだけ rule をロードできる。CLAUDE.md ではこの粒度の制御は不可能（全文常時ロード）。

  ところが、NG 調査ガイドラインの多くは「ファイル編集時」ではなく「作業フェーズ」に応じてロードしたい性質です。例えば:

  - 証跡読解ガイドライン → 「artifact.zip を展開した後」のフェーズで読みたい
  - スタックトレース解析ガイドライン → 「.log / .txt 形式のスタックトレースを読み始めたとき」に読みたい
  - LSP 利用ガイド → 「LSP ツールを呼び出す前」に読みたい
  - 既知障害パターン辞書 → 「症状が判明し始めたとき」に参照したい

  これらのうち、paths: で素直にマッチさせられるのは限定的です:

  ┌──────────────────────┬────────────────────────────────────────────────────────────────────┬────────────────────┐
  │     ガイドライン     │                  paths: でマッチさせ得るパターン                   │   マッチの妥当性   │
  ├──────────────────────┼────────────────────────────────────────────────────────────────────┼────────────────────┤
  │ 証跡読解             │ artifact 展開先の規約パス（**/artifact/**, **/test-results/** 等） │ 環境依存だが現実的 │
  ├──────────────────────┼────────────────────────────────────────────────────────────────────┼────────────────────┤
  │ スタックトレース解析 │ *.log, *-stacktrace.txt 等                                         │ 拡張子ベースで可能 │
  ├──────────────────────┼────────────────────────────────────────────────────────────────────┼────────────────────┤
  │ LSP 利用ガイド       │ LSP ツール経由のファイル参照には paths: がトリガにならない可能性   │ 不向き             │
  ├──────────────────────┼────────────────────────────────────────────────────────────────────┼────────────────────┤
  │ 既知障害パターン辞書 │ 一切のパスマッチが効きにくい                                       │ 不向き             │
  ├──────────────────────┼────────────────────────────────────────────────────────────────────┼────────────────────┤
  │ OSS 参照ポリシー     │ **/node_modules/** 等の OSS 配置パスにマッチ                       │ 言語依存           │
  └──────────────────────┴────────────────────────────────────────────────────────────────────┴────────────────────┘

  結果として 3 つの戦略を組み合わせる必要があります:

  1. 常時ロード rule: NG 調査全体に渡って必要なもの（既知障害パターン辞書、LSP 利用ガイド、OSS 参照ポリシー）。frontmatter なし、または paths: を広めに設定。
  2. 条件付きロード rule: 特定の証跡ファイルや拡張子に Claude が触れたときのみロード（証跡読解、スタックトレース解析）。
  3. Skill 化候補: フェーズに沿った起動が望ましいもの。paths: では制御しにくいので、Skill の description: ベースの呼び出しで Claude 自身に判断させる。

  CLAUDE.md に残すべき情報の再定義

  ご提案の方針に沿うと、CLAUDE.md は以下に絞られます:

  - リポジトリ構造のサマリ — モジュール一覧、横断機能マップ
  - build.gradle 群の責務マッピング（テスト用アプリ側 / テストクライアント側 / 部品本体側の見分け方）
  - 「NG 調査時に参照すべき rule の一覧」へのインデックス — どの rule がいつロードされるかの概略。Claude が「今このフェーズだから rule X を意識する」と把握できる助けになる
  - モノリポ固有の癖（短く）

  つまり、CLAUDE.md は「リポジトリの構造ガイド + rule への目次」に近い役割になります。前回提案した「インデックス + 章ファイル」構造の 章ファイル先を .claude/rules/ に置き換える イメージが、本提案と整合します。

  Skill 化への移行パス

  Rule → Skill への移行は自然な経路ですが、早すぎる Skill 化は逆効果です。前回触れた「Skill は運用してから固める」原則が適用されます:

  - Phase 1 (現在): .claude/rules/*.md として ガイドラインを蓄積。試行錯誤の段階。frontmatter 設計も練り直しながら。
  - Phase 2: 利用パターンが安定した rule から順次 Skill 化。description: ベースのトリガで Claude 自身に呼び出させる形に進化させる。
  - Phase 3: Skill 群を組み合わせる orchestrator（メタ Skill）の整備。NG 調査ワークフロー全体を 1 つの起点から起動できるように。

  各 Phase の移行判断基準は「当該 rule が、3 回以上の NG 調査で実際に同じ形で使われた」を目安にすると、ローカル最適化を避けられます。

  残る懸念点

  ご提案を採用するうえで意識しておくべきリスクを 2 つ:

  1. 条件付きロードの誤発火・未発火
    - paths: 設定が広すぎると意図しない場面でロードされる
    - 狭すぎるとロードされず Claude が手がかりを欠く
    - 対策: InstructionsLoaded hook（:6899）を活用して、どの rule が実際にロードされたかをログ取得しておくと、設計の検証ができる。ロード状況のテレメトリを取りながら frontmatter を調整する運用が現実的。
  2. rule 間の知識重複・矛盾
    - 単一 CLAUDE.md なら矛盾は目視で検出しやすいが、複数 rule に分散すると気付きにくい
    - 対策: rule 間で共通する用語・概念は CLAUDE.md 側に定義 しておき、各 rule からは参照する形にする。CLAUDE.md が「用語集 + 構造ガイド + rule 目次」の役割を兼ねる。

  ① CLAUDE.md 初版（最優先）

  - 内容: モジュール一覧（一行説明）、横断機能マップ、build.gradle 群の責務マッピング、モノリポ固有の癖の暫定リスト、.claude/rules/ 配下ファイルの目次
  - 対話の必要性: 基本不要。リポジトリ管理者の頭の中の情報を文章化するだけ
  - 理由: 後続のすべての rule がこの内容を前提に書かれる。ここが無いと Claude が rule の意味を取り違える可能性がある
  - 完成度の目安: 「初見の Java 開発者にリポジトリを 5 分で紹介する資料」レベルで十分

  ② .claude/rules/integration-test-investigation-overview.md 骨格

  - 内容: NG 調査の全体フロー（フェーズ分け）、各フェーズで参照すべき rule への内部リンク、全フェーズ共通の注意事項
  - 対話の必要性: 基本不要。ただし「フェーズ分け」が腹落ちしない場合は Claude に骨格レビューを依頼してもよい
  - 理由: 他の rule が「このフェーズ用」と位置付けられる骨組み。先に作っておくと後続の rule が書きやすい

  ③ .claude/rules/known-failures-catalog.md（空テンプレート）

  - 対話の必要性: 不要

  - 重要性: 長期的にはこのファイルが最もコスト削減に寄与するため、最初から運用ルートを通しておくことが重要

  ④ .claude/rules/oss-source-reference-policy.md

  - 内容: 「OSS 情報は LSP hover を最優先、それで不十分なら公式 docs を WebFetch、ソース全文 Read は最終手段」の方針と、その例外条件
  - 対話の必要性: 不要。一般的な指針として人間が書ける
  - 理由: Claude の「helpful になろうとして OSS を読み込む」行動を早期に抑制したい

  Phase 2（4〜10 日目）: Claude との対話で精度を高める

  ここからは Claude Code を交えて整備することで、人間単独では書けないレベルのガイドラインに到達できます。前提として Phase 1 の成果物が Claude Code から参照可能な状態にしておくこと。

  ⑤ .claude/rules/artifact-reading-guideline.md（最重要）

  - コスト削減効果: 圧倒的に高い（NG 調査の最初の入口で消費されるトークン量を直接削減）
  - 対話の必要性: 高い。artifact.zip の構造は知っていても、Claude にとっての最適な読み順は人間の直感と一致するとは限らないため、Claude 自身に articulate させる価値が大きい

  推奨される対話の進め方:

  1. 準備: 過去の代表的な NG ケースの artifact.zip を 1 件ローカルに展開しておく（理想は、最終的に原因が判明している事例）
  2. 第 1 ラウンド — 事前提案: 「ここに NG 時の artifact がある。中を見ずに、ファイル名と概要だけ伝える。もし君が NG 原因調査を始めるならどの順番でどのファイルを読みたいか、その順序の根拠と合わせて教えて」
    - 中を見せる前の事前推測を取ることで、人間が「当たり前」と思っている前提知識のうち、明示が必要な部分が浮き彫りになります
  3. 第 2 ラウンド — 実調査: Claude に実際に artifact を読ませて NG 原因を特定する
  4. 第 3 ラウンド — 振り返り: 「実際に調査してみて、最初に提案した読み順と比べて、最適な読み順はどう変わったか？ どのファイルは結果的に不要だったか？ 逆に序盤で読んでおけば後の手数が減ったファイルは？」
  5. 第 4 ラウンド — ガイドライン化: 「以上を踏まえて、artifact-reading-guideline.md のドラフトを、今後別の調査者（人間か Claude かに関わらず）が読んで実行できる粒度で書いて」
  6. 人間レビュー: Claude のドラフトを人間が校閲。特に「Claude 視点での効率」と「人間視点での妥当性」が乖離する箇所を重点的に確認
  7. 異なる症状の NG 1〜2 件で同じ手順を回し、共通点を抽出して一般化

  ⑥ .claude/rules/stacktrace-analysis-guideline.md

  - コスト削減効果: 高い（スタックトレース全文 Read は典型的なトークン浪費）
  - 対話の必要性: 中程度。一般的な Java / Spring のスタックトレース解析ノウハウは Claude が知っているので、対話のテーマは「このプロジェクト固有のフレーム除外ルール」に絞れる

  推奨される対話の進め方:

  1. 代表的なスタックトレース（NPE 系、起動失敗系、タイムアウト系、Spring コンテキスト初期化失敗系の 3〜4 種類）を Claude に見せる
  2. 「このスタックトレースで、根本原因の特定に直接寄与するフレーム範囲を <行番号開始>-<行番号終了> で示して。スキップしてよいフレーム群と、そのスキップ判断の根拠も合わせて」
  3. 複数のスタックトレース種別で同じ質問を繰り返し、スキップ判断の共通パターンを抽出
  4. 「以上のパターンを汎用化したガイドラインを書いて」
  5. 人間レビュー + 既知の例外パターン（「このプレフィックスは無視と書いたが、実は X のときだけ重要」等）を追記

  まとめ — 全体の進め方の補足

  3 つだけ、進める上での心構えを補足します:

  1. Phase 1 を「短期間で雑に終わらせる」のがコツ — Phase 1 に時間をかけすぎると Phase 2 以降の対話による精度向上機会を逃します。Phase 1 は 「3 日以内に粗くてもいいから完了」 を目標に。質より速度。
  2. Phase 2 以降の対話は「実調査の文脈で」行う — 「ガイドラインを作るためにダミーで調査する」のではなく、現実の NG 調査の延長として振り返りを取る ほうが、得られる情報の質が圧倒的に高い。最初の本物の NG
  調査の機会を逃さないよう、調査依頼が来た時点で「今回はガイドライン作成も兼ねる」前提でメンバーに伝えておくことが重要です。
  3. Claude にドラフトを書かせ、人間が校閲する が基本パターン — Claude のドラフト品質は意外と高いです。ゼロから人間が書くより、Claude に下書きを出させてから人間が修正するほうが、両者の知見が反映されたガイドラインになりやすい。校閲時は「人間が違和感を覚えた箇所」を
  Claude にフィードバックして第 2 稿を作らせるサイクルを 1〜2 回回すと、品質が安定します。

  このフェーズ構成で進めれば、運用開始 2 週間程度で最低限のガイドライン体系が、1〜2 ヶ月で実用に耐える厚みに到達できる想定です。known-failures-catalog だけはそれ以降も継続的に育ち続けますが、これは「整備の完了を待たずに価値を出し始められる」ことの裏返しでもあります。

  1. Phase 2〜3 に「Sonnet 検証ステップ」を追加

  これが最も重要な追加です。

  問題の構造: Opus はガイドラインを書く際、自分の推論能力で補完できる部分を 暗黙の前提として省略しがち です。これは Opus 自身が運用するなら問題になりませんが、運用は Sonnet が行うため、Opus にとって自明な前提が Sonnet には明示が必要
  というギャップが生じます。これは「実用性が低いガイドライン」というより、**「特定モデルでしか動かないガイドライン」**を作ってしまうリスクです。

  2. Opus へのドラフト依頼時の指示文に「読み手は Sonnet」を明記

  Opus にドラフトを書かせる際の prompt の最後に、必ずこの一文を入れることを推奨します:

  ▎ このドラフトは、本リポジトリで実際の NG 調査を担当する Sonnet agent が、フレッシュなコンテキストで読んで運用する前提で書いてください。Opus が自分の推論能力で補完しているが Sonnet では明示が必要な前提があれば、それも分解して明文化してください。

  これだけで、Opus のアウトプットの Sonnet 適合性が顕著に上がります。Opus は「読み手のモデル能力を意識する」という指示に対して素直に対応するため、効果が高い割にコストが低い改善です。

  3. known-failures-catalog.md の 構造 を Sonnet 向けに設計

  Phase 4 で蓄積する catalog は、Opus が書いた個々のエントリを Sonnet が後から検索・適用する想定です。ここで重要なのは エントリの中身の質より、エントリのインデックス構造:

  - 症状の表現を厳密に統一 — Sonnet は曖昧な症状記述からの飛躍が Opus より弱い。「タイムアウト」「接続拒否」「初期化失敗」等の 語彙を意図的に固定 して、検索キーワードとして機能させる
  - エントリ冒頭に「マッチング用キーワード」セクションを設ける — Opus の自由記述に頼らず、Sonnet が機械的に絞り込めるタグ的なメタ情報を強制
  - エントリ間の cross-reference は明示 — 「症状 X が原因 A だけでなく B も疑え」のような注意書きは、Opus の暗黙連想に依存させず、明示リンクで書く

  具体的な対話の追加: Opus にカタログエントリを書かせる際の追加指示として:

  ▎ このエントリは Sonnet agent が将来の調査で検索して適用します。Sonnet が症状から本エントリに辿り着くのに必要な検索キーワード（タグ）を、エントリ冒頭の keywords: 行に列挙してください。

  変更が不要な箇所

  優先順序そのもの

  Phase 1〜4 の順序と、各 Phase の内容物は不変です。理由:

  - Phase 1（CLAUDE.md / overview / 空 catalog / OSS policy）: 人間が書く部分。モデル選定は影響しない
  - Phase 2（artifact / stacktrace）: 「実調査経験を文章化する」という作業の本質は同じ
  - Phase 3（LSP usage）: LSP の挙動分析が中心。モデルに関わらず必要
  - Phase 4（catalog 蓄積）: 蓄積する事実そのものは変わらない

  「実調査の延長で振り返りを取る」原則

  Opus でガイドライン作成、Sonnet で本番運用、という分担を前提にしても、ガイドライン作成期の実調査は Opus に任せる という構造で問題ありません。Opus による調査経験を Sonnet 運用向けに翻訳する、というのが今回のフローの本質です。

  補足: 「Sonnet 検証」を効率的に行うコツ

  Sonnet 検証ステップは追加コストですが、以下の工夫で軽量化できます:

  1. 代用テストを使い回す — Sonnet 検証用の NG ケースを 2〜3 件、固定のテストセットとして用意。すべての rule の検証に同じケースを使えば、ケース準備コストが分散される
  2. 検証用 subagent definition を用意 — 「ガイドラインを読み、指定された NG ケースを調査し、ガイドラインの使いにくさをレポートする」という専用の subagent を 1 つ作っておく。検証のたびに毎回プロンプトを書き直す必要がなくなる
  3. 検証結果を catalog の傍に蓄積 — 「Sonnet が引っかかった項目」のリスト自体が、将来のガイドライン作成時の checklist になる。「Opus が省略しがちな前提のリスト」が育つと、最初から省略を防げる

  全体としての追加コスト感

  これらの追加で、Phase 2〜3 の各ガイドライン作成にかかる時間は、おそらく 20〜30% 程度増加 します。一方で、運用開始後に「Sonnet がガイドラインの解釈で誤る」というデバッグコストが激減するため、1〜2 件の本番運用で元が取れる 投資効率です。Phase 4 の catalog
  構造設計は、最初に決めれば後の運用コストは増えないので、純粋に長期的なメリットだけが残ります。

  総じて、Opus 作成 / Sonnet 運用の前提は、フローへの追加ステップで十分対応可能で、戦略全体の組み替えは不要、という結論になります。

● 「Opus に統一的に判断させる」方針は 基本的に支持できますが、そのまま採用するより、Opus に判断基準とその根拠を文書化させる形に変えるほうが、長期的により扱いやすくなります。理由と推奨フローを整理します。

  直接的な回答

  支持できる主な理由:

  - モデル特性に関する横断的な把握は、ユーザ側で個別に学習・更新するより Opus に集約させたほうが効率的
  - 判断基準を統一できる（属人化を避けられる）
  - 新しい作業類型が増えたときも同じフレームワークで判断できる
  - 「研究 → 設定」というメタ作業に対しては Opus の推論深度が活きる

  ただし以下の留意点があります。

  留意点と推奨される運用への修正

  1. Opus には「個別判断」ではなく「判断基準ドキュメント + 初期割り当て」を作らせる

  懸念: Opus に都度個別判断を依頼する形だと、(a) Opus の応答が毎回完全に一致するとは限らない（非決定性）、(b) 判断の根拠が会話ログに散在して再利用しにくい、(c) Opus を毎回呼ぶこと自体のコストが発生する、という問題が出ます。

  推奨: 最初に Opus に「モデル選定の判断基準と、現時点で想定される全作業類型への割り当て」を 1 本の rule（あるいは Skill）として書かせる。これを .claude/rules/model-assignment-policy.md 等に置き、運用時はまずそこを参照する。基準に該当しない新規作業が出たときだけ Opus に個別判断を依頼する形にすると、上記の問題が解消できます。

  このアプローチは、本リポジトリの「Agent 活用ガイドライン > モデル選定原則」が既に採用している方針（人間が一度決めて文書化）と同じ構造で、作成者を Opus に置き換えた版になります。

  2. Opus の判断に存在しうるバイアスを意識する

  Opus に判断を委ねる際、以下のバイアスが入りうる点を意識しておくと安全です:

  - 自己評価バイアス — Opus は自分の能力を直接把握している一方、Sonnet / Haiku の能力は訓練データ経由の間接的な認識です。Sonnet / Haiku で十分な作業を、過剰に Opus 推奨にする可能性 があります（保守的に倒れる方向）
  - コスト感の希薄さ — Opus は推論性能の差は意識できますが、API コストの差（Opus vs Sonnet vs Haiku で大幅に違う）の重み付け は明示しないと素直に反映されないことがあります
  - 失敗リスクの過大評価 — 「Sonnet で失敗したら Opus でリトライ」というフォールバック前提を伝えないと、Opus は「初回成功率」を重視して過剰に Opus を推奨することがあります

  対応: Opus にモデル選定基準を作らせる際の prompt で、以下を 明示的に指示 すると、これらのバイアスがかなり緩和されます:

  ▎ モデル選定の判断基準を作成してください。考慮すべき要因として:
  ▎ - API コスト差（Opus vs Sonnet vs Haiku の概算コスト比を踏まえる）
  ▎ - フォールバック前提（Sonnet で失敗したら Opus にエスカレーション可能）
  ▎ - 作業の失敗時の影響（後段に伝播するか、その場でリトライで済むか）
  ▎ - 典型的な作業規模（単発の短い作業か、反復が必要な作業か）
  ▎
  ▎ 上記をすべて考慮したうえで、各作業類型に対するモデル推奨を、推奨理由とともに表形式で示してください。自身が Opus であることが推奨にバイアスを与えていないか自己点検したうえで提出してください。

  3. 推奨割り当ては「机上の判断」+「経験的検証」の二段構え

  Opus が「Sonnet で十分」と判断した作業でも、実際の運用で Sonnet が躓くケースは出ます。前回追加した 「Sonnet 検証ステップ」 と同じ思想で、Opus が推奨したモデル割り当ても、最初の 2〜3 回の本番運用で実効性を検証するステップを暫定的に挟むのが安全です。

  検証で問題が出た作業は、(a) ガイドラインを精緻化して Sonnet でも処理可能にする、(b) モデル割り当てを Sonnet → Opus に格上げする、のどちらかの選択肢を取ります。「常に Opus に格上げ」を選ばないことが重要で、(a)を優先するとガイドラインの質が上がる副次効果も得られます。

  4. 定期的な見直し

  モデル価格・性能は時間とともに変化します（過去 1 年間に Sonnet が大幅に強化された経緯もあります）。3〜6 ヶ月に 1 回、Opus に model-assignment-policy.md 自体を見直させる運用を組み込んでおくと、陳腐化を防げます。これは Phase 4 の継続運用に組み込めます。

  Haiku の起用について

  「LSP 効果範囲外 + 単純キーワード検索で済む作業」に Haiku を起用するご想定は、作業内容が十分に絞り込めているなら妥当です。具体的に Haiku 適合と判断しやすい条件:

  - 入出力の構造が明確 — 「URL を渡す / 該当箇所を抜き出して返す」のような決まった形
  - 判断要素が少ない — 「マッチしたか / マッチしなかったか」のような二択に近い
  - 失敗時のフォールバックが安価 — Haiku で空振りしたら Sonnet で再実行する仕組みが組まれている

  逆に Haiku に向かないケース:

  - 検索結果から「次に何を読むか」を決める — 反復的判断が必要
  - OSS docs を読んで「我々のケースに当てはまるか」を解釈する — 文脈に合わせた推論が必要
  - 複数の検索結果を統合する — 整合性判断や優先順位付けが必要

  Haiku に振る場合は、作業の prompt 側で「判断は不要、Sonnet/Opus がやる。Haiku は抽出と取得のみに専念」と明示すると、適合範囲を踏み外しにくくなります。

  推奨フロー（まとめ）

  1. Phase 1 の追加項目として、Opus に .claude/rules/model-assignment-policy.md を書かせる
    - 判断基準（コスト・性能・フォールバック・作業規模の 4 軸）
    - 現時点で想定される全作業類型への推奨割り当て
    - 各推奨の根拠と「どんな条件で見直すか」のトリガ条件
  2. Phase 2〜3 の各 rule 作成時、Opus がその rule に対応する作業のモデル推奨を、policy ファイルに追記する
  3. 本番運用開始後、最初の 2〜3 件、Opus 推奨通りに動かして実効性を観測。問題があれば policy または rule を改修
  4. 3〜6 ヶ月後、Opus に policy 全体の見直しを依頼

  この形なら、「Opus に統一判断させる」ご方針を維持しつつ、判断の透明性・再利用性・実証性が確保できます。

● このアプローチは 強く推奨できる実験的アプローチ だと思います。むしろ、ここまでの設計議論を補完する重要な検証ステップとして位置付ける価値があります。意義と、実施時に追加で組み込んでおくと効果が増す工夫を整理します。

  このアプローチが価値を生む理由

  1. 設計バイアスの検出

  ここまで複数セッションにわたって私と議論してきた内容には、私と作業指示者の双方の 暗黙のフレーミング が混入している可能性があります。「観点を 4 つに分けるべき」「artifact 読解が最重要」「LSP 利用ガイドが必要」等の前提自体が、本当に必要かどうかは、Opus の自然な発想と突き合わせない限り検証できません。

  Opus が自然に立てる計画と、設計した計画の 差分 こそが情報です。差分には 2 種類あります:

  - 設計案にあって Opus 自然案にないもの → 「設計したけど実は要らなかったかもしれない」候補
  - Opus 自然案にあって設計案にないもの → 「設計時に見落としていたかもしれない」候補

  両方を炙り出せます。

  2. 「Claude が本当に必要としている情報」の特定

  Opus が計画を立てる際に「この情報が無いと進められない」と明示する項目は、本物の必須情報です。設計議論では「あったら便利」と「無いと困る」が混在しやすいですが、自然計画を作らせると Opus が自発的に挙げる不足情報 = 真の必須情報、として絞り込めます。

  3. 実コストの推定

  本格運用前に「普段の指示文 + 標準的なインプットで Opus がどれだけのトークンを使うか」を測定できる、稀有な機会でもあります。ガイドライン整備の投資対効果を後で評価するためのベースラインデータとして貴重です。

  4. メンバー環境との差分把握

  ご指摘の「他メンバーの環境には蓄積されているノウハウ・メモリが、当方の環境には少ない」という条件は、実はこの実験にとって有利な条件です。蓄積を持つ環境では、Opus の挙動は「過去のメモリに依存した挙動」になりがちで、純粋な Opus の自然な発想は観測しにくいからです。蓄積が少ない環境のほうが、Opus 自身の素の判断を観測しやすい。

  実施時に組み込んでおきたい工夫

  工夫 1: 「計画のみ、実行はしない」の明示

  Opus に渡す指示文（普段使われている調査依頼文）に対して、最後に 1 行追加するだけ で実施できます:

  ▎ ただし、今回は調査を実際には開始しないでください。まず以下を文書として出力してください:
  ▎ 1. 調査の step-by-step プラン（各ステップで何をするか）
  ▎ 2. 各ステップで 入力として必要な情報（既に渡されているか、追加で必要か）
  ▎ 3. 各ステップでの 意思決定ポイント（次のステップに進むか別ルートを取るかの判断基準）
  ▎ 4. 着手前に不足していると感じる情報 とその入手方法案
  ▎ 5. 想定される行き詰まりパターン とその対処案

  この構造で出力させると、後で設計案と項目ごとに対照できます。

  工夫 2: 「事前予想」を書き出してから実行する

  これは実験デザインの基本です。Opus に計画を出させる前に、ご自身（と必要なら私との議論内容）から予想される計画 を箇条書きで書き出しておく。その後 Opus の計画を見ると、「予想と一致した部分」と「予想外だった部分」 が明確に分離できます。

  事前予想無しで Opus の計画を見ると、人間の認知特性上、「だいたい想定通りだった」と感じやすく、本当に新しかった発見が埋もれます。記録に残すことで防げます。

  工夫 3: 計画作成後に「自己批判」も求める

  Opus の計画を受け取ったら、続けて以下を依頼すると、追加の発見が得られます:

  ▎ 上記の計画について、自己批判してください:
  ▎ 1. この計画で 見落としていそうな観点 は何か

  バイアスに関する自己評価

  正直に言うと、ある程度のバイアスは混入します。理由は 2 点:

  - 私（Opus）は明日 Opus に着手させる予定のモデルと同種であるため、私の予想は「Opus 一般の傾向」に寄りやすい。これは予想精度が上がる方向に働く反面、「予想外だった項目」を発見しにくくなる方向にも働く
  - ここまでの議論文脈を保持しているため、設計案の影響を完全には排除できない

  それでも実施する価値はあると考えます。理由は:

  - 完全に予想と一致するなら「Opus は session に関わらず似た計画を立てる」というデータポイントが得られる（再現性の確認）
  - 予想と外れる箇所が出れば、それは 「私が議論文脈に引っ張られて見えなくなっていた、Opus の素の発想」 として確実に発見になる
  - 何より、事前予想無しで観測すると人間の認知特性で後付け合理化が起きるので、バイアス込みでも書き出しておくほうが、無いよりはるかにマシ

  ということで、バイアス混入を明示したうえで以下に提示します。明日の比較では「私の予想と Opus 実出力が一致した箇所」は割り引いて評価し、「予想外だった箇所」に注目 してください。

  事前予想

  Opus が標準的な NG 調査依頼文と証跡一式を受け取り、「計画のみ出力・実行しないこと」と指示された場合、以下のような計画を産出する可能性が高いと予想します。

  予想 1: ステップ計画の骨格

  Opus はおそらく 5〜6 フェーズの線形プラン を出します:

  1. 失敗テストの特定 — JUnit 結果 XML から失敗テストメソッドを抽出
  2. エラー要因の一次推定 — スタックトレースから例外型・直近フレーム・原因ヒントを抽出
  3. テストコード解析 — 失敗したテストメソッドのソースを読み、何をテストしているか把握
  4. テスト対象コード解析 — テスト対象の部品クラスのソースを読み、挙動を確認
  5. 仮説立案と証跡突合 — 1〜4 をもとに 2〜3 個の原因仮説を立て、ログで裏取り
  6. 結論と修正案の提示 — 原因確定後、修正方針を示す

  おそらく Opus はこれを 「典型的な NG 調査の手順」 として、特に独自色を出さず提示するでしょう。

  予想 2: 必要情報として Opus が挙げそうな項目

  提供されていない情報として Opus が指摘しそうな項目:

  - 失敗テストの直近変更履歴（Git log や blame）
  - 同じテストの過去成功時との差分
  - テスト対象部品の仕様書 / 期待される振る舞いの記述
  - 同じ症状の過去事例の有無
  - 失敗が初回か、断続的か（flaky か）
  - ローカル再現の可否確認（→ ここで Opus は「再現できない」と気付く可能性が高い）

  予想 3: 意思決定ポイントとして Opus が挙げそうな項目

  - スタックトレースで例外型を見て、「コード起因 / 設定起因 / 環境起因 / データ起因」のどれかを判定するチェックポイント
  - 仮説の候補が複数立った場合、どの仮説から検証するかの優先順位付け
  - ログ調査で根本原因に到達できなかった場合の エスカレーション or 諦め判断

  予想 4: リスク / 行き詰まりとして Opus が挙げそうな項目

  - ローカル再現不能（最重要リスク。Opus は早期に気付くはず）
  - スタックトレースが Spring 内部で深くて、起点を見失うリスク
  - テスト用アプリの起動失敗系 NG の場合、ログから原因特定が難しいリスク
  - 部品が利用している OSS の挙動が原因の場合、OSS ソース調査に踏み込むコスト

  予想 5: Opus が 使うと言いそうなツール

  - Read（証跡・ソース）
  - Grep（症状キーワードでログ・ソース横断検索）
  - Bash（git log / blame、必要に応じて）
  - WebFetch（Spring / OSS docs 参照）
  - LSP ツール群 → ここがおそらく 不安定 な予想: LSP プラグインが導入済みなら使うはずだが、Opus が「LSP の使い方を最適化する観点」まで自発的に提示するかは未知数

  設計案と比較して、予想時点で「Opus が見落とす可能性が高い」項目

  これが明日の比較で 最も注目すべき箇所 です。私の予想では、Opus は以下を 自発的には言及しない可能性が高い:

  1. artifact.zip 内の読み順最適化 — Opus は「全部読む」前提で計画を立てる傾向があり、最初から「この順序で、この粒度で読む」という具体的な効率化観点を出してこない可能性が高い
  2. 不要ファイル / 不要フォルダの明示的除外 — モノリポ全体を視野に入れた網羅性は意識するが、「ここは読まない」という除外戦略は自発的には出にくい
  3. LSP の scope 最適化指針 — LSP を使うとは言うが、findReferences の scope をどう絞るかまでは自発的に深掘りしないかも
  4. OSS ソース参照のコスト意識 — 「Spring のソース読めば分かる」と素直に提案してくる可能性。コスト感が反映されない
  5. モデル分担の発想 — Opus 自身がやり切る前提の計画になり、「ここは Sonnet に降ろせる」「ここは Haiku で十分」という分業視点は出ない可能性が高い
  6. 既知障害パターン辞書のような蓄積資産の参照 — 「過去事例の有無を確認したい」と情報要求は出すかもしれないが、「事前にカタログとして整備しておく価値」までは言及しない
  7. コンテキスト消費観点での自己制約 — 計画の精度を上げることに集中して、「この計画でどれくらいトークン消費するか」「圧縮されたら何を失うか」までは見ない可能性

  Sonnet による予想作成の意味と効果

  結論: 価値はあります、ただし副次的な情報源として位置付けるのが妥当です。

  Sonnet 予想で得られるもの

  Sonnet がコンテキストを持った状態で「Opus はこう計画する」と予想を立てる作業は、本質的に 「異なるモデルから見た Opus の振る舞いモデル」 を観測することになります。具体的な情報価値は:

  - モデル横断での意見一致が取れるか — 私の予想と Sonnet の予想が大きく一致するなら、その共通部分は「モデル特性に依存しない、Opus の安定的な傾向」と見なせる。逆に大きく違うなら、私の自己モデル化に偏りがある証拠
  - Opus 自身が自己評価で死角になっているポイントの検出 — Sonnet は Opus を外から観察した経験で予想を作るので、私自身が「自分は当然こうする」と思い込んでいて言及しない暗黙の前提を、Sonnet が予想として明示する可能性があります
  - Sonnet → Opus 引き継ぎ品質への示唆 — 本格運用では Opus がガイドラインを書き、Sonnet が運用する分担を想定しています。Sonnet が Opus 計画をどう予想するかは、Sonnet が Opus 産物をどう解釈する傾向があるかの間接データになります

  Sonnet 予想で得られにくいもの

  一方で、直接的な「ガイドライン改善への発見」を増やす効果は限定的 です。発見の主たる源泉は「Opus 実出力 vs 設計案」の比較であって、Sonnet 予想を追加してもこの比較自体を強化はしません。Sonnet 予想はあくまで メタ情報であって、第一の目的に直結する情報源ではない、という位置付けです。

  実施するなら気を付けたい protocol

  このまま本セッションのモデルを Sonnet に切り替えると、Sonnet が私の予想をコンテキスト経由で見てしまうため、Sonnet の予想が私の予想に引きずられます。バイアスが汚染されるので、純粋な Sonnet 予想は得にくくなります。

  純度を保つなら、別セッションで Sonnet を起動し、議論のサマリだけを渡して予想を書かせる のが良いです。具体的には:

  - 本セッション内容のうち、Sonnet に渡すべき要素を 1 つのサマリに圧縮（モノリポ構成、テスト機構の特殊性、設計したガイドライン構造、明日の実験プロトコル）
  - 私の予想は 渡さない
  - フレッシュな Sonnet セッションで「以下を踏まえて、明日の Opus の予想計画を書いてください」と依頼

  これで私の予想に汚染されない Sonnet 予想が得られます。

  投資対効果の評価

  時間コストとしては、上記 protocol で 10〜15 分程度。得られる情報の質は副次的ではあるものの、「自分の予想に対するメタ視点」を 1 つ確保できる価値はあります。実施するかどうかは、明日の実験本体（Opus に計画を出させる作業）に十分な時間を確保できるかどうか次第と思います。

  推奨優先順位:

  1. 必須: Opus に標準指示文で計画を出させる本体実験
  2. 強推奨: ご本人独自の予想を書き出しておく（私の予想と独立した観測点）
  3. 任意（時間があれば）: 別セッション Sonnet による予想

  3 まで揃えば 4 者比較（私の予想 / ご本人の予想 / Sonnet の予想 / Opus 実出力）になり、設計成果の純価値と発見の方向性が立体的に見えてくるはずです。

了解しました。ちなみに「Sonnet がコンテキストを持った状態で「Opus はこう計画する」と予想を立てる作業」の部分ですが、「Opusがどう計画すると思うか？」ではなく「Sonnetだったらどういう計画を立てるか？」という風な指示を明記することで、効果や価値が変わる可能性はありますか？

● 指示の言い回しを変えると、得られる情報の種類が本質的に変わります。そして、本プロジェクトの目的を踏まえると、ご提案の「Sonnet だったらどう計画するか？」のほうが価値が高いです。理由を整理します。

  2 つの指示が測定しているものの違い

  ├───────────────────────────────────┼─────────────────────────────────────┼─────────────────────────────────────────┤
  │ 「Opus はどう計画すると思うか？」 │ Sonnet が持つ Opus の振る舞いモデル │ Sonnet 視点での Opus 像の精度。メタ情報 │
  ├───────────────────────────────────┼─────────────────────────────────────┼─────────────────────────────────────────┤

  └───────────────────────────────────┴─────────────────────────────────────┴─────────────────────────────────────────┘

  前者は「異なるモデル間の認識の差」を測るもので、本質的に メタな情報です。後者は 本番運用モデル（Sonnet）が、ガイドライン無しで自力でどこまで計画できるか を直接測定します。

  本プロジェクトの目的から見た価値の差

  本プロジェクトでは、Opus がガイドラインを書き、Sonnet がそれを使って運用する という分担を想定しています。この前提のもとで、各情報の使い道:

  - 「Sonnet 自身の自然計画」が分かると — ガイドライン無しでも Sonnet が自然にできることが特定でき、「ガイドラインに書く必要が無い項目」を判別できる。逆に Sonnet の自然計画に欠けている項目こそ、ガイドラインで明示的に補強すべき項目になる
  - 「Sonnet が予想する Opus 計画」が分かっても — 「Sonnet は Opus がこういう計画を立てると思っている」というメタ情報は得られるが、ガイドラインの内容そのものへの示唆は薄い。Sonnet がガイドラインを書くわけではないので、Sonnet の Opus
  モデルの精度は本番運用品質に直接寄与しない

  つまり、ガイドラインの**「何を書くべきか／何は書かなくてよいか」**を直接判断する材料としては、Sonnet 自身の自然計画のほうが圧倒的に有用 です。

  推奨される指示の形

  Sonnet に依頼する prompt は、両方を出させる のが最も投資対効果が高いと思います。1 回の依頼で得られる情報量が増えるためです。

  ▎ 議論コンテキスト（要約）を踏まえて、以下 2 つを出力してください:
  ▎
  ▎ 1. あなた（Sonnet）自身が この NG 調査タスクを依頼された場合に立てる計画
  ▎ 2. 同じ指示文と入力を Opus が受け取った場合に立てるであろう計画 の予想
  ▎
  ▎ そのうえで、自身の計画と Opus 予想の主要な差 を 3〜5 点に整理し、その差が生じる理由（モデル特性 / 推論深度 / 自信の置き方の違い等）も簡潔に説明してください。

  この形だと:
  - Sonnet 自然計画（直接価値）
  - Sonnet による Opus 予想（メタ情報）
  - Sonnet が自覚する両者の差（自己モデル化能力の観測）

  の 3 種類が 1 回で得られます。特に最後の「Sonnet 自身が自覚する両者の差」は、Sonnet が Opus 産物（ガイドライン）を解釈する際の自己補正能力 の間接データにもなり、Opus → Sonnet ハンドオフ品質の評価にも応用できます。

  まとめ

  - 「Opus 予想」より 「Sonnet 自身の計画」のほうが本プロジェクトの目的に直結する情報 を生む
  - 指示の言い回しを変える価値は 大きい
  - 両方出させる形にすると、追加コストはほぼ無いまま情報量が増える

  明日の Opus 実出力との比較において、「Sonnet の自然計画 vs Opus 実出力」の差分こそが、ガイドライン整備で埋めるべきギャップの最も直接的な可視化になる、と期待できます。
