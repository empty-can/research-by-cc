# NG 調査計画事前予想 — コンテキスト共有 Sonnet による予想

作成日: 2026-05-20  
作成モデル: claude-sonnet-4-6（本セッション内でモデルを Opus → Sonnet に切り替え後）  
位置付け: 議論コンテキスト全体（設計案・ガイドライン構造含む）を共有した状態での Sonnet 自身の計画。Opus が作成した事前予想の具体的内容は極力排し、「Sonnet としての自然な計画立案傾向」に基づいて作成。

---

## このファイルの読み方

- **Sonnet の特性を意識した記述**: 広く網羅するより「まず最も高確率のルートを一本試す」スタイル。仮説は絞って検証する。
- **コンテキスト由来の影響**: LSP の価値・OSS 参照コスト・ログ全文読みの非効率については議論から認識済みのため、自然にその知識が反映されている。ただし、同じ知識を持っていても、その使い方の優先順位はモデル特性に沿って判断している。
- **Opus の事前予想との差分**を比較する際、ステップ構造・仮説の扱い方・前置きの有無・不確実性の表現に特に注目すると発見が得やすい。

---

## 1. 調査の step-by-step プラン

### ステップ 0: 着手前の 1 問確認（所要 1〜2 分）

**何をするか**  
作業を始める前に、作業指示者に 1 つだけ確認する:

> 「この NG は (A) 以前は成功していたのに今回失敗した（リグレッション）、それとも (B) 今回が初回または繰り返し失敗している、どちらですか？」

**理由**  
この 1 点で調査ルートが根本から変わる。リグレッションなら「最近変更されたコード」が最重要の調査対象になり、初回失敗ならテスト設計・環境・設定の妥当性を疑う方向になる。確認せずに進むのは非効率。

**自信度**: 高

---

### ステップ 1: エラーの一次分類（所要 5〜10 分）

**何をするか**  
1. artifact.zip の JUnit 結果 XML から失敗テストケースを特定
2. 例外タイプとメッセージ（1〜3 行）を抽出
3. スタックトレースから `com.yourdomain.*`（プロジェクト固有）フレームを探す。あれば最上位フレームのクラス名・メソッド名をメモ
4. 以下の 4 類型のどれかに一次分類する:
   - **(A) コード起因**: 実装ロジックのバグ、NullPointerException 等
   - **(B) 設定起因**: Spring コンテキスト初期化失敗、プロパティ未解決、Bean 定義の問題等
   - **(C) 環境・通信起因**: タイムアウト、接続拒否、コンテナ起動失敗等
   - **(D) テスト自体の問題**: Selenium クライアントの操作が仕様と乖離、アサーション条件の誤り等

**必要な情報**: artifact.zip（JUnit 結果 XML、スタックトレース）→ 提供済みのはず  
**所要時間感**: 短い。全文読みせず必要な行だけを抽出する

**自信度**: 高

---

### ステップ 2a: （リグレッションの場合のみ）直近変更の確認

**何をするか**  
1. 対象部品に関する直近 5〜10 コミットの diff または git log を確認
2. ステップ 1 で特定したクラス・メソッドが変更されていないか確認
3. 変更が見つかれば、その変更内容を読む

**なぜ先にやるか**  
リグレッションの場合、原因はほぼ確実に「変更」にある。コードを広く読む前に変更差分を見るのが最速。数分で原因が特定できることが多い。

**必要な情報**: git log / diff（または変更ファイルの一覧）→ 提供されていなければ、リポジトリへのアクセスが必要な旨を伝える  
**意思決定ポイント**: 変更差分で原因が確定できた → ステップ 5 へ。不明 → ステップ 2b へ

**自信度**: 中。コンテキスト無しの Sonnet がこれを「最初に」やるかは不確か。

---

### ステップ 2b: スタックトレースからコードへの対応付け

**何をするか**  
1. `com.yourdomain.*` フレームのうち、例外発生地点に最も近い 1〜2 個を選ぶ
2. **LSP が使えるなら** `goToDefinition` でメソッド実装へジャンプ。使えなければ Grep
3. 対象メソッドの実装を読み、例外が発生しうるコードパスを特定
4. 読む範囲は「その 1 メソッド + 直接呼んでいる 1〜2 メソッド」に留める。最初から広げない

**必要な情報**: 部品のソースコード → 提供済み  
**意思決定ポイント**: コードを見て原因が絞れた → 仮説形成（ステップ 3）へ。コードを見ても不明 → ステップ 4（ログ確認）と並行して進める

**自信度**: 高

---

### ステップ 3: 仮説を 1〜2 個に絞って明文化

**何をするか**  
1. ステップ 1〜2 の情報から、原因仮説を **最大 2 個** に絞る
2. 各仮説を「**症状 → 原因コード箇所 → その仮説が正しければ他に観測されるはずの証拠**」の形で書く
3. 仮説を反証できる条件も明示する（「もし X ならこの仮説は否定される」）

**Sonnet としての方針**: 仮説を 3 個以上並べて同時検証しない。まず 1 番目の仮説の検証を完了してから、外れた場合に次へ進む。

**意思決定ポイント**: 仮説が 1 個に絞れた → ステップ 4 へ。2 個以上が同等 → 「ログでより簡単に確認できる」仮説を先に検証

**自信度**: 高

---

### ステップ 4: artifact のログで仮説を検証

**何をするか**  
1. artifact.zip のアプリ側ログを開く
2. **全文読みはしない**。以下の順で絞る:
   - まず ERROR / WARN レベルを grep
   - テスト失敗タイムスタンプの ±30 秒に絞る
   - ステップ 3 で「あるはず」とした証拠文字列を grep
3. 仮説と合致するか確認

**注意**: Selenium スクリーンショット（artifact.zip 内）も確認の候補。失敗時刻近辺の最後の数枚を見ると、テストアプリの UI 状態から「テストのどの操作ステップで止まったか」が分かり、コードを読む範囲を絞りやすくなる。

**必要な情報**: artifact.zip のログ・スクリーンショット → 提供済みのはず  
**意思決定ポイント**: 仮説を支持するログあり → ステップ 5 へ。仮説を否定する証拠あり → ステップ 3 に戻り別仮説を立てる。ログで判断不能 → Spring 設定ファイルの補助確認へ（後述）

**自信度**: 高。ログ絞り込みの手順の具体度合いは、コンテキスト無しだと薄くなる可能性がある。

---

### ステップ 4-補足: Spring 設定ファイルの補助確認（必要な場合のみ）

**何をするか**  
1. ステップ 1 の一次分類が (B) 設定起因 だった場合、または仮説検証でログから判断できなかった場合
2. 対象のテストケースに関係する Spring XML / プロパティファイルを **最小限**読む
3. Bean 定義の競合、プロパティ未解決、Profile 切替の想定外動作を確認

**注意**: XML については LSP によるナビゲーションサポートが無い（XML LSP は現状未導入）。Grep で特定のクラス名・Bean 名を検索して目的の箇所に絞る。

**自信度**: 中

---

### ステップ 5: 結論と修正提案

**何をするか**  
1. 根本原因を「**コード X の Y 行目が Z という理由で失敗**」と証拠チェーン付きで明示
2. 修正案を提示（コード変更 / 設定変更 / テスト修正のどれか）
3. 修正が部品本体に影響する場合は、**LSP `findReferences`** で影響を受ける他の呼び出し元を確認し、副作用の可能性を列挙
4. **確認できなかった部分は確認できなかったと明示する**。推測で断言しない

**自信度**: 高

## 2. 各ステップで必要な情報（提供済み / 追加必要）

| ステップ | 必要な情報 | 状態 |
|---|---|---|
| 0 | リグレッションか初回失敗か | **追加確認が必要**（最重要） |
| 1 | JUnit 結果 XML、スタックトレース | 提供済み（artifact.zip 内） |
| 2a | 直近 5〜10 コミットの diff または変更ファイル一覧 | **追加必要**（リグレッションの場合） |
| 2b | 部品ソースコード | 提供済み（参照ファイル一覧に含まれるはず） |
| 3 | （1〜2b の情報から作成） | 提供済み情報から生成 |
| 4 | アプリ側ログ、Selenium スクリーンショット | 提供済み（artifact.zip 内） |
| 4-補足 | Spring 設定ファイル（XML / properties） | 提供済みの場合もあり。不明なら確認 |
| 5 | （1〜4 の情報から作成） | 提供済み情報から生成 |

## 3. 各ステップの意思決定ポイント（まとめ）

```
ステップ 0
  ├─ リグレッション → ステップ 1 → ステップ 2a（先行） → ステップ 3 → ...
  └─ 初回失敗     → ステップ 1 → ステップ 2b → ステップ 3 → ...

ステップ 1（一次分類）
  ├─ (A) コード起因   → ステップ 2b → 3 → 4
  ├─ (B) 設定起因    → ステップ 4-補足を早めに → 3 → 4
  ├─ (C) 環境起因    → ステップ 4（ログを先行） → 3 → 2b
  └─ (D) テスト自体  → ステップ 2b（テストコード）を先行

ステップ 3（仮説）
  ├─ 1 個に絞れた  → ステップ 4 で検証
  └─ 2 個同等     → ログで確認しやすい方を先に

ステップ 4（ログ検証）
  ├─ 仮説支持     → ステップ 5（結論）
  ├─ 仮説否定     → ステップ 3 へ戻り別仮説
  └─ 判断不能     → ステップ 4-補足（設定確認）
```

## 4. 着手前に不足していると感じる情報

Sonnet として「これが無いと調査精度が下がる、または冒頭で時間を無駄にする」情報:

1. **「リグレッションか初回失敗か」**（ステップ 0 で確認必須。調査の方向性が根本から変わる）
2. **直近コミット一覧 / diff**（リグレッションと判明した場合に即座に使いたい。提供してもらえれば最も早い）
3. **artifact.zip の展開済みフォルダ構造**（どのファイルがどこにあるか分からない状態だと探索コストが発生する。事前に構造一覧を渡してもらえると初動が速い）
4. **失敗したテストケースの ID・メソッド名**（指示文に含まれていない場合。XML を読む前のステップとして追加が必要）

## 5. 想定される行き詰まりパターンと対処案

| パターン | 対処 |
|---|---|
| スタックトレースが OSS（Spring / JUnit / Selenium）内部フレームのみ | エラーメッセージと例外タイプから Spring の設定起因として仮説を立て、ステップ 4-補足（設定確認）を先行させる |
| ログが空、または起動ログのみで失敗時刻のエントリが無い | Selenium スクリーンショットから UI 状態を読み、テストクライアント側の assertion エラーから逆引きする |
| 仮説を 2 周検証しても原因未特定 | **「現時点で判断できた範囲」と「確認に必要な追加情報（環境での再実行結果等）」を整理して報告する。推測で断言しない**。これは失敗ではなく、次のアクションを明示する正当な成果として扱う |
| 複数モジュールにまたがる複雑なコールチェーン | LSP の `findReferences` / call hierarchy を使って呼び出し関係を図式化してから読み進める。一度に読む範囲を「1 モジュール分」に制限して順番に進む |
| OSS（Spring Boot）の内部挙動が原因と疑われる | **LSP hover で Javadoc を確認 → 公式ドキュメントを WebFetch → ソース全文読みは最終手段**。OSS ソース全文読みは開始前に作業指示者に確認を取る（大きなトークン消費が予想されるため） |

## 6. Sonnet が予想する「Opus が立てるであろう計画」

以下は、同じ指示文と入力を受け取った Opus が産出するであろう計画の予想。
Opus の事前予想の具体的内容は極力参照せず、「Opus 一般の傾向」から推定している。

---

### Opus の計画（Sonnet による予想）

#### フェーズ 1: 状況把握（情報を広く集めてから判断する）

**何をするか**  
1. JUnit 結果 XML を読み、失敗テストケースを特定
2. 失敗したテストメソッドのソースコードを読む（何をテストしているかを把握）
3. スタックトレース全体を読む（フレームを詳しく確認）
4. テスト設定ファイル（アプリ側 / クライアント側）を読む

Sonnet との相違点: Opus は「まず読む → それから判断する」スタイルで情報収集を広めに行う。Sonnet が最初にフィルタ質問を置くのに対し、Opus はすべての手元情報を読んでから判断する傾向。

#### フェーズ 2: 部品コードの解析

**何をするか**  
1. スタックトレースの `com.yourdomain.*` フレームから部品コードを読む
2. Spring 設定・依存関係・プロパティを確認
3. テストに関連する Spring Bean の定義を確認

Sonnet との相違点: Opus はコード → 設定 → ログの順に情報を集めてから仮説を形成する傾向。Sonnet は「仮説を先に立ててログで確認する」。

#### フェーズ 3: 複数仮説の形成（3〜5 個）

**何をするか**  
1. フェーズ 1〜2 の情報をもとに、原因仮説を **3〜5 個** 列挙
2. 各仮説に「尤もらしさ（高 / 中 / 低）」を付ける
3. 各仮説の検証に必要な追加情報を列挙
4. 仮説間の関連性も確認（仮説 A が正しければ仮説 C は除外できる、等）

Sonnet との相違点: Opus は仮説を「全部出してから絞る」スタイル。Sonnet は「最初から 1〜2 個に絞る」。

#### フェーズ 4: 仮説検証（上位 1〜2 個）

**何をするか**  
1. 尤もらしさの高い仮説から順に、artifact.zip のログで証拠を確認
2. 仮説が否定された場合は次の仮説へ
3. 必要に応じて OSS ドキュメントを確認（LSP hover → 公式 docs の順）
4. 各仮説に対して「この仮説が正しいなら XX のログがあるはず」という検証条件を明示

#### フェーズ 5: 結論・修正案・影響範囲

**何をするか**  
1. 根本原因を証拠チェーン付きで明示
2. 修正案を提示
3. 修正による他テストへの影響を `findReferences` 等で確認
4. **自己批判**: 見落としていそうな観点 / 過剰投資だったステップ / 着手順序の改善点 を出力

Sonnet との相違点: Opus は結果に加えて自己批判を自然に出す（今回の指示に自己批判が含まれているため特に）。

---

### Opus 計画で想定される「必要情報」

| 項目 | Sonnet 予想の Opus の扱い |
|---|---|
| リグレッション / 初回失敗の確認 | 情報収集フェーズ内に含むが、最初の前提確認ステップとして独立させない可能性あり |
| git diff / 直近コミット | 言及するが、Sonnet ほど「最初のアクション」として目立たせない可能性あり |
| artifact.zip 構造 | 調査開始後に探索しながら確認する。事前の構造把握を要求する可能性は中程度 |
| OSS ドキュメント | LSP hover と公式 docs を使う旨を明示。ソース全文読みは最終手段として挙げる |

---

### Opus 計画で想定される「行き詰まりパターン」

Sonnet の予想リストとほぼ重複するが、Opus はより多くのパターンを列挙する傾向があるため、以下のような追加パターンを出す可能性がある:

- 非同期処理 / スレッドセーフ起因のタイミング問題
- テスト実行環境の差（コンテナの OS・JVM バージョン等）
- 仮説を 3 周以上検証しても未特定の場合のエスカレーション手順

## 7. Sonnet 自身の計画と Opus 予想の主要な差（3〜5 点）

### 差 1: 「前置き確認」の有無と位置付け

| | Sonnet | Opus（予想） |
|---|---|---|
| リグレッション確認 | **ステップ 0** として独立させ、調査開始前に必ず確認する | 情報収集フェーズ内に自然に含む可能性が高い。独立ステップとして前置きしないかもしれない |

**差が生じる理由**: Sonnet は早期フィルタリングを優先するため、「方向性が変わる質問」を最初のステップとして分離する。Opus は「まず手元の情報を全部読む」ことで方向性を自然に見極めるスタイルのため、前置き質問を独立させる必要を感じにくい。

---

### 差 2: 仮説の扱い方（絞る vs 列挙する）

| | Sonnet | Opus（予想） |
|---|---|---|
| 仮説の数 | **1〜2 個に絞って順番に検証** | **3〜5 個を列挙して同時評価** |
| 検証順序 | 1 個ずつ完全に検証してから次へ | 全仮説を並列に評価してから順位付け |

**差が生じる理由**: 推論深度の差。Opus は複数の仮説を同時に「頭に置いておく」ことが得意で、情報が新たに入るたびに全仮説を更新できる。Sonnet は最確率の 1 つに集中して素早く結論を出す方向に引力が働く。コンテキスト消費の観点でも、仮説が少ないほうが読む対象を絞りやすい。

---

### 差 3: 情報収集 → 仮説の順序が逆

| | Sonnet | Opus（予想） |
|---|---|---|
| 順序 | **仮説を先に立てて → ログで確認** | **情報を広く収集して → 仮説を形成** |
| テストコード読込タイミング | 仮説立案後の絞り込みで読む | フェーズ 1 の情報収集として読む（仮説形成前） |

**差が生じる理由**: 不確実性への対応スタイルの差。Sonnet は「部分情報で仮説を立て、的を絞って読む」ことで読み込み量を減らす。Opus は「全体を把握してから判断する」ことで見落としを減らす。どちらが優れているかは NG の性質による（単純な場合は Sonnet が速く、複雑な場合は Opus が確実）。

---

### 差 4: 自己批判の扱い方

| | Sonnet | Opus（予想） |
|---|---|---|
| 自己批判 | 末尾の「自己コメント」として付記。計画の本体には含まない | 計画の最終ステップとして組み込む（今回の指示に自己批判が含まれるため） |

**差が生じる理由**: Opus は「計画の一部として自己評価を行う」ことを自然なステップと捉える。Sonnet は計画の実行可能性を高めることを優先し、自己批判は補足として後置きする傾向がある。

---

### 差 5: git diff の優先度

| | Sonnet | Opus（予想） |
|---|---|---|
| git diff / 直近コミット確認 | リグレッション確定後の **最初のアクション**として明示 | 調査手順のどこかで言及するが、「最初のアクション」として目立たせない可能性 |

**差が生じる理由**: Sonnet は「高命中率・低コストの行動を先頭に置く」スタイル。git diff はほぼゼロコストで高い手がかりを得られるため、Sonnet はこれを最優先に配置する。Opus は体系的な手順を重視するため、git diff がコード読解のフェーズの一部として位置付けられる傾向がある。

---

### 自信度まとめ

| 差異 | 発生の自信度 | 理由 |
|---|---|---|
| 差 1（前置き確認） | 中 | Opus が「情報収集の一環」として含める可能性もある |
| 差 2（仮説の扱い） | **高** | Opus の列挙傾向は一般的に強い |
| 差 3（情報収集→仮説の順序） | **高** | Opus の「まず広く読む」傾向は顕著 |
| 差 4（自己批判の位置） | 中 | 指示文に含まれているので Opus は必ず出す。Sonnet も出すかもしれない |
| 差 5（git diff の優先度） | 中 | Opus がどこで言及するか、明確な傾向は不明 |

## Sonnet 視点での自己コメント

### このプランで意図的に選んだこと

- **「ステップ 0」の前置き確認を計画の冒頭に置いた**: Sonnet は「最初に方向性を絞る」動きを好む傾向があり、確認せずに進むのが非効率と感じる
- **仮説を最大 2 個に絞った**: 全仮説を並列検証するより、最確率の 1 個から順に検証するほうが Sonnet のスタイルに近い
- **ステップ 2a（git diff 先行確認）をリグレッション時の最初の動作に置いた**: 変更差分確認は低コストで高命中率であるため、コードを広く読む前にやりたい
- **「確認できなかったと明示する」を結論ステップに組み込んだ**: 不確実性を曖昧にせず、次のアクションを明示して渡すのが Sonnet のスタイル

### コンテキスト由来で反映されたこと（バイアスの自己認識）

- ログ全文読みを避ける・OSS ソース参照のコスト意識・LSP 優先の方針は、議論文脈から持ち込んでいる。コンテキスト無しの Sonnet がここまで自発的に出すかは未知数。
- Selenium スクリーンショット活用の観点は、議論で artifact.zip の内容を詳しく聞いていたことが影響している可能性がある。

### 自信度が低い部分

- ステップ 2a（git diff 先行）: コンテキスト無しの場合にこれを「最初の動作」として明示するかは不確か
- ステップ 4 のログ絞り込みの具体的手順（±30 秒・grep）: コンテキスト無しだと「ログを確認する」で終わる可能性がある
- 「設定起因を (B) として独立させた 4 類型の分類」: Sonnet が自然にこの粒度で類型化するかは不確か
