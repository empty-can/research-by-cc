## 詳細運用ルールの所在

レビュー実施時の **詳細運用仕様**（セルフレビュー上限・レビューア確認セクション仕様・指摘記載ルール・判断依頼サマリ運用・件数表運用等）は `.claude/rules/cross-review-runtime.md` に集約。レビュー報告書ファイル（`**/レビュー/**/*.md`）またはテンプレ（`.claude/templates/cross-review/*.md`）を Claude が読むときに自動ロードされる（path-scoped rule）。本 README は概観・使い方・基本ルールのみ扱う。

## 使い方

1. レビュー対象のフェーズ配下に `レビュー/` フォルダを作成
2. 上記 3 ファイルを `<観点名>_<日付YYYY-MM-DD>.md` の名前でコピー
   - 例: `クロスレビュー_論理整合性_2026-05-01.md`
3. 各ファイル冒頭の `{{...}}` プレースホルダを埋める
4. Opus / Sonnet レビューは Agent に委任（`.claude/skills/orchestrate/` のパターン A: 並列調査を参照）
5. 作業指示者レビューは作業指示者が直接記入

> レビュー実施前に `.claude/skills/writing-guideline/SKILL.md`（プロジェクトルート相対）も参照すること（判断基準の一貫性確保のため）。

## レビューフロー

| 版 | 担当 | 作業内容 |
|---|---|---|
| 0.8 | レビュアー（Round 1） | レビュー実施・報告書作成 |
| 0.9 | レビューイ（Round 2）→ レビュアー（Round 3） | レビューイ FB 記入 → レビューア確認セクション記入・最終所見決定・修正案反映完了 |
| 0.9.1, 0.9.2, ... | 差戻し時 | Round 3 で「再指摘」判定が出た場合の細分化 |
| 1.0 | 作業指示者 | 態度表明記入・指摘対応確認 → レビュアーが修正案反映完了 |

> **重要**: 0.9 版は「レビューイ FB のみ」ではなく、**レビューア最終所見・修正案反映までを含む**。Round 2 で立ち止まらず、必ず Round 3（レビューア確認）まで実施した上で 0.9 版とする。詳細仕様は path-scoped rule の「レビューア確認セクションの仕様」を参照。

### 未到達版とスキップ版の表記

| 状態 | 定義 | 変更履歴・件数推移表のセル |
|---|---|---|
| 未到達 | 将来到達する可能性があるが、まだ到達していない | 空欄 |
| スキップ | フロー上発生しない（例: 作業指示者レビュー不要の成果物の 1.0 版） | `-` |

「忘れた（記入漏れ）」と「スキップ（構造的に不要）」を区別するため、スキップには必ず `-` を明記する。

## 指摘ラベルの定義

| ラベル | 意味 |
|---|---|
| **CRITICAL** | 修正必須。差し戻し（観点 7「承認の差し戻し条件」）レベルの指摘。解決されないと後続フェーズに着手できないもの。 |
| **IMPORTANT** | 修正推奨。解決せずとも後続フェーズに着手は可能だが、それでも小規模な手戻りの発生や、成果物の品質低下を招くリスクがあり、採用任意のSUGGESTION分類することはできないもの。 |
| **SUGGESTION** | 任意採否の改善提案。 |
| **POSITIVE** | 良い設計判断・維持してほしい点。 |

> ラベル境界の補助基準・指摘記載ルール・観点フィールド付与等の詳細は path-scoped rule を参照。

## 作業指示者の態度区分

| 態度 | 意味 |
|---|---|
| **採用** | 指摘を受け入れ、修正案を適用する |
| **条件付き採用** | 修正案を一部変更・条件を加えて採用する |
| **差戻し** | レビューイに追加情報・再検討を求める（0.9 版フェーズに戻る） |
| **保留** | 現フェーズでは判断しない（後続フェーズで判断） |
| **却下** | 指摘を受け入れない |

「保留」の内訳:

| 分類 | 意味 | 後続対応 |
|---|---|---|
| 情報収集型保留 | 判断材料が不足。後続フェーズで情報収集後に判断する | レビューイ FB フェーズで多くが解消される見込み |
| 意思決定型保留 | 現フェーズでは判断を下さない（後続フェーズの設計判断と組み合わせる等） | 申し送り事項になる可能性あり |

### 保留・却下の運用範囲

- **保留**: 「意思決定型保留」に限定する。「現時点で判断を下すことが本活動に影響がない」または「本活動のスコープ外」のいずれかを判断根拠とする
- **却下**: 作業指示者固有のコンテキスト（プロジェクト制約・スコープ外）により指摘が無効と判明した場合に限定する

## レビュー観点の取捨選択

各レビュアーが担当する観点は、レビュー対象に応じて取捨選択可能:

- 観点をスキップする場合は、観点別指摘件数表の当該観点のステータスを「スコープ外」と記入する
- スコープ外とした理由は、報告書のメタ情報セクションの「スコープ外」欄に記載する

> **注意**: 本ファイル（Level 1）のデフォルト値は、下位の `research-for-xxx/CLAUDE.md`（Level 2）または各サブフォルダ `CLAUDE.md`（Level 3）で上書き可能。`/init` 等で CLAUDE.md を新規作成する際は、上書きが必要なルールがあれば「レビュー実施ルール」節に明記すること。

## 設計方針

- **指摘エントリごとに「作業指示者の態度表明」テーブルを内蔵** — 指摘とその態度を 1 箇所にまとめ、別ファイルやドキュメント末尾を行き来する負担を排除
- **接頭辞で出所を区別** — `C/I/S/P` (論理・実用) / `U-C/U-I/U-S/U-P` (作業指示者)
  - 論理・実用は同一の ID 命名規則（ハイフンなし）を採用。両者は別ファイルで管理されるためファイル内で ID が完結する。クロスファイル参照時は観点名（論理 / 実用）で修飾
  - 作業指示者レビューは `U-` 接頭辞で他の 2 観点と視覚的に区別
- **件数サマリは記入完了後に更新** — 雛型では `<TBD>` プレースホルダ
- **変更履歴セクションを末尾に必ず保持** — 改訂履歴の追跡は各ファイル内で完結させる方針
- **配置順序: 修正案 → レビューイ見解 → レビューア確認 → 作業指示者態度表明** — レビューア・レビューイ・作業指示者の介入順序がそのまま並ぶ構造

## 用語整理（v3.0α 反映）

| 用語 | 意味 |
|---|---|
| **差し戻し** | 承認権限者が承認時に「これでは GO できない」と判断し、レビュー成果物を執筆者に戻すこと（イベント・原因） |
| **手戻り** | 上流工程の不備に起因して、後続工程の作業がやり直しになること（現象・結果） |
| **取り下げ** | レビューア指摘が事実誤認・前提取り違えで覆ること（Round 2/3 のレビューア確認セクションで処理） |

差し戻しは手戻りの代表的な原因の一つ。観点 7 の名称は v3.0α で「承認の押し戻し条件」→「**承認の差し戻し条件**」に変更。既存資産（過去成果物）の「押し戻し」表現は機械的置換せず維持。
