クロスレビュー報告書の雛型。3 種同梱:

| ファイル | 担当レビュアー | 観点（既定） |
|---|---|---|
| `論理整合性_template.md` | Claude Opus（独立第三者） | 論理整合性・カバレッジ十分性・調査目的との整合性・仮説の妥当性 |
| `実用性_template.md` | Claude Sonnet（独立第三者） | 完了条件明瞭性・命名規則遵守・文書構造・検証パターン具体性 |
| `作業指示者レビュー_template.md` | 作業指示者（人間） | 自由記入。観点欄は記入時に補足。 |

## 使い方

1. レビュー対象のフェーズ配下に `レビュー/` フォルダを作成
2. 上記 3 ファイルを `<観点名>_<日付YYYY-MM-DD>.md` の名前でコピー
   - 例: `クロスレビュー_論理整合性_2026-05-01.md`
3. 各ファイル冒頭の `{{...}}` プレースホルダを埋める
4. Opus / Sonnet レビューは Agent に委任（`.claude/skills/orchestrate/` のパターン A: 並列調査を参照）
5. 作業指示者レビューは作業指示者が直接記入

## レビューフロー

| 版 | 担当 | 作業内容 |
|---|---|---|
| 0.8 | レビュアー（Round 1） | レビュー実施・報告書作成 |
| 0.9 | レビューイ（Round 2）→ レビュアー（Round 3） | レビューイ FB を報告書に記入 → レビュアーが各指摘へ確認セクション記入・最終所見決定・修正案反映完了 |
| 0.9.1, 0.9.2, ... | レビューア・レビューイ（差戻し時） | レビューイ差戻しが発生した場合の細分化（Round 3 で「再指摘」判定が出た場合） |
| 1.0 | 作業指示者 | 態度表明記入・指摘対応確認 → レビュアーが修正案反映完了 |

> **重要**: 0.9 版は「レビューイ FB のみ」ではなく、**レビューア最終所見・修正案反映までを含む**。Round 2 で立ち止まらず、必ず Round 3（レビューア確認）まで実施した上で 0.9 版とする。

## 版数管理

### 版番号の定義

| 版 | 意味 |
|---|---|
| 0.8 | 初版（レビュアーによる Round 1 完了） |
| 0.9 | レビューイ FB + レビューア最終所見・修正案反映 完了（Round 2/3 完了の 1 巡目） |
| 0.9.1, 0.9.2, ... | レビューイへの差戻し・再取り込みが発生した場合の細分化 |
| 1.0 | 最終承認者（作業指示者）のレビュー取り込み完了（最終版） |

最終承認者のレビューが完了した版を 1.0 とし、それまでの版番号はレビューステップを逆算して決定する。

### 件数表の運用ルール（v3.0α 反映）

#### 0.8 版作成時点
- 0.9 / 1.0 列は `<TBD>` で良い（記入は各版到達後）

#### 取り下げ件数の表記
- Round 3 で取り下げが発生した場合、件数表は **取り下げ後の現役件数** を記録
- 別途、件数表の下に「取り下げ累計」行を追加して累計取り下げ件数を記録
- 例: 0.8 版で 10 件 → Round 3 で 1 件取り下げ → 0.9 版は「9 件 + 取り下げ累計 1 件」

#### 重要度変更の表記
- Round 3 で重要度変更（例: IMPORTANT → SUGGESTION）が発生した場合、新ラベルで現役件数に計上、旧ラベルから除外
- 「変動なし」と明確に区別するため、変更履歴欄にも変更内容を記録

#### 変動なし時の省略
- 観点別件数表で v0.8 から変動なしの場合は「v0.8 と同一」と省略可
- バージョンごとの値の差分が無い場合、`同左` または `←` と記述（差分が無いことを視覚的に把握しやすくするため）

### 件数表のセクション分け（v3.0α 反映、A8 該当、L3 暫定仕様）

> **L3 暫定仕様**: バージョン単位ではなく **重要度単位** でセクションを分ける。バージョンアップに伴う推移が把握しやすく、CRITICAL や IMPORTANT といった重点的指摘の状況が把握しやすいため。
> 既存資産（02.99 等）は機械的置換せず、新規執筆ドキュメントから本仕様を適用。

#### 暫定構造例

```markdown
##### CRITICAL 件数推移

| 観点 | v0.8 | v0.9 | v1.0 |
|---|---|---|---|
| ... | ... | ... | ... |

##### IMPORTANT 件数推移

| 観点 | v0.8 | v0.9 | v1.0 |
|---|---|---|---|
| ... | ... | ... | ... |
```

### 未到達版とスキップ版の表記

| 状態 | 定義 | 変更履歴の日付・内容欄 | 件数推移表のセル |
|---|---|---|---|
| 未到達 | 将来到達する可能性があるが、まだ到達していない | 空欄 | 空欄 |
| スキップ | フロー上発生しない（例: 作業指示者レビュー不要の成果物の 1.0 版） | `-` | `-` |

「忘れた（記入漏れ）」と「スキップ（構造的に不要）」を区別するために、スキップには必ず `-` を明記する。

## 指摘ラベルの定義

クロスレビューはコードに限定したものではないため、以下の定義を `code-review.md` から独立して管理する。

| ラベル | 意味 | 対応 |
|---|---|---|
| **CRITICAL** | 差し戻し（観点 7「承認の差し戻し条件」）リスクのある本質的問題、または成果物の信頼性を損なう問題。重大な論理的誤り・結論の誤り・調査目的との根本的不整合・活動の継続に支障を与える問題 | 必ず修正 |
| **IMPORTANT** | 本文の理解・運用に支障が出る問題（修正なしでは品質を著しく損なう）。論理性・正確性・品質に関わる問題 | 修正を強く推奨 |
| **SUGGESTION** | 任意採否の改善余地（修正なしでも運用可能）。改善提案・表現・読みやすさ | 任意対応 |
| **POSITIVE** | 適切な判断・良い記述（評価点） | 維持を推奨（必要に応じて強化・横展開を提案） |

### IMPORTANT / SUGGESTION 境界の補助基準（v3.0α 反映、M3 該当）

「品質を著しく損なう」「任意採否」の境界判定で迷う場合の補助基準:

- **本文全体を精読しなければ理解できない問題か**: Yes → IMPORTANT 寄り / No → SUGGESTION 寄り
- **サマリ表など本文を読まずに参照される箇所への影響があるか**: Yes → IMPORTANT 寄り / No → SUGGESTION 寄り

## 指摘記載ルール（v3.0α 反映、F02-009 由来）

### 事実認定型 vs 表現改善型の区分

指摘は以下のいずれかに分類:

- **事実認定型**: 「X は誤っている」「Y は不整合」など、事実認定に依拠する指摘
  - 必須項目: 典拠（参照すべき箇所）・誤りの認定根拠
- **表現改善型**: 「X の表現は曖昧」「Y は冗長」など、表現の改善余地を指摘
  - 必須項目: 改善後の具体例（修正案で明示）

### 根拠記述要件

- すべての指摘に **典拠** または **判断根拠** を記述
- 典拠が無い場合（推測ベース）は、その旨を明示（例: 「推測ですが」）

## セルフレビュー運用ルール（v3.0α 反映、H4 該当）

レビューア・レビューイのセルフレビューは、**前半フェーズ（新規 NG 検出）と後半フェーズ（誤検知チェック）を明確に分離** して実施する。

### レビューアセルフレビュー（フェーズ分離あり）

#### 前半フェーズ（新規 NG 検出）

- **上限**: **5 回**（モデル共通、安全マージン +50% 込み）
- **終了条件**: **直近の試行で新規 NG 検出がゼロだった** こと
- **CRITICAL 候補が含まれている間は上限なし**（CRITICAL の取りこぼしを防ぐため）
- **観点**:
  - 各観点に新規指摘候補があるか
  - 指摘候補の典拠は明確か
  - 重複・冗長指摘がないか

#### 後半フェーズ（誤検知チェック）

- **上限**: **Opus 3 回 / Sonnet 4 回**（暫定。観点規定実装時に再評価し 3 回統一を目指す）
- **終了条件**: **直近の試行で誤検知判定がゼロだった** こと
- **CRITICAL 候補が誤検知判定で全て外れた時点で通常上限に切り戻し**
- **観点**:
  - 出した指摘が事実認定として正しいか
  - ラベル選定が適切か（CRITICAL の過剰計上がないか）
  - レビューイから典拠ベース反論で覆る可能性が高い指摘がないか

### レビューイセルフレビュー（フェーズ分離なし）

- **上限**: **3 巡**（モデル共通）
- **観点**:
  - 立場表明が全件で完了しているか
  - 防衛的記述になっていないか（典拠ベースで反論しているか）
  - 補正情報の十分性が確保されているか
- **目的**: Round 4/5 差戻しリスク回避を優先

### レビューア再対応（Round 3）セルフレビュー

- **上限**: なし（取り込み後文書の整合性確認は収束が確実な作業のため打ち切る理由がない）
- **観点**:
  - 取り込み後の文書整合性が保たれているか
  - 取り下げ・重要度変更の判断根拠が明確か
  - 件数表とレビューア確認セクションが連動しているか

### レビューイ上限見直し時のチェック観点 3 つ

1. Round 4/5 発生頻度の追跡（5 回中 20% 超で見直し）
2. 主目的別カウント（立場判定 / 防衛的記述チェック / 補正情報の十分性確認）
3. 対象成果物の性質（規模・関連資産分散）

## レビューア確認セクションの仕様（v3.0α 反映、B1 該当、L3 暫定仕様）

> **L3 暫定仕様**: §9.3 トライアルで実装した方式に従う。初回運用フィードバックを集約後、v3.1 で正式化。

各指摘エントリ内、レビューイ回答の直後にレビューア確認セクションを追加する。

### 配置位置

- 「レビューイからの回答・見解・補足（問題点）」直下に「レビューア確認: 問題点」
- 「レビューイからの見解・指摘・補足（修正案）」直下に「レビューア確認: 修正案」

### 確認セクションの記入項目

| 項目 | 内容 |
|---|---|
| **レビューア態度** | `受容` / `取り下げ` / `重要度変更` / `再指摘` / `修正採用` のいずれか |
| **理由** | レビューイ回答に対する判断根拠（典拠ベース） |
| **最終結論** | 受容: 元の指摘 + レビューイ修正案を確定 / 取り下げ: 指摘自体を撤回 / 重要度変更: 例 IMPORTANT → SUGGESTION / 再指摘: 0.9.1 を発行 / 修正採用: レビューイ提案の改変版を採用 |
| **収束ステータス** | `達成` / `1ラウンド継続` / `議論継続` |

### 態度区分の定義

- **受容（Accept）**: レビューイの完全同意・部分同意を踏まえ、元の指摘および修正案を確定。最も多いケース
- **取り下げ（Withdraw）**: レビューイの典拠ベース反論で指摘自体が事実誤認・前提取り違えと判明。指摘を撤回（件数表で「取り下げ累計」に計上）
- **重要度変更（Re-label）**: レビューイの提案でラベルを変更（IMPORTANT → SUGGESTION 等）。件数表で重要度別に件数を再計算
- **再指摘（Re-issue）**: レビューイ反論を踏まえてもなお問題が残ると判断。0.9.1 を発行して再ラウンド継続
- **修正採用（Modified Accept）**: レビューイの逆提案・部分反論を取り込んだ改変版を採用。元の指摘と異なる修正案で確定

### 件数表との連動

- 受容・修正採用 → 現役件数に計上
- 取り下げ → 現役件数から除外、別途「取り下げ累計」を記載
- 重要度変更 → 新ラベルで現役件数に計上、旧ラベルから除外
- 再指摘 → 0.9.1 として枝番管理、件数表は枝番別に作成

## 収束ステータスの定義（v3.0α 反映、M2 該当）

レビューア確認セクションの「収束ステータス」項目の判定基準:

| ステータス | 判定基準 |
|---|---|
| **達成** | 最終修正案が双方合意で確定し新規論点なし |
| **1ラウンド継続** | レビューイ追加案の採否判断にレビューア側で再検証が必要 |
| **議論継続** | 認識不一致が残る |

## 作業指示者の態度区分

| 態度 | 意味 |
|---|---|
| **採用** | 指摘を受け入れ、修正案を適用する |
| **条件付き採用** | 修正案を一部変更・条件を加えて採用する |
| **差戻し** | レビューイに追加情報・再検討を求める（0.9 版フェーズに戻る） |
| **保留** | 現フェーズでは判断しない（後続フェーズで判断） |
| **却下** | 指摘を受け入れない |

「保留」の内訳:

| 分類 | 意味 | 後続対応 |
|---|---|---|
| 情報収集型保留 | 判断材料が不足。後続フェーズで情報収集後に判断する | レビューイ FB フェーズ（0.9 版）で多くが解消される見込み |
| 意思決定型保留 | 現フェーズでは判断を下さない（後続フェーズの設計判断と組み合わせる等） | 申し送り事項になる可能性あり |

## 保留・却下の運用範囲

- **保留**: 「意思決定型保留」に限定する。「現時点で判断を下すことが本活動に影響がない」または「本活動のスコープ外」のいずれかを判断根拠とする
- **却下**: 作業指示者固有のコンテキスト（プロジェクト制約・スコープ外）により指摘が無効と判明した場合に限定する

## 判断依頼サマリの運用（v3.0α 反映、A4・A5 該当、L3 暫定仕様）

> **L3 暫定仕様**: 既存資産（02.99 等）は機械的置換せず、新規執筆ドキュメントから本仕様を適用。

### 記載フォーマット（A4 該当）

- **優先度列は廃止し、見出しに移行**
- サマリ表は優先度ごとに作成

#### 暫定構造例

```markdown
##### CRITICAL（{現役件数} 件、判断依頼対象 {サマリ件数} 件）

| ID | 概要 | 差し戻しリスク |
|---|---|---|
| ... | ... | ... |

##### IMPORTANT（{現役件数} 件、判断依頼対象 {サマリ件数} 件）

| ID | 概要 | 差し戻しリスク |
|---|---|---|
| ... | ... | ... |
```

### 表に記載する/しない指摘の基準（A5 該当）

判断依頼サマリ表には、作業指示者が優先して回答すべき指摘のみ記載する:

#### 除外基準（サマリ表に記載しない指摘）

- **除外基準 1**: 優先度が `IMPORTANT` 未満（= `SUGGESTION` 以下）
- **除外基準 2**: 作業指示者の態度表明が以下に該当する内容の追認判断である指摘
  - レビューアからの指摘に対してレビューイが完全同意している
  - かつ、対応案の更なる改善案の提案といったこともなく、レビューアからの対応案をそのまま受け入れている

> 注: 除外された指摘も、本文中の指摘エントリには残る。サマリ表のみから除外する。

#### 判定タイミング・判定者

- **判定タイミング**: Round 3 完了後、判断依頼サマリ表を作成する時点
- **判定者**: レビューア（Round 3 担当者）
- **判定方法**:
  - 除外基準 1（IMPORTANT 未満）: ラベルベースで機械的判定
  - 除外基準 2（追認判断）: レビューア確認セクションの態度（受容のみ・修正採用なし・レビューイ完全同意）を判定

### CRITICAL/IMPORTANT が「該当なし」の処理（M5 該当）

該当ラベルの指摘がない場合は、該当ラベルの **見出しを残し**、表の代わりに「該当なし」という独立行を 1 行記載する:

```markdown
##### CRITICAL（0 件）

該当なし
```

## 観点別サマリ表の振り分けルール（v3.0α 反映、M6 該当）

1 指摘が複数観点にまたがる場合の集計ルール:

- 1 指摘は **主観点に 1 件計上**
- 複数観点にまたがる場合は **影響が大きい観点を主観点とする**
- 副次観点はコメントで注記

## 指摘エントリ自体の観点フィールド（v3.0α 反映、H3 該当）

各指摘の見出し直下に「**観点**: <観点名>」を 1 行追加する:

```markdown
### C1. {{タイトル}}

**観点**: 論理整合性 / カバレッジ十分性 / ...
```

## レビュー観点の取捨選択

各レビュアーが担当する観点は、レビュー対象に応じて取捨選択可能:

- 観点をスキップする場合は、観点別指摘件数表の当該観点のステータスを「スコープ外」と記入する
- スコープ外とした理由は、報告書のメタ情報セクションの「スコープ外」欄に記載する

## 設計方針

- **指摘エントリごとに「作業指示者の態度表明」テーブルを内蔵** — 指摘とその態度を 1 箇所にまとめ、別ファイルやドキュメント末尾を行き来する負担を排除
- **接頭辞で出所を区別** — `C/I/S/P` (論理) / `C-/I-/S-/P-` (実用) / `U-C/U-I/U-S/U-P` (作業指示者)
- **件数サマリは記入完了後に更新** — 雛型では `<TBD>` プレースホルダ
- **変更履歴セクションを末尾に必ず保持** — 改訂履歴の追跡は各ファイル内で完結させる方針
- **配置順序: 修正案 → レビューイ見解 → 作業指示者態度表明** — 作業指示者が最終判断者の立場でレビューイ見解の後に態度を記入できる順序（v3.0α、H2 該当）

## 用語整理（v3.0α 反映）

| 用語 | 意味 |
|---|---|
| **差し戻し** | 承認権限者が承認時に「これでは GO できない」と判断し、レビュー成果物を執筆者に戻すこと（イベント・原因） |
| **手戻り** | 上流工程の不備に起因して、後続工程の作業がやり直し（それまで実施していた作業が無駄）になること（現象・結果） |
| **取り下げ** | レビューア指摘が事実誤認・前提取り違えで覆ること（Round 2/3 のレビューア確認セクションで処理） |

両者の関係: **差し戻しは手戻りの代表的な原因の一つ**。「差し戻し」を未然に防ぐことが「手戻り」の予防に直結する。

> 観点 7 の名称は v3.0α で「承認の押し戻し条件」→「**承認の差し戻し条件**」に変更。既存資産（02.99 等の過去成果物）の「押し戻し」表現は機械的置換せず維持。
