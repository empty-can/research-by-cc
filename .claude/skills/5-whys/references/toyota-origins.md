# 5-Whys: トヨタの起源と原則

トヨタ生産システムにおける 5-Whys の歴史と核心原則。

---

## 歴史的背景

### 起源
5-Whys 手法は**豊田佐吉**（トヨタ工業創業者）によって開発され、後に**大野耐一**が 1950 年代のトヨタ生産システム（TPS）の重要な構成要素として精錬した。

### 大野耐一の有名な例

工場での大野の古典的な例:

```
問題: ロボットが動かなくなった

Why 1: なぜロボットは止まったか？
→ 回路に過負荷がかかり、ヒューズが飛んだ。

Why 2: なぜ回路に過負荷がかかったか？
→ ベアリングの潤滑が不十分で、固着した。

Why 3: なぜ潤滑が不十分だったか？
→ ロボットのオイルポンプが十分な油を循環させていない。

Why 4: なぜポンプは十分な油を循環させないか？
→ ポンプの吸込口が金属くずで詰まっている。

Why 5: なぜ吸込口が金属くずで詰まったか？
→ ポンプにフィルターがない。

根本原因: オイルポンプ吸込口にフィルターがない
対策: オイルポンプにフィルターを取り付ける
```

**重要な洞察:** 5-Whys なしの「対処」はヒューズ交換になり、ロボットはまた故障しただろう。

## トヨタのコア原則

### 原則 1: 現地現物（ゲンチ・ゲンブツ）

**定義:** 実際の場所へ行き、実際の状況を見て、実際の事実を把握する。

**5-Whys への適用:**
- 報告書だけで分析しない
- 各「なぜ」を直接観察で検証する
- 証拠は一次情報であること、伝聞ではないこと

**ソフトウェアへの相当:**
- 実際のログを読む（要約ではなく）
- 実際のコードを確認する（説明だけでなく）
- 問題が起きた実際の環境で検証する

### 原則 2: 人への尊重

**定義:** 問題はプロセスの問題であり、人の問題ではない。

**5-Whys への適用:**
- 「人為ミス」を根本原因として止まらない
- 「なぜプロセスはこのエラーを許したか？」と問う
- エラーを不可能にする、または明白にするシステムを構築する

**トヨタの哲学:**
> 「プロセスを責め、人を責めるな。すべての欠陥は贈り物だ——それは改善できるプロセスの弱点を明らかにする。」

### 原則 3: 継続的改善（改善）

**定義:** 毎日、小さな漸進的な改善を積み重ねる。

**5-Whys への適用:**
- 発見された根本原因は改善の機会
- 学習を将来の参照のために記録する
- 発見事項をチームで共有する

### 原則 4: 品質の内製化（自働化）

**定義:** 問題が発生したら止まって修正する。次の工程に送らない。

**5-Whys への適用:**
- 根本原因に即座に対処する
- 予防 > 検出 > 対応
- 問題を可視化する

## 「5」の意味

### なぜ特定的に 5 段なのか？

**短い答え:** 5 はガイドラインであり、ルールではない。

**大野の観察:**
> 「『なぜ』を 5 回聞くことで、問題の本質とその解決方法が明確になる。」

**現実:**
- 問題によっては 3 段で十分
- 7 段以上必要な場合もある
- 実行可能な根本原因に達したら止める

### 十分に深く掘れたサイン

| サイン | 例 |
|---|---|
| プロセス/ポリシーに到達した | 「コードレビューの要件がない」 |
| 欠落しているコントロールを発見した | 「入力バリデーションがない」 |
| 設計上の決定に行き当たった | 「結果整合性を選択した」 |
| トレードオフを発見した | 「テストより速度を優先した」 |

### さらに深く掘る必要があるサイン

| サイン | 例 |
|---|---|
| 答えがまだ症状レベル | 「サーバーが遅かった」 |
| 答えが責任追及 | 「開発者がミスをした」 |
| 答えが曖昧 | 「何かが間違っていた」 |
| 未変更なら問題が再発する | 「悪いデータが入力された」 |

## トヨタとソフトウェアの比較

### 共通点

| トヨタの工場 | ソフトウェアシステム |
|---|---|
| 組み立てラインの停止 | 本番インシデント |
| 不良部品 | コードのバグ |
| 機械の故障 | サービス障害 |
| 品質検査 | テスト/監視 |
| プロセスのばらつき | 設定ドリフト |

### 主な相違点

| 側面 | トヨタの工場 | ソフトウェア |
|---|---|---|
| **可視性** | 物理的・観察可能 | 抽象的・ログに記録 |
| **再現性** | 高い | 可変（競合状態） |
| **根本原因の場所** | 通常は近傍 | スタックのどこにでも |
| **修正のデプロイ** | 即座 | リリースプロセスが必要 |
| **証拠** | 物理的インスペクション | ログ・メトリクス・トレース |

### ソフトウェアへの適用上の注意

1. **分散システムの複雑さ**
   - 複数のサービスが 1 つの問題に寄与する場合がある
   - サービス境界をまたいでトレースする必要がある
   - イベントのタイミングと順序を考慮する

2. **非決定論性**
   - バグが確実に再現しない場合がある
   - 統計的証拠が必要な場合がある
   - 「なぜ 5% の確率で発生するのか？」

3. **リモートでの証拠収集**
   - 物理的に「現地現物」することはできない
   - オブザーバビリティに依存（ログ・メトリクス・トレース）
   - 適切な計装が必要

## トヨタの 5-Whys ベストプラクティス

### プラクティス 1: 書き留める

トヨタのエンジニアはすべての 5-Whys 分析を文書化する。メリット:
- 明確な思考を強制する
- 将来の問題のためのリファレンスを作る
- インシデントをまたいだパターン認識を可能にする

### プラクティス 2: 一緒に行う

トヨタでは 5-Whys はチームの活動:
- 複数の視点でブラインドスポットを補う
- 問題を共有して理解する
- 解決策のオーナーシップを集合的に持つ

### プラクティス 3: 進む前に検証する

各「なぜ」は進む前に検証しなければならない:
- 「これが真実であることをどうやって知るか？」
- 「何がこれを裏付けるか？」
- 「実際に確認したか？」

### プラクティス 4: プロセスに焦点を当てる

トヨタの根本原因の優先順位:
1. **最良:** プロセス/システムを修正する
2. **良い:** チェック/バリデーションを追加する
3. **許容:** トレーニング/ドキュメントを追加する
4. **避ける:** 人の注意力に頼る

### プラクティス 5: フォローアップする

分析だけで行動しなければ無駄:
- 対策に担当者を割り当てる
- 期限を設ける
- 効果を検証する

## トヨタの警告するよくある間違い

### 間違い 1: 解決策に飛びつく

> 「私たちが認識していない無駄が最も危険な無駄だ。」— 新郷重夫

5-Whys が完了するまで解決策を提案するのを待つ。

### 間違い 2: 症状で止まる

根本原因が「なぜなら」で始められるなら、まだ十分に深く掘れていない。

### 間違い 3: 単一原因思考

現実の問題はしばしば複数の寄与因子を持つ。必要に応じてブランチを使う。

### 間違い 4: 「人為ミス」を受け入れる

> 「すべての人為ミスは変装したプロセスエラーだ。」— トヨタの原則

常に問う: 「なぜプロセスはこのエラーを許したか？」

| 原則 | 5-Whys への適用 |
|---|---|
| **チャレンジ** | すべての仮定を疑う |
| **改善（カイゼン）** | すべての問題は改善の機会 |
| **現地現物** | 意見ではなく事実に基づいて分析する |
| **尊重** | プロセスを修正し、人を責めない |
| **チームワーク** | 一緒に分析し、一緒に責任を持つ |
