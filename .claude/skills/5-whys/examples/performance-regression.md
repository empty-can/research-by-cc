# 例: パフォーマンスリグレッション — API レイテンシ増加

パフォーマンス劣化の根本原因をたどる 5-Whys 分析例。

---

## なぜなぜ分析: 検索 API レイテンシリグレッション

### 問題記述

| 項目 | 詳細 |
|---|---|
| **What（何が）** | 検索 API の p99 レイテンシが 200ms から 800ms に増加 |
| **When（いつ）** | 2024-02-01 v2.3.0 デプロイ後に最初に観測 |
| **Where（どこで）** | search-service、全リージョン |
| **Duration（継続時間）** | 修正デプロイまで継続 |
| **Impact（影響）** | ユーザーからの苦情、検索利用率 15% 低下 |

### 検知タイムライン

```
2月1日 10:00 - v2.3.0 を本番にデプロイ
2月1日 14:00 - レイテンシアラート発火（p99 > 500ms）
2月1日 14:30 - 調査開始
2月2日 09:00 - 根本原因を特定
2月2日 15:00 - 修正デプロイ、レイテンシが正常に戻る
```

---

### Why Chain

| Why | 問い | 答え | 根拠・証拠 |
|---|---|---|---|
| **Why 1** | なぜ検索 API のレイテンシが 4 倍に増加したか？ | DB クエリが遅くなった | クエリタイミングメトリクスで DB 時間が 100ms → 600ms に増加を確認 |
| **Why 2** | なぜ DB クエリが遅くなったか？ | products テーブルのフルテーブルスキャンが発生 | EXPLAIN ANALYZE で Index Scan の代わりに Seq Scan を確認 |
| **Why 3** | なぜフルテーブルスキャンが発生したか？ | クエリの条件が変わり、インデックスが使われなくなった | クエリプランで `category_id` のインデックスが使われていないことを確認 |
| **Why 4** | なぜ新しいクエリがインデックスを使わないのか？ | 新しいフィルターが `category_id` の代わりに `LOWER(category_name)` を使用している | v2.3.0 のコード差分で変更を確認 |
| **Why 5** | なぜインデックスなしでこの変更が加えられたか？ | 開発者が既存のインデックスで対応できると思い込み、クエリレビューをしなかった | PR #1847 にクエリプラン確認の記録がない |

---

### 深掘り調査

**PR #1847 でなぜクエリレビューがなかったか？**

| Why | 問い | 答え |
|---|---|---|
| Why 5a | なぜクエリレビューがなかったか？ | チームにクエリレビューチェックリストがない |
| Why 5b | なぜチェックリストがないか？ | 検索のパフォーマンスがクリティカルとみなされていなかった |
| Why 5c | なぜクリティカルとみなされていなかったか？ | 検索レイテンシの SLO が未定義 |

**第二の根本原因:** パフォーマンス SLO なし → レビュープロセスなし → リグレッションが出荷された

---

### 根本原因

**主要根本原因:**
大文字小文字を区別しない検索のためにクエリを `LOWER(category_name)` を使う形に変更したが、その式に対する関数インデックスが存在しなかった。

**種別:** 設計ギャップ＋プロセスギャップ

**副次根本原因:**
PR レビュープロセスにクエリパフォーマンスレビューがなかった（レイテンシ SLO 未定義が原因）。

**種別:** プロセスギャップ

---

### バリデーション

| テスト | 結果 |
|---|---|
| `LOWER(category_name)` に関数インデックスを追加 | クエリが 80ms に低下 ✓ |
| インデックスありでステージングにデプロイ | p99 が 180ms に戻る ✓ |
| インデックスを削除して `category_id` フィルターに戻す | こちらも修正になる ✓ |

**選択した修正:** 関数インデックスを追加（大文字小文字を区別しない検索機能を維持）

```sql
CREATE INDEX idx_products_category_name_lower
ON products (LOWER(category_name));
```

### クエリレビューチェックリスト（新規作成）

DB クエリを変更する PR には以下を必須化:

- [ ] 新規・変更クエリに対して `EXPLAIN ANALYZE` を実行
- [ ] インデックス使用を確認（大規模テーブルで Seq Scan がないこと）
- [ ] 推定行数と実際の行数を確認
- [ ] 本番同等のデータ量でテスト
- [ ] 想定クエリパフォーマンスを記録

---

### 教訓

1. **大文字小文字を区別しない検索には関数インデックスが必要**
   - `WHERE LOWER(col) = 'value'` は `col` のインデックスを使わない
   - `LOWER(col)` にインデックスを作成しなければならない

2. **テストデータの量が重要**
   - 100行: どのクエリも速い
   - 1000万行: インデックス欠落は致命的

3. **カナリアデプロイは不可欠**
   - 1% のトラフィックで 4倍のレイテンシ増加を検知できた

4. **SLO がプロセスを駆動する**
   - レイテンシ SLO がなければ、誰もパフォーマンスレビューを優先しない
