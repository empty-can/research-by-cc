# 例: 本番インシデント — 支払いサービス障害

本番の支払いサービス障害に対する完全な 5-Whys 分析例。

---

## なぜなぜ分析: 支払いサービス障害（2024-01-15）

### 問題記述

| 項目 | 詳細 |
|---|---|
| **What（何が）** | 支払い API が 503 エラーを返し、全トランザクションが失敗 |
| **When（いつ）** | 2024-01-15 14:23 UTC、ピークトラフィック中 |
| **Where（どこで）** | 本番環境の payment-service (us-east-1) |
| **Duration（継続時間）** | 47 分 |
| **Impact（影響）** | 失敗トランザクション約 $150,000、影響ユーザー 12,000 人 |

### タイムライン

```
14:23 - 監視に最初の 503 エラーが出現
14:25 - アラート発火: payment-service エラーレート > 5%
14:28 - オンコールエンジニアが調査開始
14:35 - 特定: DB コネクションがすべて使用中
14:42 - 再起動を試みるも問題継続
14:55 - 根本原因を特定: コネクションリーク
15:02 - ホットフィックスをデプロイ
15:10 - サービス完全復旧
```

---

### Why Chain

| Why | 問い | 答え | 根拠・証拠 |
|---|---|---|---|
| **Why 1** | なぜ支払い API が 503 エラーを返したか？ | DB コネクションプールが枯渇した（使用可能 0/100） | コネクションプールメトリクスで 100/100 使用中を確認 |
| **Why 2** | なぜコネクションプールが枯渇したか？ | コネクションが確保されるが解放されていなかった | コネクション保持時間ヒストグラムで数時間保持されているコネクションを確認 |
| **Why 3** | なぜコネクションが解放されなかったか？ | 払い戻しハンドラーで connection.close() の前に例外が発生した | ログのスタックトレースで 142 行目の例外を確認 |
| **Why 4** | なぜ例外がコネクションのクローズを妨げたか？ | try-finally ブロックがなく、close() がハッピーパスにしか存在しない | RefundHandler.java のコードインスペクション |
| **Why 5** | なぜ try-finally ブロックがなかったか？ | オートコミット（明示的クローズ不要）を使う旧サービスからコードをコピーした | git blame で旧サービスからのコピーペーストを確認 |

---

### 根本原因

**特定した原因:** コネクション処理コードが、オートコミットモード（コネクションが自動クローズ）の旧サービスからコピーされた。新サービスは手動トランザクションを使用しており明示的な close() が必要だったが、コードパターンが更新されなかった。

**種別:** 設計ギャップ（誤ったパターンの適用）

**確信度:** 高（ステージング環境で再現確認済み）

---

### マルチブランチ分析

障害を悪化させた寄与因子:

```
主要ブランチ（根本原因）:
払い戻しハンドラーのコネクションリーク
    ↓
プール枯渇

寄与ブランチ（悪化要因）:
なぜもっと早く検知できなかったか？
    ↓
Why 1: コネクションプールの監視アラートがない
    ↓
Why 2: 監視ダッシュボードはあるがアラート閾値がない
    ↓
Why 3: アラートがバックログに積まれて優先化されなかった
    ↓
Why 4: コネクションプール使用率の SLO が未定義
```

### バリデーション（逆方向確認）

| 確認内容 | 結果 | 検証方法 |
|---|---|---|
| RefundHandler に try-finally を追加 | コネクションが常に解放される | ステージングでテスト済み ✓ |
| コネクションが常に解放される | プールが枯渇しない | 負荷テストで確認 ✓ |
| プールが枯渇しない | DB からの 503 エラーなし | 確認済み ✓ |
| 503 エラーなし | 支払いサービスが健全なまま | ✓ |

### 教訓

1. **コードのコピーはリスクがある** — あるコンテキストのパターンが別のコンテキストに適用できるとは限らない
2. **リソースクリーンアップには多層防御が必要** — リンティング＋レビュー＋監視
3. **アラートのない監視は不完全** — ダッシュボードはオンコールに通知しない
4. **コネクションプールはファーストクラスのメトリクス** — 可視化が不可欠
