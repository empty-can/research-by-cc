### 分類定義の運用ブレ（横断所見）

最も本質的な問題は **個別候補の誤分類ではなく、「A」ラベルの内部分散**である。現状の「A」には次の 3 つが同居している:

1. **薄い汎用ブリッジ**（jonrad / isaacphi / Tritlo / bug-ops / nzrsky / t3ta 等）— LSP を素直に MCP 公開
2. **フレームワーク型**（serena）— LSP の上にセマンティックツール層・メモリ・リファクタを載せた高次製品
3. **機能特化ブリッジ**（sminnee=リファクタのみ）— A の構造だが機能網羅性が低い

この分散自体は誤りではないが、Phase 2 のスコアリングで「A だから同等」と扱うと **serena（フレームワーク）と薄いブリッジを同じ物差しで比較**してしまう。マージ表に「A のサブタイプ注記列」を足すか、評価マトリクスで A を 2〜3 層に割ることを推奨。

## 結論の根拠妥当性

| # | 結論 | 根拠の強さ | 要再確認点 |
|---|---|---|---|
| (a) | 「Spring Boot/Gradle 専用 LSP MCP は存在しない」 | **中〜強**。Agent C が 9 クエリ（GitHub search + WebSearch）で網羅し、近縁（Spring AI demo / gradle-mcp 等）を明示的に除外している点は良い。ただし「存在しない」は**全数調査では証明不可能な否定命題**で、各クエリはページ1（25件）止まり。 | **要再確認（軽）**: 「確認範囲で発見できず」への表現緩和を推奨。特に **sts5-headless（疑義#3）は『Spring 意味論を MCP 公開する LSP 連携実装』として実在**し、「Spring Boot 専用 LSP MCP は存在しない」と一見矛盾する。「汎用的な Spring Boot LSP 補完を MCP 化した専用サーバは無いが、Spring 意味論特化の派生実装(sts5)は存在する」と精緻化すべき |
| (b) | 「Java(jdt.ls) ≫ Spring Boot ≫ Gradle の対応温度差」 | **中**。方向性（Java が最も対応厚く Gradle が最も薄い）は全 Agent の所見と整合し妥当。だが **"jdt.ls" と名指しした温度差の根拠が弱い**: A 群で「Java=jdtls」を README 明示するのは agent-lsp / mcpls / nzrsky / serena(要確認) のみで、ProfessioneIT は **jls（≠jdt.ls）**、isaacphi/axivo 等は「設定次第（未実証）」。"jdt.ls 対応" の母数は思ったより薄い。 | **要再確認**: 「Java 対応」と「jdt.ls 対応（実証済み）」を区別すべき。現状の温度差表現は前者を後者に読み替えるリスクがある。実際に jdt.ls 接続を実機検証した候補は **0 件**（全て README ベース）であることを明記すると誠実 |
| (c) | 「Spring=汎用ブリッジで条件付き可 / Gradle=named pipes で不可」 | **中〜強**。Spring の「.vsix → JAR 抽出 + jdt.ls 2層 + stdio 起動が未文書化」という条件積み上げは具体的で説得力あり。Gradle の named pipes 制約も ARCHITECTURE.md/DeepWiki 出典付き。 | **要再確認（軽）**: ①Spring 側「条件付き可」は **未実証（Wiki に tbd 多数）**であり、"可" のニュアンスが楽観的に伝わるリスク。"理論上は経路があるが未実証・難度高" を維持すべき。②Gradle「不可」は **gradle-language-server(named pipes) 限定の話**で、`gradle/declarative-lsp`(JAR 単独起動・stdio 可能性) は「未確認」止まり。"Gradle 全般が不可" ではなく "汎用的 Gradle LSP 補完は現状の stdio ブリッジでは不可" と限定すべき。BSP 経路の不在確認も「検索で出ず」止まりで否定の強度は弱い |

### 結論部の総合評価

3 結論とも **方向性は根拠に支えられており妥当**。問題は強度の表現で、いずれも「否定命題の断定」と「未実証経路の "可"」という 2 方向の過信リスクを抱える。マージ統合者（メイン Opus）が候補一覧で既に「未実証」「条件付き」「⚠️」を多用しており、**断定の暴走は概ね抑制されている**。ただし上表の精緻化を入れると、Phase 2 以降の誤誘導をさらに減らせる。

## カバレッジの穴

目的（Java > Spring > Gradle の LSP 連携 MCP 選定）に対し、5 Agent が手薄だった候補空間・角度:

1. **依存先 LSP 本体の素性調査が未着手**（最大の穴）。A 群は「ブリッジ + LSP 本体」の組であり、リスクは **ブリッジ側だけでなく LSP 本体側にも宿る**。特に ProfessioneIT が採用する **jls(idelice/jls) は 2025-12 作成の新興 Java LSP**（jdt.ls 代替）で、これ自体の成熟度・脆弱性は誰も見ていない。Phase 2 の依存スキャンは「ブリッジの package.json」だけでなく「実際に起動する LSP 本体（jdt.ls / jls / spring-boot-LS）」も対象にすべき。

2. **`go-jls`(kamichidu/go-jls) の取りこぼし可能性**。本レビュー中の検索で、Go 製・低レイテンシの Java LSP `go-jls`(★3, 2026-06 push) を確認した。これは MCP ではなく LSP 本体だが、「軽量 Java LSP を汎用ブリッジに繋ぐ」経路の選択肢として、Java LSP 本体のランドスケープ（jdt.ls / jls / go-jls）を 1 枚に整理する角度が欠けている。

3. **multilspy/solidlsp エコシステムの横展開が浅い**。serena・asimihsan/mcp-multilspy・t3ta はいずれも multilspy 系を基盤にする。multilspy(microsoft) は jdt.ls 対応が既知で、**「multilspy ベースの MCP 群」をまとめて Java 対応度で比較する角度**があれば、serena の Java LSP 実体（jdt.ls か）の確認も一括で進む。asimihsan の URL 404 もこの軸で追跡可能。

4. **実機検証の不在**（Phase 設計上の既知の穴）。全候補の Java/jdt.ls 対応が README ベースで、実際に jdt.ls を接続して動いた候補は 0。これは Phase 1 のスコープ外で妥当だが、評価マトリクス（02）で「実証済み/README のみ」を 1 軸に立てないと、Tier 1 の "Java 対応" が全て同じ確度に見えてしまう。

5. **Spring Boot の "別経路" の探索が片面的**。Agent C は「spring-boot-language-server を汎用ブリッジに繋ぐ」経路に集中したが、sts5-headless が示す「**Spring 意味論を直接 MCP 化する**」経路（LSP 補完ではなく Bean/RequestMapping 等の意味論提供）が比較軸として整理されていない。「Spring 開発支援」の目的次第ではこちらが実用的な可能性があり、目的の再確認が要る。

## 総評（マージの信頼度・修正すべき点の優先度）

**マージ全体の信頼度: 高（中の上）。** 5 Agent の分類は骨格が一貫しており、**Tier を誤って動かすレベルの誤分類は検出されなかった**。統合者が「未実証」「条件付き」「⚠️」「要確認」を随所に残しており、根拠を超えた断定はおおむね抑制されている。Phase 2 にこのまま進めても致命的な対象選定ミスは起きにくい。

**修正すべき点の優先度:**

- **[高] 「A」サブタイプの明示**（疑義#1/#6 + 横断所見）。serena（フレームワーク型）と薄いブリッジ、機能特化（sminnee）を同一物差しで比較しないよう、評価マトリクスで A を 2〜3 層に割る。
- **[高] 「Java 対応」と「jdt.ls 実証対応」の分離**（結論(b) + カバレッジ穴#1/#4）。jdt.ls 実機検証は 0 件であり、ProfessioneIT は jls(≠jdt.ls)。必達軸「Java=jdt.ls 成熟度」と候補実態のズレを評価マトリクスに反映する。
- **[中] 依存先 LSP 本体の素性を Phase 2 スコープに追加**（カバレッジ穴#1）。特に jls の成熟度・脆弱性。
- **[中] sts5-headless と結論(a) の整合**（疑義#3 + 結論(a)）。「Spring 専用 LSP MCP は存在しない」を「汎用 Spring Boot LSP 補完の専用 MCP は無いが、Spring 意味論特化派生(sts5)は存在」へ精緻化。
- **[低] 否定命題・未実証経路の表現緩和**（結論(a)(c)）。「存在しない」→「確認範囲で発見できず」、Spring「条件付き可」→「未実証・難度高」、Gradle「不可」→「汎用 Gradle LSP 補完は stdio ブリッジでは不可（declarative-lsp は未確認）」。

いずれも **個別候補の分類ラベルを書き換える必要はなく、注記の追加と評価軸の精緻化で対応可能**。マージ成果物自体は再利用に耐える品質。
