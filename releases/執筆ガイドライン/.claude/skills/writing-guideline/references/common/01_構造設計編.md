# 構造設計編（書く前に決めること）

ドキュメントの章立てを決める前・章を書き始める前に適用する観点。全ドキュメント種別共通。種別固有の追加観点は対応する種別ファイル（`計画書.md` / `調査報告書.md` / `レビュー報告書.md` / `改訂提案.md`）を併読する。

## G1-1. 想定読者像の事前宣言 `[doc-coauthoring]` `[internal-comms]`

ドキュメント冒頭またはメタ情報に、想定読者像を 1〜2 文で明示する。

| 項目 | 例 |
|---|---|
| 想定読者の役割 | 「最終承認権限を持つ人間レビューア」「03 設計フェーズ担当 Claude Agent」 |
| 想定読者の前提知識レベル | 「本プロジェクト全体の文脈を持つ前提」「事前文脈なし、本ファイルのみ参照」 |
| 想定読了時間 | 「10〜20 分」「5 分以内」 |

> **理由**: 想定読者の前提知識レベルが明示されていれば、執筆段階で「どこまで前提を書くべきか」「どこから本題に入れるか」の判断基準が明確になる。レビュー段階での「前提知識の明示不足」指摘も予防できる。

## G1-2. ドキュメント全体構成の可視化（目次・冒頭サマリ・読み方ガイド） `[作業指示者]` `[Microsoft]` `[Minto]`

以下の 4 点を必ず満たす:

1. **目次（TOC）の整備** — 章数が 5 を超える、または行数が 100 を超えるドキュメントは目次を必ず置く。各セクション名は **対応するセクションへのリンク** とする
2. **各章の 1 行説明併記** — 目次の各章名の右側に、その章の内容を 1 行で説明する
3. **冒頭サマリ構成** — 報告書系（調査報告書・最終報告書・取りまとめ）は冒頭で「**調査内容 / 調査結果 / 結論・示唆**」のサマリを提示し、その後に各詳細へ繋げる
4. **読者別読み方ガイドの提供（複数読者向けドキュメントのみ）** — 想定読者が複数（例: 承認権限者 / 後続フェーズ Agent / 設計担当者）の場合、各読者がどの章を優先的に読むべきかの動線を **表形式で提示** する

```markdown
良い例（読者別動線表）:
| 想定読者 | 優先読了章 | 読了目安 |
|---|---|---|
| 承認権限者 | §0 冒頭サマリ → §9 GO/NO-GO 整理 | 5〜10 分 |
| 03 設計担当 Agent | §3 採用候補 → §6 命名規則 → §7 引き渡し | 20〜30 分 |
| レビューア | 全章 | 25〜35 分 |
```

> **理由**: ボリュームが大きいドキュメントほど構成把握コストが急増する。冒頭で全体像を把握でき、読者別動線が示されていれば、読者は自分に必要な章だけ読めば判断ができる。認知負荷が大幅に下がる。

## G1-3. 文書モードの自意識（Diátaxis） `[Diátaxis]`

各章を執筆する前に、その章が以下のどのモードかを意識する:

| モード | 性質 | 章末スタンス |
|---|---|---|
| **Tutorial** | 段階的に手を動かして学ぶ | 学習成果としての到達点を明示 |
| **How-to** | 特定の目的を達成する手順 | 完了条件を明示 |
| **Reference** | 仕様・カタログ・参照表 | 網羅性と検索性を優先 |
| **Explanation** | 設計意図・背景・理由づけ | 理解促進を優先 |

> **理由**: 「読者が何を求めて読むか」を一意化することで、不要な脱線・冗長を回避できる。

### G1-3.1. 複数モード混在ドキュメントの扱い方

計画書・統合報告書のような **本質的に複数モードが混在するドキュメント** では、純粋なモード単一化は不可能。以下の戦略で扱う:

1. **章単位でモードを切り替える** — 1 つの章 = 1 つのモードを基本とし、章レベルではモード混在を避ける
2. **モード切り替え点の明示** — 「ここから設計意図の説明に入る」など、モード切り替えを明示する見出しまたは導入文を置く
3. **読み方ガイド（G1-2 #4）でモード別動線を補完** — 例: 「Reference 章だけ読みたい場合は §3 / §6 へ」など

```markdown
典型的な混在パターン:
- 計画書: §0〜§1（Explanation）→ §2〜§5（How-to + Reference）→ §9（Explanation）
- 統合報告書: §0（Explanation）→ §3〜§7（Reference + Explanation）→ §9（Explanation: GO/NO-GO 判断）
```

> **理由**: 複数モードを章レベルで切り分けると、読者は各章の読み方を即座に判断できる。モード切り替え点が不明だと、Reference を読むつもりで Explanation に巻き込まれる等の認知負荷が発生する。

## G1-4. 内外参照の相互リンク化 `[作業指示者]`

ドキュメント内外の参照は **必ず Markdown リンクとして記載** する:

```markdown
良い例:
- 詳細は [§3.2 採用候補](#32-採用候補) を参照
- 関連: [改善点ドキュメント](improvements/改善点名.md)

悪い例:
- 詳細は §3.2 を参照（リンクなし）
- 関連: 改善点-009（リンクなし）
```

> **理由**: リンクをクリックするだけで参照先へ飛べるため、レビューア・読者の作業コストがほぼゼロになる。手動辿り作業はレビュー効率を著しく圧迫する。
