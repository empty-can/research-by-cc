# 調査報告書 固有観点

フェーズ報告書・統合報告書執筆時に共通観点（`common/01〜03`）に加えて適用する追加観点。フェーズ別に整理。統合報告書（複数サブタスクの統合）には専用観点も含む。

## 1. 構造設計フェーズの追加観点

### 1.1 冒頭サマリは 3 部構成 `[作業指示者]`

G1-2 冒頭サマリは「**調査内容 / 調査結果 / 結論・示唆**」の 3 部構成。

### 1.2 統合報告書: 用語統一の事前合意

サブタスク間で揺れる用語（例: 「ハイブリッド検索」/「ハイブリッド RAG」、チャンクサイズ単位の「文字数」/「トークン数」/「非空白文字」）を、執筆開始前に統一定義する。

> **理由**: 用語揺れは執筆後の整合性確認時に発覚し、章全体の書き直しが必要になる。事前統一によって手戻りを予防する。

### 1.3 統合報告書: サブタスク報告書への参照容易性の準備

各採用候補・主要結論ごとに、典拠となるサブタスク報告書の該当節へのリンクを付ける構造を事前に設計する。後続フェーズの参照負荷を低減する。

## 2. 執筆中フェーズの追加観点

### 2.1 統合報告書: GO/NO-GO 判断の明示

フェーズ承認に関わる統合報告書では、§9 等に「**GO を支持する事実 / NO-GO リスク / 次フェーズ方針**」の 3 段構造で判断材料を整理する。

```markdown
構造例（§9 GO/NO-GO 整理）:
### 9.1 GO を支持する事実
- 採用候補が技術的に成立することを確認（§3.1〜§3.3）
- 想定スケールでの性能要件を満たす実測値あり（§5.4.3）

### 9.2 NO-GO リスク
- ライセンス未確定の候補 X が含まれる
- ストレージ要件が想定の 1.5 倍

### 9.3 次フェーズ方針
- §9.1 を踏まえ、フィジビリティ検証段階へ進める
- §9.2 のリスクは初動 1 週で確認
```

## 3. 完成前セルフチェックフェーズの追加観点

### 3.1 Specificity 三点セットを各エントリに必須適用

G3-5 Specificity 三点セット（what / where / evidence）を **採用候補・除外候補の各エントリに必ず適用** する。3 点が揃わないエントリは根拠補強または削除を検討。

### 3.2 iteration 収束時の切り出し検討

G3-9 iteration 収束基準で「報告書のサイズが膨張気味」と判定したら、章末の LEARNING / FOLLOW-UP セクションへの切り出しを検討する。

### 3.3 統合報告書: 章間整合性の確認

同じ仮説・採用候補・除外候補について複数章で言及する場合、表現を統一する。執筆段階で揺れが発生していないか最終チェック。

### 3.4 統合報告書: レイヤー間整合の確認

採用候補（§3.1 等）と検索アルゴリズム表（§3.4 等）が同じ候補を扱っているか、レイヤーをまたいで整合しているかを確認する。

### 3.5 統合報告書: ハマりどころ.md 等の状態同期

報告書内の「未追記」「未対応」のような **状態言及** が、参照先（ハマりどころ.md 等）の現状と一致しているかを最終チェックで確認。状態が動的に変動する場合は本文側で状態を断定せず、「最新状態は §X 参照」と明記する。

> **理由**: 状態を本文で断定すると、参照先が更新されたときに本文側が古い情報を保持してしまう。状態言及は単一ソース（参照先）に集約することで、二重管理を予防する。
